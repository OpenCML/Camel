Derive an operator's effect from its access list and its fault table

An operator's effect used to be stated beside its behaviour -- a purity flag on its
traits, a prefix rule in the built-in registration, a never-fault set next to it,
a state-only word for the ones that only touched a variable -- so the table held
several answers to one question and nothing made them agree. The record is now the
one answer: OperatorSemantics carries the access list (one item per resource, with
the mode it is used in) and the fault table (which fault, under what condition;
absent means it may fault), and pure, external and may-fault are three readings of
those two.

OperatorTraits stays as the shorthand a module writes with. OperatorTable::set
turns the word into the record -- `pure` becomes the empty access list, `state
only` and `effectful` a word about accesses that are not itemized yet, `may fault:
false` the empty fault table -- so the module call sites did not move and the
record is still the single source for everything that reads it. An operator that
itemizes no access list is read as writing the global resource, which is the
reading an undeclared operator always had.

The built-in registration stops guessing from names: the `op/`, `coll/` and `enum/`
prefix rule is gone (it cannot say that `op/set_index` returns a new array and
`op/set_index_in_place` writes one), the 168 access-free operators and the 59
conversions declare it themselves, and the 86 never-fault operators moved out of
kNeverFaults into the fault table in builtin_semantics.cpp. The verdicts are the
ones the old rules gave -- `camel inspect --ops` reports the same purity and the
same may-fault for every one of the 795 overloads -- which is why no compile result
and no run output changes.

`camel inspect --ops` prints the list item by item with each access's mode, whether
the list was declared, and the external and may-fault readings; and
`scripts/stdlib-reference.mjs --verify-ops` compares that list against the `uses`
clause of a declaration item by item in both directions: a `uses var x` item must
be a write, and a resource the operator touches must be named. A declaration that
only allocates keeps an empty list and stays state, not pure.
