# 第 7 步方案：值的多种写法（图内 e-graph）

基于 fsh-dev 681ac65a。只做设计，不含代码。依据：图存储第二版 §3.1、§3.4–3.7、§4.1、§4.3、§4.6、决定 2、4；`docs/design/rewrite/README.cn.md`（规则、策略、分析已定稿）。

## 0. 结论先行

1. **不新增节点种类，也不改节点记录。** 今天"节点 = 值"，输入指向节点。多种写法 = 若干节点被声明为同一个值（等价类）。节点记录、输入表、分块、`gc_node_ref_t`（已是 32 位）全部不变。新增的只有一张**可选的等价表**。
2. **等价表只记"哪些节点被断言等价"**（并集日志，每条带许可掩码），不记并查集本身。并查集、同余索引、按头符号的索引都是**事务内的派生状态**，解码时由日志线性重建。
3. **节点级永远是 DAG，类级可以有环。** 规则只加新节点、不改旧节点的输入，所以新节点的输入都是已存在的节点。`x = x*1` 这样的"自环"只出现在类级，提取时排除。校验器因此仍可检查节点级无环，不需要新的环检测。
4. **没有等价表的图零成本**：图头多一个标志位（`kGraphFlagHasWritings`）与一个空指针；`decode`、`commit`、`ExecPlan` 对这类图的路径不变。
5. **可执行状态 = 没有等价表。** 提取之后表被丢弃，图回到今天的样子。`ExecPlan` 只为可执行状态的图版本构建；后端、导出、`std::fvm` 入口检查。

## 2. 数据结构

### 2.1 冻结图上的等价表（`GCWritings`，可选）

```
struct GCWritingTable {            // 图版本拥有的一块独立内存，不分块
    uint32_t unionCount;
    uint32_t layerMasks;           // 出现过的许可掩码的位集（见 2.3），最多 4 个不同掩码
    struct Union { gc_node_ref_t a, b; uint8_t perms; uint8_t flags; uint16_t rule; } unions[];
};
```

- `perms`：这条等价成立所需的许可（逐位相等的规则为 0）。`rule`：产生它的规则编号（调试与 `inspect`；0 = 同余推出）。`flags`：bit0 = 同余闭包推出（可重算，持久化只为省一次重建）。
- 图头：`GCGraph::writings()` 返回指针，空 = 可执行状态；`kGraphFlagHasWritings` 复制自空否，热路径只测标志。
- 表的大小与合并次数成正比，每次提交整块复制（饱和后一次性提交一次，不是热路径）；**不分块**，也不参与 `GCNodeChunk` 共享。
- 随图版本由图空间 GC 释放（与 `bindOwn` 的图一样，释放图时释放表）。

### 2.2 事务内的 `WritingStore`（`GraphDraft` 持有 `unique_ptr`，空 = 单写法）

- **并查集**：`parent[node]`，**根取编号最小的节点**（确定性，不依赖合并顺序）；路径压缩。
- **成员表**：每个根一条节点链（按编号升序），供 e-matching 遍历"这个类的所有写法"。
- **同余索引（hashcons）**：键 = （节点种类、算子或常量载荷的字节、类型编号、**规范化后的** norm/with 输入类的根），值 = 节点。常量载荷按位比较（`0.0` 与 `-0.0` 不同，规则稿 2.2）。有控制输入或有副作用的节点**不进同余索引**，永远是单元素类（与规则稿 2.4 一致：规则不会悄悄丢掉顺序约束）。
- **头符号索引**：`HeadKey → 节点升序表`，供模式按根头符号快速找候选，`rebuild` 后更新。
- **待修复队列**（egg 的 `rebuild`）：合并后，把被合并类的使用者重新规范化，键相同的合并，直到不动点。顺序按节点编号，不按哈希表遍历顺序。
- **用到的哈希表只做查找，从不遍历**，这是确定性的硬条件（规则稿 §3"结果确定"）。

### 2.3 许可（3.4）：分层并查集

- 一条并集带掩码 `P`，只在上下文许可 ⊇ P 时可用。上下文许可 = 被匹配节点的 `nodePermissions`（区域标签授予的许可在编码时已落到节点列）。
- 实现：并集日志是唯一真相；每个**出现过的上下文掩码 S**有一层并查集 `U_S`，含日志里所有 `P ⊆ S` 的并集。加一条带 `P` 的并集时，对所有 `S ⊇ P` 的已存在层执行；新层由日志重放建立。同余闭包按层各做一遍。
- 层数 = 范围内节点上不同许可掩码的个数，实际是 1–2（默认 + 某个 `#reassociate` 块）。**上限 4 层**，超过就报错（见问题 2）。
- `#strict`（许可为空）的节点只落在 `S=0` 层，只看到逐位相等的并集。
- 提取（§4）对每个类用**该类代表节点所在上下文的层**，所以结果自然在许可之内（3.4 末条），不需要事后检查。
- 单层（所有节点同一掩码）时开销与没有分层相同：`U_S` 只有一个。

### 2.4 规则的本地表示（第 7 步交付，第 8 步编译到它）

```
struct Rule { name; requires /*perm mask*/; lhs, rhs /* 小图，形参 = Port 节点 */; bool bidir;
              std::function<bool(const Match&)> when; uint16_t id; };
```

- 与规则稿 2.2 一致：左边是一张小图，形参是模式变量；同一变量出现多次要求同一个类；`const` 形参只匹配常量类（类里任一写法是常量即可）。
- 第 8 步的 `rule` 声明只是把 Camel 语法编译成这个结构；第 7 步用 C++ 直接构造（测试用）。

## 3. 饱和（3.5）

事务内，对一张图（见问题 3 的范围）：

```
saturate(draft, rules, Budget{rounds, newWritings, unions, [timeMs]}):
  rebuild()                         // 先建索引
  repeat rounds 次:
     matches = []                   // 先收集，再应用（egg 的两阶段，避免边匹配边改）
     for rule in rules (列表顺序): for node in headIndex[rule.lhs.head] (编号升序):
         for each 绑定 b in ematch(rule.lhs, class(node)): if 许可满足 && when(b): matches.push(rule, node, b)
     apply: 对每个 match 按收集顺序：rhs 逐节点 lookupOrAdd，根与 class(node) 合并（perms=rule.requires，rule 编号）
     rebuild()
     if 本轮没有新写法也没有新并集: break
     if 超出预算: break（不报错，返回已达到的状态；参数可改为报错）
```

- **e-matching**：自顶向下回溯。模式节点与候选节点比较（种类、算子 URI/常量载荷、类型、输入个数）；子模式是变量则绑定到输入的类根（已绑定则要求同一个类），否则对输入类的每个成员递归。`when` 在匹配后、应用前执行。
- **新节点继承标签**：rhs 新建节点复制被匹配根的 `nodeAttrs`、`permissions`、区域、来源，再加"由哪条规则产生"的来源标签（规则稿 2.3）；合并不了就不生效。
- **常量折叠**：rhs 中只含常量与 `const` 变量的子表达式在应用时按规范算法求值，直接建常量节点（规则稿 2.3）。
- **预算**：默认轮数 8、新写法数 = max(4×原节点数, 1000) 且不超过 1,000,000、并集数同量级；**默认只用计数预算，保证结果可复现**。时间预算可选，用了它就不保证结果相同，返回值里标记（问题 7）。
- **确定性**：匹配按（规则列表顺序、节点编号）；应用按收集顺序；并集取小编号为根；平局按编号。同输入、同规则、同预算 → 同结果。
- 爆炸防护：交换律与结合律在预算内会产生大量写法；预算耗尽时返回当前状态，是设计内行为。不做 egg 的 BackOff 调度器（第 8 步的策略层再说）。

## 4. 提取（3.6）

```
interface CostModel { double node(const Draft&, node, std::span<const double> inputCosts); }  // 必须 > 0
extract(draft, CostModel, roots) -> 每个可达类选一个成员
```

- **贪心（树代价）**：每个类的最优代价初始 ∞；反复扫描所有类（编号升序），某写法的输入类代价都有限时算 `node(...)`，更小则更新（平局取编号小的写法）；直到不再变化。因为代价必须为正且要求输入类代价有限，被选中的写法集合**天然无环**；自环写法（`x*1` 的输入含自己所在类）永远不会先得到有限代价，被排除。
- 树代价会把共享子项重复计算；这是 egg 的标准做法。DAG 感知的整数规划提取放第 9 点（标准库，有时间上限，另一个库，不在本步）。
- **物化**：从根（出口值、所有有副作用/有控制依赖的节点、端口）沿选中写法走一遍；对选中节点把输入改为各输入类的选中成员（`setNormInputs`/`setWithInputs`/`setCtrlInputs`）；没被选中且不可达的写法节点 `eraseNode`（打墓碑）；丢弃等价表，清标志。这是一次普通的事务改写，提交走现有增量路径。
- **区域**：写法节点与被匹配根同区域（§2.4、问题 4），所以选中成员对使用者的区域可见性与原节点相同；仍由提交时的校验器检查（红线不变）。
- 代价函数可替换：内建"节点数""算子权重表"；Tiles 通过**命名注册**接入（`registerCostModel("tiles.gpu", fn)`），第 7 步只提供注册表与接口，不含 Tiles 的代价。

## 5. 可执行状态与各系统怎样看一张多写法的图

| 系统 | 多写法图 | 做法 |
|---|---|---|
| 校验器（scans 在做） | 校验"饱和状态"而非"可执行状态" | 按状态参数化：饱和状态检查——表项编号有效；同类成员**类型相同**；有副作用/有控制输入的节点是单元素类；许可掩码一致（并集的 `perms` ⊆ 两端节点的许可）；**节点级仍无环**；写法的区域与根相同。可执行状态检查——表为空，其余为现行检查。和 scans 约定入口：`validate(graph, GraphState)` |
| 增量提交 | 与单写法图同一套 | 饱和只加末尾节点和表；`sameContent` 加比较表；未改的图仍共享；闭包遍历（引用在 FUNC 载荷里）不变，因为写法节点的被调图也进引用表（建议只允许规则复制已有的被调图引用，不新造图，见问题 3） |
| 分块共享 | 新写法追加在末尾，只改最后一两块 | 与 wide 的 `test::chunks` 同形：测"饱和后共享了除末尾外的所有块" |
| 反向可达/裁剪/DCE | 活的 = 出口可达，**或**是活类的成员 | `reachable.h`、编码时裁剪、`std::opt` 的 DCE 都要用同一个 `liveNodes(graph)`；没有表时与现在相同。**在有表的图上，不认表的遍一律拒绝**（见下） |
| 不懂表的改写遍 | 守卫 | `++mutations_` 汇合点：`writings_` 非空且不在"表感知作用域"内 → 抛 `std::logic_error`（"该图有多种写法，先提取"）。只放行 `addNode` 系列（新节点是单元素类，无害）。表感知作用域只由 `saturate`/`extract`/测试遍打开 |
| `ExecPlan`（4.6） | 不为有表的版本构建 | `GCGraph::execPlan()` 在有表时抛错；后端入口 `RunScope::begin` 检查主程序及所有被调图的标志位，报 `RuntimeDiag` 并给出哪张图。校验在版本上缓存，不是每次调用都扫 |
| 导出（ONNX、dot、JSON gir） | 入口检查同上 | dot/JSON gir 是**视图**，允许显示表（把类画成虚线框）；ONNX 与代码生成要可执行状态 |
| 事实库 | 见 §8 | |
| 并发提交（4.3.1） | 表是图版本的一部分，与图同粒度冲突检测 | 无额外规则 |
| 图空间 GC | 表随图版本释放 | 释放路径加一行 |

**红线的落点**：①后端/导出入口检查（运行时、每次进入一次）；②提交时校验"饱和状态"（提交即强制）；③规则入库前随机检验（第 8 步）。

**流水线**：遍声明 `acceptsWritings`（默认否）。驱动在运行一个不接受的遍之前，若程序含有表，报错并说明哪张图、建议在其前面放 `std::opt::extract<cost>`。`saturate` 策略默认后接 `extract`，除非显式 `keep=true`（问题 1）。

## 6. 范围与不做的

- **第一阶段范围 = 一张图内的纯数据节点**（算子、常量、访问、转换）。BRCH、LOOP、FUNC（调用）、GATE、端口、有副作用的节点是**不透明的单元素类**，但它们的**输入**是类，所以规则能穿过它们的边界匹配（`map<f>->map<g>` 这类需要 FUNC 作为头符号的规则，作为"以 FUNC 为头、被调图身份相等"的头符号支持，第二阶段）。
- 这样 R2（`if`/`LOOP` 区域化）不阻塞第 7 步；R2 之后再把分支/循环区域里的节点纳入同一张图的 e-graph（区域内的类、跨区域不合并）。
- 不做：跨图饱和；跨区域合并；函数调用的同余合并（纯被调函数的两次同参调用合并，等纯度事实可用再做）；整数规划提取；Camel 语法 `rule`（第 8 步）。

## 8. 事实与提前截断

- 事实锚点是（图，节点）。多写法图里，值 = 类，事实挂在**类根节点**上；图的 `revision()` 在表或节点变化时都会换，所以多写法图上的事实整体作废、重算——这是粗粒度但正确的。
- 分析引擎（第 8 步）在多写法图上的求值：类的事实 = 各成员的 `on` 结果的 `join`（规则稿 4.2）。第 7 步只提供遍历接口 `writingsOf(root)` 与"成员的输入类根"，不实现分析。
- 提前截断（4.4）：提取后的单写法图，若某节点内容未变（编号、算子、输入的选中成员相同），其事实在图 `revision` 变化后的核对中仍可被复用——这需要事实印章从"图的 revision"细化到"节点的版本"（图存储 §4.4 的"每个节点记录最后修改于哪个版本"）。**本步不做**，列为债务（事实库的节点级印章是单独的任务）。

## 9. 验收测试：用规则复现 `std::opt::algebra`

- 语料：`test/cases/opt/generic/algebra.cml`、`algebra_boundary.cml`（已有，`algebra.plan.toml` 用它们）。
- 规则集（C++ 构造）：交换 `a+b<=>b+a`、`a*b<=>b*a`（逐位相等，无需许可）；`x*1=>x`、`x+0=>x`（浮点 `+0.0` 要看符号零，规则按位匹配，`x+0.0` 对 `-0.0` 不成立，故只在整数或 `x+(-0.0)` 成立，与 algebra.cpp 的现行处理一致）；`x-x=>0`（整数）；`(a+b)+c<=>a+(b+c)`、`(x*a)*b=>x*(a*b)`（常量折叠）、分配律 `a*(b+c)<=>a*b+a*c`，后三者需要 `reassociate`（浮点）。
- 流程：`test::saturate`（测试遍）= 饱和（计数预算）→ 贪心提取（代价 = 算子节点数，乘除权重更高）→ `std::jgir` 输出。
- 验收三条：
  1. **执行结果相同**：对 `execution.reference` 的各后端、各 `--arg x=…`，输出与不优化、与 `std::opt::algebra` 逐位一致（默认策略；`safe_fp=true` 时用不含许可规则的规则集）。
  2. **代价不劣**：提取结果的节点代价 ≤ `std::opt::algebra` 结果的代价（在语料每个函数上）。相等的函数上，结构按规范化后相同；不要求所有函数结构逐字相同——饱和+提取与贪心局部改写的选择可能在平局上不同，平局按编号确定，所以**同一输入每次一样**，这由 `writings.deterministic` 测试（跑两次比较 JSON gir）验证。
  3. **边界**：`algebra_boundary.cml`（5e-324 等）逐位一致；`-0.0` 不被 `x+0.0` 规则误改。
- 另测：预算耗尽（1 轮）→ 返回当前状态，仍可提取并运行；`#strict` 与 `#reassociate` 混合的函数。

## 11. 风险

1. **组合爆炸**（交换+结合）：靠计数预算与"先收集再应用"；默认预算保守；预算耗尽是正常返回。
2. **确定性被哈希表破坏**：规定哈希表只查找不遍历，写成代码规范，并有 `writings.deterministic`（两次运行逐字相同）。
3. **守卫覆盖不全**：靠 `++mutations_` 汇合点，但有的改写直接改冻结数据结构吗？现有 draft 里所有变更都经成员函数，此前（A2）已验证每个非 const 成员都计数；新增成员必须遵守，测试里加"遍历所有 mutator 在表上都被拒"的清单测试。
4. **区域与放置**：提取后选中的写法节点可能被放在使用者看不到的区域；用"写法与被匹配根同区域"消除，并由校验器兜底。
5. **错误/副作用语义**：`x/x=>1` 丢掉除零错误、`x*0=>0` 丢掉 NaN；语义保证不是语言保证（设计原则第 9 节），由规则的 `requires` 与第 8 步的随机检验承担；引擎只保证类型相同、顺序约束不丢。
6. **许可层的组合复杂度**：上限 4 层，超出报错；单层路径要有测试证明与无分层相同。
7. **与 wide 的 R2/R3 同时改 draft**：本步只在 `GraphDraft` 加一个成员与一个守卫，文件冲突集中在 `draft.h/.cpp` 的类声明；合并顺序在 wide R2 之后做 7.3，或把 `WritingStore` 放独立文件 `writings.{h,cpp}` 减少冲突。
8. **增量提交的"改过但内容未变"丢弃逻辑**：有表的版本一定算改过（表非空即内容不同）；`sameContent` 要覆盖，否则饱和结果会被当作没变而丢掉——这是 7.3 最需要的负例测试。
9. **JIT/FastVM 缓存按图地址**：与本步无关（有表的图不会被执行）。
