# 图存储与图 API（第二版设计）

状态：设计已与语言作者逐条确认（2026-10-19），可以按第 7 节实施。本稿取代 [图数据模型](../graph-model/README.cn.md) 中尚未实施的部分（第 4、5、9、11 步与 5.2 节 Camel 一侧的草案，以及第 3 步第 4 片的具体做法）；已实施的部分（16 字节节点记录、每图一张引用表、源码位置列、节点属性列等）作为起点，按本稿调整。

依据：设计原则 2.3（图的数据模型要定义清楚、可以对外）、2.5（图与源码往返）、第 6、7、9.4、13 节，特别是第 6 节（标签）、9.4（标签的生命周期）、第 13 节（技术栈主线）。

## 1. 现状与问题（2026-10-19 调查）

- **同一份图构造三遍**：前端建图器（8 张以节点指针为键的旁路表）→ 编码时的第二份草稿 → 冻结图 `GCGraph`；前端与改写各有一套编码。
- **改写的代价与程序大小成正比**：`commit()` 把可达闭包里每张图都解码、重编码、校验一遍，不论改没改；`std::opt` 每轮都这样做几次；峰值内存约为两份程序。
- **身份不稳定**：图的身份是 `GCGraph*` 地址（函数值直接持有）加字符串 `stableId` 与 `lineage/serial` 过渡字段；节点编号每次提交都重新编排，旧到新的对应被丢弃。
- **扫描式算法**：删除节点扫描全图（`draft.cpp` `eraseNode`）；每次连边重建对端的尾块（`appendUserRef`/`removeUserRef`）且不回收；内联器每内联一次就重新收集闭包（`inline/engine.cpp`）；提交解码整个闭包；`visitDraftGraphs` 从节点重新推导图之间的引用。
- **硬上限**：16 位编号，每图至多 65,534 个节点、65,535 条边、约 32,766 个帧槽位。
- **各后端各算一遍执行序与分支区间**，缓存挂在扩展槽上。
- **模型不能表达"一个值的多种写法"**。

---

## 2. 原则

1. **只有一种图。** 图是程序快照中的不可变值；改写产生图的新版本。"可编辑"与"冻结"不是两种格式。
2. **改写的代价与改动成正比。**
3. **身份稳定。** 图与节点的编号不随改写变化。
4. **值可以有多种写法**，是图模型的一等能力。
5. **没有扫描式的引用查找。** 任何"谁引用了 X"的问题都由按版本维护或缓存的索引回答。
6. **先求语义稳定，再求优化。** 存储取统一、简单的做法；执行性能由执行计划、`std::fvm`、`std::jit` 负责。

## 3. 核心模型：值与写法

### 3.1 值与写法

- 图由**值**组成，每个值有类型。
- 每个值有**一种或多种写法**（节点）：一个算子作用于若干输入值、一次函数调用、一个常量、一个端口……
- **节点的输入指向值，不指向节点。**
- 普通的计算图是每个值恰好一种写法的特例：值与节点一一对应，"输入指向值"就是今天的"输入指向节点"。

### 3.2 控制依赖

编译完成后，`sync`、`var` 与资源（设计原则 3.3）只留下控制依赖。**顺序用控制边表达**，不改为"状态值"：两者可以互相转换、表达力相同，控制边与源码中的 `sync` 直接对应、不需要多输出节点。改写与等价饱和时，控制输入是节点的一组普通输入，参与匹配与等价判断；规则的模式用 `sync` 写出顺序。结果没人用的副作用不执行，即没有控制边通到出口。

### 3.3 区域

**区域是同一张图里明确标出的一组节点**，不是函数：不建帧、不传参，共用所在函数的帧与槽位，执行计划把它就地摊平。区域可以嵌套，不能部分重叠，整体是一棵树；每个节点记录它所在的最内层区域，另有一张区域表记录各区域的种类、父区域、来源与标签。

| 种类 | 来自 | 性质 |
|---|---|---|
| 分支的各个分支 | `if`、`match` | **控制区域** |
| 循环的条件与循环体 | `do` | **控制区域** |
| 内联进来的函数体 | `std::opt::inline` | 标注区域 |
| 带标签或装饰器的代码块 | `#[...] { }`、`@d { }` | 标注区域 |

- **控制区域是语义**：节点只在区域被执行时才执行。把节点移出控制区域，只有在它是纯的、不会出错时才允许；提交时的校验器检查会出错或有副作用的节点位于它应在的控制区域之内（红线）。跨分支合并公共计算时，结果放到共同的外层区域，并满足同样的条件。
- **标注区域只是记录**：对优化透明，任何遍都可以把节点移出或把区域消掉，代价只是失去调试与调度用的结构信息。
- **影响结果的标签留在节点上**（如数值许可，设计原则 7.5"随节点保留"），不靠区域：节点被移出带 `#reassociate` 的代码块，仍然带着这项许可。
- **分支**：`if` 是一个带若干控制区域的节点，取代现在由 BRCH、JOIN 与推算出的范围组成的形态；执行计划把它摊平为"判断、跳转、执行分支、跳到汇合处"，性能与今天内联后的形态相同。
- **循环**：`LOOP` 从"引用条件图与循环体图两张子图"改为"带两个控制区域"，共用帧；原生执行即"跳回循环开头"，不再需要降低成尾递归。循环的控制区域每轮交出收集值（`collectionCount`）：执行计划为每个收集槽建一个数组，在区域内原地追加一轮的值，区域结束时数组随循环的值一起给出——与 ONNX `Loop` 的 scan output、自动微分的磁带是同一个形状（每轮一个值，不是闭包链）。
- **内联来源**：内联把被调函数的函数体放进一个标注区域，记录（被内联函数的 `GraphId`，调用处），嵌套内联即嵌套区域；被内联函数的声明标签挂在区域上（设计原则 9.4 的警告据此给出）。按函数的调度（13.1）找的就是这些区域。调试器把内联进来的代码显示在调用者的帧里，标注来自哪个函数、哪次调用；GIR 可视化把区域画成可展开的框。
- 历史：分支最初就是子图，执行时每次进入都要建帧，递归程序（如 fib）开销很大，因此加了内联并让后端识别内联形态。区域保留内联形态的执行方式，只把"哪些节点属于哪个分支"从推算改为记录。

### 3.4 带许可的等价

- 每个值带有许可集合：默认许可（7.3）加上它所在区域的节点标签授予的许可。
- **加入一种写法是合法的**，当且仅当在这个许可集合之内，新写法的结果是原写法允许的结果之一。规则声明自己需要哪些许可（5.2），只在被匹配的值都有这些许可时生效；逐位相等的规则不需要许可。
- 带 `#strict` 的值许可为空，只接受逐位相等的规则。
- 提取（3.5）从合法的写法中挑选，结果自然在许可之内，不需要事后检查。
- 规则新建的节点继承被匹配节点的标签，按各标签登记的合并规则；合并不了，规则不生效。

### 3.5 饱和

- 在一次事务中（4.3），把一组规则反复应用于一个范围（一个函数及其可达的子图），只增加写法，直到不再增加或用完预算（轮数、节点数、时间）。
- 发现两个值等价时用并查集合并；输入指向值，所以上层自动共享（同余闭包）。
- 规则的条件可以读值上的标签与事实（常量、形状、范围），相当于 egglog 的分析。
- **饱和只增加写法，不决定留下什么；留下什么由抽取（3.6）决定。** 保留边界：抽取不改变哪些副作用发生：有副作用的节点、控制节点与被写入的变量不由抽取裁剪（饱和不新增它们）；它们是否执行仍按设计原则 3.1——同步块之外、结果没有被使用的带副作用的调用不执行——由执行与死代码消除决定，与抽取无关；纯节点只按可达性保留（从图命名的端口、入口、出口、返回值、区域结果出发，沿被选中的写法可达的才留下）。饱和新造、又没有任何东西读取的候选写法在抽取时删掉。

### 3.6 提取

- 按代价函数为每个值挑一种写法。代价函数可替换，可以按目标定（Tiles 提供 GPU 的代价）。
- 标准库提供贪心与基于整数规划（有时间上限）的两种提取。
- 提取结果必须无环；自环的写法（如 `x = x * 1`）在提取时排除。
- **保留边界**：有副作用的节点不由抽取裁剪（3.5）；纯节点只按可达性保留——从图命名的根（端口、入口、出口、返回值、区域结果）出发，沿被选中的写法可达的纯节点才留下。节点被选中时，它读的值一并留下；控制输入改指向它所在类的选中写法，所以控制顺序不变。饱和为每个值加的候选写法不因为"是一个值的一种写法"就留下，只有被读到才留下。

### 3.7 可执行状态

- 程序快照中允许出现带多种写法的图；**多种写法可以在遍与遍之间保留**，直到执行或导出之前再提取（例如先与目标无关地饱和，最后按目标的代价提取）。
- **可执行状态**：每个值恰好一种写法、无环、类型正确。后端与导出遍在入口检查这个状态，不满足就报错。这是一条由入口校验强制的红线。
- 满足时，为这个版本的图算一次执行计划（4.6）并缓存。

## 4. 存储

### 4.1 一种布局

- 每张图一种布局：节点记录、输入表、各附加列（类型、源码位置、名字、节点标签、内联来源）。
- **多种写法**放在一张附加表中，只在图里真的有多种写法时才存在；普通的图不为此付出任何代价。
- **编号一律 32 位**：值、节点、边、帧槽位；不再有单图容量上限。每个节点的字节数比 16 位编号时约增加 40%（16 字节的热记录加 12 字节的并列列，输入表每项 4 字节），相对张量的内存可以忽略；执行性能取决于执行计划而不是节点记录的宽度。原图数据模型 R4"容量不放宽"的结论撤回。
- **各列按固定大小分块存放**（例如每 256 个节点一块），供 4.3 的版本共享。

### 4.2 快照与版本

- **程序快照**（`Program`）是一张不可变的表：`GraphId → 某个版本的图`。
- 一次提交只为改过的图生成新版本；新版本只复制改过的块，没改的块、没改的图在新旧版本之间共享。
- **快照与图版本由垃圾回收管理**（不用引用计数：快照 → 图 → 作为常量的函数值 → 快照可以成环，引用计数会泄漏；函数值本来就由垃圾回收管理）。根是流水线正在用的快照、进行中的事务、正在执行的调用所在的快照；追踪路径是"快照 → 图版本"与"函数值 → 快照"。去掉现在由图管理器手动计算可达性、逐个释放的做法，也不再把每张图登记为根。图版本不可变，适合放在老年代。正在执行的调用持有它开始时的快照，改写不影响已经在运行的代码。

### 4.3 事务

- 改写在一个私有的**事务**（工作区）中进行：成千上万处改动就是普通的原地修改，没有版本开销；饱和的并查集与同余索引也在事务中。
- **提交**：只校验改过的图与受其影响的直接依赖者（例如签名变化时的调用者），通过后产生新快照；否则返回错误值，快照不变。
- 事务不是图的一种形态，提交之后就消失。

### 4.3.1 并发

遍即函数，函数可以并行，所以多个事务同时改图是常态。

- **以图为单位、可串行化的乐观并发**：每个事务基于某个快照开始，记录读过与写过的图；提交时，若读过或写过的图在开始之后被别的提交改过，即为冲突，提交失败并返回错误值，由调用者决定重试（重试只需重新编码改过的图）。无冲突时合并进最新快照：在最新快照上替换改过的图，用一次比较并交换完成。
- **结果确定**：由并行组合子（如 `par_map<t>(fs)`）发起的一组变换按固定顺序提交（列表中的位置），不按完成先后；冲突者基于前面已提交的结果重做。同样的输入，结果与线程调度无关。
- **共享结构并发安全**：编号原子分配；类型、标签、常量的驻留表分片加锁或无锁；程序级引用索引随提交更新；事实的计算可以并行且同一事实不重复计算。
- 最常见的并行是"对许多函数分别做同样的变换"，各改各的图，几乎没有冲突。
- **发布规则**：一次提交只有在它是"打开在上下文当前程序之上的会话"（或打开在上下文此后安装的程序之上）的提交时，才替换上下文的程序；其余提交（打开在函数值所属程序、导出、图块区域、求导引擎、分离的改写之上的会话）都是私有的，由其所有者决定去向。没有冲突的过期提交合并进最新快照时，会话持有而快照没有的图一并带上，使发布的程序闭合。

### 4.4 身份

- **`GraphId`**：程序内稳定，跨版本不变，取代 `GCGraph*` 作为函数值、引用表、标签中的图引用、事实库的键。字符串 `stableId` 与 `lineage/serial` 退役。
- **函数值持（快照，`GraphId`）**。调用时按编号找图的一步，在执行计划中预先解析；`std::fvm`、`std::jit` 可以进一步优化掉。
- **`NodeId`**：在一张图的各个版本之间稳定。新节点取新编号；删除的节点留墓碑，编号不复用；只有显式整理时才重新编号，并产出旧到新的对应表，事实、标签、调度据此迁移。
- **版本号**：每张图有版本号；一个节点的版本是它内容的哈希（含它消费的节点），不逐节点存储标记。
- **事实按需、增量地重算**（rust-analyzer 的 Salsa、rustc 增量编译的做法）：每个事实记录它依据的输入事实及其版本；查询时核对，输入变了才重算这一个事实（必要时递归更新依据），重算结果与原来相同则依赖它的事实不必重算（提前截断）。`fact` 声明的依赖由引擎自动记录；事实只在被查询时计算。

### 4.5 索引（取代扫描）

| 问题 | 回答方式 |
|---|---|
| 一个值有哪些使用者 | 每个图版本按需建一次使用者索引（CSR），缓存在版本上；事务中随改动增量维护 |
| 谁调用、引用了某张图 | 程序级的引用索引，随快照增量维护（每次提交只更新改过的图的出边） |
| 删除节点 | 打墓碑，O(1)；使用者索引随之更新，不扫描 |
| 内联的工作列表 | 用调用索引维护待内联的调用，不在每次内联后重新收集闭包 |
| 提交时要校验哪些图 | 改过的图加上引用索引给出的直接依赖者 |

### 4.6 执行计划

执行序、分支区间、调用槽位、解析好的被调图，由可执行状态的图版本一次算出（原第 3 步第 4 片），所有后端共用，缓存在版本上；编码时裁剪死节点。后端不再各自计算，不再使用扩展槽。

### 4.7 标签、来源与名字

- **节点标签**：每个节点一个驻留的标签集合编号（`node_attrs.h`，已实现）。
- **声明标签**：函数（图头）、类型声明、字段、参数各有一个标签集合（6.2、6.6）。
- **内联来源**：标注区域（3.3）。
- **源码位置**：每个节点一个（已实现）。
- **名字**：`let` 绑定的名字作为一列，只在有名字时存在，供 `std::cml`、调试器、诊断使用。

### 4.8 与源码往返所需的信息（2.5）

命名类型的声明与模块归属（5.2）、函数签名与参数名、`let` 名字、控制依赖、声明与节点标签、常量（大常量引用旁边的数据文件）。图上存在而源码写不出的结构，视为语言的缺口。

## 5. Camel 一侧的图 API

### 5.1 三个层次

1. **函数到函数（入口）**：变换是 `(f: F) => F!` 的普通函数。`graph::of(f)` 打开一个事务，`graph::to::<F>(g)` 提交并还原为同类型的函数值，签名不符是错误。命令行上的遍就是作用于入口函数的变换；装饰器、`#macro` 用的是同一套东西。
2. **规则（主要写法）**：见 5.2。两种引擎：`rewrite<rules>(f)` 贪心改写；`saturate<rules, budget>(f)` 加 `extract<cost>(f)`。
3. **底层节点 API**：读值、写法、输入、使用者、标签、事实；在事务中改动、整体提交。留给分析、降低、切分推导这类复杂的变换。

### 5.2 `rule` 声明

```camel
rule mul_one(x: float) { x * 1.0 => x }

#requires(reassociate)
rule add_assoc(a: f32, b: f32, c: f32) { (a + b) + c <=> a + (b + c) }

rule fuse_map<f, g>(xs: int[]) { xs->map<f>->map<g> => xs->map<(a) => g(f(a))> }
    when is_pure(f)

export let simplify = [mul_one, add_assoc, fuse_map]
```

- `=>` 单向（贪心引擎），`<=>` 双向（等价饱和）；`when` 是条件，可以读模式变量的标签与事实。
- 所需许可是规则声明上的标签 `#requires(...)`。
- `rule` 是"两个参数相同的函数加配对"的简写（1），语义相同。规则可以导出、导入；规则列表是普通的值。
- **入库前的随机检验是强制的**：测试工具枚举全部 `rule` 声明，对每条规则用随机输入、按它声明的许可分别运行两边并比较（数值契约 7.3）；标准规则库不通过不能合并。

### 5.3 不用字符串

- 节点种类是 `enum`。
- 算子用它的声明来指：`graph::op(n) == matmul`，比较身份，不比较 URI 字符串。
- 常量用泛型取：`graph::constant::<f32>(n): f32?`。
- 被分析的程序里的类型，在写遍的代码中是 `graph::TypeRef` 值，与写遍程序自己的类型分开；`graph::type_of::<T>()` 取得 `T` 对应的 `TypeRef`。
- 节点、值、图都可比较、可作映射的键。

### 5.4 保证

- **提交时整体校验**（结构、类型、无环与否按状态而定、引用完整）：Camel 程序造不出坏图。红线，由校验器强制。
- **可执行状态由后端入口检查**（3.6）。红线。
- **规则入库前随机检验**（5.2）。红线。
- "改写不改变语义"不作为语言的保证（设计原则第 9 节）。

### 5.5 性能

规则在加载时编译为匹配程序，由原生引擎执行；Camel 代码只描述规则与条件。底层 API 的查询直接读图，不复制。

## 6. 现有消费者怎样迁移

| 消费者 | 变化 |
|---|---|
| 前端建图器 | 在事务中直接建图；删除旁路表与第二份草稿 |
| 内联、折叠、CSE、DCE、算式优化 | 在事务中局部改写、只提交改过的图；内联用调用索引维护工作列表；算式优化与 CSE 逐步改写成规则 |
| 自动微分 | 用底层 API 建新图；不再直接解码草稿；`#vjp` 读声明标签 |
| 各后端 | 读执行计划；函数值持（快照，`GraphId`） |
| 事实库 | 键为（`GraphId`，`NodeId`），按节点版本判断有效性 |
| 调试器 | 位置与名字列、内联来源；图按 `GraphId` 标识 |
| Tiles、ONNX | 读可执行状态的图与标签；Tiles 的代价函数接入 `extract` |

## 7. 实施顺序

1. **身份与快照**：`GraphId`、程序快照（引用计数）、函数值改持（快照，`GraphId`）；`stableId`、`lineage/serial` 退役。
2. **统一布局**：32 位编号、分块的列、输入指向值（一对一时与现在相同）、墓碑与整理；前端在事务中直接建图，删除第二份草稿与旁路表。
3. **索引与增量提交**：使用者索引、程序级引用索引；只校验与编码改过的图；删除第 1 节列出的扫描式算法；`std::opt` 与内联改为局部改写。
4. **执行计划**：所有后端共用。
5. **区域、标签与名字**：区域列与区域表；`if`、`match` 改为带控制区域的节点，`LOOP` 改为带两个控制区域（原生循环）；内联产生标注区域；声明标签（含参数位置）、`let` 名字列。
6. **Camel 一侧的图 API**：函数到函数、底层 API（依赖 `enum`）。
7. **多种写法**：附加表、并查集、同余闭包、`saturate`、`extract`、带许可的规则。
8. **`rule` 声明与规则引擎**：贪心与饱和两种引擎、入库前的随机检验、标准规则库。
9. **`std::cml`** 与往返测试。

每一步结束时，全部测试与随机程序测试通过；性能用 `test/plans/perf` 对比，建图与改写的时间、峰值内存应当下降。

## 8. 已确认的决定（2026-10-19）

1. 编号一律 32 位，只保留一种格式，不再有单图容量上限。
2. 只有一种图：可执行是图的一种状态；多种写法可以在遍与遍之间保留，执行与导出前提取。
3. 版本按提交产生，列分块共享；事务中原地修改。
4. 带许可的等价（3.4）。
5. 加入 `rule` 声明（5.2），所需许可用标签表示，入库前强制随机检验。
6. 函数值持（快照，`GraphId`）；先求语义稳定，按编号找图的开销留给 `std::fvm`、`std::jit`。（快照的管理见第 12 条。）
7. 清除扫描式的引用查找，改用索引（4.5）。
8. 顺序用控制边表达，不改为状态值（3.2）。
9. 区域（3.3）：控制区域与标注区域；分支与循环改为带控制区域的节点、共用帧；内联来源是标注区域；影响结果的标签留在节点上。
10. 事务采用以图为单位、可串行化的乐观并发；并行组合子按固定顺序提交，结果确定（4.3.1）。
11. 事实按需、增量地重算，结果不变则提前截断（4.4）。
12. 快照与图版本由垃圾回收管理，取代引用计数与图管理器的手动释放（4.2）。

## 9. 开工计划

第 1 节是 2026-10-19 施工前的调查，不是今天的形状：第 1 步的主体已经在这一版主干上，第 2 步的存储部分（32 位编号、分块、墓碑）、第 4 步（执行计划）与第 5 步的大部也已在。下面先按代码量一遍现状（数字都在，可复核），再写第 1 步剩下的那一处怎么做完，以及它给序列化留下什么。

### 9.1 现状：三份构造收敛到一处

| 项目 | 施工前的调查（第 1 节） | 现在（`src/` 实测） |
|---|---|---|
| 冻结图的构造点 | 3 处：前端旁路表建图 → 编码时第二份草稿 → 冻结图 | **1 处**：`GCGraphBuildAccess::constructInPlace`（`src/runtime/graph.cpp#GCGraphBuildAccess::constructInPlace`；`create` 只算字节再调它）。另有 `GCGraph::clone`（`src/runtime/graph.cpp#GCGraph::clone`）复制值头、共享块，不构造内容 |
| 编码入口 | 前端与改写各有一套 | **1 个**：`encodeToRuntimeProgram`（`src/compile/gir/graph_encode.cpp#encodeToRuntimeProgram`），6 个调用点（`userdef.cpp` 1、`definitions.cpp` 2、`rule_templates.cpp` 3） |
| 编辑用的图 | 前端旁路表 + 第二份草稿 | 前端与改写共用一份 `runtime::GraphDraft`（`include/camel/runtime/draft.h`），编码直接读它，"第二份草稿"不存在了 |
| 以节点为键的旁路表 | 8 张，键是节点指针（第 1 节） | **4 张**，键是节点编号：`nodePortNames_`、`funcTargets_`、`drefTargets_`、`operTargets_`（`include/camel/compile/gir/draft_graph_builder.h#nodePortNames_`） |
| 以图为键的地址表 | 图的身份就是 `GCGraph*` | **1 张**：`DebugMap::runtimeGraphOrigins_`，本轮删除（9.3） |

三份构造于是收敛成"一份可编辑的图（草稿）+ 一次编码"，图的内容只在一处造（`constructInPlace`）。剩下的收敛是第 2 步的"前端在事务中直接建图、删掉草稿与旁路表"，它一次改动前端、内联、自动微分与全部后端，单独一步做不成独立的一步，排在第 1 步之后。

### 9.2 第 1 步清单里已落地的部分（不再重复做）

- **`GraphId`**（`4.4`）：每程序一个 `GraphIdAllocator`（`Context::graphIds()`，`include/camel/core/context/context.h#graphIds`），建图处取号：`src/compile/gir/builder.cpp#graphIds`、`src/compile/gir/builder_generics.cpp#graphIds`，改写造的新图由编码取新号（`src/compile/gir/graph_encode.cpp#prepareGraph`）。
- **函数值持（快照，`GraphId`）**：`Function::program()` 与 `Function::graphId()`，取图走 `program->graph(id)`（`include/camel/core/rtdata/func.h#graphId`）。
- **程序快照**：`Program`（`include/camel/runtime/program.h`），`GraphId → 该图的一个版本`；快照与图版本由 GC 管（`GCGraphManager`，`include/camel/runtime/graph.h#GCGraphManager`），不是引用计数——这是第 8 节第 12 条，第 7 节第 1 步括号里的"（引用计数）"已被它取代，代码取第 12 条。
- **`stableId`、`lineage`、`serial` 退役**：`include/`、`src/`、`modules/` 里已无这三个名字。
- **其余键也已按编号**：引用表按 `GraphId`（`GCGraph::refs()`）、事实库键为（`GraphId`，节点）（`include/camel/runtime/facts.h#entries_`）、特化表按 `GraphId`、GIR 的编号由 `GraphId` 推出（`src/passes/trans/json/gir_canonical.cpp#graphIdByValue_`）。

### 9.3 第 1 步剩下的那一处：运行时图的源位置不再按地址查

"这个运行时图是从哪段源码来的"曾经有两个来源：`DebugMap::graphOrigins_`（键是 `GraphId`）与 `DebugMap::runtimeGraphOrigins_`（键是 `GCGraph*` 的地址）。后者是每次安装程序时由 `Context::registerRuntimeGraphDebugInfo` 从前者拷进来的，只为让故障报告（`ExecutionSite` 手里只有 `GCGraph*`）查得到。这与第 4.4 节"`GraphId` 取代 `GCGraph*`"相反，代价有三条：

1. **同一事实两处**：拷进地址表的值与编号表里的值随时可能不同（`cloneGirGraphDebugInfo` 改了编号表，地址表不会跟着改），故障报的行号因此可能是旧版本的。
2. **过期与泄漏**：地址表只增不减，图版本被回收后条目还在；地址被后来的图复用时，那张图会读到别人的源位置。
3. **序列化接不住**：写出去再读回来的程序，图的地址全变了，地址键一条也对不上；`GraphId` 键可以随冻结图块一起存、一起读。

做法（`4.4` 的直接后果，不引入任何新形式）：

- 删 `DebugMap::registerRuntimeGraphOrigin`、`DebugMap::runtimeGraphOrigin` 与 `runtimeGraphOrigins_`（`include/camel/core/source/manager.h`、`src/core/source/manager.cpp`）。
- 删 `Context::registerRuntimeGraphDebugInfo` 与它的 4 个调用点（`materializeRuntimeProgram`、`installRuntimeProgram`、`adoptRuntimeProgram`、`installRuntimeProgramIfCurrent`）；它唯一做的事就是那次拷贝。调试器里同一个值的地址兜底（`tools/debugger/src/core/program_index.cpp`）一并删掉。
- 故障路径不再查图级源位置：`ExecutionSite` 的位置来自抛错点自带的 hint（`RuntimeErrorReporter::describe` 优先用 `fault.hint().cachedOrigin`）与节点、PC 自己的源位置（`std::nvm` 的 `GCGraph::nodeOrigin`、`makePcExecutionSite` 的 `pcOrigin`）；`makeGraphExecutionSite` 里按 `GraphId` 查表写进 `cachedOrigin`、以及 `resolveOriginFromSite` 的图级兜底，经实测从不决定任何一条诊断的位置（判据 2），本轮一并删除，只把这段位置让给 `currentRuntimeOrigin()`。`DebugMap::graphOrigin` 与那张 `GraphId → origin` 表保留：编译期建图、入口参数诊断与调试器的函数归属仍在读它。

判据与验收：

1. **身份**：`include`、`src`、`modules` 里不再有以地址为图的身份的容器；图的身份只由 `GCGraph::id()` 给出，运行时与编译期查的是同一张 `GraphId → origin` 表。仍以 `GCGraph*` 为键的容器都是"要那一个版本对象"而不是"要哪张图"：GC 的登记表（`GCGraphManager::graphs_`、`unbound_`）、事务里的草稿表（`DraftSession::drafts_`、`edited_`）、遍内按版本建的计划与偏移表——它们随对象一起消失，不承担身份。
2. **输出逐字不变**：解释器 `std::nvm` 与另外三个后端（`std::fvm`、`std::jit`、`std::prl`）在同一批语料上的 stdout、退出码、诊断名、行、列不变——`feat/consistency/faults`、`feat/consistency/faults_optimized` 两张计划逐条比对这四个后端并且比位置。
   **这两张计划不守卫图级查表**（本节初稿曾如此声称，实测不成立，已撤回）：一次全层运行里计数（fast 7,756 条 + `feat/tools/debugger`、`feat/trans/cpp`、`feat/tools/lsp` 三张 slow 计划，11,184 个进程），`makeGraphExecutionSite` 的图级查表被执行 **629,397 次**、命中 629,396 次，而 `resolveOriginFromSite` 的图级兜底执行 **0 次**；把运行时这两处一起删掉，同一批 **7,762 条全绿**（fail 0）。位置由抛错点的 hint 与节点、PC 的源位置决定——两张故障计划里没有任何一条走到图级查表，所以它不是"有守卫的兜底"，而是没有可观测效果的兜底：删掉它不需要守卫，也不可能写出守住它的用例（删掉前后输出逐字相同）。
3. **那张表本身仍有守卫**：`DebugMap::graphOrigin` 被编译期建图、入口参数诊断与调试器的函数归属读取；把它整体改成返回无效编号时，同一批运行红 **89 条**（`entry_args.*`、`gir.rgir_snapshot`、`boundaries.agir`/`argir`、`camel_passes.*.by_cpp`、`lsp.*`、`debugger.dap_frames`、`rename.*_graph_identity` 等），这些就是它的守卫。
4. **闸门**：`-Plan all -Tier fast -Jobs 8` 新红 0、`snapshot differs` 0；GIR 金标若变单独一笔重录并说明原因（本轮预期不变：`GraphId` 不进 DOT 文本——`src/passes/trans/dot/graphviz.cpp` 不读它——`gir_canonical` 的 `g0/g1` 由遍历顺序给出）。
5. **没有过渡态**：不新增格式、不保留地址表、不留"以后再说"的分支；地址表、它的写入点与运行时那两处图级查表都是净删除。

它给后续序列化留下的东西：一张按 `GraphId` 键的源位置表可以和图块写在一起、读回来仍然对得上（地址做不到）；而"图的内容只在一处造"（9.1）意味着冻结图块就是唯一的落盘形状——声明状态那一类产物直接写这个形状即可，不必先造一个临时格式再写第二遍。
