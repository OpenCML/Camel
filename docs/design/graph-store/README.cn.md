# 图存储与图 API（第二版设计）

状态：设计已与语言作者逐条确认（2026-10-19），可以按第 7 节实施。本稿取代 [图数据模型](../graph-model/README.cn.md) 中尚未实施的部分（第 4、5、9、11 步与 5.2 节 Camel 一侧的草案，以及第 3 步第 4 片的具体做法）；已实施的部分（16 字节节点记录、每图一张引用表、源码位置列、节点属性列等）作为起点，按本稿调整。

依据：设计原则 2.11（图的数据模型要定义清楚、可以对外）、2.17–2.23，特别是 2.20（标签）、2.21（调度与标签的生命周期）、2.23（技术栈主线、图与源码往返）。

---

## 1. 现状与问题（2026-10-19 调查）

- **同一份图构造三遍**：前端建图器（8 张以节点指针为键的旁路表）→ 编码时的第二份草稿 → 冻结图 `GCGraph`；前端与改写各有一套编码。
- **改写的代价与程序大小成正比**：`commit()` 把可达闭包里每张图都解码、重编码、校验一遍，不论改没改；`std::opt` 每轮都这样做几次；峰值内存约为两份程序。
- **身份不稳定**：图的身份是 `GCGraph*` 地址（函数值直接持有）加字符串 `stableId` 与 `lineage/serial` 过渡字段；节点编号每次提交都重新编排，旧到新的对应被丢弃。
- **扫描式算法**：删除节点扫描全图（`draft.cpp` `eraseNode`）；每次连边重建对端的尾块（`appendUserRef`/`removeUserRef`）且不回收；内联器每内联一次就重新收集闭包（`inline/engine.cpp`）；提交解码整个闭包；`visitDraftGraphs` 从节点重新推导图之间的引用。
- **硬上限**：16 位编号，每图至多 65,534 个节点、65,535 条边、约 32,766 个帧槽位。
- **各后端各算一遍执行序与分支区间**，缓存挂在扩展槽上。
- **模型不能表达"一个值的多种写法"**。

---

## 2. 原则

1. **只有一种图。** 图是程序快照中的不可变值；改写产生图的新版本。"可编辑"与"冻结"不是两种格式。
2. **改写的代价与改动成正比。**
3. **身份稳定。** 图与节点的编号不随改写变化。
4. **值可以有多种写法**，是图模型的一等能力。
5. **没有扫描式的引用查找。** 任何"谁引用了 X"的问题都由按版本维护或缓存的索引回答。
6. **先求语义稳定，再求优化。** 存储取统一、简单的做法；执行性能由执行计划、`std::fvm`、`std::jit` 负责。

## 3. 核心模型：值与写法

### 3.1 值与写法

- 图由**值**组成，每个值有类型。
- 每个值有**一种或多种写法**（节点）：一个算子作用于若干输入值、一次函数调用、一个常量、一个端口……
- **节点的输入指向值，不指向节点。**
- 普通的计算图是每个值恰好一种写法的特例：值与节点一一对应，"输入指向值"就是今天的"输入指向节点"。

### 3.2 控制依赖

编译完成后，`sync`、`var` 等只留下控制依赖（设计原则第 4 节）。控制依赖是节点的一组普通输入，参与匹配与等价判断，与数据输入一样处理。

### 3.3 带许可的等价

- 每个值带有许可集合：默认许可（2.22）加上它所在区域的节点标签授予的许可。
- **加入一种写法是合法的**，当且仅当在这个许可集合之内，新写法的结果是原写法允许的结果之一。规则声明自己需要哪些许可（5.2），只在被匹配的值都有这些许可时生效；逐位相等的规则不需要许可。
- 带 `#strict` 的值许可为空，只接受逐位相等的规则。
- 提取（3.5）从合法的写法中挑选，结果自然在许可之内，不需要事后检查。
- 规则新建的节点继承被匹配节点的标签，按各标签登记的合并规则；合并不了，规则不生效。

### 3.4 饱和

- 在一次事务中（4.3），把一组规则反复应用于一个范围（一个函数及其可达的子图），只增加写法，直到不再增加或用完预算（轮数、节点数、时间）。
- 发现两个值等价时用并查集合并；输入指向值，所以上层自动共享（同余闭包）。
- 规则的条件可以读值上的标签与事实（常量、形状、范围），相当于 egglog 的分析。

### 3.5 提取

- 按代价函数为每个值挑一种写法。代价函数可替换，可以按目标定（Tiles 提供 GPU 的代价）。
- 标准库提供贪心与基于整数规划（有时间上限）的两种提取。
- 提取结果必须无环；自环的写法（如 `x = x * 1`）在提取时排除。

### 3.6 可执行状态

- 程序快照中允许出现带多种写法的图；**多种写法可以在遍与遍之间保留**，直到执行或导出之前再提取（例如先与目标无关地饱和，最后按目标的代价提取）。
- **可执行状态**：每个值恰好一种写法、无环、类型正确。后端与导出遍在入口检查这个状态，不满足就报错。这是一条由入口校验强制的红线。
- 满足时，为这个版本的图算一次执行计划（4.6）并缓存。

## 4. 存储

### 4.1 一种布局

- 每张图一种布局：节点记录、输入表、各附加列（类型、源码位置、名字、节点标签、内联来源）。
- **多种写法**放在一张附加表中，只在图里真的有多种写法时才存在；普通的图不为此付出任何代价。
- **编号一律 32 位**：值、节点、边、帧槽位；不再有单图容量上限。图占用的内存估计增加 20–25%，相对张量的内存可以忽略；执行性能取决于执行计划而不是节点记录的宽度。原图数据模型 R4"容量不放宽"的结论撤回。
- **各列按固定大小分块存放**（例如每 256 个节点一块），供 4.3 的版本共享。

### 4.2 快照与版本

- **程序快照**（`Program`）是一张不可变的表：`GraphId → 某个版本的图`。
- 一次提交只为改过的图生成新版本；新版本只复制改过的块，没改的块、没改的图在新旧版本之间共享。
- 快照用引用计数管理；正在执行的调用持有它开始时的快照，改写不影响已经在运行的代码；没有引用的旧版本立即释放。通常同一时刻只有一两个快照存活。

### 4.3 事务

- 改写在一个私有的**事务**（工作区）中进行：成千上万处改动就是普通的原地修改，没有版本开销；饱和的并查集与同余索引也在事务中。
- **提交**：只校验改过的图与受其影响的直接依赖者（例如签名变化时的调用者），通过后产生新快照；否则返回错误值，快照不变。
- 事务不是图的一种形态，提交之后就消失。

### 4.4 身份

- **`GraphId`**：程序内稳定，跨版本不变，取代 `GCGraph*` 作为函数值、引用表、标签中的图引用、事实库的键。字符串 `stableId` 与 `lineage/serial` 退役。
- **函数值持（快照，`GraphId`）**。调用时按编号找图的一步，在执行计划中预先解析；`std::fvm`、`std::jit` 可以进一步优化掉。
- **`NodeId`**：在一张图的各个版本之间稳定。新节点取新编号；删除的节点留墓碑，编号不复用；只有显式整理时才重新编号，并产出旧到新的对应表，事实、标签、调度据此迁移。
- **版本号**：每张图有版本号，每个节点记录"最后修改于哪个版本"；事实按节点判断是否有效（节点没变，事实就仍然有效）。

### 4.5 索引（取代扫描）

| 问题 | 回答方式 |
|---|---|
| 一个值有哪些使用者 | 每个图版本按需建一次使用者索引（CSR），缓存在版本上；事务中随改动增量维护 |
| 谁调用、引用了某张图 | 程序级的引用索引，随快照增量维护（每次提交只更新改过的图的出边） |
| 删除节点 | 打墓碑，O(1)；使用者索引随之更新，不扫描 |
| 内联的工作列表 | 用调用索引维护待内联的调用，不在每次内联后重新收集闭包 |
| 提交时要校验哪些图 | 改过的图加上引用索引给出的直接依赖者 |

### 4.6 执行计划

执行序、分支区间、调用槽位、解析好的被调图，由可执行状态的图版本一次算出（原第 3 步第 4 片），所有后端共用，缓存在版本上；编码时裁剪死节点。后端不再各自计算，不再使用扩展槽。

### 4.7 标签、来源与名字

- **节点标签**：每个节点一个驻留的标签集合编号（`node_attrs.h`，已实现）。
- **声明标签**：函数（图头）、类型声明、字段、参数各有一个标签集合（2.20、2.23）。
- **内联来源**：值为（被内联函数的 `GraphId`，调用处的 `NodeId`，外层来源）的链，并带上被内联函数的声明标签（2.21）。
- **源码位置**：每个节点一个（已实现）。
- **名字**：`let` 绑定的名字作为一列，只在有名字时存在，供 `std::cml`、调试器、诊断使用。

### 4.8 与源码往返所需的信息（2.23）

命名类型的声明与模块归属（2.19）、函数签名与参数名、`let` 名字、控制依赖、声明与节点标签、常量（大常量引用旁边的数据文件）。图上存在而源码写不出的结构，视为语言的缺口。

## 5. Camel 一侧的图 API

### 5.1 三个层次

1. **函数到函数（入口）**：变换是 `(f: F) => F!` 的普通函数。`graph::of(f)` 打开一个事务，`graph::to::<F>(g)` 提交并还原为同类型的函数值，签名不符是错误。命令行上的遍就是作用于入口函数的变换；装饰器、`#macro` 用的是同一套东西。
2. **规则（主要写法）**：见 5.2。两种引擎：`rewrite<rules>(f)` 贪心改写；`saturate<rules, budget>(f)` 加 `extract<cost>(f)`。
3. **底层节点 API**：读值、写法、输入、使用者、标签、事实；在事务中改动、整体提交。留给分析、降低、切分推导这类复杂的变换。

### 5.2 `rule` 声明

```camel
rule mul_one(x: float) { x * 1.0 => x }

#requires<reassociate>
rule add_assoc(a: f32, b: f32, c: f32) { (a + b) + c <=> a + (b + c) }

rule fuse_map<f, g>(xs: int[]) { xs->map<f>->map<g> => xs->map<(a) => g(f(a))> }
    when is_pure(f)

export let simplify = [mul_one, add_assoc, fuse_map]
```

- `=>` 单向（贪心引擎），`<=>` 双向（等价饱和）；`when` 是条件，可以读模式变量的标签与事实。
- 所需许可是规则声明上的标签 `#requires<...>`。
- `rule` 是"两个参数相同的函数加配对"的简写（2.18），语义相同。规则可以导出、导入；规则列表是普通的值。
- **入库前的随机检验是强制的**：测试工具枚举全部 `rule` 声明，对每条规则用随机输入、按它声明的许可分别运行两边并比较（数值契约 2.22）；标准规则库不通过不能合并。

### 5.3 不用字符串

- 节点种类是 `enum`（依赖交接任务 H1）。
- 算子用它的声明来指：`graph::op(n) == matmul`，比较身份，不比较 URI 字符串。
- 常量用泛型取：`graph::constant::<f32>(n): f32?`。
- 被分析的程序里的类型，在写遍的代码中是 `graph::TypeRef` 值，与写遍程序自己的类型分开；`graph::type_of::<T>()` 取得 `T` 对应的 `TypeRef`。
- 节点、值、图都可比较、可作映射的键。

### 5.4 保证

- **提交时整体校验**（结构、类型、无环与否按状态而定、引用完整）：Camel 程序造不出坏图。红线，由校验器强制。
- **可执行状态由后端入口检查**（3.6）。红线。
- **规则入库前随机检验**（5.2）。红线。
- "改写不改变语义"不作为语言的保证（设计原则第 4 节）。

### 5.5 性能

规则在加载时编译为匹配程序，由原生引擎执行；Camel 代码只描述规则与条件。底层 API 的查询直接读图，不复制。

## 6. 现有消费者怎样迁移

| 消费者 | 变化 |
|---|---|
| 前端建图器 | 在事务中直接建图；删除旁路表与第二份草稿 |
| 内联、折叠、CSE、DCE、算式优化 | 在事务中局部改写、只提交改过的图；内联用调用索引维护工作列表；算式优化与 CSE 逐步改写成规则 |
| 自动微分 | 用底层 API 建新图；不再直接解码草稿；`#vjp` 读声明标签 |
| 各后端 | 读执行计划；函数值持（快照，`GraphId`） |
| 事实库 | 键为（`GraphId`，`NodeId`），按节点版本判断有效性 |
| 调试器 | 位置与名字列、内联来源；图按 `GraphId` 标识 |
| Tiles、ONNX | 读可执行状态的图与标签；Tiles 的代价函数接入 `extract` |

## 7. 实施顺序

1. **身份与快照**：`GraphId`、程序快照（引用计数）、函数值改持（快照，`GraphId`）；`stableId`、`lineage/serial` 退役。
2. **统一布局**：32 位编号、分块的列、输入指向值（一对一时与现在相同）、墓碑与整理；前端在事务中直接建图，删除第二份草稿与旁路表。
3. **索引与增量提交**：使用者索引、程序级引用索引；只校验与编码改过的图；删除第 1 节列出的扫描式算法；`std::opt` 与内联改为局部改写。
4. **执行计划**：所有后端共用。
5. **标签与名字的存储**：声明标签（含参数位置）、内联来源、`let` 名字列（与交接任务 H2、H3b 合流）。
6. **Camel 一侧的图 API**：函数到函数、底层 API（依赖 H1 的 `enum`）。
7. **多种写法**：附加表、并查集、同余闭包、`saturate`、`extract`、带许可的规则。
8. **`rule` 声明与规则引擎**：贪心与饱和两种引擎、入库前的随机检验、标准规则库。
9. **`std::cml`** 与往返测试。

每一步结束时，全部测试与随机程序测试通过；性能用 `test/plans/perf` 对比，建图与改写的时间、峰值内存应当下降。

## 8. 已确认的决定（2026-10-19）

1. 编号一律 32 位，只保留一种格式，不再有单图容量上限。
2. 只有一种图：可执行是图的一种状态；多种写法可以在遍与遍之间保留，执行与导出前提取。
3. 版本按提交产生，列分块共享；事务中原地修改。
4. 带许可的等价（3.3）。
5. 加入 `rule` 声明（5.2），所需许可用标签表示，入库前强制随机检验。
6. 函数值持（快照，`GraphId`），快照用引用计数；先求语义稳定，按编号找图的开销留给 `std::fvm`、`std::jit`。
7. 清除扫描式的引用查找，改用索引（4.5）。
