# 重构总方案：结构重组、架构重构、特性与修复

> 已定（负责人 2026-11-22）。依据：核心抽象 `abstractions.cn.md`（已定）、设计原则（已定稿）。各步的施工计划由决策者写：只落实已定设计的，写完即派工并通知负责人；出现新的原则取舍或要推翻负责人既有裁定的，先请负责人定（负责人 2026-11-22）。

## 0. 三件事怎样互相牵涉

| | 是什么 | 牵涉 |
|---|---|---|
| **结构重组** | 按 `kernel/`、`parse/`、`compile/`、`lib/<模块>/`、`tools/` 搬家，立构建边界 | 动每一个文件的路径：任何一条开着的分支都会和它冲突 |
| **架构重构** | 按核心抽象第 1–19 节换掉抽象 | 第 1、2 节（图与存储）是所有代码的底子，改它会波及所有读图的地方 |
| **特性与修复** | CI 红、回归、CC 主案例等 | 改到正在重构的代码，修了也会被重构推倒 |

由此得出三条总则：
1. **搬家只做一次、纯机械、在一个窗口里完成**，不做成长期分支。
2. **架构重构先立接口、再按使用方分头迁移、最后在接口下面换实现**，让多条车道能同时动手而不互相踩。
3. **重构期间冻结新特性**（负责人已定）；修复按"修在哪一层"分流，不在马上要被推倒的代码上打补丁。

## 1. 阶段

### 阶段 0：搬家前的准备（现在就能做，彼此独立）

- **CI 四条腿转绿**，作为之后每一步的合并闸门。
- **三处依赖反转**（不机械，所以放在搬家之前、在现有布局里做）：调遍的驱动改为按名字调用、由模块登记实现；源码模块加载改为内核定义接口、编译器实现；重写核心与变换只认编译好的规则值、不读规则头。
- **搬家脚本**：由对照清单（`docs/design/architecture/layout-map.cn.md` 的做法）生成，输入是"路径 → 目标位置"的表，输出是 `git mv` 与包含路径的改写。脚本可以在任何一个 develop 头上重跑，所以不需要搬家分支。
- **差分对照工具的骨架**（第 18 节），后面每一步都用它验收。

### 阶段 1：搬家窗口

1. 所有车道把手上的分支合进 develop 或暂停；合并位确认没有开着的改动。
2. 在当时的 develop 头上跑搬家脚本，立构建目标；越层引用变成编译错误，整理成**违例清单**（每条标明归哪一步重构清掉）。
3. 能编译、CI 不差于搬家前即合入；之后所有车道在新布局上重开分支。

搬家只改路径与包含，不改行为；比对搬家前后的测试读数逐条一致。

### 阶段 2：接口先行

关键路径上的两样东西先把**接口**定下来（头文件写成最终形态，评审通过），实现先架在现有的表示之上：
- **图的读接口**：统一视图（核心抽象第 2 节）、节点种类表、端口组访问器、区域与三种边的查询。
- **算子记录与事实框架的接口**：一条记录、两个入口（第 3 节）；事实的登记、查询、按依赖失效（第 4 节）。

接口一合入，各使用方车道就开始把自己那块代码迁到新接口上。

### 阶段 3：按使用方迁移，接口下换实现

- 各使用方车道并行迁移：变换、重写、前端、执行、工具，各管自己的目录。
- 图车道在接口下面换实现：九种节点、结构节点拥有区域、不可变值与编辑会话、图空间不移动。使用方已经只走接口，所以换实现不牵动它们。
- 每块迁完，删掉它对旧访问方式的全部使用；旧访问方式没有使用者了就删掉。

### 阶段 4：Camel 化与新特性

C++ 骨架做干净之后，逐个用 Camel 重写并保留 C++ 版作对照（原则 1）；冻结解除，CC 主案例等新特性在新抽象上开发。

## 2. 车道（同时 6–8 条）

车道按**目录所有权**划分：搬家之后目录就是层与模块，一条车道独占一组目录，别的车道不改这些目录里的文件。

| 车道 | 独占的目录 | 主要工作 | 依赖 |
|---|---|---|---|
| **图** | `kernel/graph`（数据模型、存储、编辑会话、原语、GC 的图空间） | 第 1、2 节 | 关键路径的起点 |
| **算子与事实** | `kernel/ops`、`kernel/facts`、C 接口层 | 第 3、4、15、16、17 节 | 与图车道同时开工（接口互相独立） |
| **变换** | `lib/transforms` | 第 6 节：三个骨架、共有部件、二阶导 | 图与事实的接口 |
| **重写** | `kernel/rewrite`、`lib/rewrite`、`lib/std/cxx/opt` | 第 7 节 | 编辑接口与事实接口 |
| **前端** | `parse/`、`compile/` | 第 8 节：分阶段、类型检查、建图、类型函数两个入口 | 图的写入口；与新旧比对配套 |
| **执行** | `lib/std/exec`、`lib/std/nvm`、`fvm`、`prl`、`cpp` | 第 13、14 节：执行计划作为事实、值的表示、各后端只读接口 | 图的读接口与事实接口 |
| **工具与差分** | `tools/`、差分对照工具 | 第 18、19 节：自省接口的使用方、各步的验收 | 内核自省接口 |
| **合并位** | 无独占目录；管构建文件、测试金标、索引页等公共文件 | 合并、CI、闸门、违例清单记账、修复的分流 | — |

车道数可在 6–8 之间伸缩：开工初期变换、重写依赖接口，可以先并成一条；接口定下后再拆开。

## 3. 怎样互不冲突

1. **目录独占**：每条车道只改自己的目录。需要改别人的接口时，向那条车道提"接口请求"（审查页上一行），由它改、它合；不越界改别人的文件。
2. **接口先合、实现后跟**：跨车道的东西一律先合接口；接口一旦合入，只能加、不能改，要改就再提一次接口请求，由接口所在车道同时迁移它目录里的使用者。
3. **公共文件只归合并位**：构建文件、测试金标（如 `ast_hashes`）、文档索引、问题页索引是冲突热点。车道不手改它们，合并位在合并时统一重生成；能改成自动生成的，就改成自动生成（例如模块清单从各模块的声明里收集）。
4. **分支要短**：每条车道每天至少合入一次；分支落后 develop 超过约定笔数时，合并它是合并位的最高优先级（沿用负责人的规则）。
5. **测试按目录归属**：每块的测试计划跟着它的目录走，谁的目录谁维护；跨块的端到端用例归合并位。

## 4. 效率怎样最大化

- **关键路径只有一条**：图的接口 → 图的实现。其余车道在接口合入之后都能并行；所以阶段 2 的两份接口要最先、最认真地定。
- **不依赖关键路径的工作马上开**：阶段 0 的三处依赖反转、CI、差分工具；算子记录与 C 接口；前端的名字解析与类型检查拆分（主要在 `compile/` 内部）；执行车道的值表示分析。
- **每条车道内部用子代理并行**，按子目录分；车道之间靠目录独占隔开。
- **验收靠差分，不靠人工比读**：每一步用差分对照工具在同一批程序上比输出与规范图，读数自动出。

## 5. 特性与修复在重构期间怎么做

- **新特性冻结**（负责人已定）。CC 主案例等记在路线图"重构之后的新特性"里。
- **修复按位置分流**：
  - 不在当前重构范围里的代码：照常修，按普通合并流程。
  - 在当前重构范围里的代码：交给那块的车道，在新设计上修；旧代码只在缺陷影响用户可见的结果（错误结果、崩溃）时才修，并且只做最小修复。
- **CI 闸门**：阶段 0 起，每次合并 CI 四条腿不得出现新的红。

## 6. 负责人的决定（2026-11-22）

1. **迁移期间新旧访问方式可以在主线上短暂并存**；旧方式随迁移逐块减少，最后一个使用者迁走的那次合并里删除。重构期间不关注代码量，以效率为先。
2. **搬家窗口暂停所有车道**，选在各车道手上都没有大分支时做。
3. **修复按第 5 节分流**。
4. **施工计划的审批**：只落实已定设计的施工计划，决策者写完即派工、通知负责人；有新的原则取舍或推翻既有裁定的，先请负责人定。
