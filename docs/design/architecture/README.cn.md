# Camel 实现的目标架构

> **草案（2026-11-13）**：决策者起草，待负责人从原则上审定。审定之前，施工不以本文为依据。

设计原则管语言的语义，图原生设计稿（`docs/design/graph-native-optimizer/README.cn.md`）管优化器用什么写、内核留什么。本文管实现本身：系统怎么分层，哪几样东西只能有一份，内核的边界怎样在代码里守住。

起因是负责人 2026-11-13 的担心：代码两个月从 9 万行涨到 35 万行，增速过快会毁掉架构。审计报告（`docs/handover/reports/2026-11-13-architecture-audit.cn.md`）列的是症状；本文找的是症状背后的设计缺口，并给出目标形态与迁移路线。

## 1. 现状的判断

**做对了的，保留：**
- **图模型基本统一。** 存储只有一种：`GCGraph`，编码后不可变，按版本共享存储块；`Program` 把 `GraphId` 映到当前版本。可编辑的形式只有一种：`GraphDraft`。事务（`GraphTransaction`）只是持有草稿的句柄；遍级的会话（`RuntimeGraphDraftSession`）按需解码、提交时只重编码改过的图并校验。多写法（`writings`）是记在图里的等价日志，不是另一套图。旧的 `Graph`/`Node` 层已删，只剩约 30 行兼容壳。
- **事实存储已经有了。** 事实挂在（图，节点）上，带版本戳，分"图内容""派生""目标"三类，读时检查是否过期；效应、资源、形状等已是核心事实种类。
- **执行"线性化一次、按序重放"**：`ExecPlan` 按图版本缓存，nodevm、fastvm、jit 都从它取顺序。

**缺口在"图的含义"。** 图是一份，它的含义却被多处各自推导：

1. **执行语义各推一遍。** nodevm、fastvm（两个分派循环）、jit、taskflow、宏求值器各自解释 `Func`、`Brch`、`Gate`、`Loop` 等节点；taskflow 还自己推导"要等谁"，漏掉了顺序边。边的种类在 5 个文件里各列一遍；尾调用有三份判定；类型转换、复制这类节点的执行逻辑有 6–7 份。
2. **效应与可能出故障各算一遍。** 建图器在草稿上自己走一遍资源（`builder_resources.cpp`，注释自称"与 `runtime/resources.cpp` 做同样的事"）；图级的效应摘要（`effects.cpp`）与节点级的"可能出故障"（`graph.cpp` 的 `nodeMayFault`）规则不同，对同一个节点可以给出不同答案；还有第三种"是不是语句"的判定。遍驱动的效应判断（`pass.cpp` 的 `nodeHasEffect`）注释写明是从 tiles 抄来的，同一个表达式在 tiles 里另有三处；源码打印器有自己的效应不动点。
3. **算子没有一份完整的定义。** 核心有 `OperatorTable`，但一个算子的含义仍分散在各处。以整数除法 `:op/div_l` 为例：签名在 `prelude.cml` 与 `globals.cpp` 各写一遍；是否纯靠 C++ 里按名字前缀的规则；故障在 `kNeverFaults` 与 `builtin_semantics.cpp` 各说一遍；运算本身在执行器、fastvm 两个分派循环、x64 JIT、C++ 代码生成、验证翻译、ONNX 降级里各实现一遍。求导规则有 C++ 规则表与 `rulesets/*.cml` 两份，还专门写了脚本比对。编译器按算子名字做特例，是因为算子身上没有可查的属性。
4. **派生数据四套缓存。** 事实存储、`GCUseIndex`、`ExecPlan`、资源足迹缓存，各有各的失效方式。
5. **内核边界不在代码里。** 图原生设计稿定了内核包括什么，但 `include/camel` 4.9 万行头文件全部公开，模块直接引用 `src` 内部，层次有环（核心层引用编译器与执行器）。新功能默认写成 C++，没有任何东西挡着。
6. **建图器一次做完所有决定。** GIR 建图器是一个约 86 个成员的类，分在 25 个文件里，名字解析、类型推断、重载、泛型实例化、静态展开、效应测量、诊断同时进行。同一条诊断在 GCT 与 GIR 两层各查一遍的有 21 个。

根子是：系统的结构从没被整体设计过，八路施工各自就近实现。

## 2. 四个"唯一"

目标架构的核心是四条不变式。每条都说明它是什么、谁拥有它、谁只能读它。

### 2.1 唯一的图

- `GCGraph` 加 `GraphDraft`，现状已基本做到，保持。
- 派生数据只在两处：**事实存储**（分析的结果），以及**执行计划**（2.2 的缓存）。`GCUseIndex` 与资源足迹缓存并入事实存储，用同一套版本戳失效。
- 字节码、JIT 的 MIR、taskflow 的调度结构都是执行计划之后的降级产物，用完即弃，不承载语义。
- 删掉兼容壳，并更新 `docs/technical` 01、04、05 里已过时的描述（仍写着 `Graph`/`Node`）。

### 2.2 唯一的执行语义

- **语义层**（在 `runtime`）：给定一张图，算出它的执行关系。这是图上的纯函数，结果作为执行计划按图版本缓存：
  - 哪些节点被用到（数据边、同步边、区域对外部访问的使用，原则 3.1）；
  - 每个节点执行前要等哪些前驱（数据、`with`、同步、顺序），这是全仓库唯一列举边种类的地方；
  - 区域结构（臂的入口与汇合、循环的条件与体）；
  - 尾调用；
  - 故障沿依赖传播的路径（原则 3.9）。
- **共用的节点语义**（在 `execute`）：类型转换、复制、填充、存取这类节点的求值，`map`/`filter`/`reduce`/`foreach` 的语义（元素次序、结果组装、故障选择、纯度要求），调用帧的绑定，都只写一份。
- **后端只负责怎么跑**：nodevm 逐个执行，fastvm 与 jit 编成字节码与机器码，taskflow 并发调度。它们读执行关系，不另行推导。
- **nodevm 是参考实现。** 其他后端对它做差分测试：同一组用例，输出与外部访问的先后必须一致。
- 宏求值器（`std::macro`）也是一个后端，用同一套。

### 2.3 唯一的事实

- 效应、资源（带读写方式）、可能出故障、可自由安排、"是不是语句"，只在事实层用**一套规则**算出：节点级的判定与图级的摘要是同一条规则在不同粒度上的结果。
- **建图器也用它**：建图时在草稿上调用同一套分析（`graph_read.h` 已经提供了草稿与冻结图的统一读接口），不再自己走一遍。
- 遍驱动的边界检查、源码打印器、tiles、规则引擎都只读事实，不再自己组合 `isPure || hasExternalEffect`。
- **类型**：类型推断留在前端，泛型与重载在建图时就需要类型，不改成图上的分析。但"一个值能不能放到一个位置"的兼容判断只有一个函数，建图器与提交时的校验（`graph_edges.cpp` 现有的 `compatible`）共用。

### 2.4 唯一的算子定义

- `OperatorTable` 的记录扩成**完整的算子定义**：
  - 签名：以 Camel 声明为准；Camel 写不出的类型规则用 C++ 解析器，作为定义的一部分登记；
  - 效应与资源，带读写方式（原则 3.3）；
  - 故障：会在什么情况下出什么故障；
  - 属性：原地追加、切片类、区间类等，取代编译器里按名字的特例；
  - 规则：求导、转置、批处理规则按定义的标识关联到 `rulesets`；
  - 代价，供提取与调度使用。
- **纯度与故障只在定义里声明一次。** 按名字前缀推断纯度的 C++ 规则删掉，`kNeverFaults` 与 `builtin_semantics` 合成一份。
- **实现挂在定义上**：执行器内核、字节码指令、JIT、C++ 代码生成、ONNX 降级、tiles 降级都按定义的标识登记，只提供实现，不另定语义。故障行为由定义给出，各实现照着做，由一致性测试逐个比对（例如除零在每个后端都按定义报同一个故障）。
- 求导规则只留 `rulesets` 一份。C++ 规则表随引擎在对齐后一起删除（见第 5 节）。

## 3. 分层与内核接口

**层次**（只许上层引用下层）：

| 层 | 内容 |
|---|---|
| `utils` | 与语言无关的工具 |
| `core` | 值、类型、内存、算子定义（2.4） |
| `graph` | 图存储与草稿、事务与提交校验、事实（2.3）、执行语义（2.2）；现在的 `src/runtime` |
| `frontend` | 解析、GCT、GIR 建图器 |
| `execute` | 驱动：`Context`、模块加载（现在的 `core/context`、`core/module/userdef`）、遍的执行、共用的节点语义 |
| `backends` | nodevm、fastvm、jit、taskflow、宏求值器 |
| `passes` | 留在 C++ 的内核遍；测试遍是单独的库，不进 `libcamel` |
| `modules`、`tools` | 只经内核接口访问下层 |

**内核接口**：一组小而稳定的头文件（目录如 `include/camel/kernel/`），覆盖图原生设计稿第 3 节的五项：存储与提交、引擎、通用图算子、查询与编辑、执行后端的登记。模块与 Camel 标准库只能经它访问内核。

**守住的办法**：
- CI 的引用检查：允许的层间引用列成表，越界直接红；
- 遍、算子实现、后端都经登记表接入，`pass.cpp` 这类驱动不再逐个引用具体实现。

## 4. 前端

- **GCT 定名字与写出的类型**，**GIR 建图器建节点、推断类型**。名字的优先级规则只有一份，两层共用。
- `gir::Builder` 拆成有接口的部件：泛型与实例化、静态展开、类型推断与重载、诊断；效应与资源不再在建图器里算（2.3）。
- **每条诊断有唯一的归属层**；21 个两层都报的逐个定下归属，删掉另一层的。
- `visitFuncData`（1412 行）这类巨型函数先拆，再谈搬家。

## 5. 迁移路线

收敛阶段（`docs/handover/batches-2026-10-31-72h.cn.md` 第十节）按下面五条路线组织；审计报告里的条目是这些路线上的步骤。

| 路线 | 第一步 | 完成的标志 |
|---|---|---|
| 一、执行语义（2.2） | 抽出"执行前的前驱"共用函数，taskflow 改用它（顺带修掉漏顺序边） | 只有语义层列举边的种类；四个后端与宏求值器不再各自解释节点；差分测试为绿 |
| 二、事实（2.3） | **R3 作为样板**：读写分开的效应与资源写成唯一的分析，建图器与提交共用 | 仓库里 `isPure(...) \|\| hasExternalEffect(...)` 只出现在事实层；节点级与图级判定同源 |
| 三、算子定义（2.4） | R3 顺带在定义里加上读写方式；再把纯度与故障的声明合成一份 | 编译器里没有按算子名字的特例；每个后端对每个算子的故障行为通过一致性测试 |
| 四、分层与内核接口（3） | 引用检查进 CI（先只报告），`Context` 与模块加载上移，测试遍移出 `libcamel` | 引用检查为绿且是硬门槛；模块只引内核接口 |
| 五、两套实现的删除 | 冻结求导引擎；补齐 Camel 版 `fold`/`cse`/`dce` 的原语 | 求导、优化各只剩一套 |

前端的拆分（第 4 节）随路线二、三进行：效应从建图器移出、名字特例改成属性，都是在给 `gir::Builder` 减负。

## 6. 不做的事

- 不把类型推断改成图上的分析（理由见 2.3）。
- 不把两个字节码分派循环（`casevm`、`gotovm`）硬合成一个；它们为不同编译器而设，共用的是指令体，用宏共享。
- 暂不拆仓库：`tiles`、`onnx`、`ckpt` 改成可选构建目标即可。
- 不重写解析器。

## 7. 守护

| 不变式 | 机械检查 |
|---|---|
| 只有语义层列举边的种类 | 检查脚本：`orderPredsOf`、`syncPredsOf` 等只许在语义层的文件里出现 |
| 效应只经事实层判定 | 检查脚本：`isPure`/`hasExternalEffect` 的组合只许在事实层 |
| 算子语义只在定义里 | 检查脚本：算子 URI 的字面量只许出现在定义与实现登记表里 |
| 层次 | 引用检查 |
| 一件事一套实现 | 每周架构审查 |

这些检查与审计报告第三节的七条规矩一起，在每次合并时执行。
