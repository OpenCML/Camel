# Camel 实现的核心抽象

本稿回答一件事：**Camel 的实现应当由哪几个抽象组成，每个抽象管什么、对外承诺什么**。目标架构 `README.cn.md` 定了"四个唯一"与五条路线；本稿往下一层，把每个"唯一"落到具体的概念、不变式与接口上，并补上那份文档没有覆盖的三块：图的表示本身、重写引擎、类型系统对变换的表达力。判断标准是抽象是否贴合语言模型（`docs/design-principles.cn.md`），不是代码行数；行数与大文件只是把问题照出来的信号。

## 0. 为什么要重新定抽象

五份按领域的现状调查（2026-11-21）指向同一个根子：**语言模型里的概念在实现里没有对应的抽象，于是每个消费者各自从图的形状里把含义推一遍**。具体表现为四种模式，它们互相放大：

1. **含义靠约定，不靠结构。** GATE 的值是"第一个 Norm 输入"，CALL 的被调者是"With 的第 0 个"，BRCH 与 JOIN 靠负载里的编号配对，LOOP 的输入按位置分段。每个读者都要记住这些约定，于是 37 个文件各写一个按节点种类的 `switch`，种类名到字符串的表抄了 12 份。
2. **能推出的事实被存下来。** 被调者写了哪些捕获存在名叫 `reserved` 的字段里，切向实参的位置存在节点的 `tangentArgs` 上，"这张图是 `jvp` 造的"存在 `liftedFrom` 上，"门已消解"是图上的标志。设计原则 2.3 说"能从图的内容推出来就不存""变换的结果不取决于它从哪来"；这些存法逐条违反它，而且每多一份就多一处要同步。
3. **类型说不出变换需要的东西。** 切向类型说不出形状，于是加了 11 个 `*_stated` 算子、每个配 C++ 核与两套规则；类型说不出"这是提升出来的"与"这是线性的"，于是有 `liftedFrom`、`asLift` 旗标与运行时拒绝；二阶导在这里撞了六次墙。
4. **同一件事有多个实现，各自缓存。** "一个节点访问什么"至少四个读者，"未知访问"八种表示；执行语义在五个后端各解释一遍，`map` 一类高阶算子实现了五次；四套重写机制各自匹配；十一种版本戳、五套派生缓存，各有各的失效方式。

由此带来两类后果：代码量随"概念数 × 消费者数"增长，而不是随概念数增长；性能上，凡是不知道自己依赖什么的派生数据，只能整张图、整个闭包地重算（提交时改一张叶子图会一路重编码到根，每读一次事实就把可达闭包遍历一遍，顺序检查的核心是平方级）。

下面按八个抽象给出目标。每节先说它管什么，再说不变式，最后说它取代现在的哪些做法。

## 1. 图：语言层的数据模型

**管什么**：程序的唯一表示。设计原则 2.3 说它是"最重要的一项设计"，模块缓存、用 Camel 写的遍、GPU 编译、`std::cpp` 都建在它上面。

**节点**：按 `docs/design/graph-model/README.cn.md` 3.4.1（2026-10-24 定）收为九种：`DATA`、`PORT`（值）；`OPER`、`FUNC`、`CALL`、`BIND`（计算）；`BRCH`、`LOOP`（结构）；`GATE`（排序）。`CAST`、`FILL`、`ACCS` 成为构造、转换、访问算子，`JOIN` 并入 `BRCH`。这条决定已经做了，没有施工；设计原则 2.2 的十三种清单随之改写。

**结构节点拥有区域**：`BRCH` 与 `LOOP` 是"拥有若干区域的节点"（RVSDG 的 γ 与 θ）：`BRCH` 的每条臂是它拥有的一个区域，节点的值就是选中那条臂的结果；`LOOP` 拥有条件区域与循环体区域，状态经区域的入口与出口端口传递。区域只有一种形态：一条臂若只是调用另一张图，它就是一个只含一个 `FUNC` 的区域，不再有"子图形态"与"区域形态"两种臂。由此 `BRCH`/`JOIN` 的负载配对、`Arm` 区域的 `callSite`、"每个消费者处理两种臂"一并消失。

**边只有三种**：数据、同步、顺序（原则 3.1），加上"节点属于哪个区域"这一层归属关系。旧的控制边删除；`GATE` 的值是它唯一的数据输入，它要等的东西是同步边——不再有"第一个输入是值"的位置约定。

**端口有名字，不靠位置**：每种节点的输入按**端口组**声明（`CALL`：被调者、实参、上下文实参；`LOOP`：初值、状态结果；`FILL` 并入 `OPER` 后由算子签名给出），声明写在节点种类表里一处，读者按组名取，不按下标算。

**不存能推出的东西**：写掩码、切向位置、提升来历、门消解标志都从图里拿掉。它们要么能从图的内容或类型推出（推出它的函数放在第 4 节的事实层，结果缓存），要么是类型该表达的（第 5 节），要么本来就是某个遍内部的工作状态（留在那个遍里，不进图）。

**取代的做法**：37 处按种类的 `switch` 收成"节点种类表 + 端口组访问器"；按位置定义的约定全部改成端口组；第 2.3 条违例的字段逐个去掉。

## 2. 图的存储、版本与编辑

**管什么**：图作为值的存放、共享与修改。语言要求图是值，所以修改不是就地改，而是得到一个新版本。

**一个读接口**：冻结的图与正在编辑的图对外是同一个只读视图（暂称 `GraphView`）。每个谓词——活节点、可能出故障、链位、分支的汇合、聚合的元数——只对视图写一份。今天成对各写一份的约十对谓词、前端另有的 `GraphRead`、模板读者都收进它。

**编辑是对基版本的增量**：草稿 = 基版本 + 一份编辑记录（新节点、改动、删除）。读草稿时，没改过的部分直接读基版本，不先整张解码；提交只编码改过的部分，块按内容共享。今天"先解码成每节点一次堆分配的草稿、提交时整张重编码三四遍"的形状由此消失。

**编辑记录说清自己做了什么**：每次编辑留下它的种类（`replace`、`erase`、`inline`、`order`……）与它碰过的区域。提交检查按 `docs/design/graph-editing/README.cn.md` 8.1 的表，只查这些编辑种类可能破坏的项、只在碰过的区域里查。今天提交从结果反推"新造了哪些节点"、先建整图访问表再问要不要查，都不再需要。

**图与程序都是不可变的值**：没有可变变量，也就没有可变的图。修改一张图得到一张新图，旧图原样有效；草稿只是"正在搭的新值"，放弃它不留任何东西。程序是"顶层名字 → 图"的一张表，它也是值：一个遍改了 `f`，得到的是一张把 `f` 绑到新图的新表。这是设计原则 3.5"可变的是名字的绑定，不是值"在程序层的对应。

**两种引用**，与普通语言里"全局名字"和"值"的区分相同：
- **按名字**：只用于模块里声明的顶层函数及其泛型实例。名字由"模块 + 限定名 + 类型实参"推出，确定且稳定。换掉 `f` 只换表里一项，调用者一字不变，叶子改动不再一路波及到根。一张图里调用 `f` 调到哪一个，由它所在的程序决定。
- **按值**：其余一切——lambda、变换的产物、运行时造出来的图。持有者直接持有那张图，像持有一个数组一样；没人持有时由 GC 回收。运行时反复造出的图就是普通的值，不进名字表。

**图参与 GC，但不移动**：名字表与运行中的值是根，够不到的图被回收；按指针记账的图管理器由可达性追踪取代。图放在一块专用空间里，标记清除、不压缩：地址一经分配就有效到回收为止，字节码、JIT 代码、C++ 导出里写的直接地址因此不必修补，调用也不经句柄表（HotSpot 的代码缓存与类元数据是同样的做法）。普通的值（张量、元组、闭包对象）照旧在会移动的分代堆里；闭包对象搬家时它指向图的地址不变。从图出发的引用不指向会搬家的对象：图里的大常量放进不移动的老年代或随图存进图空间。一张图回收时，它的执行计划、字节码与 JIT 代码作为它的派生事实一并释放。碎片真成问题时，在安全点整理一次并重新链接，像 JIT 清理代码缓存那样，频率很低。

**`GraphId` 不再是核心概念**：进程内的身份就是值本身；调试器要的"这是哪段代码"由名字路径（"`m::train` 里第 2 个 lambda"、"`jvp` 作用在 `loss` 上"）与源码位置给出。

**调用解析在链接时做一次，热路径上是直接地址**：名字到图的解析结果放在执行计划里（它是程序版本上的一个事实，第 4 节）；FastVM 的字节码、JIT 的代码、C++ 导出的符号里写的都是解析好的直接目标，调用时不查表。执行期间名字不会改绑（改绑只发生在遍里），所以这些地址在一次执行内是静态的；遍换了某个名字的绑定，只有引用了它的执行计划与编译产物失效、重新链接，像动态链接器的重定位。按值引用的图本来就是指针。

**派生数据按依赖失效**：事实（第 4 节）记下自己读过哪些名字在当前程序里绑的哪个版本；换了绑定，只有读过它的失效。进程内的缓存以值本身为键；跨运行的缓存（以后的模块缓存）按内容算指纹，图的指纹只算它自己的内容，引用以名字出现。今天十一种互相独立的计数与戳收成这一套。

**没有单独的"程序"层**（负责人 2026-11-18："程序就是普通的函数，或者说就是 main"）：上面说的名字表不是另一层，它是函数值的一部分。一个函数值 = 它的图 + 捕获的值 + 一张"它按名字引用的那些名字各绑到哪张图"的环境表；环境表在函数值之间结构共享，通常一个模块就是同一张。`edit d = f` 改了 `f` 可达的顶层函数 `g`，交出的 `d` 带着把 `g` 绑到 `g′` 的新表；块外持有 `f` 的人手里仍是旧表。遍就是把 `main` 这个函数值变成另一个函数值。

**编辑接口的四层**：
1. **提交后的图**：上面说的紧凑、不可变、按块共享的表示。**节点编号在同一条版本线上稳定**：没改过的节点保持原编号，新节点往后追加，删掉的留墓碑；墓碑多了就压缩，压缩算一个新版本、附新旧编号的对照表。事实里"第几号节点"的结果因此跨版本有效。
2. **编辑会话**：会话内可变、发布时冻结（Clojure 的"瞬态"）。会话 = 基版本 + 覆盖层，读时先看覆盖层、没有就读基版本，不先整张解码；使用关系、区域归属等索引是"基版本的索引 + 覆盖层的补丁"，用到才算。保存点与撤销沿用图编辑设计稿 16.4 的撤销日志；饱和的临时区放在会话旁边（第 7 节）。
3. **写入口与监听**：写会话有两层入口。高层是编辑算子（`replace`、`erase`、`eval`、`inline`、`outline`、`order`、`add_param`），给 Camel 代码与需要分档检查的地方用；底层是内核的图原语（改输入、加节点、删节点、加边），给 C++ 遍用——C++ 存在的意义就是能用更底层的 API。**记录由原语层自己做**：每个原语执行时通知监听者"哪些节点脏了、碰了哪些区域"，并把这次编辑记为"底层编辑"；高层算子记为自己的种类。监听者有三类：重写引擎的工作队列、会话内的事实、提交检查。因为记录在最底层，谁改图都绕不过它。
4. **发布**：按编辑记录做分档检查——高层算子按图编辑设计稿 8.1 只查它们会破坏的项，底层编辑碰过的区域做全部检查，都只在碰过的区域及其祖先里做；然后冻结覆盖层，只为碰过的块造新块；被改的图若按名字引用就换环境表里的一项，若按值被持有就沿持有链往上造新值，到按名字引用的那层或被编辑的函数值本身为止，路径外全部共享。

**事实可以读草稿**（负责人 2026-11-21）：会话里的事实读的是改过的样子；已提交版本上的结果长期复用，草稿上的结果随会话结束丢掉。

**可参照的成熟做法**（不靠工程上的细致来保证正确）：
- 不可变表示与便宜的编辑：Roslyn 的红绿树——不可变、可共享的"绿"节点加按需生成的导航层，一次编辑只新造改动点到根的一条路径；正确性由"绿节点不可变"在结构上保证。
- 编辑记录与工作队列：MLIR 的改写器经统一接口改图、每次改动通知监听者。
- 按依赖的增量重算：Salsa（Rust 编译器、rust-analyzer）的查询依赖记录、红绿重验与提前截止。
- 增量饱和：egglog 的半朴素求值、Cranelift 的无环等价图（第 7 节）。
- 反面经验：V8 正在从可变的"节点之海"迁出（Turboshaft），规模大了以后难以维护与推理。

**取代的做法**：两套谓词、全量解码与全量重编码、调用者的传递重编码、提交时的反推、按地址作键的旁表、程序内按计数分配的 `GraphId`、按指针记账的图管理器。

## 3. 算子定义

**管什么**：一个算子的全部含义。语言里"算子"是一个概念，实现里就应当是一条记录。

**一条记录，一处声明**：签名、纯度与读写方式、故障、数值语义、索引语义、可微性与求导规则、线性、在各目标上的实现，都挂在同一条算子记录上，按算子编号（不按 URI 字符串）索引。签名用 Camel 写一次（今天 `prelude.cml` 与 `globals.cpp` 各写一遍）；属性用标签写在声明上；内核与各后端的实现按编号登记到这条记录的"实现"一栏。

**完整性可查**：一条检查枚举全部算子 × 全部方面（每个后端有没有实现、有没有求导规则、故障是否声明），缺了就说缺了，不靠"后端碰到再说"。今天整数除法的含义分散在 13 处，`div_f6` 在 FastVM、JIT、ONNX、验证里都没有条目而无人知道。

**建图期求值用同一套内核**：常量折叠、`when` 条件、静态循环界都调算子记录上的内核，不另写算术（今天 `compile/literal.cpp` 与 GCT 解释器按名字各算一遍）。

**取代的做法**：约 15 个分散的 `declare*` 入口、按字符串查找的内核表、各后端按名字建的表、张量 `OpDef` 与按名字另建的语义表并存、编译器里按算子名字的特例。

## 4. 事实：从图推出的一切

**管什么**：所有"从图的内容推出来的东西"——效应与资源足迹、可能出故障、是不是语句、形状、可达性、规范形、执行计划。原则 9.11 说分析写成事实、满足合并律与单调性。

**一个框架**：一个事实是一个声明过的函数，输入是图（经第 2 节的视图），输出是值；框架按（事实种类、`GraphId`、内容版本）缓存结果，并记录它读过哪些别的图与别的事实。读者——建图器、提交、遍、后端——一律经框架查询，不自己算，也不绕过缓存。今天每读一次事实都要遍历整个可达闭包算一个哈希，改成查依赖记录。

**效应只有一个读者**：节点的足迹 = 算子记录上声明的访问 ∪ 函数实参类型里的效应，这一条规则只写一次。建图器在草稿上、提交在新版本上、遍在任意时刻，用的都是它。"未知访问"只有一种表示：资源格里每一类资源的顶元。

**执行计划也是事实**：`ExecPlan`（执行顺序、臂入口、尾调用、存储复用）是图的一个派生事实，和其他事实一样按版本缓存，不再是挂在图上的特殊结构。

**取代的做法**：四个效应读者与八种"未知"、33 处绕过事实层的纯度判断、五套各自失效的缓存（使用索引、执行计划、事实存储、足迹缓存、规范形缓存）。

## 5. 类型：把变换需要的性质说出来

**管什么**：值的形状与函数的承诺。原则 2.3 的第三问是"是不是类型"；变换今天撞的墙，几乎都是类型说不出它需要的东西，于是在图上另存。

**函数类型说出三件事**：
- **线性**：只有求导这个库用得到，不进类型系统。求导库定义一个标签 `#linear`（与注册 `#jvp`、`#transpose` 规则同一套标签机制），`split` 交出的那一半带着它，`transpose` 检查它；用户自己实现线性算子时同样贴这个标签。
- **提升**：`jvp(f)` 的类型是 `Lift<F>`，由求导库用语言已有的**命名类型**（原则 5.2）定义，不是类型系统的新构造；它，与结构相同的普通函数类型不相等。今天"两参数的反向半与提升后的参数表类型相同"，所以只能靠图上的 `liftedFrom` 区分；类型能区分了，那份记录与 `asLift` 旗标就不需要。
- **残差**：仍是闭包的捕获（2026-11-18 定），类型里不写残差表；线性函数的类型只描述它对切向的签名。

**切向带形状**：形状是值的属性，不是算子的变体。前向求导需要把原值的形状交给反向时，由变换框架（第 6 节）把"操作数的形状"作为一种标准残差带过去，规则里写 `shape(x)` 就读得到；不再为每个会广播的算子造一个带形状的孪生算子。

**类型函数用 Camel 写**：`Tangent`、`ParamsOf`、`ResultOf` 等今天在 C++ 里按名字分派、只认名叫 `types` 的模块；按原则"只有一门语言"，它们写成编译期运行的 Camel 函数，C++ 只提供读类型结构的原语。

**函数类型有唯一的主人**：类型检查阶段（第 8 节）算出一个函数完整的类型后才建图；建图器不再在十个文件里就地改"开放类型"的出口与资源。

**取代的做法**：`*_stated` 算子族及其两套规则、`tangentArgs`、`liftedFrom`、`asLift`、运行时的"不能求导"拒绝、C++ 的类型函数分派。

## 6. 变换框架

**管什么**：`jvp`、`split`、`transpose`、`vmap` 以及以后的变换共同的部分。原则 1 说求导、批处理写成库里的组合，局部写成规则。

**一个走图骨架，各变换只写自己的那部分**：骨架负责按依赖顺序走图、递归进区域（分支、循环）、重映射端口与 `with` 参数、处理闭包与捕获、缓存被调者的变换结果；一个变换只提供"一个算子节点怎样变"（来自规则集）和少数结构节点上它自己的决定。今天三个变换各写一整套节点分支、各写一遍端口与捕获的重映射、各有一套键不同的被调者缓存，`transpose` 还要先试建一遍；这些都收进骨架。

**闭包的提升只定义一次**：提升一个函数值时，函数体里造出来的闭包，其捕获连同本层的切向一起提升；被变换函数自己的捕获来自外面，切向为零（原则 9.9）。区分看闭包在哪里造，由骨架统一处理（`docs/design/program-transforms/nested-transforms.cn.md` 2.4）。二阶导连撞六次墙的根子就是这个概念没被定义；定义在骨架里，各变换就不必各自再撞一次。

**被调者缓存是事实**：（变换、源图身份、版本、变体）→ 变换后的图，按第 4 节的规则缓存与失效，跨调用复用。

**规则语言补齐**：规则集里今天的绕法——右边不能写 `<>`、参数不能是并类型、模块之间不能共享私有函数（于是同一个助手抄三份）、没有秩多态（于是同一条法则按秩各写一遍）——都是语言表达力的缺口。按原则 1"语言暂时表达不了的，优先考虑拓宽语言"，逐项补进规则语言，补上后删掉对应的绕法。

**取代的做法**：三套节点分支、三套重映射、三套缓存、按节点编号顺序的遍历、规则集里的重复助手与按秩重复。

## 7. 重写与图编辑

**管什么**：一切"把图改成另一张图"的机制：规则改写、饱和与提取、Camel 写的遍、`edit`/`view` 块与动作规则。原则 9.12 说图操作只有三种写法：规则、`view`、`edit`。

**一个重写核心**：
- **匹配**：规则编译成模式，按根算子编号索引；匹配从一份"脏节点"工作队列出发，只看被改动波及的节点，不每轮扫全图。
- **应用**：一律经第 2 节的编辑接口，编辑记录自动说出种类与碰过的区域；已证明的规则改写属于"不新增访问"的编辑，提交时不再查效应与顺序（8.1 的"已证明规则 → 不查"一行）。
- **饱和**：等价类上的增量匹配（只对新加入的节点找匹配），预算用完交回已达到的状态而不报错（设计稿第 3 节与决定 16）；提取的代价按共享计（同一个值被多处读只算一次），不按树计。
- **条件里的事实**经第 4 节的框架查询并缓存，不在每次匹配时把依赖锥重走一遍。

**提交检查与编辑同源**：检查只在碰过的区域里做；顺序检查用区域内预先算好的可达关系，不在内层循环里为每一对节点跑一次带分配的广度优先搜索。

**两套优化遍并存的位置不变**：C++ 版留在 `std::cxx::` 下（负责人 2026-11-18），与 Camel 原生版做对比实验后再定；但两者都经同一个编辑接口与提交，旧的 `Txn` 接口由 `edit`/`view` 块取代。

**取代的做法**：四套各自匹配的机制、每轮重扫与每次调用重编译规则、规则实例按类型组合膨胀、饱和的每轮重找、事实条件的重复求值、整图的提交检查与平方级的顺序检查。

## 8. 前端：阶段各管一件事

**管什么**：从源码到图。今天 GIR 建图器在一个阶段里同时做名字解析、类型推断、重载选择、泛型实例化、静态展开、捕获分析、`var` 降低与效应测量，一个类约 160 个数据成员。

**阶段与它唯一的决定**：
1. 解析：源码 → 语法树。
2. 名字解析：名字 → 声明。优先级规则只写一次（今天 GCT 与 GIR 各写一遍）。
3. 类型检查：推断、重载、泛型实例化、静态展开，产出类型完整的树；函数类型在这里定下来（第 5 节）。重载选择只有一个解析器（今天四处）。
4. 建图：类型完整的树 → 图。这一步只做机械的翻译，不做决定；`var` 只有一种降低（直接 SSA，原则 3.5"`var` 是写法"），单元只服务 `Ref`。
5. 全程序分析：效应、捕获、线性这类跨函数的性质，经第 4 节的事实框架，用工作队列而不是按轮重扫。

**一条诊断只在一个阶段报**：今天 23 条诊断在 GCT 与 GIR 两层各查一遍；按阶段的职责归属后，各留一处。

**一个建图期求值器**：宏阶段、`when` 条件、常量折叠都用同一个求值器（执行语义与节点 VM 相同，内核来自第 3 节的算子记录）；GCT 上的私有解释器删除。

**取代的做法**：单个巨型建图器、三个建图期求值器、两层重复的诊断与降低、三种 `var` 降低、泛型实例的线性查找、每次调用重建的重载集。

## 9. 分层与内核接口

**管什么**：谁能看见谁。原则 1 说 C++ 只保留一个尽量小的图内核。

**仓库布局**（负责人 2026-11-22 同意）：遍就是函数——C++ 写的遍、执行后端、导出器，本质上都是某个模块里能调用原生 API 的 Camel 函数，目录按 Camel 名字组织；编译特指"语法树变成图"，解析单独维护。
- `kernel/`：C++ 图内核，唯一公开的 C++ API（类型、算子记录、图的数据模型与存储、编辑会话与原语、事实框架、重写核心、值与 GC）。`include/` 只留它的公开头文件，其余头文件放在各自源文件旁边。
- `parse/`：源码 → 语法树。`compile/`：语法树 → 图。
- `lib/<模块>/`：每个 Camel 模块一处，`.cml` 声明与 C++ 实现放在一起（今天的 `stdlib/` 与 `modules/` 并成这一处）；`std::nvm` 在 `lib/std/` 下，`onnx::export_model` 在 `lib/onnx/` 下。
- `tools/`：命令行、调试器、语言服务器等独立程序。
- **目录按入口的 Camel 名字，内部按组件的真实结构**：模块里不强求平铺。几个函数共用的部分（执行计划、帧、循环驱动这类执行基础设施被各个执行函数复用）放在该模块内一个共用的子目录；挂在别的组件上的实现（JIT 建在 fvm 上，按架构各有后端）就放在那个组件下面，不为了"按名字"拆散。
- 每一块是一个独立的构建目标，只把下层的头文件放进包含路径：越层引用编译不过。
- **遍只能看图**（负责人 2026-11-22，原则性要求）：把源码里的信息编进图是编译器的职责；之后运行的遍——变换、重写、优化、导出、执行——只从图上取得一切必要信息，不读语法树、不调解析或编译。规则也一样：编译器把规则编成图上的值，重写核心只认这种编译好的规则，不认语法树里的规则头。
- **依赖反转**：内核只按名字调用 Camel 函数，各模块把自己用 C++ 实现的函数登记到内核，调遍的驱动不认识具体的遍；加载源码模块由 `compile/` 实现内核定义的加载接口并登记上去。
- 重构期间冻结新特性，只修缺陷；第一步是一次物理搬家与立构建边界，不改行为。

**层次单向**：工具 → 核心（类型、算子记录）→ 图（第 1、2 节）→ 事实（第 4 节）→ 编辑与重写（第 7 节）→ 前端、变换、遍 → 执行与后端 → 模块。上层只引下层；今天核心与运行时、核心与编译器、执行与遍之间的环全部断开。

**内核接口是一份小而稳定的公开头文件**：图的数据模型与视图、类型、算子记录、事实查询、编辑接口。其余一律私有；模块只能引内核接口与它声明依赖的其他模块的接口，不能引 `src/`，也不靠"模块碰巧引用了什么"来决定导出什么。测试专用的头文件移出公开目录。

**守护是硬门槛**：引用方向、"节点种类只在种类表里列举"、"效应只经事实层"、"算子名字只在定义与登记处出现"四条检查进合并前的快层，不再只报告。

## 10. 贯穿各层的性能原则

1. **代价与改动成正比**：编辑、提交、事实失效、重写匹配，都只碰改动波及的部分。
2. **派生数据按依赖失效**：凡是缓存，都按"身份 + 内容版本 + 依赖记录"作键；不按地址，也不按"整个闭包的哈希"。
3. **热路径上不按节点分配**：读图、匹配、执行的内层循环不为每个节点做堆分配。
4. **全程序的不动点用工作队列**：建图期与分析期的跨函数传播只重算受影响的部分。
5. **检查的开销随编辑种类分档**：接口上不可能违反的，不查；运行时能便宜查的，常查；贵的，放在调试构建与测试里（原则 1"写成必须的规则都要有检查机制，而且开销可控"）。

## 11. 要负责人定的

这几条改的是语言层面的东西或已写定的原则，由负责人定：

1. **线性与提升**（第 5 节）——**负责人 2026-11-22 改定**：都是求导库的概念，不进语言内核。线性用库定义的标签 `#linear`，提升用库定义的命名类型 `Lift<F>`。这是类型系统的扩充：用户写的签名里可以出现 `linear`，`transpose` 只接受它；`Lift<F>` 不等于与它结构相同的普通函数类型。
2. **规则语言的四项扩充**（第 6 节；负责人 2026-11-22：偏上层，由决策者核实后定，规则已能写泛型与 `with` 参数）：右边能写 `<>`、参数能是并类型、规则库之间能共享函数、规则能对秩多态。每一项都是语言能力，不只是实现。
3. **设计原则 2.2 的节点清单**改为图数据模型 3.4.1 的九种，并写明"结构节点拥有区域、臂只有一种形态"。这条 10-24 已定，只是原则文本没跟上；需要负责人确认按这个改写原则。
