# 图操作的三种写法：规则、`view`、`edit`

> **设计稿（2026-11-17，决策者起草）**。负责人提出方向并在 11-17 的讨论中定下第 1 节的出发点；第 13 节记录已定的与待定的。原则文件尚未按本稿修订，施工不按本稿开工，等负责人与论文一侧讨论完再排期。

## 1. 为什么

规则与事实是 Camel 最推荐的改图方式：声明式，定义处就能检查（原则 9.11），应用后一定通过提交。但图原生语言必须让程序有足够的能力读图、改图，规则写不出的变换（按分析结果整段改写、跨函数的遍、插入一段新计算、重组循环）要有出路。

今天的出路是 `stdlib/graph.cml` 的 `graph_of`/`nodes`/`open`/`replace`/`erase`/`eval`/`add_constant`/`commit`/`abort`：图、节点、事务都是普通值，图操作和普通代码混在一起编译成图，检查只在程序主动调用 `commit` 时发生。

负责人的出发点（2026-11-17）：**对图的操作本身没有展开编译成图的必要，应当聚合成运行时的原子操作**。对 `replace`、`erase` 这样的节点求导、批处理、常量折叠都没有意义，把它们作为普通节点摆进图里，只带来"草稿句柄是图里的一个值"之类的边角情况，还会让一个遍去改另一个遍的图。所以图操作只能写在三处有明确边界的地方：

| 写法 | 做什么 | 在外层的图里是什么 |
|---|---|---|
| 规则（由 `rewrite`、`run`、`saturate` 应用） | 声明式改写 | 一个原子操作 |
| `view f as d { … }` | 读图、分析 | 一个原子操作：读 `f` 的图，交出普通值 |
| `edit f as d { … }` | 改图 | 一个原子操作：读 `f` 的图，交出新函数或错误值 |

块外的普通代码照常编译成图；每个块编译成算子表里的一个算子，在外层的图里只是一个普通的算子节点（第 5 节）。

这样也顺带解决了今天接口的三个问题：句柄会逃逸、事务会忘记提交或改到一半、读程序的人看不出哪一段在操作图。

## 2. 语法

```camel
// 改一个函数：块的值是改好的函数，或一个错误值
export func fold_zero_adds::<F>(f: F): F! when is_function::<F>() {
    return edit f as d {
        nodes(d)->filter<is_add_zero>->foreach<(n: Node) => replace(n, inputs(n)[0])>
    }
}

// 加了效应时，块头写出新的函数类型
export func log_result(f: (x: float) => float): ((x: float) => float uses console)! {
    return edit f as d: (x: float) => float uses console {
        let out = exit_of(d)
        let p = inline(out, (y: float) => println(`result = ${y}`), out)
        order(p, out)
    }
}

// 读图：块的值是体的值，类型由体推出
func count_muls::<F>(f: F): int when is_function::<F>() {
    return view f as d { len(nodes(d)->filter<is_mul>) }
}

// 整个程序：从 f 可达的全部图，块尾一次提交，全成或全不成
export func strip_debug_prints::<F>(f: F): F! when is_function::<F>() {
    return edit f as prog {
        graphs(prog)->foreach<(g: Graph) =>
            nodes(g)->filter<is_debug_print>->foreach<(n: Node) => erase(n)>>
    }
}
```

- 两种块都是**表达式**，能出现在任何表达式的位置上；块里最后一个表达式是块的值，`return` 结束的是块本身（与原则 3.4 同步块当值同一规则）。
- `edit f as d { … }` 的值类型是 `F!`（`F` 是 `f` 的类型）。块头的类型**可以省略**，省略时就是原函数的类型，提交按原函数的效应核对；**只有加了效应时才写**，写出的类型就是新的声明，块外的调用者按它算。所以块头有类型，读者就知道这次编辑改变了函数对外的承诺。
- `view f as d { … }` 的值类型由体推出，和普通块一样；块外要写明类型就照常写 `let n: int = view f as d { … }`。
- `edit` 本身是纯的：它不改 `f`，交出一个新函数，`f` 对其他持有者不变（原则 9.1）。体里写了外部访问，整个表达式才有那个效应。单独写成一条语句、值没人用，报"结果没人用"。
- 块可以嵌套，内层块对的是另一个函数值。

## 3. 哪些算子只能在块里调用

**规则：`graph` 模块导出的类型（`Graph`、`Node<T>`、`Region`、`Op`、`TypeRef`、`Tag`……）都是句柄类型；签名里提到句柄类型的函数就是图算子，只能在块里调用。** 不为每个算子单设关键字，也不在声明上另加标记。

为什么类型就够：
1. **句柄只从块头来**。`view f as d`、`edit f as d` 把 `d` 绑定成这个块的根句柄；`graph_of` 这类"从普通值拿到句柄"的函数删除。所以块外不存在任何句柄值，图算子在块外根本拿不到实参，调不了。
2. **一个标记就是第二份真相**。"这个函数是图算子"若既由签名里的句柄类型决定、又由一个关键字或标记决定，两者迟早不一致（原则：同一件事只有一份）。签名已经说了它操作什么，再标一次是重复。
3. **用户写的帮助函数自动归位**。`func is_add_zero(n: Node): bool`、`func first_input(n: Node): Node` 写在块外，签名提到 `Node`，所以只能在块里调用，并随调用它的块一起聚合进那个原子操作（第 5 节），不单独展开成图。不提到句柄的普通函数（`len`、算术）在块里照常调用。

**改图算子只收 `edit` 块的句柄**：句柄的类型带着它所属块的种类（第 4 节的标签），`replace`、`erase`、`inline`、`outline`、`order`、`eval` 要求 `edit` 块的节点；把 `view` 块的节点交给它们是类型不符，报"`replace` 需要 `edit` 块里的节点"。查询算子（`nodes`、`inputs`、`users`、`op`、`type_of`、事实查询……）两种块都收。

关键字只用在**块的边界**上：`view`、`edit` 两个，加上已有的 `rule`。类型检查靠边界判断"这里有没有句柄"，算子是否只能在块里调用由签名推出。

## 4. 句柄出不了块

每个块引入一个不可命名的作用域标签 `β`。句柄类型都带着它：`Graph<β>`、`Node<T, β>`、`Region<β>`……（源码里照旧写 `Node<T>`，标签由编译器补，不写出来）。块外没有 `β` 这个名字，所以：

1. **不能作为块的值交出**：`edit` 块的值的类型是函数类型，`view` 块的值的类型是体的类型，两者在块外都必须良构；提到 `β` 的类型不良构，报错。
2. **不能存到块外**：块外创建的 `Ref<T>`、结构体、数组，`T` 在块外定下，不可能提到 `β`；块内新建的装着句柄的 `Ref` 带着 `β`，同样出不了块。
3. **不能被离开块的闭包带走**：原则 3.3"握着什么，类型就提到什么"本来就要求闭包的类型提到它握着的句柄；握着节点的闭包类型提到 `β`，于是出不了块。在块内造、在块内调用的闭包完全允许。
4. **帮助函数对标签泛型**：签名里的 `Node` 对 `β` 泛型（与原则 3.3"没写资源子句的函数类型对资源泛型、按实例化确定"同一机制），在块里调用时实例化成那个块的标签；返回的句柄仍带这个标签。
5. **普通值可以交出**：`view f as d { show(nodes(d)[0]) }` 交出字符串，`view f as d { len(nodes(d)) }` 交出整数。

**为什么两种块都要关住句柄**：`view` 里的句柄指向已提交、不可变的图，交出去也不会悬空；要关住它，是因为一旦节点流出块，块外就会出现 `inputs(n)` 这样的图算子，它们又得作为普通节点编进图里，聚合就破了。`edit` 里的句柄另有一层理由：草稿在提交或放弃后不存在，指向它的节点会悬空。

这是 `runST` 的作用域思路（每个块一个新鲜、不可命名的类型变量）与 Xhebraj 等人（ECOOP 2022）二等值的效果；用户不写 rank-2 类型或生命周期参数。检查全在类型检查里，零运行时开销。

## 5. 编译之后：每个块是算子表里的一个算子（负责人 2026-11-17）

- **编译完成后没有块节点。** 编译器把每个 `view`/`edit` 块变成算子表里的一个新算子；外层图里它只是一个普通的算子节点，与原生算子没有区别。外层的遍、变换、导出照算子处理，看不到它的内部。
- **参数**：被读或被改的函数值，以及块捕获的外部值（闭包转换）。
- **实现**：运行块体，由同一个编译器编译、同一个虚拟机执行，不另起一套代码生成与执行器。块体（连同它调用的、签名提到句柄的帮助函数）不属于程序的图，任何遍都看不到它，这切断了"遍改遍"的递归。
- **算子允许不终止**（块体里可以有不终止的循环）。
- **命名按规范形式**：生成的算子按块体去掉写法之后的样子（规范形式，例如取其哈希）命名，参数按规范形式中第一次使用的先后排列，不按名字。这样只差写法的两个程序编译出来的图仍然相同（写法精确）；顺带得到一个按规范形式哈希的编译缓存。
- **块体内部照旧**：句柄不逃逸（第 4 节）与块尾提交检查（第 8 节）。
- **规则应用同样是一个算子**：`rewrite`、`run`、`saturate` 的内部就是一个 `edit` 块（匹配处 `inline` 右侧再 `replace`），共用同一份草稿与提交。
- **执行时机不归块管**（负责人 2026-11-17）：`edit`/`view` 只是表达手段，编译期已经变成一个算子，什么时候执行和别的算子一样由它所在的函数决定。要在早期阶段做完，就把调用它的函数标成 `#macro`，在 `std::macro` 阶段执行；不为块另设机制。
- 调试块体不靠 `std::gir` 从外面看，由跟踪选项的一个区域（如 `--trace meta`）给出。

## 6. `edit` 的语义

1. **进入块**：对目标函数值所在的程序开一份草稿，绑定到 `as` 后的名字。目标函数对块外的持有者不变。
2. **块内**：语句照普通语义求值。改图算子是对草稿句柄的写，同一草稿上的写按书写顺序（原则 3.3），不写 `sync`。每一步做能当场做的局部检查（第 8 节）；一步失败，块立即结束，之后的语句不执行。
3. **正常走到块尾**：自动提交，提交做完整检查；通过则块的值是新函数，否则是错误值。
4. **任何失败**（局部检查失败、体里出现未处理的错误值或故障、提交被拒）：放弃整份草稿，程序里不留下改了一半的图，块的值是一个错误值，说明哪一步、为什么。
5. **整程序编辑**：`edit f as prog` 的草稿覆盖从 `f` 可达的全部图（`graphs(prog)`），块尾一次提交，全成或全不成。这与今天提交以程序为单位一致。
6. **确定性**：`nodes`、`graphs` 按规范顺序返回；读写法的查询（图名、创建编号、源码位置）照原则 9.5 要求类型里声明那种能力，两种块都不放宽。

`view` 没有草稿、没有提交，读的是已提交的图，块尾什么也不做。

## 7. 编辑算子

| 算子 | 作用 | 说明 |
|---|---|---|
| `replace(old, new)` | 把读 `old` 的值的地方改为读 `new` | 现有；类型必须相容。只搬数据边，不删任何东西：`old` 若是会写的节点，它到区域出口的同步边还在，照样执行 |
| `erase(n)` | 删一个值没人读的节点 | 现有；对任何节点一样，效应节点也用它删。值还有人读就先 `replace`；效应节点在链上的位置交给后继 |
| `eval(n)` | 把 `n` 就地算成常量 | 现有 |
| `inline(at, fn, args...)` | 在 `at` 所在的区域里，把函数值 `fn` 的体以 `args` 为实参拼进来，交出结果节点 | **新增**。新节点只能由已类型检查的 Camel 代码产生，不提供"按算子名直接造节点" |
| `outline(nodes)` | 把图里的一段提成一个函数值 | **新增**，`inline` 的反向。交出的是检查过的函数值，不带草稿句柄，可以交出块 |
| `order(a, b)` | 加一条顺序边：两端都执行时 `a` 在 `b` 之前 | **新增**。插入效应时给它排位置；提交按"顺序完整"检查 |

`inline` 与 `outline` 互为反向，区域级的改写由它们组合出来，不为每种循环变换各加一个算子：
- **提出新函数**：`outline` 一段，在原处 `inline` 一次对它的调用；
- **展开循环**：`outline` 循环体，`inline` 两次；
- **合并两个循环**：`outline` 两个循环体，`inline` 一个用 Camel 写的合并循环并把两个体作实参交给它，再内联；
- **移出循环**：`outline` 与循环无关的那段，在循环外 `inline`、循环内 `replace`。移出区域的必须是纯且不会出故障的计算（原则 9.7），当场检查；
- **内联**：`inline` 被调函数的体、`replace` 接上；
- **特化、删没用的形参**（签名会变）：先写一个 Camel 闭包，如 `(y) => f(3, y)`，再对它 `edit`、内联、折叠。

位置交接（取走一个持位节点时把它在链上的位置交给后继）由这些算子自己负责，用户不写。

**写分析用的两样查询**：以节点为键、按规范顺序遍历的映射（结果不随遍历次序变）；从调用节点取被调函数的函数值（特化、复制被调函数时对它再开一个 `edit`）。分析结果带着句柄，出不了块，所以"先分析再改"写在同一个 `edit` 块里；不给节点加跨版本的稳定身份（那会让节点成为写法的一部分，原则 9.5）。

## 8. 检查与错误报告

**块内每一步（当场失败，指出这一步的源码位置）**：
- `replace`：新旧值类型相容；`new` 不是 `old` 的下游（不成环）；`new` 在 `old` 的使用者看得见的区域里。
- `erase`：节点没人读、不是效应、不是锚点。
- `inline`：实参类型与 `fn` 的形参相符；实参在 `at` 的区域里看得见。
- `outline`：这段只经由明确的入口取值、只经由明确的出口交值；不含锚点。
- `order`：不成环；两端在同一张图里。

**块尾的提交（不可关闭）**：结构、作用域、类型、无环、区域与锚点（`docs/technical/17_graph_rewrite_api_contracts.md` 第 4 节），加上：
- **效应包含**：新图的足迹不超出块头声明（省略时为原函数）的效应；
- **顺序完整**：同一资源上的冲突访问都有先后。

**错误值写什么**：违反的是哪条规则、涉及哪几个节点（`show(n)` 的形式），以及**是块里哪一步造成的**：草稿给每次改动记下发起它的那条语句的源码位置，提交时一个节点出了问题，报告能指回"第几行的 `inline` 造出了这个没有先后的写"。

**开销**：按 2026-11-15 定的分档（`docs/design/effects/analysis.cn.md` 4.1）：只用了不新增访问的算子（`replace`、`erase`、`eval`、`outline`）的块，效应包含与顺序完整是定理，发行构建里不查，调试构建与测试照查；用了 `inline`、`order` 的块照查。结构、作用域、类型、无环任何时候都查。所以不设跳过检查的"可信"模式。

## 9. 读图是一种效应

**一个块读 `f` 的图，就是读一个资源：`f` 的表示。** `view` 与 `edit` 的类型都带着这个读；它就是原则 3.1 里"读一个资源"的又一个实例，不新增效应种类，由现有的推断（只看函数体、自下而上）推出，用户一般不写。

- **这个资源只读、从不被写**：已提交的图是不可变的值，编辑交出的是新版本，不写旧图。所以它不与任何写冲突，不产生顺序边，不需要 `sync`，对执行没有开销。
- **不影响 `pure`**：`pure` 是"不写 `Ref`、不写外部资源"，读图不算写。
- **它给出一条有条件的保证**：类型里没有"读某个函数的表示"的上下文，分不开行为等价的两个函数。所以遍保持意思这件事，对不读图的程序成立；对读图的程序，依赖出在哪里由类型标出，在源码里就是那几个块。
- **哪些操作带它**：`view`、`edit` 一律带；整函数变换中结果可能取决于写法的也带（`grad` 在不可导的点上取决于写法）；用证明过的规则（判决 `proved`）做的 `rewrite` 不带（等价的函数改完仍等价），用近似或只经采样检验的规则做的带。具体名单第 13 节待定。
- **工程用处**：随机差分测试（E9）比较同一程序在不同流水线下的结果；带这个效应的程序结果本来就允许随优化变化，比对工具按类型跳过它们，不误报。

注意它不是"图不可见"：程序可以在块里读图、把读到的整数交给普通代码，这是允许的；效应只是把这种依赖如实记在类型里。

## 10. 与规则、事实、整函数变换、执行计划的关系

- **规则是首选**：定义处就检查（两侧只用什么都不访问的算子，原则 9.11），应用后一定通过提交。`edit` 的正确性在边界检查。规则写得出的，不写 `edit`。
- **事实**照旧是规则条件与块里的查询，两种块里都能问。
- **整函数变换**（`reinterp`、`split`、`transpose`，以及建在它们上的 `grad`、`vmap`）造出**签名不同**的新函数，由规则集逐节点定义，是内核算子。`edit` 改的是**同一个函数**：参数与结果不变，只允许效应变多。要改签名，写变换，或按第 7 节先写一个 Camel 闭包再 `edit`。
- **用户看到的只有图；怎么跑归后端**（负责人 2026-11-17）：设备放置、融合分组、布局、执行次序、内存回收的安排都不进图，也不是编译器的产物，是各个后端自己的步骤；可以写成公共模块供后端共用，但不强制每个后端使用。所有后端必须共同遵守的只有图与执行规则（原则 3.1，按边）。用户想影响怎么跑，用流水线阶段的参数；真有必须由用户给的信息（如多卡切分），写成图里意思为恒等的节点，到有需求时再设计。本稿的编辑算子不涉及这些。
- **宏**（`#macro`，在 `std::macro` 阶段展开）是生成代码的另一条路；宏体里操作图的部分同样只能写在这三种写法里。

## 11. 迁移

- `stdlib/graph.cml`：删除 `graph_of`、`graphs_of`、`Txn<F>`、`open`、`commit`、`abort`；查询与编辑算子的签名不变，句柄类型带上块标签；新增 `inline`、`outline`、`order`、`exit_of` 一类锚点查询；删除 `add_constant`（它是 `inline(at, () => v)` 的特例）。
- 用 Camel 写的遍（`stdlib/opt.cml` 的 `fold`/`cse`/`dce`、`examples/case-study/edits.cml`、`test/cases/modules/graph_pass/*`）：`open … commit` 改写成 `edit f as d { … }`；只读分析改写成 `view`。遍的形状不变，仍是 `(f: F) => F!`。
- `probe_handle`、`check_pass_boundary` 改成 `view` 块里的查询。
- 测试：每条现有的 `Txn` 用例改写；另加反例，各报一条具名诊断：句柄作为块的值交出、存进块外的 `Ref`、被离开的闭包带走、图算子写在块外、`view` 的节点交给 `replace`。

## 12. 示例：报错的样子

```camel
let g = edit f as d {
    replace(nodes(d)[3], nodes(d)[7])   // 第 2 行
    erase(nodes(d)[5])                  // 第 3 行
}
```

第 2 行若成环，块当场停下，第 3 行不执行，草稿丢弃，`f` 不受影响，`g` 是错误值：

```
error[EditStepRefused]: replace at line 2: the new value is downstream of the old one (would form a cycle)
```

```camel
let n = view f as d { nodes(d)[0] }
//      ^ error: a graph handle cannot leave the view block it belongs to
replace(a, b)
// ^ error: replace takes a node of an edit block; there is none here
```

## 13. 已定与待定

**负责人 2026-11-17 已定**：
- 图操作只写在规则、`view`、`edit` 三处，聚合成运行时的原子操作，不展开编译成图；`view` 保留，是读图的唯一入口。
- 编译完成后没有块节点：每个块是算子表里一个按块体规范形式命名的算子，参数按规范形式中第一次使用的先后排列；算子允许不终止（第 5 节）。
- 加 `outline`，与 `inline` 互为反向；按本质命名：`graft` 改为 `inline`（调用并当场展开），提取改为 `outline`（把一段收回成函数），删除 `add_constant`。不设 `drop_effect`：效应节点由区域出口的同步边用到，`replace` 只搬数据边，删它用 `erase`，不为效应另设算子。`view`、`edit` 两个关键字定名。
- 用户只看到图；调度与执行安排是后端自己的步骤，不是编译器的产物，也不对用户开放。
- 读图作为一种效应挂在块上（第 9 节）。

**待定**：
1. `edit` 块头类型可省略、只在加效应时写（第 2 节）。
2. 一个块能否编辑整个程序、一起提交：本稿建议能。
3. `edit` 能否改签名：本稿建议不能，只允许效应变多。
4. 规则两侧"什么都不访问"不放宽：要加效应用 `edit`，由边界按声明检查。这是对 11-14 那条的保留。
5. 不设跳过检查的"可信"模式（第 8 节的分档已经让只用公开编辑的块在发行构建里不付效应检查的代价）。
6. 带读图效应的整函数变换与 `rewrite` 的名单（第 9 节）：`grad` 带上它、训练代码的类型里因此出现它，是否接受。
7. 规则的删除保护只留 `protect_faults`：区域里的写建图时连到区域出口之后，`protect_order` 不再挡住任何东西（今天它只在 `protect_faults` 也开时才生效，没有一条用例的结果依赖它），建议删除；`protect_faults` 保留，它挡的是同步块外、可能出故障、读者被规则丢掉的纯计算（`(9/a)*0` 经 `x*0 => 0`）。这改原则 9.7 的措辞。
