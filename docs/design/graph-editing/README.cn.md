# 编辑块：把底层改图限制在一个有边界的作用域里

> **设计稿（2026-11-17，决策者起草，待负责人裁定）**。负责人提出方向（类似 `unsafe` 的块，底层改图只能在块里做，块边界自动提交），并在讨论中提出了第 1 节的要点；本稿从实现与语言整体一致性的角度展开。第 9 节列出需要负责人裁定的问题。裁定之前，原则与施工不按本稿改。

## 1. 为什么

规则与事实是 Camel 最推荐的改图方式：声明式，定义处就能检查（原则 9.11），应用后一定通过提交。但图原生语言必须让程序有足够的能力改图：规则写不出的变换（按分析结果整段改写、跨函数的遍、插入一段新计算）要有出路。

现在的出路是 `stdlib/graph.cml` 的 `open`/`replace`/`erase`/`eval`/`add_constant`/`commit`/`abort`：事务 `Txn<F>` 与节点 `Node` 是普通值，和普通代码混在一起；检查只在程序主动调用 `commit` 时发生。问题有三：

1. **句柄会逃逸**：`Txn`、`Node` 可以被返回、存进结构体、被离开的闭包带走；一个 `Node` 在它的草稿提交或放弃之后仍可被读，指向的东西已经不存在。
2. **忘了提交或提交到一半**：程序可以开了事务不提交，或在中途出错时留下半改的草稿；正确与否靠程序自己记得 `commit`/`abort`。
3. **改图与普通计算没有边界**：读程序的人看不出哪一段在改图、改的是谁。

编辑块把这三件事都收到语言层面：改图只能在一个有边界的块里做，句柄出不了块，块的出口就是唯一的提交点。

## 2. 语法

```camel
// 编辑一个函数：块的值是改好的函数，或一个错误值
let g = edit f as d: (x: f32[...]) => f32[...] uses console {
    for n in nodes(d) {
        if is_add_zero(n) then { replace(n, inputs(n)[0]) }
    }
    let p = graft(exit_of(d), (y: f32[...]) => println(y))   // 插一段新计算
    order(p, exit_of(d))
}

// 只读：看图，不改；块的值是体的值，类型里不能有句柄
let count = view f as d { len(nodes(d)->filter<is_add>) }

// 一次编辑整个程序（从 f 可达的全部图），一起提交，全成或全不成
let h = edit f as prog: F {
    for d in graphs(prog) { ... }
}
```

- `edit <函数值> as <名字>: <函数类型> { 语句 }`：`<名字>` 绑定到草稿（只在块内可见）；冒号后是**结果的函数类型**。块的值的类型是 `<函数类型>!`。
- `view <函数值> as <名字> { 表达式 }`：只读，块的值是表达式的值，类型不得提到句柄（第 3 节）。
- 改图操作（`replace`、`erase`、`graft`、`order`、`add_constant`、`eval`、`drop_effect`）只能出现在 `edit` 块里；查询（`nodes`、`inputs`、`users`、`op`、`type_of`、事实查询……）在两种块里都能用。
- 块可以嵌套，但内层块编辑的是另一个函数值；同一个函数值不能在两个同时打开的块里编辑。

这两个关键字是本稿的提议，名字由负责人定（第 9 节第 1 条）。

## 3. 类型规则：句柄出不了块

**规则：句柄类型只在它所属的块的作用域里良构。** 每个块引入一个不可命名的作用域标签 `β`。草稿、图、节点、区域这些句柄的类型都带着它：`Draft<β>`、`Graph<β>`、`Node<T, β>`（源码里照旧写 `Node<T>`，标签由编译器补，不写出来）。块外没有 `β` 这个名字，所以：

1. **不能作为结果交出**：`edit` 块的值的类型是块头写的函数类型，`view` 块的值的类型是体的类型；两者在块外都必须良构，提到 `β` 的类型不良构，报错。
2. **不能存到块外**：块外创建的 `Ref<T>`、结构体、数组，它们的 `T` 在块外定下，不可能提到 `β`；往里放句柄是类型不符。块内新建、装着句柄的 `Ref` 带着 `β`，同样出不了块。
3. **不能被离开块的闭包带走**：原则 3.3"握着什么，类型就提到什么"本来就要求闭包的类型提到它握着的句柄；握着节点的闭包类型提到 `β`，于是出不了块（规则 1、2）。在块内造闭包、在块内调用，完全允许。
4. **帮助函数照常写**：`func is_add_zero(n: Node): bool`、`func first_input(n: Node): Node` 这类写在块外的函数，签名里的 `Node` 对标签是泛型的（与原则 3.3"没写资源子句的函数类型对资源泛型、按实例化确定"同一机制），在块里调用时实例化成 `β`。它们可以收句柄、返回句柄，返回的句柄仍带调用处的 `β`，出不了块。
5. **效应输出不是逃逸**：`println(show(n))`、`println(id(n))` 交出去的是字符串与整数，不是句柄，可以。

这正是 `runST` 的作用域思路（每个块一个新鲜、不可命名的类型变量），以及 Xhebraj 等人（ECOOP 2022）二等值的效果；Camel 不需要让用户写出 rank-2 类型或生命周期参数，因为标签由块引入、在帮助函数上按实例化泛型，用户写的仍是 `Node`。检查全部在类型检查里完成，零运行时开销（原则第 1 节"接口上没有口子"一档）。

## 4. 语义

1. **进入块**：对目标函数值所在的程序开一份草稿（与现有 `RuntimeGraphDraftSession` 相同），草稿绑定到 `as` 后的名字。目标函数对块外的其他持有者不变（原则 9.1"图是值"）。
2. **块内**：语句照普通语义求值。改图操作是对草稿句柄的写，同一个草稿上的写按书写顺序（原则 3.3"同一句柄上的操作按书写顺序"），不需要写 `sync`。每一步做能当场做的局部检查（第 6 节）；一步失败，块立即结束，不执行之后的语句。
3. **正常走到块尾**：自动提交。提交做完整检查（第 6 节），通过则块的值是新函数（类型是块头声明的那个），否则块的值是错误值。
4. **任何失败**：局部检查失败、体里出现未处理的错误值或故障、提交被拒，都放弃整份草稿：程序里不留下改了一半的图，块的值是一个错误值，说明哪一步、为什么。
5. **整程序编辑**：`edit f as prog` 的草稿覆盖从 `f` 可达的全部图（`graphs(prog)` 列出它们），块尾一次提交，全成或全不成。这与今天提交以程序为单位一致，不需要新机制（第 9 节第 3 条）。
6. **`view` 块**：同一份只读快照，没有提交，块尾丢弃。
7. **确定性**：`nodes`、`graphs` 按规范顺序返回；读写法的查询（图名、创建编号、源码位置）照原则 9.5 要求类型里声明那种能力。编辑块不放宽这一条。

## 5. 编辑操作

| 操作 | 作用 | 说明 |
|---|---|---|
| `replace(old, new)` | 把 `old` 的使用者改接到 `new` | 现有；类型必须相容 |
| `erase(n)` | 删一个没人读的纯节点 | 现有；删不掉效应（原则 9.7） |
| `drop_effect(n)` | 显式删一个外部访问或句柄写 | 原则 9.7 要求的"专门删效应的操作"，与 `erase` 分开 |
| `add_constant(value)` | 加一个常量节点 | 现有 |
| `eval(n)` | 把 `n` 就地算成常量 | 现有 |
| `graft(at, fn, args...)` | 在 `at` 所在的区域里，把函数值 `fn` 的体以 `args` 为实参拼进来，返回结果节点 | **新增**。新节点只能由 Camel 代码产生（`fn` 已类型检查），不提供"按算子名直接造节点" |
| `order(a, b)` | 加一条顺序边：两端都执行时 `a` 在 `b` 之前 | **新增**。插入效应时要给它排位置；提交按"顺序完整"检查 |

位置交接（取走一个持位节点时把它在链上的位置交给后继）由这些操作自己负责（11-15 的裁定），用户不写。

## 6. 检查与错误报告

**块内每一步（当场失败，指出这一步的源码位置）**：
- `replace`：新旧值类型相容；`new` 不是 `old` 的下游（不成环）；`new` 在 `old` 的使用者看得见的区域里（作用域）。
- `erase`：节点没人读、不是效应、不是锚点。
- `graft`：实参的类型与 `fn` 的形参相符；实参在 `at` 的区域里看得见。
- `order`：不成环；两端在同一张图里。

**块尾的提交（不可关闭）**：结构、作用域、类型、无环、区域与锚点（`docs/technical/17_graph_rewrite_api_contracts.md` 第 4 节），加上 R3 的两项：
- **效应包含**：新图的足迹不超出块头声明的函数类型的效应。块头的类型可以比原函数多效应（负责人 2026-11-17："库可以给程序加效应，限制效应不是本意"），但必须写出来，块外的调用者按写出的类型算。
- **顺序完整**：同一资源上的冲突访问都有先后。

**错误值写什么**：违反的是哪条规则、涉及哪几个节点（`show(n)` 的形式），以及**是块里哪一步造成的**。为此草稿给每次改动记下发起它的那条编辑语句的源码位置；提交时一个节点出了问题，报告能指回"第几行的 `graft` 造出了这个没有先后的写"，而不只是"图不合法"。

**开销**：按 2026-11-15 定的分档（`docs/design/effects/analysis.cn.md` 4.1"开销与范围"）：只用了不新增访问的操作（`replace`、`erase`、`eval`、`add_constant`）的块，效应包含与顺序完整是定理，发行构建里不查，调试构建与测试照查；用了 `graft`、`order`、`drop_effect` 的块照查。结构、作用域、类型、无环任何时候都查。所以不需要一个"跳过检查"的可信模式（第 9 节第 2 条）。

## 7. 与规则、事实、整函数变换的关系

- **规则是编辑块的特例**：一次规则应用 = 匹配到的节点上做一次 `graft`（右侧）加 `replace`。规则引擎（`rewrite`、`run`、`saturate`）在实现上就是一个编辑块，共用同一个草稿与提交。规则仍是首选：它在定义处就检查（两侧什么都不访问，原则 9.11），应用后一定通过提交；编辑块的正确性在边界检查。
- **事实**照旧是规则条件与块里的查询，在 `view` 与 `edit` 块里都能问。
- **整函数变换（`reinterp`、`split`、`transpose`，以及建在它们上的 `grad`、`vjp`、`vmap`）是另一条路线**：它们造出一个**类型不同**的新函数（参数与结果都变了），由规则集逐节点地定义，是内核算子。编辑块改的是**同一个函数**：块头的类型与原函数的参数、结果相同，只允许效应变多（第 9 节第 4 条）。要改签名，写变换，不写编辑块。

## 8. 迁移

- `stdlib/graph.cml`：删除 `Txn<F>`、`open`、`commit`、`abort`；`replace`/`erase`/`eval`/`add_constant` 改为只在 `edit` 块里可用（实现上是带一个由块提供的 `with` 草稿参数的函数，块把草稿放进上下文，用户不写）；新增 `graft`、`order`、`drop_effect`、`exit_of` 一类锚点查询；查询函数的签名不变，`Node`/`Graph` 带上块标签。
- 用 Camel 写的遍（`stdlib/opt.cml` 的 `fold`/`cse`/`dce`、`examples/case-study/edits.cml`、`test/cases/modules/graph_pass/*`）：`open … commit` 改写成 `edit … { }`；遍的形状不变，仍是 `(f: F) => F!`，函数体是一个 `edit` 块。
- `probe_handle`、`check_pass_boundary` 保留为只读检查，改成 `view` 块里可用。
- 测试：每条现有的 `Txn` 用例改写；另加句柄逃逸的反例（作为结果交出、存进外面的 `Ref`、被离开的闭包带走），各报一条具名诊断。

## 9. 需要负责人裁定

1. **名字**：`edit`/`view` 还是别的（`unsafe` 不合适，因为它不放弃任何检查）。
2. **是否另设跳过检查的"可信"模式**：本稿建议**不设**。第 6 节的分档已经让只用公开编辑的块在发行构建里不付效应检查的代价；真跳过结构、类型检查，错误会变成运行时的崩溃，正是 E9 这两天在抓的那类。
3. **一个块能否编辑整个程序、一起提交**：本稿建议**能**，单位是"从目标可达的全部图"，与今天提交以程序为单位一致。
4. **编辑块能否改函数的签名**：本稿建议**不能**，只允许效应变多；改签名走整函数变换（第 7 节）。
5. **规则两侧"什么都不访问"这条要不要放宽**：负责人 11-17 说库可以给程序加效应。本稿建议**规则保持不放宽**（这样规则仍然"定义处检查、应用后一定通过提交"），要加效应就用编辑块，由边界按声明检查。这是对 11-14"规则两侧只用什么都不访问的算子"一条的保留，请确认。
6. **只读的 `view` 块要不要单列**：本稿建议单列，读图做分析（统计、导出、可视化）比改图常见，不该为它开一份要提交的草稿。
