# 并行调度：`std::prl` 只管并行，不管执行

## 初心

`std::prl` 要回答的只有一个问题：图上哪些计算可以同时进行。可今天它同时还在做第二件事，自己逐个解释节点。于是有两个后果：

- **起点就慢**：单线程时，它比专门的顺序引擎（`std::fvm`）慢好几倍，甚至比节点虚拟机还慢，并行先得追回这几倍。
- **加速无法如实说明**：拿"比 `nvm` 快"当判据，等于和最慢的顺序引擎比，测出的加速说明不了并行调度本身做得好不好。

所以 `std::prl` 只管调度：在图上找出能并发的部分，派给工作线程；每一段顺序执行的部分，交给最快的顺序引擎去跑。一张图里没有可并发的东西时，`std::prl` 就退化成 `std::fvm`。

## 两层分工

| 层 | 谁负责 | 做什么 |
|---|---|---|
| 并行层 | `std::prl` | 找出互不依赖的调用、`EACH` 的块、互不依赖的子图，决定拆不拆、拆给谁 |
| 执行层 | `std::fvm`（或 `std::jit`） | 每个顺序片段编成字节码执行，`EACH` 的一块就是一个字节码循环 |

`std::prl` 不再有自己的逐节点解释器。同一段代码，单线程跑在 `std::prl` 下，与直接跑在 `std::fvm` 下，执行的是同一份字节码。

## 粒度

原则 3.6 说并行调度的粒度不要细到原子级别。做法有两层：

- **静态下限**：图模块已有的 `relative_cost` 估出一次调用、一块 `EACH` 的代价；低于阈值的直接在当前线程顺序执行，不建任务。
- **动态拆分**：用惰性二分拆分（lazy binary splitting），只有在别的工作线程闲着时，才把一半工作拆出去，否则就地算完。递归采用 Cilk 式的分叉汇合：派出一半，自己算另一半，再汇合。拆分的成本只在真被别的线程取走时才付（work-first 原则）。

不为每次图的激活现建一张任务图，改用执行器的轻量异步与分叉汇合接口。若 Taskflow 的接口仍然太重，再换成自己的工作窃取队列。

## 热路径上没有共享锁

- **执行计划与"轻重"判断**：它们是图的性质，计划时算一次，存成这一版图的事实，执行时无锁读取（见 [`../effects/derived-properties.cn.md`](../effects/derived-properties.cn.md) 的"一个问题一个判定"）。
- **帧池**：每个线程一份。
- **垃圾回收的安全点**：只放在任务边界上，减少全体线程停下来等待的次数。

## 怎样如实地量

并行计算里通行的三个量：

- **T_S**：最快的顺序实现所用的时间，即 `std::fvm` 单线程。
- **T_1**：`std::prl` 在一个工作线程上的时间。
- **T_P**：`std::prl` 在 P 个工作线程上的时间。

由此得到三个指标，都要报：

| 指标 | 定义 | 说明什么 | 目标 |
|---|---|---|---|
| 工作开销 | T_1 / T_S | 为了"能并行"付出的额外成本 | 接近 1，例如 ≤ 1.1 |
| 绝对加速 | T_S / T_P | 相对最快顺序实现快了多少，这是要对外说的数 | 随 P 增长 |
| 自身扩展 | T_1 / T_P | 调度本身的扩展性 | 随 P 增长 |

只报"比 `nvm` 快"不算数。工作开销一项单独报出，"并行的执行开销高于顺序引擎"就不再是一个说不清的问题，而是一个量出来、要压下去的数。每拆出一个任务的成本（纳秒）也一并报出。

## 与其他部分的关系

- **`EACH`**（见 [`../repetition/README.cn.md`](../repetition/README.cn.md)）：`std::prl` 按节点种类与汇合方式切块，不按算子名认 `map`。按名字认高阶算子的那一段随标记算子一起删除。
- **库函数用 Camel 写之后的递归**：`reduce` 的二分递归、纯 Camel 的归并排序，都靠上面的粒度控制。没有粒度控制，细粒度的递归会被任务开销吃掉。
- **`std::fvm` 调用路径**：它是执行层，它的性能回归直接成为 `std::prl` 的回归，所以 `std::fvm` 是这一组读数的前提。

## 施工顺序

1. **实测（只读）**：在工作站净场下量三个程序：纯 Camel 的归并排序、binary-trees、fib。
   - 量 T_S、T_1、T_P（P = 1、2、4、8、16）。
   - 量每个任务的成本，以及锁上的等待时间。
   - 确认开销来自哪一处：逐节点解释、现建任务图、锁、粒度。先修最大的那一处。
2. **两层分工**：顺序片段改由 `std::fvm` 执行。判据：工作开销 T_1/T_S 显著下降，输出与 `std::nvm` 逐字节相同。
3. **粒度**：静态下限加惰性二分拆分，不再每次激活现建任务图。判据：每个任务的成本下降，细粒度递归的绝对加速出现。
4. **去锁**：计划与轻重判断进事实层，帧池每线程一份。判据：锁等待接近 0，P 增大时扩展不塌。
5. **验收**：纯 Camel 的归并排序与 binary-trees。工作开销 ≤ 1.1，绝对加速随核数增长。

前提：`std::fvm` 调用路径的回归先修好。
