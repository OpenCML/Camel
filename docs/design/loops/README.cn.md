## 0. 摘要

**结论。** 循环在图上有三种可行的映射，都满足“稳定映射”判据，区别在于循环结构是写在图上，还是每个使用者自己从递归里认出来：

| 方案 | 图上是什么 | 新增节点种类 | 主要代价 | 主要收益 |
|---|---|---|---|---|
| (a) 脱糖为自递归子图 | 与今天的尾递归完全相同 | 无 | 循环结构继续由每个后端、导出器、微分各自识别 | 改动最小；循环与尾递归是同一种东西 |
| (b) 循环节点 | 外层图里一个 `LOOP` 节点，带条件子图、循环体子图和状态边 | 1 个 | 所有遍、后端、微分、导出器都要认识它；与尾递归并存 | 循环结构只表达一次；微分、导出、即时编译、循环优化有直接的落点 |
| (c) 两层 | 语法映射到 `LOOP`；另有遍在 `LOOP` 与尾递归子图之间转换 | 1 个 | (b) 的代价加两个转换遍 | 可以逐个子系统迁移，每一步都能合入；最终尾递归也能得到循环的待遇 |

**推荐 (c)，先做“循环节点 → 尾递归子图”这个方向。** 第一步只加语法、节点、校验、打印和一个把 `LOOP` 降为自递归子图的改写；所有后端、微分、导出器在入口处调用这个降级，行为与今天的尾递归一致，全套测试保持通过，语言用户此时就能用循环。之后每个子系统各自换成对 `LOOP` 的原生处理，互不阻塞。反方向（尾递归 → `LOOP`）放在最后，是可选的优化遍。

推荐 (c) 而不是 (a) 的依据是现有编译器上的四个实测事实（第 1、3 节）：

1. 把循环写成尾递归后求梯度，在 `std::nvm`、`std::fvm` 上迭代 200 次就因递归深度 256 而终止（100 次可以）。
2. `std::macro` 对尾递归写的循环最多提前求值 64 层；100 次迭代是编译期错误。
3. `std::opt::simplify` 把循环当成“可以按轮展开的递归”，16 轮剥出 16 份循环体的特化副本，循环本身还在。
4. ONNX 导出器 3997 行里约 1700 行在从递归里恢复循环；一个循环体只写了一次 `tanh` 的程序，导出的模型里有 5 个 `Tanh`。

这些都不是 (a) 做不到，而是 (a) 之下每一处都要各自再写一遍“这其实是个循环”的识别；(b)/(c) 把它写在图上一次。

**如果负责人更看重少动底层，(a) 是成立的退路**：第 4 节的语法与语义不依赖这个选择，先按 (a) 实现、以后换成 (c)，程序不用改，只是 `std::rgir` 看到的图会变。

**最需要负责人决定的三件事**（完整清单见第 8 节）：

1. **Q1 图上的映射**：(a)、(b)、(c) 选哪个。建议 (c)。
2. **Q2 循环携带的状态从哪来**：只提供“对 `var` 赋值”的语句形式，还是同时提供“状态写在循环头、循环体的值是下一轮状态”的表达式形式。建议两种都要，后者是主形式：2.7 已定“梯度经过 `var` 直接拒绝”，只有语句形式的话，循环在被求导的函数里就用不了。
3. **Q3 语句形式的循环体是否必须是同步块**：循环体不是同步块时，体内的赋值没有任何东西依赖，按 2.1 一条都不执行（实测：分支臂里两条赋值只执行了最后一条）。建议要求写出 `sync`（`while c sync { ... }`），不做隐式规则。

**调研中发现的现有缺陷**（第 10 节）：`std::inline std::jit` 下，一个 4 个参数的尾递归函数第二次及以后的调用返回错误结果（最小复现 `examples/defect_jit_second_call.cml`，期望 `1 1 11`，得到 `1 2 17`）。

## 1. 现状：循环今天在图上是什么

今天写循环有三种办法。下面三个函数算的是同一件事（`examples/for_tail.cml`，三种写法在全部后端与流水线上结果相同【实测】）。

```camel
// 尾递归：状态是参数
func loop(xs: int[], i: int, acc: int): int {
    return if i >= len(xs) then acc else loop(xs, i + 1, acc + xs[i] * xs[i])
}

// 高阶算子：状态是 reduce 的累加值
func by_reduce(xs: int[]): int {
    return xs->reduce<(acc: int, x: int): int => acc + x * x, 0>
}

// 高阶算子 + var：状态在一个共享单元里
func by_foreach(xs: int[]): int sync {
    var acc = 0
    xs->foreach<(x: int) => sync { acc = acc + x * x }>
    return acc
}
```

### 1.1 尾递归的图

`camel examples/sum_tail.cml std::rgir`【实测】，下面是 `loop(i, n, acc) = if i > n then acc else loop(i + 1, n, acc + i)` 的输出，省略了 `ARGS`/`EXIT` 伪节点与源码位置属性：

```
subgraph "loop" {
    subgraph "__g_4__" {                 // then 臂：返回 acc
        N00 [PORT]                       // 捕获的 acc
        N00 -> EXIT
    }
    subgraph "__g_6__" {                 // else 臂：再调一次 loop
        N01 [PORT]  N02 [PORT]  N03 [PORT]          // 捕获的 i、n、acc
        N04 [DATA 1]
        N05 [OPER :op/add_l]             // i + 1
        N06 [OPER :op/add_l]             // acc + i
        N07 [FUNC loop]                  // 递归调用
        N01 -> N05; N04 -> N05; N03 -> N06; N01 -> N06
        N05 -> N07 [NORM 0]; N02 -> N07 [NORM 1]; N06 -> N07 [NORM 2]
        N07 -> EXIT
    }
    N08 [PORT i]  N09 [PORT n]  N0A [PORT acc]
    N0B [OPER :op/gt_l]                  // i > n
    N0D [BRCH]  N0C [JOIN]
    N0E [FUNC __g_4__]  N0F [FUNC __g_6__]
    N08 -> N0B; N09 -> N0B; N0B -> N0D [NORM]
    N0D -> N0E [CTRL 0]; N0D -> N0F [CTRL 1]         // 两个臂
    N0A -> N0E [WITH]; N08 -> N0F [WITH]; N09 -> N0F [WITH]; N0A -> N0F [WITH]
    N0E -> N0C [WITH 0]; N0F -> N0C [WITH 1]; N0D -> N0C [NORM]
    N0C -> EXIT
}
```

要点【实测】：

- **一个尾递归循环是三张图。** 分支的每个臂在建图时是一张自己的子图，由 `BRCH` 控制的 `FUNC` 节点调用（`src/compile/gir/builder.cpp:3030-3102`）。递归调用在臂的子图 `__g_6__` 里，所以递归是 `loop → __g_6__ → loop` 的**互递归**；运行 `std::inline` 之后臂才被并入 `loop`，变成直接的自递归。
- **“这是一个循环”不写在图上。** 图上只有分支和调用。尾位置是每个执行器按同一套判据临时判定的：出口是 `JOIN`、某个臂以这次调用结尾、拓扑序里它之后只有 `GATE`（`docs/technical/19_tail_call_optimization.md` 第 6 节；`src/execute/graph_runtime_support.cpp:300-521`）。
- 状态就是参数；每一轮不变的 `n` 也是参数，每一轮都重新传一次。

### 1.2 各后端怎样执行它

| 后端 | 尾调用的执行方式 | 非尾递归的上限 | 备注 |
|---|---|---|---|
| `std::nvm` | 同一次 `call` 内换图换帧，`goto loop_start`【读码 `nodevm.cpp:689-725`】 | 256 帧 | 每一轮线性扫过整张图的拓扑序 |
| `std::fvm` | 字节码 `TAIL`：释放当前帧、取新帧、跳到入口【读码 `gotovm.cpp:570-687`】；实测 `std::inline` 后 `loop` 的字节码为 `LGT; BRCH; JUMP×3; LADD; LADD; TAIL; JOIN; RETN` | 256 帧 | |
| `std::jit` | 只编译“纯标量算术 + 只调用自己”的图【读码 `x64_backend.cpp:102-151`】；自尾调用在 Windows 上是一条 `jmp`，在 Linux 上经 `trampolineTail`【读码 `:954-992`】 | 原生代码内无上限 | 不加 `std::inline` 时循环**不被编译**：`-v` 输出 `compile skipped for graph '__g_6__': targets non-self graph 'loop'`【实测】 |
| `std::tf` | `evalGraph` 里的 `for(;;)`，自调用复用同一帧【读码 `taskflow.cpp:1000-1061`】 | 原生栈 | 单线程顺序执行 |
| `std::macro` 求值器 | 没有尾调用优化，深度上限 64【读码 `src/execute/macro/eval.cpp:67`】 | 64 | |
| `std::cpp` | 生成普通的 C++ 互递归函数，是否变成循环取决于 C++ 编译器【实测输出 `f_loop` ↔ `f_g_6`】 | 原生栈 | |

三百万次迭代的求和，同一台（当时有其他构建在跑的）机器上各跑三次的整进程耗时【实测，仅作量级参考】：

| 写法 | `std::nvm` | `std::fvm` | `std::inline std::fvm` | `std::inline std::jit` | `std::tf` |
|---|---|---|---|---|---|
| 状态是参数（`sum_tail.cml` 改为 3000000） | 1.1–1.4 s | 0.33–0.72 s | 0.18–0.50 s | 0.20–0.25 s | 2.9–3.6 s |
| 状态在 `var` 单元里（`while_desugared.cml` 改为 3000000） | 2.2–2.4 s | 0.95–2.2 s | 0.64–1.4 s | 1.0–1.2 s | 9.1–10.7 s |

状态放在 `var` 里的同一个循环，在 `std::inline std::jit` 下慢约 5 倍：读写变量是算子 `:var/get`、`:op/assn_l`，而即时编译对任何含 `OPER` 的图回退到解释器（`-v` 输出 `compile skipped for graph 'step': pc=25 contains OPER`【实测】）。

### 1.3 现状的四个硬限制（都是实测）

**L1 循环的梯度只能算一百多次迭代。** `examples/grad_tail.cml` 对一个尾递归循环求导，迭代次数从环境变量读入：

```
N=100 camel examples/grad_tail.cml std::macro std::nvm     -> 1.90479  0.904792
N=200 camel examples/grad_tail.cml std::macro std::nvm     -> 1.81865  然后
    Error: Maximum recursion depth (256) exceeded when evaluating graph 'iterate.fwd'
N=200 ... std::macro std::fvm                               -> 同样的错误（图 '__g_6__.fwd'）
N=1000 ... std::macro std::tf                               -> 1.3677  0.367695（靠原生栈）
```

原因：自动微分为尾递归函数导出的前向函数是**非尾**递归——每一步的回传函数是一个闭包，捕获下一步的回传函数（`docs/technical/26_autodiff_as_graph_rewrite.md` 4.2：“the pullback of one step captures the pullback of the next”）。前向循环不占栈，它的梯度占栈。

**L2 `std::macro` 提前求值循环最多 64 层。** `examples/macro_loop.cml`：`count(0, 20, 0)` 被求值，`count(0, 100, 0)` 是编译期错误 `'count' could not be evaluated by std::macro: the evaluation needs more than 64 nested calls`。

**L3 `std::opt::simplify` 把循环当递归逐轮展开。** `K=3 camel examples/invariant.cml std::opt::simplify std::rgir`：循环 `loop(0, 1000000, k, 0)` 的初值是常量，于是每一轮特化出一份 `i` 为下一个常量的副本，16 轮后图里有 `loop$spec7` … `loop$spec20` 逐层嵌套的 14 份循环体，再加原来的 `loop`；每一份里 `k * k` 的乘法都还在。`sum_tail.cml` 的统计：不加遍 5 张图 25 个节点，`std::opt::simplify` 之后 22 张图 68 个节点、20 个直接调用。循环没有变快，优化的轮数与增长预算花在了剥皮上。

**L4 导出器要从递归里恢复循环。** `modules/onnx/exporter.cpp` 共 3997 行，其中尾递归到 `Loop`（`evalLoopBody`、`translateLoop`、`mergeOutcomes`，约 1037–1591 行）、线性递归到成对的 `Loop`（约 1593–2074 行）、作为值的回传函数（约 2076–2426 行）与辅助诊断合计约 1700 行【读码，按函数边界估算】。它是对函数的图做符号求值来认出循环的：先试算一遍、丢弃，找出哪些实参在变。结果：

- `examples/export_tail.cml`（循环体里写了一次 `tanh`）导出的模型有 1 个 `Loop`、4 个 `If`、**5 个 `Tanh`**【实测，用 `onnx` 包逐层计数】：循环之后要把循环体再算一遍取结果，前几轮还被化简剥出来。
- 被拒绝的形状：`match` 决定是否继续、元组或结构体作为变化的状态、两处以上的递归调用；梯度导出更窄，只接受“恰好一个 if/else 决定循环”【读码 `exporter.cpp:1382,1482,1821-1857`；`docs/technical/26` 第 469–546 行】。
- 梯度导出没有磁带：反向循环的第 `i` 步要从头重算状态，循环体执行 `n + n(n-1)/2` 次【读码 `exporter.cpp:1593-1632` 的注释，文档称为已测得】。

### 1.4 循环体内的效应：今天的规则

这几条决定第 4 节的语义，全部实测：

- `examples/effect_loop.cml`：尾递归函数体不是同步块时，体内的 `println` 不执行（给出 `EffectNotExecuted` 告警）；函数体写成同步块后打印 `0 1 2`。循环是否打印由循环体自己的块决定，与调用它的 `main` 是不是同步块无关（原则 2.4）。
- `examples/foreach_outside_sync.cml`：`xs->foreach<...>` 写在非同步函数体里、结果没人用，整个 `foreach` 不执行（告警）；写在同步块里按元素顺序执行。
- `examples/block_effects.cml`：分支臂 `{ a = 1; b = 2 }` 不是同步块时，**只有最后一条赋值执行**（它是块的值），`a = 1` 没有任何东西依赖，不执行，结果是 `2` 而不是 `12`；臂写成 `sync { ... }` 后是 `12`。
- `examples/block_return.cml`：块里的 `return` 结束的是**这个块**并给出块的值，不是离开函数：`if c then sync { return 1 } else 2` 之后的语句照常执行。原因在图上：臂是自己的子图，`return` 设的是这张子图的出口。
- 尾递归循环里的故障（`examples/fault_in_loop.cml`，第 501 轮除零）：五种流水线都报 `fault_in_loop.cml:7:62 ... DivisionByZero`，有源码位置，没有“第几轮”，也没有调用链。
- 不终止的尾递归一直运行，不受递归深度上限约束（5 秒超时被杀）。

## 2. 图上的映射：方案比较

用同一对例子贯穿：

```camel
// while：从 1 加到 n
var i = 1
var acc = 0
while i <= n sync {
    acc = acc + i
    i = i + 1
}

// for：平方和
var acc = 0
for x in xs sync {
    acc = acc + x * x
}
```

以及它们不用 `var` 的表达式形式（第 4.2 节，写法待定）：

```camel
let (i, acc) = while let (i, acc) = (1, 0); i <= n { (i + 1, acc + i) }
let acc      = for x in xs; let acc = 0 { acc + x * x }
```

### 2.1 方案 (a)：固定脱糖为自递归子图

**表达式形式**脱糖为“状态是参数”的尾递归，图就是 1.1 节的图（`while`）与 `for_tail.cml` 里 `loop` 的图（`for`，多一个隐藏的下标参数；【实测】，命令见附录 A.1）。

**语句形式**脱糖为“没有参数、捕获变量单元”的尾递归。手写的等价程序是 `examples/while_desugared.cml`，`camel examples/while_desugared.cml std::rgir`【实测】，省略同前：

```
subgraph "sum_to" {
    subgraph "step" {                       // 循环：无参数，三个捕获端口
        subgraph "__g_5__" {                // 继续的那一臂 = 循环体 + 再调一次 step
            N00 [PORT]  N01 [PORT]  N02 [PORT]              // 捕获：acc 单元、i 单元、n
            N04 [OPER :var/get]  N05 [OPER :var/get]         // 读 acc、读 i
            N03 [OPER :op/add_l]
            N06 [OPER :op/assn_l]                            // acc = acc + i
            N09 [OPER :var/get]  N07 [DATA 1]  N08 [OPER :op/add_l]
            N0A [OPER :op/assn_l]                            // i = i + 1
            N0B [FUNC step]                                  // 下一轮
            N0C [GATE]
            N06 -> N09 [CTRL]; N0A -> N0B [CTRL]; N06 -> N0B [CTRL]     // 同步块的顺序
            N0B -> N0C [NORM]; N0C -> EXIT
        }
        subgraph "__g_7__" { N0D [DATA 0]; N0D -> EXIT }     // 结束的那一臂
        N0E [PORT]  N0F [PORT]  N10 [PORT]
        N12 [OPER :var/get]  N11 [OPER :op/le_l]             // i <= n
        N14 [BRCH]  N13 [JOIN]  N15 [FUNC __g_5__]  N16 [FUNC __g_7__]  N17 [GATE]
    }
    N18 [PORT n]
    N1B [OPER :var/new]  N1E [OPER :var/new]                 // var i = 1；var acc = 0
    N1F [FUNC step]                                          // 循环在外层图里是一次调用
    N20 [OPER :var/get]                                      // 读 acc
    N1B -> N1F [WITH]; N18 -> N1F [WITH]; N1E -> N1F [WITH]
    N1F -> N20 [CTRL]                                        // 循环写了 acc：之后的读取排在它后面
    N20 -> EXIT
}
```

- **稳定映射**：满足。任何 `while`/`for` 都是“一张自递归子图 + 外层图里一次调用”，结构不随循环体的内容变化；变化的只是捕获了哪些名字、有几个参数，这与今天的函数和分支臂一样。
- **尾递归与循环是不是同一种东西**：是。循环语法只是尾递归的另一种写法。
- **对“函数是子图”与容量上限的影响**：没有。循环体在自己的子图里，外层图只多一个 `FUNC` 节点。
- **不需要改的**：图的数据结构、所有的遍、四个后端、微分、导出器、转译。
- **代价**：1.3 节的 L1–L4 原样保留；语句形式的循环（状态在单元里）不能被即时编译、不能被求导、不能导出（1.2 节与 2.7、`docs/technical/26` 4.4a）。

### 2.2 方案 (b)：循环节点

外层图里新增一种节点 `LOOP`，带两张子图：

```
LOOP 节点（在外层图 G 里）
    Norm 入边   s1 … sk     循环携带状态的初值
    With 入边   c1 … cm     捕获的值（每一轮不变的量、变量单元），与分支臂的捕获端口同一种做法
    Ctrl 入边               顺序（同步块的链、此前对被捕获变量的写入）
    节点体      { cond: 条件子图, body: 循环体子图, kind: While | For }
    出值        最终状态：k = 0 时为空，k = 1 时是那个值，k > 1 时是元组
条件子图   (with c1 … cm)(s1 … sk) -> bool          只有 While 有
循环体子图 (with c1 … cm)(s1 … sk) -> (s1' … sk')   For 的第一个普通参数是当前元素
```

语义：`s = 初值; while cond(s) { s = body(s) }; 给出 s`。`For` 没有条件子图，第一条 Norm 入边是被遍历的数组，循环体对每个元素按顺序执行一次。

`while` 表达式形式（拟议记法，现有编译器不产生）：

```
subgraph "sum_to" {
    subgraph "sum_to.loop1.cond" {
        N00 [PORT i]  N01 [PORT acc]  N02 [PORT]             // 状态 i、acc；捕获 n
        N03 [OPER :op/le_l]
        N00 -> N03; N02 -> N03; N03 -> EXIT
    }
    subgraph "sum_to.loop1.body" {
        N04 [PORT i]  N05 [PORT acc]  N06 [PORT]
        N07 [DATA 1]  N08 [OPER :op/add_l]  N09 [OPER :op/add_l]  N0A [FILL]     // (i + 1, acc + i)
        N04 -> N08; N07 -> N08; N05 -> N09; N04 -> N09; N08 -> N0A; N09 -> N0A; N0A -> EXIT
    }
    N0B [PORT n]  N0C [DATA 1]  N0D [DATA 0]
    N0E [LOOP while cond=sum_to.loop1.cond body=sum_to.loop1.body]
    N0C -> N0E [NORM 0]; N0D -> N0E [NORM 1]                 // i、acc 的初值
    N0B -> N0E [WITH 0]                                      // 捕获 n
    N0F [ACCS .1]                                            // 取出 acc
    N0E -> N0F; N0F -> EXIT
}
```

`while` 语句形式：同一种节点，`k = 0`，状态在被捕获的单元里：

```
subgraph "sum_to" {
    subgraph "sum_to.loop1.cond" {
        N00 [PORT]  N01 [PORT]                               // 捕获：i 单元、n
        N02 [OPER :var/get]  N03 [OPER :op/le_l]
        N00 -> N02; N02 -> N03; N01 -> N03; N03 -> EXIT
    }
    subgraph "sum_to.loop1.body" {                           // 同步块
        N04 [PORT]  N05 [PORT]                               // 捕获：acc 单元、i 单元
        ...  N0A [OPER :op/assn_l]  ...  N0E [OPER :op/assn_l]  N0F [GATE]
        N0A -> ... [CTRL] ...; N0E -> N0F [CTRL]; N0F -> EXIT
    }
    N10 [PORT n]  N11 [OPER :var/new]  N12 [OPER :var/new]
    N13 [LOOP while cond=… body=…]
    N11 -> N13 [WITH 0]; N10 -> N13 [WITH 1]; N12 -> N13 [WITH 2]      // i 单元、n、acc 单元
    N14 [OPER :var/get]
    N12 -> N14; N13 -> N14 [CTRL]                            // 循环写了 acc：之后的读取排在它后面
    N14 -> EXIT
}
```

`for` 表达式形式：

```
subgraph "sq_sum" {
    subgraph "sq_sum.loop1.body" {
        N00 [PORT x]  N01 [PORT acc]
        N02 [OPER :op/mul_l]  N03 [OPER :op/add_l]
        N00 -> N02; N00 -> N02; N01 -> N03; N02 -> N03; N03 -> EXIT
    }
    N04 [PORT xs]  N05 [DATA 0]
    N06 [LOOP for body=sq_sum.loop1.body]
    N04 -> N06 [NORM 0]; N05 -> N06 [NORM 1]                 // 被遍历的数组；acc 的初值
    N06 -> EXIT
}
```

- **稳定映射**：满足，而且比 (a) 更直接：一个循环一个节点，状态、捕获、条件、循环体各在固定的位置上。
- **尾递归与循环是不是同一种东西**：不是。同一个计算有两种图。理由只能是这一条：**函数是一张谁都可以调用、也可以调用自己的子图，递归是它的一种用法；循环是外层图里一个只有一个入口、只属于这一处的重复区域，回边、状态和出口是它的定义的一部分。** 尾递归是否构成循环取决于调用落在什么位置（1.1 节的判据），而且遍可以改变这一点；循环节点不存在“是不是尾位置”的问题。两种写法给出两种图，与“`if` 和 `match` 都是分支但写法不同”不是一回事，这是 (b) 最需要负责人认可的地方，也是提出 (c) 的原因。
- **对“函数是子图”与容量上限的影响**：没有。条件与循环体是独立的子图，外层图里每个循环只占一个节点；节点体多两个图指针（现有 `GCFuncBody` 是一个图指针，`include/camel/runtime/graph.h:188`）。**不把循环体内联进外层图**：内联后的回边会使图不再是无环图，拓扑序、`BRCH/JOIN` 的区域约定和所有后端都建立在无环之上【读码】，也会把循环体的节点算进外层图的容量。
- **代价**：第 5 节的全部清单；与尾递归长期并存。

### 2.3 方案 (c)：两层

语法映射到 (b) 的 `LOOP` 节点，另有两个改写：

- `loop → recursion`（降级）：`LOOP(cond, body, s, c)` 改写为一张新子图 `L(with c)(s) = if cond(s) then L(body(s)) else s` 和一个 `FUNC L` 节点。总是可行，尾位置由构造保证。
- `recursion → loop`（提升，可选的优化遍）：认出“全部递归调用都在尾位置的自递归子图”，改写为 `LOOP`。

图与判据同 (b)。多出来的性质：

- **可以逐步迁移。** 还不认识 `LOOP` 的遍把它当作带子图的不透明节点；还不认识它的后端、微分、导出器在入口处先降级，得到的就是今天已经支持的尾递归。每个子系统换成原生处理是独立的一步。
- **尾递归与循环最终可以是同一种东西**：有了提升遍，手写的尾递归也得到循环节点的全部待遇，“两种写法两种图”只是源码到图那一步的事，优化之后归一。
- **代价**：(b) 的代价，加降级约 300 行、提升约 400 行，加“优化在两种表示上都要正确”的测试负担。

### 2.4 方案 (d)：给自递归子图打标记

不加节点种类，在图上加一个“这张子图是规范形状的循环”的标记（图上已有一个表示自递归的 `looped` 位，`include/camel/compile/gir/draft_graph_builder.h:75-80`），语法脱糖时生成规范形状并打上标记，后端、微分、导出器看标记而不是各自判定。

- 稳定映射：满足，同 (a)。
- 好处：不动节点集合，后端不用改，使用者省掉识别。
- 问题：标记是“形状满足某个约定”的声明，而每个遍都可能改变形状——内联把臂并进来并插入 `GATE`，特化克隆出 `loop$specN`，折叠删掉分支。每个遍要么保持约定要么清掉标记，这是一条没有任何东西强制的隐式契约；现有的 `BRCH/JOIN` 臂区域约定已经是同类的契约，文档里记录过多次因它出的问题（`docs/technical/05_graph_ir.md` 7.5–7.6 的 slot-safe prune、JUMP 占位）。循环优化（外提、展开）仍要在“函数 + 调用点”上做。
- 结论：比 (a) 多得到的有限，多出一条脆弱的不变量。不推荐。

### 2.5 方案 (e)：循环是高阶算子

`for x in xs { ... }` 就是 `foreach`，带状态的 `for` 就是 `reduce`，`while` 可以再加一个 `iterate<cond, step>(init)`。图上是一个 `OPER` 节点，函数值作为 with 实参（`by_reduce` 的实测图：`N1B [OPER :mark/reduce_arr]`，入边是 `Function(graph=__g_10__)`、初值 `0` 和数组）。

- 稳定映射：满足。
- 这就是 `for` 今天的做法，它的局限也是现成的事实：算子对遍是不透明节点；循环体是函数值，内联与即时编译跨不过去；`map` 没有求导规则（`docs/technical/26` 第 260 行）；导出器对 `map`/`reduce`/`foreach`/`range` 没有任何下降，只有被化简折掉才能导出【读码：`modules/onnx` 内无对应条目】。
- 结论：不能作为循环的图映射，但高阶算子本身保留，`map` 仍是并行的写法（4.6 节）。

### 2.6 小结

| | 稳定映射 | 新节点 | 尾递归与循环同一种图 | L1 梯度深度 | L2 macro 深度 | L3 被逐轮展开 | L4 导出要恢复 | 即时编译 |
|---|---|---|---|---|---|---|---|---|
| (a) | 是 | 0 | 是 | 保留 | 保留 | 保留 | 保留 | 须先 `std::inline`；状态在单元里时不编译 |
| (b) | 是 | 1 | 否 | 可解 | 可解 | 不存在 | 直接 | 回边明确，仍要做跨子图编译 |
| (c) | 是 | 1 | 优化后是 | 可解 | 可解 | 不存在 | 直接；旧代码可逐步退役 | 同 (b) |
| (d) | 是 | 0 | 是 | 可解但要守约定 | 可解 | 须教会化简 | 省掉识别 | 同 (a) |

## 3. (b)/(c) 相对 (a) 具体多得到什么、多付出什么

### 3.1 多得到的

**G1 自动微分：循环的梯度不再受递归深度限制，也不再是闭包链。**
(a) 的现状是 L1。有了循环节点，循环的导数可以直接写成两个循环：前向循环多携带每一轮循环体的回传所需的中间值，反向循环按相反的顺序逐轮回传（5.6 节）。不占调用栈；迭代次数只受内存限制。(a) 之下要达到同样效果，微分库得先认出尾递归、再生成“累积磁带的尾递归”和“倒着消费磁带的尾递归”，即第三处循环识别。

**G2 导出：循环节点到 ONNX `Loop` 是一次直接翻译。**
条件子图与循环体子图直接成为 `Loop` 的体；状态就是节点的 Norm 入边，不用试算；捕获的值就是 ONNX 子图对外层名字的引用；`For` 的迭代次数就是 `Loop` 的 trip count。不需要“循环之后把体再算一遍”，循环体在模型里出现一次（现在是 5 次）。元组状态按类型展开即可，`match` 决定循环与否无关紧要（它只是条件子图里的一个分支）。约 1700 行的恢复逻辑在提升遍完成后可以退役。

**G3 遍：循环不再被当成递归。**
L3 的逐轮展开不会发生在循环节点上；内联引擎对递归的各种保护（SCC 入口保护、自调用跳过、递归函数最多 8 份类型特化，`src/passes/opt/inline/engine.cpp:499-528,716`；`include/camel/runtime/draft_inline.h:55`）与循环无关。迭代次数是小常量的循环由折叠遍一次性展开（`For` 的次数是数组长度；`While` 的条件可逐轮折叠），不靠 16 轮化简。

**G4 `std::macro`：循环按迭代执行，不占求值深度。** L2 消失；换成一个迭代步数上限（见 Q9）。

**G5 循环类优化有落点。** 不变量外提是“把循环体子图里只依赖捕获端口的节点搬到外层图，多加一条捕获边”，一处局部改写；(a) 之下要给递归函数加参数并改所有调用点（第 6 节）。

**G6 即时编译有明确的编译单元。** 现在 `std::jit` 不加 `std::inline` 根本不编译循环（1.2 节），加了之后只编译自递归的纯算术函数，而且恰好在这条路径上实测到错误结果（第 10 节 D1）。循环节点给出入口、回边、状态槽位，编译成原生循环不需要“先内联成自递归再认出尾调用”。这一条的收益最大也最远：仍然要做把条件与循环体子图编进外层函数的工作（5.5 节）。

**G7 诊断：迭代次数。** 循环的执行器手里有计数器，故障可以报“第 501 轮”；尾递归的帧被复用，没有地方记。

**G8 尾位置不会被悄悄弄丢。** 用户把循环写成尾递归时，是否真的是尾调用取决于细节（调用之后再有一条语句、同步块的 `GATE`），不是的话只在迭代超过 256 次时才暴露。循环语法没有这个问题。这一条 (a) 也有（脱糖由编译器生成），但 (a) 之下它还依赖之后的遍不破坏尾位置。

### 3.2 解释器上的执行速度：没有实测依据

`std::fvm` 上一轮尾递归迭代是 `LGT; BRCH; JUMP; LADD; LADD; TAIL`，其中 `TAIL` 要释放并重新取帧、搬运实参。循环节点可以省掉取帧与搬运，但条件与循环体是两张子图，每轮要进出两次。**解释器上循环节点是否比尾递归快、快多少，本稿没有原型、没有数据**，不把它列为收益。

### 3.3 多付出的

- 一个新节点种类，引用 `GCNodeKind::Brch` 的 24 个源文件是它会触及的范围的下界【实测 grep】；第 5 节逐项估算，合计约 4500–6000 行 C++ 加测试，分 9 步。
- **两种表示并存。** 尾递归不会消失（负责人已定尾递归要优化）。在提升遍完成之前，凡是对循环做的优化，手写的尾递归得不到；凡是对尾递归的支持（现有的导出识别），仍要维护。
- 每个新遍的作者多一种要考虑的节点。现在的遍对未知种类大多是静默跳过（`generic.cpp` 的 if 链、`isValueOnly` 的 `default: false`），校验器也没有 default 分支【读码 `src/runtime/graph.cpp:231-`】，所以漏处理不会报错，只会少优化或丢顺序——需要补校验与测试来兜住。
- 语句形式的循环在 (b) 之下同样是“状态在单元里”，同样不能即时编译、求导、导出，除非再加一个把不逃逸的单元提升为状态边的遍（6.5 节）。这一条 (a)(b)(c) 没有区别。

## 4. 语法与语义

本节不依赖 Q1 的选择。

### 4.1 语法

`for`、`in` 已是词法记号；`while` 需要新增为关键字（现有 `.cml` 文件里没有把 `while` 用作标识符的【实测 grep `test/cases`、`stdlib`、`examples`】）。在 `ctrlExpr` 下增加两条产生式，循环体复用 `stmtBlock`（因此 `sync` 写在花括号前，与 `then sync { ... }` 一致）：

```
ctrlExpr
    : IF logicalOrExpr THEN blockExpr (ELSE blockExpr)?
    | MATCH identRef '{' matchCase+ '}'
    | TRY stmtBlock catchClause+ (FINALLY stmtBlock)?
    | WHILE (dataDecl ';')? logicalOrExpr stmtBlock                    // 新增
    | FOR identDef IN logicalOrExpr (';' dataDecl)? stmtBlock          // 新增
    ;
```

条件后面直接跟 `{` 不产生歧义：`logicalOrExpr` 的后缀只有下标、调用、尖括号实参和 `!`，`{` 不能接在表达式后面【读 `src/parse/syntax/parser_expr.cpp` 的 `parseAnno`，即语言参考 8.5 的 `annoExpr`】。

```camel
while i <= n sync { ... }                       // 语句形式
for x in xs sync { ... }
for i in range(a, b) sync { ... }               // range(a, b) 是普通表达式，值是数组

while let (i, acc) = (1, 0); i <= n { ... }     // 表达式形式：循环头里声明状态
for x in xs; let acc = 0 { ... }
```

数组字面量里的推导 `[e for x in xs if c]` 不在本稿范围内，保持现在的诊断（“write it with 'map' and 'filter'”）；它对应的是无序的 `map`/`filter`，不是循环（Q8）。

### 4.2 两种形式

**语句形式**：循环头里没有声明。没有值（类型为 void）。状态是循环体与条件读写的、在循环外声明的 `var`。

```camel
var i = 1
var acc = 0
while i <= n sync {
    acc = acc + i
    i = i + 1
}
```

**表达式形式**：循环头里用 `let` 声明状态及其初值。循环体这个块的值是下一轮的状态（块的最后一个表达式，或 `return`，与分支臂完全相同的规则，见 1.4 节 `block_return.cml`）。整个循环表达式的值是最终状态。状态名只在条件与循环体里可见。

```camel
let (i, acc) = while let (i, acc) = (1, 0); i <= n {
    (i + 1, acc + i)
}

let total = for x in xs; let acc = 0 {
    acc + x * x
}

// 循环体可以是多条语句的块；值是最后一个表达式
let h = while let (h, k) = (x, 0); k < 6 && sum(h * h) >= 1.0 {
    let z = tanh(h @ w)
    (z * 0.3 + h * 0.6, k + 1)
}
```

表达式形式没有 `var`、没有赋值，循环体是纯的数据流：它可以被求导、被导出、被即时编译，按依赖求值的规则对它自然成立（循环体的值被下一轮用到，最终状态被外面用到）。它与 `reduce`（有状态的 `for`）和尾递归（`while`）表达的是同一件事，只是不用另写一个函数、不用把每轮不变的量也当参数传。

为什么两种都要：只有语句形式的话，循环在被求导的函数里不能用（2.7：梯度经过 `var` 的读写直接拒绝；“模型的计算应当用 `let` 写成纯的数据流”）；只有表达式形式的话，通用程序里“边循环边打印、边往数组里追加”的写法不方便。这是 Q2。

**类型**：循环体的值的类型必须与状态的类型一致（与分支各臂的统一规则相同，`builder.cpp:3078-3098`）；张量形状在轮与轮之间变化时按现有的 `unify` 放宽一次，仍不一致是编译期错误，用 `as` 显式转换。

### 4.3 循环携带的状态从哪来

- **表达式形式**：循环头里声明的名字，不多不少。图上是 `LOOP` 的 Norm 入边（(a) 之下是递归函数的参数）。由循环头决定，不由循环体的内容决定。
- **语句形式**：**没有循环携带的状态边。** `var` 是共享单元，条件子图与循环体子图通过捕获端口拿到同一个单元（与分支臂、lambda 捕获变量的做法相同，`docs/technical/18` 8.1），读是 `:var/get`，写是 `:op/assn*`。循环在外层图里记为“对它的子图写过的每个被捕获变量的一次写入”，沿用分支的做法（`builder.cpp:3194-3213`：进入分支等于调用它的臂）。

不采用“把循环体里被赋值的 `var` 拷进来、循环结束再拷回去”的定义：那是把按引用实现成传值再回写（第 5 节误读 4），当循环体调用的函数或闭包也持有同一个变量时，结果会不同。把不逃逸的单元变成状态边是一个优化遍的事（6.5 节），不是语言的映射。

### 4.4 循环体是不是同步块，效应何时执行

循环体是一个块，它是不是同步块由它自己写没写 `sync` 决定（2.4：函数的行为由它自己决定；循环体与分支臂一样是自己的子图）。外层是不是同步块不改变循环体内部。

| 写法 | 循环在哪 | 行为 |
|---|---|---|
| `for x in xs sync { println(x) }` | 同步块内 | 执行，按元素顺序打印 |
| 同上 | 同步块外 | 循环没有值、不写任何变量，没有东西依赖它：**整个循环不执行**，告警 `EffectNotExecuted`。与今天的 `foreach` 相同（1.4 节实测） |
| `for x in xs sync { acc = acc + x }` | 同步块外，之后有人读 `acc` | 执行：循环是 `acc` 的写入者，之后的读取排在它后面。之后没人读 `acc` 则不执行（2.7“`wait` 之后无人读取”同理） |
| `for x in xs { println(x) }`（循环体不是同步块） | 任何位置 | 语句形式的循环体的值不被使用，体内没有任何节点被依赖：**循环体什么都不做** |
| `let s = for x in xs; let acc = 0 { acc + x }` | 任何位置 | `s` 被用到就执行；循环体是纯数据流，不需要 `sync` |
| 表达式形式的循环体里写 `println` | — | 与普通块一样：循环体是同步块则执行，否则不执行并告警 |

第四行是语句形式特有的问题：迭代之间的依赖（这一轮写的 `i`，下一轮的条件要读）在循环体子图内部是看不见的，所以**语句形式的循环体只有是同步块时才有意义**。三种处理（Q3）：

- A. 语句形式的循环体隐式地是同步块。写起来最短，但引入一条“这个块没写 `sync` 却是同步块”的特例。
- B. 语句形式的循环体必须写 `sync`，不写是编译期错误，诊断指向花括号并说明原因。源码里凡有顺序的地方都看得见 `sync`。
- C. 照常编译，沿用 `EffectNotExecuted` 告警。合乎现有规则，但写出来的循环什么都不做，`while` 还会不终止。

建议 B。它不是“把未使用的效应不执行改成报错”（误读 1）：被拒绝的是一个按定义不可能有任何作用的写法，规则本身不变；以后想放宽成 A 也不破坏已有程序。

### 4.5 `break`、`continue`、循环内的 `return`

- **循环内的 `return`**：含义已经由现有规则确定——它结束循环体这个块并给出块的值（表达式形式下就是下一轮的状态）。它不离开函数，也不结束循环。`if` 的臂里今天就是这样（1.4 节）。不需要新规则。
- **`break` / `continue`：建议不加入语言。** 它们是从块的任意嵌套深度跳出的非局部控制。在图上，`break` 之后的每个节点都要挂上“还没有 break”的条件，循环体子图的形状取决于 `break` 写在第几层的哪个分支里——这正是 `try`/`catch` 被排除的理由（2.9）。等价的稳定写法：
  - 提前结束：把条件写进循环头。`for` 需要提前结束时用 `while` 加下标，或者给 `for` 加一个可选的继续条件（Q5）：`for x in xs while !found sync { ... }`，图上是同时带数组与条件子图的 `LOOP`，每轮开始前检查条件。
  - 跳过本轮剩余部分：用 `if` 把剩余部分包起来。
- 写了 `break`/`continue` 给出一条诊断，指向上面的写法。

### 4.6 迭代之间的顺序与并行

- `while` 与 `for` 的迭代**严格按顺序**：下一轮的条件与状态依赖上一轮。`for` 与 `foreach`、`reduce` 一样按元素顺序。
- **没有并行的循环写法。** 元素之间互不依赖的计算用 `map`/`filter`（无序、可并行，2.7），需要无序归约用 `para` 模块的 `unordered_reduce`。循环节点在 `std::tf` 里是一个顺序执行的项。
- 循环体**内部**的节点仍按依赖求值：循环体不是同步块时，一轮之内互不依赖的节点可以乱序或并行。

### 4.7 与 `wait` 的关系

语句形式的循环写了被捕获的变量，就和“调用一个写了被捕获变量的函数”“进入一个有臂写了变量的分支”是同一种东西（2.6）：

- 同步块内：已有顺序，写不写 `wait` 都一样。
- 同步块外：不加 `wait` 时，循环排在这些变量此前的写入者之后，此后对这些变量的读取排在循环之后，给出 `IgnoredSideEffect` 告警；加 `wait` 时，循环还排在此前用过这些变量的值的操作之后（A → 循环 → B）。
- 语法上 `wait` 现在只能加在 `assignExpr` 与块前面（`waitExpr`、`blockStmt`），不能加在 `if` 前面；循环沿用 `if` 的现状，需要时把循环写在 `wait sync { ... }` 块里。是否允许 `wait while ...` 与 `wait if ...` 一并留给负责人（Q10）。
- 表达式形式不涉及 `var`，`wait` 对它没有可依据的东西。

### 4.8 空循环与不终止的循环

- 一轮都不执行（`for` 遍历空数组、`while` 的条件一开始就是假）：语句形式什么都不发生；表达式形式的值是初始状态。这也是状态必须在循环头里给初值的原因。
- 不终止的循环一直运行，不设迭代次数上限（递归深度上限针对的是栈，循环不占栈）。执行器在每次回边处设垃圾回收安全点，循环里不断分配时回收器能运行。
- `std::macro` 提前求值时遇到不终止的循环会让编译不结束，求值器需要一个迭代步数上限，超过算求值失败（Q9）。
- 必然不终止的写法（`while true` 且循环体不是同步块）编译器可以告警，不是错误。

### 4.9 其他

- **泛型函数里的循环**：条件与循环体子图在实例化时随函数体一起构造，图上只有具体类型，无特殊之处。
- **循环里的故障**：带位置终止，诊断加上迭代序号（从 0 起）。`attempt` 隔离的边界是子图，循环体是子图，隔离一轮或隔离整个循环都是普通的调用隔离。
- **循环变量**：`for x in xs` 的 `x` 是不可变绑定（循环体子图的一个端口）。

### 5.6 自动微分（`modules/autodiff/pullback.cpp` 2347 行）

现有做法【读码与文档】：对图 `g` 构造 `g.fwd : 输入 => (值, 回传函数)`；回传函数是捕获了中间值的闭包；“递归不需要特殊处理：`D[run]` 调用 `D[run]`，每一步的回传捕获下一步的回传”。分支的每个臂作为子图求导，`JOIN` 汇合 `(值, 回传)` 对。未知节点种类报 `cannot differentiate through node kind`（`:1864`）。

**现有对线性递归的做法能否复用？** 能作为第一步的兜底，不能作为终点。第一步在求导前降级，得到的就是今天的行为，包括 L1（迭代一百多次即超过深度）。它不能复用为终点的原因：闭包链是用调用栈保存每一轮中间值的，循环节点的意义恰恰是不占栈。

**循环节点的导数（拟议）。** 只对表达式形式（纯的循环体）定义；语句形式经过 `var`，按 2.7 拒绝。

- 前向：一个 `LOOP`，状态多一项 `tape`。循环体换成 `body.fwd`，它返回 `(s', pb_i)`，把 `pb_i`（这一轮循环体的回传闭包，捕获了这一轮的中间值）追加到 `tape`。出值 `(s_n, tape)`。
- 反向：一个 `For` 型 `LOOP` 倒序遍历 `tape`，状态是 `(ds, dc)`：`(ds, dc_i) = pb_i(ds)`，`dc = dc + dc_i`。出值是对初始状态的梯度 `ds_0` 与对捕获值（权重）的梯度 `dc`。
- 条件子图不参与求导（它产出 bool）；数据相关的迭代次数体现在 `tape` 的长度上。
- 没有递归，没有闭包链，磁带是一个普通的数组值，由垃圾回收管理——与文档 26 “闭包就是磁带、不需要运行期磁带对象”的思路一致，只是把链换成了数组。

未解决的一点：`tape` 每轮追加一个元素。“`append` 一类的操作返回新值”（2.9），如果每次追加都复制数组，前向是 O(n²)。两个办法：循环节点增加“收集输出”（循环体每轮交出一个值，执行器把它们收成数组，相当于 ONNX `Loop` 的 scan output；导出时直接对应）；或运行时对只有一个持有者的数组原地追加。前者改节点的定义，后者改运行时。**这一点本稿没有验证，是第 9 节列出的最不放心之处之一。**

规模：约 500–700 行；风险高。

(a) 之下：不改则保留 L1；要解决 L1 就得在微分库里识别尾递归并生成上述两个循环的递归写法。

### 5.7 ONNX 导出（`modules/onnx/exporter.cpp` 3997 行）

循环节点到 `Loop`（拟议）：

- `While`：先在外面算一次 `cond(s_0)` 作为初始条件；`Loop` 的体是 `s' = body(s); cond_out = cond(s')`，条件子图在体内出现一次。无 trip count。
- `For`：trip count 是数组长度；体内按迭代序号取元素。带继续条件的 `for … while` 同时有 trip count 与条件。
- 携带的值就是 Norm 入边，按类型把元组与结构体展开成叶子；捕获的值是体对外层名字的引用，常量继续在体内折叠。
- 现有的拒绝条件里仍然成立的：状态的 dtype 或形状在轮与轮之间变化、状态的叶子不是张量或标量。不再有的：试算找携带集合、“循环后再算一遍”、`match` 决定循环、元组作为状态、多个返回路径的逐叶合并。
- 梯度：5.6 的前向循环与反向循环各是一个 `Loop`，磁带是前向 `Loop` 的 scan output、反向 `Loop` 的输入，循环体执行 2n 次而不是 `n + n(n-1)/2` 次。闭包不能作为 ONNX 的值，磁带的元素要按闭包捕获的叶子展开；导出器已经把闭包当作“导出期的值（函数 + 捕获的值）”处理（`value.h` 的 `ClosureKind`），这里是把它推广到数组。

规模：前向约 250 行；梯度约 300 行。现有约 1700 行的递归恢复在提升遍完成并稳定之前保留（手写的尾递归仍走它）。

**循环节点到 ONNX Loop 是否比从递归恢复更直接？** 是，前向的翻译是结构上的一一对应。梯度的导出取决于 5.6 的磁带方案。

### 5.8 `std::cpp` 转译（`src/passes/trans/cpp/runtime_emitter.cpp` 1203 行）

现在生成 C++ 递归函数，尾调用留给 C++ 编译器；对未知节点种类登记 `unknown runtime node type` 并拒绝导出（`:530-531`）。循环节点生成 `for (;;) { if (!cond(s)) break; s = body(s); }`，条件与循环体仍是各自的 C++ 函数（由 C++ 编译器内联）。约 150 行。生成的代码不再依赖 C++ 编译器做尾调用消除。第一步用降级。

### 5.9 调试器与诊断

- `tools/debugger`（约 4200 行）靠 NodeVM 的 `HitGirNode` 钩子工作，按节点的源码来源设断点与单步；没有调用栈命令【读码】。循环体是子图，每轮进入一次，按行与按节点的单步都自然成立。需要加的：进入循环节点时的一个停靠点（显示状态的当前值与迭代序号）。约 100 行。
- 故障诊断：`ExecutionSite`（`include/camel/core/error/runtime.h:66-75`）只有一个来源位置与帧深度。加一个可选的迭代序号字段，由循环的执行器在故障向外传时填入。约 60 行。
- 新的编译期诊断：`break`/`continue` 不支持；语句形式的循环体不是同步块（若 Q3 选 B）；循环体的值与状态类型不一致。

### 5.10 随机程序生成器 `test/tools/progen`

现有【读码】：生成尾递归、非尾递归、树递归、互递归、带效应的递归、`var`、同步块、`wait`、闭包与 `map`/`filter`/`reduce`/`foreach`；没有循环。参考求值器是 `model.py` 里一个急切求值的 Python 解释器，带步数上限 `MAX_STEPS = 200_000`。

要加的：`model.py` 的源码输出与 `Evaluator.stmt` 的循环分支（两种形式）、`effect_violations` 把循环体算作效应位置；`generate.py` 的 `FEATURES` 条目与生成方法（迭代次数有界，仿 `recursive_function`）、`VERSION`；`reduce.py` 里“把循环体拼到外面 / 缩小循环体”的化简步骤。约 200 行 Python。它应当紧跟第一步合入：降级遍、每个后端的原生执行、每个遍的专门处理，正确性都靠它在全部流水线上做差分。

## 6. 循环类优化

现在一个都没有【读码：在 `src/passes/opt` 与 `modules/tensor` 里搜索 loop / invariant / hoist / induction / licm，没有循环优化】。实测佐证：`invariant.cml` 里每轮不变的 `k * k + 7` 在 `std::opt::simplify` 之后仍在每一份循环体里。

| 优化 | 方案 (a)：自递归子图 | 方案 (b)/(c)：`LOOP` 节点 |
|---|---|---|
| **6.1 不变量外提** | 不变量是“只依赖每次递归原样传下去的参数”的节点。外提要给函数加一个参数，并改写**所有**调用点（递归调用与外部调用），或者拆成“外壳 + 工作函数”。跨函数签名的改写；函数被当作值传递时不能做。难 | 不变量是“循环体子图里只依赖捕获端口”的节点。把它搬到外层图 `LOOP` 之前，加一条捕获边。一处局部改写，约 150 行。要注意：`While` 可能一轮都不执行，所以只外提纯的、不会出故障的节点（除法、下标不外提，或者挂在“至少执行一轮”的条件下）。中 |
| **6.2 归纳变量与强度削减** | 要先认出“某个参数每次递归加一个常量”，即先做 (b) 的提升 | 状态边 `i' = i + c` 在循环体子图里一眼可见；`i * 4` 换成多携带一个每轮加 4 的状态。约 200 行。中 |
| **6.3 范围分析、越界检查消除** | 同上，要先认出循环 | `For` 遍历数组时元素访问不需要检查；`for i in range(a, b)` 时 `i ∈ [a, b)`，体内 `xs[i]` 的检查在 `b <= len(xs)` 时可消。需要先有一个值域的表示（现在没有）。配合 2.7“编译期能知道长度时越界是编译期错误”，可以把一部分循环内的越界提前到编译期。难（基础设施不存在） |
| **6.4 `for` 遍历 `range` 不物化数组** | 不适用（手写尾递归本来就不物化） | `for i in range(a, b)` 的稳定映射是“遍历一个数组值”；一个遍把“`For` 的数组来自 `:struct/range`”改写成带计数状态的 `While`，省掉数组。约 100 行。易 |
| **6.5 把不逃逸的变量单元提升为状态** | 把捕获的单元变成递归函数的参数与返回值。同样需要逃逸判定，另加签名改写 | 语句形式的循环捕获单元 `v`。若 `v` 在外层函数里声明，且只被直接读写（没有被闭包捕获、没有传给 `var` 形参、没有作为值传走），则：循环前 `:var/get`，作为状态边进出，循环体内的读写换成端口与返回值，循环后 `:op/assn` 写回。之后循环体是纯的，可以即时编译与导出。约 300 行。中；逃逸判定是全部的难点，现有的 `CaptureSummary`（`builder.cpp` 的 `capturedWritesOf`）只在建图期存在，遍里没有对应物 |
| **6.6 循环融合** | 很难：两个递归函数合成一个 | 两个相邻的 `For` 遍历同一个数组、后一个不依赖前一个的最终状态时，合并循环体。约 200 行。中；收益主要在张量之外的代码 |
| **6.7 向量化** | — | 循环体对每个元素做的是纯标量算术且状态是结合的归约时，换成 `map`/张量算子。这是把循环改写成 Camel 已有的数据并行形式，而不是生成 SIMD 指令。难；优先级低，这类计算本来就该写成 `map` |
| **6.8 常量次数的展开** | 现有的 `simplify` 逐轮展开，受 16 轮与 4096 节点预算限制（L3） | 折叠遍一次展开，按循环体节点数乘次数检查增长预算；次数未知或过大则不动。约 150 行。易 |
| **6.9 无效应且结果无人使用的循环删除** | 已有（调用无人使用且被调图无效应） | DCE 加一条。易 |

顺序建议：6.8、6.9、6.4（简单且直接消掉实测到的浪费）→ 6.1 → 6.5 → 6.2。6.3、6.6、6.7 等有需求再做。

## 8. 要负责人裁定的问题

### Q1 图上的映射

程序：

```camel
let (i, acc) = while let (i, acc) = (1, 0); i <= n { (i + 1, acc + i) }
```

- (a) 三张图（函数 + 两个臂），与 1.1 节相同；图上没有任何“循环”字样。
- (b)/(c) 一个 `LOOP` 节点 + 条件子图 + 循环体子图（2.2 节）。

候选：(a) 脱糖为自递归子图；(b) 循环节点；(c) 循环节点 + 双向转换。
**建议 (c)**，先做降级方向。理由见第 3 节；退路见第 7 节末。

### Q2 状态从哪来：语句形式、表达式形式，还是都要

```camel
// 语句形式：状态在 var 里
var acc = 0
for x in xs sync { acc = acc + x * x }

// 表达式形式：状态在循环头里，循环体的值是下一轮的状态
let acc = for x in xs; let acc = 0 { acc + x * x }
```

图：语句形式是 `k = 0` 的 `LOOP`，两张子图捕获 `acc` 的单元，体内是 `:var/get`、`:op/assn_l`；表达式形式是 `k = 1` 的 `LOOP`，一条状态边，体内只有 `:op/mul_l`、`:op/add_l`。

候选：只要语句形式；只要表达式形式；都要。
**建议都要，表达式形式为主。** 只有语句形式时，循环在被求导、被导出的函数里用不了（2.7）；并且它在三百万次迭代的实测里比状态作参数的写法慢约 5 倍（1.2 节）。

### Q3 语句形式的循环体是否必须是同步块

```camel
var i = 0
var acc = 0
while i < n { acc = acc + i; i = i + 1 }      // 循环体不是同步块
```

按现有规则，体内两条赋值都没有东西依赖，不执行；循环不终止。今天分支臂的同类行为：`{ a = 1; b = 2 }` 只执行 `b = 2`（`examples/block_effects.cml`，实测）。

候选：A 隐式同步；B 必须写 `sync`，否则编译期错误；C 照常编译并告警。**建议 B。**

### Q4 表达式形式的确切写法

候选：

```camel
// α：循环头里用 let，分号分隔（本稿采用）
while let (i, acc) = (1, 0); i <= n { (i + 1, acc + i) }
for x in xs; let acc = 0 { acc + x * x }

// β：状态声明放在循环体之前的圆括号里
while (i = 1, acc = 0) i <= n { (i + 1, acc + i) }
for (acc = 0) x in xs { acc + x * x }

// γ：不加新写法，表达式形式就是 reduce 与尾递归，由提升遍把它们变成 LOOP
```

**建议 α**：复用现有的 `dataDecl` 与解构，文法无歧义。γ 不加语法，但尾递归每轮不变的量也要当参数写出来，而且能否得到循环节点取决于提升遍是否认得出。

### Q5 `break`、`continue`，以及 `for … while`

```camel
for x in xs sync {
    if x < 0 then sync { break }      // 图上：这之后的每个节点都要以“没有 break”为条件
    println(x)
}
```

候选：不加 `break`/`continue`（写了给诊断）；加。另：是否提供 `for x in xs while cond { ... }`。
**建议不加 `break`/`continue`；提供 `for … while`**（图上是同时带数组与条件子图的 `LOOP`，稳定）。

### Q6 `for` 遍历什么

`for x in e` 里的 `e`：只允许数组；还是也允许字符串（按字节还是码点）、元组、将来的 `Map`/集合。
**建议第一版只允许数组**（`range(a, b)` 的值就是数组；不物化是优化 6.4）。其他类型等映射与集合的内建类型落地时一并定。

### Q7 循环节点的子图：条件与循环体分开，还是合成一张“步”图

- 分开（本稿采用）：`cond: s -> bool`，`body: s -> s'`。先判断后执行，与 `while` 的含义一致；条件可以单独折叠、单独分析迭代次数。
- 合一：`step: s -> (继续?, s')`，与 ONNX `Loop` 的体同形，少一个图指针；但“先执行一轮再判断”，`while` 要在外面多套一个分支。

**建议分开。**

### Q8 数组推导 `[e for x in xs if c]`

文法里已有，目前报不支持。它是无序的 `map`/`filter` 的另一种写法，图上是两个算子节点，映射稳定。是否随循环一起实现？**建议不随循环做**，单独立项；它与循环节点无关。

### Q9 `std::macro` 求值循环的上限

macro 函数里的循环在 `std::macro` 下被提前求值；不终止的循环会让编译不结束。候选：迭代步数上限（比如十万步，超过算求值失败，按 2.7 是编译期错误）；不设上限。**建议设上限**，数值请负责人定，并写进 `docs/cli.md` 的资源上限表。

### Q10 `wait` 能否直接加在循环与 `if` 前面

现在文法是 `dataExpr : waitExpr | ctrlExpr`，`wait if …` 不合文法。循环作为 `ctrlExpr` 沿用。是否把 `wait` 扩到 `ctrlExpr`（`wait while …`、`wait if …`）？**建议暂不扩**，需要时写 `wait sync { … }`；`docs/technical/18` 3.4 记录了块级 `wait` 目前没有对称的下降逻辑，一并处理更合适。

### Q11 循环头的状态与循环体的值类型不一致时

`while let h = x; … { tanh(h @ w) }`，`x` 是 `Tensor<f32, const [2, 2]>`，循环体给出的形状推不出来。候选：按分支的 `unify` 放宽一次，不行则报错并提示 `as`；一律要求显式标注。**建议前者**，与分支一致。

### Q12 微分的磁带放在哪（5.6）

候选：循环节点增加“收集输出”；运行时对唯一持有的数组原地追加；先用带复制的 `append`，量大再说。**建议先做小原型比较前两者再定**；这一项只影响步 8，不阻塞前面的步骤。

## 9. 推荐，以及最不放心的地方

**推荐**：Q1 选 (c)，先做降级方向；Q2 两种形式都要；Q3 选 B；Q4 选 α；Q5 不加 `break`/`continue`、提供 `for … while`。按第 7 节的顺序做，步 1–3 先合入并停下来看一次。

**最不放心的地方**，按严重程度：

1. **两种表示长期并存。** (c) 的归一依赖步 11 的提升遍；在那之前，循环优化只作用于循环节点，手写尾递归仍走老路，导出器里约 1700 行的恢复逻辑不能删。如果步 11 迟迟不做，结果就是“多了一种节点，旧的一样没少”。这是推荐 (c) 而不是 (b) 的原因，也是 (c) 的主要风险。
2. **微分方案没有验证。** 5.6 的前向/反向循环是纸面设计：磁带的追加代价、闭包数组的导出、与现有“回传是闭包”的接口怎样对接，都没有原型。如果做不顺，G1 与导出梯度的线性代价这两项收益就落空，而它们是推荐 (c) 的四条依据中的两条。
3. **解释器上的速度没有数据。** 3.2 节已说明。本稿没有把它算作收益，但“加了循环节点却没有变快”是完全可能的结果；真正的速度收益押在步 10 的即时编译上，那一步风险最高，而且现有的即时编译路径刚被实测到错误结果。
4. **语句形式的循环天生是慢路径。** 状态在单元里，读写是算子；不做 6.5 的提升，它不能即时编译、求导、导出。通用程序里人们最顺手写的恰恰是这种形式。6.5 需要逃逸分析，而副作用与引用的追踪是原则 2.8 承认的薄弱处。
5. **不透明处理的安全性靠人工清点。** 现有的遍与校验对未知节点种类大多静默跳过（5.2、5.3）。步 1 要求把 `carriesOrdering`、`mayHaveEffects`、SCC 的边、`traceGraphs` 都补上，漏一处的后果是丢顺序或丢效应而不是报错。清单是读代码列出的，可能不全；步 3 的 `progen` 差分是主要的兜底。
6. **Q3 选 B 是否合负责人的意。** 它在“循环体是普通的块”之上加了一条针对语句形式的要求；如果负责人认为循环体天然就该有序（选 A），语义更顺手，但多一条隐式规则。

## 10. 验证状态与发现的现有缺陷

### 10.1 实际运行验证的

- 尾递归、`reduce`、`foreach` 三种写法的图（`std::rgir`）；尾递归内联前后的图与 `std::fvm` 字节码。
- `examples/` 下各程序在 `std::nvm`、`std::fvm`、`std::jit`、`std::inline std::jit`、`std::opt std::fvm`、`std::opt::simplify std::fvm`、`std::tf` 上的结果（除 D1 外一致）。
- L1（梯度的深度上限，N = 50/100/200/300/1000，四种流水线）、L2（macro 64 层）、L3（`simplify` 的逐轮特化，图与统计）、L4 中“模型里 5 个 `Tanh`、1 个 `Loop`、4 个 `If`”。
- 1.4 节全部六条（循环体内的效应、`foreach` 在同步块外、臂内赋值、块内 `return`、循环内故障的诊断、不终止）。
- `std::jit` 不加 `std::inline` 时不编译尾递归循环；状态在 `var` 里时回退到解释器（`-v` 的日志）。
- 1.2 节的耗时（各三次，机器上同时有其他负载，只能看量级）。
- `std::cpp` 对尾递归的输出。

### 10.2 读代码的推断，没有运行验证

- 各后端尾调用的执行细节、安全点的位置、即时编译的资格判定与 Windows/Linux 的差别。
- 各遍对未知节点种类的行为（5.3）、校验器没有 default 分支。
- 导出器恢复循环的行数划分（约 1700 行）与被拒绝的形状清单；梯度导出的平方代价。
- 微分对递归、分支的处理方式。
- 第 5 节全部的行数估计；第 6 节各优化的难度判断。
- 第 2.2 节 `LOOP` 的图是拟议的记法，没有任何实现。

### 10.3 没有查的

- 循环节点在解释器上相对尾递归的速度（没有原型）。
- 5.6 的微分方案与磁带代价。
- `tools/debugger` 的实际操作（只读了钩子与命令的代码）。
- Windows 上的行为（实验都在 Linux 容器里；即时编译的自尾调用在两个平台上走不同的代码）。
- `std::tf` 在多线程下对带捕获写入的循环的行为。
- 泛型函数里的循环、循环与 `attempt`、循环与类型函数的交互（都只做了推理）。
- `progen` 的改动量只读了结构，没有试写。

### 10.4 发现的现有缺陷

**D1 `std::inline std::jit`：尾递归函数第二次及以后的调用返回错误结果。**

最小复现 `examples/defect_jit_second_call.cml`：

```camel
func walk(i: int, j: int, m: int, acc: int): int {
    return if j >= m then acc else walk(i, j + 1, m, acc + i * j)
}

func main(): int sync {
    println(walk(1, 0, 2, 0))     // 期望 1
    println(walk(1, 0, 2, 0))     // 期望 1
    println(walk(2, 0, 3, 5))     // 期望 11
    return 0
}
```

| 流水线 | 输出 |
|---|---|
| `std::nvm`、`std::fvm`、`std::jit`、`std::inline std::fvm`、`std::opt std::jit`、`std::opt::simplify std::jit` | `1 1 11` |
| `std::inline std::jit` | `1 2 17` |

同一个函数只调用一次时结果正确；三个参数、循环体里没有中间乘法的 `sum_tail.cml` 调用两次也正确。嵌套循环的形式（`examples/nested_tail.cml`，外层循环每轮调用一次内层）在 `std::inline std::jit` 下得到 2686515000、在 `std::opt::simplify std::jit` 下得到 2680368756，正确值是 2011522500；按参数规模缩小后 `N=2 M=2` 时得到 2 而不是 1。`std::inline` 之后该函数只调用自己，被编译成原生代码（1.2 节）；原因没有定位，没有修改。

**其余观察（不是新缺陷）**：

- `docs/technical/19_tail_call_optimization.md` 描述的 `twinFrame` 与 NodeVM 现在的实现（`tailLow`/`tailHigh`）不一致；`docs/technical/16_inline_rewrite_algorithm.md` 里的若干标识符（`buildSccGraphPlan`、各 `k…PerScc` 预算）在代码里已不存在。两处文档落后于代码【读码】。
- `modules/onnx/exporter.cpp:730` 附近的注释仍说循环体的分支用 `Where` 合并，代码与文档 26 自 2026-10-06 起用的是 `If`【读码】。
- 已归档的 `test/cases/opt/progen/findings/simplify_recursion_never_ends.cml`（F19）：`std::opt::simplify` 之后一个互递归在 `std::nvm`、`std::tf` 上超过递归深度而 `std::fvm`、`std::jit` 正常结束。它是既有发现，与“尾位置是否成立会被遍和后端的差异影响”这一点有关，本稿没有进一步分析。
