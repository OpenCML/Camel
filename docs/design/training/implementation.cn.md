# 训练基础设施实现进度

依据：[训练基础设施设计](README.cn.md)，2026-10-18。本文记录实现与实测，不替代设计稿的阶段验收。

## 已实现：设备参数树

- `Device<{a: A, b: (B, C)}>` 在类型构造时规范化为 `{a: Device<A>, b: (Device<B>, Device<C>)}`，不是运行时转换。泛型返回类型 `Device<P>` 在代入具体的 `P` 后同样规范化。
- 模块类型构造接口 `OtherType::cloneWithParams` / `cloneWithArguments` 返回 `Type*`，允许结果是普通结构体或元组。已有模块仍可用协变返回类型返回 `OtherType*`。
- `tiles::upload` / `download` 接受嵌套结构体和普通元组，保留字段顺序、元组位置与张量静态细化。当前实际传输支持 f32 张量和 `float` 叶子，包含零元素张量。
- 不支持的 `Device<T>` 叶子在编译期报出完整路径。可空、可失败包装和可变单元不按普通元组展开。
- 传输先将全部叶子复制为本机拥有的快照或设备存储所有权，再调用 CUDA；CUDA 调用不持有 Camel 移动堆指针。重建结果时禁止收集，保持尚未完成的嵌套对象有效。

## 服务器手动验证

构建与执行均在一台 Linux 服务器上，开发机不编译、不训练。使用标准 `npm run build`，安装为项目内独立运行时 `.camel-device-tree-v1` / `.camel-device-tree-v2`，保留原训练运行时。

`test/cases/modules/tiles/device_tree.cml` 在物理 GPU 2 上以 `std::macro std::nvm` 执行，六项误差均为 `0.0`：整树往返、零元素张量、f64 标量、自动微分的损失、设备端梯度更新，以及原参数所有权。显式展开的类型与 `Device<Model>` 双向兼容，泛型上传返回 `Device<P>`。

`device_tree_invalid.cml` 在设备选择为 `invalid` 时编译即失败，错误指出 `$.block.1.label` 的 `string` 叶子，无需初始化 GPU。按观察到的输出补充计划条目；未运行全量测试。

DDPM 项目新增 `examples/device-tree-step.cml`，在真实的已封存图像批量上，从随机初始化分别执行现有 VAE 和潜变量扩散模型的前向、反向与 Adam 更新。参数及优化器返回值使用 `Device<Parameters>`、`Device<(AE, AE, AE)>`、`Device<(LD, LD, LD)>`；潜变量直接保留在设备上加噪，无需先下载。新接口直接下载嵌套优化器树，写出 390 个 `.npy` 叶子。

首次运行记录：VAE loss `0.3690241159925844`，扩散噪声 MSE `1.025955108172196`；参数平方变化量分别为 `0.00011043555311198371`、`0.00018747812900134675`。这是接口与更新流程的实测，不代表图像生成质量或生产规模训练完成。

在最终 v2 运行时独立重跑相同输入，390 个文件均为有限 f32 数值，文件字节与首次运行完全相同。运行记录保存在服务器 `runs/device-tree-training-001` / `runs/device-tree-training-002`。

## 尚未完成

`std::tree` 已按作者修订完成编译期展开，见 [参数树实现](tree.cn.md)。`Bytes`、文本/二进制文件接口和原子替换已实现，见 [二进制接口](bytes.cn.md)。DDPM 已删除参数源生成器及六个生成模块，改用显式 Camel 初始化与通用树优化器；实际模型迁移前后的 390 个状态文件字节一致，VAE/扩散的短程连续训练与中断恢复也分别有 176/344 个状态文件字节一致。

第一阶段仍缺原生树检查点和遗留二进制字符串接口的收口。张量/Bytes 小端互转已实现并在独立服务器运行时验证。设备随机数、完整常驻训练步、传输统计、真正的 bf16 存储、重计算、耐久性与四卡训练继续按设计阶段推进；先前的 NCCL 草稿已独立暂存，不作为可用功能。

手动运行还暴露了已有的声明类型问题：`let p: Model = { ...带具体形状的张量... }` 通过结构可赋值检查后，又因结构体的显式转换只接受相同类型而被拒绝。当前示例通过返回类型为 `Model` 的初始化函数构造参数。该缺陷尚未修复；不能为通过测试而修改显式转换的既定语义。

## 持续目标与实施顺序（2026-10-19）

用户已要求以 Codex goal 持续完成设计稿及从零训练文生图项目。目标处于 active 状态，没有人为设置 token 预算。阶段完成以设计稿第 11 节的验收为准，训练进程启动、损失下降或样图文件存在不能代替生产质量验收。

当前补齐第一阶段时发现的前置依赖：设计原则 5.9 早已裁定显式类型实参 `f::<T>(x)`、与上下文参数并用 `f::<T><w>(x)`，以及由期望类型推出返回位置变量。现已接入前端和算子类型解析，不能以 dtype 字符串或参照树接口替代。训练设计稿中的 `from_bytes<f32>`、`load_tree<T>` 记法已更正为 `from_bytes::<f32>`、`load_tree::<T>`。
