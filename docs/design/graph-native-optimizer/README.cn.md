# 图原生的优化器：用 Camel 写图变换与图优化

负责人定方向（设计原则第 1 节"图变换与图优化用 Camel 自己写"）；决策者起草宏观设计。次序由负责人另定，本稿只给结构、边界和判据。

## 1. 为什么

- **一门语言里同时写程序和优化。** Camel 能原生表示两样东西：待优化的程序，以及优化算法本身（规则、事实、作用在图上的函数）。二者在代码里组合，即把遍当作函数作用在一个函数上（`f->simplify`）；也可以在流水线里组合（`--passes`）。同一个遍在两处是同一个值，参数也是同一套。这里不追求"程序自带优化自己的知识"，只要求两样东西都能用原生代码写、能自由组合。
- **图原生到优化器为止才算完整。** 源码就是图，遍是作用在图上的函数。如果这些函数是 C++ 写的，用户就看不见、换不了、也组合不了，"图原生"只停在语法表面。
- **C++ 写的遍是第二份真相。** 规则、代数律、副作用与故障的判断，在声明和规则集里写过一遍，C++ 遍里又写一遍，两份会漂。近两周的审查里，这类返工反复出现。
- **复杂的变换已经证明能这样写。** 求导、转置、批处理正在从 C++ 引擎搬进库：每个原语只写局部规则，循环、分支、调用由少数通用图算子处理，`grad` 是一个组合。其余的优化照同一个模式来。

## 2. 三层：Camel 代码在哪里跑

用 Camel 写的优化器慢不慢，要看 Camel 代码处在哪一层：

| 层 | 写什么 | 谁执行 | 代价与什么成正比 |
|---|---|---|---|
| 一、声明 | 规则的左右两边、事实、规则集、代价表 | 内核的引擎：匹配自动机、右边模板、事实的不动点求解、等价饱和与提取 | 引擎的工作量，接近原生 |
| 二、逐次表达式 | 规则的 `when`、右边里现算的部分、代价函数 | Camel 后端，每匹配或每触发一次算一次 | 匹配与触发的次数 |
| 三、命令式程序 | 用 Camel 循环遍历节点或函数的全程序代码 | Camel 后端，逐节点 | 程序的节点数乘以每节点的解释开销 |

**设计目标：工作尽量落在第一层，第三层压到最薄。**凡是能写成一个批量原语的，就不写成逐节点的循环。第二层靠两种办法收窄：条件尽量写成"查事实"，让引擎事先算好；常见形状编译成模板，其余交给 JIT。

反例就在今天的库里：`stdlib/opt.cml` 的 `cse` 对每个节点在同一张图的全部节点里找一个相等的更早节点，一轮是节点数的平方，再循环到不动点。这正是第三层的写法。它要改成第一层：相等的值合并成一个节点，本来就是等价饱和里同余闭包的结果，用内核的饱和引擎做，Camel 一侧只声明"什么算相等"。

## 3. 内核：留在 C++ 的东西

内核里放什么不靠一条固定判据，逐个具体讨论。讨论时有两个方向：
- 语言暂时表达不了的，优先考虑拓宽语言（第 5 节）；
- 处在每个程序每次执行热路径上的，是放进内核最常见的理由。比如规则引擎若用 Camel 写，每条规则都会被它解释执行，第一层就退化成第三层。

按现在的讨论，内核包括：

1. **图的存储与提交**：草稿、事务、提交、提交时的整图校验（三条红线的强制机制），以及版本和回收的根。
2. **引擎**：
   - 规则匹配，模式集预编译成匹配自动机；
   - 右边模板；
   - 事实的不动点求解（`join`/`meet`/`widen`/`narrow`）；
   - 等价饱和与按代价提取；
   - 策略组合子的调度（`seq`、`first`、`repeat`、`until`、`alternate`）。
3. **通用图算子**：语言写不出、又是很多变换共用的那几个：
   - `reinterp` 一族，包括 `first_with_as_param`；
   - `split`、`transpose`；
   - 复制图并改端口分类；
   - 区域的拼接与拆出，内联要用。

   每加一个，都要说明它被至少两种变换共用。
4. **图查询与编辑的原子操作**：读节点、读边、读效应与故障的事实，以及事务内的替换和删除。今天的 `graph` 模块已经有大半。
5. **执行后端**：解释器、字节码虚拟机、JIT、并行调度、张量内核，以及导出。

不在这个清单里的都属于 Camel：每一个优化遍、每一套代数律、每一个变换的组合方式、每一个代价模型。

## 4. Camel 一侧的四种写法

| 写法 | 适用 | 今天的 C++ 遍或模块会变成 |
|---|---|---|
| **规则加事实** | 局部的代数改写、常量折叠、按事实开火的改写 | `opt::algebra`、`opt::fold`、`opt::order`、去虚化（"被调值已知"是一项事实，开火时改成直接调用） |
| **饱和加提取** | 等价改写的全局选择、公共子表达式 | `opt::cse`、`opt::saturate`、`opt::extract` |
| **作用在图上的函数** | 全程序的分析与变换：先查询、再一次事务提交 | 内联（何时内联是一项代价事实，拼接由区域算子做）、特化、去函数化的分析部分、融合的分组 |
| **库里的组合** | 程序变换 | 求导、`vmap`、`remat`（进行中） |

`std::opt` 本身变成一个 Camel 函数：用策略组合子把各个规则集和遍串起来，不再是 C++ 里写死的流水线。用户能读它、改它，也能换掉其中一步。

### 4.1 造图靠求值，不靠拼装

变换要造出原图里没有的计算时（求导、批处理、展开），不用"新建一张图、一个节点一个节点地加、再提交"的命令式拼装，而是**写一段普通的 Camel 代码，在输入已知时对它求值，剩下来的那部分就是新图**，即部分求值。以前向求导为例：

- 求导写成一个解释器，沿着 `f` 的图逐节点求值，每个算子查它的 `jvp` 规则，算出（值，切向）。
- `f` 的结构、算子、规则在变换时都已知，只有输入值未知。`std::macro` 加内联、特化、折叠、去函数化，把"沿图走、查规则"全部算掉。
- 剩下的就是 `jvp(f)` 的图。它是一段普通程序，不需要节点句柄，也不需要事务。

简例：

- `pow(x, 3)` 部分求值得到 `x * x * x`；
- 一个按 `[Mul(2.0), Add(3.0)]` 运行的小解释器，部分求值得到 `x * 2.0 + 3.0`；
- 让同一个解释器处理（值，导数）对，得到导数 `dx * 2.0`。

事务只作为规则引擎内部改图的机制，不作为造图的接口。

**适用范围**：本质是"换一套语义重新运行程序"的变换（前向求导、批处理、量化、代价与形状估算、插桩）。本质是"重组程序结构"的变换（融合、公共子表达式、调度、去函数化）不硬写成解释器，用规则、事实、区域算子。

**风险与对策**：
- 部分求值必须消干净，残余里不留闭包和间接调用。这由去函数化和内联来保证。
- 静态与动态在写法上标明（`#macro`、常量参数），不靠部分求值器猜。
- 消不干净的地方，编译器指名报出来。
- 展开设上限，超了报出来。

**先做小样**：前向求导写成解释器，在现有求导用例上比三件事：
- 产出的图与 C++ `jvp` 是否相同、节点数是否相同；
- 变换耗时；
- Camel 代码行数与对应的 C++ 相比。

数字好，再考虑 `split`、`transpose` 是否照此重写。小样的排期由负责人定。

### 4.2 工具与覆盖

| 工具 | 管什么 | 现状 |
|---|---|---|
| 规则 | 局部的模式改写：代数化简、窥孔优化 | 已有 |
| 事实 | 数据流分析，给规则当条件 | 已有；限于每个值一项、平凡数据 |
| 等价饱和加提取 | 在等价写法里按代价挑一个：公共子表达式、重结合的选择 | 已有（`saturate`/`extract`） |
| 策略组合子 | 把规则集与遍串起来：先后、择一、重复、到不动点 | 已有（`seq`/`first`/`repeat`/`until`/`alternate`） |
| 部分求值 | 换语义重跑：求导、批处理、展开（4.1） | `#macro` 加 `std::macro` 已有；质量待小样验证 |
| 通用图算子 | 语言写不出、又被多个变换共用：`reinterp`、`split`、`transpose`、`first_with_as_param` | 已有，在 C++ 里 |
| 类型层计算 | 算出变换后的签名：`Gradient<F>`、`Pullback<F>` | 已有 |

配套：图查询 API（读图）；规则校验与许可制（改写的正确性）。

| 一类变换 | 例子 | 用什么 | 覆盖 |
|---|---|---|---|
| 局部改写 | 折叠、代数化简 | 规则加事实 | 能 |
| 全局择优 | 公共子表达式、最省的写法 | 饱和加提取 | 能 |
| 换语义重跑 | 前向求导、`vmap`、量化、代价估算 | 部分求值 | 能，待小样 |
| 线性代数类 | 转置、反向传播的残差 | `split`、`transpose` | 能 |
| 过程间分析 | 去虚化、按调用点特化 | 规则加事实 | 缺程序级事实 |
| 结构调整 | 内联、外提成函数、循环融合与拆分 | 区域算子 | 要补 |
| 生成新声明 | 去函数化为每族生成 `enum` | 拓宽语言 | 要补 |
| 按代价决策 | 融合分组、内联与否 | 代价模型 | 要补 |
| 降级与后端 | 字节码、JIT、ONNX 导出、GPU 切块 | 内核 | 留在内核 |

**还要补的**：
- **区域算子**：拼入（内联）、外提（子图成函数）、循环的合并与拆分、链上调序。它们与 `split`、`transpose` 同一性质：语言写不出、又被多个变换共用。策略在 Camel 里写，例如"哪些调用该内联"写成事实加代价，算子只负责执行。
- **三项语言扩展**（第 5 节，逐项拿给负责人定）：
  - 程序级事实，事实要能落在函数上、能是集合；
  - 由编译期的值生成类型；
  - 显式的代价模型。
- **留在内核**：降级与后端；与后端绑得很紧的调度和内存规划，暂留，以后具体讨论。

**建议的先后**：
1. 区域算子里的"拼入"，内联马上要用；
2. 部分求值的小样；
3. 程序级事实；
4. 代价模型；
5. 由值生成类型。

## 5. 要补的能力：优先拓宽语言

下面几项先按"拓宽语言"考虑，每一项写成扩展提议，逐条拿给负责人定。每个提议都要说清它在图上长什么样（第 5.5 节）。

1. **程序级的事实**：见 5.1 节的提议。
2. **批量查询**：按模式、按事实批量选出节点和函数，交给引擎去找，不在 Camel 里写循环。
3. **成组的原子改写**：一族调用点要么全改、要么全拒，比如去函数化的改签名。事务要能跨图，并且明确"整组失败就整组拒绝"。
4. **由事实生成类型和函数**：比如每族一个 `enum`。类型是编译期的值，这一步走类型函数，不走 C++ 原语。
5. **规则应用的控制**：终止（燃料、轮数）与代价模型都要显式写出，不藏在引擎里。
6. **分层的度量**：每个遍运行时，要报出时间分别花在引擎、第二层表达式、第三层 Camel 代码里各多少。这是第 2 节那条边界的依据，也是第 8 节第一个研究问题的数据。
7. **图 API 能新建，不只能改**：新建节点、区域和函数。有了这一项，`split`、`transpose` 这类通用图算子本身也可以用 Camel 写成图上的函数；它们只在编译期做，或在运行时按图缓存后只做一次，落在第三层也可以接受。届时它们是否还留在内核，具体讨论。
8. **代码里与流水线里调用遍的写法一致**：源码里写 `f->std::opt<rules: [...]>`，与命令行 `std::opt rules=[...]` 是同一个遍、同一套参数。语言参考 9.8 节里这一项还列为尚未实现；它是"在代码里组合"这半边的前提。

### 5.1 提议：程序级事实

**要回答的问题**：
- 一个函数值可能是哪几个函数？去虚化、去函数化要用。
- 一个参数在所有调用处是否都是同一个常量？按调用点特化要用。
- 一个函数在哪里被调用？内联要用。

现在的事实到函数边界就停，而且值只能是平凡数据。

**做法**：
1. **事实仍是"一个值的性质"，不新增"函数上的事实"。**"一个函数值可能是谁"就是那个值上的一项事实；"一族有哪些成员"是把这一类值的事实并起来。
2. **调用图由引擎内置地算出。**事实要沿调用传播，就得先知道调用会调到谁；而在 Camel 里，被调的是谁要靠"函数值可能是谁"来回答。两者互相依赖。所以"函数值可能是哪些函数"（控制流分析，0-CFA）是引擎内置的分析，与传播在同一个不动点里一起算；用户声明的事实再沿这张调用图传播：
   - 参数的事实是所有调用处实参事实的 `join`；
   - 调用结果的事实是被调函数出口的事实。
3. **看不见的地方一律按"未知"处理。**这是正确性的底线，有三处：
   - 函数值传进看不见内部的原生算子（例如 `map` 在算子内部调用它、交给 `.cmo` 模块）；
   - 函数值存进数组、结构体或 `var`，再取出来，这一路要跟住；
   - 运行时才造出的函数（变换现场造的、宏求值造的），不在静态集合里。
4. **集合型事实只用内置的并与交，加一个"未知"值。**不开放自定义的 `join`：自定义的若不单调，不动点可能不终止，结果也不可靠，引擎无法自动检查。用户在 `case` 里只给出"能确定是哪几个"。
5. **精度先做不区分调用处的版本**，配合"先内联、先按调用点特化、再分析"。不够用再考虑区分调用处（1-CFA），以实测为准。

**为什么可行**：
- 程序里的函数有限，集合的高度有限，不动点必然终止；
- 0-CFA 最坏是三次方，只在遍用到时才算，同一版程序算一次就缓存；
- 事实只是查询，不改变任何程序的图，不影响"程序即图"；
- 调用就是把实参连到被调图的端口，事实沿边传播，跨调用只是同一条规则的延伸。

**正确性的保障**：漏掉任何一处"看不见"，去虚化都会把调用改错，而且程序不会报错。所以上线时要配差分检查：同一个程序开、关用到这项事实的遍各跑一次，结果必须一致。

**第一步**：引擎内置 `targets` 分析；用它把去虚化写成"规则加事实"，删掉 C++ 的去虚化遍。在基准程序上量三个数：
- `targets` 精确到单个函数的比例；
- 分析耗时；
- 差分检查是否全过。

数字出来，再定集合型事实与用户事实跨调用这两步。

**别处的做法**（供对照，细节以正式调研为准）：
- Doop 一类的 Datalog 指针分析，在同一个不动点里边算调用图边做指针分析（on-the-fly call graph），精度靠可选的上下文敏感来调；
- MLIR 的数据流框架默认跨私有函数传播，对外部函数和间接调用按"未知"处理；
- egglog 把 Datalog 式的分析和等价饱和放进一门语言，要求合并函数满足格的性质。

### 5.5 边界：不改变"程序即图"的定位

规则系统，以及以后扩展的图改写能力，本身也是 Camel 程序、也是图（设计原则第 1 节）。拓宽语言、加强改写能力的提议，都不能让 Camel 偏离程序即图的定位；遇到可能偏离的提议，拿出来具体讨论。

## 6. 现状

- **已经在**：
  - 图事务（`open`、`replace`、`erase`、`commit`）；
  - 图查询（`nodes`、`inputs`、`users`、`kind`、`effects`、`may_fault`、`region_of` 等）；
  - 规则与事实；
  - 等价饱和与提取（`rewrite`、`saturate`、`extract`）；
  - 策略组合子；
  - 规则校验（`modules/verify`）；
  - 程序变换的三个算子。
- **两套并存的**：`fold`、`cse`、`dce` 在 `stdlib/opt.cml` 里有 Camel 版本，`std::opt::fold`、`std::opt::cse`、`std::opt::dce` 又有 C++ 版本。按"不留两套"，迁移的第一步就是让 Camel 版本在全量用例上与 C++ 版本给出相同的图，然后删掉 C++ 版本。Camel 版的 `cse` 同时改成饱和的写法（第 2 节）。
- **还是 C++ 的**：`opt::inline`（约 1500 行）、`defun`（约 1750 行）、`generic` 的其余部分（约 3400 行）、`specialize`、`devirtualize`、`tensor::fuse`、`std::macro`。

## 7. 迁移的规矩

每迁移一个遍：
1. **同一次合并里删掉对应的 C++**，不留开关，不留后备路径。
2. **输出相同的图**：在全量用例和基准程序上比较 `std::gir` 的输出；有差别的，逐条说明是 Camel 版更好还是缺陷。
3. **全量闸门持平**。
4. **记下编译时间及其分层**（第 5 节第 6 条）。编译时间的预算等第一个遍迁移完、有了实测数字再定。
5. **记下删掉的 C++ 行数。**

迁移时遇到"语言写不出"的地方，先问能不能补成一个通用的原语（第 3 节第 3 条的标准）；补不成的，才算内核的边界，写进第 3 节。

## 8. 研究问题

这几条在迁移过程中逐步攒证据，素材照旧记进决策者的笔记，成熟一条整理一条：

1. **声明与引擎的边界**：原语怎么设计，才能让复杂的优化写得简单，又能被内核高效执行？量出三层各自的时间占比；给出"哪些优化能完全落在第一层"的刻画；比较同一个优化写在不同层上的代价。
2. **小内核的表达力**：少数通用图算子加局部规则，足以写出求导、批处理、重算、去函数化、内联。目标是给出一个可以论证的结论。
3. **变换是运行时函数时涌现的性质**：嵌套求导闭合；通过函数值的调用，提升时不必知道是哪张图；挪动 `with` 参数只能在签名上做，不能靠调用。
4. **带效应的图改写**：同步链的语义怎样保证改写不丢、不乱效应；结构语句在链上占一格。
5. **可验证的数值改写**：许可制与规则校验。
