# 规则语言第二版（设计稿）

状态：已定（决策者 2026-10-22，负责人："都加上吧，越强越好"）。第一版见同目录 [README.cn.md](README.cn.md) 与 `docs/technical/46_rules.md`。

目标：规则库从"逐类型、逐算子罗列定律"变成"少量通用定律加 ML 专用的图替换"，并且每条规则都能被 `check` 检验。**不加保留关键字**：只扩展 `rule`、`when` 能写什么，`analysis` 改为 `fact`（7.5），全部是上下文关键字，复用元组、函数类型、Camel 函数调用。

---

## 1. 类型泛型与值语义

- **规则在名字后声明类型参数**（设计原则 5.5）：`rule sub_self::<T>(x: T) { x - x => 0 }` 对所有类型实例化；字面量在实例里取 `T`。只对部分类型成立的写在条件或要求里（`#requires<no_nans, no_infs>`、`when is_integer::<T>()`），不复制规则。
- **`const c` 在 `when` 与右边里是常量的值**，类型是形参的类型：`when c1 != 0 && sign(c1) == sign(c2)`。需要节点本身（读事实、形状）时写 `node_of(c)`。
- **形参的类型由匹配器检查**：`const c: T` 只匹配类型为 `T` 的常量，规则不再写 `isI32` 一类的守卫。
- **`fact` 的子句同理**（7.5）：模式变量在子句里是节点（事实挂在节点上），常量变量是值。

## 2. 算子变量

- 形参可以是函数类型：`op: (T, T) => T` 在模式里匹配任意二元算子，在右边原样使用。
- **算子的性质由 `when` 读取**：`commutative(op)`、`associative(op)`、`identity::<T>(op)`（单位元，没有时为 null）、`distributes(mul, add)`。这些性质来自算子的语义声明（10.4 要求每个原子算子声明定律）；Camel 定义的函数由其定义推出或用标签声明。
- 例：
  ```camel
  rule neutral(x: T, op: (T, T) => T) { op(x, e) => x } when e == identity::<T>(op)
  rule distribute(a: T, b: T, c: T, mul: (T, T) => T, add: (T, T) => T) {
      mul(a, add(b, c)) => add(mul(a, b), mul(a, c))
  } when distributes(mul, add)
  ```

## 3. 多根模式

- 左边是元组时，元组的各项是**同一张图里同时存在**的几个值，共用形参：
  ```camel
  rule divmod(x: T, y: T) { (x / y, x % y) => divmod(x, y) }
  rule qkv(x, wq, wk, wv) { (x @ wq, x @ wk, x @ wv) => split3(x @ concat(wq, wk, wv)) }
      when same_shape(wq, wk, wv)
  ```
- 右边是同样元数的元组，各项依次替换左边各项。匹配按共享的形参连接（先匹配含最少变量的一项，再按共享变量找其余项）。
- 只有左边各项都存在才触发；它们之间不要求相邻，也不要求在同一区域之外的任何关系，除了**都不依赖彼此的结果**（否则替换会成环，匹配器拒绝）。

## 4. 条件与右边可以调用 Camel 函数

- `when` 与右边都可以调用任意纯的 Camel 函数，在改写时求值，参数是常量变量的值、属性与形状：
  ```camel
  rule perm2(x: T, const p: int[], const q: int[]) {
      x->permute<p>->permute<q> => x->permute<compose(p, q)>
  } when !is_identity(compose(p, q))
  rule perm_id(x: T, const p: int[]) { x->permute<p> => x } when is_identity(p)
  ```
- 读形状：`shape(x)`（形状已知时是值，未知时条件为假）；读属性：`attr(x)` 一类。
- 右边调用的函数结果成为新节点的常量或属性；调用失败（故障）时该次改写不发生。

## 5. 代价是 Camel 函数

- `extract<cost>(p)`：`cost` 是 `(op: Op, args: Shape[]) => float` 一类的 Camel 函数（具体签名随 `graph` 模块定），给出一个写法的代价；抽取取总代价最小的写法。
- 标准库给出 `rules::nodes`（节点数）、`rules::flops`（按形状估算）等；Tiles 给出自己的代价模型。字符串形式 `extract(p, 'nodes')` 删除。

## 6. 结合交换匹配

- 声明了结合律与交换律的算子（第 2 节的性质），匹配器把一串同一算子的项看作**多重集**：`a + b + c` 不展开成各种括号与顺序，模式 `x + 0` 在多重集里找 `0`。
- 交换律、结合律不再写成规则（它们是匹配器的语义），饱和不再因此爆炸（H118 的超时）。
- 这一节不改语法，只改匹配器与抽取。

## 6.5 调用与绑定的模式；统一的项视图（负责人 2026-10-24）

- **调用模式**：模式里的 `f(x)`，`f` 是函数类型的模式变量时，同时匹配直接调用（`FUNC`）与调用函数值（`CALL`）——图上分开表示，匹配视图上统一，规则不关心是哪一种。`f` 写成具体的函数名时只匹配调用它的节点。
- **绑定模式**：`f<w>` 匹配 `BIND`（上下文参数的绑定，含闭包），右边也可以构造它。例：
  ```camel
  rule call_bound(f, w, x) { (f<w>)(x) => f<w>(x) }      // 先绑定再调用 = 带着上下文直接调用
  ```
- **统一的项视图**：匹配器把每种节点都读成"头部 + 有序端口 + 区域"：`OPER` 的头部是算子，`FUNC`/`BIND` 是目标图，`CALL` 是第 0 个端口，`BRCH`/`LOOP` 带区域，`DATA`/`PORT` 是叶子，`GATE` 被看穿。模式编译器只面对这一种形状，以后增加节点种类不改规则系统。依赖图模型设计稿 3.4.1 的目标节点集（转换、构造、访问并入 `OPER` 之后，`(a, b).0 => a`、`f32(f64(x)) => x` 这类规则才写得出）。

## 7. 控制区域上的模式

- 模式可以写分支与循环：
  ```camel
  rule same_arms(c: bool, a: T) { (if c then a else a) => a }
  rule const_cond(a: T, b: T)   { (if true then a else b) => a }
  ```
- 循环上的变换（不变量外提、相邻循环融合）属于本节的第二步：模式能匹配 `loop` 的头与体。
- **跨绑定的模式用高阶模式**（负责人 2026-10-24）：模式里出现 `x => …`（lambda、循环状态、区域的端口）时，其中的模式变量能否用到 `x`，由它是否写成作用在 `x` 上决定——`x => e(x)` 的 `e` 可以用到 `x`，`x => c` 的 `c` 不能用到 `x`（只匹配与 `x` 无关的子图）。"是否依赖循环状态"由模式的形状表达，不另写条件查询。右边可以构造 lambda。例：
  ```camel
  rule hoist_map(xs, c) { map(xs, x => x * c) => (let k = c; map(xs, x => x * k)) }
  rule map_fusion(xs, f, g) { map(map(xs, x => f(x)), y => g(y)) => map(xs, x => g(f(x))) }
  ```
  模式变量作用在哪些绑定参数上，对应 slotted e-graph（PLDI 2025）里 e-class 的"槽"；引擎今后换成 slotted 表示时规则不变。语义依赖设计原则 4.4"函数值没有身份"。
- **丢掉的部分与移出绑定的部分，用同一个谓词：纯且不会出故障**（设计原则 3.4、9.7）。丢掉：右边没用到的模式变量绑定的子图必须可自由安排（`x * 0 => 0` 不作用于 `(a / b) * 0`）；抽取时同样不得选丢掉可能出故障部分的写法。移出：右边把一个模式变量从 `x => …` 里移到外面（如 `hoist_map` 把 `c` 移出），等于让它在零轮、空数组、未选中的臂时也执行。引擎统一检查：被移出的子图必须是纯的，且其中每个算子按算子表属于"不会出故障"的保守类（整数除法、下标、可能溢出的转换等不属于）；否则这次匹配不适用，`explain`/`why_not` 报为"会提前执行可能出故障的计算"。这与"右边丢掉的部分必须是纯的"是同一类引擎检查，规则作者不必逐条考虑。
- 区域按图内区域（图存储设计稿第 5 步）匹配，替换保持区域结构合法，由校验器检查。

## 7.5 事实：`fact` 取代 `analysis`

第一版的 `analysis` 名字说的是动作，没说出产物；子句 `initial`/`join`/`on` 是格论术语，输入又是隐含的。第二版改为声明**图上每个值的一项事实**（与图存储的"事实"同一个概念）。结构与 `rule … { … } when …` 相同——头、花括号里的主体、尾随子句：

```camel
fact depth::<T>(v: T): int match v {
    case const c => 1
    case x + y   => max(depth(x), depth(y)) + 1
    case _       => 0
} join max

fact range::<T>(v: T): Interval match v {
    case const c => Interval(c, c)
    case x + y   => range(x) + range(y)
    case abs(x)  => range(x).abs()
    case _       => Interval::of_type::<T>()
} join Interval::union
  meet Interval::intersect
  widen Interval::widen
  narrow Interval::narrow

rule abs_nonneg(x: T) { abs(x) => x } when range(x).lo >= 0
```

- **头 `fact 名字(参数): 事实类型`**：输入显式；`T` 可在分支里使用（如 `case _` 按类型给出范围）。规则的 `when` 与其他事实里按函数调用查询。
- **主体 `match v { case … }`**：与普通的 `match` 同一种写法，只是被匹配的是 `v` **在图上的构造方式**——`case x + y` 把"由加法得到的值"拆成两个操作数，如同按变体拆一个代数数据类型。模式与 `rule` 左边同一种写法；`case _` 必需。多个参数时匹配元组：`fact aligned(a: T, b: U): bool match (a, b) { case (x * c, y * c) => … }`。
- **尾随子句**，每个接一个二元函数（已有函数的名字，或 lambda `(a, b) => …`），顺序不限，可以换行：
  - **`join`**（必需）：分支汇合，"两者之一"，最小上界。
  - **`meet`**（可选）：同一个值的等价写法，"两者都成立"，最大下界；省略时等价写法也用 `join`（正确但不精确）。
  - **`widen`**（可选）：循环中迭代时加速收敛；省略时迭代到上限退回 `case _` 的事实。
  - **`narrow`**（可选）：`widen` 收敛之后再收紧，找回被 `widen` 丢掉的精度（如循环条件 `i < n` 给出的上界）。
- `fact`、`join`、`meet`、`widen`、`narrow` 是上下文关键字（`fact` 在声明开头，其余只在 `fact` 声明的主体之后）；`match`、`case`、`_` 沿用原义。第一版的 `analysis`、`initial`、`on` 删除，不保留旧写法。
- 理论对应：`join`/`meet`/`widen`/`narrow` 即抽象解释的 ⊔/⊓/∇/Δ；egg 的 `Analysis::merge` 合并的是等价写法，对应这里的 `meet`。

## 8. `check` 的覆盖

- 第 1 节之后，常量变量是值，条件能在采样值上求值：带 `when` 的规则也做采样对照（今天只能走引擎路径）。
- 多根规则对每一项分别对照；带算子变量的规则对每个满足条件的已登记算子各检验一次；带结合交换的规则按多重集采样。
- 规则库进入标准库之前必须通过 `check`，不变。
- **丢弃的部分必须是纯的**（设计原则 9.7）：匹配时，右边没有用到的左边模式变量所绑定的子图，若含有效应（或其中有节点被同步边、顺序边连着），这次匹配不适用。引擎统一检查，`explain`/`why_not` 报告为"会丢掉效应"。`check` 的采样对照不受影响（采样值是纯的）。

## 8.1 形式化验证（负责人 2026-10-24 要求列入）

`check` 的采样对照可能漏掉边界（整数溢出、NaN、负零、次正规数）。在它之外增加**用 SMT 求解器证明规则**（参照 LLVM 的 Alive2）：把"左边等于右边"翻译成对**所有**输入成立的命题，交给求解器——要么证明成立，要么给出反例。与 `check` 一样只在规则进入标准库前做一次（CI），不在优化时跑。

- **翻译**：整数按位向量（`int` 64 位、`i32` 32 位，回绕语义）；浮点按 IEEE 浮点理论（f64、f32、f16、bf16）；`when` 条件与 `fact` 的结论作为前提；常量参数是符号常量。
- **许可就是前提**：`finite_math` 的四项是"输入与中间值不是 NaN/无穷/负零/次正规数"的假设；`refine_accuracy` 的规则证明"右边不比左边差"（误差界）而非相等；`reassociate`/`contract` 一类本来就改变舍入的规则，证明它们在**实数**上相等（这正是许可允许的那一种不等）。
- **覆盖不到的**用 `check` 兜底并在报告里标明：张量的整体性质、带区域的模式、调用外部函数的条件。
- **报告**：每条规则标 `proved`、`refuted`（附反例）或 `sampled`（只做了采样）。标准库的规则以 `proved` 为目标；`refuted` 的规则不得入库。
- **依赖**：求解器（Z3）作为可选的构建依赖，只在验证时需要，不进 `camel` 的运行时。

## 8.5 规则是值，规则集是数组，调度是普通函数

- **`rule` 声明一个类型为 `Rule` 的值**（像 `let` 声明的常量），不是函数；第一版的 `(() => Rule)[]` 改为 `Rule[]`。泛型规则是一个值，引擎在匹配处按类型实例化。
- **规则集就是数组**：`let algebra = [sub_self, combine, distribute]`，可以拼接、过滤（`algebra->filter<(r) => !rule_two_way(r)>`），不加 `ruleset` 关键字。
- **调度是普通的 Camel 函数**：遍是函数变换 `(f: F) => F!`（设计原则 9.x"遍就是函数变换"），`rewrite`（单向到不动点）、`saturate`（等价饱和）、`extract`（抽取）都是这种函数，组合就是函数组合与管道：
  ```camel
  export func simplify(f: F): F! {
      return f->saturate<algebra, budget: { rounds: 6, nodes: 200000 }>
              ->saturate<fusion>
              ->extract<rules::flops>
  }
  ```
- 标准库给出几个组合子（与 egglog 的 `run-schedule`、Stratego 的策略对应），本身也是用 Camel 写的函数：`repeat<pass, n>`（重复 n 次或到不动点）、`seq<[a, b, c]>`、`until<pass, cond>`、`alternate<a, b>`（交替到双方都不再变）。预算（轮数、写法数、时间）是参数，不是全局设置。
- 使用：写好的函数就是遍，`camel f.cml mylib::simplify std::fvm` 施加在整个程序（根函数）上；在 Camel 里对单个函数直接调用：`loss->simplify`。

## 8.6 关系：没有函数体的 `fact` 由规则推导

- **有函数体的 `fact`**（7.5）按值的构造方式**计算**，适合"每个值的一项性质"。
- **没有函数体的 `fact` 是一张由规则填写的关系表**，与"没有函数体的 `func` 是原生算子"同一个约定（10.4）：
  ```camel
  fact dominates(a: T, b: U): bool join or
  fact same_shape(a: T, b: U): bool join or
  ```
- **规则的右边可以是事实**：左边匹配值的构造或已有的事实，右边断言新的事实；引擎按半朴素求值（semi-naive）跑到不动点：
  ```camel
  rule dom_trans(a: T, b: U, c: V) { (dominates(a, b), dominates(b, c)) => dominates(a, c) }
  rule shape_add(x: T, y: T)       { x + y => same_shape(x + y, x) } when same_shape(x, y)
  ```
  左边是元组时与多根模式（第 3 节）同一种写法；右边断言多个事实时也写元组。
- 带格的关系（事实类型不是 `bool`，如"`a` 到 `b` 的最短距离"）用 `join`/`meet` 合并，与 egglog 的 `:merge` 相同。
- 改写规则与推导规则可以放在同一个规则集里一起饱和：事实可以让改写的条件成立，改写产生的新值又可以推出新的事实。

## 8.7 解释：两个值为什么相等，一条规则为什么没触发

- **主要的用户界面是调试器 camel-db**，不进核心的命令行：在饱和后的程序里选中一个值（源码位置或图节点，调试器本来就能指认），命令 `explain <run> [<a> <b>]`（给出两个值时比较它们，或读取整份记录）给出一条改写链并指明规则和两个节点位置，`why_not <run> <rule> <value>` 说明规则为什么没在这里触发——模式在哪个子项不匹配、哪个条件为假（显示条件里各个值）、缺哪项许可、哪个事实还不知道。调试器不重跑改写：它调用模块自己的读取器，读运行时留下的 `Proof`；两者对同一条记录给出同一个答案。VS Code 里在等价图视图（H225）中点选两个写法即显示证明。
- **Camel 里是普通函数**，参数是值而不是源码位置：`explain(g, a, b): Proof!`、`why_not(g, r, v): string`；`Proof` 可以打印成逐步推导：
  ```
  x * 2 + x * 3
    = x * (2 + 3)     by combine        (#requires reassociate)
    = x * 5           by fold
  ```
- **证明可以复核**：每一步可以单独用 `check` 的方法在采样值上对照。
- **代价按需付**：来源记录默认关闭，由遍参数打开（`saturate<…, explain: true>`）。调试器读取已经打开的记录；`run` 没有打开时，`explain` 原样给出库的 `NoAttribution` 错误值并说明怎样打开，而不是替用户重跑一次改写。

## 8.8 速度

- 以 H226 的对照为基线，目标是不慢于旧 C++ 定律表，饱和的规模与 egg 同量级。
- 手段（按测量结果选用）：规则集编译为匹配自动机并进模块缓存（H226 第 4 项）；增量 e-matching（只在新增或改变的写法上重新匹配）；合并后的重建批量进行（egg 的延迟重建）；结合交换匹配（第 6 节）消掉交换、结合规则的爆炸。

### 8.8.1 饱和期间的紧凑写法（负责人 2026-10-24 要求针对性优化）

饱和会新建大量写法，而今天每个写法都是一个完整的图节点（类型、标志、区域、端口角色、来源……），经草稿图的建节点流程建出。同一个值的各种写法，这些信息大半相同；重复复制它们是饱和的主要开销。做法：

1. **按值的信息只存一份，挂在类上**：类型（形状）、所在区域、数值许可上下文、源码位置——同一个值的每种写法都相同，所以存在类上，不存在写法上。
2. **写法只存它自己的那一点**：算子 id、各输入的类 id（小数组内联）、常量的值（若是常量）、产生它的规则与匹配（供 `explain`）。放在饱和专用的连续内存区里，用完整块释放，不经 GC，也不经草稿图。
3. **hashcons 先查后建**：右边构造一个写法前，以（算子、输入的类）为键查表，已有就复用——同余表本来就有这张表，紧凑写法直接用它作存储。
4. **只在需要时落回图上**：抽取选中的写法建成真正的图节点，其余丢弃；转储、`explain`、或流水线要求保留多写法状态到下一个遍时，才把类的全部写法物化成图节点（今天的 `WritingUnion` 日志格式不变）。
5. **原图的节点就是初始写法**：饱和开始时不复制原图，原图节点以它们的编号作为写法登记，紧凑区只装新写法。

**定位**：引擎内部采用 egg 的结构——类上挂按值的信息（EClass）、写法的输入指向类（ENode）、先查后建的表（hashcons）；引擎边界保持图原生——进出都是程序图，原图节点即初始写法，等价按数值许可分层，多写法状态以日志落在图上、可跨遍保留。

不变的：语义、规则写法、抽取结果、转储所见——同一程序同一规则集，改前改后抽取出的图逐字相同（验收的第一条）。

验收：上一条的逐字相同；H226 负载与一组 egg 对照表达式上，饱和到同一规模时的**退休指令数**与**峰值内存**（不用墙钟，主机负载大）；与 egg 在同一规则集、同一表达式上的对照（每秒处理的写法数、每个写法的字节数）写进报告。先测基线再改，两次测量都留存。

### 8.8.2 待评估：介于 `simplify` 与 `saturate` 之间的一档（参照 Cranelift 的 aegraph）

现在有两档：`simplify` 单向改写到不动点（便宜，丢掉其他写法），`saturate` 完整饱和（强，贵）。aegraph 的做法是中间一档：新写法建出时当场套用规则一次，只把新写法并入已有的类、从不合并两个旧类，因此不需要合并后的同余重建，图保持无环、开销有上界，同时保留候选写法按代价抽取。适合作为默认流水线与 JIT 的选择。**等 8.8.1 的基线与改后测量出来再定**：紧凑写法之后饱和若已足够快，就不需要这一档。

aegraph 的另一个前提——有副作用的指令留在骨架上、纯计算浮动——Camel 不需要另做：三种边（设计原则 3.1）之后，纯计算只有数据边，效应由同步边与顺序边串起，这本身就是骨架与浮动的划分。

## 8.9 按目标支持抽取

- 代价函数可以对"目标不支持的写法"给无穷大代价：`extract<supported_by<onnx>>`、`extract<supported_by<device>>`。等价类里只要有一种写法目标支持，抽取就选它；全部不支持时才报"无法导出/设备做不出"，诊断指出是哪个值、它有哪些写法。
- ONNX 导出与 `#gpu` 的编译先饱和、再按此抽取，"不支持"的错误因此只在真正没有可行写法时出现。
- **待评估：抽取时一并决定放置**（参照 aegraph 的 elaboration）：从类里挑写法的同时决定纯计算在哪里执行——放在支配它全部使用者的区域，能移出循环体或臂的移出（循环不变量外提），必要时在使用处重算以免长时间占用。移出的条件与第 7 节相同：纯且不会出故障。与按目标抽取一起设计。

## 8.10 以精度为目标的规则与抽取

- 规则库 `rules::accuracy`：`log(1 + x) => log1p(x)`、`exp(x) - 1 => expm1(x)`、`sqrt(x*x + y*y) => hypot(x, y)` 一类，换成数值上更精确的写法（Herbie 的方向）。
- 这类改写改变结果的位（变得更准），由新的数值许可 **`refine_accuracy`** 门控（"允许换成误差不更大的写法"），默认不授予；`#strict` 下不适用。许可的名字可推翻。
- 抽取代价是误差估计（按采样或按每个算子的 ulp 界），`extract<rules::error>`；`check` 对这类规则验证"右边的误差不大于左边"，而不是逐位相等。

## 8.11 转译与执行也是改写

- **转译即降低**：目标的算子用无体声明写成**目标算子**（只在图上占位，没有执行器，如 `onnx::Add`）；降低规则把 Camel 的写法改写成目标算子（`rule lower_add::<T>(a: T, b: T) { a + b => onnx::Add(a, b) }`，带条件的映射用 `when`）；饱和后按目标支持抽取（8.9），选不出时指出是哪个值；最后遍历图输出。与 Cranelift ISLE 把指令选择写成规则同一个思路。转译遍做完输出后给出空图（设计原则 9.x"遍的输入与输出都是图"）。
- **执行即改写到范式**：Camel 的操作语义写成一组规则（标准库 `semantics`）——常量输入的算子折叠为值、条件为常量的分支选中一臂、状态为常量的循环展开一轮——`rewrite` 到不动点，图就化为结果。它不求速度，用途是**可执行的语义定义**：向用户展示程序怎样一步步求值（配合 `explain`），并作为 nvm、fvm、jit、`std::cpp` 差分测试的参照（与 K 框架、PLT Redex 的可执行语义同一类）。有副作用的算子按同步块的顺序改写，与设计原则第 3 节一致。
