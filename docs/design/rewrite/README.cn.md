# 规则、策略、分析：Camel 的图重写体系（设计稿）

状态：第 6 节的 16 条已于 2026-10-20 全部按建议确认（第 8 条按区域修订）。前提：[图存储与图 API（第二版）](../graph-store/README.cn.md)（值与写法、事务、可执行状态、`rule` 声明的大方向）。

## 1. 为什么需要四样东西

主流编译器的图重写都由四样东西配合完成，局部规则只是其中之一：

| 支柱 | 做什么 | 先例 |
|---|---|---|
| **规则** | "找到这个形状，换成那个形状"：化简、规范化、融合模式、强度削减 | GCC `match.pd`、MLIR DRR/PDLL、Cranelift ISLE、Halide 化简器、GHC `RULES`、PyTorch `replace_pattern` |
| **策略** | 控制规则在哪里、按什么顺序、用到什么时候为止 | Stratego/Rascal 的策略组合子、MLIR 的贪心驱动、egg 的调度器 |
| **分析** | 推导规则条件要用的事实：常量、取值范围、形状、活跃性 | LLVM/MLIR 的数据流分析、egglog 的分析（格与合并） |
| **算法式的遍** | 需要全局判断的变换：内联决策、循环变换、调度、切分、自动微分 | 各编译器的大部分优化遍 |

规则能覆盖绝大部分"化简"，覆盖不了绝大部分"优化"。第四样由图 API 的底层节点接口承担（图存储第二版 5.1）；本稿设计前三样，加上降低时的合法性检查。

原则：语言本身只增加**规则**与**分析**两种声明（第 2、4 节），因为声明让工具能枚举它们并强制检验；策略、合法性检查都是标准库里的普通函数。匹配与求不动点由原生引擎执行，Camel 代码只描述"是什么"。

## 2. 规则

### 2.1 写法

```camel
rule mul_one(x: float)                 { x * 1.0 => x }
rule sub_self(x: float)                { x - x => 0.0 }
rule fold_mul(x: float, const a: float, const b: float) { (x * a) * b => x * (a * b) }

#requires(reassociate)
rule add_assoc(a: f32, b: f32, c: f32) { (a + b) + c <=> a + (b + c) }

rule map_map<f, g>(xs: int[])          { xs->map<f>->map<g> => xs->map<(v) => g(f(v))> }
    when is_pure(f) && is_pure(g)

rule mm_add(a: Tensor<f32>, b: Tensor<f32>, c: Tensor<f32>) {
    // 融合是实现选择，记在节点属性上，右边仍是程序的原算子（设计原则 9.6）；`@fused` 是一个
    // 声明了授予 `tensor.fusion` 的算子，与 `@numeric` 同一机制。
    a @ b + c => @fused { a @ b + c }
}
```

- `rule 名字<上下文参数>(形参) { 左 => 右 }`；`<=>` 表示双向等价；`when` 后接条件。
- 规则可以带标签：`#requires(...)` 声明所需许可（图存储第二版 3.3）。
- `rule` 是"两个参数相同的函数加配对"的简写（设计原则 1），语义相同。规则可以导出、导入，规则的列表是普通的值。

### 2.2 左边：模式

- **左边是普通的 Camel 表达式**，编译成一张小图；匹配就是在目标图中找同样形状的子图。形参是模式变量。
- **字面常量要求完全相等**。浮点数逐位比较：`0.0` 不匹配 `-0.0`。
- **可交换算子的操作数顺序**：二元算子在当前元素类型上声明了交换律时（`sem::OperatorSemantics::binary` 的 `BinaryLaw.commutative`，算子语义 7.4），单方向规则（`=>`）先按程序写下的顺序匹配；该顺序没有产生可接受的匹配时，才把这个算子的两个输入对调再试一次（H118）。替换仍按规则右边的写法构造，匹配器从不改写右边的操作数顺序，所以定律写成 `x * c1 + x * c2` 也能命中 `x * c2 + x * c1`。双向规则（`<=>`）已经写下了两个方向，饱和把它编译成反向规则，匹配器不再替它交换（否则重排定律的匹配翻倍，`rules::saturate_all` 会超时）。没有声明交换律的算子（`-`、`/`、整数张量算术）永远不会被对调，因为那会改变值。
- **同一个模式变量出现多次，要求是同一个值**（在等价饱和中是同一个等价类），不只是结构相同。
- **`_` 开头的形参**匹配任意值、右边不使用（命名约定）。
- **`const` 修饰的形参只匹配常量**（如 `fold_mul` 的 `a`、`b`）。
- **类型**：模式变量只匹配类型相同的值。要对多种类型适用，写成泛型规则（2.5）。
- **控制依赖、分支与循环**：模式里用 `sync` 写出的顺序就是控制边，匹配时也要对上；`if`、`match`、循环在图上是带控制区域的节点（图存储第二版 3.3），可以作为整体出现在模式中。
- **调用用户函数**：左边可以出现对某个函数的调用，匹配的是对**这个函数**（按身份，不按名字字符串）的调用。这使库作者可以为自己的函数写化简规则，与 GHC 的 `RULES` 相同。
- **多个出口**：左边可以是元组，`(e1, e2) => (r1, r2)`，表示同时匹配两个通过模式变量相连的子图，一起替换。

### 2.3 右边：替换

- 右边是普通的 Camel 表达式，只能用左边的模式变量、常量与可以调用的函数。
- **只由常量与 `const` 模式变量组成的子表达式在改写时求值**（如 `fold_mul` 的 `a * b`），按规范算法逐位计算，不使用任何许可，所以常量折叠本身不引入额外误差。
- **新节点继承被匹配节点的标签**（按标签登记的合并规则；合并不了则规则不生效）。
- **右边可以用块上的标签给新节点加标签**：`#fused { ... }`，用的就是已有的节点标签机制。
- **来源**：规则造出的节点带一个"由哪条规则产生"的节点标签，供调试器、`inspect`、诊断使用。

### 2.4 控制依赖

- 模式按数据输入匹配。
- 被匹配的根节点的控制输入转给替换后的根节点。
- 被匹配的内部节点（根以外）要求：没有模式之外的使用者，也没有控制输入；否则不匹配。这样，规则永远不会悄悄丢掉或移动一个顺序约束。

### 2.5 泛型规则

```camel
rule add_zero::<T>(x: T) where is_numeric::<T>() { x + zero::<T>() => x }
```

- 模式变量的类型可以是类型变量（在 `rule` 名字后声明，`rule r::<T>`），约束写在 `where` 后（设计原则 5.6 预留的位置）。
- 引擎按匹配到的值的类型实例化规则。

### 2.6 条件 `when`

- 在匹配成功之后、替换之前执行，是普通的 Camel 表达式，结果为 `bool`。
- 可以读：模式变量的类型、标签、分析的结果（第 4 节，如 `range(x).lo >= 0.0`）、纯度与副作用（算子的标准标签）。
- 不能有副作用；运行在改写的时刻（遍执行时），不是程序运行时。

### 2.7 两种方向与两种引擎

| | 贪心改写 `rewrite` | 等价饱和 `saturate` |
|---|---|---|
| `=>` | 从左到右替换 | 加入右边作为同一个值的新写法 |
| `<=>` | 不允许（会打转），编译期报错 | 两个方向都加入 |

### 2.8 强制检验

测试工具枚举全部 `rule` 声明：对每条规则生成随机输入（按形参类型；`const` 形参取随机常量），分别运行左右两边，按规则声明的许可比较（无许可则逐位相同，有许可则按数值契约的误差界）。标准规则库不通过不能合并。

## 3. 策略

策略就是变换，变换就是函数 `(f: F) => F!`（图存储第二版 5.1）。所以策略组合子是标准库里的普通高阶函数，语言不增加任何东西：

```camel
import { rewrite, saturate, extract, seq, fixpoint, try, within } from graph

let simplify = fixpoint<rewrite<[mul_one, sub_self, fold_mul]>, 20>   // 反复直到不变，至多 20 轮
let optimize = seq<simplify, saturate<algebra_rules, budget>, extract<gpu_cost>>
let only_hot = within<(n) => has_tag(n, hot), optimize>               // 只作用于带 #hot 的节点
```

| 组合子 | 含义 |
|---|---|
| `rewrite<rules>` | 贪心：按节点编号顺序、规则在列表中的顺序，各用一遍 |
| `saturate<rules, budget>` | 等价饱和，预算为轮数、节点数、时间 |
| `extract<cost>` | 按代价提取 |
| `seq<t1, t2, ...>` | 依次执行，任一失败则整体失败 |
| `fixpoint<t, n>` | 反复执行直到图不再变化，至多 n 轮 |
| `try<t>` | 失败就当作没做 |
| `first<t1, t2>` | 先试 t1，失败再试 t2 |
| `within<pred, t>` | 只作用于满足条件的节点所在的区域 |

**结果确定**：引擎按节点编号与规则顺序进行；饱和的匹配顺序、并查集的合并顺序、提取时的平局，都按编号决定。同样的输入、同样的规则与预算，结果每次相同。预算耗尽时，返回已达到的状态，不报错（可以通过参数改为报错）。

**提取的保留边界**（协调者 2026-10-21 裁定；图存储第二版 3.5、3.6）：

- **抽取不裁剪有副作用的节点。** 抽取不改变哪些副作用发生：有副作用的节点、控制节点与被写入的变量不由抽取裁剪（饱和不新增它们）；它们是否执行仍按设计原则 3.1——同步块之外、结果没有被使用的带副作用的调用不执行——由执行与死代码消除决定，与抽取无关。
- **纯节点只按可达性保留。** 从图命名的东西（端口、入口、出口、返回值、区域结果）出发，沿被选中的写法可达的纯节点才留下；饱和新造、又没有任何东西读取的候选写法在抽取时删掉。抽取代价只在纯计算的合法写法之间挑选，不改变"哪些副作用发生"。

## 4. 分析

### 4.1 写法

分析给每个值计算一个事实，例如取值范围：

```camel
analysis range: Interval {
    initial         => Interval::all()                       // 不知道时的值
    join(a, b)      => hull(a, b)                            // 分支汇合时合并
    widen(a, b)     => widen_interval(a, b)                  // 循环中保证收敛（可省）

    on (const c: float) => Interval::point(c)
    on (x + y)          => range(x) + range(y)
    on (x * y)          => range(x) * range(y)
    on (abs(x))         => abs(range(x))
}
```

- `analysis 名字: 事实的类型 { ... }`。
- `on (模式) => 事实`：与规则左边相同的模式写法，右边计算这个值的事实，可以引用输入的事实（`range(x)`）。没有对应 `on` 的值取 `initial`。
- `join` 合并分支汇合处的事实；`widen` 用于循环，可省。
- 分析的结果在规则的 `when` 中按名字读取：`range(x)`。
- **声明可以带参数，参数是模式变量**（协调者 2026-10-21 裁定）：`analysis pair(a: Node, b: Node): bool { ... }` 是一个普通的多参数函数，`when` 里写成 `pair(x, y)`，参数是规则的模式变量。它回答的是**这几个部分所属的那个值**的事实——`on` 子句按顺序匹配一个有这些部分作为操作数的值，所以条件的作者不必给"整个匹配"另起名字；语言也不新增这种命名语法。不带参数的分析仍是 v1 的单值形式（`range(n)`）。
- 一个分析不带参数时，它就是"每个值的事实"；带参数时，它读的是由这些部分指认的那个复合值的事实。两种形式共用同一组 `on` 子句、同一个事实种类与同一套求值。

### 4.2 求值

- 引擎沿数据依赖传播，在汇合处 `join`，在循环处用 `widen` 求不动点。
- 多参数查询先用参数找到那个值：在第一个部分的使用者中，`on` 子句能匹配、且它的操作数正是这些部分（按模式绑定变量的顺序）的那一个；`on` 子句按书写顺序、值按节点编号取舍，所以结果确定。参数不指认任何值时是错误值，不是 `initial`。
- 结果作为事实挂在值上（图存储第二版的事实库），按节点版本判断有效性；改动后沿使用者索引增量重新计算受影响的部分。
- 在等价饱和中，一个值的多种写法各自算出事实，用 `join` 合并（egglog 的做法），因此更多的写法只会让事实更精确或不变。

### 4.3 强制检验

工具枚举全部 `analysis` 声明，用随机事实检验 `join` 的交换律、结合律、幂等律，以及 `on` 的单调性；用随机程序检验事实的正确性（实际运行的值落在推出的事实之内）。不通过不能合并进标准库。

### 4.4 内建分析

常量、类型、形状、纯度与副作用由标准库提供，尽量也用 `analysis` 写成；做不到的（依赖原生信息的）由原生实现提供同样的接口。

## 5. 合法性检查

逐级降低之后要求图满足某种条件，例如"不再有高层算子"：

```camel
let lowered = seq<lower_to_tiles, legal<(n) => is_tiles_op(n)>>(f)
```

`legal<pred>` 是标准库函数：检查每个节点满足条件，否则返回列出违规节点（带源码位置）的错误值。不增加语法。
