# 官方示例计划：经典、高难、工业规模

状态：计划（2026-10-20，语言作者提出）。现有的 `examples/` 是"每个程序做一件事"的短示例；本计划是另一套：**完整的 AI 程序**，用来证明 Camel 的主张，也用来逼出语言与实现的不足。

## 1. 要证明什么

语言作者的判断：**性能上限与 Python 技术栈（PyTorch、JAX，含 `torch.compile`、XLA）齐平，同时写法更可读、更清爽，就是胜利**；生态不是障碍（AI 时代软件开发成本大幅下降）。控制流复杂、动态性强的工作负载尤其重要，因为那里 Python 技术栈确实吃力：`torch.compile` 遇到依赖数据的控制流会断图，JAX 的 `while_loop` 不能反向求导。

所以每个示例都要同时给出四样东西：

1. **Camel 实现**：按当前的设计原则写，代码就是展示品，追求清楚、可读。
2. **对照实现**：同一任务的 PyTorch 实现（必要时加 JAX），按各自社区的惯用写法，不故意写差。
3. **结果一致**：两边的数值结果按数值契约（设计原则第 7 节）比较：严格模式下逐位或在误差界内，默认模式下在合理的容差内；训练类示例比较训练曲线与最终指标。
4. **度量**：代码行数与并排对照（可读性）、吞吐与峰值内存（性能）、编译时间；工业规模的示例另报 MFU（模型浮点利用率）。

### 第二层：高难（控制流与动态性，Camel 的主场）

| # | 示例 | 难点 | 展示的 Camel 能力 |

| D6 | **动态网络**：混合专家（按数据路由）、提前退出网络、束搜索解码 | 依赖数据的分派与提前终止 | 分支与循环在编译后的图中保留 |
| D7 | **HMC / NUTS 采样** | 蛙跳积分的循环、NUTS 动态建树 | 循环、递归、可复现的随机数 |
| D8 | **图神经网络**：消息传递（稀疏邻接） | 不规则的稀疏结构 | 收集与散射、按声明的性质并行 |
| D9 | **智能体**：多步推理的研究助手，每步并行调用多个工具（搜索、读网页、运行代码） | 长耗时的网络调用、超时、竞速与取消、流式接收模型输出 | 没有 `async`/`await` 的自动并发、无序资源、整个流程就是一张图；对照 LangGraph（[网络、并发与流](../io-concurrency-streams/README.cn.md)） |
| D10 | **概率编程**：贝叶斯回归、层次模型、高斯混合，用 NUTS 与变分推断（SVI）求后验；对照 NumPyro（同一模型、同一数据、同一推断算法） | 同一个模型要被多种推断算法以不同方式解释（抽样、给定参数求对数密度、条件化） | `sample`/`observe` 是 `prob` 资源上的效应；每种推断是用 Camel 写的遍，把模型图变换成对数密度函数等，再接 `grad`、`vmap` 与规则优化——NumPyro 用效应处理器逐个解释，Camel 变换整张图；依赖 H246 |

## 3. 硬件约束

可用的最强机器是 **8 张 RTX 3090**（每张 24 GB 显存）。工业规模在这里的含义是"**把这台机器用满、长时间稳定运行，并在同一台机器上与 Python 技术栈对比**"，而不是绝对的参数规模：

- 1 亿到 3.5 亿参数的模型可以完整训练；10 亿参数要靠优化器状态与梯度的按卡切分（每个参数在 FP32 下连同梯度与 Adam 状态约 16 字节，10 亿参数即约 16 GB，再加激活），能做但很紧，不作为第一目标。
- 3090 的 BF16 吞吐不占优，混合精度以 FP16 加损失缩放为主。
- 对比只在同一台机器上进行，结论是"同硬件下与 PyTorch 齐平或更好"，不追求与公开的大规模结果比较。

## 4. 组织方式

- 放在仓库顶层 `showcase/` 下，每个示例一个目录：Camel 实现、对照实现（`baseline/`）、数据获取脚本、运行与比较脚本、`README.cn.md`（说明任务、运行方法、结果表格与并排对照的要点）。
- 每个示例都有一个**小规模配置**（几秒到一分钟，进测试的 `slow` 层，保证示例不会悄悄坏掉）和一个**完整配置**（产出 README 中的结果）。
- 结果表格由脚本生成，注明机器、版本、日期；不手工抄数字。
- 示例暴露的语言或实现问题，记入示例 README 的"遇到的问题"一节，并按交接任务书的格式提问或立项。

## 6. 旗舰示例的当前状态：朴素写法进，专家写法出

设计稿：`docs/design/showcase/naive-in-expert-out.cn.md`（已定，本分支合并 `develop` 后已在树内）。示例在
`examples/models/naive-in-expert-out/`；本节的"现在能跑"指这个目录今天的代码，不是设计稿里的全部目标。

**今天能跑**

- `train_step.cml`：一个小 Transformer 的一个训练步——两段 pre-LN、4 头注意力、RMSNorm、
  GELU MLP、逐位置的朴素 softmax 交叉熵、Adam——在 `std::nvm`、`std::fvm`、`std::jit` 上输出
  相同的固定种子损失，16 步内从 3.4656 降到 1.5680。朴素写法就是教科书写法：`exp(s)/sum(exp(s))`、
  `log(softmax)`、Q/K/V 三个独立投影，没有减最大值、没有 `log_softmax`、没有融合 QKV。
  源码的每个签名和字段都写着形状（`Tensor<f32, [8, 16, 64]>` 与 `TokenStates` 等别名），
  `1 / sqrt(d_head)` 是算出来的而不是字面量 `4.0`，参数计数是模型的 `param_count` 函数。
  `main` 的输入是 `--arg bench=... --arg init_dir=... --arg final_dir=...`，程序不读环境变量；
  线程数由命令行 `-t` 给出，运行时的每个池都从这一个数取大小（`CAMEL_NUM_THREADS` 已不再读取）。
- `torch_impl.py`：同一模型、同一份初始权重与数据的 PyTorch 朴素、专家（`F.scaled_dot_product_attention`、
  `F.log_softmax`、融合 QKV）与 `torch.compile(朴素)` 三个实现，外加一个 float64 参考；四个实现由
  `measure.py` 一条命令驱动。
- `measure.py`：每个实现每步耗时（去掉预热后的中位数）、整进程峰值常驻内存、最终损失与逐参数相对
  float64 参考的最大绝对差。四个实现按轮转顺序交错跑三轮，表里给出轮间范围；机器、线程数、版本、
  构建提交、负载均值与逐轮原始数据写进同一个 JSON，并打印一张人看的表。
- `accuracy.py` 与 `accuracy.cml`：softmax、log_softmax、交叉熵、矩阵乘归约在 bf16/f32/f64 下的
  首个非有限输入、朴素与专家形式在同一输入上的行为，以及矩阵乘归约的 fp64 误差。Camel 侧跑的是
  f32 的可测部分。

**Camel 侧还缺什么**

- **数值类型**：`Tensor` 的公开元素类型是 f32、f64、bf16、f16、i32、i64、bool，元素类型就是写下的那一个
  （`modules/tensor/dtype.h`）。bf16/f16 每个元素两字节（`camel/core/rtdata/half.h`），写入它们的转换会舍入；
  写下的转换就是程序要的精度，不需要数值许可（设计原则 7.2-7.3，2026-10-23 裁定）。读出到更宽的类型总是精确的。
  内核在 f32 中计算、存回元素类型时只舍入一次。bf16 溢出的测量因此也可以在 Camel 里做了；fp64
  误差现在也可以在 Camel 里测。Camel 的 f32 阈值与 PyTorch 的 f32 阈值逐项一致。
- **块只是元组，不是 `Block[]`**：H17 的原生数组语法与带形状的 `Tensor<f32, [...]>` 已经可用，但
  "循环迭代一个依赖可微参数的张量数组"仍被拒绝（反向要把每轮的梯度散射回数组，而数组元素还没有零切向量）。
  模型因此写 `blocks: (Block, Block)`，前向用
  `static loop ... for (i, B) in fields (Block, Block)`；没有 `block0`/`block1` 字段，也没有复制块体。
  H17 能对 `Block[]` 求导后，元组换成数组、静态循环换成
  `loop h = x for b in m.blocks`。
- **`f32[b, t, d]` 还进不了张量算子**：`exp`、`@`、`sum` 接收的是 `Tensor`，不是核心数组类型；
  `let x: f32[2, 3] = randn(...)` 是 `DeclaredTypeMismatch`。示例用带形状的
  `Tensor<f32, [8, 16, 64]>`（以及 `TokenStates` 等别名），每个形状都写全；但
  `Tensor<f32, [b, t, d]>` 里的维度名不绑定（会报 `DimensionNameUsedOnce`），所以只写常量形状，
  由别名与顶部注释说明含义。
- **没有写成类型的 dtype 转换**：`f32(oh)` 没有张量重载，`oh as f32[...]` 是
  `DynamicCastForbidden`；示例用数值提升（f32 * int64 得 f32）代替旧的 `cast(oh, 'float32')`
  字符串。带类型的张量转换仍是缺口。
- **算子与规则**：没有融合 QKV/注意力算子，也没有 `rules::accuracy`、`rules::fusion` 的规则流水线，
  所以朴素源码不会自动变成专家写法；`softmax`、`log_softmax` 与融合交叉熵作为普通算子已经存在，
  但示例刻意不调用它们。融合 QKV 可以手写成 `concat` 后切片，但还没有规则替用户做这件事。
- **自动微分**：`one_hot`、`argmax`、比较与下标的位置等以离散值为输入的算子，回传按定义为零（9.9），
  标签不需要 `stop_gradient`；`one_hot` 注册的是空规则，不是让用户给标签加标记。
- **解释与对照**：`explain` 的改写链依赖规则语言第二版；PyTorch 侧没有做设计的第 5 节
  "杀死搜索"（Inductor 的模式匹配实测），因此"别人做不到"这一句还不能写。
