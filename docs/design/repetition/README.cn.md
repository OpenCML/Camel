# 重复：`EACH` 与 `LOOP`

## 初心

程序里的"重复"在图上原本只有两种写法：一个 `LOOP` 节点，或者一个把元素函数当参数的内置算子（`map`、`filter`、`reduce`、`foreach`）。后一种是黑盒，"怎样逐个元素跑"写在每个后端各自的内核里。这带来四个后果：

1. **算子反过来调后端**：内核要回调当前后端去执行元素函数，算子不再是值到值的函数。
2. **每个后端各写一遍循环**：字节码虚拟机里，这个循环是一段 C++ 代码，每个元素都要付一次完整的调用入口；JIT 没有循环可编。
3. **图上没有"各轮互不依赖"这条性质**：并行调度器只能按算子名去认。
4. **遍看不见结构**：融合、求导、批处理都只能为每个算子单写规则。

把它们在前端编成 `LOOP` 也不行。`LOOP` 带状态，下一轮依赖上一轮，"各轮互不依赖"同样丢了。

所以图上要有两种重复，各对应一种节点，语言里各有一种写法；库里的函数式算子全部用这两种写法加普通递归写成，没有内置的重复算子。语义只说结果是什么，怎么调度由后端决定，这正是"算什么与怎么跑分开"在重复上的落点。

用 Camel 自己实现的东西越多，语言越成熟，同时对优化的要求也越高：调用开销、递归的粒度、循环的降低，都要由编译器与后端做好，不能再由一个手写的内核兜底。这是要走的方向。

## 两种重复

| | 语言写法 | 图上 | 是什么 |
|---|---|---|---|
| 无依赖的重复 | 推导式 `[e for x in xs if c]` | `EACH` | 每一轮各算各的 |
| 有状态的重复 | `loop … for x in xs do …`（状态可不写） | `LOOP` | 每一轮用上一轮的结果，或效应按顺序 |

另外还有普通的递归：它在图上就是函数调用，两次互不依赖的调用本来就可以并发。

划分有理论依据，就是列表同态（Bird–Meertens 形式化与"第三同态定理"）：能在列表上并行计算的函数，恰好可以写成"先 `map`、再用一个结合运算归约"；一般的从左到右折叠只能顺序算。

## `EACH` 节点

`EACH` 由三样组成：

- **迭代空间**：一个或几个等长的数组或范围，决定有几轮。长度不等时，与 `zip` 一样产生故障。范围直接按下标迭代，不先转成数组。
- **体区域**：一个区域，输入这一轮的元素（以及下标），输出这一轮的结果。它与分支的臂、循环的条件与体是同一套区域机制，由同一个"拥有区域的节点"编辑原语建造。
- **汇合方式**：只有两种。
  - **按位置收集**：第 i 轮的结果放在第 i 位，对应没有 `if` 的推导式。
  - **按位置保留**：留下条件为真的那几轮的结果，保持原来的顺序，对应带 `if` 的推导式。

`EACH` 的各轮之间没有先后。由此直接得出两条规则，都不是新加的：

- **体里写共享资源，提交拒绝**。提交检查本来就要求"冲突的访问有先后"，`EACH` 的各轮之间没有先后，所以体里一旦出现与另一轮冲突的写，就被拒绝。冲突按资源效应系统的四条等式判断：同一个资源上的一对访问，至少一方是写，又不满足交换，就是冲突（见 [`../effects/README.cn.md`](../effects/README.cn.md)）。
- **体里给外面的 `var` 赋值是编译错误**。原则 3.5 说循环体里给外面的 `var` 赋值会成为循环携带的状态；`EACH` 没有携带的状态，所以不允许。这与"闭包不能给捕获的名字赋值"是同一个道理。

故障规则沿用原则 3.6：报下标最小的那个故障，所有后端一致。

## 库函数怎样写

| 库函数 | 写法 | 图上 |
|---|---|---|
| `map(xs, f)` | `[f(x) for x in xs]` | `EACH`，按位置收集 |
| `filter(xs, p)` | `[x for x in xs if p(x)]` | `EACH`，按位置保留 |
| `fold(xs, init, f)` | `loop acc = init for x in xs do f(acc, x)` | `LOOP` |
| `foreach(xs, f)` | `loop for x in xs do f(x)` | `LOOP`；各轮足迹不冲突时，优化遍可以改写成 `EACH` |
| `find`、`any`、`all` | 带 `while` 的 `loop`，找到就停 | `LOOP` |
| `reduce(xs, op, unit)` | 二分递归：左右两半各自归约，再用 `op` 合并；空数组得 `unit` | 函数调用 |
| `scan(xs, op, unit)` | 同一棵树上的两遍算法（先自底向上归约，再自顶向下分发） | 函数调用 |

函数写法都保留，用来组合流水线（`xs->map<f>->filter<p>`）、传递已有的函数；推导式用来直接写表达式。两种写法是同一个构造，实现只有一份。

### `find`、`any`、`all`：找到就停

`find` 的结果是下标最小的命中，以及在它之前碰到的故障。找到就停的 `loop` 恰好就是这个语义：下标 3 故障、下标 7 命中，结果是故障；下标 2 命中、下标 5 故障，结果是命中，下标 5 根本不算。

它们暂时是顺序的。并行查找可以做到同样的语义：切块同时找，找到下标 i 后，完全落在 i 之后的块就可以停，取最小的下标。这与原则 3.6 的并行故障规则是同一条。等有实际负载需要时，可以把它作为 `EACH` 的第三种汇合方式加回来，那只是加速，不改语义。

### `reduce`：合并树由定义给出

`reduce` 的定义就是二分递归，这棵递归树是由元素个数唯一决定的平衡二叉树。所以：

- **确定**：结果在所有后端上逐位相同，浮点数也是。
- **自然可并行**：左右两半的递归调用互不依赖，并行调度器照常并发执行，不需要任何特殊机制。
- **数值更好**：两两合并求和的误差随 log n 增长，从左到右累加的误差随 n 增长。

`op` 不必声明满足结合律。语义已经由定义给出，`op` 不满足结合律时结果照样确定，只是不再等于从左到右折叠。想要从左到右，就用 `fold`。编译器若改变合并树的形状，属于 `reassociate` 许可（原则 7.2）。

`scan` 的第 i 位，是前 i+1 个元素按 `op` 合并的结果，例如 `[1, 2, 3, 4]` 用加法得 `[1, 3, 6, 10]`。它用在三类地方：

- **累计量**：累计和、累计最大值。
- **并行的 `filter`**：先对"保留与否"做前缀和，才能并行算出每个保留元素的位置。这是后端调度 `EACH` 时内部的事。
- **线性递推的并行求解**：例如 JAX 的 `lax.associative_scan`。

## 名字只说结果，不说调度

能否乱序、能否并行，由性质决定，不由名字决定：元素函数纯、各轮效应不冲突、合并树固定。这是原则 3.6"并行来自声明的性质，不来自名字"在库函数命名上的直接推论。所以库里没有 `unordered_` 一类的名字。

## 各后端怎样调度同一个 `EACH`

| 后端 | 调度方式 |
|---|---|
| `std::nvm` | 下标从 0 走到 n−1，每轮执行一次体区域 |
| `std::fvm` | 字节码生成时把体区域降成一个字节码循环，体内联，不再每个元素调用一次 |
| `std::jit` | 编译同一个循环 |
| `std::prl` | 按原则 3.6 的粒度，用节点的相对代价把下标范围切块并发；嵌套的 `EACH` 先只并行外层 |
| `std::cpp` | 翻译成一个 `for` |
| GPU 与 ONNX | 体是逐元素运算时，借批处理规则集提升成张量运算；否则用 ONNX 的 `Loop` |

调试器单步时，按下标 0 到 n−1 的顺序走。

## 对优化的要求

库全部用 Camel 写之后，性能由编译器与后端负责。具体有三件：

- **调用开销**：递归版 `reduce` 有约 n 次调用。调用入口要足够便宜，小规模的叶子要能展开成循环。展开必须保持同一棵合并树，因为树是语义的一部分。
- **递归的粒度**：并行调度器面对细粒度的递归，要按相对代价决定在哪一层以下改为顺序执行，不能每次调用都建一个任务（原则 3.6）。
- **循环的降低**：`EACH` 与 `LOOP` 在字节码里都要降成真正的循环，体内联。

验收用一个现成的例子：`benchmarks/parallel/cases/merge_sort.cml` 是并行调度器对比节点虚拟机的归并排序。当初调度能力不够，叶子与合并都只能交给内置的 `array::sort`、`merge_sorted`，以绕开细粒度的递归。库改成 Camel 之后，要用纯 Camel 写的归并排序（递归到小块，合并也用 `loop` 写）证明 `prl` 相对 `nvm` 的加速。

## 和其他部分的关系

- **资源效应系统**：`EACH` 节点的足迹是体的足迹，"可能故障"也由体推出。这与分支、循环取区域内合取是同一套（见 [`../effects/derived-properties.cn.md`](../effects/derived-properties.cn.md)）。
- **求导**：
  - `map` 的反向是对体求反向的 `EACH`。被所有元素共享的输入（例如捕获的权重），各元素的余切要用确定的顺序相加，例如用 `reduce` 的那棵树，否则梯度不可复现。
  - `filter` 的反向把梯度散回保留的位置。
  - 带效应的 `loop` 里，效应只在正向执行，反向是纯的（原则 9.9）。
- **批处理**：体是逐元素运算的 `EACH`，与 `rulesets/vmap.cml` 的批处理规则互相转换。
- **优化遍**：
  - `cse`、`fold`、`dce`、`inline` 都要认得 `EACH` 的体，C++ 版与 Camel 版两套都要。
  - 新的优化机会：把每一轮都相同的计算提到体外；不带状态、各轮足迹不冲突的 `LOOP` 改写成 `EACH`。
  - `EACH` 套 `EACH` 的融合（推导式接推导式），用 Camel 写成一个遍。
- **图编辑 API**：`graph` 模块的查询（`kind`、`region_of`）、规则匹配与提交检查都认得 `EACH`。
- **流**：`EACH` 只用于长度已知的有限集合，也就是数组与范围。惰性的流只能消费一次，走自己的路。
