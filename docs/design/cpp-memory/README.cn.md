## 0. 摘要

**负责人的问题是：把 `std::cpp` 发扬光大，会不会和内存管理模型的设计相冲突。** 回答分三层。

1. **今天不冲突，因为今天的 `std::cpp` 根本没有碰到内存管理。** 它只转译标量和字符串；字符串是运行时堆（auto space）上的对象，生成的代码用裸的 `String *` 拿着它，不登记根、不计数、不拷贝。之所以不出事，是因为生成的程序**从头到尾到达不了任何安全点，于是从不回收**：两百万个短命字符串的程序，字节码解释器在分代回收下占 14 MB，生成的程序占 205 MB（默认回收器）或 429 MB（分代，且慢 3–6 倍）；给 64 MB 的堆上限，解释器跑完，生成的程序以"auto space 耗尽"结束。两种回收器下都安全，代价是内存只增不减（2.2）。

2. **只要它开始转译数组、闭包、`map`，冲突立刻出现，而且是静默的。** 这些构造要调用 Camel 函数，而调用 Camel 函数就是安全点。手写一段与生成代码同样形状的 C++，只加一处安全点轮询：分代回收下打印出**另一个字符串的内容，退出码 0**；默认回收器在强制回收下同样读到别的字符串；安全点毒化模式下段错误。把那个指针登记到影子栈（一个注册给回收器的根表）之后，四种设置下都正确（2.3）。

3. **所以"发扬光大"之前必须先选内存模型。** 语言层面没有障碍——10.5 已定"内存管理的方式不进入语言的语义，各后端可以选适合自己的方式"——障碍全在工程上：仓库里的 C++ 算子都按"对象在运行时的堆上、通过 `ArgsView` 里的槽传递、调用期间不回收"来写，生成的代码要调用它们，就要么住在同一个堆上并告诉回收器自己的引用在哪，要么在边界上转换。

**设计空间有四类**（第 4 节逐类展开，4.6 是对照表）：

- **甲：住在运行时的堆上，生成的代码给出精确的根**（影子栈／根帧）。算子不用改，两种回收器都成立，同一套机制可以解开即时编译"带帧的代码在移动式回收下怎么办"的结；代价是跨安全点存活的引用要放在内存里。手写原型量到的开销在测量噪声之内到 15% 左右。不能脱离运行时部署。
- **乙：生成的代码自带内存模型**（引用计数、C++ 值类型、区域）。Camel 的值不可变、除了变量单元之外不成环，图上又直接有"每个值被谁用"的信息，是引用计数的好材料；能脱离运行时。代价是现有的算子库不能原样用：要么每个算子的结果做一次"认领"遍历，要么重写一套。
- **丙：保守扫描原生栈，或者干脆不移动、不回收。** 生成的代码零开销；但对象今天不带类型，保守扫描到一个数组也不知道它的元素是不是引用——除非给每个对象头里加一个类型字。
- **丁：混合。** 最有用的一条与上面三类都不冲突：先把不逃出函数的元组、结构体、`T?`、`T!`、变量单元变成 C++ 的局部值，根本不上堆。

**建议**（第 5 节）：主线走"丁 + 甲"，分四步；乙作为以后单独的"独立部署"模式，是否要做取决于负责人对 `std::cpp` 定位的回答（Q1）；丙不单独做：它的前提是每个对象带类型，而 [`any` 的报告](../any-typing/README.cn.md)建议的治理办法并不需要这一点（Q6）。**无论选哪条，第一步都是把今天这个子集做对**：现在被转译的 201 个程序里，只有 126 个（63%）编得过并且与解释器的输出、退出码一致（1.5），测试计划里的 4 个用例没有一个编译过生成的 C++。

**需要负责人确认的事**（第 6 节，共 8 条）里最要紧的三条：

1. **Q1 `std::cpp` 的首要目标**：同一运行时上的预编译后端（追求速度）、脱离运行时的独立部署，还是给人读的 C++ 导出。三者对内存模型的要求不同。
2. **Q2 一个后端可以不回收某些垃圾（甚至完全不回收）是否算符合语义。** 今天的生成代码就是完全不回收；引用计数不回收经过变量单元形成的环。
3. **Q4、Q5 故障的位置、递归上限、尾调用的常数栈**在生成的程序里是否必须与调度器一致。今天都不一致：故障没有源码位置，非尾递归没有上限（三百万层直接段错误），一千万步的尾递归循环段错误。

**调查中发现的现有缺陷**共 12 项，见附录 B。其中会让程序算错而不报错的有四项：浮点常量只保留六位小数（`1e-7` 变成 `0`）；对字符串的 `match` 比较的是对象地址，永远走默认分支；同步块里的分支被推迟到它的值第一次被使用的地方，副作用顺序错；分支的值被用两次，被选中的臂就执行两次。

## 1. `std::cpp` 今天是什么

### 1.1 位置、模式与规模

`std::cpp` 是一个转译遍：吃掉图，往标准输出写一个 C++ 翻译单元，不再往下传图。【读码 `src/passes/trans/cpp/cpp_export.cpp:98-146`】有四个模式和四个别名【读码 `src/execute/pass.cpp:315-321、422-425`】：

| 遍 | 别名 | 作用 |
|---|---|---|
| `std::cpp` | `std::cxx` | 以 `main` 为入口，生成带 `int main()` 的可执行程序源码 |
| `std::cpp::module` | `std::cppmod` | 不要求 `main`，把顶层的具名函数都写出来，没有 `int main()` |
| `std::cpp::inspect` | `std::cppinspect` | 同上，每个函数前加一段注释列出节点的种类与槽位 |
| `std::cpp::bench` | `std::cppbench` | 先找名叫 `fib` 的图，找不到再用 `main`【读码 `runtime_emitter.cpp:274-281`】 |

源码规模：`runtime_emitter.cpp` 1,227 行、`bridge.cpp` 505 行、`cpp_export.cpp` 146 行、`cpp_bridge_runtime.cpp` 86 行、头文件 `include/camel/passes/trans/cpp/cpp_bridge.h` 241 行；另有一个把"转译 + 调 clang"包起来的小工具 `tools/camel-cpp/main.cpp` 227 行。`lower.cpp`（105 行）里有一张"哪些算子可以直接写成 C++ 运算符"的表，但 `findCppOperatorSpec` **没有任何调用点**，这张表是死的。【读码：全仓库检索该函数名只有定义与声明】

### 1.2 输出的样子

```camel
func fib(n: int): int {
    return if n <= 1 then n else fib(n - 1) + fib(n - 2)
}
func main(): int sync { println(fib(32)); return 0 }
```

`camel docs/design/cpp-memory/examples/accepted/a01_fib.cml std::cpp`【实测，删去了三个与 `o_io_println` 同样形状的算子访问器】：

```cpp
#include "camel/passes/trans/cpp/cpp_bridge.h"
#include "camel/core/rtdata/base.h"
#include "camel/core/type.h"
#include <iostream>
using namespace camel::core::type;
using namespace camel::core::rtdata;
using namespace camel::execute::cppbridge;

namespace generated {
inline BoundOperator &o_io_println() {
    static auto &op = bridge().bind(":io/println");
    return op;
}
// o_op_add_l、o_op_le_l、o_op_sub_l 同上

static inline Int64 f_g_4(Int64 v_arg_0) { return v_arg_0; }

static inline Int64 f_g_6(Int64 v_arg_0_) {
    const Int64 v1_op_sub_l = o_op_sub_l().call<Int64>({val(Type::Int64(), v_arg_0_), val(Type::Int64(), 1LL)});
    const Int64 v2_fib = f_fib(v1_op_sub_l);
    const Int64 v3_op_sub_l = o_op_sub_l().call<Int64>({val(Type::Int64(), v_arg_0_), val(Type::Int64(), 2LL)});
    const Int64 v4_fib = f_fib(v3_op_sub_l);
    const Int64 v5_op_add_l = o_op_add_l().call<Int64>({val(Type::Int64(), v2_fib), val(Type::Int64(), v4_fib)});
    return v5_op_add_l;
}

static inline Int64 f_fib(Int64 v_arg_0__) {
    const Bool v1_op_le_l = o_op_le_l().call<Bool>({val(Type::Int64(), v_arg_0__), val(Type::Int64(), 1LL)});
    return (v1_op_le_l) ? (f_g_4(v_arg_0__)) : (f_g_6(v_arg_0__));
}

static inline Int64 f_main() {
    const Int64 v1_fib = f_fib(32LL);
    const Int64 v2_io_println = o_io_println().call<Int64>({val(Type::Int64(), v1_fib)});
    const Int64 v3_value = 0LL;
    return v3_value;
}
} // namespace generated

int main() {
    initialize();
    int ret = 0;
    try {
        ret = static_cast<int>(generated::f_main());
    } catch (const std::exception &e) {
        std::cerr << "Error: " << e.what() << std::endl;
        ret = 1;
    } catch (...) {
        std::cerr << "Unknown error" << std::endl;
        ret = 1;
    }
    finalize();
    return ret;
}
```

读这段输出能看到今天的全部设计：

- **一张图一个 C++ 函数**，分支的每条臂也是一张图，所以也是一个函数（`f_g_4`、`f_g_6`）。
- **没有帧**。形参是 C++ 形参，节点的值是 `const` 局部变量。这是 `09_gir_cpp_fib_lowering.md` 定下的方向（"把 `Frame` 彻底编译掉"）。
- **每个算子都经"桥"调用**，包括 `n - 1` 这样的整数减法。那份文档第 3.3 节写的"纯值算子内联为 C++ 运算符"没有实现（1.1 的死表）。
- **`int main()` 用 `try`/`catch` 把一切异常变成 `Error: …` 和退出码 1。**

### 1.3 能转译的子集

**类型只有七种**：`int32`、`int64`、`float32`、`float64`、`bool`、`string`、`void`。【读码 `bridge.cpp:113-129`】一张图的返回值、形参、`with` 形参、常量、算子的结果与实参只要有一个不在这七种里，整个程序被拒绝（`TranslationRefused`，带源码位置）。【读码 `runtime_emitter.cpp:344-433`】

**节点**【读码 `runtime_emitter.cpp:381-534`】：

| 节点 | 处理 |
|---|---|
| `DATA`、`PORT`、`OPER`、`BRCH`/`JOIN`、`CAST`、`COPY`、`GATE` | 转译（类型在七种之内时） |
| `FUNC` | 转译，但被调函数不能有捕获（"std::cpp does not translate closures yet"） |
| `CALL`（经函数值调用）、`FILL`（构造结构体、元组、数组、闭包）、`ACCS`（取成员）、`BIND`、`SYNC`、`DREF` | 拒绝 |

**程序层面**：必须有 `main`；`main` 不能带参数【读码 `cpp_export.cpp:104-119`】；`main` 必须声明返回整数，否则不是拒绝而是内部错误（附录 B D10）；模块顶层的值只能是字面量【读码 `runtime_emitter.cpp:1062-1084`】。

每种被拒绝的构造在 `examples/refused/` 里有一个最小程序，它们在 `std::fvm` 上都能运行。`bash docs/design/cpp-memory/tools/run_examples.sh docs/design/cpp-memory/examples/refused std::cpp`【实测，只留拒绝理由】：

| 程序 | 拒绝理由（原文） |
|---|---|
| `r01_array` | function 'main' uses a constant of type 'int[]', which has no C++ literal |
| `r02_tuple` | function 'pair' returns a value of type '(int, int)' |
| `r03_struct` | function 'main' uses a constant of type '{ x: int, y: int }' |
| `r04_closure` | function 'main' uses a constant of type '(x: int) => int' |
| `r05_funcvalue`（`range->map->reduce`） | the result of operator ':struct/range' in function 'main' has type 'int[]' |
| `r06_nullable` | an anonymous function returns a value of type 'int?' |
| `r07_fallible`（`parse_int(..) !! -1`） | a 'with' parameter of an anonymous function has type 'int!' |
| `r08_var` | the result of operator ':var/new' in function 'main' has type 'var int' |
| `r09_map` | a 'with' parameter of an anonymous function has type 'int?' |
| `r10_tensor` | function 'main' uses a constant of type 'int[]'（形状字面量先被拒绝） |
| `r11_main_args` | 'main' takes parameters, and std::cpp does not translate the parameters of the entry function yet |

一句话：**今天的 `std::cpp` 是"标量递归函数加字符串打印"的转译器。**

### 1.6 每种值今天怎样表示

| 值 | 生成的 C++ 里是什么 | 出处 |
|---|---|---|
| `int`、`i32`、`float`、`f32`、`bool` | `Int64`、`Int32`、`Float64`、`Float32`、`Bool`（`rtdata` 里的标量别名），按值放在形参和 `const` 局部变量里 | 【实测 1.2】【读码 `bridge.cpp:131-150`】 |
| `string` | `String *`：指向运行时 auto space 里的 `String` 对象的裸指针。字面量写成 `String::from("…", mm::autoSpace())`，**每求值一次分配一个新对象** | 【实测 `examples/accepted/a02_strings.cml`】【读码 `bridge.cpp:191-199`】 |
| `void`（如 `println` 的结果被丢弃） | `slot_t` | 【读码 `bridge.cpp:145-146`】 |
| 数组、元组、结构体、映射、集合、张量 | 不支持（拒绝） | 1.3 |
| 函数值、闭包 | 不支持（拒绝）。没有捕获的具名函数只能被直接调用 | 1.3 |
| `T?`、`T!` | 不支持（拒绝） | 1.3 |
| `var` 单元 | 不支持（拒绝，`:var/new` 的结果类型 `var int` 不在七种之内） | 1.3 |
| `any` | 不支持（拒绝） | 1.3 |

字符串虽然在七种之内，实际能用的范围很窄：它一旦成为一个语句级的局部变量（声明被写成 `const String * v = …`，是"指向常量的指针"），再作为返回值或传给另一个生成的函数（形参是 `String *`）就编译不过。【实测 `examples/defects/d08_string_local.cml`】【读码 `runtime_emitter.cpp:1170`：一律在 `cppTypeFor` 的结果前拼一个 `const `】只有"从一个算子直接流进下一个算子"的字符串能通过。

### 1.7 算子、函数、分支、尾调用、高阶算子各是怎么出来的

**调用 C++ 算子**【读码 `runtime_emitter.cpp:817-854`；`cpp_bridge.h:69-88、154-240`】：每个用到的算子 URI 生成一个访问器，第一次调用时按 URI 在运行时的算子表里查到函数指针并存在函数内的 `static` 里。一次调用是 `o_xxx().call<返回类型>({val(类型, 值), …}, {with 实参…})`：把每个实参转成一个槽（`slot_t`）连同它的 `Type *` 填进桥对象里的两组 `std::vector`（普通实参一组，`with` 实参一组，**整个进程共用一份**），在它们上面建两个 `ValueArgsView`（虚函数接口），然后调用 `slot_t op(ArgsView &with, ArgsView &norm, Context &)`，把返回的槽转回 C++ 类型。也就是说，生成的代码调用算子的方式与调度器完全一样（同一个函数指针、同一个接口），只是实参来自一块临时区而不是帧。

这块临时区不可重入：假如被调用的算子反过来执行了生成的代码，后者再调用任何算子都会覆盖外层算子正在读的实参。今天不会发生，因为没有算子会回调（见下面"高阶算子"）；这是将来要改的地方。【读码 `cpp_bridge.h:196-202、228-229`】

`COPY` 在生成的代码里什么都不做，原样用输入的表达式（解释器对对象做一次拷贝）；在今天的七种类型里这分辨不出来。【读码 `runtime_emitter.cpp:960-962`】

**调用用户函数**：直接的 C++ 调用。`with` 实参排在普通实参之后，成为普通的 C++ 形参。【读码 `runtime_emitter.cpp:881-905`】

**分支**：`JOIN` 被写成 C++ 的条件表达式 `(条件) ? (臂 1) : (臂 2)`，多路的 `match` 写成一串 `(选择子 == 常量) ? … : …`。【读码 `runtime_emitter.cpp:906-959`】臂是函数调用，所以没被选中的臂不执行。但这个表达式是一段**文本**，被粘贴到每一个使用 `JOIN` 的值的地方，不在它该执行的位置上落成语句。由此有两个缺陷（附录 B D4、D5）：分支的值被用两次，文本就出现两次，被选中的臂执行两次；同步块里排在分支之后的效应，会跑到分支之前。字符串上的 `match` 则因为 `==` 比较的是两个 `String *`（常量每次都是新分配的对象）而永远不相等（D3）。

**尾调用**：没有任何处理，就是 C++ 的 `return f(...)`。一个尾递归的循环 `loop` 变成 `f_loop` 与它的臂函数 `f_g_6` 两个互相调用的函数，栈会不会增长取决于 C++ 编译器。`clang++ -O2` 下一千万步的循环段错误；把原生栈设为不限之后同一个程序给出正确结果，说明原因就是栈。【实测 `examples/defects/d10_tail_loop.cml`；附录 A】非尾递归同样没有深度上限（D7）。[循环设计稿](../loops/README.cn.md)（1.2 的表）已经记过"是否变成循环取决于 C++ 编译器"。

**高阶算子**（`map`、`filter`、`reduce`、`foreach`、`apply`、`attempt` 等）：不支持，而且今天的结构支持不了。它们在运行时里**不是 C++ 算子**，而是 `:mark/map_arr` 这样的标记，由每个调度器自己实现（共 8 个标记）【读码：检索 `":mark/` 得到 `map_arr`、`apply_arr`、`filter_arr`、`reduce_arr`、`foreach_arr`、`unordered_reduce_arr`、`unordered_foreach_arr`、`isolate`】。生成的代码要支持它们，就得自己把它们写成 C++ 循环。

### 1.8 构建、链接与运行

## 2. 生成的代码今天怎样管理内存

### 2.1 做法：运行时的堆上的对象，裸指针拿着，不告诉任何人

```camel
func main(): int sync {
    println('hello, ' + 'camel' + ' #' + string(1))
    ...
```

`camel docs/design/cpp-memory/examples/accepted/a02_strings.cml std::cpp`【实测，节选】：

```cpp
const String * v1_op_add_s = o_op_add_s().call<String *>({
    val(Type::String(), String::from("hello, ", mm::autoSpace())),
    val(Type::String(), String::from("camel", mm::autoSpace()))});
```

- 对象在**运行时的回收堆**上：字面量由生成的代码自己在 `mm::autoSpace()` 里分配，算子的结果由算子在同一个堆上分配。
- 生成的代码用**裸指针**拿着它们：C++ 的局部变量、形参、表达式里的临时值。没有 `RootHandle`，没有引用计数，没有登记任何根；桥的那块实参临时区也不是根。【读码 `cpp_bridge.h:69-88`；`runtime_emitter.cpp` 全文没有 `RootHandle`、`registerExternalRootTracer`、`safepoint` 字样】
- 这些裸指针**跨越分配点**：上面一条语句里，第一个 `String::from` 的结果在第二个 `String::from` 分配期间就悬在表达式里。按句柄规则这是允许的——分配不是安全点，不回收也不移动任何对象（规则 1 与"不是安全点"一节）。

### 2.2 今天是安全的，原因是它从不回收

回收只在安全点发生；安全点只有"调用 Camel 函数（由调度器轮询）、高阶算子的每个元素、宏求值器、遍的边界、显式调用"这几种（句柄规则第 1 节）。生成的程序里没有调度器，没有图，能转译的算子没有一个会执行 Camel 代码（那需要函数值，而函数值被拒绝），算子自己也不触发回收【读码：在 `src/builtin` 与 `modules` 的 `.cpp` 里检索 `safepoint(`、`minorGC()`、`majorGC()` 无结果】，生成的代码自己也不轮询。所以：**生成的程序从 `initialize()` 到 `finalize()` 一次安全点都到达不了，回收器一次都不运行。**

`bash docs/design/cpp-memory/tools/measure_all.sh memory`【实测】，程序是 `examples/accepted/a04_string_churn.cml`（两百万次迭代，每次造几个马上就没用的字符串）：

| | `std::fvm` | `std::cpp` 生成的程序 |
|---|---|---|
| 默认回收器：回收次数 | 2 次整堆回收 | **0**（统计行：`major=0 … deferred=1`，有一次回收请求一直挂着） |
| 默认回收器：峰值常驻内存 | 123 MB | **205 MB** |
| 默认回收器：用时（秒） | 2.30 [1.35, 3.12] | 0.85 [0.83, 1.01] |
| `CAMEL_GC=generational`：回收次数 | 37 次小回收 | **0** |
| `CAMEL_GC=generational`：峰值常驻内存 | **14 MB** | **429 MB** |
| `CAMEL_GC=generational`：用时（秒） | 1.24 [0.67, 1.57] | **5.43 [2.59, 7.70]** |
| 分配总量 | 85 MB | 127 MB（字面量 `'item-'` 每次迭代重新分配一个） |
| `CAMEL_GC_HEAP_LIMIT_MB=64` | 正常结束 | `Error: The auto space (run-time values) is exhausted … 96.0 MB of the limit of 64.0 MB are in use`，退出码 1 |

三点：

1. **内存只增不减。** 程序的存活数据不到 1 KB，生成的程序占了 205 MB。任何长时间运行、持续分配的程序最终会耗尽内存。
2. **分代回收下更糟。** 4 MB 的出生区填满之后没有人来回收它，之后的每次分配都退到年老区的空闲链表里（统计行：`alloc_young_mb=2.6 alloc_elder_mb=124.8`），又慢又占地方。分代回收器对"从不到达安全点的程序"是负优化。
3. **毒化和压力设置对生成的程序没有任何作用。** `CAMEL_GC_POISON=1`、`CAMEL_GC_STRESS_SAFEPOINT=1 CAMEL_GC_STRESS_MODE=major`、`CAMEL_GC=generational CAMEL_GC_VERIFY=both …` 下 `a02_strings` 的输出都正确，统计行里回收次数都是 0。它们检查的是"安全点上有没有拿错指针"，而这里没有安全点。所以**不能用现有的回收器测试手段去证明今天的生成代码"安全"**——它只是没有被检验的机会。

### 2.3 一旦生成的代码能到达安全点

转译数组、闭包或 `map`，生成的代码就要调用 Camel 函数值、要为长循环轮询回收，裸指针就会跨过安全点。现有转译器产生不了这样的程序，所以这里用一段手写的 C++ 演示：`examples/handwritten/roots.cpp`，形状与生成的代码相同（运行时堆上的 `String`、C++ 局部变量里的裸指针），只多一处 `mm::safepoint()`，代表"这里本来会调用一个 Camel 函数"。四种写法：

- `raw`：今天的生成代码——裸指针，不轮询；
- `raw-poll`：裸指针，轮询；
- `shadow`：把局部变量的地址和它的静态类型登记到一个影子栈里（影子栈通过 `registerExternalRootTracer` 注册给回收器，整个程序只注册一次），轮询；
- `handle`：用 `mm::RootHandle` 拿着，轮询。

工作负载 `keep`：开头造一个字符串，再造两百万个别的字符串，最后读开头那个。`bash docs/design/cpp-memory/tools/poll_demo.sh`【实测】：

| 写法 | 默认回收器 | `CAMEL_GC=generational` | `CAMEL_GC_POISON=1` | 默认回收器 + 每 1000 个安全点强制整堆回收 |
|---|---|---|---|---|
| `raw` | 正确 | 正确 | 正确 | 正确 |
| `raw-poll` | 正确（碰巧） | **打印 `item-18189`，退出码 0** | 段错误（139） | **打印 `item-1000`，退出码 0** |
| `shadow` | 正确 | 正确 | 正确 | 正确 |
| `handle` | 正确 | 正确 | 正确 | 正确 |

（正确的输出是 `the string kept from the start / 22888896`。）另外两个负载 `loop`（每次迭代持有上一个字符串）与 `calls`（500 层递归，每层持有一个字符串跨过下面的调用）在 `raw-poll` 下：分代与强制整堆回收时碰巧正确，毒化模式下打印出一个天文数字（`8294236160000000`）而退出码仍是 0。

这张表就是冲突本身：

- **分代回收器**把对象搬走，裸指针读到的是后来分配在同一地址上的别的对象。
- **默认回收器**不搬对象，但它只认根：没有登记的引用所指的对象会被当作垃圾释放，那块内存再被别人用。裸指针在默认回收器下**同样不安全**，只是要等到真的回收了才出事（默认回收器要分配几十 MB 的小对象之后才第一次回收）。句柄规则的原话是"在 mark-sweep 下违规要等到对象被释放才显现"。
- 两种情况下都**不报错**：程序给出错误的结果并以 0 退出。这与分代回收报告 6.4 记录的 `any` 缺陷是同一种失败方式。

### 2.4 小结

| 问题 | (a) 默认回收器（mark-sweep，不移动） | (b) 分代回收器（年轻对象会移动） |
|---|---|---|
| 今天的生成代码安全吗 | 安全：没有安全点，不回收 | 安全：同上 |
| 今天的代价 | 内存只增不减（205 MB 对 123 MB） | 内存只增不减，且更慢、更占内存（429 MB 对 14 MB；5.4 秒对 1.2 秒） |
| 裸指针跨分配点 | 安全（分配不是安全点） | 安全（同上） |
| 裸指针跨安全点（今天产生不了，2.3 手写演示） | **不安全**：对象被释放后读到别的对象；要等回收真的发生 | **不安全**：对象被搬走；每 4 MB 分配就发生 |
| 桥的实参临时区 | 不是根；今天不需要是 | 同左 |
| 把指针登记到影子栈或 `RootHandle` | 安全 | 安全，每次安全点之后须从登记处重新读 |

## 3. 设计要受哪些事实约束

### 3.1 语言一侧：留出的自由，和三处例外

10.5 的裁定："内存管理的方式不进入语言的语义：对象没有可观察的身份，回收的时机不可观察，C++ 算子通过句柄接触对象。各后端可以选适合自己的方式。"由此得到三条后端可以依赖的推论：

- **共享一个对象与各拿一份拷贝，程序分辨不出来。** 后端可以按值拷贝，也可以共享；可以把对象从一处搬到另一处。
- **回收得早、晚、还是根本不回收，程序分辨不出来。** 一个后端不回收某些垃圾，在语义上不算错，只是资源问题（今天的生成代码就是这样）。这一点需要负责人明确认可（Q2）。
- **值由下往上构造、构造之后不可变**（给变量或它的一个字段、元素赋值得到的是一个新值，3.5），而且类型不能直接包含自身（5.2 的递归只经数组、映射、集合与 `enum`），所以一个值只能引用比它先存在的值，**值之间不会成环**。

但有三处"身份"是存在的，任何方案都要单独对待：

1. **变量单元。** `var` 是一个单元，闭包按引用捕获它（3.5："闭包对变量的捕获也是引用"）。两个闭包捕获同一个 `var`，一个写、另一个要读到。单元**必须共享，不能拷贝**。环也只可能经过它产生：一个单元里放着一个捕获了这个单元的闭包。
2. **`var` 实参被算子原地修改。** 今天的 `append` 的签名是 `<value: T> (var arr: T[]) => T[]`，实现是在原数组上追加再把同一个数组返回。【读码 `src/builtin/modules/globals.cpp:1382-1388`；`src/builtin/operators/struct.cpp:194-199`】【实测 `examples/defects/o01_append_needs_var.cml`：把 `let` 数组交给 `append` 是 `ImmutablePassedToVarParam`】也就是说，**运行时层面存在被原地修改的数组**（以及张量的显式原地算子，11.3）；被修改的对象必须是调用方看得见的那一个。这与 11.3"`append` 一类的操作返回新值，不原地修改"的说法对不上，本稿只记录（附录 B 观察 O1），它对内存模型的含义是：凡是经 `var` 到达的对象，后端不能悄悄换成拷贝。
3. **外部资源的包装对象。** `ForeignResourceObject` 带释放函数，`dispose` 之后"包装对象仍然有效并报告已释放的状态"（句柄规则第 9 条）。它有状态，拷贝它等于让一个资源有两个主人。必须共享。

### 3.2 运行时一侧

| 事实 | 出处 | 对生成代码的含义 |
|---|---|---|
| 分配不是安全点：不回收、不移动 | 句柄规则第 1 节；`gen.h:356-360` | 两个安全点之间可以随便用裸指针。只有**跨安全点存活**的引用需要处理 |
| 安全点由执行者决定在哪：调度器在调用处轮询，算子里没有 | 句柄规则第 1 节 | 生成的代码自己决定在哪轮询（函数入口、循环回边）。不轮询就永不回收 |
| **对象不带类型**：回收器靠"到达这个对象的那个槽的静态类型"去追踪它里面的引用 | 句柄规则第 5 节 | 生成的代码登记一个根，必须同时给出它的静态类型；保守地扫描到一个对象，不知道怎么追踪它（4.4） |
| 分代：64 KB 以下的年轻对象会移动；年老对象与大对象不动 | 分代回收报告第 2 节 | 安全点之后一切裸指针（包括指向对象内部的）作废，要从根重新读 |
| `registerExternalRootTracer`：任何代码可以注册一个"我的根在这里"的回调 | `gen.h:328-330`；帧池就是这样接入的（`frame.h:385-399`） | 生成的代码可以用它接入一个影子栈。【实测 2.3 的 `shadow`】 |
| `RootHandle`：创建和销毁各取一次分配器的锁 | `root_handle.h:33-37` | 适合"每次算子调用一个"，不适合"每次函数调用一个"（4.2 的数字） |
| 有原生帧（即时编译的代码）在栈上时，安全点被拒绝并抛出逻辑错误 | `gen.cpp:304-310`；`fastvm.cpp:740-749` | 即时编译今天靠"编译出的代码不调用任何东西"躲开这个问题；生成的 C++ 没有这个计数，也没有这个保护 |
| C++ 算子的接口是 `slot_t op(ArgsView &with, ArgsView &norm, Context &)`，结果直接在 `mm::autoSpace()` 上分配 | `operator.h:45-58`；`src/` 与 `modules/` 的 `.cpp` 里有 182 处 `autoSpace()` | **算子的结果必然在运行时的堆上**，不管生成的代码想把自己的值放在哪 |
| 算子可以把实参里的引用**原样拷进**自己新建的容器，不经任何登记（规则 6：往本次调用里新建的对象里写可以用普通的存储） | 句柄规则第 2 节规则 6 | 对回收器无害；对引用计数是问题：算子让一个对象多了一个引用者却没有加计数（4.3） |
| 高阶算子不是 C++ 算子，由各调度器实现 | 1.7 | 生成的代码要自己实现它们 |

### 3.3 图数据模型一侧

设计稿（[graph-model](../graph-model/README.cn.md)）里与本题有关的：每个节点有类型（`TypeId`）与"值是变量单元"的标志（3.4）；图有四位效应摘要（3.3）；算子表项声明纯度、`mayFault`、`callsGraphs`（Q1）；第 6 节把 `std::cpp` 列为"约 200 行"的消费者，前提是它"按执行序把每张图译成一个 C++ 函数"这个读法不变。转译器还需要模型提供什么，在 4.7。

## 4. 设计空间

### 4.1 三个要回答的问题

任何方案都要回答：

- **问题一：对象住在哪。** 运行时的堆，还是生成的代码自己的内存。
- **问题二：谁知道原生帧里有哪些活的引用。** 生成的代码明说（精确的根）、对象自己记数（引用计数）、回收器去猜（保守扫描）、或者按结构整块处理（区域）。
- **问题三：生成的代码与 C++ 算子怎样交换值。** 仓库内 21 个模块加内建算子、仓库外的第三方模块，都按 3.2 的接口和句柄规则写成。

下面用同一个小函数贯穿各方案：

```camel
func tag(name: string, xs: string[]): string {
    let head = first(xs)            // 调用 Camel 函数：安全点
    return name + ': ' + head       // name 跨过了那个安全点
}
```

### 4.2 方案甲：住在运行时的堆上，生成的代码给出精确的根

对象照旧在 auto space 上，算子照旧调用。生成的代码遵守与调度器相同的纪律：**跨安全点还要用的引用放在回收器看得见、改得了的地方，安全点之后从那里重新读。**

拟议的输出：

```cpp
static String *f_tag(String *name, Array *xs) {
    RootFrame<1> roots({Type::String()});   // 把这一帧挂上影子栈：两次写内存；析构时摘下
    roots[0] = name;                        // name 在安全点之后还要用：进帧
    String *head = f_first(xs);             // xs 之后不再用：不进帧。被调函数自己负责自己的形参
    // 从这里到返回没有安全点：裸指针随便用（句柄规则第 1 条）
    String *t = o_op_add_s(roots.get<String>(0), k_colon());
    return o_op_add_s(t, head);
}
```

要点：

- **只有跨安全点存活的引用进帧。** 这要一次活跃分析，在数据流图上很直接：一个节点的值在某个安全点节点之后还有使用者，它就要进帧。不含任何安全点的图（叶子函数、纯标量函数）一个槽都不需要，生成的代码与今天一样。
- **实参与返回值不需要额外保护。** 从求出实参到被调函数入口之间没有安全点；返回值从 `return` 到调用方把它存好之间也没有。这正是调度器今天的约定（句柄规则第 4 节"Argument passing"）。
- **轮询放在函数入口与循环回边**，开销是读一个原子布尔量加一次分支（`mm::safepoint()` 的快路径，`gen.h:698-706`）。
- **高阶算子写成 C++ 循环**：结果数组进帧，每个元素的调用是安全点，每轮从帧里重新读数组——与三个调度器里的写法一样。
- **根的表示有三种选法**：（1）影子栈，每个函数一个带静态类型表的帧，链成链表（上面的写法）；（2）句柄作用域，一个全局的句柄数组加栈顶指针；（3）直接用运行时的 `Frame`。今天的 `RootHandle` 太重（创建和销毁各取一次锁），不能每次函数调用用一个。`09_gir_cpp_fib_lowering.md` 已经否定了"把整个 `Frame` 搬到 C++ 栈上"，理由是标量也被迫进内存；这里的做法是标量留在 C++ 局部变量里，只有引用进帧。
- **栈映射不在选项里。** 生成的是 C++ 源码，C++ 编译器不给出"这个调用点上哪些寄存器和栈槽里是引用"的表。要栈映射得换成生成 LLVM IR 并使用它的 statepoint 机制，那是另一个后端。

**开销（手写原型，不是转译器输出）。** `tools/measure_all.sh roots`，两百万次【实测，秒；峰值常驻内存】：

| 写法 | `loop`，默认回收器 | `loop`，分代 | `calls`，默认回收器 | `calls`，分代 |
|---|---|---|---|---|
| `raw`（今天：不轮询、不回收） | 0.26 [0.24, 0.49]，84 MB | 0.83 [0.50, 0.86]，164 MB | 0.32 [0.28, 0.39]，81 MB | 0.82 [0.69, 1.02]，161 MB |
| `raw-poll`（轮询，不登记根：不安全） | 0.38 [0.34, 0.81]，91 MB | — | 0.45 [0.39, 0.53]，95 MB | — |
| `shadow`（影子栈） | 0.41 [0.33, 0.69]，91 MB | **0.25 [0.21, 0.33]，11 MB** | 0.51 [0.42, 0.58]，95 MB | **0.33 [0.25, 0.40]，11 MB** |
| `handle`（`RootHandle`） | 0.65 [0.43, 0.97]，91 MB | 0.21 [0.18, 0.32]，11 MB | 0.70 [0.51, 0.87]，95 MB | 0.46 [0.41, 0.55]，11 MB |

- `raw` 的时间里没有回收（它从不回收）；其余三行有。所以该比的是 `raw-poll` 与 `shadow`：差别在 `loop` 上不到 10%，在 `calls`（每次调用挂一帧）上约 15%，都与同一行的最小–最大区间重叠。**在这个原型上，影子栈的开销量不出比噪声明显更大的值。**
- `RootHandle` 每次调用一个要比影子栈多花 35–55%（`calls`），印证了它的头文件里写的"不要按循环元素用"。
- **有了根，分代回收器才发挥作用**：`shadow` 加分代是全表最快的一格，内存 11 MB；`raw` 加分代最慢、最占内存（2.2 第 2 点）。
- 原型只有字符串、只有一个根。数组的数组、闭包、深的调用链上是多少，没有量（第 7 节第 1 条）。

**逐项评估：**

| 方面 | 评估 |
|---|---|
| 性能 | 标量代码零开销（不进帧）。持有引用的函数每次调用多两次内存写，每个跨安全点的引用多一次存、每次使用多一次取。C++ 编译器不能把这些引用留在寄存器里跨调用 |
| 与现有 C++ 算子 | **原样可用**，两种回收器下都成立。桥的实参临时区要改成每次调用在栈上建（现在是进程里共用一份，不可重入，1.7） |
| 与即时编译 | **同一个问题，同一个解法。** 即时编译今天只编译"不调用任何东西"的图，就是因为带帧的原生代码没有栈映射（句柄规则第 4 节；分代报告 6.1：分代下损失 93 张图里的 9 张，最坏慢 21 倍）。让编译出的代码在调用之前把引用写进同一个影子栈，它就可以调用算子和别的图，而不需要栈映射；`nativeCodeDepth` 的"有原生帧就拒绝安全点"可以对遵守这个约定的代码放开。`lane/jit-coverage` 的工作在本工作树里看不到【未查】，这里只能说方向一致 |
| 独立部署 | **不行。** 需要回收器、类型对象、算子表，也就是 `libcamel`（8.6 MB）。可以设想切出一个不含编译器的"仅运行时"库，大小与工作量【未查】 |
| 对语言语义的要求 | 没有 |
| 主要风险 | 转译器的每一个活跃分析错误都是一个静默的内存错误。必须把"生成的程序在 `CAMEL_GC_POISON=1` 下跑一遍"放进测试——这个机制对生成的程序现成可用【实测 2.3：`raw-poll` 在毒化下立刻暴露，`shadow` 通过】 |

### 4.3 方案乙：生成的代码自带内存模型

生成的代码不依赖回收器。三种做法差别很大。

#### 乙一：引用计数

每个堆对象带一个计数。转译器在图上插入"加一"与"减一"：一个值有 k 个使用者就多出 k−1 份引用，最后一次使用之后减一，减到零就释放。拟议的输出：

```cpp
static RcString *f_tag(RcString *name /*借用*/, RcArray *xs /*借用*/) {
    RcString *head = f_first(xs);            // 得到一份所有权
    RcString *t = rc_add_s(name, k_colon()); // 算子借用实参，返回新对象
    RcString *r = rc_add_s(t, head);
    rc_drop(t); rc_drop(head);               // 各自的最后一次使用之后
    return r;
}
```

**Camel 比多数语言更适合这条路**，理由都来自 3.1：

- 值不可变、由下往上构造，所以**不成环**，不需要环检测。唯一的例外是经过变量单元的环（Q2）。
- **图本身就是引用计数需要的信息。** 一个节点的输出被哪几个节点使用、分支的哪条臂没有用到它，都是边，不用另做分析。这是 Lean 4 与 Koka 的做法（"Counting Immutable Beans"、Perceus）在 Camel 上的直接对应：它们从函数式的中间表示里推导同样的信息。
- 没有可观察的身份，所以**计数为 1 时可以原地复用**：`xs->append<x>` 这类"返回新值"的操作，在 `xs` 没有别的使用者时直接改它。这是引用计数独有的收益，跟踪式回收器给不了。今天的实现用"要求 `var` 实参"达到原地修改的效果（3.1 第 2 点）；有了计数，`let` 值上的同类操作也能做到。
- 外部资源在最后一个引用消失时立刻释放，不必等回收器（今天"没有及时性保证"，句柄规则第 9 条）。

**难处在问题三（算子）。** 算子的结果在 auto space 上；更要紧的是算子会把实参里的引用原样拷进新建的容器而不通知任何人（3.2）。`split` 返回一个新数组，里面是新字符串，没问题；`slice`、`concat`、`reverse` 返回的新数组里放的是**实参数组的元素**，这些元素多了一个引用者，计数却没变。三条出路：

1. **认领遍历。** 每个算子返回之后，生成的代码对结果做一次按类型的遍历：新对象（计数为 0）置 1 并继续往里走，旧对象（计数不为 0）加一。遍历器是现成的（每个对象类都实现了按类型访问子引用的 `updateRefs`）。不用改任何算子，代价是每个算子结果多一次与结果大小成正比的遍历。【未验证：只是设计，没有原型】
2. **算子表声明"结果是否引用实参的内容"**，只对声明了的做认领。要逐个算子审计。
3. **另写一套算子。** 计数版本的字符串、数组算子作为模板库，随生成的代码编译。工作量是内建算子约 95 个函数体加各模块的算子（句柄规则第 7 节的统计）。

对象头今天是 64 位：48 位大小、4 位年龄、1 位标记、1 位状态、4 位区域、6 位保留。【读码 `include/camel/core/mm/alloc/header.h:39-53`】放计数要么加一个字（每个对象多 8 字节），要么在"引用计数模式"下挪用回收器的那 16 位做一个饱和计数。【未验证】

**手写的标尺**（`examples/handwritten/rc.cpp`，不链接运行时，`malloc` 加一个非原子的计数）【实测，同 4.2 的负载】：`loop` 0.14 秒、9.4 MB；`calls` 0.18 秒、9.6 MB。比 4.2 最快的一格（影子栈加分代：0.25 与 0.33 秒，11 MB）快一倍左右。但这是整套东西的比较（`malloc` 对比带锁的运行时分配器、没有运行时的启动），不能读成"引用计数比精确根快一倍"。

| 方面 | 评估 |
|---|---|
| 性能 | 每次复制引用一次加、每次丢弃一次减并判零；计数为 1 时的原地复用能把一些 O(n) 的"返回新值"变成 O(1)。没有停顿。并行的 `map` 把值交给别的线程时计数要原子化，或者在交接处转移所有权 |
| 与现有 C++ 算子 | **不能原样用。** 见上面三条出路 |
| 与即时编译 | 没有交集。一个进程要么计数要么跟踪；生成的程序是独立的进程，这没问题，但"把生成的原生模块装进解释器进程里用"就做不了 |
| 独立部署 | 可以不要回收器；算子仍来自 `libcamel`，除非走第 3 条出路 |
| 对语言语义的要求 | 经过变量单元的环不回收，需要认可"不回收某些垃圾不算错"（Q2）；或者语言禁止这种环 |
| 主要风险 | 加减不配对是静默的内存错误或泄漏；与算子库的契约是全新的，仓库外的模块都要跟着改 |

#### 乙二：C++ 的值类型

字符串是 `std::string`，数组是 `std::vector<T>`，元组与结构体是 C++ 的 `struct`，`T?` 是 `std::optional<T>`，闭包是带捕获的函数对象，变量单元是 `std::shared_ptr<T>` 或者（不逃逸时）一个局部变量。

```cpp
static std::string f_tag(const std::string &name, const std::vector<std::string> &xs) {
    std::string head = f_first(xs);
    return name + ": " + head;
}
```

- 这是**最像人写的 C++**，C++ 编译器对它优化得最好，脱离运行时最彻底，嵌进别人的 C++ 工程最自然。
- 默认的拷贝是深拷贝。要不慢，就得在最后一次使用处移动、其余地方借用——需要的分析与引用计数相同；大的不可变数据想共享，就得用 `shared_ptr<const T>`，那又回到引用计数。
- **现有的算子库完全用不上**（布局不同），只能重写，或者在每次算子调用的边界上转换。张量、外部资源（3.1 第 3 点）必须共享，不能按值。
- 对标量、小的元组与结构体、`T?`、`T!`，这其实是最好的表示——不该上堆。这一部分单独拿出来就是 4.5 的丁一。

#### 乙三：区域

"一段计算里分配的东西放在一个区域里，算完整块丢掉，结果拷出来。"拷贝不可观察（3.1），所以这是合法的。

- 最粗的区域就是今天：整个程序一个区域，从不释放（2.2）。对短的批处理程序，这甚至是最快的（4.2 表的 `raw` 一行）。
- 细一些：每次 `map` 的元素调用、每轮 `LOOP` 一个区域，把结果或循环状态拷出来。这里有一个图原生的好性质：**`LOOP` 节点的状态边就是这一轮结束时全部的活值**（设计原则 2.1 的对应表："状态由循环头决定，不取决于循环体里写了什么"），不需要扫描任何栈就知道该拷什么。
- 代价是"拷出来"与结果的大小成正比。循环状态是一个越来越长的数组时，每轮都拷一遍，总量是平方级；要避免就得让结果直接分配在外层区域里，那是完整的区域推断，复杂度很高。
- 算子的结果仍然在 auto space 上，区域管不到它们，除非给算子传分配器。

单独作为方案不够；作为甲的补充（"这段循环里不必轮询，结束时一次清掉"）在分代回收器下没有必要，出生区已经是这样一个区域。

### 4.4 方案丙：保守扫描，或者不移动、不回收

**丙零：明确地不回收。** 就是今天，加一句承诺和一个出口：生成的程序不回收，堆上限到了就以明确的错误结束。对"算一次就退出"的程序够用，零工作量。需要 Q2 的认可。它不能支持长时间运行的服务，也解决不了 2.3（一旦支持高阶算子，就有安全点；除非生成的代码在自己的进程里把回收整个关掉）。

**丙一：保守地扫描原生栈。** 回收时把每个线程的栈和寄存器里"看起来像指向 auto space 里某个对象"的字都当作根；被这样指到的对象不移动。生成的代码什么都不用做，值可以留在寄存器里，这是三类方案里**生成代码最快**的一种。

障碍有两个，第二个是决定性的：

1. 要能从任意一个地址判断"这是不是某个对象的开头或内部"，三个空间（出生区、年老区的空闲链表、大对象）各要一张对象起点的索引。【未查：现有分配器能否枚举块】
2. **对象不带类型**（3.2）。保守地找到一个 `String` 没有问题，它没有子引用；找到一个 `Array`，回收器不知道它的元素是标量还是引用，无法往下追踪。今天回收器靠"槽的静态类型"知道这一点，而原生栈上的一个字没有静态类型。**不给每个对象加一个类型字，保守扫描只能保住对象本身，保不住它引用的东西。**

所以丙一的前提是"对象头里有类型"。`any` 的治理也碰到同一堵墙（[那份报告](../any-typing/README.cn.md) 2.5：`any` 槽里的引用之所以追踪不了，同样是因为对象不带类型），但它建议的出路是让剩下的动态值成为"自描述对象"（4.4），**不**给每个对象加类型字。按那个建议，丙一的前提不会顺带到来（Q6）。此外还有工程上的代价：每个平台各一套取栈边界与寄存器的代码；与地址消毒器冲突；被误认的整数会把垃圾留住；分代回收器要支持"钉住"被原生栈指到的年轻对象（出生区是连续的指针碰撞分配，钉住的对象会在里面留下洞）；难以写出确定性的测试。

| 方面 | 评估 |
|---|---|
| 性能 | 生成的代码零开销；回收时多扫栈 |
| 与现有 C++ 算子 | 原样可用 |
| 与即时编译 | 同样解开带帧的原生代码的问题，而且编译出的代码不用改 |
| 独立部署 | 不行 |
| 对语言语义的要求 | 没有 |
| 主要风险 | 依赖对象头的改动；平台相关；不可复现的保留与遗漏 |

### 4.5 方案丁：混合

**丁一：不逃出函数的聚合值不上堆。** 一个元组、结构体、`T?`、`T!` 或变量单元，如果在同一张图里被构造（`FILL`、`:var/new`）又只被拆开（`ACCS`、`??`、`:var/get`），就不需要成为对象：元组和结构体是 C++ 的 `struct` 或若干个局部变量，`T?` 是"值加一位标记"，没有被闭包捕获的 `var` 是一个 C++ 局部变量。函数返回元组时，生成的函数直接按值返回 `struct`。只有交给算子、放进数组、被闭包捕获的时候才装箱。

这一条与甲、乙、丙都不冲突，而且**不需要做任何内存模型的决定**：它减少的是堆对象的数量。1.4 的表里，第一个拒绝理由是 `T?`、`T!`、元组、变量单元、结构体的程序共 181 个，这是不碰堆就能拿回来的部分的上限（它们后面可能还有别的不支持的构造）。

**丁二：两种模式并存。** 10.5 允许各后端各选各的。`std::cpp` 链接运行时、走方案甲，所有算子和模块都能用；另设一个模式（比如 `std::cpp::standalone`）走方案乙，只接受不依赖动态模块的程序，产出不需要 `libcamel` 的 C++。两者共用转译器的前半段（活跃分析、结构化控制流、丁一），只在"堆值怎么表示、怎么调算子"上分叉。

**丁三：按图选择。** 不含安全点的图（纯标量、叶子）照今天的样子生成，不要帧；这部分图在 `std::opt::inline` 之后正是即时编译今天能编译的那一类。只有持有引用跨安全点的函数付出代价。这其实是甲的活跃分析的自然结果，列在这里是因为它回答了"会不会拖慢数值代码"：不会。

## 5. 建议与分阶段计划

### 5.1 建议

**主线：丁一 + 甲（影子栈形式的根帧）+ 丁三。乙作为以后单独的模式，丙不单独做。**

理由：

1. **算子生态决定了问题三的答案。** 内建算子、21 个模块、仓库外的第三方模块都按"对象在运行时的堆上、调用期间不回收、通过句柄"来写，句柄规则刚刚审计过约 480 处。甲是唯一让它们在两种回收器下都原样可用的方案。乙要么给每个算子结果加一次遍历，要么重写算子库，要么改动一份刚立下的契约。
2. **甲的机制可以一物两用。** 即时编译"带帧的代码在移动式回收下没有栈映射"的问题，用同一个根帧接口就能解。做一次，两个后端受益。
3. **代价量得出来而且不大。** 标量代码不受影响（丁三）；持有引用的代码在原型上是噪声内到 15%。相比之下，今天每个算子经桥调用的开销是 20–60 倍（1.9），那才是性能的大头，而它与内存模型无关。
4. **正确性有现成的检验手段。** 安全点毒化对生成的程序直接可用。
5. **丁一先行**，因为它不需要任何内存模型的决定，就能把 `T?`、`T!`、元组、结构体、不逃逸的 `var` 拿回来。

**不选乙作主线，原因在算子库，不在语言。** 单看语言，Camel 的值语义非常适合引用计数（4.3 的四条理由），原地复用和及时释放是甲给不了的。如果负责人对 Q1 的回答是"独立部署是首要目标"，结论应当反过来：先做乙，并接受重写一套算子。

**不单独做丙。** 它的前提（对象带类型）是一项影响每个对象的改动，不该为 `std::cpp` 一个消费者去做。如果 `any` 的治理要做它，再回头看。

### 5.2 分阶段

规模是净改动的估计。前两步不涉及内存模型，无论 Q1 怎么答都要做。

| 步 | 内容 | 规模 | 风险 | 做完之后 |
|---|---|---|---|---|
| 0 | **把今天的子集做对。** 分支落成结构化的 `if`/`else` 语句（修 D4、D5、D11，同时使内联后的图可以转译）；字符串局部变量的 `const` 位置（D1）；浮点常量按最短可回读的规则写（D2）；字符串的比较走算子（D3）；`exit` 与未声明返回类型的 `main`（D9、D10）；`camel-cpp` 在 Linux 上可用、文档与实际一致（D12）。**测试计划里每个 `std::cpp` 用例都编译并运行生成的程序，与 `std::fvm` 比较输出**；`cpp_build_run.py` 的对照进 CI | 约 500 行 + 测试 | 低 | 201 个程序里编得过且结果一致的从 126 个到接近全部（故障与递归的三项取决于 Q4、Q5） |
| 1 | **标量算子内联**（启用 `lower.cpp` 的表，最好改为读算子表的声明）；**自尾调用变成循环**，臂函数并入所在函数；非尾递归的计数与上限、故障位置表（按 Q4、Q5 的回答） | 约 400 行 | 低 | `fib` 这类程序比即时编译快（1.9 手改版本的数字）；一千万步的循环不再段错误 |

| 4 | **即时编译接入同一个根帧接口**，放开"含 `OPER`、调用其他图"的限制 | 属于即时编译的工作，本稿不估 | — | 分代回收下不再损失被编译的图 |
| 5 | **并行**：`map` 的元素交给工作线程，每个线程一个影子栈，进出区域的约定与任务流调度器相同 | 约 500 行 | 高 | 生成的程序用上多核 |
| 6（视 Q1） | **独立模式**（乙）：引用计数或值类型；一套随代码编译的算子库；不链接 `libcamel` | 2,000 行以上，外加算子库 | 高 | 可嵌入别的 C++ 工程的产物 |

依赖：0 → 1 → 2 → 3；3 需要图数据模型迁移计划的第 2、3 步（算子表与 `ExecPlan`）才能读到 `callsGraphs` 与臂区间，否则转译器要自己再维护一份"哪些算子是安全点"的名单。4、5 在 3 之后。6 与 3 之后的各步独立。

## 6. 要负责人确认的问题

### Q1 `std::cpp` 的首要目标是哪一个

三个目标对内存模型的要求不同：

```
camel model.cml std::cpp > model.cpp
```

- 甲：**同一运行时上的预编译后端。** `model.cpp` 链接 `libcamel`，能用全部算子和模块，追求比即时编译更快、覆盖更全。
- 乙：**脱离运行时的独立部署。** `model.cpp` 加一个小的支持库就能编进任何 C++ 工程或设备，不带回收器、不加载 `.cmo`。
- 丙：**给人读、给人改的 C++ 导出。** 输出要像手写的代码，用标准库类型。

**建议甲为首要目标，设计上不堵死乙**（转译器前半段共用，5.2 第 6 步）。理由见 5.1。丙与乙二是同一条路，可读性是它的副产品。

### Q2 一个后端可以不回收某些垃圾，算不算符合语义

```camel
func main(): int sync {
    var f = (x: int): int => x
    f = (x: int): int => if x == 0 then 0 else f(x - 1)    // 单元里的闭包捕获了这个单元：一个环
    return f(3)
}
```

10.5 说"回收的时机不可观察"。今天的生成代码完全不回收（2.2）；引用计数回收不了上面这种环。

- 甲：认可。后端回收多少是它自己的质量问题，不是语义问题；文档里写明各后端的行为。
- 乙：不认可完全不回收，但认可"经过变量单元的环可以不回收"。
- 丙：都不认可；语言禁止单元里的值（直接或间接）捕获这个单元，使值之间绝对无环。
- 丁：都不认可；所有后端必须回收一切垃圾（排除单纯的引用计数）。

**建议甲**，并把它作为 10.5 那一条的一句补充写进设计原则。不建议为了一个后端的方便去限制语言（丙）：3.5 明说闭包按引用捕获变量，上面的写法是它的直接后果。

### Q3 把"哪些东西有身份"写明

3.1 列出的三处例外，建议明确写进 10.5，否则"对象没有可观察的身份"会被后端读得过宽：

- 变量单元有身份（共享它的各方看到同一个值）；
- 经 `var` 形参交给算子原地修改的对象，就是调用方的那一个；
- 外部资源的包装对象有身份；
- 除此之外的值，后端可以任意拷贝、共享、搬移。

候选：如上写明；或者只保留第一条，把第二条消掉（让 `append` 等真的返回新值，如 11.3 所写，原地修改完全交给后端的优化）。**建议先如上写明**；第二条与 11.3 的出入请负责人裁定（附录 B 观察 O1）。

### Q4 生成的程序里，故障要不要带源码位置；递归上限要不要执行

```camel
func quot(a: int, b: int): int { return a / b }      // quot(7, 0)
```

今天：解释器给出 `error[RuntimeDiag::DivisionByZero]` 加文件、行、列；生成的程序印 `Error: DivisionByZero`。解释器在 1000 层非尾递归处报错；生成的程序没有上限，三百万层时段错误。

- 甲：都要一致。生成的程序里带一张"故障点 → 文件:行:列"的表，每个可能故障的调用点传入自己的编号；每次非尾调用加一、返回减一，超过上限报同样的诊断。
- 乙：位置要，递归上限不要（它是调度器的属性；生成的程序以原生栈为限，但溢出时要给出明确的错误而不是段错误）。
- 丙：都不要求；生成的程序是另一种产物。

**建议甲。** 3.9 的"故障默认带位置终止"没有区分后端；计数的开销是每次调用两条指令。

### Q5 尾调用在生成的程序里是否保证常数栈

3.9："尾递归要做优化，程序应尽量写成尾递归或循环"。今天生成的程序在一千万步的尾递归循环上段错误（D8）。

- 甲：保证。自尾调用生成循环；互相尾调用用 `[[clang::musttail]]`（只有 clang 支持）或者把互相调用的一组函数合成一个带状态的循环；`LOOP` 节点直接生成循环。
- 乙：只保证自尾调用与 `LOOP`；互相尾调用不保证。

**建议甲的前两项加 `LOOP`，互相尾调用先按乙处理并给出明确的诊断**，等 `LOOP` 落地后大多数循环不再以尾递归的形式出现。

### Q6 对象头里要不要有类型（与 `any` 的报告联动）

今天对象不带类型，回收器靠槽的静态类型追踪。给每个对象加一个类型字（每个对象多 8 字节）会同时改变三件事：`any` 位置上的值可以被追踪；写屏障不再需要调用方给出类型；保守扫描原生栈成为可能（4.4）。

- 甲：不加；`any` 用别的办法治理，`std::cpp` 走精确根。
- 乙：加；之后重估丙一（尤其对即时编译）。

[`any` 的报告](../any-typing/README.cn.md)建议的做法（4.4：剩下的动态值做成自描述的模块对象）属于甲。**本稿与它一致，建议甲**：精确根不需要对象带类型，为了保守扫描给每个对象加 8 字节不值得。列出这一条，是因为这两件事碰的是运行时的同一个性质，应当一起定。

### Q7 算子表与图摘要要不要为转译器多带几条声明

- (1) 图的效应摘要加一位"可能到达安全点"（4.7）。**建议加**：它由节点自下而上算出，不是人工声明，成本低，甲与即时编译都要用。
- (2) 算子声明"结果是否引用实参的内容"。**建议现在不加**：只有引用计数需要，等 Q1 决定要做乙再说。

### Q8 生成的函数对外的签名用什么类型

`std::cpp::module` 把函数写出来给别的 C++ 代码调用。今天签名里直接是 `String *`【读码 `runtime_emitter.cpp:722-756`】，调用它的用户代码于是拿着运行时堆上的裸指针——这等于把句柄规则交给了最终用户。

```cpp
String *generated::f_greet(String *name, Int64 n);                 // 今天
std::string generated::greet(std::string_view name, int64_t n);    // 候选
```

- 甲：对外的签名只用 C++ 标准类型，在边界上拷贝；函数内部才是运行时对象。
- 乙：对外用运行时类型，文档里要求使用者遵守句柄规则。

**建议甲。** 10.5："模块不得跨调用保存指向 Camel 对象的裸指针"，把这个要求转嫁给生成代码的使用者不现实。

## 7. 最不放心的地方

1. **影子栈的开销只在一个极小的手写原型上量过。** 一个根、只有字符串、没有嵌套容器、没有闭包，机器负载又高到同一格的最小值与最大值差两三倍。"噪声内到 15%"这个数不能直接外推到"每个函数有五六个引用、调用很深"的真实程序上。5.2 第 3 步动手之前，应当先在一台安静的机器上，对两三个真实的函数手写出带根帧的版本再量一次。

2. **闭包在生成的代码里怎么表示，没有想透。** 运行时的 `Function` 对象持有的是一张图的指针（`rtdata/func.h:44-49`），回收器通过那张图的布局追踪它的捕获。生成的程序里没有图。本稿设想的是"代码指针 + 捕获元组"的一种新对象，由生成的代码所链接的支持库注册给回收器；但函数值还会被打印、被放进 `any`、被传给以后可能出现的"接受函数值的 C++ 算子"。这些地方今天都假定它是 `Function`。这是第 3 步标"高"的另一半原因。

3. **引用计数的两个关键设想都没有验证**：用现成的 `updateRefs` 对算子结果做"认领遍历"是否对所有对象类都成立（张量视图、表、外部包装各有自己的实现）；在对象头里挪出 16 位做计数是否可行。如果 Q1 的回答指向乙，这两点要先做原型。

4. **1.4 的拒绝理由只是"第一个"。** 转译器遇到第一个不支持的构造就停，所以"数组 140 个、张量 135 个"说的是先撞上谁，不是补上谁能拿回多少程序。丁一能拿回的程序数（181 个的上限）尤其可能偏高：一个先因 `T?` 被拒绝的程序，后面多半还有数组。要得到真实的数字，需要让转译器在分析阶段把一个程序的全部问题都列出来，这要改转译器，本稿没有做。

5. **并行完全没有碰。** 生成的代码今天是单线程的；桥的实参区是进程共用的一份。任务流调度器里"工作线程只在区域内读写对象槽"的约定，生成的代码怎样遵守，本稿只有一行字（5.2 第 5 步）。

6. **只在 Linux x86-64、clang、libstdc++ 上构建和运行过。** Windows（`camel-cpp` 唯一支持的平台）上生成的代码能否编译、MSVC 是否接受，没有查。16 秒的编译时间是在负载下量的，但主要原因是头文件：生成的翻译单元包含了运行时的大半。

7. **`std::cpp::module`、`::inspect`、`::bench` 三个模式只看了输出的样子**，没有编译，也没有查它们与入口模式在覆盖率上的差别。

8. **即时编译一侧的现状是读文档得到的。** `lane/jit-coverage` 的工作在本工作树里不可见；"同一个根帧接口可以给即时编译用"是从句柄规则第 4 节与分代报告 6.1 推出来的方向，没有读过那条线的代码，也没有和它的作者核对过。
