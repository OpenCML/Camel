## 0. 摘要

**这份模型是什么。** Camel 的计算图今天有三种内存形态（前端建图用的、遍改写用的、后端执行用的），彼此靠拷贝转换，图与图之间靠指针相连，名字、类型、源码位置散在十来张旁路表里。本稿给出一份**与形态无关的定义**——程序、模块、图、节点、边、端口各是什么，每种节点的输入输出、类型规则、纯度、故障与求值约束——再规定它的三种落地形态（可编辑的草稿、冻结的只读图、磁盘上的缓存）是同一份数据的三种排布。建图层重构、模块 root 合并、模块缓存、用 Camel 写遍、GPU 内核与 `std::cpp` 这几件事都照这一份定义做。

**最重要的六个决定。**

1. **一切引用都是下标，图引用图只走一张表。** 节点引用是图内 16 位序号；一张图对别的图的全部引用（直接调用的被调图、循环的条件图与循环体图、函数常量指向的图）集中在这张图自己的"图引用表"里，表项是全程序的图编号。节点记录里没有任何能装下"另一张图的节点"的字段，"不出现跨图的节点引用"由数据结构保证，校验只需查表。图编号在改写前后不变：改写一张图只换掉编号表里的一项，不必像今天这样把整个可达闭包重新编码一遍（3.2、3.7）。
2. **节点种类收成 14 种，每种一张卡片。** 现有 15 种里 `BIND` 没有任何地方产生、`DREF` 只是建图期的占位，两者移出对外模型；新增 `LOOP`。`&&`/`||`、`??`、可空收窄、`attempt`、部分应用、模块顶层值、导入都不添加节点种类，各自落在已有种类上（3.5、3.6）。
3. **名字、类型、算子、源码位置都驻留成编号，放在图旁边的表里。** 类型做结构驻留（今天每张图平均为类型分配 1.4 KB 且从不释放，化简之后类型占的内存超过图本身）；算子名今天在每个 `OPER` 节点里存一份字符串，改为算子表的编号，纯度与"可能故障"是表项上的声明；每个节点的源码位置是与节点数组平行的一列（3.8）。
4. **实体的标识是"模块 + 限定名"，这也就是命名空间的内部形式。** 捕获的模块级值按实体绑定，不再按名字在调用处解析；模块对程序的贡献是"它的顶层节点段 + 它的函数图集 + 它的接口"，接口有指纹（3.9）。
5. **加载分三步：声明、建图、链接。** 先收集导入闭包里所有模块的声明，再按需建函数体与顶层值，最后在链接步一次性把"函数传递地用到哪些模块级值"算成不动点并接好端口。互相导入、顶层声明与书写顺序无关、值的环路诊断都由这个流程给出（3.9.4）。
6. **冻结的图是一段不含指针的连续内存，缓存文件就是它。** 节点 16 字节定长，边只存一份（今天每条边在边表里存两份，化简后最大的图用掉了 16 位边表容量的 40%），每图固定开销目标 64 字节（今天约 2.8 KB，而全部图里 37% 是分支臂，中位数 2 个节点）。`.cmc` 缓存 = 文件头 + 模块接口 + 这些图块 + 模块内编号表；加载是查表改写编号，与模块贡献的大小成线性，不解析、不做类型检查（第 4 节）。

**需要负责人确认的三件事**（完整清单见第 9 节）：

1. **Q1 节点种类清单**：移出 `BIND`、`DREF`，新增 `LOOP`，`attempt` 与 `map`/`reduce` 等保持为带"会调用子图"标志的算子节点；算子除纯度外再声明"是否可能故障"。
2. **Q4 接口指纹里放什么**：导出函数传递捕获的模块级值、效应摘要、推断出的返回类型、泛型函数体都算接口——这些变了，导入方的缓存失效。
3. **第 8 节命名空间的五个选择**：其中 `import x from m` 现在的实现（给模块起别名）与语言文档（导入一个名字）相反，需要定一个。

**调查中最值得知道的事实**（第 1 节）：编译一个 84 行的程序，前端在建图与编码两步上做了约 2.5 万次堆分配（每个图节点约 67 次），占启动之后全部分配的七成；每张图被完整地构造三遍；`src/compile/gir/validate.cpp` 的校验没有任何调用点；命名空间比"做了一半"要完整（限定名、嵌套、`using`、类型同名命名空间都能用），缺的是块内的非限定查找、块里的值、别名与作用域规则。发现的现有缺陷见附录 B。

## 1. 现状

### 1.1 一张图的三种形态与一次编译走过的路

| 形态 | 类型 | 用在哪 | 节点怎么存 | 出处 |
|---|---|---|---|---|
| 建图期 | `DraftGraphBuilder`（`shared_ptr` 持有），内含一个 `GraphDraft` | GCT → GIR | 同"草稿"，外加 7 张以节点指针为键的哈希表 | 【读码 `include/camel/compile/gir/draft_graph_builder.h:37-203 # "class DraftGraphBuilder {"`】 |
| 草稿 | `GraphDraft` | 各改写遍 | 每节点一个 56 字节的头（`DraftNode`）加一块 64/96/128 字节的尾（负载与六个邻接表），来自 4 KB 的页 | 【读码 `include/camel/runtime/draft.h:46-174 # "class GraphDraft *owner = nullptr;"`】 |
| 运行期 | `GCGraph` | 四个后端、宏求值器、导出器、调试器 | 一段变长的节点块：40 字节的头（`GCNode`）加各种类的负载，邻接是指向公共边表的六个切片 | 【读码 `include/camel/runtime/graph.h:118-281`】 |

**建图期与运行期不是同一个结构，而且中间还有第三份。** 前端把一张图建在 `DraftGraphBuilder` 的草稿里；编码时为每张图新建第二个草稿，只拷入出口可达的节点并重新编号（`prepareGraph`）；再由第二个草稿编码成 `GCGraph`。【读码 `src/compile/gir/graph_encode.cpp:379-596 # "PreparedGraph prepareGraph(const graph_ptr_t &graph) {"`】也就是说每个节点在一次编译里被构造三次。之后每个改写遍再把 `GCGraph` 解码成草稿、改完重新编码。

**图与图之间是指针。** `GCGraph` 里 `FUNC` 节点的负载是被调图的指针（`GCFuncBody::calleeGraph`，`graph.h:172-174`），函数常量是静态区里指向 `Function` 对象、再指向图的指针，另有 `dependencies_`、`subGraphs_`、`staticGraphRefs_` 三个图指针数组（`graph.h:443-449`）。后果是：**一张图被改写后地址变了，所有指向它的图都得重新编码**。`RuntimeGraphDraftSession::commit()` 因此对整个可达闭包里的每一张图重新分配、编码、校验，不管改了几张。【读码 `src/runtime/draft_session.cpp:727-782`；`docs/technical/17_graph_rewrite_api_contracts.md` 1.1】通用的改写驱动 `rewriteReachableGraphs` 则先把每一张可达的图都解码成草稿再问"你要改吗"。【读码 `src/passes/opt/generic/rewrite.cpp:200-216`】

内存来自三块按段增长的空间，各有 256 MB 的总上限：图空间（`GCGraph`，可释放）、永久空间（类型与布局，**从不释放**）、元空间（建图期的常量与函数值）。【读码 `include/camel/core/mm.h:25-35`；`docs/cli.md` "Resource limits"】一张 `GCGraph` 是图空间里的一次分配（`src/runtime/graph.cpp:982-993 # "GCGraphDebugRecord *createGraphDebugRecord(std::string mangledName,"`）。

### 1.2 节点种类的完整清单

`GCNodeKind` 有 15 个值【读码 `graph.h:60-76`；编译期的 `NodeType` 与它一一对应，`include/camel/compile/gir/types.h:28-44`】。下表的"占比"是 1.10 的普查结果（769 个程序，未加任何遍）。

| 种类 | 是什么 | Norm 入边 | With 入边 | 负载 | 占比 |
|---|---|---|---|---|---|
| `DATA` | 常量 | — | — | 无；`dataIndex` 为负，指向图的静态区 | 29.9% |
| `OPER` | 算子调用 | 普通实参 | `with` 实参 | 算子函数指针 + **URI 字符串**（内嵌在节点里） | 29.8% |
| `PORT` | 形参、`with` 形参、闭包捕获 | — | — | 无；属于哪一类由图的三张端口表决定 | 13.8% |
| `FUNC` | 直接调用另一张图 | 普通实参 | `with` 实参（含传下去的捕获值） | 被调图指针 | 11.0% |
| `CALL` | 经函数值调用 | 普通实参 | 第 0 条是被调的函数值，其余是 `with` 实参 | 只有保留字段 | 2.6% |
| `BRCH` | 分支头 | 第 0 条是选择子 | `match` 各 case 的比较值 | 配对的 `JOIN`、臂表（每臂一对头/尾节点） | 2.5% |
| `JOIN` | 分支汇合 | 第 0 条是配对的 `BRCH` | 各臂的臂尾，按臂序 | 配对的 `BRCH`、臂数 | 2.5% |
| `ACCS` | 取元组下标或结构体字段 | 被取的值 | — | 下标，或字段名字符串（内嵌） | 2.5% |
| `GATE` | "值 + 顺序"的会合：把 Norm 输入原样送出，但排在 Ctrl 输入之后 | 值 | — | 无 | 2.3% |
| `FILL` | 往一个常量模板里填入算出来的元素，得到元组/数组/结构体/闭包 | 第 0 条是模板（`DATA`） | 要填入的各个值 | 种类（Tuple/Array/Struct/FunctionClosure）与每个值填到哪个位置 | 1.9% |
| `CAST` | 类型转换（值装入 `T?`/`T!`、`as`） | 被转换的值 | — | 无；目标类型就是节点的类型 | 0.8% |
| `COPY` | 浅拷贝一个对象 | 被拷贝的值 | — | 无 | 0.3% |
| `SYNC` | 纯顺序的汇合点：只有 Ctrl 入边 | — | — | 无 | 0（只有内联遍产生） |
| `BIND` | 注释写的是"部分应用" | — | — | — | **0：没有任何代码创建它** |
| `DREF` | 建图期"还没定下来指谁"的名字占位 | — | — | — | 0：编码时遇到即报错 |

- `BIND`：全仓库只有两处定义它的构造函数（`draft_graph_builder.cpp:203`、`draft_construct.cpp:255`），没有调用者；部分应用实际做成了闭包（见 3.5 的卡片）。后端里为它留着的分支都是死代码。【读码，检索 `addBindNode`】
- `SYNC`：前端不产生，`inlineCallableInDraft` 在被内联体有多个入口时新建一个（`src/runtime/draft_inline.cpp:1988-1992`）。
- 每个节点头上还有：类型指针 `dataType`、槽位 `dataIndex`（正数是帧槽，负数是静态区下标，0 是没有值）、两个标志位（`macro`、`constant`）。【读码 `graph.h:101-132`】

### 1.3 边

三种：`Norm`、`With`、`Ctrl`。【读码 `draft.h:40-44`】

- `Norm` 与 `With` 都是数据边，区别是"接在目标节点的哪一组输入上"；这两组输入在每种节点上的含义见上表。它们与语言里"普通参数 / `with` 参数"的区分对应（设计原则 4.4），但 `CALL`、`FILL`、`BRCH`、`JOIN` 借用了 `With` 这一组做别的事。
- `Ctrl` 是控制边：目标排在源之后，不传值。来源有四处【读码 `src/compile/gir/builder.cpp`】：同步块里相邻表达式之间的链（`lastSyncedNode_`，`:6016-6029`、`:6305-6311`）；`wait` 与变量写入的排序（`recordWrite`/`orderAfterLastWriter`）；`BRCH` 指向各臂的入口（`:5796`）；臂捕获的外部值指向 `BRCH`（"先于分支就绪"，`:5750-5756`）。
- **不变量**（提交时检查，1.7）：每条输入边在对端的输出表里出现，反之亦然；三种边合起来无环。
- **节点是否执行由可达性决定**：所有后端共用一个取执行序的函数，从出口沿三种入边反向标出需要的节点【读码 `src/execute/graph_runtime_support.cpp:115-150`】。"同步块之外没人用的效应不执行"（设计原则 3.1）在图上就是"出口到不了它"；同步块的效应会执行，是因为控制链最终接到出口的 `GATE` 上。
- **每条边存两份**：`GCGraph` 的边表里，每个节点的输入与输出各占一段，16 位寻址的"边表项"上限数的是两份之和。【读码 `src/runtime/graph.cpp:574`："one for each input and one for each user of every node, that is two per edge"】而四个后端里只有任务流调度器有两处读输出表（1.8）。

### 1.4 图怎样持有子图与依赖图

`GCGraph` 有三张图指针表与一个外层图指针【读码 `graph.h:312-314、459-465`】：

- `dependencies`：`FUNC` 节点调用的图、分支臂的图；建图器在每次建 `FUNC` 节点或函数值时登记（`builder.cpp:3574`、`:5741`）。
- `subGraphs`：写在这张图"里面"的函数与臂，按词法归属。
- `staticGraphRefs`：静态区里函数常量指向的图。
- `outerGraph`：词法上的外层图。

三张表都能从节点重新推出来，实际上提交时也确实按节点的引用重建前者（`collectDraftDependencyGraphs`，文档 17 的 2.3）。它们的用途只有一个：从 root 出发求可达闭包（编码、每次提交、垃圾回收的图根）。`std::rgir` 输出里图的嵌套反映的是"第一次被谁引用"，不是词法结构：1.1 之后所有例子里用户函数都印在 `main` 的簇里面。【实测】

### 1.5 名字、类型、源码位置各存在哪里

| 信息 | 建图期 | 运行期 |
|---|---|---|
| 图的名字 | `DraftGraphBuilder::name_`、`stableId_` | `GCGraphDebugRecord` 里三个 `std::string`：`stableId`、`mangledName`、`name`（`src/runtime/graph_build.h:23-29 # "std::string mangledName;"`） |
| 节点的调试标识 | `nodeDebugIds_`：**每个节点一个 `std::string`**（`draft_graph_builder.h:205`） | 无 |
| 端口名 | `nodePortNames_`（哈希表，节点指针 → 字符串） | 形参名在函数类型里；捕获端口没有名字 |
| 字段名（`ACCS`） | `nodeAccsKeys_` | 内嵌在节点负载里；NodeVM 每次访问先构造一个 `std::string` 再查（`nodevm.cpp:592-596`） |
| 算子 | `operTargets_`（节点指针 → `shared_ptr<OperatorIndex>`） | 内嵌在节点里的 URI 字符串 + 函数指针 |
| 被调图 | `funcTargets_`（节点指针 → `shared_ptr` 图） | 节点里的图指针 |
| 类型 | `Type*`，分配在永久空间 | 同一个指针 |
| 源码位置 | 节点头上的 `origin`（64 位）；语义部件另存在 `SourceContext` 里以字符串为键的表 | 每图一张 `unordered_map<节点引用, origin>`（`graph_build.h:28`） |
| 捕获了哪些名字 | **函数类型对象上**的 `closureRefs`（字符串列表，建图时就地追加，`builder.cpp:1009-1012`） | 同左 |

类型没有驻留：`TupleType::create` 每次调用都在永久空间里新分配一个（`src/core/type/composite/tuple.cpp:104-131`）；变量单元类型 `TupleType::cell` 用一把互斥锁加线性查找去重（`:135-147`）。每张图有自己的帧布局元组类型，改写后重新编码又生成新的，旧的留在永久空间里。函数类型对象是可变的：返回类型在建图时才填（`setExitType`，`builder.cpp:65-73`），捕获名也往里加。

函数类型的形参名不参与类型相容：`func sub(a: int, b: int)` 可以传给 `(x: int, y: int) => int` 的位置【实测，打印 7】；按名字传参尚未支持（`FeatureNotSupported: kwargs`）【实测】。

### 1.6 顺序、效应、捕获、泛型在图上的表示

- **`sync` 块**：没有专门的节点。块内相邻表达式之间一条 `Ctrl` 边；块的值经一个 `GATE`（Norm 接值，Ctrl 接链尾）交出去。【实测，见 3.5】
- **`wait` 与 `var`**：变量是一个单元（`:var/new` 建，`:var/get` 读，赋值算子写）；排序靠 `Ctrl` 边，依据是"谁用过这个变量"。【实测】
- **纯度**：不在图上。算子的纯度在一张全局的、以 URI 字符串为键、带读写锁的注册表里（`OperatorTraitsRegistry`，`include/camel/core/operator_traits.h:44-97`），三个位：`pure`、`elementwise`、`stateOnly`；遍每问一次做一次字符串哈希查找。函数的效应：`sync` 修饰符在函数类型上；"这张图的出口是否依赖效应""它写了哪些捕获的变量"是建图器内部的表（`effectfulGraphs_`、`captures_`，`src/compile/gir/builder.h:164-209 # "std::vector<compile_graph_ptr_t> builtBodies;"`），建完就丢，遍看不到。
- **故障**：没有任何声明。哪些节点可能故障只能由读者自己按算子名判断。
- **捕获**：闭包捕获的值是图上的一类端口（`closureNodes`）；函数第一次被直接调用时，捕获端口就地改成 `with` 端口，此后每个调用处按**名字**在调用处的作用域里再解析一次并连 `WITH` 边。【读码 `builder.cpp:972-1025`、`:3591-3625`；模块 root 设计稿 1.2】这段逻辑依赖"这张图用过没有"（`usedGraphs_`），函数被调用之后再发现新的捕获就是 `ClosureCaptureAfterSelfCall`。
- **泛型**：模板是建图器里的一个对象（GCT 子树 + 声明处的四个作用域），不是图；每组类型建一张名为 `first<int>` 的普通图。【读码 `builder.h:221-280`；实测】
- **分支臂是独立的图**：前端为每条臂建一张子图，外层图里是一个 `FUNC` 节点，既是臂头也是臂尾；臂用到的外层值是它的 `with` 端口。【读码 `builder.cpp:5697-5798`；实测】内联之后臂的节点并进外层图，成为 `BRCH` 与 `JOIN` 之间的一段。

### 1.7 "提交"是什么，校验哪些不变量

提交有三处：前端编码（`encodeToRuntimeGraph`）、改写会话的 `commit()`、`GraphDraftGroup::encode()`。三处在每张图编码之后调用同一组校验，**所有构建模式都执行**，失败抛异常并被遍驱动转成 `PassInternalError`【读码 `src/runtime/graph.cpp:232、1175-1181`，`src/runtime/branch_arms.cpp:99`；`docs/technical/17_graph_rewrite_api_contracts.md` 第 4 节】：

1. 锚点、端口、闭包节点、所有边的节点引用有效；槽位在范围内；没有残留的 `DREF`；
2. 邻接表双向一致；
3. `BRCH` 有唯一的选择输入，`BRCH`/`JOIN` 的臂数与负载一致；
4. `GATE` 同时有值输入与控制输入；
5. `FUNC` 有被调图，`CALL` 有被调输入；
6. 分支臂不变量（`BRCH` 与 `JOIN` 之间的每个活节点恰好属于一条臂）；
7. 一次提交的图全部编码后：每个 `FUNC` 的实参数等于被调图的端口数。

没有检查的：类型（边两端的类型是否相容）、无环（靠取执行序时自然暴露）、图引用是否指向仍然存在的图。

`src/compile/gir/validate.cpp`（412 行）里的 `assertGraphSealingPreconditions` 等三个函数是用 `ASSERT` 写的旧校验，除了彼此之外**没有调用点**。【读码，检索 `src/`、`include/`、`modules/`、`tools/`】

## 2. 设计目标与判据

后文每个决定回指这里的编号。

**来自设计原则。**

- **R1 语法元素与图有稳定的映射。** 每种语言构造在图上的形状不取决于它里面写了什么（1 的判据）；每种节点的含义不取决于谁在读它。
- **R2 没有跨图的节点引用。** 图与图之间只有"图引用图"；这一条要能机械地校验（2.2）。
- **R3 不用语法糖模拟控制流。** 新构造落在已有节点上，或加一种节点，不引入"形状满足某个约定"的隐式契约（1）。
- **R4 单图容量 65,535 不放宽**，节点与边都是 16 位寻址（2.4）。模型不得让容量被表示方式白白吃掉。
- **R5 按依赖求值、`sync`/`wait` 是控制边**：模型只有"数据边 + 控制边 + 可达性"这一套执行规则（3.1–3.5）。
- **R6 源码层的限制只在"源码到图"这一步生效**（9.5）：模型定义的是图合法与否，不替遍规定优化策略；但遍需要的事实（纯度、效应、故障）必须能从图上读到，不靠建图器的私有表。

**来自六个消费者。**

- **R7 可序列化、可重定位。** 图的任何部分不含进程地址；把一个模块的图搬进另一个进程、拼进公共 root，只需要改写编号（模块缓存）。
- **R8 小图要便宜。** 分支臂、lambda、泛型实例是独立的图而且极小；每图的固定开销以几十字节计，建一张图的分配次数是常数（建图层重构）。
- **R9 改写是局部的。** 改一张图的代价与这张图的大小成正比，不与程序大小成正比；改写的结果要么整体通过校验，要么不生效（各遍、用 Camel 写遍）。
- **R10 读图不需要知道实现。** 每种节点的输入、输出、类型、纯度、故障、求值约束有一份规范定义；认算子、认被调图、认字段不靠比较字符串（GPU 内核、`std::cpp`、导出器、用 Camel 写遍）。
- **R11 实体有全程序唯一、与装载顺序无关的标识**："模块 + 限定名"（模块 root、命名空间、缓存、诊断与调试器里显示的名字）。
- **R12 诊断与调试信息不丢、但不拖累热路径。** 每个节点能回到源码位置；这些信息与执行用的数据分开存放，用到才读（调试器、语言服务器、缓存）。
- **R13 可以演进。** 加一种节点、加一个字段不使旧的缓存被误读，也不要求所有消费者同时改（`LOOP` 及以后的节点）。

## 3. 数据模型本体

### 3.1 总览

```
Program（一次编译得到的整个程序；一个不可变的快照）
 ├─ 模块表     Module[]        每个模块：名字、导入、声明的实体、对 root 的贡献、接口
 ├─ 实体表     Entity[]        "模块 + 限定名" → 值 / 函数 / 泛型模板 / 类型 / 算子 / 命名空间
 ├─ 图表       Graph[]         图编号 → 冻结的图；第 0 号是 __root__
 ├─ 类型表     Type[]          结构驻留；类型编号相等 ⇔ 类型相同
 ├─ 符号表     Symbol[]        驻留的字符串（名字、字段名、算子 URI）
 ├─ 算子表     Operator[]      URI、类型规则、声明的性质（纯度、可能故障……）
 └─ 位置表     Origin[]        源码位置与派生链

Graph（一张图）
 ├─ 签名与角色
 ├─ 端口表     普通形参 | with 形参 | 捕获            ← 值进入这张图的唯一途径
 ├─ 节点数组   Node[]          定长记录，图内序号寻址
 ├─ 输入表     NodeId[]        每条边一个表项，按目标节点分段，段内依次是 Norm、With、Ctrl
 ├─ 负载区     每种节点自己的附加数据（被调图在引用表里的下标、算子编号、填充位置、臂表……）
 ├─ 常量池     这张图的 DATA 节点的值
 ├─ 图引用表   GraphId[]       这张图引用的全部其他图                ← 图引用图的唯一途径
 ├─ 出口       exit（完成点）、result（返回值所在的节点）
 └─ 位置列     每个节点一个 OriginId（冷数据，可以不装载）
```

两条贯穿全稿的规则：

- **图里只有图内的东西。** 节点的输入是本图节点的序号；别的图只出现在图引用表里；别的模块的值只以"捕获端口 + 它绑定的实体"出现。
- **表里的东西按编号引用，编号不是地址。** 同一份图数据放在草稿里、冻结块里、缓存文件里，差别只是编号指向哪张表的哪一版（R7）。

### 3.2 标识

| 标识 | 宽度 | 范围 | 含义 | 稳定性 |
|---|---|---|---|---|
| `NodeId` | 16 位 | 一张图内 | 节点在节点数组里的序号；`0xFFFF` 表示"无" | 冻结的图内不变；改写后重新编号，旧图的编号经"来源"列可追溯（3.8） |
| `SlotId` | 16 位有符号 | 一张图内 | 正数是帧槽，负数是常量池下标的相反数，0 是没有值 | 同上 |
| `GraphId` | 32 位 | 全程序 | 图表的下标 | **改写不改变它**：一张图被改写后仍是同一个编号，只是表项换成新的冻结块；新建的图（特化、泛型实例、梯度图）得到新编号 |
| `TypeId` | 32 位 | 全程序 | 类型表的下标 | 进程内不变；缓存里是模块内编号 |
| `SymId` | 32 位 | 全程序 | 符号表的下标 | 同上 |
| `OperId` | 32 位 | 全程序 | 算子表的下标 | 同上 |
| `EntityId` | 32 位 | 全程序 | 实体表的下标；对外的名字是"模块 + 限定名"（3.9.1） | 同上 |
| `OriginId` | 32 位 | 全程序 | 位置表的下标 | 同上 |
| `ModuleId` | 16 位 | 全程序 | 模块表的下标 | 同上 |

容量：一张图至多 65,535 个节点、65,535 条边（输入表的表项）、32,767 个帧槽与 32,767 个常量。与今天相比，节点上限不变，**边的上限实际翻倍**（每条边只占一个表项，R4）。

### 3.3 图

| 字段 | 内容 |
|---|---|
| `id` | `GraphId` |
| `role` | `Root`、`Function`（具名函数、泛型实例）、`Lambda`、`Arm`（分支臂）、`LoopCond`、`LoopBody`、`Forwarder`（部分应用与函数值的转发图，3.6）、`Synthetic`（遍造出来的：特化、提升、梯度） |
| `name` | 显示用的名字（`SymId`），用源码里的写法：`first<int>`、`shapes::Tools::area` |
| `entity` | 这张图实现的实体（函数）；臂、lambda、遍造的图没有 |
| `owner` | 所属模块 |
| `lineage` | 它由哪张图派生（特化、克隆、内联前的原图）；没有则为空。取代今天按字符串前缀（`loop$tspec3`）判断来历的做法 |
| `signature` | 函数类型（`TypeId`）：`with` 形参类型、普通形参类型、返回类型、修饰符（`sync`、`macro`）。**不含形参名与捕获**，它们在端口表里 |
| `ports` | 三段：普通形参、`with` 形参、捕获。每个端口：对应的 `PORT` 节点、名字、是否是变量单元（`var`）、捕获端口另有绑定（3.7） |
| `effects` | 这张图的效应摘要，四个位：出口依赖外部效应、写了捕获的变量、读了捕获的变量、可能故障。由节点与被调图的摘要算出（3.10 的 I14），不是声明 |
| `exit` / `result` | `exit`：图的完成点，可达性从它算起；`result`：返回值所在的节点（没有返回值时为空）。两者不同当且仅当 `exit` 是一个 `GATE` |
| 节点、输入表、负载区、常量池、图引用表、槽位类型表、位置列 | 见 3.4、3.7、3.8、第 4 节 |

今天的 `outerGraph`（词法上的外层图）不进模型：它只在建图器解析名字时有用，建完之后图与图之间没有"里外"关系，只有引用。转储时把一张图印在谁里面，按 `owner` 与名字分组即可。

### 3.4 节点、边、端口

**节点**是一条定长记录：

| 字段 | 含义 |
|---|---|
| `kind` | 种类，见 3.5 |
| `flags` | `constant`（值在编译期已知）、`macro`（调用的是 `macro` 函数）、`var`（值是一个变量单元） |
| `type` | 输出值的类型（`TypeId`）；没有值的节点是 `void` |
| `slot` | 输出放在哪（`SlotId`） |
| 输入 | 输入表里的一段，分成 `Norm`、`With`、`Ctrl` 三小段，各自有序 |
| 负载 | 由种类决定 |

每个节点**至多一个输出值**。多个结果用元组加 `ACCS`。

**边**是"目标节点的某一组输入里的第几个 → 源节点"。三组的含义：

- `Norm`、`With`：数据边。目标读源的值。两组各自按位置对应目标的两类参数；每种节点怎么用这两组见卡片。
- `Ctrl`：控制边。只表示"目标排在源之后"，不读值。

**规则 E1（求值）。** 一次激活（一次调用这张图）中：

1. 只有**活**节点可能执行：从 `exit` 沿三组输入可达的节点。
2. 一个节点在它的全部输入（三组）执行完之后执行，至多一次。
3. 位于某个 `BRCH` 与它的 `JOIN` 之间的节点，只在它所属的臂被选中时执行（3.5 的 `BRCH` 卡片）。
4. 除此之外没有顺序：互不可达的两个活节点可以按任意顺序或并行执行。

`sync` 块、`wait`、"没人用的效应不执行"都是这四条的结果，没有另外的规则（R5）。

**端口**是值进入一张图的途径。三类，都是 `PORT` 节点，区别在图的端口表里它属于哪一段：

| 类别 | 语言里是什么 | 值由谁给 |
|---|---|---|
| 普通形参 | `func f(x: T)` 的 `x` | 调用处的 `Norm` 实参 |
| `with` 形参 | `with <w: T> func f(...)` 的 `w` | 调用处的 `With` 实参 |
| 捕获 | 函数体里用到的、定义在别处的值 | 直接调用：调用处的 `With` 实参（排在声明的 `with` 实参之后）；作为函数值：建闭包时的 `FILL` |

### 3.5 节点卡片

十四种。数值编码沿用现有枚举（`DATA`=0 … `GATE`=13），`BIND`（9）与 `DREF`（14）两个值保留不用，`LOOP` 取 15。

每张卡片的"纯度与故障"一栏用四个词：**纯**（结果只取决于输入，可提前算、可合并、没人用可删）、**只涉及状态**（读写程序自己的变量）、**有效应**、**可能故障**（除零、越界一类，带位置终止或在 `attempt` 边界上变成错误值）。

#### `DATA` 常量

| | |
|---|---|
| 语法元素 | 字面量；`null`；函数名作为值（没有捕获时）；被 `std::macro` 或折叠遍算出来的值 |
| 输入 | 无（可以有 `Ctrl` 输入，表示"这个值在某事之后才交出"——只在改写后出现，等价于套一个 `GATE`） |
| 输出 | 常量池里的一个值；`slot` 为负 |
| 类型 | 字面量的类型；函数常量是函数类型 |
| 纯度与故障 | 纯；不故障 |
| 不变量 | 常量池下标有效；值是函数常量时，它指的图在图引用表里 |

函数常量在转储里是 `Function(graph=main, tupleSlots=0)`：一张图加上捕获槽的个数。

#### `PORT` 端口

| | |
|---|---|
| 语法元素 | 形参、`with` 形参、被捕获的名字 |
| 输入 | 无 |
| 输出 | 调用方给的值；`var` 形参与被捕获的变量给的是单元 |
| 纯度与故障 | 纯；不故障 |
| 不变量 | 恰好出现在图的端口表的一段里；捕获端口有绑定（3.7） |

#### `OPER` 算子调用

| | |
|---|---|
| 语法元素 | 运算符（`a + b`、`a == b`、`a & b`）、对 C++ 算子的调用（`println(x)`、`xs->take<3>`）、编译器插入的内建算子（`:var/new`、`:var/get`、`:op/tag_is_null` 等） |
| 输入 | `Norm`：普通实参；`With`：`with` 实参；`Ctrl`：顺序 |
| 负载 | `OperId` |
| 输出与类型 | 一个值。类型由该算子的类型规则从实参类型算出，建图时确定并写在节点上；遍改变了实参类型后经算子表重新求（今天的 `OperatorResolverRegistry`） |
| 纯度与故障 | 取自算子表的声明：`pure` / `stateOnly` / 有效应；`mayFault`。没有声明的按"有效应、可能故障"对待（设计原则 3.3） |
| 求值约束 | E1。带 `callsGraphs` 标志的算子（`:mark/map_arr`、`:mark/reduce_arr`、`:mark/foreach_arr`、`:mark/isolate` 等）在执行中调用实参里的函数值，调用次数与顺序由算子自己规定（`map`、`filter` 元素间无序，`reduce`、`foreach` 有序，设计原则 3.6） |
| 不变量 | 入边数与算子签名一致 |

#### `FUNC` 直接调用

| | |
|---|---|
| 语法元素 | 对一个编译期就知道是哪张图的函数的调用：`f(x)`、`f<w>(x)`、`x->f<w>`；分支臂的入口；泛型函数的调用（指向实例） |
| 输入 | `Norm`：普通实参，个数与顺序等于被调图的普通形参；`With`：先是声明的 `with` 实参，再是被调图各捕获端口的值，按被调图端口表的顺序 |
| 负载 | 被调图在本图的图引用表里的下标 |
| 输出与类型 | 被调图的返回值；类型是被调图签名的返回类型（臂的调用节点在汇合类型更宽时取汇合类型） |
| 纯度与故障 | 取被调图的效应摘要 |
| 求值约束 | E1；被调图是一次新的激活，它里面执行什么由它自己的图决定（设计原则 3.2） |
| 不变量 | `Norm`、`With` 入边数等于被调图对应端口数（今天的校验第 7 条） |

这是"图引用图"。图上没有"把被调图的节点放进来"这回事，只有一个节点和引用表里的一项。

#### `CALL` 经函数值调用

| | |
|---|---|
| 语法元素 | 调用一个运行时才知道是谁的函数值：形参 `f` 的 `f(x)`、闭包 `add5(1)`；`__root__` 对 `main` 的调用 |
| 输入 | `With` 第 0 条：被调的函数值；`With` 其余：`with` 实参；`Norm`：普通实参 |
| 输出与类型 | 函数值类型的返回类型 |
| 纯度与故障 | 按函数值的**类型**：带 `sync` 修饰符的有效应，否则只可能故障。写捕获变量的函数必须声明 `sync`（设计原则 3.5 的闭环），所以类型足以判断 |
| 不变量 | `With` 至少一条；第 0 条的类型是函数类型，实参个数与之相符 |

| | |
|---|---|
| 语法元素 | 含有算出来的元素的元组、数组、结构体字面量（`(a, b)`、`[a, b, 3]`、`{ x: a, y: b }`）；带捕获的函数值（闭包） |

#### `ACCS` 取成员

| | |
|---|---|
| 语法元素 | `t.0`、`p.y`；解构绑定 `let (a, b) = t` 的每一项 |
| 输入 | `Norm` 一条：被取的元组或结构体 |
| 负载 | 元组下标，或字段名（`SymId`） |
| 输出与类型 | 该成员；类型是成员的类型 |
| 纯度与故障 | 纯；不故障（下标与字段在建图时已对照类型检查过） |

数组下标 `xs[2]` 不是 `ACCS`，是算子 `:op/idx_arr`（可能故障：越界）。

#### `CAST` 转换

| | |
|---|---|
| 语法元素 | 值进入 `T?`/`T!` 的位置（每一层一个 `CAST`，设计原则 3.8）；`null` 进入 `T?`；`v as T`；`?->` 把错误原样传下去时换载荷类型 |
| 输入 | `Norm` 一条 |
| 输出与类型 | 节点的类型就是目标类型 |
| 纯度与故障 | 纯（装入时分配一个盒子）；带检查的 `as`（如 `t as Tensor<const [3]>`）可能故障，其余不故障 |

数值之间的转换（`float(x)`、`int('12')`）是算子，不是 `CAST`。【实测】：`return if c then 7 else null`（函数声明返回 `int?`）的两条臂分别是 `DATA 7 → CAST` 与 `DATA null → CAST`。

#### `COPY` 拷贝

| | |
|---|---|
| 语法元素 | 函数体里用字面量初始化一个 `var`（`var i = 1`）：常量先拷一份再装进变量单元，免得变量与常量池共用一个对象 |
| 输入 | `Norm` 一条 |
| 输出与类型 | 同类型的一份浅拷贝；非对象的值原样送出 |
| 纯度与故障 | 纯；不故障 |

#### `BRCH` 与 `JOIN` 分支

| | `BRCH` | `JOIN` |
|---|---|---|
| 语法元素 | `if`、`match`、`a ?? b`、`a !! b`、`x ?-> f`、`a && b`、`a \|\| b`、可空收窄（3.6） | 同左，与 `BRCH` 成对 |
| 输入 | `Norm` 第 0 条：选择子（`if` 与标记分支是 `bool`，`match` 是被匹配的值）；`With`：`match` 各 `case` 的比较值，按书写顺序；`Ctrl`：顺序，以及各臂捕获的外部值（保证它们先于分支就绪） | `Norm` 第 0 条：配对的 `BRCH`；`With`：各臂的臂尾，按臂序 |
| 负载 | 配对的 `JOIN`；臂表：每臂一对（臂头，臂尾） | 配对的 `BRCH`；臂数 |
| 输出与类型 | 被选中的臂的序号（内部用） | 被选中的那条臂的值；类型是各臂类型的汇合（一条臂可以装入另一条的形式，如 `int` 与 `null` 汇合成 `int?`）。没有 `else` 的 `if` 类型是 `void`，不取值 |
| 纯度与故障 | 自身纯、不故障；整个分支的效应是各臂之并 | 同左 |
| 求值约束 | 选出一条臂；只有这条臂的节点执行。`if`：真选第 0 臂，假选第 1 臂。`match`：与第 i 个比较值相等选第 i 臂，都不等选最后一臂 | 在被选中的臂的臂尾之后 |
| 不变量 | 臂数：`if` 为 2，`match` 为 `With` 入边数 + 1；分支臂不变量（见下） | `With` 入边数等于臂数；`Norm` 是它的 `BRCH` |

**臂有两种合法的形态，模型都定义：**

- **子图形态**（前端产生）：每条臂是一张 `role = Arm` 的图，外层图里是一个 `FUNC` 节点，`BRCH` 以一条 `Ctrl` 边指向它，它以一条 `With` 边进 `JOIN`；它既是臂头也是臂尾。臂用到的外层值是它的捕获端口。**这是语法到图的映射**：臂里写了什么不改变外层图的形状（R1）。
- **区域形态**（内联之后）：臂的节点直接在外层图里，位于 `BRCH` 与 `JOIN` 之间。一条臂 = 从它的臂尾沿输入可达、且位于分支内部的节点。

**分支臂不变量**沿用现有定义（`docs/technical/17_graph_rewrite_api_contracts.md` 4.1 的五条）：对每个活的 `BRCH`，分支内部的每个活节点恰好属于一条臂；臂以臂尾定义；两个分支要么不相交要么嵌套；臂读到的分支外的值排在 `BRCH` 之前、无条件执行。

`abs(x) = if x < 0 then 0 - x else x`【实测】：

```

    subgraph "__g_6__" { N03 [PORT]  ARGS -> N03 [WITH_PORT 0]; N03 -> EXIT } // 臂 1：x
    N04 [PORT x]  N05 [DATA 0]  N06 [OPER :op/lt_l]
    N07 [JOIN]  N08 [BRCH]  N09 [FUNC __g_4__]  N0A [FUNC __g_6__]
    N04 -> N06 [NORM 0|0]; N05 -> N06 [NORM 0|1]
    N06 -> N08 [NORM 0|0]                      // 选择子
    N04 -> N08 [CTRL 0|0]                      // 臂捕获的 x 先于分支就绪
    N08 -> N09 [CTRL 0|0]; N08 -> N0A [CTRL 1|0]
```

#### `LOOP` 循环（新增）

| | |
|---|---|
| 语法元素 | `loop s = 初值, t = 初值 while 条件 do 循环体`、`loop s = 初值 for x in xs do 循环体`、`loop … for x in xs while 条件 do …`（设计原则 3.10 的 `do` 式） |
| 输入 | `Norm`：`for` 形式第 0 条是被遍历的元素数组（字符串、映射、张量在循环所在处先由 `__iter__` 算子转换成它，见 `docs/technical/39_loops.md` 2a 节），然后是 k 个状态的初值；`With`：m 个捕获的值，条件图与循环体图共用这一份；`Ctrl`：顺序 |
| 负载 | `kind`：`While`、`For`、`ForWhile`；条件图与循环体图在图引用表里的下标（`For` 没有条件图） |
| 条件图 | `role = LoopCond`；端口：k 个普通形参（状态）+ m 个捕获；返回 `bool` |
| 循环体图 | `role = LoopBody`；端口：（`for` 形式多一个当前元素）+ k 个状态 + m 个捕获；返回下一轮的状态：k = 1 时是那个值，k > 1 时是 k 元组 |
| 输出与类型 | 最终状态；类型与循环体图的返回类型相同 |
| 语义 | `s ← 初值；[对 xs 的每个元素 x，按顺序] 当 条件(s) 为真：s ← 循环体([x,] s)；给出 s`。`ForWhile` 在取每个元素之前先看条件 |
| 纯度与故障 | 两张子图效应摘要之并；可能故障；可能不终止 |
| 求值约束 | E1 之外：各轮严格顺序；每一轮是条件图与循环体图的一次激活；每条回边是一个回收安全点 |
| 不变量 | `Norm`、`With` 入边数与两张子图的端口数一致；条件图返回 `bool`；循环体图的返回类型等于状态类型；两张子图的捕获端口个数与顺序相同 |

状态写在循环头上，所以 k、各状态的类型、初值都在 `LOOP` 节点的入边上，与循环体里写了什么无关（R1）。循环体是独立的子图，不并入外层图：外层图保持无环，容量也不被循环体占用。

`sum_to` 的例子：

```camel
func sum_to(n: int): int {
    let (i, acc) = loop i = 1, acc = 0 while i <= n do (i + 1, acc + i)
    return acc
}
```

图（`std::rgir`【实测，2026-10-15，`lane/loop`】；节点序号与下面一致。图上没有 `role` 字段：两张子图由 `LOOP` 节点的负载指认，名字是 `函数.loopN.cond`、`函数.loopN.body`）：

```
subgraph "sum_to" {
    subgraph "sum_to.loop1.cond" {                         // role = LoopCond
        N00 [PORT i]  N01 [PORT acc]  N02 [PORT n]         // 两个状态；捕获 n
        N03 [OPER :op/le_l]
        N00 -> N03 [NORM 0|0]; N02 -> N03 [NORM 0|1]; N03 -> EXIT
    }
    subgraph "sum_to.loop1.body" {                         // role = LoopBody
        N04 [PORT i]  N05 [PORT acc]  N06 [PORT n]
        N07 [DATA 1]  N08 [OPER :op/add_l]  N09 [OPER :op/add_l]
        N0A [DATA (0, 0)]  N0B [FILL]                      // (i + 1, acc + i)
        N04 -> N08; N07 -> N08; N05 -> N09; N04 -> N09
        N0A -> N0B [NORM 0|0]; N08 -> N0B [WITH 0|0]; N09 -> N0B [WITH 0|1]; N0B -> EXIT
    }
    N0C [PORT n]  N0D [DATA 1]  N0E [DATA 0]
    N0F [LOOP while cond=sum_to.loop1.cond body=sum_to.loop1.body]
    N0D -> N0F [NORM 0|0]; N0E -> N0F [NORM 0|1]           // i、acc 的初值
    N0C -> N0F [WITH 0|0]                                  // 捕获 n
    N10 [ACCS .1]                                          // 取出 acc
    N0F -> N10 [NORM 0|0]; N10 -> EXIT
}
```

条件与循环体是图里的两个控制区域（`GCRegionKind::LoopCond` / `LoopBody`），没有把 `LOOP` 降级成子图的改写：每个后端都在程序自己的图上按 `camel/execute/loop_frame.h` 的轮次协议执行这两个区域（`docs/technical/39_loops.md`；op-semantics 11.4）。对照用的手写尾递归图不是运行时走的路。

#### `GATE` 门

| | |
|---|---|
| 语法元素 | 同步块的值（块的最后一个表达式的值，要等块里前面的表达式都完成）；`return` 在有待完成的顺序时；内联后被调体的值出口与完成点不是同一个节点时 |
| 输入 | `Norm` 一条：值；`Ctrl` 至少一条：要等的节点 |
| 输出与类型 | 把 `Norm` 输入的值原样送出，类型相同；不占新的槽位 |
| 纯度与故障 | 纯；不故障。但它**承载顺序**：读它的节点因此排在它的 `Ctrl` 输入之后，删除或绕过它会丢掉这个顺序 |
| 不变量 | 至少一条 `Norm`、至少一条 `Ctrl`（今天的校验第 4 条）。失去全部 `Ctrl` 输入的 `GATE` 在提交时消去 |

#### `SYNC` 汇合点

| | |
|---|---|
| 语法元素 | 无直接对应；内联一个有多个入口节点的函数体时，用它把调用处的顺序前驱交给每个入口 |
| 输入 | 只有 `Ctrl` |
| 输出 | 无值；别的节点以 `Ctrl` 边等它 |
| 纯度与故障 | 纯；不故障；承载顺序 |

### 3.7 图与图的关系

一张图 G 与别的图只有下面三种关系，全部经由 G 的**图引用表**：

| 关系 | 出现在 | 语言里是什么 |
|---|---|---|
| 直接调用 | `FUNC` 节点的负载（引用表下标） | 函数调用、分支臂、泛型实例的调用 |
| 循环的子图 | `LOOP` 节点的负载（两个下标） | 条件与循环体 |
| 函数常量 | 常量池里函数值的图字段（引用表下标） | 函数作为值、闭包、`__root__` 调用 `main` |

- **依赖** = 引用表。今天的 `dependencies`、`subGraphs`、`staticGraphRefs` 三张表合成这一张，不再有可能与节点不一致的第二份数据。
- **可达闭包**：从 root 的引用表出发的传递闭包。没被引用的图不属于程序。
- **递归**：引用表里可以有自己；图与图之间可以成环。单张图内部永远无环。
- **值怎样跨图**：只经由端口。调用处的实参边在调用方图内，被调图里对应的是端口节点；闭包的捕获值在建闭包的那张图里是 `FILL` 的 `With` 输入，在被调图里是捕获端口。

**捕获端口的绑定。** 每个捕获端口记着它捕获的是什么，两种：

- `Local`：词法上外层图里的一个值（lambda 捕获外层函数的局部量、臂捕获外层图的值、部分应用绑定的实参）。它由建这张图的函数值或调用这张图的 `FUNC` 的那张图直接给出，绑定里不需要记别的。
- `Entity(e)`：某个模块顶层的值，`e` 是它的实体编号。

规则 C1（实体捕获的传递）：一张图 G 有绑定为 `Entity(e)` 的捕获端口，当且仅当 G 的某个节点直接用到 `e`，或 G 的引用表里某张图有这样的端口。直接调用处，调用方用自己绑定到 `e` 的端口（调用方是 root 时用 `e` 的那个 root 节点）接一条 `With` 边；函数值处同样接到 `FILL` 上。于是每个实体捕获沿引用链一路通到 root，root 上正好有那个值。这就是今天单模块内已经在做的事（模块 root 设计稿 1.2 的四条规则），把键从名字换成实体，并把"传递"这一步从建图时的就地改写挪到链接步统一做（3.9.4）。

**"没有跨图的节点引用"怎样机械地校验**（R2）：

1. 节点记录里能指向节点的字段只有输入表项与 `BRCH`/`JOIN` 负载里的配对与臂表，它们都是 16 位的图内序号；校验"小于本图节点数"即可。没有任何字段的位宽或类型能装下"图 + 节点"。
2. 能指向图的字段只有引用表项；校验"是图表里存在的编号"。`FUNC`、`LOOP`、函数常量里的是引用表下标，校验"小于引用表长度"。
3. 实体表里"值"这一类表项记的是 root 上的节点序号。它在图的外面（是名字表的一项，不是某张图的一部分），只在链接步用来接边；链接之后图上只有普通的边与端口。

今天不满足这一条的地方有两处（1.8）：建图器导出值时放进模块导出表的裸节点指针，和 `GCGraph` 里处处可见的图指针。前者换成实体表项，后者换成引用表。

### 3.8 名字、类型、源码位置、诊断与调试信息

**原则：执行用得到的在图里，其余在旁边的表或列里，用编号关联**（R12）。

| 信息 | 放在哪 | 键 |
|---|---|---|
| 图的名字、所实现的实体、来历 | 图头的三个编号 | `SymId`、`EntityId`、`GraphId` |
| 端口名 | 端口表 | `SymId` |
| 字段名（`ACCS`） | 节点负载 | `SymId` |
| 算子 | 节点负载 | `OperId` → 算子表：URI、签名的类型规则、性质、运行时的函数指针 |
| 类型 | 节点的 `type`、图的 `signature`、槽位类型表、常量池 | `TypeId` → 类型表 |
| 源码位置 | 位置列（与节点数组平行）、图头的一个 `OriginId`（函数的声明处） | `OriginId` → 位置表 |
| root 节点对应哪个顶层声明 | root 的"节点名"列（稀疏：节点序号 → 实体） | `EntityId` |
| 语义部件（"这个节点的被调者是源码里哪一段"等，语言服务器与调试器用） | 不在模型里；语义查询层自己的表，按 `OriginId` 关联 | `OriginId` |

**类型表。** 类型按结构驻留：两个类型相同当且仅当编号相同。这要求类型对象不可变，所以今天挂在函数类型对象上的两样东西移走：捕获名移到图的端口表；"建图时才填的返回类型"改为先有图、图建完再驻留它的签名。形参名不属于类型（现状已是如此，1.5），显示函数签名时名字取自端口表。每张图的帧布局不再是一个元组类型对象，而是图块里的一个 `TypeId` 数组，随图释放。

**算子表。** 每个算子一项：

| 字段 | 含义 |
|---|---|
| `uri` | `":op/add_l"`、`"tensor:matmul"` |
| `pure` / `stateOnly` | 现有含义 |
| `mayFault` | 新增：可能出故障（除零、越界、转换放不进目标类型）。没有声明的按"可能"对待 |
| `elementwise` | 现有含义 |
| `callsGraphs` | 新增：执行中会调用实参里的函数值（高阶算子与 `attempt`）。遍据此知道"效应取决于传进来的函数" |
| 类型规则、类型折叠 | 现有的 resolver 与 type folder |
| 实现 | 运行时的函数指针；缓存里不存，装载时按 URI 解析 |

遍与后端认算子用编号比较；常用的内建算子有编译期常量形式的编号（R10）。

**位置表。** 沿用现有的 `SourceContext`（文件、区间、位置及其派生链），改两点：位置编号收成 32 位、按模块连续分配，使一个模块的位置可以整段写进缓存、装载时加一个基数；节点 → 位置从"每图一张哈希表"改为与节点数组平行的列。

**改写怎样保持位置**（沿用今天的规则，`draft.h:80-82`）：替换一个节点的新节点继承它的位置；内联进来的节点保留被调图里的位置；遍新造的节点取触发它的节点的位置。位置列因此总是满的，调试器与诊断不需要"稳定的节点标识"。

**诊断所需**：编译期诊断只在编译这个模块时产生，缓存命中的模块不重放警告（Q5）；运行期的故障位置经位置列与位置表得到，所以位置表与文件表进缓存，源文本不进（显示代码行时再读源文件，读不到就只给行列号）。

**调试器所需**：位置列（节点 → 行）、它的反向索引（装载后一次建成）、端口名与图名（变量视图）、root 节点名列。都在上表里。

### 3.9 模块

#### 3.9.1 实体与"模块 + 限定名"

**实体**是程序里有名字的东西。它的对外标识是三元组：

```
( 模块名 , 限定名路径 , 重载判别 )        例： ( shapes , [Tools, area] , (float, float) )
```

- 模块名：`module` 声明给的名字，或文件名。
- 限定名路径：从模块顶层到这个声明经过的命名空间，加上它自己的名字。顶层的 `pi` 是 `[pi]`，`namespace Tools { func inc }` 是 `[Tools, inc]`。
- 重载判别：只有函数有，是它的普通形参与 `with` 形参的类型列表；同名不同参数的函数是不同的实体。

写出来是 `shapes::Tools::area`。这就是**命名空间的内部形式**：命名空间不是一种对象，是实体名字里的路径前缀；`namespace`、`using`、`import` 只决定源码里的一个名字解析到哪个实体（第 8 节）。

实体的种类与它"是什么"：

| 种类 | 定义 | 在图上 |
|---|---|---|
| 值 | root 上的一个节点 + 类型 + 是否 `var` | root 的节点；函数里的捕获端口 |
| 函数 | 一张图（`GraphId`） | `FUNC`、函数常量 |
| 泛型模板 | 模板体（声明的语法树与类型方案）+ 已建的实例表（类型实参 → `GraphId`） | 实例的 `FUNC` |
| 类型 | `TypeId` | 无节点 |
| 算子 | `OperId` | `OPER` |
| C++ 模块的值 | 一个无参算子 + "是值"的标记（模块 root 设计稿 5.5 (ii)） | root 上一个无输入的 `OPER` |

捕获端口的绑定、诊断里显示的名字、调试器的变量名、ONNX 初始化器的名字、缓存里跨模块的引用，用的都是这个标识（R11）。

#### 3.9.2 模块对程序的贡献

一个模块编译之后是一个**模块单元**：

| 部分 | 内容 |
|---|---|
| 头 | 模块名、源文件、源文件内容的散列、它导入的模块及当时各自的接口指纹 |
| 实体 | 它声明的全部实体（导出的与没导出的），每个带种类、限定名、类型、定义 |
| 顶层段 | 它的顶层 `let`/`var` 的初始化表达式建出的节点：一段节点、它们之间的边、它们的常量；用到别的模块的值的地方是一个"外部输入"占位，记着实体 |
| 图集 | 它的函数、lambda、分支臂、循环子图，以及归它所有的泛型实例 |
| 接口 | 导出的实体及其对导入方可见的事实；接口指纹 |
| 表 | 这个单元用到的类型、符号、算子、位置，按模块内编号 |

**公共 root** 由各模块的顶层段拼成：全程序一张 `__root__`，每个顶层值是它上面的节点，一个节点属于哪个模块记在 root 的"所有者"列里（建成时每个模块是连续的一段；遍改写之后只保证每个节点仍有所有者）。入口模块多贡献两到三个节点：`main` 的函数常量、装入捕获值的 `FILL`（有捕获时）、`CALL`，以及 `main` 带参数时 root 的端口。被导入模块里名叫 `main` 的函数是普通函数。

合并的不是函数：函数各是各的图，在图表里各占一项。合并的只是每个模块那几个顶层节点（模块 root 设计稿 2.6：673 个程序的 root 加在一起 1,432 个节点）。

#### 3.9.3 接口与接口指纹

接口是"导入方编译自己时依赖的、关于这个模块的全部事实"。对每个导出的实体：

| 实体 | 计入接口的事实 |
|---|---|
| 值 | 限定名、类型 |
| 函数 | 限定名、签名（参数类型、是否 `var`、返回类型——包括没有声明而推断出来的）、修饰符；**它传递捕获的实体列表**（C1）；**效应摘要** |
| 泛型模板 | 限定名、类型方案、**模板体的散列**、模板体里引用到的本模块其他实体各自的接口事实（递归） |
| 类型 | 限定名、类型的结构 |
| 命名空间 | 它的成员表 |

**接口指纹**是把上述事实按限定名排序后写成规范字节串的散列（128 位），再混入模型版本号。它不含：函数体、没导出也没被模板引用的实体、源码位置、注释。

- 改一个导出函数的函数体，只要它用到的模块级值没变、有没有效应没变、返回类型没变，指纹不变，导入方的缓存继续有效。
- 让一个导出函数开始使用一个新的模块顶层值，指纹变了：导入方调用它的每一处都要多传一个值，导入方必须重新编译。这是"函数经捕获端口取值"的直接后果（Q4）。
- 改泛型函数的函数体，指纹变了：实例是在使用方的类型下重新检查函数体建出来的。

互相导入的一组模块（导入图的一个强连通分量）共同决定彼此的捕获列表与效应摘要，所以作为一组编译，组内任何一个源文件变了，整组重新编译；对组外仍是每个模块各有自己的指纹。

#### 3.9.4 三步加载

今天是"遇到 `import` 就把被导入模块完整编译完"（1.9），所以互相导入无法进行。改为三步：

**第一步：声明。** 从入口文件出发，求出导入闭包里的全部模块；每个模块只做到"知道它声明了什么"：

- 解析源文件（缓存有效的模块跳过，直接读单元里的实体与接口）；
- 登记每个顶层声明：种类、限定名、写出来的类型（函数没写返回类型、值没写类型的，记为"待定"）、是否导出；
- 所有模块都登记完之后，解析每条 `import`、`using namespace`：名字是否存在、是否冲突（两个模块带来同名同签名的函数、值与函数同名等），在这一步报告。

这一步不看任何函数体，所以模块之间怎样互相导入都没有关系。

**第二步：建图。** 按需建每个实体的定义，每个实体有三个状态：已声明、正在建、已建成。

- 建一个函数体或一个顶层值的初始化表达式时，遇到对别的实体的引用：需要它的类型而它"待定"，就先去建它；它"正在建"，就是环——
  - 函数：环上的函数必须写明返回类型。没写的报现有的 `CallingIncompleteFunction`（今天同一个模块里没写返回类型的互递归就是这条诊断【实测】），跨模块时消息里列出环上的函数与各自的文件。
  - 值：`ModuleValueCycle`（新），定位在闭合环的那次引用，列出整条链：`a::x (a.cml:3) → b::y (b.cml:5) → a::x`。
- 调用一个函数时只按它**声明的**形参连实参边，不管它捕获了什么；函数体里直接用到的模块级值登记为绑定到实体的捕获端口。泛型实例在这一步按需建，全程序每组类型一张。
- 缓存有效的模块没有这一步：它的图已经在单元里。

顶层声明因此与书写顺序无关：`let a = b + 1` 写在 `let b = 2` 前面，建 `a` 时先去建 `b`。

**第三步：链接。**

1. **算捕获的不动点**（C1）：每张新建的图传递地需要哪些实体。缓存来的图这一项已经在接口里。
2. **接线**：给每张新建的图补上传递来的捕获端口，给每个 `FUNC` 与函数值的 `FILL` 补上对应的 `With` 边。分支臂的 `FUNC` 同时让被捕获的值以 `Ctrl` 边先于 `BRCH`。
3. **算效应摘要**的不动点；据此报告"带效应但不会执行"的警告与"写了捕获的变量却没声明 `sync`"的错误。
4. **拼 root**：把各模块的顶层段接到一张图上，外部输入占位换成对应实体的 root 节点；建入口调用。
5. **冻结**：每张图校验（3.10）并排成冻结块；root 上出口到不了的节点（没人用的顶层值）在这一步消失。

第 1、2 步取代了今天建图器里"函数第一次被调用时把捕获端口就地改成 `with` 端口、此后的调用按名字补边"的那段逻辑，以及它带来的 `ClosureCaptureAfterSelfCall`（函数先被调用、后发现新捕获）与"顶层值必须先声明后使用"两个限制。

#### 3.9.5 互相导入时的两种环

| 环 | 例子 | 判定 | 结果 |
|---|---|---|---|
| 函数互相调用 | `a` 的 `even` 调 `b` 的 `odd`，`odd` 调 `even` | 不是错误：图引用图可以成环 | 两张图，互相在对方的引用表里。没写返回类型时见上 |
| 顶层值互相依赖 | `a` 的 `let x = b::y + 1`，`b` 的 `let y = a::x * 2` | 第二步里引用到"正在建"的值 | `ModuleValueCycle` |
| 值经函数成环 | `let a = f()`，`f` 的函数体用到 `a` | 同上：建 `a` 时建 `f` 的调用，链接步发现 `f` 捕获 `a`，而 `a` 的节点依赖这次调用 | `ModuleValueCycle`（今天同模块内是 `ClosureCaptureAfterSelfCall`，消息不达意） |
| 模块互相导入但值不成环 | `a` 的 `x` 用 `b` 的 `y`，`b` 的 `z` 用 `a` 的 `x` | 不是错误 | root 上三个节点，无环 |

第三行的判定落在链接步的第 4 小步：拼好的 root 必须无环，有环时沿环回溯出涉及的顶层值并报告。

### 3.11 版本与演进

**版本号**：`主.次`，写在每个缓存文件头与 `Program` 上。本稿定义的是 `1.0`。

**承诺稳定的**（主版本内不变）：

- 节点种类的数值编码与 3.5 各卡片的语义；
- 三种边的含义与规则 E1；
- 规则 C1 与"图引用图只走引用表"；
- 实体标识的形式（模块 + 限定名 + 重载判别）；
- 接口指纹覆盖的事实清单；
- Camel 一侧的查询与改写算子（5.2）一旦发布之后的签名。

**不承诺的**：冻结块的内存排布、草稿的内部结构、缓存文件的节区布局（靠文件头的版本号与编译器构建标识整体失效，不做跨版本读取）、算子编号与类型编号的具体数值、效应摘要的位分配。

**兼容规则。**

- **加节点种类**：次版本加一，取下一个数值，同时给出它到已有种类的降级改写（像 `LOOP` → 尾递归那样）。只读的消费者遇到不认识的种类必须报出"不支持的节点种类"并指明图与位置，不得跳过；改写的消费者遇到不认识的种类把它当作"有效应、可能故障、承载顺序、不可删除"的黑盒。
- **加字段**：只加在负载区或新的列里；旧字段的含义不变。
- **加算子性质**：缺省值取保守的一侧。
- **改已有种类的语义、改边的含义、改 E1**：主版本加一，要经语言作者同意。
- **删种类**：数值保留不用，不复用。`BIND`、`DREF` 即是这样处理的。

## 4. 内存与存储表示

同一份数据有三种排布。它们一一对应，互相转换是一遍线性的拷贝加编号改写，没有"第二种图"。

| 形态 | 谁用 | 可变 | 编号指向 |
|---|---|---|---|
| **草稿** | 前端建图、各遍改写 | 是 | 进程内的全程序表 |
| **冻结块** | 后端、只读的遍、调试器、Camel 一侧的图值 | 否 | 进程内的全程序表 |
| **缓存文件** | 模块缓存 | 否 | 文件自带的模块内表 |

### 4.1 冻结块

一张冻结的图是图空间里**一段连续的、不含任何地址的内存**：一个定长的头，后面按固定顺序排着各个数组。各数组的起点由头里的计数算出，不存偏移。

**节点记录，16 字节：**

```
struct Node {
    uint8_t  kind;        // 种类
    uint8_t  flags;       // constant / macro / var
    int16_t  slot;        // SlotId
    uint32_t type;        // TypeId
    uint16_t inBegin;     // 输入表里本节点第一条输入的下标；Norm 段从这里开始
    uint16_t withBegin;   // With 段的起点
    uint16_t ctrlBegin;   // Ctrl 段的起点；到下一个节点的 inBegin 为止
    uint16_t payload;     // 负载区里的偏移（8 字节为一字，见 3b 的实施记录）；kNoPayload（0xFFFF）表示没有负载
};
```

节点数组末尾多放一个哨兵节点，所以三段的长度都是两个相邻字段之差。节点序号就是数组下标：遍历是一个 `for`，按序号取节点是一次乘法（今天节点是变长的，按"8 字节块的偏移"寻址，遍历要逐个跳，`graph.h:361-393`）。

**图头，64 字节**：块长、模型版本、`role`、标志与效应摘要、`id`、`name`、`entity`、`lineage`、`owner`、`signature`、函数声明处的 `OriginId`，十个 16 位计数（节点、输入表项、负载字、常量、引用、三类端口、槽位），`exit`、`result`。

**各数组：**

| 数组 | 每项 | 内容 |
|---|---|---|
| 节点 | 16 字节 | 上述记录，节点数 + 1 项 |
| 输入表 | 2 字节 | `NodeId`；每条边一项 |
| 负载区 | 4 字节的字 | `FUNC`：引用表下标。`OPER`：`OperId`。`ACCS`：下标或 `SymId`（最高位区分）。`FILL`：种类与个数，后接各填充位置。`BRCH`：配对的 `JOIN` 与臂数，后接每臂的（臂头，臂尾）。`JOIN`：配对的 `BRCH`。`LOOP`：`kind`、条件图与循环体图的引用表下标 |
| 端口表 | 12 字节 | 节点序号、标志（`var`、绑定种类）、名字 `SymId`、绑定的 `EntityId`（`Local` 绑定为 0） |
| 图引用表 | 4 字节 | `GraphId` |
| 槽位类型表 | 4 字节 | 每个帧槽的 `TypeId`（帧布局；回收器按它追踪帧里的对象） |
| 常量池 | 4 + 8 字节 | 每个常量的 `TypeId` 与一个槽值；对象常量的槽值是常量区里对象的编号（见下） |
| 位置列 | 4 字节 | 每个节点的 `OriginId`；冷数据，放在块尾 |

**对象常量**（字符串、数组、元组、结构体、张量、函数值）不在图块里：它们是堆对象，放在程序的常量区（今天各图的静态区元组，回收器把它们当根追踪，分代回收下直接分配在老年代、不移动——`docs/technical/36_gc_handle_rules.md` 的规则不变）。常量池的槽值存的是常量区里的编号，装载时换成对象。函数值常量是（引用表下标，捕获值列表）。

**使用者（输出）方向不存在冻结块里。** 后端几乎不用它（1.8）。需要它的消费者（改写遍在草稿上本来就有；只读的分析）调用 `uses(graph)` 取一个按需建立并缓存的反向索引，代价是一遍输入表。

**执行计划也不在冻结块里。** 执行序、每个 `BRCH` 的各臂区间、每个调用的实参槽位表、解析好的被调图与算子函数指针，今天各后端各算一遍；改为每张图一份 `ExecPlan`，第一次有后端要时算出，按 `GraphId` 与快照版本缓存，四个后端与宏求值器共用。NodeVM 往冻结图里写算子指针的 `const_cast` 由此消失。

### 4.2 草稿

草稿是同一套字段的可增长版本：

```
GraphDraft
  nodes     可增长数组，每项 = 16 字节的节点记录 + 输入段与使用者段在边池里的（起点，容量，各组条数）+ OriginId
  edges     边池：一个可增长的 NodeId 数组；每个节点的输入表与使用者表是其中的一段，
            放不下时整段搬到池尾并把容量翻倍，空洞超过一半时整理
  payload   负载区，同冻结块
  ports / refs / consts / slotTypes   可增长数组
  free list 被删节点的序号，供新节点复用
```

- **一张草稿的堆分配次数是常数**（几个数组，各自倍增），与节点数无关；数组来自一个随编译会话整体释放的区域分配器。今天建一张图是每节点约 30 次 `malloc`（1.10）。
- 冷信息都是节点记录上的编号或平行数组，不再有以节点指针为键的哈希表。
- 草稿里的节点序号在一次编辑期间稳定（删除只是进空闲表），所以遍可以拿着序号做事，不需要指针。
- **冻结**：求活节点 → 按序重新编号 → 按 4.1 的顺序写出各数组 → 校验。一遍，线性。没有中间的"第二个草稿"。
- **解码**：冻结块 → 草稿是数组的拷贝加一遍建立使用者表。

前端建图与遍改写用的是同一个草稿类型，同一组编辑操作（5.1）。

### 4.3 全程序的表与三块空间

| 表 | 放在 | 增长方式 | 释放 |
|---|---|---|---|
| 图表（`GraphId` → 冻结块） | 图空间 | 分段的指针数组（每段 1,024 项）；快照之间共享没变的段 | 没有快照引用的冻结块逐个释放 |
| 冻结块 | 图空间 | 每张图一次分配 | 同上 |
| 类型表 | 永久空间 | 只追加；`TypeId` → 类型对象经一个分段索引；另有一张"结构 → 编号"的哈希表做驻留 | 不释放——驻留之后它的大小是程序里**不同**类型的个数，不再随提交次数增长 |
| 符号表 | 永久空间 | 只追加的字节区 + 偏移数组 + 哈希表 | 不释放 |
| 算子表、实体表、模块表 | 永久空间 | 只追加 | 不释放 |
| 位置表 | 元空间 | 按模块成段追加 | 随模块 |
| 草稿、建图器的作用域等 | 元空间里的会话区域 | 区域分配 | 会话结束整体释放 |

**段式增长与下标寻址怎样配合。** 所有"编号 → 东西"的表都是"高位选段、低位段内下标"的两级结构：加段不搬动已有的段，所以编号一经分配永远有效，别处持有的编号不需要更新；一次查找是两次取数。图内的数组则必须连续（16 位下标直接寻址），所以一张图是一次分配、整块落在一个段里——一张图最大约 2 MB（65,535 个节点与 65,535 条边全满时），远小于段长（图空间每段 64 MB）。

**快照。** `Program` 是不可变的：一次提交产生一个新的快照，它与旧快照共享所有没改的冻结块与图表段，只为改了的图分配新块。旧快照在没人持有后释放它独占的块。"导出某个函数时在一份脱离主程序的拷贝上做改写"（今天的 `trackDetached`/`releaseDetached`，`graph.h:470-474`）就是持有一个旧快照，不需要专门的机制。

### 4.4 与现状相比

按 1.10 普查的语料（6,513 张图、47,064 个节点、53,014 条边，不加遍）估算新排布的字节数，与今天的实测对照：

| | 今天（实测） | 模型（按 4.1 的排布计算） |
|---|---|---|
| 节点 | 40 字节的头 + 负载（`OPER` 另加 16 字节与内嵌的 URI） | 16 字节 × 47,064 = 753 KB |
| 边 | 每条 2 × 2 字节 | 2 字节 × 53,014 = 106 KB |
| 负载 | 在节点里 | 约 108 KB（`OPER`、`FUNC`、`ACCS`、`JOIN` 各 4 字节，`BRCH` 12 字节，`FILL` 约 8 字节） |
| 图头 | `GCGraph` 对象（含 8 个扩展槽 64 字节）+ 调试记录（三个字符串、一张哈希表） | 64 字节 × 6,513 = 417 KB |
| 端口、引用表、槽位类型、常量池 | 分散在图对象、类型对象、静态区元组里 | 78 + 26 + 188 + 169 = 461 KB |
| 源码位置 | 每图一张 `unordered_map`，在普通堆上【未量】 | 4 字节 × 47,064 = 188 KB |
| **图合计** | **图空间 4,458 KB（每节点 97 字节、每图 701 字节），不含位置与名字** | **约 2,030 KB（每节点 43 字节，含位置与名字）** |
| 类型 | 永久空间 6,629 KB（每图 1,364 字节，11 次分配），不释放 | 程序里不同类型的个数 × 类型大小；每图不新增类型对象【驻留后的实际数字未量：今天没有办法数出不同类型的个数】 |
| 建图期 | 元空间峰值 4,768 KB（每图 750 字节）；`malloc` 每节点约 30 次（建图）+ 约 36 次（编码） | 草稿的几个数组；每图常数次分配 |
| 一张 2 个节点的分支臂图 | 约 2.8 KB（三块空间合计的每图均值） | 64 + 3 × 16 + 几个表项 ≈ 130 字节 |

化简之后的差距更大：今天每个最终留下的图平均被重新编码 6 次（1.10），模型下只有被改的图重新冻结；永久空间里每节点 185 字节的类型不再产生。

这些是按排布算出来的预期，不是测量；第 7 节的第 2、3 步各自以"同一语料上的字节数与 `malloc` 次数"为验收数字。

### 4.5 缓存文件格式（草案）

**字节序**：小端。**对齐**：每个节区 8 字节对齐。**校验**：每个节区一个 64 位校验和，文件头自带一个。

**文件头，96 字节：**

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 8 | 魔数 `89 43 4D 4F 0D 0A 1A 0A`（`\x89CMO\r\n\x1a\n`） |
| 8 | 2 + 2 | 模型版本：主、次 |
| 12 | 4 | 标志：有调试节区、有模板节区、属于一个互相导入的组…… |
| 16 | 16 | 编译器构建标识（版本号与构建配置的散列）。不同即整体失效 |
| 32 | 8 | 影响前端的选项的摘要 |
| 40 | 16 | 源文件内容的散列（128 位） |
| 56 | 16 | 接口指纹 |
| 72 | 4 + 4 | 节区个数、节区表偏移 |
| 80 | 8 | 文件总长 |
| 88 | 8 | 头的校验和 |

**节区表**：每项 32 字节——四字符标签、标志、偏移、长度、校验和。

| 标签 | 内容 | 何时读 |
|---|---|---|
| `IMPT` | 导入的模块：名字、解析到的路径、编译时它的接口指纹；互相导入的组的其他成员及其源文件散列 | 判断是否有效 |
| `IFAC` | 接口事实（3.9.3）：导出的实体、签名、捕获列表、效应摘要 | 别的模块以它为依据编译时 |
| `SYMS` | 符号：字符串 | 装载 |
| `TYPS` | 类型：后序排列，每项是类型构造子加操作数（模块内的 `TypeId`/`SymId`）；C++ 模块提供的类型记为（模块名，类型名，参数） | 装载 |
| `OPRS` | 用到的算子：URI 与签名 | 装载（按 URI 解析成本进程的 `OperId`，并核对签名） |
| `EXTN` | 外部引用：本单元引用到的别的模块的实体（模块名、限定名、重载判别） | 装载 |
| `ENTS` | 本模块声明的全部实体及其定义的位置（哪个图块、顶层段的哪个节点、哪个类型） | 装载 |
| `GRPH` | 图块的目录与各图块（4.1 的排布，编号是模块内的） | 装载 |
| `ROOT` | 顶层段：一个图块，另带外部输入表（哪些输入位置对应哪个外部实体）与各节点对应的本模块实体 | 装载 |
| `CNST` | 对象常量：按类型编码（字符串的字节、数组与元组的元素、结构体的字段、映射与集合的条目、函数值的图与捕获值）；C++ 模块的对象经模块提供的编码函数 | 装载 |
| `TMPL` | 泛型函数与带参数的类型声明：声明的源码切片与它的位置基数 | 有人要一个缓存里没有的实例时 |
| `ORIG` | 位置表、区间表、文件表 | 第一次需要源码位置时（故障、调试器、`std::rgir`） |

**为什么不需要重定位表。** 图块里每个要改写的编号都在类型已知的位置上：节点的 `type`、按节点种类解释的负载字、端口表的名字与绑定、引用表、槽位类型、常量池的类型、位置列。装载器按 4.1 的排布走一遍就知道哪些字是哪种编号，各加上或查出本进程的值。这是"图内部用下标而非指针"带来的：没有任何一处需要"这里有个地址，请修正"的记录。

**与 C++ 模块的 `.cmo` 区分。** 读文件头的前 8 个字节：

| 开头 | 是什么 |
|---|---|
| `89 43 4D 4F 0D 0A 1A 0A` | Camel 模块缓存 |
| `7F 45 4C 46`（ELF）、`4D 5A`（PE）、`CF FA ED FE` / `CE FA ED FE` / `CA FE BA BE`（Mach-O） | C++ 模块，交给动态装载器 |
| 其他 | 报"不是一个 Camel 模块文件"，给出路径与读到的前几个字节 |

魔数的第一个字节大于 `0x7F`，不会被当成文本；中间的 `\r\n` 与 `\x1a` 能暴露被文本模式传输改坏的文件。写缓存的一方只覆盖"不存在的文件"或"魔数是 Camel 缓存的文件"，遇到别的一律不写并提示；写入是先写临时文件再改名。

### 4.6 各样东西怎样进缓存

| 东西 | 做法 |
|---|---|
| 函数、lambda、分支臂、循环子图 | 图块。建成时的形态（前端的产出，已做完捕获接线），不是任何遍之后的形态 |
| 顶层值 | 顶层段里的节点；实体表指着它 |
| 泛型模板 | `TMPL` 里的源码切片。实例是普通的图块，带"（模板实体，类型实参）"的键，归声明模板的模块所有；哪个模块先要到某个实例，就存在哪个模块的缓存里，装载时同键的只留一份 |
| `macro` 函数 | 普通的图块，签名带 `macro`。宏求值是 `std::macro` 遍的事，发生在装载之后，结果不进缓存 |
| 类型、带参数的类型声明 | `TYPS`；带参数的（类型函数）与泛型模板一样存切片 |
| 名字表 | `SYMS`、`ENTS` |
| 源码位置 | `ORIG`；源文本不存 |
| 诊断所需信息 | 运行期故障要的位置在 `ORIG`；编译期的警告不重放（Q5） |
| 调试器所需信息 | 位置列、端口名、图名、root 节点名都在图块与 `ROOT` 里；"位置 → 节点"的反向索引装载后建 |
| C++ 算子 | `OPRS` 里只有 URI 与签名；实现由本进程的模块给出，签名对不上则缓存失效 |
| 遍的结果（内联、特化、宏求值之后的图） | 不缓存。缓存"不必等同实际编译的最终结果"，它只消掉解析与分析 |

不能进缓存的情形：常量里有某个 C++ 模块的对象而该模块没有提供编码函数。这样的模块标为"不可缓存"并说明原因，每次从源码编译。前端建出的图里的常量几乎都是字面量；张量常量主要来自宏求值，那已经在装载之后。

### 4.7 失效条件

模块 M 的缓存有效，当且仅当全部成立：

1. 文件头的魔数、模型版本、编译器构建标识、选项摘要与本进程一致；
2. M 的源文件内容的散列与文件头里的一致（每次都算，不依赖修改时间；散列一个源文件的代价远小于解析它【未量】）；
3. `IMPT` 里每个导入：名字今天解析到的仍是记下的那个文件，并且那个模块**现在的**接口指纹等于记下的指纹（它自己可以是缓存命中的，也可以是刚重新编译的）；
4. M 属于互相导入的组时，组内每个成员的源文件散列都没变；
5. `OPRS` 里每个算子在本进程里存在且签名相同。

任何一条不成立，M 从源码重新编译并重写缓存。第 3 条使失效沿导入链传播得恰到好处：被导入模块改了函数体而接口没变，导入方不动。

### 4.8 装载一个缓存模块并拼入公共 root

输入：通过了 4.7 的单元文件。输出：程序的各表多了这个模块的内容，公共 root 多了它的顶层段。

1. **符号**：`SYMS` 的每个字符串驻留进符号表，得到"模块内 `SymId` → 全程序 `SymId`"的数组。O(字符串总长)。
2. **类型**：`TYPS` 按后序逐个驻留（操作数先经映射换成全程序编号），得到类型映射数组。O(类型数)。
3. **算子、外部引用、实体**：`OPRS` 按 URI 查出 `OperId`；`EXTN` 的每项在实体表里查出 `EntityId`（被引用的模块已经先装载）；`ENTS` 的每项登记进实体表。O(项数)。
4. **图编号**：给 `GRPH` 的每张图分配一个 `GraphId`；带实例键的先查全程序的实例表，已有就复用那个编号并跳过这个图块。O(图数)。
5. **图块**：把每个图块拷进图空间，按 4.5 走一遍改写编号——节点的 `type`、负载里的 `OperId`/`SymId`、端口表、引用表（模块内图号 → `GraphId`，外部的经第 3 步）、槽位类型、常量池、位置列（加上本模块的位置基数）。O(图块字节数)。
6. **常量**：`CNST` 里被用到的对象在常量区里建出来。O(常量字节数)。
7. **顶层段**：把 `ROOT` 的节点追加到 root 的草稿：节点序号加上 root 当前的节点数，槽位、常量池下标、引用表下标各加上各自的基数；每个节点的所有者记为本模块；实体表里本模块的值指向新序号。O(顶层段大小)。
8. **外部输入**：所有模块的顶层段都追加完之后，把每个外部输入占位换成对应实体的 root 节点序号。O(外部输入数)。因为先追加、后接线，各模块的装载顺序无关紧要。
9. 全部模块装载完，照常走链接步的第 4、5 小步（建入口调用、冻结并校验 root）。

总代价：**与这个模块贡献的字节数成线性**，每个字节被读一次、每个编号被改写一次；不解析、不做名字解析、不做类型检查、不算捕获。新编译的模块与缓存来的模块在第 7 步之后没有区别。

没有被任何东西引用的图（库里这个程序没用到的函数）可以不装：第 5 步改为从入口模块的引用表出发按需装载图块。`GRPH` 的目录为此存在。

## 5. 接口

### 5.1 C++ 一侧

三层，从只读到可写：

**(1) 只读视图：`GraphView`、`ProgramView`。** 冻结块与草稿都实现它，所以一个分析写一次，两处都能用。

```
ProgramView
    graph(GraphId) -> GraphView          root() -> GraphView
    reachable(GraphId) -> 范围            // 引用表的传递闭包
    type(TypeId) / symbol(SymId) / oper(OperId) / entity(EntityId) / origin(OriginId)
    resolve(module, path, signature) -> EntityId

GraphView
    id() role() name() signature() effects() exit() result()
    nodes() -> 序号范围                    node(NodeId) -> NodeRef
    normPorts() withPorts() capturePorts() // 端口：节点、名字、绑定
    refs() -> GraphId 的范围               // 这张图引用的全部图

NodeRef
    kind() type() slot() flags() origin()
    norm() with() ctrl() -> NodeId 的范围   // 三组输入
    // 按种类取负载；种类不对是断言失败
    oper() -> OperId                       // OPER
    callee() -> GraphId                    // FUNC
    constant() -> (TypeId, 槽值)            // DATA
    field() -> 下标或 SymId                 // ACCS
    fill() -> (种类, 位置表)                // FILL
    branch() -> (选择子, 各 case 值, 臂表, join)   // BRCH
    loop() -> (kind, cond, body, 状态初值, 捕获)   // LOOP
    // 按角色取输入，免得每个消费者自己记"CALL 的被调者是 With 第 0 条"
    calleeValue() args() withArgs()        // CALL
    template_() holes()                    // FILL

uses(GraphView) -> UseIndex                // 反向索引，按需建，缓存
    users(NodeId) -> (使用者, 哪一组, 第几个) 的范围
```

**(2) 给后端的冻结视图：`ExecPlan`。** 每张冻结图一份，按需算、缓存、所有执行类消费者共用：

```
ExecPlan
    order() -> NodeId[]                    // 活节点的一个执行序（今天的 buildReachableExecutionTopoIndices）
    armRange(brch, i) -> order 里的区间     // 每条臂
    callTarget(i) -> 冻结图指针             // FUNC：已解析
    operImpl(i) -> 算子函数指针             // OPER：已解析
    argSlots(i) -> SlotId[]                // 调用与算子的实参槽位
    frameLayout() -> 槽位数、哪些槽要追踪
    tailCalls() -> 哪些调用在尾位置
```

**(3) 改写：`Rewrite` 事务。**

```
Rewrite tx(program);                       // 基于一个快照
GraphDraft& d = tx.edit(graphId);          // 第一次取时从冻结块解码；只有被取过的图会重新冻结
GraphId g = tx.create(role, signature, name, lineage);   // 新图，立即有编号，可以被别的草稿引用
Program next = tx.commit();                // 冻结被改的图、校验 3.10、产生新快照；失败则抛出，program 不变

GraphDraft                                 // 前端与遍共用
    addData / addPort / addOper / addFunc / addCall / addFill / addAccs / addCast / addCopy
    addBranch(选择子, case 值, 臂) -> (brch, join)     // 成对地建，不出现"先建空的再整体重写"
    addLoop(kind, cond, body, 初值, 捕获) / addGate(值, 等待) / addSync(等待)
    link(kind, from, to) / unlink / replaceInput
    replaceAllUses(old, new) / erase(node)
    replaceNode(old, new)                  // 保持顺序的替换（今天 generic/rewrite.h 的 replaceNode）
    inlineCall(funcNode) -> (valueExit, ctrlEntry, ctrlExit)    // 今天的 inlineCallableInDraft
    setExit / setResult / ref(GraphId) -> 引用表下标
```

与今天的差别：

- `commit()` 只重新冻结 `edit()` 过的图。图编号不变，所以引用它们的图不用动（R9）。
- 改写驱动先在只读视图上找到要改的地方，再 `edit()`；不再"把每张图都解码一遍再问"。
- 相互引用的一组新图不需要 `GraphDraftGroup` 那样的占位键：`create()` 直接给编号。
- 绕过接口的几处（1.8）各有了正门：算子指针在 `ExecPlan` 里；改节点负载经类型化的 setter；建分支一步完成。

### 5.2 Camel 一侧（为"用 Camel 写遍"预留）

**图是值。** 快照不可变、编号稳定，所以图与节点可以直接是 Camel 的值，不需要句柄表或生命周期规则：

| Camel 类型 | 是什么 | 实现 |
|---|---|---|
| `Program` | 一个程序快照 | 指向快照的引用 |
| `Graph` | 某个快照里的一张图 | （快照，`GraphId`） |
| `Node` | 某张图里的一个节点 | （快照，`GraphId`，`NodeId`） |
| `Edit` | 对一张图的一处改动的描述（一个普通的值） | 结构体 |
| `Term` | 一小棵"要新建的节点"的表达式树，叶子是已有的 `Node` 或常量 | 结构体 |

它们由一个内建模块 `graph` 提供，与 `Tensor` 一样是模块类型。遍是一个 `(Program) => Program!` 的函数：返回新的快照，或一个说明校验为何失败的错误值。

**查询算子（最小集）。** 都是纯的。

```camel
import graph

// 程序与图
graph::root(p: Program): Graph
graph::graphs(p: Program): Graph[]                 // 从 root 可达的全部图
graph::find(p: Program, name: string): Graph?      // 按"模块::限定名"
graph::name(g: Graph): string
graph::role(g: Graph): string                      // 'function' | 'arm' | 'lambda' | ...
graph::nodes(g: Graph): Node[]
graph::exit(g: Graph): Node
graph::ports(g: Graph): Node[]

// 节点
graph::kind(n: Node): string                       // 'OPER' | 'FUNC' | 'DATA' | ...
graph::inputs(n: Node): Node[]                     // Norm 组
graph::with_inputs(n: Node): Node[]
graph::ctrl_inputs(n: Node): Node[]
graph::users(n: Node): Node[]
graph::oper(n: Node): string?                      // OPER 的 URI，否则 null
graph::callee(n: Node): Graph?                     // FUNC 的被调图
graph::type_name(n: Node): string                  // 用源码里的类型名
graph::is_pure(n: Node): bool
graph::may_fault(n: Node): bool
graph::const_int(n: Node): int?                    // 常量的值，按类型各一个；不是该类型的常量则为 null
graph::const_float(n: Node): float?
graph::const_string(n: Node): string?
graph::location(n: Node): string                   // 'file:line:column'
```

常量按类型各有一个取值算子，是因为 Camel 没有运行时判断类型的能力（设计原则 5.10）。

**改写算子。** Camel 的值不可变，所以改写不是"改这张图"，而是"给出一组改动，得到一张新图"：

```camel
// 要新建的节点：一棵表达式树
graph::node(n: Node): Term                          // 已有的节点
graph::lit(v: int): Term                            // 常量（各类型各一个）
graph::call(uri: string, args: Term[]): Term        // 一个 OPER
graph::invoke(g: Graph, args: Term[]): Term         // 一个 FUNC

// 改动
graph::replace(n: Node, by: Term): Edit             // n 的所有使用者改读 by；n 不再被用到则删除，顺序约束保留
graph::erase(n: Node): Edit                         // n 没有值的使用者时删除它
graph::retarget(n: Node, g: Graph): Edit            // FUNC 改为调用另一张图

// 提交：整体校验（3.10），通过才得到新图
graph::apply(g: Graph, edits: Edit[]): Graph!
graph::with_graph(p: Program, g: Graph): Program!   // 用新图替换快照里同一个编号的图
```

例一，`x * 1 → x`，用查询与改动直接写：

```camel
import graph

func mul_one(g: Graph): Graph! {
    let hits = [n for n in graph::nodes(g)
                  if graph::oper(n) == ':op/mul_l' && graph::const_int(graph::inputs(n)[1]) == 1]
    return graph::apply(g, hits->map<(n: Node) => graph::replace(n, graph::node(graph::inputs(n)[0]))>)
}
```

（`==` 用在 `string?`、`int?` 上是设计原则第 15 节的未决项之一；按现有规则这里要先 `?? ''`、`?? 0` 拆开。）

**模式规则：用函数的图当模式。** 函数是子图，函数值带着它的图。所以一条改写规则可以写成**两个参数相同的 Camel 函数**：左边的函数体是要找的形状，右边的是换成的形状，形参是模式变量。

```camel
// x * 1 → x
func lhs(x: int): int { return x * 1 }
func rhs(x: int): int { return x }
let mul_one = graph::rule(lhs, rhs)
```

`graph::rule(lhs, rhs)` 读出两张图：`lhs` 的图是 `PORT x`、`DATA 1`、`OPER :op/mul_l`、出口；匹配就是在目标图里找一个 `:op/mul_l` 节点，它的第二个输入是值为 1 的常量，把第一个输入绑定给 `x`；替换是把 `rhs` 的图以这个绑定实例化进来（这里就是 `x` 本身），再把匹配到的节点的使用者接过去。类型由函数签名给出，规则只匹配类型相符的节点，所以对 `float` 要另写一条（或写成泛型函数，每个实例一条规则）。

例二，把 `map` 接 `map` 融合。两个元素函数是模式变量，写成 `with` 形参（它们是"配置这次变换的东西"，设计原则 4.4）：

```camel
with <f: (a: int) => int, g: (b: int) => int>
func map_map(xs: int[]): int[] { return xs->map<f>->map<g> }

with <f: (a: int) => int, g: (b: int) => int>
func map_fused(xs: int[]): int[] { return xs->map<(a: int) => g(f(a))> }

// 附加条件：f 没有效应（否则"先对所有元素做 f，再做 g"与"逐个元素做 f 再做 g"可以被观察到）
let fuse = graph::rule(map_map, map_fused, (m: graph::Match) => graph::is_pure(m['f']))
```

例三，一个遍：对每张图反复应用一组规则直到不变。

```camel
export func simplify(p: Program): Program! {
    return graph::rewrite(p, [mul_one, fuse])       // 内建的驱动：遍历可达的图，匹配、替换、整体校验
}
```

命令行上写 `camel x.cml mypasses::simplify std::fvm`：编译器装载 `mypasses` 模块，在当前快照上调用它导出的 `simplify`，用返回的快照继续流水线；返回错误值时报告为这个遍的失败。

**数据模型为这一层提供的东西**：不可变的快照（一个 `Graph` 值永远是它被取出时的样子）；稳定的图编号（`with_graph` 有明确的含义）；提交时的整体校验（`apply` 要么给出合法的图要么给出错误值，Camel 程序造不出坏图）；每种节点的规范语义（`is_pure`、`may_fault` 有定义）；函数值到图的直接对应（模式规则的基础）。

这一节是方向性的草案：算子的名字与确切签名、泛型规则怎样写、`Match` 的形式，等数据模型落地（第 7 节第 5 步）之后再定稿。

## 7. 迁移计划

每一步能独立合入，合入后全套测试通过。规模是净改动的估计；"验收"是这一步做完后应当看到的数字或行为。

**与 AST/GCT 重构的衔接。** AST/GCT 的重构先行。本计划需要它交付四样东西，请在它的设计里留出：

1. **声明索引**：不看任何函数体就能列出一个模块的顶层声明（种类、限定名、写出来的类型、是否导出）与它的 `import`。三步加载的第一步只读这个。
2. **按声明取 GCT**：一个函数体、一个顶层值的初始化表达式可以单独请求，不必一次建完整个模块。
3. **`import` 不触发被导入模块的编译**：今天在建 GCT 时编译被导入模块（`src/compile/gct/builder.cpp:397-454 # "namespace blocks it is written in; the GIR builder finds them on its"`），要挪到驱动里。
4. **按声明取源码切片与模块内连续的位置编号**：缓存里的泛型模板与位置表靠它。

**步骤。**

第 2 步里与设计不同的地方：

- **形参名留在函数类型里，作为驻留键的一部分。** 设计（3.3、3.8）说签名不含形参名、显示时从端口表取。但今天类型在诊断与图转储里自己打印形参名（`(a: int, b: int) => int`），节点上带的就是这个类型；按设计去掉会改变用户看得到的输出。所以名字以 `SymId` 存在签名里、参与驻留，不参与 `equals`/`assignableFrom`。代价是"类型编号相等 ⇔ 类型相同"只有一个方向：两个只差形参名的函数类型相容、编号不同。把显示改成从端口表取名字之后，这一项可以按设计去掉。
- **前端正在建的函数的签名不驻留**（`OpenFunctionType`）。设计说"先有图、图建完再驻留它的签名"；但建图器用这个签名对象的身份认"同一个函数的前向声明与定义"（`enterScope`、`rejectRedeclaredFunction`），没写返回类型的函数的值在函数体建完之前就已经带着它。这两处查找改成按实体认之前，这里只把可变性收进一个专门的类：一个程序定义的每个函数一个开放签名，其余函数类型一律驻留。
- 符号表与算子表的存储在表自己的、从不释放的块里，没有放进永久空间（算子在模块装载时就登记，那时命令行还没有配置空间上限；也使"永久空间 = 类型"这个度量保持干净）。算子的实现（函数指针）没有进算子表，它按 `Context` 由执行器管理器解析；NodeVM 往冻结图里回写函数指针的做法（附录 B 的 D6）因此原样保留，等第 3 步的 `ExecPlan`。调度器与遍按 URI 查实现、印诊断的地方仍取 URI 文本，这不是"认算子"。`mayFault` 只为实现里完全没有故障路径的内建算子声明了"不故障"（带类型后缀的加、减、大小比较，`and`/`or`/`not`），其余一律是缺省的"可能故障"；没有任何遍读它。
- 驻留之后，`std::opt` 里按类型查重的特化缓存命中得更多，少做了几次重复的特化；特化图名字里的序号（`forward$spec64` → `forward$spec61`）因此在一个程序（`test/cases/modules/nn/residual_mlp.cml`）的化简后转储里变了，图的内容不变。全语料 1,176 个程序不加遍、1,117 个程序 `std::opt::inline` 后的转储与诊断逐字节相同。

**与算子语义协议的衔接（2026-10-15）。** 第 3 步的 3a–3c 之后，[算子语义协议与图事实](../op-semantics/README.cn.md)（设计稿）在本模型上加三样东西：算子表项旁一份带版本的 `OperatorSemantics` 记录与稳定标识 `protocol:name@主.次`（第 9 步的 `OPRS` 节区随之记版本）；每节点一个字节的数值许可列（与位置列平行，全为 0 时不存，随图块进 `.cmc`）；挂在快照上的事实库，印记用第 5 步的 `(GraphId, 修订号)`，第 5 步之前用每个冻结图编码时分配的序号过渡。`LOOP` 的消费接口与 I18–I20 三条不变量也在那份设计稿里，随第 10 步实施。

## 8. 命名空间

### 8.1 现状

"做了一半"的实际情况是：**路径这一半做完了，作用域这一半没做。**

内部形式【读码】：命名空间不是一种对象。AST 建造时维护一个路径栈，把块里声明的函数与类型的名字加上前缀（`src/parse/ast/builder.cpp:219-237、786-815`）；之后各层看到的就是一个带路径的名字 `Tools::inc`。建图器把函数登记在以完整名字为键的作用域里。模块的导出表是一棵按路径分层的名字树（`include/camel/common/ns.h`）；`import m` 登记"本地前缀 `m` → 模块 `m`"的绑定，`using namespace m::Tools` 把匹配前缀的导出名逐个登记为本地名（`src/core/module/module.cpp:157-279 # "if (nsIt != importedNamespaceBindings_.end()) {"`）。名字解析的顺序在 `visitDRefNode`（`builder.cpp:2799-2969`）：局部值与捕获 → 泛型模板 → 带装饰器的函数 → 本模块的函数 → 导入的实体 → 报错。

### 8.2 补全方案

把 3.9.1 的实体标识当作基础：命名空间是实体名字里的路径，下面每一条只规定"源码里的一个名字怎样解析到实体"，图上都没有任何变化。

**N1 块内的非限定查找。** 在 `namespace A { namespace B { … } }` 里写一个不带前缀的名字，依次在 `A::B`、`A`、模块顶层、导入的名字、内建名里找，取第一个找到的层；同一层里的同名函数是一个重载集。

```camel
namespace Models {
    type Box = { x: int }
    func mk(x: int): Box { return { x: x } }      // Box 即 Models::Box
    func twice(b: Box): Box { return mk(b.x * 2) } // mk 即 Models::mk
}
```

这是今天缺的"作用域这一半"里最要紧的一条：没有它，命名空间里的代码每个名字都得写全。建议：做。

**N2 `using namespace` 的范围、对象与冲突。**

- 对象：导入的模块与命名空间，以及本模块的命名空间（第 6 行）。
- 范围：写在哪个块里就在哪个块里生效——模块顶层、`namespace` 块、函数体（第 13 行今天漏到了整个模块）。
- 冲突：`using` 不产生错误；**用到**一个由两条 `using` 带来、无法区分的名字时才是错误 `AmbiguousName`，列出两个来源（第 14 行今天静默取其一）。

```camel
import lib
import lib2
using namespace lib::Tools
using namespace lib2::Tools
println(inc(1))        // 错误：inc 既是 lib::Tools::inc 又是 lib2::Tools::inc，写出限定名
```

建议：三点都做。

**N3 名字的优先级只有一条规则。** 今天有三种不一致的行为（第 15、16 行，以及按名字导入的同名函数合并成重载集）。建议定为：

| 层（从近到远） | 来源 |
|---|---|
| 1 | 当前块与外层块里声明的局部名字 |
| 2 | 所在命名空间及各层外层命名空间、模块顶层声明的名字 |
| 3 | 按名字导入的（`import { f } from m`） |
| 4 | `using namespace` 带来的 |
| 5 | 内建的与 C++ 模块随导入自动带入的算子组 |

取第一个有这个名字的层。同一层里：同名的函数组成重载集，签名相同是错误（第 2、3 层在声明或导入处报，第 4 层在使用处报）；值与函数同名是错误。跨层不合并。算子组（`+` 等）例外，各层合并，因为那是算子重载的本意。

这回答了模块 root 设计稿的 Q11（两个模块导出同名、签名不同的函数）：按名字导入的在同一层，合并成重载集；签名相同才是冲突。请负责人确认（Q7）。

**N4 导入的写法。** 现状与文档相反的那一条需要定：

| 写法 | 今天 | 建议 |
|---|---|---|
| `import m` | 命名空间 `m` | 不变 |
| `import { a, b } from m` | 引入名字 | 不变 |
| `import { a as b } from m` | 语法错误 | 做（设计原则 10.2 已定） |
| `import m as x` | 语法错误 | **做**：给模块起别名，`x::f` |
| `import a from m` | 给模块起别名 `a`（`a::f`） | **改为引入一个名字**，等价于 `import { a } from m`，与语言文档 5.2 一致 |

理由：`import a from m` 读起来是"从 m 里要 a"，文档也这么写；起别名用 `as` 与改名的写法一致。仓库里依赖现有含义的程序【未查】需要随之改写。请负责人确认（Q7）。

**N5 命名空间里的值。**

```camel
namespace Config {
    export let limit = 10
}
func main(): int sync { println(Config::limit); return 0 }
```

值是 root 上的一个节点，实体是 `模块::Config::limit`；与顶层的 `let` 只差名字里的路径。命名空间块不是同步块，块里的 `let` 之间没有顺序（与模块顶层一致）。`var` 可以写，不能导出（已定）。建议：在"导入值"那一步（第 7 节第 7 步）之后做。

**N6 `use` 的去留。** `use inc = lib::Tools::inc` 想做的事有三种现成的写法：`import { inc } from lib::Tools`（若允许从命名空间按名字导入）、N4 的 `as`、`let inc = lib::Tools::inc`（只对单个函数值）。建议：**不实现 `use`，把这个保留字退掉**；同时允许 `import { … } from m::N`（`from` 后面可以是模块里的命名空间）。保留一种写法，与标准库"只保留一种写法"的约定一致。请负责人确认（Q7）。

**N7 模块可以用自己的名字限定自己的东西。** `module shapes` 里写 `shapes::area` 与写 `area` 相同（第 19 行）。用处：与被 `using` 带进来的同名函数区分时有话可说；诊断里显示的全名可以原样粘回源码。建议：做。

**N8 显示。** 图名、端口名、诊断与调试器里一律显示完整的实体名 `模块::路径::名字`，在不引起歧义时省略模块名（第 21 行今天总是不带模块名，两个模块各有一个 `Tools::inc` 时分不清）。

**实施顺序**：N1、N2、N3、N7 只动名字解析，相互独立，可以随时做（各 50–200 行，加上表 8.1 里缺的测试）；N4、N6 动语法；N5 在导入值之后；N8 随实体表（第 6 步）。

### Q1 对外的节点种类清单

图上能出现的节点种类定为这 14 种（3.5）：

```
DATA  PORT  OPER  FUNC  CALL  FILL  ACCS  CAST  COPY  BRCH  JOIN  LOOP  GATE  SYNC
```

三点需要点头：

- (1) **移出 `BIND` 与 `DREF`。** `BIND` 没有任何代码创建；部分应用今天就是闭包（图在 3.6）。`DREF` 是建图器内部"这个名字还没定下来指谁"的占位，不出现在任何建成的图里。
- (2) **高阶算子与 `attempt` 保持为 `OPER`**，在算子表里带一个 `callsGraphs` 标志，不为它们另设节点种类。图上的样子就是今天的样子（3.6 的 `attempt` 与 `map`/`filter`）。


### Q2 分支臂的两种形态都算合法的图

```camel
func abs(x: int): int { return if x < 0 then 0 - x else x }
```

前端给出的是"每条臂一张子图"（3.5 的图）；`std::opt::inline` 之后臂的节点并进外层图，成为 `BRCH` 与 `JOIN` 之间的一段。两种形态今天都存在、都被校验。

- 甲：两种都是模型的一部分。语法到图的映射是子图形态；区域形态是遍的产物，由分支臂不变量约束。
- 乙：只承认子图形态，内联遍不得把臂并进外层图。
- 丙：前端直接产生区域形态，不为臂建子图。

**建议甲。** 乙使每个分支在执行时多两次调用，今天的后端性能建立在内联臂之上；丙使外层图的形状取决于臂里写了什么，违背 1 的判据，也使 `&&`/`||`、`??`、收窄这些"右边只在需要时求值"的构造失去统一的说法。甲的代价——全部图里 37% 是中位 2 个节点的臂图——由"让图变便宜"解决（第 4 节），而不是由改变映射解决。

### Q3 `LOOP` 的三个细节

循环设计稿留下、本稿需要定下才能写卡片的三点：

```camel
let total = loop acc = 0 for x in xs { acc + x }
let found = loop hit = -1 for x in xs while hit < 0 { if x > 9 then x else hit }
```

- (1) **条件图与循环体图共用一份捕获表**（`LOOP` 的 `With` 输入），各自有同样的捕获端口，用不到的端口闲置。候选：各有各的捕获表。建议共用：读图的人只看一处就知道循环依赖哪些外部值。
- (2) **`for … while` 是同一种节点的第三个 `kind`（`ForWhile`）**，不是 `For` 套一个分支。建议如此：提前结束是循环头的一部分（3.10：不加 `break`）。
- (3) **多个状态时，循环体返回一个元组**，`LOOP` 的值也是这个元组，外面用 `ACCS` 取。候选：让 `LOOP` 成为唯一有多个输出的节点。建议元组：保持"每个节点至多一个值"。

### Q4 接口指纹里放什么

```camel
// lib.cml                                    // main.cml
module lib                                    import { area } from lib
let scale = 2.0                               func main(): int sync { println(area(3.0)); return 0 }
export func area(r: float): float {
    return 3.14159 * r * r          // (A)
    // return 3.14159 * r * r * scale   (B)
}
```

`lib` 从 (A) 改成 (B)：`area` 开始使用模块顶层的 `scale`。图上 `area` 多了一个绑定到 `lib::scale` 的捕获端口，`main` 里调用它的 `FUNC` 节点要多一条 `With` 边，`main` 自己也要多一个端口。所以 `main.cml` 的缓存必须失效。

本稿把下列事实都算进接口指纹（3.9.3）：导出函数的签名（含推断出的返回类型）、它传递捕获的模块级值、它的效应摘要；泛型函数的函数体。

- 甲：如上。改函数体而这些事实不变，导入方的缓存继续有效。
- 乙：指纹只含写出来的签名；捕获不进指纹，改为每次装载时在链接步对所有图（包括缓存来的）重新接线。缓存的图块不再是"装进来就能用"的。
- 丙：任何源码改动都使所有导入方失效（指纹 = 源文件散列）。

**建议甲。** 乙把一部分分析留到了每次装载，与"缓存要消掉线性的分析开销"的定位相反；丙最简单，但库的一处小改动会重编所有使用者。甲的代价是泛型库（`stdlib/array.cml` 全是泛型函数）的任何函数体改动都使使用者失效——泛型的实例本来就建在使用者的类型上，这避不开。

### Q5 缓存的位置、开关与警告

- (1) **放哪。** 模块查找本来就在每个目录里先找 `名字.cmo`（1.9）。候选：甲，与源文件同目录的 `名字.cmo`；乙，源文件旁的子目录 `__cmo__/名字.cmo`；丙，用户目录下按路径散列的集中缓存。**建议乙。** 甲最贴合"占用就占用了，读文件头区分"，但同一目录里若既有 `x.cml` 又有 C++ 模块 `x.cmo`，今天的规则是后者胜出，缓存没有地方写；乙没有这个问题，源码目录里也只多一个可以整体忽略的子目录。文件头照样按 4.5 区分，放在哪都认。
- (2) **开关。** 候选：默认开；默认关，`--cache` 打开。**建议先默认关**，到 `progen` 的"有缓存 / 无缓存"对照跑稳之后改为默认开。
- (3) **缓存命中的模块，编译期的警告还显示吗。** 候选：不重放（只在真正编译时出现）；存下来每次重放。**建议不重放**，`camel check` 忽略缓存、总是完整检查。
- (4) **只有缓存、没有源文件。** 建议第一版不支持：缓存只是加速，找不到源文件就按"模块不存在"处理。

### Q6 顶层声明与书写顺序无关

```camel
let area = pi * r * r      // 今天：UnresolvedReference 'pi'
let pi = 3.14159
let r = 2.0
```

三步加载（已定要做）之下，这个程序自然可以通过：建 `area` 时先去建 `pi` 与 `r`。函数之间今天已经与书写顺序无关。

- 甲：顶层的 `let`/`var` 与书写顺序无关，只看依赖；成环是 `ModuleValueCycle`。
- 乙：仍要求先声明后使用，三步加载只用于函数与跨模块。

**建议甲**（模块 root 设计稿的 Q10 同此）：root 上节点的先后本来就不由书写顺序决定，程序表达的是依赖。函数体里的局部 `let` 不在此列，仍是先声明后使用。

### Q8 Camel 一侧图 API 的方向

5.2 的三个决定需要负责人认可方向，细节以后再定：

- (1) **图与节点是不可变的值**，遍是 `(Program) => Program!`；
- (2) **改写是"一组改动 → `apply` → 新图或错误值"**，不提供就地修改；
- (3) **模式规则写成一对参数相同的函数**，左边函数的图是模式，右边的是替换，形参是模式变量：

```camel
func lhs(x: int): int { return x * 1 }
func rhs(x: int): int { return x }
let mul_one = graph::rule(lhs, rhs)
```

**建议三点都采纳。** (3) 是图原生的直接用法：规则不需要另一套描述图的小语言，Camel 的函数就是图。它的限制是每条规则只对一组具体类型成立（`:op/mul_l` 只是 `int` 的乘法），多种类型要写成泛型函数。

### Q9 设计原则第 15 节里与图相关的未决项：本稿的建议

- **模块 root 合并的具体做法**：3.9 与 4.8。合并的是各模块的顶层节点段；函数各是各的图。
- **副作用追踪在各个遍之下如何保持**：把今天建图器私有的两份摘要（图的出口是否依赖效应、图写了哪些捕获的变量）变成图上的效应摘要，提交时由节点重新算出并校验（I14）。遍不负责"保持"它，只是不可能提交一张摘要与内容不符的图；遍把效应删掉或挪动是否正确仍由遍自己负责（设计原则第 9 节）。
- **带 `var` 上下文参数的函数能否部分应用**（`partial-application-var`）：图上没有困难——`add<t>` 是一个捕获了 `t` 的单元的 `Forwarder` 图，它的效应摘要里"写了捕获的变量"一位为真，它的函数类型带 `sync`。建议允许，并要求得到的函数值的类型带 `sync`，使每次调用被记为对 `t` 的一次写入。
- **`!=` 用在单独的 `T?` 上**：收窄规则使 `x != null` 成为合法的写法，但它只在"直接作为 `if` 的条件"时有定义；`let b = x != null` 仍需要一个答案。建议 `x != null` 与 `x == null` 在任何位置都有定义（就是 `:op/tag_is_null` 及其取反），其余 `T?` 之间的比较保持为错误。

### Q11 `v as T` 的目标类型与 `v` 的类型相同时是否合法（实施第 2 步时发现）

```camel
let xs = [1, 2]
let ys = xs as int[]        // 今天：DynamicCastForbidden: Dynamic cast from 'int[]' to 'int[]' is not allowed
let t  = (1, 2)
let u  = t as (int, int)    // 今天：同上，'(int, int)' to '(int, int)'
```

【实测 2026-10-13】。而 `type A = int[]` 之后对形参 `p: A` 写 `p as A` 可以通过【实测】。原因在实现：数组与元组类型的转换规则只认"同一个类型对象"，而每写一次 `int[]` 就是一个新对象。这不是哪条裁定规定的行为，但它是今天可观察的行为。

它挡住了第 2 步里最直接的一块：把程序能写出来的数组、元组类型也驻留。驻留之后上面两行会通过编译（转换什么也不做）。

候选：(a) 相同类型之间的 `as` 合法，是空操作；(b) 保持是错误，但改成按结构判断并给出"转换到自身"的专门诊断；(c) 维持现状。
**建议：(a)。** 选 (a) 或 (b) 之后数组与元组类型即可驻留；选 (c) 则这两类类型只能继续每次新建。

**已按 (a) 实施**（第 2 步）：数组、元组、结构体到自身类型的转换按结构判断，什么也不做；上面两行、`s as S`（`s: S`）与 `[4, 5] as int[]` 都通过，在四个后端上输出相同【实测】；数组与元组类型随之驻留。

## 10. 最不放心的地方

1. **类型驻留（第 2 步）是整个计划里最容易低估的一步。** 类型对象今天是可变的（返回类型后填、捕获名追加），代码里处处按指针比较类型，C++ 模块还能注册自己的类型与类型规则。驻留要求"建好之后不再变"，这会碰到泛型里尚未解析的类型变量、形状待定的张量类型、递归的结构体类型。本稿只给出了目标，没有逐类核对每种类型能不能做成不可变的。如果这一步做不干净，退路是先只驻留"已经完全解析的"类型，其余仍按指针，收益打折但其他各步不受影响。

2. **捕获接线挪到链接步，改变了建图器里最脆弱的那段逻辑的时序。** 今天函数的端口在它第一次被调用时就定了，之后的代码（包括 `wait` 的写入追踪、"效应不会执行"的警告、同步块的控制链）都在一张"端口已经齐了"的图上工作。挪到链接步之后，第二步建图时函数的捕获端口还不全。写入追踪依赖"这个函数写了哪些捕获的变量"，它同样要变成链接步的不动点；这在 3.9.4 里只用一句话带过，实际要把 `recordWrite`/`capturedWritesOf` 那套机制一起搬。这是第 8 步标"高"的原因。

3. **接口指纹的完备性无法靠审查保证。** 指纹漏掉任何一个"导入方实际依赖的事实"，结果就是静默地用了过期的缓存——最坏的一类错误。本稿列出的事实清单（3.9.3）是从现有建图器读出来的，但像"算子的类型规则读了被导入模块里某个常量的值"（张量形状的折叠）这样的依赖，可能绕过实体表。防线只能是测试：`progen` 的"有缓存 / 无缓存"对照，以及在调试构建里对每个缓存命中的模块抽样重新编译并比对图块。

4. **图引用表与稳定的 `GraphId` 给内联与特化带来的换算，没有做过原型。** 把被调图的节点拷进调用方时，负载里的引用表下标、常量池下标都是被调图自己的，要逐个换成调用方的。道理简单，但今天这些地方存的是指针，拷贝是原样复制；改成下标后每个拷贝节点的地方都多一步，漏一处就是引用错了图——而且因为下标总是"在范围内"，校验 I1 拦不住，要靠 I13（实参数与端口数相符）与类型级的 I10 兜底。

5. **`ExecPlan` 共用之后，四个后端对"执行序"的隐含假设会第一次被摆到一起。** 它们今天都从同一个函数取序，但各自在后面做了不同的加工（NodeVM 的臂入口表、FastVM 的跳转回填、任务流的分组）。收成一份的过程中很可能发现它们对同一张图的理解在边角上并不一致。这是好事，但会让第 3 步比估计的长。

6. **Camel 一侧的 API（5.2）是全稿里论证最薄的一节。** "用函数的图当模式"在例子上很顺，但没有碰过真正的难处：带控制边的模式、分支与循环作为模式、匹配到的节点还有别的使用者时怎么办、规则之间的终止性。它是方向，不是设计。

7. **缓存的收益没有量过。** 1.10 量出了"建图 + 编码占启动后分配的七成"，但没有把"解析 + 分析一个被导入模块"的用时从总用时里分离出来，也没有模拟过装载的用时。第 9 步的第一件事应当是用一个只做 4.8 第 1–5 小步的原型量出这个比值，再决定格式的细节值不值得做到本稿这么细。
