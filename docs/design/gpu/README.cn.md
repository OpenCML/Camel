## 1. 现状（2026-10-21 读 `modules/tiles`）

**做得扎实的**：数值正确性（逐位与 ulp 的差分测试、规范 NaN、负零、f64 累加的确定性归约）、生命周期与所有权（不跨 CUDA 工作持 GC 指针、固定内存的传输次序）、区域提取（`tiles::compile` 提取纯的、依赖凸的、受支持的区域，插入驻留输入与主机读取）、索引映射（转置、置换、切片、变形与逐元素的融合）、行内多归约（softmax、小 layernorm）、编译后的源码缓存。

**与外部报告对得上的缺口**：

| 缺口 | 现状 | 后果 |
|---|---|---|
| 支持面窄 | 只有 f32、连续张量；矩阵乘只有二阶、16×16 共享内存块、f32 FMA；没有 bf16/f16、没有 Tensor Core、没有批量矩阵乘、没有 gather/scatter；分支只在编译期常量时可选，循环只支持逐元素体，`while` 不支持；求导只覆盖部分规则 | 训练步中大量算子（bf16 GEMM、注意力的形状操作、embedding、反向）落回 CPU |
| 回退是静默的 | 不支持算子的节点"留在 CPU 上正常执行"；`#gpu` 范围内已改为编译期错误（H218），范围之外仍留在主机 | 用户以为在 GPU 上，GPU 利用率 0–10% |
| 同步 | 公共调用在返回前等待完成；每次调用上传新的主机输入 | 每次下放都付一次往返与同步 |
| 驻留是 Tiles 私有的 | 驻留张量存在 Tiles 自己的存储里，不是 Camel 的值 | 区域之间可以驻留，跨调用、跨循环轮次的权重仍回到主机 |
| 数值过于保守 | 不使用重结合（求和串行、f64 累加），不做 fast-math | 设计原则 7.3 默认授予 `reassociate` 与 `contract`，Tiles 没有用上 |
| 显存池小 | 设备 64 MiB / 32 项 | 训练规模下频繁直接分配 |
| 图形式过时 | 读子图形式的分支与循环 | 区域（2026-10-21）之后需要改为读图内区域 |

## 2. 放置：用户声明意图（设计原则 13.4）

- `#gpu`、`#cpu` 写在函数、块或模块上；范围内的计算（含它调用的函数、它的梯度、优化器）面向加速器编译。卡的选择通常在运行时（`--devices`）；需要时源码可以写具体设备。
- **数据的驻留、搬运与同步由编译器从图上推出**：一个值的生产者与所有使用者都在 GPU 上，它就留在显存；从主机流入的值在边界上传；主机观察时（打印、`download`、转为主机标量、写文件）下载。循环状态两端都在 GPU 上时整个循环期间常驻（权重、优化器状态、EMA）。
- 剖析报告列出每个边界传输与同步点（第 5.6 节），用户看得见搬运发生在哪里。

## 3. 统一：GPU 上的数组就是 Camel 的数组值

数据块（设计原则 10.5）已经带设备字段。**设备上的张量就是数据块在设备上的数组值**，不再是 Tiles 私有的驻留存储：

- 一个值在哪个设备上，是它的数据块的属性；同一个程序里主机与设备的值用同一种类型（`f32[n, m]`）。
- 引用计数、原地写（计数为 1）、DLPack（设备字段，与 PyTorch 的 CUDA 张量零拷贝交换）对设备上的块同样成立。
- 主机读设备上的块时下载（并在剖析中记为一次同步）。

## 4. 执行模型：整段编译、异步、缓存

- **整段编译**：`#gpu` 范围的图整体交给 Tiles 编译，一次编译、按形状签名缓存，之后每次调用只是提交（相当于 CUDA Graph，不需要事后捕获）。
- **异步**：提交 GPU 工作后立即返回，结果是"设备上的值"；只有主机观察时才同步。这与按依赖求值一致，语义不变。
- **编译缓存跨运行**：编译产物按内容哈希存到磁盘缓存，第二次运行不再编译（外部报告的启动 73 s）。
- **显存池**按工作集自适应，不是固定的 64 MiB。

## 5. 性能所需的能力（按训练常用的顺序）

1. **支持面**：bf16/f16（在 `change_precision` 许可下）与 Tensor Core 矩阵乘、批量矩阵乘、`take` 与散射加、注意力常用的形状操作、softmax/layernorm/rmsnorm、键式随机数（dropout）、`where`、比较与选择、整数下标运算；循环与分支在设备上执行（图内区域，已有统一表示）。
2. **使用已授予的许可**：`reassociate`、`contract` 默认授予（7.3），Tiles 据此用并行树归约与 FMA；`#strict` 时退回现在的精确算法。
3. **融合**：逐元素链、规范化与广播乘、注意力的 QKV/reshape/permute、矩阵乘的前后处理；能写成规则的写成规则（规则引擎），调度由 Tiles 负责。
4. **优化器的多张量融合**：对整棵参数树的一次 Adam/EMA 更新编译为少量 kernel，不是每个叶子各几个。
5. **CPU 路径**：没有 GPU 或刻意留在 CPU 上的计算——逐元素融合、计数为 1 原地写（H17 P6）、默认多线程。
6. **剖析**：`std::profile`（或流水线参数）报告每个算子的设备与时间、kernel 个数、主机设备传输的次数与字节、同步点、编译时间按阶段；对"主机上对张量逐元素循环"给出提示。
7. **多卡**：`#shard` 加 `--devices`，数据并行的梯度归约（NCCL）——在单卡达标之后。

**验收基准**：外部报告的扩散模型训练步、C2（MLP）、一个小型 Transformer 训练步，在 3090 上与 PyTorch（同精度设置）对照；外部报告的依赖链微基准进入性能基线。

## 6. 已定的问题（2026-10-21，语言作者同意；H218 执行）

1. **`#gpu` 范围里遇到不支持的算子**：**编译期报错并指出算子与范围**（`RuntimeDiag::GpuScopeUnsupported`），不警告、不回退。静默回退正是外部报告里 GPU 利用率 0–10% 的原因；需要刻意留在主机上的部分由编译器的区域分析排除（范围之外），调试时 `--devices cpu` 整体跑在 CPU。
2. **设备上的数组就是普通的数组值**（第 3 节），取代 Tiles 私有的驻留存储。
3. **`@gpu` 装饰器与 `run`、`run_device` 删除**（不考虑兼容）：放置只写 `#gpu`，设备由 `--devices` 在执行时选择；不再有"在源码里调用一次设备执行"的算子。`run_preferred_resident` 保留为 `tiles::compile` 与测试使用的内部入口（可回退），范围之外的行为不变。

## 7. 实施顺序（交给施工方，先交计划）

1. **G0** 剖析工具与基准：先能看见（外部报告的微基准、C2、一个 Transformer 步进入基线）。
2. **G1** `#gpu`/`#cpu` 标签、`--devices`、不支持算子的诊断；Tiles 改读图内区域。已落地：`--devices`（H105，2026-10-22，点名的设备缺失时报 `DeviceUnavailable`）；`#gpu` 标签与"范围内不支持的算子是编译期错误"（H218，2026-10-22，`tiles::compile` 读标签、报 `GpuScopeUnsupported` 并指出范围与算子）。仍未做：`#cpu` 标签、驻留推导、Tiles 读图内区域。
3. **G2** 设备上的数据块与数组值、驻留推导、主机观察时的下载、异步提交。
4. **G3** 整段编译与缓存（内存中与磁盘）、自适应显存池。
5. **G4** 支持面：bf16/Tensor Core、批量矩阵乘、`take`/散射加、规范化、随机数、设备上的分支与循环。
6. **G5** 使用已授予的许可（并行归约、FMA）、融合、优化器多张量融合。
7. **G6** CPU 路径提速与编译启动提速。
8. **G7** 多卡数据并行。

每一步以基准对照验收；数值正确性的差分测试（Tiles 现有的逐位与 ulp 体系）保持。
