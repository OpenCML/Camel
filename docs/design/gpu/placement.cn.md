# 放置解析

状态：已实现（`modules/tiles/src/placement.cpp`）。本文记录 `docs/design/gpu/plan.cn.md` §2.2 的查询，以及 S2 留给 S3 的三个决定。查询只回答放置；选择执行器是后续步骤。

## 查询

```cpp
PlacementDecision placementOf(const runtime::GCGraph &graph, runtime::gc_node_ref_t node);
```

`PlacementDecision` 给出 `Placement`（`Host` / `Gpu` / `GpuRequired`）、事实来源（节点、区域、函数体、无）、事实原文（`"gpu"` / `"cpu"`）和区域 id。解析顺序：

1. 节点自己的 `tiles.placement`；
2. 节点所在区域链上最近的一个有该事实的区域（带标签的块、Arm、LoopBody）；
3. 函数体（region 0）的事实；
4. 什么都没有：主机。

`#cpu` 与未知值都回答 `Host`；`#cpu` 的事实仍然出现在报告里。`GpuRequired` 表示函数体本身写了 `#gpu`：这个图作为一个单元在设备上，调用者不能把它当作主机函数。`Gpu` 表示节点或嵌套区域写了 `#gpu`，而这个图的函数体没有：这段代码在设备上，但图的整体放置仍是主机。两者都表示设备；区分只记录"哪一层要求的"，使后续的编译单元与拒绝逻辑不必再走一遍区域链。

`tiles::compile` 在改写前打印 `TILES_PLACEMENT`，每个图一行 JSON（函数体答案、各放置的节点数、带事实的区域及其节点数）。程序里没有任何放置事实时不打印，未打标签的程序输出不变。这个遍仍然不按答案选择执行器；拒绝与段编译在 S4 及之后。`placementOf` 也不跨调用传播：一个没有标签的被调函数自己回答 `Host`，调用点的设备性属于后续的编译单元规则。

## S2 留给 S3 的三个决定

### 1. 全节点盖章，而不是只给可执行节点盖章

决定：保留 S2 的全节点盖章。`placementOf` 对任何节点都先读它自己的属性，属性缺失时才走区域链。

理由：改写会把节点搬出原来的块（内联、区域抽取），属性跟着节点走，区域不一定跟；先读节点属性，搬动之后放置不变。若改成只给可执行节点盖章，端口、常量与合成节点就没有放置事实，区域链成为唯一来源，块区域一旦被改写合并，这些节点会静默改变放置；"一个节点恰好一个放置"也不再成立。

反过来的后果：需要给区域链补一套"节点种类到是否可执行"的例外，并且每个改写都要证明它保留了区域身份。

### 2. `#gpu`/`#cpu` 是核心标签，不是 Tiles 的模块标签

决定：保留 S2 在 `src/core/tags.cpp` 的声明。两者写同一个键 `tiles.placement`，`read_by` 只把 `tiles::compile` 记为读者。

理由：设计原则 6.2 把标准标签定为语言自己的名字，13.4 把 `#gpu`/`#cpu` 定为放置标签；标签的可用性不能取决于程序是否导入了 Tiles，`camel inspect --tags` 也不该为了看见它而加载一个模块。键必须在任何 Tiles 图存在之前登记，核心是唯一满足这一点的位置。

反过来的后果：不导入 `tiles` 的程序会把 `#gpu` 当成未声明的标签；同一个拼写可以由不同模块登记成不同的键，"一个键"就不再是全局不变式；核心的图编码与哈希看到的是一个未登记的键。

### 3. 普通 `std::gir` 显示块的事实，但不画块簇

决定：普通 `std::gir` 为每个带事实的区域打印一行 `region #N <kind> parent=<id> attrs="..."`；簇仍只由 `std::gir_regions` 画。`std::jgir` 的 `regions` 一直带属性。

理由：复核的第 4 条要求区域属性与节点属性出现在 `std::gir`/`std::jgir` 里。事实是图内容，簇是布局；把簇塞进紧凑视图会改动所有已有区域图的 golden，并把审查用的视图变成布局视图。打印一行事实同时满足可见性与"紧凑视图不画布局"。

反过来的后果：普通 `std::gir` 看不到块区域的放置，只能从节点属性反推；"驻留由图推出"在审查与 golden 里就无法检查，复核第 4 条落空。若改成在普通视图画簇，则所有含区域的既有 golden 都要重写，且 `std::gir` 与 `std::gir_regions` 的区别消失。
