# 状态、闭包与内存：可变单元活不过它的那次调用

> **设计稿（2026-11-14）**：负责人认同方向（"如果真的能大幅简化，牺牲仅仅是一个命令式的写法习惯，那对我们来说是非常大的好事"），本稿待负责人审定。审定之前，原则与施工不按本稿改。

## 1. 为什么

近两天理论侧查出的问题，约一半落在闭包与可变状态的交界上：闭包逃逸、效应遮蔽怎么判、"握着单元而类型不提"、逃出遮蔽范围的夹带、规则丢掉闭包后最终写入的去留。根子是：效应规则（排序、遮蔽、哪些写必须执行）都建立在"静态地知道谁能碰到哪个变量"上，而按引用捕获、又能离开函数的闭包，让"一个变量活多久、谁能碰到它"从写法上看不出来。

Camel 的最高倾向是：计算是数据流，值是值；`var` 只是为方便留的口子（原则 3.5）；图是值，可以被变换（求导、导出、批处理、缓存）；默认并行、结果确定；上下文在运行时注入，而不是写死在代码里（技术总览的设计哲学第 6 条）。全局可变变量与"带私有可变状态的闭包"与这些都相冲突。

而真正写出来的代码已经不用它们：标准库、示例、展示程序、基准测试里模块顶层的 `var` 一个都没有，仅有的 45 处都在测这个功能本身的用例里（35 个文件）；标准库用循环携带状态的写法（`loop acc = … for x in xs do …`）有 28 处。

## 2. 三条规则

**规则一：状态作为值流动。** 这是首选写法：循环携带状态、函数接收旧状态并返回新状态、`with` 上下文参数在调用处注入。第 4 节列出常见需求的标准写法。

**规则二：可变单元活不过声明它的那次调用。**
- `var` 局部变量活在声明它的那次调用里；`var` 形参是调用者的局部变量，在这次调用期间借给被调者。
- 闭包可以按引用捕获 `var`，**当且仅当它不离开声明这个变量的那次调用**。离开有三条路：作为结果交出去；写进不属于这次调用的地方；交给会把它存起来的函数。判定由唯一的效应分析做（`docs/design/effects/analysis.cn.md`），依据是原则 3.3"握着什么，类型就提到什么"：一个类型里提到这个变量的值走了三条路中的任何一条，就是离开。
- 离开的闭包捕获了 `var`，是编译错误。诊断给两种改法：捕获它当时的值（`let x = c; () => x`），或把状态作为返回值交出去。**不隐式改成按值捕获**：那会悄悄改变语义。
- 交给 `foreach`、循环这类只在调用期间使用闭包的函数是允许的：它们的足迹表明不把参数存起来。

**规则三：模块顶层没有 `var`。** 模块顶层只有 `let`：常量、函数、类型。需要跨调用累积的状态，按规则一传递；配置与上下文用 `with` 注入。

## 3. 对效应系统的影响

可变单元从不比声明它的那次调用活得长，于是：
- **效应遮蔽恒成立**：函数自己的局部变量永远不会被外面碰到。"遮蔽怎么判""逃逸走哪几条路"不再是语义问题，只剩规则二那一处编译期检查。
- **"活得比函数长的变量"只剩 `var` 形参**：对它的最终一次写由出口用到（原则 3.1），其他变量的写都是函数内部的事。
- **模块变量那一整套**（原则 3.5"模块顶层的 `var`"一段、它与捕获的关系）删除。
- **原则 3.3"握着什么，类型就提到什么"保留**，但只在一次调用之内起作用：它是规则二检查的依据。
- **区域的根**（原则 3.1）= 出口 + 对外部资源的写 + 对 `var` 形参的最终写入。
- **其余不变**：读是依赖、写是效应、外部资源分读写、`pure` 就是没有写入、冲突的定义、`var` 形参的别名特化（原则 3.5）、`map` 要求 `pure`、故障沿依赖传播。
- ECOOP 汇总的七项里，第 4、5、6 项（规则丢闭包后的最终写入、经内层闭包藏单元、逆变位置的遮蔽）在这个设计下不再出现；演算的不变式简化为"单元不离开它的调用"。

## 4. 常见需求的标准写法

| 需求 | 写法 | 先例 |
|---|---|---|
| 计数、累加 | `loop n = 0 for x in xs do if p(x) then n + 1 else n` | fold |
| 训练循环 | `loop state = init for batch in data do step(state, batch)`，`step` 是纯函数，返回新的参数与优化器状态 | JAX、optax |
| 随机数 | 显式的随机数种子，按需拆分，作为值传递 | JAX 的 PRNG key |
| 日志、指标 | 写外部资源（打印、文件），或由生成器逐个交出 | 流 |
| 缓存、记忆化 | 库里的函数变换 `memo(f)`，缓存由运行时管理；键里含读到的外部资源的状态（原则 3.3 的约定） | 图上的变换 |
| 配置、共享上下文 | `with` 上下文参数，调用处注入 | Camel 已有 |
| 交互程序、事件处理 | 状态对事件流做折叠：`update(state, event) -> state`，界面由状态算出 | Elm 架构、Redux |
| 函数内部的命令式写法 | 局部 `var` 照常用；编译器把它化成 SSA（原则 3.5） | — |

**提供一个显式的可变单元 `Cell<T>`，作为出口。** 上表写不出的情形确实存在：外部框架掌控事件循环、回调之间要共享状态（GUI、服务器、Python 库回调 Camel 函数）；带回指针的可变结构。`Cell<T>` 是句柄类型（原则 3.3，每个值一个资源）：在入口或调用者那里创建，显式作为参数或 `with` 传递，`get` 读、`set`/`update` 写，对同一个单元的访问按书写顺序。它与全局变量的区别是出现在参数与类型里，不是藏在外面的环境状态，所以图仍然自足，规则一到三照样成立；离开调用的闭包可以捕获单元句柄（句柄是值），不能捕获 `var`。**单元的内容里不能再有单元**（先严后松）：这样不会成环，程序的值仍只靠计数回收（第 5 节）；出现确实需要的程序再放宽，那时单元之间的环交给垃圾回收。

## 5. 内存管理

原则 10.5 的三层不变，各层的职责因此变得清楚：

1. **编译期规划**：`var` 单元永远不离开它的调用，可以放在调用帧里，由编译期规划分配与释放，**不进垃圾回收堆**。按引用捕获它的闭包也活不过这次调用，持有的是帧里的位置。
2. **带计数的值**：不可变的值（数组、结构体、闭包）用引用计数，计数为 1 时"返回新值"的操作原地进行（原则 10.5 已有的 Perceus 做法）。状态作为值传递时，旧状态在最后一次使用后计数归一，新状态原地写出，**性能与直接修改相同**。这是"函数式写法不付代价"的保证，Koka（Perceus）与 Lean 4（functional but in place）已证明它在实践中成立。
3. **垃圾回收堆**：只剩图、快照，以及可能成环的结构。没有可变单元逃逸，不可变的值之间不会成环（成环需要事后修改或惰性的自引用；递归函数是图引用自己，不是值的环）。所以程序的值都可以只靠计数回收，回收时机确定，张量在最后一次使用后立即释放；垃圾回收只管编译器一侧的对象。"不可变的值不会成环"要在实现上核实一次（递归的 lambda、`with` 绑定的函数值）。

## 6. 改动清单

**原则**：
- 3.3"握着什么，类型就提到什么"一条注明只在一次调用之内；
- 3.5 删除"模块顶层的 `var`"一段，"闭包对变量的捕获也是引用"改为规则二；
- 3.1 区域的根改为第 3 节的写法；
- 10.5 写进第 5 节；
- 新增规则一、三与第 4 节的标准写法（放进教程，原则只留规则）。

**实现**（并进第十一节第 3 路 R3）：
- 规则二的编译期检查由唯一效应分析做；建图器里的保守遮蔽判法与建图器、运行时之间的桥接删除；
- 模块顶层 `var` 改为编译错误，诊断指向第 4 节的写法；
- `var` 单元改为帧内分配（第 4 路执行语义与内存规划，排在 R3 之后）；
- 核实不可变值不成环，之后把程序值移出垃圾回收堆（排在收敛阶段）。

**测试**：35 个测模块顶层 `var` 的用例改写或删除；测"工厂函数返回带私有状态的闭包"的用例改为编译错误的用例。

## 7. 代价，以及主流语言为什么不这样做

负责人问：代价真的只有写法习惯吗？如果是，为什么传统语言不这样设计？答：不止。面向并行、变换与可靠性的语言大多这样限制（Rust：借用局部的闭包不能逃出、全局可变要显式的锁；Haskell：`runST` 封住局部状态；JAX、Futhark：被编译的函数必须纯；Elm：没有可变状态；Clojure：值不可变），而且**每一家都留了显式的可变单元作出口**（`Rc<RefCell>`、`IORef`、`atom`）。通用命令式语言不这样做，是因为下面这些代价：

1. **状态要层层手传**：许多地方共用的日志器、连接池、缓存，要一路传下去，改了还要带回来。`with` 解决读的一半，带回来的一半要写出来。
2. **回调与外部框架**：外部掌控事件循环时，回调之间需要长期存在的可变状态。Elm 式折叠只在 Camel 自己掌控循环时可用。这是要提供 `Cell<T>` 的理由。
3. **带环、带共享的可变数据结构**（并查集、带回指针的图）：不可变的值不成环，要改写成"数组加下标"的形式，或者用单元。
4. **性能悬崖**：计数为 1 才原地更新；不小心多留了一份旧状态，每次更新就悄悄变成整份复制。要有工具：编译器在可能退化为复制的地方给出提示，`inspect` 能列出每次复制的原因。
5. **保守判定的误拒**：闭包经函数值交给不知底细的函数时，只能当作会被存起来而报错。诊断要给出改法（捕获值、改传单元）。
6. **用户写不了自己的缓存**：记忆化靠运行时的 `memo` 变换；要自定义策略，就把缓存放进单元。
7. **生态与上手**：从 Python 移植的代码、习惯命令式的用户要换思路；不再能写"工厂函数返回带私有可变状态的闭包"、全局计数器、全局缓存。

Camel 的定位（图原生，面向并行、变换、确定性）落在 Rust、JAX、Haskell 这一侧，这些代价是同类语言都接受的；出口（`Cell<T>`）、性能提示与清楚的诊断，是把代价压低的三件事。
