# 原生多维数组、内存管理与互操作（设计稿）

> 2026-10-21 更新：通用机制已落到核心内存层（`mm::Block`、`mm::blockSpace()`、`std::mem::blocks()`），判据是类型系统的**纯数据**（不含引用：数字、布尔、复数、只由它们组成的结构体与元组）。数组只是它的一个使用者，`Bytes` 是另一个；长字符串、表列、内存映射与设备内存后续接入。

状态：方向已由语言作者确认（2026-10-20），细节待实施前逐条确认（第 8 节）。与 [图存储与图 API（第二版）](../graph-store/README.cn.md) 一起构成下一轮重构的地基；总览见 [重构总纲](../blueprint/README.cn.md)。

---

## 1. 为什么要做

- **张量在核心之外**：今天的张量是 `tensor` 模块（C++）提供的类型，形状检查写在模块的类型解析器里。若为它在核心语法里加简写，就是核心为模块开特例；而"类型里带大小的多维数组"本是数值计算的通用需求（图形中的定长向量与矩阵、仿真的网格、图像、长度固定的序列、导出所需的静态大小）。
- **避免各领域各造一套**：Python 生态的数组分裂（NumPy、PyTorch、JAX、CuPy 互不兼容，后来补了 DLPack 与 Array API 标准）根源在于语言没有原生的多维数组。Camel 现在定下一个核心数组与一个内存交换约定，各领域建在它上面。
- **内存管理不适合 AI 负载**：张量的数据今天是回收器管理的大对象，训练步里大量完整回收说明了这一点。大量、短命、很大的数据块不适合用追踪式回收管理，而图上本来就知道每个值最后在哪里被用到。
- **互操作**：数组要能与 PyTorch、NumPy、CUDA 库零拷贝交换。

## 2. 原生多维数组

### 2.1 类型

```camel
int[]            // 一维，长度运行时才知道，可以追加；与 int[?] 相同
f32[3]           // 一维，长度为 3
f32[n, 784]      // 二维，n 是维度名
u8[h, w, 3]      // 三维
string[n]        // 元素可以是任何类型
int[][]          // 数组的数组：每行可以长短不一，与多维数组不同
```

- **只有一种多维数组类型** `T[维度...]`：元素类型加形状。"张量"是元素为数值类型的多维数组，`Tensor` 保留为它的别名；长写法 `Tensor<f32, [n, m]>` 去掉 `const`。
- **`f32[m, n]` 而不是 `f32[m][n]`**：后者读作"数组的数组"，而多维数组是一个整体的对象，形状是一个整体（与 NumPy 的 `shape=(m, n)`、Fortran 的 `a(m, n)` 一致）。
- **值语义**：数组是不可变的值；"修改"产生新值，实现上在只有一个引用时原地进行（4.3）。
- **追加只用于长度未知的一维数组**（`T[]`）；对 `T[3]` 追加会改变它的类型，是编译错误。

### 2.2 维度

- **在形参类型里第一次出现、且不是已有名字的维度名，自动绑定**为维度变量（取代 `constas`）；已有的名字（常量）是引用：

  ```camel
  const IN = 784
  func dense(x: f32[b, IN], w: f32[IN, h]): f32[b, h]
  ```

- **只出现一次的维度名给出警告**，提示"如果确实是任意大小，写 `?`"——防止写错名字悄悄放松检查。只出现在返回类型里的名字仍是错误（设计原则 5.4）。
- **`?`**：不需要名字的任意大小（编译期未知，调用处做运行时检查，与 `as` 相同）。
- **`..s`**：任意维数，与泛型的可变元数同一个记号：

  ```camel
  func relu(x: f32[..s]): f32[..s]
  func first_row(x: f32[n, ..rest]): f32[..rest]
  ```

- **线性运算**：`f32[n + 1]`、`f32[2 * n]`，相等可判定；其余结果为未知。
- **维度名只活在类型里**，不能与运行时的变量同名（不做依赖类型）；函数体中取大小用 `shape(x)[0]`。命名维度不产生新的实例（5.4）。
- 元素类型可以是类型变量：函数头声明 `T` 后写 `T[n, m]`。

### 2.3 运算放在哪里

核心只负责类型、形状、下标与切片的语义。逐元素运算、矩阵乘、归约、卷积等仍是库函数（现在的 `tensor` 模块，可以改名），它们的事实（纯度、故障、数值分类、下标映射）是算子声明上的标准标签（设计原则 6.6）。Tiles 编译的对象就是这个原生类型。

### 2.4 元素类型

- 数值元素类型的精确语义写在数值契约（第 7 节）里：整数、`f32`、`f64`、`f16`、`bf16`、复数，以及按需加入的 fp8、int4 等格式。新格式变化很快，集合要能按需扩充：加一种格式就是补一条定义（位宽、编码、舍入、特殊值）。
- 结构体与元组只有在字段全是纯数据时才是纯数据；`T?`、`T!` 与变量单元不是（空值/失败/单元身份在字段表之外），按普通数组存。

## 3. 存储与内存交换约定

### 3.1 两种存储

| 元素 | 存储 |
|---|---|
| 纯数据（数字、布尔、复数、只由它们组成的结构体/元组） | **紧凑的连续数据块**（就是今天张量的数据） |
| 其他类型（字符串、含引用的结构体、`T?`/`T!`、闭包、数组……） | 普通数组：每个元素是一个槽位，可以含引用 |

**红线：紧凑数据块里只放纯数据，不放引用。**（"数据块是叶子"）这是第 4 节的引用计数与第 5 节的零拷贝交换安全的前提：数据块之间不可能成环。由类型系统保证：`type::isPureDataType()` 递归判定并逐类型缓存，`type::arrayStorageFor()` 只看它；没有调用点自己选布局。

结构体/元组的紧凑布局由 `type::pureDataLayout()` 给出：字段按自然对齐依次排列，元素大小为对齐后的总字节数，`fieldOffsets` 记录每个字段的偏移。数组元素按这个布局逐元素存放，所以**结构体数组没有逐元素的 `Struct` 对象**；读取时按布局物化一个 `Struct`/`Tuple` 供字段访问，写入时按字段拆回字节。填充字节在写入前清零，因此两个相等的值字节也相等，紧凑比较可以用 `memcmp`。

### 3.2 运行时表示与 DLPack

纯数据数组在运行时由两部分组成：

- **数据块对象**（`mm::Block`）：数据指针、字节长度、设备、所有者信息、引用计数、释放方式（自己分配的，或外部的带释放回调）。数据**不在可移动的堆里**，交给外部的指针始终有效（设计原则 10.5）。小于 256 字节的数据内联在 `Array`/`Bytes` 对象里，不分配数据块。
- **数组值**：指向数据块的引用，加上元素类型、形状、步长、字节偏移。视图（切片、转置、变形）是共用数据块、形状与步长不同的数组值。

这组字段与 **DLPack** 的 `DLTensor`（数据指针、设备、元素类型、维数、形状、步长、字节偏移）一一对应，因此与 PyTorch、NumPy、JAX、CuPy、CUDA 库之间的交换是零拷贝的。**DLPack 只导出元素是数值标量的数组**：它没有结构体 dtype；结构体数组留给 Arrow 一项。

`Bytes` 是数据块的另一个使用者：小于阈值内联，较大的二进制值放在数据块里；文件读取直接读进数据块，Python `bytes` 以外部数据块借用其缓冲区（不可变，释放回调持有 `PyObject`），不需要中间拷贝。

**布局只到步长为止**：分块、对齐、填充、交错等是调度与后端的选择（13.1），不进入数组的语义与运行时表示。

### 3.3 设备

`Device<T>`（已有）表示值在某个设备上；设备上的数组是设备内存中的数据块，表示同上。搬运是普通的有副作用的操作（3.3、13.3）。

### 3.4 不进核心的：稀疏、量化、分布式、参差、表格

它们在算法上与稠密数组不同，由库定义为**命名类型**，内部由核心数组加元数据组成：

- 稀疏（CSR）：`type Csr<T> = { values: T[], col: int[], row_ptr: int[], shape: (int, int) }`；
- 量化：整数数组加缩放与零点；
- 分布式：每卡一块核心数组加切分描述（与 `#shard` 一致）；
- 表格：由若干列数组组成的结构体。

**防止分裂**：

1. 这些类型内部都用核心数组，互相转换、与稠密数组一起运算有共同的基础；
2. 共同的接口用泛型表达而不是继承：库为自己的类型提供 `to_dense`、`shape` 等函数，泛型代码通过 `match type` 或签名上的 `where` 约束使用（参考 Julia 的 `AbstractArray` 接口）；
3. 交给底层的一律是 3.2 的数据块；
4. 标准库先给出稀疏与量化的标准实现，作为样板。

## 4. 内存管理：三层

设计原则 10.5 不变：内存管理不进入语言的语义，回收的时机不可观察。三层都是实现方式，各管一类东西，互不重叠：

| 层 | 管什么 | 怎么管 |
|---|---|---|
| **1. 编译期规划** | 生命周期能从图上看出来的纯数据块（绝大多数中间结果：激活值、梯度、临时量） | 编译时决定何时分配、何时释放、哪些数据块复用；运行时不需要回收 |
| **2. 引用计数** | 生命周期看不出来的纯数据块（存进数据结构、被闭包捕获、从函数返回、与外部交换） | 最后一个引用消失时立刻释放；**计数为 1 时原地更新** |
| **3. 分代追踪回收** | 其余对象：结构体、闭包、字符串、元素为引用的数组、图与快照 | 现有的分代回收器，不变 |

### 4.1 第 1 层：编译期规划

- 依据图上的使用者索引与区域结构（图存储第二版）算出每个数据块值的最后一次使用；在执行计划中记录"某节点执行后释放哪些数据块"，以及数据块的复用。
- 静态形状已知时，可以给出一个函数的**峰值内存估计**（`camel inspect --memory`，训练设计稿已提到），例如"这一步需要 N GB 显存"。
- 只作用于纯数据块；**不含纯数据数组的程序（如 fib）不插入任何释放动作**，执行路径与今天完全相同。

### 4.2 第 2 层：引用计数

- 只有数据块对象带计数；数组值、视图持有数据块时计数加一。并行执行（`std::prl`、多线程内核）用原子操作。
- 数据块是叶子，不会成环，计数一定能归零。

### 4.3 原地更新是有保证的行为

**计数为 1 时，"返回新值"的数组操作（追加、按下标更新、逐元素运算写回等）原地进行**——这是对用户的性能承诺，不是尽力而为的优化。语义不变（值仍是不可变的，原地发生在没有别人能看到旧值的时候）。`std::cpp` 今天已经这样做（设计原则 10.5）。

### 4.4 第 3 层

现有的分代回收器保持不变，它对小型逻辑计算的优势（如 `std::fvm` 上的递归）原样保留。图与程序快照也由它管理（图存储第二版 4.2）。

## 5. 各后端怎样落地

| 后端 | 第 1 层 | 第 2 层 | 第 3 层 |
|---|---|---|---|
| `std::nvm`（参考解释器） | 执行计划中的释放清单，解释器照着释放 | 数据块对象带计数 | 分代回收 |
| `std::fvm` | 编译字节码时在最后一次使用处插入释放指令 | 增减计数的指令只作用于数据块 | 分代回收 |
| `std::jit` | 同 fvm，由字节码带入 | 机器码内联增减计数 | 分代回收；需补齐栈映射（今天分代模式下编译的图较少） |
| `std::prl` | 每个任务各自的计划 | **原子**计数 | 各工作线程在安全点配合 |
| `std::macro` | 同 nvm | 同 nvm | 同 nvm |
| `std::cpp`（独立 C++） | 最后一次使用处 `std::move`（已在做） | 引用计数（已在做），纯数据块沿用 | 无；经变量单元形成的环不回收（10.5 允许） |
| Tiles（GPU） | 显存按计划分配与释放，内存池作为底层的分配器 | 显存数据块带计数 | — |

第 1、2 层的语义在所有后端相同；`std::cpp` 证明只靠这两层也能工作。

## 6. 跨语言互操作

### 6.1 Camel 调用 Python

- Python 对象仍是外部资源对象，回收时经回调减少 Python 的引用计数（现状不变）。
- **数组零拷贝**：PyTorch、NumPy 的数组经 DLPack 进入时，Camel 建一个引用外部内存的数据块对象，计数归零时调用 DLPack 的释放回调；Camel 的数组交给 Python 时，交出一个 DLPack 胶囊，胶囊被销毁时减少 Camel 一侧的计数。数据块不含引用，这种交换不会形成跨语言的环。

### 6.2 Python 调用 Camel（Camel 作为 Python 包被嵌入）

- Python 持有的 Camel 值登记为回收的根。
- **跨语言的环**（Python 对象持有 Camel 闭包，闭包又捕获了这个 Python 对象）**第一期不回收**，在文档中写明；以后需要时再接入 Python 的循环回收（让 Python 的回收器能遍历 Camel 的对象）。

### 6.3 线程与 GIL

- 在工作线程上调用 Python 前取得 GIL。
- 释放 Python 对象的回调可能出现在回收器的线程上：统一放进一个队列，由持有 GIL 的线程集中执行，回收过程中不等锁。

### 6.4 其他语言与库

C/C++ 库（cuBLAS、cuDNN、原生模块）经 3.2 的数据块交换：拿到的是数据指针与形状步长，所有权留在 Camel；原生模块不得跨调用保存指向 Camel 对象的裸指针（10.5），要长期持有就增加数据块的计数。

## 7. 红线与保证（每条有强制机制）

| 红线 | 强制机制 |
|---|---|
| 紧凑数据块只放纯数据，不放引用 | 类型系统：`isPureDataType()` 判定，结构体/元组按布局逐元素存放 |
| 交给外部的数据指针在所有者释放之前一直有效 | 数据块数据不在可移动的堆里；计数归零才释放 |
| 计数为 1 时原地更新 | 测试：对每种"返回新值"的数组操作，验证计数为 1 时不复制（以分配计数断言） |
| 小型逻辑计算不因新的内存管理变慢；张量程序的时间与峰值内存应当下降 | 每一步重构后重跑性能基线（`docs/performance/graph-store-baseline.md` 的脚本，其中有 `fib.deep`、小对象分配、训练一步） |

## 8. 细节（2026-10-20 已全部按建议确认）

1. 维度绑定的规则（2.2）：已有名字为引用，否则在形参中第一次出现时绑定；只出现一次时警告；`?` 表示不需要名字的任意大小；`..s` 表示任意维数。
2. `Tensor` 保留为长写法 `Tensor<f32, [n, m]>` 的别名；`tensor` 模块不改名。
3. 现有的一维数组 `T[]`（可追加、元素可以是任何类型）与多维数组的迁移：`T[]` 就是 `T[?]`，现有程序的行为不变；需要核对的是现有数组算子（`map`、`filter`、`sort` 等）对多维数组的含义（按第一维）。
4. 复数是核心数值类型 `c64`、`c128`，紧凑存储；虚数字面量用后缀 `i`（设计原则 5.1）。
5. 第 1 层规划在形状未知（`?`）时退化为第 2 层，峰值估计给出上界或"未知"。

## 9. 实施顺序（与图存储第二版交织）

1. **数据块对象与引用计数**（第 2 层），张量改为"数组值 + 数据块"；DLPack 交换改为零拷贝。
2. **原生多维数组类型**：类型规则、维度绑定、形状检查从 `tensor` 模块的解析器移入核心；`T[...]` 语法；`Tensor` 别名。
3. **原地更新的保证**与测试。
4. **第 1 层编译期规划**：依赖图存储第二版的使用者索引与执行计划（第二版第 3、4 步之后）。
5. **各后端**：fvm 的释放指令、jit 的计数与栈映射、prl 的原子计数、`std::cpp` 的纯数据块。
6. **互操作**：Python 嵌入的根登记、GIL 队列。
7. **稀疏、量化的标准库样板**。

每一步：全部测试通过；性能基线对比（第 7 节）。
