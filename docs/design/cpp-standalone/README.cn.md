## 0. 摘要

负责人选了“独立部署”作为 `std::cpp` 的首要目标：生成的代码自带内存模型（乙），运行时的堆加精确根不是主线。本稿给出这条主线的完整做法。

**产物。** `camel x.cml std::cpp` 写出一个 C++20 翻译单元。它只包含 `camel/standalone/runtime.h`——随 Camel 安装在 `$CAMEL_HOME/include` 下、只依赖 C++ 标准库的一组头文件——用任何 C++20 编译器一条命令就能编成可执行文件，**不链接 `libcamel`、不加载 `.cmo`、进程里没有回收器、类型系统和算子表**。程序用到某个没有独立译法的算子（张量、Python、ONNX 等）时，翻译单元另外包含 `camel/standalone/bridge.h` 并要链接 `libcamel`；这个边界只在算子调用的那一条语句里存在，运行时的对象不进入生成的代码（第 9 节）。

**主要的决定**（理由与实测在各节）：

| 问题 | 决定 | 节 |
|---|---|---|
| 标量 | `int64_t`、`int32_t`、`double`、`float`、`bool`、`std::complex<float>`、`std::complex<double>`；加减乘与取负按回绕写成 `rt::add` 等内联函数（C++ 的有符号溢出是未定义行为）；`/`、`%` 带故障位置（复数的 `/` 是 `rt::complexDiv`，复数的零是故障） | 4 |
| 字符串、数组、映射、集合、函数值、变量单元 | 带引用计数的句柄（非原子），C++ 的拷贝构造加一、析构减一，最后一次使用处 `std::move` | 4、5 |
| 元组、结构体、`T?`、`T!`、错误值 | C++ 的值类型（生成的 `struct`、`rt::Opt<T>`、`rt::Fallible<T>`），不上堆；里面的句柄照常计数 | 4 |
| 身份 | 只有 10.5 列明的有身份：变量单元、经 `var` 参数就地修改的对象、外部库包装的对象；其余的值按值语义处理，共享与拷贝由生成的代码自由选择。`append` 等返回新值（11.3），计数为 1 时就地追加只是优化 | 5.2 |
| 回收 | 引用计数，计数为 1 时“返回新值”的算子原地改（不可观察）；经变量单元形成的环不回收（10.5 允许） | 5 |
| 分支 | `if`/`else` 语句（修 D4、D5）；子图形态的臂并入所在函数；内联之后的区域形态同样认（修 D11） | 6 |
| 执行序 | 与 `std::fvm` 用同一个执行序（`buildReachableExecutionTopoIndices`），所以语言没有规定先后的效应，在生成的程序里也与解释器同序 | 6.1 |

| 递归上限 | 与调度器的计数规则相同（每个打开的非尾调用计一次，入口那次不计）；计数作为隐含参数沿调用传递，在调用处检查；默认值取转译时的设置；`main` 跑在一个按上限留足了栈的线程上 | 7.4 |
| 算子 | 一张“URI → 译法”的表：内联的 C++ 表达式、头文件里的函数、或运行时模块（桥） | 8 |
| 测试 | `test/tools/cppexec/`：转译、编译、运行，与 `std::fvm` 比较标准输出与退出码；进默认测试集的是一份精选清单，全语料的对照另跑 | 11 |

## 1. 目标与约束

### 1.1 “脱离运行时”指什么

- **产物**：可执行文件不依赖 `libcamel`，也不在运行时读 Camel 安装里的任何文件（标准库的 `.cmo`、`CAMEL_HOME`）。
- **构建**：需要一个 C++20 编译器和 `camel/standalone/` 这一组头文件。头文件只依赖 C++ 标准库，另外复用 `include/camel/utils/` 里两个本来就只依赖标准库的头文件（`number_text.h`：数与文字之间的规则；`int_div.h`：整数除法的回绕），这样浮点数转文字、整数除法在解释器与生成的程序里是同一份代码。这两个头文件因此必须保持只依赖标准库，文件头的注释里写明。
- **例外**：程序用到没有独立译法的算子时链接 `libcamel`（第 9 节）。转译时给出一条警告，指出是哪个算子、在哪里，使用者知道为什么产物不是独立的。

### 1.2 语义上要守住的

裁定原文要求的三条：故障带源码位置终止、遵守递归上限、尾调用不使栈增长。此外按设计原则的一般要求：

- 按依赖求值：只有活节点（从出口可达）执行（3.1）；同步块与 `wait` 的顺序就是图上的控制边（3.4）。
- 整数加减乘回绕，最小整数除以 -1 回绕（5.1）；除零、越界、转换越界是故障（3.9、5.1）；浮点数转文字只有一种规则（7.7）。
- 只有显式声明了返回类型的 `main` 的返回值才算程序的结果；没有被处理的错误值到达 `main` 的出口打印到标准错误、退出码非零（3.9、9.8）。
- 输出在各平台是相同的字节，Windows 上不写 `\r\n`（11.5）。

### 1.3 可以不同的

- 回收：何时回收、是否回收不可观察（10.5）。生成的程序用引用计数，经变量单元形成的环不回收（5.4）。
- 对象身份：10.5 列明了有身份的东西——变量单元、经 `var` 参数就地修改的对象、外部库包装的对象；其余的值没有可观察的身份，后端可以随意复制或共享（5.2）。
- 并行：`map`、`filter` 的元素之间没有顺序（3.6），生成的程序第一步顺序执行它们（13 的 Q6）。

- 一个类型算不算实现了，不看它在一个后端上跑得通，看它在四个后端上说的是不是同一句话。`std::nvm`、`std::fvm`、`std::jit` 与 `std::cpp` 写出的程序，对同一份输入的标准输出与退出码必须逐字节相同；一条只在一个后端上赢了的用例，是那条路自己的缺陷，不是这个类型的证据（`run.py --four-backends`）。
- 同一输入两种输出，先停止加用例：一条不确定的生成规则，会让以后每一次红都变成“这次运气不好”。转译是一份程序到另一份程序的函数，不是进程的函数——同一条命令对同一份输入连跑二十次，写出的程序必须逐字节相同（`narrow_repeat.py`）；两次不一样，先把它变成可复现、定位到写出它的那一步，再谈别的东西。已经发生过一次：`for i in a..b` 的数组用“装着区间两端”的那个节点的类型来声明，程序里只要有同形状的值（两个整数），那个类型就写成结构体，写出来的是 `const Tuple ..._items = rt::range(...)`，编不过。
- 把“不稳定”压成“稳定地错”是进步；把“稳定地错”修掉再压成“稳定地对”，才算修完。所以那条守卫不只盯当初出错的那个程序：`expect.txt` 里的每一个程序各跑五次，任何一个写出两种写法都报出名字与两个哈希（`narrow_repeat.py --expect=test/tools/cppexec/expect.txt --runs=5`）。缺陷的形状会被下一次改动换掉，只盯着它当初的样子，等于把守门人派去守一扇已经拆掉的门。
- 一条只在一个用例上成立的性质，进闸门时要铺成全部用例；否则它测的是那个用例，不是这个性质。“生成的程序不链 `libcamel`”原来只在一条窄类型用例上钉着，现在对 `expect.txt` 里的每一个程序各查一次链接行与 `ldd`（`run.py --standalone --expect=…`），答案必须是 `test/tools/cppexec/bridged.txt` 那一份名单——**159 个里 158 个不链，1 个仍链**：`re:test`（正则引擎不在头文件里）。**两个方向都查**：多出第三个是红，名单里的某个不再链也是红——只能变长的名单什么也没说。原本在这里的四个都写成了规则、名单因此短了四行（`math:max_l`、`math:sqrt_d`，以及两个张量构建算子 `tensor:zeros`/`tensor:ones`——它们的结果是元素，不是运行时对象，所以不再过桥）：一笔修完就删一行，名单才有读的意义。
- 名单里的每一条都要写明它是“缺口”还是“例外”；写成“已知”两个字的，下一个人既不会修也不会放过。`bridged.txt` 里只剩 `re:test` 一条，带一句“exception, not a gap”——它的答案就是桥，谁去“修”它等于把桥拆了。
- 故障句是语言的一部分；重写一句像样的，比写错一行代码更难查——因为它读起来是对的。`tensor:zeros`/`tensor:ones` 的规则第一版给负长度写的是一句自己的话（`Tensor shape cannot contain negative extents`），量出来 `std::fvm` 印的是内核的 `zeros: Shape cannot contain negative values`，于是程序在它唯一打印的那一行上与解释器不一致。现在 `fault_*` 用例的故障句全部对 `std::fvm` 逐字比较（`run.py --faults`，47 个用例，stdout 与 stderr 合起来比，退出码一起比），仍不一致的两个写在 `test/tools/cppexec/fault_words.txt` 里、都标成缺口，名单两个方向都查。
- 域外与 NaN 的行为，先写一行决定再写代码，而且这一行要与 `std::fvm` 逐字节一致：`sqrt(-1.0)`、`sqrt(-4.0)` 与 `sqrt(nan)` 都答 `nan`（`is_nan` 为真），**不是故障**；`math:sqrt_f`/`math:sqrt_d` 因此写成 `std::sqrt`，用例 `math_sqrt_domain.cml` 把这六行输出钉住。先量后写，量出来不一致就停下——把自己以为的行为写成规则，比不写更糟。

## 3. 总体结构

### 3.1 编译器一侧

```
图（今天的 GCGraph；图存储线合入后是冻结视图）
  └─ 程序分析   入口与 root 上的顶层值；要译的图（具名函数、lambda、泛型实例）；
                 哪些图是分支臂（并入调用它的函数）；调用图与它的强连通分量（尾调用合并、递归）
  └─ 函数分析   每张图：执行序；块与分支的嵌套；每个节点的 C++ 类型与名字；
                 尾位置的调用；可能故障的节点（→ site）；每个值的最后一次使用（→ std::move）
  └─ 发射       类型声明（元组、结构体、闭包）→ site 表 → 函数的前向声明 → 函数体 → 入口
```

源文件（`src/passes/trans/cpp/`）按这几步分开：`program_emitter`（程序分析与整体布局）、`function_emitter`（一张图的块、分支、语句）、`cpp_types`（类型到 C++ 的映射与聚合类型的声明、常量的字面量）、`operator_rules`（算子译法表）、`fault_sites`（故障位置与报告文字）、`bridge`（运行时模块的边界）。今天的 `runtime_emitter.cpp`、`lower.cpp`（那张没有调用点的表）与 `include/camel/passes/trans/cpp/cpp_bridge.h` 的大部分随之删除。

转译器只经过一处取算子的 URI（`operatorUri(graph, node)`）：图存储线合入后 `OPER` 节点带的是 `OperId`，那时只改这一处，并且改为从算子表项读纯度、`mayFault` 与 `callsGraphs`（图数据模型 3.5 的 `OPER` 卡片），转译器自己的表只剩“怎么写成 C++”。

### 3.2 产物

一个 `.cpp` 文件，依次是：

1. 文件头注释：源文件、怎样构建（独立的程序是一条命令；要链接运行时的写明为什么）。
2. `#include "camel/standalone/runtime.h"`（要运行时的再加 `bridge.h`）。
3. `namespace <模块名> {`：聚合类型的声明；site 表；函数的前向声明；函数体。
4. `int main(int argc, char **argv)`：把参数交给 `rt::run`，后者设好输出、递归上限与大栈线程，调用入口，接住故障并报告，返回退出码。

一个朴素递归的斐波那契程序译出来应当是这个样子（拟议；阶段 2 之后以实际输出为准）：

```cpp
// Generated by `camel <program>.cml std::cpp`.
// Standalone: c++ -std=c++20 -O2 -I"$CAMEL_HOME/include" <program>.cpp -o <program>
#include "camel/standalone/runtime.h"

namespace fib {
namespace rt = camel::standalone;

// Places that can fault, with the source excerpt a fault there reports.
constexpr rt::Site site_1{"<program>.cml", 4, 36, "__g_6__", " 4 |     return if n <= 1 ..."};
constexpr rt::Site site_2{...};

int64_t fib(rt::Depth depth, int64_t n) {
    if (n <= 1) {
        return n;
    }
    const int64_t v1 = fib(rt::call(depth, site_1), rt::sub(n, 1));
    const int64_t v2 = fib(rt::call(depth, site_2), rt::sub(n, 2));
    return rt::add(v1, v2);
}

int64_t main_(rt::Depth depth) {
    rt::println(fib(rt::call(depth, site_3), 32));
    return 0;
}

} // namespace fib

int main(int argc, char **argv) { return camel::standalone::run(argc, argv, fib::main_); }
```

### 3.3 运行时头文件

`include/camel/standalone/`，只用 C++20 标准库，全部 `inline`：

## 4. 值的表示

**同一个类型只有一种表示，而且表示由类型决定，不由值从哪个模块来。** 下表把 Camel 的类型列到 C++；一个类型在这一列里只出现一次，所以 `tensor:ones` 返回的 `T[..]` 与自己写的 `[1.0, 2.0]` 是同一行的同一个 `rt::Array<T>`。经桥的值也在边界上换成这个表示（第 9 节），不另有一种写法。

**一个类型只有能被打印出来，才算被实现了：打印不出来的类型，它的算术对不对无从谈起。** 所以每加一种值类型，先做的是存储与它的文字（`appendText`、`formatArg`），然后才是算术、比较与转换——`bf16`、`f16` 就是按这个次序做的，`0.1` 读作 `0.1` 而不是它加宽后的 `0.100097656`，这条规则先立住。

**打印是语言的一部分：值的形状不印出来，读的人就分不清一个元素和一个单元素数组。**

| Camel | C++ | 说明 |
|---|---|---|
| `int`、`i32` | `int64_t`、`int32_t` | 加减乘、取负、`+=` 等用 `rt::add` 一类的内联函数：经无符号运算回绕，编译出来与 `+` 相同；比较直接写 `<` 等 |
| `float`、`f32` | `double`、`float` | 直接写 `+ - *`；`/` 除以零是故障（与运行时一致【读码 `src/builtin/operators/ops.cpp` 的 `__builtin__div__`】），所以写成 `rt::div(a, b, site)` |
| `bf16`、`f16` | `rt::BF16`、`rt::F16` | 十六位存储；一次舍入就是存回时按就近取偶的那次（`include/camel/standalone/half.h`，与 `camel/core/rtdata/half.h` 同一条规则）。`+`、`-`、`*` 与一元 `-` 直接写（在 `float` 里算、存回时舍入一次），`/` 是 `rt::div`（零是故障，与 f32 同一个），`^` 是 `rt::pow`；比较按加宽后的值（两个零相等，NaN 与任何值都不等、也不成序；`==`、`!=` 直接写，序用 `<=>`）；文字是该类型自己的最短文本（`halfText`，7.7），`println`、`string(x)` 与空的 `{}` 用的是它，任何别的格式说明按加宽后的 f32 写；`bf16(x)`、`f16(x)` 与 `as` 是 `static_cast`（一次舍入），`bf16(s)`、`f16(s)` 是 `rt::halfFromText`，其报告与解释器逐字相同；常量写成 `fromBits`，NaN 的载荷也不丢 |
| `bool` | `bool` | `&`、`\|` 两边都已求值，写 `&&`、`\|\|` 不改变语义；`&&`、`\|\|` 运算符在图上本来就是分支（4.2） |
| `c64`、`c128` | `std::complex<float>`、`std::complex<double>` | 两个部分就是 `std::complex` 的两个 `float`/`double`：`+`、`-`、`*`、一元 `-`、`==`、`!=` 直接写，`/` 是 `rt::complexDiv`（复数的零是故障），整数指数的 `^` 是 `rt::pow`（反复平方，与运行时同一个算法）；`abs`、`re`、`im`、`conj`、`exp` 是 `rt::complexAbs`、`rt::complexReal`、`rt::complexImag`、`std::conj`、`std::exp`；文字是 `camel::utils::complexText`，格式说明按两个部分写（`camel/standalone/format.h`，与解释器同一条规则，NaN 的部分不写符号）；`main` 的这类参数从 `--arg` 读语言里的复数文字（`rt::EntryKind::C64` / `C128`），实数文本是实部、虚部为 0 的复数（`1.5` 是 `1.5+0i`） |\r\n| `string` | `rt::Str` | 一个指针大小的句柄，指向 `{计数, 长度, 容量, 字节}`；空串是空指针。字面量是静态存储的“永生”对象（计数从一个不会减到零的值开始），不分配 |
| `T[]`、`T[..]`、`T[2, 2]` | `rt::Array<T>` | 句柄，指向 `{计数, 长度, 容量, 维数, 各维长度, T 元素}`；元素是 `T` 的 C++ 表示，`int[]` 是连续的 `int64_t`。维数是值的一部分（5.4）：字面量带着类型写明的各维长度，`shape` 读的就是它；`T[..]` 只固定元素类型，长度由值自己带着。张量就是这个类型——`tensor:ones` 的 `T[..]` 与 `[1.0, 2.0]` 是同一个 `rt::Array<T>`，打印、取维数、求元素数只有一个实现。计数为 1 时“返回新值”的算子在原处改（5.2） |
| 元组 `(A, B)` | 生成的 `struct`（`Tuple_i64_str { int64_t _0; rt::Str _1; }`） | 按值。带 `==`（逐个元素，4.2）与打印 |
| 结构体 `{ x: A }` | 生成的 `struct`，字段同名 | 按值。类型有别名时用别名作类型名 |
| 枚举 `enum { A(T), B { x: A }, C }` | 生成的 `struct`：`tag`（第几个变体）与 `std::variant<std::monostate, A, B, C> value`，每个变体一个嵌套的载荷 `struct`；`make<Tag>`、`get<Tag, Index>` 由声明生成。递归枚举里传递包含该枚举自身的字段用 `std::shared_ptr` 间接持有（C++ 不能按值容纳无限类型）：`make` 装箱、`get` 与打印解引用，析构、相等与打印都用显式栈（`camel/standalone/recursive.h`），一百万节点的链不递归 | `tag` 与字段下标在图上都是常量，所以是模板参数（`Shape::make<1>(2.0, 3.0)`、`rt::enumField<1, 0>(x)`）。按值。带 `==`（先比 `tag`，再比载荷）与打印（`Shape::Rect { w: 2.0, h: 3.0 }`，与解释器逐字节相同） |
| `T?` | `rt::Opt<T>` | 标量是“值 + 一位标记”；句柄类型用空句柄表示空，不多占位 |
| `T!` | `rt::Fallible<T>` | “值 + 错误句柄”，错误句柄非空即出错 |
| 错误值 | `rt::Error` | 句柄，指向固定的内建结构：种类名、消息、源码位置（3.9） |
| 函数值 | `rt::Fn<R(Args...)>` | 句柄，指向 `{计数, 代码指针, 捕获的值}`；每个 lambda 一个生成的闭包类型。没有捕获的函数常量是静态的永生对象，不分配 |
| `var T`（变量单元） | 不逃出所在函数时是一个 C++ 局部变量；否则 `rt::Cell<T>`（句柄） | 5.3 |
| `Map<K, V>`、`Set<K>` | `rt::Map<K, V>`、`rt::Set<K>` | 句柄，按键排序的数组；操作返回新值，计数为 1 时原地改。遍历与打印按键排序（11.3），与运行时一致。要换成持久化的树，等量过再说 |
| `void` | 不产生 C++ 值；要占位时是空的 `rt::Unit` | 没有 `else` 的 `if` 的空臂（3.7） |
| `PyObject`、`Device<T>` 等不透明对象 | `rt::Foreign`（句柄，内部是运行时的 `RootHandle`） | 只出现在链接运行时的程序里（第 9 节）。只有语言本身就不让人拆开看的对象走这里；张量不在此列，它就是上面 `T[..]` 那一行的原生数组 |
| `any` | 拒绝 | 5.1：编译之后不应当有运行时还不确定的类型；`any` 正在收紧（5.10），不为它设计表示 |

**为什么值类型只给元组、结构体、`T?`、`T!`。** 它们在运行时里也是不可变的（字段不可赋值，3.5），按值拷贝与共享分辨不出来（1.3）；按值放在 C++ 的栈上和寄存器里，不分配。数组、映射、字符串可能很大，按值拷贝的代价与大小成正比，所以是带计数的句柄，计数为 1 时可以就地改（5.2）。

**对外的签名。** 10.6 裁定 `std::cpp` 生成的模块接口用标准 C++ 类型。`std::cpp::module` 写出的每个函数因此另有一个对外的包装：`int64_t`、`double`、`bool`、`std::string`、`std::vector<T>`、`std::optional<T>`、`std::tuple` 与生成的 `struct`（字段是标准类型）、`std::function`，在边界上转换；内部的 `rt::` 类型不出现在对外的签名里。阶段 1 先做标量与字符串。

## 5. 内存

### 5.1 引用计数

每个句柄类型是一个小的 C++ 类：拷贝构造加一，析构减一，减到零释放（并递归地释放它拿着的句柄），移动不改计数。转译器在**每个值的最后一次使用处**写 `std::move`，于是“传给下一个算子然后再也不用”的值不产生加减。图上直接有这个信息：一个节点的使用者都是边；在按执行序排好的语句里，最后一个使用者之后的位置就是最后一次使用。

计数不用原子操作：生成的程序是单线程的（1.3）。将来并行执行 `map` 时，在交给别的线程之前把计数换成原子的，或者在交接处转移所有权（第 14 节）。

【实测】两百万个短命字符串（附录 A 的 `churn.cpp`）：

| | 用时 | 峰值内存 |
|---|---|---|
| `std::fvm`（默认回收器） | 0.76 s [0.73, 1.15] | 123.5 MB |
| 独立的 C++，引用计数 | 0.27 s [0.17, 0.39] | **9.7 MB** |
| 独立的 C++，从不释放（“丙零”） | 0.33 s [0.29, 0.54] | 125.9 MB |

引用计数既比不释放快（释放的内存马上被下一次分配用上，不需要向系统要新页），内存又与存活数据成正比。

### 5.2 身份与就地修改

10.5：有身份的只有变量单元、经 `var` 参数就地修改的对象、外部库包装的对象；其余的值没有可观察的身份，后端可以随意复制或共享。同一条规则定下 `append` 返回新数组、不修改原数组，“旧值不再被使用时可以在原处追加”只是实现层面的优化，标准库的其他算子同此。

本基线的运行时还是旧的做法【实测 附录 A 的 `g1.cml`：`var xs = [1, 2]; xs->append<3>; println(xs)` 打印 `[1, 2, 3]`；图上 `append` 的输入是 `:var/get` 读出的数组，实现在原数组上追加，`src/builtin/operators/struct.cpp` 的 `__append_arr__`】。裁定的迁移把“写成语句、结果没有被使用的 `xs->append<5>`”定为编译期错误，所以这种依赖原地修改的程序以后不会到达转译器。生成的程序直接按裁定的语义做：

- 数组、映射、字符串是带计数的句柄，**按值语义**：拷贝句柄就是共享，没有人能通过一个句柄看见另一个句柄上的修改，因为修改只发生在计数为 1 的时候。
- “返回新值”的算子（`append`、`concat`、`slice`、字符串拼接、映射的 `put` 与 `remove`）按值接收第一个实参：转译器在它的最后一次使用处写 `std::move`，计数为 1 时直接在原处改，否则先拷贝。例如循环里的 `acc = acc->append<x>` 或 `acc + piece`，`acc` 被移动进算子，计数为 1，就地追加，摊还 O(1)。这就是 Perceus 式的“唯一时复用”。
- 有身份的三样另行处理：变量单元见 5.3；经 `var` 参数就地修改的对象由单元承载（`var` 参数传的是单元）；外部库包装的对象只出现在链接运行时的程序里（第 9 节）。

在运行时完成迁移之前，旧语义下“写成语句的 `append`”在两种后端上的结果会不同；这类程序在迁移后是编译期错误，不作为差异处理。

### 5.3 变量单元

`var x` 在图上是 `:var/new` 建立的单元，读写是 `:var/get` 与赋值算子（3.5）。

- **单元不逃出所在的函数**（它的使用者只有 `:var/get`、赋值算子，以及并入本函数的分支臂里的这两种）：一个 C++ 局部变量。这是绝大多数 `var` 的情形。
- **否则**（作为 `var` 实参传给别的函数、被闭包捕获、交给别的算子）：`rt::Cell<T>`，一个句柄，指向 `{计数, T 值}`。传参、捕获都是拷贝句柄，所有人看到同一个值，满足 3.5“闭包对变量的捕获也是引用”。

### 5.4 环

值由下往上构造、构造之后不变（3.5），所以值之间不成环；数组的原地修改只能追加已经存在的值，也不成环——除非数组里放进了一个拿着这个数组的闭包，那必须经过变量单元或 `var` 形参，同样归到下一种。唯一的环经过变量单元：单元里放着一个捕获了这个单元的闭包。引用计数不回收它。10.5 已经裁定“后端可以少回收甚至不回收垃圾”，所以这是允许的；它泄漏的是一个闭包和一个单元，大小与程序写了多少这样的变量成正比，与运行多久无关（每次执行到那个 `var` 才产生一个）。若将来要回收，加一个只扫描单元的环检测（单元是唯一能成环的节点），不影响别的部分。

### 5.5 没有选的做法

- **区域（竞技场）**：每次 `map` 的元素调用、每轮循环一个区域，结束时把结果拷出来再整块释放。拷出与结果的大小成正比，循环状态是一个越来越长的数组时总量是平方级；要避免就得做区域推断。引用计数没有这个问题，而且图上的使用信息本来就够用。
- **不回收**：最简单（今天就是这样），但长时间运行、持续分配的程序会耗尽内存；上表也显示它并不更快。
- **C++ 标准库的值类型**（`std::string`、`std::vector`）：拷贝是深拷贝，要不慢就得做与引用计数相同的“最后一次使用”分析；共享又要退回 `shared_ptr`。只有元组、结构体、`T?`、`T!` 用值类型（第 4 节）。
- **`std::shared_ptr`**：两个字（对象指针与控制块指针）、原子计数、控制块另外分配。自己的句柄是一个字、非原子、计数与数据在一起。

## 6. 控制流与顺序

### 6.1 执行序

每张图的语句按 `buildReachableExecutionTopoIndices` 给出的执行序排列【读码 `src/execute/graph_runtime_support.cpp`】。这是 `std::fvm` 编字节码用的同一个序（图数据模型 5.1 把它定为 `ExecPlan::order()`）。它是三组边（数据、`with`、控制）的拓扑序，只含从出口可达的活节点，并把每个分支的臂排成连续的一段。

用同一个序有一个具体的好处：**语言没有规定先后的两个效应**（同步块之外互不依赖的两次打印），在生成的程序里与在 `std::fvm` 上也是同一个先后，于是两者的输出可以逐字节比较。这不是语义的要求（3.1），是测试的便利，代价为零。

只有活节点被译出来：同步块之外结果没被用到的效应不执行（3.1、第 14 节误读 1）。

### 6.2 分支

`BRCH`/`JOIN` 译成语句：

```cpp
int64_t v4;                      // JOIN 的值；没有值（void）时不声明
if (cond) {
    ... 臂 0 的语句 ...
    v4 = <臂 0 的值>;
} else {
    ... 臂 1 的语句 ...
    v4 = <臂 1 的值>;
}
```

`match` 是一串 `if`/`else if`，比较用该类型的 `==`（字符串按内容，修 D3）。这个复合语句放在执行序里 `BRCH` 所在的位置，臂里的节点只出现在臂里：分支只执行一次（修 D4），分支之后的效应在分支之后（修 D5）。

臂的两种形态（图数据模型 3.5、设计原则 2.2）都认：

- **子图形态**：臂是一个 `FUNC` 节点，被调图是臂图。把臂图的语句并入当前函数，臂图的端口绑定到 `FUNC` 节点的实参。并入是递归的（臂里还有分支）。
- **区域形态**（`std::opt::inline` 之后）：臂的节点在当前图里，位于 `BRCH` 与 `JOIN` 之间，按执行序里的区间取出（修 D11）。

不能并入的 `FUNC`（具名函数、泛型实例、`std::opt::inline` 留下的普通调用）是 C++ 的函数调用。

### 6.3 尾调用

**自尾调用**：函数体包在 `for (;;) { ... }` 里，尾位置上对自己的调用写成“算出新的实参、赋给形参、`continue`”。尾位置：函数的返回值就是这个调用的值，中间只经过 `JOIN`（臂的值）与 `GATE`（且 `GATE` 等的节点都排在调用之前）。形参因此不是 `const`；句柄类型的形参被赋值时，旧值的计数照常减一。

**互相尾调用**（`is_even` / `is_odd`）：在“尾调用图”（只看尾位置的调用）上求强连通分量；一个分量里有多个函数时，把它们合成一个函数：各自的形参都是局部变量，一个 `switch` 选当前在哪个函数里，尾调用改变选择子再 `continue`；每个原函数保留一个入口，转调合成的函数。这是可移植的写法（不依赖 `[[clang::musttail]]`，MSVC 没有它）。合成在阶段 2 就做了：转译器先把每个函数写一遍，记下它在尾位置调用了哪些别的函数，再按这张图分组（返回类型不同的不合成，它们之间的尾调用仍是普通调用）【实测 `test/cases/trans/cpp/exec/tail_calls.cml`：一对互相尾调用的函数跑一百万步】。

**经函数值的尾调用**（续延传递风格）：照普通调用处理，计入递归深度并使用栈。这与调度器不同（调度器的尾调用一律不计数），列入第 14 节。

**`LOOP` 节点**（循环线设计中，图数据模型 3.5）：落地之后直接写成 C++ 循环；在那之前它在入口处被降级为尾递归子图，走上面的路。

### 6.4 效应与顺序

同步块（3.4）与 `wait`在图上就是控制边；执行序已经尊重它们（6.1），转译器不需要别的处理。`GATE` 不产生语句，它的值就是输入的值；`SYNC`（内联遍的汇合点）只承载顺序，也不产生语句——今天它被当作“同步块”拒绝（D11），新转译器认它。

**一个可能失败的语句，不能因为它的值没人读就不跑；丢一个值只是浪费，丢一次检查就是丢一次故障。**

## 7. 故障、错误值、`attempt`、递归上限

### 7.1 故障

可能故障的算子（除零、越界、转换越界、文字不是一个数、`slice` 越界、`head` 空数组……）在生成的代码里多一个实参：它的 `site`。`site` 是一个 `constexpr` 对象，带转译时渲染好的两种报告（默认格式与一行格式）、种类的名字、消息与位置（`include/camel/standalone/core.h` 的 `Site`）。出故障时头文件里的函数抛出 `rt::Fault{种类, 实参, site}`。

`rt::run` 接住它：先刷新标准输出，再按 `CAMEL_ERROR_FORMAT`（`text`，或测试用的 `short`）写出报告，退出码 1。**报告写在标准输出上**，因为解释器就写在那里【实测：用 `std::fvm` 跑一个会除零的程序，`2>/dev/null` 仍然打印出报告；`2>&1 >/dev/null` 什么也没有】。

报告的文字与解释器逐字节相同。做法是把它拆成三部分，各自取自编译器的唯一出处：

- **种类的名字、消息、提示与源码摘录**：全部由编译器自己的渲染器（`src/core/error/diagnostics/render.cpp`）在转译时按诊断表（`getRuntimeDiagInfoMap`）渲染好，作为字符串常量写进 site；头文件不重写渲染器，免得两份代码在制表符、宽字符、长行截断上不一致。
- **运行时才知道的实参**（越界的下标、数组的长度、参数名）：渲染时留下占位符——字节 0x1F 加一位数字，数字是它是 `fault()` 的第几个实参；头文件在故障发生时用实参替换。
- **转译时已经知道、运行时可以不同的实参**（递归上限）：整份报告直接写成转译时的上限，`Site::filled` 另记下这段文字；故障发生时头文件用生效的值替换它**第一次**出现的地方。所以生成程序的报告里总是实际生效的数字，与解释器逐字节相同。

颜色：解释器在终端上给报告上色；生成的程序不上色（测试与管道里两者都没有颜色）。

**一个类型的故障报文是它契约的一部分：能算对而报错报得不一样，等于两个人对同一件事有两个说法。** 所以 `bf16`、`f16` 的三种转换报文与除零报文各有程序钉着（`test/cases/trans/cpp/fault_narrow_*.cml`），比的是整个标准输出与退出码，不是关键字。

**两份同类报告共用一个 site，等于让第二份替第一份说话；故障之间的差异必须作为实参传进去，不能靠 site 的名字区分。** 这一条是踩出来的：`SiteTable::siteFor` 按（节点，种类）建键，同一个转换的两份越界报告种类相同、位置也相同，于是第二份永远拿到第一份的文字——f16 越界时报的是 f32 的范围。改法就是把它当成一份报告：范围作为 `fault()` 的实参、在故障发生时填入，一份 site 的两种说法都与解释器逐字节相同。

`CAMEL_ERROR_FORMAT=short` 的报告不钉：它是**显示风格**，不是契约。一行格式是给人扫一眼用的，改排版不算改语义，钉住它只会把一份打印习惯变成不许动的规矩；契约是默认格式下那段文字（种类、消息、位置、提示），那也是解释器与生成程序真正共有的东西。

### 7.2 错误值与 `attempt`

错误值（`T!` 的错误一侧，3.9）是 `rt::Error`：种类名、消息、位置。`throw error('Kind', 'message')` 构造它，位置是转译时已知的 site。`??`、`!!`、`->` 与 `match` 的固定模式在图上是分支（2.1 对应表），按 6.2 译出，条件是 `rt::Opt::has_value()` 或 `rt::Fallible::failed()`。

`attempt(f, x)`（`:mark/isolate`）是一次带标记的调用（设计原则 2.1 对应表）：

```cpp
rt::Fallible<int64_t> v7 = rt::attempt([&] { return risky(rt::call(depth, site_5), x); });
```

`rt::attempt` 用 `try`/`catch (const rt::Fault &)` 把故障变成错误值，消息与位置取自故障。递归上限的故障也能被隔离，与调度器一致【未查：调度器是否隔离递归上限故障，阶段 3 实测】。被隔离的调用里已经产生的输出保留（与调度器相同：输出是效应，不回滚）。

没有被处理的错误值到达 `main` 的出口：打印到标准错误，退出码非零（3.9），与解释器的写法相同（阶段 3 对照）。

### 7.3 程序的入口与退出

- `main` 声明了整数返回类型：返回值的低 8 位是退出码【实测：`return 300` 的退出码是 44】；`main` 是纯的（没有 `sync`）时也一样，不打印【实测 `func main(): int { return 7 }`：没有输出，退出码 7】。
- `main` 声明了别的返回类型：值按 `println` 的写法打印到标准输出，退出码 0【实测：返回 `'hi'` 打印 `hi`；返回 `0.1 + 0.2` 打印 `0.30000000000000004`】。
- 没有声明返回类型：不打印，退出码 0（D9 的第二半）。
- `exit(n)`（`:exit`、`process:exit`）：刷新输出，退出码 n（D9 的第一半；今天被 `catch (...)` 吞成 `Unknown error`）。
- 带参数的 `main`（9.8：值来自命令行）：生成的程序接受与命令行工具相同的 `--arg 名字=值`，按形参声明的类型读取（整数、浮点数、复数、`bool`、`string`；复数是语言里的复数文字，如 `1+2i`、`-2i`，实数文本则是实部、虚部为 0 的复数，如 `1.5`），缺少时给出带位置的错误（13 的 Q7）。
- root 上算出来的顶层值（10.1：在 `main` 开始之前求值）：root 图本身也译成一个函数 `entry_`，它算出顶层值再调用 `main`；今天这种程序被拒绝。

### 7.4 递归上限

规则与调度器相同【读码 `include/camel/execute/limits.h`】：数“同时打开的、不在尾位置的调用”，入口对 `main` 的那次不计；上限 L 时，`main` 调用的 `depth(L - 1)` 是能跑完的最深一次。故障报告名字是**发出调用的那张图**、位置是调用处【实测：`Maximum recursion depth (1000) exceeded when evaluating graph '__g_6__'`，位置是 `depth(n - 1)`】。

三种做法的实测【实测：`proto/fib_sa.cpp`、`proto/fib_sa2.cpp`，`fib(37)`，各 9 轮】：

| 做法 | 用时 | 相对 |
|---|---|---|
| 不计数 | 0.083 s [0.075, 0.088] | 1.0 |
| 计数作为隐含参数，调用处检查 `depth + 1 > limit` | 0.123 s [0.110, 0.126] | 1.5 |
| 计数放在全局变量里，被调函数入口加一、出口减一（RAII） | 0.181 s [0.164, 0.202] | 2.2 |

选第二种：每个会发出调用的函数多一个形参 `rt::Depth depth`，调用写成 `f(rt::call(depth, site), ...)`，`rt::call` 检查后返回 `depth + 1`。计数在寄存器里，不读写内存；检查放在调用处，所以报告的图名与位置与调度器一致；不发出任何调用的叶子函数不需要这个形参。尾调用写成循环，不经过 `rt::call`，所以不计数，与调度器一致。

上限的默认值是转译时的设置（`--max-recursion-depth`，否则 1000），写进生成的程序；运行时不再改变它，与解释器相同。生成程序里每个调用点的报告写成转译时的上限（`Maximum recursion depth (1000) ...`，不留占位符）；`rt::call` 把生效的上限交给 `fault()`，`Site::filled` 让报告里的数字换成它，所以报告里总是实际生效的值。

**原生栈。** 上限可以调到一百万（`kMaxDepthLimit`），每层几十到几百字节，主线程的默认栈（Linux 8 MB、Windows 1 MB）不够。`rt::run` 在一个新线程上运行程序，栈的大小按上限留足（每层按 512 字节估，至少 64 MB，最多 1 GB；只是保留地址空间，用到的页才占内存）：POSIX 用 `pthread_attr_setstacksize`，Windows 用 `CreateThread` 的栈大小参数。这是头文件里唯一与平台相关的代码。

## 8. 算子

转译器内部一张表，键是 URI，值是译法：

| 译法 | 例 | 生成的代码 |
|---|---|---|
| 内联表达式 | `:op/lt_l`、`:op/eq_b`、`:op/not`、`:op/mul_d` | `a < b`、`!a`、`a * b` |
| 回绕的整数运算 | `:op/add_l`、`:op/neg_i` | `rt::add(a, b)`、`rt::neg(a)` |
| 带位置的头文件函数 | `:op/div_l`、`:op/idx_arr`、`:op/dtol`、`:op/stol` | `rt::div(a, b, site_3)` |
| 头文件函数 | `:io/println`、`:str/format`、`:op/add_s`、`:str/join`、`:struct/zip`、`math:sqrt`、`time:now`、`rand:*`、`statistics:mean` | `rt::println(a, b)` |
| 变量单元 | `:var/new`、`:var/get`、`:op/assn_*` | 局部变量的声明、读、赋值（5.3） |
| 调用子图的算子（`callsGraphs`） | `:mark/map_arr`、`:mark/reduce_arr`、`:mark/isolate` | C++ 循环与 `rt::attempt`（7.2） |
| 运行时模块（桥） | `tensor:*`、`python:*`、`onnx:*`，以及还没有独立译法的模块算子 | 第 9 节 |

表里每一项的行为以运行时的实现为准，按 URI 一一对照着写（例如整数乘方是 `static_cast<int64_t>(std::pow(base, exp))`【读码 `ops.cpp` 的 `__builtin__pow__`】，浮点除以零是故障）。打印的文字用 `camel/utils/number_text.h` 的 `floatText`，与运行时同一份代码。

`random` 模块的算子（`rand:seed`、`rand`、`randn`、`randint`、`choice`、`sample`、`shuffle`）由 `camel/standalone/random.h` 译：与模块用同一个 `std::mt19937_64`（默认种子相同）和 `camel/utils/random.h` 的同一套分布（整数用 Lemire 的方法，正态用极坐标法与 fdlibm 的对数），洗牌与抽样的取下标方式也照模块写，所以种子相同时生成的程序与解释器打印相同的数【实测：`draws.cml`、`modules/std/random/basic.cml`】。

内部算子 `:op/assn_owned` 与 `:struct/append_arr_in_place`（`acc = acc->append<v>` 按 `append` 声明的原地形式改写成的两个节点，`:var/take(acc)` 交出变量单元里的数组）写成 `acc = rt::append(std::move(acc), v);`，捕获或经 `var` 参数共享的单元写成 `acc.set(rt::append(acc.take(), v));`：变量在这次调用里交出它的数组，没有别人拿着时 `rt::append` 原地追加，这正是解释器里执行计划标的“复用输入自身的存储”与数组自己的计数（`Array::canWriteInPlace`）所做的；元素若是表达式先算进一个局部，读到的仍是交出之前的数组。`:var/peek`（不结束那份证明的读）在生成的程序里与 `:var/get` 相同，引用计数本身就记着同一件事【实测：`consistency/new_values/rebinding_loop.cml`、`peek_loop.cml`、`peek.cml` 与 `std::fvm` 相同】。

运行时里有两处行为看起来是意外，生成的程序照样复现，并报告给负责人（第 14 节）：`println<'{}+{}'>(1, 2)` 打印 `1+2` 之后多一个空行；`print<'{}-{}'>(3, 4)` 在末尾加了换行【实测 `m5.cml`】。【10.6：这是解释器的缺陷，已修掉，生成的程序随之改正。】

阶段 1 优先给 `std::cpp` 今天能译的 205 个程序用到的算子独立译法【实测：其中 195 个用 `:io/println`、56 个用 `:str/format`，其余是标量运算、字符串运算、`time:now`、`env:get_env` 与一批 `math:*`】；剩下的经桥，程序照样能编译运行，只是要链接运行时。

## 9. 运行时模块的边界

**何时。** 一个算子在表里没有独立译法，而它的实参与结果都能在独立的表示与运行时的表示之间转换（标量、字符串、数组）时，经桥调用。不能转换的（`any`、函数值交给运行时算子）拒绝。

**怎样。** 生成的代码写：

```cpp
const rt::Array<double> v5 = op_4.call<rt::Array<double>>(site_4, {rt::bridge::arg(n)}, {});
```

`op_4` 是一个按 URI 第一次使用时在运行时的算子表里查到并缓存的访问器。`bridge::call` 在调用的这一条语句里：把实参转换成运行时的值（字符串在运行时的堆上新建一个），放进**每次调用在栈上新建**的实参区（今天的实参区是整个进程共用一份，不可重入），调用算子，把结果转换回独立的表示。运行时堆上的对象只活在这一条语句里，期间没有安全点（句柄规则第 1 节），所以不需要登记根；生成的代码从不拿着运行时的指针。

**张量。** 张量是 `T[..]`，第 4 节那一行的原生数组，所以在桥上做的事和别的数组一样：结果从运行时的张量拷成程序自己的 `rt::Array<T>`（元素逐个按值取、维数一起带过来），需要时实参再拷回去。转换要拷贝，这一点接受；以后要零拷贝共享存储，那是不改语义的优化。于是 `println` 一个张量就是打印 `rt::Array`，嵌套格式与解释器逐字一致——同一个类型只有一种表示，值从哪个模块来不改变它。

**不透明对象**（`PyObject`、`Device<T>`）在语言里本来就不可拆开，独立的一侧写不出比名字更多的东西，只能由运行时拿着。它们在生成的程序里是 `rt::Foreign`：一个带计数的句柄，里面是一个 `mm::RootHandle`。计数减到零时释放 `RootHandle`，对象交回运行时的回收器。生成的程序在桥调用之间（此时它不拿着任何运行时的裸指针）调用一次 `mm::safepoint()`，回收器可以运行。这样“运行时对象只经句柄接触”（10.5）在生成的代码里同样成立。

**故障。** 运行时的算子抛出 `RuntimeFault`。`bridge::call` 接住它，换成带调用处 site 的 `rt::Fault`，种类、消息与提示取自运行时自己的诊断表（此时 `libcamel` 已经链接），报告的格式与 7.1 相同。

**初始化。** 第一次桥调用时建立运行时的 `Context`（模块查找路径来自 `CAMEL_HOME` 与可执行文件所在目录，与今天的 `cpp_bridge_runtime.cpp` 相同），只加载用到的模块；程序结束时释放。没有桥调用的程序什么都不做。

**转译时的警告。** 程序要链接运行时，转译时给出警告 `RuntimeDiag::TranslationLinksRuntime`（`docs/diagnostics.md`），位置是第一个经桥的算子，消息里列出全部经桥的算子。生成的文件头注释写同样的内容与构建命令。桥运载数、布尔、字符串与数组（张量与别的数组一样，在边界上转换）；实参或结果落在这几类之外的运行时算子仍然拒绝。

## 10. 构建与工具

- **一条命令**：`c++ -std=c++20 -O2 -ffp-contract=off -I"$CAMEL_HOME/include" x.cpp -o x`。`-ffp-contract=off` 与运行时自己的构建相同（`docs/build-options.cn.md`）：`a * b + c` 不合并为一次乘加，生成的程序与解释器在有 FMA 的平台上也打印相同的数。要链接运行时的程序另加 `-L"$CAMEL_HOME/bin" -lcamel` 与运行时自己的依赖，文件头注释写全。
- **`camel-cpp`**：今天它自己重做了一遍命令行工具的解析与编译，只在 Windows 上能找到 `libcamel.lib`（D12）。改为一个小的驱动：调用同目录下的 `camel <文件> std::cpp` 得到 `.cpp`，再用 `$CXX`（否则依次找 `clang++`、`g++`、`cl`）按上一条编译；需要运行时时加上链接参数。不再链接 `libcamel`。
- **CMake**：不提供。`docs/cpp_export_build.md` 里的“方式 A”（`CPP_GEN_SOURCE`、`cpp_gen` 目标）在 CMake 里不存在（D12），文档改写为上面两种。生成的是一个文件、一条命令，使用者把它放进自己的 CMake 工程只需要一个 `add_executable` 与一个包含目录，文档给出这三行。
- **编译时间**：旧的产物包含运行时的大半头文件，`a01_fib.cpp` 编译 6.9 秒【实测，负载下】。新的产物每个约 1–2.5 秒（全语料的中位数 2.1 秒，负载 13–24）【实测】，几乎全花在 libstdc++ 的 C++20 头文件上（单独包含 `<string>` 0.6 秒、`<ostream>` 0.95 秒【实测】），不是 `camel/standalone/` 自己。`cppexec` 用 clang 时先把 `runtime.h` 预编译一次，单个程序的编译约快一半【实测：1.6–1.9 秒对 4.2–5.2 秒，同一负载】。

### 12.4 变基到 `fsh-dev` 的 `d270689c` 时的改动

- **图的存储。** 算子以 `OperId` 识别：变量与 `:mark/` 算子按 `oper::VarNew`、`oper::VarGet`、`oper::MapArr` 等与 `OperatorTable::isAssignment` 认，不再比较 URI 文字；译法表（第 8 节）仍以 URI 为键，那是算子的公开名字，模块算子也没有固定的 id。函数类型不再带捕获的名字，捕获形参的名字取 `graph->captureNames()`（与 `std::gir` 相同）。帧布局的改动不影响转译器（它不读帧）。
- **模块。** 所有模块的顶层值在同一个根图里，根图的出口是对入口 `main` 的调用；转译器本来就这样找入口，算出来的顶层值照旧写成 `top_level`，导入的字面量值作为实参传给 `main_`（`module_root.plan.toml` 的 `root.values_cpp` 改为检查 `main_(0, 3.14159)`）。
- **`&&`/`||` 是分支、`x == null`、窄化。** 都落在已有的 `BRCH`/`JOIN` 与 `:op/tag_*` 上，生成代码的写法不用改；清单加入 `consistency/logical/short_circuit.cml`、`pure.cml` 与 `consistency/narrowing/narrow.cml`，与 `std::fvm` 相同【实测】。
- **`any`。** `TypeCode::Any` 已删除；`Json` 类型不翻译（拒绝，语料里 3 个程序）。
- **随机数。** 见第 8 节：与 `random` 模块同一套算法，种子相同时输出相同。
- **浮点。** 运行时以 `-ffp-contract=off` 构建（`3af224da`），生成程序的构建命令（文件头注释、`camel-cpp`、`cppexec`、`docs/cpp_export_build.md`）也加上，否则有 FMA 的平台上 `a * b + c` 可能合并而与解释器差最后一位。顺带修了要链接运行时的程序的文件头注释：构建命令里原来写出了字面的 `\n`。
- **分代回收成为默认。** 只影响 12.3 里 `std::fvm` 一侧的数字。
- **`:op/assn_owned` 与 `:var/peek`。** 见第 8 节：前者（`append` 的原地形式）写成变量交出数组的 `rt::append`，后者当作读。

未提交的改动不属于任何树：谁切分支，谁就可能把它带走。这台机器是跨车道共用的，所以改动要么提交，要么先说清楚。

## 13. 要负责人确认的问题

### Q1 故障的报告要不要与解释器逐字节相同

候选：

- 甲：相同。生成的程序把报告写在标准输出上（解释器就写在那里），文字、源码摘录、`CAMEL_ERROR_FORMAT` 都一样，只是不上色。
- 乙：只要求带位置；格式由生成的程序自定（例如写在标准错误上、一行）。

**建议甲**，并按甲做：测试可以逐字节比较两种后端，使用者看到的诊断也一致；代价是生成的文件里每个可能故障的位置多一段源码摘录的字符串。这里只问“是否要求”，不改变解释器的行为。

### Q2 递归计数的代价

精确计数让调用密集的代码慢约 1.5 倍（7.4 的表；不计数的 `fib(37)` 0.083 秒，计数 0.123 秒，`std::jit` 的 `fib(32)` 0.035 秒、独立的 0.017 秒）。

- 甲：与调度器相同地精确计数（本稿的做法）。
- 乙：不计数，只在原生栈将尽时以同一个诊断终止。快，但上限不再是 1000 层，而取决于每层的栈帧大小，与调度器不一致。
- 丙：由一个转译时的选项决定（要等“给遍传参数”的机制，9.3）。

**建议甲**：裁定说“遵守递归上限”，而上限是一个可以对照的数。将来有了遍参数可以加丙。

### Q3 运行时里看起来是意外的两处打印

`println<'{}+{}'>(1, 2)` 打印 `1+2` 和一个空行；`print<'{}-{}'>(3, 4)` 打印 `3-4` 和换行【实测】。生成的程序照样复现。这两处是有意的吗？如果是缺陷，修运行时，生成的程序同一次修改。【10.6：是缺陷，运行时与生成的程序都已改正。】

### Q4 （已无需确认）互相尾调用

原来问的是“合成之前的过渡”；阶段 2 已经实现了合成（6.3），这一条不再需要裁定。剩下的差别只有一处：返回类型不同的两个函数之间的尾调用仍是普通调用（计数、用栈），列入第 14 节。

### Q5 `std::cpp::bench`（10.6：删去，已删）

这个模式先找名叫 `fib` 的图，找不到才用 `main`，看不出用途。建议删去这个模式与别名 `std::cppbench`；`std::cpp::module`、`std::cpp::inspect` 保留。

### Q6 生成的程序里的 `map`、`filter`

3.6 说元素之间没有顺序、并行调度器可以并发执行。生成的程序第一步按下标顺序执行：一个元素出故障时报的就是下标最小的那个（3.6 的“并行的 map 中一个元素出了故障”一条），已经开始的元素跑完、没开始的不再开始，都自然成立。建议先这样，并行放在阶段 5。

### Q7 生成的程序怎样接收 `main` 的参数（10.6：`--arg name=value`，与命令行一致；已实现，见 `include/camel/standalone/entry.h`）

9.8：“运行时由外部给值（命令行）”。建议与命令行工具相同：`./x --arg n=3 --arg name=hi`，按 `main` 的形参类型解析，缺少时给出带位置的错误（与 `camel` 的诊断相同）。另一个候选是按位置（`./x 3 hi`），更像普通的程序，但与 `camel` 的写法不同。

### Q8 打印怎么分清“秩为零的值”与“没记下秩的值”

一个秩为零的值**就是**元素（5.4），打印成 `1.5`；一个秩为一、只含一个元素的值打印成 `[1.5]`。生成程序里的 `rt::Array` 分不出这两者：`push` 有意把秩留成 0（“被追加的数组就是它装的东西的一维”），而 `rt::sorted`、被追加出来的行、`window`、comprehension 这类产出者都不记秩。于是“无秩且只有一个元素就印元素”这条规则会让 `float_reduce.cml` 印 `2.0` 而不是 `[2.0]`、让 `rebinding_loop.cml` 的 `[0]` 印成 `0`——两条都在必须一致清单里，闸门当场变红，规则已按这一步退回（`93c26b92d`）。

两条路，等裁定：

1. **让值自己带上这个区别**：`push`/追加一族产出的一维数组也记下 `{size}`，秩为零只剩“真的是元素”一种含义。一条规则留在 `appendText` 一处；代价是动 `push` 这条有意留 0 的原语，以及所有靠它生长的路径。
2. **按静态类型分派**：秩为零的值只出现在类型是 `T[..]`（`anyRank`）的位置上，打印点知道这个类型。规则就写在打印点上（数组实参一处、生成的结构字段文字一处），运行时 `appendText` 不动。两处，就是两笔。

现在的状态：一条规则都还没有；`shape` 回答的维数（`95e0017db`）与空结构的 `{}`（`b11c1caf8`）已经修好，与这条无关。

## 14. 最不放心的地方

1. **“`append` 返回新值”**（11.3）已由另一条线迁移：`append`、`extend`、`apply` 与 `algo` 的排序返回新值，`acc = acc->append<v>` 经 `append` 的原地形式写成 `:op/assn_owned`，转译器照第 8 节译。那条线合入之后，原先因“在原地追加”而不同的 5 个程序在两种后端上结果相同，`cppexec` 不再有 `differs: in-place append (11.3)` 一类（12.1 最后两行）。
2. **引用计数的正确性**靠头文件里的少数几个类与转译器写 `std::move` 的位置。`std::move` 写错的后果是读到被移走的空句柄，而不是悄悄读到别的对象；11 的计数检查与地址消毒器能发现泄漏与重复释放。
3. **故障报告的“逐字节相同”**依赖转译时渲染的摘录与运行时的渲染一致；渲染器以后改格式时两者同时改（同一份代码），但 `CAMEL_ERROR_FORMAT=json` 这类格式本稿没有覆盖，第一步只做 `text` 与 `short`。
4. **执行序与 `std::fvm` 相同**只在两者都用 `buildReachableExecutionTopoIndices` 时成立；即时编译线或图存储线如果改了 `std::fvm` 取序的方式，这一点要跟着检查（`ExecPlan::order()` 统一之后自然成立）。
5. **桥只在一条语句里**这一点，对“会回调 Camel 函数的运行时算子”不成立；今天这样的算子（高阶算子）都由转译器自己写成循环，第三方模块里如果有，要拒绝。
6. **生成的代码里，只有两处移动**（尾调用改写形参、局部变量的 `x op= v`）。别的地方的“最后一次使用”还没有分析：局部值都是 `const`，一个只用一次的数组传给 `append` 时仍要先拷贝。语料里没有因此出错的，只是慢；12.3 最后一行是已经覆盖的那种写法。
7. **经函数值的尾调用、返回类型不同的互相尾调用**仍是普通调用，计数且用栈（6.3）。
8. **只在 Linux、clang 上实测过。** Windows（MSVC 与 clang-cl）的编译、大栈线程、二进制模式的标准输出要在阶段 2 之后核实【未查】。
