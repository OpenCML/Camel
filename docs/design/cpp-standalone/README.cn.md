## 0. 摘要

负责人选了“独立部署”作为 `std::cpp` 的首要目标，调研稿第 5 节的建议（运行时的堆 + 精确根为主线）因此作废，它在 4.3 里留作“以后的独立模式”的那条路（乙：生成的代码自带内存模型）成为主线。本稿给出这条主线的完整做法。

**产物。** `camel x.cml std::cpp` 写出一个 C++20 翻译单元。它只包含 `camel/standalone/runtime.h`——随 Camel 安装在 `$CAMEL_HOME/include` 下、只依赖 C++ 标准库的一组头文件——用任何 C++20 编译器一条命令就能编成可执行文件，**不链接 `libcamel`、不加载 `.cmo`、进程里没有回收器、类型系统和算子表**。程序用到某个没有独立译法的算子（张量、Python、ONNX 等）时，翻译单元另外包含 `camel/standalone/bridge.h` 并要链接 `libcamel`；这个边界只在算子调用的那一条语句里存在，运行时的对象不进入生成的代码（第 9 节）。

**主要的决定**（理由与实测在各节）：

| 问题 | 决定 | 节 |
|---|---|---|
| 标量 | `int64_t`、`int32_t`、`double`、`float`、`bool`；加减乘与取负按回绕写成 `rt::add` 等内联函数（C++ 的有符号溢出是未定义行为）；`/`、`%` 带故障位置 | 4 |
| 字符串、数组、映射、集合、函数值、变量单元 | 带引用计数的句柄（非原子），C++ 的拷贝构造加一、析构减一，最后一次使用处 `std::move` | 4、5 |
| 元组、结构体、`T?`、`T!`、错误值 | C++ 的值类型（生成的 `struct`、`rt::Opt<T>`、`rt::Fallible<T>`），不上堆；里面的句柄照常计数 | 4 |
| 共享 | **与运行时共享得一样多**：运行时里两处拿着同一个对象，生成的程序里两处拿着同一个句柄。所以 `append` 这类在原地改数组的算子（调研 3.1 第 2 点、附录 B O1）行为不变，不需要先等那条裁定 | 5.2 |
| 回收 | 引用计数，计数为 1 时“返回新值”的算子原地改（不可观察）；经变量单元形成的环不回收（2.12 允许） | 5 |
| 分支 | `if`/`else` 语句（修 D4、D5）；子图形态的臂并入所在函数；内联之后的区域形态同样认（修 D11） | 6 |
| 执行序 | 与 `std::fvm` 用同一个执行序（`buildReachableExecutionTopoIndices`），所以语言没有规定先后的效应，在生成的程序里也与解释器同序 | 6.1 |
| 尾调用 | 自尾调用写成循环；互相尾调用的一组函数合成一个带状态的循环（第二步）；`LOOP` 节点落地后直接写成循环 | 6.3 |
| 故障 | C++ 异常 `rt::Fault`；每个可能故障的位置一个 `site`；报告的文字与解释器逐字节相同（源码摘录在转译时由编译器自己的渲染器渲染好，消息与提示取自诊断表）；`attempt` 是 `try`/`catch` | 7 |
| 递归上限 | 与调度器的计数规则相同（每个打开的非尾调用计一次，入口那次不计）；计数作为隐含参数沿调用传递，在调用处检查；默认值取转译时的设置，`CAMEL_MAX_RECURSION_DEPTH` 照样生效；`main` 跑在一个按上限留足了栈的线程上 | 7.4 |
| 算子 | 一张“URI → 译法”的表：内联的 C++ 表达式、头文件里的函数、或运行时模块（桥） | 8 |
| 测试 | `test/tools/cppexec/`：转译、编译、运行，与 `std::fvm` 比较标准输出与退出码；进默认测试集的是一份精选清单，全语料的对照另跑 | 11 |

**阶段**（第 12 节）：0 本稿 → 1 新的转译器骨架、测试工具、标量与字符串的子集做对 → 2 标量直接写成运算、尾调用、递归上限、带位置的故障 → 3 起逐步加数组、元组与结构体、`T?`/`T!`、闭包、变量单元、高阶算子、映射与集合，每一步量一次覆盖率。

**要负责人确认的事**共 7 条（第 13 节），最要紧的两条：故障报告是否要与解释器逐字节相同（本稿按“相同”做）；递归计数的代价（调用密集的代码慢约 1.5 倍）是否接受。

## 1. 目标与约束

### 1.1 “脱离运行时”指什么

- **产物**：可执行文件不依赖 `libcamel`，也不在运行时读 Camel 安装里的任何文件（标准库的 `.cmo`、`CAMEL_HOME`）。
- **构建**：需要一个 C++20 编译器和 `camel/standalone/` 这一组头文件。头文件只依赖 C++ 标准库，另外复用 `include/camel/utils/` 里两个本来就只依赖标准库的头文件（`number_text.h`：数与文字之间的规则；`int_div.h`：整数除法的回绕），这样浮点数转文字、整数除法在解释器与生成的程序里是同一份代码。这两个头文件因此必须保持只依赖标准库，文件头的注释里写明。
- **例外**：程序用到没有独立译法的算子时链接 `libcamel`（第 9 节）。转译时给出一条警告，指出是哪个算子、在哪里，使用者知道为什么产物不是独立的。

### 1.2 语义上要守住的

裁定原文要求的三条：故障带源码位置终止、遵守递归上限、尾调用不使栈增长。此外按设计原则的一般要求：

- 按依赖求值：只有活节点（从出口可达）执行（2.1）；同步块与 `wait` 的顺序就是图上的控制边（2.2、2.6）。
- 整数加减乘回绕，最小整数除以 -1 回绕（2.10）；除零、越界、转换越界是故障（2.9、2.10）；浮点数转文字只有一种规则（2.10）。
- 只有显式声明了返回类型的 `main` 的返回值才算程序的结果；没有被处理的错误值到达 `main` 的出口打印到标准错误、退出码非零（2.10）。
- 输出在各平台是相同的字节，Windows 上不写 `\r\n`（2.11）。

### 1.3 可以不同的

- 回收：何时回收、是否回收不可观察（2.11、2.12）。生成的程序用引用计数，经变量单元形成的环不回收（5.4）。
- 对象身份：没有可观察的身份（2.11），所以元组、结构体按值拷贝，字符串可以共享也可以拷贝。但凡是运行时**在原地修改**的对象，生成的程序与运行时共享得一样多（5.2），这不是身份可观察，而是修改要被看见。
- 并行：`map`、`filter` 的元素之间没有顺序（2.7），生成的程序第一步顺序执行它们（13 的 Q6）。

## 3. 总体结构

### 3.1 编译器一侧

```
图（今天的 GCGraph；图存储线合入后是冻结视图）
  └─ 程序分析   入口与 root 上的顶层值；要译的图（具名函数、lambda、泛型实例）；
                 哪些图是分支臂（并入调用它的函数）；调用图与它的强连通分量（尾调用合并、递归）
  └─ 函数分析   每张图：执行序；块与分支的嵌套；每个节点的 C++ 类型与名字；
                 尾位置的调用；可能故障的节点（→ site）；每个值的最后一次使用（→ std::move）
  └─ 发射       类型声明（元组、结构体、闭包）→ site 表 → 函数的前向声明 → 函数体 → 入口
```

源文件（`src/passes/trans/cpp/`）按这几步分开：`program_emitter`（程序分析与整体布局）、`function_emitter`（一张图的块、分支、语句）、`cpp_types`（类型到 C++ 的映射与聚合类型的声明、常量的字面量）、`operator_rules`（算子译法表）、`fault_sites`（故障位置与报告文字）、`bridge`（运行时模块的边界）。今天的 `runtime_emitter.cpp`、`lower.cpp`（那张没有调用点的表，调研 1.1）与 `include/camel/passes/trans/cpp/cpp_bridge.h` 的大部分随之删除。

转译器只经过一处取算子的 URI（`operatorUri(graph, node)`）：图存储线合入后 `OPER` 节点带的是 `OperId`，那时只改这一处，并且改为从算子表项读纯度、`mayFault` 与 `callsGraphs`（图数据模型 3.5 的 `OPER` 卡片），转译器自己的表只剩“怎么写成 C++”。

### 3.2 产物

一个 `.cpp` 文件，依次是：

1. 文件头注释：源文件、怎样构建（独立的程序是一条命令；要链接运行时的写明为什么）。
2. `#include "camel/standalone/runtime.h"`（要运行时的再加 `bridge.h`）。
3. `namespace <模块名> {`：聚合类型的声明；site 表；函数的前向声明；函数体。
4. `int main(int argc, char **argv)`：把参数交给 `rt::run`，后者设好输出、递归上限与大栈线程，调用入口，接住故障并报告，返回退出码。

`a01_fib.cml` 译出来应当是这个样子（拟议；阶段 2 之后以实际输出为准）：

```cpp
// Generated by `camel a01_fib.cml std::cpp` from docs/.../a01_fib.cml.
// Standalone: c++ -std=c++20 -O2 -I"$CAMEL_HOME/include" a01_fib.cpp -o a01_fib
#include "camel/standalone/runtime.h"

namespace a01_fib {
namespace rt = camel::standalone;

// Places that can fault, with the source excerpt a fault there reports.
constexpr rt::Site site_1{"docs/.../a01_fib.cml", 4, 36, "__g_6__", " 4 |     return if n <= 1 ..."};
constexpr rt::Site site_2{...};

int64_t fib(rt::Depth depth, int64_t n) {
    if (n <= 1) {
        return n;
    }
    const int64_t v1 = fib(rt::call(depth, site_1), rt::sub(n, 1));
    const int64_t v2 = fib(rt::call(depth, site_2), rt::sub(n, 2));
    return rt::add(v1, v2);
}

int64_t main_(rt::Depth depth) {
    rt::println(fib(rt::call(depth, site_3), 32));
    return 0;
}

} // namespace a01_fib

int main(int argc, char **argv) { return camel::standalone::run(argc, argv, a01_fib::main_); }
```

`include/camel/standalone/`，只用 C++20 标准库，全部 `inline`：

## 4. 值的表示

| Camel | C++ | 说明 |
|---|---|---|
| `int`、`i32` | `int64_t`、`int32_t` | 加减乘、取负、`+=` 等用 `rt::add` 一类的内联函数：经无符号运算回绕，编译出来与 `+` 相同；比较直接写 `<` 等 |
| `float`、`f32` | `double`、`float` | 直接写 `+ - *`；`/` 除以零是故障（与运行时一致【读码 `src/builtin/operators/ops.cpp` 的 `__builtin__div__`】），所以写成 `rt::div(a, b, site)` |
| `bool` | `bool` | `&`、`\|` 两边都已求值，写 `&&`、`\|\|` 不改变语义；`&&`、`\|\|` 运算符在图上本来就是分支（2.11） |
| `string` | `rt::Str` | 一个指针大小的句柄，指向 `{计数, 长度, 容量, 字节}`；空串是空指针。字面量是静态存储的“永生”对象（计数从一个不会减到零的值开始），不分配 |
| `T[]` | `rt::Array<T>` | 句柄，指向 `{计数, 长度, 容量, T 元素}`；元素是 `T` 的 C++ 表示，`int[]` 是连续的 `int64_t`。可以原地修改（5.2） |
| 元组 `(A, B)` | 生成的 `struct`（`Tuple_i64_str { int64_t _0; rt::Str _1; }`） | 按值。带 `==`（逐个元素，2.10）与打印 |
| 结构体 `{ x: A }` | 生成的 `struct`，字段同名 | 按值。类型有别名时用别名作类型名 |
| `T?` | `rt::Opt<T>` | 标量是“值 + 一位标记”；句柄类型用空句柄表示空，不多占位 |
| `T!` | `rt::Fallible<T>` | “值 + 错误句柄”，错误句柄非空即出错 |
| 错误值 | `rt::Error` | 句柄，指向固定的内建结构：种类名、消息、源码位置（2.9） |
| 函数值 | `rt::Fn<R(Args...)>` | 句柄，指向 `{计数, 代码指针, 捕获的值}`；每个 lambda 一个生成的闭包类型。没有捕获的函数常量是静态的永生对象，不分配 |
| `var T`（变量单元） | 不逃出所在函数时是一个 C++ 局部变量；否则 `rt::Cell<T>`（句柄） | 5.3 |
| `Map<K, V>`、`Set<K>` | `rt::Map<K, V>`、`rt::Set<K>` | 句柄，按键排序的数组；操作返回新值，计数为 1 时原地改。遍历与打印按键排序（2.10），与运行时一致。要换成持久化的树，等量过再说 |
| `void` | 不产生 C++ 值；要占位时是空的 `rt::Unit` | 没有 `else` 的 `if` 的空臂（2.10） |
| 张量、`PyObject` 等外部对象 | `rt::Foreign`（句柄，内部是运行时的 `RootHandle`） | 只出现在链接运行时的程序里（第 9 节） |
| `any` | 拒绝 | 2.11：编译之后不应当有运行时还不确定的类型；`any` 正在收紧（2.12），不为它设计表示 |

**为什么值类型只给元组、结构体、`T?`、`T!`。** 它们在运行时里也是不可变的（字段不可赋值，2.9），按值拷贝与共享分辨不出来（1.3）；按值放在 C++ 的栈上和寄存器里，不分配（调研 4.5 的丁一）。数组、映射、字符串可能很大，按值拷贝的代价与大小成正比，而且数组会被原地修改（5.2），所以是句柄。

**对外的签名。** `std::cpp::module` 写出的函数签名用上表的类型。它们是生成的程序自己的类型，不是运行时堆上的指针，调用方不用遵守句柄规则（调研的 Q8 因此不再成立）；`rt::Str` 可以与 `std::string_view` 互相转换。

## 5. 内存

### 5.1 引用计数

每个句柄类型是一个小的 C++ 类：拷贝构造加一，析构减一，减到零释放（并递归地释放它拿着的句柄），移动不改计数。转译器在**每个值的最后一次使用处**写 `std::move`，于是“传给下一个算子然后再也不用”的值不产生加减。图上直接有这个信息：一个节点的使用者都是边（调研 4.3 列的理由）；在按执行序排好的语句里，最后一个使用者之后的位置就是最后一次使用。

计数不用原子操作：生成的程序是单线程的（1.3）。将来并行执行 `map` 时，在交给别的线程之前把计数换成原子的，或者在交接处转移所有权（第 14 节）。

【实测】两百万个短命字符串（调研的 `a04_string_churn`，附录 A 的 `churn.cpp`）：

| | 用时 | 峰值内存 |
|---|---|---|
| `std::fvm`（默认回收器） | 0.76 s [0.73, 1.15] | 123.5 MB |
| 独立的 C++，引用计数 | 0.27 s [0.17, 0.39] | **9.7 MB** |
| 独立的 C++，从不释放（“丙零”） | 0.33 s [0.29, 0.54] | 125.9 MB |

引用计数既比不释放快（释放的内存马上被下一次分配用上，不需要向系统要新页），内存又与存活数据成正比。

### 5.2 与运行时共享得一样多

运行时里有在原地修改对象的算子：`append`、`extend` 的签名是 `(var arr: T[])`，实现是在原数组上追加再返回同一个数组【读码 `src/builtin/operators/struct.cpp` 的 `__append_arr__`】；图上是 `:var/get` 读出数组、交给 `:struct/append_arr`【实测 附录 A 的 `g1.cml`：`var xs = [1, 2]; xs->append<3>; println(xs)` 打印 `[1, 2, 3]`，图上 `append` 的输入是 `:var/get` 的结果】。修改经过的是**数组对象**，不是变量单元。

所以生成的程序不能把数组当作值来拷贝（“写时拷贝”也不行：变量单元与 `:var/get` 的结果同时拿着这个数组，计数是 2，一拷贝修改就丢了）。规则是：**运行时用同一个对象的地方，生成的程序用同一个句柄**；修改作用在句柄指向的对象上，所有拿着它的人都看得见，与运行时完全一样。这条规则让生成的程序不依赖调研 Q3 / 附录 B O1（`append` 是原地修改还是返回新值）的裁定：裁定之后运行时怎么改，生成的程序跟着同一张算子表改。

“计数为 1 时原地改”只用在**语义上返回新值**的算子上（`concat`、`slice`、字符串拼接、映射的 `put` 与 `remove`）：计数为 1 说明没有别人拿着它，改了也没人看得见。例如循环里的 `acc + piece`，`acc` 在最后一次使用处被移动进拼接，计数为 1，直接在 `acc` 的缓冲区后面追加，摊还 O(1)。

### 5.3 变量单元

`var x` 在图上是 `:var/new` 建立的单元，读写是 `:var/get` 与赋值算子（2.5）。

- **单元不逃出所在的函数**（它的使用者只有 `:var/get`、赋值算子，以及并入本函数的分支臂里的这两种）：一个 C++ 局部变量。这是绝大多数 `var` 的情形。
- **否则**（作为 `var` 实参传给别的函数、被闭包捕获、交给别的算子）：`rt::Cell<T>`，一个句柄，指向 `{计数, T 值}`。传参、捕获都是拷贝句柄，所有人看到同一个值，满足 2.5“闭包对变量的捕获也是引用”。

### 5.4 环

值由下往上构造、构造之后不变（2.9），所以值之间不成环；数组的原地修改只能追加已经存在的值，也不成环——除非数组里放进了一个拿着这个数组的闭包，那必须经过变量单元或 `var` 形参，同样归到下一种。唯一的环经过变量单元：单元里放着一个捕获了这个单元的闭包（调研 Q2 的例子）。引用计数不回收它。2.12 已经裁定“后端可以少回收甚至不回收垃圾”，所以这是允许的；它泄漏的是一个闭包和一个单元，大小与程序写了多少这样的变量成正比，与运行多久无关（每次执行到那个 `var` 才产生一个）。若将来要回收，加一个只扫描单元的环检测（单元是唯一能成环的节点），不影响别的部分。

### 5.5 没有选的做法

- **区域（竞技场）**：每次 `map` 的元素调用、每轮循环一个区域，结束时把结果拷出来再整块释放。拷出与结果的大小成正比，循环状态是一个越来越长的数组时总量是平方级（调研 4.3 乙三）；要避免就得做区域推断。引用计数没有这个问题，而且图上的使用信息本来就够用。
- **不回收**：最简单（今天就是这样，调研 2.2），但长时间运行、持续分配的程序会耗尽内存；上表也显示它并不更快。
- **C++ 标准库的值类型**（`std::string`、`std::vector`）：拷贝是深拷贝，要不慢就得做与引用计数相同的“最后一次使用”分析；共享又要退回 `shared_ptr`。而且数组必须共享（5.2）。只有元组、结构体、`T?`、`T!` 用值类型（第 4 节）。
- **`std::shared_ptr`**：两个字（对象指针与控制块指针）、原子计数、控制块另外分配。自己的句柄是一个字、非原子、计数与数据在一起。

## 6. 控制流与顺序

### 6.1 执行序

每张图的语句按 `buildReachableExecutionTopoIndices` 给出的执行序排列【读码 `src/execute/graph_runtime_support.cpp`】。这是 `std::fvm` 编字节码用的同一个序（图数据模型 5.1 把它定为 `ExecPlan::order()`）。它是三组边（数据、`with`、控制）的拓扑序，只含从出口可达的活节点，并把每个分支的臂排成连续的一段。

用同一个序有一个具体的好处：**语言没有规定先后的两个效应**（同步块之外互不依赖的两次打印），在生成的程序里与在 `std::fvm` 上也是同一个先后，于是两者的输出可以逐字节比较。这不是语义的要求（2.1），是测试的便利，代价为零。

只有活节点被译出来：同步块之外结果没被用到的效应不执行（2.1、第 5 节误读 1）。

### 6.2 分支

`BRCH`/`JOIN` 译成语句：

```cpp
int64_t v4;                      // JOIN 的值；没有值（void）时不声明
if (cond) {
    ... 臂 0 的语句 ...
    v4 = <臂 0 的值>;
} else {
    ... 臂 1 的语句 ...
    v4 = <臂 1 的值>;
}
```

`match` 是一串 `if`/`else if`，比较用该类型的 `==`（字符串按内容，修 D3）。这个复合语句放在执行序里 `BRCH` 所在的位置，臂里的节点只出现在臂里：分支只执行一次（修 D4），分支之后的效应在分支之后（修 D5）。

臂的两种形态（图数据模型 3.5、设计原则 2.12）都认：

- **子图形态**：臂是一个 `FUNC` 节点，被调图是臂图。把臂图的语句并入当前函数，臂图的端口绑定到 `FUNC` 节点的实参。并入是递归的（臂里还有分支）。
- **区域形态**（`std::inline` 之后）：臂的节点在当前图里，位于 `BRCH` 与 `JOIN` 之间，按执行序里的区间取出（修 D11）。

不能并入的 `FUNC`（具名函数、泛型实例、`std::inline` 留下的普通调用）是 C++ 的函数调用。

### 6.3 尾调用

**自尾调用**：函数体包在 `for (;;) { ... }` 里，尾位置上对自己的调用写成“算出新的实参、赋给形参、`continue`”。尾位置：函数的返回值就是这个调用的值，中间只经过 `JOIN`（臂的值）与 `GATE`（且 `GATE` 等的节点都排在调用之前）。形参因此不是 `const`；句柄类型的形参被赋值时，旧值的计数照常减一。

**互相尾调用**（`is_even` / `is_odd`）：在“尾调用图”（只看尾位置的调用）上求强连通分量；一个分量里有多个函数时，把它们合成一个函数：各自的形参都是局部变量，一个 `switch` 选当前在哪个函数里，尾调用改变选择子再 `continue`；每个原函数保留一个入口，转调合成的函数。这是可移植的写法（不依赖 `[[clang::musttail]]`，MSVC 没有它）。阶段 2 先做自尾调用；合成放在阶段 3 之后，在那之前互相尾调用按普通调用计数（13 的 Q4）。

**经函数值的尾调用**（续延传递风格）：照普通调用处理，计入递归深度并使用栈。这与调度器不同（调度器的尾调用一律不计数），列入第 14 节。

**`LOOP` 节点**（循环线设计中，图数据模型 3.5）：落地之后直接写成 C++ 循环；在那之前它在入口处被降级为尾递归子图，走上面的路。

### 6.4 效应与顺序

同步块（2.2）与 `wait`（2.6）在图上就是控制边；执行序已经尊重它们（6.1），转译器不需要别的处理。`GATE` 不产生语句，它的值就是输入的值；`SYNC`（内联遍的汇合点）只承载顺序，也不产生语句——今天它被当作“同步块”拒绝（D11），新转译器认它。

## 7. 故障、错误值、`attempt`、递归上限

### 7.1 故障

可能故障的算子（除零、越界、转换越界、文字不是一个数、`slice` 越界、`head` 空数组……）在生成的代码里多一个实参：它的 `site`。`site` 是一个 `constexpr` 对象，带模块名、文件、行、列、所在图的名字与报告用的源码摘录。出故障时头文件里的函数抛出 `rt::Fault{种类, 实参, site}`。

`rt::run` 接住它：先刷新标准输出，再按 `CAMEL_ERROR_FORMAT`（`text`，或测试用的 `short`）写出报告，退出码 1。**报告写在标准输出上**，因为解释器就写在那里【实测：`camel d03_div_zero.cml std::fvm 2>/dev/null` 仍然打印出报告；`2>&1 >/dev/null` 什么也没有】。

报告的文字与解释器逐字节相同。做法是把它拆成三部分，各自取自编译器的唯一出处：

- **种类的名字、代号、消息模板、提示**：取自诊断表（`getRuntimeDiagInfoMap`），程序用到哪几种故障就写出哪几种，放在生成的文件里；头文件只按模板填入实参。
- **源码摘录**（`  --> 文件:行:列`、行号槽与 `^^^` 那几行）：转译时用编译器自己的渲染器（`src/core/error/diagnostics/render.cpp`）对 site 的位置渲染好，作为字符串常量写进 site。不在头文件里重写一个渲染器，免得两份代码在制表符、宽字符、长行截断上不一致。为此给渲染器加一个公开的小函数，只渲染摘录。
- **运行时才知道的实参**（越界的下标、数组的长度、递归上限的值、出故障的图名）：头文件按消息模板的 `{0}`、`{1}` 填入。

颜色：解释器在终端上给报告上色；生成的程序不上色（测试与管道里两者都没有颜色）。

### 7.2 错误值与 `attempt`

错误值（`T!` 的错误一侧，2.9）是 `rt::Error`：种类名、消息、位置。`throw error('Kind', 'message')` 构造它，位置是转译时已知的 site。`??`、`!!`、`?->` 与 `match` 的固定模式在图上是分支（第 1 节对应表），按 6.2 译出，条件是 `rt::Opt::has_value()` 或 `rt::Fallible::failed()`。

`attempt(f, x)`（`:mark/isolate`）是一次带标记的调用（设计原则第 1 节对应表）：

```cpp
rt::Fallible<int64_t> v7 = rt::attempt([&] { return risky(rt::call(depth, site_5), x); });
```

`rt::attempt` 用 `try`/`catch (const rt::Fault &)` 把故障变成错误值，消息与位置取自故障。递归上限的故障也能被隔离，与调度器一致【未查：调度器是否隔离递归上限故障，阶段 3 实测】。被隔离的调用里已经产生的输出保留（与调度器相同：输出是效应，不回滚）。

没有被处理的错误值到达 `main` 的出口：打印到标准错误，退出码非零（2.10），与解释器的写法相同（阶段 3 对照）。

### 7.3 程序的入口与退出

- `main` 声明了整数返回类型：返回值的低 8 位是退出码【实测：`return 300` 的退出码是 44】；`main` 是纯的（没有 `sync`）时也一样，不打印【实测 `func main(): int { return 7 }`：没有输出，退出码 7】。
- `main` 声明了别的返回类型：值按 `println` 的写法打印到标准输出，退出码 0【实测：返回 `'hi'` 打印 `hi`；返回 `0.1 + 0.2` 打印 `0.30000000000000004`】。
- 没有声明返回类型：不打印，退出码 0（D9 的第二半）。
- `exit(n)`（`:exit`、`os:exit`）：刷新输出，退出码 n（D9 的第一半；今天被 `catch (...)` 吞成 `Unknown error`）。
- 带参数的 `main`（2.7：值来自命令行）：生成的程序接受与命令行工具相同的 `--arg 名字=值`，缺少时给出带位置的错误（13 的 Q7）。
- root 上算出来的顶层值（2.11：在 `main` 开始之前求值）：root 图本身也译成一个函数 `entry_`，它算出顶层值再调用 `main`；今天这种程序被拒绝（调研 1.3 的 `r12`）。

### 7.4 递归上限

规则与调度器相同【读码 `include/camel/execute/limits.h`】：数“同时打开的、不在尾位置的调用”，入口对 `main` 的那次不计；上限 L 时，`main` 调用的 `depth(L - 1)` 是能跑完的最深一次。故障报告名字是**发出调用的那张图**、位置是调用处【实测 `d02_deep_recursion.cml`：`Maximum recursion depth (1000) exceeded when evaluating graph '__g_6__'`，位置是 `depth(n - 1)`】。

三种做法的实测【实测：`proto/fib_sa.cpp`、`proto/fib_sa2.cpp`，`fib(37)`，各 9 轮】：

| 做法 | 用时 | 相对 |
|---|---|---|
| 不计数 | 0.083 s [0.075, 0.088] | 1.0 |
| 计数作为隐含参数，调用处检查 `depth + 1 > limit` | 0.123 s [0.110, 0.126] | 1.5 |
| 计数放在全局变量里，被调函数入口加一、出口减一（RAII） | 0.181 s [0.164, 0.202] | 2.2 |

选第二种：每个会发出调用的函数多一个形参 `rt::Depth depth`，调用写成 `f(rt::call(depth, site), ...)`，`rt::call` 检查后返回 `depth + 1`。计数在寄存器里，不读写内存；检查放在调用处，所以报告的图名与位置与调度器一致；不发出任何调用的叶子函数不需要这个形参。尾调用写成循环，不经过 `rt::call`，所以不计数，与调度器一致。

上限的默认值是转译时的设置（`--max-recursion-depth`、`CAMEL_MAX_RECURSION_DEPTH`，否则 1000），写进生成的程序；运行时 `CAMEL_MAX_RECURSION_DEPTH` 仍然可以改它，与解释器相同。

**原生栈。** 上限可以调到一百万（`kMaxDepthLimit`），每层几十到几百字节，主线程的默认栈（Linux 8 MB、Windows 1 MB）不够。`rt::run` 在一个新线程上运行程序，栈的大小按上限留足（每层按 512 字节估，至少 64 MB，最多 1 GB；只是保留地址空间，用到的页才占内存）：POSIX 用 `pthread_attr_setstacksize`，Windows 用 `CreateThread` 的栈大小参数。这是头文件里唯一与平台相关的代码。

## 9. 运行时模块的边界

**何时。** 一个算子在表里没有独立译法，而它的实参与结果都能在独立的表示与运行时的表示之间转换（标量、字符串，之后加数组、元组等）时，经桥调用。不能转换的（`any`、函数值交给运行时算子）拒绝。

**怎样。** 生成的代码写：

```cpp
const double v5 = rt::bridge::call<double>(op_4, site_4, {rt::bridge::arg(x)}, {});
```

`op_4` 是一个按 URI 第一次使用时在运行时的算子表里查到并缓存的访问器。`bridge::call` 在调用的这一条语句里：把实参转换成运行时的值（字符串在运行时的堆上新建一个），放进**每次调用在栈上新建**的实参区（今天的实参区是整个进程共用一份，不可重入，调研 1.7），调用算子，把结果转换回独立的表示。运行时堆上的对象只活在这一条语句里，期间没有安全点（句柄规则第 1 节），所以不需要登记根；生成的代码从不拿着运行时的指针。

**外部对象**（张量、`PyObject`）不能转换，只能由运行时拿着。它们在生成的程序里是 `rt::Foreign`：一个带计数的句柄，里面是一个 `mm::RootHandle`。计数减到零时释放 `RootHandle`，对象交回运行时的回收器。生成的程序在桥调用之间（此时它不拿着任何运行时的裸指针）调用一次 `mm::safepoint()`，回收器可以运行。这样“运行时对象只经句柄接触”（2.11）在生成的代码里同样成立。张量支持放在阶段 3 之后。

**故障。** 运行时的算子抛出 `RuntimeFault`。`bridge::call` 接住它，换成带调用处 site 的 `rt::Fault`，种类、消息与提示取自运行时自己的诊断表（此时 `libcamel` 已经链接），报告的格式与 7.1 相同。

**初始化。** 第一次桥调用时建立运行时的 `Context`（模块查找路径来自 `CAMEL_HOME` 与可执行文件所在目录，与今天的 `cpp_bridge_runtime.cpp` 相同），只加载用到的模块；程序结束时释放。没有桥调用的程序什么都不做。

**转译时的警告。** 程序要链接运行时，转译时给出一条警告（新的诊断，`docs/diagnostics.md` 随之更新），位置是第一个经桥的算子，并列出全部经桥的算子。生成的文件头注释写同样的内容与构建命令。

## 10. 构建与工具

- **一条命令**：`c++ -std=c++20 -O2 -I"$CAMEL_HOME/include" x.cpp -o x`。要链接运行时的程序另加 `-L"$CAMEL_HOME/bin" -lcamel` 与运行时自己的依赖，文件头注释写全。
- **`camel-cpp`**：今天它自己重做了一遍命令行工具的解析与编译，只在 Windows 上能找到 `libcamel.lib`（D12）。改为一个小的驱动：调用同目录下的 `camel <文件> std::cpp` 得到 `.cpp`，再用 `$CXX`（否则依次找 `clang++`、`g++`、`cl`）按上一条编译；需要运行时时加上链接参数。不再链接 `libcamel`。
- **CMake**：不提供。`docs/cpp_export_build.md` 里的“方式 A”（`CPP_GEN_SOURCE`、`cpp_gen` 目标）在 CMake 里不存在（D12），文档改写为上面两种。生成的是一个文件、一条命令，使用者把它放进自己的 CMake 工程只需要一个 `add_executable` 与一个包含目录，文档给出这三行。
- **编译时间**：今天的产物包含运行时的大半头文件，`a01_fib.cpp` 编译 6.9 秒【实测，负载下】；只用标准库的原型 0.22 秒【实测】。阶段 1 量真实头文件的数字。

## 13. 要负责人确认的问题

### Q1 故障的报告要不要与解释器逐字节相同

候选：

- 甲：相同。生成的程序把报告写在标准输出上（解释器就写在那里），文字、源码摘录、`CAMEL_ERROR_FORMAT` 都一样，只是不上色。
- 乙：只要求带位置；格式由生成的程序自定（例如写在标准错误上、一行）。

**建议甲**，并按甲做：测试可以逐字节比较两种后端，使用者看到的诊断也一致；代价是生成的文件里每个可能故障的位置多一段源码摘录的字符串。这里只问“是否要求”，不改变解释器的行为。

### Q2 递归计数的代价

精确计数让调用密集的代码慢约 1.5 倍（7.4 的表；不计数的 `fib(37)` 0.083 秒，计数 0.123 秒，`std::jit` 的 `fib(32)` 0.035 秒、独立的 0.017 秒）。

- 甲：与调度器相同地精确计数（本稿的做法）。
- 乙：不计数，只在原生栈将尽时以同一个诊断终止。快，但上限不再是 1000 层，而取决于每层的栈帧大小，与调度器不一致。
- 丙：由一个转译时的选项决定（要等“给遍传参数”的机制，2.7）。

**建议甲**：裁定说“遵守递归上限”，而上限是一个可以对照的数。将来有了遍参数可以加丙。

### Q3 运行时里看起来是意外的两处打印

`println<'{}+{}'>(1, 2)` 打印 `1+2` 和一个空行；`print<'{}-{}'>(3, 4)` 打印 `3-4` 和换行【实测】。生成的程序照样复现。这两处是有意的吗？如果是缺陷，修运行时，生成的程序同一次修改。

### Q4 互相尾调用在合成之前

阶段 2 只把自尾调用写成循环；互相尾调用（6.3 的合成）放在阶段 4。在那之前，互相尾递归在生成的程序里要计入递归深度并使用栈，与调度器不同（调度器上它不计数）。

- 甲：接受这个过渡，阶段 4 补齐。
- 乙：在补齐之前拒绝含互相尾调用的程序。

**建议甲**；转译时对这样的调用给一条警告。

### Q5 `std::cpp::bench`

这个模式先找名叫 `fib` 的图，找不到才用 `main`（调研 1.1），看不出用途。建议删去这个模式与别名 `std::cppbench`；`std::cpp::module`、`std::cpp::inspect` 保留。

### Q6 生成的程序里的 `map`、`filter`

2.7 说元素之间没有顺序、并行调度器可以并发执行。生成的程序第一步按下标顺序执行：一个元素出故障时报的就是下标最小的那个（2.10 的“并行的 map 中一个元素出了故障”一条），已经开始的元素跑完、没开始的不再开始，都自然成立。建议先这样，并行放在阶段 5。

### Q7 生成的程序怎样接收 `main` 的参数

2.7：“运行时由外部给值（命令行）”。建议与命令行工具相同：`./x --arg n=3 --arg name=hi`，按 `main` 的形参类型解析，缺少时给出带位置的错误（与 `camel` 的诊断相同）。另一个候选是按位置（`./x 3 hi`），更像普通的程序，但与 `camel` 的写法不同。

## 14. 最不放心的地方

1. **共享的规则是从运行时的算子实现里一个一个读出来的**（5.2）。哪些算子在原地改它的实参，今天没有声明，只能读实现；漏掉一个，生成的程序就会在那个算子上与解释器不同。算子表加“修改哪个实参”的声明之后（图数据模型 Q1 的方向），转译器改为读声明。
2. **引用计数的正确性**靠头文件里的少数几个类与转译器写 `std::move` 的位置。`std::move` 写错的后果是读到被移走的空句柄，而不是悄悄读到别的对象；11 的计数检查与地址消毒器能发现泄漏与重复释放。
3. **故障报告的“逐字节相同”**依赖转译时渲染的摘录与运行时的渲染一致；渲染器以后改格式时两者同时改（同一份代码），但 `CAMEL_ERROR_FORMAT=json` 这类格式本稿没有覆盖，第一步只做 `text` 与 `short`。
4. **执行序与 `std::fvm` 相同**只在两者都用 `buildReachableExecutionTopoIndices` 时成立；即时编译线或图存储线如果改了 `std::fvm` 取序的方式，这一点要跟着检查（`ExecPlan::order()` 统一之后自然成立）。
5. **桥只在一条语句里**这一点，对“会回调 Camel 函数的运行时算子”不成立；今天这样的算子（高阶算子）都由转译器自己写成循环，第三方模块里如果有，要拒绝。
6. **只在 Linux、clang 上实测过。** Windows（MSVC 与 clang-cl）的编译、大栈线程、二进制模式的标准输出要在阶段 2 之后核实【未查】。
