# 图上的三种边：数据、同步、顺序（设计稿）

状态：已定（负责人 2026-10-23 同意，写入设计原则 3.1）。

数表：[`liveness-fills.cn.md`](liveness-fills.cn.md)——"被用到"这条判定落在哪六处、每处填哪几个字段、从输入侧还是用户侧读，每行带 `文件#符号`、行号与上次改动它的提交。

## 1. 三种边（已定）

| 边 | 含义 | 来源 |
|---|---|---|
| **数据边** | 值从哪来；被用到的节点经它把"被用到"传给它读的节点；也决定先后 | 值的传递（含捕获、区域的输入输出） |
| **同步边** | 同步块里语句之间的边：后一条在前一条之后，并且前一条因此被用到 | `sync` 块（含函数体的 `sync`）里的语句链，链尾连到块的值 |
| **顺序边** | 只排序：两端都执行时，前者在后者之前；不传递"被用到" | 同一资源上的效应之间；同一 `var` 的写与写之间；内联展开的同步链（第 5 节第 7 条） |

- 三种边都是图的原生边，不借用"令牌"一类从命令式语言模拟声明式语义的概念。
- **纯计算没有顺序边；纯且不会出故障的计算也不在同步链上**（可能出故障的计算留在链上，因为故障可观察，3.4）：它执行与否完全由值是否被用到决定，先后完全由数据依赖决定。同步链只连带效应的语句（设计原则 3.4，2026-10-24 改：同步块只给效应排序，计时用 `time::timed`）；唯一的例外是块的值接收链尾的同步边。优化遍（规则匹配、公共子表达式合并、常量折叠、删死代码）因此不再被控制边挡住。
- 原来"一律生成控制边"的建图方式改为按来源生成这三种边；"控制边"这个种类不再存在。

## 2. 执行规则（已定）

一个节点执行，当且仅当从程序的结果出发，沿**数据边或同步边**能到达它；顺序边不参与。在要执行的节点之间，先后同时遵守三种边。

由此推出（与设计原则 3.1 一致）：同步块之外、结果没有被用到的效应不执行；同步块里的语句都执行，按书写顺序；同一资源上两个都执行的效应按书写顺序；不同资源之间没有先后，除非在同一个同步块里。

>
> **更正：** 本节"同一资源上两个都执行的效应按书写顺序"只保证**执行的先后**，不保证**读拿到哪个版本**。20:35 曾据这一条说"未登记的写只由同步块和资源顺序保证，不为它造版本边"；22:50 的裁定已收回这句话——登记表现在按**保守的写者集合**登记（程序里所有写该变量的函数，建图前整个程序扫一遍），看不见的写不再存在。见 [`reviews/questions-2026-10-31-two-references-write-one-object-outside-a-sync-block.md`](../../handover/reviews/questions-2026-10-31-two-references-write-one-object-outside-a-sync-block.md)。

## 1.5 数据边只有一种，端口带角色（已定）

普通参数与上下文参数（`with`）在语义上不同（部分应用、求导、特化、导出都依赖这个区分），但**在图上是同一种数据边**：节点的输入是一列有序的端口，每个端口带角色（普通 / 上下文），角色来自被调函数的签名。不关心角色的遍只看到一个输入列表；关心角色的遍读端口的角色。同步边与顺序边不是数据，不进输入端口列表，单独存放。

| | 存放 | 谁读 |
|---|---|---|
| 数据边（端口带角色） | 节点的输入端口列表 | 所有遍 |
| 同步边 | 节点的同步前驱 | 调度、存活判断 |
| 顺序边 | 节点的顺序前驱 | 调度 |

## 3. 效应的返回值（已定）

`println(x)` 返回 `x`。目的是方便写 `x->println->f` 这样的调试代码，看数据在每个阶段的样子；它不是让效应执行的机制。（按第 2 节，`x->println->f` 里 `println` 的值被 `f` 用到，所以它自然执行。）

## 4. 各个遍怎么对待三种边

- **删死代码**：沿数据边与同步边判断是否被用到；删掉节点时把穿过它的顺序边接上（A→B→C，删 B 后保留 A→C）。
- **调度**：拓扑序遵守三种边；不同资源之间没有边，并行调度器可以并发。
- **内联、改写**：原样复制；替换节点时把它的同步边、顺序边转给替换者。
- **`std::cml`**：同步边与顺序边都可从源码的 `sync` 与资源重新推出，不需要专门的源码表示。

## 5. 表示细节（决策者 2026-10-23，答论文侧的追问；施工中若发现与此冲突的用途，以问题文件提出）

1. **端口的角色由节点种类给出**。调用类节点（算子调用、函数调用）的实参端口取被调签名的角色：普通或上下文；`CALL` 的第一个端口是被调值。结构类节点没有签名，它们的端口按位置由节点种类定义：`JOIN` 的第 0 个端口是 `BRCH` 的值（选中的臂号），其后是各臂的结果（按臂的序号）；`LOOP` 的端口是初始状态、各区域的结果与轮次计数；`BRCH` 的端口是条件。不关心角色的遍只看到一列端口。
2. **`BRCH` 与臂之间没有边**，只靠区域归属：臂是 `BRCH` 拥有的 `Arm` 区域（区域的父是它的 `BRCH`）。结构规则改写为：**属于某条臂区域的节点，只在那条臂被选中时执行**（取代"等待 `BRCH` 的活节点都在它的某条臂里"）。
3. **`SYNC` 节点删除；`GATE` 保留为"同步链之后放行一个值"的节点，只在需要时生成**（决策者 2026-10-24 更正同日"`GATE` 删除"）。同步链的链尾连到块的值，但块的值节点可能**不归这个块独有**：形参、常量、被别处也用到的节点、或建在块外的节点。往这样的节点上挂同步边，会让它的**所有**使用者都排到链之后、并把链拉活，这是错的。所以：块的值节点归这个块独有（在块里新算出来、没有别的使用者）时，链尾的同步边直接连到它；否则生成一个 `GATE`——一个数据端口读那个值、一个同步前驱是链尾，值原样放行。`GATE` 不再有控制输入（控制边已不存在）；它是纯的传值节点：匹配与求值时**透过** `GATE` 看它的值；但 `GATE` 本身不能删除、也不能被它的输入替换（那样同步边会转到共享的值节点上，回到上面的问题），除非它的同步前驱已经不存在。按"改写不丢效应"的判据，带同步边的 `GATE` 算含效应，引擎本来就不会让规则丢掉它。

3.1 **`GATE` 的两种用处，各有一句判据**（2026-11-03，链位 `GATE` 落地后量出来的）：**链位 `GATE` 必有下文，块的值 `GATE` 是链的最后一站**。一条纯值语句站到同步链上时，链的位置由 `GATE` 表示（纯值上不许挂顺序边，第 4.6 条），链**从它继续往下走**，所以链位 `GATE` 必定有后继；块的值 `GATE` 把块的值交给链尾，它自己就是这条链的最后一站，不再有后继。于是"有没有后继"就是这两种用处的判据——全语料 2858 个链位全部有后继，3546 个块值全部没有（一串 `sync` 块的值也一样）。链位 `GATE` 还必定有前驱：链上还没有人时（块的第一条语句就是纯值），那个纯值本身就是链的开头，**不造 `GATE`**——位置只在有先后的时候才有意义，而没有前驱的 `GATE` 会被封存检查拒绝（"GATE node N without a wait"），这一条是 196 个这样的 `GATE` 换来的。
4. **`std::opt::ctrl` 改为只做顺序边的传递约简**（A→B→C 已在时删去 A→C），改名 `std::opt::order`。同步边是一条链，没有冗余；纯计算上不再有任何非数据边，所以这个遍的工作量大幅缩小。
4.5 **"用到"按节点种类定义，执行规则不另加条款**。一个要执行的节点用到哪些输入端口由它的种类决定：调用类用到全部端口；`JOIN` 用到第 0 个端口（因而 `BRCH` 执行）和**被选中的那条臂**的结果端口；`LOOP` 用到初始状态，并按轮次用到各区域的结果。执行规则仍是"从结果出发，沿被用到的数据端口或同步边可达"；臂、循环体里的节点之所以只在选中或有轮次时执行，正是因为 `JOIN`、`LOOP` 只在那时用到它们的结果。
4.6 **提交时检查的结构规则**（图封存时由校验器检查，违反即内部错误）：任何纯节点上没有顺序边；顺序边的两端都是效应节点或可能出故障的节点（`GATE` 算在内）；任何**可自由安排**（纯且不会出故障）的节点上没有顺序边，来源是同一资源上的效应、同一 `var` 的写，或内联展开的同步链（第 7 条）；同步边只连同一个同步块直接写着的相邻语句（或链尾到块的值）；同步边是一条链，所以同一个块的语句里，一条语句最多跟一条、也最多被一条跟（一条语句被两条跟着就是分叉，分叉的链不是链，内部错误）；`JOIN` 的第 0 个端口来自同一区域的 `BRCH`。
5. **已定（负责人 2026-10-23）**：改写不改变哪些效应执行——规则右边丢掉的部分必须是纯的，`x * 0 => 0` 不作用于 `println(5) * 0`（设计原则 9.7，规则语言第二版第 8 节）。
6. **`var` 的读写**（决策者 2026-10-23；`:var/after` 的签名由作者 2026-10-31 定为 `(var T, any) => var T`）：`var` 降为"建 cell"加普通的写。每次写（赋值、写了捕获变量的调用）产出变量的新版本；每次读（`:var/get`、读了捕获变量的调用）有一个数据端口接到书写上最近一次写的产出（没写过则接建 cell 处），调用上这个端口的角色是"捕获"。写与写之间是顺序边，写取 cell 作位置、不取上一次写的产出。**对同一个 cell，一次写排在上一次写之后的每一次读之后，用顺序边表示**（作者 2026-11-03 裁定）；读包括 `:var/get` 和读了捕获变量的调用。这条先后由建 `var` 写的那一处自己写出，**不由链位承担**——读站在哪条链上是另一件事：`sync` 块里把纯节点从链上拿掉、换成 `GATE` 之后，写仍由这条边排在读之后。由此"读用到最近一次写、没被读的写不执行"（F3）直接由数据边与顺序边表达。写者是一次**经由函数值的调用**时，它写了哪个变量这一层不知道（它捕获了哪些变量由运行时的值决定），读的那个数据端口接在 `:var/after(cell, call)` 上：结果是那个单元本身，第二个实参是那次调用、**可以是任意值（含 `void`）、不被读**——这条边就是"读用到它"让调用执行的全部凭据（3.1）。
7. **内联与同步链：不需要 `BLOCK`**（决策者 2026-10-24，取代同日"经 `BLOCK` 挂链"；3.4 改为只给效应排序之后）。同步链上只有带效应的语句，所以一条调用语句被内联时：函数体直接拼进调用者；从链上前一条语句向函数体里每个效应节点**与可能出故障的节点**连一条**顺序边**，再从它们向后一条语句连一条（两端都是效应或可能出故障，合 4.6）；函数体的结果代替原来的调用接回同步链（值节点不归该处独有时经 `GATE`）。纯计算不受约束。写在同步块里作为一条语句的嵌套块 `{ … }` 同样处理。这取代了旧 `SYNC` 节点在内联中的作用（负责人说明：`SYNC` 原用于内联后让子函数的全部输入在某个节点之后执行，保持函数边界划定的顺序）；不在同步链上的调用，函数边界本来就不规定先后，内联后直接拼接。
8. **区域自身没有语义，语义来自它的所属节点**（决策者 2026-10-24）：区域分两类，界线是"有没有所属节点"。没有所属节点的区域（标签、装饰器、内联体）只是分组标记，遍可以溶解，不影响执行。有所属节点的区域，其含义由所属节点的种类给出，种类是封闭的一小组：分支节点（臂：只在被选中时执行）、`LOOP`（条件与体：按轮次执行）。这与 RVSDG 的 γ/θ/λ 节点、MLIR"区域的语义由其父操作定义"相同。把节点移入或移出这类区域会改变语义，由封存检查与"移出的部分必须纯且不会出故障"约束。

## 6. 一个区域的端口能被谁读（已定 2026-11-03，08:10 收窄）

1. 区域 `R` 的端口（落在 `R` 里的 `PORT` 节点）只有三类读者：`R` 里的节点、`R` 所嵌套于的区域里的节点（内层读祖先），以及 `R` 的**所属节点**（`R.owner`；只有分支的臂与 `LOOP` 的条件、体有所属节点，内联体、标签这类只是分组标记，没有）——**但所属节点只能读 `R` 的出口**（`R.result`，循环条件区同样有出口），不论这个出口是什么种类的节点。
2. 别的读者一律不行，问的是同一件事——读取发生时端口所在的框架在不在：区域里的端口是该区域产出的值，区域跑时它才在；循环体的端口每轮都换，轮到它的是那台循环自己，不是它的邻居。
3. 于是"跨枝读"与"外层读内层"被同一条判据拒绝，唯一的例外是所属节点读自己区域的**出口**：`do s` 的出口恰好是状态端口，`do s + 1` 的出口是 `Oper`，两者对 `LOOP` 是同一件事，所以判据落在"这个端口是不是该区域的出口"，不落在读者的身份，也不落在出口的节点种类上。所属节点读该区域的**其他**端口照样拒绝。违反它的图在封存时与第 4.6 条同处报内部错误（`camel::runtime::checkGraphCrossReferences`），违规文本点名两侧的区域、种类与父区域。
