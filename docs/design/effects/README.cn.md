# 资源效应系统

## 初心

Camel 的程序是图，图上的节点只要数据到齐就能执行；与外界打交道的操作（打印、写文件、读时钟）却有先后，有的能删、有的不能。资源效应系统回答一个问题：**一次访问，遍可以对它做哪些变换。** 删掉它、把两次合成一次、和别的操作调换先后——每一种都只在某些访问上成立。把"哪些变换成立"写进资源的声明，遍就不必认识具体的算子：死代码消除、合并重复计算、重排与并行，全部从资源声明读出来。

设计原则第 3 节给出规则（资源、句柄、`uses`、`pure`、推断、同步块）；这里讲这些规则背后的框架，以及各个资源修饰词从哪里来。

## 四条等式

对一次访问，遍能做的变换归结为它满足的四条等式：

- **丢弃**：结果没人用的访问可以删。死代码消除依赖它。
- **复制**：两次相同的访问等于一次。合并重复计算依赖它。
- **交换**：两次访问可以调换先后。重排、并行、"不排序"依赖它。
- **擦除**：在语义里，这次访问等于什么都没做。

前三条来自 Kammar 与 Plotkin 对依赖效应的优化的刻画（*Algebraic foundations for effect-dependent optimisations*，POPL 2012）：编译器能做的变换，恰好由效应操作满足哪些等式决定。Benton、Kennedy、Hofmann、Beringer 以读、写效应证明这些变换何时成立（*Reading, writing and relations*，APLAS 2006）；按区域区分读写的效应系统始于 Gifford 与 Lucassen（1986）。第四条是 Camel 为"观察"加的。

## 读与写各自满足什么

**读**（不改变资源的访问）总满足丢弃；两次读之间没有写时满足复制；读与读满足交换。改变资源的"读"——从标准输入取走一行、读时钟（读到的值随时间变）——按写算（原则 3.3）。所以读不需要修饰词。

**写**默认什么都不满足：不能删、不能合、同一资源上不能调换。写可能满足的等式各有一个修饰词：

| 修饰词 | 写满足的等式 | 遍因此可以 | 例子 |
|---|---|---|---|
| `unordered` | 写与写交换：w₁; w₂ = w₂; w₁ | 不排序、并行 | 计数器累加、往集合里加元素 |
| `idempotent` | 同样的写复制：w(v); w(v) = w(v) | 合并重复的写；中断后重做、推测执行 | 把张量搬到设备、设定随机种子、确保目录存在 |
| `overwriting` | 后写覆盖先写：w(v₁); w(v₂) = w(v₂)（中间没有读） | 删掉被覆盖的写（死存储消除） | 把文件内容整个重写、设定一个配置值 |

另外两个修饰词不是写的等式，而是限定资源本身：

| 修饰词 | 意思 | 例子 |
|---|---|---|
| `readonly` | 只有读，没有写 | `graph`、`spelling` |
| `observed` | 只有写，且写在语义里满足擦除：w = 什么都没做 | `debug::channel` |

"冲突的访问自动有序"（原则 3.3）就是交换的反面：同一资源上至少有一方是写、且这对访问不满足交换的，按书写顺序排序。

## 组合

修饰词可以叠加，等式也就叠加；有的组合相互矛盾，编译器在资源声明处拒绝：

- **`unordered` + `idempotent`**：写既可交换又可合并，就是向一个半格做并（join）。例如往集合里加元素、取最大值、置位标志。这样的写在任何并行调度下结果都确定，是确定性并行的基础（LVars，Kuper 与 Newton，2013）。
- **`overwriting` 蕴含 `idempotent`**：w(v); w(v) 按覆盖等于 w(v)。两个都写不报错，但只需写 `overwriting`。
- **`unordered` + `overwriting` 矛盾**：两次写既能调换、又只留后一次，推出两次写必须相同。拒绝。
- **`readonly` 与任何写的修饰词矛盾**：它没有写。拒绝。
- **`observed` 与 `readonly` 矛盾**：只读的东西无从观察。拒绝。`observed` 上再写 `unordered`、`idempotent`、`overwriting` 是多余的：语义上它已经等于什么都没做。

## 由框架推出的规则

**`observed` 不能被读。** 一次访问在语义里可擦除，前提是它影响不了程序算出的任何值，也就是信息只从程序流向它、不流回来（无干涉）。能读回的观察资源是矛盾的，所以编译器拒绝任何读 `observed` 资源的操作；这条检查是擦除成立的必要条件，不是另加的规定。

**`observed` 的语义与实现分两层。** 语义层它等于什么都没做：不进函数的资源集，不影响 `pure`，不产生排序，差分测试比较输出时不比它。实现层它是调试者要看到的真实输出：遍可以挪动它，但不能删除、不能把两次合成一次。剥离它是一个显式的遍（`std::strip_debug`），导出遍把它当恒等。

**`unordered` 只让写与写交换。** 写与写可以调换，读与写之间照常排序：一个既可写又可读的资源（读出当前计数的计数器），读看到的是写的累计，必须排在相关的写之后。只有在资源不可读时，`unordered` 才等于"完全不排序"。

## 调试观察

标准库在 prelude 里提供命名空间 `debug`：资源 `debug::channel` 声明为 `observed`，`debug::print(x)`（带格式写 `debug::print<fmt>(x)`）把 `x` 写到标准错误、带 `[文件:行]` 前缀、交回 `x` 本身，所以能串在管道里：`x->debug::print->f`。它可以写在纯函数里，加一行不改变函数的类型；求导时是恒等，导数穿过它、打印的是原值；批处理下打印整批的值。

程序自己的输出用 `print`、`println`，写 `console`，参与排序，交回 `void`。链式观察交给 `debug::print`，所以打印函数不再交回参数。

## 编译期与运行时

- **推断**：资源推断按访问的种类累加，`observed` 的访问不计入。
- **建图**：冲突且不满足交换的访问之间加顺序边；同步块里按书写顺序加同步边。`observed` 的访问不加任何排序边，节点带"必须保留"。
- **遍**：死代码消除只删满足丢弃的访问，合并重复计算只合并满足复制的访问，重排只调换满足交换的访问，死存储消除只删被 `overwriting` 覆盖的写。遍问的是资源声明里的等式，不认识具体算子。
- **调度**：`idempotent` 的写可以在中断后重做、可以推测执行；其余的写只执行一次。
- **声明检查**：修饰词的矛盾组合在资源声明处报错；读 `observed` 资源的操作在调用处报错。
- **运行时**：区域执行时其中的访问照图执行；`observed` 的输出与 `console` 上的输出之间没有先后保证。

## 先例

- **Spectator aspects**（Clifton 与 Leavens，*Spectators and Assistants*，2002）：只看不改的切面单独成一类，可以无视它来推理被织入的代码。
- **Ghost code**（Dafny、Why3、F\*）：只为规约存在、编译时擦除的代码，与 `observed` 互为对偶：ghost 在语义里有、运行时擦掉；`observed` 在运行时有、语义里擦掉，两者都靠无干涉成立。
- **LVars**（Kuper 与 Newton，*LVars: Lattice-based Data Structures for Deterministic Parallelism*，FHPC 2013）：只允许单调地向半格做并的写，任何调度下结果都确定，即 `unordered` + `idempotent`。
- **JAX 的效应**：区分有序与无序效应；`jax.debug.print` 是无序的调试效应，能写在 `jit` 的纯函数里，因带效应而不被消除。
- **Koka 的 `trace`、Haskell 的 `Debug.Trace`**：靠绕过类型系统（`unsafe-total`、`unsafePerformIO`）让纯代码能打印，优化器可能丢掉或重复它。Camel 把观察做成效应系统里正式的一种访问，并以"不能被读"的检查保证擦除可靠。
