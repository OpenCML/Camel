# 变换的嵌套：二阶导、元学习、高阶代码

> **设计稿（2026-11-18，决策者起草，负责人讨论中）**。来由：ECOOP 两位系统方向的审稿人指出，变换不能嵌套（`grad(grad(f))`、元学习 `L(θ − α∇L(θ))` 做不到），而任意组合正是 JAX 的长处。结论先说：**与 JAX 同等的嵌套能力没有根本性障碍，缺的是三件实现上的事**；只有"函数的代码到运行时才出现"这一类在运行前做不完，要么拒绝、要么运行时再变换（附录 A.2）。负责人 2026-11-18 批准第 2 节开工、附录 A.2 暂不做，施工计划见 `docs/handover/plans/2026-11-18-nested-transforms.cn.md`。

## 1. 为什么今天做不到

负责人："`grad` 的语义就是返回求导后的图，不是待执行的图。"今天的库没有照这个语义写。`lib/vjp/vjp.cml` 把变换写进了交出的闭包里：

```camel
return <...ws> (...xs) => {
    let (y, lin) = split(jvp(f))<...ws>(...xs)   // 每次调用都重新 split
    (y, transpose(lin))                           // 每次调用都重新 transpose
}
```

后果有两个，出自同一处：
- **外层看不懂内层**：导数函数的图里没有"导数怎么算"，只有"调用时先造一个函数、再调用它"。外层变换遇到的是运行时才算出来的函数，问不出调用的是谁，只能拒绝（`test/cases/modules/autodiff/second_order_refused_vjp.cml` 钉的就是这句）。
- **每步重做变换**：训练循环里每一步都重新 `split`、`transpose` 一次（负责人 11-17 指出的"每次执行 step 都要跑一次 grad"是同一个根子）。

写成这样有两层原因：`split(jvp(f))` 本身不需要实参，本可以在闭包外先算好，只是写进了调用里；更深的一层在 `split` 的输出形状——它交出的线性一半 `lin` 是一个运行时闭包，捕获着这次调用算出的残差，所以 `transpose(lin)` 只能等到运行时拿到闭包才能做。

对照：原生的 `autodiff.grad`（`lib/autodiff/pullback.cpp`）在改写时就对静态函数建好导数图，所以今天能做二阶导（`second_order_nest.cml` 得 12）；JAX 靠追踪，外层追踪时内层已执行完。两者的共同点都是：**外层看到内层时，内层的变换已经做完了**。

## 2. 三件实现上的事

### 2.1 库的形状：`grad(f)` 求值时做完变换，交出只调用已知图的函数

> **2026-11-18 13:40 修订**：下面第 1、3 条"残差作显式参数"作废，改为 GNC 的形状——前向交出 `(y, pb)`，`pb` 是代码静态、捕获残差的闭包；理由与新写法见施工计划 `docs/handover/plans/2026-11-18-nested-transforms.cn.md` 甲。拒绝判据与展开见同一计划乙第 2–4 条。

1. `split` 交出两张静态的图：前向 `fwd: x ↦ (y, 残差)`，线性一半 `lin: (残差, 切向量) ↦ 切向量`。残差是显式参数，不再是闭包里捕获的运行时值。
2. `transpose` 作用在这张静态的 `lin` 上，得到 `bwd: (残差, 余切) ↦ 余切`，同样是一张静态的图。
3. `vjp(f)` 先算出 `fwd`、`bwd`，再交出 `(x) => { let (y, r) = fwd(x); (y, (ct) => bwd(r, ct)) }`；`grad(f)` 交出 `(x) => { let (_, r) = fwd(x); bwd(r, 1.0) }`。`with` 值照今天的规则在调用处传给 `fwd`。

变换只在 `grad(f)` 求值时做一次。

### 2.2 变换递归进闭包捕获的函数

改完之后，`grad(f)` 交出的是一个闭包，捕获着 `fwd`、`bwd` 两个函数值。外层变换遇到它，要能对捕获的函数递归变换：闭包就是"图 + 捕获的值"，捕获的数值照常提升（前向求导里带切向量），捕获的函数值随闭包一起变换，对它们的调用按 4.1（`README.cn.md`）"调用换成对 `reinterp<H>(被调函数)` 的调用、同一被调函数只生成一份"处理。

**闭包本身不是问题，代码未知才是**（负责人 2026-11-18 问"传入静态图，变换过程中是不是也会产生闭包"）：会。`vjp` 交出的反传函数 `(ct) => bwd(r, ct)` 就是一个闭包，捕获着这次调用算出的残差 `r`；被变换的函数体里写的 lambda，变换后也还是闭包。这些都没关系：闭包是"代码 + 捕获的值"，它们的代码是一张编译时就有的图（`vjp` 体里写的那个 lambda、函数体里写的 lambda），捕获的是数据或已知的函数值，外层变换照常递归。今天出问题的，是闭包的**代码本身**要到运行时才由 `split` 造出来，而且每次调用都重造。所以 2.2 要处理的是一般的闭包（包括函数体里的 lambda），判据是"变换执行时它的代码是否已知"，不是"它是不是闭包"。

变换执行的那一刻，捕获的值是具体的：在运行时，`grad(grad(f))` 先求内层，得到的闭包里 `fwd`、`bwd` 已经是具体的图；在 `std::macro` 阶段，它们是常量。所以这里不需要问"调用的是哪个函数"，也不需要按值的来历拒绝。今天 GNC 在这里返回 Unsupported（"类型会变的函数类型捕获"），Lang 也要补上。

### 2.3 规则互相覆盖

二阶导时，外层的前向求导要穿过内层的反向一半，而反向一半里是转置规则产出的算子（转置的矩阵乘、广播的求和、切片的散射……）。这些算子都要有前向规则，否则第二层停在缺规则的地方。数量有限，补齐即可；JAX 的原语表也满足同样的封闭要求。验收：对 `lib/rulesets/transpose.cml` 能产出的每个算子，`lib/rulesets/jvp.cml` 里都有规则，写成一条自动检查。

## 3. 覆盖的用法

| 用法 | 怎么成立 |
|---|---|
| `grad(grad(f))`、Hessian、`jvp(vjp(f))` | 2.1 + 2.2 + 2.3：内层交出只调用已知图的闭包，外层递归进去 |
| 元学习 `L(θ − α∇L(θ))` 对 θ 求导 | 同上：`∇L` 是捕获了 `fwd`、`bwd` 的闭包，外层对它的调用递归变换 |
| `vmap(grad(f))`（逐样本梯度） | 同上 |
| `map(f, xs)` 求导，`f` 是 lambda、具名函数或捕获了 θ 的闭包 | 2.2：调用处的函数值是具体的，随之递归变换；捕获的 θ 带切向量 |
| 调用哪个函数由运行时数据决定 | 附录 A.2：运行时分派 |
| 对函数本身求导（泛函导数） | 不支持：函数没有切空间；JAX 同样不支持 |
| 不透明算子、块算子 | 声明了规则才行（附录 A.3） |

**不会混淆扰动**：嵌套求导的经典陷阱是内层把外层的切向量当成自己的。Camel 的变换是按类型的源变换，不是带标签的追踪，每一层把值换成自己的 `Lift<T>`：第二层前向求导的值是"对的对"，两层的切向量在结构上分开；被内层捕获的外层值，在内层看来是普通输入、切向量为零，它在外层的切向量由外层的提升照常传递。验收用经典例子钉住：`d/dx (x * (d/dy (x + y)) 在 y=1 处) 在 x=1 处`应得 `1`（混淆的实现得 `2`）。

## 4. 对 GNC 定义的改动（论文与证明由 ECOOP 一侧跟进）

1. `reinterp` 的 Unsupported 收窄：
   - `CALL`/`BIND` 与函数类型的 `CAP`：被调或被捕获的函数值是具体的（常量，或闭包里捕获的值），就递归 `reinterp`；
   - 非惰性算子：有声明的规则就用，没有才 Unsupported（只剩不透明算子与块算子）；
   - 被调函数值在变换时真正未知的情形，见附录 A.2；不加 A.2 时它仍是 Unsupported，范围与 JAX 相同。
2. `split` 的结果形状：两张图，残差是前向的一个输出、线性一半的一个输入（不是闭包捕获）。`transpose` 作用在线性一半上。
3. 一条"按类型提升的嵌套不混淆扰动"的引理。
4. 与已有定理的关系：读图效应已在 11-17 的定理里（不读图的上下文分不开行为等价的两个函数）；`grad` 带读图效应，那条定理对它本来就不做保证，嵌套不改变这一点。

## 5. 代价与风险

- **`split` 输出形状的改动**会波及所有用到 `split` 结果的地方（`vjp`、`grad`、`has_aux`、导出、测试的金标），要一并迁移；内测不计兼容，旧形状删除。
- **代码膨胀**：嵌套 k 层，图大约增长到原来的 2^k 倍，与 JAX 相同。
- **两套求导要收成一套**：原生 `autodiff.grad` 今天能做的二阶导，由规则组合的 `grad` 接过来之后，删掉原生的那套（11-13 审计里的"两套求导"）。在这之前，论文里的嵌套能力以实测通过的那一套为准。
- **验收**：二阶导、Hessian、`jvp(vjp(f))`、元学习、`vmap(grad(f))`、`map(f, xs)` 求导、扰动混淆的经典例子，各一条用例，四个后端一致；`second_order_refused_vjp` 那两条改为钉正确的数值。

## 附录 A：边角情形

### A.1 提前到运行前做（`std::macro` 阶段）

`grad`、`vjp` 已标 `#macro`（负责人 11-15）。2.1 改完后，参数是已知函数时，`grad(f)` 在 `std::macro` 阶段就能求出那个闭包，`fwd`、`bwd` 作为常量；要做的只是让 `split`、`transpose` 的内核在这个阶段对常量参数运行。这只是把 2.1 的那一次变换挪到运行前，不影响正确性；没写这个阶段的程序，在运行时 `grad(f)` 求值时做一次。执行时机由调用者决定（负责人 11-17）。

### A.2 调用哪个函数由运行时数据决定：运行时分派

静态的图变换在变换时不知道调用的是谁，这是固有的。做法是：变换遇到这样的调用 `v(args)`，产出 `T(v)(args')`，`T(v)` 是一个变换算子节点，运行到这里时对 `v` 的图做变换（`jvp`、`split` 已有这一形状）。结果按（变换, 规则集, 被调函数的图）缓存。代价：变换后的函数带读图效应；缺规则时在运行时作为一次故障，带被调函数的源码位置与缺的原语名。

### A.4 与 JAX 的对照（2026-11-18 更正）

此前几处写"这一块 JAX 做不到"，说过头了，更正如下：
- JAX 的变换是宿主语言（Python）里的函数，在运行时调用、当场追踪。运行时才出现的 Python 函数（读进来的、动态拼出的），只要由 JAX 原语构成，`jax.grad` 照样能对它求导，换一个函数就重新追踪、按函数身份缓存。所以"运行时才出现的函数能求导"不是 Camel 独有的。
- JAX 做不到的是**在编译后的计算里**按数据选函数再求导：`jit` 之内函数必须在追踪时已知，有限个候选要写成 `lax.switch`，任意函数只能经宿主回调，回调不可微。
- Camel 的运行时分派相当于后一种情形：变换在程序自己的执行里发生，不经宿主语言。这是表示上的不同（图是一等值，变换是程序里的算子），能力上的增量有限：只在虚拟机类后端上成立，编译成独立程序时与 XLA 一样做不到。

### A.3 不透明算子与块算子

C++ 写的不透明算子与块算子（`view`/`edit` 编译成的算子），变换看不到内部。它们可以声明自己的变换规则（与原语的 `#jvp`、`#transpose` 同一套机制，相当于 JAX 的 `custom_vjp`）；没有声明的，变换拒绝。块算子的参数与结果都是函数值，对它求导的需求很少，默认拒绝即可。
