# 变换的嵌套：二阶导、元学习、高阶代码

> **设计稿（2026-11-18，决策者起草，待负责人讨论）**。来由：ECOOP 两位系统方向的审稿人指出，变换不能嵌套（`grad(grad(f))`、元学习 `L(θ − α∇L(θ))` 做不到），而任意组合正是 JAX 的长处。本稿不安排施工；第 7 节列出要负责人定的事。

## 1. 现状（决策者核对过的代码）

1. **两套求导**。原生的 `autodiff.grad`（`modules/autodiff/pullback.cpp`）能做二阶导：`test/cases/modules/autodiff/second_order_nest.cml` 得 12。它的内层变换是在改写时对一个静态函数建好的算子。用规则组合的 `grad`（`stdlib/vjp.cml`：`vjp` = `split(jvp(f))` 再 `transpose`，`grad` 是 `vjp` 在种子 1 处读出）不能嵌套：`second_order_refused_vjp.cml` 钉的就是这个拒绝。
2. **拒绝的位置与原因**：外层变换遇到内层导数函数里"通过函数值的调用"，问"调用的是哪个函数"，答不上来就拒绝（"which function it calls is not evident where it is called"）。答不上来的根子是 `split` 的前向一半**到运行时才建出图**（`modules/transforms/split_operator.cpp#splitKernel` 运行时读 `function->graph()` 再建）。所以内层导数在外层变换时还不是一张图。
3. **已经有的运行时分派**：`jvp` 遇到通过函数值的调用，会写一个运行时的 `jvp(v)` 节点（`modules/transforms/jvp.cpp` 约 316 行）；`split` 遇到"签名答一对"的函数值调用，会写运行时的 `split(v)`（`split.cpp` 约 861 行）。另外有两处按值的来历拒绝：值是从元组里读出的，或是某个调用的返回值。
4. **规则集 4.1 的静态部分**：`reinterp` 遇到具名调用，换成对 `reinterp<H>(被调函数)` 的调用，同一被调函数只生成一份（"特化属于程序"）。
5. **GNC 的 `reinterp`**（`ECOOP2027/draft/sections/s-defs.tex` 第 545 行）在三种情况下返回 Unsupported：可达图里有 `CALL`/`BIND`；根上有类型会变的 `CAP`（包括函数类型的捕获）；有非惰性算子，其端口或结果类型会变、又不是基本类型（块算子的端口是函数类型，属于这一种）。

## 2. 思路：JAX 的"追踪时"在 Camel 里对应什么

JAX 能任意嵌套，是因为变换作用时函数总是已知的：追踪把 Python 的高阶性在追踪时展开掉了，变换看到的只有一阶的 jaxpr。Camel 不追踪，但有两样对应物：
- **`std::macro` 阶段**就是 Camel 的"追踪时"：负责人 11-15 定库的变换为 `#macro`，11-17 定"块的执行时机由调用它的函数决定，要早做就标 `#macro`"。参数是已知函数值的变换，在这个阶段求值成一张静态的图。
- **剩下真正在运行时才知道的函数值**，由变换在运行时分派：对拿到的函数值当场变换，再调用。JAX 做不到这一点（它要求函数在追踪时已知），这是 Camel 比 JAX 多出来的一块。

所以方案分两层：**能静态展开的一律静态展开，展开不了的运行时分派**。两层用同一套规则集，只在"什么时候知道被调函数"上不同。

## 3. 方案

### 3.0 先改库的形状：`grad` 交出的是求好导的函数，不是"每次调用时再求导"（负责人 2026-11-18）

负责人："grad 的语义就是返回求导后的图，不是待执行的图。"今天的 `stdlib/vjp.cml` 把变换写进了交出的闭包体里：

```camel
return <...ws> (...xs) => {
    let (y, lin) = split(jvp(f))<...ws>(...xs)   // 每次调用都重新 split
    (y, transpose(lin))                           // 每次调用都重新 transpose
}
```

于是导数函数的图里没有"导数怎么算"，只有"调用时先造一个函数再调用它"。外层变换看到的是一个运行时才算出来的函数，只能拒绝；训练循环里每一步也都重做一次变换（负责人 11-17 指出的"每次执行 step 都要跑一次 grad"是同一个根子）。

改法：**变换在 `grad(f)` 求值时做完，交出的函数只调用已经建好的图。**
1. `split` 交出两张静态的图，而不是"前向函数 + 运行时闭包"：前向 `fwd: x ↦ (y, 残差)`，线性一半 `lin: (残差, 切向量) ↦ 切向量`——残差是显式的参数，不是闭包里捕获的运行时值。
2. `transpose(lin)` 作用在这张静态的 `lin` 上，得到 `bwd: (残差, 余切) ↦ 余切`，同样是一张静态的图。
3. `vjp(f)` 先算出 `fwd`、`bwd`，再交出 `(x) => { let (y, r) = fwd(x); (y, (ct) => bwd(r, ct)) }`；`grad(f)` 交出 `(x) => { let (_, r) = fwd(x); bwd(r, 1.0) }`。函数体里只有对两张已知图的调用。

这样，即使不写 `std::macro` 阶段：`grad(grad(f))` 在运行时先求内层，得到一个闭包，它捕获的 `fwd`、`bwd` 此刻已是具体的图；外层变换作用在这个闭包值上，闭包是"图 + 捕获的值"，捕获的函数值是具体的，按 4.1 递归变换即可，不需要问"调用的是哪个函数"。变换也只在 `grad(f)` 求值时做一次，不再每步重做。

3.1、3.2 在此基础上处理剩下的情形：3.1 让这一切在运行前完成，3.2 处理函数值真正由运行时数据决定的情形。

### 3.1 静态层：已知函数上的变换在 `std::macro` 阶段求值

1. **变换算子可以在 `std::macro` 阶段对常量函数值求值**。`jvp`、`split`、`transpose`、`vmap`，以及建在它们上的 `vjp`、`grad`，参数是编译期已知的函数值时，就在这一阶段运行，结果是一张静态的图（一个函数常量）。`split` 的前向一半不再只在运行时建：同一个内核在阶段里对常量参数运行，交出的就是图。这与块编译成算子、参数为常量时提前求值是同一回事（11-17 的裁定），不需要新机制。
2. **由内向外到不动点**：`grad(grad(f))` 先求内层，得到一张一阶的导数图 `G1`；外层的参数 `G1` 于是也是常量，接着求外层。外层遇到 `G1` 里对已知函数的调用，都是具名调用，按 4.1 递归变换。
3. **高阶函数按常量函数实参特化**：`map(f, xs)` 里 `f` 是 lambda 或具名函数时，阶段把调用处特化成 `map_f(xs)`（"特化属于程序"，与 4.1 同一条规则）。特化之后，`f` 在 `map_f` 的体里是具名调用，变换可以穿过。
4. **捕获了函数值的闭包**：闭包是"图 + 捕获的值"。函数类型的捕获，若捕获的函数已知，就随闭包一起递归变换；捕获的数值照常提升（前向求导里带切向量）。这对应 GNC 里"类型会变的函数类型 `CAP`"那一条。

### 3.2 动态层：运行时才知道的函数值，在运行时分派

1. **所有变换对"通过函数值的调用"一律写运行时分派**：调用 `v(args)` 变成 `T(v)(args')`，其中 `T(v)` 是一个变换算子节点，运行到这里时对 `v` 的图做变换。`jvp`、`split` 已有这一形状，补齐 `transpose`、`vmap`。
2. **删掉按来历的拒绝**："值是从元组里读出的"、"值是某个调用的返回值"都不再是拒绝的理由。函数值从哪来不重要，运行时它是一张图，变换照常作用。这正是 9.5 的精神：不按来历判断。
3. **嵌套自然成立**：外层变换遇到内层运行时分派产生的值 `w = T(v)`，同样写 `T'(w)`；运行时 `w` 已是一张具体的图，`T'(w)` 照常作用。
4. **缓存**：运行时变换的结果按（变换, 规则集, 被调函数的图）缓存；图是不可变的值，按图的身份与版本作键，跨图共享时再按规范形式的哈希。训练循环里每轮命中缓存，只付一次变换的代价。
5. **类型上如实标出**：运行时分派要读被调函数的图，所以变换后的函数带上"读图"效应（11-17 已定读图是一种效应，`grad` 带它已在待定项里）；运行时变换可能拒绝（规则集里缺规则），所以变换算子声明"可能出故障"，拒绝在运行时是一次故障，带被调函数的源码位置与缺的原语名。

### 3.3 不会混淆扰动

嵌套求导的经典陷阱是扰动混淆：内层求导时，把外层的切向量误当成自己的。Camel 的变换是按类型的源变换，不是带标签的追踪，每一层把值换成自己的 `Lift<T>`：第二层前向求导的值是"对的对"，两层的切向量在结构上分开。被内层捕获的外层值，在内层看来是普通的输入，切向量为零；它自己在外层的切向量由外层的提升照常传递。所以不需要标签。验收时用经典例子钉住：`d/dx (x * (d/dy (x + y)) at y=1) at x=1` 应得 `1`（混淆的实现会得 `2`）。

### 3.4 不透明的算子与块算子

块算子（`view`/`edit` 编译成的算子）和 C++ 写的不透明算子，变换看不到内部。按已有的机制处理：算子可以声明自己的变换规则（与原语的 `#jvp`、`#transpose` 规则同一套，相当于 JAX 的 `custom_vjp`）；没有声明的，变换遇到它时拒绝，静态层在编译期拒绝，动态层在运行时作为故障。块算子的参数是函数值、结果也是函数值，对它求导的需求很少（在改图的过程中求导），默认拒绝即可。

## 4. 覆盖的用法

| 用法 | 走哪一层 | 说明 |
|---|---|---|
| `grad(grad(f))`、Hessian、`jvp(vjp(f))` | 静态 | 由内向外求值，每一层看到的都是一阶图 |
| 元学习 `L(θ − α∇L(θ))` 对 θ 求导 | 静态 | `∇L` 在阶段里展开成具名的导数函数，外层对它的调用是具名调用 |
| `vmap(grad(f))`（逐样本梯度） | 静态 | 同上 |
| `map(f, xs)` 求导，`f` 是 lambda 或具名函数 | 静态 | 按常量函数实参特化 |
| `map(f, xs)` 求导，`f` 是捕获了 θ 的闭包 | 静态 | 闭包随函数一起变换，捕获的 θ 带切向量 |
| 被求导函数的参数里有函数值，由运行时数据决定调用哪个 | 动态 | 运行时分派，带读图效应，结果缓存 |
| 对函数本身求导（泛函导数） | 不支持 | 函数没有切空间；JAX 同样不支持 |
| 不透明算子、块算子 | 声明了规则才行 | 与 `custom_vjp` 同理 |

## 5. 对 GNC 定义的改动（论文与证明由 ECOOP 一侧跟进）

1. **把"变换的参数是常量函数时可以提前求值"写成一条等式**：`T(lit f) ⟶ lit (T f)`。它与阶段的求值顺序无关，因为 `T` 在规范形式上是确定的函数。需要一条"分阶段可靠性"引理：提前求值与运行时求值给出同一个函数。
2. **`reinterp` 的三个 Unsupported 改为**：
   - `CALL`/`BIND` 的被调值是常量函数（含闭包常量），就递归 `reinterp`；是未知值，就产出 `CALL(T(v), args')`。其中 `T` 是一个运行时变换算子，类型为提升后的函数类型，带读图效应，可能出故障。
   - 函数类型的 `CAP`：捕获的函数是常量就递归变换；否则同上，经运行时分派。
   - 非惰性算子：有声明的规则就用；没有就 Unsupported（只剩这一处，范围是不透明算子与块算子）。
3. **扰动混淆**：一条引理，说明按类型提升的嵌套不会混淆两层的切向量。
4. **与已有定理的关系**：读图效应已在 11-17 的定理里（不读图的上下文分不开行为等价的两个函数）。`grad` 带读图效应，所以那条定理对 `grad` 本来就不做保证；嵌套不改变这一点。

## 6. 代价与风险

- **运行时分派的代价**：第一次调用付一次变换，此后命中缓存。变换后的函数带读图效应、可能出故障，类型里看得见。
- **拒绝可能推迟到运行时**：只发生在动态层；静态层仍在编译期拒绝。把可以静态展开的情形最大化（3.1 第 3、4 条），动态层只留给真正由数据决定的函数值。
- **代码膨胀**：嵌套 k 层，图大约增长到原来的 2^k 倍，与 JAX 相同。特化也会复制高阶函数，按（函数, 常量实参的规范形式）去重。
- **两套求导要收成一套**：原生 `autodiff.grad` 今天能做的二阶导，要由规则组合的 `grad` 接过来，然后删掉原生的那套（11-13 审计里的"两套求导"）。在这之前，论文里的嵌套能力以库的 `grad` 为准。
- **依赖 `std::macro` 阶段**：没写这个阶段的程序，嵌套仍然正确，但走动态层，付运行时的第一次变换与读图效应。这与 11-17 的裁定一致：执行时机由调用者决定。
