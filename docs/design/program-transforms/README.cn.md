# 程序变换：三个图算子与函数类型的拆拼

负责人 2026-10-28 定方向；决策者起草。规范以 [设计原则](../../design-principles.cn.md) 5.6、9.9 为准，本稿给出设计与施工顺序。

## 1. 为什么

- **图是值，变换图的程序也应当是 Camel。** 现在 `fold`、`cse`、`dce` 与规则饱和已经是作用在图值上的 Camel 程序；求导与导出不是：求导在 `modules/autodiff/pullback.cpp`（约 4,800 行），导出在 `modules/onnx/exporter.cpp` 加降级代码（约 7,200 行）。
- **图接口只能改、不能建。** 求导要造出原图里没有的计算（伴随量、反向循环、类型不同的新函数），现在的 `replace`/`erase`/`eval`/`add_constant` 一样也做不出来。
- **现在的 C++ 求导靠闭包串回传，闭包一个也没消掉。** 一个带调用、分支和循环的小程序，整轮 `std::opt` 之后仍有 7 个闭包、7 次间接调用（去函数化另立任务，见交接复核页）。
- **求导里的大部分代码在处理循环、分支、调用、闭包，不在求导本身。** 这些结构应当在通用的图算子里处理一次，所有变换共用。

所以：**每个原语只写局部规则；循环、分支、调用由三个通用的图算子处理；求导、前向求导、导出都是这三个算子的组合，写在库里。** 这与 JAX 的分解相同（`jvp` 加线性化加转置），区别在于 Camel 的算子直接作用在图上，不靠追踪。

## 2. 类型：拆开与拼出函数类型

声明写不出的部分，做成不带右边的类型函数（原则 5.6、9 节"签名的唯一来源"），只加三个：

```camel
type ParamsOf<F>    // 函数的普通参数，作为一个参数包
type WithOf<F>      // 函数的 with 参数，作为一个参数包
type ResultOf<F>    // 函数的返回类型
```

拼回去用已有的写法 `(..P) => R`。新增一条规则：**类型表达式里，`..` 后面跟一个用到参数包的类型表达式，对包的每个成员各展开一次**；`when` 里的 `..pred::<A>()` 表示包的每个成员都满足。

```camel
type Tangent<T>  = …                                   // 原则 9.9 的切空间，按类型逐个定
type Pullback<F> = (ct: Tangent<ResultOf<F>>) => (..Tangent<ParamsOf<F>>)
type Vjp<F>      = (..ParamsOf<F>) => (ResultOf<F>, Pullback<F>)
type Gradient<F> = (..ParamsOf<F>) => (..Tangent<ParamsOf<F>>)

func zip::<..A>(..xs: ..A): (..ElementOf<A>)[] when ..is_array::<A>()
```

`zip` 是第一条验收：它今天卡在 C++ 里，正因为结果类型要对参数包逐个取元素类型。

## 3. 原语的规则

内置原语（`prelude` 里的 `func operator +` 等，以及 tensor、math 的原语）的规则写在**规则集模块**里，
例如 `stdlib/rulesets/jvp.cml`。**一个模块是不是规则集，由它的路径前缀决定**：`stdlib/rulesets/` 下的
模块是规则集，其他模块是库；索引只从这样命名的模块里建，所以一个库不会因为写了 `rule` 就被当成规则集。
一条规则属于哪一族，是因为它声明在哪个模块里；**它是哪个原语的规则，由它的左边决定**——`rule jvp_add
{ x + w => … }` 的左边头就是 `+`，**而且左边的运算符连同它的元数一起才是键**：`-x` 是一元取负
（`__neg__`），`x - w` 是二元减法（`__sub__`），两者写同一个 `-`，是两条规则、两个原语。变换按"原语 →
规则集模块里左边以它（运算符与元数）为键的规则"建一张索引，一条规则集一张。

```camel
// 规则集模块里（例如 stdlib/rulesets/jvp.cml）：左边的运算符与元数就是这条规则所属的原语
rule jvp_add::<T>(x: T, w: T) when is_float::<T>() {
    x + w => (dx: T, dw: T) => add_tangent(x, w, dx, dw)
}

rule jvp_mul::<T>(x: T, w: T) when is_float::<T>() {
    x * w => (dx: T, dw: T) => mul_tangent(x, w, dx, dw)
}
```

**前向与转置是两个规则集**：`stdlib/rulesets/jvp.cml` 收前向规则，`stdlib/rulesets/transpose.cml` 收转置
规则。它们的左边往往一模一样（`add_jvp` 与 `add_t` 都写 `x + w`），而一个规则集里一个原语只有一条规则，
所以这两族分居两个模块——一个模块不兼任两族，正如一个模块不兼任库和规则集。规则右边的数学由库
（`stdlib/autodiff.cml`）里那几个切线/余切函数写着，规则只是把它接到原语上。

程序自己写的函数才用标签（相当于 JAX 的 `custom_jvp`）：标签放在 `prelude`，规则写在用户自己的模块里，
可以 `import`。

```camel
#jvp(my_jvp)
func my_fn(x: float): float { … }

rule my_jvp(x: float) {
    my_fn(x) => (dx: float) => …
}
```

- **同一原语在同一规则集里有两条键相同（运算符与元数都相同）的规则，报编译错误**：否则谁生效取决于书写顺序。
- **用户函数既有 `#jvp` 标签、规则集里又有以它为头的规则时，以标签为准。**
- **缺规则必须拒绝**（原则 9.9）：变换遇到一个没有对应规则的原语，在那个原语处给编译期诊断，点名原语与缺的是哪种规则。
- 线性原语只有十几个（加、减、取负、乘以已知值、矩阵乘、求和、广播、改形状、切片、拼接、转置、`where` 的选择），`#transpose` 规则只给它们写。

## 4. 三个图算子

三者都是函数到函数的变换，结果是新的函数值，类型由第 2 节的类型函数算出。图上的结构（调用、分支、循环、效应、`var`）在三个算子里各处理一次，规则只管原语。

### 4.1 重新解释 `reinterp`

```camel
func reinterp::<F, H>(f: F): Reinterp<F, H> when is_function::<F>() && is_rule_set::<H>()
type Reinterp<F, H> = (..H.Lift<ParamsOf<F>>) => H.Lift<ResultOf<F>>
```

把 `f` 的图里每个原语换成规则集 `H` 给它的含义，其余结构原样保留。`H` 是一个规则集，带一个类型函数 `Lift<T>`，说明每个值被换成什么（前向求导里 `Lift<T> = (T, Tangent<T>)`）。

- **原语**：换成 `H` 里它的规则，实参是已经重新解释过的输入。
- **常量与捕获的值**：由 `H` 的 `lift` 提升（前向求导里切向量为零）。
- **调用**：换成对 `reinterp<H>(被调函数)` 的调用；同一个被调函数配同一个 `H` 只生成一份（与"特化属于程序"同一条规则）。
- **分支**：条件原样保留，每条臂重新解释。
- **循环**：状态的类型按 `Lift` 换掉，循环体重新解释。
- **效应**：`H` 对效应原语没有规则时拒绝；前向求导的规则集让效应原语原样执行、切向量为零（原则 9.9：效应只在正向执行）。

前向求导就是 `reinterp<jvp>`。导出 ONNX 是另一个规则集：每个原语解释成"往模型里写一个节点"。

值先出现、切线后出现是对的次序——但只有切线由链上算出来的那一天，`jvp` 才叫前向模式（作者，2026-10-31）。

机制通了的标志不是能算，是算它的规则只有一份、且写在语言里（作者，2026-10-31）。

诊断和读数的区别不是措辞：读数跑完还在，诊断让进程停在原语上（作者，2026-10-31）。这条诊断在构建期发出——`jvp(f)` 一开始建图就停在缺规则的那个原语上，`f` 的 `file:line:col`，进程不往下跑；载体仍是 runtime fault（`RuntimeFault` + `ExecutionSiteHint` 指到那个节点的 origin），不是编译前端那条通道。要不要把 `jvp` 挪进编译阶段（pass 或宏求值器）是另一件事，等作者点名。

节点级的复制抄得动，区域级的复制抄不动——因为区域是图的一个属性，不是节点的（作者，2026-10-31）。分支的每一条臂都是同一张图里的一个区域：抄 `Brch`/`Join` 之前先建区域、抄完再把每条臂的退出值升成 `(值, 切线)` 交给 `Join`；`reinterp<jvp>` 处理 `Brch`/`Join` 的代码只有 `modules/transforms/jvp.cpp` 一处，`defunctionalize.cpp` 里那套动作序列只是"怎么写一个分支"的配方，不是第二份分支语义。

### 4.2 拆分 `split`

```camel
func split::<F>(f: F): Split<F>
```

把一个"一部分输入现在就有、另一部分以后才有"的函数拆成两个：前一个只用现在就有的输入，算出能算的一切，并把后一个要用的中间值（残差）作为输出；后一个接残差与其余输入。线性化就是 `split(reinterp<jvp>(f))`，"现在就有"的是原始输入，"以后才有"的是切向量。

- **循环**：每一轮的残差作为收集输出保存，是值不是闭包（原则 9.9 现有规定），后一个函数里循环按同样的轮数执行，逐轮取残差。
- **分支**：条件是残差，后一个函数按同一个条件选臂。
- **调用**：被调函数各自拆分，残差按调用嵌套。

### 4.3 转置 `transpose`

```camel
func transpose::<F>(f: F): Transpose<F> when is_linear::<F>()
type Transpose<F> = (ct: Tangent<ResultOf<F>>) => (..Tangent<ParamsOf<F>>)
```

对一个对其输入线性的函数（残差是已知值），把数据流反过来。

- **原语**：换成它的 `#transpose` 规则；
- **一个值被用了几次**：反过来就是几份相加；
- **循环**：倒着走，逐轮取 `split` 留下的残差；
- **分支**：用同一个条件选转置后的臂。

不是线性的函数交给它，是编译期错误。

### 4.4 求导是库

```camel
func vjp::<F>(f: F): Vjp<F> when is_function::<F>() {
    let (fwd, lin) = split(reinterp<jvp>(f))
    return (..xs: ..ParamsOf<F>) => {
        let (y, res) = fwd(..xs)
        (y, (ct) => transpose(lin)(res, ct))
    }
}
```

`grad`、`with_grad`（对第一个 `with` 参数，原则 9.9）写在 `vjp` 之上。带 `#vjp` 规则的原语，在线性化时作为一个整体：它的残差是回传要读的值，转置时直接用它给的回传。输出图里没有回传闭包，转置直接产出反向的数据流。

## 5. 实现与对照

- 三个算子各有一份 Camel 参考实现与一份原生实现，原生的用 `#impl` 标出（原则 6.2），差分测试对照。Camel 参考实现在实例化时遍历函数的图并展开成代码，需要元层（`static for`、`match type`）能读图的结构，这一块随第 6 节第 6 步单独定写法。
- 求导的验收对照三样：有限差分、现在的 `pullback.cpp`、ADBench 能表达的 GMM、BA、LSTM。三个调度器的值与解释器一致。新路线全过之后，`pullback.cpp` 删除，不留兼容层。

## 6. 施工顺序

只写依赖，不写时间。

1. **类型**：`ParamsOf`、`WithOf`、`ResultOf`，类型表达式里的包展开，`when` 里的 `..pred`。验收：`zip` 改成声明，删掉它的 C++ 签名。
2. **规则**：`#jvp`、`#transpose`、`#vjp` 能按结构读出（`graph` 模块的标签读取不再只给文本）；逐元素、矩阵乘、归约、改形状各族原语的规则写进标准库。
3. **`reinterp`**：先直线代码与调用，再分支，再循环。验收：`reinterp<jvp>` 的结果与有限差分、现有 C++ 求导一致。
4. **`split`**：同样的顺序。
5. **`transpose`** 与库里的 `vjp`、`grad`、`with_grad`：自动微分全部计划转到新路线，全过后删除 `pullback.cpp`。
6. **Camel 参考实现**：三个算子用 Camel 写，原生实现以 `#impl` 挂上，差分对照。
7. **导出**：ONNX 导出改写为一个规则集上的 `reinterp`。
