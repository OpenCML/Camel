本稿回答两个问题：Tiles 以什么形式进入 Camel 的编译流水线；类似 Triton 的"由人写内核"在 Camel 里应当长什么样。它与语义稿分工：语义稿规定核心对外提供的算子语义、数值许可与图事实；本稿规定 Tiles 怎样使用它们，以及需要语言作者裁定的新写法。

## 0. 摘要

1. **分界**：计算的语义（迭代域、索引映射、归约规律、数值许可、资源、形状等事实）放在 Camel 的图上，由核心的协议声明与校验；Tiles 只私有物理层：布局、分块、线程映射、流与事件、内存池、调优结果。
2. **主入口是一个遍：`std::tiles`**。它在编译期把图中能上 GPU 的区域切成子图，替换为一个"在设备上执行这张图"的算子节点，其余部分照常在 CPU 上执行。编译依据类型里的形状；命名维度编译一次即覆盖所有批量大小。现有的 `run<fn>`、`source<fn>`、`inspect<fn>` 保留为便捷入口与调试工具。
3. **类似 Triton 的部分用 Camel 自己写**：块级内核就是普通的 Camel 函数，以"对张量的块做 `map`"的形式调用。它本身是一张图，可以用 `std::rgir` 查看、可以求导，**并且能在 CPU 解释器上直接运行**；按第 7 节的数值契约，基本运算逐位一致，CPU 运行就是 GPU 内核的参考语义。这一节的写法需要裁定（第 6 节）。
4. **先后**：归约融合（softmax、layernorm 各成一个内核）→ 矩阵乘接 cuBLAS → 异步与设备常驻 → 语义迁到核心协议 → `std::tiles` 遍 → 块级内核。

## 1. 现状（2026-10-15，`modules/tiles`）

【读码】Tiles 是一个运行时库：`run<fn>(inputs)` 在调用时取函数的图，按实际输入特化，翻译为私有中间表示（`camel::tiles::Program`：节点为 `std::string op` 加整数属性与形状），做单一用途逐元素链的贪心融合（每组至多 64 个运算；共享结果与归约是物化边界），以字符串拼出 CUDA 源码，经 NVRTC 编译执行；按源码文本缓存最近 32 个模块。执行同步、串行；每次调用重新上传输入。

【读码】值得保留的：不开快速数学、保留 f32 舍入点、不重排归约；标量除零报故障；执行前校验拓扑、形状、存储生命周期与读写不重叠；编译后不持有回收器指针；设备内存经外部资源控制块管理；读图而不执行追踪；转置、置换、切片表示为"偏移 + 步长"的索引映射，逻辑索引与线程摆放分开；文档如实写明限制。

结构性问题（详见给 Tiles 的评价）：语义只存在于私有表示里，图上与其他遍看不到；运行时按值特化（主机标量写成源码常量，缓存键是源码文本），没有用上 Camel 的静态形状类型与 `std::macro`；只是库函数，不是流水线上的遍；归约不融合；代码生成直接拼字符串。矩阵乘的显式 `fmaf` 已由后续的 7.1 数值细则裁定为规范算法的一部分，须保持 k 递增的连续累加链。

## 2. 分界：语义在图上，物理在 Tiles

| 层 | 内容 | 归属 | 依据 |
|---|---|---|---|
| 算子语义 | 迭代域与索引映射、归约规律、可能故障、资源读写、定义图 | 核心协议，模块声明 | 语义稿 |
| 程序授予的许可 | `@numeric(...)` 的五项许可 | 写在源码上，随节点保留 | 7.5 |
| 可推出的事实 | 形状、域、范围、别名 | 图事实（第二类：可重算，可带依赖缓存） | 语义稿 |
| 区域划分 | 哪些节点组成一个设备区域 | `std::tiles` 遍的输出，体现为图的改写 | 本稿第 3 节 |
| 物理计划 | 布局、分块、线程与块的映射、共享内存、融合分组、存储复用 | Tiles 私有 | IC 稿的调度图、资源图 |
| 目标相关结果 | 生成的代码、调优结果 | Tiles 的编译缓存（第三类持久化） | 语义稿 |
| 运行资源 | 设备地址、流、事件、活动分配 | 仅在运行时，不持久化 | 语义稿 |

这条线的意义：凡是"程序在算什么"的信息，`std::rgir` 都看得见，自动微分、ONNX、`std::cpp`、将来的 CPU 向量化后端都能复用；凡是"在这块 GPU 上怎么算最快"的信息，留在 Tiles，不污染图。IC 稿的计算图对应前两层与第三层，调度图与资源图对应后三层。

## 3. `std::tiles` 遍

### 3.1 用法

```
camel train.cml std::macro std::tiles std::fvm
```

`std::macro` 先把能提前算的都算掉（包括 `grad` 的展开）；`std::tiles` 切出设备区域；`std::fvm`（或 `std::jit`、`std::prl`）执行其余部分并在需要时调用设备区域。

### 3.2 区域划分

一个节点可以进入设备区域，当且仅当：

- 它的算子在核心有语义声明，且 Tiles 声明能实现它（在 Tiles 的算子覆盖表里）；
- 它是纯的，或只读写已声明的设备资源（语义稿的资源协议）；
- 它的输入输出类型是张量或标量，形状由类型给出或可由图事实推出；
- 不是效应、不是 `sync` 链上的节点（`sync`、`wait` 保持原义，不变成 GPU 同步原语）。

区域是满足上述条件的极大连通子图，再按两条规则切开：区域内每个值只在区域内或区域出口被使用；区域不跨越分支的臂与 `LOOP` 的体（第一阶段；`LOOP` 原生化之后可以整体收入区域）。

### 3.3 图上的形状

区域被抽成一张函数图 `R`，原位置换成一个节点：

```
OPER :tiles/exec   With 0 = 函数常量 R   Norm = R 的输入
```

`:tiles/exec` 是一个带 `callsGraphs` 声明的普通算子，图上不增加节点种类（与 `attempt`、`map` 同类）。它的语义就是"调用 `R`"：去掉 `std::tiles`，或在没有 GPU 的机器上，执行器把它当作普通调用，结果相同（数值契约内逐位一致）。这使 `std::tiles` 成为一个纯粹的性能遍。

设备与主机之间的搬运是图上显式的 `:tiles/upload`、`:tiles/download` 节点，插在区域边界上；相邻两个区域之间的值留在设备上，不经过主机。`inspect` 显示的计划与 `std::rgir` 显示的图一一对应。

### 3.4 编译时机与形状

- 区域的输入形状由类型给出（`Tensor<f32, const [2, 3]>`）或含命名维度（`const [constas n, 784]`）。按符号形状编译一次，内核以运行时参数接收 `n`；同一区域对所有批量大小复用同一份代码。
- 形状含未知维度（`?`）时，退回到调用处按实际形状特化（今天的做法），结果进入 Tiles 的编译缓存。
- 主机标量不再写成源码常量，而是内核参数；只有图上的常量（`DATA`）才进入代码。
- 编译缓存的键：区域的语义指纹（区域子图的结构、各算子的"协议:名字 + 语义版本"、许可、符号形状）+ 设备架构 + 编译器版本 + 调度策略。不再以生成的源码为键。

### 3.5 执行

- 流与事件、内存池、异步提交由 Tiles 管理；`:tiles/exec` 对 CPU 执行器表现为一个同步算子，内部可以异步，只要它的结果在被 CPU 使用之前完成。
- 设备上的故障（除零、越界）写入故障字，在结果被取用时报告为该 `:tiles/exec` 节点的故障，位置指向区域里出故障的那个源节点（图事实里保留源码位置；第 3 步第三片的位置列）。
- 分代回收：区域执行期间不持有托管指针（现有纪律）；`:tiles/exec` 在入口把输入固定或拷出，与今天相同。

### 3.6 与现有 `run<fn>` 的关系

`run<fn>(inputs)` 等价于"对 `fn` 的整张图做一次 `std::tiles`，然后调用"。保留它作为交互式与测试入口；`source<fn>`、`inspect<fn>`、`benchmark<fn>` 继续作为调试工具，改为基于同一套区域与计划。

## 4. 结构化内核表示（Tiles 私有）

在"区域"与"CUDA 源码"之间加一层小表示，分块、融合、线程映射都在这层做：

```
kernel softmax_rows(x: f32[n, 1024], y: f32[n, 1024]) grid [n]
  for row in block.x:                         // 并行维 → 线程块
    t   = load x[row, 0:1024]                 // 访问映射 + 掩码
    m   = reduce max over t                    // 归约维 → 块内归约
    e   = exp(t - m)
    s   = reduce add over e  (order: tree, permitted by @numeric(reassociate)? else sequential)
    store y[row, 0:1024] = e / s
```

它由三样东西组成：迭代域（来自语义稿的索引模型）、带掩码的载入与存储、归约（带顺序策略）。打印为 CUDA C 交给 NVRTC 的现有做法保留；以后需要时可换成 LLVM 的 NVPTX 后端。这层是 Tiles 的实现细节，不是 Camel 的规范语义（与今天的私有表示同等地位），但它的输入必须完全来自图上的语义与事实。

## 5. 数值契约在 Tiles 中的落实

按第 7 节：

- **默认**：基本运算正确舍入、按书写顺序、不收缩为乘加融合；归约按规范顺序。默认模式下 GPU 结果与 CPU 逐位一致，测试可以用逐位比较取代容差。
- **矩阵乘**：规范算法从 +0 开始，按 k 递增连续做 FMA，不需要额外的 `contract` 许可；分块不能改变该累加链。普通逐元素乘加的收缩仍需 `contract`。Tensor Core 改变输入或累加精度时需要 `change_precision`，改变合并顺序时还需独立的 `reassociate` 许可；接 cuBLAS 时必须确认所选算法满足实际获得的许可，无法保证时不选用该实现。
- **并行归约**：浮点加法的树形归约改变合并顺序，需要"改变归约顺序"许可；`unordered_reduce` 本身授予这一项（仅这一项）。没有许可时按规范顺序归约（可以分块，但块内与块间的合并顺序必须等价于规范顺序）。`maximum` / `minimum` 按已裁定的 NaN 与正负零规则处理后，可以依据其归约规律重排，不需要加法归约的许可。
- **超越函数**：用 GPU 的实现，满足写明的 ulp 上界；测试对这类函数用上界而不是逐位比较。
- **审计项**：矩阵乘的跨块 k 顺序与尾块排除；`sum_to` 与 `sum_axis` 的累加类型差异（f32 与 f64）要在语义声明里写明，作为算子的原始语义。

## 6. 块级内核（需要裁定）

### 6.1 目标

自动编译（第 3 节）服务普通张量程序；当专家需要控制分块、数据复用与块内算法时（attention、自定义归约、量化内核），提供一种"由人写内核"的方式。这是 Triton 的位置。Camel 的版本有三个与 Triton 不同、且只有图原生语言能做到的性质：

1. 内核是普通 Camel 函数，即一张图：可以 `std::rgir`、可以求导、可以被其他遍改写。
2. 内核在 CPU 解释器上能直接运行，结果就是参考语义；数值契约保证默认模式下与 GPU 逐位一致。
3. 并行结构是显式的数据流（"对块做 `map`"），不是指针加程序编号的命令式写法。

### 6.2 推荐写法：块类型加对块的 `map`

```camel
import { Tensor } from tensor
import { Tile, tiles } from tiles

// 一个块：静态形状的小张量，只能在内核里出现
func softmax_row(x: Tile<f32, [1, constas B]>): Tile<f32, [1, B]> {
    let m = x->max<axis: 1>
    let e = (x - m)->exp
    return e / e->sum<axis: 1>
}

func softmax(x: Tensor<f32, const [constas n, 1024]>): Tensor<f32, const [n, 1024]> {
    // 把 x 按 [1, 1024] 切块，对每一块调用 softmax_row，按同样的切法拼回
    return x->tiles<[1, 1024]>->map<softmax_row>->untile
}
```

- `x->tiles<[bm, bn]>` 把张量看作块的网格；尾块带掩码，掩码由块的形状与张量形状推出，用户不必写。
- `map` 就是现有的高阶算子：块之间互相独立，天然对应 GPU 上的线程块；CPU 上它就是普通的 `map`。
- 块上的运算是张量运算的子集（逐元素、按轴归约、`@`、广播），语义与张量相同，只是形状静态且较小。
- 需要跨块循环的内核（矩阵乘的 K 维）用 `LOOP`：

```camel
func matmul_block(a: TileRow<f32, [BM, K]>, b: TileCol<f32, [K, BN]>): Tile<f32, [BM, BN]> {
    return loop acc = Tile::zeros<[BM, BN]>() for k in range(0, K / BK)
        do acc + a->block<k, BK> @ b->block<k, BK>
}
```

  这正是 Tiles 要求 `LOOP` 保留结构化形式的原因：块级内核里的循环必须原样到达 Tiles，才能流水化与做双缓冲。

### 6.3 备选：Triton 式的指针与程序编号

```camel
@kernel
func softmax_row(x: Ptr<f32>, y: Ptr<f32>, n: int, stride: int) {
    let row  = program_id(0)
    let offs = arange(0, 1024)
    let t    = load(x + row * stride + offs, mask: offs < n)
    ...
    store(y + row * stride + offs, e / s, mask: offs < n)
}
```

熟悉 Triton 的人上手快，但它是命令式的：`store` 是效应，内核的语义依赖写入的位置与顺序；CPU 参考语义要另行定义；与图原生、按依赖求值的方向相悖。**不推荐作为主写法**；如需要，可以作为第 6.2 节表达不了的情形（不规则写入、原子累加）的低层逃生口，放在以后。

### 6.5 `@kernel` 标注（已定）

块级内核的函数上可以写 `@kernel`：

```camel
@kernel
func softmax_row(x: Tile<f32, [1, 1024]>): Tile<f32, [1, 1024]> {
    let m = x->max<axis: 1>
    let e = (x - m)->exp
    return e / e->sum<axis: 1>
}
```

- 含义：**这个函数必须能编译为块级内核**。编译器据此检查：只用块上的运算、没有效应、块形状是常量；不满足时在这个函数上报错，而不是到运行时才退回 CPU。
- 它不改变语义：去掉 `@kernel`，或在 CPU 上执行，它仍是普通函数，结果仍是 GPU 结果的参考语义。
- 它由 Tiles 模块提供，是标注而不是语言关键字（与计划中的 `@numeric(...)` 同类；行首的 `@` 是标注，见 4.1）。编辑器与语言服务器据此标出内核。
- 写法仍是第 6.2 节的函数式写法；`@kernel` 不引入第 6.3 节的指针与程序编号。
- **实现途径（2026-10-19）**：核心已有通用的节点属性与"授予属性的装饰器"，`@kernel` 可以完全在 Tiles 模块里实现，不需要核心为它写代码：模块导出 `attrDecoratorGroup("kernel", "tiles:kernel", 0, ...)`（`camel/core/module/attr_decorator.h`），在 `load()` 里以 `attr::registerKey("tiles.kernel", {...})` 登记这个键（值的种类与合并规则：标记用 `Unit`，嵌套取内层，只与相同的值合并），再 `OperatorTable::declareGrant("tiles:kernel", {.key = "tiles.kernel"})`，执行器把 `kernel` 映射到 `attrDecoratorIdentity`。程序写 `@kernel func f(...)`（或 `@kernel { ... }`）时，建图阶段就给 `f` 自己的节点及其中写下的分支臂、循环体、lambda 加上属性 `tiles.kernel`（不含被调函数）；Tiles 以 `GCGraph::nodeAttrs(ref)`（`camel/core/node_attrs.h` 的 `attr::valueOf(set, attr::key("tiles.kernel"))`）读出并据此检查。属性随内联、克隆、`LOOP` 降低保留，`std::gir` 显示为 `attrs="tiles.kernel"`。值的种类还有任意宽度的标志集、整数、字符串、图的引用与元组（如设备偏好可用一个 `Symbol` 值的键）。数值许可（`nodePermissions`）暂不变，待 `enum` 实现后一并迁到同一机制，届时另行说明。

### 6.4 原子与不规则写入

scatter-add、直方图一类的内核需要原子累加。原子累加改变合并顺序，按 7.2 需要"改变归约顺序"许可；语义稿的 gather/scatter 声明（地址依赖数据、写冲突、是否需要原子合并）给出它的语义。第一阶段不提供，列为后续。

## 7. 分阶段计划

| 阶段 | 内容 | 依赖核心 | 交付给用户的 |
|---|---|---|---|
| T1 | 归约融合：softmax、layernorm、按行归约各成一个内核；按规范顺序或经许可的树形顺序 | 无（先在 Tiles 私有表示里做） | 常见模型层的速度 |
| T2 | 矩阵乘接 cuBLAS，按数值许可选模式；去掉默认路径上的 `fmaf` | 数值许可的图上表示（语义稿第一阶段） | 矩阵乘速度、逐位一致的默认模式 |
| T3 | 异步执行与设备常驻：流、事件、内存池；相邻调用间的值留在设备上 | 资源协议（语义稿，可并行） | 去掉每次上传 |
| T4 | 语义迁到核心协议：先迭代域与索引映射，再归约与许可；私有表示改为"读核心语义 + 物理计划" | 语义稿第一、二阶段 | 其他遍能看到并复用这些信息 |
| T5 | `std::tiles` 遍：区域划分、`:tiles/exec`、符号形状编译、语义指纹缓存 | 图事实（语义稿）；第 3 步第四片的共享执行计划 | 整个程序自动受益，不必手包 `run` |

## 8. 已裁定的问题（2026-10-15，六条均按建议）

1. **分界**：语义（迭代域、索引映射、归约、许可、资源、形状事实）放在 Camel 图上，Tiles 只私有物理层。建议：采纳。
2. **主入口**：以 `std::tiles` 遍为主、`run<fn>` 为便捷入口；`:tiles/exec` 是带 `callsGraphs` 声明的普通算子，语义等于调用区域子图，去掉该遍结果不变。建议：采纳。
3. **块级内核的写法**：甲，块类型加对块的 `map`（第 6.2 节，函数式，CPU 上即参考语义）；乙，Triton 式指针加程序编号（第 6.3 节，命令式）。建议：甲为主写法，乙暂不提供。
4. **名字**：`Tile<T, [shape]>`、`x->tiles<[...]>`、`->untile`、`Tile::zeros` 等，是否就用这些，或另取。建议：先用这些，以 Tiles 模块的导出为准，不进入语言关键字。另定：`@kernel` 作为 Tiles 模块提供的可选标注（第 6.5 节）。
5. **块的形状**：块的形状必须是编译期常量或 `constas` 绑定的名字（第一阶段只接受常量）。建议：如此。
6. **原子与不规则写入**：第一阶段不提供，以后经"改变归约顺序"许可提供。建议：如此。

## 9. 最不放心的地方

1. **区域划分的粒度**。极大连通子图可能把两个各自适合不同调度的部分捆在一起；第一阶段宁可切得细，由 Tiles 在区域内部再分组。
2. **符号形状编译的代价**。一份代码覆盖所有批量大小，会失去对固定小形状的特化收益；可能需要"符号形状编译一份，常见形状再特化几份"的两级缓存。
3. **块级内核的表达力边界**。"对块做 `map`"覆盖规则的分块计算，但 attention 一类需要块间通信（在线 softmax 的跨块归约）；第 6.2 节的 `LOOP` 加块内归约能写出 FlashAttention 的结构，但还没有逐行推演验证。
4. **逐位一致的默认模式的性能**。按规范顺序归约在 GPU 上会慢；这是数值契约的有意取舍，许可是唯一的出口，需要让用户容易知道何时该授予。

## 10. 2026-10-16 评审与下一步（语言作者已同意，交 Tiles 执行）

依据：对 `develop` f2a12a5e 时 `modules/tiles` 的评审（读 README、IMPLEMENTATION、`docs/design/tiles-targets`、`docs/design/native-subgraph-call` 与源码结构；未在 GPU 上运行）。

### 10.1 已经做对、继续保持的

语义开始上图（算子标识与版本、数值分类、索引实例、`rowMajorView` 推出的物理映射、按归约规律选择并行最大值）；NVRTC 的 `fmad`、`prec-div`、`prec-sqrt`、`ftz` 显式固定并进入缓存键；只在授予 `contract` 时收缩乘加；矩阵乘按规范 FMA 链；主机标量成为运行时参数；同一行内多个归约共享中间值（softmax、layernorm 成为一个内核）；结构化内核表示 `kernel_ir`；区域间传输规划与常驻复用；原生算子回调 Camel 子图的通用服务（四个后端与并行调度器）。`@gpu` 作为"希望在 GPU 上执行"的显式标注保留，与 `std::tiles`（自动）和 `@kernel`（专家内核）并存。

### 10.2 三处纠正（按此执行）

1. **编译期编译、按区域退回。**
   - `@gpu` 函数在编译期按类型中的形状（含 `constas` 命名维度）编出内核；只有形状含未知维度时才退回调用处特化。规划与校验的结果随编译产物缓存，不再每次调用都做。
   - 退回 CPU 的粒度是区域：不支持的节点留在 CPU，其余照常在 GPU 上，而不是整个函数一起退回。把已有的区域抽取与外提（目前只在测试遍里）接成正式入口；同一机制即是第 3 节 `std::tiles` 的自动入口。
2. **逐位测试取代容差。** 按设计原则 7.1 的数值契约，加减乘除、开方、矩阵乘的 FMA 链、按规范顺序的求和、`max`/`min`/`relu` 等与 CPU 逐位相同；测试与基准的正确性门槛对这些运算改为逐位比较，只有超越函数按算子声明的 ulp 上界比较（从 `OperatorTable::semantics(id)` 读取）。容差只保留给放宽算法。按设计原则 7.3（2026-10-18），Tiles 默认可以改变归约与矩阵乘的累加顺序（并行求和、cuBLAS f32），因此测试分两类：安全模式下按上述规则逐位比较；默认模式下检查同一设备两次运行逐位相同，并按算子声明给出的误差上界与 CPU 比较。
3. **写明退回对结果的影响。** 超越函数在 GPU 与 CPU 上可以在 ulp 上界内不同，因此同一个 `@gpu` 函数在有无 GPU 时，涉及超越函数的结果可能在最后几位不同。在文档中写明；相关测试按 ulp 上界写。

### 10.4 核心这边相应的已知缺口

以下五项与 `argmax`/`argmin` 已于 2026-10-16 由核心修复（分支 `lane/core-gaps`），不需要 Tiles 处理：

- ~~空张量求 `mean` 时内核与定义图的故障种类不同~~：内核也报 `DivisionByZero`，与定义的除法同一诊断。（Tiles 自己的 `mean of empty tensor` 检查仍是另一种诊断，宜照此统一。）
- ~~int64 求和以 f64 累加~~：全量与按轴的 int64、布尔求和都在 int64 里精确累加并回绕；全量的 `sum`/`mean` 最后一次转为 f64。声明的归约律 `sum_i64`、`mean_i64` 等的累加类型改为 int64。
- ~~`exp` 对次正规结果冲刷为零~~：次正规结果在 2 ulp 内（实测正规 1.01 ulp、次正规 0.76 ulp），声明里去掉了 `not_ieee: subnormals`。Tiles 的 `exp` 也应给出次正规结果。
- ~~可选的 CBLAS 后端不遵守规范算法~~：按 7.3，CPU 上按库实现的 f32 矩阵乘默认可用，条件是可复现（7.6）；图上仍是 `tensor:matmul`，实现选择记在节点的 `tensor.kernel` 属性上（`tensor::fuse` 写，见 H102）。安全模式（`tensor::fuse(safe_fp=true)`）与 `#strict` 节点用规范算法。库只改累加的顺序与分组，不改算子身份（9.6）。
- ~~ONNX 导出的 `Slice` 仍截断~~：常量边界在已知长度上于导出时证明；其余边界经一个 `Gather` 守卫，越界时 ONNX Runtime 与 Camel 一样失败；在两臂都计算再选择的分支里这样的切片拒绝导出（带位置的诊断）。
