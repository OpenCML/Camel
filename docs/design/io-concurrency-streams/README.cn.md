# 网络、长耗时副作用的并发与流（设计稿）

状态：已定（2026-10-20，语言作者授权协调者按闭环原则定稿；设计原则 3.3、3.9、13.6）。依据：设计原则 3.3（资源）、3.4（`sync`）、3.1（按依赖求值）、13（AI 技术栈）；[重构总纲](../blueprint/README.cn.md)。

本稿覆盖近期与中期：智能体所需的网络与并发（近期），流（中期）。多机分布式运行时（大数据）列为长期方向，只在第 5 节给出约束。

---

## 1. 目标与已有的基础

| 方向 | 本质 | Camel 已有的 | 缺的 |
|---|---|---|---|
| 智能体 | 调用模型 → 调用工具 → 判断 → 再调用，是一张图（LangGraph 等框架在库里造这张图） | 循环、`enum`（消息、工具调用）、`Json`、资源系统、Python 互操作 | 网络与 HTTP；长耗时副作用的并发、超时、取消；流式接收 |
| 流式处理 | 数据源源不断地流过一张算子图（Flink、Beam） | 数据流图、资源、并行调度 | 流类型；窗口、按键聚合等算子；异步 I/O |
| 大数据 | 程序切分到多台机器执行的有向无环图（Spark） | 切分标签、表格是数组组成的结构体 | 多机运行时、超出内存的数据、Arrow/Parquet、容错 |

**核心主张：Camel 不需要 `async`/`await`。** 按依赖求值的语义本来就允许彼此独立的计算同时进行；有副作用的操作由资源系统排序（3.3）。只要运行时在一个操作等待网络时去做别的事，并发就自然出现，程序员不必把函数分成"同步版"与"异步版"（没有 Rust、C#、Python 的"函数着色"问题）。

## 2. 网络与长耗时的副作用（近期）

### 2.1 无序资源

问题：按 3.3，用到同一资源的副作用按书写顺序执行。若所有 HTTP 请求都用资源 `net`，就会排成一队，智能体的多个工具调用无法并行。

**建议：资源声明可以标明"无序"**：

```camel
export resource net unordered            // 用到它的副作用之间不保持书写顺序，可以同时进行
export resource stdout                   // 默认：有序
```

- 无序资源上的副作用之间没有顺序约束，彼此独立时可以同时执行；与其他资源、`sync` 块的关系照旧（`sync` 块内**它自己直接写着的**语句仍按书写顺序；写在里面的臂、循环体与嵌套块按各自的写法，3.4）。
- 先例：JAX 把副作用分为有序与无序两种。
- 需要顺序的请求（同一会话的连续请求）写在 `sync` 块里，或者以后用"按对象的资源"（会话对象，3.3 已列为以后）。

### 2.2 运行时：等待时不占线程

- 长耗时的副作用（网络、磁盘、子进程、调用模型）由运行时交给 I/O 层异步执行（Windows 的 IOCP、Linux 的 io_uring 或 epoll），执行器在等待期间运行图上其他就绪的节点。
- 这是运行时的实现，语义不变：结果与按某个合法顺序逐个执行相同。
- `std::nvm` 作为参考实现可以同步阻塞地执行（正确但不并发）；`std::prl` 与以后的执行器实现真正的重叠；`std::cpp` 生成的程序使用同一个 I/O 层的库版本。

### 2.3 超时

```camel
let r = http::get(url, timeout: 5.0)    // r: Response!
```

- 超时是调用的参数，超时返回错误值（`T!`，与其他可恢复的错误相同），不是故障。

### 2.4 竞速与取消

```camel
let answer = first_of(ask(model_a, q), ask(model_b, q))   // 先完成者的结果；另一个被取消
```

- `first_of` 是标准库算子：参数中先成功完成的那个的结果；其余的被取消。
- **取消是可观察的**（一个请求可能已经发出了一半），所以只有声明为**可取消**的副作用才能被取消：资源或算子声明 `cancellable`；不可取消的副作用即使输了也执行完，结果丢弃。
- 被取消的副作用不得留下不一致的状态：这是声明 `cancellable` 的库的责任（与 6.2 标签由库负责的原则一致）。

### 2.5 网络模块

- `net`：TCP、UDP 的底层原语（C++）。
- `http`：请求与响应（方法、头、正文、状态码）、流式正文（返回流，见第 3 节）、超时、重试由调用者组合。
- 正文的类型：文本是 `string`（UTF-8），二进制是 `Bytes`；`Json` 正文有便捷的读写。
- 安全：TLS 由底层库提供；证书校验默认开启。

### 2.6 智能体示例（官方示例 D9）

一个研究助手：多步推理，每步可以并行调用多个工具（搜索、读网页、运行代码），工具调用自动并行；整个流程本身就是一张图，可以用 `std::gir` 看到；与 LangGraph 写的同一智能体对照代码与延迟。

## 3. 流（中期）

### 3.1 流类型

```camel
let lines: string.. = fs::read_lines("big.log")      // 惰性、可能无限
let tokens: string.. = llm::stream(prompt)            // 模型边生成边交出
```

- **流 `T..`**（2026-10-24 改，设计原则 5.4）：按需产生、可能无限长的序列，是**值**——只有来源与去处是效应，中间的变换是纯函数。取代原来"`Stream<T>` 是句柄类型、`next(s)` 写 `uses s`"的写法：那会让纯的变换链也带上效应，挡住融合、并行与驻留执行。同一来源上的读取仍按顺序（来源是资源）。
- 来源：文件按行或按块、网络连接、消息队列、模型的流式输出、定时器；也可以由普通数组转换而来。

### 3.2 遍历与变换

```camel
let n = loop count = 0 for line in lines while count < 1000 do
    if line->contains('ERROR') then count + 1 else count

let errors = lines->filter<is_error>->map<parse_record>     // 惰性：不立刻拉取
for r in errors->window(seconds: 60) do report(r)            // 按时间窗口
```

- `for x in s` 遍历流（与 H4b 把 `for` 扩展到字符串、映射、张量是同一件事，流只是又一种可遍历的东西）；流结束时循环结束，无限流上的循环靠 `while` 条件或外部停止。
- `map`、`filter` 等作用于流时是惰性的，产生新的流；按需执行的规则不变：没有被拉取的流不执行。
- 标准库提供窗口（按数量、按时间）、按键分组与聚合、合并多个流、批处理（把流切成数组给张量计算）。
- **背压**是拉取模型自带的：下游不拉，上游就不产生。

### 3.3 编译

- 流的流水线在图上就是一串惰性的算子，编译时可以融合成一个循环（与张量的融合同理）；彼此独立的阶段按声明的独立性并行。
- 每个流上的顺序保持；跨流的合并按到达顺序，这是可观察的不确定性，由合并算子的声明说明。

### 3.4 自定义的流与驻留的流水线（负责人与决策者 2026-10-24，已定，见设计原则 5.4）

- **生成器即定义一个流**：除了库提供的来源，用户可以用"每轮交出一个值"的循环定义流（现有循环收集槽的惰性版本），例如数据加载器按批交出。消费者拉一次，循环走一轮。
- **驻留执行**（负责人提出的"图结构不变，数据在图中流动"）：一个以流为输入的函数，除了"每个元素把整张图跑一遍"，还可以让图**驻留**、元素像流水线一样流过——每个节点在输入就绪时处理下一个元素，多个元素同时在图中的不同位置。这是数据流机的原始执行模型（Dennis 的数据流机、Kahn 进程网络），与 Camel"按依赖执行"同源。
- **语义只有一个，执行方式是执行器的选择**：两种执行方式结果相同，前提与 Kahn 进程网络的确定性条件一致——每条边上元素保持先后、节点只按到达的输入计算。同一程序既可以按批也可以按流跑（Beam 的统一模型）。
- 要定的：跨元素的状态（`scan`/`fold`，对应循环状态）；同一资源上、跨元素的效应顺序（按元素的先后，顺序边随元素展开）；缓冲与背压在驻留模式下怎样保持（拉取模型自带背压，驻留时每条边一个有界缓冲）；按时间的窗口引入的不确定性在声明里说明。

## 4. 表格与 Arrow（与流、大数据相关）

- 表格是由若干列数组组成的结构体（原生多维数组设计稿 3.4）。每一列直接对应 Arrow 的列；通过 **Arrow C 数据接口**与 Pandas、Polars、DuckDB 零拷贝交换（与数组兼容 DLPack 同一思路）。
- 读写 CSV、Parquet、Arrow IPC 由库提供；大文件以流（按批）读取。

## 5. 长期：多机分布式运行时（大数据）

只定约束，不在本轮设计：

- 语义与单机相同：切分是标签与调度（13.4），程序不因在几台机器上运行而改变含义。
- 分区、洗牌、溢出到磁盘、容错（重算或检查点）由运行时负责。
- 先例：Spark 的 DAG、Beam 的统一模型（同一程序既能批处理又能流处理）。Camel 的流（第 3 节）与数组从一开始就按这个统一来设计。

## 6. 需要语言作者决定的问题

1. **资源可以声明为无序**（`resource net unordered`），用到它的副作用之间不保持书写顺序。
2. **不引入 `async`/`await`**：并发由按依赖求值与资源系统自然得出，运行时在等待时执行其他就绪的节点。
3. **超时是调用的参数，超时返回错误值**（不是故障）。
4. **取消只作用于声明为可取消的副作用**；`first_of` 作为标准库算子。
5. ~~`Stream<T>` 是标准库类型~~ —— 已由第 3.1 节与设计原则 5.4 取代（2026-10-24）：流是核心类型 `T..`，是值；拉取不是效应，来源与去处才是。
6. **表格兼容 Arrow C 数据接口**，零拷贝交换。
7. **长期方向**：多机运行时，批处理与流处理统一的模型。

## 7. 定稿时补上的闭环（2026-10-20）

- **按对象的资源**：流、会话、文件句柄需要"同一个对象上有序、不同对象互不约束"，而设计原则 3.3 原先只有按类别的资源（`var` 除外）。补为**句柄类型**：带 `#resource` 的类型，每个值是一个资源，操作写 `uses 形参名`，与 `var` 形参对称。
- **与 `sync` 的关系**：`sync` 块内**它自己直接写着的**语句仍按书写顺序，包括无序资源上的副作用；写在里面的臂、循环体与嵌套块不继承这个顺序（3.4）。
- **与按需执行的关系**：并发只决定已经要执行的副作用怎样重叠，不决定执不执行。
- **不确定性**：只有 `first_of` 这类取决于完成先后的算子引入不确定性，写在其声明中；测试用确定的替身。
- **求导**：流与数组一样没有切向量，按 9.9 拒绝。
- **各后端**：`std::nvm` 逐个阻塞执行（正确但不并发）；`std::prl` 与以后的执行器实现重叠；`std::cpp` 使用同一个 I/O 层的库版本。

### 3.5 生成器的执行（决策者 2026-10-24）

生成器本身就是驻留的：每拉一次，它从上次停下的地方继续一轮，状态（循环状态、上次停在哪一臂）一直保留——它是流水线的来源节点，图在整个流的生命期里驻留。所以"涉及流"的判据包括产生流的图，不只是消费流的图。生成器内部，元素之间只经状态相连；不依赖上一个元素的那部分计算可以**提前算出后面的元素**（预取），条件与把计算移出循环相同：被提前的部分必须纯且不会出故障，并且放在有界缓冲里；来源上的读取（效应）只在被拉取时发生，不预取。
