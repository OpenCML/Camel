# 下一轮重构总纲

状态：2026-10-19 与语言作者的长线讨论的系统整理。本文件是下一轮大规模重构的总指南：说明有哪些大块、各自定到了哪里、彼此的依赖、实施的先后、还有哪些问题待定，以及实施时必须守住的红线。

**本文件不重复规范的内容**：每一块的裁定以 [设计原则](../../design-principles.cn.md) 为准（规范性文件），细节以各设计稿为准；本文件只给出全貌与指向。两者不一致时，以设计原则与设计稿为准，并修正本文件。

---

## 0. 总的方向

- **图原生**：Camel 只建模计算的意图，语言元素与图直接对应；遍、优化、导出、微分、执行都是对图的操作。
- **只有一门语言**：类型层的计算、图的变换、规则、调度都用 Camel 本身写（1）。
- **从上到下的 AI 技术栈**：模型与训练 → 算子 → 块内核 → 调度 → 目标，同一份语义贯穿各层，每一层都能在 CPU 上核对（13）。
- **自己的库尽量用 Camel 写**，暴露语言的不足并吸纳进核心；C++ 原生模块合法但不过度依赖（10.4）。
- **红线要少，且每条都有强制机制**；倾向就按倾向记（见第 4 节）。
- **不考虑兼容成本**：内测阶段，旧写法直接退役并给出指向新写法的诊断，不做过渡层。

## 1. 八个大块

### A. 图模型与存储（第二版）

- 设计稿：[图存储与图 API（第二版）](../graph-store/README.cn.md)（已确认）。
- **要点**：只有一种图，快照中的不可变版本；值可以有多种写法（等价饱和是模型的一部分），"可执行"是一种被检查的状态；**区域**分控制区域（分支、循环，共用帧，循环可原生执行）与标注区域（内联来源、带标签的块）；顺序用控制边表达；32 位编号，无单图上限；列分块，提交只复制改过的块；`GraphId`、`NodeId` 稳定，函数值持（快照，`GraphId`）；快照与图版本由垃圾回收管理；事务以图为单位、可串行化的乐观并发，并行组合子按固定顺序提交；事实按需、增量地重算；所有"谁引用了 X"都用索引回答，不扫描。
- **与 RVSDG 的关系**：结构上向 RVSDG 靠拢（结构化节点与区域），顺序用控制边而不是状态值。相关工作见论文仓库 `TSE2027/research/graph-native-findings.md` 第 4 节。

### B. 图 API 与重写体系

- 设计稿：图存储第二版第 5 节；[规则、策略、分析](../rewrite/README.cn.md)（草案，16 条待定）。
- **要点**：三层 API（函数到函数的变换为入口；规则为主要写法；底层节点 API 为补充），不用字符串比较；`rule` 声明（`=>` 单向、`<=>` 双向、`when` 条件、`#requires` 所需许可），入库前强制随机检验；策略是标准库里的高阶函数；`analysis` 声明（待定）；合法性检查是库函数；等价饱和中的等价定义为"在值的许可之内可互换"（带许可的等价）。
- **内置库按难度依次改写到这套 API 上**，作为对 API 的检验：算式化简（改为规则库）→ 张量融合（规则加提取）→ 内联、折叠、CSE、DCE（底层 API）→ 切分（读标签与推导）→ 自动微分（用 Camel 写）。执行后端与 `std::macro` 的求值器保留原生实现。

### C. 类型系统与泛型

- 设计原则 1、5、6；设计稿：[泛型按结构展开](../generic-structure/README.cn.md)（方案 A，第 7 节为长线风险）。
- **要点**：一门语言，类型是编译期的值；`func` 与 `type` 对称（`F<...>` 只在类型位置）；原语以标记出现且数量固定（`typeas`、`constas`、`typeof`、`fields`）；简写可以有、语义只有一套；高阶类型；计算出的字段名加方括号；结构类型有限，递归经由 `enum`；泛型函数可省略返回类型；签名上 `where` 放约束（第二期）。命名类型（有名字的结构体与 `enum`），字段顺序属于类型，泛型函数体中的名字在定义处查找再加类型所在模块，泛型类型不变。`enum` 封闭、可穷尽。
- **实施**：交接任务 H1（`enum`）、H5（命名类型）；泛型第一期（`match type`、`static for`、推导式、`..`、返回类型推断）尚未排入任务书，依赖 A 的事务与区域，以及 H1、H5。

### D. 标签与装饰器

- 设计原则 6、9.4。
- **要点**：`@` 是变换（函数、代码块、类型函数作装饰器，一行一个、有序）；`#` 是编译期事实（`tag` 声明、`on` 位置、别名组、单个可省方括号），语言不赋予标签含义，含义由库定义、由读取它的遍实现并处理掉；标签属于声明，内联时随区域保留来源；算子的各项事实（纯度、故障、资源、数值分类、下标映射）都是标准标签；`macro` 改为标准标签 `#macro`；删除 `inner`、`outer`、`atomic`、`shared`；`#` 不再是注释。
- **实施**：交接任务 H2（标签机制、数值许可与 `#vjp`、`#macro` 改为标签）、H6。

### E. 效应与资源

- 设计原则 3.3。
- **要点**：`resource` 声明资源类别；资源是函数类型的一部分（`uses` 列表、`pure`），Camel 函数由编译器推出，原生算子写在签名中；每个 `var` 是资源；同一函数体内同一资源的副作用按书写顺序；副作用按需执行不变；`sync` 块保持原意；`wait` 与前缀 `sync func` 退役。
- **实施**：交接任务 H7。

### F. 数值契约

- 设计原则 7。
- **要点**：规范算法是参照；`reassociate`、`contract` 默认允许，`approx_math`、`change_precision`、`finite_math`、`nondeterministic` 用标签授予；`#strict` 与安全模式收紧；同一设备可复现；许可是节点标签，随节点保留。
- **实施**：随 H2 迁移到标签；默认值随 `NumericPolicy` 调整。

### G. AI 技术栈

- 设计原则 13；[Tiles 路线](../tiles-route/README.cn.md)第 10、11 节。
- **要点**：调度原则上由执行时注入（遍参数、调度文件），粒度到函数，也可以用 Camel 写成变换；`Tile` 加 `#kernel` 的专家路径保留；低层计算也是 Camel 图，物理操作由后端库登记；`Device<T>` 保留，搬运是普通副作用，异步不进入语义；分布式用 `#shard` 标签加 `shard` 遍；部署不另设格式；`std::cml` 导出源码，图与源码往返由测试强制。
- **实施**：Tiles 由另一位 AI 负责；核心侧随 A、B、D 推进。

### I. 原生多维数组、内存管理与互操作

- 设计稿：[原生多维数组、内存管理与互操作](../arrays-memory/README.cn.md)；设计原则 5.4、10.5。
- **要点**：数组与张量统一为核心类型 `T[维度...]`；形状检查进核心；稀疏、量化等是库中的命名类型；数值数组的运行时表示兼容 DLPack，零拷贝互操作；内存管理三层（编译期规划、缓冲区引用计数、分代回收），缓冲区是叶子，计数为 1 时原地更新有保证；各后端的落地方式与 Python 互操作的规则。
- **实施**：与 A 交织（第 1 层规划依赖第二版的使用者索引与执行计划）；红线是小型逻辑计算不变慢、张量程序的时间与峰值内存下降。

### H. 其余已定事项

- `string` 保证 UTF-8，`Bytes` 内建（已实施）；遍参数通用语法（已实施）；流水线由用户显式组合，模块不能自动加入遍（9.2 已改，代码待 H6 删除）；`macro` 求值失败按运行时故障处理。

## 2. 依赖与实施的先后

```
H1 enum ─┬─────────────────────────────┐
H5 命名类型 ─┤                            │
H2 标签 ──┼──┐                           │
H7 资源 ──┘  │                           │
             ▼                           ▼
A1 身份与快照 → A2 统一布局 → A3 索引与增量提交 → A4 执行计划
                                   │
                                   ▼
                    A5 区域、标签、名字的存储（分支、循环改为控制区域）
                                   │
                    ┌──────────────┼───────────────┐
                    ▼              ▼               ▼
            B1 图 API（函数到函数、底层）  C 泛型第一期   std::cml 往返
                    │
                    ▼
            B2 多种写法与饱和 → B3 规则与分析引擎 → B4 内置库改写
```

建议的阶段：

1. **第一阶段（语言表面）**：H1、H2、H5、H6、H7，可以并行，彼此依赖很少。
2. **第二阶段（图存储地基）**：图存储第二版第 7 节第 1–4 步。
3. **第三阶段（结构）**：第 5 步（区域、标签、名字）。
4. **第四阶段（API）**：图 API 第一层与第三层；泛型第一期；`std::cml` 与往返测试。
5. **第五阶段（重写体系）**：多种写法、饱和、提取；`rule`、`analysis`、策略；标准规则库。
6. **第六阶段（改写内置库）**：按 B 中的顺序。

每一步结束时：全部测试与随机程序测试通过；性能用 `test/plans/perf` 对比；所写的东西与设计原则、设计稿一致。

## 4. 实施时必须守住的红线（每条都有强制机制）

| 红线 | 强制机制 |
|---|---|
| Camel 程序造不出结构上坏的图 | 提交时的整体校验 |
| 后端只看到可执行状态的图（每值一写法、无环、类型正确） | 后端与导出遍入口的检查 |
| 会出错或有副作用的节点不被移出它的控制区域 | 提交时的校验 |
| 规则在入库前通过随机检验；分析满足合并律与单调性 | 测试工具枚举 `rule`、`analysis` 声明 |
| 图与源码往返一致 | 对全部测试用例与随机程序的往返测试 |
| 结果确定（同样的输入、同样的配置，结果相同） | 并行组合子的固定提交顺序；饱和与提取按编号决定；重复运行比对 |
| 同一设备上数值结果可复现（未授予 `nondeterministic` 时） | 重复运行逐位比对 |
| 承诺（`pure`、`uses`）不被违反 | 编译器检查 |

其余的都是倾向或质量要求，不是红线（例如"调度原则上不进源码"、"遍不改变语义"）。
