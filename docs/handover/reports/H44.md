任务书的三项（`docs/handover/README.cn.md` 第 5 节 H44 行）：ONNX 重名输出、折叠常量的 Safe
结构体 CAST（不依赖它展开）、结构体作为循环状态。第 1 项已合入；第 2 项查清了机制但没有以安全

## 设计上的选择

### 第 1 项：第二个输出用不合并的 Identity，而不是改输出名

- 另一个做法是保留共享节点、让两个输出直接指向同一个名字以外的名字。ONNX 允许一个值被两个
  输出引用，但那样两个输出名指向同一份值，模型输出张量的"身份"仍是一个；而 Camel 里
  `(y, y)` 是两个输出。给定第二个输出一个自己的 Identity，语义最直白：一个输出一个值。
- 另一个做法是给重复的那次改名（例如 `y_1`）。名字对用户可见（Python 里按名字取输出），
  自动加后缀会让用户看到自己没写过的名字；`appendIdentity` 以调用方给的名字为提示
  （`fresh(name)`），输出名就是调用方要的那个。
- 没有改 `Emitter::node` 的 CSE：结构性合并本身是对的（同一个图的同一个计算只该有一份）；
  要改的是"输出"这一层。

### 第 2 项：查清后不落地，保留 `constantOf` 的 workaround

任务书要求：先让展开不依赖 CAST，再打开 `std::opt` 的结构体 CAST 折叠、删掉
`modules/onnx/passes/export.cpp` 里 `constantOf` 穿过 CAST 的 workaround。按这个顺序做了实验，
结论是"展开依赖 CAST"只是表面现象，真正的问题是**运行时的特化在导出简化里没有止境**。

复现与测量（`test/cases/modules/onnx/refusals/unended_unrolling.cml`）：

- 保持 workaround、不折叠：`std::macro std::opt onnx::export` 0.084 s 成功；算子路径 0.29 s；
  `typed_constant_ends_unrolling` 两条路径 60–88 ms（基线）。
- 打开 Safe 结构体 CAST 折叠（`src/passes/opt/generic/generic.cpp` 的 `foldStaticCast` 增加
  `safeStruct`）：导出在 ~22–40 s 后报
  `the simplification of the exported function did not end: unrolling the recursion of 'walk'
  filled the memory the compiler keeps graphs in (the graph 'model' it was building takes
  ~244928 bytes ...; the function the export received had 46 nodes in 3 graphs)`。
  `model` 每轮变大（节点 id 21/46/76/…，每次都是同一个调用点的另一份内联体）。

机制（`CAMEL_H44_DEBUG` 插桩，已删除）：

1. 导出会对入口图反复跑"简化 + 内联 + 特化"直到不动点（`kMaxExportRounds = 4096`）。
2. 每轮是一次新的 `RuntimeGraphDraftSession`，特化缓存按会话存放，所以上一轮造出的
   `walk$spec0`、`walk$tspec1`、`walk$tspec2$tspec4` … 下一轮查不到，又造新的。
3. 内联器把"调用点更精确"的实参喂给递归调用，`specializeDirectFuncInDraft` 于是再造一层
   特化；`kMaxTypeSpecializationsPerRecursiveFunction = 8` 按"当前可达的提交闭包"计数，旧特化
   一旦不可达就不再计数，于是永远数不到 8。
4. 会话里造出的图不在 `RuntimeCallGraphSccInfo` 的分析里（`componentOf` 查不到），所以在
   "这个调用是不是递归的"判断上被当成普通函数，被内联进 `model`；内联体里的递归调用又被
   下一轮特化。循环就这样闭合了。

试过并撤回的修法：

- 让 `shouldSkipRecursiveInline` 也拒绝"调用到递归"的被调方：挡住了 `export_slice_loop` 一类
  合法程序（入口函数小、必须被内联才能看见 `export_model` 请求）——撤回。
- 给会话特化图加 `kGraphFlagSpecialized`，只拒绝把它内联进外部调用方：`export_gated_gru_step`
  这类训练步导出依赖这种内联（展开 T=3），被拒后 `slice_grad` 的轴不再是常量——撤回。
- 把 `onCallCycle` 改成"跟到底"的 `graphReachesCallCycle`，并对"分支臂里、调用点落在环上"的
  调用**清掉全部绑定**（不只是常量绑定）：`unended_unrolling` 的导出 0.084 s 成功，但
  `export_gated_gru_step` 回归（同上）。单独恢复这项清空后 GRU 正常、walk 又开始无限展开。
  两者需要的信息（"这个类型细化是不是导出展开需要的那一个"）在 `collectDirectFuncSpecializations`
  里拿不到，属于语义判断。

因此选择：**不打开折叠**，并把实验改动全部撤回——`foldStaticCast` 与 `constantOf` 都保持
`ce16c788` 的状态（`constantOf` 仍穿透 CAST）。这样 `std::opt` 的结构体 CAST 折叠仍是一个
待做的改动，而不是半开的状态；`src/runtime/draft_inline.cpp`、`src/passes/opt/inline/engine.cpp`
里试过的运行时改动也没有留下。

## 待决问题

### Q1：递归的展开在"分支取决于运行时数据"时有没有语义上的上限

例子：

```camel
func walk(x: Tensor, k: int): Tensor {
    return if k >= 6 | sum(x * x) < 1.0 then x else walk(tanh(x) * 0.3 + x * 0.6, k + 1)
}
```

`k` 是编译期可见的计数器，展开 6 层后条件变成常量、循环闭合；但若递归的继续条件完全由数据
决定（例如 `if sum(x) < 1.0 then x else walk(x * 0.5)`），导出的语义是"直到不动点"，而图上的
展开没有上限。

建议：把"能导出为 Loop 的递归"限定为"递归调用的实参类型在每一层不变"（当前导出器已经在
`exactTypeOf` 上做了这件事），并在运行时特化一侧给出同样的界限：对"调用点在分支臂里"的递归
调用，不因实参更精确而产生新的特化。前者已在导出器里；后者会影响 `export_gated_gru_step`
这类合法的定长展开，所以需要作者定"哪种类型细化算展开、哪种算优化"。

影响：挡住第 2 项（结构体 CAST 折叠）的落地；也挡住任何"折叠让常量更早出现"的优化。

### Q2：一次 pass 的反复简化要不要共用一个 draft 会话

例子：导出器的 `simplifyFully` 每轮调用一次优化 pass，每次都新建 `RuntimeGraphDraftSession`；
特化缓存、`specializationNonce` 都按会话清零。于是同一份特化在下一轮重造，图的身份每轮都变。

建议：把"一轮 pass"与"一次会话"分开——`OptimizeRewriteConfig` 或 pass 的参数里带一个可复用
的会话，导出器的多轮简化共用一个。这样 `walk$spec0` 第二轮就能查到，展开自然停下。

影响：这是第 2 项真正需要的修法；不确定是否会与"会话即一次提交"的现有不变量冲突，所以没有
自行改。

### 第 3 项：结构体作为循环状态

- 现状：ONNX `Loop` 的 carried 值只接受张量/标量；结构体状态在 `isCarriable` 处被拒绝。
- 设计轮廓：
  1. `flattenValue` 已能把一个值拆成叶子（`If` 输出用它），把它推广到结构体：按字段声明顺序
     递归展开，叶子是张量或标量；`rebuildValue` 反向重组。
  2. `emitLoop` 的 carried 输入按叶子各建一个输入（名字由路径拼出，例如 `state.w`），
     init 来自结构体示例值的叶子；循环体入口用 `rebuildValue` 把叶子重组成结构体，跑完
     body 后用 `flattenValue` 拆下一次状态；`Loop` 的输出再重组回结构体。
  3. 非张量叶子（`int`/`float`/`bool`）走 ONNX 的标量类型（`int64`/`float`/`bool`），
     需要在循环体两端加 Cast，和现有 `If` 分支的标量处理共用。
  4. 验收：`test/cases/modules/onnx/ort_struct_loop.cml`（状态含两个张量 + 一个计数器，
     跑 0..6 层，ORT 与 NumPy 对比）；再补一个"结构体里再套结构体"和一个"空结构体"的用例。
- 没做，因为前置条件（第 2 项）没有满足。
