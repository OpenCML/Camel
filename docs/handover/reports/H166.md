### 1.2 观察到的拒绝

```text

'pyplot:plot', which no loaded module implements.
  --> /tmp/h166probe/stdlib/pyplot.cml:3:1
```

### 1.3 代码路径

`Builder::declareNativeOperator`（`src/compile/gir/builder_modules.cpp:357-486`）对每条无体声明
做两次检查：

1. **执行器**（377-382）：`context_->execMgr().findWithoutImport(uri)` 必须找得到。这里已经
   通过——`ExecutorManager::find` 按 `:` 取协议、派发到已登记工厂，再用名字后缀查
   `Executor::opsMap_`（`src/execute/executor.cpp:101-121`）。`modules/python/module.cpp` 的
   `load()` 在 641 行登记 `"python"` 工厂，`modules/pyplot/module.cpp` 在 314 行登记
   `"pyplot"` 工厂，执行器表里也确有 `py_exec`/`plot`。所以拒绝不是「执行器没加载」。
2. **纯度**（385-390）：

   ```cpp
   const auto registered = OperatorTable::instance().find(uri);
   if (!registered) { ... NativeDeclarationNotLoaded ... }
   ```

   `OperatorTable::find`（`src/core/operator_table.cpp:151-164`）对 `Effect::Undeclared` 返回
   `nullopt`，而这两个模块的 `load()` 从未调用 `OperatorTable::declare`。所以第一个检查通过，
   第二个失败——报错文本与执行器检查相同，仅凭文本会误判。

### 1.4 H157 的 13 条与「是不是全部原因」

`camel inspect --ops` 在补齐之前枚举出 `python` 的 12 条 URI（`py_call` 两个 URI，其余 10 个
名字各一条）与 `pyplot` 的 1 条，共 **13 条**，全部 `"purity":"undeclared"`。H157 的估算
**精确成立**。

补上注册后，同一对探针声明（`py_exec` + `plot`）`camel check` 直接退出 0；再把完整的
`pyplot`（8 条）与 `python`（6 条）声明放进去，同样退出 0。因此对这 7 个名字，**缺纯度就是
全部原因**，不是更深机制问题的症状：签名先通过了 GCT，执行器也在，只差注册事实。

真正的「症状」在覆盖面：`test/cases/modules/stdlib/registry_all.cml` 原先不导入这两个模块
（它只收「不需要外部运行时」的模块），而 `camel inspect --ops` 遇到声明装载失败仍然退出 0
（`tools/camel-cli/main.cpp:433-443`），所以 13 条未声明纯度长期没有被仓库里的门禁看到。本次
把两个模块加入 `registry_all`，并让 `inspect --ops` 继续只做枚举（它的退出码语义不在本任务
范围内，未改）。注意：加入后 `registry_all` 的「无外部运行时」注释改为说明「加载内嵌解释器，
不需要外部 Python、显示或 GPU」。

一个操作上的坑值得记下：`/tmp` 副本里必须放**这次构建**的 `.cmo`。第一次复测时副本里仍是旧
`.cmo`，补了注册的新二进制没有生效，纯度还是 `undeclared`，症状与修复前一样；把
`out/latest/stdlib/{python,pyplot}.cmo` 一并复制过去后才是真正的复测。

## 2. 修复：把纯度注册进 `OperatorTable`

两个模块各自在 `load()` 的 `loaded_ = true` 之前调用：

```cpp
camel::core::OperatorTable::instance().declare("pyplot", {{"plot", false}});
```

```cpp
camel::core::OperatorTable::instance().declare(
    "python",
    {{"py_call", false}, {"py_call_kw", false}, {"py_exec", false}, {"py_eval", false},
     {"py_run", false}, {"py_attr", false}, {"py_import", false}, {"py_print", false},
     {"py_println", false}, {"py_wrap", false}, {"py_unwrap", false},
     {"py_dispose", false}});
```

全部是 `effectful`，逐条理由写在源码注释与第 3、4 节：

- `py_call`/`py_call_kw`/`py_exec`/`py_eval`/`py_run` 执行任意 Python：可能打印、改对象、写
  文件；
- `py_attr` 可能触发 property/descriptor（任意 Python 代码）；
- `py_import` 执行模块体并写 `sys.modules`；
- `py_print`/`py_println` 写解释器的标准输出；
- `py_wrap` 创建解释器对象（身份与引用计数是可观察状态），`py_unwrap` 读取可能被 Python 改过
  的对象，`py_dispose` 改引用计数；
- 没有一条是 `stateOnly`：它们的状态是解释器，不是程序的变量；也没有声明 `pure` 或资源——
  声明 `pure` 会真的隐藏副作用，而资源名只能靠猜（`py_call` 可以写任意文件），按全局顺序处理
  才是保守且正确的。

### 2.1 行为中性的证明

用一个同时导入两个模块并调用 13 个算子的探针程序（`/tmp/h166probe/probe.cml`），在注册提交
前后各跑一次：

| 输出 | 注册前 | 注册后 |
|---|---|---|
| `camel check` | 0 | 0 |
| `camel inspect --ops` | 13 条 `python`/`pyplot`，全部 `undeclared` | 同样的 13 条，字段逐字相同，**只有 `purity` 变成 `effectful`** |
| `camel probe.cml std::jgir` | — | 与注册前 **SHA-256 相同**：`6662958c68a21a5a6d507aec7bc5b2031d1750e97b3d39d877c9d8d70e0e485f` |

`inspect --ops` 的 diff 只有 13 行 `-...undeclared` / `+...effectful`，`with`/`norm`/签名一个字
都没动；`jgir` 是逐字节相同。原因也清楚：未声明时 `Undeclared` 本来就按 effectful 处理
（`docs/design-principles.cn.md` 3.3），注册只是把隐含的语义写实，优化遍看到的仍是「有副作用、
不可折叠、不可合并」。

### 2.2 迁移后的 `inspect --ops`

声明文件接上以后，同一探针的这 13 条才变成具体签名：`pyplot:plot` 从
`(data: (typeas T)[], filename?: string) => void`（`norm:-1`）展开为 8 条（4 种元素类型 × 2 种
参数个数，`norm:1/2`）；`python` 的 6 个固定签名变成声明里的参数名与类型；5 个留在 C++ 的名字
（`py_call` 两条、`py_print`、`py_println`、`py_wrap`、`py_unwrap`）逐字保持原样。这正是任务书
要求的「`with`/`norm` 变具体、其余不变」的阶段。

## 3. `pyplot` 的迁移

### 3.1 为什么是 8 条

`pyplot:plot` 只有 1 个名字、1 个 URI，但签名是「`i32`/`int`/`f32`/`float` 四种元素的数组，可带
可不带输出文件名，返回 `void`」。无体声明写不出「这四种之一」：写成 `(typeas T)[]` 会接受
`string[]`，而内核明确拒绝；也不能写可选参数 `filename?: string`（声明语法没有可选参数）。所以
四种元素类型各写一条、两种参数个数分开，共 **8 条声明**。H157 的「补纯度后 8 条声明」估算
**成立**；这也顺带验证了「同一 URI 的多条同参数个数重载」能被装载器和 `inspect --ops` 正确
处理（`statistics:mean` 已有先例，但 `pyplot` 是 1 个名字 8 条的极端形状）。

### 3.2 改动

- 新增 `stdlib/pyplot.cml`：`module pyplot`，8 条无体 `export func plot(...)`，文档注明
  「八条声明是同一个算子」「可选参数/联合元素类型写不出」。

## 6. 待作者裁定：`PyObject<T>` 不能出现在声明里

### 6.1 现象

在探针声明里写：

```camel
export func py_wrap(x: typeas T): PyObject<T>
```

`camel check` 给出：

```text
error[SemanticDiag::InvalidTypeArgument]: ... a type variable cannot be an argument of a module type
  --> python.cml:3:...
```

诊断码 `0x03000020`，位置是 `src/compile/gct/builder.cpp:4877-4881`：模块类型（`PyObject`）
的类型实参若含类型变量就拒绝；旁边的注释说明「`Map`、`Set` 的参数是普通类型，数组/元组可以带
类型变量，模块类型只收具体类型」。

### 6.2 为什么这是问题

`py_wrap`/`py_unwrap` 的 C++ 解析器恰恰是**参数化模块类型**：`PyObject<T>` 保存被包装值的
Camel 类型，`py_unwrap` 靠它把值取回。今天这两个算子只能留在 C++ 的 `DynamicFuncTypeResolver`
里，声明文件写不出它们的类型。H157 把它记为「阻塞：`PyObject<T>` 不接受类型变量」，H166 确认
根因是 GCT 的这条通用规则，不是 `python` 模块的特例。

### 6.3 需要作者回答的问题

声明语法（无体 `export func`）是否应当允许**类型变量作为模块类型的实参**，当且仅当该模块类型
在 C++ 侧本来就是参数化的？

可选方向（本报告不选，等裁定）：

1. **允许**：在声明上下文中放开「模块类型实参不得含类型变量」，由模块自己的类型参数个数/约束
   决定是否合法。风险是别的模块类型（带具体参数、但 C++ 侧不接受变量）会被错误接受，需要模块
   导出「可参数化」的标记。
2. **加专用语法**：例如声明里写类型构造器/别名，让 `PyObject<T>` 成为一个合法的参数化类型名，
   而不是绕过 GCT 的检查。成本更高，但把规则集中在类型系统。
3. **保持阻塞**：`py_wrap`/`py_unwrap` 永久留在 C++ 的计算签名里，账本如实记录。代价是
   `python` 永远有 2 个名字不能声明。
