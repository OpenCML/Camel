# H37 — a library program computes its module-level values

Worktree `D:\Projects\Camel-wt\h37-let`, branch `handover/H37-library-let` (from `develop`).
Everything is left in the working tree: no commit, no new branch, no push.

A pass written in Camel (`camel_pass`, the `compileAsLibrary` route) read `0` for every
module-level value of its own module — a silent wrong value, not a diagnostic:

```text
module h37let
import { Program } from graph
let two = 2
let four = two + two
func compute(): int { return 7 }
let seven = compute()
export func show(p: Program): Program! sync {
    println(two); println(four); println(seven)
    return p
}
```

```text
camel tiny.cml h37let::show std::nvm   # before
0
0
0
42
```

The design frame is design principles **10.1** (a module's top-level code is not run by
default; one `__root__` graph for the whole program; functions read top-level values through
capture ports bound by "module + name"; a top-level `let` is a node of the root, computed when
something depends on it, before `main` starts), **3.5** (captures are by reference) and **5.1**
(a literal takes its type from context).

---

## 1. Root cause, with the evidence

**The library program's module-level root graph is not executed — it is not even part of the
tool program: `libraryFunction` encoded the pass function graph alone, and the external
`callGraph` binds only ordinary ports; a capture is bound only by a call's with-inputs or by a
function value's closure tuple, so the pass's capture ports kept the frame default 0.**

The two halves, each verified before any change:

1. **Nothing executes the root.** `DefinitionStore::libraryFunction` (the only producer of a tool
   program, used by `src/execute/camel_pass.cpp`) took the function's graph from the module's
   export table and called `encodeToRuntimeProgram(function, …)`. The encoder walks what the
   function reaches (`collectReachableGraphs`: sub-graphs, dependency graphs, static function
   references, FUNC targets, loops) — never the module's root graph — and logs the miss:

   ```text
   GIREncode  Encoding 1 reachable compile graphs.
   GIREncode  Prepare compile graph 'h37let::show'.
   GIREncode  Resolve outer graph for 'h37let::show': outer='__root__' prepared=false.
   GIREncode  Encoded runtime root 'h37let::show' with 1 runtime graphs.
   ```

   `outer='__root__' prepared=false` is the root graph referenced (for the capture's origin,
   debug metadata) and absent from the program. The `-vv --log-include GIREncode` run above is
   the whole tool program: one graph.

2. **Nothing binds the capture.** `NodeVMSchedPass::callGraph` (called from
   `CamelPass::apply`) asserts one argument per **norm** port and sets those slots only; it does
   not look at with-ports or closure nodes. In an ordinary run the binding comes from elsewhere:
   `fillFrameForIndirectCall` copies the callee's `Function::tuple()` into the target graph's
   closure slots (`src/execute/graph_runtime_support.cpp:1107-1130`), and
   `bindDirectCallFrameSlots` does the same for a direct call's with-inputs. A tool program has
   neither: no call node, no function value. The three capture ports therefore kept their frame
   default, `0`, which is exactly what was printed.

Which of the two it is: **the root is not executed**. Binding the ports without executing the
root could not work in general, because `let seven = compute()` needs `compute` to run; and the
runtime graph deliberately carries no mapping from a capture port to a module-level value
(`GCGraph::captureNames()` is debug metadata only: "what a capture is bound to at run time is
the closure tuple and the with-inputs of a call", `include/camel/runtime/graph.h`). The
missing piece is the computation, so the fix had to execute the root.

## 2. The fix, and why at that layer

The library is compiled as **a program of its own whose entry is the pass function**, built by a
builder of its own; the tool program the context keeps is that program, and the graph the pass
runner calls is its **root**:

| layer | code | change |
|---|---|---|
| graph builder | `src/compile/gir/builder.h`, `program.cpp` | `buildLibraryEntry(module, entryFunction)`: `buildFrom(unit, callEntry=true)` with the entry name recorded for `buildEntryCall` (it was `buildFrom(…, false)` for a library) |
| entry call | `src/compile/gir/builder.cpp` (`buildEntryCall`) | the entry name is `main` for a program, the pass function for a library program; when it is a library's, the root graph's type takes the entry's exit type as well as its parameters, so the root has the pass's signature (`(Program) => Program!`) |
| module | `include/camel/core/module/userdef.h`, `src/core/module/userdef.cpp` | `compileAsProgram(entryFunction, problem, root)`: parsed, GCT, a fresh `Builder`, `declareModule`, export check, `buildLibraryEntry`; the builder is kept with the module (`programBuilders_`), the module's own program graph is left alone (`buildingProgramOfItsOwn_`), and the old restriction stays ("a library compiled on its own (X) imports modules written in C++ only") |
| store | `include/camel/runtime/definitions.h`, `src/runtime/definitions.cpp` | `library()` split into `importLibrary()` (import only) + compile-as-library; `libraryFunction` uses `compileAsProgram` and encodes `rootGraph` instead of the function graph; `LibraryFunction::graph` is documented as that program's root |

Why this layer, and not binding the ports: a program computes its top-level values before
`main` starts, and the pass is now that program's entry, so the root graph does exactly what a
program does — no new binding rule, no capture-origin map in the runtime, `callGraph` unchanged.
Because the root graph's exit is the call of the function value that `buildEntryCall` makes,
`fillFrameForIndirectCall` binds the function's captures from that value's closure **after** the
top-level values have been computed, which is the same rule an executable uses. Unused
module-level values stay dead and are not computed (checked: a `let unused = print(…)` in a pass
module prints nothing, without a warning — design 10.1, "被依赖才求值").

The compile is a program of its own, not a re-use of the module's library build: an entry call
per requested function cannot share one root graph (one call node holds one signature), and a
pass module may export several passes (locked: two passes of one module each run their own
root).

| `camel_pass_module_importing_a_camel_module_is_refused` (`camel_import_values.cml`) | a pass module importing a module written in Camel is refused with "a library compiled on its own (camel_import_values) imports modules written in C++ only" (task H36 item 1), not run with the imported value reading 0 |

The third case is the "imports the value from another module" case with the restriction that is
in force: a module written in C++ is the only kind a library compiled on its own may import
today. The fourth case locks the refusal so that, when H36 item 1 lands, this test is updated
deliberately instead of the value silently returning to 0.

**Operator-definition programs (same route): affected, and it is a refusal.** A definition
library is encoded as the function graph alone (`DefinitionStore::build`), so a definition that
reads a module-level value has a capture node and is refused by the existing check
`its graph does not take exactly the declared parameters` (`src/runtime/definitions.cpp:339`).
That is a diagnostic, not a wrong value; the check now has a test:
`bad_definitions.cml` exports `captured` (reads `first_axis = 1`), `test::definitions` declares
it for `tensor:matmul`, and `modules.definitions` expects
`DEFINITION capture refused: the definition of 'tensor:matmul' is refused: its graph does not take exactly the declared parameters`.

## 4. What else the same cause explains

| place | what happens | why |
|---|---|---|
| an operator definition (`DefinitionStore::build`) that reads a module-level value | refused: "its graph does not take exactly the declared parameters" | same encode-one-function-graph route; the capture node is what the check sees. Locked (see above) |
| a rule written in a module (rule engine, `modules/rewrite`) whose body reads a module-level value | refused at rule build: `RuleInvalid: Rule 'same': the right side reads a port that is not a parameter` (`src/runtime/rules.cpp:130`) | the rule maker's graph is called through `callGraph` without a closure, and the rule validator already refuses any non-parameter port. A diagnostic, not a silent 0 |
| a module-level constant in a **signature** (an array extent, a `const [n]` tensor dimension) | not affected | signatures are compile-time; the constant is part of the type the builder writes, and the encoded graph carries no runtime read of it |
| a **default argument** | not applicable | Camel has no default arguments on functions; the defaults of a pass's own parameters are pass parameters (H36 item 2), and a pass with `with` parameters is refused today as "is not a pass", so no value is read |
| a pass module applied twice | top-level values are computed again per run (locked by `camel_pass_module_level_values_run_each_time`) | the tool program is run once per application; see open question 1 |

## 7. Open questions

1. **A pass applied twice computes the library's top-level values twice.** One run of a program
   computes its top-level values once; here each application is one run of the tool program. The
   cases lock the current behaviour. Computing once would need the context to keep the tool
   program's root frame (or the values) alive between runs — a decided change of what a run of a
   tool program means, not made here.
2. **A pass module that the processed program itself imports.** `compileAsProgram` declares the
   module on a builder of its own, so the module's export table now points at the tool program's
   graphs. The program is already built and encoded when passes run, so nothing reads those
   entities afterwards in the tests; a later lazy use of them (a generic instance built at run
   time, say) would want the entities of two builders separated. Not observed; worth a check if
   a pass module is ever also imported by its program.
3. **Camel-module imports for a pass library** are still H36 item 1, and stay a refusal with a
   diagnostic (locked). When H36 lands, the third case in §3 should become a passing value case
   rather than the refusal one.
