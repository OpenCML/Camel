## 3. 脚本的契约（`scripts/release-gate.mjs` / `npm run release-gate`）

**入口**：`package.json` 的 `"release-gate": "node ./scripts/release-gate.mjs"`；`docs/npm-scripts.md` 有一节说明；`docs/test-plans.md` 的 “Running The Tests” 指向它。项目对聚合命令的既有做法就是 `npm run` 别名（`check`、`test`、`test:all`），这里照做。

**三个阶段，顺序固定**：

1. **fast 层**：`smoke` + `test/plans/feat` + `test/plans/gpu/profile.plan.toml`，`--tier fast`。前两个等于 `npm run test` 的目标；第三个是 fast-tier 但没有任何闸门目标能到它的计划（6 条）。
2. **slow 层**：H154 §3 的 11 个计划文件，**逐个点名**。点名文件会让 runner 跑完整个计划（slow 用例不再被 tier 滤掉）；这也意味着其中 6 个快层计划会在两个阶段各跑一次（约 273 条重复），这是 runner 只能按文件选择的代价，脚本把它打印出来。
3. **静态检查**：`--verify-ops`、`--verify-doc`、`diagnostics-catalog --check`、`check-doc-links --all`、`check-retired-names`、`check-doc-snippets`、`stdlib-declarations --check`、`check-std-includes`，共 8 项。

**诚实性（这是 H154 的教训）**：

- 每次运行都打印**跳过清单**：19 个计划文件，按名字、按理由（见 §4），并明说“这些用例是 UNKNOWN，不是绿”。
- 也打印**不归它跑**的东西：debug 层（`--tier debug`，需要 Debug 构建）。
- **拒绝**按 tier/目录选：`--tier`、`--all`、`--suite` 一律 exit 2，消息里点名 `agents/test.md` 的政策；`--include`/位置参数如果是（或目录里包含）19 个文件之一，同样 exit 2 并列出是哪个、为什么。
- **不构建**；用 `scripts/build-info.js check --tag <out 下的 tag>` 校验安装的构建戳与本树来源一致，不一致就 exit 2（H149：不能拿别的 revision 的 `out/latest` 测这棵树）。安装不在 `out/` 下时，脚本明说“无法核对构建戳”，不假装核对过。
- 阶段失败即非零退出（runner 的 exit 1 或任一静态检查非零）；没有 `[SUMMARY]` 的阶段按失败处理，不按“无输出=通过”。
- `--only fast|slow|static` 是给排查用的**部分运行**：会打印 `PARTIAL RUN, not a gate result`，不会伪装成门禁。
- `--dry-run` 只打印命令与跳过清单；`--jobs` 默认 8（`-Jobs 12` 在共享主机会让 `gpu_preference.no_device.*` 假超时）。
- 自检：`SLOW_PLANS`/`FAST_TARGETS` 与 `FORBIDDEN` 有交集、或 slow 列表里的文件不存在，脚本 exit 1，不静默跳过。

**退出码**：`0` 所选阶段全过；`1` 有阶段失败；`2` 拒绝或无法开始（禁止集、缺构建、参数错误）。拒绝发生在任何命令启动之前。

## 5. 新红的分诊：`compile_bench.smoke`（过期期望，已修）

### 5.1 现象（第 1 次门禁，`1fb0b425d`，快层唯一失败）

```text
[FAIL] compile_bench.smoke  613.69 ms
    [INFO] expected exit 0, got 1
    [INFO] stdout does not start with "ok compile benchmark"
    [INFO] output contains 'FAIL'
```

在主机上直接跑 `python3 benchmarks/compile/bench.py check` 得到两行：

```text
arith10/passes: loaded library modules ['rules', 'graph', 'math']; expected ['rules', 'math']
chain-3/passes:  loaded library modules ['rules', 'graph', 'math']; expected ['rules', 'math']
  … The program's own modules were ['main'] / ['main','bm_0000','bm_0001','bm_0002']
```

### 5.2 根因：H141 的 `graph` 声明化，pin 没跟上

- `bench.py` 的 `PASS_LIBRARY_MODULES = ("rules", "math")` 是 H144 立的 pin，注释写明它允许在“库重构（`stdlib/rules.cml` 的 import 变了，或出现/消失一个声明模块）”时更新；它要抓的正是这种变化。
- H144 的修复 `de7d12868`（08:59）修的是**用户模块**计数（H147 的 4 → 6），与本条无关。
- H141 的 `df0aa1993`（09:30，合并 `5b1988d62`，在 H144 之后）把 `graph` 改成声明模块 `stdlib/graph.cml`；`stdlib/rules.cml:11` 就写着 `import { Program, Node, constant } from graph`。于是 `std::opt` 的代数阶段加载 `rules` 时会把 `graph` 从 Camel 源编译进来，和 H112 之后的 `math` 一样被计入“按需编译的库模块”。
- 证据它**不是泄漏**：`modules_user` 没有变（`['main']`、`['main','bm_0000'…]`），变的是 `modules_library`；H141 的报告本来就记录 `graph` 成为声明模块、`--verify-ops` 365 → 367。
- 所以：**不是 H147 那条红复发，也不是新回归，是 H141 落地后遗留的过期期望**。H154 在 `37079f9f5` 上跑 compile bench 时 H141 还没合并，所以 H154 看到的是绿的。

### 5.3 修法与验证（独立提交 `788a179b2`）

- `PASS_LIBRARY_MODULES = ("rules", "graph", "math")`，注释与失败消息改成 `rules/graph/math`，并写明 `graph` 自 H141、`math` 自 H112 起是 Camel 写的声明模块。
- 同一提交把 `docs/technical/38_compile_pipeline_cost.md` 里两个由同一原因变旧的数改对：chain-3 的 total `6 → 7`，chain-128 的 total `131 → 132`。

- 第 2、3、4 次门禁（`788a179b2` 与 `8439c65a7`）里 `compile_bench.smoke` 都是绿的。
