## 1. 实参元素的诊断位置与引用文本

### 问题

GCT 的 `literalElements_` 只记每个元素的**精确值**（H27b 为「只舍入一次」加的），不记元素在源码里的位置。GIR 在实参位置转换元素时（`compositeDataInType` → `literalElementInType`）手上只有整个字面量的 GCT 节点，于是

```camel
func sum32(xs: i32[]): i32 { ... }
sum32([1, 3000000000])
```

报在 `[`（`14:19`），引用的是 `literalValueText` 的规范文本（`1e40` 写成 `1e+40`）。声明位置走 GCT 的 `literalNodeInType`，落在元素上，但引用文本同样是规范文本，与 5.1（「消息引用源码里的写法」）和 H24 为标量声明位置加的 `sourceTextAt` 不一致。

### 改动

- **GCT 记下元素的位置**（`include/camel/compile/gct/tree.h`、`src/compile/gct/tree.cpp`）：`literalElements_` 的值类型从 `std::vector<std::optional<literal::Value>>` 改为 `std::vector<Tree::LiteralElement>`，`LiteralElement { std::optional<literal::Value> value; source::origin_id_t origin; }`。`clone()` 原样复制（元素条目按数据对象共享，位置也跟着走）。
- **填位置**（`src/compile/gct/builder.cpp`）：`writtenLiteralValue` 换成 `writtenElement`，数组元素与结构体字段都取 `node->origin()`；值仍只对数字字面量记录（嵌套复合、名字、算出来的元素没有自己的值，但有位置，嵌套复合的内部元素有各自的条目）。
- **在转换处使用**（`src/compile/gir/builder_control.cpp`、`builder.h`）：新增 `literalElementAt` / `writtenValueOf`；`literalElementInType` 的 `written` 参数从「精确值指针」改为 `const GCT::Tree::LiteralElement *`。`compositeEntersIn` / `compositeDataInType` 相应取 `element->value`。元素有位置时，`LiteralNotRepresentable` 报在**元素的 origin**；GCT 没留下元素（旧数据、名字等）时才退回整个字面量的位置。
- **引用源码写法**（`src/compile/gir/builder_diagnostics.cpp`）：`rejectLiteralData` 增加可选参数 `writtenAt`（元素 origin），为空时从 `sourceTextOf(written)` 回退到 `textAtOrigin(writtenAt)`，再回退到 `literalValueText(data)`。`textAtOrigin` 与 GCT 的 `sourceTextAt` 同规则（≤60 字节、单行）。
- **声明位置一并统一**（`src/compile/gct/builder.cpp`）：`literalNodeInType` 把元素的源码文本传给 `reportLiteralCastFailure`（新增可选参数 `written`），所以声明里的 `let xs: f32[] = [1e40, 2.0]` 也引用 `'1e40'`，与标量声明位置（H24 的 `declaredValue`）一致。位置、诊断名、原因文本都不变；既有用例没有依赖规范文本的期望（下方「改动的期望」）。

### 效果

| 位置 | 之前 | 现在 |
|---|---|---|
| `let xs: f32[] = [1e40, 2.0]` | `4:22`，`'1e+40'` | `4:22`，`'1e40'` |
| `pick([1e40, 2.0])`（`f32[]` 形参） | `6:18`（`[`），`'1e+40'` | `6:19`（元素），`'1e40'` |
| `sum32([1, 3000000000])`（`i32[]`） | `14:19`（`[`） | `14:23`（元素） |
| `px({ x: 1e40, y: 0.0 })` | `13:16`（`{`），无引用文本期望 | `13:21`（字段），`'1e40'` |

嵌套复合字面量沿用 H27b 的按数据对象取条目的做法：外层元素没有值、只有位置，内层元素在自己的条目里有位置与值，所以内层报错也落在内层元素上。

## 2. 部分应用的上下文实参

### 问题

`f<w>` 作值走 `Builder::partialApplicationOf`（`src/compile/gir/builder_calls.cpp`）。它选候选时只问 `entersImplicitly(withTypeAt(i), boundType)`，而实参位置的字面量按 5.1 是「有期望类型的位置」：`scale<2>`（`with <k: f32>`）与 `at<[7.0, 8.0]>`（`with <xs: f32[]>`）都被判为不能绑定，报 `PartialApplicationRefused`（`<int>` / `<float[]>` 不能绑定到 `<k: f32>` / `<xs: f32[]>`），而在调用处写 `at<[7.0, 8.0]>(1)` 是好的（H27b）。

### 改动

- **候选判断**（`fits`）：逐个上下文实参与普通形参一样判断 —— `assignableFrom` / `entersImplicitly` / 数字字面量的精确值 `literal::kindEnters` / `compositeLiteralEntersIn`。后两条用的正是 H27b 为普通实参建的规则；放不进类型的元素**仍算进入**，由转换报错（和调用处同一条口径，不退化成 `PartialApplicationRefused`）。
- **选定之后转换**：被调函数唯一确定后，对 `entersImplicitly` 不成立的（即靠字面量 / 复合字面量进入的）上下文实参调用 `coerceTo(arg.node, withTypeAt(i), arg.expr)`，再 `bindTemporary` 捕获。捕获的是**形参类型**的值，所以部分应用内部的 `f<w>(...)` 拿到的是已经转换好的值；复合字面量的转换走 `compositeLiteralInType`，越界元素在**元素位置**报 `LiteralNotRepresentable`（第 1 项的成果）。
- **名字仍不转换**：`scale<n>`（`n: int`）仍被拒（`PartialApplicationRefused`），与 5.1「变量永不转换」一致。

### 覆盖

`test/cases/consistency/partial_application/context_arguments.cml`（四后端一致）：`scale<2>` 得 `6.0`、`at<[7.0, 8.0]>(1)` 得 `8.0`、`offset<{ x: 1, y: 2 }>(0.5)` 得 `1.5`。负例：`err_context_argument_name.cml`（名字，`13:18`，`PartialApplicationRefused`）、`err_context_argument_out_of_range.cml`（`at<[1.0, 1e40]>`，`12:22`，`'1e40'`、`type 'f32'`，不是 `NoMatchingFunction`、不是整个字面量）。

## 3. 管道调用的额外实参

### 问题

`visitLinkExpr`（`src/parse/ast/builder.cpp`）对每个 `->` 都建一个 `Call`：被调者是右边的整个表达式，实参只有左边。于是 `1->add(2)` 降级成 `add(2)(1)`，报 `NoMatchingFunction`（`add: (a: int, b: int) => int`），而 4.4 说它是 `f(x, a, b)`。

### 旧 / 新降级

- 旧：`Call(callee = <右边表达式>, Data = [receiver], NamedData = [])`。右边本身就是 `add(2)` 这个调用时，外层调用变成「把 `add(2)` 的结果再用 `1` 调一次」。
- 新：右边是 `ReservedExprLoad(Call)` 时，把它**自己的** `Data` 列表前插 receiver，沿用它的被调者 `callee` 与 `NamedData`，直接以这个调用作为管道的值：

  ```text
  x->f(a, b)  ⇒  Call(callee = f, Data = [x, a, b], NamedData = <原样>)
  x->f()      ⇒  Call(callee = f, Data = [x])
  x->f<w>(a)  ⇒  Call(callee = f<w>, Data = [x, a])
  ```

  实参节点从右边的 `Data` 列表上摘下（`setParent(nullptr)`）再挂到合并后的列表；新列表的 token range 与 origin 取 `expr(i-1)..expr(i)`（本段 `receiver ?-> f(a)`），标点与语义部件保留（`Operator` 仍是箭头，`Receiver` / `Argument 0` 仍是 receiver，后面的实参依次编号）。右边不是调用（`x->f`、`x->f<w>`、`x->a.b`、lambda）时保持旧形状，行为不变。`?->` 的 receiver 标记（`NotNullThen`）照旧放在实参 0，GCT 扫实参找标记，所以 `safe_div(8, 2) ?-> add(1)` 也成立。

### 覆盖

`test/cases/compile/callform/pipeline_arguments.cml`（新计划 `test/plans/feat/compile/call_syntax.plan.toml`，四后端一致）：普通函数 `1->add(2)` → `3`；带 `with` 实参 `1->bump<10>(2)` → `13`；泛型 `1->pick(2)` → `2`（`pick(a: typeas T, b: T): T`）；无额外实参 `1->inc()` → `2`；链式 `1->add(2)->add(3)` → `6`；`?->` 带额外实参 `(safe_div(8, 2) ?-> add(1)) !! -1` → `5`。

链式时 receiver 进入**第一个**（最内层）调用：`a->f(1)->g(2)` 即 `g(f(a, 1), 2)`。4.4 只写了单段形式，这是本实现对多段的一致取法，见第 7 节。

## 6. 改动的期望与理由

只改了两条既有期望，都是本任务第 1 项要求的行为变化；没有为了让测试通过而改任何语义。

1. `literal_context.plan.toml` / `context.array_argument_out_of_range`：期望列 `19` → `23`。`sum32([1, 3000000000])` 的报错从整个字面量的 `[` 移到元素 `3000000000` 的起点（第 14 行第 23 列）；诊断名、引用的 `'3000000000'`、`type 'i32'`、范围文本都不变。
2. `literal_context.plan.toml` / `context.struct_argument_out_of_range`：期望列 `16` → `21`（`{` → 字段 `1e40` 的起点），并在 `expect_output_contains` 里加上 `'1e40'`。原用例只查 `type 'f32'` 与范围文本，没有锁定引用文本；加上它是为了把「引用源码写法」钉住（`1e40`，不是 `1e+40`）。

新增（不是修改）：`context.array_argument_element_text`、`partial_application.context_arguments`、`partial_application.err_context_argument_name`、`partial_application.err_context_argument_out_of_range`、`call_syntax.pipeline_arguments`，以及 5 个新 `.cml` 与 `ast_hashes.txt` 里对应的 5 行。

声明位置的 `context.array_element_out_of_range`（`8:25`、`'3000000000'`）未改，仍通过：声明位置的报错位置与 H24 相同，只是引用文本从规范文本变成了源码写法（该用例两种写法相同）。

## 7. 未决 / 语言问题

1. **链式管道的 receiver 落在哪个调用**：`x->g(1)(2)` 现在读作 `g(x, 1)(2)`（receiver 进入第一个 / 最内层调用），旧读法是 `(g(1)(2))(x)`。4.4 只规定了 `x->f(a, b)` 一段的形式；多段时「进入第一个调用」是本实现的取法，需要语言作者确认（另一种可能是进入最外层）。
2. **上下文实参的重载选择**：`fits` 现在接受「字面量按值进入」的候选。若同一个名字有 `with <k: f32>` 与 `with <k: int>` 两个候选，`scale<2>` 以前按 `int` 精确选中，现在两个都「进入」而变成 `PartialApplicationRefused`（有歧义）。普通调用位置的精确优先规则（H27b 的 `accepts(f, false)` 先跑一遍）是否也要用于 `f<w>` 的上下文实参，是一个独立问题，没有擅自决定。
3. **声明位置的引用文本**：本任务把复合字面量声明位置的引用文本统一成源码写法（`literalNodeInType` → `reportLiteralCastFailure(..., written)`），与标量声明位置（H24）一致。若希望声明位置继续引用规范文本、只让实参位置引用源码写法，需要另行规定；当前实现是「所有位置都引用源码写法」（5.1）。
4. **`?->` 的 `Receiver` 语义部件**：仍锚在 `?->` 运算符（旧行为），实参 0 的 origin 是 receiver 值。若下游工具（LSP / 语义高亮）希望 `Receiver` 指向值本身，可以再调整；本任务保持既有元数据不变，AST 快照因此没有既有文件的改动。
5. **命名实参过管道**：`x->f(a: 1)` 仍按既有规则报 `FeatureNotSupported`（kwargs 未支持），与本次改动无关。
6. **源码文本读取的小重复**：GCT 的 `sourceTextAt` 与 GIR 新增的 `textAtOrigin` 规则相同但各在一层（GCT 只有 AST 节点，GIR 只有 origin）。若以后再加第三处，可以抽到 `source` 工具里。
