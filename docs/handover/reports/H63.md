# H63 — 抽取的保留边界按作者裁定实现

分支 `handover/H63-extract-boundary`，起点 `origin/develop` `043ac0eb`（H61 合入提交）。任务只有
一处：`DraftWritings::extract` 的预选集合与作者裁定不符。本文记录复现、每种形状的判定、修改后
的判据，以及验证用的计划与数字。

依据是作者在 `docs/handover/reviews/H24-H25-H26.md` 末尾"H38b 开放问题（协调者裁定）"第 2 项，
以及之后对措辞的更正 `8ea4b403`（合入 `9e25f2c7`）：保留集合是**有副作用／承载顺序／被写入的
变量**；纯节点（包括带控制输入的纯节点）只按可达性保留。更正删除了协调者误加的括注"按依赖求值
只适用于纯计算"——**设计原则 3.1 不变**。抽取只决定保留什么，不决定"没人用的副作用调用执行不
执行"；后者仍由 3.1 的求值规则回答。本分支的 `docs/design/{rewrite,graph-store}` 仍停在更正的
父提交上，修订后的文字在 `origin/develop`；本分支没有改这两份文件，以免制造合并冲突。

## 1. 复现：饱和造出的死写法留在抽取结果里

`src/runtime/writings.cpp` 的 `extract` 原先用

```cpp
if (draft_.alive(node) && !multi[node] && !takesPart(node)) { select(node); }
```

预选。`takesPart` 只对 `shapeOf == 1` 成立，所以这条条件除了选中副作用节点、控制节点和被写入
的值（shape 2），还无条件选中**不参与同余的纯节点**：shape 3（带控制输入的纯节点）与
`shapeTakesPart` 不覆盖的种类。最直接能被饱和造出来的是后一类：规则右端写出的字符串常量是
GC 追踪类型的静态 `DATA`，`shapeOf` 返回 2，但它只是一个纯值。

用例 `test/cases/modules/rules/extract_boundary.cml`：

```camel
rule tag_y(a: string, b: string) { a + b => a + 'y' } when isY(b)
func tag(s: string): string { return s + 'y' }
```

`when` 用 `constant(n, '')` 与字符串比较，保证定律是等式。`check` 先 `saturate(p, [tag_y], 4)`
再 `extract(q, 'nodes')`，在两步之间打印 `tag` 图的节点数与"没人读的字符串常量"数。饱和每一轮
都在上一轮写出的新写法上再匹配一次，右端每次都写出一个新的 `'y'` 常量。

修复前的可执行文件（`043ac0eb` 的构建，未含本分支改动）：

```
tabled nodes 33 unread constants 0
extracted nodes 18 unread constants 15
```

`std::gir` 打出的 `tag` 图（抽取之后）里，真正的常量还带着源位置，其余 15 个没有任何边：

```
N01 [label="y", type="DATA", origin=1580, span="32:15-32:18", ...]
N02 [label=":op/add_s", type="OPER", origin=1581, ...]
N03 [label="y", type="DATA", value_type="string"]
...
N11 [label="y", type="DATA", value_type="string"]
F02 -> N00 ...; N02 -> O02 ...; N00 -> N02 ...; N01 -> N02 ...
```

也就是说：饱和新增 15 个候选写法（15 个 `:op/add_s` + 15 个常量），代价模型全部选了原写法，
15 个新 `add` 是 shape 1、被删；15 个新常量是 shape 2、被无条件留下。修复后同一条命令（同一
用例、同一二进制重新构建）：

```
tabled nodes 33 unread constants 0
extracted nodes 3 unread constants 0
```

图回到 `N00`（端口 `s`）、`N01`（`'y'`）、`N02`（`:op/add_s`）三个节点，程序输出 `ay by`。
回归项 `rules.extract_keeps_no_unreachable_pure_node` 锁定这三行输出。

H61 §3.2 把这处概括为"饱和新增的、带控制输入又没人读取的纯节点会留在抽取结果里"。按本轮的
观察，这个例子不准确：饱和的 `build` 从不给新节点控制输入，所以复现出来的死节点是右端写出的
GC 追踪常量，不是 shape 3。shape 3 的无条件保留是同一判据的潜在过度保留（前端对未使用的纯结果
有诊断，正常程序不会留下这样的节点），这次一并按裁定改掉，但**能观察到的缺陷是常量这一类**。

## 2. 每种形状的判定

`shapeOf` 的三个值来自 `shapeTakesPart`（`src/runtime/writings.cpp`）；`carriesOrdering` 是
`src/passes/opt/generic/rewrite.cpp` 里泛型重写"不得重排"的同一判据（函数/调用节点运行图，
分支/汇合/同步/循环承载顺序，有控制输入的 `GATE` 等待，非纯 `OPER` 有副作用）。

| `shapeOf` / 种类 | 是不是纯 | 裁定下必须保留吗 |
|---|---|---|
| shape 1：纯 `OPER`、`CAST`、`ACCS`、非 GC 追踪的静态 `DATA`，无控制输入、未被写入、不读被写变量 | 纯 | 否，只按可达性 |
| shape 3：同上，但有控制输入 | 纯（控制输入只给它排序） | 否，只按可达性；被保留下来的值或控制边读到它时才留 |
| shape 2 中的非纯 `OPER`（含只有状态、无外部副作用的算子） | 有副作用／改程序状态 | 是 |
| `FUNC`（直接调用另一张图） | 运行图（被调者可能有副作用），承载顺序 | 是 |
| `CALL`（经函数值间接调用） | 运行图，承载顺序 | 是 |
| `JOIN`、`BRCH`、`SYNC`、`LOOP` | 控制节点，承载顺序 | 是 |
| `GATE` 有控制输入 | 等待，承载顺序 | 是 |
| `GATE` 无控制输入 | 纯 | 否，只按可达性 |
| 被写入的值（`writtenInPlace`，经 `var` 参数或对象写入） | 被写入的变量 | 是 |
| GC 追踪类型的静态 `DATA`（`dataIndex < 0`，字符串、张量常量等） | 纯值 | 否，只按可达性——复现的死节点就是它 |
| 非静态 `DATA`（`dataIndex >= 0`）、`FILL`、`COPY`、`ACCS` 等其余纯种类 | 纯值 | 否，只按可达性 |

与 H61 §7 的一处更正：那里把 `FUNC` 与纯 `CALL` 列为"结构节点、被错误保留"。按更正后的裁定，
它们**运行另一张图**、承载顺序，保留是对的；真正的过度保留只在纯值上（shape 3 与上表最后两行）。

## 3. 现在的选择（`DraftWritings::extract`）

新增局部谓词 `carriesOrdering(draft, node)`（与泛型重写的同名判据一致，注释指明出处），预选改成：

```cpp
for (gc_node_ref_t node = 0; node < slots; ++node) {
    if (draft_.alive(node) && (writtenInPlace(node) || carriesOrdering(draft_, node))) {
        select(node);
    }
}
```

随后仍从图命名的东西出发做可达性：端口、入口、出口、返回值、所有区域结果，以及每个保留节点读到
的"该类选中的写法"（普通输入、`with` 输入与控制输入都算；控制输入保证排序不被删掉）。纯节点只有
被这条闭包读到才留下。两处细节：

- **不再有 `!multi` 条件**。被并进同一个类（`multi`）的副作用／控制节点也照样选中：抽取不因某个
  等价类整体不可达就把类里的副作用或分支裁掉。这比旧代码保守一点，是裁定"不由抽取裁剪"的直接
  结果。
- 注释改写为裁定原话，不再声称条件是"an effect, a control node, a written variable"——旧注释比
  实际选择窄，是 H61 记录这处缺陷的起因之一。

## 5. 与设计原则 3.1 的关系

更正的裁定把两件事分开：**抽取保留什么**（有副作用／承载顺序／被写入的变量，其余按可达性）与
**保留的副作用执行不执行**（3.1：同步块之外、结果没被使用的带副作用调用不执行）。本轮只改前者，
没有改求值语义。上一版裁定里"按依赖求值只适用于纯计算"的括注如果成立，会要求"凡是留下的副作用
都执行"，与 3.1 第一条冲突；作者已确认那是协调者的误写并删除。本轮因此没有留下两读之间的
悬案。会随读法不同的是**一个结果没人用的副作用节点**（同步块之外）：按 3.1 它被保留但不执行；
按误写的括注它必须执行。现在实现与 3.1 一致。

## 6. 遗留

- 若一个等价类整体不可达、类里又有副作用节点，抽取现在会保留那个节点，但它没有用户，调度仍不会
  执行它——这与 3.1 一致；如果将来要让"保留"意味着"执行"，那是 3.1 的改动，不是抽取的。
- shape 3 的过度保留已按同一判据修掉，但当前前端与饱和都不产生"带控制输入、又没人读"的纯节点，
  所以没有为它单独造用例；形状表里给了判定，复现覆盖的是 GC 追踪常量。
- 未改 `docs/design/{rewrite,graph-store}`（修订版在 `origin/develop`）；`docs/technical/44` §5、
  §7 与 `docs/handover/README.cn.md` 的 H61 行已按"缺陷已修"更新。
