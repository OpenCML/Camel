### 仍然失败的 `04_staticness`

`nontail-export` 期待诊断里出现 `04_staticness/program.cml:44:73)`（第 44 行的递归调用 `settle(t * 0.5)` 本身），现在出现的是 `44:79`（同一次调用的实参 `(t * 0.5)`）。最小复现（`tmp/rec.cml`）：

```cml
func f(x: float): float {
    return if x > 1.0 then f(x * 0.5) + x else x
}
```

`std::gir` 里 `f` 的 FUNC 节点（`origin=127`）span 是 `3:28-3:37`，即实参表 `(x * 0.5)`，不是整个调用表达式；`main` 里的非递归调用 `f(4.0)` 同样落在 `7:13-7:18`（实参表）。也就是说直接调用建出来的 FUNC 节点带的是实参表的 origin，导出器按“递归整体报在调用处”取 `nodeOrigin(site)`，于是列号落到实参上。

期望（`44:73`，调用处）是对的，所以没有改期望去迁就；要在建图器里让直接调用的 FUNC 节点使用整个调用表达式的 origin（`44:73-44:88`）。这属于 origin 记录，不是导出器的判断，留作缺陷。

## 2. 格式化器的崩溃

**原因**：`tools/format/fmt.cpp` 的 `NK::` 分派没有 `TypeArguments` / `NamedTypeArgument` 的规则，遇到 `f::<int>`、`f::<A = int>` 直接 throw。`camel-format` 单跑时表现为 `camel-format: no rule for TypeArguments`；`camel-parsecheck hashes` 不捕获异常，于是整个进程以 `0xC0000409` 退出（这正是基线里 546 个文件左右就死掉的原因）。

**修复**：

- `tools/format/fmt.h` / `fmt.cpp`：新增 `visitTypeArguments`（`::<` + 类型列表或具名实参列表 + 尾逗号 + `>`）与 `visitNamedTypeArgument`（`IDENT ' = ' type`），注册进 `NK::` 分派。
- 顺带把枚举的排版与声明风格统一：结构体变体与结构体模式在 `{` 前留空格（`Rect { w, h }`、`Rect { w: float, h: float }`），元组模式括号内不留空格（`Circle(r)`），尾逗号仍按列表规则。
- `tools/parsecheck/main.cpp`、`snapshot.cpp`：`dump` / `hashes` / `fmtcheck` 捕获异常，打印 `error <file>: <what>`，计为失败并继续处理其余文件，不再整进程崩溃。

**测试**：新增 `test/cases/format/match_and_type_arguments.cml`（`match` 的臂分别是字面量与枚举模式；带位置与具名两种显式类型实参）与对应 golden、计划项 `format.match_and_type_arguments_snapshot`。`node scripts/test.js test/plans/feat/format`：9/9 通过。

## 3. 内部算子按编号引用

**没有做**，停下来记问题：按现在的分层，“按编号引用”缺少一个设计决定。

现状：内部算子在 `OperatorGroup::create("__enum_make__", {{":enum/make", resolver}})` 登记的是**实体名**（`__enum_make__`，模块的导出名）与**算子 URI**（`:enum/make`，`OperId` 按 URI 驻留）两套名字。建图器引用它们有两条路：

- `applyTagOperator` / `applyInternalOperator`：造一个带 `DREF("__enum_make__")` 的合成 GCT，交给 `visitLinkNode`，顺带得到捕获、重载决议、权限戳与 origin。改成按 `OperId` 直接建 `OPER` 节点会绕过这些，行为不是“不变”而是“少做”。
- `variableOperator("__var_new__")`：`module_->getImportedEntity(name)` 按导入层查实体，`Module` 的实体表按 `Reference`（名字）建，没有按 `OperId` 的入口。

缺的是：`OperId` 标识一个 URI，而建图需要的是**算子组**（一个组可以带多个重载，`OperGroup::resolve` 用它做决议）。`OperatorTable` 的条目只保存 URI、traits、resolver、语义，不保存组；模块的实体表也不认 `OperId`。所以“登记时取得 `OperId` 保存”只能得到编号，**没有从编号回到组的路径**。

可以做的选择（需要设计判断）：

1. 在 `OperatorTable` 的条目里加一个 `oper_group_ptr_t`/回调（登记时由模块给出），建图器用 `OperId` 查组再 `resolve`；内部算子的 `OperId` 在 `enum.cpp` 等处 `intern(":enum/make")` 时保存为常量。
2. 或者把内部算子做成 `oper::` 命名空间里的编译期常量（像 `oper::VarNew`），并只把**比较**（`heap->oper == oper::VarGet`）改成编号，建图仍走名字；这只能覆盖“判断”，覆盖不了“引用”。
3. 或者给 `Module` 加“按 `OperId` 取实体/组”的入口，由 `exportEntity` 时顺便登记。

倾向 1（组跟着条目走，`OperId` 是唯一键），但这会动 `OperatorTable` 的公开结构与所有 `declare*` 调用方，属于设计决定，没有自行选。

## 待决问题

1. **默认数值许可与 `@numeric` 并存期间的口径**（H2）。2.22 把 `reassociate`/`contract` 定为默认允许，但 `@numeric(...)` 装饰器与 `jgir` 的 `numeric` 字段还在。本报告按 2.22 改了 3 处数值断言（`graph.default`、`integrated.graph.false/true`）和 1 处事实计数（`rewrite_opt`）。H2 用标签重写这一块时，这些用例应连同 `@numeric` 的退役一起重写。
2. **导出拒绝的诊断优先级**（语言作者/ONNX 设计）。请求位于运行时分支的臂内时，有两个可说的理由：分支决定是否执行请求，或目标函数根本不能导出。现在的顺序是“目标的拒绝优先，其次才是分支”（`nontail` 的递归拒绝因此保留）。若认为分支应当优先，改 `readEntryRequest` 的判断顺序即可。
3. **`04_staticness` 的列号**（建图器 origin）。直接调用的 FUNC 节点应带整个调用表达式的 span；现在带实参表的 span。修它会让 `04_staticness` 恢复，并让所有“报在调用处”的诊断更准。
4. **内部算子如何按编号引用**（第 3 节）。`OperId` 只标识 URI，建图需要算子组；需要一个 `OperId → 算子组` 的登记（`OperatorTable` 条目带组，或 `Module` 按 `OperId` 查实体）。三种做法见第 3 节，倾向第一种。
