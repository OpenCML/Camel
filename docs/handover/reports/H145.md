# H145 — 声明化的模块在 `::` 后重新列出成员

分支 `handover/H145-lsp-declaration-exports`，起点 `origin/develop` `e5544f744`（H138 之后）。
H19 的声明化把 11 个模块的签名搬进 `stdlib/<m>.cml`（`bytes`、`str`、`math`、`json`、`io`、
`re`、`random`、`fs`、`time`、`algo`、`statistics`），C++ 侧只留计算签名。语言服务器是这些
模块的消费者：`math::` 之后补全为空，hover、签名帮助与查找引用在“正在输入、还不编译”的文本上
也一起失效。本批只改消费者侧，编译器与声明机制一行未动。

## 1. 现象与复现

在主机上用计划跑 `lsp.editing`（95 条检查）：

```
FAILED: the exports of a module after `::`
    []
FAILED: with their signatures
2 of 95 checks failed
```

同一棵树上另写一个临时探针（不入库），文本是**能编译**的 `import math` + `math::sqrt(4.0)`：
hover 与签名帮助都能出结果，但 hover 的模块行写的是 “Function of the built-in module”。把文本
改成**不能编译**（末尾留一个没写完的 `let bad =`）后：hover `null`、签名帮助 `null`、
`textDocument/references` 返回 `[]`。

H112 §6 第 3 条曾把同样的空补全怀疑成“LSP 与 didChange 的时序 flake”；在 `e5544f744` 上单独
重跑、串行重跑都稳定复现，不是时序。

## 2. 洞在哪

**`src/service/semantic/analyze.cpp:991`（基点 `e5544f744`）。**

`catalog()` 先把“按命名空间导入的模块”收进 `spaces`（`module.importedNamespaces()`，以及文本
不解析时从语法树回退的 `context->importModule(...)`，`analyze.cpp:970-989`），然后在
`analyze.cpp:990-993` 把它们筛掉：

```cpp
for (const auto &[prefix, mod] : spaces) {
    if (!mod || !mod->loaded()) {     // <-- 洞
        continue;
    }
```

成员本身在 `analyze.cpp:1015-1043` 枚举，来源是
`context->programExports().forEachExportedEntity(*mod, ...)`（`analyze.cpp:1018`）与
`mod->nativeEntityNS()`（`analyze.cpp:1020`）。这两处都不缺东西；缺的是**走到它们之前**。

`mod` 是 `Context::loadModuleFrom` 为“`.cmo` 旁有同名 `.cml`”返回的**声明模块**
（`src/core/context/context.cpp:741-767`）：它先 `mod->load()` 加载 C++ 实现，再用
`UserDefinedModule::fromFile` 编译声明文件、`setDeclarationModule(true)`、
`setImplementation(mod)`，最后 `inheritExportsFrom(*mod)`（`:756-766`）。它是一个
`UserDefinedModule`，而 `loaded()` 只有在 `load()` 成功（`include/camel/core/module/userdef.h:161-165`）
或程序图建好（`src/core/module/userdef.cpp:246-263` 的 `setProgramGraph`）之后才为真。
非入口模块的 `compile(Done)` 到 `Declared` 就返回（`userdef.cpp:190-194`）：一个只被
`import`、还没被程序用到的模块停在 `Declared`，`loaded()` 是假。

补全发生的时刻恰好是这个状态：

- 文本不解析：`main` 根本没有编译，`importModule` 只把模块建出来（stage `None`）；
- 文本解析但不编译：模块最多到 `Declared`，`main` 的程序没建完；
- 只有整个程序建完，所有被导入的模块才随 `setProgramGraph` 一起 `Done`。

于是迁移前不是问题——`math` 是 C++ 的 `BuiltinModule`，`importModule` 会当场 `load()`，`loaded()`
为真，`exportEntity` 注册的 `sqrt` 等直接可见；迁移后 `math` 变成声明模块，同一个
`importModule` 故意不再 `load()`（`context.cpp:427-430` 把“Camel 写的模块由导入方在 GCT 里声明”
写进了注释），`loaded()` 一直是假，整个命名空间被跳过。**不是“C++ 不再导出”本身让列表空掉，而是
LSP 用 `loaded()` 当作“声明可读”的条件；声明其实在 `Declared` 阶段就已经可读。**

被跳过的模块里，声明名和计算签名其实都已经在同一个对象上：

- `inheritExportsFrom`（`src/core/module/module.cpp:353-365`）把 C++ 模块的实体（`math` 的
  `sqrt`、`shl`、`shr`，`json` 的 `encode`、`decode_as`，以及 `pi`/`e`/… 这些值）复制进声明模块；
- 声明文件编译到 `Declared` 时，`Builder::declareModule` → `exportNativeOperators`
  （`src/compile/gir/builder_modules.cpp:488-541`）把每条无体 `export func` 变成
  `DeclaredFuncTypeResolver` 组，同名组用 `replaceEntity`、新名用 `exportEntity` 写进同一张
  `nativeEntityNS`；
- `ProgramExports::forEachExportedEntity`（`module.cpp:454-469`）本来就是“程序实体 + 原生实体”
  的并集。

所以“声明 ∪ C++ 计算签名”的并集在**加载器给的对象上已经存在**，LSP 只是没有请它先声明。

## 3. 修法

**`src/service/semantic/analyze.cpp:990-1013`**：不再要求 `loaded()`；模块未加载时调用
`mod->declareEntities()`，再用原来的枚举路径。每个模块单独 `try/catch`，一个坏掉的声明模块不会
带走其它命名空间。

`declareEntities()` 不是新造的接口：`ProgramExports::importedEntity` 在解析任何导入名之前就是
这样做的（`src/core/module/module.cpp:483-490`：`binding.mod->declareEntities()`）；
`camel inspect --ops` 也是先对所有未加载模块 `module->load()` 再 dump
（`tools/camel-cli/main.cpp:436-441`）。LSP 是唯一一个用 `loaded()` 把这条既有路径挡在外面的消费者。

这样得到的是**一个模块对象的并集**，不是第二份签名，也没有 LSP 自己的 `.cml` 解析器：

- 声明名：来自 `stdlib/<m>.cml` 的编译（`DeclaredFuncTypeResolver`）；
- 计算签名：仍是 C++ `exportEntity`/`DynamicFuncTypeResolver` 注册的实体，经
  `inheritExportsFrom` 继承；
- 值与类型：同样继承。

另有一处同名的小洞：`src/service/semantic/queries.cpp:398-435` 的 `targetAt` 在
`facts.isOperator` 时提前返回，`math::sqrt` 的 `external` 永远是 `nullptr`，于是 hover 把模块
成员说成 “the built-in module”（迁移前也如此，与 H19 无关）。修复把“按路径前缀查命名空间成员”
提到这个提前返回之前，运算符调用仍用编译器解析出的 `operatorSignatures`，但模块名现在是
`math`。四个查询（补全、hover、签名帮助、查找引用）都读同一张 `namespaces_`，这一处修好后
它们同时恢复。

## 4. 两种形态

迁移后的模块正好两种：

| 形态 | 模块 | 测试 |
|---|---|---|
| 声明 + 计算签名并存 | `math`（`sqrt`/`shl`/`shr` 在 C++，`abs` 等 6 个重载在 `math.cml`）、`json`（`encode`/`decode_as` 在 C++，`decode` 等在声明里）、`random`（`choice`/`sample`/`shuffle` 在 C++）、`algo`（7 个排序族在 C++，`argsort` 6 条在声明里） | `math::` |
| 只有声明 | `bytes`、`str`、`io`、`re`、`fs`、`time`、`statistics` | `re::` |

`test/cases/tools/lsp/editing.test.mjs` 在原有的补全块上扩展（保留原来的两条断言）：

- `math::`：`sqrt` 仍在，`detail` 逐字等于 `(val: float | double) => float | double`（C++ 算的）；
  `abs` 也在，`detail` 以 `(x: i32) => i32` 开头并带 `(+5 overloads)`（声明里的 6 条）；
- `re::`：成员恰好是 `['test']`，`detail` 是 `(pattern: string, text: string) => bool`；
- hover：`math::sqrt` 给出签名并写 `Function of module \`math\``；`re::test` 给出声明签名；
- 签名帮助：`math::sqrt(` 得到 `sqrt: (val: float | double) => float | double` 且第 0 个参数
  活跃；`math::abs(` 得到 `abs: (x: i32) => i32`。

检查数从 95 条增到 **105 条**，10 条新增全部覆盖上面两种形态与四个查询中的三个（补全、hover、
签名帮助）。`re` 是声明模块里最小的一个（H126），`math` 是“两种形态并存”里最小的一个。

## 5. 其它消费者与“为错误的原因工作”

| 消费者 | 迁移后是否坏 | 结论 |
|---|---|---|
| 补全（`::` 之后） | **坏** | 本批修复的主症状；`namespaces_` 空。 |
| hover | **在“正在输入”的文本上坏**；在能编译的文本上“为错误的原因工作” | 能编译时签名来自 `CallResolved`/`OperatorReferenced` 记录的 `operatorSignatures`，不读模块导出，所以 `sqrt` 的签名仍出现；但 `external` 为空，模块行写成 “the built-in module”。修复后两条路都读 `namespaces_`，模块名正确。 |
| 签名帮助 | **在“正在输入”的文本上坏**；能编译时正常 | 只走 `namespaces_`（`queries.cpp:1437-1448`）；能编译意味着该模块已随程序图 `Done`，所以没暴露。修复后在两种文本上都可用。 |
| 查找引用 / 高亮 | **在“正在输入”的文本上坏**（返回 `[]`） | 同样走 `namespaces_`（`occurrences`，`queries.cpp:480-543`）；修复后恢复。 |
| `camel inspect --ops` | 没坏 | 它先对未加载模块 `load()` 再 `dumpOperators`（`tools/camel-cli/main.cpp:436-441`），`describeOperators` 读 `nativeEntityNS`（`src/core/module/introspect.cpp:147-193`），声明与计算签名都在。`--verify-ops` 用的就是它。 |
| `scripts/stdlib-reference.mjs`（参考页、`--verify-doc`、`--verify-ops` 的声明侧） | 没坏 | 读 `.cml` 文本，不经 `exportEntity`；H137 的 `scripts/stdlib-declarations.mjs --check` 同样读文本。 |
| `camel inspect --tags` / 标签转储 | 没坏 | 读 `declaredTags_`，不是实体表。 |
| `benchmarks/compile/bench.py check` | **基线红，与本批无关** | `chain-3` 期望 4 个 user module、实际 6 个：按需的 `rules` 库与声明模块被计入 user module。H112 §5 第 5 条已记录并归工具维护者；本批没有改 `--time-phases` 或模块计数，semantic 层只被 `camel-ls` 调用（`tools/lang-server/*.cpp`），`camel --time-phases` 不经过它。 |
