## 1. 已落地

### 1.1 数组表示（计划 2.1–2.3）

- `Array` 不再假设“一个元素一个 8 字节 slot”。新增存储类别：

  ```cpp
  enum class Storage : uint8_t { Slots, Compact };
  ```

  - `Compact`：元素是数值（`Int32/Int64/Float32/Float64/Bool/Byte`），按元素宽度连续存放；
  - `Slots`：其余元素类型（引用、字符串、元组、嵌套数组、JSON、Python 对象……），保持原来的
    `slot_t` 布局。
- 元素类型在**创建时**确定：`Array::create(allocator, const ArrayType *, extents, zeroInit)` 按
  `type::arrayStorageFor(elemType)` 一次性选存储；`Array::create(allocator, n)` 仍是 slots（没有类型
  时无法知道元素宽度）。
- 小数值数组**内联**在 `Array` 对象里：`numel * elementSize <= 256`（`kInlineArrayBytes`）时不分配
  缓冲区，`dataPtr_` 指向对象尾部。导出 DLPack 或取视图（需要稳定地址/可增长）时一次性提升为
  `Buffer`，此后再不内联。
- 多维：对象尾部依次是 `extents_`（rank × 8）、`strides_`（rank × 8）和内联数据；`Array::view`
  共享缓冲区并带元素偏移；`size_`/`numel_`/`capacity_`/`offset_` 改为 64 位。
- `getSlot`/`setSlot` 对紧凑数组按元素类型读写（`Int32`/`Float32` 读时零扩展，`Bool` 规范化为
  0/1），`data()` 只允许 slots 或 8 字节元素，其余用 `dataAs<T>()`；`get<T>/set<T>` 按 T 的宽度。
- 所有创建点迁移到有类型的工厂：`src/builtin/operators/{higher_order,struct,ops}.cpp`、三套调度器
  （nodevm/fastvm/taskflow）的 map/filter/reduce、`loop_driver.h` 的 collection tape、`modules/random`、
  `modules/algo`、`modules/bytes`、`modules/tensor`（含 `createTensor`/`viewTensor`）、`modules/tiles`、
  `modules/onnx`、`json`/`python` 互操作、`graph_encode`、`draft_session` 等。
- 读取可能紧凑的数组改为 `getSlot(i)`（调度器、`loop_driver`、`tensor/interop`、json、python）。
  这一批修掉了两个真实的越界读：`coll/fromArray`（`[3,1] as Set<i32>` 把 1 读成 40）和
  `algo` 的原地排序（i32/f32 数组按 8 字节 slot 排序会写坏缓冲区）。

### 1.2 缓冲区与 GC（计划 2.4–2.6）

- `camel::core::array::Buffer`（`include/camel/core/array/buffer.h` + `src/core/array/buffer.cpp`）：
  原子引用计数、外部内存 + release 回调、DLPack 兼容字段；Camel 拥有的数据从
  `mm::bufferSpace()`（`CAMEL_BUFFER_LIMIT_MB`，默认 256 MB，不移动）分配，数据地址 64 字节对齐；
  统计 `bufferBytesLive/Peak`、`bufferLiveCount/Creations`。
- 数组的 finalizer 只把 `Buffer::release()` 投递到**延迟释放队列**
  （`camel/core/mm/deferred.h`，`src/core/mm/deferred.cpp`）；队列在分配器解锁后的安全点执行，
  因为 finalizer 持有分配器锁而释放缓冲区要拿 buffer space 的锁。`foreign.cpp` 原有的同类队列
  也迁到这一处。
- live buffer 字节参与 GC 记账：
  - `bufferBytesGrowthUnlocked()`（自上次收集以来新增的字节）计入 young 触发预算、large/elder
    预算与 major 触发；
  - `oldBytesHeldUnlocked()` 计入 `bufferBytesLive()`，因此 `CAMEL_GC_HEAP_LIMIT_MB` 覆盖缓冲区；
  - `Buffer::create/grow` 在真正取内存前调用 `autoSpace().checkBufferBytes(bytes)`，让缓冲区分配
    也能触发 major 收集/在超限时抛出 `MemoryExhausted`（`gen.h` 新增 `checkBufferBytes`）。
  - 收集后把 `bufferBytesAtCollection_` 重置为当前 live 字节。
- `mm::profiler` 的 JSON/文本报告新增 `buffers` 块/行。

### 1.3 DLPack（计划 3.3）

- 新的核心头/实现 `include/camel/core/array/dlpack.h`、`src/core/array/dlpack.cpp`：
  `toDLPack(Array *)` 零拷贝导出（retain 缓冲区，managed tensor 的 deleter 释放），
  `fromDLPack(const DLManagedTensor *, IAllocator &)` 零拷贝导入（`Buffer::adoptExternal` +
  `Array::wrap`，最后一个数组消失时调用生产者的 deleter）。
- 只接受 CPU、连续、`lanes == 1`、行主序；支持 `f32/f64/i32/i64/bool/byte`。
- 外部缓冲区 `camelOwned() == false`，`Array::canWriteInPlace()` 为假：导入的 DLPack 数据**永不**
  原地写（批复的判据 3）。
- `modules/tensor/dlpack.h` 改为包含核心头并把名字引入 `camel::tensor`；
  `tensorToDLPackCopy`/`tensorFromDLPackCopy` 保留旧名、改为委托核心零拷贝实现（当前没有其它
  调用者）。
- `Array::wrap` 是新增的公开构造：在既有缓冲区上建数组（外部内存/共享视图），retain 缓冲区。

### 1.4 原地更新（计划 2.12，部分）

- `Array::canWriteInPlace()`：紧凑、内联，或缓冲区唯一 + Camel 所有 + `offset_ == 0` + 非视图。
- `OperatorTable::reusesOperand` / `declareReusesOperand`：算子在注册处声明“可能返回其操作数”，
  `algo` 的 `*_in_place` 已声明；这是批复要求“接口留在 `reusesOperand`”的那一处事实。临时值的
  使用者计数（`relu(exp(x))`）仍未做。
- `algo` 原地排序在 `inPlace && canWriteInPlace()` 时才写原数组，否则复制；排序算法改为按元素
  宽度（`T *`）而不是 `slot_t *`，修掉 i32/f32 的排序破坏。
- `append` 的原地路径（`buf` 唯一时 `grow`）与 `assn_append` 的已有机制沿用；逐元素算子与循环
  状态的原地写**未接入**（见第 4 节）。

## 2. 表示选择与理由

| 选择 | 理由 |
| --- | --- |
| 数值用紧凑存储、其余用 slots | 紧凑缓冲区只能放数值（红线：无引用 ⇒ 无环），这是 DLPack 零拷贝与原地写安全的前提；非数值仍用 8 字节 slot，不需要为它们做元素宽度。 |
| 小数组 ≤256 字节内联 | 小逻辑程序（循环状态、`range(3)`、shape 数组）不因“所有数组都要 Buffer”而多一次分配/释放；256 字节覆盖常见 shape/小向量，又不会让 `Array` 对象过大。 |
| 提升时机只在导出/视图/增长 | 内联数组的地址在对象内，一旦把 `data()` 交出去（DLPack、视图、内核）就必须稳定；只在入口处提升一次，避免每次读写都判分支。 |
| 形状/步长放对象尾部 | rank 通常 0–4，避免为 extents/strides 再分配；视图共享缓冲区。 |
| live buffer 字节计入**硬上限**，新增字节计入**触发预算** | 只计触发会让“只分配大缓冲区”的程序绕过 `CAMEL_GC_HEAP_LIMIT_MB`（OOM 测试会从 16 MB 处失败变成不失败）；只计硬上限又会让缓冲区增长不触发收集。两个都记，语义与 GC 其它空间一致。 |
| 延迟释放队列 | finalizer 在分配器锁内运行，`bufferSpace().free` 需要另一把锁；直接释放会死锁。队列泄漏单例，避免静态析构顺序问题。 |
| DLPack 零拷贝 + 外部 Buffer | 红线要求“交出去的数据指针在最后一次释放前有效”；外部 Buffer 的 release 回调正好表达生产者的 deleter。导入数据标为 external，原地判据自动拒绝。 |
| 原地写要求 `unique && camelOwned && !view` | 引用计数只数“几个数组值持有缓冲区”，数不到“两个 slot 指向同一个数组值”；因此仍保留今天的 `holdsUnsharedArray`/`:var/take` 作为判据 1，运行期再查 2、3。 |

## 6. 过程记录与已知限制

- 误跑 `feat/modules/autodiff.plan.toml`（含 PyTorch 对比，任务书要求不要运行），已停止，未据其
  结果改任何代码或期望；失败根因是 H21 的 `value_and_grad` 语义变化。
- DLPack 导入把生产者内存经 `Buffer::adoptExternal` 计入 live buffer 字节；如果生产者本身就是
  Camel 数组（导出的 managed tensor 再导入），同一块内存会被计两次。这是有意的保守记账（宁可
  多触发收集），但会让 `bufferBytesLive` 在 round-trip 后高于实际；若要求精确，需要在 managed
  tensor 的 `manager_ctx` 里带回原 `Buffer` 并识别，计划里没有这一步。
- 非 `autoSpace` 的分配器上 `fromDLPack` 走复制路径（该堆不运行数组 finalizer，共享会泄漏生产者
  的引用）；这与旧 `tensorFromDLPackCopy` 的行为一致。
- 内联数组在提升后，之前通过 `dataAs` 拿到的指针失效；目前只在导出/视图/增长入口提升，代码路径
  已按此约束写，但这是一个容易被以后的新调用点破坏的隐式前提，值得在类型层落地时用“稳定地址”
  类型或注释固定下来。
- `Buffer::create` 现在会对 buffer 字节做 GC 上限检查；`CAMEL_BUFFER_LIMIT_MB`（buffer space 自身
  的上限）仍然独立存在，两者语义不同：前者是“程序存活值”的上限，后者是“缓冲区空间”的硬上限。

## 7. 开放问题（留给语言作者）

1. **缓冲区字节是否应计入 `CAMEL_GC_HEAP_LIMIT_MB` 的硬上限，还是只参与触发节奏？** 我按“是”
   实现（否则纯张量程序可以绕过上限，OOM 用例也不再在 16 MB 处失败）。若语言作者认为上限只应
   约束 GC 堆对象、缓冲区由 `CAMEL_BUFFER_LIMIT_MB` 单独约束，需要改回并把 OOM 诊断改为在
   buffer space 处报。
2. **DLPack round-trip 的重复记账**：是否接受“同一块内存在 live 统计里出现两次”的保守近似，还是
   要求精确（需要在 managed tensor 里保留原 Buffer 身份）？
3. **`std::mem::buffers()` 的形态**：批复写的是“调试内建”，但没有说它是 pass 还是 `.cml` 可调用
   函数。我按 pass（`std::gc::buffers`）做了自检；若要求函数形态，需要定它的返回类型（字符串？
   结构体？）和是否在 release 构建可用。
4. **临时值原地更新**：批复把“使用者计数”留给协调者一方的图存储重构，H17 只在
   `OperatorTable::reusesOperand` 留接口。是否需要在 H17 内先接一个保守版本（只在单使用者、
   且使用者是 `:op/assn_owned` 时），还是等图存储重构后统一接？
