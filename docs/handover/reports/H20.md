### 1. 替换协议（`modules/tree/src/checkpoint_io.cpp`）

目的地 `D`、临时目录 `T = D.pending-<pid>-<序号>`、旧检查点 `P = D.previous`，三者同父目录：

1. **恢复**：`P` 存在而 `D` 不存在（上次在两次改名之间死亡）→ 把 `P` 改回 `D`；`D`、`P` 都在 → `P` 是发布后没删掉的过期备份，删除它。`D` 是符号链接、junction 或其他重解析点时，在动任何东西之前拒绝：改名只移动该条目本身，而清理不能跟随链接。
2. **写**：`snapshot()` 先把整棵树复制成原生字节（序列化或资源错误到不了文件系统），再在 `T` 中逐文件 `CREATE_NEW`/`O_EXCL` 写入并 `FlushFileBuffers`/`fsync`。
3. **交换**：`D` 存在时先 `D → P`，再 `T → D`；两次都是单卷上的单条目改名。Windows 的 `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` 只对文件有效、不能原地替换目录，POSIX 的 `rename()` 也拒绝非空目标目录，所以交换必然是两次改名，`P` 让这段窗口可恢复。
4. **清理**：成功后删除 `P`；删不掉不算保存失败（新检查点已经发布，`load_tree` 在 `D` 存在时忽略 `P`，下次保存的恢复步骤会删它）。

`D` 本体从不被写入，读方只可能看到旧的完整检查点或新的完整检查点。失败时：交换之前出错 → 什么都没动，只删本次创建的 `T`；`T → D` 失败 → 把 `P` 改回 `D`（回滚也失败时，错误信息给出 `P` 的路径，旧检查点仍是完整的，`load_tree` 能读）；`D → P` 本身失败 → `D` 未动。崩溃窗口：第一次改名之前（旧检查点完好）、两次改名之间（`D` 缺失、`P` 完整：下次保存先恢复，`load_tree` 读 `P` 并在标准错误上警告）、第二次改名之后（`D` 新、`P` 过期）。被杀死留下的未用 `.pending-*` 从不被读取。

边界情况：

| 情况 | 行为 |
|---|---|
| 目标不存在（父目录也不存在） | 建父目录，直接发布 `T → D` |
| 目标已存在（目录、文件、空目录、满目录） | 整体替换，旧目录/文件先成为 `P` |
| 目标存在 + `P` 也存在（上次清理失败） | 先删过期的 `P`，再替换 |
| 目标缺失 + `P` 存在（改名之间死亡） | 先把 `P` 改回 `D`，再替换 |
| 目标是符号链接 / junction / 重解析点 | 拒绝（`FileSystemError`），不动任何条目 |
| 临时目录建不出（权限、父目录只读） | 失败；旧检查点逐字节不变；不留下任何本次创建的条目 |
| `T → D` 改名失败 | `P` 改回 `D`；回滚失败则报出 `P` 的路径 |
| 目标路径为空、根、含 `\0` | 拒绝（`invalid checkpoint directory`） |
| 跨卷 | 三者同父目录，正常不可能跨卷；只有目标本身是挂载点/指向另一卷的重解析点时才可能，前者按重解析点拒绝，若 OS 仍报 `EXDEV`/`ERROR_NOT_SAME_DEVICE` 则明确失败，**不复制**（复制会破坏“要么旧、要么新”） |

Windows 规则：`D → P`、`P → D` 用 `MoveFileExW(..., MOVEFILE_WRITE_THROUGH)`（目标必须不存在）；`T → D` 用**不带** `MOVEFILE_REPLACE_EXISTING` 的 `MoveFileExW`，目标若被并发创建就失败而不是静默覆盖；Windows 没有目录 `fsync`，内容持久性由每文件的 `FlushFileBuffers` 加写穿透改名保证。Linux 发布用 `renameat2(RENAME_NOREPLACE)`，aside/restore 用 `rename(2)`，每次交换后 `fsync` 父目录；没有 `SYS_renameat2` 的平台明确失败（不回退到可能覆盖目标的普通改名）。

`load_tree` 改为先经 `checkpointReadDirectory()` 选目录：`D` 存在就直读，缺失而 `P` 存在就读 `P` 并在标准错误打印
`warning: tree.load_tree: '<D>' is missing; reading the previous checkpoint an interrupted save_tree left at '<P>'`。
它仍然只读文件系统（`Read` + 标准错误 `Write`，资源声明不变），不修改目录。

### 2. `fs::remove` / `fs::remove_dir`（`modules/fs/operators.cpp`、`module.cpp`）

签名：`remove(path: string) => void!`、`remove_dir(path: string) => void!`（`TupleType::fallible(Type::Void())`），纯度 `false`，资源 `externalAmbient("fs", AccessMode::ReadModifyWrite)`，与 `mkdir`/`mkdirs` 一致。

| kind | 何时 |
|---|---|
| `NotFound` | 路径不存在（`ENOENT`、`ERROR_FILE_NOT_FOUND`、`ERROR_PATH_NOT_FOUND`）：报错而不是静默成功 |
| `PermissionDenied` | 文件系统拒绝（`EACCES`、`EPERM`、只读文件系统、`ERROR_ACCESS_DENIED`、共享冲突） |
| `IOError` | 其余：`remove` 拿到目录、`remove_dir` 拿到文件、目录非空，以及其他错误 |

`Error.location` 与其它 C++ 算子一致是算子名 `<fs::remove>` / `<fs::remove_dir>`（调用点由内核不知道）；消息形如 `'<路径>': is a directory; use fs.remove_dir`、`'<路径>': is a directory that is not empty; remove its contents first`、`'<路径>': no such file or directory`，路径用 UTF-8。

`remove` 删文件或符号链接/junction 条目本身（不跟随）；真实目录即使为空也拒绝并指向 `remove_dir`。`remove_dir` 只接受真实目录，非空明确失败、**不递归**（递归删除既不是原子的，又会跟随重解析点），符号链接/junction 拒绝（`use fs.remove`），文件报 `is not a directory`。按设计原则 3.9，缺失路径不是“已经达成”，而是带 kind 的错误值；`match`/`??`/`!!` 拆开。

## H20-2 张量的取行与标签

判据来自 `docs/design-principles.cn.md` 3.9（故障）、5.1（不隐式转数值）、5.4（下标与切片、`take`、负数下标是故障）、9.9（自动微分）、10.5（引用计数为 1 时才就地）、11.5（打印）、以及 `docs/handover/reviews/H13-H14.md` 对 `take`/`one_hot`/按目标类型重载的答复。H21 的下标语法尚未落地，所以这一轮只提供函数形式 `take(t, indices)`，不新增 `t[idx]` 语法。

### 1. `take`

**做什么.** `tensor::take(t, indices)` 沿第一维按 `indices` 取行：结果是 `[len(indices)] + shape(t)[1:]`，元素类型与 `t` 相同。`indices` 是 `int[]` 或一维整数张量（`int64` 或 `int32`）。重复下标保留并保持给定顺序；`indices = []` 是空的、尾部维度正确的结果（未标注的空字面量也接受）；标量张量没有第一维，`take` 拒绝（`TensorDimensionMismatch`）。

**表示选择：拷贝，不是视图.** 任意行序不是缓冲区的仿射视图，若声称是视图，后续 10.5 的就地规则就不再成立（同一缓冲区可能被两个“视图”以不同行序引用）。`slice` 仍然是产生视图的算子；`take` 返回一份拷贝，测试与报告都按这个事实写。

**越界与负下标：** 能静态知道的在编译期报，运行期知道的在调用处报故障（3.9，不做 Python 式回绕）：

| 情形 | 结果 |
|---|---|
| 常量下标、第一维静态已知 | `SemanticDiag::ArgumentsRejected`，消息含下标与长度（推断抛 `ShapeError`） |
| 运行期下标越界/为负 | 定位到 `take` 调用处的 `RuntimeDiag::IndexOutOfRange`：`Index -1 is out of range for the first dimension of the input tensor of length 4.` |

**反向.** 反向是内部算子 `tensor:take_grad(t, indices, dy)`（不导出、不参与重载解析）：按 `t` 的形状新建零张量，把结果的每一行**加**回 `indices[i]` 行。重复下标因此累加（对第 0 行取两次，反向在第 0 行的梯度是 2），这正是 gather 的转置。dtype 跟随 `t`（float/int/bool；bool 用逻辑或累加）。`take` 的 VJP 只引用这个内部算子。

**ONNX.** `tensor:take` 降为 `Gather(axis = 0)`。下标操作数：常量 `int[]` 直接变成 i64 initializer（数组没有自己的操作数名），张量下标走 i64 输入/initializer。常量下标在导出时对静态已知的第一维做检查，越界是 `ExportError`，不产生任何节点。`nn:embedding` 原本就是同样的 `Gather` 映射，现在两处一致。

**`std::cpp`：** 本轮不可用。`std::cpp` 目前整体拒绝张量（design/cpp-standalone 的第 5 阶段），任何签名里出现 `Tensor` 的函数都会得到定位的 `TranslationRefused` 并指出参数类型。这是标准 C++ 后端的张量桥接依赖，不是 `take` 的缺口；现有 `trans.cpp` 的 `refuse_tensor` 测试覆盖这条拒绝路径。报告不在这一轮给 `std::cpp` 增加张量表示。

### 2. `one_hot`

`tensor::one_hot(labels, classes)` 接受与 `take` 下标相同的整数形式，返回二维数值张量 `[len(labels), classes]`：每行在类标处为 1.0，其余为 0.0。

- **元素类型固定 f32。** H15（字面量上下文类型）未落地，没有逐元素类型标注可选 f64；f32 是张量栈的默认数值类型，也是 `nn` 损失期望的类型。
- `classes < 0`：常量时是编译期 `SemanticDiag::ArgumentsRejected`（推断抛 `ShapeError`）；运行期是定位的 `InvalidArgument`。
- 类标不在 `[0, classes)`：定位到 `one_hot` 调用处的 `IndexOutOfRange`，消息是 `Index 3 is out of range for the class dimension of one_hot of length 3.`；负类标不回绕。

### 3. `softmax_cross_entropy` 按目标类型重载

`nn::softmax_cross_entropy(logits, target)` 与 `nn::softmax_cross_entropy_grad(logits, target, dy)` 各自是**两个算子、同一个导出名、不同签名**，由 `OperatorGroup` 的普通重载解析选择，不是运行期分支：

| 目标类型 | 选中的定义 | 目标含义 |
|---|---|---|
| 浮点元素类型的 `Tensor`，或数值数组 | `nn:softmax_cross_entropy` | `[batch, classes]` 的独热/分布行 |
| 已知整数元素类型的 `Tensor`，或 `int[]` | `nn:softmax_cross_entropy_labels` | 每个 logits 行一个类标 |

- 独热定义在目标 dtype 已知为整数时返回“不匹配”，整数定义只在目标 dtype 已知为整数时匹配。
- 整数形式检查 rank 2、每行一个类标（`TensorDimensionMismatch`）与类标范围（定位的 `IndexOutOfRange`，`the class dimension of softmax_cross_entropy`）。
- 两种形式用**同样的循环顺序**（行最大值、`exp` 求和、`log` 求和、`loss -= logit[label] - logZ`），因此同一条 logits 与等价目标的损失、梯度逐位相等；测试用 `sum(abs(a - b))` 断言 `grad_diff=0.0`。整数形式的梯度是 `dy * (softmax(logits) - one_hot(labels))`，循环顺序也与独热内核相同。
- `softmax_cross_entropy_grad` 有同样的两个定义，`value_and_grad` 对两种形式都无需新 API。
- 目标 dtype **未定**（裸 `Tensor` 形参）时保留独热形式，即改动前的写法；这是本轮的已知限制，见待决问题。

## H20-3 键式随机数的最小集

判据来自 `docs/design-principles.cn.md` 13.5（无状态随机）、`docs/design/training/README.cn.md` 4.1（`Key` 不透明 128 位、Philox4x32-10、跨设备逐位一致），以及 `docs/handover/reviews/H13-H14.md` 的答复（`random::key`、`split`、`permutation`，纯函数）。

### 1. 算子

| 算子 | 签名 | 语义 |
|---|---|---|
| `random.key(seed)` | `int -> Key` | 由种子得到 128 位 key |
| `random.split(key)` | `Key -> (Key, Key)` | 两个独立的子 key，纯函数 |
| `random.permutation(key, n)` | `(Key, int) -> int[]` | `[0, n)` 的均匀随机排列，纯函数 |

三者都注册为 `pure = true`，不声明任何资源，既不读也不推进进程生成器。同一参数调用两次得到同一个值；围绕它们的 `rand()` 抽取与不调用时相同（测试先 seed、抽一次、调用三者、再抽一次，然后重新 seed 复现）。`n = 0` 给 `[]`，`n = 1` 给 `[0]`，都不消耗抽取；`n < 0` 是定位到调用处的 `InvalidArgument`：`Invalid argument of 'random.permutation': the permutation length is -1; it must be non-negative.`

### 2. `Key` 的表示

```
type Key = { hi: int, lo: int }        // 值 = (hi << 64) | lo，两半按无符号位解释
```

H5（名义类型）尚未落地，这是过渡表示：`random` 导出 `Key`（`random.Key` 可命名它），两个字段都是 int64，按内容比较，可存进树/数组。打印形式确定：`{ hi: 1350887118657991639, lo: -7139630017956984517 }`；解释器与 `std::cpp` 生成的 C++ 结构体字段顺序相同，因此打印和 `==` 在各调度器与翻译后的 C++ 中一致。

### 3. 算法（规范性）

`include/camel/utils/philox.h` 是唯一实现，random 模块的内核与 `std::cpp` 写出的程序都包含它：

- **块函数**：8 个 32 位字（`c0..c3`、`k0..k1`），10 轮
  `p0 = M0*c0`、`p1 = M1*c2`、`c0 = hi(p1) ^ c1 ^ k0`、`c1 = lo(p1)`、
  `c2 = hi(p0) ^ c3 ^ k1`、`c3 = lo(p0)`，然后 `k0 += W0`、`k1 += W1`；
  `M0 = 0xD2511F53`、`M1 = 0xCD9E8D57`、`W0 = 0x9E3779B9`、`W1 = 0xBB67AE85`。
  `mulHigh` 用 32 位分片求 64×64 乘积的高半，因此 MSVC（没有 `__int128`）也能构建。
- **`key(seed)`**：Philox key = `seed`、counter = 0 的块，按低位在前打包：`lo = o0:o1`，`hi = o2:o3`。
- **`split(k)`**：两个子 key，domain 分别是 `0x9E3779B97F4A7C15` 与 `0xD1B54A32D192ED03`；每个都是 Philox key = `k.lo`、counter = `(k.hi, domain)` 的块，同样打包。
- **`permutation(k, n)`**：从 `[0, n)` 开始，`i` 从 `n-1` 递减到 1，抽 `j ∈ [0, i]` 并交换。每次抽取是 Philox key = `k.lo`、counter = `(k.hi, 0x8000000000000000 + 抽取序号)` 的块的低 64 位字 `o0:o1`；抽取序号在每次块（包括被拒绝的块）后递增。`j` 用 Lemire 的乘减拒绝法：`hi = mulHigh(r, i+1)`、`lo = r * (i+1)`，当 `lo < 2^64 % (i+1)` 时拒绝。
- 因为每次交换都从剩余前缀中均匀选择，`permutation` 在 `n!` 个排列上均匀。
- 算法不读时钟、不读环境、不用全局状态；头文件只用标准库与整数运算。

### 4. 确定性与 `std::cpp`

四个调度器、解释器与翻译后的 C++ 调用同一个头文件，因此 key、split 的子 key、排列逐位一致。`std::cpp` 用 `camel/standalone/random.h` 的 `rt::randomKey<Key>(seed)`、`rt::randomSplitKey<Tuple, Key>(key)`、`rt::randomPermutationKey<Array, Key>(key, n, site)`；没有生成器、没有状态，翻译器可以共享或重排这些表达式。慢层测试 `keyed_random.std_cpp_agrees` 编译并运行三个程序，与 `std::fvm` 的输出逐字节比较。
