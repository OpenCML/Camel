## 1. `macro` 现在做什么，`#macro` 增加了什么

按设计原则第 8 节的词汇：`macro` 是函数声明上的一个编译期标记，**没有阶段、不是必需的**——流水线里没有 `std::macro` 时，被标记的函数就是普通函数，调用照常运行；有 `std::macro` 时，这个遍可以对“实参全为常量”的调用提前求值，把结果变成常量，从而让后续的常量折叠、特化看到它，而求值失败按“遍运行中的故障”处理。旧实现把这个含义放在函数类型的 `Modifier::Macro` 里：解析器把关键字 `macro` 记成修饰符，`std::macro` 通过 `FunctionType` 读它，失败则用编译期诊断拒绝程序；这条路径有两个结构性问题，一是标记属于“声明”而不是“函数类型”，函数值被转发一次（`forwardingGraphOf`）或从泛型实例化出来时标记就可能丢，二是编译期诊断把“遍运行失败”说成了“编译错误”，与第 8 节冲突。`#macro` 把同一个含义放回声明：它是标准标签（`on func`，无参数，无 `read_by`），解析成普通的 `TagUse`，语义索引把它记在声明上，GIR 在函数图上置 `kGraphFlagMacro`，并在每个调用点上置 `kGCNodeFlagMacro`；`std::macro` 只展开被标记的图，标记随图编码/解码和函数值转发一起走，不再依赖函数类型。标准标签不声明 `read_by` 是刻意的：没有 `std::macro` 的程序里 `#macro` 不产生任何“无人读取”的告警，因为第 8 节说这个标记不必被任何遍读取；求值失败改为走运行期诊断汇（`RuntimeErrorReporter` + `RuntimeDiagSink`），阶段是 `pass:std::macro`，程序不运行、失败前已经产生的输出保留——它和任何遍运行中的故障一样，不再是编译错误。

实现上的落点：

- `include/camel/core/tags.h` / `src/core/tags.cpp`：标准标签 `macro`（`on = Func`，无 `read_by`），`tag::declaresMacro(attr::AttrSetId)`。
- `src/compile/gir/builder.cpp`、`builder_generics.cpp`、`builder_decorators.cpp`、`builder_operators.cpp`：在函数图、泛型实例化、装饰器图、算子值图上置 `kGraphFlagMacro`；`builder_calls.cpp` 的 `forwardingGraphOf` 复制该标志；`draft_graph_builder.cpp` 的 `addFuncNode` / `addOperNode` 给调用点置 `kGCNodeFlagMacro`。
- `include/camel/runtime/graph.h`：`kGraphFlagMacro = 1 << 0`（`GCGraphFlag`），`GCGraph::isMacro()`；`include/camel/runtime/draft.h`：`GraphDraft::isMacroGraph()`。
- `src/compile/gir/graph_encode.cpp`：`prepareGraph` 把 `graph->draft().flags()` 复制到新 draft，`constructInPlace` 用 `GCGraphDerivation{kInvalidGraphId, prepared.draft->flags()}`。这是本次暴露的**基础设施缺陷**：在此之前没有任何图级标志需要穿过编码，draft 重建时标志被静默丢掉，`#macro` 的调用点标记正确、运行时图却不再自称 macro；修复后 `std::macro` 在编码后的图上仍认得它。
- `src/execute/macro/eval.cpp`：`MacroEvaluator::executeFunction` 要求 `runtimeGraph->isMacro()`；`reportFailures()` 用 `RuntimeFault(RuntimeDiag::MacroEvaluationFailed, {callee, reason}, ...)` 经运行期报告器描述，设 `diagnostic.stage = "pass:std::macro"`，交运行期汇。
- `include/camel/core/data/composite/func.h` / `.cpp`：`FunctionData::isMacro()` 读 `graph()->isMacro()`；`modules/autodiff/pullback.cpp` 改用图/被调函数的 `isMacro()`。
- 删除 `FunctionType` 的 `Modifier::Macro`（枚举、`to_string`/`from_string`、`ModifierSet::macro()`），删除关键字 `macro` 的词法/语法入口，解析器注释同步。

## 2. 现有宏测试对形状的约束

`test/cases/trans/macro/` 原有 16 个用例（本次新增 4 个，共 20 个；计划 26 个测试），覆盖的正是第 8 节允许的几种形状：普通常量求值（`basic`、`chain`、`pipeline`）、分支与深链（`branch_chain`、`deep_chain`）、闭包与函数值（`functor`、`function_arg`、`closure_isolation`、`closure_runtime_call`、`static_object_access`）、副作用（`macro_effect`、`failed_evaluation`）、失败（`failed_depth`、`failed_no_rule`、`failed_unreached`）、非静态参数（`not_static`）。它们对标记的形状只有一个隐含约束：`std::macro` 必须能判断“被调用的这个函数是 macro”，**不管这个函数值是直接调用、作为参数传进来，还是从泛型/装饰器/算子表里产生**。旧实现靠 `FunctionType` 上的修饰符，函数值转发时会丢；本次把判断放到图上并补上 `forwardingGraphOf` 的复制之后，这些用例的输出不变，说明新形状与旧行为兼容。

有三处是**冲突**，按“设计原则优先”处理并记录：

1. **失败的性质**：旧代码把 `std::macro` 的求值失败报成编译期诊断，测试描述和 `docs/technical/13_macro_system_progress.md` 也写着“编译期错误”。第 8 节说它和任何遍运行中的故障相同，因此现在是运行期故障。位置（调用处或报错算子处）、错误码 `0x0400000E`、`std::macro` 缺席时的行为都不变；变的只是诊断性质、阶段和措辞。`failed_evaluation.error`、`failed_no_rule.error`、`failed_depth.error`、`failed_unreached.error` 的断言与描述已按新规则改；`failed_evaluation.json` 断言 `stage === 'pass:std::macro'`。
2. **“程序不运行”的后果**：旧规则说“即使运行期执行不到也拒绝程序”，现在说“在遍运行时停止”。对测试的可见影响相同（退出码 1、不打印 `main start`），但原因不同；描述已改。
3. **AST 快照**：`#macro` 是 `TagUse` 节点，不是修饰符，因此 38 个转换过的 `.cml`（及 12 个文档代码块）的 AST 哈希变了；`test/plans/feat/parse/golden/ast_hashes.txt` 更新了 45 条（39 条来自本次，6 条是 `origin/develop` 上 `c8e71dca4` 改了 `fields` / `match type` 的解析却漏更的旧快照，见第 6 节）。`macro` 关键字从词法表删除后，`test/cases/tools/grammar/keywords.cml` 的 scopes 金样也更新了（45 个关键字）。

另外两个原有约束保持不变：`macro_round_lifetime_gc` / `gc_macro_constants` 要求每轮产生的常量在轮后被 GC 正确回收，图的标志不能把它们钉住；`feat/compile` 下的 macro 用例（`refuse_grad`、`effects`、`static_expansion` 等）要求无 `std::macro` 时函数是普通函数、有 `std::macro` 时失败在遍里停止。这两组在改动后全绿。

## 3. 展开、轮、预算与失败

`std::macro` 的展开是**按轮**的：一遍扫描图，对每个调用点，若被调函数的图带 `kGraphFlagMacro` 且所有实参都是 DATA（常量），就用 `MacroEvaluator` 求值，把结果写回成 DATA 节点；有变化就再扫一轮，直到不动点。`not_static` 的调用（有非静态实参）原样留给运行时，不是失败。这个循环沿用既有的两个上限：

- **深度**：`--max-macro-depth`，默认 64（范围 1..1000000，环境变量 `CAMEL_MAX_MACRO_DEPTH`）。`failed_depth` 用 `count(20)` 成功、`count(100)` 失败在 64 层。
- **轮数**：`--max-macro-rounds`，默认 1,000,000（范围 1..2^40，环境变量 `CAMEL_MAX_MACRO_ROUNDS`）。它限制一次求值里的**循环迭代**，不是“展开轮数”；`round_budget.cml` 用 `triangle(1000)` 验证：默认打印 `500500`，`--max-macro-rounds 3` 在调用处 `12:13` 报 `MacroEvaluationFailed`。

失败在任何一轮发生都走同一条路：`RuntimeFault` 带上被调函数名和原因，报告器给出位置（调用处，或失败算子自己的位置），阶段 `pass:std::macro`，运行期汇的第一个错误就让 CLI 停止流水线；已经打印的输出保留。没有新增诊断码，`docs/diagnostics.md` 只重算了 `MacroEvaluationFailed` 的帮助文字（“compile-time error”改为“fault during the run of the pass”）。

**一轮产生另一个 `#macro` 的情况**：当前实现不做特殊处理。如果某轮求值结果是一个带 macro 标志的函数值，它作为常量留在图里；下一轮扫描若在调用点上用它且实参全为常量，就会继续展开。展开轮本身没有单独的上限，只有上面的循环轮数上限和遍驱动程序；这一点列为待决（第 7 节第 3 条），没有自行加规则。

## 4. 位置、禁止形式与新用例

标签机制沿用第 6.2 节：`#macro` 是声明标签，位置是 `func`；写在别处是 `SemanticDiag::TagNotAtPosition`，参数个数不对是 `SemanticDiag::TagArgumentCount`。本次新增：

- `test/cases/trans/macro/tag_positions.cml`：顶层函数 `square`、嵌套函数 `twice`、泛型函数 `pick(x: typeas T)` 三种位置；输出 `49`、`6`、`5`，证明顶层、嵌套、泛型实例化都保留了标记（泛型那一份走 `builder_generics.cpp`）。
- `test/cases/trans/macro/tag_on_block.cml`：`#macro { ... }` 在块上，`TagNotAtPosition`，行 7 列 6（标签名处，不是 `#`）。
- `test/cases/trans/macro/tag_with_argument.cml`：`#macro<1>`，`TagArgumentCount`，行 6 列 2；标准标签没有声明参数，因此带实参被拒绝。
- `test/cases/trans/macro/round_budget.cml`：轮数预算，见第 3 节。

“禁止的形式”按第 6.2 节和标签声明实现：`#macro` 只能写在函数声明上；块、表达式、类型、字段、参数上的 `#macro` 都会被位置检查拒绝（`on func`）。lambda 没有声明，因此不能带声明标签；bodyless 的 native 声明目前被静默忽略（标签在 native 早退之后才解析），这一点列为待决（第 7 节第 5 条），没有自行加诊断。

## 7. 待决问题

按任务要求，以下问题设计原则没有说清，报告而不自行决定：

1. **`#macro` 能否带参数**（例如 `#macro<1>` 表示展开轮数或深度）？当前标准标签声明为无参数，`TagArgumentCount` 拒绝任何实参；第 6.2 节只说标签可以有实参，第 8 节没有规定 `#macro` 的实参含义。
2. **宏的值可以是什么**？当前求值器把任意值都物质化成常量，包括函数值/闭包（`functor` 把闭包传给普通函数 `sink`，`function_arg` 把函数参数传进宏）。第 8 节说“形成常量”，但没有说函数值是否算可提前求值的常量；如果函数值不算，`functor` 的形状需要改。
3. **一轮产生另一个 `#macro` 时怎么办**？当前按不动点继续展开，展开轮没有单独上限；`--max-macro-rounds` 限制的是一次求值内的循环迭代。是否要给“展开轮”设预算，或者禁止宏产生新的宏？
4. **`#macro` 能否写在 lambda / 块上**？第 6.2 节只给 `func`、`type`、`field`、`nodes`、`param` 五个位置，lambda 没有声明；当前块上的 `#macro` 是 `TagNotAtPosition`。是否希望 lambda 表达式也能被标记？
5. **bodyless native 声明上的 `#macro`**：当前在 native 早退之后才解析标签，因此被静默忽略。是否应当报“这个标签在这里没有意义”的诊断？
6. **无 `read_by` 的选择**：标准标签没有声明谁读它，因此没有 `std::macro` 的程序完全安静。这是按“标记不是必需的”做的；如果希望提示“这个程序有 `#macro` 但流水线没有 `std::macro`”，需要另定一条诊断。
