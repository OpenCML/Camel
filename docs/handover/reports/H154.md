## 0. 一句话结论

**slow 层不是绿的，也不是“一条红”。** 可跑的 134 条 slow 用例里 **133 条绿、1 条真红**（`debugger.dap_protocol`，

## 1. 清单：slow 层到底有哪些东西

### 1.1 怎么算“slow 层”

两层定义叠在一起，缺一不可：

1. `tier = "slow"` 写在计划头上 → 该计划的**全部**用例属于 slow 层；
2. `tier = "slow"` 写在单个 `[[tests]]` 上 → 只有那几条属于 slow 层，同一个计划里的其他用例仍在快层。

`npm run test` 是 `node ./scripts/test.js --tier fast`（`package.json`），而 tier 过滤只作用于**目录**目标；
命名一个计划**文件**会把它整个跑完，不管 `--tier`。所以：

- 快层闸门（`smoke` + `feat/**`）**永久跳过**第 1 类计划，以及第 2 类里那些带 slow 的用例；
- `test/plans/**` 里的 `gpu/**` 与 `perf/**` 根本不在快层闸门的目标里（闸门只给 `smoke` 与 `feat`），
  它们**只有** `--tier all` 或命名文件才会跑。

tag 不能当层用：`gc`、`progen`、`torch` 这些 tag 在 fast 层计划上也有（`feat/mm/gc_poison_sweep`、
`feat/opt/progen_simplify`、`feat/mm/graph_space` 等），它们每次闸门都在跑。本报告的清单按 tier 取，
tag 只用来确认某个 slow 条目的**性质**（stress / progen / PyTorch），从而决定是否排除。

## 2. 排除项：没跑的，和为什么

`agents/test.md`（General Policy 最后一条）点名了“只在里程碑、由协调者、在安静的机器上跑”的几类：
投毒扫描、GC 压力计划（`gc.collection_trees_*`、`gc_elder_*`）、progen 随机程序检查、PyTorch 对照、
perf/timeit 计划。任务书又加了“需要独占机器的都不跑”。主机 `88zjwei` 是共享的（32 核，清扫期间抽样到
的 1 分钟 load 是 9–53，H147 记录过 150–215 的时段），所以下面这些**一次都没跑**：

| 排除的计划 / 条目 | 用例 | 原因 |
|---|---|---|
| `perf/fib`、`perf/para`、`perf/startup`、`perf/training_steps` | 19 | `kind = "benchmark"`：测的就是机器负载，默认独占跑；上限/中位数在共享机器上没有信号 |
| `perf/gc` | 6 | 分钟级 soak、GB 级存活集（`agents/test.md` 的 GC soak） |
| `perf/collections_fuzz` | 4 | 分钟级随机程序与差分（progen/fuzz 类） |
| `perf/showcase_c1/c2/c6/d5` | 4 | PyTorch 对照（`skip_unless` 里就有 `torch`） |
| `feat/mm/gc` | 45 | GC 压力 + 投毒：`CAMEL_GC_STRESS_*`、`CAMEL_GC_POISON=1` |
| `feat/mm/gc_collections` | 73 | 集合压力：每个用例都在 `CAMEL_GC_STRESS_ALLOC` + `VERIFY=both` 下 |
| `feat/mm/gc_elder_exhaustion` | 22 | `gc_elder_*`，被 `agents/test.md` 点名 |
| `feat/opt/progen` | 2 | progen 随机程序 × 25 格 |
| `feat/modules/autodiff` 的 5 条 slow | 5 | PyTorch 对照 |
| `feat/modules/onnx` 的 2 条 torch slow（`ort_train_step_adam`、`resnetbn_train_step_export`） | 2 | PyTorch 对照 |
| `feat/modules/onnx` 的另外 2 条 slow（`pass_export_equals_export_model`、`export_tree_recursion`） | 2 | **连带排除**：runner 没有“按用例名选”的开关，命名计划文件会把它俩和上面两条 torch 的一起跑 → 整个文件不跑，缺口记在这里 |

这些缺口不是“通过”，是**这一层仍然没人知道的部分**，发布判定必须把它们当成未知，而不是绿。

补充两条与排除相关的事实：

- 主机现在有 CUDA 12.3（`/usr/local/cuda/bin/nvcc`）与 8×RTX 3090，所以 `gpu/tiles`、`tiles_rows`、

- `perf/**` 与 `gpu/**` 不在快层闸门的目标里（闸门是 `smoke` + `feat/**`），也就是说这 10 + 5 个计划
  **既不进快层，也很少有人跑 slow**：它们是这一层里最黑的部分。

### 4.2 `debugger.dap_pipeline` 与 `debugger.dap_session` —— 抖动（适配器与 worker 的连接）

两者都是**快层**用例（`debugger.plan.toml` 里 12 条中的 2 条），因为本层清扫是命名计划文件跑的，所以
它们每一轮都在。跑法同上（`-Jobs 8`、`-NoBuild`；同一时段抽到的 1 分钟 load 22–53）。

| 轮次 | 时间 | `dap_pipeline` | `dap_session` | 其它 |
|---|---|---|---|---|
| 第 1 批 | 21:28 | 过（200 ms） | 过（234 ms） | `dap_protocol` 红 |
| 复跑 1 | 21:34 | **红（267 ms）** | 过 | `dap_protocol` 红 |

| 收尾（HEAD `0ee01ba02`） | 21:56 | 过（530 ms） | 过 | `dap_protocol` 红（61.54 s） |

**计数：`dap_pipeline` 10 轮 1 红；`dap_session` 10 轮 1 红。** 历史上同一条 `dap_pipeline` 在

所以它是**慢性抖动**，不是本次引入。

两条的原话（用例自己打印的）：

- `dap_pipeline`：`FAILED: step a consuming translation pass`，`1 of 36 checks failed`；
- `dap_session`：`FAILED: std::fvm: continue is accepted`，适配器回
  `{"success":false,"message":"The program being debugged has ended."}`，`1 of 99 checks failed`。

**分诊：(c) 抖动，不是超时，也不是期望陈旧。**

- 不是超时：两次失败都在 0.3–0.4 s 内返回，用例里等待事件的那些地方一次都没等到超时；
  加长 `timeout_ms` 不会改变任何东西。
- 不是期望：期望的答案（这一遍能被步进、`continue` 被接受）本来就是这个调试器该做的事。
- 线索：两条都是“本该在停止状态下被服务的请求没有被服务”。`dap_session` 那句
  `The program being debugged has ended.` 是适配器在 `ask()` 拿不到 worker 的回答时给的
  （`tools/debugger/src/dap/adapter.cpp` 的 `ask(action, args)` 分支），也就是说
  **适配器 ↔ worker 的 HTTP 通道**在会话中途失败了一次；`dap_pipeline` 的 `camel/nextPass`
  走同一条 `ask()` 通道。两条红落在同一族里。
- **是否随负载变化：本任务无法判定。** 三次红都落在清扫期间 load 22–53 的时段里，而这套用例
  在本任务里**没有一次**在低负载下跑过（主机上没有安静时段可供对照），所以“负载相关”只是
  与 H43/H76/H147 观察一致的猜测，不作为结论。

**修了什么：** 只做了安全的一步——`dap_pipeline` 那条检查原来只报“检查失败”，把适配器的原话丢了
（这正是 H43/H76/H147 只能把它记成“负载间歇”的原因）。现在它把响应体一起打出来（§5 提交 1），
下一次再红就能直接看见原因。**没有**做猜测性的改法：6 次复现批没能在 `dap_pipeline` 上重现，
改也就无法验证；让它在停止态一定被服务，要动的是 worker 的 HTTP 请求生命周期（设计问题），
留给调试器那条线（与 H150 同一块地，但不属于 `dap_protocol` 的修复）。

## 5. 改了什么

### 5.1 提交 1：让被拒的步进说出适配器的原话

`test/cases/tools/debugger/dap_pipeline.test.mjs` 的那条检查从

```js
check((await consumed.request('camel/nextPass')).success, 'step a consuming translation pass')
```

改成先把响应接下来，再连同响应体一起断言。理由：这是唯一一条会偶发红的检查，而它原来的失败信息只有
“检查失败”，把适配器的回答丢了——H43、H76、H147 三次撞到它，都只能记成“负载间歇”。改动只加诊断、
不改断言（`success` 仍是同一个判据），失败时的行为完全不变，成功时一个字节都不多写。
证据：§4.2 的 9 轮计数；复现批里这条检查 6 次全过，说明改动不会让它变红。

### 5.2 没有改的，以及为什么

- **`debugger.dap_protocol` 不动**：真红，确定性，需要设计决定（折叠常量该由索引层还是遍来标注、
  存活副作用的 origin 由谁保留），H150 正在修（§4.1）。
- **没有把任何计划从 slow 移到 fast，没有删计划，没有改期望值去凑绿。**
- **没有加 `skip_unless`**：本轮没有任何“缺前置”的用例——需要系统 C++ 编译器的两条
  （`agree_with_fvm`、`keyed_random.std_cpp_agrees`）与需要 CUDA 的三份 gpu 计划都真的跑了并通过；
  主机有 CUDA 12.3 与 8×RTX 3090（H154 之前的“主机没有 nvcc”的记法已过期）。
- **两条 DAP 抖动不做猜测性修复**：见 §4.2 结尾。

### 5.3 建议（不改，交给协调者/作者）

1. 发布前的 slow 清扫**用显式计划文件清单**（§3 的四条命令），不要用 `-Plan test/plans -Tier all`：
   后者会把 §2 里按 policy 不该在共享主机上跑的 200 条全部跑起来。
2. 若要让 `gpu/**`（102 条）不再隐形：它既不在 `smoke`+`feat` 闸门里，也没有
   `test/plan-selection.json` 规则，改 `modules/tiles/**` 不会选中它。把 `test/plans/gpu` 加进合并闸门
   是流程决定（不是“把 slow 挪进 fast”），需要协调者拍板。

## 6. 为什么这些红能躺这么久

三层原因叠在一起，缺一层都藏不住：

1. **`npm run test` 就是 `--tier fast`**（`package.json`）。tier 过滤只作用于目录目标，所以
   `node scripts/test.js test/plans/feat/tools` 这类目录目标会把 slow 用例逐条滤掉；只有**命名计划文件**
   才整计划跑。日常闸门是 `smoke` + `feat/**` 的目录目标 → slow 用例一条都不进。
2. **slow 标记是 2026-10-20 一次性加的**（`617198cc3`，“The test runner runs plans in parallel, and every
   plan states whether it belongs to the fast or the slow layer”，H10）。同一天起 `dap_protocol` 这类
   原本每次闸门都跑的用例被移出闸门 —— 从那一刻起，它红还是绿，闸门都不知道。`dap_protocol` 里
   出问题的那段“优化之后”的检查在 **2026-10-16** 被 `434aeaf88` 改写成现在的样子（+16/−4 行），
   10-20 被划进 slow；H147 在 **2026-10-21** 命名文件才第一次看见它红
   （`reports/H147-release.md` §3.4）。
3. **`gpu/**` 与 `perf/**` 连“可见”都没有**：闸门的目标是 `smoke` + `test/plans/feat`，这两个目录
   不在其中；`test/plan-selection.json` 里也没有 `tiles`/`gpu` 的规则（`grep -n 'tiles\|gpu'` 只命中
   `perf` 的两条），所以 `--changed` 改到 `modules/tiles/**` 也不会选 `gpu/tiles`。它们只有
   `npm run test:all`（无目标、`--tier all`）或命名文件才跑。也就是说：**H147 §3.5 推荐的发布前命令
   `-Plan test/plans -Tier all` 能覆盖它们，但没有任何合并闸门会跑它们**，`gpu/**` 的 102 条用例
   在日常流程里从来没被跑过 —— 本次清扫第一次把它们跑绿（§3）。

由此得到一条应当写进流程的结论：**“slow” 不是“更慢的快层”，它是没人看的层**。把一条用例移进 slow，
等于把它从所有日常闸门里删掉，而且没有任何东西会因为它的红而失败。发布判定若要用这一层，必须
显式列出要跑的计划文件（本报告 §3 的命令），不能假设 `-Plan smoke,test/plans/feat` 覆盖了它。
