## H16-1 `Json` 访问器接受 `Json!`；`JsonTooDeep` 错误种类

判据来自 `docs/design-principles.cn.md` 11.2（`Json` 的访问器接受 `Json!`、错误原样传下去、`decode(text)->get<'a'>` 的类型是 `Json?!`、太深的文档报 `JsonTooDeep`）、第 14 节（不为通过测试改语义），以及 `docs/handover/reviews/H9-H11.md` 对 H11 待决问题的答复（新增 `JsonTooDeep`，默认上限 10000，以后作为 `decode` 的可选参数）。没有新增第二条错误通路：访问器的结果就是普通的 `T?!`，由 `??`、`!!`、`match` 拆开，与 `T!` 的既有用法一致。

### 1. 改动

#### 1.1 类型规则（`modules/json/module.cpp`）

`isJsonOrNullable` 换成 `accessorResultType`，按实参的静态类型给出结果类型：

| 实参类型 | 访问器结果 |
|---|---|
| `Json` | `R?` |
| `Json?` | `R?` |
| `Json!` | `R?!` |
| `Json?!` | `R?!` |

`Json?!` 也接受，因为它是访问器对 `Json!` 给出的结果类型：设计原则 11.2 的 `decode(text)->get<'a'>` 若要继续 `->as_int`，第二个访问器就必须接受 `Json?!`。断言这一点的测试见 3.1（`good->get<'a'>->get<1>->as_int`）。

`get<key>`、`get<index>` 与 `as_bool`、`as_int`、`as_float`、`as_string`、`as_array`、`as_object` 都走这条规则。`kind`、`is_null` 不变：它们是对整个值作答（`string`、`bool`），不是取值器，也不接受 `Json?`；若让它们接受 `Json!` 就要另定 `string!`、`bool!` 的结果，见待决问题。

#### 1.2 运行期（`modules/json/operators.cpp`）

- `JsonAccessorArg`：按静态类型剥掉 nullable / fallible 层。null 的 `Json?`（以及 `Json?!` 的外层 null）表示“没有东西可取”；失败的 `Json!` 记下**原来那个失败的 `Json!` 值**（`slot_t failed`），不是重新造一个错误。
- `jsonAccessorResult`：失败 → `makeSome(failed, nullable(fallible(R)))`，即把同一个失败值放进 nullable 层；成功 → `makeSome(makeOk(value, fallible(R)), …)`；没有可取的值 → `NullSlot`。`Json` / `Json?` 实参仍走原来的 `makeSome(value, nullable(R))`，行为与改前逐字节相同。
- `payloadIf` 增加结果类型参数，`as_float` 保留“整数也是 float”的既有规则。
- GC：新值都用 `makeSome` / `makeOk` 连同静态类型写入（写屏障），失败值放进 nullable 时其类型是 `fallible(R)`；没有无类型槽。`Json?!` 的两层就是这个类型看到的两个 `Tuple`，追踪仍沿类型走。

#### 1.3 `JsonTooDeep`

`decode` 与 `decode_as` 在解析前的深度扫描命中时都返回 `makeError("JsonTooDeep", …)`（改前是 `JsonParseError`）。消息改为：

```
the JSON document nests deeper than the limit of 10000 levels (at line 1, column 10001);
decoding a deeper document would exhaust the native stack: decode a shallower document or
set CAMEL_JSON_MAX_DEPTH to a larger limit
```

即：说明文档比上限更深、点出上限（10000）、给出越界括号的 1-based 行与列；`CAMEL_JSON_MAX_DEPTH` 这个既有设置不变。`Error.location` 与其它算子一致是算子名（`<json::decode>` / `<json::decode_as>`），因为算子不知道调用处；文档内位置在消息里。错误值的打印走 `printTaggedSlots`，输出 `error JsonTooDeep: <message>`（由 `value.deep_json_depth` 覆盖）。

关于诊断目录：`node scripts/diagnostics-catalog.mjs` 只枚举编译器/运行时的**诊断**（`LexicalDiag`、`SemanticDiag`、`RuntimeDiag` 等），错误值的 kind 是字符串，不在其中；运行 `--write` 后 `docs/diagnostics.md` 无任何变化（170 条，无新增）。Json 的故障类诊断只有 `RuntimeDiag::JsonEncodeUnsupported`。因此 `JsonTooDeep` 记录在错误值的目录里，即 `stdlib/signatures/json.cml` 的 `@fails` 与由它生成的 `docs/stdlib-reference.md`。

### 3. 测试与结果

#### 3.1 新用例（`test/cases/modules/std/json/json_accessor_error.cml`，新计划 `test/plans/feat/modules/json_accessor_error.plan.toml`）

一个程序、四个后端（nvm/fvm/jit/prl）加 `std::opt::inline std::opt std::fvm`，输出快照逐字节比对，四个后端的输出还互相核对。它锁定：

1. **失败的 `Json!`**：`get<'a'>`、`get<0>`、`as_int`、`as_string`、`as_array`、`as_float`、`as_object` 的结果都不是 null，其错误与原错误 `==`（同 kind、同 message、同 location）——第一行七个 `true`；随后打印 `JsonParseError <json::decode>`。这同时证明没有崩溃。
2. **普通 `Json`**：`report(j: Json)` 里 `j->get<'a'>->get<0>->as_int ?? 0` 给出 `5`，`j->get<'s'>->as_string ?? '?'` 给出 `hi`（改前的行为不变）。

### 5. 待决问题

1. **`kind` / `is_null` 是否也接受 `Json!`**：两者今天是 `Json -> string` / `Json -> bool`。接受 `Json!` 需要把结果改成 `string!` / `bool!`（`is_null` 也可讨论 `Json?`），这是新的签名，不属于本项“访问器”。未改，等语言作者定。
2. **其它层序**：本项接受 `Json?!`（访问器自己产生的层序），不接受 `Json!?`（fallible 套 nullable）；`decode_as` 也仍只接受 `string` / `Json`。若希望 `Json!?` 可链式取值或 `decode_as` 也传播错误，需要单列决定。
3. **错误值 kind 没有目录机制**：`docs/diagnostics.md` 由枚举生成，只覆盖编译器诊断；错误值 kind（`JsonParseError`、`JsonTypeError`、`JsonTooDeep`、`ParseError`、`IOError`…）目前只在 `@fails` 文档里列出。若要把错误值 kind 也纳入可检索的目录，需要一个独立于 `Diagnostic` 枚举的来源。
4. **深度上限作为 `decode` 的可选参数**：设计原则 11.2 记为“以后开放”，本项按任务保持 `CAMEL_JSON_MAX_DEPTH` 不变，未新增参数。
