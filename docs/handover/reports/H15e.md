## 1. Names now used

The old names are deleted, not aliased (design principles: a superseded form is removed, not kept
alongside).

| place | before | now |
|---|---|---|
| `include/camel/standalone/entry.h`, `EntryKind` | `ComplexFloat`, `ComplexDouble` | **`C64`, `C128`** |
| `EntryArguments` getters | `complexFloat(i)`, `complexDouble(i)` | **`c64(i)`, `c128(i)`** |
| `src/passes/trans/cpp/program_emitter.cpp` (what `std::cpp` writes) | `rt::EntryKind::ComplexFloat/ComplexDouble`, `args.complexFloat(...)`/`args.complexDouble(...)` | **`rt::EntryKind::C64/C128`**, **`args.c64(...)`/`args.c128(...)`** |
| `include/camel/standalone/format.h`, `FormatArg::Kind` | `Complex32`, `Complex64` (the part width) | **`C64`, `C128`** |

The core's `TypeCode::Complex64`/`Complex128` are **not** renamed: they are the type codes of
`c64`/`c128` (the code name counts the value's total width, and it is not a runtime-entry name).
The ambiguity the review named was the old `FormatArg::Kind::Complex64`, which meant `c128`
(2 × 64 bits) while `TypeCode::Complex64` means `c64` (2 × 32 bits); that word no longer names
two widths anywhere.

The generated program now reads, for `main(z: c128, w: c64)`:

```cpp
const rt::EntryArguments args(argc, argv, {{"z", rt::EntryKind::C128}, {"w", rt::EntryKind::C64}}, ...);
return static_cast<int>(main_(0, args.c128(0), args.c64(1)));
```

The emitter test (`entry_args.cpp_complex_open`) asserts exactly those names, so the rename is
visible where these names surface.

## 2. The entry reader reads the language's number grammar

### 2.1 The rule

A real entry argument, and **each part** of a complex one, is one whole number token read by
`camel::utils::parseWholeFloat` (`include/camel/utils/number_text.h`), not by `strtod`. That
parser is the language's rule, not the C library's: an optional sign, then decimal digits, an
optional `.` with digits on both sides, an optional exponent, or `inf` / `nan` (reference 2.5.2
and 2.5.1). A complex text is split by `splitComplexText`; each part is read at the width the
parameter declares (`float` for `c64`, `double` for `c128`). A text that is not written as a
complex number is its real part with an imaginary part of zero, so `1.5` is `1.5+0i`, exactly as
`let z: c128 = 1.5` under design principles 5.1.

The two readers call the same helper: `src/execute/entry_args.cpp::parseFloat<T>` and
`include/camel/standalone/entry.h::readNumber<T>`, and `readComplex<T>` / the complex branch of
`loadValue` have the same shape. They therefore accept and refuse the same texts:

| text | value | accepted |
|---|---|---|
| `1.5`, `-2`, `1e-3`, `1E-3` | `1.5+0i`, `-2+0i`, `0.001+0i`, `0.001+0i` | yes |
| `+1.5` | `1.5+0i` (a leading `+` is the number's sign, reference 2.5.1) | yes |
| `inf`, `-inf`, `nan` | `inf+0i`, `-inf+0i`, `nan+0i` | yes |
| `1+2i`, `0.5-0.25i`, `-2i` | unchanged complex texts | yes |
| `0x1.8p1` | — | **refused** (no hexadecimal float, reference 2.5.2) |
| `1.`, `.5` | — | **refused** (digits on both sides of the point, 2.5.2) |
| ` 1.5`, `1.5 ` | — | **refused** (no blanks; the whole text is the token) |
| `INF`, `Infinity`, `nan(1)` | — | **refused** (the language writes `inf`/`nan` lowercase) |
| `1e9999`, `1e-9999` | — | **refused** (out of range; not silently `inf`/`0`) |
| `1_000` | — | **refused** (no digit separators) |
| `abc`, `1+`, `1+2`, `1+2j`, `1+2i5` | — | refused |

`parseWholeFloat` itself was made to follow 2.5.2: it used to accept `.5` and `1.` because
`from_chars`/`strtod` do, although the reference calls both syntax errors. It now rejects them,
so **the conversion functions share the same grammar too**: `float('.5')` and
`parse_float('.5')` now fault where the old parser read `0.5`; the consistency golden pins that
(§5). This is the "one grammar, one rule" choice: there is no second, more permissive number text
for the command line, and none for `float(s)` either.

### 2.2 What changes for real entry arguments

The old reader was `strtod` on the whole string, so the command line silently inherited C forms
the language does not write. Before/after for a real `float` parameter:

| `--arg rate=…` | before (`strtod`) | now (`parseWholeFloat`) |
|---|---|---|
| `0x1.8p1` | `3` | refused |
| `1.` | `1` | refused |
| `.5` | `0.5` | refused |
| ` 0.5` (leading space) | `0.5` (strtod skips blanks) | refused |
| `0.5 ` (trailing space) | refused | refused (unchanged) |
| `INF` | `inf` | refused (`inf` is the language's text) |
| `1e9999` | `inf` | refused (out of range) |
| `1e-9999` | `0` | refused (out of range) |
| `+0.5` | `0.5` | `0.5` (a leading `+` is allowed) |
| `1.5`, `1e-3`, `inf`, `nan` | unchanged | unchanged |

The located message is the same `RuntimeDiag::EntryArgumentInvalid` at `main`; only the set of
readable texts changed. For a complex parameter the same table applies to the real fallback and
to each part (`1+2.` and `1e9999+2i` are refused too).

### 2.3 The located error and the help text

The refusal keeps its form and names the real form:

```
error[RuntimeDiag::EntryArgumentInvalid]: Cannot bind the argument 'z' of 'main': 'abc' is not a
complex number (write 1+2i, -2i, 0.5-0.25i or a real number such as 1.5).
```

The help text of `RuntimeDiag::EntryArgumentMissing` now says that a complex parameter also takes
a real number for its real part:

> `--arg name=value` (a number; a complex number written as the language writes one, such as
> `1+2i` or `0.5-0.25i`, or a real number such as `1.5` for its real part; true/false or text
> for a scalar; …)

`docs/diagnostics.md` was regenerated for that sentence (`node scripts/diagnostics-catalog.mjs
--write`, then `--verify-doc`). `std::cpp`'s `EntryArguments` reports the same sentence byte for
byte, which `cppexec` checks.

### 2.4 Where the change lives

- `src/execute/entry_args.cpp` — `parseFloat<T>` is `parseWholeFloat<T>`; the complex branch
  reads a `c64`'s parts as `float` and a `c128`'s as `double`; the header comment of
  `include/camel/execute/entry_args.h` states the whole-token rule and its refusals.
- `include/camel/standalone/entry.h` — `readNumber<T>` and `readComplex<T>` do the same, at the
  same widths; `EntryKind::C64` / `C128`; the getters; the file comment.
- `include/camel/utils/number_text.h` — `parseWholeFloat` now enforces the reference's literal
  grammar (digits on both sides of the point); its comment says the command line uses it.
- `src/passes/trans/cpp/program_emitter.cpp` — the renamed kinds and getters (the runtime does
  the reading).
- Docs: `docs/cli.md`, `docs/cli.cn.md`, `docs/language/04_execution_model.md` (+ English),
  `docs/cpp_export_build.md`, `docs/design/cpp-standalone/README.cn.md`,

## 4. Changed expectations, and why

1. **`entry_args.complex_real_hex` changed from accepted to refused.** The previous test pinned
   `0x1.8p1` as `3+0i` because it followed `strtod`; the language's grammar has no hexadecimal
   float, so the test now pins the located refusal. The old expectation was the defect the
   follow-up removes, not a regression.
2. **The real entry parser's accepted set changed.** `0x1.8p1`, `1.`, `.5`, a leading blank,
   `INF`, `1e9999` and `1e-9999` were readable through `strtod`; they are now refused. Table in
   §2.2. `+0.5` stays accepted. These are the point of the follow-up and each has its own test.
3. **The `number_text` consistency golden changed for `.5`.** `float('.5')` and
   `parse_float('.5')` now fault instead of giving `0.5`, because `parseWholeFloat` enforces the
   reference's "digits on both sides of the point" rule. Two lines of
   `test/plans/feat/consistency/golden/number_text.txt` changed; no other output in that file
   did. The alternative would be one grammar for literals and a looser one for conversions,
   which is the defect this review closes.
4. **`docs/diagnostics.md` was regenerated** because the `EntryArgumentMissing` help text gained
   the real-number form. That is the only catalog change; `catalog.doc_is_generated` passes.
5. **`cppexec` grew from 78 to 83 programs.** The old `z=1.5` accepted program stays; the old
   hex program now expects the refusal; `z=+1.5`, `z=1.` and the three real-parameter programs
   are new.
6. **The AST snapshot line for `complex.cml`** was regenerated earlier in this worktree when its
   doc comment gained the real-text sentences (main moved from line 9 to 11); it is still one
   line changed in `test/plans/feat/parse/golden/ast_hashes.txt`.

No other expectation changed; no GIR snapshot changed.

## 6. Open questions

1. **The conversion functions now share the strict grammar.** This follow-up changed
   `parseWholeFloat`, so `float('.5')`/`float('1.')` fault, not only entry arguments. I chose
   that because reference 2.5.2 calls both forms syntax errors and "one grammar, one rule" is the
   point of the review. If the language author wants conversions to keep accepting the C
   library's forms, that needs a second, documented rule for conversions — the two-parser
   situation this change removes. Please confirm the scope.
2. **An out-of-range number says "is not a number".** `1e9999` is refused with the same
   `'…' is not a number` sentence as `abc`, although `parseWholeFloat` distinguishes
   `OutOfRange`. The integer path already says "is not an integer" for `out_of_range`, so this
   follows the existing wording rather than introducing a new sentence just for the command
   line. If the message should name the range, both readers can use the status.
3. **`TypeCode::Complex64`/`Complex128` in the core** still carry the old style. They are type
   codes, not the entry/runtime kind names the review targeted; renaming them would touch every
   backend and is not this item.
4. **A complex value inside a struct or tuple entry argument** is still refused (the aggregate
   loader accepts only leaves with a file loader), as in H15d; struct-of-scalars entry arguments
   remain a separate item.
