# 断言不是守卫：`ASSERT` 在 `NDEBUG` 下是 `((void)0)`

2026-10-31 的 `exit 139` 之所以**一声不响**，原因就一行宏：

```cpp
// include/camel/utils/assert.h
#ifdef NDEBUG
#define ASSERT(condition, message) ((void)0)
```

`ASSERT` 是**调试期的断言**，发布构建里一个字节都不留。所以任何“发布构建也必须在”的检查
——越界、空值、类型不符——写成 `ASSERT` 就等于**没写**：进程不会报错，它会继续用错的值走下去，
直到在别处变成段错误、二次释放或静默的错结果。

## tonight 的两个实例

1. **`Variant::updateRefs`**：`enumTypeOf()` 用两条 `ASSERT` 守着“类型非空”“必须是 enum 类型”。
   发布构建里两条都消失，于是 GC 拿着一个函数类型去追 `Variant`，`updateRefs+31` 直接崩。
   `ab124a00e` 把它换成了**发布构建里也在的分支 + 报告 + `abort`**（`exit 134`，带读数），
   无声的崩才变成点名的话。
2. **同一晚的反例**：给草案槽位改类型时，索引合法性一度写成 `ASSERT(index < size)`。发布构建里
   它消失，负索引（静态区索引，见 `FrameView`）越界写，进程报的是
   `double free or corruption (out)`——比原来的崩更难查。改成 `if (index <= 0 || ...) return;` 才对。

## 判据

- **调试期不变量**（状态在正确的代码里永远不会违反、违反即程序写错）：`ASSERT` 合适。
- **发布构建的运行期守卫**（越界、空指针、类型不符，输入或程序都可能导致）：**必须是分支**，
  并且要么给出可读的报告，要么返回值，不能只是“在 debug 里响一声”。
- 一条 `ASSERT` 要问自己：**`NDEBUG` 之后这句守卫还在吗？** 不在，就不是守卫。
