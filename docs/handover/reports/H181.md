# H181 — `camel` 的其余分支：每条编译/装载路径都要自己回答"有错吗"

分支 `handover/H181-cli-diagnostics`（工作树 `D:\Projects\Camel-wt\h181-cli-diagnostics`），起点
`origin/develop` `58881b837`。任务书：H172 只修了 `inspect --ops`（列表分支打印完无条件
`return 0`，从不读任何模块的 `Diagnostics`），没人审计其余 CLI 路径；这种"渲染了东西却退出 0"
的形状会重复。本任务枚举每条会装载模块或编译的路径，在主机二进制上实测退出码与 stderr，
修掉吞错的路径，补每个修复的红证，并把"有没有失败"这个判断收进一个 helper。

结论：**形状不止一处，但比 H172 报告里写的少**。真正撒谎的只有 `inspect --gct`：构造树阶段
失败（缺模块导入、声明模块装载失败）时它把半棵树/看似完整的树打印出来再退出 0；组合 dump
（`--gct` 与 `--gir`/`--ops` 同时给）会先把树打出来，再报诊断退出 1。另有三个用法错误
（非法 `--timeit` 值、`--timeit` 与 `--profile` 同用、run 没有输入）打印原因后退出 0。
run、check、`--gir`/`--tns`/`--instances`/`--facts`/`--tags`、`--ops`、`--timeit` 在四种失败形态下
退出码和诊断本来就是对的；`--timeit` 从不给编译失败的程序报时间（今天如此，本次把它钉住）。
`--tok`/`--cst`/`--ast`/`--gen`、`-i`/`-s`、`--version` 的 0 是文档契约，不改。没有新增诊断码。

顺带修正 H172 报告表格的一行（`docs/handover/reports/H172.md:100`）：它说 `--gct` 会落到
`!mainModule->loaded()` 并"退出 1，诊断到 stdout"。实测与代码都不是：`--gct` 只调
`compile(GCT)`，随后在 dump 块末尾 `return 0`，根本走不到 run/check 的 loaded 闸门。

## 3. 修复

### 3.1 `inspect`：在第一次 dump 之前问一次

`tools/camel-cli/main.cpp:386-399`：编译块结束后、`if (Inspect::dumpGCT ...)` 之前，统一调用
`camel_cli::failIfModuleErrors(...)`；有错误就 dump 诊断、`return 1`，一个字节的 dump 都不打印。
`--ops` 因为列表占着 stdout，诊断与"哪个声明模块、哪个文件"走 stderr（H172 的契约），也不打印
`compileSummary`；其余 dump 的诊断仍走 stdout 并打印 `compileSummary(false)`。原 394-403 的旧闸门
（只覆盖 GIR/TNS/Instances/Facts/Tags，且在 `--gct` 打印之后）删除——它正是组合 dump 先打树的
原因。

这个位置也是"新增路径不容易忘"的结构保证：**任何以后加进 `inspect` dump 块的输出都自动在闸门
之后**，不可能在失败时先打印。

### 3.2 `--ops` 的装载后再问一次

`main.cpp:447-459`：`module->load()` 循环之后再次调用同一个 helper。编译阶段没装载的导入模块
（程序没用到的 import）在这里装载，声明文件失败只能在这一刻发现；H172 的行内扫描（遍历
`allUserModules()`、收集 `declarationModule()`、手写 stderr 行）整段删除，行为不变。

### 3.3 run / check / `--timeit` 用同一个判断

`main.cpp:465-468`（run/check）与 `timeit.cpp:472`：`!mainModule->loaded()` 换成
`findModuleFailures(...).any`。对 Done 路径两者等价（编译失败必有诊断），但新判断说的是
"有错"，不是"没到 Done"；`--gct` 这种故意停在中间阶段的路径不会被误判。

### 3.4 三个用法错误

`tools/camel-cli/config.cpp:871`、`:1000`、`:1010`：在 `return false` 前置 `exitCode = 1`。
（`config.cpp` 里其余用法错误本来就置 1 或 `std::exit(1)`；这三处是漏网。）错误文本没动，
脚本仍能按文本匹配。

### 3.5 文档（`docs/cli.md`）

- inspect 段：`--gct` 纳入"构建失败就报诊断、不 dump"规则，并写明"`--gct` 停在构造树，只有
  后续图阶段才会发现的错误不抑制它"；`--tok`/`--cst`/`--ast`/`--gen` 明说只读解析树、语义错误
  可以退出 0。
- `--timeit` 条目：编译失败是失败的一轮，报诊断、不记时间、不打汇总、退出 1。
- 开头：不能执行的命令行（未知选项、非法值、`--timeit`+`--profile`、缺输入）报 stderr、退出 1。

## 4. 共用的"有错吗" helper

`tools/camel-cli/module_failures.h` / `.cpp`：

```cpp
struct ModuleFailures {
    bool any = false;
    std::vector<const camel::core::module::UserDefinedModule *> declarationModules;
};
ModuleFailures findModuleFailures(const camel::core::context::context_ptr_t &ctx);
void reportModuleFailures(const camel::core::context::context_ptr_t &ctx,
    const ModuleFailures &failures, std::ostream &diagnosticsOut, bool json,
    std::ostream *declarationFilesOut = nullptr, bool wrapInArray = true);
bool failIfModuleErrors(const camel::core::context::context_ptr_t &ctx,
    std::ostream &diagnosticsOut, bool json,
    std::ostream *declarationFilesOut = nullptr, bool wrapInArray = true);
```

`findModuleFailures` 遍历 `ctx->allUserModules()`（主模块 + 所有导入的 `UserDefinedModule`，
不含 builtin），任一模块 `diagnostics()->hasErrors()` 即 `any = true`，并把
`declarationModule()` 非空的模块收进 `declarationModules`。`reportModuleFailures` 先按需打印
`camel: the declaration module '<name>' failed to load from '<path>'`，再
`ctx->dumpAllModuleDiagnostics(...)`。`failIfModuleErrors` = 查 + 报 + 返回 bool。

为什么不是 `loaded()`：`--gct` 成功时 `loaded()` 也是 false（它只到 GCT，设计如此）；`--ops`
在编译后还可能装载新模块，主模块的 `loaded()` 不覆盖它们。而"编译返回 false"的每个出口前，
`src/core/module/userdef.cpp` 都往某个模块的 `Diagnostics` 里写了错误——所以"任一用户模块有错误
诊断"才是所有路径共同的真相，`loaded()` 只是恰好在 Done 路径上同义的代理。`allUserModules()`
包含主模块，因此 run/check 的失败仍然被这个判断覆盖。
