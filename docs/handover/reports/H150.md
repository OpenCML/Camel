# H150：调试器在 `std::opt` 期间把规则库当成被调试程序；`dap_pipeline` 的收尾竞态

日期：2026-10-22
分支：`handover/H150-dap-protocol`，自 `origin/develop` 的 `913f71d2a`。
代码提交：见本报告之后的提交；报告与看板行在同一条后续提交里。

## 0. 结论

- `debugger.dap_protocol` 的 4 条失败不是 `std::opt` 改错了图，也不是期望陈旧：调试器把 `std::opt` 代数步**为规则库自己执行**的那段程序当成了被调试程序，索引了一次 `stdlib/rules.cml` 的运行，于是 `calls.cml` 的每个断点都被标成“没在运行的图里”，真正的程序开始时也不再重新解析。`calls.cml` 第 16、17 行的 origin 在优化后的图里都还在（§2.2），所以“第 16 行只剩常量、第 17 行还能停”这两条期望是对的，**没有改**。
- 修复用“只有调度遍才是在跑程序”这一事实：`ExecutionObserver` 新增 `passStarting(schedules, root)`，`applyPassesDetailed` 在每遍开始前通知；调试器只在调度遍里保留帧、索引运行，改写/翻译遍（`std::opt` 的规则库、宏的函数）执行什么都不算程序的运行。
- 修 `dap_protocol` 的过程中把 `dap_pipeline` 的“负载间歇”也定位成了真竞态：适配器收到 `finished` 就杀 worker，而让程序跑完的那条命令（`continue`、`nextPass`）的 HTTP 回答可能还在 worker 的服务器线程上没写完，客户端于是收到“被调试程序已经结束”。在 24 个忙循环的负载下 100 次里红 7 次；用 `workerCallMutex_` 把“杀 worker”和“在途命令”串起来后 120/120 绿。
- 验收：`debugger.dap_protocol` 与 `debugger.dap_pipeline` 在**连续五次**完整计划运行里全绿（§4.1），`feat/opt` 710/710，`feat/tools` 除既有基线红 `lsp.editing` 外全绿。

## 1. 复现：四条失败断言原文

`debugger.dap_protocol` 是 `tier="slow"` 的用例，目录运行会跳过它，必须点名计划文件。单独运行主机上的 `out/latest/bin/camel-db` 后：

```
FAILED: opt: the folded sum loses its breakpoint with the constant-only reason
    ... "id": 2, "line": 16, "message": "The code on this line is not in the graph that runs: a pass removed or replaced it.", "reason": "failed", "verified": false ...
FAILED: opt: the surviving effect stops at its source line
    expected 17
    actual   undefined
FAILED: opt: only the surviving breakpoint is hit
    expected [3]
    actual   undefined
FAILED: the test threw: TypeError: Cannot read properties of null (reading 'top')
    at .../dap_protocol.test.mjs:230:49
4 of 80 checks failed
```

即：第 16 行本应是 `ConstantOnly`（“只定义常量”），实际是“被某一遍删掉或换掉”；第 17 行的 `println` 本应停住，实际根本没有 `stopped` 事件，后面的 `waitStop()` 返回 `null`，取 `stop.top` 时抛出。

场景（`dap_protocol.test.mjs` 的 `opt` 段）：以 `['std::opt', 'std::fvm']` 运行 `calls.cml`，在 `let a = double(x)`（14 行）、`let c = a + b`（16 行）、`println(c)`（17 行）设行断点。

## 2. 原因与证据

### 2.1 观察者看到的第一段执行不是 `calls.cml`

`DebugCore` 在 `beginRun` 装上 `ExecutionObserver`，它对**这次运行里所有 VM 执行**都会回调，包括各遍自己发起的执行。临时插桩（已删）打印每次 `firstNodeOfRun` 看到的东西，`std::opt` 段得到：

```
[probe] running root=__root__ payload=1 program=0x... graphs=283 lines=223
[probe] graph rules::simplifyWith ...
[probe] graph rules::int_add_zero ...
[probe] current program ... same=0
```

223 条 line 的源文件全是安装里的 `stdlib/rules.cml`，图名是 `rules::simplify`、`rules::simplifyWith`、`rules::int_add_zero` 等；`programOfRuntimeGraph(root)` 与 `currentRuntimeProgram()` 比较为 `same=0`。也就是说 `std::opt` 的代数步在同一个 context 里执行了**规则库模块自己的程序**（`modules/rewrite/module.cpp` 用 `NodeVMSchedPass::callGraph(maker->program(), ...)` 跑规则）。

原来的 `DebugCore` 把这段执行当成运行开始：`firstNodeOfRun` 用 `rules.cml` 的根索引，`reverifyAll()` 把 `calls.cml` 的断点全部判成 `Removed`/`ConstantOnly`；`runIndexed_` 从此为真，等真正的 `std::fvm` 开始跑 `calls.cml` 时不会再用它的根索引一次，断点也就永远不会再解析回来。结果是 §1 的“第 16 行被某一遍删掉”和“第 17 行不停”。

这也解释了为什么 H112 的 `commitChecked`/`mayPublish_` 与“`std::opt` 移动 origin”都是误导：`std::opt` 没有把它们挪走（下一节），调试器只是看错了程序。

### 2.2 `std::opt` 之后第 16、17 行的 origin 还在

用 `std::jgir` 看优化后的图（`camel calls.cml std::opt std::jgir`），`calls.cml` 仍有：

```
DATA "10"        origin 179   file calls.cml line 16   （原 `a + b` 的 span）
:io/println ...  origin 181   file calls.cml line 17
```

第 16 行是折叠后的常量（`ConstantOnly` 成立），第 17 行是保留下来的效果（可执行、可停）。所以用例的两条期望是**正确的**；按任务书，这种情况不改期望。

### 2.3 `dap_pipeline` 的间歇是适配器杀 worker 的竞态，不是超时

`dap_pipeline` 在门禁里偶尔红（H147 §3.4、`store-and-rules.md` 都记过“负载下”），原输出只有 `expected exit 0, got 1`。在 24 个忙循环下跑 100 次，红 7 次，其中 5 次是同一条检查：

```
FAILED: step a consuming translation pass
    stepped: { "success": false, "message": "The program being debugged has ended." }
FAILED: continue runtime
```

`camel/nextPass` 与 `continue` 都是“让程序继续跑”的命令。适配器收到 worker 的 `finished` 事件后立刻 `killWorker()`；而这两条命令的 HTTP 回答是 worker 的服务器线程写的，程序线程同时往下跑、跑完、发 `finished`。负载大时 `kill` 先到，回答被截断，`core()` 的 POST 失败，适配器就回“已经被调试程序结束”——尽管命令其实成功了。这与“等一个协议保证的事件”无关，是适配器自己的收尾顺序问题。

## 3. 修改

### 3.1 调试器只观察调度遍（`dap_protocol`）

- `include/camel/execute/observer.h`：`ExecutionObserver` 新增带默认空实现的
  `virtual void passStarting(bool schedules, runtime::GCGraph *root)`。
- `src/execute/pass.cpp`：`applyPassesDetailed` 在创建每一遍之后、`apply` 之前，用已有的
  `dynamic_cast<GraphSchedulePass *>` 结果通知观察者（同一个 `schedules` 也用于原来的
  stage 名与入口参数检查，没有第二次转换）。
- `tools/debugger/src/core/debug_core.{h,cpp}`：`DebugCore::passStarting` 记 `observingRun_`；
  只有调度遍把它置真，并清空 `stack_`/`activationBase_`、把 `runIndexed_` 置假，让该遍的第一个
  节点重新索引它真正拿到的程序。`beforeNode`/`beforeInstruction` 在 `!observingRun_` 时直接返回：
  改写/翻译遍执行的图不产生帧、不索引运行、不触发断点重算。
- `beginRun` 把 `observingRun_` 复位。

这样“改写遍为自己执行”与“调度遍执行被调试程序”由流水线的事实区分，不依赖“当前 program 指针是否相等”这类代理判断；宏展开遍执行用户函数时也不会再被当成运行。

### 3.2 让收尾杀掉 worker 之前先等在途命令（`dap_pipeline`）

`tools/debugger/src/dap/adapter.cpp`：新增 `workerCallMutex_`，`core()` 在整个 POST 与其回答期间持有；`coreEvent("finished")` 在 `killWorker()` 前取同一把锁。于是 `continue`/`nextPass` 的回答一定先落地，worker 才被杀。没有加大任何超时。

### 3.3 用例加的守卫

- `dap_protocol.test.mjs` 的 `opt` 段：在拿到 `stopped` 之后断言“存活断点（id 3）从未收到
  `verified:false` 的 `breakpoint` 事件”。这正是本缺陷的失败面：在旧实现里三个断点都会在规则库
  运行后被撤回，这条会红；如果第 17 行该停却没停，后面的 `waitStop`/`hitBreakpointIds` 仍然会红。
- `dap_pipeline.test.mjs`：把 `camel/nextPass` 的回答与边界一起作为失败详情打印，下次再红能直接
  看到原因，而不是只有 `expected exit 0, got 1`。

`std::opt` 的源码、规则库、golden 与期望一处未动。
