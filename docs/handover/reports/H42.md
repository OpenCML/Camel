## 机制：一张表为什么是进程级共享的

旧实现里每个 `Module` 对象有一张 `exportedEntityNS_`。实体是"程序造出来的东西"：

- 写：`Builder::exportDeclarations` 写函数图集、泛型模板、顶层值节点、tag；
  `Builder::exportOperatorOverloads` 写算子组与 `group#k`；`Module::exportType` 在 GCT 写
  类型（这一项与程序无关，见下）。
- 读：`Module::getImportedEntity`（按导入层合并，带 per-module 缓存）、
  `getExportedEntity`（`compileAsProgram` 入口、`DefinitionStore::build`）、
  `exportedEntityNS`（语义分析的命名空间列表、`introspect` 的算子描述）、
  `importedOperatorOverloads`/`exportedOperatorOverloads`、
  `importAllRefsFromMod`/`importAllRefsFromImportedNamespace`、
  `reportImportNameConflicts`。

`Module` 对象按 `Context` 缓存，主程序和每个 `compileAsProgram` 的 pass 程序共用同一个对象，
于是这张表被几个程序共用。设计原则 10.1 说全程序只有一张 `__root__`，各模块顶层的节点都在
上面，函数经捕获端口取值，捕获按「模块 + 名字」绑定：导出实体（一个函数的图、一个顶层值节点、
一个模板）是某个程序 `__root__` 上的东西，本来就不该属于模块对象。

在旧实现下会坏的场景（不只是理论）：

1. 同一个 `Context` 上"主程序 + 一个 Camel pass 程序"同时活着（`camel x.cml m::pass`）：
   两个程序声明同一个模块时，第二个声明被当作重名拒绝；`compileAsProgram` 用
   `clearExportedNamespaces` 绕开，代价是把第一个程序的图从表里抹掉——第一个程序错用第二个
   程序造出来的图（H37 评审问题 2 记的就是这个）。
2. 同一个模块作为两个 pass 的导入（新用例 `two_camel_passes_share_a_module`）：第二个 pass
   清表再导出，第一个 pass 的表内容和它已经编好的图不再对应。
3. 宿主在一个 `Context` 上运行两次程序 / 重新加载：第二次会看到第一次留下的名字（同名被拒），
   清表又会抹掉还在用的图。
4. 两个引擎各一个 `Context`：这条路径本来就不共享（`Module` 按 `Context` 缓存），不是 H42
   的问题；可表达的失败是第 1、2、3 条，都在一个 `Context` 内。

## 做的时候发现的问题：模块被标成 Done，主程序不再声明它

把表改成 per-program 后，`pass_module_imported_by_the_program` 失败（46/47）：

```
error[SemanticDiag::ImportNameNotExported]: Reference 'bump' is declared as imported but is not
exported by its module.
```

插桩确认有两个不同的 `ProgramExports`：pass 程序（`sharedvals::run`）的表里有
`sharedvals::bump`、`twice`，主程序的表里没有；主程序在 `ImportNameNotExported` 处查的是
自己的表。

原因是 `compileAsProgram` 在两个地方把模块标成 `Done`（并把 `loaded_` 置真）：
`setProgramGraph` 的 `buildingProgramOfItsOwn_` 分支，和 `compileAsProgram` 结尾。模块的
`stage_` 是模块对象上的，主程序之后 `sharedvals->compile(Declared)` 看到 `till <= stage_` 直接
返回，于是没有把 `sharedvals` 声明进主程序的表。旧实现里这被"表在模块上"掩盖了：主程序
虽然没声明，却仍能读到 pass 程序留下的名字（这正是 H42 要消除的串用）。

修法：程序自己的构建不再把模块标成 `Done`/`loaded_`；模块的前端阶段（parse、GCT）仍然共享，
再声明一次只是把它的名字写进另一个程序的表（图是那个程序的 builder 造的）。`stage_` 的跨程序
含义见"未做"与"开放问题"。

## 决定

- **类型留在 `Module`。** 类型声明在 GCT 建一次，与程序无关，且互相导入的模块在任何一个程序的
  builder 声明它之前就要能查类型（`getImportedType`/`declareTypes`）。所以
  `exportedTypeNS_` 不动；`exportDeclarations` 里"把本地类型再导出一次"的分支删掉——GCT 已经
  `Module::exportType` 过了（`GCT::Builder` 对 `export` 列表里的类型当场导出）。
- **C++ 模块的 native 实体留在 `Module`。** 算子组、常量、tag 是模块加载时写一次的，与程序
  无关；`ProgramExports::exportedEntity` 在程序表没有该名字时回退到 `getNativeEntity`，
  `forEachExportedEntity` 先程序名、后未被遮蔽的 native 名。内建模块（`importModule("")`）的
  算子查找仍直接读模块。
- **缓存跟着表走。** 合并结果按 (importer, 名字, 层) 缓存在 `ProgramExports::imported_`，任何
  `exportEntity` 写入都整表清空（装饰形式的导出发生在函数体建好之后，早先缓存的合并结果必须
  作废）。import binding 的记录仍只在 GCT 发生，声明/建体阶段的查询在 binding 完整之后，因此
  不需要从 `Module` 反过来清各程序的缓存。
- **`compileAsProgram` 的入口查找用新 builder 的表**（`builder->exports().exportedEntity`），
  不再读模块的表；`DefinitionStore` 的库函数查 Context 的表（`compileAsLibrary` 把库声明进
  Context 的程序）。
- **`importAllRefsFromImportedNamespace` 删除。** 它在 `03d1c77b` 已经没有任何调用者，且实现
  依赖模块级的 `exportedEntityNS`；留着只会误导。
- **`isTheProgramBeingCompiled()` 删除。** 两个 `stage_ = Done` 的例外都去掉了，这个判断没有
  使用者。
- **`ProgramExports` 放在 `module.cpp`**，不新增源文件：它是 `Module` 的伴生类型，实现与
  `Module` 的导入解析相邻。
- 历史报告/评审里对 `clearExportedNamespaces` 的描述不改：那是当时状态的记录，不是现行文档。

## 没做，以及为什么

- **没有把 `Module::stage_` 改成按程序记录。** 只去掉了 `compileAsProgram` 的两处 `Done`：前端
  阶段（parse、GCT）本来就是模块共享的，`declare` 现在每个程序各做一次。更彻底的做法是让
  `stage_` 只表示前端、把"声明/建体"完全移到程序侧状态；那会动 `compile` 的状态机，超出
  "导出表 per-program"这一项，留给后续。
- **没有为"宿主在同一 Context 上连续跑两个程序"加用例。** 现在 CLI 一个 Context 一个程序，
  可表达的是同一条 pipeline 的多个程序（新用例覆盖）；同一 Context 复用两次没有现成入口，
  见开放问题。
- **没有把 C++ 模块的 native 表并入 `ProgramExports`。** native 名字与程序无关，且内建模块
  查找直接读模块；并进去只会多一层间接。
- **没有改历史报告。** H36/H36b/H37/H38 与评审文档里"模块导出表"的描述保持原样。
- **没有新增诊断。** 行为不变：同样的导入解析顺序、同样的合并规则、同样的算子重载顺序。

## 开放问题

1. 宿主若复用同一个 `Context` 依次编译两个程序，`Context::programExports()` 与 Context 同寿命，
   第二个程序会看到第一个程序留下的名字（同名 insert 被拒，被当成"已导出"）。要支持需要
   定义"程序开始"的时点并重建表；现在没有这样的入口，CLI 也不走这条路径。
2. `ProgramExports::imported_` 在 import binding 变化时不再由 `Module` 失效（`Module` 不知道有
   哪些程序的表）。当前顺序（GCT 记完 import，之后才 declare/build）下安全；若将来允许"声明
   后补记 import"，需要显式的失效入口（例如由 Builder 在 markImported 后清自己的表）。
3. `UserDefinedModule::loaded_` 现在不再表示"这个模块的某个程序已经建好"（`compileAsProgram`
   之后停在 GCT/Declared）。语义分析对 `UserDefinedModule` 不走 `loaded()` 判断，暂时无影响；
   若以后有读者按 `loaded()` 判断"图可用"，需要改成按程序判断。
4. `forEachExportedEntity` 用 `Reference::toString` 的集合去重程序名与 native 名。对
   "程序名遮蔽同名 native 名"够用；如果将来 namespace 前缀与实体名混在同一张表里要求更细的
   合并，这个去重需要结构化。
