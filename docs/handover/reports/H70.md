## 1. 用例

```camel
func spin(n: int): int {
    return if n <= 0 then 1 else spin(n - 1)
}

func walk(n: int, k: int): int {
    let a = k % 97
    let b = a * 3 + 10
    let c = b % 89
    let d = c * 7 - 5
    let e = d % 83
    return if n <= 0 then k else walk(n - 1, e) + spin(k % 2)
}

func tick(k: int): int { return k * 7 + 1 }

func main(): int sync {
    var k = 5
    let p = walk(6, k)
    let q = walk(4, k)
    let t = tick(1) + tick(2) + tick(3)
    println(p)  // 87
    println(q)  // 16
    println(t)  // 45
    return 0
}
```

每一部分都是为这条性质服务的，换掉就会变味：

- **`n` 驱动展开**：每份 `walk` 副本里 `walk(n - 1, e)` 的 `n` 是常量，下一轮把它绑成字面量，于是副本
  连成 `walk(6) → walk(5) → walk(4) → …` 的链。链是"后来某一轮会再次请求前面某一份"的来源。
- **第二个参数来自单元（cell）**：`var k` 的读是读单元，前端不折叠，所以 `k` 上的算术留在图里，
  副本不会小到被折叠掉；同时 `walk(6, k)` 只绑 `n` 一个形参（`k` 不是常量），键是"被调图 + n 的值"。
- **`spin(k % 2)` 是锚**：`k % 2` 不是常量，这个调用永远不会被特化，因此每份 `walk` 副本里都留着一条
  指向递归函数（`spin`）的调用。于是副本"到达递归"，SCC 分析给出 `acyclic = false`，内联器不把它
  内联进调用者——这才是它在后面几轮里**仍然从根可达**的原因。若副本的链不再到达任何递归（例如把
  `spin` 去掉、只留 `walk(n - 1, e)`），链会逐轮"降温"：最底下的副本先被内联，上一层再被内联，
  最后全部沉进 `main`，条目按 H44c 的规则随图一起失效——那就退回 `simplify_growth_budget` 那种
  "造一份、死一份"的形态，锁不住表的用处。运行期 `k % 2` 只取 0/1，`spin` 至多递归一步，不会加深。
- **常量两两不同**：`cse` 会合并相同的常量；一旦它改写了 `walk` 本身，`walk` 的 `revision` 就变了，
  为它造的条目会在提交时因"被调图不是条目记的那一版"全部失效。第一版用例的常量用了两个 `1`，
  实测 `revision` 从 2 跳到 15，第一轮的条目全部被删，于是 `walk(4)` 又被造了一份（多出 `spec6`）。
  现在 `97/3/10/89/7/5/83` 各出现一次，`walk` 的 `revision` 全程是 3。
- **`tick` 是另一侧**：三次常量调用在造出副本的那一轮就被内联进 `main`，提交时闭包不再持有那三张图，
  `graph(id) == nullptr`，条目被删。表的计数因此不随"造过又死掉"的副本增长。

## 2. 为什么这条特化跨轮仍可达（实测）

`std::opt` 在本用例上跑了 13 轮（13 次 rewrite 会话）。为了看清"造/取回/删"，在本地临时加了 4 行
`CAMEL_LOG_INFO_S` 的构建（**未入树**，见第 5 节），`-vv` 下的顺序是：

```
[NEW]   base='walk' rev=3 bindings=1 -> 'walk$spec0'  nonce=0   // 第一轮：main 的 walk(6)
[NEW]   base='walk' rev=3 bindings=1 -> 'walk$spec1'  nonce=1   // 第一轮：main 的 walk(4)
[NEW]   base='tick' rev=4 bindings=1 -> 'tick$spec2'  nonce=2   // 第一轮：tick(1/2/3)
[NEW]   base='tick' rev=4 bindings=1 -> 'tick$spec3'  nonce=3
[NEW]   base='tick' rev=4 bindings=1 -> 'tick$spec4'  nonce=4
        （本轮提交：tick 的三张图已不在闭包里，三条条目被删）
[NEW]   base='walk' rev=3 bindings=1 -> 'walk$spec6'  nonce=6   // 后面的轮次
[NEW]   base='walk' rev=3 bindings=1 -> 'walk$spec7'  nonce=7   // walk(6) 副本要 walk(5)
[NEW]   base='walk' rev=3 bindings=1 -> 'walk$spec8'  nonce=8
[REUSE] base='walk' rev=3 bindings=1 -> 'walk$spec1'            // walk(5) 副本要 walk(4)：取回第一轮那份
[NEW]   base='walk' rev=3 bindings=1 -> 'walk$spec10' nonce=10  // walk(3) 副本要 walk(2)
[NEW]   base='walk' rev=3 bindings=1 -> 'walk$spec11' nonce=11  // walk(1) 副本要 walk(0)
        （walk(0) 副本的体只剩 `return k`，被内联进 walk(1) 副本；它的 1 节点图由内联区域
         引用着，仍由程序持有，条目留下）
```

要点：

1. **`[REUSE]` 不是会话内缓存命中**。`walk$spec1` 是第一轮造的；发起请求的 `walk$spec7` 是后面轮次
   造的（它的 nonce 是 7，前面的 `tick$spec2/3/4` 已经提交并删除过）。取回靠的是 `Program` 上的表：
   键 `(walk 的 GraphId, revision 3, {n: 4})` 命中，返回 `GraphId`，`work_->graph(id)` 还在，
   `walk$spec1` 也被程序持有、被 `main` 调用。
2. **条目留下的条件**（`draft_session.cpp` 提交末尾）：程序还持有那张特化图，且被调图仍是条目记的那一版
   （`id` 与 `revision` 都对）。本用例里 7 份 `walk` 副本都从根可达，所以 7 条都留下；`tick` 的三张图
   不在闭包里，三条都被删。
3. **名字有空号**（`spec2/3/4` 是 `tick` 的，`spec5`、`spec9` 是别的带绑定请求消耗掉的 nonce）：
   nonce 每次"带绑定的特化请求"都会消耗（H44c 已说明，闭包去虚拟化也走这条路），所以断言只能写
   "集合恰好是这 7 个"，不能写连续编号。

## 3. 三种设计下的数字

同一用例、`std::opt std::stats std::jgir`：

| 设计 | `specializations`（表条数） | 可达的 `walk$` 副本 | 程序形态 |
|---|---|---|---|
| **当前**：程序级表 + 提交时裁剪 + 跨轮复用 | **7** | **7** | **12 图 174 节点** |
| 表随会话（查表看不到上一轮的条目） | 7 | 12 | 17 图 254 节点 |
| 表钉住它点名的图（H44b 的形态） | 10 | 7 | 12 图 174 节点 |

- **表随会话**：`walk$spec7` 的 `walk(4)` 请求看不到第一轮的表，于是再造一份；它的链在随后几轮里
  继续请求 `3/2/1/0`，每层都再造一份——多出 5 份副本（`spec9/12/13/14/15`），图从 12 张涨到 17 张、
  节点 174 → 254，而表条数仍是 7（键相同，后写的覆盖先写的）。所以**"表条数"单独看不出会话级表**，
  必须同时断言"可达副本数 / 图数"。
- **钉住**：`tick` 的三条条目不再随图删除，表报 10；程序形态不变（钉住的图从根不可达，不进入
  `graphs`/`nodes` 的统计，H44b 的 fib 也是这样：20 条、7 图 425 节点）。所以**"表条数"单独也看不出
  钉住**，7 vs 10 正是这条用例的另一半。
- 三种数字都来自实测：后两种是把 `findSpecialization` 的程序表查找临时短路、把提交裁剪临时改成
  "图没了也保留"，各重建一次跑出来的；这些开关没有进树（见第 5 节）。

## 4. 回归会读到什么

- 谁把表改回"跟着会话走"：`specializations` 仍是 7，但 `walk$` 副本变成 12、图 17、节点 254，
  断言直接红；`walk$spec7` 的 `FUNC` 也不再指向 `walk$spec1`。
- 谁把提交改成钉住（H44b 那种）：`specializations` 变 10，第一条断言红。
- 谁让副本的链不再到达递归（比如删掉 `spin` 调用、或把它变成常量调用）：副本会被逐轮内联、条目逐轮
  失效，`walk$spec7 → walk$spec1` 这条边和 7 份副本的集合都会变，红。
- 谁让 `cse` 改写 `walk` 本身（例如再引入重复常量）：`revision` 变化，第一轮的条目被删，
  `walk(4)` 会被再造一份，副本数与名字都会变，红。
- 最容易被误判成"只是为了凑数字"的：`tick`。它不是装饰——它让"条目该死的时候会死"出现在同一个
  用例里，否则 7 vs 10 那一半没有证据。
