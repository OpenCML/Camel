## 1. 复合字面量作实参进入形参类型

### 问题

重载解析的"进入"规则（`src/compile/gir/builder_operators.cpp` 的 `enteringTypes`）只让数字字面量按值进入形参类型；数组 / 结构体字面量在 GCT 里已经落成 `float[]`、`{ x: float }`，与 `f32[]`、`{ x: f32 }` 不相等，于是

```camel
func pick(xs: f32[]): f32 { return xs[0] }
pick([1.0])
```

报 `NoMatchingFunction`（`argument types: <> (float[])`）。同一缺陷出现在三处，共用一个判断：

1. **普通调用、方法式调用、`with` 实参**：都走 `enteringTypes`。`norm({ x: 1.0, y: 2.0 })`（结构体形参）、`[2.5]->pick`、`at<[7.0, 8.0]>(1)` 同样被拒。
2. **程序自己声明的运算符**：`chooseOperatorOverload` 用 `accepts(funcType, true)`（也就是 `enteringTypes`）判断非泛型重载，`genericOperatorAccepts` 判断泛型模板；两边都只看 `entersImplicitly`。
3. **泛型实例化**：`resolveGenericCall` 在类型变量绑定之后，对每个实参再查一次 `entersImplicitly`；`join(xs, [2.0])`（`T` 已由 `xs` 定为 `f32`）的 `[2.0]` 在这里被拒。

### 改动

- **新增"能不能进入"的判断**（`src/compile/gir/builder_control.cpp`、`builder.h`）：`Builder::compositeLiteralEntersIn(node, target, origin)`，以及匿名命名空间里的 `compositeEntersIn` / `elementEntersIn`。它与 `compositeDataInType` 走同一条路——数组逐元素、结构体逐字段（字段数必须相同、名字必须在）、tagged 类型永不进入、只认静态 `Data` 节点（`dataIndex < 0`，运行时槽不是字面量常量）、元素值取 `Tree::literalElementsOf` 记下的**写下的精确值**——但不建数据、不报错。注释写明两者必须一致：探测接受的，转换一定接得住；转换报的错就是唯一的错。
- **`enteringTypes`**：原来只判"数字字面量的值能进入"，之后加一条复合字面量的探测；命中就把该实参记为形参类型。精确优先的那一遍（`accepts(f, false)`）不变，所以既有"精确重载先赢"的选择不变。
- **`genericOperatorAccepts`**：签名增加 `const std::vector<Argument> &normInputs`，逐个实参先 `entersImplicitly`，否则用同一个探测；调用处（`chooseOperatorOverload`）传入 `normInputs`。这样程序声明的泛型运算符（如 `func operator -(a: (typeas T)[], b: T[]): T[]`）也认复合字面量操作数。
- **`resolveGenericCall`**：类型变量绑定完成后的最后一次检查，`entersImplicitly` 不成立时先探测复合字面量；成立就 `coerceTo` 转换成形参类型、更新 `inputAt(i).node` 与 `typeAt(i)` 后继续，不成立才走原来的 `reject("... is '...' here (...)")`。转换只在这里做一次，报错也在这里报。
- **转换本身没有改**：仍然只在被调函数确定之后发生（普通调用在 `enterParameters` 的 `enter` 里对每个实参 `coerceTo`；泛型在 `resolveGenericCall` 里；泛型运算符先由模板选中、再走 `resolveGenericCall`）。`coerceTo` → `compositeLiteralInType` → `compositeDataInType` → `literalElementInType` 用 `literalElementsOf` 的精确值逐元素重建（H27 的基础设施），实参位置因此与声明、返回位置一样"只舍入一次"。

### 为什么探测与转换分开

重载解析要对每个候选问"接受不接受"，此时还没有被选中的被调函数。若在探测时就转换，会对每个候选各建一遍数据，而且候选不该被选中时也会报出本不该报的错（例如另一个候选才该赢时的越界元素）。所以探测只回答"形状与种类能不能进"，值的范围留给 `coerceTo`：**放不进目标类型的元素仍算"进"**，转换时才报 `LiteralNotRepresentable`——不会退化成 `NoMatchingFunction`。反过来，写成名字的元素（`pick([n])`，`n: int`）、别的种类的元素（`pick(['a'])`）不进入：名字是变量，变量永不转换；这与 5.1 一致。

### 精确值的锁定

`test/cases/compile/literals/context_composite_argument.cml` 里，`1.0000000596046447753906251`（比 1.0 与下一个 f32 的中点大一点点）作为数组元素与结构体字段各出现一次，`{:.9g}` 都打印 `1.00000012`，不是 `1.0`。这与 H27 的 `context.composite_rounding` 是同一个十进制；区别只在这次字面量写在**实参**位置，类型由形参给出。

### 诊断的位置与引用文本

实参位置的转换发生在 GIR，手上只有整个字面量的 GCT 节点：`LiteralNotRepresentable` 指向字面量的开头（`[` / `{`），消息引用的是出错元素的**精确值文本**（`'3000000000'`、`'1e+40'`），因为 GCT 的 `literalElements_` 只记值、不记元素的位置与源码文本。声明位置仍由 GCT 的 `literalNodeInType` 报在元素上、引用源码写法（H24 的 `context.array_element_out_of_range` 仍是 8:25）。这是本次没有改动的差异，见第 5 节。

## 5. 未决

1. **实参位置的元素诊断**：GIR 只有整个字面量的位置，`LiteralNotRepresentable` 因此指向 `[` / `{`，消息引用精确值的规范文本而不是元素在源码里的写法（`1e40` 显示为 `1e+40`）。要让实参位置也像声明位置那样指到元素、引用源码写法，得让 GCT 在 `literalElements_` 旁边记下每个元素的位置（或文本），再传给 `compositeDataInType`。本次没做（会改动诊断位置，属于新的口径），记录在这里。
2. **`f<w>` 作值（部分应用）仍不转换上下文实参**：`let g = at<[7.0, 8.0]>` 被 `partialApplicationOf` 拒（`PartialApplicationRefused`，说 `<float[]>` 不能绑定到 `<xs: f32[]>`）；标量也一直如此（`with <k: f32>` 下 `scale<2>` 被拒，`scale<0.5>` 可以）。在调用处写 `at<[7.0, 8.0]>(1)` 是好的。`f<w>` 作为值要不要对上下文实参做同样的进入与转换（以及标量顺带），是一个独立的问题，没有擅自决定。
3. **内建 / C++ 模块算子的实参**：按设计原则 5.1 的未决项 `entering-operator-args`，内建算子的形参类型由 C++ 的类型规则从实参算出、调用前没有目标类型，因此 `len([])` 仍是元素类型不定的 `[]`、`xs->append<5>` 仍要写 `5 as int?`。代码里原有的 `DESIGN-QUESTION(entering-operator-args)` 原样保留，本次只改程序自己声明的重载与泛型模板。
4. **管道调用带额外实参**（既有缺陷，与本次无关）：设计原则 4.4 写 `x->f(a, b)` 即 `f(x, a, b)`，现在 `1->add(2)`（`add(a: int, b: int)`）被降成 `add(2)(1)` 并报 `NoMatchingFunction`。`[2.5]->pick`（不带额外实参）不受影响，本次的用例用的是这种写法。
5. H27 报告第 8 节的两条遗留由本报告关闭；H27 / H24 等历史报告按任务书保持历史口径，未改。
