# H68 报告

分支 `handover/H68-operid`，基于 `origin/develop` `9e25f2c7`。只做 H8 第 3 项：把建图器
（以及编译期其他代码）里"用字符串名引用内部算子"的地方，改为在登记时取得 `OperId` 保存、
按编号引用，行为不变。

结论：所有编译期自己发出、不可被程序重载的内部算子都改成按编号引用；`grep -rn
'Operator("__' src` 只剩两处 `applyTagOperator("__not__", ...)`，见 §3 的理由。测试：
`feat.compile.enum`／`tagged`／`tag_permissions` 88/88，`modules`+`compile`+`smoke`
1919 项 0 失败（1 跳过），整个 `feat` 层 4770 项 0 失败（11 跳过）。

## 1. 做法

### 1.1 编号

`include/camel/core/operator_table.h` 的 `namespace oper` 里，原来只有 `VarNew`、
`VarGet`、`VarPeek` 三个编译期常数编号。内部算子沿用这同一种编号（已有的先例：
pass、后端用 `body->oper == oper::VarGet` 判断），新增 17 个：

| 编号 | URI | 登记的组 |
| --- | --- | --- |
| `VarTake = 4` | `:var/take` | `__var_take__` |
| `AssnOwned = 5` | `:op/assn_owned` | `__assn_owned__` |
| `AssnAppend = 6` | `:op/assn_append` | `__assn_append__` |
| `SetField = 7` | `:op/set_field` | `__set_field__` |
| `SetIndex = 8` | `:op/set_index` | `__set_index__` |
| `TagIsNull = 9` | `:op/tag_is_null` | `__is_null__` |
| `TagNullValue = 10` | `:op/tag_null_value` | `__null_value__` |
| `TagIsError = 11` | `:op/tag_is_error` | `__is_error__` |
| `TagErrorValue = 12` | `:op/tag_error_value` | `__error_value__` |
| `TagErrorInfo = 13` | `:op/tag_error_info` | `__error_info__` |
| `TagThrow = 14` | `:op/tag_throw` | `__throw__` |
| `EnumMake = 15` | `:enum/make` | `__enum_make__` |
| `EnumTag = 16` | `:enum/tag` | `__enum_tag__` |
| `EnumField = 17` | `:enum/field` | `__enum_field__` |
| `CopyArray = 18` | `:struct/copy_arr` | `__copy_arr__` |
| `AppendOwned = 19` | `:struct/append_arr_owned` | `__append_owned__` |
| `MacroCmp = 20` | `:macro/cmp` | `__cmp__` |

`kWellKnownOperatorUris` 按同一顺序补齐。表构造时就把这些 URI intern 好（`OperId` 是
进程内编号，不落盘），所以**编号在进程启动即有效，早于任何模块加载**。

### 1.2 编号到组：登记时保存

`Module::exportEntity`（`src/core/module/module.cpp`）在把一个实体登记到模块时，若它是算子组，
就把它的每个 URI `intern` 成编号、记进 `nativeOperatorGroups_`（`OperId → oper_group_ptr_t`）；
`Module::nativeOperatorGroup(OperId)` 是查回的唯一入口。这就是 H8 报告 §3 里的第三种方案：

- 不往 `OperatorTable` 的条目里加组指针（条目仍然只描述算子：uri、pure/stateOnly/mayFault、
  规则、签名；"实现/实体由模块持有"这条现有分工不变）；
- 也不把组指针一路传进建图器（调用点分散在 4 个文件，穿透成本高）；
- 模块本来就是算子组的登记者和持有者，按编号取组正是"在登记时取得并保存"的字面做法。

初始化顺序：编号是编译期常数、表构造时 intern；**组**要等 `GlobalsBuiltinModule` 构造时
`exportEntity` 才有。每个模块（含用户模块）的构造都会 `importAllRefsFromMod(ctx->importModule(""))`
环境导入内建模块（`src/core/module/userdef.cpp`），即编译任何程序模块之前内建模块一定已经登记完，
所以这里不需要"惰性但只做一次"的形式。`Builder::internalOperatorGroup` 在查不到时 `ASSERT`
（内建模块少了编译器自己要发的算子 = 编程错误，与原来 `$builtin::` 分支的 `ASSERT` 一致）；
两个原本"缺了就跳过优化"的位置（§2 的 `__append_owned__`、`__copy_arr__`）保持返回空指针的写法，
不把可容忍的缺失变成断言。

### 1.3 从 GCT 到 GIR：编号跟着节点走

GCT 节点是 32 字节、不能再塞一个 32 位编号，所以编号放在树内旁表（和 `tagUses_`、
`literalValues_` 相同的做法）：

- `Tree::makeDRef(OperId oper, const std::string &name)`：记 `operRefs_[node] = oper`；
  **节点上的名字仍是原来的实体名**（`__enum_tag__`，不是 `:enum/tag`），所以 `inspect --gct`
  输出、引用该节点的诊断、按名字识别算子的代码（`foldLiteralCall`、`pathAssignmentOf` 等）都不变。
- `Tree::operRefOf(node)` 读回；`Tree::clone` 复制这条记录（泛型实例化、`let (p, q)` 拆分会克隆子树）。
- `Builder::visitDRefNode` 顶部加一条"有编号"分支：直接取内建模块登记的组，建 DREF，
  做和 `$builtin::` 分支相同的 `genericCalleeAllowed_ = false`、`refOrigin_`、origin 登记与
  `operatorReferenced(name, signatures)` 记录，**不再经过 `nodeAt`／`importedEntity` 的名字解析**。

## 3. 没有改的地方，每处一行理由

| 位置 | 用法 | 为什么保留名字 |
| --- | --- | --- |
| `gir/builder_enum.cpp:557` | `applyInternalOperator("__eq__", …)` | `__eq__` 是可重载组，`isOverloadableOperatorGroup` 按名字从所有层收集重载；编号只对应一个 URI |
| `gir/builder_control.cpp:1173`、`gir/builder_operators.cpp:2494` | `applyTagOperator("__not__", …)` | 同上（`!x` 用户可写、可重载） |
| `gct/builder.cpp:1923/1926/1929` | `makeDRef("__not__")`、`"__neg__"`、`"__inv__"` | 一元运算符，可重载 |
| `gir/builder_operators.cpp:852`、`:1259` | `makeDRef("__assn__")`、`"$builtin::__assn__"` | 赋值组每个类型一个 URI（`:op/assn_int` 等），按操作数类型选重载，没有单一编号 |
| `gir/builder_operators.cpp:1107`、`:1186` | `isDref(…, "__idx__")`、`makeDRef("__idx__")` | `[]`，可重载 |
| `gir/builder_control.cpp:1905` | `importedEntity("__iter__")` | `__iter__` 有多个 URI（`:struct/iter_str`、`:coll/map_items`、张量），不是单一编号；代码里有注释 |
| `gct/builder.cpp:2042` | `binaryOperatorGroup(...)` 产出 `__add__` 一类名字 | 可重载的二元组 |
| `gir/builder_literals.cpp:68-77` | 折叠用的 `__add__`…`__ge__` 名集合 | 折叠识别的是**用户写的**算子（可能被用户重载），不是编译器自己发出的算子，是另一件事 |
| `gir/builder_diagnostics.cpp:410` | `name.starts_with("__assn")` | 只是选诊断措辞（"赋值" 还是 "这个值"），读名字前缀，不查算子 |
| `gir/builder_operators.cpp:2357` 附近 | `name().starts_with("__assn")`、`oper::isVariableRead` | 判断"这是不是编译器造的赋值/读变量"，同样只看名字前缀 |
| `src/core/operator_names.cpp` | `kForms`、`kCompound`、`binaryOperatorGroup`、`displayNameOf` | 登记表本身就是"名字的唯一来源"，也是 `isOverloadableOperatorGroup` 的定义处 |
| `src/builtin/**` | `OperatorGroup::create("__enum_make__", …)` 等 | 登记处：名字在这里被登记，编号由这里产生 |
| `gir/builder_helpers.h:427` | `kBuiltinPrefix = "$builtin::"` | `$builtin::` 名字路径仍然要用于 `filter`／`map`（公开的内建算子）与 `__assn__`；这一项只改了内部算子的引用方式 |
| `gct/builder.cpp:3192/3198` | `$builtin::filter`、`$builtin::map` | 公开内建算子（用户可写 `filter(xs, f)`），不是内部算子 |

验收用的 `grep -rn 'Operator("__' src` 现在只剩上表的两处 `applyTagOperator("__not__", …)`
（`gir/builder_control.cpp:1173`、`gir/builder_operators.cpp:2494`；该模式匹配到的是
`applyTagOperator("__` 的结尾，不是 `Operator("__x__")` 构造），理由已在上表。

## 4. 行为

- **诊断、GCT 输出、导出、打印**：节点标签仍是实体名，`operatorReferenced` 记的名字、签名不变。
  `test/` 里出现的内部名字样都是**解析后的 URI**（`label=":op/tag_is_null"`，见
  `feat/compile/golden/tagged_null_then.dot`、`feat/consistency/golden/{entering,narrowing}_graph.dot`
  与 `collections.plan.toml` 的断言），不是 `__x__` 实体名；这些 golden 与断言原样通过，
  等于把"行为不变"钉住了一部分。
- **找不到算子时**：原来按名字找不到会走到"未定义的名字"或 `$builtin::` 分支的 `ASSERT`；
  现在编号路径的 `ASSERT` 覆盖同样的编程错误。内建模块是环境导入的，"内建模块缺这个算子"之外
  没有别的失败情形，所以失败方式不变。
- **唯一的语义差异**：名字路径会把环境内所有同名绑定合并（`importedEntity`），也允许程序自己
  声明 `__x__` 把它遮蔽；编号路径直接取内建模块登记的那一组。差别只出现在"程序自己声明了
  同名 `__x__`"这种病态写法上，而这正是"按编号引用内部算子"的定义所要求的（内部算子不再受
  名字解析影响）。

## 5. 测试

| `modules`、`compile`、`smoke`（74 个计划） | 1919 项，1918 通过，0 失败，1 跳过（`unicode.paths`，环境相关，基线同样跳过） |

`feat` 第一次跑时 `feat.compile.return_type` 的 `nested_return.compile_time` 失败：该用例的
`timeout_ms = 5000`（它专门测 20 层嵌套返回的编译时间），并行 8 路时跑到 5.02 s 被判超时，
报 `expected exit 0, got null`。单独跑该计划 1.33 s 通过，重跑整个 `feat` 层也通过——是负载下的
超时，与本次改动无关（这条用例不经过本项改到的任何调用点）。
