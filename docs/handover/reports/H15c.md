## 1. A format specification applies to both parts of a complex number

**The rule** (now in `docs/language/02_lexical.md` §2.5.3 and `docs/language/en/02_lexical.md` §2.5.3):

- A specification is split into its **number part** — sign, `#`, zero padding, width, `.precision`, type
  letter — and its **layout part** — fill, alignment, width. The number part writes *each part* of the
  complex value; the layout part is applied *once*, to the whole text, with the default alignment on the
  right. A `+` or space sign belongs to the real part only; the sign of the imaginary part is the
  separator between the two parts, so it is never doubled.
- `{}` (no specification) writes the plain text of H15b, `3+4i`, with no parentheses.
- Zero padding and `=` alignment are errors, as they are for a complex number in Python.
- The parts are numbers of the value's width (`f32` parts for `c64`, `f64` for `c128`), so a type letter
  that a float does not accept (`s`, `d`) is an error, and the shortest-text rule of each width applies
  when the specification does not give a precision or a type.

This is a deliberate mirror of Python: `format(3+4j, '>12.2f')` pads the whole text, it does not pad each
part.

**Interpreter.** `src/builtin/operators/complex_format.h` (new) has `LanguageComplex<T>` and a
`fmt::formatter` for it. Its `parse` keeps the raw specification text, rejects `0`-padding and `=`
alignment with `fmt::format_error` (so the compiler turns a literal one into a located
`SemanticDiag::ArgumentsRejected` at the format string), and then hands the *number part* to the base
formatter (`fmt::formatter<T>`) for validation. Its `format` writes the real part, the separator, the
magnitude of the imaginary part (formatted with the same number part, sign removed) and `i`, then pads the
whole text. The split itself is `include/camel/utils/format_spec.h` (new): `splitNumberFormatSpec` and
`padFormatText`, counting code points, so the interpreter and the standalone runtime share one rule.
`src/builtin/operators/str.cpp` pushes `LanguageComplex<Float32/64>` in `checkFormatPattern` and reads the
parts from the boxed `Complex` in `__format__`; `src/builtin/operators/io.cpp` does the same for the
`println`/`print` path.

**C++ backend.** `formatComplex` in `include/camel/standalone/format.h` reproduces the rule with the
standalone formatter: the same `splitNumberFormatSpec`/`padFormatText`, the same two error messages, each
part written by the existing `formatFloat`. A `FormatArg` gained the `Complex32`/`Complex64` kinds, and
`formatArg` classifies a `std::complex<T>` as one. The runtime checks in the C++ program are defensive:
a format string is a compile-time constant in a Camel program, so an invalid specification is always
rejected by the compiler; the generated program can never see one.

## 2. The numeric contract for the complex functions

Declared in `modules/math/semantics.cpp`, in a new `declareComplexFunctions()` (called from
`declareMathOperatorSemantics`, and the header comment now states the complex rows). `camel inspect --ops`
on `test/cases/modules/stdlib/math_functions.cml` shows them:

| URI | class | compute | ulp | permissions | not IEEE |
|---|---|---|---|---|---|
| `math:re_c` / `math:re_z` | exact | f32 / f64 | — | `finite_math` | — |
| `math:im_c` / `math:im_z` | exact | f32 / f64 | — | `finite_math` | — |
| `math:conj_c` / `math:conj_z` | exact | f32 / f64 | — | `finite_math` | — |
| `math:abs_c` / `math:abs_z` | bounded | f32 / f64 | 4 | `approx_math`, `change_precision`, `finite_math` | `nans` |
| `math:exp_c` / `math:exp_z` | bounded | f32 / f64 | 4 | `approx_math`, `change_precision`, `finite_math` | `nans` |

For example, verbatim from the inspection:

```
OPERATOR {"module":"math","name":"abs","uri":"math:abs_c",...,"semantics":{"key":"math:abs_c@1.0",
 "numeric":"bounded","compute":"f32","ulp":4,"sensitive_to":["approx_math","change_precision","finite_math"],
 "not_ieee":["nans"],"algorithm":"sqrt(re^2 + im^2) in f32 without intermediate overflow or underflow
 (hypot), within 4 ulp; an infinite part gives +inf even when the other is NaN"}}
```

**Why these classes.** The review says: `re`, `im`, `conj` exact; `abs`, `exp` "the same class as the
corresponding real function (no correct-rounding promise, error bound per platform)". Reading "the
corresponding real function" as *the function the complex one is built from*:

- `re`, `im` read one part and `conj` flips one sign bit: no arithmetic, Exact. (`finite_math` can still
  change the result: flushing a subnormal part, for instance.)
- `abs` is `hypot(re, im)` — it is **not** the real `abs` (`math:abs_f/_d`, which is Exact because it
  only clears a sign bit). `hypot` rounds, so declaring Exact would promise bit-exact `sqrt(re²+im²)`
  with intermediate scaling, which the implementation does not deliver. Bounded, 4 ulp: the same bound the
  module gives the real `hypot` (`math:hypot_f/_d`), which is the platform's accuracy.
- `exp` of a complex number is `std::exp(std::complex)` — its magnitude is the platform's `exp` and its
  direction the platform's `sin`/`cos`. It is a composition, so the 2 ulp target of the real `exp` does
  not describe it; 4 ulp is the module's platform bound for a composition of that shape. (This is the one
  place where I did not follow the coordinator's suggestion of "2 ulp like the real exp": 2 ulp is a
  promise the composition does not keep. Recorded under open questions for the language author.)
- Both declare `not_ieee: ["nans"]` because neither always propagates a NaN, which the platform behaviour
  (probed, not assumed) shows: `hypot(+inf, NaN)` is `+inf`, and `std::exp(std::complex(-inf, NaN))` is
  `0+0i`. Both are the C standard's special cases, so the contract says "exact special cases" rather than
  "NaN always wins".

`declareComplexFunctions` is a separate function rather than rows in `declareElementaryFunctions` because
the complex functions are not one overload family: they are seven URIs whose classes differ (three exact,
two bounded).

**Test.** `test/plans/feat/modules/operator_semantics.plan.toml`,
`declared_math_numeric_semantics`: the `expected` map now holds the ten entries above and still asserts
that every registered `math:` operator is covered and that the counts match — the completeness check that
made item 2 visible in the first place. 4/4 tests pass.

## 3. `^` is defined for complex numbers; `%` is not

**Semantics** (documented in `docs/language/03_data_model.md` §3.2 end, §3.2.1, and the English mirror;
the operator tables of `06_expressions.md` in both languages now say "the four real numeric types, `c64`,
`c128`", state that `%` is never defined for complex, and give `^` its complex rule):

- `z ^ n`, `n` of type `int` or `i32`: **repeated squaring**, the same sequence of complex multiplies in
  the same order as `std::complex`'s `operator*` — so `z ^ 2` is bit for bit `z * z`, and `z ^ 3` is
  `(z * z) * z`. The result is a fixed sequence of IEEE operations on the parts, so it agrees bit for bit
  across backends, like `+`, `-`, `*`, `/`. A negative `n` takes the reciprocal (`1 / z^|n|`), computed
  without a fault: a negative exponent is not a fault for real numbers either (`x ^ -1` is `0`), and a
  zero base gives infinities/NaNs in the parts instead of a located fault.
- `z ^ w`, `w` of type `c128`/`c64`: `std::pow(complex, complex)`, the platform's function — the same
  class as the real `^` (which declares no numeric semantics at all, because `std::pow` is opaque to the
  contract): no correct-rounding promise, bounded by the platform. When `w` is *whole valued* (imaginary
  part exactly `0`, `|real| <= 2^53`) the repeated squaring is used, so `z ^ (2+0i)` is `z ^ 2` bit for
  bit, and `z ^ 2.0` (a real literal, which the literal rule turns into a `c128` because the other operand
  is one) is exact as well.
- `%` stays undefined for complex (no order, no integer remainder): the docs say so explicitly.

**Implementation.** `src/builtin/operators/ops.cpp`: `integerPower<T>` (repeated squaring with a reciprocal
for a negative exponent, no fault), `complexPower<T>` (whole-exponent detection: imaginary part `0`,
`|re| <= 2^53`, else `std::pow`), `powerOperand<T>` (a complex right operand, an `int` or an `int64`
right operand), `complexPowBinary<T>`, and the four wrappers `__builtin__pow_c__`,
`__builtin__pow_z__`, `__builtin__assn_pow_c__`, `__builtin__assn_pow_z__` (`ops.h`). The wrappers are
registered in `src/builtin/executors/builtin.cpp` and in the `__pow__`/`__assn_pow__` groups of
`src/builtin/modules/globals.cpp`:

```
:op/pow_c      (c64, c64)     :op/pow_z      (c128, c128)
:op/pow_c_i    (c64, i32)     :op/pow_z_i    (c128, i32)
:op/pow_c_l    (c64, int)     :op/pow_z_l    (c128, int)
```

and the six `:op/assn_pow_*` with the cell first, which is what makes `z ^= 3` legal. Nothing else gained
a complex overload: `+ - * /`, `==`, `!=` and the conversions were H15b's, and a `float` *variable*
exponent still needs `c128(x)` (the language has no implicit conversion between numbers) — recorded under
open questions.

**Verified by hand** (`a = 3+4i`): `a^2 = -7+24i`, `a^3 = -117+44i`, `a^0 = 1+0i`,
`a^-1 = 0.12-0.16i`, `a^(1+1i) = -1.6271590399255336+1.1248463410919414i`, `a^n` with
`let n = 3` = `-117+44i`, `(1.5+0.5i)^2 = 2+1.5i`, and `var k = 1+2i; k ^= 3` gives `-11-2i`. All of
these are in `test/cases/trans/cpp/complex_scalar.cml`, whose C++ build prints the same values as
`std::fvm`.

## 4. `std::cpp` lowers complex values to `std::complex<T>` — the full lowering, not a refusal

`cppexec` reports the complex program as `same`, **standalone** (no runtime linked): the generated C++ is a
complete translation of a program that uses complex numbers. Concretely:

- **Types** (`src/passes/trans/cpp/cpp_types.cpp`): `c64` → `std::complex<float>`, `c128` →
  `std::complex<double>`, which also covers arrays (`rt::Array<std::complex<double>>`), tuples, structs
  and enums that carry complex fields (`appendText` and `operator==` of the generated structs then find
  the overloads below).
- **Constants**: `std::complex<double>{3.0, 4.0}`, each part a shortest-round-trip float literal (the
  existing `cppFloatLiteral`, so NaN and infinities are `std::numeric_limits<...>`).
- **Arithmetic**: `+`, `-`, `*`, unary `-`, `==`, `!=` are the C++ operators (`std::complex`'s arithmetic
  on the parts, in the same order as the runtime's `complexBinary`). `/` is `rt::complexDiv(a, b, site)`,
  which faults with `RuntimeDiag::DivisionByZero` at the operation's site when the divisor is the complex
  zero — `std::complex`'s own division would give an infinity, so this is a runtime function with the
  fault site.
- **`^`**: `rt::pow` overloads for `(std::complex<T>, std::complex<T>)` and `(std::complex<T>, int64_t)`,
  with the same algorithm as `ops.cpp` (`integerPower` repeated squaring, the whole-exponent detection,
  `std::pow` otherwise), so the C++ program and the interpreter make the same roundings.
- **Math functions** (`math:abs_c/_z`, `re_c/_z`, `im_c/_z`, `conj_c/_z`, `exp_c/_z`):
  `rt::complexAbs` (`std::hypot` of the parts, as `__math_abs__`), `rt::complexReal`, `rt::complexImag`,
  `std::conj`, `std::exp`.
- **Conversions**: `itoc`/`ltoc`/`ftoc`/`dtoc` and the `…toz` forms → `rt::complexFromReal<float/double>`,
  `ctoc`/`ztoz` identity, `ztoc`/`ctoz` → `rt::complexFromComplex<T>` (each part converted),
  `ctos`/`ztos` → `rt::toText`.
- **Text**: `appendText(std::string&, std::complex<T>)` writes `camel::utils::complexText`, the runtime's
  own function, so plain printing is identical (`3+4i`, `0-2i`, `-1+0i`, `nan+4i`, `3-0i`).
- **Formatting**: `formatComplex` (see item 1).
- `include/camel/standalone/complex.h` is new and holds the runtime half; `format.h` includes it, and
  `runtime.h` includes it before `format.h`.

**One refusal remains, and it is not about complex values:** a `main` that takes a complex parameter
cannot read it from the command line. The translator refuses the program with a located
`RuntimeDiag::TranslationRefused`:

```
error[RuntimeDiag::TranslationRefused]: ... the parameter 'z' of 'main' has type 'c128', and std::cpp
reads from the command line only the parameters of type int, i32, float, f32, bool and string ...
```

The interpreter rejects the same program at the same argument with `EntryArgumentInvalid` ("a value of type
'c128' cannot be given on the command line"), so the two agree that the case is unsupported; there is no
silent loss. Nothing else that mentions a complex type is refused — verified with the program in
`test/cases/trans/cpp/complex_scalar.cml`, and by a manual probe with a struct and a tuple carrying complex
fields (printing and equality, `same`).

**Tests.** `test/plans/feat/trans/cpp.plan.toml`: new fast test `complex_numbers` (the translation contains
`std::complex<double>{3.0, 4.0}`, `std::complex<float>`, `rt::complexDiv(`, `rt::complexAbs(`, `rt::pow(`,
`std::exp(`, `rt::toText(` and nothing of the runtime); the program itself is built and compared with
`std::fvm` by `agree_with_fvm` through `test/tools/cppexec/expect.txt` (new entry
`test/cases/trans/cpp/complex_scalar.cml`). The program covers arithmetic, `/` including its fault, `^`
with an integer, a variable and a complex exponent, `^=`, comparisons, `square(z)` as a function taking and
returning a complex value, `c64`/`c128` conversions, `re`/`im`/`abs`/`conj`/`exp`, `string(z)`, formatted
printing, an array of complex numbers and a NaN part, then faults on the complex zero and must report the
same text and exit code as the interpreter.

## 5. DLPack: a real complex round trip

The encoding (`src/core/array/dlpack.cpp`) was H15b's: code 5, 64 bits for `c64`, 128 for `c128`, lanes 1.
This task adds the round trip:

- **C++ side** (`src/core/array/block_selftest.cpp`, run by the `std::gc::blocks` pass and therefore by
  `feat/mm/blocks.plan.toml`): a 20-element `c128` array (320 bytes, block backed from the start) is
  filled with `1.5-2.5i`, `0+1i`, `-3.25+0i`, `-0.0+0.5i` repeated; export asserts dtype
  `{code 5, bits 128, lanes 1}`, the same data pointer (zero copy) and a block reference count of at least
  2; import asserts the same address, `Complex128` and 20 elements, and that every part reads back,
  **including the sign of the zero** (`std::signbit` of both parts). A 40-element `c64` array is the same
  test at 64 bits (`{5, 64, 1}`, 8-byte elements, both parts read back as `f32`).
- **NumPy side** (`test/cases/feat/mm/dlpack_complex.py`, new test `dlpack_complex_numpy` in
  `feat/mm/blocks.plan.toml`): NumPy is imported, so the test is gated with
  `skip_unless = ["${python}", "-c", "import numpy"]` and is skipped where NumPy is absent (it prints
  `dlpack complex: PASS` and the dtype line when it runs). It checks NumPy's half of the same contract for
  the same parts the C++ round trip writes: `np.complex128` is 16 bytes, its bytes are the (real,
  imaginary) `float64` pairs in machine order (`tobytes()` against `struct.pack("=dd", …)`), and the
  `DLManagedTensor` NumPy's own `__dlpack__` announces has dtype code 5, bits 128, lanes 1, `ndim == 1`,
  shape 20, and a data pointer equal to the array's (`ctypes` reads the capsule). It also checks the parts
  with a negative zero survive as bytes.

**Why this split, stated plainly:** a capsule bridge from a Camel array to a Python object does not exist
yet (`modules/python` has no DLPack entry point; the H17 plan's interop step is the capsule wrapper), so
one cannot drive Camel's export from NumPy or NumPy's import from Camel today. The C++ round trip is the
real round trip (export → import → every part read back, zero copy); the NumPy test pins the *other* side
of the contract to the same dtype and the same bytes, so the two cannot drift apart silently. When the
capsule bridge lands, the NumPy test should become an end-to-end `from_dlpack(camel_array)` check; that is
recorded as an open question rather than pretended here.

## 9. A defect found, not fixed here

A **negative-sign NaN** under a format specification prints differently in the two paths, and it is not
complex-specific:

```
let n = sqrt(-1.0)          // -NaN on this platform
println(n)                  // nan        (both sides, the rule "a NaN has no sign")
println<'{:.2f}'>(n)        // fvm: -nan   cpp: nan
```

The interpreter hands the value to `fmt`, which writes the sign bit; the standalone `formatFloat` drops the
sign of a NaN (`std::signbit(v) && !std::isnan(v)`), which is what `docs/language/02_lexical.md` §2.5.2 says
("NaN 不带符号"). One of the two is wrong: either the interpreter's formatted float text should lose the
sign too (my reading of the text rule), or the rule needs to say that a specification keeps the sign. It is
a float defect, not a complex one, so H15c does not change either side; the complex test uses `math::nan`
(a positive NaN), where both agree. This is the first open question below.

## 10. Decisions and open questions

Decisions taken here (recorded because the review leaves the details to the implementation):

1. A complex format specification mirrors Python: number part per part, layout part once for the whole
   text, zero padding and `=` alignment rejected. Chosen over "one part only" or "both parts padded
   independently" because Python's rule is the one users know and the one the review names
   ("`{:.2f}` on `3+4i` gives `3.00+4.00i`, as Python does"), and because per-part padding would make
   `{:>12.2f}` depend on the digit count of each part.
2. `abs` is Bounded 4 ulp and `exp` is Bounded 4 ulp (not Exact, not 2 ulp), as argued in §2: the
   declaration must describe the function that is actually called, not the real function it resembles.
3. `z ^ n` is repeated squaring and is exact for the sequence; a negative `n` takes the reciprocal and
   does not fault; `z ^ w` is `std::pow`, with the whole-exponent detection; `%` stays undefined.
4. `std::cpp` translates complex values fully (item 4 gave the choice, and it was contained), with the
   single exception of a complex `main` parameter read from the command line, which is refused at the
   parameter — never silently dropped.
5. The DLPack round trip is the C++ one, with a NumPy-gated test for the other side of the dtype/byte
   contract, because no Camel↔Python capsule bridge exists yet.

Open questions for the language author:

1. **Negative NaN under a format specification.** Should `'{:.2f}'` on a sign-bit NaN write `nan` (the
   text rule, and what the C++ program does) or `-nan` (what the interpreter does through `fmt`)? One of
   the two paths should change; it is a float question, so H15c left both alone.
2. **`abs` and `exp` contract class.** Is 4 ulp accepted for complex `abs` (hypot) and `exp` (a
   composition of the platform's `exp`, `sin`, `cos`)? The alternative — declaring `abs` Exact because
   the real `abs` is — would promise something `hypot` does not deliver.
3. **A real variable as a complex exponent.** `z ^ 2.0` works (the literal becomes `c128`), but
   `let x: float = 0.5; z ^ x` is `NoMatchingFunction`; the user must write `z ^ c128(x)`. Should a
   `c ^ f` / `z ^ d` overload exist, or is "same type, or an integer exponent" the intended rule?
4. **Complex `main` parameters.** Should `--arg z=1+2i` be readable (an `EntryArguments` reader plus a
   `std::cpp` entry translation), or is "not on the command line" the intended answer for every complex
   value at the boundary?
5. **End-to-end DLPack test with NumPy.** Once the capsule bridge exists, the NumPy test should call
   `np.from_dlpack` on a Camel array (and hand a NumPy array to Camel) instead of comparing the two sides
   separately.
