# H30 — A Debug build that links, and a Debug test layer

Branch: `handover/H30-debug-tier` (from `develop`). Everything is in the working tree; nothing was
committed, branched or pushed.

Three things were asked for: a Debug build that links, a `debug` layer in the test runner, and a
deliberate view escape that aborts only in Debug. All three are in place. The layer is opt-in and
runs; it is **red today**, and the failures are real Debug-only defects that a Debug build has
never been run enough to expose. Section 7 lists them; that list is the layer's first output, not
a regression of this task.

## 1. The Debug build did not link, and H16 item 5 had never been done

The starting point was not "the export switch is off and we must add explicit exports"; H16 item 5
says `WINDOWS_EXPORT_ALL_SYMBOLS` was turned off in favour of explicit exports, but in this tree it
was still **on**:

```cmake
set_target_properties(libcamel PROPERTIES WINDOWS_EXPORT_ALL_SYMBOLS TRUE)
```

That switch generates a `.def` with every global symbol. Release stayed under the PE limit of
65,535 exports; Debug emitted **75,682** and `lld-link` refused:

```
lld-link: error: too many exported symbols (got 75682, max 65535)
```

So Debug could not link, and the premise "debug was never proven to link because exports are
explicit" was wrong — the blanket switch was the cause. Two smaller Debug-only defects were on the
way: `graph_runtime_support.cpp` called `arrayType->elementType()`, a member that does not exist
(Release's `NDEBUG` had compiled the block out; `elemType()` is the real name), and the assertion
helper the new guard needed was not exported.

### What replaced the switch

`WINDOWS_EXPORT_ALL_SYMBOLS` is now `FALSE`, and `libcamel` links against an explicit `.def` that
is generated immediately before every link (`CMakeLists.txt`, `cmake/make_libcamel_def.cmake`):

```
cmake/libcamel_exports.def        463 symbols every configuration exports
cmake/libcamel_exports_debug.def  3 symbols only a Debug build defines
cmake/libcamel_exports_<CFG>.def  the file actually passed to the linker
```

The per-configuration file is needed because `lld-link` takes one `/DEF`, and three profiler
symbols (`start_advanced_tracing`, `stop_advanced_tracing`, `generate_advanced_report`) exist only
in a Debug build. `make_libcamel_def.cmake` concatenates the common file with the Debug-only one
when `CFG` is `Debug` and leaves the file alone when its content is unchanged. `LINK_DEPENDS` lists
both inputs so that editing the `.def` relinks `libcamel` — without it the first Release link after
an edit silently kept the old exports and failed on the tool executables instead.

### How the export list was built

Not from the source: from what the artifacts actually import. The import tables of every tool in
`out/latest/bin` and of every `.cmo` module (464 names) gave the common list, plus three
Debug-discovered names: `assertStoredValueIsNotView` (the new view guard, called from an inline
header function), and the profiler's `RegisterType` / `SetHandler` / `clearPostAllocDebugHook` /
`runtimeDataType`. A Debug/Release `nm` diff then found the seven names that were missing, of which
four are defined in Release and three are Debug-only — which is why the list is split per
configuration rather than shared.

One mangled name is hand-written in the file because the symbol is a member with an inline
`std::optional` return type and `tiles-plan-check` imports it:

```
?key@OperatorTable@core@camel@@QEBA?AV?$optional@UOperatorKey@sem@core@camel@@@std@@I@Z
```

**Maintenance:** a new exported symbol now needs a line in `cmake/libcamel_exports.def`. The
failure is loud and names the symbol (`undefined symbol: ...`), not silent.

### Result

`npm run debug` is green end to end (477 targets on the first build, 369 on the rebuild after the
header edit; 75–86 s on this machine), artifacts are collected to `out/debug`, and

```
Camel v0.2.15 (Debug 261021_004246_v0.2.14_264_gd8141a57_dirty)
```

The `(Debug ...)` marker is what the runner's preflight checks. `npm run build` (Release) is green
as well.

## 2. Addressing the Debug tree

`scripts/collect-out.js` now maps configuration to tree explicitly:

| Script | Configuration | Tree |
|---|---|---|
| `npm run build` | Release | `out/latest` |
| `npm run debug` | Debug | `out/debug` |
| `npm run profile` | RelWithDebInfo | `out/latest` (unchanged) |

The tag mirroring into the compatibility directory only happens for `latest`, so a Debug run can
never overwrite the Release installation. `CAMEL_HOME=out/debug` is the whole addressing story for
the CLI; `docs/cli.md` has a "Release and Debug installations" table.

## 3. The Debug layer

`test/tools/run-tests.mjs` gained a fourth layer next to `fast`, `slow` and `all`, selected with
`--tier debug`. It is opt-in: nothing in the default `fast` run or in `--tier all` pays for it.

**Plan selection** reuses the existing mechanism. Plans opt in with a new field

```toml
debug_tier = true   # also selected by --tier debug (Debug build)
```

and a test can additionally be marked `tier = "debug"`, exactly like `slow`. Eighteen plans are
marked, covering the areas the task named (smoke; mm blocks, complex, mem_blocks, capacity; linear
loops, hof_declared, collections_and_structs, basic_runtime, captured_writes, closures_and_state,
operators; tensor bounds, compound_assign, named_dims, shape_diagnostics, shape_inference,
shape_types). With no target on the command line `--tier debug` scans the whole plan tree, because
its own abort plan lives in `test/plans/debug`, which the default `smoke` + `feat` target does not
reach. Naming a plan file still runs that plan in full.

**Which binary.** `--build release|debug` (or `CAMEL_TEST_BUILD=debug`) picks the tree;
`out/latest` and `out/debug` are the only accepted values. `--tier debug` forces `debug`, and
`--tier debug --build release` is refused with a message instead of silently running Release.
Every test gets `CAMEL_HOME` and every tool path from the selected tree.

**A missing Debug binary is a failure, not a fallback.** The preflight checks the binary and the
Debug marker before any test starts:

```
[FAIL] no Debug binary at D:\...\out\debug\bin\camel.exe
       build it with: pwsh -NoProfile -File D:\...\camel-build.ps1 -Path D:\... -Config Debug
       The Debug tier never falls back to out/latest.
```

Exit code 2. The check was verified by renaming the binary.

**Timeouts.** Unoptimised code runs the same loops tens of times slower, so on the Debug build each
test's timeout is multiplied by four (`DEBUG_BUILD_TIMEOUT_SCALE`); `CAMEL_TEST_TIMEOUT_SCALE` still
composes with it. A test that exceeds the scaled timeout is still a failure.

**The escape plan.** `test/plans/debug/view_escape.plan.toml` runs a real program (not a synthetic
self-test pass) through `std::gc::views_escape`; see section 4.

Documentation: `docs/test-plans.md` (a "Layers: fast, slow And debug" section, the `debug_tier`
field, the build table and the addressing rules) and `docs/cli.md` (the two installations and the
`--version` marker).

## 4. The deliberate escape that must abort

The case from `docs/handover/reports/H29.md` is a reduce whose accumulator is the compact-element
view the round just read. The view is tied to the thread-local view ring, so it may not be stored.

The store now has one named boundary, `storeReduceAccumulator` in
`include/camel/core/rtdata/array.h`, used by the nvm reduce operator
(`src/builtin/operators/higher_order.cpp`):

```cpp
const slot_t raw  = invokeFunction(ctx, functionOf(with), {}, args);
const slot_t next = materializeCallResult(
    raw, functionOf(with)->graph()->funcType()->exitType());
storeReduceAccumulator(cell.getAs<Array>(), next, cellType);
```

`storeReduceAccumulator` asserts `CAMEL_ASSERT_NOT_VIEW` (Debug only, compiled out under `NDEBUG`)
and then stores. The nvm now materialises a view before the store, exactly as the bytecode VM
already did, so the assertion means "a caller forgot", not "this program is unusual".

**Why a `.cml` program alone cannot produce the abort.** A well-formed program never hands a view
to the store: the compiler makes the value, and both VMs materialise before storing. The escape is
only observable if something stores the view *without* materialising — i.e. a bug in the runtime.
To exercise the guard deterministically, `debugRunViewEscapeSelfTest()`
(`src/core/rtdata/view_selftest.cpp`) builds a compact `(int, int)` array, takes
`getElementView(0)`, and calls `storeReduceAccumulator` with that view directly. That is the same
store the reduce operator uses; the self-test skips only the materialisation the operator performs.
It is reachable as a pass — `std::gc::views_escape`, alias `std::gcviews_escape` — and prints
`VIEW_ESCAPE not-caught: ...` and returns 0 if the guard is compiled out (Release).

**Evidence (Debug, exit code 3):**

```
Camel Debug Assertion Failed:
    Location   : ...\src/core/rtdata/view.cpp(180)
    Function   : assertStoredValueIsNotView
    Expression : false
    Suggestion : A compact element view escaped into the reduce accumulator ((int, int)).
                 A view is tied to the thread-local view ring and must be materialised before
                 it is stored.
Stack Trace:
<1> D:\...\src\core\rtdata\view.cpp(174): libcamel!camel::core::rtdata::assertStoredValueIsNotView+0xD8
<2> D:\...\include\camel\core\rtdata\array.h(711): libcamel!storeReduceAccumulator+0x152
<3> D:\...\src\core\rtdata\view_selftest.cpp(116): libcamel!camel::core::rtdata::debugRunViewEscapeSelfTest+0x228
<4> D:\...\src\execute\pass.cpp(302): libcamel!`anonymous namespace'::GcViewsEscapePass::apply+0x39
<5> D:\...\src\execute\pass.cpp(1267): libcamel!applyPassesDetailed+0x807
```

**Release:** the same pass prints `VIEW_ESCAPE not-caught: the store guard is compiled out of this
build` and exits 0.

The test is a **positive** test: `expect_exit = 3`, `expect_stderr_contains` the assertion header and
the suggestion, and `expect_output_not_contains` the not-caught line. If the guard disappears, the
test fails because the exit code is 0 and the not-caught line is present — it cannot pass silently.
Both the canonical name and the alias are covered.

## 5. Two pre-existing Debug defects fixed here

Running the new layer immediately aborted 176 of 324 tests. Two causes were in the runtime, not in
the tests, and both were invisible in Release because the assertions are compiled out:

1. **`Array::setSlot` / `setSlotSlow` rejected the append position.** `appendSlot` stores the new
   element at `size_ == numel_` and only then increments the count, but the bound was
   `flatIndex < numel_`, so every compact append of an aggregate aborted in Debug (149 tests,
   `array.h(439)` / `array.h(446)`), typically while the compiler built static data
   (`conv.cpp` → `draft_graph_builder.cpp`). The bound is now inclusive with a comment; Release
   behaviour is unchanged (the assertion does not exist there) and the write was always inside the
   capacity that `appendSlot` had just grown.
2. **The nvm reduce did not materialise the accumulator.** With the guard in place,
   `loops.reduce_element_view.nvm` aborted with "A compact element view escaped into the reduce
   accumulator" — the Release build only worked because `setSlot` materialises a view quietly.
   The operator now calls `materializeCallResult` before the store, matching `fastvm.cpp`.

These two changes took the layer from 148/324 to 286/324.

## 7. What the layer found, and why it is red

38 of 324 tests fail. None is caused by the layer or by the escape work; each is a Debug-only
assertion that a Release-only test history never reached. Grouped by cause:

| Count | Assertion | Where |
|---|---|---|
| 10 | `castSlotFrom only allowed when castSafetyFrom returns Safe` | `src/core/type/base.cpp:228` |
| 9 | `Accessing uninitialized slot` (`fromSlot` of a `DeadSlot`, through `materializeCallResult`) | `include/camel/core/rtdata/base.h:166` |
| 4 | `Runtime Function graph cannot be null` | `src/core/rtdata/func.cpp:72` (`grad_*` autodiff loop tests) |
| 2 | `a loop body's collection slots do not match` | `modules/autodiff/pullback.cpp:1506` |
| 2 | `Trying to release a frame that is not on top` | `include/camel/core/context/frame.h:513` (`loops.fault.fvm/.prl`) |
| 6 | timeout at the scaled budget | `hof_compact_element_view` x3 (240 s), `inside_recursion` x3 (80 s) |
| 5 | exit 1, `MaxRecursionDepthExceeded` with "the native stack ... is full" | see below |

The recursion group is a Debug property, not a defect in a pass: with `-O0` the interpreter's
frames are about 90 KiB, so a 32 MiB tool stack fills at ~363 open calls — `deep(400)` fails in
Debug and `deep(250)` passes, where Release reaches 500 comfortably. It surfaces as a runtime
diagnostic, not an assertion, and the plan's expected stdout then does not match.

Working through these is the follow-up work the layer exists to drive. This report deliberately
does not change semantics (cast legality, frame ownership, autodiff collection matching) to make a
test pass.

## 9. Open questions

1. **The layer is red.** Should the 38 known failures be fixed before the layer is documented as a
   gate, or should the marked set shrink to the plans that pass and grow as the defects are fixed?
   Shrinking now would hide exactly what the layer was built to find, so it was not done.
2. **Debug stack size.** The tools link with a 32 MiB stack; Debug frames make that worth ~360
   interpreted calls. A larger `/STACK` for Debug tools (or a Debug-lower default depth) would turn
   five diagnostics into passes, but it changes a limit the language design treats as deliberate.
3. **Layer cost.** 487 s for 324 tests is dominated by three 240 s timeouts and three 80 s
   recursion runs. The multiplier makes the budget honest but the layer slow; trimming those six
   tests or lowering the multiplier are the two levers.
4. **`Accessing uninitialized slot` through `materializeCallResult`.** Nine tests reach it, all in
   view-returning collection paths. It may be the same class of defect as H29's (a `DeadSlot` slot
   used as a value) or a legitimate empty slot; it needs its own diagnosis before anyone "fixes" it.
5. **Export maintenance.** The `.def` is a hand-maintained list now. If the team prefers generation,
   a post-build import-table scan could produce it, but the current failure mode (linker names the
   symbol) is already clear.
