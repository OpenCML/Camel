| 旧名 | 新名 | 提交 | 规模 |
|---|---|---|---:|

改名是**只改拼写**：模块名、目录、CMake 目标、`BuiltinModule` 的名字、执行器工厂名、算子 URI、签名文件、测试目录与所有导入处一致地换名；没有改任何算子的实现、参数、纯度、资源或故障文本（故障文本只随模块前缀改，例如 `crypto.sha256_rounds`→`hash.sha256_rounds`）。

三个旧名不再是模块，也没有别名或过渡层：导入旧名在**导入处**得到带位置的 `SemanticDiag::ModuleRenamed`，消息点名新名。三个正例（`*_new.cml`）与三个反例（`*_old.cml`）都在 `test/plans/feat/modules/rename.plan.toml` 中。

## 2. 改名规则与落点

Camel 的模块名同时是导入名、算子 URI 前缀、执行器协议名、`BuiltinModule(name)` 的名字和 CMake 目标名，所以一次完整改名要同时改这些地方。以 `sys`→`env` 为例（另外两个同样）：

| 位置 | 旧 | 新 |
|---|---|---|
| 目录 / CMake | `modules/sys`、`add_camel_module(NAME sys)` | `modules/env`、`add_camel_module(NAME env)` |
| 顶层 CMake | `add_subdirectory(modules/sys)` | `add_subdirectory(modules/env)` |
| 模块类 | `SysModule` | `EnvModule` |
| 内置模块名 | `BuiltinModule("sys", ctx)` | `BuiltinModule("env", ctx)` |
| 执行器工厂 | `registerExecutorFactory("sys", ...)` | `registerExecutorFactory("env", ...)` |
| 执行器 / opsMap | `SysExecutor`、`createSysExecutor`、`getSysOpsMap` | `EnvExecutor`、`createEnvExecutor`、`getEnvOpsMap` |
| 算子 URI | `sys:get_env`、`sys:get_cwd` | `env:get_env`、`env:get_cwd` |
| C++ 入口符号 | `__sys_get_env__`、`__sys_get_cwd__` | `__env_get_env__`、`__env_get_cwd__` |
| 故障文本 | `sys.get_env`、`sys.get_cwd` | `env.get_env`、`env.get_cwd` |
| 签名文件 | `stdlib/signatures/sys.cml` | `stdlib/signatures/env.cml` |
| 测试 | `test/cases/modules/std/sys/**` | `test/cases/modules/std/env/**` |

`os`→`process` 与 `crypto`→`hash` 的落点相同：

- `modules/os` → `modules/process`：`OSModule`/`OSExecutor`/`createOSExecutor`/`getOSOpsMap`（若原类名不同则按实际类名）→ `ProcessModule`/`ProcessExecutor`/`createProcessExecutor`/`getProcessOpsMap`；URI `os:*`→`process:*`（`sleep`、`whoami`、`cpu_count`、`set_terminal_raw_mode`、`has_input`、`get_char`、`get_chars`、`clear_input_buffer`、`exit`）；`stdlib/signatures/os.cml`→`process.cml`；`std/os`→`std/process`。
- `modules/crypto` → `modules/hash`：`CryptoModule`/`CryptoExecutor`/`createCryptoExecutor`/`getCryptoOpsMap` → `HashModule`/`HashExecutor`/`createHashExecutor`/`getHashOpsMap`；URI `crypto:sha256_str`/`crypto:sha256_bytes`/`crypto:sha256_rounds` → `hash:*`；`stdlib/signatures/crypto.cml`→`hash.cml`；`std/crypto`→`std/hash`。

全局 `sleep` 与 `exit` 仍然不需要导入；它们的 URI 随所属模块变成 `process:sleep`、`process:exit`，首次查找时自动加载 `process`。`globals.cpp`、`stdlib/signatures/globals.cml`、`builtin.cpp`、`operator_rules.cpp` 的字符串同步改了，行为不变。

`scripts/stdlib-reference.mjs` 的模块表、`docs/stdlib-reference.md`、`docs/diagnostics.md`、`benchmarks/pipeline/exclusions.json`、`test/plans/feat/parse/golden/ast_hashes.txt` 都随名字更新；`test/plans/feat/modules/std.plan.toml` 的三块用例名/路径改为 `env.basic`、`process.basic`、`hash.basic`。`test/cases/tools/grammar/keywords.cml` 里的 `import os` 是**词法/语法测试里的任意模块名**，只被解析、不被编译，保持原样（它测的是 `import ... as` 的写法，不是标准库模块）。

## 3. 诊断：旧名不是别名

设计原则第 1 节要求“旧写法直接删除，不加别名、不加过渡层”；本任务又要求旧名**有一个点名新名的、带位置的拒绝**。实现按后者：

- 新码 `SemanticDiag::ModuleRenamed = 0x000185`（目录显示 `0x03000185`），加在 `include/camel/core/error/diagnostics/messages/semantic.h` 的 `LambdaParameterWithoutType` 之后，满足“新码从 0x185 起”。
- 消息：`The module '{0}' was renamed to '{1}'.`
- 帮助：`Import '{1}' instead; '{0}' is no longer a module (handover H114).`
- `src/core/context/context.cpp` 的匿名 `renamedModules()` 表：
  ```cpp
  {{"sys", "env"}, {"os", "process"}, {"crypto", "hash"}}
  ```
- 检查在 `Context::importModule` 的入口、空名字检查之后、候选路径解析之前执行，所以即使 `out/latest/stdlib/` 里还留着旧的 `sys.cmo`/`os.cmo`/`crypto.cmo`，旧名也不会被加载；旧名现在是错误，而不是“碰巧还能用”。
- 反例用例断言导入行（`env_old.cml:6:`、`process_old.cml:6:`、`hash_old.cml:6:`）、消息原文和帮助原文；正例用例证明新名能导入并真正执行算子（`env` 读环境/工作目录；`process` 调 `whoami`/`cpu_count`/`sleep(0)`；`hash` 算 `sha256('abc')` 与一轮 `sha256_rounds`）。

**与设计原则的冲突（必须记录）**：设计原则禁止“指向新名的退役诊断”，只允许直接删除并通过普通错误暴露；本实现为了满足任务书的要求保留了这条诊断。它是**有意的例外**，不是遗漏；如果以后按设计原则收紧，应删除 `SemanticDiag::ModuleRenamed`、`renamedModules()` 与三个 `*_old` 反例，让旧名退回普通的 `ModuleNotFound`/语法错误。报告把这一点留给协调者裁定。

## 4. 图恒等证明

每个模块有一份只含字面量、可由 `std::jgir` 翻译而**不执行**的样本；翻译不读环境、不读机器、不睡眠、不算哈希，所以图只由源码和算子 URI 决定，跨机器一致。样本：

- `test/cases/modules/rename/env_identity.cml`
- `test/cases/modules/rename/process_identity.cml`
- `test/cases/modules/rename/hash_identity.cml`

`test/cases/modules/rename/identity.mjs` 读 `std::jgir` 的 JSON，把 `case_path` 换成常量 `CASE`，再把 `\b<now>:` 换成 `MODULE:`，对规范化后的 JSON 做 SHA-256；`rename.*_graph_identity` 三个计划断言摘要与改名前相同：

| 模块 | 规范化后的 SHA-256 |
|---|---|
| `sys`→`env` | `31e343f49b0e3b1a985bd49d034d2b53e609bfe822c08bd13792ffaf92b807d4` |
| `os`→`process` | `ef0d12bcfa08cb37d4586b9783068818724ed2857faf4a71386929571bb7049f` |
| `crypto`→`hash` | `e24d1896575924d33fec0d21de336dda49114dc1cadc8f05575e8a94bef57bd8` |

三个摘要都通过，说明改名只改了 URI 的模块前缀，节点、边、类型、位置和其余属性一个没动。

## 6. 未做的事与遗留

- **只改名，不拆模块**。`process` 里仍有终端算子 `set_terminal_raw_mode`、`has_input`、`get_char`、`get_chars`、`clear_input_buffer`；按职责它们更接近 `io`/终端，而不是进程与机器。`whoami`/`cpu_count` 留在 `process` 是合理的。`env` 的 `get_env`/`get_cwd` 也合理，但它们声明的资源名仍是 `process:environment`（“进程的环境”），这是旧代码就有的名字，本步只改拼写，没有改资源名。
- **`exit`/`sleep` 仍是全局内建**，只是 URI 变成 `process:*` 并自动加载 `process`。计划里的 `:io/exit` 与“删除全局 `sleep`”属于后续步骤，本步不做。
- **`crypto` 只有哈希**，改名 `hash` 后没有别的算子需要分流；`hash` 与 `crypto` 的旧名只出现在历史文档（`changes.log`、`docs/design/stdlib/README.cn.md` 的改名讨论）与本次的反例/恒等样本中，属于有意保留。
- **旧名诊断与设计原则的冲突**已在 §3 记录；如果协调者按设计原则裁定，删除诊断即可，不需要动改名本身。
