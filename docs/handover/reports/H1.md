## 做了什么

- **类型层**：`EnumDecl` / `EnumType` / `EnumVariant` / `VariantShape`（`include/camel/core/type/enum.h`、`src/core/type/enum.cpp`）。声明与实例分开，实例按声明与实参驻留；递归用原型 + `EnumHole` 处理；名字修饰与 `Map`/函数等带参数类型一致；`EnumType` 是 `OtherType` 的子类，`GC_Traced`。
- **解析与 AST**：`enum` 关键字、类型声明体、三种变体形状、枚举变体的元组/结构体模式（`src/parse/syntax/parser_type.cpp`、`parser_expr.cpp`）；AST 的 `EnumTypeLoad` 与 `EnumPatternLoad`；结构体模式支持简写与改名；字段位置出现嵌套模式在 AST 建树时给出“暂不支持”。
- **建图（GCT/GIR）**：声明与变体表进 GCT；构造与匹配在 GIR 里降级为**已有的节点种类**——构造是一次带显式类型实参的内部算子调用（`__enum_make__`），匹配是 `__enum_tag__` 取标签后一条 `==` + `BRCH`/`JOIN` 的嵌套分支链，字段用 `__enum_field__` 取出。穷尽检查、重复臂与 `case _` 之后的臂、未知变体、字段个数/名字/类型、泛型实参推断都在建图时报出，位置是源码区间。
- **算子**：`src/builtin/operators/enum.{h,cpp}`，三个内部算子都是普通算子（登记纯度、资源与语义），结果类型由各自的 `FuncTypeResolver` 决定（构造用显式类型实参，取字段用静态的标签与下标），不在建完调用后改节点类型。
- **运行时**：`rtdata::Variant`（标签 + 字段槽），`updateRefs` 追踪字段，打印与相等按内容（复用新的 `src/core/rtdata/equality.cpp`，带环检测）。`std::nvm`、`std::fvm`、`std::jit`、`std::prl`、`std::macro` 都通过；`std::cpp`、ONNX、autodiff 给出带位置的明确拒绝。
- **退役联合类型**：`A | B` 与 `T ? U` 在 GCT 给出 `UnionTypeRetired` / `ReservedTypeQuestionRetired`；`stdlib/signatures/*.cml` 的 66 行联合签名展开为多条声明；`scripts/stdlib-reference.mjs` 的“每个声明都要有说明”改为每个名字的第一条声明（同一个算子的多条声明共享一份说明），文档已重新生成。

## 设计上的选择

1. **不新增节点种类**（2.13 原文）。构造 = 装入标签与数据，匹配 = 取标签、分支、取字段。`T?`/`T!` 用的是同一种做法（`TUPL` + `BRCH`），照它实现。
2. **内部算子而不是建图特例**。三个 `__enum_*__` 算子像其它内建算子一样登记（URI、纯度、资源、executor），调度器不需要按名字判断；`std::macro` 能像其它纯算子一样求值它们。
3. **类型由算子的解析器决定**。`__enum_make__` 的显式类型实参是完整的 `EnumType`（`f::<Enum>` 的 GCT `TAPP` → `explicitOperatorTypes_`）；`__enum_field__` 的 `(tag, index)` 必须是静态字面量，因为字段类型取决于变体。曾在建完调用后覆盖节点类型，会导致后续期望类型推断看到错误的结果类型，已改掉。
4. **声明与实例分开**。一个 `EnumDecl` 对应源码里一次声明；`EnumType::get(decl, args)` 得到实例并驻留。这样 `Option<int>` 与 `Option<float>` 是两个类型，递归（`Tree<T>` 的字段引用自身）靠原型 + 洞，不必让实例在构造过程中自我引用。
5. **穷尽匹配的“多出来的一条臂”**。列全所有变体时，分支链最后一层的 else 是一份最后臂的副本，不可达，只为让 `BRCH` 的第二条臂与 `JOIN` 有值。没有把它做成“省略 else”的新节点形态：那会给调度器增加一种必须认识的结构。
6. **模式前缀可选，但单元变体要写全限定名**。`case Circle(r)` 与 `case Shape::Circle(r)` 都接受（与构造一致）；`case Empty` 会被读成一个绑定名，所以单元变体必须写 `Shape::Empty`，与“模式里的裸名字是绑定”这条既有规则一致。
7. **结构体变体的构造经由结构体值**：要求实参是一个结构体，按声明的字段名逐个 `ACCS` 取出，字段必须齐全且不许多；没有为“命名字段构造”发明新的 GCT 节点。
8. **泛型实参的推断**：从字段实参 `unifyTypeVars`，失败时用 `expectedValueType_` 的类型参数（`let x: Option<int> = Option::None`、返回位置、调用实参位置），仍失败是 `EnumTypeArgumentNotInferred`。这与 2.10 的“延迟到上下文能确定时”一致，没有引入新的推断规则。
9. **autodiff 拒绝而不是给 0**：把依赖微分参数的值放进 `enum` 时，活动集在那里结束，导数没有规则。`refuseActiveEnum` 在 `Backward::run` 的活动分析里报错，复用 `refuseActiveCollection` 的机制。
10. **文档与实现同步的方式**：签名文件里一个算子的多条声明共享第一份文档注释；脚本按“每个名字的第一条声明”检查说明与纯度，避免为了脚本把同一段说明抄 4 遍。

## 用户可见的变化

- 新增 `type E = enum { ... }`、`E::Variant(...)`、`E::Variant { ... }`、`E::Unit`、`case E::Variant(...)`、`case E::Variant { f }`、`case E::Unit`、`case _`；列全变体时可以省略 `case _`。
- 打印：`println(Shape::Rect { w: 2.0, h: 3.0 })` 输出 `Shape::Rect { w: 2.0, h: 3.0 }`；`println(Shape::Empty)` 输出 `Shape::Empty`。
- 相等：`Shape::Circle(1.0) == Shape::Circle(1.0)` 是 `true`，`Shape::Circle(1.0) == Shape::Empty` 是 `false`。
- 取字段 `s.radius` 现在报 `EnumFieldAccess`，并提示用 `match`。
- `A | B` 以前能写但没有值能进入，现在报 `UnionTypeRetired`；`T ? U` 报 `ReservedTypeQuestionRetired`（以前是 `FeatureNotSupported`）。
- `camel-format` 能格式化枚举声明与构造；`enum` 成为关键字（不能再作名字）。
- 拒绝：`std::cpp`、ONNX、autodiff 遇到枚举报带位置的错误（见测试），不会崩溃或给错值。

## 自查（第 2 节逐条）

- **按名字写特例**：没有。`enum` 关键字进的是词法表；构造/匹配没有在调度器或优化遍里按名字分支；三个内部算子按统一注册机制登记。
- **绕过通用机制**：没有新增节点种类，没有新增图结构；类型走的是 `OtherType` + 驻留，与 `Map`/`Set` 同一套。
- **多个事实来源**：变体表只在 `EnumDecl`；字段名只在 `EnumVariant`；模式与构造都从它派生；打印与相等都从它派生。
- **写死的位宽/封闭枚举**：标签是 `u32` 但由 `variantCount()` 决定值，没有上限常量；字段槽是 `slot_t` 数组，个数来自声明。
- **测试驱动的临时实现**：没有为通过测试加分支；穷尽检查与诊断都走通用诊断机制。
- **兼容层**：没有；`A | B` 与 `T ? U` 是直接给退役诊断，`UnionType` 类没有再加语言入口。
- **只支持一个后端**：不是；四个调度器 + 宏都有测试，另外三处是明确拒绝（有诊断、有测试），`std::cpp` 的支持没做完（见下）。

## 待决问题

### Q1：变体是否随类型一起导出，跨模块如何使用？
例子：
```cml
// a.cml
export type Shape = enum { Circle(float), Empty }
// b.cml
import { Shape } from a
let s = Shape::Circle(1.0)      // 现在可以
```
建议：随类型导出，变体不需要单独 `export`，限定名里的类型名就是导入的那个名字（已按此实现并验证）。若要允许 `import { Circle } from a`，需要另一套名字规则。
影响：影响跨模块写法的稳定性；现在没有测试锁定它，定下来后应加一个。

### Q2：`enum` 能否作 `Map` 的键与 `Set` 的元素？
例子：`let m = [(Shape::Empty, 1)] as Map<Shape, int>` 现在是 `CollectionKeyNotAllowed`（“值没有顺序”）。
建议：本任务不做。若要做，要求所有字段类型可排序，并按“变体在声明中的顺序、再逐字段”定义顺序；这需要作者确认，因为它是用户可见的顺序。
影响：挡住“枚举作键”的库函数与测试；不影响现有功能。

### Q3：`T?`、`T!` 是否改由 `enum` 实现？
建议：本任务不改。它们在图上已经是“标签 + 载荷 + 分支”，与枚举同构；改成 `enum` 只会让内建类型依赖用户层机制，且会改变打印与错误值的表示。
影响：只影响将来是否统一实现；不影响现在的语义。

### Q4：泛型实参推断的边界
例子：
```cml
let x: Option<Option<int>> = Option::Some(Option::None)   // 内层 None 目前推不出
```
建议：先要求写出内层类型（`Option::Some(Option::None as Option<int>)` 或分两步），把“期望类型穿过构造的实参”作为后续规则明确下来。现在的规则是“字段实参 → 期望类型”，没有再往内层传。
影响：挡住嵌套泛型枚举的省略写法；不影响 `Option<int>` 这一层。

### Q5：`json` 的访问器是否接受 `Json!`？
例子：`json::get<'a'>(decode(text))` 现在是 `NoMatchingFunction`（`Json!` 不是 `Json` 或 `Json?`）。H1 要求“按 2.14 同时接受 `Json!`，使解析失败也能链式取值”。
建议：如果“失败也能链式取值”是指失败原样传播，那么 `get` 的返回类型应是 `Json!` 而不是 `Json?`，这是类型规则的变化；如果是指失败时给 `null`，那需要运行期把错误吞掉。两者都是语义决定，我没有自行选择，签名文件暂时只声明 `Json` 与 `Json?`。
影响：挡住 `decode(text)->get<...>` 的一步链式写法；不影响先 `!!` 再取值。
