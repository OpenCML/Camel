任务：`feat/opt` 上一条没人认领的红用例 `fold_struct_cast.in_return_position`——`mk` 的返回位置声明为
具名结构体 `P`，`std::opt` 折出的常量却带着匿名结构体的形状类型。判断是期望错还是编译器错，找出是
哪个改动移动了它。

## 1. 结论：编译器错，期望对

`func mk(): P { return { a: three(), b: 1.5 } }` 的返回值应当是 **`P`**（具名类型），不是
`{ a: int, b: float }`（形状）。依据见第 3 节；用例的断言正是设计原则要求的东西，所以修编译器，
不改期望。

- 错在 `Builder::adaptExitValue`（`src/compile/gir/builder_control.cpp`）：它只在"声明类型**不可
  赋值自**返回值的类型"时才把返回位置的类型套到值上；具名结构体对同序、同名字段的匿名值恰好是
  "可赋值"的，于是转换被跳过，返回值留在形状类型上。
- 移动它的改动是 **H88** 的第 2 个提交 `a87b57d4b`（"Apply a position's expected type in one
  place"）。它删掉了 `visitExitNode` 里自 H5（`44137514`）起就有的"返回位置的结构体显式
  `coerceTo`"那一段，理由是 `adaptExitValue` 已经覆盖；但 `adaptExitValue` 的判据是
  `assignableFrom`，覆盖不了"只差名字"的情况。

## 2. 失败的程序与它的图（修复前）

用例 `test/cases/opt/generic/fold_struct_cast.cml`：

```camel
module fold_struct_cast

type P = { a: int, b: float }

func three(): int { return 3 }

func mk(): P { return { a: three(), b: 1.5 } }

func main(): int sync {
    let p = mk()
    println(p.a)
    println(p.b)
    return 0
}
```

主机上直接跑（Release 构建，`camel <case> std::gir`），`mk` 的图是：

```text
N02 [label="{ a: 0, b: 1.5 }", type="DATA", value_type="{ a: int, b: float }"];
N03 [label="{ a: int, b: float }", type="FILL", value_type="{ a: int, b: float }"];
N03 -> O02 [label="0", type="EXIT"];
```

**没有 CAST**，函数的 EXIT 值直接是匿名结构体类型；同一张图上 `mk` 的 FUNC 节点是
`value_type="P"`，即声明没错，是返回位置的值没有被命名。`std::opt` 之后（用例的形态）折出的常量
`{ a: 3, b: 1.5 }` 仍然是 `value_type="{ a: int, b: float }"`，CAST 数为 0，于是
`assert(out.includes('value_type="P"'))` 失败——这正是用例报的红。

## 3. 它该是什么类型，为什么

设计原则是规范：

- 5.2："**有名字的结构体与 `enum` 是命名类型**：`type Point = { x: float, y: float }` 创建一个新
  类型，它的身份是名字加声明它的模块"；"没有名字的结构体值可以直接用作结构相同的命名类型 …
  **两个命名类型之间必须显式转换**（`m as Seconds`），即使结构相同"。
- 5.1："把值转成它自己的类型是合法的，什么也不做"——转换只命名值被当作的类型，不移动值。

两者合起来是：值在 `P` 的位置上就是 `P`，图上的类型必须是那个名字。若返回位置保留形状类型，名字
就被擦掉了：这个值此后可以不经 `as` 进入另一个同形状的具名类型，正是 5.2 禁止的；`value_type` 也会
对读图的人说错话。H5（`44137514`，"Named struct types are nominal"）把这条落成了实现：
`coerceTo` 对"目标具名 + 源匿名、字段同名同序"建一个 `CAST(target)`（不移动一个字段），字段异序则
逐字段拷贝成目标类型。返回位置本应走同一条规则；H88 之前的 `visitExitNode` 就是显式调用
`coerceTo` 的。

## 4. 是哪个改动移动了它

### 4.1 代码链条

- `StructType::assignableFrom`（`src/core/type/composite/struct.cpp:534`）对"具名目标 + 匿名源"
  按布局返回 **true**（只有"具名 → 具名"才 false）。它是"这个值能不能放在这个位置"，不是"这个值
  是不是这个类型"。
- `coerceTo` 本身是对的：可赋值之后仍会看"目标是具名结构体、类型不相等、转换 Safe"，建出
  `CAST(target)`（`builder_control.cpp:499-508`）。错在**调用点**把它整个跳过了。
- `adaptExitValue` 的判据是 `!position->assignableFrom(valueType)`；对本案它求值为 false，于是既
  不建 CAST，也不走异序拷贝。`git log -S "position->assignableFrom(valueType)"` 指向 `3a7e3e3bc`
  （H5 之前就有的字面量定位工作），那时还没有具名结构体，判据没有问题；具名结构体落地后，
  `44137514` 在 `visitExitNode` 里补了一段显式的结构体 `coerceTo` 绕开它。
- `a87b57d4b`（H88 第 2 个提交）把 `visitExitNode` 收成一句 `resNode = adaptExitValue(...)`，删掉
  了那段绕行；它删的正是本案赖以成立的那一步。H88 的提交信息写"Behavior is unchanged"，验收里却
  没有 `feat/opt`（跑的是 parse/compile/trans/modules/smoke），所以没人看到。

### 4.2 为什么既有用例没抓到

H5 的 `test/cases/trans/cpp/named_structs.cml` 里唯一的具名结构体返回是
`func swap(p: Point): Point { return { y: p.y, x: p.x } }`——字段**异序**，`assignableFrom` 为假，
走的是逐字段拷贝分支，所以一直是对的；没有"同序、只差名字"的返回用例。本案正好是那一种。

## 5. 修复

`adaptExitValue` 的判据由"不可赋值"改成"**不是同一个类型**"：

```cpp
Type *position = expectedExitTypeHere();
if (position != nullptr && !position->equals(valueType)) {
    if (node_handle_t entered = coerceTo(value, position, gct->at(0))) {
        return entered;
    }
}
```

即"位置声明了类型、而值还没有这个类型，就套用它"——与 `checkValue` 在其它每个位置上做的事完全
相同。`coerceTo` 自己决定：字段同序 → `CAST(target)`（不移动），异序 → 拷贝成目标类型，两者都不
成立 → 返回 `nullptr`，值原样留下，由 `checkDeclaredReturn` 报它该报的诊断。

没有放宽任何规则：

- 值已经就是声明类型（`equals`）时不建节点，转换自己的类型仍然"什么也不做"；
- `T?` / `T!` 的装箱不受影响（tag 不同，`assignableFrom` 本来为假，以前也会走 `coerceTo`）；
- 两个具名类型之间仍然不隐式转换：`coerceTo` 的结构体分支要求源是**匿名**的，具名 → 具名照旧
  报"需要显式 `as`"。

## 6. 证据（修复后，Release）

同一条命令、同一份构建：

- `camel <case> std::gir`（未优化）：`FILL`（匿名，作为构造）之后是
  `N04 [label="CAST", type="CAST", value_type="P"]`，EXIT 的值是 `P`。
- `camel <case> std::opt std::gir`：CAST 节点数 **0**，折出的常量
  `N01 [label="{ a: 3, b: 1.5 }", type="DATA", value_type="P"]`。
- `camel <case> std::opt std::jgir`（JSON 导出，报 `outputType`）：该节点
  `"label": "{ a: 3, b: 1.5 }"`，`"outputType": "P"`。
- `std::cpp`（未优化形态；它要求未被换过的入口图）对同一个程序给出 `P mk(...)` 与
  `return P{v1_three, 1.5};`，C++ 后端给返回值的类型也是 `P`。
- 值不变：`std::opt std::nvm`、`std::opt std::fvm`、`std::opt std::jit` 都打印 `3` 与 `1.5`。

两个"报类型"的图导出（`std::gir` 的 `value_type`、`std::jgir` 的 `outputType`）在修复后都是 `P`，
方案要求的那条断言由这两种形态直接钉住（用例用的是前一种）。
