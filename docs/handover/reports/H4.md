## H4d 自动微分支持 `LOOP`（设计）

设计已获语言作者确认（四个问题的答复见 H4d 报告末尾的「决定」），实现分两步：先给循环节点加收集输出，
再由自动微分使用它。本报告这一节记的是设计，不是实现。

依据：设计原则 3.10（循环）、3.5（梯度不经 `var`）、9.9（自动微分是库，不是语言核心）、第 14 节；`docs/design/loops/README.cn.md` §5.6 与 Q12；`docs/technical/39_loops.md`；`include/camel/runtime/loop.h` 的 `LoopView`。

### 1. `LOOP` 是什么、今天怎样执行、拒绝发生在哪里

**节点。** 一个循环是外层图里的一个 `LOOP` 节点（`include/camel/runtime/graph.h:116-123`，节点体 `GCLoopBody`，`:239`）：Norm 入边是「可遍历数组（`For`/`ForWhile`）+ k 个状态初值」，With 入边是条件图与循环体图**共用**的捕获表，Ctrl 入边是顺序；节点体是形式（`While`/`For`/`ForWhile`）与两张子图。节点的值是最后一个状态：k = 1 时是那个值，k > 1 时是 k 元组。`LoopView`（`include/camel/runtime/loop.h:64-130`）是消费者的只读视图：形式、`stateCount`、`stateType(j)`、`iterable()`、`initialState(j)`、`captures()`、`condGraph()`/`bodyGraph()`、两张图的端口（`condStateParam`、`bodyElementParam`、`bodyStateParam`、`cond/bodyCapturePort`）、`nextState()`/`nextStateComponent(j)`、效应摘要。

**执行。** 每一轮的顺序与端口布局只有一份，在 `include/camel/execute/loop_driver.h`：`driveLoopRounds`（`:85-103`）先调条件图（`While`/`ForWhile`），再取下一个元素（`For`/`ForWhile`），再调循环体图，体图的结果就是下一轮的状态；`bindLoopRound`（`:56-71`）把元素、k 个状态、m 个捕获绑进这一轮的帧。解释器只提供帧与调用：`std::nvm` 原生（`NodeVMSchedPass::evalLoop`）、`std::fvm`/`std::jit` 默认在入口用 `lowerLoopsToTailRecursion`（`include/camel/runtime/loop_lowering.h`）降级、`std::macro` 原生意并按 `--max-macro-rounds` 限轮数、`std::prl` 在入口降级（`docs/technical/39_loops.md:90-101`）。

**拒绝。** 在 `modules/autodiff/pullback.cpp:1933-1943`，`Backward::visit` 的 `case GCNodeKind::Loop`：

```
failAt(forward_.nodeOrigin(node),
       "cannot differentiate through a 'loop' expression yet{}; write the loop as a "
       "tail-recursive function, which is differentiated")
```

到达路径：`Engine::gradient`/`Engine::build`（`:2225-2286`、`:2288-2367`）→ `Backward::run` 逆序扫描（`:1624-1629`，只有 `gradients_` 里有梯度的节点才 `visit`）→ `visit`。前向改写 `ForwardRewrite::run`（`:930-970`）不碰 `LOOP`，所以前向图原地保留循环，只有反向扫到它时抛错。它是 `failAt`，**立即抛**，不像函数值的那些拒绝先进 `refused_` 再由 `Engine::refuse` 挑源码序最前的一条。测试：`test/cases/loops/grad_refused.cml`，计划 `loops.grad_refused`、`loops.grad_refused_lowered`（`test/plans/feat/linear/loops.plan.toml:302-324`）。

### 2. 反向：每轮要存什么、存在哪、怎么释放

**存什么。** 不存整份状态，存**每一轮循环体的回传闭包**：`body.fwd` 返回 `(s', pb)`，`pb` 按现有机制捕获这一轮规则要读的残差（`Backward::finishCaptures`，`pullback.cpp:2084-2115`；`addClosure`，`:304-311`）。这就是今天递归版每步在栈上的那一层闭包（`pullback.h:30-34`：「捕获的残差与回传闭包就是磁带」），只是从调用栈搬到堆上、串成一个序列。状态本身不必另存：规则要用的状态值已经是某个残差，会被闭包捕获。

**前向：`LOOP` 多携带一个状态（磁带）。** 在 `ForwardRewrite` 里加一个 `rewriteLoop(node)`（与 `rewriteCall` 同级），用 `Engine::planFor(bodyGraph)`（`:2116-2130`，按图记忆、递归安全）拿到体图的 `(s', pb)` 计划，然后：

1. 体图包装图：端口 `(元素?, s1…sk, tape)` + 同样的 With 捕获；调用 `body.fwd`，`ACCS` 取出 `(s', pb)`，把 `pb` 追加进磁带，`FILL` 出新的 `(k+1)` 元组状态。
2. 条件图包装图（只有 `While`/`ForWhile`）：端口 `(s1…sk, tape)` + 同样的捕获；调用原条件图，丢掉 tape 端口，返回 `bool`。
3. 原地改造这个 `LOOP` 节点：节点体换成两张包装图，Norm 入边末尾补一条**空磁带的常量**（元素/初值/次序不变），节点类型改成 `(状态, 磁带)`；With 入边不动（捕获表本来就只有一份）。
4. 记账成一次「调用点」：`state = ACCS 0(loop)`、`tape = ACCS 1(loop)`、`pb = addClosure(forward, 反向循环图, pb 类型, {tape})`，把 `loop` 的所有值使用者换成 `state`，并把 `sites_[state] = CallSite{pb, inputs = 捕获… + 初值…, plan}`。这一步的簿记与 `ForwardRewrite::split`（`:979-1019`）逐行相同（`replaceAllValueUses`、`sites_` 里输入的重定向、Ctrl 使用者与 output/exit/return 的重定向），只差 `split` 现在假定**节点自己的值**已经是 `(value, pullback)`，而 `LOOP` 的值是 `(状态, 磁带)`。建议把 `split` 抽成 `split(valueNode, pullbackNode, plan, inputs)` 两个节点都传入的形式，一处实现两种节点共用；不要复制一份 `splitLoop`。**`Backward` 一行都不用改**：`Backward::visit` 先查 `sites_`（`:1892-1895`），命中就走 `visitCallSite`，用 `plan.tangentIndex` 把返回的切向量分别累加回 `initialState(j)` 与 `captures()[c]`（`:1952-1968`）。`plan` 用 `makePlanTypes` 造，端口序按现有约定「With 在前、Norm 在后」（`portTypesOf`，`:446-454`；`pullback.h:66-72`）。

**反向：一个倒着走的 `While` 型 `LOOP`。** 状态 `(i, ds…, dc…)`：`i = len(tape) - 1`，条件 `i >= 0`；每轮 `pb = tape[i]`、`(ds, dc_i) = pb(ds)`、`dc += dc_i`、`i -= 1`；循环的值是最终的 `(ds_0, dc)`。循环体图是新造的：`:op/idx_arr`（`src/builtin/modules/globals.cpp:1143-1157`）取元素、`addCall`（`pullback.cpp:264-270`，动态 `CALL`，被调值是磁带元素）调用、`ACCS` 拆元组、`:op/add` 累加、`:struct/len_arr`（`:1338`）算长度、常数 1 与减法走下界。一轮也不执行时（空磁带）反向循环不跑，`ds_0 = dy`、`dc = 0`，与「循环的值就是初值」一致。

**与图存储 / GC 的关系。** 新造的四张图（两张包装图、反向循环的条件图与体图）是 `Engine::group_` 里普通的 `GraphDraft`（`reserve`/`define`，`pullback.cpp:2344-2366`），随整个导数一起由 `GraphDraftGroup::encode` 编码（`src/runtime/draft_session.cpp:1041-1076`）——它对 `GCLoopBody` 的两个图指针本来就走同一套前向引用重映射（`visitDraftGraphs` `:355-403`、`encodeDraftGraph` `:475-542`），与 `addFuncNode` 的被调图一样。`GraphDraft` 有 `addCallNode`/`addLoopNode`（`include/camel/runtime/draft.h:324,332`）。**不动图存储、不动 GC**：唯一新增的是「多一个数组值」。峰值内存 = 轮数 × 每轮残差（与递归版每一帧同量级，只是不在栈上），在整个反向期间都必须活着。

一个实现细节：`LoopView` 只接受冻结的 `GCGraph`，而变换手里是 `GraphDraft`。建议在 `camel/runtime/loop.h` 增加一个 draft 版访问器（或 `LoopShapeOf(const GraphDraft&, node)`），让端口布局的知识仍然只有一处，而不是在 autodiff 里再抄一遍 `element? + k` 的约定。

### 3. 轮数未知时怎么办

**设计不需要提前知道轮数。** 磁带是运行期长出来的数组，长度就是实际轮数，反向循环从 `len(tape)-1` 开始；`While` 的轮数由条件决定、`For` 的由数组长度决定，两者都不进入变换期的判断。代价只有一项：**存下每一轮**，`O(轮数)` 的堆内存。

三种取磁带的方式，代价差别很大：

| 方式 | 每轮代价 | 总计 | 备注 |
|---|---|---|---|
| (a) 节点增加「收集输出」（scan output，ONNX `Loop` 的 scan） | O(1) | O(n) 内存、O(n) 拷贝 | 执行器每轮把一个值收进数组；要改节点定义（op-semantics 11） |
| (b) 体图里 `:struct/append_arr`（`src/builtin/operators/struct.cpp:215-223` 每轮复制整个数组） | O(i) | **O(n²) 拷贝** | 不改任何东西，今天就能写出来 |
| (c) 不存，反向时重算 | 内层重算 i 轮 | O(n²) 时间、O(1) 内存 | 导出器对尾递归的梯度就是这么做的（`modules/onnx/exporter.cpp:1621-1640`：「no tape: the cost is quadratic in n」） |

设计取 (b) 做第一步的实现（正确、零新机制），目标形态是 (a)（线性、且正好对应 ONNX 的 scan output，见 `docs/design/loops/README.cn.md` §5.6 与 Q12）；(c) 作为对照保留。**是否允许磁带无上限地长、要不要一个上限或检查点（checkpointing）策略，不在本设计里定**（见 Q2）。

### 4. 嵌套与并行

**循环套循环。** 内层循环就是外层循环体图里的一个节点。外层体图被 `Engine::planFor` 登记成一个待建计划；外层的反向扫到内层 `LOOP` 时，同一条 `rewriteLoop` 再走一遍，得到内层的「前向循环 + 反向循环」，它们活在外层体图的 `.fwd` / `.pb` 里。内层磁带在外层每一轮里新建，被内层的 pullback 捕获，再被外层追加进外层磁带——内存是各轮内层磁带之和，这是反向模式本身的代价，不是这套设计的额外开销。计划的递归安全由现有的 `plans_` 记忆与 `pending_` 队列保证（`:2116-2130`、`:2349-2361`）。条件图不需要导数（`bool` 没有切向量），所以条件图里的循环不会被改写；条件图本身也不进计划。

**对并行调度器的要求。** 循环按定义严格顺序（原则 3.10、`docs/design/loops` 4.6；`std::prl` 在入口降级，`39_loops.md:97`），梯度不要求调度器新增任何并行能力，但要求四件事：

1. 轮与轮之间不得拆成任务、不得重排；反向循环是顺序折叠，不能被当成 `unordered_reduce`。
2. **每一轮必须是 GC 安全点**：梯度的前向循环每轮分配一个闭包。今天 `driveLoopRounds` 的 `beforeRound` 提供了它（nvm 与 macro 原生执行、降级形态走调用边界）；将来 `std::fvm` 的原生字节码循环（`39_loops.md:170-173`）必须在回边补一个，否则不断分配的循环永远不回收。
3. 即时编译不得编译会分配的循环体：`std::jit` 的资格判定只收纯标量图（`src/passes/sched/jit/x64_backend.cpp:102-151`），梯度循环含 `CALL`/`FILL`，自然不入选；这条限制要写进判定而不是靠运气。
4. `std::prl` 每次运行对「执行期拿到的函数图」的降级缓存（`39_loops.md:111-119`）同样适用：合成出来的循环要么被降级、要么被原生执行，不能出现「源码图有 `LOOP`、字节码按降级帧布局执行」的错配——这一点现有实现已经排除，梯度图只是多几个循环，不需要新规则。

另一个附带后果：`std::macro` 的轮数上限对两个循环都计数，`grad` 下的循环实际上限减半（前向 n 轮、反向 n 轮）。

### 5. 待决问题

#### Q1：磁带放在哪里——给 `LOOP` 增加「收集输出」，还是先用复制式 `append`，还是重算？

例子：`let dp = grad(loss)(p0)`，`loss` 里是 `loop p = p0 for d in ds do step(p, d)`；轮数 n 未知。
建议：**第一步用 (b)（`:struct/append_arr`，O(n²) 拷贝），目标形态 (a)（节点的 scan output，O(n)）**；(c) 只在需要「零额外内存」时用。选 (a) 要改节点定义与 op-semantics 11，并影响 ONNX 的 `Loop` 映射（§5.6、§5.7、Q12），是语言表面的契约，所以由语言作者定；它不确定下来不挡第 1–2 步的实现。
影响：不定 (a) 就只能交付二次代价的梯度（今天导出器的梯度就是二次的）；定了 (a) 才能同时把「梯度的 ONNX 导出」做成线性。

#### Q2：长循环的磁带允许无上限吗？要不要上限或「拒绝」

例子：`loop acc = 0 for x in xs do acc + f(acc, x)`，`xs` 有一千万个元素，求梯度要留一千万份残差。
候选：不设上限（今天递归版的栈也不设，深浅由用户控制）；给 `grad` 一个可配置的轮数上限，超过按资源耗尽处理并带位置报告；用检查点技术把内存降到 `O(√n)` 但多算一遍。
建议：**先不设上限**，与现有递归梯度一致；如果要设，必须同时写进 `docs/cli.md` 的资源上限表，并且是「故障」还是「编译期拒绝」要定清楚（编译期无法知道轮数，所以只能是运行期故障，或者按「循环最多可能跑多少轮」在静态可判时拒绝）。
影响：不定它，第 1 步按无上限实现；定了才谈检查点。

#### Q3：循环遍历的数组本身依赖被求导的参数时，拒绝还是支持？

例子：`func f(w: float): float { return loop acc = 0 for x in scale(xs, w) do acc + x }`。
现状：数组今天没有切向量（`op/idx_arr`、`map` 都没有规则），把它的梯度丢掉不会有任何提示。
建议：**拒绝**，诊断带位置，措辞沿用「数组不是可微值」这一类；与 `map` 的拒绝一致。以后要支持，得先有数组的切向量，那是另一个任务。
影响：不拒绝就会静默返回错误梯度；拒绝则这部分循环暂时不可求导。

#### Q4：循环体（或条件）里有副作用时，`grad` 允许吗？

例子：`loop acc = 0 for x in xs do sync { println(x); acc + x * w }`。
现状规则：`grad` 允许被求导的函数有副作用，前向照常执行（`docs/technical/26` 4.4 末），反向是纯的。按同一规则，循环体的效应在前向每轮执行一次，反向不再执行。
建议：**沿用现有规则**（允许，效应只在正向发生），只把「可微类型的 `var` 在循环体/条件里被读」按 3.5 拒绝（循环体是子图，等价于「在被调函数里读」，`checkVariableReads` 的现有判据扩展到两张子图）。
影响：若作者认为循环体内的效应应当拒绝，诊断与测试要另写；`var` 那一条属于库的既有约束，不是新语义。

#### Q5：梯度的 ONNX 导出是否与本设计的磁带方案同批做？

例子：`onnx::export` 一个含 `loop` 的梯度函数（今天 `loops.onnx_refused*` 直接拒绝）。
建议：**不在 H4d 内做**；但第 1 步选磁带形态时要照顾它（(a) 的 scan output 正好对应 ONNX `Loop` 的 scan output，闭包要按捕获的叶子展开）。
影响：只影响顺序，不影响本设计能否落地。

### 6. 第一版做什么（最小的可用增量）

每步都能单独合入、且**只放开一种形状，其余形状继续按 §1 的 `failAt` 拒绝**（宁可拒绝，不可静默丢梯度——这是库里现有的取舍，`pullback.cpp:1919-1932` 的注释是同一理由）。

1. **`For`、k = 1、无捕获、`tape` 用 `append` 数组。** 加 `rewriteLoop`：两张包装图 + 原地改造 `LOOP` + 把 `split` 抽成共用形式后记 site + 反向 `While` 循环；`Backward` 不改。验收用例就是最小的那个循环，例如
   `func f(x: float): float { return loop y = x for k in [1.0, 2.0, 3.0] do y * k }` → `grad(f)(x)` 应得 6（1·2·3）。
   与有限差分对比，跑 `std::nvm`、`std::fvm`、`std::macro`（`grad` 需要 `std::macro`）。其余形状（`While`、有捕获、k > 1）仍走旧拒绝，把 `case GCNodeKind::Loop` 的消息改成具体缺哪种形状。
2. **捕获（权重）**：累加 `dc`，把 `plan` 的端口序与 `sites_` 的 `inputs` 对齐。这是训练的实际形状（`loop p = p0 for d in ds do step(p, d)` 的 `p0` 与捕获的权重都要求导），用例对权重与初值都做差分对比。
3. **`While`/`ForWhile`（条件包装图）与 k > 1 的元组状态**：`nextStateComponent` 展开、切向量按 `ACCS` 拆。
4. **嵌套**、以及 Q3/Q4 的拒绝规则：活跃的可遍历数组、循环体/条件里的 `var` 读、效应策略；`checkVariableReads` 扩展到两张子图，诊断文本点名 `loop`。
5. **按 Q1 换磁带形态**（`scan output`），把第 1 步的二次代价改成线性；之后再做 Q5 的梯度导出，并退役 `loops.grad_refused*` 两个拒绝测试（改成有限差分正例，理由写进提交信息，不是为通过而改期望）。

顺带要改的既有测试：`test/cases/loops/grad_refused.cml` 与 `test/plans/feat/linear/loops.plan.toml:302-332` 的两条拒绝在对应步骤完成后变成正例；`loops.grad_refused_lowered` 的「降级之后仍拒绝」这条语义随之消失（`39_loops.md:121-130` 有关 `:graph/original` 的那段行为不变）。

## H4c ONNX 导出 `ArgMax`

分支：`handover/H4cf-onnx`（worktree `D:\Projects\Camel-wt\h4cf-onnx`），2026-10-20。

### 做了什么

`modules/onnx/lowering.cpp` 的 `lowerArgMax` 之前发一个 ONNX `ArgMax`（`axis`、`keepdims`）就返回。ONNX `ArgMax` 的 `select_last_index=0` 只保证并列取第一个；NaN 的排序未定义，`-0` 与 `+0` 比较相等，所以它不实现设计原则 7.7。现在按元素类型分三路：

- `int64`：直接 `ArgMax`（整数没有 NaN 和 `-0`，「首个最大」就是 7.7）。
- `bool`：`Cast` 到 `int64` 再 `ArgMax`（false < true，没有 NaN）。
- `float32`/`float64`：组合子图，见下。其它元素类型抛 `ExportError`；`exporter.cpp` 的 `applyOper` 会把源码位置加到最内层节点，诊断因此带位置。

注册的最低 opset 改为 12（`add("tensor:argmax_axis", lowerArgMax, 12)`）：`select_last_index` 是 opset 12 引入的，组合里靠它保证并列取第一个。

### 组合出的子图（float32/float64）

记输入 `x`，归约轴 `a`；所有 mask 都与 `ArgMax` 的结果同形（`keepdims` 与调用一致），因此不需要 `Squeeze`：

1. `nanMask = Not(Equal(x, x))` —— IEEE 754 的 NaN 判据（`x != x`）。
2. `hasNaN = Cast(ReduceMax(Cast(nanMask, int64), a, keepdims), bool)` —— 该轴有没有 NaN。
3. `nanFirst = ArgMax(Cast(nanMask, int64), a, keepdims, select_last_index=0)` —— 第一个 NaN 的位置。
4. `y = Where(nanMask, -inf, x)` —— NaN 不再参与数值比较；用 -inf 而不是 0，保证它不会赢过任何有限值或 +inf。
5. `valueFirst = ArgMax(y, a, keepdims, select_last_index=0)` —— 数值最大者中第一个的位置；`y` 里已经没有 NaN。
6. 有符号零：`plusZero = And(Equal(y, 0), Greater(Reciprocal(y), 0))`，`anyPlus = Cast(ReduceMax(Cast(plusZero, int64), a, keepdims), bool)`，`plusFirst = ArgMax(Cast(plusZero, int64), a, keepdims, select_last_index=0)`，`maxValue = ReduceMax(y, a, keepdims)`，`usePlus = And(Equal(maxValue, 0), anyPlus)`。
7. `value = Where(usePlus, plusFirst, valueFirst)`：最大值是 0 且轴上有 +0 时取第一个 +0（7.7 的 +0 > -0），否则取第一个零（此时只有 -0）。
8. `result = Where(hasNaN, nanFirst, value)`：有 NaN 时第一个 NaN 胜出。

`Reciprocal(+0) = +inf`、`Reciprocal(-0) = -inf` 是 ONNX Runtime 的 IEEE 行为，也是这里不经过位级访问就能区分两种零的写法。标准 ONNX 没有 `Bitcast`（我在 opset 17 上试过：`No Op registered for Bitcast`），所以没有位级方案。

### 用到的 ONNX 算子

`Equal`、`Not`、`Cast`、`ReduceMax`、`ArgMax`（`select_last_index=0`）、`Where`、`Reciprocal`、`Greater`、`And`；`bool` 输入多一个 `Cast` 到 `int64`。能力表 `modules/onnx/capabilities/onnxruntime-cpu.json` 里这些算子对 `float32`/`float64`/`int64`/`bool` 都支持，不需要改能力表。

### 测试与结果

新用例 `test/cases/modules/onnx/ort_argmax.cml`：从 `float32 [2,8]` 和 `int64 [2,8]` 各导出一个三元组 `(argmax(x,1), argmax(x,1,true), argmax(x,0))`，所以也覆盖了「轴不是最后一维」。`test/cases/modules/onnx/ort_argmax.py` 用 NumPy 按 7.7 独立算期望（整数按首个最大），在 ONNX Runtime 上跑固定用例：并列、有 NaN（第一个 NaN 胜出）、`-0`/`+0` 混排、全 NaN、负数、`+0` 在 `-0` 之后、`±inf`、全相等；`float32` 另加 40 组随机数组（含 NaN 与两种零），`int64` 加 20 组随机数组。计划项 `ort_argmax` 在 `test/plans/feat/modules/onnx.plan.toml`，`skip_unless` 检查 numpy/onnx/onnxruntime。

结果：`ort argmax: 0 failing`、`PASS`；整个 ONNX 计划 125/125 通过（含本条与下面的切片用例）。没有跳过的用例。

### 待决问题

1. **`argmin` 仍不导出。** `tensor:argmin_axis` 没有 ONNX lowering，所以 7.7 的 argmin 规则（第一个最小值；有 NaN 时第一个 NaN；`-0 < +0`）在导出器里仍是拒绝。H4c 只要求 `ArgMax`；补 `argmin` 需要对称的组合（`ArgMin`、`+inf` 替换、`-0` 优先）或共享同一个子图生成器。要不要现在补？
2. **`Reciprocal` 的零行为是后端契约。** 这里依赖 `1/+0 = +inf`、`1/-0 = -inf`；ONNX 规范没有把除零写成强制语义，ONNX Runtime 的 CPU 后端按 IEEE 实现，测试也覆盖了。对另一个后端，+0 修正可能不成立；如果要更稳，需要 ONNX 增加 `Bitcast`（目前没有）。是否把这一条写进能力表/后端契约？
3. **opset < 12 的导出被拒。** 组合依赖 `select_last_index`，最低 opset 因此是 12；更早的 opset 上旧版 `ArgMax` 规范本身也是取第一个，但组合里的 `ArgMax` 没有 `select_last_index` 可用，NaN/-0 仍要靠组合。当前导出器默认 opset 是 17，实际不受影响；如果以后要支持 11，需要确认旧版 `ArgMax` 的「第一个」保证并去掉属性（未验证）。

## H4f ONNX 导出器的切片规则

### 问题

审查 `modules.cn.md` 第 14 条：导出器不能自己重述「切片越界是故障」这类规则。改之前 `lowerSlice` 重述了三件事：轴的归一化、`step > 0`、以及「边界必须在 `[-n, n]`」。最后一条甚至没有写出来：它用 `Gather` 一个长度 `n+1` 的零向量、下标 `b - (b < 0)` 来制造越界故障，正确性依赖 ONNX `Gather` 允许最小 `-(n+1)` 的负下标，这个证明只存在于注释里。核心的 `sliceIndexing` 遇到依赖模型的边界直接返回 `nullopt`，导出器读不到规则，只能自己写。

### 改了什么

**核心声明（一份规则）。**

- `include/camel/core/index_semantics.h`：新增 `OperandCheck { operand, param, lower, upper, onInvalid }` 和 `IndexedInstance::checks`。它说的不是访问映射，而是「这个操作数在进入时必须落在 `[lower, upper]`，否则按 `onInvalid` 处理」；切片的越界故障第一次进入声明，而不是导出器的注释。
- `src/core/index_semantics.cpp`：`validate()` 检查 `operand` 是合法操作数、`param` 是同一操作数的 `Static`/`Runtime` 参数、上下界是只含参数与常量的表达式（`Exprs::mentionsDim` 为假，因为 check 约束的是参数）；`toString()` 加一行 `check operand i in [lo, hi] else fault`，`tensor::test_index_eval` 的 `show_*` 查询因此能看到它。
- `modules/tensor/ops/indexing.h` / `indexing.cpp`：`IndexBuilder::runtime(name, operand)`（Runtime 参数）与 `IndexBuilder::check(operand, param, lower, upper)`。`sliceIndexing` 重写：
  - `axis` 是 `Static` 参数（归一化后的轴），`step` 是 `Static`（缺省 1）；
  - `n = extent(0, axis)`；
  - `start`/`stop` 是 `Derived` 参数：常量边界且 extent 已知时带值（值由 `kernels::normalizeSliceBound` 算），否则没有值（归一化要按符号分支，不是准仿射表达式，参数只声明它的范围）；
  - 原始边界：常量是 `Static`，依赖模型的是 `Runtime`；只要归一化值未知，就加 `check(operand, raw, -n, n)`；
  - `len` 是 `Derived`，只在两个边界都已知时带值；`where` 仍是 `0 <= start <= n`、`0 <= stop <= n`、`0 <= len`、`1 <= step`。
  - 常量边界 + 未知 extent 以前返回 `nullopt`（「等 extent 知道再说」），现在也给出实例：边界照样进 check，归一化值未知。这保留了旧导出器在这个形状上的能力，也是 `tensor::test_index_eval` 里 `slice_unknown_extent` 从 `none` 变成 `instance` 的原因（计划里的期望已改，理由写在这里）。
- `modules/tensor/kernels/layout.h`/`layout.cpp`：把「一个边界怎么归一化」抽成 `normalizeSliceBound(extent, bound)`，`normalizeSliceBounds` 调它两次；声明与 kernel 从此读同一个函数，边界规则只有一份。

**导出器读声明。**

- `modules/onnx/lowering.h`：`LowerContext` 带一个可选的 `core::sem::IndexedInstance`，`instance()` 只读访问；`modules/onnx/exporter.cpp` 的 `applyOper` 在调用 `def->infer` 之后，对声明了 `index` 的算子调 `tensor::ops::instantiate(*def, inferContext)`，把实例传下去。导出器不再自己调 `instantiate` 或猜参数位置。
- `modules/onnx/lowering.cpp` 的 `lowerSlice`：
  - 从实例读 `axis`（`Static` 参数 1）、`step`（`Static` 参数 4，缺省 1）、以及操作数 2/3 的 `check`；
  - 两个边界都是常量且声明没有 check（即声明已证明在范围内）时，发普通 `Slice`，直接用原始常量（ONNX `Slice` 自己会归一化负边界）；
  - 否则逐个边界发 guard：常量也 guard（未知 extent 的常量边界现在有 check）；`check` 的区间必须正好是以轴 extent 参数为中心的 `[-n, n]`（用 `Extent` 参数 + `isNegationOf` 验证 `lower = -upper`），否则拒绝并说明「ONNX 的 guard 表达不了这个区间」；
  - guard 仍是 `Gather(zeros[n+1], b - (b < 0))`，但现在它的合法性来自声明的 `[-n, n]`，不是导出器自己记得的规则；`zeros` 的长度 `n+1` 来自 `Shape`，所以 extent 可以在运行时才知道；
  - 没有实例、没有 check、check 不是 fault、区间不是 `[-n, n]`、或 `speculative()` 分支臂上的边界无法证明时，抛带位置的 `ExportError`，消息点名 `tensor:slice`、轴和原因，不再 clamp 或猜。
- 结果形状：走 guard 的路径把该轴的长度标成未知（`kUnknownDim`），因为 guard 只保证不越界，不保证长度；常量且已证明的路径用 `sliceInfer` 的结果形状。

### 用到的 ONNX 算子

普通路径：`Slice`。guard 路径：`Shape`、`Gather`、`ConstantOfShape`、`Cast`、`Less`、`Sub`、`Add`、`Unsqueeze`（`n+1` 个零、负下标修正、把标量边界升成 1 维）。没有新增能力表条目。

### 测试与结果

- 新用例 `test/cases/modules/onnx/ort_slice_start.cml` / `ort_slice_start.py`，计划项 `ort_slice_start`：
  - `MODE=start`：`slice(x, 0, int(sum(x)), 3)`，在 ONNX Runtime 上跑 start = 3、1、0、-2、-3（有效，含 `-n` 与 0）和 -4、4、-5（Camel 故障、ORT 也必须失败）。这组值把「区间是 `[-n, n]` 而不是 `[0, n]`」「负值从尾部数」「end 在 start 之前是空区间」分开；如果把规则重述成 clamp 或把下界写成 0，`-2`/`-3` 或 `-4` 会不同。
  - `MODE=constant`：`slice(x, 0, -2, 3)`，常量边界 + 已知 extent 走普通 `Slice`，期望 `x[-2:3]`。
  - `MODE=dynamic`：常量边界 `[1:3]` 落在 `reshape(x, [int(12/sum(x)), int(sum(x))])` 的轴上，extent 只有运行时才知道；sum 为 12/6/4/3 时有效，为 2/1 时 Camel 故障、ORT 也必须失败。这覆盖「未知 extent 的常量边界也要 guard」，以及旧导出器有、重构中一度丢掉的能力。
  - 结果：`ort slice start: 0 failing`、`PASS`。
- 原有用例保持：`ort_slice_bounds`（依赖模型的 end）`0 failing`；`ort_time_axis` `14 models, 0 failing`；`bounds.plan.toml` 8/8（含 `slice_runtime`、`slice_untaken_branch`）；`index_semantics.plan.toml` 5/5；整个 ONNX 计划 125/125（含 `export_slice_loop`、`pass_export_slice_loop`、`ort_slice_bounds`、`ort_time_axis`、`ort_argmax`、`ort_slice_start`）。
- 跳过的：没有。ORT 用例的 `skip_unless` 只在没有 numpy/onnx/onnxruntime 时跳过；本次环境有（onnx 1.23、onnxruntime 1.30），实际执行。

### 待决问题

1. **未知 extent 下的声明不自足。** `len` 与 `start`/`stop` 之间没有约束（准仿射表达式不能写 `len = max(0, ceil((stop - start)/step))`，也不能写「非空时 `start + step*(len-1) < stop`」这种带条件的式子），所以「访问在 `[0, n)` 内」只对算子的实际参数值成立，不能从 `where` 推出来。`tensor::test_index_eval` 对未知参数不做符号检查，导出器只用 `check`，因此不影响本次；但一个想从声明做静态证明的消费者会缺这一条。要不要给表达式语言加 `max`/`ceil` 或析取？
2. **常量边界的归一化要 extent。** 现在未知 extent 的常量边界给出实例、带 check，但 `start` 的归一化值仍是未知；如果以后有消费者需要「常量边界的归一化值」，它必须先专门化 extent。这是有意的（负常量的归一化确实依赖 extent），不是遗漏。
3. **`speculative()` 的拒绝仍然存在。** 分支条件依赖模型时，导出器无法证明该臂上的切片边界在范围内，仍拒绝；旧导出器也拒绝。`slice_untaken_branch` 覆盖的是「分支没被走到」的另一类情形（它通过）。如果以后要给分支臂做按条件的 guard，需要 ONNX `If` 里也能表达故障，这超出 H4f。
4. **`lowering.cpp` 变长了。** 现在 1160 行，超过 `agents/refactor.md` 对新文件建议的 800 行；它是既有文件，本次没有拆。如果要拆，`lowerArgMax` 与 `lowerSlice` 可以进单独的文件，但会牵动匿名命名空间里的 `reduceAxes`/`findParam` 等共享 helper，建议单独一次改动。
### 决定（语言作者，2026-10-20）

1. **磁带存残差值，循环节点加「收集每轮输出」**：每轮 O(1)、总体 O(n)；残差是普通值，ONNX、`std::cpp` 都能表示，将来导出只加一张映射。不先做"每轮复制整个数组"的版本。这是图层面的能力，不新增源码语法；改节点定义，同步改算子语义第 11 节与共用的循环驱动。
2. **磁带不设上限**：轮数无法在编译期知道，人为上限只会让正常的长训练失败；内存耗尽按资源耗尽带位置报告，不在命令行另加轮数上限。将来用 `#recompute` 检查点降到 O(√n)，本次不做，但磁带设计不排斥它。
3. **遍历或捕获的数组本身依赖被求导的参数时拒绝**，带位置诊断，与 `map` 的拒绝一致；判据是"该数组在活动集里"，诊断点名 `loop` 与哪个数组。给数组补切向量是另一个独立任务。
4. **循环体有副作用时沿用现有规则**：允许，效应只在正向执行一次，反向是纯的；"读可微类型的 `var` 要拒绝"这条检查扩展到条件图与循环体，诊断点名 `loop`。
5. **ONNX 导出不同批做（A）**：先把语言里的循环梯度做对；磁带按"残差值 + 槽位清单"设计，导出时只加映射、不改表示。`While` 的导出成立（`trip_count` 可选，只靠条件停止；反向轮数就是收集到的个数），嵌套循环的参差数组留到导出时处理（ONNX 序列类型）。

## H4e 数学模块的数值声明

### 做了什么

- 新增 `modules/math/semantics.cpp` 与 `modules/math/semantics.h`：`math` 模块 89 个算子的数值语义声明集中写在一张表里（照 `modules/tensor/ops/semantics.cpp` 的写法），每条记录用 `OperatorTable::declareSemantics` 在模块加载时登记，版本 1.0。
- `modules/math/module.cpp`：在登记完全部算子的 traits 之后调用 `declareMathOperatorSemantics()`（登记检查第 2 条要读 traits）。
- `modules/math/CMakeLists.txt`：把 `semantics.cpp` 加进模块源文件。
- `test/plans/feat/modules/operator_semantics.plan.toml`：新增 `declared_math_numeric_semantics`，用 `camel inspect --ops` 观察声明，并对每个 math 算子核对类别、计算类型、许可敏感性、ulp 与特殊值。

### 哪些算子得到什么声明

`math` 模块导出的全部 89 个算子都有记录；没有遗漏，也没有第二个声明机制。

| 类 | 算子（URI 后缀） | 声明 | 许可敏感性 |
|---|---|---|---|
| `Exact` | `abs_f/d`、`round_f/d`、`ceil_f/d`、`floor_f/d`、`trunc_f/d`、`min_f/d`、`max_f/d`、`clamp_f/d`、`sign_f/d`、`is_nan_f/d`、`is_inf_f/d` | 无舍入；`compute` 为 f32/f64 | `finite_math`（NaN、±0、次正规数的假设可以改变结果） |
| `Exact` | `abs_i/l`、`min_i/l`、`max_i/l`、`clamp_i/l`、`sign_i/l`、`gcd_i/l`、`lcm_i/l`、`bit_and_i/l`、`bit_or_i/l`、`bit_xor_i/l`、`bit_not_i/l`、`shl`、`shr`、`bin_i/l`、`oct_i/l`、`hex_i/l` | 无舍入、无算术舍入；`compute = Void` | 无（`reassociate`/`contract`/`approx_math`/`change_precision`/`finite_math` 都改不了） |
| `CorrectlyRounded` | `sqrt` | 一次正确舍入的开方；`compute = Float32` | `approx_math`、`change_precision`、`finite_math` |
| `Bounded` | `exp_f/d`、`log_f/d` | **2 ulp**；`compute` 为 f32/f64 | `approx_math`、`change_precision`、`finite_math` |
| `Bounded` | `sin_f/d`、`cos_f/d`、`tan_f/d`、`asin_f/d`、`acos_f/d`、`atan_f/d`、`sinh_f/d`、`cosh_f/d`、`tanh_f/d`、`log2_f/d`、`log10_f/d`、`log1p_f/d`、`expm1_f/d`、`atan2_f/d`、`pow_f/d`、`hypot_f/d` | **4 ulp**；`compute` 为 f32/f64 | 同上 |

补充说明：

- `math:sqrt` 是四个数值类型共用一条 URI（i32/f32 → f32，i64/f64 → f64），所以记录写的是窄的浮点情形（f32），算法说明里写明宽的那一路；这与张量声明“描述 f32 情形”的约定一致。
- `pow` 与 `hypot` 的 `specials.nans = false`：C 标准规定 `pow(x, ±0)`、`pow(1, y)` 即使另一个操作数是 NaN 也得 1，`hypot(±inf, NaN)` 得 `+inf`，不是 NaN 传播。其余算子保持 IEEE 特殊值（NaN、±inf、±0、次正规数都精确）。
- 故障（`clamp` 的 NaN 边界/lo>hi、`gcd`/`lcm` 溢出、`shl`/`shr` 越界计数）这次没有声明 `FaultSpec`：第 15 条要的是数值语义；traits 仍是 `mayFault = true`，消费者按“可能故障”保守读。见“没做完的”。
- `math.abs` 的最小整数：`docs/stdlib-reference.md` 已写明“没有正对应值，绝对值未定义”，实现的 `std::abs(INT_MIN)` 因而落在定义域外；声明的算法串里如实写了这一点，没有把它当成声明与实现不一致，也不把它算作未声明的故障。

### 每个上界的来源

- `exp`、`log`：**2 ulp**。设计原则 7.1 直接写了“标准库的目标是 `exp`、`log` 不超过 2 ulp”；语言参考（`docs/language/03_data_model.md`）也这样写；张量模块的 `tensor:exp`/`tensor:log` 已经声明 2 ulp（`modules/tensor/ops/semantics.cpp`），这里保持一致。
- 其余 `Bounded`：**4 ulp**。C++ 标准不规定 C 数学函数的 ulp 精度。Windows 上的实现是 UCRT，微软文档说的是“多数情况在 ±1 ULP 内，但也可能有更大的误差”，并且结果可能随 CPU 和 Windows 版本变化（[Math and floating-point support](https://learn.microsoft.com/en-us/cpp/c-runtime-library/floating-point-support?view=msvc-170)），所以 1 ulp 不是可以承诺的上界。4 ulp 与 `docs/design/op-semantics` Q4 的候选 A 给 `tanh`、`sigmoid`、`gelu`、`erf` 举的库目标一致，也给跨 CPU/系统版本留了余量。
- `sqrt`：设计原则 7.1 要求开方按 IEEE 正确舍入；IEEE 754 也要求 `sqrt` 正确舍入。声明为 `CorrectlyRounded`，不给 ulp 上界。
- 这些上界是**承诺**，不是对某台机器实测结果的复述；实测只是确认当前平台没有超出承诺。

- **自动微分**：`math:sqrt` 的 VJP 在 `modules/math/module.cpp` 按 URI 登记，不读数值声明，也不需要读：反向规则是算子自己的事，数值声明描述前向算子的误差。没有新增按名字的特例。

## H4d 第一步：循环的收集输出

分支/工作区：`handover/H4d-impl`（`D:\Projects\Camel-wt\h4d-impl`），2026-10-20。本步只做「循环节点 + 执行器收集输出」；自动微分本身的重写（前向/反向循环）与 ONNX 导出**不在本步**，`pullback.cpp` 与 `modules/onnx` 未改。

### 1. 前提（负责人 2026-10-20 的裁定，照录，不再讨论）

- 磁带存**残差的值，不是闭包**；循环节点获得「收集它每轮产生的值」的能力。
- 选「节点上的收集输出」，并直接实现原地追加；**不做** `:struct/append_arr` 的 O(n²) 版本。每轮 O(1) 摊还、总计 O(n)；残差是普通值，ONNX 与 `std::cpp` 能表示；与图存储 v2 的「控制区域每轮收一个值」同形。
- 不设轮数上限；内存耗尽按资源耗尽（`RuntimeDiag::MemoryExhausted`）带源位置报出。
- 不排除将来的 `#recompute` 检查点标签（O(√n)）；磁带的表示不因它改变。
- 导出与 Q3/Q4 的拒绝规则是后续步骤；**磁带的表示不因导出而改变**。

### 2. 节点形状

`LOOP` 的载荷（`GCLoopRef` 与 `GCLoopBody`）里原 `reserved2` 改名为 `collectionCount: uint32_t`（`include/camel/runtime/graph.h`；大小不变，`GCLoopRef` 仍是 16 字节），`loopCollectionCountOf`/`setLoopCollectionCount` 读写它，编解码、克隆、会话的图枚举都照旧经过它。有 `s` 个收集槽时，**节点的值类型**是 `(T_0 … T_{k-1}, U_0[] … U_{s-1}[])`：前 k 个分量仍是状态（忽略磁带的消费者读到的位置不变），后 s 个是每轮收集的数组；**循环体图的返回类型**是 `(T_0 … T_{k-1}, U_0 … U_{s-1})`，第 c 个收集槽每轮交出一个 `U_c`。`s = 0` 时与今天完全相同（k = 1 给那个值，k > 1 给 k 元组）。计数必须放在节点里：k = 2 时值 `(状态, 数组)` 与「两个状态、第二个恰是数组」在类型上无法区分。数组由这次循环独占（循环体看不到它们），随工作元组被 GC 追踪。

**设计上的选择。** 备选是「载荷里显式列出每个槽的类型」。否掉的理由：节点的值类型与循环体图的返回类型已经逐位给出了这些类型，再存一份会多一处可不同步的真相；真正缺的信息只是「有几个槽」，所以只加计数。另一个备选是「值类型加一个隐藏包装类型」来消除 k = 2 的歧义；否掉是因为它改变节点值的可见形状，而计数不改变。

### 3. 执行器与降级

- **共享驱动** `include/camel/execute/loop_driver.h`：`LoopShape` 增加 `collectionCount`、`valueType`、`origin` 与 `collecting()`；`s > 0` 时建一个 `(状态…, 新数组…)` 工作元组，放在节点的槽位（NodeVM 的帧、FastVM 的 `self`）或宏求值器 `RootHandle` 里；每轮把状态的各分量写回，把循环体结果的后 s 个分量用 `Array::append(value, ArrayType)` 原地追加。`MemoryExhausted` 被捕获后 `during("collecting the values a loop produces each round", shape.origin)`，在循环处报出。宿主接口改为 `callRound(shape, target, element)`，由驱动经 `loopStateComponent` 统一读状态，三个解释器不再各自推导布局。
- **NodeVM**（`nodevm.cpp`）、**FastVM 原生循环**（`fastvm.cpp`，`BytecodeExtra` 的 `loop` 子结构带 `mark` 与 `collectionCount`，`compile.cpp` 写入）、**宏求值器**（`eval.cpp`）都走这个驱动；FastVM 原生循环的源位置由执行器的 pc 补上。
- **降级**（`loop_lowering.cpp`，fvm/jit/prl）：新增两个隐藏算子——`:loop/collector`（循环前建一个空数组）与 `:loop/collect`（原地追加，返回磁带），登记在 `src/builtin/executors/builtin.cpp`，不在 `OperatorTraits` 的纯算子集合里（默认有副作用，遍不得重排或删除）；`next` 的下一状态 `FILL` 是 `(状态…, 磁带…)`，循环体调用的返回类型用体图的 `(状态…, 值…)`。`s = 0` 的降级一行未变。
- **`LoopView`** 增加 `collectionCount`、`valueIsTuple`、`valueComponentCount`、`stateValueIndex`、`collectionValueIndex`、`collectionArrayType`、`collectionElemType`、`nextStateIsTuple`、`bodyResultType`、`bodyStateResultIndex`、`bodyCollectionResultIndex`、`nextCollectionComponent`，以及自由函数 `loopValueComponent`/`loopStateValue`/`loopCollectedValue`：自动微分将来直接读，不必重推布局。提交校验（I18）在 `s > 0` 时要求值元组是「状态类型 + 数组类型」、体图返回「状态类型 + 元素类型」，严格相等。
- 内存耗尽的源位置：nvm/宏/降级（fvm/jit/prl）以及 FastVM 原生循环都在循环处报出（`pass.cpp` 在 `e.origin()` 无效时回落到 `currentRuntimeOrigin()`；FastVM 的两个执行环与 JIT 的 operator helper 在捕获 `MemoryExhausted` 时补当前 pc 的来源）。

### 4. GC

工作元组要么是循环节点帧槽里的值（NodeVM/FastVM），要么被宏求值器 `mm::RootHandle` 根住；槽位/根的类型就是 `(状态…, 数组…)`，`ArrayType` 的元素类型被追踪，因此磁带里的元素在回收器看来是活的。每轮之间的安全点由 `beforeRound` 提供；分配不移动对象，所以追加期间持有的裸指针在下一个安全点之前有效。没有运行期磁带对象，也没有手动释放：循环结束后磁带随循环的值一起成为普通 GC 值；反向闭包若将来捕获它，寿命与现有闭包链相同。

### 1. 影响分析：今天「形状常量」怎么表示

**影响面。** 核心类型（新增 `extent.h`，`other.h` 两个虚函数）、张量模块、词法/语法/AST、GCT、GIR、语义诊断、格式化器（新语法节点需要规则）、语言参考与张量技术文档、测试。没有动遍、后端、调度器，也没有新增图节点种类（运行时检查复用 `CAST`）。

### 2. 实现与设计选择

**2.1 编译期维度：`ExtentForm`。** 新增 `include/camel/core/type/extent.h`：

- `ExtentForm` 三态：`Unknown`、`Constant`、`Linear`（常数项 + 若干个「名字 × 整数系数」）。
- `linear()` 合并同名项、丢掉零系数、按名字排序，使相等可判定（`n + n` 就是 `2 * n`）。
- `evaluate(values)`：所有名字都绑定时给值，否则 `nullopt`。
- `bind(value, values)`：把这个等式告诉它的名字；常数必须相等，只有一个未绑名字时解出它（并检查整除），多于一个就**不猜**、留作未定；与已绑值矛盾返回 `false`。
- `toString()`：`?`、`3`、`n`、`2 * n - 1`。

**2.2 与具体类型解耦。** 核心不认识 `Tensor`：

- `TypeArgument` 增加 `shared_ptr<const std::vector<ExtentForm>> extents`（三选一，与 `type`/`data` 并列）。
- `OtherType` 增加两个虚函数：`extentForms(out)`（按该类型声明的顺序给出维度；默认 `false`）与 `withExtentValues(values)`（把已绑名字换成具体值；默认 `nullptr`，无名字可换时返回 `this`）。
- 张量模块实现它们：只要有一个维度写了名字就保留 `forms_`；驻留键包含 forms（`[n, 3]` 与 `[?, 3]` 是两个对象，签名才能记住名字），但 `equals`/`assignableFrom`/`castSafetyFrom`/`mangle` 只看 dtype 与形状——与形参名同样的取舍。`cloneWithArguments` 遇到 `argument.extents` 时：常数项进形状，非常数项在形状里记 `?`，forms 原样收下。

**2.3 语法。** `constas` 是关键字（`token_kinds.def`，`Type` 类），只在 `const` 类型实参内部被接受（`parser_type.cpp` 的 `ConstDataScope`），产生 `ConstasData` 节点 → AST `ConstAsLoad`；别处写它是普通语法错误。格式化器补了 `ConstasData` 规则（`tools/format/fmt.cpp`）——否则 `camel-format` 对任何用了新写法的程序直接抛 `no rule for ConstasData`，`frontend.format_keeps_ast` 与 `frontend.fuzz_lossless_tree` 会因此失败。

**2.4 GCT：把维度读成线性式。** `visitFuncType` 给每个函数声明开一个维度作用域；与 `typeas T` 一样，先扫一遍**所有形参类型**里的 `constas` 名字（`collectDimensionNames`），再逐个读类型，因此名字可以出现在绑定它的形参之前。`dimBindAllowed_` 只在形参类型期间为真：返回类型、嵌套函数类型里的 `constas` 报 `ConstasNotAllowed`；同一名字第二次 `constas` 报 `DimensionNameAlreadyBound`；从未绑定就写名字报 `DimensionNameNotBound`。`namesDimension` 把「带普通名字的 `const` 数组」都交给维度读取器，因此只在返回类型里出现的 `n` 得到的是名字错误，而不是「形状必须是整数常量」。

`visitExtent` 的语法就是设计原则 5.4 的线性式：整数字面量、已绑名字、`constas`、一元 `-`、`+`/`-`、乘以常数（任一侧是常数）；除法、两个命名维度的乘积、调用等一律**记为未知**，不是错误；非整数常量（小数、字符串、布尔）报 `InvalidExtentExpression`。

**2.5 GIR：调用点绑定、检查、转换。** 直接调用时（`targetOperator == nullptr`）：

1. 对每个带命名维度的形参，从实参类型取 `extentForms`，只把**静态已知（常数）**的维度用 `bind` 绑进本次调用的 `ExtentValues`；矛盾在**那个实参**上以 `DimensionMismatch` 报出（位置取实参表达式的 origin）。
2. 全部绑完后，再用 `withExtentValues` 把每个命名形参细化；实参维度静态未知时，把实参经 `castNodeTo` 转成细化后的类型——就是 `as` 的带检查转换，未知维度因此**在调用处运行时检查**，编译期放过。
3. 同一组绑定也用来细化声明的返回类型；返回值经同样的带检查转换。于是 `: Tensor<[n]>` 这种关系也在调用处成立（函数体没兑现就在运行时失败），而函数仍然只有一张图。

`var` 形参（单元而非值）与算子调用（它们自己的形状推断负责）不参与。绑定时只读直接 `OtherType` 形参：元组/结构体/数组里的张量、函数类型形参这次不在范围内。

**2.6 不产生新实例。** 名字只活在签名与调用点的静态类型里：实例化从来看不到它们，图里保存的仍是签名类型（`value_type="Tensor<float32, [n, k]>"`），每次调用的具体类型只出现在调用者的 `CAST` 上。测试 `single_instance` 用 `std::rgir` 断言：恰好一个 `dense` 子图、两个 `FUNC` 节点、没有 `dense<...>` 这样的实例名。

## H4b `for` 遍历字符串、映射、张量

分支：`handover/H4b-for-iterate`（worktree `D:\Projects\Camel-wt\h4b-for-iterate`），2026-10-20。实现、文档、测试都在工作区里，没有提交。

一句话：`for x in xs` 的 `xs` 现在可以是数组、字符串、映射或张量。字符串给码点（每个元素是只含该字符的字符串，与 `s[i]` 相同，11.1），映射给 `(键, 值)` 对并**按键升序**（11.3；实现里没有插入序可给），张量沿第一维给子张量。实现只有一条：`Builder::visitLoopNode` 在循环所在处把非数组序列按类型经内部算子组 `__iter__` 转成元素数组，`LOOP` 节点、`driveLoopRounds`、下降、`std::macro` 与所有后端仍然只见到数组——没有按后端写的迭代代码，也没有按名字分派。

### 1. 每种序列给什么

| 序列 | 元素 | 顺序 | 空的情形 |
|---|---|---|---|
| `T[]` | 元素本身 | 下标 | 0 轮 |
| `string` | 只含一个码点的 `string` | 码点，从左到右 | 空串 0 轮 |
| `Map<K, V>` | `(K, V)` 元组 | **键升序**（11.3），不是插入序 | 空映射 0 轮 |
| `Tensor` | 去掉第一维的子张量（同一份数据的视图，不复制） | 第一维 | 第一维为 0 时 0 轮 |

- **字符串按码点**：`for c in '中文'` 两轮，元素是 `'中'`、`'文'`；`'中文🙂'` 三轮（10 字节，3 个码点）。元素与 `'中文'[i]` 是同一个值（同一套解码：`camel::utf8::decodeOne`），所以 `c == s[i]` 成立。
- **映射按键序**：见第 3 节。
- **张量的元素类型**：rank 2 给 rank 1，rank 1 给 **rank 0** 子张量（`sum(x)` 就是那个数）；形状未知的 `Tensor` 给元素类型 `Tensor`。rank 0 的张量没有第一维：形状已知（`Tensor<f32, []>`）时编译期 `LoopSequenceNotIterable`，否则运行期故障（`iter` 的 infer/内核各自拒绝）。
- **元素类型就是循环体看到的类型**：I18 不变——元素端口类型 = 元素数组的元素类型。
- `for … while` 的次序不变（先条件、再取元素），四种序列都能配；`while` 形态不涉及序列。
- 空的情形一律 0 轮、值是初始状态（`iterate_empty.cml`：字符串、映射、张量第一维 0、空数组、条件一开始就假，五个都是初值）。
- 其余类型（`int`、元组、集合……）仍是 `SemanticDiag::LoopSequenceNotIterable`。

### 2. 实现：一次转换，一条驱动

**builder。** `src/compile/gir/builder.cpp:8211-8255` 的 `visitLoopNode`：序列已经是 `Array` 就照旧；否则 `module_->getImportedEntity("__iter__")` 取算子组，用序列的类型 `resolve` 一个重载（`statics` 空、`Modifier::None`），成功就 `addOperNode` 一个 OPER、`stampPermissions`、用 `registerNodeOrigin(..., "gir.loop.iter")` 记住循环里的位置、`linkNodes(LinkType::Norm, sequence, array)`；失败或没有这个组则 `SemanticDiag::LoopSequenceNotIterable`。之后 `ASSERT` 结果是数组，`elementType = ArrayType(type)->elemType()`。**每个后端、下降、macro 看到的都还是「数组 + 元素类型」**，它们一行没改。

**三个 `__iter__` 重载，各归各的模块**（同名算子组由 `Module::getImportedEntity` 合并，`src/core/module/module.cpp:414-438`；同一 URI 的 resolver 后写覆盖前写，这是 `OperatorGroup::publishResolvers` 本来的行为）：

| 重载 | 在哪 | 做什么 |
|---|---|---|
| `:struct/iter_str` | 内建 `globals` 的 `__iter__` 组（`src/builtin/modules/globals.cpp:1352-1360`），内核 `__iter_str__`（`src/builtin/operators/struct.cpp:43`） | `ArrayType::create(Type::String())`，按 `utf8::decodeOne` 每码点一个 `String::from(text.substr(...), mm::autoSpace())` |
| `:coll/map_items` | 内建集合的 `__iter__` 组（`src/builtin/operators/collection.cpp:411-413`） | 与 `items(m)` 同一个 `typed(...)` 定义（`:232`），所以 `for` 与 `items` 的次序永远一致 |
| `tensor:iter` | 张量模块 `utilityOps()` 的 `OpDef`（`modules/tensor/ops/utility_ops.cpp:219-226`，`.exports={"__iter__"}`） | `iterInfer`（`:107`）与 `iterKernel`（`:119`）：每行 `TensorObject::createView(t, rowShape, allocator, i * inner)` |

张量模块的 `__iter__` 以 `__` 开头，所以 `exportDefaultImportRef` 让它随 `import tensor` 自动可见（`modules/tensor/module.cpp:63-70`）；程序写不到这个名字。`exports` 只有 `__iter__`，因此不会多出一个公开的 `iter(t)` 函数。

**张量视图。** `TensorObject::createView` 多了一个 `uint64_t elementOffset = 0`（`modules/tensor/tensor.cpp:82`，声明在 `tensor.h`）：范围检查 `elementOffset + numelOf(shape) <= source->numel_`；拷贝路径从 `data_ + elementOffset * elementSize` 起；视图路径把偏移算进 `ownerDataOffset_`。元素是只读共享的视图（张量值不可变，算子都返回新张量），所以 `for row in m` 既不复制数据也不会改到 `m`。

**std::cpp。** `:struct/iter_str` 有一条独立译法：`r[":struct/iter_str"] = runtimeFunction("chars")`（`src/passes/trans/cpp/operator_rules.cpp`），运行时新增 `rt::chars`（`include/camel/standalone/array.h`，码点拆成单字符 `Str`）。所以字符串循环能被 `std::cpp` 独立译出并跑（`test/tools/cppexec/expect.txt` 新增 `test/cases/loops/iterate_string.cml`）；映射与张量本来就不是 `std::cpp` 携带的类型，报 `RuntimeDiag::TranslationRefused`（映射在值类型上就拒绝，张量在下降后 `rec` 的 `Tensor[]` 形参上拒绝）。

**诊断。** `SemanticDiag::LoopSequenceNotArray` 改名 `LoopSequenceNotIterable`（码仍是 `0x000120`，目录 id `0x03000120`），文案列出四种序列，hint 里说明码点、键序、第一维（`include/camel/core/error/diagnostics/messages/semantic.h`、`src/core/error/diagnostics/messages/semantic.cpp`）。

### 3. 映射的遍历顺序：按键序，有证据

任务的原话是「插入顺序，如果映射实现保持插入顺序；否则提问」。查证结果：**实现不保持插入序，无法给插入序，也不该给**。

1. **实现**：映射是持久化 B+ 树（`rtdata::Table`），`include/camel/core/rtdata/collection.h:23-44` 写得很清楚——叶子按 `data[0..size) = keys, ascending`，整棵树「Keys are strictly ascending across the whole tree under compareKeys」。插入序没有被记录在任何地方，给不出。
2. **规范**：设计原则 11.3（`docs/design-principles.cn.md:605`）「映射的遍历与打印按键排序」。按插入序遍历会与这条规范的打印次序不一致，同一份映射两个次序。
3. **既有行为**：`items(m)` 就是键序（本次让它与 `__iter__` 共用同一个定义），`keys(m)`/`values(m)` 也是；`for` 与它们一致才不会有第四种次序。

所以**键序**是这次的语义规则，写进了语言参考第 6 章（中英）与 `docs/technical/39_loops.md` 2a 节。证据测试是 `iterate_map.cml`：字面量写成 `[(3,'c'), (1,'a'), (2,'b')]`（插入序 3,1,2），遍历得到 `a`、`b`、`c`，最后一个键是 3，且每轮的键都大于上一轮（`ordered` 为 1）。

如果语言作者要的是插入序，那是映射表示的改变（现在没有这个信息），列在下面 Q1。

### 6. 待决问题

**Q1 映射的遍历顺序：键序（已实现）还是插入序？**
现状：按键序，依据 11.3 与 B+ 树表示（第 3 节）。要插入序就得在映射里记插入序（或换表示），并同时改 `items`/`keys`/`values`/打印，是语义变更，不是循环一处的事。建议维持键序。

**Q2 rank 1 张量的元素：rank 0 子张量（已实现）还是数值？**
现在 `for x in v`（`v` 是 `Tensor<f32,[n]>`）给 `Tensor<f32,[]>`，`sum(x)` 拿到数；而 `v[i]` 给的是 `f32` 数。两种都自洽，但同一份数据两种取法元素类型不同。选 rank 0 的理由：形状未知的 `Tensor` 的元素类型才定义得出来（`Tensor`），rank 1 → 数值会让「未知秩」那条规则变成「秩 1 时又特例成数值」，I18 的元素类型要按秩分支。若作者要统一成数值，改 `iterInfer`/`iterKernel` 一处即可，影响 `iterate_tensor.cml` 的期望。

**Q3 `Set` 要不要可遍历？**
没有实现。`items(es)` 已有（升序），差一个 `__iter__`/`tensor` 式重载；语义上「集合无重复、升序」是确定的。没做是因为任务只点了字符串、映射、张量，而且集合的遍历顺序虽由 11.3 的打印次序暗示，却没有明文。建议下一项任务加。

**Q4 非数组序列在循环处物化成数组：O(n) 内存。**
字符串、映射、张量各生成一个元素数组（张量是视图数组，开销是 n 个对象头，不是 n 份数据；字符串是 n 个单字符字符串；映射是 n 个元组）。这是「一个 LOOP 只有一种形态」的代价，换来所有后端与下降零改动。惰性游标（让驱动直接从序列取第 i 个元素）是以后的优化，和循环设计稿 6.4「`range` 不物化」是同一类工作；那时 `__iter__` 可以变成一个「取第 i 个元素 + 长度」的协议，节点与驱动仍只有一处改。

**Q5 `std::macro` 只覆盖到字符串。**
`std::macro` 折一个 macro 函数调用要求每个实参是静态 DATA 节点；字符串字面量是，映射/张量值要经 `as Map<...>`（CAST）或 `new`（OPER），所以折不了，`iterate_macro.cml` 只覆盖字符串（折成 2、3）。这不是循环的问题：macro 求值器的循环走的就是同一个 `driveLoopRounds`，序列在帧里是 `__iter__` 算子的结果，真跑到了也能取元素。要不要让 macro 认这些常量是 macro 折叠本身的范围，不是 H4b 的。

**Q6 设计原则 3.10 的这句话要协调者更新。**
`docs/design-principles.cn.md:209`（英文 `docs/design-principles.en.md:212` 同）仍写「`for` 目前只遍历数组，字符串、映射、张量以后再加」。按任务要求没有改设计原则；现在「以后」到了，§1 的语义应当并进 3.10（以及 11.1/11.3 若要写元素形态）。这是规范文字的唯一缺口，实现与其它文档都已按 §1 对齐。
