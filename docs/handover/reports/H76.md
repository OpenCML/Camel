# H76 — 标准库重新规划的第 0、1 步：约定页与"声明即签名"的机制（`bytes` 试点）

分支 `handover/H76-stdlib-step1`，起点 `origin/develop` `60c39d4e`。任务书是 H19 的第 0、1
步；写法以 `reviews/H19-plan.md` 的批复为准：**没有 `native` 关键字**，原生实现就是模块里一个
**无函数体**的 `export func name(...): T`，它按「模块名:函数名」绑定 C++ 算子，源码里不写 URI，
只有约定外的名字才用 `#op<'模块:函数'>` 标签。本文说明机制、载入规则为什么这样定、`bytes`
试点证明了什么、每个新用例能抓住哪种破坏，最后是计划与数字、待决问题。

## 1. 第 0 步：`docs/stdlib-conventions.cn.md`

一页约定，后续各批迁移按它判：一个事实只写一处（声明是类型的唯一来源，C++ 只留实现、资源、
语义、原地属性）、声明怎么写（无体、`export`、同目录同名的 `.cml`）、命名（模块名小写、
函数名动词、参数顺序、`format<args>` 这类尖括号例外）、错误（`T!` 与错误种类）、模块住在哪里
与分层。它在 `docs/design/stdlib/README.cn.md` 第 2 节点 3 被引用，`docs/stdlib-reference.md`
的页头也指向它——约定页与生成页互为入口，新人从哪边进都能找到另一页。

正文是规矩，不是散文：每条一句话，能写成"检查项"的写成检查项。第 3 步以后每批迁移都在它的
框架里报"这一批动了哪几条"。

## 2. 第 1 步的机制

### 2.1 语法：无体就是声明

`funcDecl : frontMatter 'func' identRef parentParams (':' typeExpr)? stmtBlock?`
（`src/parse/syntax/parser.cpp:942`）。有无函数体只看下一个记号：`{` 或 `sync {` 是函数体，
其余就是声明（`parser.cpp:970`）。`sync` 属于函数体，由 `parseStmtBlock` 读掉，所以判断要看
两个记号。

前端只有一处"无体"的判断，其余各处都读 GCT 的标记：

- AST：无体时 `FuncDecl` 没有 `StmtBlock` 孩子，也不建 `ValueProducer`（它没有值）。
- GCT：`FUNC` 带 `kFlagB`（`nativeDeclaration()`，`include/camel/compile/gct/node.h:168`），
  唯一的孩子是类型；缺返回类型报 `NativeDeclarationIncomplete`（没有类型就没有签名）。
- 模块合成 `DECL` 时把标记与标签使用一起带过去（`src/compile/gct/builder.cpp` 的
  `visitModule`）：`#op` 写在 FUNC 上，而 GIR 在 DECL 上编译它。
- 格式化器把无体声明原样打回去（`tools/format/fmt.cpp`），否则 `check` 会把它改坏。

### 2.2 声明变成模块的算子组

`declareNativeOperator`（`src/compile/gir/builder_modules.cpp:197`）：

1. **URI**：`#op<'...'>` 有就用它，没有就是 `<模块>:<名字>`；没有 `:` 报
   `InvalidOperatorURI`（`std::gir` 的 URI 必须有协议）。
2. **校验**：`ExecutorManager::findWithoutImport(uri)`（执行器已注册，且**不**重新 import 自己）
   与 `OperatorTable::find(uri)`（模块 `load()` 时 `declare` 过它的算子特性）都要有；否则
   `NativeDeclarationNotLoaded`，位置在声明处。这是"声明了却没人实现"的唯一诊断，不是静默，
   也不是到调用点才炸。
3. **签名**：`DeclaredFuncTypeResolver`（`include/camel/core/type/resolver.h:261`）只拿声明的
   `FunctionType` 做事——非泛型按参数个数与可赋值性检查；泛型用 `unifyTypeVars` 绑定，要求所有
   可绑定变量都定下来，`substituteTypeVars` 换成实参类型再检查可赋值性。`fixedSignature()`
   对泛型返回空（参数形状每次不同），所以算子组不把它当固定签名参与重叠检查。
4. **去重**：同模块里同名的非泛型规则重复报 `Redeclaration`；`OperatorGroup::create` 再兜一次。

`declareModule` 在第二轮（函数体之前）调 `exportNativeOperators`：把攒下的规则做成一个
`OperatorGroup`，`Module::exportEntity(name, group)` 进**模块自己的** `nativeEntityNS_`。这一步
是"声明是模块的实体"的关键：

- `inspect --ops` 读 `nativeEntityNS()`，所以声明的签名出现在工具里；
- `bytes::size` 这类限定名经 `ProgramExports::exportedEntity` 的 native 回退找到它；
- `exportDeclarations` 对已有 native 实体的名字直接跳过（`builder_modules.cpp:352`），程序表里
  不会再有第二份。

本模块内的引用（`#op` 指到别的模块、或同模块的声明）在 `builder_expr.cpp` 的 NREF 分支里先查
本模块的 native 组（`gir.dref.native`），再走导入层——这就是"同模块的无体声明优先于调用方导入
的同名重载"。

泛型声明不登记模板（`registerGenericTemplates` 跳过无体 FUNC），每个实例由算子的参数类型直接
实例化，所以图上是 **OPER**，不是对模板实例的 CALL。

### 2.3 载入规则：`.cmo` 旁的 `.cml` 是它的声明模块

查找顺序**没动**：`Context::getModulePathAndKind` 仍在同一目录先找 `xx.cmo` 再找 `xx.*`。改的是
`tryLoadModule`（`src/core/context/context.cpp:695`）：加载 `.cmo` 成功后，若同目录有
`<stem>.cml`：

1. `mod->load()`——让 C++ 模块注册执行器、算子表（`OperatorTable::declare("bytes", …)`）与资源；
   这是它唯一一次被 `load`，之后只作为实现被引用；
2. `warnUndeclaredOperatorTraits(*mod)`——C++ 没声明纯度的老问题照旧提示；
3. `UserDefinedModule::fromFile(moduleName, <stem>.cml, ctx)` 造声明模块，
   `setDeclarationModule(true)`、`setImplementation(mod)`，**返回声明模块**。

所以同名 `.cml` 既不是遮蔽（名字仍指 `.cmo` 那个模块，执行器、资源、语义都来自它），也不是死
代码（声明被编译、被导出、被检查）。安装树里 `collect-out` 把 `stdlib/bytes.cml` 和
`bytes.cmo` 放在同一目录，正好走这条路径——它不是只在测试里成立的旁路。

声明模块里只能有无体声明：有函数体就在 GCT 报 `DeclarationModuleHasBody`（位置在函数签名），
模块一载入就报，不会等到调用。

## 3. `bytes` 试点证明了什么

C++ 侧删掉的是**重复的签名**：`modules/bytes/module.cpp` 里原来的
`OperatorGroup::create` + 6 条 `StaticFuncTypeResolver`（`encode`、`decode`、`from_array`、
`to_array`、`size`、`concat`）。留下的是内核（`bytesEncode`…）、`BytesExecutor`、
`OperatorTable::declare("bytes", …)`（声明模块没有执行器，算子的纯度/语义仍由 C++ 声明）、
`registerExecutorFactory`。

签名与文档搬到 `stdlib/bytes.cml`（`module bytes` + 6 个无体 `export func`，注释逐字搬过去）。
`stdlib/signatures/bytes.cml` 删除；`scripts/stdlib-reference.mjs` 的 `bytes` 条目改成
`{ source: 'bytes.cml', declaration: true }`，生成器直接读声明，`docs/stdlib-reference.md`
的 bytes 一节文本不变（只多了页头指向约定页的那行）。

这证明的事实，逐条都有用例：

1. **调用方按声明检查**：`bytes_type.cml` 传 `int`，报 `NoMatchingFunction`，消息里的重载是
   `<bytes:size>: (content: Bytes) => int`——`content` 这个名字**只**写在 `.cml` 里，C++ 不再
   有第二份签名。`bytes_arity.cml` 同理（两个参数对一个）。
2. **调用到达 C++ 算子**：`bytes_arity`/`bytes_type` 之外，`native.tag_exception` 与
   `native.tag_exception_qualified` 真的跑出结果（`3\n3\n`、`4\n`），不是只过类型检查。
3. **泛型声明按类型实例化，图上是 OPER**：`native.operator_on_the_graph` 在 `std::gir` 输出里
   要求至少两个 `label=":op/idx_arr"`，一个 `value_type="int"`、一个 `value_type="string"`，且
   没有 `native_generic::at` 的 CALL。
4. **声明是模块的实体**：`inspect --ops` 看得见（`registry.purity_declared`），`bytes::size` 与
   `bytes_tag::size` 都找得到，`inspect --ops` 的名字、URI、参数个数、纯度与迁移前一致
   （`registry.purity_declared`、`registry.signatures_match`）。
5. **四个调度器不变**：`modules.bytes` 的两条与 `native.generic_declaration`/`_fvm` 分别覆盖
   `std::nvm`、`std::fvm`、`std::jit` 的既有路径（`native.generic_declaration` 的默认 pass 是
   `nvm`，`_fvm` 显式 `std::fvm`；`prl`/`jit` 由既有计划跑）。

`stdlib-reference.mjs --verify-ops` 也过：`bytes` 的 URI 与参数个数逐个对上 `OperatorTable`
里实际注册的算子。

## 4. 用例与它们能抓住的破坏

`test/plans/feat/compile/native_declarations.plan.toml`（order 340，9 条）：

| 用例 | 坏成什么样会红 |
|------|----------------|
| `native.generic_declaration` / `_fvm` | 声明没被实例化（类型变量留空）→ 编不过或值错；`at(words, 2)` 与 `at(ints, 1)` 各走一次 |
| `native.operator_on_the_graph` | 声明被当普通函数建了图（CALL），或 OPER 的 `value_type` 不是实例化后的类型 |
| `native.declaration_not_loaded` | 校验被去掉 → 退出码 0、没有 `NativeDeclarationNotLoaded`；诊断位置跑到调用点 → `missing_module.cml:` 对不上 |
| `native.wrong_arity` | 不按声明检查参数个数（"执行器在就算数"）→ 不再是 `NoMatchingFunction` |
| `native.wrong_type` | 同上，且签名回退到 C++（消息里没有 `content`）→ 少一个断言 |
| `native.tag_exception` | `#op` 没被读（URI 变成 `bytes_tag:size`）→ `NativeDeclarationNotLoaded`；声明没进模块实体 → 未解析 |
| `native.tag_exception_qualified` | 声明只进了程序表、没进模块实体 → `bytes_tag::size` 未解析 |
| `native.declaration_module_has_no_body` | 载入规则没生效（`.cml` 被当普通模块或死代码）→ 退出 0；规则生效但没诊断 → 退出 0 |

## 6. 待决问题

1. **声明模块不能用实现模块导出的类型与值。** `bytes` 的签名只用到 `Bytes`、`string`、`int`，
   碰不到这一条；`tensor` 之类要写 `Tensor` 的模块会碰到：`Tensor` 是 C++ 模块 `exportType`
   进程序表的，而声明模块是另一个模块，`import` 它只会拿到它的实体，不包含那些类型（也拿不到
   它导出的常量）。三个方向：(a) 允许声明模块 `import` 实现模块，并让实现模块导出的类型对声明
   模块可见；(b) 让 `Module::exportType` 同时进 `nativeEntityNS_`；(c) 声明里不写类型名，由 C++
   提供。**迁移 `tensor` 前必须先定这一条。**
2. **泛型声明之间的重叠不检查。** 泛型的 `fixedSignature()` 是空，`rejectOverlappingRules` 只比
   有固定签名的规则；两个泛型声明（`at<T>`、`at<U>`）会按顺序取第一个。`chooseOperatorOverload`
   的"更具体"比较也没有把声明规则算进去。
3. **非 `export` 的无体函数也是声明。** 批复的写法是 `export func`；实现没有要求 `export`
   （`func f(): int` 在模块顶层同样变成声明并导出算子组）。是补一条"必须 `export`"的诊断，还是
   就这样，需要定。
4. **入口模块里声明的默认 URI 是 `main:<名字>`。** 入口模块的运行时名字是 `main`
   （`tools/camel-cli/main.cpp:285`），不是文件里 `module` 声明的名字。`bytes` 这类被导入的模块
   不受影响；入口模块写无体声明本来就多半是笔误，但报出来的 URI 会让人困惑。
5. **`#op` 指定别的模块已发布的算子会替换算子表里的解析器。** `OperatorGroup::publishResolvers`
   是 `setResolver`（覆盖）。试点里 `bytes_tag` 的声明与 `bytes` 的声明逐字相同，无害；若签名
   不同，全局算子表会悄悄换成新签名，而 `bytes` 自己导出的组仍是旧的。要不要禁止"重声明别人
   的算子"，或规定以谁为准。
6. **`inspect --ops` 的签名文本变了**（对 `bytes` 现在带参数名 `content` 等）。`--verify-ops`
   只比 URI 和参数个数，所以没有红；但编辑器提示、文档差异测试若依赖旧文本，会看到变化。
7. **声明模块里的 `export let`/`export type` 目前照常进程序表**，而 C++ 模块的常量在模块实体
   里。两者是否该一致，等第 1 条定了再一起处理。
8. **载入规则只看同目录。** 用户目录里一个 `x.cml` 与借来的 `x.cmo` 放在一起就会被当成它的
   声明模块（我认为这就是"声明模块"的定义，但值得在约定页里写一句）。
