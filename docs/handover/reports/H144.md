# H144：`compile_bench.smoke` 的模块计数数错了对象

日期：2026-10-22
分支：`handover/H144-bench-module-count`，自 `origin/develop` 的 `e5544f744`。
代码提交：`de7d12868`；本报告与看板行在同一条后续提交里。

## 0. 结论

- `chain-3/passes` 的 6 个模块是真的：程序自己的 4 个（`main`、`bm_0000`、`bm_0001`、`bm_0002`）加 2 个库模块（`rules`、`math`）。H121 已证明按需加载与 facts 失效是正确的，所以这是**测量数错了对象**，不是编译器或流水线错了。
- 采读法 (a)：用例里的 “user modules” 指**程序自己的模块**，chain-3 固定是 4。读法 (b) 的合理部分不丢：总数 6 是真实成本，报告与断言都单独保留并钉住库模块集合。
- 基准现在能从 `gct` 阶段报告的 `detail` 里说出**哪些**模块被加载；检查信息同时给出程序自己的模块与库模块。旧检查只有 `{'modules': 6}`，看不出这 6 个是谁。

## 1. 复现：数出来的到底是哪些模块

在 develop 的集成树（`verify`，`9d1edc06e`）上原样复现旧检查：

```
FAIL
chain-3/passes: expected 4 user modules, got {'ast.nodes': 10367, 'gct.nodes': 6430, 'graph.edges': 498, 'graph.graphs': 32, 'graph.nodes': 398, 'modules': 6}
```

本分支的检查把名单打印出来（主机 `88zjwei` 的 Release 构建）：

```
ok compile benchmark: 6 cases, allocation shim used
  arith10/compile: 1 modules loaded: 1 user (main); 0 library (none)
  arith10/passes: 3 modules loaded: 1 user (main); 2 library (rules, math)
  arith10/fvm: 1 modules loaded: 1 user (main); 0 library (none)
  chain-3/compile: 4 modules loaded: 4 user (main, bm_0000, bm_0001, bm_0002); 0 library (none)
  chain-3/passes: 6 modules loaded: 4 user (main, bm_0000, bm_0001, bm_0002); 2 library (rules, math)
  chain-3/fvm: 4 modules loaded: 4 user (main, bm_0000, bm_0001, bm_0002); 0 library (none)
```

这 6 个的来历：

- `main`、`bm_0000`、`bm_0001`、`bm_0002` 是 `gen_modules.py` 为 chain-3 生成的工程本身，四个程序自己的模块。
- `rules` 是 H100 之后 `std::opt` 的代数步在**遍运行时**才第一次解析 `rules::simplify` 时按需编译的 `stdlib/rules.cml`（H112 §6、H121 §0）。
- `math` 是 `stdlib/rules.cml` 的 `import math` 带出来的：安装里的 `math.cmo` 旁边有 `math.cml`，`Context::loadModuleFrom` 把它作为声明模块加载成 `UserDefinedModule`（H19/H94 的声明模块规则），它和 `rules` 一样走 GCT，所以计入 `counters.modules`。
- `graph`、`rewrite`、`tensor` 是 C++ 模块（`cmo_load` 阶段），没有 Camel 源码的编译，不在 `modules` 里；`tensor_definitions` 只在某个张量算子定义第一次被请求时编译，chain-3 的整数程序没有请求它。

`counters.modules` 只数个数，分不出这 4 与 2；`gct` 阶段的 `detail` 里有模块名，所以基准从阶段报告里取名单，不需要改编译器。

## 2. 该断言哪个数：读法 (a)，两个数都留

`docs/technical/38_compile_pipeline_cost.md` 说明这个基准量的是成本和成本的结构，模块规模表的横轴是生成器要求的模块：

- §1.3：`| 多模块 | gen_modules.py 生成的工程，N = 1、2、4……128 个模块；每个模块 8 个函数、约 40 行；形状为 flat、chain、fan |`
- §5：`| 模块数 | 墙钟 (ms) | …`，以及 `**主体是线性的**：每个约 40 行的模块约 4.5 ms、15.6k 次分配、1.15 MB 常驻内存，与同样行数的单文件程序的成本相当。`
- 开篇：`本文回答三个问题：一次 camel x.cml <遍> 的时间与内存花在哪里……`

这些引文支持的读法是 **(a)**：`user modules` 是程序自己的模块，用来算「每个自己模块的成本」；把 6 当成 `user` 会把库模块混进这条横轴，§5 的「每多一个程序自己的模块」就不再成立。

读法 (b) 说的「总数是诚实成本」也对，而且不能丢：`std::opt` 编 `rules`/`math` 花的是真实时间（上面的报告行里 `pass:std::opt` 60.82 ms，`library` 14.33 ms）。所以实现是：(a) 为主断言，(b) 作为单独的数保留：

- `user` = 程序自己的模块数，chain-3 钉死为 4；
- `total` = 这次运行编译过的全部模块数，chain-3/passes 钉死为 6；
- `library modules` 单独列出并单独钉住，任一回归都会红。

## 3. 新断言与报告里的两个数

`benchmarks/compile/bench.py` 现在：

1. 从阶段报告取名单：每个 `gct` 阶段的 `detail` 是模块名（`src/core/module/userdef.cpp`），`module_names()` 按首次进入 GCT 的顺序给出完整名单；`entry_module()` 用 `gir` 阶段的 `detail` 认出程序自己的入口模块。
2. 分类：生成工程用 `gen_modules.py` 的已知名单（`main` 加 `bm_*`）判“自己的模块”，单文件程序用入口模块；其余都是库模块。
3. 断言：
   - `counters.modules` 必须等于名单长度（计数器与名字必须一致，防止报告被截断却仍然“数对”）；
   - 程序自己的模块必须等于生成器给的名单，chain-3 恰好 4 个：`main, bm_0000, bm_0001, bm_0002`；arith10 恰好 1 个：`main`；
   - `passes` 的库模块集合必须等于 `PASS_LIBRARY_MODULES = ("rules", "math")`；`compile` 与 `fvm` 必须没有库模块。常量上有注释：库被重构（`rules.cml` 的导入变化、声明模块出现或消失）时这条允许改，改它就是这次回归要提示的事。
4. 报告：阶段表加两行 `modules (user / total)` 与 `library modules`；模块规模表加 `user`、`total` 两列（原来的 `modules` 横轴保留）。`run` 的渲染结果（`--sets modules --modules 3 --pipelines passes --rounds 3`）：

```
| phase (self, ms) | chain-3 (165 lines) |
|---|---:|
...
| **wall** | **109** |
| peak RSS (MB) | 37.5 |
| modules (user / total) | 4 / 6 |
| library modules | rules, math |
```

规模表变成 `| modules | user | total | wall min | …`，编译流水线下 `modules=N`、`user=N+1`、`total=N+1`；带遍的 chain-128 则是 128 / 129 / 131。

## 4. 失败信息

负例（只在主机检出上临时把 `PASS_LIBRARY_MODULES` 改成 `("rules",)`，跑完已恢复）：

```
FAIL
arith10/passes: loaded library modules ['rules', 'math']; expected ['rules'] (see PASS_LIBRARY_MODULES: the on-demand rules/math import of std::opt). The program's own modules were ['main']
chain-3/passes: loaded library modules ['rules', 'math']; expected ['rules'] (see PASS_LIBRARY_MODULES: the on-demand rules/math import of std::opt). The program's own modules were ['main', 'bm_0000', 'bm_0001', 'bm_0002']
```

信息里有实际加载的模块、期望值、原因（`std::opt` 的按需 `rules`/`math`），以及程序自己的模块。用户数不对时给出 own / library / total 三个名单；计数器与名单不一致时给出计数器值和名单。

## 5. 测试

- 主机 `88zjwei`：Release 构建 625 个目标，`BUILD_EXIT=0`。
- `compile_bench.smoke`：通过；单独跑 1/1（`[PASS] compile_bench.smoke 1.15 s`），`feat/tools` 里 609.78 ms。
- `feat/tools`：30 条，19 通过、1 失败、10 跳过。失败是 `lsp.editing`（95 条检查里 2 条：`the exports of a module after ::` 与 `with their signatures`）；在 `verify`（develop `9d1edc06e`，不含本分支任何改动）上逐字相同，是既有基线红（H112 §9 记过这条），不是本任务引入。10 条跳过是 VS Code grammar 的依赖未安装（`editors/vscode` 没 `npm install`）。
- 负例见 §4：退出 1，信息正确。

## 6. 没改什么

- 不改编译器、遍流水线或库导入；`rules`、`math` 的加载是真实成本。H121 已证明它正确。
- 不删列、不删数：原来的阶段列与 `modules` 横轴都在，只增加 `user`/`total` 与库模块名。
- 没有新增 `npm run` 别名。

## 7. 遗留

- `lsp.editing` 是 develop 的既有红，不属于 H144；H112 §9 曾记为时序 flake，但当前在 `9d1edc06e` 上可稳定复现，建议另立任务。
- `tensor_definitions` 在 chain-3 的 `passes` 上没有加载。将来某个遍请求张量算子定义时，库模块会变成 3 个；`PASS_LIBRARY_MODULES` 的注释就是改这里的入口。
