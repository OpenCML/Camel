### 1.3 为什么类声明保持一个

`src/compile/gir/builder.h` 共 1196 行，声明了 `Builder` 的全部成员，其中包括私有嵌套类型 `Argument`、`CapturedUse`、`OperatorOverloads`、`GenericTemplate` 等，以及 `failedBodies_`、`declarations_`、`scopes_` 这些成员容器。

不按组拆声明的理由（不是"懒"，是这几条）：

1. **成员之间互相调用是交叉的，不是一个方向。** `visitLinkNode`（operators）调 `chooseOperatorOverload`（operators）与 `visitOperand`（calls）；`buildBranch`（control）调 `buildArmGraph`（control）与 `coerceTo`（control），再调 `visitBodyNode`（control）与 `insertNode`（核心）；装饰器组调 `applyTagOperator`（decorators）与 `buildDecoratedGraph`（decorators）；诊断组被几乎每一组调。按"谁能独立编译"切，切不出来——这正是"按功能切文件、声明留一个"能成立、而"按模块拆类"不能成立的原因。
2. **拆声明就要动封装。** 组成员互相调用的是私有成员；拆成多个类或把私有成员摊到头文件，都是改设计，不是搬移。
3. **纯搬移的定义要求如此。** 声明一个字节没改，`builder.h` 不在 `git status` 里，评审可以只看 `.cpp`。
4. 声明留一个，还有一个直接好处：新增的 9 个 `.cpp` 都只 include `builder.h` + `builder_support.h` + `builder_helpers.h`，不需要任何"哪个文件里有什么"的额外头，编译单元之间的依赖没有变复杂。

长期（允许改设计时）可以在 `builder.h` 里加一段"成员 → 实现文件"的索引注释，或者把 `Builder` 拆成几个协作对象；那都属于重构，见第 4 节。

### 1.4 共享辅助函数：从匿名命名空间到 `builder_helpers.h`

原文件有两个匿名命名空间（第 53–408 行、第 2864–2869 行），里面混着四类东西：被多组使用的自由函数、只被一组使用的自由函数、常量、`using` 声明。

处理判据（每个都记了理由，可复核）：

- **被两组以上使用 → `builder_helpers.h`，函数加 `inline`。** 共 34 个自由函数（其中 23 个原来靠匿名命名空间获得内部链接、这次加了 `inline`；11 个原本就写了 `inline`）+ 1 个结构体（`ConversionGap`）+ 2 个常量（`kSourceContextExtraIndex`、`kBuiltinPrefix`）。加 `inline` 是 C++ 里"允许多处定义同一实体"的最小改动；函数体、签名、名字一个字符没变。
- **只被一组使用 → 跟着使用者进那个文件的匿名命名空间。** 这样不扩大共享面：
  - 空值判定与收窄（`isNullLiteral`、`nullTestOf`、`collectNullTests`、`conjunctsOf`、`mentionsName`、`rightSideOf`、`nullComparison`、`isLogicalBranch`、`isNarrowedName`）→ `builder_control.cpp`；
  - `splitQualifiedName`、`lastSegmentOf` → `builder_enum.cpp`；
  - `reportFunctionReference` → `builder_expr.cpp`（只被 `visitDRefNode` 用）；
  - `applyTagOperator` → `builder_decorators.cpp`；`applyInternalOperator` → `builder_enum.cpp`（只被 `visitEnumConstruction` 用）。
- **`using camel::core::displayNameOf; using camel::core::operatorSymbolOf;`** 跟着函数一起搬到头文件。这两个 `using` 声明原来在文件后段（所有 include 之后），搬进头文件后出现过一次编译错误：头文件在 `camel/core/operator_names.h` 之前被解析。修法不是改代码，而是让头文件自己带上它依赖的工程头（见本节下文），这也是"纯搬移"的正确修法。
- 头文件里保留 `using namespace camel::core::{error,context,module,data,type};`，因为搬进来的函数体用的是这些命名空间里的名字（与原文件全局 `using` 一致），否则每一行都要加限定。

`builder_helpers.h` 带 `#pragma once`，并且**必须在 `builder.h` 之后包含**（它的签名用到 `builder.h` 的别名 `graph_set_ptr_t` 等）。它不 include `builder.h`：那个头文件没有 include guard（见"待决问题"），二次包含会重定义。这一点写进了头文件开头的注释。

`builder_helpers.h` 的 include 清单取"这些函数原来是和哪些头一起编译的"：即原 `builder.cpp` 的工程头（`gct.h`、`static_function.h`、`operator_names.h`、`operator_traits.h`、`runtime/control.h`、`runtime/graph.h`、`core/module/entity_internal.h` 等，其中 `entity_internal.h` 是 `EntityAccess` 的完整定义，缺它头文件编译不过）加上 `<algorithm> <atomic> <cctype> <cstddef> <format> <optional> <string> <string_view> <utility> <vector>`。头文件因此不依赖包含顺序。

### 2.12 一次一组、逐组提交

搬移是机械的、可重放的：每一组的行区间固定，剩下的行留在 `builder.cpp` 的原位置。为了让"每次搬一组、单独提交"可以真正执行（而不是事后手工拆分），`build/split-gir-builder.mjs` 支持 `--stage=N`（从 `HEAD` 读原文件，不需要先 `git checkout`）：

```
node build/split-gir-builder.mjs --stage=0   # builder_helpers.h；builder.cpp 里两个匿名命名空间被头文件取代
node build/split-gir-builder.mjs --stage=1   # + builder_generics.cpp
node build/split-gir-builder.mjs --stage=2   # + builder_expr.cpp
node build/split-gir-builder.mjs --stage=3   # + builder_operators.cpp
node build/split-gir-builder.mjs --stage=4   # + builder_calls.cpp
node build/split-gir-builder.mjs --stage=5   # + builder_control.cpp
node build/split-gir-builder.mjs --stage=6   # + builder_enum.cpp
node build/split-gir-builder.mjs --stage=7   # + builder_decorators.cpp
node build/split-gir-builder.mjs --stage=8   # + builder_modules.cpp
node build/split-gir-builder.mjs --stage=9   # + builder_diagnostics.cpp（终态，等于当前工作树）
```

每个 stage 都是"完整的树"，可以单独编译——我逐个验过（见 3.1 的表）。提交建议：

1. `builder_helpers.h` + `builder.cpp`（匿名命名空间的函数改 `inline` 移到头文件、`builder.cpp` 里加一行 include）：纯搬移；
2. 之后每个 stage 一个提交（新增一个 `.cpp`、`builder.cpp` 缩小），提交信息写"纯搬移：把 X 组移到 X.cpp"。

工具在 `build/`（gitignored），是临时工具，不进仓库；协调者若希望把它留下，可以移到 `scripts/`。

### 3.6 `git diff --color-moved` 与它的局限

按任务书要求跑了：

```
git add -N src/compile/gir/builder_*.cpp src/compile/gir/builder_helpers.h
git diff --color-moved --stat
```

```
 src/compile/gir/builder.cpp             | 8326 +------------------------------
 src/compile/gir/builder_calls.cpp       |  596 +++
 src/compile/gir/builder_control.cpp     | 1458 +++++
 src/compile/gir/builder_decorators.cpp  |  369 ++
 src/compile/gir/builder_diagnostics.cpp | 1056 +++++
 src/compile/gir/builder_enum.cpp        |  575 ++
 src/compile/gir/builder_expr.cpp        | 1020 ++++
 src/compile/gir/builder_generics.cpp    |  974 ++++
 src/compile/gir/builder_helpers.h       |  666 +++
 src/compile/gir/builder_modules.cpp     |  283 ++
 src/compile/gir/builder_operators.cpp   | 1817 +++++
 11 files changed, 8871 insertions(+), 8269 deletions(-)
```

（`git add -N` 只是为了把未跟踪的新文件纳入 `git diff`，随后 `git reset` 复原；工作树与索引现在都只有"`builder.cpp` 已修改 + 10 个未跟踪新文件"。）

**但 `--color-moved` 对这次改动给不出结论**：git 的移动检测只在**同一个文件对**内生效，跨文件的搬移在 diff 里就是一个全新文件（整片绿色），不会标成"moved"。我验证过这一点：`git diff --color-moved -- src/compile/gir/builder_enum.cpp` 的 hunk 头是 `@@ -0,0 +1,575 @@`，全部是新增色。所以"用 `--color-moved` 自查"这条要求在跨文件搬移上不适用。

等价的做法（能真的把"moved"标出来）：把搬走的正文按新顺序拼成一个文件，`git diff --no-index --color-moved=blocks` 对照 `HEAD:builder.cpp`。这样同一个文件对里既有"从这里删"又有"在这里加"，git 才会标 moved。结果：

```
added lines in the concatenation: 4864
  detected as moved: 4615
  reported as new  : 249

runs of moved lines: 182, longest 342, 56 runs of 20 or more
```

4615 / 4864 的行被标成 moved；剩下 249 行是 `}`、空行、`return x;` 这类短行——git 的块匹配对重复短行无法归属（同一片段在别处也出现），不是说它们是新代码；它们由 3.5 的逐字节校验覆盖。182 段连续 moved、最长 342 行，与"每个函数体整段搬走"的形状一致。

结论：`--color-moved` 的跨文件局限 + 3.5 的逐字节校验与行核算，三样一起构成"确实只有搬移"的证据；其中逐字节校验是最强的一条（它能证明"新文件里没有一行新逻辑"，比颜色更硬）。

## 4. 留给重构的想法（本项只记录，没有做）

1. **`builder_operators.cpp` 仍太大（1817 行）。** `visitLinkNode` 一个函数约 949 行（原 5509–6457 行），里面依次做：解析被调者、算子重载选择、参数收敛与 `STAR`/`SPREAD` 处理、就地改写、调用节点收尾。它有清晰的阶段边界，适合拆成 4–5 个私有成员函数。这是最值得做的下一步，但属于改逻辑。
2. **`#define DEBUG_LEVEL -1` 是死代码。** 原文件里它没有使用者（`CAMEL_LOG_DEBUG`/`CAMEL_LOG_TRACE` 在 gir 目录里一次都没出现），现在被复制到 10 个文件里。删掉即可，但那是"改"，不是"搬"。
3. **`Builder::registerTreeOrigin` 没有调用者。** 定义在 `builder_diagnostics.cpp`（原 8550 段附近），声明在 `builder.h`；`src/compile/gir` 里搜不到调用（`tree.cpp` 里的 `registerTreeOrigin(out, origin, kind)` 是另一个三参数的静态函数）。疑似历史残留。
4. **`builder_helpers.h` 里的 34 个函数按原顺序排列**，没有按功能排；而且它一次性 include 了 16 个工程头（含 `numeric_convert.h`、`core/rtdata/string.h` 等），其中一部分可能只被个别函数用到。可以按实际使用收窄。
5. **10 个 `.cpp` 复制了整份 include 块。** 这是为了"include 集合与搬移前一致"，代价是每组都背着别人的头（例如 `builder_modules.cpp` 不需要 `runtime/control.h`）。后续可以按组收窄，缩短编译时间。
6. **诊断组里混着"源码文本与位置"的工具**（`sourceTextOf`、`sourceLocationOf`、`conversionTextOf`、`describeGaps`、`tupleElementTexts`）。它们不是诊断本身，而是"把源码/类型写成人读的字符串"；以后可以单独一个文件。
7. **`builder.cpp` 剩下的 21 个成员里，`visitFuncNode`/`buildFuncBody`/`stampPermissions`/`buildEntryCall` 是一组**（"函数体与入口"），与"会话/作用域/节点插入"其实可以再分一次。搬移时把它们留在 `builder.cpp` 是因为它们是所有组的公共路径，也是"文件至少要有一个实现"的那个文件。
8. **`builder.h`（1196 行）没有 include guard。** 这次因此把 `builder_helpers.h` 定为"必须在 `builder.h` 之后包含"，并在注释里写明。加一行 `#pragma once` 就好，但那是改。
9. **`Builder` 的成员字典**：可以在 `builder.h` 里加一段"成员 → 实现文件"的索引注释（不动声明），方便按名字找文件。现在只能靠 `grep`。
10. **`builder_support.h` 的注释还列着旧的三件套**："shared by the source files the builder is split into (builder.cpp, program.cpp, captures.cpp)"。现在是 11 个文件；注释该更新（属于"改注释"，不在搬移里做）。
