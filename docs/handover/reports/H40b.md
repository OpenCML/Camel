## 1. What was asked

The review of H40 left four items, all in this task:

1. **Block pressure must be able to ask for a full (major) collection.** Record the block bytes that
   arrays promoted to the elder space hold; when they pass a threshold, request a major collection.
   H40's section 9, item 2 is the argument: a promoted block can be released only by a major
   collection, and the only block-driven request was the *minor* trigger.
2. **Rewrite `feat/mm/gc_pacing`.** Its premise (arrays live in the large-object space, so
   `CAMEL_GC_GROWTH_PERCENT` and `CAMEL_GC_LARGE_BUDGET_MB` pace them) is dead: array data lives in
   data blocks outside the collected heap. The new plan must test what the collector promises now:
   what asks for a collection, how much one frees, how the pacing base is measured after deferred
   releases, and that a churn-only program does not raise its high-water mark.
3. **Regression cases.** The reviewer wanted locked: "a training-style loop's peak stays near its
   live set", plus a block-pacing case. The minimal reproduction from H40 section 8 is the right
   shape for the training case: its refusal is gone (9.9's discrete-value rule), and the loop still
   runs the softmax-cross-entropy + integer-label + `grad` path that the C2 showcase uses.
4. **Correct the `H13` / README narrative.** "`take` raised the peak from 111 to 262 MiB" is false;
   the peak was collection pacing. `H13` and the C2 READMEs must say so.

## 2. What the collector promises now

The mechanism the plan locks, as the code stands:

* **Minor trigger.** A minor collection is asked for when `birthSpace_.used() + blockBytesGrowth`
  reaches `minorTriggerBytes_` = 90 % of the birth space (3,774,873 bytes at the default 4 MB). The
  window of block bytes a collection lets through is therefore fixed, and the high-water mark of a
  program with live set `L` and allocation step `A` is about `L + window + A`, however many steps it
  runs. `CAMEL_GC_NURSERY_MB` scales the window.
* **The base is taken after the deferred releases** (H40's fix). A dead array's block is queued by
  its finalizer and released by `runDeferredReleases()` after the collection unlocks;
  `noteBlockBytesAfterDeferredReleases()` then re-reads the live count. If the base included those
  bytes, every window would have to beat the previous one's pre-release peak and the high-water mark
  would climb linearly (measured again below).
* **Major triggers.** Large-object budget, elder allocation budget, heap limit, and now promoted
  block bytes. The first three are unchanged.
* **Mark-sweep** has no birth space and no window: the same churn is held until the elder budget asks
  for a major (36 MB peak for 180 MB of garbage, measured below).

## 3. The new rule: blocks held by promoted values

`rtdata::Object` grows one virtual with a default of zero,
`size_t blockBytesHeld() const noexcept` (`include/camel/core/rtdata/base.h`); `Array` and
`BytesObject` override it with the bytes of the block they own. No subclass is forced to change.

In `forward()`'s `promote` lambda (`src/core/mm/gen.cpp`), the bytes the promoted value holds are
added to `elderBlockBytesSinceSweep_`; when they pass `elderBlockBudget_` a major collection is
requested with the cause `promoted block budget`. The request is merged with a pending major, as the
other causes are. In `sweepOldGen`, the same iteration that collects the unreachable headers sums
`blockBytesHeld()` over the survivors (no extra pass), and after the sweep:

```
elderBlockBytesSinceSweep_ = 0;
elderBlockLiveBytes_       = liveBlockBytes;
elderBlockBudget_          = max(largeObjMinBudget_,
                                 largeObjGrowthPercent_ % of liveBlockBytes);
```

That is the large-object rule, on purpose: both are pure data outside the collected heap that only a
major can reclaim, so the floor is `CAMEL_GC_LARGE_BUDGET_MB` (default 4 MB) and the growth is
`CAMEL_GC_GROWTH_PERCENT` (default 100). With the default a program that keeps `B` bytes of promoted
blocks live holds at most about `2B` plus one window, and a program that keeps none holds about one
floor plus the window. The initial budget, before any sweep, is the floor.

Three statistics-line fields make the rule observable and are what the plan asserts:
`by_elder_block_budget=` (requests by this cause), `elder_block_live_mb=` (block bytes the last sweep
left in promoted values), `elder_block_budget_mb=` (budget in force). They are also in the
`CAMEL_GC_PROFILE` JSON. `CAMEL_GC_STATS=2`'s per-major line is unchanged.

## 4. The new `gc_pacing`

Thirteen tests, four new cases (`test/cases/feat/mm/gc/`), tier `slow` and a 120 s timeout each. All
numbers below are read from `std::mem::blocks()` in the program or from the `CAMEL_GC_STATS` line;
nothing is timed. The counts are asserted as bounds, not equalities, because the parallel scheduler
allocates the same values in a different order (the old plan's `growth_25_prl` exact count was the
documented flake).

| test | what it locks | observed (final build) |
|---|---|---|
| `live_fvm` | 40 MB live + 200 × 0.8 MB temporaries: peak = live + 4.8 MB (window + one temporary), low = live + 0.8 MB, all but the window released, no large-object request | base 40.0 MB, peak 44.8 MB, low 40.8 MB, released 196, `minor=41`, `by_large_budget=0` |
| `live_steps` | the same with 600 temporaries: the peak does not move | peak 44.8 MB, released 596, `minor=121` |
| `live_nvm` | the same numbers on the node VM | identical |

| `churn_nvm`, `churn_prl` | the same on the other back ends | identical |
| `churn_mark_sweep` | the other collector: no minor collections, the major comes from the elder budget, peak tens of MB | peak 36.0 MB, `major=42`, `by_elder_exhausted=42`, `minor=0` |

## 7. Entries deleted, and the premise that died

The old plan had eight tests: `growth_default_fvm`, `growth_default_nvm`, `growth_50_fvm`,
`growth_25_fvm`, `growth_25_nvm`, `growth_25_prl`, `growth_10_floor_fvm`, `floor_64_fvm`, all over
one case, `gc_large_pacing.cml` (40 MB live array + 200 × 0.8 MB temporaries). **The premise that
died: that this workload exercises the large-object space and is paced by its budget.** Array data
is in `mm::Block`, so the workload never enters the large-object space: the case reports
`large_live_mb=0.0`, `large_high_water_mb=0.0`, `major=0`, `by_large_budget=0` on both the old and
the new binary, and `CAMEL_GC_GROWTH_PERCENT` / `CAMEL_GC_LARGE_BUDGET_MB` had no effect on it. The
eight entries and `gc_large_pacing.cml` are deleted (nothing else used the case).

Coverage is not lost: the same knobs are now exercised where they do act. `promoted_floor` locks the
floor on the promoted-block budget, and the growth percentage still paces the large-object space
(other plans) and this budget. What changes materially is that the *nursery size* is the knob that
paces block churn, and the plan locks that instead (`churn_nursery8`). The large-object space
itself is still covered negatively by `gc_soak` (`large_high_water_mb <= 4`), but no plan now
varies the growth percentage for a large-object workload: no Camel program reaches that space —
arrays, strings and bytes put their data in blocks, and the wrappers are small.

## 8. 设计上的选择

* **One rule for "bytes only a major can free".** The promoted-block budget reuses the large-object
  floor and growth percentage rather than introducing a third pacing knob. The numbers the plan
  locks are the observable form of the rule (`budget_mb`, `elder_block_budget_mb`).
* **Count at promotion, measure at sweep.** The counter is per promoted value, so it records garbage
  as soon as it becomes garbage; the live base is re-measured at every major in the iteration the
  sweep already does, so the budget follows what survived. Resetting at the sweep (not at the minor)
  is what keeps the rule "bytes promoted since the last *full* collection".
* **A virtual with a zero default.** `blockBytesHeld()` lives on `rtdata::Object`; `Array` and
  `BytesObject` override it. A value type that does not own a block pays nothing and changes
  nothing.
* **The request is a request.** It goes through `requestCollectionAtSafepointUnlocked`, so it merges
  with a pending major and runs at the next safepoint; no collection starts inside promotion.
* **`Bytes` is counted too.** The reviewer named arrays, but a promoted `BytesObject` has exactly
  the same ownership problem; leaving it out would make the rule depend on the value type.
* **Bounds, not counts.** The plan asserts peaks, ranges and causes; the only equalities are the
  byte totals the program computes itself (`steps × temp`).

## 9. 待决问题

1. **Shared blocks are counted per view.** An array view shares its owner's block (`Array::block()`,
   no separate allocation), so promoting `n` views of one block counts its bytes `n` times and can
   ask for a major earlier than needed. Over-counting is conservative (an early major, never a
   missed one), and no measured workload does this, but should the counter count a block once (by
   identity, or only when the last reference goes)?
2. **A block adopted after promotion is not counted.** An array promoted while empty that later
   grows a 40 MB block adds nothing to `elderBlockBytesSinceSweep_`; only the other triggers can
   collect it. Under-counting is safe but silently weaker. Is promotion-time counting the right
   contract, or should the array tell the allocator when it adopts a block while old?
3. **The first major after a large live array is promoted.** The initial budget is the floor, so the
   40 MB live array in `live_fvm` asks for one immediate major, which then measures 38.1 MB of live
   blocks and raises the budget to 38.1 MB (100 %). Should the first budget instead be seeded from
   the promotion that crossed it (avoids one major), or is one major to learn the live base
   acceptable?
4. **The floor knob now has two meanings.** `CAMEL_GC_LARGE_BUDGET_MB` floors both the large-object
   and the promoted-block budget. Should promoted blocks get their own variable, or is one knob for
   "data only a major can free" the clearer contract?
5. **The gauge can read 0 at exit.** `elder_block_live_mb` is what the *last* major left; if that
   major ran while the alive rows were still young, the value is 0 even though the program holds
   promoted blocks. The plan does not assert it at 0/600 steps for this reason (it does assert
   `>= 12` in `promoted_fvm`, where the last major is late enough). Should the line report the gauge
   of every major instead (`CAMEL_GC_STATS=2`), or a running max?
6. **Mark-sweep does not use this path.** It has no promotion, so the new request never fires there;
   its block pressure reaches the elder budget through `blockBytesGrowth` in the allocation check
   (36 MB peak for the churn case). Is that enough, or should mark-sweep also have an explicit
   promoted-block-like budget for blocks adopted while old?
