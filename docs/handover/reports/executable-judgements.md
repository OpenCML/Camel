# 可执行的判据：一句话 + 它落在哪

- **账本的四个数（files / references / constructions / decode）只能降，最后一步必须归零**：`test/cases/runtime/graph_draft_ledger/check.mjs` 对 `baseline.json` 执行，计划 `feat/runtime/graph_draft_ledger.plan.toml`（`tier = "fast"`，每次闸门都跑），记数行 `[LEDGER] recorded files 66 references 535 constructions 3 decode 6`。
- **诊断页每条示例是钉住的，加一条用例不能挪动别的诊断**：`diagnostics/examples.tsv` + `node scripts/diagnostics-catalog.mjs --verify-doc`（绿即 `docs/diagnostics.md is up to date`）；把被钉的用例移走再 `--write`，页面一个字节都不动。
- **受控文件必须被某条选中规则选中**：`test/plan-selection.json`，由 `test/tools/selftest/run.mjs` 的 `plan-selection:` 检查执行——`diagnostics/examples.tsv` 第一天就是这么被咬住的。
- **冻结只做一种环判定，`sync` 环被拒**：`test/plans/feat/opt/edges.plan.toml` 的 `test::edges_sync_cycle`；把冻结收回 4 种边，这条立刻红。
- **环丢弃的会话数看得见**：`std::stats` 输出的 `cycle_dropped_sessions`（`src/passes/trans/stats/stats.cpp`）。
- **`develop` 上造不出"多条改写合成的环"**：`opt-cycle-composition-not-found-on-develop.md`——拿掉守卫那一支，fast 层 7898 条一条不红。
- **一次落地值不值，看一个数**：闸门的 `[SUMMARY] total / pass / fail / skip / known failures`，不是"我看过了"。
- **报绿之前先报"这张计划有几条进了这一层"**：`tier` 写在计划头上（`test/plans/gpu/tiles.plan.toml:3` 是 `tier = "slow"`，103 条里只有 1 条 `tier = "fast"`），`[SUMMARY] total` 只含**被选中并真的跑了**的条目——`[PLAN] gpu.tiles` 后面跟几条就是几条，不是 103；慢层只有三张计划（`feat/mm/gc_pacing` 15、`feat/mm/gc_soak` 22、`gpu/tiles` 103，合计 140 条），fast 闸除了那个例外一条都不跑。（改之前的形状；整张 slow 现在只剩 `gpu/tiles`，见本页最后一条。）
- **同一个用例在两层的两份条目会分叉**：`a3d119690` 把 `feat/modules/tiles.plan.toml` 的 `gpu_scope.macro_expansion_publishes_the_derived_graph` 翻成 `behavior`，`gpu/tiles.plan.toml` 的 `grad_expand.scope_sees_the_derived_graph` 留成 `negative`；闸门四趟全绿（slow 层没跑），那份红到有人整张跑 slow 才被看见。翻一条用例的 `kind` 之后，先 `git grep -n '<case 路径>' -- test/plans` 数一遍有几份。
- **`known failures: 2` 这个数只有在两条都登记了失败形态与认领人时才有意义**：否则它只是"两个不知道"——查法见 `known-failures-two.md`（两条都在 `effects_model_edges.plan.toml`，都在等第 9 条第二半，而车主 `lane-order-region` 已不在）。
- **中转仓库里某条引用该不该删**：`git merge-base --is-ancestor <sha> refs/camel-tmp/develop`（`build-host-staging-refs.md`）。
- **一个指错位置的诊断，比没有诊断更贵**：它会让人去改那个位置。`let (x, y) = <四元组>` 过去报 `SemanticDiag::InvalidAccessIndex: Invalid access index: '2'`，箭头指着 `func`（1:1）；读者读到的是"函数声明有问题"，而去改函数。同一个错误现在报 `TupleUnpackingCountMismatch` 在 `let (` 上（`src/compile/gir/builder_expr.cpp` 的 ACCS 分支按 `GCT::Tree::unpackCount` 与元组长度比对）。反向也一样：`let (x, y) = <二元组>` 过去静默丢值，现在同一句诊断。
- **在主机上手动跑任何测试之前**：先复刻闸门的导出（`LD_LIBRARY_PATH=$HOME/camel-eval/conda/envs/clang/lib`、`CAMEL_HOME=<树>/out/latest`、`CAMEL_TEST_SHOW_OUTPUT=1`），否则 `camel` 报 `GLIBCXX_3.4.36 not found`，读到的红全是自己造的。
- **一条新诊断的迁移成本，要用"全树有几处"来报**：报"我改了三处"听起来像运气——读者没法判断是自己运气好还是树里本来就没有。分母要报出来（`unpack-count-migration.md`：265 处 `let (`，3 处要改，`stdlib`/`examples`/`test` 各 0），而且分母只有整层编译才拿得到，grep 数不出"名字比元素少"。
- **三张慢计划 140 条测试，我们的闸每晚跑 1 条**：`feat/mm/gc_pacing` 15 条、`feat/mm/gc_soak` 22 条、`gpu/tiles` 103 条整张是 `tier = "slow"`，fast 闸只跑 `gpu/tiles` 里那 1 条例外。**先整张跑一次，再谈要不要把它们挪进快层**——没跑过的绿不是绿，是没读数。**（按这条办过一次了：`gc_pacing` + `gc_soak` 37 条 / 6.7 秒 / 零红，条件满足；翻成 `feat/mm/gc_*` 的账本也翻了——整闸 `total` 8032 → 8069——但 `consistency.runner` 当场红：`plan-selection.json: 'feat/mm/gc_pacing.plan.toml' is a plan an ordinary change must not run`，那 8 个用例的目录镜像又只指向 milestone 的 `feat/mm/gc.plan.toml`。**已回退**，理由写进 `docs/test-plans.md` 的 slow 一节：这条不是"快且稳"不够，是"这一类计划普通改动不许跑"的政治决定，收窄类别还是改名，得作者拍。）**
- **把一条测试从慢层挪进快层的唯一条件是"它快且稳"**：`37 条 / 6.7 秒 / 零红` 就是那个条件，不需要讨论。反过来说，"在慢层待着没被跑过"不是一条测试安全的理由：`gpu/tiles` 那 102 条挪不动是另一件事——它要卡、跳过的条数随卡忙闲摆动、整张 89 秒，那不叫"快且稳"，叫"看机器"。
- **一条测试进闸的代价不是它自己的耗时，是它和别人的争用**：`feat/mm/gc_pacing` + `gc_soak` 整张跑 37 条 6.7 秒、零红，放进 fast 层后整闸 `total` 只 +37，但 `wall` 从 227.5 s 涨到 275.3 s（**+47.8 s**）——七倍于它们自己的耗时，因为它们是内存带宽的活。**这笔账只有整闸能报**，单跑这两张永远看不见；所以"便宜"这个判断必须在整闸里做，落地写进 `docs/test-plans.md` 的 slow 一节。
- **同一个错在英文页犯两次**：`docs/language/en/` 比中文页深一层，`../handover/...` 会解析到 `docs/language/handover/...`。中文页链接对、英文页链接错，`docs.links.reader_facing` 只在合并时现形（本地 `check-doc-links` 若只跑中文页就看不到）。改了中英两份规则就同时改两条链接，并跑 `feat/docs_links.plan.toml`。
- **"每晚跑"如果只是一句话，它会在第一周就被忘掉**：把它写成一条能粘进终端的命令，它才会真的跑。慢层的入口就是 `node scripts/test.js test/plans --tier slow --jobs 8`（没有 nightly 脚本、计划格式也没有 `includes`），实测 163 条、131.4-160.5 s；`gpu/tiles` 在内，跳过条数随卡忙闲在 19-47 之间摆动。**跑一次就发现它不绿**：`agree_with_fvm` 三处 "does not build: clang: error: linker command failed"，是主机的 C++ 链接，不是这次的改动。
- **`never` 不是一种值，是一条控制流边**：写出器要先认出它（`isValueType`/`endsFlow`、`bridgeCarries`），才谈得上翻译它——把 `never` 当结果类型去绑定，生成的 C++ 是 `const void v1_fail = …;`，clang 只报 "variable has incomplete type"，读者看不出是类型模型错了。
- **两个后端"正文相同、诊断名不同"等于把同一件事报成了两件事**：`fail<'X'>` 的标签就是那半句被丢掉的话——桥（`src/execute/standalone_bridge.cpp` 的 `describe`）只读 `fault.diag()` 的目录名，丢掉 `RuntimeFault::kind()`，于是 VM 报 `RuntimeDiag::NoPremise`、C++ 报 `RuntimeDiag::ProgramFault`。**名字取自读者写下的那个词，不取自它在目录里的位置。**
- **一条诊断说"这个功能还没实现"，而它已经实现了，那条诊断就是在撒谎**：它该说的是"你的写法缺什么"——`yield` 在非流类型的函数头里，从 `FeatureNotSupported('generators')` 改成 `SemanticDiag::YieldRequiresStreamHead`（写出器早就有生成器了）；真正**没实现**的那一处（机器收不下的循环形状）保留 `FeatureNotSupported`，因为那里的确是缺口。
- **一条诊断落到了错误的格子上，说明那条路把"这是哪种错"的判断弄丢了**：先找出它把值读成了什么，再谈支持它——`(int, int)..` 本来就读成了流类型（探针能编能跑），丢的是**拒绝的类别**：函数头检查与生成器机器的收窄共用一个 lambda，于是"循环跨 yield 带两个值"这个机器缺口被报成了"头没写流类型"，还报在函数那一行。两个判断分开，各报各的。
- **新加一条诊断，等于同时欠一条点名它的测试**：诊断登记表不会自己满足，它只会在闸门上替你把欠账报出来（合并树上 `catalog.coverage_zero`：`0x03000206 SemanticDiag::YieldRequiresStreamHead is declared and no test mentions it`）。加诊断的那一笔就该把用例一起写，**并且重跑 `node scripts/diagnostics-catalog.mjs --write`**——生成的文档（`docs/diagnostics.md`、`diagnostics/examples.tsv`）不同步，`catalog.doc_is_generated` 会另开一笔红。
- **一条负例在自己树上绿、在合并树上红，先怀疑它的期望写的是"今天的状态"，而不是"这条规则"**：`stream.yield_lowering_refused` 钉的是"两状态 `loop` 生成器被拒"，而 `origin/develop` 的 `src/compile/gct/builder.cpp` 比我的树多 211 行/少 35 行——合并树上那条 `loop` 已被**降低**（打出 `1`、退出 0）。负例要么钉规则、要么跟着上游改；钉"今天拒绝什么"的负例，会在别人实现它的那一刻变成假红。
- **两棵树给出相反读数时，先把两棵树并起来再判**：判据说"今天"，指的是**合并后的今天**。我按自己的树把一条负例判成"对"，合并 `origin/develop` 后同一条用例的整个形状已被降低、用例本身都被上游删了——先并、再判，省掉一轮来回。
- **一个诊断在语言面上已经没有形状能触发它，它就不是守卫，是空话**：留着它的唯一理由是还能被人从别的入口叫到（`FeatureNotSupported('generators')` 今天三种极端形状全被接受，只剩"没有入口"这一个理由）。
- **一个数被别人量错过一次，就值得第二个从零写的脚本**：对不上时值钱的不是平均数，是**两份命令**——我独立从零数出 `1064 / 3200`（640 点名算子、424 类型层面），h-fmt 的自报是 `999 / 3195`；差 65，其中 666 条落在我这边的 `modules/` 里、多是窄浮点类型（`bf16[]`、`f16`）的拒绝，正是 `lane-narrow` 在做的那一族。**分母的两个数（3200 与 3195）差 5 个文件，两份命令都在报告里**，谁少算了 5 个或 65 个，一跑就现。
- **一条"没实现"的诊断在实现之后必须消失**：留着它，报的就是假话（作者裁定 2026-10-31：生成器机器收不下的形状是**编译器缺陷**，按内部错误报、附最小程序，不另立"形状不支持"的诊断）。`git grep -n "generators" -- src include` 从 5 处降到 4 处，剩下的全是注释与无关的 `resource_semantics.h` 措辞。
- **`reportUnbuiltShape`（`src/compile/gct/builder.cpp:5713`）是缺陷报告，不是语言面的拒绝**：它报 `InternalDiag::UnknownInternalError`，措辞里写"send the program, this is a compiler defect"。八个调用点全在同一条路上（按出现顺序）：`:5997`（`yield` 无值）、`:6101`、`:6122`（分支臂/`if` 里的形状）、`:6212`、`:6224`（`case`/`match` 臂）、`:6299`（`case` 节点）、`:6372`（`from` 之后无语句）、`:6408`（循环尾的形状）。**以后有人搜 `UnknownInternalError`，这八处全是缺陷路径**，不是"语言不支持"。
- **一条诊断消失之后，它原来的调用点要能一眼认出是缺陷路径**：否则下一个人会把内部错误当成语言面的拒绝（`reportUnbuiltShape` 的八个调用点就是这条的实例：名字与措辞都指向"缺陷"，不指向"不支持"）。
- **"还没实现"和"这个目标没有"是两句话**：前者是缺口，后者是能力边界——混着说，普查就会替一个不存在的缺口排工。`std::mem::blocks()` 读运行时块空间（作者裁定 2026-10-31：A，拒绝且说实话），措辞里**去掉了 "yet"**，改成"a program std::cpp writes has no runtime block space of its own: the counters are not available on this target"；用例同时钉 `expect_output_not_contains = ["yet", "has no translation"]`，那条不变量就是钉子。普查里这 10 个程序单列成"目标不具备"，不算缺口。
- **一句拒绝、一个类型、39 个程序的格子，先按程序数排进计划，再按句数派工**——两个数都要，但派工看后者。`tensor:ones`(39)+`tensor:zeros`(32) 两格各 1 句、1 类型，**真翻译 0、换桶 71**：原句把 `int[]`（形状参数）说成"没有翻译"，而数组是翻译得了的，缺的是 tensor 值本身——**换桶就是把拒绝挪到它真正缺的东西上**。
- **一个缺口落在 270 个程序上时，先问这 270 个是不是都在等同一个类型**；是的话，**派工单位是类型，不是程序**（`tensor:ones/zeros/load_npy/reshape` = 369 个程序，`Tensor` 在 `src/passes/trans/cpp` 里出现 0 次——一件活的 369 张脸）。
- **随机值能不能跨桥，先问桥带不带种子**：不带种子的桥，翻过去也复现不了。`rand:uniform_array`（23）+`rand:normal_array`（3）的拒绝原先点名 `Key`——而 key 可以在 C++ 侧算（`rt::randomStream` 用的是同一套 philox），真正拦路的是它们造出来的**带形状的数组**；换桶 26、真翻译 0，说的是同一件 tensor 缺口。
- **两个后端要给出同一份输出，最省的办法不是各写一遍语义，是让一个共用的实现过桥**：张量在生成程序里是 `rt::Foreign`（带计数的句柄，里面是运行时的 `RootHandle`），语义只在运行时 tensor 模块里实现一份（作者裁定 2026-10-31 05:50，设计稿第 9 节与第 194 行）。写第二份"数 + 形状"的语义，等于把"同一输入同一输出"交给两条代码去守。
