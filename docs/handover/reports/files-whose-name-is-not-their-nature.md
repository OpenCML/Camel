# 名字与性质不符的四处文件

四处都回到代码核过。每条五件事：叫什么、实际是什么、谁会判断错、一条能区分"装载面还是别的东西"的读数、代价与建议。第 3 处是整棵树的问题，单独成节；末尾记下这三条更正怎么来的。

## 1. 诊断消息表：`src/core/error/diagnostics/messages/semantic.cpp`

- **叫什么、在哪**：诊断消息表 `semantic.cpp`，在 `src/core/error/diagnostics/messages/`。`src/compile/` 下没有这个文件——按名字去 `src/compile/` 找会找不到。
- **实际是什么**：生成物。`scripts/diagnostics-catalog.mjs` 从 `diagnostics/registry.tsv` 反写 5 个分节的 `.h`/`.cpp` 与 `docs/diagnostics.md`；文件第 4 行写着 "Generated by ... Do not edit"（`semantic.cpp:4`）。本条表 237 条 = registry 里 237 行 semantic（全表 302 个码）。
- **谁会判断错**：下一个要改诊断措辞或加诊断码的人。他会改这条 `.cpp`（或 `docs/diagnostics.md`），以为改了就生效；实际他会被构建拦住，必须先改 `registry.tsv` 再跑 `--write`。**这是"当场红"，不是"下次生成才丢"**：`--check` 挂在 `libcamel_objects` 的构建依赖上（`CMakeLists.txt:106` 的检查，`:113` 的依赖），手改过不了。这一点要说清，否则读者会以为这文件没人管、改了会悄悄没。
- **读数**：
  ```
  $ node scripts/diagnostics-catalog.mjs --check        # 手改一条消息之后
  diagnostics registry: 1 problem(s)
  - src/core/error/diagnostics/messages/semantic.cpp is not what diagnostics/registry.tsv produces; run `node scripts/diagnostics-catalog.mjs --write`
  ```
  改回后再跑：exit 0（"302 codes ... the emitted headers agree"）。
- **代价与建议**：已经是第三选（生成物 + `--check`），代价 0，不动。要改就改 `registry.tsv`。

## 2. 五个"签名"：`stdlib/signatures/*.cml`

- **叫什么、在哪**：`stdlib/signatures/{autodiff,ckpt,nn,tensor,tiles}.cml`，放在会被 import 的 `stdlib/` 根下，写法与声明同形（`#op(...)` + 无函数体 `func`），共 75 条。
- **实际是什么**：参考镜像，不参与编译。头部自述：`autodiff.cml:37`、`nn.cml:25`、`tiles.cml:19` 都是 "For reference only: these declarations are not compiled."；`tensor.cml:8-9` "this file is for reference only (it is not compiled)"；`ckpt.cml:4` "(reference metadata, not compiled)"。读者只有脚本：`scripts/stdlib-reference.mjs`（生成 `docs/stdlib-reference.md`、跑 `--verify-ops`）与 `scripts/camel-for-ai.mjs:46`（生成给 AI 的参考）。真实声明在 `stdlib/<模块>.cml`；C++ 侧已声明的名字由 `modules/<模块>/module.cpp` 的 `kDeclaredOperators` 跳过导出（`modules/nn/module.cpp:30`、`modules/tensor/module.cpp:60`）。
- **谁会判断错**：下一个想给某算子"补个签名 / 加个默认值 / 让它进库"的人。他会改这里，以为改了接口；编译行为与程序行为都不变——权威写法一在 `stdlib/<模块>.cml` 的声明，二在 `modules/<模块>` 的 C++ 解析器。
- **读数**：
  ```
  $ git grep -n "stdlib/signatures" -- src include CMakeLists.txt
  （无输出：没有任何编译路径读它）
  $ node scripts/stdlib-reference.mjs --verify-doc
  docs/stdlib-reference.md is up to date
  ```
- **代价与建议**：选"移到别处"——挪到 `docs/reference/signatures/`（或 `internal/`），离开可 import 的 `stdlib/` 根。代价约 10 行：5 个模块的 `computed:` 路径、三个脚本的读法、一两处链接。要更彻底再上第三选：由 `inspect --ops` 反向生成并纳入 `--check`（要主机上的构建，贵一档）。

## 3. `docs/design/` 整棵树没有英文版：`program-transforms/README.cn.md` 只是一个样本

- **叫什么、在哪**：程序变换设计稿，`docs/design/program-transforms/README.cn.md`；目录里只此一个文件。
- **实际是什么**：中文单版。`docs/design/` 下 18 份设计 README，`.en.md` 为 0；英文的 `design-principles.en.md:437` 直接把读者链到这份中文稿。全仓 20 个 `.en.md` 分布在顶层文档、教程、`docs/language/en/` 与 handover 的快照里，没有一份在 `docs/design/`。
- **结论（比这一处文件大）**：**"缺英文版"不是这一处的缺陷，是整个 `docs/design/` 树的现状。** 所以"英文版同笔对齐"这条纪律今天没有执行对象——它要求一件不存在的东西。一次"补英文同段"的改动只有两种走法：先造一份英文版（157 行一次性，且此后每次改设计稿都要成对改），或把要求收窄到"已有英文对的文件"。不问清是哪一种，执行者只能跳过或自造半份。
- **谁会判断错**：按英文原则读文档的人，点进去落到中文；或接到"中英文同笔"要求的人，找不到英文文件，只能跳过或另造一份。
- **读数**：
  ```
  $ git ls-files docs/design/program-transforms
  docs/design/program-transforms/README.cn.md
  $ (git ls-files "docs/design/**/*.en.md").Count
  0
  ```
- **代价与建议**：要求不变就补 `README.en.md`（157 行，且进入"每次改都要改两遍"的名单）；要求只对成对文件成立，就在 `design-principles.en.md:437` 标一句 "(Chinese only)"，1 行。后者便宜且诚实。

## 4. 规则集模块里没有 `rule`：`stdlib/rulesets/jvp.cml`

- **叫什么、在哪**：前向求导的规则集模块，`stdlib/rulesets/jvp.cml`。
- **实际是什么**：7 个形状像规则的普通函数，不是 `rule`。文件里有 `Lift<T>`、`lift`、`zero_tangent` 和 7 个标量 `*_jvp` 的 `func`（`add_jvp` 连 `export` 都没有），**`rule` 声明 0 条**；`rule` 声明 10 条全在 `stdlib/autodiff.cml`（前向 5：`add/sub/mul/div/neg_jvp`，转置 5：`*_t`）。索引只对模块名以 `rulesets.` 开头的模块建（`src/compile/gir/program.cpp:658-659`）：`rulesets.jvp` 以它开头却没有规则，`autodiff` 有 10 条却不以它开头。
- **判据（这一处的关键）**：**名字叫规则集模块，装的是 7 个形状像规则的普通函数，而真正的 `rule` 声明全在 `autodiff` 里。** 这比"空的"更危险：空文件一眼看穿；这个文件有类型、有零切向量、能编译，还被 `test/cases/compile/rulesets/jvp_lift.cml` 导入，**看起来有内容**——照着它加规则的人不会怀疑自己走错了地方。
- **谁会判断错**：下一个按设计稿第 3 节给前向求导加规则的人。设计稿说"写在规则集模块里，例如 `rulesets/jvp.cml`"，他会打开这个文件，照着 `add_jvp` 加一条 `func`；那不是 `rule`，不进索引，前向求导不会变。反过来他也会以为 `autodiff.cml` 的 10 条 `rule` 不属于任何规则集。
- **读数**：
  ```
  $ (Select-String stdlib\rulesets\jvp.cml -Pattern '^\s*(export )?rule ').Count
  0
  $ (Select-String stdlib\autodiff.cml    -Pattern '^export rule ').Count
  10
  $ git grep -n "rulesets\." -- src/compile/gir/program.cpp
  659:            unit->module->name().rfind("rulesets.", 0) == 0) {
  ```
  索引本身在测试里有读数：`test/plans/feat/compile/rulesets.plan.toml` 期望 `RULESET rulesets.probe_rule_heads + -> add_rule`。
- **代价与建议**：选"移到别处"——把 5 条前向 `rule` 从 `autodiff.cml` 搬进 `rulesets/jvp.cml`，名字与索引才对得上。代价：5 条规则、两处头部说明、引用它们的用例，中等。更便宜但不解决问题的是改名 `rulesets/lift.cml`（承认它只有类型那一半），索引仍然为空；删掉那 7 个 `*_jvp` 则要改 `jvp_lift.cml` 的 import 与期望输出。

## 总结判据

1. **名字与位置替人做判断，所以名字错了比内容错了贵。** 内容错了，测试或构建会把它顶出来；名字错了，人只会走到错的地方改一通，然后一切照旧地绿着——错的地方没被检验，于是连"没改对"都不会有人说。可复用的问法：**不看内容，只凭名字和位置，能不能正确回答"改这里会不会改变行为"？**
2. **生成物是一套，不是一件：来源、生成器、产物、检查。** 只装前三件，手改产物会在下一次生成时无声消失；四件都装，手改当场变红。所以"它是生成的"要能站住，得能指出那条会红的命令——例如 `--check` 挂在构建依赖上，才不是"下次再说"。
3. **不参与编译的文件，唯一的风险是漂移，而漂移只有检查能挡。** 它不在构建里，也没有测试会因它变红；它今天对，只说明今天有人对过。要么让它从真声明生成，要么每次改动后比一次，"读着觉得对"不算一种检查。

## 这三条更正怎么来的

每一条都是回到代码里核对时发现的，不是从上一轮读数里抄来的：

- **第 1 处**：按名字去 `src/compile/` 找不到文件（`git ls-files "**/semantic.cpp"` 只中一个，在 `src/core/error/`）；再手改一条消息跑 `--check`，才看见它是当场红，而不是下次丢。
- **第 4 处**：两种 pattern 各数一遍——`^\s*(export )?rule ` 在 `jvp.cml` 得 0，`^export rule ` 在 `autodiff.cml` 得 10；再看那 7 个 `func` 和 `jvp_lift.cml` 的导入，才知道"空的"是错的，真正的问题是"看起来有内容"。
- **第 3 处**：`git ls-files "docs/design/**/*.en.md"` 得 0，才把"这一处缺英文"改成"整棵树没有英文"，纪律没有执行对象。

**若照抄前一轮的读数，这份报告会写错三处**：把生成物写成"下次生成才丢"、把规则集写成"空的"、把一处缺口写成孤例。**核对不是礼貌，它是唯一能把"读数"变成"事实"的步骤。**
