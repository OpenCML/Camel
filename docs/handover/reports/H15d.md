## 1. A NaN's sign never appears in text

### 1.1 The rule and where it lives

`docs/language/02_lexical.md` §2.5.2 (English: `docs/language/en/02_lexical.md`) has the decisive line in
its table of float texts:

> 无穷、NaN | `inf`、`-inf`、`nan` | **NaN 不带符号（不会打印 `-nan`）**

> Infinities, NaN | `inf`, `-inf`, `nan` | **A NaN has no sign (`-nan` is never printed)**

The same section says a float's text is the shortest text that reads back as the same number, and design
principles 7.7 requires that rule to be one rule, shared by `string`, `println` and `format`. Design
principles 7.7 also constrains only the **value** of a NaN from ordinary arithmetic ("普通算术产生的 NaN
不受此约束"): nothing here decides the sign bit of `sqrt(-1.0)`, and nothing here changes it. The defect was
at the **text boundary**: the value kept its sign bit, but the text of that value is decided, and it has no
sign. So the fix is to not write the sign, not to change the value.

**Honest note on the principles.** 7.7 states that a NaN prints as `nan` (in the parenthetical of the value
bullet) and that the float-to-text rule is one rule across `string`/`println`/`format`; it does not itself
spell out "the sign bit is never written". The explicit sentence is in the language reference §2.5.2, and
the H15c check restates it as the defect's rule. So the rule followed here is the documented one, not one
invented in this task. Question 1 in §6 asks whether 7.7 should carry the sentence too.

### 1.2 Every path that writes a float, and what changed

| path | before | after |
|---|---|---|
| interpreter, `println(x)` / `string(x)` / `'{}'` / `${x}` (no specification) | `nan` (`camel::utils::floatText`) | unchanged: `nan` |
| interpreter, `format`/`println` with a specification (`{:.2f}`, `{:>8}`, `{:e}`, `{:+}`) | `-nan` for a sign-bit NaN, because `fmt::formatter<T>::format` writes the sign bit | **fixed**: `camel::utils::withoutNaNSign(value)` is handed to `fmt` |
| interpreter, complex with no specification (`complexText`) | `nan`, and `+nani` for a NaN imaginary part | unchanged |
| interpreter, complex with a specification (`specText`) | real part `-nan`; an imaginary NaN wrote `-nan+-nani`, because its magnitude kept the sign | **fixed**: both parts go through `withoutNaNSign` |
| `std::cpp` generated program, float with and without a specification (`include/camel/standalone/format.h::formatFloat`) | `nan` | unchanged (already `signbit(v) && !isnan(v)`) |
| `std::cpp` generated program, complex (`formatComplex`, `complexText`) | `nan`, `+nani` | unchanged |

The two interpreter files:

- `src/builtin/operators/float_format.h` — the specification branch is now
  `fmt::formatter<T>::format(camel::utils::withoutNaNSign(f.value), ctx)`; the no-specification branch is
  still `camel::utils::floatText`, which never wrote a sign. The header comment records why.
- `src/builtin/operators/complex_format.h` — `specText` takes `withoutNaNSign(value.real)` and
  `withoutNaNSign(negative ? -value.imaginary : value.imaginary)`; the separator is still decided by
  `std::signbit` of a non-NaN imaginary part, so `3-0.00i` keeps its minus (`-0` is not a NaN) while a NaN
  imaginary part is `+nani`.
- `include/camel/utils/number_text.h` — `withoutNaNSign<T>(value)` returns
  `std::numeric_limits<T>::quiet_NaN()` for a NaN and the value itself otherwise (signs of `-0.0` and
  `-inf` are untouched). It is shared with the entry-argument reader of §2.

`withoutNaNSign` is used instead of `std::abs` or `-value`: `-value` on a NaN may or may not clear the sign
bit depending on the platform, while `std::numeric_limits<T>::quiet_NaN()` is defined to be a positive
quiet NaN. The **value** is not changed in any program variable; only the copy handed to the formatter is
made positive.

## 2. A complex number as an entry argument

### 2.1 The grammar

The text is the complex text of the language (reference §2.5.3), which is what an imaginary literal is
written as:

```
text        := imaginary-only | real imaginary-with-sign
imaginary-only := <float> "i"                 -- "4i", "-2i", "1e-3i"
real        := <float>
imaginary-with-sign := <float> ("+"|"-") <float> "i"   -- "1+2i", "0.5-0.25i", "-1.5-0.25i"
```

- The text must end with a lowercase `i`; the part before it must be non-empty.
- The imaginary part begins at the **last** `+` or `-` that is not at position 0 and not the sign of an
  exponent (`e`/`E` before it). Without one, the whole text is the imaginary part, so `-2i` is `0-2i` and
  `4i` is `0+4i` (the leading sign is the number's own sign, exactly as `-2i` is `-(2i)` in the language).
- Each part is read by the same whole-string float parser as a `float` entry argument (`strtod`, which must
  consume the entire part), so `1e-3`, `.5`, `inf` and `nan` read as they do for a float. `nani` is
  `0+nani`; `infi` is `0+infi`; and no NaN part can print a sign (§1).
- A real text (`1.5`, `nan`) is **not** a complex number and is refused, rather than taken as the real part
  with an imaginary part of zero: "a real text is not a complex number" is the rule stated in
  `include/camel/execute/entry_args.h` and the docs.
- Malformed forms are refused at the argument: `1+`, `1+2`, `1+2j`, `1+2i5`, `abc`, `i`, `+i`.

The split lives in `include/camel/utils/number_text.h` (`splitComplexText`), so the interpreter and the
generated program read one grammar, not two.

### 2.2 Interpreter

`src/execute/entry_args.cpp`, `loadValue`: new `case TypeCode::Complex64:` / `Complex128:` that
`splitComplexText`s the text, parses both parts with the same `parseFloat` used for a float parameter
(now taking a `std::string_view`; it copies for `strtod`), on failure `refuse`s with

```
'1+2' is not a complex number (write 1+2i, -2i or 0.5-0.25i)
```

and on success creates the boxed value with `rtdata::Complex::create(real, imaginary, declared->code(),
mm::autoSpace())`, wrapped by `rooted(...)` so the bound value survives a collection while the entry graph
is built. `c64` rounds both parts to `f32` inside `Complex::create`, so the parts are the declared width.
The failure is a located `RuntimeDiag::EntryArgumentInvalid` at the entry function (`main`), naming the
parameter and showing the text; the program does not run. The header comment of
`include/camel/execute/entry_args.h` lists the type and its grammar next to `int`/`float`/`bool`/`string`.

### 2.3 `std::cpp`

The located refusal that H15c left for a complex entry parameter is gone:

- `include/camel/standalone/entry.h` gained `EntryKind::ComplexFloat` (a `c64`, its parts read as `float`)
  and `EntryKind::ComplexDouble` (a `c128`, its parts as `double`), the getters `complexFloat(index)` /
  `complexDouble(index)`, and `readComplex`, which reuses `camel::utils::splitComplexText` from the same
  header as the interpreter, reads the parts with `strtod`, and reports the same message and the same
  located `EntryArgumentInvalid`/`EntryArgumentMissing` reports as `camel` (the compiler renders them into
  the two `Site`s with the values as marks, byte for byte).
- `src/passes/trans/cpp/program_emitter.cpp` maps `TypeCode::Complex64` to
  `{"z", rt::EntryKind::ComplexFloat}` and `args.complexFloat(i)`, and `Complex128` to
  `{"z", rt::EntryKind::ComplexDouble}` and `args.complexDouble(i)`; the parameter's declared type is
  `std::complex<float>`/`std::complex<double>`.
- A parameter **bound** when the program is translated becomes a constant:
  `main_(0, std::complex<double>{1.0, 2.0}, std::complex<float>{0.5f, -0.25f})`.
- The message of the remaining refusal (a tensor or a struct) now lists the accepted types:
  "only the parameters of type int, i32, float, f32, c64, c128, bool and string". The old text was changed
  because the set of accepted types changed, not to make a test pass.

Observed for `test/cases/compile/entry_args/complex.cml`:

```
camel ... std::cpp                                     -> EntryKind::ComplexDouble / ComplexFloat, args.complexDouble(0), args.complexFloat(1)
camel ... --arg z=1+2i --arg w=0.5-0.25i std::cpp      -> std::complex<double>{1.0, 2.0}, std::complex<float>{0.5f, -0.25f}
```

## 4. Changed expectations, and why

1. **`value.float_special`** (in `test/plans/feat/consistency/values.plan.toml`) changed from
   `kind = "behavior"` with `expect_stdout_starts_with = "inf\n-inf\n"` to a snapshot against the new
   `test/plans/feat/consistency/golden/float_special.txt`. The old test existed only because the NaN text
   was platform-dependent ("`-nan` with glibc"): it compared the backends with each other and pinned only
   that the output starts with `inf`/`-inf`. Now that the text is decided by §2.5.2, the case pins the whole
   output (all four backends agree) and the NaN lines are part of it. The description was rewritten to say
   so. This is a strengthening, not a relaxation: the old assertion is still true, and the new one is
   stricter.
2. **`entry_args.cpp_struct_refused`**: the expected message now says "int, i32, float, f32, c64, c128,
   bool and string" instead of "int, i32, float, f32, bool and string". The message changed because complex
   parameters are now read from the command line; the test asserts the message the implementation should
   give, and no other behaviour in that test changed.
3. **No other expectation changed.** No existing golden file was touched (the only golden change is the new
   `float_special.txt`), and no GIR snapshot changed. Two generated artifacts were regenerated:
   - `docs/diagnostics.md`, with `node scripts/diagnostics-catalog.mjs --write` (166 diagnostics), because
     the `EntryArgumentMissing` help text now mentions a complex number
     (`src/core/error/diagnostics/messages/runtime.cpp`). That help text is not asserted by any test, and
     the catalog's own plan passes.
   - `test/plans/feat/parse/golden/ast_hashes.txt`, with
     `python test/tools/parsecheck/check.py snapshot --update`: 5 lines added and 3 replaced (2118 files).
     The three replaced lines are the three cases whose comments/body changed above; the added lines are

## 6. Open questions

1. **Should design principles 7.7 itself state "a NaN's sign is never written"?** The rule is currently in
   the language reference §2.5.2 (and restated in the H15c check). 7.7 requires one text rule and writes a
   NaN as `nan`, which entails it, but a reader of the principles alone cannot see the sentence. I did not
   edit the principles (they are the author's).
2. **`NAN` under `{:E}`.** The uppercase type letters write `NAN`/`INF` (fmt and Python do the same), so
   "the text is `nan`" holds for the absence of a sign, not for the case of the letters. Is that the
   intended reading of "one text rule", or should a specification never change the letters either?
3. **Naming.** The entry kind is `ComplexFloat`/`ComplexDouble` while `FormatArg::Kind` in the standalone
   runtime uses `Complex32`/`Complex64` for the same two widths. I chose the `std::complex` names for the
   entry reader because the parameter type is written `c64`/`c128` but the C++ type is
   `std::complex<float>`/`std::complex<double>`; unifying the two is a small follow-up.
4. **A real text for a complex parameter is refused** (`--arg z=1.5`), not read as `1.5+0i`. That follows
   "read as an imaginary literal is written" and keeps a typo visible, but if a real text should be
   accepted as the real part, this is the place to decide it.
5. **A complex value inside a struct or tuple entry argument** is still refused, exactly as every scalar
   leaf is today: `loadAggregate` accepts only a member "of a type with a file loader, such as
   `Tensor`", and a complex number has no such file form. If struct-of-scalars entry arguments are
   wanted, that is a separate item (it would cover `int`/`float` leaves too).
