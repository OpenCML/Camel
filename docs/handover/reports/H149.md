# H149：`-NoBuild` 复用的安装必须是这份源码构建的（构建戳与守卫）

- 工作树 `D:\Projects\Camel-wt\h149-nobuild-guard`，分支 `handover/H149-nobuild-guard`。
- 基线：`origin/develop` `4579d211d`（H144 合并后）；本分支不 merge/rebase。
- 任务板：H149。
- 结论：`npm run build` 现在在 `out/<tag>/build-info.json` 里记下这份安装的源码内容；
  `camel-remote.ps1 -NoBuild` 在主机上把它与即将验证的树比较，**内容不同就拒绝**（退出码 4），
  同时打印两边的 revision（HEAD + 脏标记）、两边的指纹和变动的文件。内容相同则一个字都不多打。
  覆盖开关是 `-AllowStale`（显式、仍然打印全部不匹配信息并说明"继续"）。

## 0. 结论表

| 问题 | 答案 |
|---|---|
| 戳是什么 | `out/<tag>/build-info.json`（Release/Debug/每个 release 镜像 tag 各一份） |
| 谁写 | 构建自己：`scripts/common.js: writeBuildInfo()`，由 `scripts/collect-out.js` 在收集完产物后调用；本地 `npm run build`、主机构建、release wheel 都带它 |
| 戳里有什么 | `schema`、`config`、`tag`、`builtAt`、`revision`（`git rev-parse HEAD`）、`dirty`/`dirtyCount`/`dirtyPaths`、`git`（是否可用）、`fingerprint`（`version`、`roots`、`files`、`hash`、`fileHashes`） |
| 守卫比什么 | 只比指纹：把构建会读的每个文件按 `相对路径\0内容 SHA-256\n` 排序聚合。revision 与脏标记只用于人读的消息 |
| 不匹配时 | 退出码 4，打印 `built from:` 与 `this tree:` 两行、两边的指纹、`changed since the build` 文件清单，并说明 plan 会跑到旧二进制/旧 `stdlib` 上 |
| 覆盖 | `-AllowStale`：仍然打印同样的不匹配块，最后一行改成 `-AllowStale was given: continuing anyway` |

| 触发 | `src/`、`include/`、`modules/`、`tools/`、`stdlib/`、`third_party/`、`cmake/`、`CMakeLists.txt`、`conanfile.txt` 的内容变化 |
| 没有戳 | 拒绝，并告诉使用者先不带 `-NoBuild` 构建一次 |
| `git` 不可用 | 告警一次，`revision` 记 `null`、`git: false`；指纹仍然有效（它是文件内容），守卫照样生效 |

## 2. 戳记录什么

`out/latest/build-info.json`（主机构建 #1 的原文，节选；完整文件 68,970 字节）：

```json
{
  "schema": 1,
  "config": "Release",
  "tag": "latest",
  "builtAt": "2026-10-22T01:19:15.131Z",
  "revision": "4579d211d649225c16353f422186c5819178f288",
  "dirty": true,
  "dirtyCount": 4,
  "dirtyPaths": [
    "docs/npm-scripts.md",
    "scripts/collect-out.js",
    "scripts/common.js",
    "scripts/build-info.js"
  ],
  "git": true,
  "fingerprint": {
    "version": 1,
    "roots": ["src", "include", "modules", "tools", "stdlib", "third_party", "cmake", "CMakeLists.txt", "conanfile.txt"],
    "files": 1125,
    "hash": "edd3ba1b8fe742c0b88e56791a7d3b97658dc0d843956b74a22697f358962382",
    "fileHashes": { "CMakeLists.txt": "d46ffb7ca372eefc", "...": "1125 条，每条取 SHA-256 前 16 位" }
  }
}
```

- **由构建写**：`collect-out` 在 `Artifacts collected` 之后调用 `writeBuildInfo(config, tag)`；
  Release 镜像 tag 各写一份（`tag` 字段写自己，守卫才能说清在哪个目录里看）。
  `scripts/build-info.js stamp` 调的是同一个函数（只给报告/排查用，构建不经过它）。
- **脏树照实记**：构建 #1 是在实现还没提交时做的，戳里就是 `dirty: true`、4 个路径
  （`docs/npm-scripts.md` 与 3 个 `scripts/` 文件）；这批内容确实就是那台二进制的内容。提交
  之后内容没变，守卫在 revision 变化（`4579d211d6` → `9582e32d6`）的情况下依然放行（记录三·前置）。
- **不含绝对路径、主机名**：只有仓库相对路径。因此把 `out/<tag>/` 整个打包不影响可移植性。
- **release 产物**：`pypi-rollup.js` 把 `out/<tag>/` 整树拷进 wheel 的 `.cmlenv`，所以 wheel 里
  也会有 `build-info.json`（67 KB，内容即上表）。这是允许的：它说明那个 wheel 的二进制是从
  哪份源码来的。没有收集器/打包器按文件名枚举 `out/latest/`，多这个文件不影响它们。
- **git 不可用**：`revision: null`、`git: false`，并在构建日志里告警一次："the source
  fingerprint is still recorded, so -NoBuild can still tell whether the install matches this tree"。
  这是有意的选择：拒绝构建会让离线/无 git 的环境无法构建，而指纹不依赖 git。

## 3. 守卫比较什么（以及为什么不比 revision）

### 3.1 指纹

`sourceFingerprint()` 遍历 `BUILD_INFO_ROOTS`（上表 7 个目录 + 2 个根文件），跳过 `.git`、
`node_modules`、`build`、`out`、`__pycache__` 与产物扩展名（`*.o/obj/a/lib/so/dll/dylib/pdb/ilk/
cmo/pyc/pyo/pyd/exe`），对每个文件算 SHA-256，按 `相对路径` 排序后聚合
`sha256(rel \0 内容哈希 \n)`。1125 个文件、约 11 MB，在主机上 < 1 s（每次 `-NoBuild` 一次，
和 push/scp 的连接代价比可以忽略）。

同一个内容在 Windows 与 Linux 上算出同一个值：本地预检（Windows，工作树）与主机构建 #1
（Linux）都是 `edd3ba1b8fe7`。

### 3.2 为什么是内容，不是 commit

`git rev-parse HEAD` 不知道"这次提交有没有动二进制"。任务书要求的两侧都要照顾：

- 只改 `docs/`、`test/`、`scripts/` 的提交不应该要重建（否则每条文档提交后第一次 `-NoBuild`
  都挨一记，人就会习惯性加 `-AllowStale`，守卫随即失效）；
- `src/` 动一个字节就必须拒绝。

记录三·前置就是这条规则的正向证明：实现提交前后**内容完全相同**、HEAD 不同、脏标记从
`dirty: 4` 变成 `clean`，守卫静默放行。反过来，记录一里 HEAD 相同、只有工作树多了一行注释，
守卫拒绝。

### 3.3 为什么这些路径、不是整棵树

| 路径 | 在指纹里 | 理由 |
|---|---|---|
| `src/`、`include/`、`modules/`、`tools/` | 是 | 编译进 `camel`、`libcamel`、`.cmo`、工具；`include/` 还整树安装到 `out/<tag>/include` |
| `stdlib/` | 是 | `collect-out` 原样复制到 `out/<tag>/stdlib`；**H139 的假绿就是这里** |
| `third_party/` | 是 | 根 `CMakeLists.txt` 把 `third_party/*.cpp` glob 进 libcamel |
| `cmake/`、`CMakeLists.txt`、`conanfile.txt` | 是 | 决定编译选项、源文件集合、导出列表与依赖版本 |
| `test/` | 否 | 用例与计划在跑计划时才读；改用例本来就该立刻生效（记录二） |
| `docs/`、`agents/`、`editors/`、`pypi/` | 否 | 构建不读 |
| `scripts/` | 否 | 构建工具本身不是被编译的内容。**例外**：改 `collect-out` 会改变"新构建会安装什么"，这种改动请自愿重建一次（见 §5.3） |
| `assets/`、`examples/`、`benchmarks/`、`showcase/`、`exemplars/` | 否 | 不参与构建 |

产物被排除是必要的：`collect-out` 会把 `.cmo` 写进源码树的 `stdlib/`（H138 的机制），它们是
每次构建的产物，不是输入。

## 5. 诚实的边角

### 5.1 未跟踪的脏树照实记

构建 #1 就是脏树（实现未提交，4 个文件）。戳里 `dirty: true` + 路径清单，守卫随后拿内容比，
放行。反过来，构建之后把某个未跟踪的 `src/` 新文件删掉，指纹会变、守卫会拒绝——正确。

### 5.2 `test/` 的改动不该让守卫说话

用例与计划在跑计划时读，改完立刻生效；重建二进制对它们没有影响。记录二证明放行。改 smoke
自己用的用例而 golden 没跟着更新时，红的是 `inspect.tok_snapshot`（测试内容变了），不是守卫。
两个信号必须分开，否则"测试红"会被误读成"安装不对"。

### 5.3 `scripts/` 也不在指纹里，但有一个自愿重建的例外

`collect-out`/`common.js` 不编译，但它们决定 `out/<tag>/` 里放什么。改了安装配方之后继续
`-NoBuild`，复用的是一个按旧配方装的安装——它仍然是"这份源码编译的二进制"，只是布局可能不全。
本批不把 `scripts/` 放进指纹：任务书明确要求脚本改动不需要重建，而把它放进去会让每条工具
改动都逼一次 400 s 构建。规矩是：**改 `collect-out`/`common.js`/`.cmo` 清单之后，主动重建一次**
（§5.8 把它列为已知残余）。

### 5.4 `-Tier debug` 检查 `out/debug`

计划运行器在 `--tier debug` 时读 `out/debug`（`test/tools/run-tests.mjs` 的 `preflightBuild`），
所以守卫按 `$Tier` 选 tag：`debug` 检查 `out/debug`，其余检查 `out/latest`。`-Config Debug` 但
不带 `-Tier debug` 时，计划其实跑的是 `out/latest`，守卫也就检查 `out/latest`——检查的是
**计划实际会用的安装**，不是上一次构建写的那一个。

### 5.5 `git` 不可用

告警 + `revision: null`，指纹继续工作。理由：指纹是文件内容，不依赖 git；而拒绝构建会让无 git
的环境无法构建。消息里 `built from:` 会写 `unknown revision (git unavailable)`。

### 5.6 比守卫老的分支

`camel-remote.ps1` 在工作站上（仓库外），旧分支的检出里没有 `scripts/build-info.js`。这时主机上
的远端块打印：

```
[camel-remote] WARNING: scripts/build-info.js is missing in this checkout; -NoBuild cannot verify out/latest (the tree predates the H149 guard)
```

然后照常跑。这是唯一诚实的洞：旧分支无法被守卫，拒绝会让所有旧工作树无法收尾。分支一旦包含
本提交（合并 develop 之后自动如此），守卫就开始工作。

### 5.7 手工跑 `out/latest/bin/camel` 绕过守卫

守卫挂在 `camel-remote.ps1 -NoBuild` 上；直接跑 `out/latest/bin/camel` 或
`node scripts/test.js --build release` 时没人比较戳。任务书的要求是"远端脚本的 `-NoBuild` 可
检测"，本批没有把守卫塞进计划运行器：`node scripts/test.js` 本地运行时 `out/latest` 就是刚构建
的，多一次 1125 文件的哈希只是噪音（但它确实能抓到"H138 式"的手工陈旧安装）。留给协调者决定。

### 5.8 已知残余

1. `npm run out`（只收集、不编译）会按**当前**源码写戳，但 `build/` 里可能是上一次的产物。
   这是"collect 不是 build"的既有语义；只走 `npm run build` 时不存在。报告明说：不要拿
   `npm run out` 当构建。
2. 指纹是粗粒度的：`src/` 里任何字节都会逼一次重建（哪怕只是注释）。这是有意的，重建一次
   ~130 s（增量），比一次假绿便宜。
3. 每文件哈希截断到 16 位（64 bit）只用于"哪些文件变了"的消息；聚合哈希用完整 SHA-256，
   判定不依赖截断值。
4. 戳跟着 `out/<tag>/` 走。跨机器复制 `out/latest` 时（本流程不做）两边指纹可能因换行/路径
   集合不同而不同，守卫会拒绝——宁可拒绝。

## 8. 给 skill 的段落

> **`-NoBuild` 现在有守卫（H149，2026-10）。** `npm run build` 会在 `out/<tag>/build-info.json`
> 里记下这份安装的源码内容（构建会读的全部路径的 SHA-256，外加 HEAD 与脏标记）；
> `camel-remote.ps1 -NoBuild` 在主机上先比较它，内容不同就退出 4，打印两边的 revision
> （HEAD + 脏标记）、两边指纹和变动的文件。**先看这四行再决定下一步**：`built from:` 是安装
> 的来源，`this tree:` 是要验证的树，`changed since the build:` 是差在哪，最后一行告诉你是重建
> 还是加覆盖。只改 `docs/`、`test/`、`scripts/` 不会触发（用例在跑计划时读，不需要重建）；
> `src/`、`include/`、`modules/`、`tools/`、`stdlib/`、`third_party/`、`cmake/` 动一个字节就会
> 触发——`stdlib/` 也在里面，因为 `-NoBuild` 读 `out/latest/stdlib` 这份副本（H139 的假绿）。
> 只有显式 `-AllowStale` 能放行，它会自己声明"这个结果不描述这棵树"；不要在没有这一类声明的
> 情况下把 `-AllowStale` 写进任何脚本。分支比守卫老（没有 `scripts/build-info.js`）时只告警；
> 改过 `collect-out`/`common.js` 之后要主动重建一次。事故账单：H129 9 条、H132 1 条、H139 一条
> 无意义的绿。
