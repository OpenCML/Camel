# H110 控制输入不再使子项失去规则匹配

## 0. 结论

**问题**：一个节点的**控制输入**该不该让它退出"定律只谈它的数据输入"的重写？按 H95 的裁定，
控制边只安排两个操作之间的顺序，不改变值（设计原则 3.3、3.4），所以定律在数据上成立就该在
带控制边时也成立——前提是重写引擎不把计算移过控制边安排的顺序。

**答案**：`shapeTakesPart` 里那道守卫保护的既不是形状推断，也不是定律的可靠性，而是**顺序**：
`rewrite` 过去只搬运**根节点**的控制输入，子项一旦被定律吃掉，它的等待就丢了。现在匹配时收集
"定律不再读取的每个算子子项"的控制输入，替换的写法全部接管；形状 3（只能作根）随之删除，
带控制边的纯节点和不带的节点一样参与同余类与子项匹配。

**计数**（`std::opt(safe_fp=false/true)` 后的 `main`，add/mul 个数）：

| 用例 | H100 之后 | H110 之后 | 差从哪来 |
|---|---|---|---|
| `integrated.graph.false` | 15 | **10** | −4：`strict_coefficients`、`relaxed_coefficients` 各一次 `float_combine`（2 乘 1 加 → 1 乘）；−1：`underflow_sensitive` 的 `t + t`（`t = x * 0.1`，内联后带控制边）现在由 `float_combine` 合成 `x * 0.2` |
| `integrated.graph.true` | 15 | **14** | −1：`strict` 的 `x * 3 + x * 3` 现在由 `float_double` 直接合成 `x * 6`（精确加倍，不需要许可）；`strict_coefficients` 仍是 3，严格策略不合并系数 |
| `gradient.false` / `.true` | 5 | **5** | 与控制边无关，见 §3.3：是 `x * c` 不匹配常量在左边的 `c * x`，不是本轮的守卫 |

程序值不变：四个后端（nvm/fvm/jit/prl）输出逐字符一致，加固安全模式与不加固一致。

**顺序证据**：新增 `order.graph` 钉住"改写后的乘积仍带着原来的控制边"，`order.execution` 在
四个后端钉住打印顺序；提取阶段本来就把同一值的所有写法等待过的东西并到留下的写法
（`src/runtime/writings.cpp` 的 `extract`，904–917 行），所以让带控制边的节点进同余类也是安全的。

## 1. 这道守卫原来保护什么

### 1.1 两处代码，一个死参数

`src/runtime/writings.cpp` 里有两处把控制输入挡在外面：

```cpp
bool shapeTakesPart(..., size_t ctrlInputs) {
    if (ctrlInputs != 0) return false;
    ...
}
```

但两个调用点（`shapeOf` 与 `lookupOrAdd`）都传 `0`，这个参数从来没起过作用。真正起作用的是
`shapeOf`：

```cpp
takes[node] = !yes ? 2 : draft_.ctrlInputsOf(node).empty() ? 1 : 3;
```

形状 3 的含义是"本该参与，但有控制输入，因此只能作规则的根"。`canBeRoot`（1 或 3）用在
`rewrite` 的根过滤、`saturate` 的根列表与 `matchFrom` 的 `at == 0` 分支上；`takesPart`（1）用在
子项、`lookupOrAdd` 的同余资格与提取的保留判断上。历史（`af8756fc1`）说明形状 3 是为了让
"等待某事物的纯节点"能作规则根：**替换它的写法接管等待**。

### 1.2 它不是为了形状推断，也不是为了定律

`shapeOf` 的其余部分只看数据：常量、转换、访问、纯算子，不写回、不读变量。形状推断不需要
"有没有控制边"这个信息——控制边不进入 `NodeKey`，也不进入类型。定律的可靠性也不依赖它：
定律的语句只提数据输入，H95 已裁定控制边不改变值。所以这道守卫唯一的实际作用是防止重写把
计算**移过**控制边安排的顺序，而它做到这一点的方式是"干脆不匹配"，代价是定律在该图上不触发
（H100 §4 的 11 → 15）。

### 1.3 真正缺的那一步

`rewrite` 里过去是：

```cpp
const std::vector<gc_node_ref_t> waits(draft_.ctrlInputsOf(node)...);
```

只取**根**的等待。定律吃掉的是子项：`float_combine` 吃掉两个 `x * c` 的乘积，`float_fold`
吃掉内层乘积。这些节点被 `eraseUnused` 删掉后，它们的控制边也就没了，新写法不会等它们等过的
事物。所以只要"替换写法接管子项的等待"这一步补上，允许子项带控制边就是安全的。

## 2. 规则（实现）

`src/runtime/writings.cpp`、`include/camel/runtime/writings.h`：

1. `shapeTakesPart` 删掉 `ctrlInputs` 参数与早退；`shapeOf` 只返回 1（参与）或 2（不参与）；
   `canBeRoot` 删除，所有调用点改用 `takesPart`。带控制边的纯节点因此进入同余类，也能作子项。
2. `matchFrom` 新增 `std::vector<gc_node_ref_t> *waits`：匹配到一个算子子项时把
   `ctrlInputsOf(candidate)` 去重后压入，递归返回时把 `waits` 恢复到进入前的长度；`rewrite`
   在 `emit` 时把当前 `waits` 快照到 `chosenWaits`（根的控制输入由调用方预先放入），
   `saturate` 不建替换写法，传 `nullptr`。
3. `rewrite` 在 `build` 之后用 `chosenWaits` 作为等待集合：`made < before`（重写结果是一个
   已经存在的写法）且等待非空时**不改写**——给已有节点加控制边可能造环，这保留了原来的保守
   行为；其余情况把每个 `wait != made` 挂到 `made` 上。
4. 注释与头文件同步：控制输入"只排序、不改变值"，以及 `matchFrom` 的 `waits` 契约。

`shapeTakesPart` 的注释、`shapeOf` 的注释、`DraftWritings` 的类注释、`extract` 的注释都改成
同一条规则；`docs/technical/44_values_with_several_writings.md` 的 §3、§4、§5、§7 同步。

**为什么这是安全的**：

- 被定律**保留**的项（作为 `x` 绑定的值）自己带着控制边，顺序随它走；
- 被定律**吃掉**的算子子项，其控制输入被新写法接管，计算不会提早到那个 effect 之前；
- 同余合并（两个只差控制边的写法并成一类）不丢顺序：`extract` 在选择留下的写法时，会把同一
  值的所有写法的控制输入并到它身上（`writings.cpp` 904–917 行，注释原文 "The other writings
  of this value that waited for something (control inputs): the writing that stays waits for it
  too."）。这也是 H95 关于"共享由运行时单元标记回答"的同一条设计：值相同，等待是值的属性
  之外的顺序。

## 3. 计数

### 3.1 默认策略：15 → 10

`test/cases/opt/generic/algebra.cml`，`camel ... --arg x=2 "std::opt(safe_fp=false)" std::jgir`：

| 留下什么 | 条数 | 说明 |
|---|---|---|
| `x * 6.0` | 1 | `strict`：`x*3 + x*3` 由 `float_double` 合成，再折系数 |
| `x * 0.2` | 1 | `underflow_sensitive`：`t + t`（`t = x*0.1`，带控制边）由 `float_combine` 合成 |
| `x * 8.0` ×2 | 2 | `strict_coefficients`、`relaxed_coefficients` 各一次 `float_combine`（各 2 乘 1 加 → 1 乘） |
| `x*3 + x*5` | 3 | `mixed_permissions`：两个乘积在带许可的块**外**，与根节点的许可不同，规则不匹配（保持原样，H87 的既有行为） |
| `x + 1`、`(x+1) * 6` | 2 | `branch` |
| `dtof * 6` | 1 | `strict32`（`dtof` 不算 add/mul） |

合计 10 个 add/mul（`shared_product` 是 `sync` 函数，没有被内联进 `main`，它的两个乘积在它自己
的图里）。控制边：`n25 x*0.2 ctrl=[n23 x*6]`、`n27 x*8 ctrl=[n25]`、`n29 x*8 ctrl=[println]`、
`n12/n13 ctrl=[n29]`——被改写、被合并的乘积仍然排在它原来等的事物之后。

H100 记录的旧 C++ 基数是 11。旧 `simplify<T>` 的 `combine` 分支对 `a == b`（同一个乘积相加）
同样会走"系数求和"（`required` 只有 `kReassociate`，同号非零时成立），所以 11 不能逐条对应当前
的图；本轮以实测的 15 → 10 为准，并给出上面逐条定律的归因。

### 3.2 严格策略：15 → 14

`std::opt(safe_fp=true)`：`strict_coefficients`/`relaxed_coefficients` 仍是 3 条（严格策略不给
`reassociate`），`underflow_sensitive` 仍是 `x*0.1` 与 `(x*0.1)*2` 两条（`float_combine` 需要
`reassociate`，`float_fold` 需要 `no_infs`，默认都不给）。少的 1 条是 `strict`：`t + t`
（`t = x*3`，带控制边）现在由 `float_double` 直接合成 `x*6`——`exactDoubling(3)` 成立，精确加倍
不需要任何许可，所以严格策略也允许。这正是"守卫不该按控制边一刀切"的直接证据：值的变换是精确
的，旧守卫却因为 `t` 带控制边而不匹配。

### 3.3 `gradient.*` 为什么仍是 5（不是控制边）

H100 §4 把 `gradient.false/.true` 的 4 → 5 也记在控制边这一项下。本轮实测：**这条与我的改动
无关，改前改后都是 5**。`std::opt` 后 `main` 里的五个算子是
`add(x,1)`、`mul(3.0, add)`、`mul(x,2.0)`、`mul(mul(3.0,add),2.0)`、`add(...)`，没有一条带控制边。
缺的定律是 `3.0 * (x+1)` 与 `3.0 * (x+1)` 相加时由 `float_double`（或 `float_combine`）合成
`6.0 * (x+1)`，而 `float_double` 的模式 `x * c` 不能匹配常量在左边的 `c * x`，于是
`float_add_self`（`t + t => t * 2`，不需要子项）先把和吃掉了。实测：

```
let t = 3.0 * (x + 1.0);  t + t   =>  (3.0 * (x+1)) * 2.0     // 3 条 add/mul
let t = (x + 1.0) * 3.0;  t + t   =>  6.0 * (x + 1)           // 2 条 add/mul
```

所以这是**交换律匹配**的缺口（模式只按操作数位置匹配），不是控制边，也不是许可
（`exactDoubling(3)` 成立）。它记在 §6 的开放点里；本轮没有扩大改动面去改匹配器的交换
尝试。`gradient.*` 的期望因此保持 5，测试不变绿是因为它本来就没红。

## 4. 顺序证据

新增 `test/cases/opt/generic/algebra_order.cml`：`scaled` 在同一个实参表里被调用两次，
`std::opt::inline` 把第一次调用的 effect 串成第二次函数体入口乘积的控制输入，两条定律
（`float_combine` 的 `t+t`）在带控制边的乘积上触发。

- `order.graph`（`std::opt::inline std::opt::algebra std::jgir`）：两个 `:op/mul_d` 的系数是
  `0.2`（定律触发），没有 `:op/add_d` 留下（和确实被折叠），并且每个改写后的乘积都有控制边：
  至少一条指向 `:io/println`（它原来等的 effect），两条乘积之间那条也还在（内联给出的顺序）。
- `order.execution`（`std::opt` + nvm/fvm/jit/prl）：四个后端都输出
  `first` / `scaled 0.4 0.4` / `last`，与不加任何遍时逐字符一致；`backends_agree` 也钉住四个
  后端互相一致。

没有这个修复时，`order.graph` 的断言会失败：`t+t` 的乘积带控制边，`float_combine` 不匹配，
和只能由 `float_add_self` 变成 `t * 2`，于是每次调用留下 `x*0.1` 与 `(x*0.1)*2` 两个乘积
（两次调用共 4 个，且没有 `0.2` 这个系数），而不是两个 `x*0.2`。

`feat/trans` 与 `feat/linear` 的 effect/sync 用例全绿（§5），说明没有 effect 顺序变化。

## 6. 开放点

- **交换律匹配**：模式 `x * c` 不匹配常量在左边的 `c * x`。后果是 `gradient.*` 停在 5，而不是
  旧 C++ 的 4（§3.3）；`shared_product` 也因同样的原因停在 2 个乘积（`t = x*3` 的常量在左边，
  `t*2` 不能折成 `x*6`）。这是匹配器"是否尝试操作数置换"的问题，会改变很多用例的计数，应单开
  任务。
- `float_fold` 需要 `no_infs`（7.3 默认不给）：`(x*c1)*c2` 在系数绝对值小于 1 时可能把中间结果
  推进次正规/零，所以这条许可要求本身是对的；本轮没有动它。
- 本轮没有改 `saturate` 的等待搬运（它不建替换写法），也没有改提取阶段的等待合并——后者已经
  满足需要（§2）。
