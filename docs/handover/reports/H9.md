## 2. `alloc_small` 的偶发访问冲突

[H8 报告](H8.md) 第 6 节记的现象：`camel --timeit std::nvm/5 test/cases/perf/gc/alloc_small.cml --arg reps=200000 --output-format json` 偶发以退出码 `3221225477`（即 `0xC0000005`）结束；约三十次 `--timeit` 调用里两次（`std::nvm/5` 一次、`std::jit/5` 一次），同一条命令重跑即过。

**结论先说：这一项没有查出原因，也没有修任何东西。** 按下面的规模重复运行之后，崩溃一次都没有再出现（`≈4,700` 个进程、`≈130,000` 次"重建模块与图、建 Context、执行、销毁"的循环），所以既没有调用栈，也没有可以指向的缺陷。本节写下的是：复现脚本、复现频率的统计、调试构建没能用上的原因，以及**已排除的可能与证据**；另外记下同一命令上发现的另一种偶发失败（第 5 小节的 `i32` 索引），它没能解释崩溃，但说明这条路径上确实还有不确定的东西。

### 2.1 复现脚本

`test/tools/timeitloop/timeitloop.py`（新增，见 [脚本](../../../test/tools/timeitloop/timeitloop.py)）：

```powershell
python3 test/tools/timeitloop/timeitloop.py --runs 500 --count --jobs 8 --gc both
```

- 每次运行是一个新的 `camel` 进程，命令行就是上面那条命令（`--iterations` 改的是 `std::nvm/<n>` 里的 n）；stdout、stderr 都是管道，与 `test/tools/perfbaseline/baseline.py` 跑它的方式相同，父进程一直读到 EOF。
- 任何非零退出码都算一次失败（既包括 `0xC0000005`，也包括 `--timeit` 的其它失败）：把该次的 stdout、stderr 存成 `tmp/timeitloop/FAILED-<n>-0x<code>.stdout.txt|.stderr.txt`，并把退出码写进 `tmp/timeitloop/failures.log`；结束时打印"进程数、迭代数、失败数、每进程失败率"。
- `--gc mark-sweep|generational|both` 设置子进程的 `CAMEL_GC`（与 `test/tools/gcbench/gcbench.py` 一样按环境变量选回收器）；`both` 按进程交替，两个回收器看到同一段时间里机器的漂移。默认不设 `CAMEL_GC`，即 generational。
- `--camel <path>` 可以指向别的构建（断言构建、带符号的构建，见 2.3）。

合计 **4,656 个进程、130,100 次迭代**，`0xC0000005` 一次也没有。另有两次专门打开压力模式的运行（`CAMEL_GC_STRESS_SAFEPOINT=1`：10 个进程 × 10 个迭代；`CAMEL_GC_STRESS_ALLOC=1`：10 个进程 × 10 个迭代，`reps=2000`），也都没有失败。

注：断言构建那两批一共 260 个进程，其中 20 个是**我自己杀掉的**：调试时用 `Stop-Process -Force` 清理残留进程，把正在跑的两批一起杀了。被杀掉的进程退出码是 `-1`（`0xFFFFFFFF`）、stdout 与 stderr 都是 0 字节；.NET 的 `Process.Kill()` 就是用 `-1` 调 `TerminateProcess` 的，已单独验证过（见 2.4 第 8 条）。真正的 `--timeit` 失败一定会留下 stdout（`--output-format json` 的摘要或一行运行时诊断），且退出码不是 `-1`；所以这两行的"失败"是 0。

**频率。** 按 H8 的 2/30 ≈ 6.7% 的进程失败率，4,656 个进程里应当出现约 310 次；实际 0 次，`P = (1-0.067)^4656 ≈ e^-321`（约 `10^-140`）。反过来，0/4,656 给出的 95% 上界是 `3/4656 ≈ 0.064%` 每个进程（rule of three）。运行量也不是"跑得太轻"：H8 量到的 `alloc_small` 的 `std::nvm` 均值是 156.0 ms/迭代（[性能基线](../../performance/graph-store-baseline.md)），这里同一台机器上量到的是 165–172 ms/迭代（计划里的压力测试 10 个迭代 1.72 s），每次迭代的分配量与回收行为是同一量级。

### 2.3 调用栈：没有拿到，以及为什么

没有崩溃就没有调用栈。为了崩溃一旦出现能马上取栈，做了两个构建，都记在这里：

- **`npm run debug` 在这份代码上链不出来**：

  ```text
  lld-link: error: too many exported symbols (got 72842, max 65535)
  ```

  原因在 `CMakeLists.txt` 的 `WINDOWS_EXPORT_ALL_SYMBOLS TRUE`：`-O0` 下每个内联函数与模板实例都要导出，Debug 的 `libcamel.dll` 超过 PE 的导出上限（Release 因为 `-O3` 把大部分内联掉了才没超）。这是构建系统的问题，超出本项范围，没有改（见待决问题 2）。
- **替代的"调试构建"**：`tmp/build-assert`，配置为 `RelWithDebInfo` 且 `CMAKE_CXX_FLAGS_RELWITHDEBINFO="-O2 -g3 -fno-omit-frame-pointer"`（不带 `-DNDEBUG`）。于是 `ASSERT` 与 `EXEC_WHEN_DEBUG` 的检查全部有效，`.dll` 带 DWARF，`lldb` 可以展开。用它跑了 26,000 次迭代（见表中断言构建的两行），没有断言失败，也没有崩溃。崩溃若出现，取栈的方式是：

  ```powershell
  $env:CAMEL_HOME = "$PWD\tmp\home-assert"
  & G:\DevEnvs\LLVM\bin\lldb.exe --batch `
      -o "run --timeit std::nvm/100 test/cases/perf/gc/alloc_small.cml --arg reps=2000 --output-format json" `
      -o "thread backtrace all" `
      -o "quit" `
      tmp\home-assert\bin\camel.exe
  ```

  （`tmp/home-assert` 是把 `out/latest` 的目录结构复制一份，再把 `bin/camel.exe` 与 `bin/libcamel.dll` 换成 `tmp/build-assert` 的产物；`tmp/` 不入库。）
- **ASan 没能用上**：`-fsanitize=address` 在 Windows 上要求动态 CRT（`/MD`），而 conan 预编译的依赖是静态 CRT（`/MT`），`libcamel.dll` 链接时报
  `lld-link: error: /failifmismatch: mismatch detected for 'annotate_string'`。要用 ASan 得先让依赖全部用 `/MD` 重建，不在本项范围内。

### 2.4 已排除的可能与证据

1. **合并没有修它，也不是合并引入的。** `git log --oneline e8abfc30..HEAD -- src include tools` 只有四个提交：两个合并提交、`c467161f`（`std::stats` 的 `bytes` 字段与基线脚本）、`c431e1bc`（设计原则编号）。`git diff e8abfc30..HEAD -- src/execute/entry_args.cpp src/core/mm/mm.cpp tools/camel-cli/main.cpp` 是**纯注释**（设计原则条目改号）；`timeit.cpp`、`context.cpp`、`gen.cpp`、`graph.cpp` 没有改动。
2. **H8 当时的二进制不可得，但它的代码就是现在的代码。** H8 在它自己的工作树里跑基线，那个工作树（`h8-*`）已经删掉；主 checkout 里留下的是 `develop`（983b32a1）的构建（01:23:20），不是 H8 的二进制。不过 H8 的工作已经合进 `develop`，再经 `927cdcb0` 进入本分支，而 `src/` 里从 H8 之后到 HEAD 的改动只有设计原则改号（纯注释）与 `std::stats` 的 `bytes`（第 1 条），所以现在跑的 Release 构建与 H8 当时跑的代码在语义上没有差别。顺便也把主 checkout 那个 `develop` 构建跑了 164 个进程 / 3,700 次迭代，同样 0 次失败。
3. **负载/并行不是充分条件。** 大部分运行是在其它分支的构建与测试同时在跑的时候做的（期间机器上有 14 个来自其它 worktree 的 `camel` 进程），本项自己也开 5–16 个并行进程。H8 报告也注明当时机器上有别的工作。两者都不足以触发。
4. **不是某个回收器专有的。** 不设 `CAMEL_GC` 时默认是 generational（用 `CAMEL_GC_STATS=1` 看到 `minor=190 moved=1690 promoted=90`，是移动式），另外跑了 `CAMEL_GC=mark-sweep`、两者交替，以及 `CAMEL_GC_STRESS_ALLOC=1`（每次分配后收集）、`CAMEL_GC_STRESS_SAFEPOINT=1`（每个 safepoint 收集）、`CAMEL_GC_VERIFY=1`（每次收集前后校验整堆）、`CAMEL_GC_POISON=1`（safepoint 投毒，读已释放对象会读到毒值）。没有崩溃，也没有一次堆校验失败。
5. **与迭代次数无关的形态都试过**：每进程 5、20、50、100、2000 次迭代。H8 的频率（每次调用约 7%）如果只是"5 次迭代太少、没撞上"，那么每进程 2,000 次迭代的 64,000 次迭代里应当撞上几百次。
6. **输出路径单独试过**：`--output-format json`（`stdout`/`stderr` 的文件描述符在计时窗口内被 `_dup2` 到 NUL，`std::cout`/`std::cerr` 的 streambuf 换成 `ostringstream`）、`--output-format text`（不做这两层重定向）、`-vv`（info 级日志，走 `std::cerr`）、stdout/stderr 为管道（父进程读到 EOF）、`Start-Process` 重定向到文件——合计千余个进程，都没有失败（见上表）。非法访问若出在这一层，`text` 与 `json` 两种形态不太可能同时躲过；但这一点只是旁证，不是证明。
7. **不是进程退出路径**：`--timeit` 的 JSON 摘要是在返回前写出的；崩在退出路径上会留下完整的 stdout 而以非零码结束，这类记录在 130,100 次迭代里一次也没有。
8. **不是我的脚本把非崩溃当成了崩溃**：脚本只把非零退出码算失败；`Stop-Process` 杀掉的进程退出码是 `-1`（`0xFFFFFFFF`）、输出为空，与 `0xC0000005`（`3221225477`）明显不同；上表那 20 次已按此剔除。

在代码里查过、但既没有证据支持也没有证据否定的方向（都写在这里，供下一个接手的人少走一遍）：

- `Context` 销毁与 GC 根集合的交界：`Context::~Context` 在 `runtimeGraphMgr_` 存在时先 `autoSpace().setObjectRootSet(nullptr)`，再 `runtimeGraphMgr_.reset()`（`src/core/context/context.cpp:105-108`）；`GCGraphManager` 的析构函数在锁内 `releaseDetached()`、`clear()`，再把 `pinned_` 里的图逐个释放（`src/runtime/graph.cpp:1860-1871`）；`replaceRoot` 先释放旧图、后 `rebuildGcRoots()`（`graph.cpp:1772-1783`），这中间 `gcRoots_` 仍指向已释放的图，但这段窗口里没有任何自动空间分配，收集不会被触发（`graphSpace()` 是 `GrowableFreeListAllocator`，`free` 不收集）。
- 标记位的地址复用：`graphSpace()` 的块被 `FreeListAllocator::alloc` 复用时用 `installHeader` 重新构造头（`new (header) ObjectHeader(size)`，`raw_ = 0`，`marked_` 是 `raw_` 的一位，因此一并清零），`clearMarks` 也会遍历整个 `graphSpace`（commit `e59b2573` 修掉的那类"陈旧标记位漏扫静态区"问题，在当前代码里已经覆盖）。
- `FramePool` 的尾部快速复用（`include/camel/core/context/frame.h` 的 `acquireImpl`）：只比较 `runtimeGraph_`（以及 `MatchStaticArea` 时的 `staticArea_`），不比较 `dynamicAreaType_`。在一次执行内图不会被替换，所以现在是对的；但如果将来在运行期提交草稿（替换图）并把地址复用给新图，这里会拿到旧类型布局的帧。这一条是**写下来提醒**，不是本项的证据。
- `RuntimeGraphDraftSession` 提交时 `staticSlotTypes_` 与 `staticSlots_` 的长度关系、`buildStaticAreaInArena` 用类型长度建静态区：两边一致（`appendStaticSlot` 同时 push，`encodeDraftGraph` 会把 `staticSlots` 补齐到类型长度），没有找到能让"节点引用的静态槽下标 ≥ 类型元组长度"的路径。

### 2.5 顺带发现：同一命令的另一种偶发失败（`[]` 的索引类型读成 `i32`）

在 2,000 个进程的那一批里，**有一个进程以退出码 1 结束**（不是 AV），stdout 是一行运行时诊断，stderr 为空：

```json
[{"range":{"start":{"line":12,"character":43},"end":{"line":12,"character":44}},
  "severity":"Error","code":"0x04000032","source":"Camel",
  "message":"'[]' does not support a value of type 'i32'; it takes an integer index, or a field name for a struct.",
  "data":{"stage":"run","name":"RuntimeDiag::OperandTypeUnsupported","moduleName":"alloc_small",
          "modulePath":"test\\cases\\perf\\gc\\alloc_small.cml",
          "suggestion":"Convert the value to a supported type before the call."}}]
```

位置是 `alloc_small.cml` 第 13 行（0 基的 12 行）的 `xs[2]`，列 43 就是那个 `[`。也就是说 `:op/idx_arr` 取到的第二个实参在运行期报出来的类型是 `i32`，而 `__builtin__idx__` 要求 `int`（`i64`）：

- `src/builtin/operators/ops.cpp` 的 `__builtin__idx__` 读 `view.code(1)`，不是 `TypeCode::Int64` 就报 `OperandTypeUnsupported`；
- `view.code(1)` 对静态槽（负的 data index，字面量就是这样）走 `Frame::codeAt(-idx)` → `staticDataLayout()->codeAt(idx)`，对动态槽走 `dynamicAreaType_->codeAt(idx)`；
- 而 `std::jgir` 的输出里这个字面量是 `DATA 2`、`outputType int`，`xs[2]` 的 `:op/idx_arr` 两个输入分别是 `PORT xs`（`int[]`）与 `DATA 2`（`int`）。正常情况下这里读到的是 `i64`。

所以要么静态槽的类型表在这一格上是 `i32`（与节点的 `outputType` 不一致），要么帧拿到的是另一个布局的类型元组。我没有把它复现第二次（后续 1,000 个进程、以及全部其它批次里再没出现），也没有抓到出问题那次的现场，因此**不能**说它与 2.1 的 AV 同源；它只是同一个命令上另一种"重跑即过"的不确定现象，记在这里作为线索（待决问题 3）。

### 2.6 压力测试（两种回收器）

`test/plans/perf/gc.plan.toml` 增加两条（计划是 `tier = "benchmark"`，不进默认开发集）：

| 测试 | 回收器 | 断言 |
| --- | --- | --- |
| `gc_timeit_cycles.generational` | `CAMEL_GC=generational` + `CAMEL_GC_STATS=1` | 退出 0；stdout 是 `"kind": "timeit"` 且 `"iterations": 10`；stderr 的统计行里 `minor >= 10`（每次迭代都收集过）、`moved > 0`（移动式确实移动了对象） |
| `gc_timeit_cycles.mark_sweep` | `CAMEL_GC=mark-sweep` + `CAMEL_GC_STATS=1` | 退出 0；同样检查 `"iterations": 10`；统计行里 `major >= 10` |

命令就是会崩的那条（只是把 `/5` 改成 `/10`，让一个进程里多做几次重建-销毁）：

```powershell
node scripts/test.js test\plans\perf\gc.plan.toml
```

结果（整个计划一起跑）：`total: 6, pass: 6, fail: 0`，其中 `[PASS] gc_timeit_cycles.generational 2.24 s`、`[PASS] gc_timeit_cycles.mark_sweep 2.95 s`，另有四个原有的长时测试（27.7 s、101.2 s、5.6 s、5.5 s）也一并通过。断言里要求"每次迭代都收集过"是有意的：这保证压力测试真的走到了收集路径，而不是因为 reps 调小、分配量不够而空转通过（实测 10 个迭代：generational `minor=190`、`moved=1690`、`promoted=90`，`graph_allocs=140`；mark-sweep `major=17`、`elder_reserved_mb=64`）。

这个测试锁住的是"10 次重建-销毁不会崩，且两种回收器都真的在收集"。它抓不到 1/50,000 量级的偶发事件——那需要 `test/tools/timeitloop/timeitloop.py` 的长时间循环（`--runs 500 --count --jobs 8 --gc both` 约 10 分钟），两者分工写在了计划的 `desc` 里。

### 2.7 待决问题

1. **崩溃的原因仍未查明。** 要定案需要的证据是其中一项：一次带栈的崩溃（2.3 的断言构建 + LLDB），或 H8 当时的环境记录。H8 报告说 `baseline.py` 对非零退出重试并在标准错误记一行——如果那次的 `[baseline] ... exited with 3221225477` 行还能找到（当时的控制台输出或日志），它至少能回答"当时是否导出了别的 `CAMEL_*` 变量"。请协调者确认是否还有这份记录；没有的话，这一项只能以"未复现 + 已排除清单"结案。
2. **`npm run debug` 在这份代码上链不出来**（导出符号 72,842 > 65,535）。H9 是否要修（关掉 `WINDOWS_EXPORT_ALL_SYMBOLS` 改用显式导出，或给 Debug 单独减导出），是构建系统的判断，不在本项范围。修好之后这一项才有"官方调试构建"可用。
3. **`i32` 索引（2.5）是否与 AV 同源**：需要再拿到一次出现时的进程现场。最小的下一步是在 `__builtin__idx__` 报 `OperandTypeUnsupported` 之前，把该帧的 `runtimeGraph()` 名字、`staticArea_->size()`、`staticDataLayout()->size()` 与那一格的类型打出来（只在诊断路径上，正常路径不加开销），然后照 2.1 的循环跑。
4. **`--timeit` 失败时不知道是第几次迭代**：现在的 JSON 摘要只在成功时写出，失败时没有任何迭代号。要不要把"失败的迭代号"加进 JSON（哪怕只在失败时输出），是输出格式上的判断，所以停在这里。
