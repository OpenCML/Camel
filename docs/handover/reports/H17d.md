# H17d：map 元素循环按存储类特化；原地写的判定改看值；收集 pass 的拒绝改为回退

分支 `handover/H17d-fvm-residual`（从 `develop` 开出，树上含 H28 的元素视图与数据块改名）。所有改动留在工作树，未提交、未建分支、未推送。

对应交接要求的三条：优先级 1（fvm/jit 在 `map_int_only` / `map_tuple` / `map_str` 上约 5% 的残余，`map_arr` 是平的）、优先级 2（把原地写扩展到"名字指向的元组"）、优先级 3（收集 pass 不得把合法程序当内部错误拒绝）。第 6 节是留给作者裁决的问题；没有把任何裁决写进设计原则、`changes.log` 或其他文档。

## 0. 结论

1. **残余的成因找到了，就在 `map` 的元素循环里**：每个元素都在问同一组两个问题（存储类、元素宽度），而答案整次调用不变。把这两个决定提到循环外、按类编译出循环体之后，fvm/jit 上 8 字节整型元素的 `map` 快 **10%–17%**，走 H28 元素视图的 `map` 快 **7%**（视图让元素不再被物化，但它自己的每元素判断也一并提了出来）。`map_str` / `map_arr` 没有可归因的变化：它们的每次元素成本由慢路径写（写屏障、出线调用）支配，分派只占其中 1%–3%；`map_tuple` 只有 2%–4%（聚合复制支配）。按构造的拆分见 1.3，噪声底见 1.4。
2. **"名字指向的元组"今天就已经被原地改写**：GIR 里 `let` 不产生节点，`let r = (xs->append<7>, n + 1)` 之后返回 `r`，返回的是同一个 FILL——H17c 报告第 165 行"返回值是一个名字，不是 FILL，就不改写"的说法是错的。判定现在改写为"看图上返回的那个值"（穿过 block 的 GATE 锚点，不穿 CALL），`test/cases/loops/state_in_place.cml` 用三个新形状把这个事实锁住：名字、名字的别名都只分配 1 个块，调用返回的元组仍是 199。
3. **收集 pass 不再拒绝**：需要磁带又原地写数组的循环，回退到复制 append（`runtime::fallBackToCopyingAppend`），磁带因此拿到每回合一个数组；`grad` 穿过这类循环的梯度与复制形式一致。原先的 `throw std::runtime_error` 删除。

## 1. 优先级 1：元素循环按存储类特化

### 1.1 计数剖析（一次构建）

Release 构建没有 PDB，`samply` 在 Windows 上抓不到符号，所以按交接允许的计数路线：在 `fastvm.cpp`（与 `map` 元素循环同一个 TU，避免 LTO 造成的多份计数器）临时数每个元素落到哪条路径，`n=8000`，跑完 `map` 调用后从同一 TU 打印，然后**全部撤销**（`git checkout --` 复原，从干净树开始真正的改动）。每个元素、每次 `map` 调用：

| 用例 | 读（每个元素） | 写（每个元素） | 类对 |
|---|---|---|---|
| `map_int_only` | `compact8`，2 个判据 | `compact8`，2 个判据 | Direct / Direct |
| `map_tuple` | `compact8`，2 个判据 | 聚合 memcpy，3 个判据 | Direct / Aggregate |
| `map_str` | `compact8`，2 个判据 | `setSlotSlow`，2 个判据 + 一次出线调用 | Direct / Slow |
| `map_arr` | 同 `map_str` | 同 `map_str` | Direct / Slow |

8000 个元素、每元素 4–5 个判据，全部在问同两个问题：`isSlots()` / `isCompact() && isAggregateElement()` / `elementSize_ == sizeof(slot_t)`。整次调用的答案不变，所以这是可以提到循环外的决定，而循环里的分支是真分支（结果依赖数组）。

同一个计数也解释了 `map_arr` 为什么平：它的类对与 `map_str` **完全相同**，差别只在每个元素的回调里多一个数组字面量（3 次分配 + 复制），元素访问的份额被稀释——不是另一种分派。

`nvm` 的元素循环在 `src/builtin/operators/higher_order.cpp`，有同样的分派，**本次不动**：nvm 的每次元素成本由 `invokeFunction` 支配，实测平（1.2 的 nvm 列）。

### 1.2 改动

**`include/camel/core/rtdata/array.h`**（`Array` 在全局命名空间，与文件里其余部分一致）：

- `Array::ElementRead { Direct, View, Slow }` 与 `Array::ElementWrite { Direct, Aggregate, Slow }`，各自由一个 `elementRead()` / `elementWrite()` 决定一次；写比读多一个区分（槽数组可能持有引用，必须过写屏障）。
- `template <ElementRead R> slot_t readElement(i, layout)`：`Direct` 是一次 `slot_t` 装载；`View` 是 `pureViewOf` 的视图（要求 `ensureBlock()`，不物化元素）；`Slow` 是 `getSlotSlow`。
- `template <ElementWrite W> void writeElement(i, value, arrayType)`：`Direct` 一次存储；`Aggregate` 是 `setSlot` 原有的"槽形状聚合 → memcpy、否则慢路径"；`Slow` 是 `setSlotSlow`。
- `dispatchElementAccess(read, write, body)`（3×3）与 `dispatchElementRead(read, body)`（3 个），用 `std::integral_constant` 把类变成编译期常量，**在循环外**选一次循环体。

**`src/passes/sched/fastvm/fastvm.cpp`**：`evalMarkedOperator_{map,filter,reduce,foreach}_arr` 各自把元素循环包进上面两个 dispatch。三条守住的性质：

- **只提决定，不提指针**：元素回调是安全点，数组对象（内联紧凑数组连它的字节）会移动，所以每回合仍从 frame 重新取数组、再把数组传给 `readElement` / `writeElement`。
- `readClass` 在 `ensureBlock()` **之前**算好（`ensureBlock` 可能移动数组），此后不再碰 `source` 指针。
- 结果数组的写类在 `Array::create` 之后从新数组取（之后没有分配，指针有效）。
- 视图读保持零分配：`map` 的结果数组之外不再分配（`loops.hof_compact_element_view` 仍是 10,000 个 `(int, int)` 元素只分配 map 与 filter 的两个数组）。

## 2. 优先级 2：名字指向的元组

### 2.1 事实：今天已经改写，H17c 的说法是错的

H17c 报告第 165 行说"如果 body 写成 `let r = (xs->append<7>, n + 1) return r`，返回值是一个名字，不是 FILL，就不改写"。核对 GIR 与分配计数：**`let` 绑定不产生 GIR 节点**，名字就是它指向的那个值，所以这样的 body 与直接写元组的 body 得到同一个 FILL，早就被改写了。实测（`std::mem::blocks()` 前后读一次，200 回合）以下形状都是 **1** 次分配：直接写、`let r = …; r`、`let step = …; let r = step; r`（名字的别名）、带类型标注的 `let r: (int[], int) = …`、`sync { … }` 里返回、嵌套 block 里返回、中间夹一条效应语句。

唯一不改写的是**调用返回的元组**（`return stepOf(xs, rounds)`）：那条 FILL 在另一个图里，循环状态的原地写只对"返回它的图同时也构造它"成立；分支的两个 arm 各自成图、捕获 `r`，所以 `if c then r else r` 也按调用处理。这两条与交接给的规则一致，保持保守。

### 2.2 改动：判定改为看图上返回的那个值

`src/compile/gir/builder_control.cpp` 新增 `loopStateValueOf(node)`：从 `draft.returnNode()` 出发，穿过**锚点**——只穿单输入的 GATE（`sync { …; r }` 这类 block 把值排在效应之后留下的锚点，GATE 原样转发它的值）——直到第一个不是锚点的节点。遇到 CALL 就停下（上面 2.1 的保守规则）。`markLoopStateInPlace` 的判定因此写成"看返回的那个值"，而不是"看 returnNode 本身"。

这个改动在今天的图上是**等价**的（`let` 不产生节点，GATE 也早已被 `setBodyResult` 解掉），它的价值是把判定说成它真正的意思，并给"名字"一个不再依赖 GIR 细节的理由；行为由 2.3 的用例锁住，防止将来 GIR 给 `let` 加节点时悄悄退化。

### 2.3 证据（`test/cases/loops/state_in_place.cml` 追加三行）

```
200 0 7 199 1      // growNamed：let r = (xs->append<7>, rounds + 1) 之后返回 r
200 0 7 199 1      // growNamedAlias：let step = …; let r = step
200 0 7 199 199    // growThroughCall：返回 stepOf(xs, rounds)，调用返回的元组
```

三行都是 `长度 首元素 末元素 回合数 分配块数`。前两行 1 个块（原地写，与直接写元组的 `grow` 相同），第三行 199（复制 append，跨函数保持保守）。四个后端（nvm/fvm/jit/prl）输出相同。

## 3. 优先级 3：收集 pass 不再把合法程序当内部错误

### 3.1 组成

- `GraphDraft::retargetOperNode(id, uri)`（`include/camel/runtime/draft.h` + `src/runtime/draft_construct.cpp`）：把 OPER 节点的算子换成 `uri` 那个（`op = nullptr`，`oper = intern(uri)`），镜像 `DraftGraphBuilder::retargetOperNode` 的做法。
- `runtime::fallBackToCopyingAppend(GraphDraft &body)`（`include/camel/runtime/loop.h` + `src/runtime/loop.cpp`）：扫一遍草稿，把每个 `:struct/append_arr_owned` 重定向为复制形式的 `:struct/append_arr`，返回改了几个。注释里写明理由：磁带要"每回合一个值"，原地写只有同一个数组，所以需要磁带的一方回退到复制——这是回退，永远不是拒绝。
- 两个需要磁带的地方调用它：`test::loop_collect`（收完 state/tape 之后、改 body 之前；原来的 `throw std::runtime_error` 删除）与 autodiff 的 `Engine::buildLoopBody`（`GraphDraft::decode(body)` 之后立刻调用，所以在构建 `.tape.fwd` 之前就换掉）。

保持不变的：拥有者图里的 `:struct/copy_arr`（私有首值拷贝）留着——复制 append 不写参数，这次拷贝在这个形状里是多余的，但无害；`nvm`/`prl` 的执行器对两种 append 都支持。

### 3.2 证据

- **磁带**（新用例 `test/cases/loops/collection_in_place.cml`，`test::loop_collect`，六个后端）：

  ```
  ([0, 7, 7, 7, 7], [[0, 7], [0, 7, 7], [0, 7, 7, 7], [0, 7, 7, 7, 7]], [[0, 7], [0, 7, 7], [0, 7, 7, 7], [0, 7, 7, 7, 7]])
  ```

  两个槽各 4 个条目，长度逐回合 2、3、4、5——**每回合一个数组**。如果没有回退，四个条目全是同一个最终数组（`[0, 7, 7, 7, 7]` 重复四遍），这正是 H17c 拒绝的理由。`for` 形状同样。程序是合法的：改动前它被 `test::loop_collect` 以内部错误拒绝。
- **梯度**（新用例 `test/cases/modules/autodiff/loop_grad_in_place.cml`）：`growLiteral` 从字面量 `[0.0]` 开始（原地写的候选），`growSeed` 从形参开始（一直是复制形式），同一个计算取 `grad`：`a=2.0 b=2.0`，`with_grad` 的 `(4.0, 2.0)` 也一致。`std::gir` 的结构证据：原 body `growLiteral.loop1.body` 仍是 `:struct/append_arr_owned`，微分出来的 `growLiteral.loop1.body.tape.fwd` 是 `:struct/append_arr`——回退只发生在需要磁带的那一份图上，主体代码不动。
