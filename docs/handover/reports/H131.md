# H131 — 标准库声明化的下一批：`fs`

分支 `handover/H131-fs-declarations`，起点 `origin/develop` `16a784009`。任务书是 H19 计划的
第 10 步（其余固定签名模块声明化）；前面几批是 `bytes`（H76/H94）、`str`（H104）、`math`
（H113）、`json`（H115）、`re`（H126），本批按第 10 步的顺序取 `fs`。一个模块一个提交；
`tree`、`ckpt`、`rules`、`rewrite` 未动。

## 1. 选中的模块与边界

`modules/fs` 注册 15 个算子，全部是固定签名（`StaticFuncTypeResolver`），也是本批迁移的全部：

| 名字 | 签名 | 效果（`@effect`，仅文档） |
|---|---|---|
| `read_text` | `(path: string) => string` | reads a file |
| `try_read_text` | `(path: string) => string!` | reads a file |
| `read_chunk` | `(path: string, offset: int, size: int) => Bytes` | reads a file |
| `read_bytes` | `(path: string) => Bytes` | reads a file |
| `write_bytes` | `(path: string, content: Bytes) => void` | writes a file |
| `replace` | `(path: string, content: Bytes) => void` | writes and replaces a file |
| `write_text` | `(path: string, content: string) => void` | writes a file |
| `exists` | `(path: string) => bool` | reads the file system |
| `is_file` | `(path: string) => bool` | reads the file system |
| `is_dir` | `(path: string) => bool` | reads the file system |
| `file_size` | `(path: string) => int` | reads the file system |
| `mkdir` | `(path: string) => bool` | changes the file system |
| `mkdirs` | `(path: string) => bool` | changes the file system |
| `remove` | `(path: string) => void!` | removes a file |
| `remove_dir` | `(path: string) => void!` | removes a directory |

逐条对照 H94 结尾留下的限制：

1. **计算签名**：`fs` 没有 `DynamicFuncTypeResolver`，15 条都固定，不受限。
2. **值**：没有 `exportValue`，没有 `export let` 可写，不受限。
3. **资源与效果**：15 个算子**每一个都有**。这是本批与前面几批最大的不同，处理见第 4 节：
   声明只写签名，纯度与资源事实原样留在 C++ 的 `OperatorTable::declare`/`declareResources`。
4. **原地形式、泛型声明、核心 `:op/...` 前缀、`uses`**：都没有，不受限。

所以 15 条全部迁移，没有"停在 C++ 并逐条报告"的条目；本批也不需要扩展声明语法。H19 第
7a 步（`fs` 的错误约定：`read_text` 改 `T!`、加 `list_dir`/`remove_all`）是另一步，本批按
**当前**实现声明；那一步改签名时改的是同一份 `stdlib/fs.cml`，声明仍是唯一来源。

## 2. 声明模块 `stdlib/fs.cml`

`stdlib/signatures/fs.cml` 移到 `stdlib/fs.cml`，成为与 `fs.cmo` 同名的声明模块，也是这 15
条签名的唯一来源。结构：

- 文件头的"Signatures of ... / For reference only"换成与 `str`/`math`/`io` 相同的说明：
  这是 C++ 模块的声明，C++ 只留内核、执行器、算子特征与**资源**；
- 第一条注释写明本批的边界：**声明只写签名，不写效果**；每个算子都有副作用，调用必须在
  `sync` 块可达才会执行，效果与资源事实在 `modules/fs`；
- `module fs` + 15 条无体 `export func`。描述、`@effect`、`@fails`、`@example` 从原签名文件
  逐字搬来；没有 `#op`（默认 URI 就是 `fs:<名字>`，与 `ExecutorManager`、`OperatorTable`
  一致），没有 `with`，没有泛型。

`@effect` 仍是文档注释，不是类型的一部分：`FunctionType` 里没有效果/资源（H94 第 3 条：
`uses` 不进类型），参考页按 `@effect` 渲染"With effects"一行。声明没有把任何效果写进类型
位置，资源仍是 C++ 的事实。

## 3. C++ 侧删掉了什么

`modules/fs/module.cpp`：

- 删掉 15 条 `StaticFuncTypeResolver`（11 个 `exportEntity` 语句 + 2 个覆盖 `write_bytes`/
  `replace` 与 `remove`/`remove_dir` 的循环）与整个构造函数体；
- 删掉只服务签名的 include：`camel/core/operator.h`、`camel/core/type/bytes.h`、
  `camel/core/type/composite/tuple.h`、`camel/core/type/resolver.h`，以及
  `using namespace camel::core::type;`；
- 构造函数变为 `FsModule::FsModule(context_ptr_t ctx) : BuiltinModule("fs", ctx) {}`，
  与 `str`/`re` 的写法一致；补一段文件头，写明签名在 `stdlib/fs.cml`。

**留下**的部分就是"一个事实只写一处"里 C++ 该留的：

- `load()` 里的 `registerExecutorFactory("fs", …)`；
- `operators.cpp` 的 15 个内核、`getFsOpsMap()`，`binary.cpp` 的二进制内核与原子替换，
  `FsExecutor`；
- `OperatorTable::instance().declare("fs", …)` 的 15 条纯度（全部 `false`）；
- `OperatorTable::instance().declareResources("fs", …)` 的 15 条资源（8 条 `read`、7 条
  `rmw`，全部 `ambient`、`external`）。

`git grep '"fs:'` 在 `src/`、`modules/`、`include/`、`tools/` 只剩
`src/execute/standalone_bridge.cpp` 里一句"`fs:read_text` 是 fs 的算子，加载它一次"的注释，
不是签名文本。C++ 不再持有这个模块的任何签名。

## 4. 效果与资源：声明不写，C++ 不动

### 4.1 `std::jgir` 前后

三份样本，同一台 Linux 主机、同一路径，迁移前后各翻译一次（`std::jgir` 不执行）：

| 样本 | 规范化后的 SHA-256 |
|---|---|
| `test/cases/modules/std/fs/basic.cml` | `419fc92a33a40422c17679a48469ea05c1f892e6da684db5ddad5976f0fde31a` |
| `test/cases/modules/fs_binary_roundtrip.cml` | `cd5f0e9d1d724a075e1d6f54425a040d5e1eb2e942291909bf47f448dac90f23` |
| `test/cases/modules/std/fs/remove.cml`（`--arg mode=0 --arg path=`） | `e4d82a530ccdbc591abb125f498d8b3c737ecf66c4f682d5fcfaacc3a6418214` |

规范化只做一件事：把 `"origin": "<数字>"` 换成常量。原始输出的差异**只有**这些 origin id；
节点、边、类型、算子 URI、`effect` 角色、分支/闭包结构逐字节相同。origin id 在迁移后整体
后移（例如 `526` → `750`）：`stdlib/fs.cml` 作为声明模块先于入口程序被解析，它的 15 条声明
在 origin 表里占了位置；这是声明模块本身的位置编号，不是图的变化。把 origin 归一后三份
摘要与迁移前逐位相同。

`smoke` 的 GIR/CST/AST 快照全绿（10/10），说明节点种类与既有快照没有被这次迁移改变。

### 4.2 资源事实逐条不变

`camel inspect --ops` 的 15 条 fs 记录，迁移前后：

| 事实 | 迁移前 | 迁移后 |
|---|---|---|
| 算子数 | 15 | 15 |
| `purity` | 全部 `effectful` | 全部 `effectful` |
| `resources` | 8 条 `read ambient fs; external`，7 条 `rmw ambient fs; external` | 完全相同 |
| `semantics.key` | `fs:<名字>@1.0` | 完全相同 |
| `numeric`/`sensitive_to` | `opaque` / 六个敏感标签 | 完全相同 |
| `with`/`norm` 个数 | 0 / 1–3 | 完全相同 |
| 签名文本 | `(string) => bool`、`(string, int, int) => Bytes`、… | 多了参数名：`(path: string) => bool`、`(string, offset: int, size: int) => Bytes`、… |

唯一的区别是签名文本里的参数名。参数名是声明签名的组成部分（H94 第 6 条："签名文本保留
参数名"，`bytes`/`str`/`math`/`json` 迁移后 `inspect --ops` 也是这样），不是效果或资源的变化；
去掉参数名后，迁移前后的 `inspect --ops` 输出逐行相同。

`feat.modules.resources` 计划仍然打印
`RESOURCES node main 29 fs:exists: read ambient fs; external`，3/3 通过；`fs.basic`、`fs.remove`
与 `fs.remove_permissions` 全过（`modules.std` 25/25）。

### 4.3 为什么效果不写进声明

声明语法没有 `uses`，`FunctionType` 也不含效果/资源；`@effect` 是文档注释。把效果写进声明
的类型位置既没有语法可写，也会把资源事实变成第二份。约定页第 1 节的表把资源与语义留给
`declareResources`/`declareSemantics`，本批照它执行，没有为 `fs` 单开例外。
