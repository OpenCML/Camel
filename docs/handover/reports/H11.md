## 1. 按内容比较相等改为迭代，以及深数据的其他递归

本节对应 H11 第 1 项。起点是 `handover/H11-1-deep`；改动都留在工作树中，未提交。

### 1.1 先看到的现象

在 Windows（1 MB 主线程栈）上，用 `std::nvm` 复现：

| 数据 | 操作 | 改前 |
|---|---|---|
| 100 万个 `Chain::Cons(i, rest)` 节点 | `a == b` | 退出码 `-1073741571`（`0xC00000FD`，栈溢出） |
| 同上 | `string(a)` | 同上 |
| 10 万层 `Nest::More([...])`（递归枚举经过数组） | `==`、`string` | 20 万层时溢出；10 万层按 1 MB 栈尚未溢出，但每层帧更小只是碰巧 |
| 10 万层嵌套 JSON 文本 | `json.decode` | 退出码 `0xC00000FD`；`lldb` 在崩溃点看到约 65 000 层 `JsonValue::fromJson`，没有 nlohmann parser 帧 |
| 递归枚举 `enum Chain { Nil, Cons(int, Chain) }` | `std::cpp` 转译 | 转译期就递归耗尽（`cpp_types` 沿字段类型下降，且 C++ 不能按值容纳递归类型），输出 0 字节 |

`std::gc::major/minor` 在程序数据存在之前运行，不能用来在深数据上触发追踪；GC 追踪本身见 1.5。

### 1.2 按内容比较相等（`src/core/rtdata/equality.cpp`）

`valuesEqualByContent` 改为显式工作栈（`std::vector<EqualPair>`，元素是 `{a, b, type}`），一个循环处理：

- 标量、字符串（保留 `this == other` 的同一性捷径）；
- 数组、元组（含 `T?` / `T!`，错误值比较错误结构）、结构体；
- 枚举：先比 `tag`，再按 `tag` 的字段数压入各字段；
- `Map` / `Set`：用 `table::detail::Cursor` 按条目比较，键用 `compareKeys`，值保留 `Table::equals` 的同一性捷径；
- 其他类型仍走 `object->equals(rhs, type, true)`（模块对象的既有语义）。

语义没有改：数组没有同一性捷径（含 NaN 的数组不等于自身），字符串有，`Map` 的值有，枚举按 tag 与载荷递归比较。测试 `value.content_equality` 等 124 项原样通过。

### 1.3 打印（`src/core/rtdata/print.cpp`，`include/camel/core/rtdata/base.h`）

`printSlot` 的递归函数体移到新文件 `print.cpp` 的 `printValue`；`printSlot` 保留为薄封装（`printSlotSafe` 不动）。`printValue` 用一个 `PrintItem` 工作栈（类型 / 字面文字 / 槽），逐字节复刻原来的格式：

- 数组 `[a, b]`，元组 `(a, b)`、`T?`、`T!`（含 `error kind: message`），结构体 `{}` / `{ x: v }`；
- `Map` / `Set` 经 `table::detail::forEachLeaf` 按键序打印 `{k: v}`；
- 枚举 `Shape::Circle(1.0)` / `Shape::Rect { w: 2.0, h: 3.0 }` / 空变体。

非 GC 标量、空值、非复合对象仍直接写，不经过栈。`value.enums`、`value.content_equality`、`print_formats` 的 4 个后端输出未变。

### 1.4 类型的 `toString` / `equals` / `mangle`（`src/core/type/text.cpp`，`include/camel/core/type/text.h`）

新增 `typeToString` / `typeMangle` / `typeEquals`，分别用显式工作栈遍历 `Array`、`Tuple`（含 cell、`T?`/`T!`）、`Struct`、`Function`、`Map`/`Set`、枚举实例：

- `toString` 与 `mangle` 把“字面文字 + 子类型”拆成工作项，输出与原先逐字节相同；
- `typeEquals` 用待比较对栈，复刻原来的判断顺序与细节：元组比 `size/cell/tag`，结构体按**字段名**查找（不是顺序），函数比 `with`/普通参数的 `var` 标记与结果类型，枚举比声明与类型实参，集合比参数；
- 复合类型的 `toString`/`mangle`/`equals` 改为调用这三个函数；基本类型、类型变量、模块类型（`Tensor`、`Json` 等）仍走自己的虚函数，不改变其文字。

类型不是数据：类型树的深度是源码写出的嵌套（或泛型实例化的嵌套），不是值的深度；但仍然不应由原生栈决定能否表示。`isContentComparableImpl` 还是递归的——它只看类型，且只被类型兼容性检查调用；如果以后要连类型深度也限死，再按同一办法改（见 1.8）。

### 1.5 GC 的追踪：本来就是显式栈

没有改代码。`src/core/mm/gen.cpp` 的 `markObject`、`scanRelocatedObjects`、`forward` 都用显式工作列表；`updateRefs` 只把直接子引用交给 `relocate`，不沿数据递归。GC 不按对象图的深度使用原生栈。

### 1.6 JSON 的编码与解码（`modules/json/operators.cpp`）

先分别定位“10 万层为什么会崩”：

- nlohmann 的 parser 是递归下降（`detail/input/parser.hpp` 自己写着 recursive descent），serializer（`dump`）也是递归；
- 但 10 万层这次崩溃的栈上是 `JsonValue::fromJson`（约 65 000 层），没有 parser 帧，说明这次是**模块自己的转换递归**，parser 已经返回；
- 1 000 000 层时栈溢出得太深，`lldb` 只能拿到损坏的栈顶，无法区分是 parser 还是转换先溢出。

因此只把 `fromJson` 改成迭代并不能让任意深度安全：parser、`dump`、`nlohmann::json` 的析构都还是递归。按任务允许的“可控诊断”处理：

- 在 `decode` / `decode_as` 解析之前，用显式栈扫描文本的 `[`/`{` 深度（忽略字符串里的括号），超过 `CAMEL_JSON_MAX_DEPTH`（默认 10000）就返回一个普通的 `JsonParseError` 错误值，**不解析、不崩溃**；
- 消息给出深度上限、出错括号的 1-based 行与列，以及替代办法（解更浅的文档，或调大 `CAMEL_JSON_MAX_DEPTH`）；没有静默截断；
- 10 000 层仍然可以解码（`deep_json_depth.cml` 的第二行），10 万层得到：

  `error JsonParseError: the text nests deeper than 10000 levels (at line 1, column 10001); ...`

编码侧的深度由解码侧封顶：`Json` 只能由 `decode`/`decode_as` 得到，而它们的输入已被限制；`camelToJson` 对普通 Camel 值的递归深度由静态类型深度决定，不是任意数据深度。

### 1.7 `std::cpp` 的递归枚举（`src/passes/trans/cpp/cpp_types.cpp`，`include/camel/standalone/recursive.h`）

表示（报告要求的“设计上的选择”在 1.8）：

- 先给正在生成的枚举登记名字，再走它的字段：递归字段查到自己时得到名字而不是无限下降；
- 字段类型**传递包含**该枚举时（直接是自己的字段、`T?`/`T!`、`T[]`、`Map`/`Set`、元组/结构体/函数等），该字段声明为 `std::shared_ptr<X>`；其余字段仍按值。Camel 值不可变、载荷可共享，所以间接持有不改变值语义；
- `make<Tag>` 对装箱字段做 `rt::box<X>(...)`（即 `std::make_shared`，包成模板使 `X` 可以在枚举定义之后再完整），`get<Tag, Index>` 返回 `*field`（值），打印对装箱字段解引用；生成文件仍然只依赖 `camel/standalone/runtime.h`；
- 生成的 `operator==` 用 `std::vector<std::pair<const E *, const E *>>` 工作栈比较节点，直接递归字段按指针入栈，其他装箱字段用 `rt::boxedEqual`（比较指向的内容，不比较指针）；
- 生成的 `appendText` 用 `std::vector<std::function<void()>>` 动作栈：直接递归字段的动作只把子节点压回 `emit`，不嵌套调用；其余字段仍调运行时/生成的 `appendText`；
- 析构不能沿链递归：生成的 `~E()` 把装箱字段 move 到线程局的待释放栈，最外层析构调用 `rt::drainDestroyed()` 逐个释放。`rt::beginDestroy`/`endDestroy` 只数“当前是否在生成类型的析构里”，不改变普通对象的释放。

实测 1 000 000 节点、两棵独立构造的链：`std::cpp` 生成物用 `clang++ -O2` 编译后 `len(string(a))` 与 `a == b` 均与 `std::fvm` 相同，约 1 秒跑完，退出码 0；`test/tools/cppexec/run.py --expect` 64/64 与 `std::fvm` 一致（包含该程序）。

表示与转译覆盖“直接字段”和“经运行时容器（`E?`、`E[]`、`Map`/`Set`）的字段”：三者的小数据都实测可编译、打印与比较。**深数据的栈安全目前只保证直接字段链**；经过 `E[]` 的 100 万层在生成物中仍会溢出（10 万层成功），经过**生成的元组/结构体**间接包含自身的形状（如 `enum E { Node((E, int)) }`）还不能编译。这两类形状列在 1.10。

### 1.8 设计上的选择

- **装箱位置**：只对“传递包含该枚举自身”的字段装箱，不是所有枚举字段；其余字段按值，避免无谓的分配与间接。装箱用 `std::shared_ptr`，因为生成代码只允许依赖标准库与 `runtime.h`，且共享载荷符合 Camel 值不可变的语义。
- **相等与打印**：解释器侧统一用显式栈；`std::cpp` 侧也为递归枚举生成显式栈，且装箱字段比较指向的内容（`rt::boxedEqual`），否则默认的 `shared_ptr` 相等会比指针。
- **析构**：递归值即使打印/相等不递归，释放仍会递归；用“最外层析构排空待释放栈”的办法解决，没有引入垃圾回收或 arena。
- **JSON**：没有选择“只把 `fromJson` 改迭代”，因为 nlohmann 的 parser、serializer、析构仍是递归，改了也只把崩溃点挪走；选择在解析前做可配置的深度诊断。
- **类型文字**：没有为深类型引入深度上限；类型深度由源码/实例化决定，改为迭代后不再受原生栈限制。

### 1.10 待决问题

1. **JSON 默认深度 10000**：这个数取在“1 MB 主线程栈下深拷贝/打印仍有余量”的位置，不是语言语义给出的数。是否要改成 `json.decode` 的参数（遍参数机制已有，但模块算子没有参数），以及默认值定为多少，需要负责人确认。现在用 `CAMEL_JSON_MAX_DEPTH` 覆盖。
2. **JSON 的错误分类**：深度超限现在复用 `JsonParseError`（它是可恢复的错误值）。是否应新增一个诊断种类（例如 `JsonDepthLimit`），以便程序区分“文本不合法”和“文本太深”？
3. **`isContentComparableImpl`**：仍是递归，只沿类型结构，不沿数据。当前没有会导致实际崩溃的输入（类型深度来自源码），但如果要“所有随任何深度递归的地方都迭代”，它和 `containsEnumHole`、`findInvalidCollectionKey` 等类型遍历也应一并改；本次未改，因为不随数据深度增长。
4. **`std::cpp` 递归枚举经生成的元组/结构体间接包含自身**：如 1.7 末尾所述，当前可编译、可运行的是直接字段和运行时容器（`E?`、`E[]` 的表示已装箱，已验证小数据可编译并打印/比较）。`enum E { Node((E, int)) }` 仍会生成一个在 `E` 之前定义、按值持有 `E` 的元组，实测 `std::cpp` 转译成功但 `clang++` 报 `unknown type name 'E'`。需要“生成聚合类型也按同一规则装箱，或把定义推迟到枚举之后”，这是一块独立的代码生成工作，建议单独列项。
5. **字段类型含递归枚举但非直接自身（如 `E?`、`E[]`）的 `std::cpp` 深数据**：表示已装箱，`make`/`get` 已解引用，小数据可编译并打印/比较；但生成的 `appendText`/`operator==` 对这类字段最终仍调用 `appendText`/`boxedEqual` 的递归版本。实测 `Node::Link(Node[])` 的 10 万层在 `clang++ -O2` 下成功，100 万层退出 `-1073741571`（`0xC00000FD`）；直接字段链的 100 万层成功。其余形状要么为每个“深类型表达式”生成专用打印/相等，要么接受诊断，需负责人选择。
6. **生成的 `appendText` 用 `std::function` 动作栈**：实现简单，但每个节点一次 `std::function` 分配可能较慢；当前 1M 链约 1 秒，可接受。若要压性能，可改用带 `kind`/指针的 POD 帧。

## 2. `match` 的诊断与覆盖检查的测试补全

### 先说已有的

`test/plans/feat/compile/enum.plan.toml` 原本已有四类覆盖：`err_not_exhaustive`（漏一个变体，位置 `8:12`，诊断列出 `Rect`）、`warn_duplicate_case`、`warn_after_wildcard`、`err_unknown_variant`。正例是 `shapes`：一个列全变体、不写 `case _` 的 `match`，一个只列部分变体、以 `case _` 收尾的 `match`。

手动跑这些用例后确认三处缺口，都作为缺陷补齐（不是改期望迁就实现）：

1. **列全所有变体后再写 `case _` 没有任何诊断。** 这个通配符永远不会命中；任务书把它列为"多余的 `case _`"。
2. **单元变体写成绑定名 `case Empty` 的诊断不指名。** 原消息是"The pattern 'case' does not match …"：把 `case` 当作模式名，既不说 `Empty` 是什么，也不说该写 `Shape::Empty`。
3. **两个警告已有位置，但测试只匹配文本**；漏变体只有"漏一个"的例子，没有"漏多个并按声明顺序列全"的例子。

### 改动

- 新警告 `MatchWildcardRedundant`（`SemanticDiag`，`0x03100132`，Warn），在 `Builder::visitEnumMatch` 的臂循环之后发出：`case _` 存在且 `covered` 全部为真时，定位在通配符那个 `case` 的 origin。图不变（通配符仍是默认臂），只报告它不可达。
- `EnumPatternMismatch` 的裸名字分支：`caseNode->caseType() == CaseType::Bind` 时用绑定名作模式名；若它是该枚举声明的变体，消息说明"模式里的裸名字是绑定，变体要写限定名"，并按变体形状给出 `case Shape::Empty` / `case Shape::Circle(...)` / `case Shape::Rect { ... }`；若不是变体，也说明裸名字是绑定、枚举模式要写 `Shape::<variant>`。位置仍是该 `case` 的起点（`err_bare_unit_variant.cml:9:9`）。
- 测试：
  - 新增 `err_not_exhaustive_many.cml`：漏 `B`、`C`、`D`，断言"`'B', 'C', 'D'`"全列出，位置 `9:12`。

  - `shapes` 增加 `expect_output_not_contains`：正例上不得出现 `EnumVariantCaseRepeated`、`MatchWildcardRedundant`、`MatchCaseAfterWildcard`。

## 3. H8 报告中记下、未处理的小问题
