## 2. `match` 的诊断与覆盖检查的测试补全

### 先说已有的

`test/plans/feat/compile/enum.plan.toml` 原本已有四类覆盖：`err_not_exhaustive`（漏一个变体，位置 `8:12`，诊断列出 `Rect`）、`warn_duplicate_case`、`warn_after_wildcard`、`err_unknown_variant`。正例是 `shapes`：一个列全变体、不写 `case _` 的 `match`，一个只列部分变体、以 `case _` 收尾的 `match`。

手动跑这些用例后确认三处缺口，都作为缺陷补齐（不是改期望迁就实现）：

1. **列全所有变体后再写 `case _` 没有任何诊断。** 这个通配符永远不会命中；任务书把它列为"多余的 `case _`"。
2. **单元变体写成绑定名 `case Empty` 的诊断不指名。** 原消息是"The pattern 'case' does not match …"：把 `case` 当作模式名，既不说 `Empty` 是什么，也不说该写 `Shape::Empty`。
3. **两个警告已有位置，但测试只匹配文本**；漏变体只有"漏一个"的例子，没有"漏多个并按声明顺序列全"的例子。

### 改动

- 新警告 `MatchWildcardRedundant`（`SemanticDiag`，`0x03100132`，Warn），在 `Builder::visitEnumMatch` 的臂循环之后发出：`case _` 存在且 `covered` 全部为真时，定位在通配符那个 `case` 的 origin。图不变（通配符仍是默认臂），只报告它不可达。
- `EnumPatternMismatch` 的裸名字分支：`caseNode->caseType() == CaseType::Bind` 时用绑定名作模式名；若它是该枚举声明的变体，消息说明"模式里的裸名字是绑定，变体要写限定名"，并按变体形状给出 `case Shape::Empty` / `case Shape::Circle(...)` / `case Shape::Rect { ... }`；若不是变体，也说明裸名字是绑定、枚举模式要写 `Shape::<variant>`。位置仍是该 `case` 的起点（`err_bare_unit_variant.cml:9:9`）。
- 测试：
  - 新增 `err_not_exhaustive_many.cml`：漏 `B`、`C`、`D`，断言"`'B', 'C', 'D'`"全列出，位置 `9:12`。
  - 新增 `err_bare_unit_variant.cml`：`case Empty`，断言 `EnumPatternMismatch`、位置 `9:9`、消息含 `'Empty' is a variant…` 与 `case Shape::Empty`。
  - 新增 `warn_redundant_wildcard.cml`：列全 `Circle`、`Empty` 后再写 `case _`，断言 `MatchWildcardRedundant`、位置 `10:9`、程序仍运行并打印 `1.0`。
  - `warn_duplicate_case`、`warn_after_wildcard` 改为同时断言诊断名、code 与行/列（`9:9`、`10:9`），不再只查文本。
  - `shapes` 增加 `expect_output_not_contains`：正例上不得出现 `EnumVariantCaseRepeated`、`MatchWildcardRedundant`、`MatchCaseAfterWildcard`。
- 文档：`docs/language/03_data_model.md`、`docs/language/en/03_data_model.md` 与 `docs/language/06_expressions.md`、`docs/language/en/06_expressions.md` 写清"裸名字是绑定名、单元变体写限定名"与新警告；`docs/technical/42_enums.md` 的诊断清单同步。
- `node scripts/diagnostics-catalog.mjs --write` 重新生成 `docs/diagnostics.md`（164→165 个诊断）。

新增 `.github/workflows/perf-baseline.yml`（名称 **Performance baseline**）：

- 只由 `workflow_dispatch` 触发（可选 `rounds`，默认 `3`），不随 push/tag/PR 运行；独立 workflow，因此不会进入、也不会失败主流水线。
