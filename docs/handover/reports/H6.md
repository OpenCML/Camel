### 1.4 自动微分的前提：一个需要作者确认的冲突（待决问题 1）

设计原则 9.9 说“没有执行过 macro 的图信息不足以做微分，所以使用 `grad` 等需要流水线里有 `std::macro`；不满足时库应给出清楚的诊断”。但当前代码在**没有** `std::macro` 时也能求导：

```
camel test/cases/modules/autodiff/scalar_grad.cml std::nvm
# 输出 scalar_grad df=(12.5, 7.25) vg=(17.5, (12.5, 7.25)) dg=12.0，退出 0
```

`test/plans/feat/modules/autodiff.plan.toml` 的 `fused_grad_check` 甚至特意写“without std::macro, so grad sees the fused graphs”，并期望成功。因此自动微分模块目前没有“缺少 `std::macro`”这个前提可诊断；它是否应该诊断、还是 9.9 的表述应随运行期求导能力的演进而修订，需要语言作者决定。本次没有为了让 9.9 成立而加一个会拒绝现有测试的诊断。

## 2. 第 3 项：遍参数

### 2.1 增长预算改为 `growth_budget` 参数

- `include/camel/passes/opt/config.h`
  - 删除 `kGrowthBudgetEnvVar`，保留 `kDefaultGrowthBudgetNodes = 4096`（今天的默认值不变）。
  - 新增 `struct GrowthBudget { size_t nodes = kDefaultGrowthBudgetNodes; bool written = false; std::string passName; }`。`written` 区分“流水线写了参数”与“用默认值”，`passName` 记住是哪个遍拥有这个预算，供后续遍解释。
  - `OptimizeRewriteConfig::growthBudgetNodes` 改为 `GrowthBudget growthBudget{}`。
  - `InlineReport` 的 `budgetFromEnvironment` 改为 `budgetFromParameter`，并增加 `passName`。
- `src/passes/opt/inline/engine.cpp`
  - 删除 `optimizeGrowthBudget()`：不再 `getenv` / `strtoull`，不再有环境变量覆盖路径。
  - 预算直接取 `config.growthBudget.nodes`；报告写 `config.growthBudget.written` / `passName`。
  - 预算耗尽的 `-v` 警告改为“the growth_budget parameter of <pass>”，不再提环境变量。
- `src/execute/pass.cpp`
  - 新增 `growthBudgetParameter()`：`growth_budget: int = 4096`，文档说明“特化和内联可复制的节点数；0 表示不再复制”。
  - 新增 `growthBudgetOf(args, passName)`：取 `args.getInt`，负值按 0 处理（避免把负数转成巨大的 `size_t`），`written = args.given("growth_budget")`。
  - `std::opt` 声明 `{safe_fp, growth_budget}`；`std::opt::inline`（含 `::small`、`::arm`、`::hybrid`）、`std::opt::specialize`、`std::opt::devirtualize` 都声明并转交 `growth_budget`。`std::opt` 的所有轮次仍共用一个预算（`growthSpentNodes` 机制未动）。
- 构造链：`InlineRewritePass`、`SpecializeRewritePass`、`DevirtualizeRewritePass` 的构造函数接受 `const GrowthBudget & = {}` 并保存；`std::opt` 走 `OptimizeRewriteConfig`。默认构造的遍（测试、C++ 调用）仍是 4096。
- `modules/onnx/passes/export.cpp`：拒绝消息的“预算来源”改成 `the default` / `set by the growth_budget parameter` / `set by the growth_budget parameter of <pass>`；“怎么调高”改成 `raise the budget by writing a larger growth_budget on <pass> (for example <pass>(growth_budget=8192))`。`modules/onnx/exporter.cpp` 内部仍用最大预算，只更新注释，行为不变。
- 文档：`docs/cli.md` / `docs/cli.cn.md` 的参数表新增 `growth_budget: int = 4096`，环境变量清单删掉 `CAMEL_OPT_GROWTH_BUDGET`，资源上限表把“可调”改为遍参数，ONNX 拒绝说明改为参数/遍；`docs/technical/16_inline_rewrite_algorithm.md` 的预算说明改为 `OptimizeRewriteConfig::growthBudget`。

为什么给所有引擎遍而不只给 `std::opt::inline`：环境变量原本被 `std::opt`、`std::opt::inline`、`std::opt::specialize`、`std::opt::devirtualize` 共用；如果只给 inline，`std::opt(growth_budget=0)` 就无法表达，ONNX 的“先跑 `std::opt`”这条主路径也失去调预算的手段。任务书写的是“`CAMEL_OPT_GROWTH_BUDGET` 改为 `std::opt::inline` 的参数”，这里的做法保留了同一语义，但把参数放到所有使用重写引擎的遍上；默认值和各遍行为不变。

### 2.2 `--timeit` 仍是 CLI 选项

## 3. 待决问题（按第 4 节提交给语言作者）

1. **自动微分是否仍以 `std::macro` 为前提（设计原则 9.9 与实现冲突）。** 设计原则说没有 `std::macro` 时信息不足、库应诊断；但 `scalar_grad.cml` 只用 `std::nvm` 就能求导成功，`fused_grad_check` 也特意不跑 `std::macro`。要么 9.9 需要修订（运行期求导已能处理这些图），要么自动微分应加“缺少 `std::macro`”的诊断并调整这些测试。本次没有改。
2. **调试用的追踪变量是否改为遍参数。** 任务书第 3 项要求“按第 4 节提问”。目前仍在环境里的追踪/统计变量包括：`CAMEL_EFFECT_TRACE`（效应顺序追踪）、`CAMEL_TYPE_STATS`（类型表统计）、`CAMEL_STARTUP_PROFILE`（启动阶段计时，CLI 在遍之前读取）、`CAMEL_TIME_PHASES`（阶段计时）、`CAMEL_ONNX_TRACE` / `CAMEL_ONNX_DUMP` / `CAMEL_ONNX_PREP_STATS`（ONNX 导出器内部追踪）、`CAMEL_TENSOR_OPSTATS`、`CAMEL_GC_STATS` / `CAMEL_GC_PRINT_CONFIG` / `CAMEL_GC_LOG_MOVES` / `CAMEL_GC_VERIFY` 等 GC 调试变量，以及 `CAMEL_LOG_*`（编译期日志开关，Release 下 `DEBUG`/`TRACE` 站点被编译掉）。
   我的看法（供作者决定，不是本次的改动）：这些变量大多观察的是**进程**（启动、分配器、日志、调度器内部），不是在配置某个遍；有的在流水线开始前就被读取（`CAMEL_STARTUP_PROFILE`），改成遍参数反而要求先有一个遍才能打开追踪。建议保留为环境变量/CLI 诊断选项，并在文档里继续按“进程环境”归类；如果作者希望其中某些（如 `CAMEL_EFFECT_TRACE`、`CAMEL_TYPE_STATS`）成为某个遍的参数，需要先确定它们属于哪个遍、追踪输出写到哪里、以及遍没有运行时是否仍要能打开。
3. **负的 `growth_budget`。** 本次按 0 处理（不再把 `-1` 转成巨大的无符号数）。如果作者认为负值是用户错误、应当报 `InvalidPassParameter`，可以再改；这属于参数校验策略，不影响本次的机制。
