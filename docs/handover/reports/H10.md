## 1. 测试按项并行执行

### 1.1 做了什么

`test/tools/run-tests.mjs`：

- 执行方式由 `spawnSync` 改为异步 `spawn`：`runProcess()` 收集 stdout/stderr、退出码和
  信号，超时用 `taskkill /pid <pid> /T /F` 杀掉整个进程树（POSIX 上 `detached` 起进程组后
  杀组）。测试、`skip_unless` 前置条件和 `verify_script` 都改用它。
- `--jobs N`（默认 `os.availableParallelism()`，即核数）限制同时运行的测试数；`--jobs 1`
  就是原来的串行执行。`--jobs` 只由 runner 进程解释，测试自己无法改变邻居的数量。
- `class Slots`：FIFO 计数信号量。普通测试取 1 个槽位；串行测试（见 1.2）取全部 `jobs` 个
  槽位，所以它不会和任何测试重叠，也不会被饿死。
- 输出顺序与串行完全相同：每个测试完成时把自己的结果放进 `entries[i]`，`drain()` 只按
  计划/测试顺序打印已经完成的结果；计划头在它的第一个结果之前打印。`[SUMMARY]`、失败
  `[INFO]` 行、`summary.json` 的字段都不变（`summary.json` 另加 `tier`、`jobs`、`wall_ms`）。
- 依赖（`compare_to`、`backends_agree` 的参照后端）用 promise 等待：参照测试先完成才判断
  比较；参照失败/跳过时依赖测试按原语义跳过。
- 每个测试的临时目录在 H9-4 的路径上再加一层计划 id：
  `tmp/test/run/<run>/<plan id>/<test>`，两个计划里同名的测试因此不会撞目录。
- `--update-golden` 强制 `--jobs 1`：黄金文件的内容不能取决于哪个测试最后写完。
- 运行日志目录名加进程 id（同一秒内跑两次 runner，例如自检，日志与 `summary.json` 不再
  互相覆盖）。

### 1.4 并行正确性

- `test/tools/selftest/run.mjs` 扩展了三个夹具：
  - `parallel.plan.toml`：6 个 sleep 400 ms 的测试，`--jobs 4` 与 `--jobs 1` 的
    `[PASS]/[FAIL]` 行、顺序、`[SUMMARY]` 必须逐字相同，且探针日志显示至少两个区间重叠；
  - `serial.plan.toml`：两个 `parallel = false` 加一个普通测试，任何两个区间都不重叠；
  - `tier.plan.toml`：计划 fast、一个测试覆盖为 slow，`--tier fast|slow|all` 分别选中
    2/1/3 个测试。
  原有的后端矩阵与临时目录检查保留。
- 并行还查出一个串行时看不出来的错误：`shapes.nvm` 这个名字同时出现在 `compile/enum` 与
  `para/handoff` 两个计划里，而 `backends_agree` 的参照原来按裸测试名查找。串行时参照恰好刚
  跑完（同名结果被后完成的覆盖），所以一直是对的；并行时按名字静态解析会取到另一个计划的
  同名测试，`compile.enum` 的 `shapes.fvm/jit/prl` 于是一次 `--tier fast --jobs 8` 里全部
  报 “differs from shapes.nvm”（3 个假失败）。修复：参照先在本计划内找，找不到才按名字找
  （`lookupCompleted`），`--tier` 的依赖闭包与等待链也做同样处理（`byPlanName`）。修复后
  `compile/enum` + `para/handoff` 一起 `--jobs 8` 全通过。
- 真实计划的串行/并行对比（`feat/compile`，724 项）：

  | 运行 | 墙钟 | 结果 |
  | --- | --- | --- |
  | `--tier fast --jobs 1 test/plans/feat/compile` | 47.5 s | 724 项：723 通过、1 失败 |
  | `--tier fast --jobs 8 test/plans/feat/compile` | 18.6 s | 724 项：723 通过、1 失败 |

  两次的 724 条 `[PASS]/[FAIL]` 状态行逐条相同（名称与顺序）、`[SUMMARY]` 相同、失败
  详情文本相同（`[INFO] expected exit 0, got 1` + `stdout does not contain
  'docs/diagnostics.md is up to date'`），退出码都是 1。
- 失败信息完整：并行时每个失败仍打印自己的 `[FAIL]` 行、`[INFO]` 详情和被比较的
  `stdout_normalized`（`printFailedOutput`），不因为邻居的输出而混入或丢失；`--jobs 1`
  与 `--jobs 8` 的 `feat/compile` 失败文本逐字相同（上表）。
- 全量并行运行时查出的第二个问题：带参照的测试（`compare_to`、`backends_agree`）在参照
  完成后才 `acquire` 槽位，而这时循环已经把其余几千个测试都排进了 FIFO 队列，于是它们
  排到队尾、整轮运行的最后才执行；顺序打印因此在整个运行期间被第一个未完成的参照测试
  挡住，看起来像“卡住”。修复：这类测试用 `slots.acquire(tokens, priority = true)` 插到
  队首，参照一完成就接着跑。修复后 `smoke` 的 10 项在 0.2 s 内按序打印完，`feat/compile`
  的 724 项在 18.6 s 内按序打印完。这个修复是在 2.4 的 217.7 s 计时之后加入的，只改排队
  顺序，不改测试集合与结果；1.4 的 `feat/compile` 串并对比是在修复后跑的。

### 1.5 设计选择

- 用信号量而不是固定分片：长测试不会让一个分片拖尾；FIFO 保证先排队的先跑。
- 串行测试取“全部槽位”而不是单独一把锁：语义是“此刻只有我”，实现只需一个计数器，且
  与 `--jobs 1` 自然一致。
- 结果按序打印而不是按完成顺序：输出（以及基于输出做断言的脚本）与串行一致，这是并行
  可行性的前提。代价是第一个未完成的测试会挡住它后面的输出；带参照的测试因此用优先队列
  紧跟参照（1.4），否则它们会排到整轮的最后，让输出在整个运行期间停住。
- 超时杀进程树：测试会启动编译器/解释器（`agree_with_fvm` 起 C++ 编译器、python 测试起
  解释器），只杀直接子进程会留下孤儿进程继续占 CPU。基线里旧 runner 的 `spawnSync`
  超时没有杀掉一个 200 秒的 camel 进程（实测 274.8 秒后才被人工结束，见 3.4），新 runner
  的 `taskkill /T /F` 是为此选的。
- 没有在 runner 里给测试设线程数：测试内部是否多线程（torch、基准）不属于“测试级并行”
  的语义，见 8 节 Q1。

## 2. fast / slow 分层

### 2.1 规则

`tier` 取 `fast` 或 `slow`，可以写在计划上（该计划所有测试的默认层），也可以写在单个
`[[tests]]` 上（覆盖计划）。只有 `slow` 是特殊的：其他任何值（旧的 `smoke`/`feat`/
`perf` 标签）都算 fast，旧计划不改也能跑。规则写在 `docs/test-plans.md`：

- 新测试默认 fast；单个测试约 5 秒以上必须 slow，并在 `desc`/注释里写清时间为什么是固
  有的；整计划都慢时在计划上写 `tier = "slow"` 并说明。
- 慢层包含：与 PyTorch 的对比、GC 压力与投毒扫描、随机程序检查（progen、fuzz）、性能基
  准，以及其他单个耗时的测试。
- 分层过滤会保留依赖：一个测试被选中时，它的 `compare_to` 参照（以及后端参照）即使属于
  另一层也会一起运行，避免“参照被过滤掉所以失败”。

### 2.2 实施

- `test/plans/**` 的 150 个计划都写上了 `tier`：`perf/**`、`gpu/**`、`feat/mm` 的 GC 压
  力与投毒计划、`feat/opt/progen` 是 slow，其余计划 fast；单个超过 5 秒的测试在 2.3 的
  表里逐个标 slow。
- `npm run test` → `node ./scripts/test.js --tier fast`；`npm run test:all` →
  `node ./scripts/test.js --all --tier all`；显式目标默认仍是 fast，慢测试加 `--tier all`。
- runner 启动时打印 `[INFO] tier: ..., tests: ..., jobs: ...`；选中的测试数为 0 时提示
  `--tier all`（例如只给了一个 slow 计划）。
- 过滤后重新构建计划列表：计划和测试的顺序不变，`[SUMMARY]` 的总数只统计选中的测试。

### 2.5 是否达成与理由

分层本身达成：fast 层从“全部 5962 项、串行 3173 s（约 53 分钟）”缩到 4012 项、测试时间
合计 320.9 s；>5 秒的 82 个测试（合计 2206 s）全部在 slow 层，fast 层里几乎没有 5 秒以上的
单测试（最慢的 `runner.backend_matrix` 4.9 s，它是串行测试）。8 核 2 分钟的目标在空闲机器
上按 320.9/8 ≈ 40 s 有余量，但本机被其它 worktree 占去约 60% CPU，实测 181–239 s（最终
217.7 s），没有达到 120 s；数字与机器条件的关系见 2.4 与 Q3。

fast 层的主要剩余时间不是单个慢测试，而是项数（约 4000 项 × 启动/编译开销）：`modules.onnx`
118 项、`consistency.attempt` 143 项、`consistency.values` 136 项等。要继续压低，方向是减少
每个测试启动 `camel.exe` 的次数（合并小测试）或按改动选择计划（第 5 节的 `--changed`），
而不是再往 slow 里搬。

## 4. 最慢测试的收缩（ResNet 与 PyTorch 的对比）

### 4.1 实测

本机（28 核，测量时有其它负载）：

| 测试 | 深度 | 墙钟 |
| --- | --- | --- |
| `resnet_gradient_smooth_vs_torch64` | tanh，无折点 | 6.3 s |
| `resnetbn_gradient_smooth_vs_torch64` | tanh，20 个 batch_norm | 14.5 s |
| `resnet_gradient_relu_kinks_vs_torch64` | relu，折点归因 | 21.1 s |
| `resnetbn_gradient_relu_kinks_vs_torch64` | relu + BN，折点归因 | 42.6 s |
| `resnetbn_train_step_export` | 一步训练 + 导出对比 | 9.2 s |

任务书给的 248 / 530 秒在本机没有复现（同一份代码、同一输入），所以“最慢”在本机是 GC 计
划与投毒扫描，不是 ResNet。无论绝对值如何，四个测试都 >5 秒，已按第 2 节进 slow 层。

### 4.2 能否缩小网络/批量而不丢检查

做法：给 `benchmarks/tools/grad_referee.py` 加 `--batch N`、`--size S`，从基准输入里取前
N 个样本、S×S 的裁剪，权重与网络结构不变，把裁剪后的输入通过 artifacts 同时交给 Camel
和 PyTorch。实验矩阵（`--no-fd --no-sensitivity --require`，与计划一致）：

| 模型 / 测试 | 输入 | 判定 | 折点数 | 墙钟 |
| --- | --- | --- | --- | --- |
| resnet，折点（基线全量） | 16×3×32×32 | PASS-KINK | 2 个命名单元 | 21.1 s |
| resnet，折点 | 8×3×16×16（1/4） | PASS（直接比较） | 0 个反转 | 6.1 s |
| resnet，折点 | 16×3×32×32（1/2，只缩 batch） | PASS-KINK | 2 个命名单元 | 18.9 s |
| resnetbn，折点（基线全量） | 16×3×32×32 | PASS-KINK | 3 个命名单元 | 42.6 s |
| resnetbn，折点 | 8×3×16×16（1/4） | PASS（直接比较） | 0 个反转（有 1 个 relu 判定不同，但梯度仍直接落在 1e-4 内） | 8.7 s |

（1/4 输入下判定退化成直接比较：折点检查的代码没有运行，等于只留了“梯度对得上”这一半；
这正是任务书要求“同样的检查保留”时不能接受的。1/2 输入下折点检查仍在，但时间只从 21.1 s
降到 18.9 s——代价在网络的 62 个权重与 17 层卷积，不在 batch。）

### 4.3 结论

**不采纳缩小**：1/4 输入把折点检查变成直接比较（0 个反转单元），1/2 输入只省 10%，时间
主要花在与 batch 无关的网络上。四个测试保持原输入、留在 slow 层（第 2.3 节），理由写进
`benchmarks/tools/grad_referee.py` 的新选项说明与本节。`--batch` / `--size` 选项留在
referee 里（默认行为不变），供以后在更快机器上做同样的实验。`resnet*_smooth` 两个 tanh
测试没有折点检查，理论上可以缩，但按上面的测量收益同样很小，这次没有改。

见第 8 节 Q6（任务书与本机的耗时差异；是否需要按相对代价而不是绝对秒数决定）。

## 5. `--changed`

### 5.1 映射

`test/plan-selection.json`：有序规则表，每条是路径前缀 → `test/plans` 下的计划（文件或目
录）。第一个匹配的规则生效；一个改动文件可以命中一条规则，所有文件的并集按计划顺序运行。
规则覆盖：runner/自检、`src/passes/sched`、`src/passes/opt`、其它 `src/passes`、`src/compile`、
`src/parse`、`src/core`+`src/runtime`、`src/execute`、各 `modules/`、`stdlib/`、`tools/`、
`examples/`、`benchmarks/`、`docs/`、`editors/`、构建定义、`test/cases/<目录>`；最后一条
`"self": true` 让 `test/plans/` 下的改动选中被改的计划本身。

### 5.2 行为

- `node scripts/test.js --changed` 用 `git diff --name-only origin/fsh-dev` 加
  `git ls-files --others --exclude-standard` 取改动（含未提交、未跟踪）。
- 没有规则匹配、git 读不到基线分支、或没有任何改动时，退回整个 fast 层（并打印
  `[INFO] --changed: ...` 说明原因）。
- 显式给了目标时以目标为准，`--changed` 不生效；`--tier all` 可以叠加。
- 选中的计划仍然受分层过滤，默认只跑它们的 fast 测试。

### 5.3 验证

本工作树对 `origin/fsh-dev` 有 320 个改动文件（含未跟踪的计划与配置），`--changed` 的
选择：

```text
[INFO] --changed: 320 changed file(s) select 171 plan(s)
[INFO] discovered plans: 135
[INFO] tier: fast, tests: 4024, jobs: 8
```

171 个目标（计划文件与计划目录）经 runner 展开、去重后就是全部 135 个计划
（`test/plans/` 的自选规则把 150 个计划文件各选自己，加上 `test/cases/` 与 `docs/` 等目录
规则选中的计划目录），所以这一组“改遍了所有子系统”的改动退化成整个 fast 层——这是设计内
的退化：选择只影响“跑哪些计划”，不影响层与并行。
为了不在这台共享机器上再跑一遍全量 fast（第 2.4 节刚测过），读到选择结果后即停止运行，没
有把这次 `--changed` 当作计时样本。

映射规则本身由自检逐条断言（`test/tools/selftest/run.mjs`）：`src/passes/sched/fastvm/`
→ `smoke` + `feat/linear`，`docs/` → `feat/docs_links.plan.toml`，`test/plans/smoke/core.plan.toml`
→ 自身，以及无匹配路径返回 `null`（调用方退回 fast 层）；`node test/tools/selftest/run.mjs`
通过。

## 8. 待决问题

### Q1：测试内部的线程数与 `--jobs` 的关系
例子：8 核上 `--jobs 8` 跑慢层，四个 ResNet/PyTorch 测试同时启动，每个 torch 默认按机器
核数开线程，实际线程数远超 8，彼此拖慢。建议：runner 给测试统一设置
`OMP_NUM_THREADS`/`CAMEL_BENCH_THREADS`（或测试自己在 `envs` 里写），还是把这类测试标
`parallel = false`？前者会改变浮点求和顺序，需要基准维护者确认容差仍然有效。

### Q2：两个 runner 实例的隔离
例子：同一工作树同时跑 `npm run test` 和 `npm run test:all`，两个 runner 都会清
`tmp/test`，并可能写同一个 `tmp/examples/tiny_model.onnx`。建议：runner 用独立的临时根
（例如 `tmp/test/run-<pid>`）并把固定路径改为 `CAMEL_TEST_TMPDIR` 下的路径；这需要改
examples 与少数测试，是否作为后续项？

### Q3：5 秒阈值的机器差异
例子：任务书里 ResNet 折点测试 248/530 秒，本机 21/42 秒；同一测试在不同机器上可能跨过
5 秒线。建议：阈值按“本机 fast 层总预算”校准（例如 fast 层不超过 2 分钟），而不是固定
秒数；或让分类由一次测量的结果生成（本报告 2.3 的表就是这样得到的）。

### Q4：显式目标的默认层
例子：`node scripts/test.js feat/mm/gc_soak` 在默认 fast 下选中 0 个测试。现在会打印
“this selection has no fast tests: --tier all runs both layers”。建议：保持现状（显式、
可预期），还是让“目标是单个计划且它全是 slow”时自动跑 slow？

### Q5：投毒抽样的大小
例子：每个源计划只抽第一个成功测试，可能抽到不含集合/闭包的小程序；`fast_sample = 1`
只保证“每个计划的某个 safepoint 被投毒一次”。建议：保持 1，合入前全量；或按计划风险
（涉及集合/闭包/迭代器的计划抽 2–3 个）。

### Q6：ResNet 收缩的判据
例子：任务书的 248/530 秒与本机 21/42 秒差一个数量级；是否值得为 20–40 秒的测试改基准
输入（并更新 desc 里的数字）。建议：若 4.2 的实验保留折点，就采纳裁剪（slow 层总时长
也受益）；否则保留并说明。

### Q7：`--changed` 的映射维护
例子：`test/cases/modules/` 映射到 `feat/modules`、`feat/tools`、`feat/trans` 三个目录，
粒度偏粗；改一个 case 可能跑几百个测试。建议：先按目录跑，等实际使用中发现问题再细化；
基线分支名 `origin/fsh-dev` 是否要环境变量覆盖？

### Q8：全量并行的完成测量
例子：全量 `--tier all --jobs 8/28` 在共享机器上多次启动都因其它 worktree 的负载与时间预算
被停止（1.3），所以报告里的全量数字只有“之前”的串行 3173 s 与 fast 层的并行 217.7 s。
建议：在空闲机器上补一次 `npm run test:all -- --jobs 8` 并把墙钟/失败名单填进 1.3 与 9 节；
在此之前不要把“全量并行 ≈ 2844/8 ≈ 355 s”当结论。
