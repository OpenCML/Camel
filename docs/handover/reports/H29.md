# H29：元素视图不能流进 reduce 的累加器

状态：修复完成，工作树未提交。复现、根因、修复、用例、验证计数与变更的期望见下；性能见第 7 节。

## 1. 现象与复现

最小复现（四个后端各跑一次）：

```camel
[(1, 30), (2, 6), (3, 20)]->reduce<(a: (int, int), b: (int, int)): (int, int) => if b.1 > a.1 then b else a, (0, 5)>
```

| 构建 | nvm | fvm | jit | prl(taskflow) |
|---|---|---|---|---|
| 修复前 | `(1, 30)` | `(3, 20)` | `(3, 20)` | `(1, 30)` |
| 修复后 | `(1, 30)` | `(1, 30)` | `(1, 30)` | `(1, 30)` |

nvm/taskflow 的值是对的，fvm/jit 返回的是**最后一个被读到的元素** `(3, 20)`，而不是 `b.1` 最大的 `(1, 30)`。

用例 `test/cases/loops/reduce_view.cml`（14 行，fvm，修复前后）：

```
修复前                                修复后
(3, 20)                               (1, 30)     // reduce 选择元素，槽形 (int,int)
(0, 5)                                (0, 5)      // 每轮返回 a：不变
(6, 56)                               (6, 56)     // 每轮新建元组：不变
(3, 20)                               (3, 20)     // 每轮返回 b：碰巧最后一个是 b
(3, 20)                               (1, 30)     // map 恒等后的 reduce
{ x: 3, y: 20 }                       { x: 1, y: 30 }   // 槽形 struct P
{ ok: true, y: 30 }                   { ok: true, y: 30 } // 非槽形 Q，3 个元素
((0, 0), 5)                           ((0, 0), 5) // 嵌套聚合，3 个元素
(1, 30)                               (1, 30)     // loop 左折叠，元组状态
(3, 20)                               (1, 30)     // filter 后 reduce
(3, 40)                               (1, 60)     // map 后 reduce
(1, 199)                              (200, 0)    // 200 个槽形元素：复用单元
(1, 199)                              (200, 0)    // 200 个恒等 map 后的 reduce
{ ok: true, y: 72 }                   { ok: true, y: 200 } // 200 个非槽形元素：环回绕
```

`{ ok: true, y: 72 }` 是环回绕的直接指纹：累加器留着 ring 第 0 格的视图，再读 128 个元素后第 128 次读复用第 0 格，`y = 200 - 128 = 72`。

## 2. 根因

### 2.1 哪个值是视图

`Array::getElementView`（`include/camel/core/rtdata/array.h`，H28）对紧凑纯数据聚合数组返回**视图**：一个 `Struct`/`Tuple` 头加上 `kViewFlag`，字段从块的元素字节直接读。视图不是值，它绑定产生它的那次读：

- 槽形元素（每个字段都是 8 字节叶子、无填充，例如 `(int, int)`、`P = { x: int, y: int }`）——所有视图共用一个线程局部单元（`src/core/rtdata/view.cpp` 的 `reusedStructView`/`reusedTupleView`），每次读只改这个单元的 `ViewData.bytes`。**同一个 `slot_t` 指针**，内容随下一次读变化。
- 非槽形元素（例如 `Q = { ok: bool, y: int }`，bool 是一字节）——线程局部 view ring（128 格）。前 128 次读各占一格，第 129 次读回绕覆盖第 0 格。

### 2.2 逃逸路径（fvm/jit）

`FastVMSchedPass::evalMarkedOperator_reduce_arr`（`src/passes/sched/fastvm/fastvm.cpp`）：

1. `arr->readElement<kRead>(i, viewLayout)` 读第 i 个元素。紧凑聚合数组的读类是 `ElementRead::View`，所以 `args[1]` 就是元素视图；槽形类型下它是那个复用单元。
2. 回调 `(a, b) => if b.1 > a.1 then b else a` 在 b 胜出时**直接返回 b**，即返回视图本身。
3. `callElement(site, frame)` 把回调结果原样返回。
4. `currFrame.set(self, next)` 把视图存进 reduce 的累加器槽。
5. 下一轮 `currFrame.get<slot_t>(self)` 取出这个指针当 `a`；同一次 `readElement` 把元素 i+1 的字节写进同一个复用单元，`a` 于是变成元素 i+1。三轮之后累加器里的视图指向最后一个元素，结果 `(3, 20)`。

jit 走同一段 `callElement`（`invokeCallOrJit`），行为逐字相同。

nvm/taskflow 不走这个 frame 槽：累加器是一个 1 元素 `Array` 单元（`src/builtin/operators/higher_order.cpp` 的 `__reduce_arr__`），`Array::setSlot` 对聚合元素**存的时候就物化了视图**——`setSlot` 的字节拷贝快路径用 `isViewSlot` 把视图排除出去，交给 `setSlotSlow`，后者物化。所以 nvm 一直是对的。

### 2.3 为什么 H28 评审第 1 条的检查没抓到

- `CAMEL_ASSERT_NOT_VIEW` 在 `include/camel/core/rtdata/view.h:105` 是 `#ifndef NDEBUG`，而本树规定的构建固定 `Release`，每一条断言都被编译掉。故障构建里没有任何检查在运行。
- 即使在 Debug 构建里，H15b 报告第 4 节列出的断言点也只有：结构体/元组字段存储、数组元素存储（`Array::setSlotSlow`）、FILL 到元组/数组/结构体、闭包捕获、外部（foreign）rooted/pinned 句柄。fvm 的累加器是 `Frame::set`，不在表里，也没有检查。
- 不能在 `Frame::set` 上加一刀切的检查：回调执行期间，元素视图**合法地**活在形参槽里（H17d 的三条不变量：“提升判断，不提升指针”）。视图只允许活过一次同步调用；不允许的是它跨到下一次读之后仍然被当作值保存。检查必须放在“值存活过这次调用”的那一次存储上——也就是 reduce 的累加器（以及 loop 的状态槽）。

## 3. 修复

### 3.1 只在“值存活过元素”的存储点物化

物化的判据是**值的生命周期**，不是调用边界：回调返回的东西如果马上被写进输出数组（字节拷贝）、被当布尔读掉、或被丢弃，视图和元素同生共死，不需要物化；只有被保存下来、下一轮还要读的值才需要变成真正的对象。

| 位置 | 处理 |
|---|---|
| fvm/jit reduce 累加器（`fastvm.cpp:809`） | 存储前 `materializeCallResult(callElement(...), accumulatorType)` |
| nvm/taskflow reduce 累加器（`higher_order.cpp:127`） | 不额外物化：`cell.set` 的 `setSlot` 已用 `isViewSlot` 把视图排除出快路径并物化 |
| fvm/jit loop 状态（`fastvm.cpp:721`） | `setStateValue` 里按状态类型物化 |
| `map` 输出 | 不物化：`Array::set` 把元素字节拷进输出数组，视图随本轮结束 |
| `filter` 谓词 | 不物化：结果是 bool |
| `foreach` | 不物化：结果被丢弃 |
| 闭包捕获、FILL、外部句柄 | 不物化：H15b 的断言点与存储点已覆盖（本轮复核，见 6 节） |

`materializeCallResult`（`include/camel/core/rtdata/aggregate.h:62`）保持内联：退出类型不是 `Struct`/`Tuple` 时一次类型码比较就返回；是的话直接读视图标志，只有真是视图才走 `materializeIfView`（auto space 里分配一个真实对象）。它放在 `aggregate.h` 而不是 `view.h`，因为 `view.h` 被 `struct.h`/`tuple.h` 包含，看不到具体类。

fvm 的累加器类型在 reduce 开始前解析一次（`functionOf` 的可移动性只影响这一次读，类型指针是进程内驻留的）；loop 状态类型每轮从 `currFrame.typeAt<Type>(self)` 取，一轮一次。

### 3.2 为什么不在调用边界物化

第一版把物化放在 `callElement`（fvm/jit 的每个回调）和 nvm 的 `map`/`filter`/`reduce` 回调上，理由是“调用边界最省心”。它是对的，但代价落在 `map` 上：恒等形状的回调每元素都返回视图，于是 `map` 每元素多分配一个 `Tuple`——这正是 H28 被否掉的那笔开销。`map_chain` 实测 fvm **+5.9%**、jit **+4.1%**（对 0.7% 的 A/A 噪声底），越过 3% 红线。改为只在存储点物化后，`map`/`filter`/`foreach` 的返回路径回到原来的零成本，`callElement` 原样返回，`HigherOrderCallSite::exitType` 字段与 `elementResultType` 辅助函数一并删除。

### 3.3 让检查真的会响

在三个“值存活过元素”的存储点加 `CAMEL_ASSERT_NOT_VIEW`：

| 位置 | 断言对象 | 类型来源 |
|---|---|---|
| `fastvm.cpp:809`（fvm reduce 累加器） | `next`（下一轮要读的值） | `accumulatorType` |
| `higher_order.cpp:127`（nvm reduce 累加器） | `next` | `cellType->elemType()` |
| `fastvm.cpp:721`（fvm loop 状态槽） | `value`（下一轮要读的状态） | `currFrame.typeAt<Type>(self)` |

这三处正是 2.2 的逃逸落点：以前它们都是无检查的 `Frame::set` / `Array::set`。Debug 构建下若删掉 3.1 的物化，断言会在第一次 b 胜出的那一轮中止，而不是在 128 轮之后给出错值。

同样的检查不能加在 `Frame::set` 上（理由见 2.3）；`Struct::set`/`Tuple::set`、数组元素、FILL/闭包捕获、foreign 句柄的 H15b 断言点保持不变，本次改动没有新增绕过它们的路径。

### 3.4 自检

`src/core/rtdata/view_selftest.cpp` 的 `debugRunViewSelfTest()` 增加第二行输出：

```
VIEW_SELFTEST ok normal=clean escape=caught
VIEW_ACCUMULATOR ok alias=detected kept=stable
```

它构造 3 个 `(int, int)` 的紧凑数组，`ensureBlock()` 后：

- 读元素 0 的视图 → 过存储边界（`materializeCallResult`）得到累加器会保存的值；
- 再读元素 1，比较：两个视图是**同一个指针**（`alias=detected`，复用单元确实存在），元素 0 的视图现在读到 `(2, 6)`；
- 物化后的值仍读 `(1, 30)` 且 `isViewSlot == false`（`kept=stable`）。

这一行用 `isViewSlot`（始终编译）而不是 `CAMEL_ASSERT_NOT_VIEW`（Release 编译掉），所以它在发布构建也能观测到“复用单元会别名、物化后的值不会动”这个事实本身。计划期望在 `test/plans/feat/mm/complex.plan.toml`（见第 5 节）。

## 4. 分配代价

- fvm/jit：标量/数组/函数等非聚合累加器——每元素一次类型码比较，**零分配**；聚合累加器且回调返回真实对象——两次头读取，零分配；只有回调返回视图时每元素一个 `Struct`/`Tuple`（auto space）。复现的 3 个元素里只有 b 胜出的 1 轮分配；`bestMany`（第一个元素最大，b 从不胜出）0 次；`identity` 每轮 1 次。
- nvm/taskflow：**没有新增分配**——`setSlot` 原本就把视图物化进单元，`__reduce_arr__` 的 Release 代码与修复前一致（断言编译掉；只多解析一次累加器类型）。
- `map`/`filter`/`foreach`：**零新增**。恒等 `map` 的输出仍然由 `Array::set` 的字节拷贝写入，不产生中间对象。
- loop 状态：每轮一次类型比较；只有状态本身是视图时才分配（当前代码里没有这样的来源，见 8.4）。
- **没有新增块分配**：`loops.hof_compact_element_view` 的 10,000 元素计数原样通过（map/filter 各 1 个输出块，reduce/foreach 0）。

## 7. 性能

按 H17c 的纪律：同一台机器、交错测量、取中位数，不跨构建相减执行时间。命令为 `--timeit std::<backend>/10`，`map_chain` `n=2000, reps=20`，五轮交错（帧内顺序交替）。

噪声底，两种算法都测：

| 算法 | nvm | fvm | jit |
|---|---:|---:|---:|
| A/A（同一二进制两次拷贝） | +0.7% | −0.2% | −0.7% |
| 布局噪声（同一提交 + 一处不执行的无关函数，放在两个热函数之前重建） | −0.7% | +1.2% | +0.3% |

目标对比（before = 修复前快照，after = 最终构建）：

| 后端 | before 中位数 | after 中位数 | 差 | 相对噪声底 |
|---|---:|---:|---:|---|
| nvm | 19.11 ms | 19.54 ms | **+2.3%** | 在 0.7% 底之上，在 3% 红线之内 |
| fvm | 12.71 ms | 12.58 ms | **−1.0%** | 在底之内 |
| jit | 12.75 ms | 12.63 ms | **−0.9%** | 在底之内 |

nvm 的 +2.3% 不是每元素执行代价：nvm 的 `__reduce_arr__` 在 Release 下与修复前代码等价（断言编译掉；唯一的增量是每次 reduce 调用多解析一次累加器类型），物化在 `setSlot` 里原本就发生。它落在测量底与布局带之间的原因只能是整个二进制（fastvm.cpp、自检）带来的布局差异；H17c 已记录不改变被执行的代码、只改地址就能让 nvm 的 `map_chain` 动 4%。

被否掉的第一版（调用边界物化）在同一方法下是 nvm +1.5%、fvm **+5.9%**、jit **+4.1%**——fvm/jit 越过红线，因此改为存储点物化。分配面：该程序上没有回调返回视图，fvm/jit 的 reduce 每元素只多一次类型码比较，`map/filter/foreach` 零增量。

## 8. 开放问题

1. **Debug 断言没有实际触发过**：本任务规定只用 `camel-build.ps1` 构建，而它固定 Release（`scripts/build.js` 硬编码 `config = 'Release'`），`CAMEL_ASSERT_NOT_VIEW` 被编译掉。因此第 3.3 节的断言只有代码位置与自检（Release 可观测的同一判据）作证；要看到中止需要 `npm run debug`，按任务约定没有运行。
2. **nvm 的 +2.3% 归因**：如上，nvm 的 Release 路径与修复前等价，差值来自二进制布局；要硬归因需要一个“同提交 + 一处不执行的无关改动”的对照构建按同一函数布局重复，本次只做到函数级探针（±0.7%）。
3. **nvm 依赖存储器物化**：nvm 的累加器安全来自 `Array::setSlot` 的 `isViewSlot` 排除；断言保留，以便存储路径以后改成裸槽位（fvm 就是裸槽位）时 Debug 能先响。
4. **loop 状态**：fvm 的 loop 元素读走 `getSlot`（已物化），状态存储现在也物化；当前代码里没有把视图写进 loop 状态的来源（HOF 不再交出视图），这一层是防御性的，`foldLoop` 作为契约覆盖。
5. **`foreach`**：结果被丢弃，不物化。若将来有算子保留回调结果，应走同一个 `materializeCallResult`，并在保留点加断言。
6. **extension slots**：图的 extra slot 只存 `uintptr_t` 元数据（entry pc、flags、调用计数），不存对象值，视图不可能落到那里；闭包捕获、FILL、foreign 句柄仍由 H15b 的断言点覆盖，本次改动没有改变它们的路径。`complex.views_selftest_alias` 与 `blocks` 计划通过，作为回归证据。
