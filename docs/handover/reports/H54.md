# H54：CPU 每算子开销

本报告对应 `docs/handover/README.cn.md` 的 H54，分支 `handover/H54-cpu-op-cost`（基于
`origin/develop` `c2a13984`）。作者的原话（`docs/handover/reviews/H24-H25-H26.md` 末尾）：

> 另立 **H54（CPU 每算子开销）**：H48 实测 64³ 的 `tensor:matmul` 每次 45–78 µs、首次
> `tensor:add` 6 ms，主机分派与线程池同步远超计算本身。小矩阵不进线程池（按工作量阈值）、
> 查清首次调用的 6 ms、压低每算子的分派成本；以 H48 的 `dependency_chain` 与两个训练步验收。

三项都查清了，两处是真缺陷，已修；一处（45–78 µs）主要是 H48 当时的机器负载。以
`test/plans/perf/training_steps.plan.toml` 验收：两个训练步的中位数各降 45–49%，链降 5–7%，
`transformer_step` 降 12–18%。

## 1. 三个成本分别是什么

### 1.1 首次调用的 6 ms：线程池构造

`modules/tensor/kernels/parallel.cpp` 的池是函数内 `static WorkerPool`，构造函数创建
`thread_count - 1 = 31` 个 `std::thread`。旧代码的 `parallelFor` **无条件**先调 `pool()`：

```cpp
void parallelFor(int64_t count, int64_t grain, const RangeFn &fn) {
    if (count <= 0) return;
    pool().run(count, grain, fn);   // 就算 chunks <= 1 也先把池建出来
}
```

所以「第一次调用 `parallelFor` 的算子」付这笔钱——H48 里恰好是 `tensor:add`（64×64 广播，
4096 个元素，只有 1 个 chunk，本来就在调用线程上跑），于是它记成 6.17 ms。这笔钱是创建线程，
不是 H48 猜的分配器预热、页错误或设备查询。

同一份代码在 load 57 上做 A/B（`CAMEL_H54_FORCE_POOL` 临时开关，已移除）：

| 首次 `tensor:add` | 时间 |
| --- | --- |
| 旧行为，32 线程（首次调用建池） | **1.58 ms** |
| 旧行为，`CAMEL_NUM_THREADS=1`（没有线程要建） | 23.4 µs |
| 新行为 | **21.3 µs** |

1.58 ms 与 23.4 µs 的差就是 31 次线程创建；H48 的 6.17 ms 是同一件事在 load 85–90 上的读数
（新线程第一次被调度的延迟随负载放大）。

**处理**：池只在「真的要把范围拆给多个线程」时创建，并且判断本身不创建池
（`parallelWouldSplit` 只读一个原子里记的线程数）。链上的全部算子都只有 1 个 chunk，于是
永远不碰池。

没有走另一条路（启动期预热）：那样会给 `dependency_chain` 这种从不并行的程序凭空加
1.5–4 ms 启动成本——按本次的中位数那正好是链的 20–45%，为了省一个不存在的首调成本而付费。

### 1.2 分派成本：`std::function` 与线程池的「惊群」

两处，都由 `parallel.cpp` 承担：

1. **内联路径也要建 `std::function`。** `parallelFor` 的签名是 `const RangeFn &`，所以
   调用者的 lambda 一律先转成 `std::function`。`gemm.cpp:matmul()` 的 lambda 捕获 7 个
   指针，超过 libstdc++ 的 16 字节 SBO，于是**每次 matmul 都多一次堆分配**，哪怕范围只有
   1 个 chunk。现在 `parallelFor` 是头文件里的模板：范围不需要拆时直接 `fn(0, count)`，
   不构造 `std::function`、不碰池的任何锁。
2. **一个 3 个 chunk 的区域叫醒 31 个 worker。** `wake_.notify_all()` 之后，被叫醒但抢不到
   块的 worker 各自空转 4096 次 `_mm_pause`（≈66 µs）才睡回去；也就是每个区域烧掉
   29×66 µs 的 CPU，在共享主机上把调用者自己挤掉。现在只 `notify_one` 需要的
   `chunks - 1` 次（睡着的 worker 会被点醒，已经在自旋的 worker 自己看得到新的 generation）。

实测（32×784×128 的 matmul，3 个 chunk，每块约 25 µs）：

| | 时间 |
| --- | --- |
| 单线程，全部内联 | 49 µs |
| 惊群，load 62 | 950 µs |
| 只点醒需要的 worker，load 27 | 82 µs |

950 µs → 82 µs 是这一步的主要收益（两者负载不同，82 µs 那组是在 load 27 上量的，同一时刻
内联的 49 µs 是在 load 62 上量的）；82 µs 仍高于 49 µs，所以这种尺寸（见 1.3）现在干脆
不进池。

### 1.3 阈值：12 µs → 40 µs，且只有一个地方定义

旧代码的 grain 是散在各 kernel 里的魔数：elementwise `1<<15`、reduce `1<<12`、
gradient `4096`、layout `16384/inner`、relu `1<<15`、gemm `kFlopsPerWorker = 2 MiFLOP`。
它们互不相干，也没有一处写着「为什么是这个数」。

现在只有一处策略（`modules/tensor/kernels/parallel.h`）：

- `kMinWorkPerWorkerNs = 40000`：一个 chunk 至少要有 40 µs 的串行工作才值得交给别的线程；
- `kNsPerFloat = 0.17`：一次普通 f32 逐元素遍历每元素 0.17 ns（实测），各 kernel 用它换算
  自己的单位成本；
- `grainForWork(nsPerUnit)`：把单位成本换算成「一个 worker 的量」。

`gemm_blocked.inl` 的 `kFlopsPerWorker` 由 `kMinWorkPerWorkerNs / kNsPerFlop` 算出
（`kNsPerFlop = 0.010`，实测 128³ 45.4 µs、256³ 334 µs），elementwise / reduce / gradient /
layout / relu 的 grain 一律 `grainForWork(rate)`。40 µs 是实测定的：

| 一条算子/一轮，中位数 | 单线程（全内联） | 进池 |
| --- | --- | --- |
| f32 广播乘，262144 元素 | 46 µs | 33 µs（8 chunk） |
| f32 广播乘，1048576 元素 | 181 µs | 144 µs（8 chunk） |
| matmul 128³ | 45 µs | 30 µs（2 chunk） |
| matmul 256³ | 334 µs | 156 µs（8 chunk） |
| matmul 32×784×128（3 chunk，每块 ~25 µs） | 49 µs | 82 µs（3 线程） |

每块 25 µs 时拆开是亏的，每块 55 µs（256³/8）时是 2.1 倍收益；交叉点在 25–55 µs 之间，取
40 µs。同一张表也说明为什么小矩阵不该进池：64³（0.52 MFLOP，~6 µs）永远只有 1 个 chunk。
按这个策略，C2 训练步的 32×784×128 也回到内联——这正是下面 mlp 步降一半的原因。

## 2. 数字

环境：Linux 主机，32 核 EPYC 7343，Release，`-Jobs 8`，机器同时跑别的任务。验收计划给的是
**10 次运行的中位数**（`timeit_*_10`），每次运行开始前记了 load average。

### 2.1 验收计划

| 测试 | 改前（load 29–70） | 改后（load 34–41，三次运行的中位数） | 变化 |
| --- | --- | --- | --- |
| `dependency_chain.nvm` | 9.31 ± 0.79 ms | 8.84 ± 0.46 ms | −5% |
| `dependency_chain.fvm` | 9.39 ± 0.74 ms | 8.69 ± 0.50 ms | −7% |
| `mlp_step.nvm` | 93.95 ± 5.74 ms | **48.14 ± 1.57 ms** | **−49%** |
| `mlp_step.fvm` | 88.20 ± 6.82 ms | **48.37 ± 1.77 ms** | **−45%** |
| `transformer_step.nvm` | 6.63 ± 0.72 ms | 5.83 ± 0.42 ms | −12% |
| `transformer_step.profile` | 25.32 ms | 20.71 ms | −18% |

三次运行（load 41 / 37 / 35）的链上中位数是 8.85 / 8.71 / 8.84 ms，离散度比改前小一半
（±0.46 对 ±0.79）：链不再碰线程池，也就不再受池的锁与唤醒影响。

每步（程序自测 `ms_per_step`）：

| | 改前 | 改后 |
| --- | --- | --- |
| `dependency_chain` 每轮墙钟 | 23.5 µs（H48，load 85–90） | 17.6 µs（load 57），min 17.0 |
| `mlp_step` | 1.88 ms（计划 93.95/50）；H48 在同一台机上报 16.2 ms/步 | **0.96 ms**（计划 48.14/50），程序自测 1.05–1.10 |
| `transformer_step` 每步 | 137.4 µs（H48） | 118 µs（5.83/50） |

H48 的 16.2 ms/步与 45–78 µs 的 matmul 是同一台机器在 load 85–90 上的读数：同一份 64³
matmul 在 load 18 上是均值 8.0 µs、最小值 6.72 µs，其中 6.17 µs 是 GEMM 本身。也就是说
H48 那个「单算子 70 µs」里，绝大部分是主机争抢与池的惊群，不是算子开销。

### 2.2 每算子地板的拆分

`std::profile` 的算子表 + 临时插桩（500 轮，load 18，均值 / 最小值；插桩已移除）：

| 算子 | 调用 | 首次 | 之后均值 | 最小值 |
| --- | --- | --- | --- | --- |
| `tensor:matmul`（64³） | 1000 | 61.9 µs | 8.0 µs | **6.72 µs** |
| `tensor:add`（64×64 广播） | 503 | 20.7 µs | 2.7 µs | **0.70 µs** |
| `tensor:relu` | 500 | 9.9 µs | 1.6 µs | — |
| `tensor:zeros` | 3 | 13.0 µs | 5.4 µs | — |
| `tensor:sum` | 1 | 3.5 µs | — | — |

最小值的拆解：

| 段 | matmul 64³ | add 64×64 |
| --- | --- | --- |
| 整条算子 | 6.72 µs | 0.70 µs |
| 规划 + 类型 + 分配 | 0.41 µs | 0.48 µs（其中 `createTensor` 0.22） |
| 计算内核 | 6.17 µs（GEMM） | 0.06 µs（逐元素循环） |
| 其余（VM 调用、`parallelFor`） | 0.14 µs | 0.16 µs |

- 64³ 的 GEMM 是 0.52 MFLOP / 6.17 µs ≈ **85 GFLOP/s**，约为该核 AVX2 FMA 峰值
  （3.7 GHz 下 118 GFLOP/s）的 72%。这条链的地板就在这里：一轮是
  `relu(x @ w + b) @ w`，两个 matmul（6.72 + 6.72）+ 广播 add（0.70）+ relu（约 0.4）≈
  14.5 µs，实测中位数 17.6 µs，剩下的 3 µs 是这一轮另外两个标量算子与循环本身。**链已经
  贴着地板跑**：主机侧（VM 调用 + 规划 + 分配 + `parallelFor`）只剩 1.1 µs，占 6%。
- 小算子的地板是 **0.70 µs**（4096 元素的广播 add），其中输出张量 0.22 µs、广播规划
  0.26 µs、VM 的算子调用与 `parallelFor` 0.16 µs。链上的 `:op/add_l` 均值 125 ns，可以看作
  VM 每算子调用本身的价格。
- 也就是说「每算子的分派成本」现在是 **0.1–0.5 µs 量级**，是计算的零头；它不是 H48 那个
  70 µs 的来源。

## 3. 改了什么

`modules/tensor/kernels/`：

- `parallel.h` / `parallel.cpp`：池改成「按需创建」（`parallelWouldSplit` 不创建池、
  `pool()` 只在 `runParallelChunks` 里）；`parallelFor` 变成头文件模板，内联路径不构造
  `std::function`；`wake_.notify_all()` → 只点醒 `chunks - 1` 个 worker；线程数缓存在
  原子里（`configuredThreadCount`），`numThreads()` 不再需要先把池建出来；策略常数
  `kMinWorkPerWorkerNs`、`kNsPerFloat`、`grainForWork` 放在这里。
- `gemm_blocked.inl`：`kFlopsPerWorker` 由策略常数与实测的 `kNsPerFlop` 算出（4 MFLOP，
  原来 2 MiFLOP）。
- `elementwise.cpp` / `reduce.cpp` / `gradient.cpp` / `layout.cpp` / `gemm.cpp`（relu）：
  各自的魔数换成 `grainForWork(rate)`；transcendental 仍是 8 倍率但写成
  `grainForWork(kNsPerFloat * 8)`。
- `tensor/module.cpp` 未改动：没有启动期预热（理由见 1.1）。

数值不变：逐元素算子按元素独立，归约拆的是互不相交的 lane，GEMM 保持每个输出元素的 K 方向
累加顺序；worker 数与 chunk 数只影响「谁算哪一段」。

## 4. 剩下什么

- **C2 训练步现在的大头是 `nn:adam`**：1.16 ms/步，占每步的 62%（101770 个参数、每次
  11 ns/参数，标量循环、没有向量化）。这不是分派成本，不属 H54，是下一个可做的事。
- **阈值随主机负载移动**：唤醒 + join 在安静机器上是 2 µs 量级，load 60 时是几十 µs。40 µs
  是按这台共享主机的实测定的；在独占机器上可以把 `kMinWorkPerWorkerNs` 调到 10–15 µs，
  只动一个常数、不动任何 kernel。
- **worker 仍自旋 4096 次 pause（≈66 µs）** 才睡回去，但只在本次被点醒的 worker 上发生。
  按区域工作量调整自旋长度理论上还能省一点，本次没测到收益，没有动。
- `tensor:add` 的广播规划仍是 3 个 `std::vector` 分配（0.26 µs/次，503 次共 0.13 ms，占链的
  1.4%），不值得为它加一条快路径。
- 设备（tiles）路径完全没有碰。
