# H75 — Tiles 区域/LOOP 重构后的 16 个红灯：归因、修复与期望更新

分支 `handover/H75-tiles-regions`，起点 `origin/develop` `60c39d4e`。任务：把 H71 扫描记下的
16 个 GPU/Tiles 红灯逐个复现、按**实际**失败分组，判定每一组是 develop 上的回归、过期的期望
（并说明哪种行为才是对的、改计划），还是未实现的用例（在计划里注明原因），修真正的小回归，
需要设计决策的进"待决问题"。

结论：135 个 GPU/Tiles 用例现在 **135 绿**。16 个红灯的分布是——

- **8 个是真回归**，都在 `modules/tiles/src/compiler.cpp`：7 个是结构体 `CAST` 没人降低
  （`aggregate_outputs`×3、`resident_outputs`×3、`device_parameter_tree_training`），1 个是
  多状态 LOOP 把常量模板当成了捕获（`multi_state_loop_device`）。
- **1 个是测试形态过期**（`core_view_maps`）：`grad` 写在交给 `run<f>` 的 wrapper 里，而它的
  loss 捕获了值，`std::macro` 展不开，`run` 又按契约没有 CPU 回退。
- **2 个是期望过期**：`static_regions`（`@gpu` 名在 `std::macro` 下被改写成未装饰的函数）与
  `multi_state_loop_boundaries`（所有后端现在都给出同一个区域形状）。
- **4 个是计划期望与 CLI 契约冲突**（`resident_fallback_fault`×4）：运行期故障按
  `docs/cli.md` 写在标准输出上，旧行为没有被改坏，故障也没有被吞。
- **1 个是负载误红**（`extrema_canonical_bits`）：单独跑 3 次分别 9.45 s / 8.95 s / 9.21 s。

## 2. 组 A：结构体 `CAST` 没有降低（7 个，真回归）

**现象**：`outputs.cml`、`resident_outputs.cml`、`device_tree.cml` 在 `std::nvm` 下编译
（`tiles::compile`）时报 `unsupported cast or tensor shape assertion failed`，节点形如
`g2n10 CAST outputType="Results"`：源类型是匿名结构体字面量，目标类型是声明的
`type Results = { ... }`。

**根因**：`44137514`（命名结构体名义化，设计原则 5.2）之前，声明位置的结构体字面量在
builder 里被 `entered = structType->equals(built->type())` 折掉，图上没有 `CAST`；名义化之后
匿名类型与命名类型不再相等，前端按"匿名值落到命名位置"的规则**留下一个 `CAST`**（同序是恒等
转换，异序按字段名逐个复制）。Tiles 的 `Cast` 分支只认张量目标：

```cpp
out                = eval(f, ins.front());
const auto *target = tensor::asTensorType(node->dataType());
if (!target || out.tensor == SIZE_MAX || !target->assignableFrom(out.type))
    throw std::runtime_error("unsupported cast or tensor shape assertion failed");
```

结构体值的 `tensor == SIZE_MAX`，所以必然抛。这是 develop 上的真回归：前端合法的程序，
Tiles 降低不了。

**修复**（`modules/tiles/src/compiler.cpp`，`case rt::GCNodeKind::Cast`）：目标与源都是结构体
且 `target->assignableFrom(out.type)` 时，按目标类型的字段名重排已求值的 `out.fields`（同序
不动），再把 `out.type` 设成目标类型；否则落回原来的张量检查。语义与前端一致：同序是恒等
转换、不复制；异序是按名字段复制，Tiles 里字段本来就是一槽一个 `Value`，重排即可。

**证据**：`test/cases/modules/tiles/outputs.cml`、`resident_outputs.cml` 退出 0；
`device_tree.cml std::macro std::nvm` 打出 6 行 0；计划里 7 个用例全绿（§8）。测试没有改：
程序合法，期望也没过期。

## 3. 组 B：多状态 LOOP 把常量模板当捕获（1 个，真回归）

**现象**（改进错误消息后可直接看出是谁）：

```
tiles: scalar_swap node 8: loop capture must be a tensor or f64 value ((float, float))
```

`loop_multi_device.cml` 的 `scalar_swap` 是 `(float, float)` 两个状态的多状态循环，next-state
是 `FILL` 出来的元组；被当成捕获的是那个 `FILL` 的**模板**（`(0.0, 0.0)` 这样的常量元组）。

**根因**：`60ab7619`（H43，LOOP 变成所在图的区域）之后，循环体、条件、next-state 结果都在
LAS 的同一张图里，`c912ea15` 又把轮次计数器作为最后一个 **With** 输入、把 `roundPort()`
加进 `regionNodes()`。`LoopView::externalInputs(true)` 会扫描区域节点的输入并**把常量也列
出来**：next-state `FILL` 的模板 `Data` 节点、轮次计数器的初始常量都被当成"捕获"。Tiles
的 `materialize` 只接受张量或 f64，常量元组就抛。真正的循环值（外层的张量/标量）从来不是
问题。

**修复**：`Compiler::loop` 与 `loopEligibility` 两处都改成 `view.externalInputs(false)`——只
捕获真正的值。常量的求值本来就不依赖捕获：`eval()` 对 `Data` 节点走 `g->staticArea()` 就地
求出，`FILL` 的模板只需要骨架、不需要作为区域输入。两处必须同时改，否则
`loopEligibility` 会为常量预绑定 `placeholder`，遮蔽 `eval` 的常量路径。顺手把
`materialize` 的错误消息带上场景（`"loop initial state"` / `"loop capture"` /
`"loop next state"`）和实际类型，正是它直接指出了本组的元凶。

**证据**：`loop_multi_device.py` 四个 VM 全 PASS；`loop_multi_boundaries.py` 也一起绿了
（它的 LOOP 用例走同一条降低路径）。

## 4. `static_regions`：期望过期（`@gpu` 名被 `std::macro` 改写）

`gpu_regions.cml` 原来用 `@gpu func mixed`，然后 `regions<mixed>()`。在
`['std::macro','std::nvm']` 组合下，`std::macro` 把 `mixed` 这个**名字**改写成装饰器宏要包的
那个**普通函数**（`Function(graph=mixed)` 指向未装饰的图），于是 `regions<mixed>()` 看到的是
普通图（1 个区域），而不是装饰后的 outline 图（0 个区域 + 1 个 `context_arguments`）。其余
四个组合没有 `std::macro`，看到的是装饰后的图，断言一直成立。

哪种行为才是对的？`regions<f>` 的语义是"看 `f` 现在指的那个函数"；宏把装饰器调用展开掉之后
`mixed` 指的就是普通函数，这一点本身是 `std::macro` 的既有行为（宏展开，不是缺陷；`@gpu`
的语义仍然在 `gpu(mixed)` 这个算子调用上）。测试要锁的是**装饰后的图**，所以改为在 `main`
里显式 `let decorated = gpu(mixed)`，再 `regions<decorated>()`：五个组合看到的是同一个值、
同一张图，断言统一。计划 `test/plans/gpu/tiles_decorator.plan.toml` 的 `static_regions` 行
加了注释说明这一点。行为断言（`cpu detour once`、`56.0`、`12.0`）不变。

## 5. `multi_state_loop_boundaries`：期望过期（所有后端现在同一个形状）

`loop_multi_boundaries.py` 原来对 `std::fvm/std::jit/std::prl` 走 else 分支，期望
`len(regions) == 1`，注释写的是"降低型后端把原始结构化图交给看图算子，装饰器的私有运行时副本
是另一份"。H43 之后函数值自带自己的 program 与 graph，看 `regions<decorated>` 时四个后端都
看到装饰器 outline 后的图：`{"regions": [], "excluded": [{"reason": "node_kind"} ×2,
{"reason": "context_arguments"} ×1]}`。也就是说 else 分支编码的旧行为已经不存在。

改为统一断言（0 个区域、恰好 1 个 `context_arguments`），并在测试和计划里写清"被 outline 的
那次调用被分析当作 context argument 排除"。计划超时同时从 180 s 提到 360 s：这条用例以前在
第二个后端就失败，现在 16 个子进程跑到底（单独跑 114.3 s，并行扫描下更长），180 s 不够。

## 6. `core_view_maps`：测试形态过期（`grad` 留在 wrapper 图里）

`core_views.cml` 原来写

```camel
let df = (v: Tensor<f32>): Tensor<f32> => grad(loss)<v>()
```

`loss` 捕获了 `weights`，所以 `grad(loss)` 不是宏静态的（`std::macro` 的
`noteNotStatic`），它作为运行期算子 `autodiff:grad` 留在 `df` 的 wrapper 图里；
`run<df>` 只降低这张图，而 `run` 按契约**没有 CPU 回退**，于是
`unsupported or effectful operator 'autodiff:grad'`。反序列化/`tiles::compile` 之外，
`core_views` 的另 9 个用例（`gradients`、`layout_grad`、`mean_grad`、`cast_like`、
`device_tree` 等）也是"`grad` 写在 wrapper 里"这一形态，但它们的 loss 没有捕获值，
`std::macro` 能就地展开，所以只有这一条红。

修法是把变换绑到 wrapper 外面（语言推荐写法，也是真正在测"Tiles 编译 pullback 图"）：

```camel
let dl = grad(loss)
let df = (v: Tensor<f32>): Tensor<f32> => dl<v>()
```

五个包装（`df`/`dn`/`dk`/`de`/`dw`）一起改；`inspect<fixed>` 与 `EXPAND_SOURCE` 的断言不变。
`run` 不能降低 live `autodiff:*` 算子的限制记入待决（§9 Q1），不在本任务里改设计。

## 7. `resident_fallback_fault`：计划期望与 CLI 契约冲突（4 个）

**现象**：退出码 1、故障种类与位置都对

```
cpu fault once
error[RuntimeDiag::DivisionByZero]: Attempted division by zero.
  --> test/cases/modules/tiles/resident_fallback_fault.cml:5:16
```

但计划原本 `expect_stdout_exact = "cpu fault once\n"`，实际标准输出是程序那行**加上**诊断。

**判定：不是新洞，也不是旧行为被改坏。** `docs/cli.md` 第 61 行写的是"编译错误或运行期故障
打印在标准输出，警告打印在标准错误"；第 118 行也只把"没人处理的错误值"（`UnhandledError`）
放到标准错误。代码路径：`tools/camel-cli/main.cpp:585-589`，pass 执行失败后
`ctx->runtimeDiagSink()->dump(os, useJsonFormat)`，而 `os` 就是 `std::cout`（同文件 171 行
`ostream &os = cout;`）；`--output-format json` 时诊断数组同样在标准输出。运行期故障没有被
吞：CPU 回退被执行了一次（`cpu fault once` 只出现一次），随后是 `RuntimeDiag::DivisionByZero`
和准确位置，退出码 1。所以旧行为（CLI 的既定契约）在，测试的期望写错了。

计划改为 `expect_stdout_starts_with = "cpu fault once"` + `expect_output_contains`
（诊断名与位置）+ 一段 `verify_script`（那一行只出现一次，诊断紧随其后）。没有改 CLI：把
运行期诊断改到标准错误会破坏 `docs/cli.md` 的契约和编译期诊断的同一渠道。

## 8. `extrema_canonical_bits`：负载误红

H71 记的是 60 s 超时。单独跑（同一构建、`-Jobs` 无关）三次：

```
run1 wall=9.45s   run2 wall=8.95s   run3 wall=9.21s   （三次 exit 0，四后端全 PASS）
```

H71 那次是共享宿主的争用（该用例要起 15 个子进程；H71 用 `-Jobs 12`，本次复跑时宿主
load average 38–55）。同一轮全量扫描里它又一次在 60.01 s 超时，于是把预算提到 180 s：
这不是掩盖缺陷（失败是精确的 `timeout_ms`，不是断言），而是这条 driver 的 60 s 在两次
独立的全量扫描里都不够。`static_regions`（10 个子进程、12 s）同样处理。

## 9. 待决问题

1. **`run<f>` 对 wrapper 图里的 `autodiff:*` 没有回退，也没有可读诊断。**
   `core_view_maps` 的旧形态会得到 `unsupported or effectful operator 'autodiff:grad'`；
   H49 第 7a 步会删掉 `run`，所以本任务只把用例改成合法形态，不在这里加回退或新诊断。
   需要作者确认：`run` 在删除前是否应当给出"这个算子不能被 `run` 降低，请先把变换绑到
   wrapper 外"这样的定向诊断，而不是泛泛的 effectful operator。
   （`with_grad` 同理会撞上；`device_tree` 的 loss 没有捕获值，`std::macro` 展开后不触发。）
2. **`std::macro` 把 `@gpu` 名改写成未装饰的函数**：`regions<name>` 因此看不到装饰后的图。
   这是宏展开的自然结果（`@gpu` 只是 `gpu(f)` 的糖），但"装饰器的名字在宏之后指向谁"没有
   文档。测试已改为显式 `gpu(f)`，不改宏语义；需要作者裁定是否要让被装饰的名字在宏之后
   仍指向装饰结果。
3. **`LoopView::externalInputs(bool constants)` 的默认语义**：Tiles 现在显式传 `false`（常量
   就地求值，不作捕获）。核心的 loop 降低（`host`/`fvm`）是否也应当把常量排除在捕获之外，
   还是保持"常量也算捕获"？本任务只改 Tiles 的两处调用点；`src/runtime/loop.cpp` 的接口不动。
   **H91 已完成**：作者的裁定是"常量不是捕获"，核心的 `externalInputs` 默认（`false`）不含
   常量，判据从"`DATA`"改为"值在构建期已知"（`DATA` 或 `isConstant()` 标记），默认值在两处
   声明上写明；核心本来就没有捕获表，常量在区域内就地求值。见 `reports/H91.md`。
