# H140 — 标准库声明化的下一批：`ckpt`（结论：没有可声明的固定签名，不迁移）

分支 `handover/H140-ckpt-declarations`，起点 `origin/develop` `cd39898fc`（H133 之后）。任务书是
H19 第 10 步的下一批模块声明化，模块是 H108 由 `tree` 改名来的 `ckpt`。**本批没有迁移任何算子**：
`ckpt` 的 7 个算子没有一个具有声明能承载的固定签名，三条机制限制逐条有探针证据（第 3 节）。
所以 `stdlib/signatures/ckpt.cml`、`modules/tree/`、参考页与 AST 快照都没有改动，也没有新增声明
用例——没有声明可测（第 5 节）。本批交付的是这份报告与看板行，以及给作者的两条待决项（第 7 节）。

一句话结论：**`ckpt` 的声明迁移与 H108 的遍历是同一件事，按任务书的停手条件停在报告。**

## 0 结论摘要

- **5 个树 intrinsic**（`tree_map`/`tree_reduce`/`tree_unzip`/`tree_leaves`/`tree_paths`）不是能跑的
  算子：`checkpointKernels()` 只有 `save_tree`/`load_tree`，这五个由编译器
  `Builder::expandTreeCall` 按树形状展开。没有执行器，无体声明在**加载声明模块时**就报
  `SemanticDiag::NativeDeclarationNotLoaded`（`0x0300017C`）；探针里 5 条声明全部这样被拒
  （第 3.1 节）。它们的返回类型是"同一形状的结果树 / 叶子元组"，也写不进一个 `FunctionType`。
- **`save_tree` 能写成声明**（两条元数规则），探针里加载成功、`native_state_checkpoints` 的 10 个
  模式全过、效果与资源逐字不变；代价是**丢掉编译期的叶子检查**：`ArgumentsRejected`
  （`0x0300001C`）+ `tree leaf 'weights'` 变成运行期的 `RuntimeDiag::FileSystemError`
  （`0x04000036`），程序真的开始写 `out/never`（第 3.2 节）。`unsupported_leaf_is_a_compile_error`
  因此红。声明承载的是类型，不是"`T` 的每个叶子都可存"这条谓词。
- **`load_tree` 连形状都写不出**：结果类型取自 `::<T>` 显式类型实参或期望类型，声明看不到它们；
  H103 的 `native.declaration_type_argument` 已经把这个缺口钉成用例（第 3.3 节）。
- 这三条限制都不是本批能加的语法：谓词要 `where`/类型函数（H51 第二期，`docs/handover/README.cn.md`
  H51 第 4 条），显式类型实参要声明机制本身改动（H103），编译器展开要 H51 13.3 的 Camel 改写。
- **H108 的阻塞状态不变**（第 7 节）：作者裁定没下来之前，`save_tree`/`load_tree` 留在 C++；
  本轮新增的只是把它的影响面量清楚——不只遍历重写被挡，声明迁移也被同一批缺口挡住。
- 验收：四个计划 2836 条，**2832 通过 / 3 失败 / 1 跳过**（3 条失败是 H114 的 `rename.*_graph_identity`
  旧摘要，基线就红；跳过是 Windows-only 的 `unicode.paths`），与改动前的基线一致；
  `--verify-ops` 与 **365** 条已注册重载一致；参考页无 diff；诊断目录仍 **202** 条。

## 1 选中的模块与"一个事实只写一处"的现状

`modules/tree` 注册 7 个算子（目录名仍是 `tree`，H51 允许；模块名、URI、`.cmo` 都是 `ckpt`）。
`docs/handover/reports/H19-plan.md` 第 2 节的账本已经把这一行划给 H51：

| 模块 | 今天 | 之后 | 步骤 |
|---|---|---|---|
| `tree` | `tree` + `ckpt` | H51 | H51 |

同一份计划第 103 行写得更直接："`stdlib/tree.cml`、`tree_*`、`ckpt` 拆分、`modules/tree`、
`tree.plan.toml`、树用例 | H51（步骤 13）| **不碰**。"所以 H19 第 10 步从来没有把 `ckpt` 算进
"固定签名模块"；本批的结论正好是它在代码上的理由。

逐条对照 H94 结尾与约定页第 1 节留下的限制：

| 名字 | 声明要写的东西 | 今天由谁给 | 能不能写 |
|---|---|---|---|
| `tree_map` | `with <f: (leaf: A) => B>`、`(tree: T) => U` | 编译器展开（`src/compile/gir/tree.cpp`） | **不能**：无执行器；结果类型是"同形状的 B 树" |
| `tree_reduce` | `with <f: (acc: R, leaf: A) => R>`、`(tree: T, init: R) => R` | 同上 | **不能**：无执行器（类型本身可写，但没人会按它检查，见 3.1） |
| `tree_unzip` | `(tree: T, reference: S) => U` | 同上 | **不能**：无执行器；结果是"每叶一个元组的树 → 元组棵树" |
| `tree_leaves` | `(tree: T) => L` | 同上 | **不能**：无执行器；结果是叶子元组 |
| `tree_paths` | `(tree: T) => P` | 同上 | **不能**：无执行器；结果是字符串树 |
| `save_tree` | `(dir: string, tree: T, dataset_manifest_sha256?: string) => void`，且叶子可存 | `SaveResolver`（`modules/tree/src/checkpoint.cpp:358`） | **形状能写，谓词不能**（3.2） |
| `load_tree` | `::<T>(dir: string, dataset_manifest_sha256?: string) => T!`，且叶子可存 | `LoadResolver`（`checkpoint.cpp:385`） | **不能**：结果类型取自 `::<T>`/期望类型（3.3） |

`stdlib/signatures/ckpt.cml` 自己第 3 行写着 "These declarations are reference metadata."——它是参考
元数据，不是声明：里面 `tree_map` 的 `T`/`U`、`tree_leaves` 的 `L` 都是占位，参考页照原样打印
（`tree_leaves: (tree: T) => L`），任何调用都不可能按它绑定。把这份文件搬去 `stdlib/ckpt.cml` 并
删掉 C++，先撞上的是第 3.1 节的执行器检查，再往后是第 3.2/3.3 节的谓词与类型实参。

## 2 判据：声明机制要求什么

`declareNativeOperator`（`src/compile/gir/builder_modules.cpp:357`）在加载声明模块时逐条检查：

1. URI 有协议前缀，且 `ExecutorManager::findWithoutImport(uri)` 能找到**执行器**（`:377`）；
2. `OperatorTable::find(uri)` 能找到**纯度**（`:385`）；
3. 声明的 `FunctionType` 交给 `DeclaredFuncTypeResolver`；泛型的类型变量在调用时由
   `unifyTypeVars` 从**实参**绑定，定不下来的变量是编译期错误（`docs/language/07_statements.md:241`）；
4. 声明是本模块算子组的唯一来源，加载后经 `exportNativeOperators` → `replaceEntity` 顶掉 C++ 的
   同名组（H94 第 1 条）。

把上表逐条对照这四条：五个 intrinsic 缺第 1 条；`save_tree` 缺第 3 条的一种（谓词不是类型）；`load_tree`
缺第 3 条的另一种（结果类型不在实参里）。所以这不是"写法没找对"，是机制边界。`inspect --ops` 也
把这件事写在了记录里：

```text
OPERATOR {"module":"ckpt","name":"save_tree","with":-2,"norm":-2,...}
```

`-2` 的定义是 "when the resolver does not tell"（`include/camel/core/module/introspect.h:52`）：
**7 条记录全部是 `with:-2, norm:-2`**，注册表自己说这 7 个算子都没有固定签名。

## 3 探针（未提交，只为把边界量出来）

两次探针都在 Linux 主机上构建并跑计划，改动在本地 `git checkout` 撤销，工作树最终与 `cd39898fc`
一致。

### 3.1 五个 intrinsic：没有执行器，声明在加载时被拒

写一份只含五条声明的 `stdlib/ckpt.cml`，删掉 `modules/tree/module.cpp` 里五个
`exportEntity`/`TreeResolver`（`checkpointKernels()` 不动，它本来就只有 save/load）。构建通过，
模块加载失败：

```text
error[SemanticDiag::NativeDeclarationNotLoaded]: The declaration 'tree_map' names the operator
'ckpt:tree_map', which no loaded module implements.
  --> .../stdlib/ckpt.cml:4:1
help: A body-less declaration stands for an operator of a loaded C++ module. Import the module
that implements it, and check that the URI names its function; a declaration whose
implementation is not loaded is not a function.
```

5 条声明各报一次（`tree_map`/`tree_reduce`/`tree_unzip`/`tree_leaves`/`tree_paths`），随后导入方
各得一条 `UnresolvedReference` 与一条 `ImportedModuleHasErrors`，共 11 条。计划：
`feat.modules.ckpt` 0/2、`feat.modules.checkpoints` 0/3——整个模块载入不了。

这条检查是对的：它们本来就不是"一个能跑的算子的签名"，是编译器在建图时按树形状展开的构造
（`Builder::expandTreeCall`，`builder_operators.cpp:1872` 调用；展开产出 ACCESS/FILL/CALL 等普通
节点）。即使把声明改成能通过检查的形状，展开仍先于解析器发生，声明里的类型没有任何读者——
那正是 H108 说的"没有使用者的声明模块就是死代码"。

### 3.2 `save_tree`：能声明，代价是编译期的叶子检查

只保留 `save_tree` 的两条声明（2 参、3 参，各写 `typeas T`），删掉 `SaveResolver` 与它的
`OperatorGroup`，`load_tree` 与五个 intrinsic 不动：

```camel
export func save_tree(dir: string, tree: typeas T): void
export func save_tree(dir: string, tree: typeas T, dataset_manifest_sha256: string): void
```

加载成功，`inspect --ops` 里 save/load 的记录变成 2 条 `save_tree` + 1 条 `load_tree`（第 4.2 节）。
`feat.modules.ckpt` 2/2 绿；`feat.modules.checkpoints` **4/5**：`native_state_checkpoints`（10 个
模式，含四个调度器与进程重启）全过，`unsupported_load_target_is_a_compile_error` 也过（`load_tree`
仍是 C++），唯一红的是 `unsupported_leaf_is_a_compile_error`：

```text
error[RuntimeDiag::FileSystemError]: 'ckpt.save_tree' failed for 'out/never':
weights: unsupported checkpoint leaf type float[].
  --> test/cases/modules/nn/checkpoint_unsupported_leaf.cml:5:5
```

它在**运行期**才失败，而且真的开始了写目录。原来的编译期诊断是

```text
error[SemanticDiag::ArgumentsRejected]: ...
tree leaf 'weights' has type float[], which a checkpoint cannot hold (tensor, Bytes, string, ...)
```

差别不是格式：`unsupportedLeaf()`（`checkpoint.cpp:352`，沿 `core::type::tree::firstRejectedLeaf`
走静态类型）是 `SaveResolver`/`LoadResolver` 拒绝调用的**唯一**理由，声明里没有任何位置可以写
"`T` 的每个叶子都是这八种之一"。`where` 约束与类型函数属于 H51 第二期（`docs/handover/README.cn.md`
H51 第 4 条："类型位置的同一套写法（类型函数）与 `where` 约束属于第二期，本项只预留位置"），今天
没有这个机制。

### 3.3 `load_tree`：结果类型取自类型实参，声明绑不了

`LoadResolver::resolveForCall`（`checkpoint.cpp:391`）从 `types`（`::<T>`）或 `expected`（结果的
期望类型）取目标类型，再按它检查叶子。声明机制的两条路都不通：

- 返回类型写成 `typeas L`：H103 的用例 `native.declaration_type_argument` 已经证明"`::<T>` 与
  期望类型永远到不了声明的解析器"，调用报 `NoMatchingFunction`；
- 返回类型写成具体类型：那就不是 `load_tree` 了，实例化链上的每个调用点都要各自一条声明。

H103 §3 与约定页第 2 节第 46 行把这条写成通则（"返回类型取自类型规则或取自类型实参时，声明给不出
这条规则"），`json::decode_as` 是同一个形状。

## 5 为什么没有"三条用例"

前几批的三条用例（导入方看到声明的类型、错元数、错类型在**声明处**诊断）都以"声明是真的、调用按
它检查"为前提。本批没有声明，三条用例就没有被测对象；硬写只能测到别的东西：

- 五个 intrinsic 的错元数/错类型在**展开处**报 `ArgumentsRejected`（"invalid number of tree
  arguments"、"tree structure differs"），不在声明处。结构那一条已经被
  `shape_mismatch_reports_first_path` 钉住（`tree leaf 'block'` / `tree structure differs`）；错元数
  那一条今天没有用例，本批也不加——展开处的诊断不是声明用例，加了只会把"声明不存在"记成一条
  通过；
- `save_tree`/`load_tree` 的两条编译期负例（`unsupported_leaf_is_a_compile_error`、
  `unsupported_load_target_is_a_compile_error`）恰好是"声明写不出谓词"的反证：它们必须继续在
  编译期红，而这只有在签名仍由 C++ 解析器给时才成立；
- 显式类型实参的缺口已经有 `native.declaration_type_argument`（H103）。

所以本批不加用例，也不改这三条既有用例——改了就是把语义退化记成新基线。

## 7 H108 的阻塞状态

H108 §0 的结论原样有效：

> `stdlib/ckpt.cml` 没有写：它要声明的只能是第 4 节那些新原语，而那些原语只有配合第 3 节的
> Camel 遍历才有意义；单独提交一份没有使用者的声明模块就是死代码。

§2.1 把缺口定在"`spec` 能由 `T` 在编译期算出来"这一条：

> 它有两个前提：(1) `spec` 能由 `T` 在编译期算出来；(2) `open` 拿 `spec` 一次校验完，所以
> `get` 不再返回错误。第 (2) 条是设计稿自己列的、需要 nn 一侧确认的行为变化……不是本次的障碍。
> 障碍在第 (1) 条。

§2.2 说明它为什么写不出来：

> 于是 `type_spec` 能沿结构拼出 `{…, …}`（字段名来自 `n`），走到 `case _` 就没有任何东西可以
> 拼出 `f32[3,4]`。设计稿第 140 行那个 `{ … }` 正是这个洞。

§2.4(e) 对"只迁移 save 一半"的回答：

> save 侧确实**不需要**内核读静态类型（`ckpt_put` 用值自己的 dtype/shape，结构由 Camel 的
> `save_at` 走），能写；但任务要求不要把模块留成半迁移，而且验收的 load 图仍然读静态类型，
> 所以不做。

**本轮的消息是：H108 的选项 3 之前，声明迁移也做不到。** 三条理由各有独立证据：

1. 五个 intrinsic 没有执行器（3.1），声明机制的第一条检查就拒绝；它们的 Camel 改写是 H51 13.3
   （H108 §2.3 也把"按类型分 URI 的算子"归到 H103 的既有结论里）。
2. `save_tree` 的声明能加载，但叶子谓词没有写法（3.2），而这条谓词就是 H108 §2.3 那套"静态叶子
   类型逐项比较"的编译期半边。
3. `load_tree` 的结果类型取自 `::<T>`/期望类型（3.3），是 H103 已经钉住的另一件事。

作者裁定（H108 §3）要回答的仍是同一组问题，只是现在可以补一句：**选项 1（补"静态类型 → 值/文本"
的路）落地之前，`save_tree`/`load_tree` 的签名只能留在 C++ 解析器里；声明要等它，和遍历要等它
是同一个原因。** 要给声明单独开一条路，需要的是另一条机制——类型变量上的谓词（`where` / 类型
函数，H51 第二期）——那比 H108 的选项 1 更大，也更不应该由本批顺手加。

H108 §4 已经写给将来的原语做了同样的区分，可以直接对照：

> | `ckpt_put` | `(h: Ckpt, path: string, x: L) => Ckpt` | 每叶一个重载（8 种），用**值**的 dtype/shape；**可声明** |
