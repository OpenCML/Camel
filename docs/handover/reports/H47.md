# H47 报告：Tiles 现状与差距

分支：`handover/H47-tiles-gap`，基于 `origin/develop` `ea3a196c`；本文件所在的提交是这一支唯一的改动（本任务只读，不改代码）。

测量环境：`ssh 88zjwei`，AMD EPYC 7343（32 逻辑核）/ 503 GB / 8 × RTX 3090 / 驱动 580.95.05（CUDA 13.0）/ NVRTC 12.3 / Ubuntu 22.04；全部时间用 `taskset -c 3` 钉核，取多次运行的最小值。测量期间 1 分钟负载 85–90（机器上另有一个常驻的 22 GB DDPM 训练进程），GPU 侧数字受邻居影响很大，凡受影响的都在表下注明。Camel 版本 v0.2.24（`package.json`）。

测量程序都放在主机 `/tmp/h47/`，不进仓库；文末附命令。

## 0. 结论

1. **只有"前向图里能被静态类型识别的一段"会上 GPU。** C2 的真实训练步（形状是运行时值）一个算子也不下放：`tiles::compile` 之后图里 0 个 `tiles:run_preferred_resident`、0 个 `tiles:retain_preferred`、0 个 `tiles.region`。
2. **即使把 C2 的形状写成静态的，24 个算子/步里也只有 10 个（42%）下放，而且下放的全是前向。** 反向的 12 个算子在自动微分图里，输出类型是 `Tensor`（没有形状），区域分析看不见；`relu` 的反向还要 `gt`（bool 张量），Tiles 的 dtype 只有 f32/f64。
3. **下放没有加速，反而略慢。** 静态步 CPU 2.166 ms/步，GPU 路径 2.228 ms/步（各 5 次取最小）；机器更忙时的一次对照是 CPU 2.69、GPU 4.89 ms/步。每步 10 次上传（1,127,760 B）、5 次下载（57,200 B）、7 个同步点；传输是**逐叶子串行**的，每个叶子单独建 stream、单独同步（2.1 实测每叶约 60 µs 固定 + 按 ~0.5 GB/s 计的字节成本），省下的至多是整个前向（CPU 上 0.25–0.36 ms/次，含两个 GEMM）。
4. **编译启动不是 73 s。** 本机第一次用 GPU 是 0.7–1.3 s（驱动初始化 + 一个 4 kernel 模块 292 ms；之后每个简单区域模块 35–42 ms），而 Tiles 自己的遍只有 1.3 ms。
5. **回退是"静默且昂贵"的。** 设备不可见时（`CUDA_VISIBLE_DEVICES=-1`）区域仍然被 outline，运行时每次调用都重试一次 `cuInit`，静态步变成 1.5–2.1 s/步，比 CPU 慢约 1000 倍。

## 1. 现状

### 1.1 一次调用走的路

- 遍：`tiles::compile`（`region_pass.cpp`）→ `outlineRegions`（`region_outline.cpp:76`）→ 每个可达图 `analyzeRegions`（`graph_regions.cpp:179`）→ `partitionRegions`（`regions.cpp:21`）→ 每个区域 `extractRegion` 成纯函数，顺手 `compileTypes` 一次；**这次失败被吞掉**（`region_outline.cpp:132-135`）→ 图里插入 `tiles:retain_preferred`（上传）、`tiles:run_preferred_resident`（执行）、`tiles:download`（下载）（`region_outline.cpp:105-160`、`module.cpp:482-487`）。
- 运行时每次调用：`preferGpuKernel`（`module.cpp`）→ `prepare`（按实参形状再特化一遍）→ `executeResident`（`cuda.cpp:514-516`）→ `submitProgram` 后 `completion->wait()` → 逐个下载（`downloadValue` 再等一次完成，`cuda.cpp:410`）。

所以"编译一次、执行多次"只对 CUDA 模块成立；**每次调用都要重新特化、重新规划存储、重新上传全部输入**。实测：同一个区域函数第二次调用 0.19–0.21 ms，第一次 1.29–2.61 s（见 2.5）。

### 1.2 能下放什么

- 准入表是硬编码的 20 个名字（`graph_regions.cpp:42-71`）：`neg abs exp log sqrt rsqrt relu add subtract multiply divide maximum minimum matmul sum_axis mean_axis max_axis sum_to`，外加 `tensor:sum`→`sum_all`、`tensor:mean`→`mean_all`。
- 每个节点还要过 `eligibility`（`graph_regions.cpp:72-166`）：无控制边、无 context 参数、纯、无外部效果、语义声明 major == 1、输出是**静态 f32 张量**、`NodeInstance` 的域参数全部已知、操作数不是 f64 标量、matmul 秩 2、归约轴唯一、索引契约能生成。任何一条不满足就写一个排除原因（`inspect`/`regions` 会打印）。
- **编译器其实会降更多**（`compiler.cpp:779-871`）：`cast_like`、`broadcast_like`、`expand_axis`、`ones_like`、`zeros_like`、`matmul_grad_lhs`、`matmul_grad_rhs`、`transpose`、`permute`、`slice`、`reshape` 共 11 个族有降级，但不在准入表里，区域分析永远不会选它们（实测见 2.7、3.H3）。
- dtype 只有 f32/f64（`modules/tiles/include/tiles/dtype.h`）：bool（`gt`）、int64（`take` 的索引、分类标签、`argmax`）都进不了编译区域。
- 循环只接受 `LoopKind::For` + 有状态 + 静态 `int[]` 域（`compiler.cpp:885-906`）；图中的 `while` 不行。分支只支持"特化时已知的布尔条件"（`compiler.cpp:444-456`），区域分析里没有 Arm 的概念（见 2.7）。

### 1.3 区域怎么划

`partitionRegions`（`regions.cpp:21-134`）的做法：

1. 只保留从图输出反向可达的活跃节点；
2. 相邻且都合格的节点可以合并，前提是合并后"商图"仍然无环——即**依赖凸**：GPU 段不能把 CPU 节点夹在中间形成环（`regions.cpp:47-110`）；
3. 贪心、确定性、直到不能再合并（`regions.cpp:89-110`）；全局代价优化留给 `schedule.cpp`；
4. 每个连通分量一个 region；region 之间的边如果能"前一个 region 的输出直接给后一个用"，就记一条 `resident` 边（`regions.cpp:170-176`），否则算上传（`regions.cpp:162-169`）。

传输规划只看**区域边界**（`planRegionTransfers`，`regions.cpp:136-197`）：每个区域输入要么上传，要么从前一个 region 的设备值直接取；`embedded` 常量跳过；区域输出被主机节点用到才下载。**没有任何跨调用缓存**，所以同一组权重在每一步、每个区域都要重新上传。

### 1.4 谁决定下放

- **自动**：`tiles::compile` 遍，整个可达程序，按图的静态类型判断；没有标签，没有 `--devices`（`src/core/tags.cpp` 里没有 `gpu`/`cpu` 这两个标签）。
- **显式（函数级）**：`@gpu` / `gpu(fn)`（`module.cpp:489-510`）给函数包一层"上传-执行-下载"，每次调用走 `preferGpuKernel`，不支持时回退 CPU 原函数。
- **显式（调用点）**：`run` / `run_device` / `source` / `inspect` / `benchmark`（`module.cpp:531-549`）。它们按实参**值**特化，所以不需要静态类型；`run_device` 返回私有的 `Device<T>` 外部资源，`run` 下载后返回普通值。
- `compileTypes` 失败不阻止 outline（`region_outline.cpp:132-135`）：运行时再试一次，失败就悄悄跑 CPU（代价见 2.6）。

### 1.5 编译缓存

- 源码缓存：结构键（不是指针，`codegen_cache.cpp:28-60`），32 条 / 16 MiB LRU（`codegen_cache.cpp:26`），进程内。
- 模块缓存：`source` + 编译选项精确比较，32 条（`cuda_backend.cpp:272-338`），进程内。
- **没有磁盘缓存**：换进程、换形状都要重新 NVRTC。实测每个简单模块 35–42 ms，4-kernel 前向模块 292 ms（2.5）。

### 1.6 内存池

- 设备 64 MiB / 32 块，pinned 主机 16 MiB / 32 块（`include/tiles/internal/cuda_backend.h:121-122`）；256 B 粒度、best-fit（`cuda_pool.cpp:26-72`）；比 idle 上限大的块直接还给驱动（`cuda_pool.cpp:119`）；teardown 时 drain（`cuda_backend.cpp:242-248`）。
- 设备缓冲按值生命周期复用（`schedule.cpp::planStorage`），**没有跨调用的驻留**；`Device<T>` 是唯一的例外，但它走的是私有存储（见 1.9）。

### 1.7 流与事件

- 每次提交新建一个 non-blocking stream 和一个 completion event（`cuda_resources.cpp:Resources::Resources`、`cuda_submission.cpp:22-37`），提交结束就销毁；跨提交只用 `depend()`：同 context 用 event wait，否则先 `wait()`（`cuda_submission.cpp:71-110`）。没有 stream 池，也没有 CUDA Graph。
- 公共调用全部同步：`executeResident` 等完成（`cuda.cpp:516`），`execute` 等完成再下载（`cuda.cpp:484-488`），`downloadValue` 再等（`cuda.cpp:410`）。没有给用户留异步句柄。

### 1.8 主机设备传输

- 每个输入先拷进 pinned staging，再 `cuMemcpyHtoDAsync` 到设备（`cuda.cpp:268-284`）；提交时 `upload(false)`，与 kernel 在同一条 stream 上按序执行（`cuda.cpp:494-507`）。
- 下载是 D2H + 同步（`downloadValue`）。
- 权重不驻留：静态 C2 步每步把 4 个权重 + x 上传**两遍**（前向区域一遍、反向图里重算前向的区域一遍），共 1,127,760 B（2.3）。
- 没有 DLPack 桥：`modules/tensor/dlpack.h` 只是 C ABI 类型，tensor 模块没有导出 dlpack 转换算子；数据块的 `device_` 字段（`include/camel/core/mm/block.h:112,156`）只有 `adoptExternal` 会写，Tiles 既不读也不写。

### 1.9 与执行计划、区域、数据块的接口

- **执行计划**：没有接口。`src/execute/exec_plan.cpp` 里没有 `tiles` / `compiled_region` / `Device` 字样；Tiles 在遍里改写图，改完之后就是普通算子。
- **区域**：Tiles 自己读 `GCGraph` 的 `Loop` / `LoopView`（`graph_regions.cpp:187`、`compiler.cpp:885`），但不用 `ControlRegions`（整个模块没有 include）；分支/循环的内建区域语义它用控制边和 LoopView 重写了一遍（后果见 2.7）。
- **数据块**：不接。`Device<T>` 是 `ForeignResourceObject` + `shared_ptr<DeviceValue>`（`module.cpp::wrapDevice`、`resident_storage.cpp`），与数据块的引用计数、固定地址、`device_` 字段是两套东西；没有 DLPack。

## 2. 实测

口径：时间都是进程内 `now()` 围住被测循环；CPU 路径 `std::nvm`/`std::fvm`，GPU 路径加 `tiles::compile` 遍或 `run<f>`。所有 CPU 侧数字 `taskset -c 3`；GPU 是 4 号卡（测量时 0 %、17 MiB）。

### 2.1 依赖链微基准与每次调用的成本

程序一：64×64 f32 的 1 / 8 / 32 个依赖逐元素算子（`y*x`、`y+b` 交替），300 步（先做一次预热调用），以及 512×512 的 8 算子版本。程序二：同一张 8 元素张量重复 1/2/3/5 个参数，函数体只有加法与求和，测每次 `run<f>` 的成本；再把它换成 5 张 100×1000 的 f32（每张 400 KB）。

| 形状 | 算子数 | CPU µs/次调用 | CPU µs/算子 | GPU µs/次调用 | GPU µs/算子 | 首次调用 ms |
|---|---|---|---|---|---|---|
| 64² | 1 | 8.7 | 8.7 | 383 | 383 | 790 |
| 64² | 8 | 24.1 | 3.0 | 375 | 47 | 757 |
| 64² | 32 | 37.5 | 1.2 | 375 | 11.7 | 770 |
| 512² | 8 | 257 | 32 | 3668 | 459 | 912 |

读法：

- CPU 侧每算子 1–3 µs（64²）到 32 µs（512²），随张量大小走，随算子数摊薄。
- GPU 侧的本底是**每次区域调用的固定成本**：1 个算子和 32 个算子都是约 375 µs。它不随算子数涨，只随参数叶子数涨（见下表）。这 375 µs 与公开 `run<>` 的 1 叶 126 µs 量级不同，因为两条路径不同（图内的 `run_preferred_resident` 有 5 个叶子，且 `retain` 与 `execute` 各调一次 `deviceInfo()`）；512² 那一行是单次运行，当时 GPU 2 上有邻居占 58 %，只作量级参考。可复现的结论是：**固定成本在"区域调用"和"叶子"上，不在"算子"上**。
- 首次调用 0.76–0.91 s 是驱动初始化 + NVRTC，不是算子时间（2.5 拆开）。

**每次调用的成本随叶子数走，不随算子数走。** 同一张 8 元素张量重复的 1/2/3/5 个参数、函数体只有加法与求和：

| 每次 `run<f>` 调用 | 1 叶 | 2 叶 | 3 叶 | 5 叶 | 5 叶 × 400 KB（共 2 MB） |
|---|---|---|---|---|---|
| µs/次 | 126 | 196 | 263 | 284–450 | 4930 |

读法：约 60 µs 固定 + 每叶 60–80 µs；叶子变大后按 ~0.5 GB/s 计（2 MB 入 + 0.4 MB 出 ≈ 4.9 ms）。原因是 `run` / 区域传输**逐叶子**走 `transferTree`（`tree_transfer.cpp:116-123`）→ 每个叶子一次 `uploadValue`（`cuda.cpp:415-449`）：新建 `Resources`（新 stream）、从 pinned 池取块、`memcpy`、异步 H2D，然后**对该叶子单独 `cuStreamSynchronize`**。作为对照，`benchmark` 与 `submitProgram` 走的是批量路径（`DeviceRun::upload`）：5 个叶子共 563,880 B 一次上传 0.061 ms、一次同步（2.4），同样的字节快 20 倍以上。

C2 前向区域有 5 个叶子（563,880 B），按上表是 **1.1–1.4 ms/次**（机器忙、~0.5 GB/s 时；安静时可到 ~1 GB/s，约 0.6 ms）；而同一前向在 CPU 上是 **0.25–0.36 ms/次**（同一程序里 2000 次调用，三次取最小：355/257/248 µs）。也就是说：在 C2 的尺寸上，**下放前向本身就要比 CPU 慢 1.5–5 倍**，省下的 GEMM 时间远不够付传输。

### 2.2 C2 的真实训练步（动态形状）

`camel train.cml ... tiles::compile std::jgir`：

- `tiles:run_preferred_resident` 0 个、`tiles:retain_preferred` 0 个、`tiles.region` 0 个。
- 每步算子（图口径）：`logits` 5 + `logits.fwd` 5 + `logits.pb` 10 + `loss` 2 + `grad(loss)` 3 + `nn:adam` 1 + `take` 2 = **28 个，下放 0 个**。
- 50 步训练循环最小 1.20 ms/步（纯 CPU）；加 `tiles::compile` 最小 1.36 ms/步（图完全一样，差异是噪声）。`tiles::compile` 遍本身 0.31 ms，纯属白跑。

### 2.3 静态形状的 C2 步

同一个 MLP（784-128-10、batch 50、softmax 交叉熵、Adam），只是把形状写成静态的（`as Tensor<f32, const [50, 784]>` 等）。

| 项 | 数值 | 来源 |
|---|---|---|
| 每步算子总数 | 24（`loss` 7 + `grad(loss)` 17），另有 `nn:adam` 1 个原生算子 | `std::jgir` |
| 下放到 GPU | 10（`loss` 前向 5 + `grad(loss)` 里重算的前向 5） | `std::jgir` 区域图 |
| 主机→设备 | 10 次（5 个输入 × 2 个区域），1,127,760 B（按输入张量尺寸求和，每次区域调用 563,880 B） | `regions` 的 uploads |
| 设备→主机 | 5 次，57,200 B（两个区域被主机消费的 5 个输出） | `regions` 的 downloads |
| 执行提交 | 2 次；前向区域 4 个 kernel（`inspect` 实测），反向区域同样的 5 算子链、4 个输出，≥4 个 | `inspect` |
| 同步点 | 7 个等待（2 次执行完成 + 5 次下载完成），另有 10 次 pinned staging 拷贝 | `cuda.cpp:410,516` |
| 步时间（CPU） | 2.166 ms（5 次最小；3 步预热后 200–300 步） | 进程内计时 |
| 步时间（GPU） | 2.228 ms（同上） | 进程内计时 |
| 其中前向一次（CPU） | 0.25–0.36 ms（5 个算子，单独测得） | 进程内计时，2000 次 |
| 其中前向一次（GPU，5 叶） | 0.6–1.4 ms（按 2.1 的每叶/字节成本；安静时 ~1 GB/s，忙时 ~0.5 GB/s） | 2.1 表 |
| 设备不可见时 | 1.5–2.1 s/步（1/3/6 步的边际 2.14 s/步） | 进程内计时 |

两条路径的损失累加逐位一致（同一 20 步的对照：两边都打印 `total=4240.089805`）——GPU 只做前向，其余完全相同，所以这不是数值差异，是**没有收益**。同一次对照里 CPU 2.69 ms/步、GPU 4.89 ms/步（当时机器更忙，未做 5 次取最小）：GPU 路径对主机/驱动争用比 CPU 路径敏感得多。把 2.1 的传输模型代进来正好对上——忙时 1.1 MB/步的逐叶传输要 ~2.2 ms，安静时（~1 GB/s）只要 ~1.1 ms，这就是"最小 2.228"与"忙时 4.89"两个数之间的全部差别。

### 2.4 单个前向区域的主机/设备分解

`benchmark<logits>((m, x))`（5 个输入、1 个输出、4 个 kernel）：

| 字段 | 数值 |
|---|---|
| `kernels` / `values` | 4 / 10 |
| `logical_bytes` / `allocated_bytes` | 644,680 / 589,480 |
| `upload_host_ms`（5 个张量） | 0.061 ms |
| `device_median_ms`（p50 / p90） | 0.0378 / 0.0424 ms |
| `download_host_ms` | 0.017 ms |
| `first_upload_execute_download_host_ms` | 0.140 ms |
| `compile_load_host_ms` | 292.9 ms（冷） |
| `initialization_host_ms` | 716.6 ms |
| `median_speedup`（相对不融合） | 1.047×（4 vs 5 kernel，融合等于没帮上忙） |
| 正确性 | 500/500 位相同 |

即：在这条**批量**路径里，首次调用 0.140 ms 中设备只占 27 %（0.0378 / 0.140），主机上传/下载/准备占大头。注意这不是区域实际走的路径：区域与 `run` 是逐叶子传输（2.1），同样的 563,880 B 要 1.1–1.4 ms，是这里的 10–20 倍。**同一个引擎，两条传输路径差一个数量级**——这是 H47 发现的最便宜的一处性能缺陷。

### 2.5 编译启动的阶段拆分

`--time-phases`，静态步（steps=1，GPU 路径）：

| 阶段 | ms |
|---|---|
| startup（含 context / tiles 模块加载） | 3.77 |
| parse | 0.72 |
| compile（gct 1.95、gir 1.24、declare 0.15） | 3.36 |
| encode | 0.29 |
| pass `std::macro` | 0.30 |
| pass `tiles::compile` | **1.34** |
| pass `std::nvm`（CUDA 初始化 + NVRTC + 1 步） | **703.5** |
| teardown | 0.02 |
| 总计 | 713.6 |

C2 动态（2 步）总计 46.6 ms：parse 1.17、compile 4.92、encode 0.57、macro 0.42、`tiles::compile` 0.31、nvm 35.4。

首调用探针（同一进程内两个不同的区域函数）：

| 事件 | 时间 |
|---|---|
| 第一个区域首次调用（驱动初始化 + NVRTC） | 1.29–2.61 s（3 次） |
| 同一函数第二次 | 0.19–0.21 ms |
| **另一个**区域函数首次（只有 NVRTC） | 35–42 ms |
| 它第二次 | 0.19–0.20 ms |

结论：Tiles 自己的选择/调度/代码生成在遍里只有 1.3 ms；启动成本几乎全在 CUDA 驱动初始化（0.7–2.5 s，受邻居影响很大）和 NVRTC（简单模块 35–42 ms，4-kernel 前向 292 ms）。**没有磁盘缓存，所以每个新进程都要重付一遍。**

### 2.6 没测到的，以及为什么

- 外部报告的 73 s 启动、0.66 s/步、batch 无关性、优化器 0.19 s/步：没有原始程序，且是 v0.2.14；本机是 v0.2.24，C2 步只有 1.2–2.2 ms，量级完全不同。**不能拿报告的数字当本版本的基线，也不能反过来证伪它。**
- 3090 上的 batch 无关性：本机 CPU 步本身只有 1–2 ms，且负载 85–90，做 batch 1/8/128 的对比会被噪声淹没；没有做。
- PyTorch 对照：任务书禁止跑 PyTorch 重测试，没做。
- **每次调用的成本里，"准备"与"传输"各占多少没有拆开**：`run<>` 的 126 µs–4.9 ms 是 `prepare`（特化 + 调度 + 存储规划）与逐叶传输之和，`benchmark` 只报传输和设备时间。这正是 H48 要先加计数器的原因；本报告只能给上界与下界。
- 73 s 的拆解需要报告方的程序；本报告只能给本版本的等价分解（2.5）。

### 2.7 区域分析的三个探针

1. **标量字面量**：`x * 1.5 + 0.25`（`1.5`/`0.25` 是 f64 DATA）→ 两个算子都被判 `scalar_tensor_operand`，整个函数 0 区域；改成张量操作数 `x * x + b` 立刻得到 1 个区域（5 上传/1 下载）。所以"逐元素 MLP 里有标量常数"会整段掉出 GPU。
2. **臂里的区域**：`if flag then { let y = x * b; return exp(y) } else { return x }`。`x*b` 有控制边被排除；`exp(y)` 没有直接控制边，**被划成了区域**（jgir 里 `choose/tiles.region/0`）。今天没有语义错误：上传节点的输入也被条件执行，`flag=false` 时不跑（实测结果正确）。但区域分析里没有 Arm 的概念，这一段完全依赖运行时的条件传播，且没有任何测试覆盖。
3. **自动微分的类型**：`grad(loss)` 里的 12 个反向算子输出类型全是 `Tensor`（无形状）；`tensor:sum_to` 虽然在准入表里，也因 `unresolved_type` 选不中。显式 `inspect<derivative>` 会失败：C2 的损失报 `operator 'tensor:cast' needs a statically known f32 tensor result`，带 relu 的 MSE 报 `tensor:gt needs ...`；把 relu 去掉后，整个"前向 + 反向"能编成**一个 plan：31 个值、19 个 kernel**。也就是说：**降级能力有，区域选择没有。**

## 3. 差距：五个假设与五个请求

外部报告没有给"假设/请求"编号，下面按 `perf-report-2026-10-21.md` 第 5–11 行的七条事实归纳出五个假设（H1–H5）与五个请求（R1–R5），归纳方式写在每条里。

### H1 "每步耗时与 batch 几乎无关" ⇒ 主要计算在 CPU 单线程逐算子

- **现在如何**：C2 动态步 0 下放；静态步 10/24 且只下放前向；反向、损失、Adam、`take` 全在 CPU。
- **差多少**：batch 无关性的直接原因（逐算子主机成本 + 反向/优化器在 CPU）一条没变；静态步 GPU 比 CPU 慢 3 %（最小值的比较；机器忙时慢得更多，见 2.3）。
- **在哪**：`graph_regions.cpp:42-71`（准入表）、`compiler.cpp:885-906`（循环只 For）、`modules/autodiff/pullback.cpp`（VJP 不赋静态类型）。

### H2 "单算子约 70 µs，与张量大小无关"

- **现在如何**：CPU 路径 1–32 µs/算子（随张量大小）；GPU 路径的固定成本按**叶子**走：每叶 60–80 µs（32 B 时）+ 按 ~0.5 GB/s 计的字节成本，与算子数无关；C2 的 5 叶前向是 0.6–1.4 ms/次，CPU 同一前向 0.25–0.36 ms/次。
- **差多少**：固定成本从"每算子"变成"每区域调用"，但 C2 每步仍有 2 次这样的调用，且 15 次传输/7 个同步点。
- **在哪**：`cuda.cpp:514-516`（每次 prepare + wait）、`regions.cpp:136-197`（每次全量上传）。

### H3 "`mm` 链每轮多约 90 µs（≈ 单线程 128³ GEMM）"

- **现在如何**：CPU 128³ GEMM 实测 52–54 µs；`matmul` 能进区域，但 `matmul_grad_lhs/rhs` 不在准入表（`compiler.cpp:806-841` 有降级），所以**反向 GEMM 一定在 CPU**。C2 的整个前向（含两个 GEMM）在 CPU 上 0.25–0.36 ms/次，这就是 GPU 最多能省的部分。
- **差多少**：与报告同量级（53 vs 90 µs，机器不同）；但"反向 GEMM 上 GPU"是 0。
- **在哪**：`graph_regions.cpp:42`（表）vs `compiler.cpp:806`（降级）。

### H4 "优化器每步约 0.19 s（约 40 叶子 × 3–5 个逐元素算子）"

- **现在如何**：`nn:adam` 是一个原生算子，整棵树在 CPU 的一个节点里；Tiles 看不到逐叶子更新，也没有多张量融合。
- **差多少**：完全没有覆盖；这是 H50 的"优化器对整棵参数树做多张量更新"。
- **在哪**：`modules/nn/optim.cpp`（原生实现）、`graph_regions.cpp`（准入表里没有优化器算子）。

### H5 "编译启动约 73 s"

- **现在如何**：本机第一次用 GPU 0.7–1.3 s，之后每模块 35–42 ms（2.5）。
- **差多少**：无法解释 73 s；可能是 v0.2.14 上"很多函数/形状各编译一次"，或把别的开销算了进去。需要报告方的原始程序才能对上。
- **在哪**：`codegen_cache.cpp:26` / `cuda_backend.cpp:272-338`（只有内存缓存，没有磁盘缓存）。

### R1 gather/scatter

- **现在如何**：`tensor:take` 存在，但不在准入表，索引是 int64 → dtype 不支持；scatter-add 没有。
- **差多少**：v0.2.16 起有 `take`（报告已知），但 Tiles 用不上。
- **在哪**：`modules/tiles/include/tiles/dtype.h`、`graph_regions.cpp:42`。

### R2 训练步的图捕获（CUDA Graph）

- **现在如何**：没有。每次调用一条新 stream、逐个 `cuLaunchKernel`、一次 `cuStreamSynchronize`。
- **差多少**：C2 每步 2 个区域、合计约 8 个 kernel（前向 4 个实测，反向同链 ≥4），捕获的收益有限；报告的扩散模型步才是目标。
- **在哪**：`cuda_submission.cpp`、`cuda.cpp:285-320`。

### R3 异步下发与显存池

- **现在如何**：池有（64 MiB/32），异步没有（公共调用全同步）。
- **差多少**：池容量比报告场景（0.4–2 GB）小一个量级；异步需要先有"设备值作为普通值"（G3）。
- **在哪**：`cuda_backend.h:121-122`、`cuda.cpp:514-516`。

### R4 常用融合

- **现在如何**：有逐元素融合、行区域、归约 epilogue（`schedule.cpp`、`README.md:453-482`），但只在 region 内；对 C2 前向 4 个 kernel 的加速比 1.047×。
- **差多少**：跨 region 融合、把融合写成规则（设计 G4）都没有。
- **在哪**：`schedule.cpp`（融合）、`region_outline.cpp`（跨 region 不做）。

### R5 `run_device` 的边界与同步说明

- **现在如何**：`executeResident` 等待（`cuda.cpp:516`），`run_device` 返回的设备值再被下载时又等一次；文档没有一页说清"什么时候同步、什么时候只入队"。
- **差多少**：语义要随 `#gpu` 重新定义（设计已定删除 `run_device`）。
- **在哪**：`cuda.cpp:410,516`、`modules/tiles/README.md:22-236`（API 一节）。

## 4. 过时、依赖旧图形式或与设计原则冲突的地方

按"挡 H48 / 挡 H49 / 表面"分组。行号都是本分支的。

### 挡 H48（先能看见）

1. **没有每算子/每 kernel 的设备时间与主机时间，没有每步 kernel 数、传输次数/字节、同步点计数。** `cuda.cpp` 只有整段的 `benchmark`；`--time-phases` 只到遍一级。这是 H48 的 G0 本体。
2. **`benchmark` 的字段没有稳定 schema 和文档**（`cuda.cpp::benchmark`），不能当基线；跨版本名字已经变过。
3. **没有"主机上对张量逐元素循环"的提示**（H48 第 1 条）。
4. **CPU 路径没有同一套计数器**：CPU 侧没有 per-op 时间/次数，无法和 GPU 路径同表比较。

### 挡 H49（G1–G3）

5. **区域选择是类型驱动的**：`graph_regions.cpp:97-99` 要求静态 f32 形状，`shape()` 对 `Tensor` 返回空。动态形状的 C2 永远选不中。设计要的是按形状签名整段编译（`docs/design/gpu/README.cn.md` §3/G3）。
6. **自动微分的 VJP 节点输出类型是 `Tensor`**（无形状），区域分析全部看不见；实测 `sum_to`、`matmul_grad_*` 都在 `grad(loss)` 里且类型是 `Tensor`。文件：`modules/autodiff/pullback.cpp`（建 VJP 节点处没有赋静态类型）。
7. **准入表落后于降级**：11 个族（`cast_like`、`broadcast_like`、`expand_axis`、`ones_like`、`zeros_like`、`matmul_grad_lhs`、`matmul_grad_rhs`、`transpose`、`permute`、`slice`、`reshape`）compiler 能降但表里没有。`graph_regions.cpp:42-71` vs `compiler.cpp:779-871`。
8. **dtype 只有 f32/f64**（`modules/tiles/include/tiles/dtype.h`）：bool（`gt`）、int64（索引、标签）进不了编译区域。`Tensor<i64, const [50]>` 类型系统接受，Tiles 入口拒绝（"tiles currently requires f32 tensors"）。C2 的分类标签因此在任何情况下都进不了区域。
9. **私有 `Device<T>` / 驻留存储与数据块 `device_` / DLPack 是两套**（`module.cpp::wrapDevice`、`resident_storage.cpp`、`include/camel/core/mm/block.h:112,156`、`modules/tensor/dlpack.h`）。设计 G3 要的是数据块设备字段与 DLPack（`docs/design-principles.cn.md` §10.5）。
10. **`@gpu` / `run` / `run_device` / `retain_preferred` / `run_preferred_resident` 仍在公开 API**（`module.cpp:482-549`），设计已定删除；`retain_host` / `run_host_resident` 等测试用执行器也还在（`module.cpp:470-487`）。
11. **循环只接受 `LoopKind::For` + 有状态 + 静态域**（`compiler.cpp:892`）；分支只支持特化时已知的条件（`compiler.cpp:444-456`）。设计 G5 要设备上的分支与循环。
12. **`GCGraph*` 身份**：`region_outline.cpp:94` 的 `unordered_map<GCGraph*, RegionAnalysis>`、`compiler.cpp:60,78` 的 `GCGraph* function` / `active`、`compiled_region.cpp` 的锚点 `{function->program(), function->graph()}`。全模块没有 `stableId`（grep 为空），所以图重编码/复制后事实锚点与缓存都会失配——设计要求稳定身份。
13. **区域分析不认 Arm 区域**：只排除有直接控制边的节点（`graph_regions.cpp:83`）；臂内部更深的节点会被划进区域（2.7 实测 `exp` 被划出），今天靠上传节点的输入也被条件执行才没出错；`region_extract.cpp` 只有 Loop 的复制，没有 Arm 的处理，也没有测试。
14. **传输是逐叶子串行的**：每个叶子新建 `Resources`（新 stream）、从 pinned 池取块、`memcpy`、异步 H2D，再**对该叶子单独同步**（`tree_transfer.cpp:116-123`、`cuda.cpp:415-449`）。批量路径（`DeviceRun::upload`，`cuda.cpp:504-505`）5 个叶子一共 0.061 ms；逐叶路径同样字节要 0.6–1.4 ms。C2 的前向因此比 CPU 还慢 1.5–5 倍（2.1、2.3）。**这是最便宜的一处收益：先合批，再谈别的。**
15. **`deviceInfo()` 每次调用都重做**：`retainPreferredKernel` / `runPreferredResidentKernel` 每次都 `cuInit` + 查设备属性（`module.cpp:341-359`）；设备不可见时每步 10 次失败探测，把"回退"变成 1.5–2.1 s/步（2.3）。

### 表面 / 一致性

16. **设备不可见时仍然 outline**：`region_outline.cpp` 在遍阶段不做设备探测，运行时每次调用重试 `cuInit`（`cuda_backend.cpp::deviceInfo`），1.5–2.1 s/步（2.3）。应在遍阶段决定"没有设备就不 outline"，或缓存失败结果。
17. **64 MiB 设备池太小**：比 idle 上限大的块直接不缓存（`cuda_pool.cpp:119`），而报告的场景是 0.4–2 GB；池策略要按 G3 自适应。
18. **文档与代码不一致**：`modules/tiles/README.md:405` 说自动微分的 grad 函数可以 `run`，`:416` 又说控制流与不支持的导数算子还要做；`IMPLEMENTATION.md:113-118` 的空归约 `LawEmpty::Initial` 缺陷（设计原则 §7.7 要求故障）仍未修。
19. **"只支持 f32"与 bf16 降级不一致**：`modules/tiles/README.md` 与 `mixed_gemm.cpp` 的 bf16 cuBLAS（三许可下）并存，`docs/technical/ddpm-primitives.md` 已经写了 bf16 GEMM。
20. **命名**：`tiles::compile` 与设计里的 `#gpu` 编译不是一回事；`tiles:run_preferred_resident` 这类内部名字会出现在用户可见的 `std::jgir` 里。

## 6. H48 需要什么才叫得见

**今天已有**：

- `--time-phases`：parse / gct / gir / encode / 每个遍（含 `tiles::compile`）/ teardown 的墙钟和分配（`docs/technical/38_compile_pipeline_cost.md`）。
- `benchmark<f>`：`initialization_host_ms`、`compile_cache_hit`、`compile_load_host_ms`、`allocation_setup_host_ms`、`first_upload_execute_download_host_ms`、每次的 `upload_host_ms`、`device_ms`（CUDA event，p50/p90）、`download_host_ms`、正确性门。
- `inspect<f>`：`values` / `kernels` / `logical_bytes` / `allocated_bytes` / `stages` / 每阶段成员。
- `regions<f>`：区域成员、输入、输出、传输、每个被排除节点的原因。
- `std::stats`、`std::jgir`（标签里带算子 URI，可以数节点、数区域）。

**要加的，按最小改动排序**：

1. **运行时计数器**（新 `std::profile` 遍或 `tiles` 的环境开关）：每次 execute 记 `(region, launches, device_ns, host_submit_ns, prepare_ns)`；每次 upload/download 记 `(bytes, host_ns, direction, leaf_index)`；每次 wait 记一个同步点；按步聚合，输出 JSON。位置：`cuda.cpp` 的 `submitProgram` / `upload` / `downloadValue` / `executeResident`，`tree_transfer.cpp` 的逐叶循环，`cuda_submission.cpp` 的 `CompletionEvent`。
2. **每算子设备时间**：在 `schedule.cpp` 的 launch 边界插 event（每个 launch 已经有 `Program::launches`），把每 kernel 时间按 `stages.members` 摊回算子；kernel 名字进 codegen 的符号表。
3. **Tiles 内部阶段拆分**：`region_pass.cpp` / `region_outline.cpp` 里给 analyze / extract / compileTypes 各开一个 phase；`prepare` 里给 specialize / schedule / codegen / module-load 各开一个 phase。这样"编译启动"才能像 2.5 那样在进程内拆开。
4. **主机逐元素循环提示**：在 fvm/执行器的张量算子分派点计数，小张量高调用次数时打一行诊断（H48 第 1 条）。
5. **CPU 路径同一套计数器**：tensor 算子的 host 实现（或 fvm 分派点）记同样 schema，才能给出"每算子主机开销（CPU 与 GPU 分开）"。
6. **基线**：把 2.1–2.5 的表写成 `test/plans/perf` 的数字（依赖链、C2 静态步、C2 动态步），沿用 `test/tools/benchmark-tiles.py` 的口径；本报告的数值是在负载 85–90 的共享机器上取的，正式基线要在空载时重测。

**验收**：一次运行能直接打印本报告 2.3 那张表（24/10、10 次上传/5 次下载/字节数、7 个同步点、每算子主机时间），且 CPU 与 GPU 两列同 schema。
