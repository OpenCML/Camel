## 3. Item 1 — a stale commit with no conflict merges into the newest snapshot

### 3.1 What it did

`RuntimeGraphDraftSession::commit` encoded the closure, then:

```cpp
if (!detached && graphState_ != GraphState::NonExecutable &&
    context_->currentRuntimeProgram() == program_ && program_->root() == oldRuntimeRoot) {
    program_ = context_->installRuntimeProgram(committed);
} else {
    committed->setOriginal(...);   // a private program: the history forks here
    program_ = committed;
}
```

A session that another commit had overtaken (its `program_` is no longer the context's) always
took the second branch. That is correct for a session that runs a function value of an old program
(the callers that do this routinely), but it is a fork for every pass that edits the program: the
next pass starts from the fork, and the earlier work is only visible if the driver happens to
install the fork. Design 4.3.1 asks for a merge.

### 3.2 What it does

The decision is made once, up front:

```cpp
const bool installing = !detached && graphState_ != GraphState::NonExecutable &&
                        program_->root() == oldRuntimeRoot;
const Program *current = context_->currentRuntimeProgram();
const bool merging = installing && current != nullptr && current != program_ && conflicts().empty();
const Program *base = merging ? current : program_;
```

* **No conflict**: the session's graphs have the same content in `current` (that is what
  `conflicts()` says). The drafts are re-keyed to the graphs `current` holds; the work table is
  taken from `current` and the graphs the session holds and `current` does not are carried over
  (specializations the session made, and the graphs of a private program a pass made: see 8.1); the
  commit encodes on top of that program and publishes it.
* **Conflict**: unchanged — the commit stays private and hands back a program of its own;
  `commitChecked()` still throws `GraphCommitConflict`.

Publication is one compare-and-swap, not a lock:

```cpp
context_->installRuntimeProgramIfCurrent(expected, committed)   // expected == base
```

`Context::installRuntimeProgramIfCurrent` → `GCGraphManager::replaceRootIfCurrent` swaps
`current_` only while it is still `expected`. A commit that lost that race (another commit
published in between) re-checks `conflictsWithProgram(now)`: while it is still conflict-free it
remakes its table over the program that is there now, binding the versions it encoded itself
(`fresh`) and taking everything else from `now`; up to four attempts, after which it stays private.
A merge that is overtaken twice is rare enough that a retry bound is better than a spin; four is a
constant in the function, not a user-visible cap (8.2).

The function values of the graphs a commit leaves as they were are retargeted *after* publication:
they must name the program that was actually installed, which the rebase can have replaced.

### 3.3 The defect the merge exposed

The first version of the merge replaced the work table with `*current` and re-keyed only the
drafts. `test::regions` + `std::opt` (`opt.regions.regions.survive_optimization`) then failed with
`Runtime graph '__root__' has FUNC node 18 whose callee graph is not encoded`: the graphs the
session had created itself, and the graphs of the private program the region pass handed on, are
in the work table but not in `current`. They are carried over now (`const std::vector<GCGraph *>
own = work_->graphs();` before the table is replaced), and the closure walk reaches them again.
The failing case is part of the fast layer and green again.

### 3.4 Test

`test::commit_merge` (`src/passes/test/edges.cpp`) opens two sessions over one program, edits the
root in the first and an unrelated graph in the second, commits the first and then the second
(which is now stale), and prints:

```
MERGE stale=1
MERGE installed=1 first_kept=1 second_kept=1 root_edited=1
```

`installed` is `context's program == the commit`; `first_kept` compares the merged root's node
count with the version the first commit made (a merge may encode a new version of the root for the
function value it holds, so pointer identity is the wrong question); `second_kept` is its own
graph now having a different version than before the commit.

## 4. Item 2 — a graph encoded but bound into no program is released

### 4.1 Why it was not

`RuntimeGraphDraftSession::adoptGraph` binds a graph a pass encoded into the session's `work_`
table. That table is a `Program` the collector does not trace (a copy, `reserveProgram` only for
the program the commit publishes), so the graph was reachable from nothing the sweep walks: it
lived until the context ended. The handover document lists this ("encoded graphs bound to no
program live to the context end").

### 4.2 What it does

`GCGraphManager::noteUnbound(graph)` registers the graph in `graphs_` and in a second set,
`unbound_`:

* the sweep leaves the graphs of `unbound_` alone — the drafts may still reach them;
* `settle(keep)` (the pass driver calls it after every pass) clears `unbound_` and then collects,
  so a graph no program bound by the end of the pass is freed like any other;
* binding the graph in a program (`noteGraph`) or releasing it (`release`) takes it out of
  `unbound_`; `clear()` clears the set.

`settle` used to return early when it had nothing provisional to keep; it now also runs when
`unbound_` is not empty, otherwise the pass-end collection that frees those graphs would not
happen.

### 4.3 Why not `reserveProgram` for the work table

The obvious alternative — let the session reserve its work program, so that the collector sees it —
was rejected: `Engine` creates a session per gradient, so 4000 gradients would be 4000 reserved,
dense tables, and `graph_space.grad_in_a_loop` asserts `graph_peak_kb < 6000`. The set is O(the
graphs one session encoded), which is what the pass actually holds.

### 4.4 Test

`test::graph_release` (`src/passes/test/graph_release.cpp`): decodes the root, gives it a new id,
adds 20000 sync nodes, encodes it as `test$unbound` (646816 bytes), `adoptGraph`s it, collects and
prints that it is still alive; the pass then ends, `settleRuntimeGraphs` + `collectRuntimeGraphs`
run (what the driver does between passes), and the next round prints that it was freed:

```
GRAPH_RELEASE alive=1 freed=1 encoded=646816 before=2144 after=2144
```

`before`/`after` are `mm::graphSpace().usage().usedBytes` around the second collection: the graph's
646816 bytes are gone and the space is back at the size of the program.

## 5. Item 3 — `jitFnToGraph_` entries of released graphs

### 5.1 Why it was not

`FastVMSchedPass` kept `std::unordered_map<jit::JitEntryFn, GCGraph *> jitFnToGraph_` and only ever
inserted into it. Its own comment said it was sound only because nothing was freed; once the graph
space collects (H40's part 3), the version a late-compiled graph was compiled for goes away and the
entry stayed — 4000 entries for 4000 gradients, and a recycled address could make the map answer
with another graph.

### 5.2 What it does

The map's lifetime is the code's lifetime: an entry is named by the `CodeLease` of the JIT code
compiled for that version (`std::fvm`'s `CodeSpace` ranges, `leaseCode`/`compileLate`).

* `CodeLease` gained `std::function<void()> onRelease`, called from its destructor after the range
  is released.
* The map moved into a `JitGraphCache` (`byFn`, a mutex) that the leases hold through a
  `std::weak_ptr`; `attachJitEntry(graph, fn)` inserts the entry and sets the lease's `onRelease` to
  erase it.
* `jitFnToGraph(fn)` reads through the shared cache; the last lease of a version erases its entry.

`jitFnToGraph_` is gone (no alias, no second map). The `CAMEL_GC_STATS` line prints
`fvm_jit_entries=<n>` (JIT builds only).

### 5.3 Test

`graph_space.jit_entries_of_freed_versions` runs `test/cases/feat/mm/gc/graph_space_grad.cml`
(4000 gradients) under `std::jit` with `CAMEL_GC_STATS=1` and `CAMEL_GRAPH_GC_MB=1` and asserts
`0 < fvm_jit_entries < 1000`. Measured: **4000 without the fix, 306 with it**. A build without the
JIT prints no such line and the check is skipped (the JIT is x86-64 only).

## 6. Item 4 — node-level fact marks

### 6.1 What it did

A fact kind could name a node anchor, but validity was always the graph's revision
(`Dependency::Anchors`) or the revision plus a rehash of the dependency cone (`Dependency::Cone`).
`core.shape` — the shape of a node, read from that node's record alone — was a `Cone` kind, so every
rewrite of the graph recomputed every shape (`H38` §2.1.6 lists this as the O(n) `is_written_slot`
problem's cause).

### 6.2 What it does

* `Dependency::Node`: a third rule. `Stamp` holds one `NodeMark {graph, node, hash}` per anchor;
  `FactStore::stampNow` fills them, `find` compares them, and the fact is valid while they are
  equal, whatever happened to the graph's revision.
* The version of a node is `GCGraph::nodeContentHash(ref)`: FNV-1a over the node's record (kind,
  flags, reserved, slot, type), the nodes it consumes (Norm, With, Ctrl, in order) and its payload.
  Offsets are read as counts, so a node that moved to another chunk hashes the same; a node that a
  rewrite renumbered reads as changed.
* `core.shape` becomes `Dependency::Node`; `shapeCone` is deleted.
* Kind checks: a `Node` kind anchors nodes (not a graph) and needs no cone. The fact dump prints
  `"nodes": [{"graph", "node", "hash"}]`.
* `inspect --facts` prints, for a shape:
  `"stamp":{"revisions":[…],"epoch":0,"target":0,"nodes":[{"graph":"layer","node":2,"hash":"cb35b5432fc1a5d3"}]}`.

### 6.3 Why a hash and not a stored per-node mark

Design 4.4's wording is "each node records the version in which it was last changed". A stored
mark costs 8 bytes per node: a 90000-node graph (the scale programs) would grow by 720 KB, about
28 % of that graph's node space, for information the content already carries. The hash is the same
answer without the bytes; the price is that it is computed when a `Node` fact is stamped or
checked (O(record + payload) per fact, no caching) instead of read. This is a deviation from the
design's wording and is raised as Q2.

### 6.4 Test

`test::facts_node` (`src/passes/test/facts.cpp`) stores a `facttest.node` fact at the root's entry
node and a `facttest.kind` fact, adds a sync node and commits, then changes the anchored node's
slot and commits, then restores it:

```

FACTS node_version kept      // the fact about the node did not change
FACTS node_other node=valid graph=stale   // the node rule and the graph rule side by side
FACTS node_self node=stale   // the anchored node itself changed
```

## 7. Item 5 — the draft reads from the borrowed block: profiled, not done

Temporary timers around `GraphDraft::decode` and `encodeDraftGraph`, printed at exit
(`DRAFT_PROFILE`, reverted before the first commit; logs not kept, the numbers below are from the
runs).

| workload | total | decode | encode |
|---|---|---|---|
| `graph_space_grad.cml` under `std::jit` (4000 gradients, 12000 encoded graphs) | 594 ms | 8.5 ms, 8000 decodes | 26.7 ms, 12000 encodes |
| `scale_wide_8000.cml` (3 graphs, 24207 nodes) through `std::opt std::nvm` | 446 ms | 42 ms, 28 decodes | 10.7 ms, 14 encodes |

Opening and encoding are **6 %** of the gradient workload and **12 %** of the rewrite pass on a
24000-node program. A draft reads a borrowed block for at most that: the remaining 88–94 % is
parsing, the rewrites themselves and execution. The encoder is already proportional in what it
allocates — an unchanged `GCNodeChunk` is shared with the base version (`shares`), so a graph whose
one node changed allocates one chunk — and the O(n) cost that is left is the decode (which builds
the draft's node views) and the chunk comparison that finds the share.

Recommendation: do not do it. A borrowing read changes the draft's storage contract (every edit
path, `encodeDraftGraph`, the fact store's node lookups, `sameContent`), and the draft is the
component every rewrite goes through; 12 % of a pass run does not pay for it. If a future workload
shows more (a pass that commits per node rather than per graph, or a graph an order of magnitude
larger), the measurement to repeat is the two above.

## 8. Design choices

### 8.1 Carrying the session's own graphs into a merge (Q1)

A merging session may hold graphs the snapshot does not: the specializations a pass built into its
private program, and the graphs a session encoded itself. The merge carries them over, so the
published program holds them next to the snapshot's versions. Alternatives: refuse to merge when
the session holds graphs the snapshot does not (that reintroduces the fork for exactly the
pipelines the merge is for: the region pass and the rewrite passes build on a private program), or
make the pass driver install a pass's program before the next pass starts (a change of the driver's
contract, and it does not help a single pass that commits twice). See Q1.

### 8.2 Publication: compare-and-swap with a bounded retry

`replaceRootIfCurrent` is the CAS the design asks for ("one compare-and-swap instead of a lock").
A lost CAS is retried by rebuilding the table over the program that is there now, at most four
times, after which the commit stays private. The bound is a constant in `commit()`: a retry loop
without a bound can live-lock two sessions that keep publishing, and a setting for it would be a
knob nobody tunes. The retry binds only the versions the commit made (`fresh`); every other graph
of the closure is taken from the program that is there now, so a retry cannot write back a stale
version of a graph this session never read.

### 8.3 `unbound_` instead of reserving the work program

Section 4.3. A reserved program per session would be thousands of dense tables in the gradient
workload, and the graph space's peak is asserted in a plan test.

### 8.4 Node version = content hash (Q2, Q3)

Section 6.3. The hash includes the nodes the node consumes, so a rewrite that renumbers a graph
makes every node of it new. That is the conservative reading of "version of a node" and it is what
a stored mark that a rewrite bumps would say. The alternative — hash only the record, so shapes
survive renumbering — would make `Dependency::Node` mean "reads the node's record, not the nodes it
consumes", which is true of `core.shape` and not of a kind that reads its inputs' types. Q3.

### 8.5 Where the JIT map lives

`JitGraphCache` is a `shared_ptr` held by the pass and `weak_ptr`s by its leases: the pass may end
before the code does (`RunScope` keeps the code alive for the run), and the cache must die with
whichever comes last, not with the pass. The alternative — clearing the map in `apply` — loses the
entries of code that is still leased, and the interpreter finds the graph of an entry through this
map.

### 8.6 The changes in the graph-store area (Q4)

README §5 says the 施工方 must not change the graph-store area (`draft_session.cpp`,
`program.cpp`, `graph.cpp/.h`, `context`) without raising it first. Items 1–3 cannot be done
anywhere else: the merge, the unbound set and the publication CAS are `RuntimeGraphDraftSession`
and `GCGraphManager` changes. They are the ones in this report, kept as small as the invariants
allow (no change to `Program`'s table semantics, `Program::bind`, the closure walk or the encoder);
the lane is raised as Q4 for the coordinator to confirm.

### 8.7 No compatibility layers

`jitFnToGraph_` is deleted, `core.shape`'s `shapeCone` is deleted, and no new name is an alias of an
old one.

## 11. Self-check (README §2)

   `Dependency`, never on a graph/operator/module name.
2. **No second mechanism.** `noteUnbound` extends the manager's existing registry and sweep; the

   the retry bound in 8.2, which is a livelock guard, not a capacity.
5. **No ad-hoc semantics.** Everything here is technical (this section and section 8); the design
   questions are Q1–Q4, skipped where they block nothing.
6. **Expectations were not bent to pass.** The three changes are listed line by line in section 9
   with their cause; `MERGE ... root_edited` was corrected after the printed line's meaning was

8. **Every back end.** The runtime changes sit under every scheduler; the JIT change is inside

## 12. Open questions

### Q1: does a merge carry the graphs the session holds and the snapshot does not?

Example: the region pass builds specialization `g8` in a private program; a later `std::opt`
session over that program edits the root and commits. `g8` is in the session's work table, the
context's program has no `g8`, and the root's FUNC node refers to it.
(a) the merge publishes the snapshot plus `g8` (what this branch does);
(b) the commit refuses to merge (stays private) because the session is not a subset of the
snapshot;
(c) the pass driver installs each pass's program before the next pass starts.
Proposal: (a). (b) turns every rewrite of a private program back into a fork, and (c) is a driver
contract change that does not cover a pass that commits twice. The graphs carried over are the ones
the published program's graphs refer to, so the published program is closed.
Impact: the semantics of design 4.3.1 for a session that is not a subset of the snapshot, and
whether items 1 and 2 interact with the 丙 lane's driver.

### Q2: a node's version is a hash of its content, not a stored mark

Example: `docs/design/graph-store` 4.4 says a node records the version it was last changed in.
This branch computes `GCGraph::nodeContentHash(node)` when a fact is stamped or checked and stores
no per-node mark.
Proposal: keep the hash and amend 4.4 to say the version of a node is a hash of its content;
nothing is stored per node. A stored 32/64-bit mark costs 8 bytes per node — 720 KB on a 90000-node
graph, about 28 % of its node space — for the same information.
Impact: the design text, and any later work that wants to compare node versions without hashing
(a cache could be added without changing the rule).

### Q3: does a node's version include the nodes it consumes?

Example: `std::opt` rewrites `main` in place and renumbers its nodes. With the consumed nodes in the
hash, no node of `main` keeps its version (`main valid=0 stale=11`); without them, the shapes of
nodes whose record did not change would stay valid across the renumbering.
Proposal: keep them. A fact kind that reads its inputs' types is a real case, and such a kind must
use `Dependency::Anchors`/`Cone` if the rule does not cover the inputs. Dropping them would make
`Dependency::Node` mean "reads this node's record only, not the nodes it consumes", which is a
weaker contract to state in one sentence than the hash.
Impact: how much the node rule buys in a renumbering rewrite (the measurement is in 6.4 and 9), and
the `is_written_slot` node cache H38 §2.1.6 wants: that cache is per pass, not a fact, and this
rule does not replace it.

### Q4: items 1–3 change the graph-store area; is that lane mine?

Example: README §5 tells the 施工方 not to change the graph-store area and to raise it first; this
branch changes `src/runtime/draft_session.cpp`, `src/runtime/program.cpp`,
`src/runtime/graph.cpp/.h` and `src/core/context/context.cpp` (8.6).
Proposal: accept them for H39 — the three items are definitions of the store's own debts (the
handover document names them), and each change is confined to the publication/unbound/cache paths.
Impact: review and merge order with the 丙 lane; if the coordinator prefers, items 1–3 can be moved
to that lane and this branch keeps items 4 and 5.

### Q5: should every build print `fvm_jit_entries`?

Example: item 3's plan test asserts a bound on `fvm_jit_entries`, which only a JIT build prints;
on a build without the JIT the line is absent and the test asserts nothing.
Proposal: leave it (the JIT is x86-64 only, and a `0` from a build without a JIT would be a lie).
Impact: the test is a no-op on other architectures; a real check there would need a different
observable.

* **The commit still re-encodes every graph the session created**: a session's specialization is
  encoded once by `adoptGraph` and again by the commit's copy of it, and the encoded original waits
  for the pass's end (item 2) instead of being freed when the commit replaces it. Making the commit
  adopt the session's encoding when it is unchanged (`sameContent`) is the next step; it needs the
  revision/identity bookkeeping the commit already does for adopted function values.
* **`GCGraphManager::replaceRoot` is still O(graphs) per install** and the work table is still
  copied per commit (the A2 handover's "what is left"). Neither was touched.
* **The closure walk** is still the pass's dominant cost in `std::opt::inline` (A2's note); the
  merge does not add to it (it reuses or invalidates the cache exactly as a private commit did).
* **`nodeContentHash` is not cached**: a `Node` fact rehashes its node on every `find`. Cheap for a
  shape (a record and a few payload words); a kind that stores many node marks would want the hash
  in the draft.
* **The GC stress plans** were not run (they are out of the fast layer's scope by the rules of this
  task).
