### 1.5 这不是"多出来的工作"：同类构建之间的布局差异本身就有几个百分点

本分支的改动（多状态判定与 `std::cpp` 的一条算子规则）对这三个程序的**执行**没有一行会被执行到：benchmark 里没有多状态循环，`identity()` 只在 `std::cpp` 里用。但它的构建让同样的程序变成了：

| 程序 | 8c97e968 | 本分支最终 | 变化 |
|---|---|---|---|
| map_chain nvm | 18.06 ms | 17.26 ms | −4.4% |
| alloc_small nvm | 175.75 ms | 169.93 ms | −3.3% |

把两个构建的测量顺序反过来再测（5 轮 × 10 次）得到同样的方向（map_chain 17.33 vs 18.09，alloc_small 168.0 vs 175.4），所以不是测量漂移，是二进制本身。也就是说：**在这套构建上，不改变任何被执行的代码、只让代码/数据的地址变化，就能让 nvm 的时间动 4%**；`fb8f6e4e` 那次 +20%（filter 微基准）是同一类效应落在更敏感的位置上。

结论（如实写）：

- 追到的第一个变慢点是 `fb8f6e4e`（H11-1-deep 里"用显式栈做比较/打印/命名"的重构），它没有改执行路径、图不变、fvm/jit 不变、只在数据相关分支的解释执行上出现；单独构建复现，全新构建复现，入口对齐无效。按现有证据，它是**代码/数据布局引起的分支预测类效应**，不是语义缺陷，也不是 H17 加的工作。
- 因此**没有可以在"小程序路径"上实施的源码修复**：这条路径没有多做什么。硬要"修"，只能做编译器/链接布局层面的操作（固定函数顺序、固定加载地址之类），那是构建系统的决定，不属于本任务，也不该由一次交接偷偷引入。
- 可采取的行动是测量纪律：nvm/fvm/jit 的**执行**时间不要跨构建比较（4%–20% 可以由无关改动造成）；同一构建内的比较、与时间无关的列（字节/节点）不受影响。`docs/performance/graph-store-baseline.md` 已在本次按这个口径补了一节复核（见第 6 节）。

## 2. 优先级 2：循环状态的原地写扩展到多个状态

### 2.1 判据（逐状态，与 `t = t->relu` 同一条）

`Builder::markLoopStateInPlace` 现在先取出 body 的返回值，再对**每个状态**独立判断：

1. body 的返回值在单状态时是那个 `:struct/append_arr` 调用本身；多状态时是一个 **Tuple 的 FILL**，其 With 输入是计算出来的分量，载荷 `GCFillBody::slots()` 说明每个输入填的是元组的第几个位置。写成常量的分量不占 With 输入：`(xs->append<7>, 0)` 在 `std::gir` 里是 With 只有 append 一个输入的 FILL，第二个分量在 Norm 的 `(null, 0)` 模板里，因此它没有可改写的 append。
2. 该状态的下一个值必须正好是 `state->append<v>`：Norm 输入只有一个，且那个节点是该状态的形参端口（按端口名 `loopStateName(j)` 匹配），形参在 body 里的使用次数正好 1（Norm + With 合计）。
3. 该状态的首值是字面量（`DATA` 或 `FILL`）且类型是数组。
4. `__append_owned__` / `__copy_arr__` 能以相同实参类型解析。

每个满足条件的状态各自做两件事：把它的首值换成 `:struct/copy_arr`（一次私有拷贝），把它的 append 节点重定向为 `:struct/append_arr_owned`。**不影响其他状态**：`loop xs = [0], rounds = 0 …` 只改写 `xs`，`rounds` 保持普通更新；`loop rounds = 0, xs = [0] …` 改写的是第二个状态，所以规则不是"只认状态 0"。`k == 1` 的路径与 H17b 完全一样（不额外分配 vector）。

### 2.2 分配证据

`test/cases/loops/state_in_place.cml` 追加了三个会改写的多状态形状与两个对照，`std::mem::buffers()` 在每次操作前后各读一次（`nvm`/`fvm`/`jit`/`prl` 四个后端输出相同，见第 3 节）：

```
200 200 1 199
0 7 0 7 3 0 7
6 1 0 5
200 0 7 199 200 0 7 199
200 0 7 200 10 8
200 0 7 199 200 7 199
1 1 2 199 199
200 0 7 0 1
```

- 第 4 行 `200 0 7 199 200 0 7 199`：`growCounted(200)`（数组在状态 0、计数器在状态 1）与 `countAndGrow(200)`（数组在状态 1）各只多 **1** 个 buffer——都只拷贝了数组状态；计数器没有被当成数组，也没有被跳过。
- 第 5 行：`growBoth(200)` 两个状态都可 append，多 **2** 个 buffer，`xs[0] == 0`、`ys[0] == 10`（`[0]`/`[10]` 两个字面量都没被改写）。
- 第 6 行：`growCountedFrom([0], 200)` 的数组来自形参（循环不拥有）→ **199**；`growAndPeek(200)` 的 body 里还读了 `len(xs)`（形参使用次数 2）→ **199**。
- 第 7 行按顺序是五段分配数：`growCounted`、`countAndGrow`、`growBoth`、`growCountedFrom`、`growAndPeek` → **1 1 2 199 199**。
- 第 8 行：`growConst(200)` 的第二个状态的下一值是常量 `0`（不是 append，也没有可改写的节点），第一个状态仍然只多 **1** 个 buffer，结果 `200 0 7 0 1`——常量分量没有干扰另一个状态的判定。

`std::gir` 的结构证据：`growCounted`、`countAndGrow` 各有 1 个 `:struct/append_arr_owned` 与 1 个 `:struct/copy_arr`（copy 落在各自数组字面量的首值上，第二个函数的是状态 1）；`growBoth` 有 2 个 owned append 与 2 个 copy；`growCountedFrom`、`growAndPeek` 仍是 `:struct/append_arr`（无 copy）。

### 2.3 连带改动（保持"三步同步"）

- **反向规则**：`:struct/append_arr_owned` 的 VJP 规则没有改（`appendArrayVjp` 只看输出的梯度，按算子级别生效，与状态个数无关）。手工验证：对一个多状态原地写的循环求梯度（`xs` 从 `[0.0]` 开始 append `w`，取 `xs[0] + xs[1]`）得到 1.0，与语义一致。
- **C++ 转译**：`:struct/append_arr_owned` 原有的 `append` 映射继续有效；但 H17 插入的 `:struct/copy_arr` 在 `std::cpp` 里**没有规则**——任何被原地改写的循环（包括 H17b 就已覆盖的单状态）一进 `std::cpp` 就被拒绝。本次补上规则：`:struct/copy_arr` → `identity()`。理由是独立的：转译后端里的 `Array` 是值，`rt::append` 按值收数组、块被别人共享时复制、独占时原地写，所以这次"私有拷贝"在这个后端无事可做，值与解释器相同。新增 `test/cases/trans/cpp/loop_state_in_place.cml`（单状态 `grow`/`gather` + 四个多状态形状，含常量分量）并加进 `test/tools/cppexec/expect.txt`，由 `feat/trans/cpp.plan.toml` 的 `agree_with_fvm` 实际编译运行、与 fvm 输出比对。
- **收集 pass 的拒绝**：`test::loop_collect` 仍然拒绝（body 里出现 `:struct/append_arr_owned` 就拒绝，与状态个数无关）。用一个只含多状态原地写循环的程序直接跑 `test::loop_collect`（需要 `CAMEL_ENABLE_TEST_PASSES=1`）复现了同一条信息：`test::loop_collect cannot collect a loop whose state is written in place: every tape entry would be the same final array`。
- 私有拷贝与字面量私有性都保留：每个被改写的状态各自一次拷贝，`grow` 第二次调用仍从 `[0]` 开始（第 2 行）。

## 5. 未决问题（请作者裁决；没有写进任何文档）

1. **多状态改写只覆盖"body 直接返回那个元组 FILL"的形状**。如果 body 写成 `let r = (xs->append<7>, n + 1) return r`，返回值是一个名字，不是 FILL，就不改写（保守）。要不要扩展到"名字指向的元组"或"调用返回的元组"？
2. **收集 pass 的拒绝是硬错误**：一个需要磁带、又原地写数组的循环会被当成编译器内部错误（`RuntimeDiag::PassInternalError`）拒绝，程序本身是合法的。是否应改为"回退到复制 append，使微分仍能进行"，还是保持拒绝（H17b 的原始选择）？这关系到 `grad` 能否穿过这类循环。
3. **测量口径**：nvm/fvm/jit 的执行时间在同类构建之间会有 4%–20% 的布局噪声（1.5）。是否需要在构建层面固定布局（例如函数分段 + 确定性排序），还是把"执行时间不跨构建比较"写成基线文档的规则？本次按后一种处理，只更正了文档。
4. **1.6 的残留**：`map_chain` 的 fvm/jit 从 base 到 head 还有 +9%/+6%，`map_arr` 却是平的。是否值得在 H18 用一个构建、按构造拆开再查（tuple 创建、`string(int)`、`map` 的元素调用各占多少）？
