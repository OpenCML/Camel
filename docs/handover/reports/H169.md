## 0. 结论

- H159 看到的那条红是真的，而且它报出的三个名字**本身也已经过期**：在 `6755585c8` 上
  `std::opt` 实际编译的库模块是 **`rules, graph, math, tensor`** 四个，不是 `rules, graph, math`。
  H144 在 09:05 钉死 `("rules", "math")` 时是对的；09:32 H141 把 `graph` 变成声明模块
  （`stdlib/graph.cml`），10:12 H151 又把 `tensor` 变成声明模块（`stdlib/tensor.cml`）。名单在
  27 分钟后过期，67 分钟后又过期；H162 补成三个名字（协调者随后在 `d729691df` 补上 `tensor`）仍然
  只是把下一次过期推后。
- **来路**：`stdlib/rules.cml:11-14` 显式 `import { Program, Node, constant } from graph`、
  `{ abs, trunc } from math`、`{ Tensor } from tensor`；`std::opt` 的代数步按 H100 走
  `rules::simplify`，`rules` 作为"遍的工具程序"编译时，每个**有 Camel 声明文件**的导入模块都被
  编译到 Declared（`gct` 阶段）。`graph` 没有注册任何遍，`std::opt` 也没有请求 `graph` 的遍，所以
  不是"`std::opt` 需要一个由 `graph` 注册的遍"；它是"`rules` 真实地导入了 `graph` 的名字"叠加
  "声明模块在导入时急切编译"。
- **哪个世界：依赖是 intended，多出来的编译是 migration 的真实成本。** `rules` 确实命名
  `graph` 的 `Program` / `Node` / `constant`，不能删这个 import；但 `graph.cml` 被解析一遍并不是
  `rules` 类型检查所必需——把安装里的 `graph.cml` 拿掉，`std::opt` 仍编译通过，`std::jgir` 输出
  逐字节相同，模块数 5→4。**`graph` 一次 `std::opt` 的中位数是 0.844 ms**（parse 0.395、gct 0.247、
  declare 0.197；61 轮，p10 0.796、p90 0.931）。这是 H141 把 `graph` 放进急切声明路径的收费，不是
  `std::opt` 的语义依赖；要不要退掉它是 H142 的 Q2（惰性声明，改动"何时加载声明/何时报错"），本任务
  不替作者决定，也不删 `rules.cml` 的 import。
- **修法**：`bench.py` 不再保存库模块名单。库模块由两个事实派生：阶段树证明它是遍加载的
  （`library` 阶段本身，或在该库的 `gct` 阶段内编译），并且它以自己的声明命名自己
  （`stdlib/<name>.cml` 写着 `module <name>`）。`check` 断言"数到的库模块集合 == 阶段树证明的集合"、
  "每个库模块都有自己的声明"、`passes` 仍真的加载了库；并把每个库模块的 parse/gct/declare/body
  自身时间打出来、写进 `results.md` 的新表。没有把成本改名成期望值：四个库模块和 `graph` 的
  0.84 ms 都在输出里。
- **验收**：`compile_bench.smoke` 绿（596.67 ms）；同一次主机计划 `smoke + feat/opt + feat/trans +
  compile_bench` **765/765 通过，0 失败**（构建 20.3 s、计划 7.9 s、`-Jobs 8`）。

## 1. 来路：哪条 import、哪个遍、哪次模块编译

### 1.1 阶段报告说的

十行、无 import 的程序（`/tmp/h169_opt.cml`，`square` + `main`），只跑 `std::opt std::null`：

```text
CAMEL_TIME_PHASES=/tmp/h169.json camel /tmp/h169_opt.cml std::opt std::null
counters: {'ast.nodes': 9833, 'gct.nodes': 5717, 'graph.nodes': 12, 'modules': 5}

pass:std::opt
  resolve:rules
  parse:rules
  gct:rules
    cmo_load:graph  cmo_load:math  cmo_load:rewrite  cmo_load:tensor
    parse:graph    gct:graph    declare:graph
    parse:math     gct:math     declare:math
    parse:tensor   gct:tensor   declare:tensor
  library:rules
```

`counters.modules` 的 5 = 程序自己的 `main` + 库的 `rules` + `rules` 导入的 `graph`、`math`、
`tensor`。`rewrite` 只有 `cmo_load`，没有 `parse`/`gct`/`declare`，因为它没有
`stdlib/rewrite.cml`（只在 C++ 里注册）——这一点正是派生规则要用的：**没有声明文件的导入不是
模块编译，不该出现在库模块表里**。

### 1.2 代码路径

1. `src/execute/pass.cpp:1387` 的 `resolvePassWithModule`：`std::opt` 的代数步通过
   `applyRegisteredPass("std::opt::algebra")` 走到 `rules::simplify`（H100 §1.1）；模块没注册时
   先 `ctx->importModule("rules")`，再 `registerCamelPass`（`:1411`）。
2. `src/execute/camel_pass.cpp:257` → `DefinitionStore::libraryFunction`
   （`src/runtime/definitions.cpp:295`）→ `module->compileAsProgram(functionName, ...)`
   （`:309`，`src/core/module/userdef.cpp:319`）。Camel 遍走的是这条 `compileAsProgram`，不是
   `compileAsLibrary`（后者用于算子定义的库，`:256`）。
3. `compileAsProgram` 先 `compile(CompileStage::GCT)` 编译 `rules` 自己，再 `collectImports()`
   对每个导入调用 `mod->compile(CompileStage::Declared)`（`src/compile/gct/builder.cpp:732` 的
   `compileImportedModules`）。`graph` / `math` / `tensor` 都是 `UserDefinedModule`（声明模块），
   于是各走一次 parse → GCT → declare。
4. 为什么 `import graph` 拿到的是声明模块而不是 C++ 模块：`src/core/context/context.cpp:730` 的
   `loadModuleFrom` 先 `cmo_load` 找到 `graph.cmo`，再找它旁边的 `graph.cml`；有就把
   `UserDefinedModule` 作为声明模块返回，并 `inheritExportsFrom(*mod)`（`:741-766`，H94 裁定 1）。
   H141 之前 `graph` 的签名在 `stdlib/signatures/graph.cml`，不在 `.cmo` 旁边，所以只加载 C++
   模块、没有 Camel 编译；H141 把文件搬到 `stdlib/graph.cml`，它才进入这条路径。H151 对 `tensor`
   做了同一件事。

### 1.3 三种可能的区分

| 假设 | 结论 | 证据 |
|---|---|---|
| `std::opt` 需要一个由 `graph` 注册的遍 | **否** | `modules/graph` 没有 `registerModulePass`；`std::opt` 请求的是 `rules::simplify`，不是 `graph::*` |
| 有东西间接 import 了 `graph` | **是，且是真实的** | `stdlib/rules.cml:11` 显式导入 `Program, Node, constant`，不是泄漏；`rules` 的守卫函数调用 `constant`（`:60-65` 等） |
| 模块因为声明加载的方式被急切编译 | **是，这就是成本** | H141 把 `graph.cml` 放到 `.cmo` 旁边；`gct` 阶段内 `parse/gct/declare:graph`；拿掉 `graph.cml` 后同一程序不再编译它 |

时间线也支持"是迁移带来的收费，而不是 H100 的旧账"：

```text
09:05  4579d211d  Merge H144  pin ("rules","math")，当时为真
09:32  5b1988d62  Merge H141  graph 成为声明模块（stdlib/graph.cml）
10:12  1224fcc4f  Merge H151  tensor 成为声明模块（stdlib/tensor.cml）
10:24  788a179b2  H162 把 pin 改成三个名字（仍在 H151 之前的分支上）
10:50  72c421872  H162 合入 develop：compile_bench 仍红（少 tensor）
10:54   d729691df  协调者把 pin 补成四个名字，develop 转绿
```

H162 的名单是在"三个库模块"的树上写的，合入时 `tensor` 已经在了；这再次说明名单不是正确的
抽象。H169 把它整个删掉。

## 2. 价钱：`graph` 一次 `std::opt` 0.84 ms

### 2.1 方法

主机 `88zjwei`（EPYC 7343，32 核，与别的任务共用），Release 构建，`-Jobs 8`。程序就是 §1.1 的
十行、无 import 程序，流水线 `std::opt std::null`，每个版本先预热 3 次；然后 61 轮，**同一轮内
A/B 交替**（A = 正常 `out/latest/stdlib`，B = 同一份 stdlib 的副本，删掉 `graph.cml`），
`CAMEL_TIME_PHASES` 交给编译器自己记阶段。负载（`/proc/loadavg` 1 分钟）A/B 都是 21–28 的中位数
21.7。表里是**自身时间**（阶段减去嵌在里面的阶段）的中位数，括号是 p10–p90。

### 2.2 结果

| 项 | A（正常） | B（无 `graph.cml`） |
|---|---:|---:|
| `counters.modules` | 5（`main` + 4 库） | **4**（`main` + 3 库） |
| 整次运行 | 39.889 ms（37.125–43.659） | 38.128 ms（35.860–40.898） |
| `rules`（parse+gct+body） | 22.683 ms（21.401–23.966） | 22.21 ms |
| **`graph`（parse+gct+declare）** | **0.844 ms（0.796–0.931，min 0.768，max 1.085）** | **0** |
| `graph` parse / gct / declare | 0.395 / 0.247 / 0.197 | — |
| `math` | 1.789 ms（1.700–1.878） | 1.85 ms |
| `tensor` | 0.282 ms（0.270–0.325） | 0.29 ms |

**归因用逐模块阶段时间，不用整进程差。** A−B 的整次运行配对差中位数是 2.144 ms，但 p10 −1.833、
p90 4.950，跨零；在 40 ms 的运行上，主机的调度噪声与 `rules` 的 22 ms 主体把 0.8 ms 的差别盖住
了。`graph` 自己的三个阶段是同一进程内直接量到的，61 轮的 spread 只有 ±0.07 ms，所以
**0.844 ms 是可归因、可复现的数**；整进程差只用来证明"删掉它不炸、模块数确实少一个"。

### 2.3 删掉 `graph.cml` 的行为等价

同一程序改成 `std::opt std::jgir`，用两份 stdlib 各跑一次：

```text
sha256  00bbd31a6a71c5fe62f41b1b9ac04f57329a314acfaeb6e9885a7890e7802b3a  /tmp/h169_jgir_normal.txt
sha256  00bbd31a6a71c5fe62f41b1b9ac04f57329a314acfaeb6e9885a7890e7802b3a  /tmp/h169_jgir_nograph.txt
cmp: IDENTICAL（各 6615 字节）
```

这证明两件事：

1. `rules` 需要的是 `graph` 导出的**名字**（`Program`、`Node` 由 C++ `exportType`，`constant` 是
   H141 留在 C++ 的 6 条计算签名之一），不是 `graph.cml` 这份声明文件的解析结果；
2. 因此 0.844 ms 是**声明加载机制**的成本，而不是"`std::opt` 需要一个 graph 遍"的成本。

但"删掉"不是无条件安全的：用同一份无 `graph.cml` 的 stdlib 跑
`test/cases/modules/graph_types.cml`，会红在 `current` / `nodes` / `id` 上
（`SemanticDiag::ImportNameNotExported`），因为这些算子只在
`stdlib/graph.cml` 里声明。所以正确的省法不是"不编译声明模块"，而是"用到未由 C++ 导出满足的名字
时才编译"——那正是 H142 Q2 的惰性声明，会改变声明加载与错误报告的时机，属于作者裁定，不是本任务
可以顺手改的。**本任务不删 `rules.cml` 的 `graph` import。**

## 3. 哪个世界，为什么

- **依赖是 intended。** `rules` 的规则与守卫直接写 `Node`、`Program`、`constant`；H100 让
  `std::opt::algebra` 就是 `rules::simplify`，这条 import 是库的接口，不是偶然的传递依赖。删掉它
  会改变库的依赖图，必须由回答 H142 Q2 的人一起决定。
- **成本是真实的、迁移引入的。** H141（`graph`）和 H151（`tensor`）把签名搬到 `.cmo` 旁边，
  于是每个导入它们的程序都为 parse/GCT/declare 付费。`graph` 是 0.844 ms，`tensor` 是 0.282 ms
  （H151 之后）；`math` 的 1.789 ms 是 H112/H113 的同一类成本，早已在 H144 的账上。对
  `std::opt` 来说，这四个库模块合计约 25 ms（`rules` 的 22 ms 是规则库自己的体）。
- **所以基准不能说"这三个名字是预期的"，也不能把 `graph` 改名成"预期成本"了事。** 正确的表述是：
  今天急切的声明加载让 `graph` 必须编译，`std::opt` 每次付 0.84 ms；如果 H142 Q2 以后改成惰性
  声明，这笔钱才会消失。基准的职责是**把这个数和它的来路一起报出来**，并在集合变化时仍然说真话。
  这正是 H144 的"user / total 两个数都不能消失"的延长线：现在再加一条"每个库模块多少钱"。

## 4. 修法：让基准从证据里取名，而不是从常量里抄名

### 4.1 两个事实，一个集合

`benchmarks/compile/bench.py` 删除 `PASS_LIBRARY_MODULES`，新增：

- `pass_loaded_modules(report)`：从阶段树取集合。一个 Camel 库被遍当作工具程序加载时，
  `UserDefinedModule::compileAsProgram` 打开 `library` 阶段（`detail` 是模块名）；该库导入的
  模块在它的 `gct` 阶段里编译。于是"有 `library` 阶段"或"`gct` 阶段嵌在某个 pass-loaded 模块的
  `gct` 里"的模块就是遍按需加载的。程序自己的 import 在程序的 `gct` 下，没有这样的祖先，天然分开。
- `stdlib_declaration(name)`：要求 `stdlib/<name>.cml` 存在，且其中有一行 `module <name>`。这是
  "库模块以自己的声明命名自己"；名字仍然来自运行，但合法性来自声明文件。
- `module_phase_costs(report)`：按模块汇总 `parse` / `gct` / `declare` / `library` 的自身时间。

**没有从 import 语句里读集合。** 阶段树是"实际发生了什么"，import 文本是"应该发生什么"；两者
不一致时，基准应该报实际发生的。对没有声明文件的导入（`rewrite`），实际发生的是 `cmo_load`，
没有 `gct` 阶段，所以它不会进集合、也不会被计价——这回答了"库导入一个非声明模块时怎么办"：
它不花模块编译的钱，名单里就不该有它。

### 4.2 断言（`cmd_check`）

`passes` 流水线：

1. 必须有库模块（否则这条测量路径根本没跑）；
2. `modules_library` 必须等于 `pass_loaded_modules` 给出的集合（数到的与阶段树证明的一致）；
3. 每个库模块必须通过 `stdlib_declaration`（不是标准库声明模块就红，并说明"名单不是在这里维护的"）。

`compile` / `fvm` 仍然断言没有库模块。程序自己的模块数仍钉在输入集给的名字上，`counters.modules`
仍必须等于阶段名单长度。

- 每个 `passes` 结果把 `pass_loaded`、`module_cost_ms` 写进 `results.json`；`results.md` 新增
  `## Library modules compiled on demand` 表（parse / gct / declare / library body / total）。
- `check` 逐个打印库模块的钱，例如最终树上：
