# stream 重写说明

文件：`stream.cml`。依据：设计原则 5.4（流：值、一次消费、`tee`、不能被捕获、`yield`）、3.10（`for` 遍历流）、`reviews/questions-2026-10-23.md` 的 H248（线性、`tee` 默认 8、`T..` 类型）。没有编译过。

## 设计

流是值：步进函数加状态，`T..` 是 `() => (T, T..)?`；一次调用是一次拉取，回答"下一个元素与流的其余部分"或 `null`。所有变换都是纯的、惰性的 Camel 函数，建在唯一的生产者 `unfold` 上。**关键约束**：lambda 不能捕获流（5.4），所以每个变换把上游流作为 `unfold` 的**状态**（步进函数的实参），而不是闭包里的自由变量；步进函数只捕获非流的配置（`f`、`pred`、`k`）。元组可以装流（状态是 `(T.., int)`），符合"流不能作数组、映射、集合的元素，元组可以"。

## 函数表

| 名字 | 处理 | 理由 |
|---|---|---|
| `unfold(state, step)` | 保留 | 唯一的生产者；`yield` 生成器编译成同样的值 |
| `empty::<T>()` | 新增 | 空流，`pull_chunk` 与使用者都要 |
| `from_array(xs)` | 新增 | 数组变流，`unfold` 一行 |
| `iterate<f>(x)` | 新增 | x, f(x), f(f(x)), … 无限流，`unfold` 一行 |
| `map<f>`、`filter<pred>`、`take<n>`、`scan<f, init>`、`chunks<k>`、`zip(a, b)` | 新增 | 设计原则 5.4 点名的变换（`map`、`filter`、`scan`、`batch`、`zip`）；全是纯函数。`take` 不预取第 n+1 个元素（H248：带效应的映射函数计数恰为 n）。`zip` 两个参数地位对等，都是普通参数 |
| `batch(s, k)` → `chunks<k>` | 改名并放宽 | 设计稿的 `batch` 得到 `T[k]..`，批大小在类型里，这要求 `k` 是类型层的常量，`with` 参数做不到；`chunks<k>` 得 `T[]..`，最后一块可以短。若要定长的 `T[k]..`，等类型函数能从常量算出类型（以后加 `batch`） |
| `collect(s)` | 新增 | 流变数组，`loop … for x in s do out->append<x>`；无限流不返回 |
| `tee<n = 8>(s)` | 新增（原子） | 共享需要缓冲的内部状态，写不成纯 Camel：C++ 原语 `stream:tee`，签名 `(T.., T..)`；语义是两个各自看到完整同一串元素的流，`n` 只是缓冲提示、不改结果；`n < 1` 编译期诊断（常量时）。线性检查（每个流一个消费者、循环体里消费循环外的流是错误）是图上的校验，不在库里 |
| `merge`、按时间的窗口 | 不在这里 | 它们依赖到达顺序或时钟，要声明不确定性，归拥有时钟的库 |

没有写 `pure`：变换的纯度由编译器从体推出；`tee` 的纯度（对外是纯函数）在 C++ 登记。没有 `fail`（`take`/`chunks` 的参数不合法时得空流），没有 `!->`/`?->`（流元素的错误由元素类型 `T!` 表达，变换不吞也不传）。

## C++ 侧

- 新增 `stream:tee`：两个读端共享一个缓冲，各自的 `rest` 是新的流值；报告 `STREAM_TEE`（`std::profile`）见 H248。
- 其余无（`unfold` 与变换都是 Camel）。

## 待验证的写法

1. `unfold` 的返回 `() => match …` 与签名 `T..` 的等价（`T..` 是函数类型的别名还是核心类型，H248 选的是核心类型 A）：若 `T..` 不接受 lambda，`unfold` 需要一个原子（`stream:unfold`），其余不变。
2. 步进 lambda 的 `st.0()`：对元组字段取出的函数值直接调用。
3. `scan`、`chunks`、`zip` 里 `case x => match … ` 的嵌套与块 `{ let total = …; (total, …) }` 作为 `case` 的臂。
4. 元组装流时的线性检查：`st.0` 取出的流被 `st.0()` 消费，`next.1` 放进新状态。需要检查器允许"元组的一个分量被消费、其余分量继续使用"。
5. 同名的 `map`、`filter`、`take`、`zip` 与前奏、`array` 里的数组版共存：靠实参类型（`T..` 对 `T[]`）区分，要求导入同名时是追加重载，不是遮蔽（与 `bytes::len` 同一个问题）；若不行，流的版本用 `s->map<f>` 的前奏重载——即让核心的 `map` 等同时接受流。

## 迁移

只有 4 个文件用到 `unfold`/`stream`；旧签名未变。新增函数需要新用例（尤其"一个流两个消费者"的诊断、`take` 不预取、`tee` 后两边看到同一串元素）。

## 待决策者裁定

1. `batch` 与 `chunks`（见上），推荐 `chunks`。
2. `map`/`filter` 等放在 `stream` 里还是让前奏的同名函数直接接受流。推荐前者（前奏保持小，数组与流是两种类型，导入决定用哪个）。

## 修订（决策者 2026-10-26）

- `unfold(state, step)` 是核心里唯一从（状态，步进函数）造出流的原语；若 `T..` 不能在 Camel 里用 lambda 造出，`unfold` 就是核心的一个原子（`stream:unfold`），本文件里的 Camel 体改为无体声明，其余全部不变。待验证点 1 因此成为核心项。
- 同名函数（`map`、`filter`、`take`、`zip`）与前奏的数组版是一个重载集，不遮蔽（核心的跨模块重载规则，见 `std.notes.md` 修订）；待验证点 5 作废。

## 接入时定下的（2026-10-27）

- `tee` 是 Camel 函数，宽度是 `with` 参数：`s->tee<n>`，默认 8。两侧共用的缓冲放在被闭包写的变量里，原生核函数做不到返回共享可变状态的闭包，所以不设 `#op`。
- 以流为状态的 `unfold(s, …)` 写法会被 `StreamCaptured` 拒：`unfold` 返回的闭包会持有这个流。`map`、`filter`、`chunks` 把上游流放进元组状态，经私有的 `advance` 推进。
