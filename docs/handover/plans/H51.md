### 0.2 最危险的三步

1. **步骤 7 + 8：`with` 函数实参与自动内联。** `tree_map<twice>` 里的 `twice` 是泛型函数，`tree_map<bump>` 里是重载集合；两者都不能在 `tree_map` 这一层定成一个具体函数类型。当前 `tree.cpp` 用 `bindTemporary` + 每个叶子重新 `visitLinkNode` 绕开了类型，新语言层必须在**不建运行期函数端口**的前提下表达同一件事；自动内联又必须让最终图与旧展开逐节点一致（不能多出 `Inline` 区域）。这两步必须先在最小例子上做可行性验证，再写库。
2. **步骤 6：变长参数与编译期元组。** 现语言只有 `...` 的语法占位（报“未实现”）和 `..` 区间；函数类型没有 rest 参数，端口按固定元数建。`..ts` 若被实现成运行期元组，会多出 FILL/ACCS，`tree_map` 的图就不可能和旧展开相同；必须把它定成“编译期实参列表 + 展开后直接成为 N 个实参”，并同时处理 `indices`、`..e` 展开、与 `?..`/命名实参的冲突。
3. **步骤 13 + 14：模块名与 ONNX/`nn` 兼容面。** `tree` 目前是 C++ 内建模块，文件模块 `stdlib/tree.cml` 会遮蔽它，`save_tree`/`load_tree` 随之消失；必须把内建模块改名（建议 `ckpt`）并保留包装。`nn:sgd`/`nn:adam` 是 ONNX 训练导出的识别点，删 C++ 优化器会直接打断 `onnx` lowering；这条要有作者决定，不能藏在“删代码”里。

### 0.3 需要作者裁定的问题

见第 7 节。最关键的三个是：`with` 函数实参的可调用语义（Q1）、`constas` 值参数是否属于第一期（Q2）、`tree` 内建模块改名与 ONNX 兼容（Q7、Q8）。

## 1. 现状：今天 `tree_map` 是怎么展开的

### 1.1 入口与五个 URI

五个 `tree_*` 不是普通库函数，而是编译器内建展开：

- `include/camel/core/type/tree.h` 定义“什么算内部节点、字段名/字段类型/路径、叶子遍历”（`isInternal`、`arity`、`childType`、`childName`、`childPath`、`forEachLeaf`）。
- `src/compile/gir/tree.cpp:38` 的 `Builder::expandTreeCall` 按算子 URI 识别：
  - `tree:tree_map`
  - `tree:tree_reduce`
  - `tree:tree_unzip`
  - `tree:tree_paths`
  - `tree:tree_leaves`
  （`tree.cpp:44-46`；其他 URI 返回 `nullptr`。）
- 调用点在 `src/compile/gir/builder_operators.cpp:1923-1930`：`std::holds_alternative<oper_group_ptr_t>(drefTarget)` 且该 `LINK` 没有显式算子类型时，先试 `expandTreeCall`；成功就直接返回展开出的节点，不再走普通调用。
- `modules/tree/module.cpp:24-35` 的 `TreeResolver::resolve` 返回 `std::nullopt`，注释写明“编译器按每个叶子分别解析回调”；`module.cpp:45-57` 把五个名字导出为 `OperatorGroup`，`load()` 里 `module.cpp:64-70` 把五个名字登记进算子表。
- `stdlib/signatures/tree.cml` 只是参考签名（`inner func ... return 'tree:...'`），不是编译单元；真正的语义在 C++。

### 1.2 `tree_map` 的展开过程

`expandTreeCall` 的结构（行号均指 `src/compile/gir/tree.cpp`）：

1. 校验 with/norm 实参个数（`:55-59`）。`map` 要求 1 个 with（回调）和至少 1 个 norm（第一棵树）。
2. `pack`（`:71-103`）按一个**具体类型**建结构体/元组：
   - 叶子槽位来自 `slots`；
   - 空结构体/空元组用静态数据节点；
   - 非空用 `GCFillKind::Struct` / `Tuple` 的 `FILL`，每个槽位 `LinkType::With`。
3. `compatible`（`:104-114`）在**每个内部节点**检查其余树的 kind、arity、字段名和声明顺序；不一致就以当前路径报 `tree structure differs` / `tree fields ... differ`。
4. `bindTemporary(with.front().node)`（`:119`）把回调函数值命名一次；`invoke`（`:120-140`）对每个叶子新建 `DREF(callback)`，把参数也各 `bindTemporary` 后建 `DREF`，再 `visitLinkNode(call)`。泛型/重载 DREF 保持“名字”，由普通调用解析器按该叶子的实参类型实例化。
5. `walk`（`:146-198`）：
   - 内部节点：先对所有输入做 `compatible`，再逐字段 `access(value, i)`，递归，最后 `pack(shape, children)`；
   - 叶子：`tree_map` 调 `invoke(values)`；`tree_reduce` 调 `invoke({accumulator, values.front()})` 并检查返回可赋给累加器类型；`tree_paths` 建 `StringData(path)` 静态节点（`:172`）；`tree_unzip` 收集每个叶子的分量元组；`tree_leaves` 收集叶子。
6. `tree_unzip` 的收尾（`:208-221`）按 reference 形状逐分量重建树，最后 `pack` 成“树的元组”；空 reference 无法推断分量数时报错（`:206-207`）。

因此对 `{ w: Tensor<f32>, block: (Tensor<f32>, Tensor<f32>) }`，旧展开的图就是：对 `w` 取 ACCS、对 `block` 取 ACCS、对 `block.0`/`block.1` 取 ACCS、每个叶子一次直接调用 `f`、最后按同形 FILL。**没有** `BRCH`、`LOOP`、`CALL tree_map`，也没有 `Inline` 区域。H51 的新展开必须仍是这张图。

### 1.3 为什么不能保留硬编码

- 五个函数各自手写 walk/pack/unzip，是类型层逻辑的第五份拷贝（编译器、tree.h、checkpoint、tiles/transfer、nn/checkpoint 各有一套）。
- `tree_map` 的回调按叶子解析、按类型共享实例、按路径报错，这些正是泛型实例化应该提供的；继续硬编码会让 `optim`、`save_tree` 等新库无法复用。
- 设计稿第 6 节已经把“用 Camel 写这五个”定为第一期验收；H51 第 2 项要求删除核心硬编码。

### 1.4 已有的、可复用的机器

- **泛型模板/实例**：`src/compile/gir/builder_generics.cpp:787` `instantiateGeneric`；实例缓存按类型绑定扫描（`:819-825`）；实例名 `name<types>`（`:827`）；深度上限 `kMaxInstantiationDepth = 128`（`:833`）；失败时 `DiagLabel` + `addRelatedToErrorsFrom`（`:853`、`:977-991`）。
- **调用解析**：`resolveGenericCall`（`builder_generics.cpp:278`）已经能处理“等待中的泛型函数实参”（`waiting`，`:407-438`）：把一个泛型函数名按参数类型实例化后再传给外层。它解决的是**外层调用时就能定下**的回调；`tree_map<twice>` 恰恰不能在这一层定，见步骤 7。
- **返回类型推断**：`buildFuncBody`（`src/compile/gir/builder.cpp:551`）在 `!funcType->hasExitType()` 时把图放入 `inferredExitGraphs_`（`:596-598`），`setBodyResult`（`:608`）从函数体设置退出类型。`instantiateFunctionType` 返回的 `OpenFunctionType` 本来就可以没有退出类型。问题不在“有没有这个机制”，而在“递归调用/静态分支是否会在退出类型尚未确定时读取它”。
- **常量折叠**：`src/passes/opt/generic/generic.cpp:184` 的 `staticArmOf` 识别静态分支，`:250` 的 `pruneBranch` 把静态条件的分支替换成被选分支，`:537` 的 `foldDraft` 折叠纯算子调用。`join` 的 `if a == ""` 会在 `std::opt::inline` + `std::opt::fold` 后变成常量选择，`a + "." + b` 再折成字符串常量。
- **内联**：`src/runtime/draft_inline.cpp:1256` `inlineCallableInDraft`；当前除非调用占满整个 arm，否则 `:1330` 会建一个 `Inline` 区域。H51 的自动内联必须能在不记录区域的情况下把实例体拼进调用者。

## 2. 验收物：到底比较什么，怎么比

“输出与现在逐字节相同”要分三层，不能只靠一句“跑一下看看”。

### 2.1 P0：程序 stdout 逐字节

- 对象：`test/cases/modules/tree_operations.cml`、`tree_training.cml`、`nn/checkpoint_roundtrip.cml`、C2 训练、`test/plans/feat/compile/collections.plan.toml` 的 `tree_paths` 用例。
- 方式：现有 `expect_stdout_exact` / golden 文件，一个字节都不改。
- 这是“行为不变”的硬门槛；任何一步让这些失败，先停下修，不进入下一步。

### 2.2 P1：构建后的 GIR 图逐节点（`tree_map`/`tree_reduce`/`tree_unzip`/`tree_leaves`）

- 对象：`tree_map`、`tree_reduce`、`tree_unzip`、`tree_leaves` 的展开结果（`tree_paths` 见 P2）。
- 产物：`camel <case> std::opt::dce std::jgir` 的 JSON。只跑 **DCE**（`std::opt::dce`），不跑 inline/fold：`same_shape`/`check_one` 只做类型检查，展开后会留下无用户的访问/调用；DCE 把它们删掉，旧实现没有这些节点，删除后两边才可比。`tree_map` 对 `f` 的调用是可达的，DCE 不会删。
- 归一化：`normalize_origins`（`test/tools/run-tests.mjs:414` 把 `"origin": "[0-9]+"` 换成 `<ORIGIN>`）。只归一化 origin，其他字段必须相同。
- 比较：golden 文件，逐字节比较归一化后的 stdout。
- **临时绑定的边界**：旧 `tree.cpp` 的 `invoke` 用 `bindTemporary` 给回调和每个实参建 `DREF`（`tree.cpp:115-130`），新库的普通调用可能不建同样的临时名。P1 的首选仍是 raw `std::jgir` 逐字节；如果差异**只**是临时 `DREF`/`NREF` 的名字/数量，而 `std::stats` 的 operators/calls/closures/branches 一致、且没有多出 `CALL`/`ACCS`/`FILL`，则允许加一个 `normalize_temporaries` 归一化器（新增，需评审）或退回“operators/calls 多重集”比较。这个退路不能掩盖多出的访问/填充/调用；它只处理临时命名。该差异记入 R3，不静默通过。
- 必须满足的结构条件（测试直接断言）：
  - 没有名为 `tree_map`/`tree_reduce`/`tree_unzip`/`tree_leaves` 的 `CALL`；
  - 没有 `regions` 里的 `inline` 条目（自动内联不能留下 `Inline` 区域）；
  - 没有 `BRCH`/`LOOP`/`CASE` 节点（`match type`、`static for`、`static loop` 都在建图期消掉）；
  - 节点/边/字段顺序与旧图相同。
- 旧图 golden 的采集：在**删除 `tree.cpp` 之前**的提交里，用旧实现跑同一 case（同样 `std::opt::dce std::jgir`），`node test/tools/run-tests.mjs --update-golden <plan>` 生成并提交；然后新实现只读这份 golden。这样“新实现与旧实现相同”不是靠记忆，而是靠提交历史里的基线。

### 2.3 P2：`tree_paths` 的常量折叠

- `tree_paths` 的路径在源码里是普通字符串值，设计稿明确“由常量折叠遍化为字符串常量节点”（`generic-structure/README.cn.md:102`）。
- 方式：`camel <case> std::opt::inline std::opt::fold std::opt::dce std::jgir`，归一化 origin，再与旧实现同一管线的 golden 逐字节比较。
- 附加断言：每个路径叶子的 `DATA` 是 `StringData` 常量，不是 `CALL join`；`join` 的 `if` 已被 `pruneBranch` 消掉。
- 这条比 P1 弱（允许中间节点被优化掉），但正是设计稿承诺的形态；若 `std::opt` 折不掉 `join`，步骤 10 需要给 `fold` 补纯字符串拼接/静态分支，而不是改语义。

### 2.4 P3：统计与下游

- `std::stats` 的 `GRAPH_STATS {json}`（graphs/nodes/edges/operators/calls/closures/branches）作为 golden：`tree_training.cml` 与 C2 训练步的计数不得增加。
- autodiff：`with_grad` 包住 `tree_map` 的损失，梯度 stdout 与旧 golden 相同；`tree_map` 内联后不应留下高阶函数值。
- Tiles：`test/plans/gpu/tiles_transfer.plan.toml` 的 device 传输用例保持；没有 GPU 时按现有 skip 规则，不新增硬件依赖。
- 时间：不作为验收门槛（见 Q11）；只记录节点数/算子数。

### 2.5 诊断的兼容边界

交接文字里的“逐字节”按**程序输出**理解。诊断是另一条兼容面：

- 必须保留：错误位置（源文件/行/列）、静态路径信息（如 `block.0`）、`tree structure differs` 这个语义；
- 允许变化：诊断码、措辞、标签格式（从 `ArgumentsRejected` 变为 `StaticError`/`StaticFieldNotFound` 等）。
- 受影响的 `test/plans/feat/modules/tree.plan.toml:16-21` 目前断言 `"tree leaf 'block'"` 与 `"tree structure differs"`。新实现至少保留后者；前者若不能逐字保留，更新该断言并在计划里记录为“诊断格式变化”，不把它算作行为回归。
- 如果作者要求诊断也逐字节相同，见 Q4；那会把步骤 9 的工作量显著放大（需要为 `static error` 增加“库自定义标签/路径渲染”）。

## 3. 语言层步骤（1–11）

### 步骤 1：`match type` 与固定 R3 叶子边界

**目标**：在实例化时按类型的形状选一条分支，只有被选中的分支建图、做类型检查；`struct`/`tuple` 只匹配 R3 内部节点，`T?`/`T!`/单元格落到叶子 case。

**词法/语法/AST**

- 不加新关键字：`match` 已有，`type` 已有；`case` 已有。`struct`/`tuple` 用上下文关键字（只在 `match type` 的 case 位置识别），`#leaf` 复用已有的 `#` 记号 + 上下文名 `leaf`。
- `src/parse/syntax/parser_expr.cpp`：
  - 在 `parseMatch`（`:856`）开头检测 `match` 后是否紧跟 `type`；是则转 `parseMatchType`。

### 步骤 2：静态泛型的返回类型推断

**目标**：带 `match type`/`static` 构造的泛型函数可以省略返回类型，由实例化后的函数体推出；递归回到正在实例化的同一个键时报错，而不是给出半个类型。

### 步骤 3：`fields T`、`static for`、`t.[n]`

**目标**：按结构体/元组的字段顺序展开函数体；`n` 是编译期字符串（结构体字段名/元组下标的十进制字面），`F` 是字段类型；`t.[n]` 在编译期取字段。

**词法/语法/AST**

- `include/camel/parse/syntax/token_kinds.def` 增加 `KwStatic`（`static` 成为保留字；`fields` 不成为关键字，保持上下文名）。这会改 `scripts/check-grammar.mjs` 与语言参考的关键字表；同步。
- `parser_expr.cpp`：
  - `parseStaticFor`：`'static' 'for' '(' identDef ',' identDef ')' 'in' 'fields' typeExpr '=>' blockExpr`（`(n, F)` 也可写成 `(n, F, tags)`，见 Q5；第一期先接两元）。

- `src/parse/ast/builder.cpp`：新增 visit；`SpreadValue` 仍留给步骤 6。

**GCT**

- `NodeKind` 增加 `SFOR`、`SACC`。

- `SACC` 子节点：target、key；payload 无（key 在 GIR 期求值）。
- `src/compile/gct/builder.cpp`：`visitStaticFor`、`visitStaticAccess`；`static for` 的 body 里 `n`/`F` 进入 GCT 的静态作用域（`declaredTypeVars_`/`staticNames_`），`F` 是 `TypeVarType`。

**GIR/建图**

### 步骤 4：结构体/元组推导式

**目标**：`{ static for (n,F) in fields T => [n]: e }` 生成同形结构体；`( static for (n,F) in fields T => e )` 生成同形元组；空形状得到 `{}`/`()`；字段类型由 `e` 推出。

**语法/AST**

- `parseStructData`（`:773`）：看到 `'{' 'static' 'for'` 转 `parseStructComp`；字段语法是 `'[' dataExpr ']' ':' dataExpr`，`[n]` 必须是当前 `static for` 绑定的 `n`（或编译期字符串常量）；普通 `n: e` 仍按字面字段名解析（设计原则 5.2/6.4）。
- `parseTupleData`（`:790`）：看到 `'(' 'static' 'for'` 转 `parseTupleComp`；元素是 `dataExpr`，步骤 6 允许 `..e` 作为元素（展开/拼接）。
- AST：`DataType::StructComp`、`TupleComp`；`StructCompLoad { generator; pairs; }`，`TupleCompLoad { generator; elements; }`；`generator` 是步骤 3 的 `StaticForLoad`。
- 解析约束：一个推导式只能有一个 `static for` 生成器；生成器后不能再写逗号分隔的普通元素（避免“静态 + 运行期混合”的歧义）。

**GCT**

- `NodeKind` 增加 `SCOMP`；payload 存 `Struct`/`Tuple`；子节点：`TYPE`（被展开的类型）、`SFOR`（生成器）、`EXEC`（body）。
- `visitStructComp`/`visitTupleComp` 在 GCT 期只做结构化降级，不展开。

**GIR**

- `visitComprehensionNode` 复用步骤 3 的字段循环，收集每个字段的 body 值：
  - struct：类型 `StructType(fieldNames, bodyTypes)`，名字来自 `fields T` 的 `n`；空形状用静态空结构体；
  - tuple：类型 `TupleType(bodyTypes)`；空形状用空元组；
  - 构造复用抽出的 `Builder::packValue(kind, shape, values, origin)`（从 `tree.cpp:71-103` 的 `pack` 提取，放 `builder_static.cpp`，不保留 tree 专用逻辑）。`packValue` 负责 `GCFillKind`、`addFillNode`、`LinkType::With`、空形状的 `addStaticDataNode`。
- 字段名/类型必须与 `fields T` 一致；body 返回 `void` 时报 `StaticComprehensionVoidElement`。
- 嵌套推导式：内层 body 可以继续是 `SCOMP`，递归展开。
- 空形状不执行 body，因此 body 里的类型错误不会被检查（与 `if constexpr` 一致）；但如果 body 有未定义名字，GCT 仍可能先报（同步骤 1 的限制）。

**测试**

  - struct/tuple 推导式，字段类型逐字段不同；
  - 空 struct/空 tuple；
  - 嵌套（结构体里有元组）；
  - `tree_map` 的迷你版（回调 `twice`）；
  - 负例：`[n]` 不是绑定的 n、body 返回 void、生成器缺失。
- `test/plans/feat/compile/static_expansion.plan.toml`。
- `std::jgir` 断言没有 `SCOMP`，FILL 的槽位顺序与字段顺序一致。

**解锁**：`tree_map`、`tree_paths`、`tree_leaves`（配合步骤 6 的展开元素）。

**风险**：空形状的返回类型没有 body 可推（struct 用字段名、tuple 用 `()`）；`[n]` 与普通 `n:` 的解析分界；`packValue` 抽出来后必须保持旧 `tree.cpp` 的 origin 注册（`registerTreeOrigin`）以让 P1 图等价；推导式的字段类型推断与步骤 2 的返回推断相互依赖。

### 步骤 5：`static loop`

**目标**：在编译期按字段顺序展开的折叠；`static loop acc = init for (n,F) in fields T do body`，结果是最终状态；不建 `LOOP` 节点。

**语法/AST**

- `parseLoop`（`:1047`）已有 `loop state = init ... for ident in expr ... do blockExpr` 的结构；新增 `'static' 'loop'` 前缀，复用 `LoopState`/`LoopFor`/`LoopWhile` 的 AST 形状，或新增 `StaticLoopLoad { states; generator; body; }`。
- `static loop` 只允许 `for (n,F) in fields T`，不允许 `while`/普通 `for`。
- 支持多状态（与普通 loop 一致）：`static loop a = ..., b = ... for ... do ...`，结果是一个元组；H51 的 `save_at` 用单状态，`tree_reduce` 用单状态。

**GCT**

- `NodeKind` 增加 `SLOOP`；子节点：`TYPE`、每个状态的初值、`EXEC` body；payload 存状态名、`n`/`F` 名。
- `visitStaticLoop` 结构化降级。

**GIR**

- `visitStaticLoopNode`：
  - 初始化 `current[state] = visit(init)`；
  - 对每个字段：绑定 `n`/`F`，把状态名绑定到当前值，`visitBodyNode`，得到新值；多状态要求 body 返回同形元组；
  - 循环结束返回最后一个状态（单状态）或状态元组；
  - 空字段返回初值；
  - 不建 `LOOP`、不建 `BRCH`。
- 状态类型必须稳定：每轮新值可赋给初值类型；否则 `StaticLoopStateTypeChanged`（或者按普通循环的 `LoopBodyTypeMismatch`，保持诊断风格）。
- body 里的 `return` 与普通函数一致：走 `EXIT`，不是“跳出 static loop”。

**测试**

- `test/cases/compile/static_expansion/static_loop.cml`：
  - 单状态对 struct/tuple 求和；
  - 空结构返回初值；
  - 多状态（例如同时累计和与计数）；
  - 状态类型改变负例；
  - `tree_reduce` 的迷你版（先减后加的顺序）。
- `std::jgir` 断言没有 `LOOP`，展开为直线调用/运算。

**解锁**：`tree_reduce`、步骤 12 的 `save_at`（如果做）。

**风险**：多状态返回元组的顺序；`static loop` 与普通 `loop` 的解析歧义（`static` 前缀已区分）；body 中的 `F` 类型变量作用域。

### 步骤 6：`..ts`、`..e`、`indices`、`constas` 值参数

**目标**：变长实参在编译期元数已知；`ts` 是编译期元组；`f(t, ..ts)` 展开成 N 个实参；`static for (j) in indices ts` 遍历；函数可以有 rest 参数；`..e` 在元组推导式/调用中展开。

**这是全计划最需要先做“最小可行性验证”的一步。**

#### 6.1 语法

- 函数参数：`parseParentParams`（`src/parse/syntax/parser.cpp:1216`）允许 `'..' identDef`（**第一期 rest 参数不写类型**，元组类型在调用点由实参得出；设计稿的 `tree_map(t: typeas T, ..ts)` 正是这样写），且必须是最后一个参数；一个参数表最多一个 rest。AST `ParamDeclLoad` 增加 `isRest`（`include/camel/parse/ast/other.h:31`）。如果写了 `: typeExpr`，先报 `RestParameterTypeNotSupported`（第二期再定逐元素还是整元组语义，见 Q2）。
- 编译期值参数：`'constas' identDef ':' typeExpr`（复用 `KwConstas`）；`n` 是编译期常量，调用时必须给常量，进入实例键。设计稿 `column(constas n, ts)` 已经这样写；如果作者不接受，见 Q2。
- 调用实参：`parseArguments`（`parser_expr.cpp:627`）在位置实参里识别 `'..' dataExpr` 为 `SpreadArgument`；`..` 只能出现一次且必须是最后一个位置实参；命名实参不能与 `..` 混用（`VariadicArgumentNotLast`）。
- `parseIndexValue`（`:574`）里 `'...'` 仍报“未实现”（本计划不把 `...` 变成 `..`；`...` 将来属于另一语义）。
- `indices`：在 `static for` 的 iterable 位置识别上下文名 `indices`，解析为 `IndicesOf { value }`；`indices ts` 的 `ts` 必须是元组类型（rest 元组或普通元组），元数为编译期常量。
- 元组推导式元素 `..e`：`( static for ... => ..e )` 把 `e` 的元组元素拼接到结果；实现为语法糖，GIR 期展开。
- **静态元组值**：元组推导式、`column` 这类“所有元素都是编译期已知节点、只被 `..`/`.[j]` 消费”的元组，在 GIR 里先表示成 `StaticTuple { type, elements }` 这一**建图期值**，不立刻建 `FILL`。`..e` 对 `StaticTuple` 做拼接；只有它逃逸到运行期位置（打印、作为普通实参、返回）时才物化成 `FILL`。这是 `tree_leaves`/`column` 不产生中间 1 元组 FILL 的关键；否则 P1 会多出旧图没有的死节点。

#### 6.2 类型表示

- `FunctionType`（`include/camel/core/type/composite/func.h`）增加 rest 元数据：`bool hasRest`（模板专用）；参数名列表仍只存固定参数。`FunctionTypeFactory::addRestArg` 新增。rest 的**元组类型**不存进模板签名，而是实例化时由实参元组给出；`tree_map(t, ..ts)` 的各棵树可以不同类型。
- 模板签名里 rest 只是一个标记；实例化时按实参数的 `TupleType` 展开成 N 个固定参数，`ts` 在函数体里是这个 N 元组的编译期绑定。实例的 `FunctionType` 不再有 rest 标记。
- `OpenFunctionType` 的 `hasExitType`/`with/norm` 计数逻辑要区分模板与实例：模板的 `normTypesCount()` 不含 rest，实例的 `normTypesCount()` 是 N；这是这一步最容易漏的地方。
- 运行期 ABI 不允许 rest：**带 rest 的函数必须是可静态展开的**（函数体含 `match type`/`static` 或显式 `static` 注解；见 Q3）。把 rest 函数当值、导出、或作为非展开调用：`VariadicFunctionNeedsExpansion`。

#### 6.3 GCT/GIR

- GCT：`ParamDecl` 的 rest 标记；`LINK` 的实参里 `Spread` 节点（`NodeKind::SPRD` 或 `LINK` 的 payload 标记）；`INDCS` 节点。
- GIR：
  - `expandStaticCall`（与步骤 8 的自动内联共用）在解析调用前把 `..e` 展开：
    - `e` 是 `StaticTuple`：直接把 N 个元素节点拼进实参表，不建 `FILL`；
    - `e` 是运行期元组/FILL（例如用户显式构造的元组）：取 FILL 的槽位；若该 FILL 只被这次展开使用，标记为可删除，避免 P1 多出死节点；
    - `e` 是其他运行期元组：`VariadicArgumentNotTuple`（不能接受运行期变长）。
  - 展开后调用按 N 个位置实参处理；模板的 rest 绑定为这 N 个节点的元组（编译期结构，不建 FILL）。
  - `indices ts`：取 `ts` 的类型 `TupleType` 的 arity，生成 `0..N-1` 的编译期整数序列；`static for` 每轮绑定 `j` 为常量。`indices` 的操作数只用于取类型，**不建值节点**（`ts` 是 `leaves.[0]` 这类 StaticTuple 元素时，`.[0]` 也是编译期选择，不建 ACCS）。
  - 静态访问 `st.[j]`：若 `st` 是 `StaticTuple`，是编译期选择，直接返回第 j 个元素节点，不建 `ACCS`；若 `st` 是运行期元组值，才建 `ACCS`。
  - 元组推导式的 `..e` 元素：在收集元素时把 `e` 的 N 个元素插入结果，而不是建一个嵌套元组。
- `f(t, ..ts)` 中 `f` 是 with 回调时，展开后的 N 个实参就是回调实参；回调为泛型/重载时，每个叶子的调用按步骤 7 解析。

#### 6.4 与现有规则的关系

- `hasVarArgument`（`builder_operators.cpp:2397-2436`）处理的是算子组的 `varParameters`（`include/camel/core/type/resolver.h` 的 `vector<bool>`），与函数 rest 是两套机制。H51 **不改**算子组的变长解析；`tree` 的五个函数不再走算子组，因此不会冲突。测试要覆盖“普通变长算子的既有行为不变”。
- `?..`（`QuestionDotDot`）是 tag 传播/可空访问，与 `..` 不是同一记号；解析时按最长匹配，`?..` 优先。
- `a..b` 区间在表达式位置仍是区间；`..e` 只在实参/推导式元素位置识别，不改变区间语法。
- 命名实参 + `..`：禁止；`..` 必须是最后一个位置实参；rest 参数必须是最后一个参数。

#### 6.5 测试

- `test/cases/compile/static_expansion/variadic.cml`：
  - `func sum(..xs)` 展开 0/1/3 个实参；
  - `..` 展开普通元组变量、展开推导式结果、展开 rest 绑定；
  - `indices ts` 遍历 rest 元组；
  - `constas n: string` 的 `column` 风格函数；
  - 元组推导式 `..e` 拼接；
  - 负例：rest 不在最后、`..` 不在最后、`..` 后还有命名实参、展开运行期元组、把 rest 函数当值。
- `test/plans/feat/compile/static_expansion.plan.toml`。
- `std::jgir`：`f(t, ..ts)` 展开后是 N 个 `DREF` 实参，没有 `FILL`/`ACCS` 组成的元组；rest 函数实例的端口数是 N，不是 1 个元组端口；`tree_leaves`/`column` 的中间结果不出现 1 元组 FILL。
- 静态元组值的逃逸测试：把 `column` 的结果直接打印，必须物化成 FILL；只被 `..`/`.[j]` 使用时不得物化。

### 步骤 7：`with` 函数实参的身份与可调用绑定

**目标**：`tree_map<twice>`、`tree_map<bump>`（重载集合）、`tree_map<(a,b)=>...>`（lambda）都能工作；函数身份进入实例键；同一个类型 + 同一个函数只实例化一次；递归 `tree_map<f>` 复用同一个身份。

**现状与难点**

- 当前 `resolveGenericCall` 对 `waiting` 泛型实参（`builder_generics.cpp:407-438`）会在外层调用时就把它实例化成 `FuncData`。对 `tree_map<twice>`：
  - `tree_map` 的 `with <f: (leaf: A) => B>` 中 `A`/`B` 不是由 `t` 绑定的（`t` 只绑定 `T`）；
  - `wanted` 仍是含 `A`/`B` 的函数类型；`instantiateGenericAs(twice, wanted, ...)` 要么因 `A/B` 未定失败，要么把 `twice` 固定成一个叶子类型；两种都不对。
  - `tree.cpp` 之所以能工作，是因为它在每个叶子拿到**具体实参类型**后才 `visitLinkNode`（`:120-140`）。
- 重载集合 `bump` 根本不是一个具体函数类型；把它们塞进 `with` 端口再调用，会在端口类型上失败。

**建议的语义（需作者确认，Q1）**

把**函数类型的 `with` 参数**定义为“编译期可调用绑定”，而不是运行期函数值端口：

- `with` 实参可以是：具体函数图、lambda 图、泛型模板名、重载集合、或另一个 `with` 可调用绑定；
- 它不建运行期端口；实例体里对 `f` 的每次**调用**在实参类型已知时解析（普通 `visitLinkNode` 逻辑），因此 `twice`/`bump` 按每个叶子的类型实例化；
- 实例键记录函数身份（图指针 / 模板指针 + 名字 / 重载集合的名字 + 模块 / 外层可调用绑定的键）；
- 把 `f` 当**值**使用（传参、放入结构体、返回）时：如果它只有一个具体函数图，可以物化；泛型/重载集合则报 `GenericFunctionAsValue`（沿用现有函数名作值的诊断风格）；
- 递归 `tree_map<f>` 里的 `f` 是当前实例的 with 参数，必须复用同一个 `WithKey`，不能按端口节点新建身份。

**改动**

- AST/语法：不新增源语法；`with <f: ...>` 的声明不变，`tree_map<f>` 的调用不变。
- GCT：`LINK`/`WITH` 的实参保留“名字/重载集合”形态；不要过早降成 `FUNC` 值。`GCT::NodeKind::DREF` 已经能表示名字，关键是 GIR 不要在 `enterScope` 时强制物化。`with <f: (leaf: A) => B>` 里的 `A/B` 在声明处允许保持未绑定（它们只是调用点的形状提示）；如果当前 `visitFuncType`/`declaredTypeVars_` 会以“类型变量未确定”拒绝，在本步骤放宽这一处，并测试 `tree_map<twice>` 能过 GCT。
- GIR：
  - `GenericInstance`（`builder.h:687`）增加 `std::vector<WithKey> withKeys`；`GenericTemplate` 缓存比较从“仅 bindings”改为“bindings + withKeys”（`builder_generics.cpp:801-825`）。
  - `WithKey`：`variant<graph_ptr_t, template_ptr_t, OverloadSetKey, OuterWithIndex>`；提供 `same()`/`display()`。
  - `Builder::withCallable_` 栈：进入静态实例时记录每个 with 参数当前绑定的 `WithKey`；`resolveGenericCall` 遇到“实参是当前 with 参数”时复用外层 key。
  - `instantiateGeneric` 的实例名：`tree_map<twice><{...}>` 或 `tree_map<f#2><{...}>`；同类型不同 f 不能撞名。
  - 调用解析：`visitLinkNode` 的 callee 若是 `with` 可调用绑定，按该绑定解析（具体图/模板/重载集合）；如果该绑定是泛型模板，则用实参类型实例化，与普通泛型名调用共用 `resolveGenericCall`。
  - 端口：静态实例不建 with 可调用端口；如果实例图仍需要 `with` 端口，在自动内联时把它绑定到调用者的可调用绑定，不生成运行期值。
- 诊断：`WithCallableUsedAsValue`、`WithCallableNotCallable`；实例键标签里显示函数身份（`f = twice` / `f = bump`）。

**测试**

- `test/cases/compile/static_expansion/with_callables.cml`：
  - `tree_map<twice>` 对 `{int,float}` 得到两个不同实例；
  - `tree_map<bump>`（int/float 重载）每个叶子选对重载；
  - `tree_map<lambda>` 与 `tree_map<另一 lambda>` 同类型不同实例（用 `std::jgir` 的实例名/节点差异断言）；
  - 同一函数在同一类型两处调用只产生一个实例（设计稿 3.1.1 `:82`）；
  - 递归 `tree_map<f>` 的每个字段复用同一个 `WithKey`，不因深度多出实例；
  - 负例：把 `f` 当值传给普通函数（泛型时）报错；重载集合当值报错。
- `test/plans/feat/compile/static_expansion.plan.toml`。
- 现有 `test/cases/compile/generics` 的 with 泛型用例保持绿。

**解锁**：`tree_map`/`tree_reduce` 的真实回调；`tree_unzip` 不需要回调。

**风险**：这是“函数值”与“函数名”边界最模糊的一步；`with` 参数既可能被调用也可能被当值，必须定一条清晰规则。若作者不接受“可调用绑定”而坚持“with 参数是运行期值”，则需要引入 `with <f: callable>` 新类型，或限制调用方只能传具体 lambda；两种都会改变设计稿 3.1.1 的 `tree_map<twice>` 用例。见 Q1。

### 步骤 8：含静态构造的实例自动内联

**目标**：`tree_map<T>` 的实例体在调用处展开，最终图里没有对 `tree_map` 的 `CALL`，没有 `Inline` 区域，节点顺序与旧 `tree.cpp` 展开一致；用户不写内联标注；编译期有预算/深度保护。

**两种实现路线（本步骤先做 8a 可行性，再选）**

- **8a. 展开式实例（推荐）**：静态实例不进入程序的图列表；在调用处按实例键构建一个“实例体图”，然后把它拼进调用者的当前区域，参数用实参节点替换。实例体可以缓存（每键一份），拼接时克隆；克隆不记录 `Inline` 区域。
- **8b. 先建普通图，再用 `inlineCallableInDraft`**：`src/runtime/draft_inline.cpp:1256` 已有内联器；需要新增 `recordRegion=false`（当前 `:1330` 无条件 `addInlineRegion`，除非调用占满整个 arm），并把静态 with 可调用绑定正确替换。路线 8b 复用现有代码，但实例图的 with 端口/可调用绑定会留下痕迹，图等价更难保证。

计划建议：**先按 8a 做一个只含 `match type` + `static for`、不含回调的最小实例**，用 P1 golden 证明节点顺序；再加回调（步骤 7）；如果 8a 在缓存/克隆上成本过高，退回 8b 并接受“实例键一份图 + 克隆”的模型。无论哪条，最终 P1 必须逐字节过，否则不算完成。

**改动**

- `builder.h`：`StaticExpansion` 结构（模板、bindings、withKeys、实例图/片段）；`staticExpansions_` 缓存；`inliningStatic_` 标志；`spliceGraphIntoCurrentRegion(graph, argMapping, recordRegion=false)`。
- `builder_generics.cpp`：`instantiateGeneric` 对“需要静态展开”的模板走 `expandStaticCall`，不返回普通 `FuncData`；普通泛型仍走原路径。
- `src/runtime/draft_inline.cpp`：如果走 8b，`inlineCallableInDraft` 增加 `recordRegion` 参数；静态调用传 `false`；`addInlineRegion` 不调用。
- `src/compile/gir/program.cpp` / `reachable.cpp`：静态实例图不加入 `program->graphs()`，或者加入但不可达；确保 `collectReachableGraphs` 不输出它们。
- 预算：`kMaxStaticExpansionNodes`（建议初值 1,000,000，可配）与 `kMaxInstantiationDepth`；超限 `StaticExpansionTooDeep`/`StaticExpansionTooLarge`，带实例链。
- 缓存：同键实例只构建一次；克隆的节点 origin 指回调用点/模板；测试 P1 的 origin 已归一化，但 `origin` 的文件/行仍需合理（指回模板或调用点均可，需统一）。
- **建图期返回值**：静态实例的函数体可能返回 `StaticTuple`（例如 `column` 的元组推导式）。实例体不能先把它物化成 `FILL` 再返回，否则 `..column(...)` 展开后会留下死 FILL；`expandStaticCall` 必须能拿到实例的 `StaticTuple` 返回值并直接拼接。这是 8a 相对 8b 的关键优势；若走 8b，需要在克隆后删除“只被展开消费”的 FILL，或者把 `column` 内联进 `tree_map`。

**测试**

- 测试：`test/cases/modules/tree_operations.cml` 的 P1 `std::opt::dce std::jgir` golden（旧实现采集）。
- `test/plans/feat/compile/static_expansion.plan.toml`：
  - 实例体含 `match type`/`static for` 的函数调用后，`std::opt::dce std::jgir` 中没有该函数的 `CALL`、没有 `regions`；
  - 同一类型多处调用，节点数线性增加、实例图不重复出现；
  - 递归实例的深度/节点预算负例；
  - `std::stats` 的 graphs/nodes/edges 与旧一致。
- `test/cases/compile/static_expansion/auto_inline_compile_time.cml`：一个 12 字段结构体 + 12 个相同 `Block`，确认不会指数爆炸（节点数上界断言）。

**解锁**：步骤 13 的图等价；步骤 14 的 autodiff/Tiles 看到普通节点。

**风险**：这是全计划最可能“做出来但图不一样”的一步。若实例图克隆顺序与旧 `tree_map` walk 不同，P1 立刻暴露；若保留 `Inline` 区域，`std::jgir` 的 `regions` 不同；若实例图可达，`collectReachableGraphs` 多出图。缓存与克隆的交互还会导致同一实例在不同调用点 origin 不同，需要统一策略。

### 步骤 9：实例化链诊断、`static error`、深度上限

**目标**：失败时能从叶子一路看到实例链与静态路径（`blocks.1.w`）；库可以用 `static error "..."` 给出自己的消息；实例化深度可配。

**诊断链**

- `Builder` 增加 `std::vector<StaticFrame>`：`{ kind: Type/For/Loop/Call, name, pathSegment, origin }`；进入 `match type` case、`static for` 字段、`static loop` 迭代、泛型实例时压栈/出栈。
- `DiagLabel` 的文本：`tree_map<{...}>` → `field 'block'` → `element 1` → `field 'w'`；`path` 由 `static for` 的 `n` 拼接，与设计稿 3.1.4 一致。
- `addRelatedToErrorsFrom(diagsBefore, instanceLabel, 3)`（`builder_generics.cpp:977-991`）已有“只保留前 3 条”的策略；静态路径标签加在同一机制里，避免每个叶子重复刷屏。
- 共享实例失败：缓存里同一个实例被多个调用点使用，第一次失败就终止；诊断指向第一个路径（与旧 `firstRejectedLeaf` 一致）。测试固定这个“第一路径”行为。

**`static error`**

- 语法：`'static' 'error' STRING`（第一期只接受字符串字面量；如需拼接/路径，见 Q4）。
- AST：`StaticErrorLoad { message; }`；GCT：`SERR`；GIR：`visitStaticErrorNode` 直接 `diags_->of(SemanticDiag::StaticError).atOrigin(...).commit(message)` 并 `throw BuildAbortException()`；不建节点。
- 只在被选中的分支/展开中出现；未选分支不触发。
- 诊断码：`StaticError = 0x000172`；消息格式 `static error: <message>`；静态路径作为 related label（如果 Q4 允许）。
- 用例：
  - `match type T { case _ => static error "no leaf" }` 对 int 触发；
  - 对 struct 不触发；
  - 嵌套实例里的 `static error` 带完整链。

**深度上限**

- `include/camel/execute/limits.h`：新增 `kDefaultMaxInstantiationDepth`（沿用 128）、`kMaxInstantiationDepthEnvVar = "CAMEL_MAX_INSTANTIATION_DEPTH"`；`src/compile/gir/builder.h:729-730` 的常量改为从上下文读取。
- `include/camel/core/context/context.h` 的 `EntryConfig` 增加 `maxInstantiationDepth`；CLI 增加 `--max-instantiation-depth`（与 `--max-recursion-depth` 同风格）；`src/execute/options` 解析。
- 超限诊断：`GenericInstantiationTooDeep`（已有 `0x000055`）或新 `StaticExpansionTooDeep`；消息包含深度、实例链前 3 层。
- 测试：一个自递归泛型在默认深度报错；`--max-instantiation-depth 4` 更早报错；环境变量覆盖。

**测试**

- `test/cases/compile/static_expansion/diagnostics_chain.cml`：三层嵌套 `match type`/`static for` 的错误，断言输出含 `blocks`、`1`、`w`（不要求逐字格式）。

```camel
// stdlib/tree.cml（示意；最终以步骤 1–10 落地的语法为准）
with <f: (leaf: A) => B>
export func tree_map(t: typeas T, ..ts) {
    same_shape(t, ..ts);
    return match type T {
        case struct => { static for (n, F) in fields T =>
            [n]: tree_map<f>(t.[n], ..column(n, ..ts)) }
        case tuple => ( static for (n, F) in fields T =>
            tree_map<f>(t.[n], ..column(n, ..ts)) )
        case _ => f(t, ..ts)
    }
}

func column(constas n: string, ..ts) {
    return ( static for (j) in indices ts => ts.[j].[n] )
}

with <f: (acc: R, leaf: B) => R>
export func tree_reduce(t: typeas T, init: typeas R) {
    return match type T {
        case struct | tuple => {
            static loop acc = init for (n, F) in fields T do
                tree_reduce<f>(t.[n], acc)
        }
        case _ => f(init, t)
    }
}

export func tree_leaves(t: typeas T) {
    return match type T {
        case struct | tuple => ( static for (n, F) in fields T => ..tree_leaves(t.[n]) )
        case _              => (t,)
    }
}

export func tree_paths(t: typeas T) { return paths_at(t, "") }
func paths_at(t: typeas T, here: string) {
    return match type T {
        case struct => { static for (n, F) in fields T =>
            [n]: paths_at(t.[n], join(here, n)) }
        case tuple => ( static for (n, F) in fields T =>
            paths_at(t.[n], join(here, n)) )
        case _ => here
    }
}
func join(a: string, b: string): string { return if a == "" then b else a + "." + b }

export func tree_unzip(values: typeas V, reference: typeas R) {
    check_one(reference, values);
    let leaves = tree_leaves(values);
    let sample = leaves.[0];              // 空树：static error
    return ( static for (j) in indices sample =>
        rebuild(j, values, reference) )
}
func rebuild(constas j: int, values: typeas V, reference: typeas R) {
    return match type R {
        case struct => { static for (n, F) in fields R =>
            [n]: rebuild(j, values.[n], reference.[n]) }
        case tuple => ( static for (n, F) in fields R =>
            rebuild(j, values.[n], reference.[n]) )
        case _ => values.[j]
    }
}
```

说明：

- `column`/`rebuild` 的 `constas` 是步骤 6 的编译期值参数；如果作者不接受，`column` 可以内联，但 `tree_unzip` 的 `rebuild` 仍需等第二期类型位置（Q2/Q9）。
- `tree_leaves` 的 `..tree_leaves(...)` 是“元组推导式元素展开”，把子树的叶子元组拼平；这是步骤 6 的一部分。
- `tree_reduce` 旧实现只接受“一棵树 + 初值”（`tree.cpp:55-59` 要求正好 2 个 norm），所以新签名**没有 rest**；不要给它加多棵树，否则是新增行为而不是等价改写。`static loop` 用 `struct | tuple` 合并两个分支，字段顺序由 `fields T` 保证。
- 多棵树的形状检查：`tree_map` 开头调 `same_shape(t, ..ts)`。`same_shape(a: typeas A, ..bs)` 对每个 `bs.[j]` 调 `check_one(a, bs.[j])`；`check_one(a: typeas A, b: typeas B)` 是**以 A 为基准**的检查：A 是内部节点时，B 必须是同 kind、同 arity、字段名集合相同；A 是叶子时停止（B 可以是任意聚合值，旧 `tree_map` 的叶子回调就是这么做的）。实现约 20 行：`match type A`，struct/tuple 分支里双向遍历字段（对 `fields A` 的每个 `n` 取 `b.[n]`，再对 `fields B` 的每个 `m` 取 `a.[m]`），然后递归；缺字段/多字段都会在正确的路径报 `tree structure differs`。**字段顺序**的严格检查需要 `static for` 的索引/zip（见 Q5）：双向存在性检查能发现缺/多，但 `{a,b}` 与 `{b,a}` 会被当成同形；旧 `tree.cpp:110-113` 会报“字段名或声明顺序不同”。第一期先记录为已知差异，测试只覆盖缺/多/kind 不一致。`tree_unzip` 用 `check_one(reference, values)`（基准是 reference）；它在 reference 的内部节点要求 values 同形，在 reference 叶子处允许 values 是分量元组。`same_shape`/`check_one` 不返回值，所有分支静态展开，运行时无节点。
- `tree_map` 的 `f` 是步骤 7 的可调用绑定；`f(t, ..ts)` 在叶子按实际类型解析。
- `tree_unzip` 的 `sample = leaves.[0]`：`leaves` 的类型是叶子元组的元组；`.[0]` 取第一个叶子元组，`indices sample` 得到分量数。空树没有 `.[0]`，用 `static error "unzip tuple arity cannot be inferred from an empty reference tree"` 匹配旧消息。`rebuild` 在 reference 的每个叶子取 `values.[j]`；如果某个叶子的分量数少于 sample，`.[j]` 报越界。旧实现的 `tree.cpp:175-186` 还要求每个叶子元组 arity 与第一个一致；`same_shape(reference, values)` 只检查树形状，不检查叶子元组 arity，因此再加一个 `check_leaf_arity`（约 10 行，`match type R` + 叶子处比较元组 arity）或在 `rebuild` 的 `.[j]` 越界处报同一消息。第一期优先后者，测试覆盖“短元组”的负例。
- `tree_leaves` 对叶子返回 `(t,)`（1 元组）；空结构返回 `()`；与旧 `leaves` 向量一致。

## 7. 只有语言作者能定的问题

每条给建议；建议不是既定语义，未定前不实现。

**Q1. `with` 函数实参的语义：运行期函数值，还是编译期可调用绑定？**

- 背景：`tree_map<twice>`（泛型函数）与 `tree_map<bump>`（重载集合）无法在 `tree_map` 这一层定成一个具体函数类型；当前 `tree.cpp` 按叶子重新解析。
- 选项：
  - (a) 函数类型的 with 参数是**编译期可调用绑定**：不建运行期端口，每次调用按实参类型解析；当值使用时只有具体函数可物化，泛型/重载报错；
  - (b) 新增 `with <f: callable>` 或 `with <f>` 的类型，明确“只可调用”；
  - (c) 只允许具体 lambda/单态函数作为 with 实参，`tree_map<twice>`/`<bump>` 改为 lambda 包装（会改变设计稿 3.1.1 与现有测试）。
- **建议 (a)**：它最接近现有 `tree.cpp` 行为和设计稿 3.1.1，不新增源语法；把“可调用绑定”写成一条语言规则，并明确“当值使用”的限制。若作者认为 with 参数必须是值，则 (b) 更显式，但需要新的类型种类；不建议 (c)，它会丢掉现有测试覆盖的用法。

**Q2. `constas` 值参数与无类型的 `..ts` rest 参数是否属于第一期？**

- 背景：设计稿 3.1.1 的 `column(constas n, ts)` 需要把字段名 `n` 作为编译期值传进 helper；`tree_unzip` 的 `rebuild(j, ...)` 需要 `j` 作为编译期下标。设计稿的 `tree_map(t: typeas T, ..ts)` 又没给 `ts` 写类型，且各棵树的类型可以不同（`tree_map(p, tuple_tree)`），所以本计划按“rest 参数无类型、调用点给出元组”实现。
- 选项：
  - (a) 加 `constas name: T` 函数参数；rest 参数无类型（本计划）；
  - (b) 不加 `constas`，`column` 内联，`tree_unzip` 等第二期类型位置；
  - (c) 给 rest 参数加类型（逐元素同型或整元组），`constas` 另议。
- **建议 (a)**：`constas` 复用已有概念，设计稿已经这样写；rest 无类型是设计稿 `..ts` 的直接读法，也避免“异构 rest 用一个元素类型”表达不了的问题。代价是实例键多一个值维度、rest 函数必须展开；需要测试。若作者认为超出第一期，H51 的 `tree_unzip` 需要降级为“保留 C++ 实现”或等第二期，这会与第 2 项“五个都改写”冲突，必须明确。

**Q3. `static for`/`static loop`/带 rest 的函数是否必须自动内联？**

- 背景：rest 没有运行期 ABI；静态展开如果不内联，会留下对实例的 `CALL`，autodiff/Tiles 看到的图就变了。
- 选项：
  - (a) 含 `match type`/`static for`/`static loop`/rest 的函数实例**一律内联**，用户不写标注；
  - (b) 只在调用点需要时内联，其他保留 `CALL`；
  - (c) 用户显式 `inline` 标注。
- **建议 (a)**：与设计稿第 7 条一致；在步骤 8 实现，rest 函数因无 ABI 必须走这条。若作者担心编译期成本，加节点/深度预算（步骤 8），而不是保留运行期 rest。

**Q4. 诊断是否必须与旧 `tree` 逐字节相同？`static error` 能否拼接路径/自定义标签？**

- 背景：旧 `tree.cpp` 的 `fail` 产生 `tree leaf 'block'` + `tree structure differs`；新库用 `static error` 只能给字符串字面量（本计划第一期）。`test/plans/feat/modules/tree.plan.toml:21` 断言这两个子串。
- 选项：
  - (a) 只要求程序 stdout 逐字节；诊断保留位置/路径/语义，措辞可变；更新该断言；
  - (b) 诊断也逐字节；`static error` 需要支持编译期字符串表达式/路径标签，或库保留一个专用诊断入口；
  - (c) 折中：`static error` 只接受字面量，但编译器把当前静态路径作为 related label，测试断言路径与消息关键字。
- **建议 (c)**：既不把路径变成字符串表达式，也保留 `blocks.1.w` 这类信息；`tree structure differs` 作为 `static error` 的字面量可保留，`tree leaf '...'` 作为编译器标签格式统一。若作者要求 (b)，步骤 9 需要额外设计。

**Q5. `fields T` 的第三个绑定 `tags` 与字段顺序检查，第一期做到什么程度？**

- 背景：设计稿第 6 节说需要字段标签时写 `(n, F, tags)`；H51 的五个函数不需要 tags。另一方面，旧 `tree.cpp:110-113` 会检查其余树的**字段声明顺序**，而只用 `(n,F)` + `t.[n]` 的双向存在性检查分不出 `{a,b}` 与 `{b,a}`。
- 选项：
  - (a) 解析 `(n,F,tags)`，但 tags 绑定为空（或 `string` 元组），完整标签第二期；字段顺序差异第一期不报（已知差异），测试只覆盖缺/多/kind；
  - (b) 第一期只接受 `(n,F)`，写三个报“第二期”；同时为 `static for` 加一个索引绑定（如 `(i,n,F)`）以严格检查顺序；
  - (c) 完整实现 tags 与顺序检查。
- **建议 (a) 或 (b)**：H51 的五个函数不依赖 tags；如果作者要求 `tree_map` 的负例与旧实现完全一致（包括字段换序），选 (b) 的索引绑定；否则 (a) 足够，并在计划里把“换序不报”记为已知差异。不要为了顺序检查引入 type-level zip。

**Q6. `static` 是否成为保留关键字？`fields`/`struct`/`tuple`/`error` 呢？**

- 背景：`scripts/check-grammar.mjs` 与语言参考有完整关键字表；`static` 作为修饰符/构造前缀，冲突面较大。
- 选项：
  - (a) `static` 保留；`fields`/`struct`/`tuple`/`error` 上下文关键字；
  - (b) 全部保留；
  - (c) 全部上下文。
- **建议 (a)**：`static` 是语义修饰符，保留最清晰；其余只在固定位置出现，上下文关键字避免破坏现有标识符。需要更新关键字文档/检查脚本。

**Q7. `tree` 内建模块改名 `ckpt`，公开 API 由 `stdlib/tree.cml` 承担，可以吗？**

- 背景：文件模块遮蔽内建模块；不改名则 `save_tree`/`load_tree` 消失。
- 选项：
  - (a) 内建改名 `ckpt`，`tree` 成为 Camel 库，`save_tree`/`load_tree` 做包装；
  - (b) 保留内建 `tree`，五个函数放到新模块 `tree_ops`，用户改 import；
  - (c) 把 checkpoint 也搬进 `nn` 或其他模块。
- **建议 (a)**：保持 `import tree` 的用户 API 不变，只把实现拆开；`ckpt` 的 URI/CMake/文档一次性改完。若作者不希望改内建模块名，(b) 是退路，但五个函数就不再是 `tree` 的名字，与 H51 第 2 项的表述不符。

**Q8. `optim` 的 API 与 `nn`/ONNX 兼容面？**

- 背景：任务要求删 `nn` 的 C++ 优化器；ONNX 训练导出识别 `nn:sgd`/`nn:adam`（`modules/onnx/lowering_grad.cpp:747-749`）；C2 用 `adam_state`/`adam`。
- 选项：
  - (a) `optim` 用 `sgd_init/update`、`adam_init/update`、`adamw_init/update`，`nn` 保留 Camel 包装（签名不变），ONNX 暂时识别包装/展开图；
  - (b) 删除 `nn` 包装，所有调用点改 `optim`，ONNX lowering 改为识别 `optim` 展开后的图；
  - (c) 保留 `nn` 的 C++ 算子专门给 ONNX，其他走 `optim`（与“删 C++ 优化器”冲突但最稳）。
- **建议 (a) + 后续 (b)**：先保 API 兼容，ONNX 用展开图/包装兜底；C++ 优化器可以删，因为包装是 Camel。ONNX 的具体识别方式需要作者/ONNX 负责人确认；若短期做不到，(c) 作为临时门禁，不要静默删。

**Q9. `tree_unzip` 是否必须第一期改写？若返回推断无法表达“树的元组”，是否提前类型位置？**

- 背景：设计稿归档 Q10 说 `tree_unzip` 的结果类型需要类型位置；H51 第 2 项要求五个都改写。本计划用 `leaves.[0]` 的类型 + `indices` + `constas j` 试写，但这是新机制的组合。
- 选项：
  - (a) 按本计划试写；能过就第一期完成，不能过则 `tree_unzip` 暂留 C++ 并记录例外；
  - (b) 提前做类型位置（与第 4 项“第二期”冲突）；
  - (c) 改 `tree_unzip` API，让调用者提供分量数/类型。
- **建议 (a)**：先用最小例验证；返回值推断如果能表达“tuple of structs”，就不需要类型位置。若失败，宁可把 `tree_unzip` 标为 H51 例外，也不要在第一期仓促做类型函数。需要作者认可“五个中四个 + 一个例外”是否可接受。

**Q10. 未选 `match type` 分支的名字解析是否也要延迟？**

- 背景：GCT 仍会对未选分支做名字解析；设计稿说“不建图、不做类型检查”，没说名字解析。
- 选项：
  - (a) 只延迟 GIR/类型检查，GCT 名字解析仍做（本计划）；
  - (b) 未选分支完全延迟到选中时，需要 AST 保留/重新降级，改动大。
- **建议 (a)**：与 `if constexpr` 的常见实现一致；文档写明限制。若作者要求 (b)，步骤 1 的工作量显著增加，需要单独立项。

**Q11. 性能验收用节点/算子计数还是墙钟时间？**

- 选项：
  - (a) 图结构（节点/边/算子/调用/闭包/分支计数）+ 行为 golden，不设时间门槛；
  - (b) 加墙钟上限；
  - (c) 只用行为测试。
- **建议 (a)**：`std::stats` 与 P1/P2/P3 是稳定、可复现的验收；时间只记录不断言。若作者要性能门槛，另立基准计划，避免 H51 因机器波动红。
