# 变换引擎用 Camel 实现（施工计划）

> 决策者 2026-11-18，负责人同日定："变换引擎尝试用 camel 实现，C++ 实现的不着急删，用来对比实现。"方向依据：11-07 负责人"图变换用 Camel 自己写，C++ 只留小图内核"。车道 J，排在车道 A（看不到写法，同在 `stdlib/graph.cml`）合入之后。

## 第一步：图编辑接口补齐已定的算子

编辑块的语法已定（`docs/design/graph-editing/README.cn.md` 第 15 节，负责人 2026-11-18），算子也已定：`inline`（调用并当场展开）、`outline`（把一段收回成函数）、`order`、`replace`、`erase`、`eval`，以及读出顺序边、同步边、区域归属的查询。先在今天的接口（`stdlib/graph.cml` 的草稿与提交）上把这些算子补齐，提交走同一个检查入口（六项检查）。编辑块语法定下后，算子不变，只换外壳。

## 第二步：用 Camel 写 `reinterp`（前向求导）

`stdlib/` 下新文件，一个 Camel 函数：读被变换函数的图，逐个节点按规则集把右侧 `inline` 进来，效应骨架（访问节点、出口 `GATE` 的尾随写、同一资源上的先后）原样照抄，访问类原语按规则集一对一解释。规则集用现有的 `stdlib/rulesets/jvp.cml`。

## 第三步：`split`、`transpose`、局部 `Ref` 化成值

同样用 Camel 写：`split` 用事实分出"只依赖现在已有输入"的部分，`outline` 成前向、线性两段，效应骨架全部进前向；`transpose` 沿线性部分倒着 `inline` 转置规则；局部 `Ref` 化成值是把每次 `get` `replace` 成它所接那次写存进去的值，再删掉 `set`（"`Ref` 不逃出函数"写成事实）。

## 对照验收

C++ 实现保留，作对照：
- 同一批用例（`test/plans/feat/compile/transforms.plan.toml`、`autodiff` 相关、变换嵌套的验收用例），Camel 引擎与 C++ 引擎产出的图规范形式相同（`same_graph`），运行结果相同；
- 不同时逐条列出，判定哪边对；
- 记录两边的变换耗时，供以后决定是否删除 C++ 实现（删除要负责人点头）。

## 补充（2026-11-18 21:30，ECOOP 一侧提醒）

`reinterp` 会改每个节点的类型，只靠"增删形参、换出口值"不够：在被变换函数的草稿上逐个 `replace`，每一步都会因新旧类型不同被当场拒绝。做法：**不在原函数的草稿上改，而是另建目标函数**——用 `view` 读源函数的图，对一个目标类型的空壳函数（如 `(x: A, dx: A') => fail("unbuilt")`，类型就是 `Reinterp<F, H>`）开 `edit`，按源图的拓扑序逐个把规则右侧 `inline` 进来，最后 `replace` 出口；提交对照目标类型检查。效应骨架按源图一比一照抄进目标图。`split`、`transpose` 同理。
