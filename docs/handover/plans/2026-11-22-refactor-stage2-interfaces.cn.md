# 重构阶段 2 施工计划：接口先行

依据：重构总方案（已定）第 1 节阶段 2；核心抽象第 1–4 节（已定）。现状读数来自一次只读盘点（2026-11-22，按搬家前的路径记）。阶段 1 关窗后开工。

本阶段只做两件事：**把两份接口写成最终形态，先架在现有表示上，再迁几个最能检验接口的使用者**。大规模迁移与换实现是阶段 3。

## 现状里与接口有关的事实

**图**
- 两种表示：冻结的 `GCGraph`（`runtime/graph.h`）与可变的 `GraphDraft`（`runtime/draft.h`，外加 `GraphTransaction`、`DraftNodeRef`、编辑会话、建图器）。两者共用一套词汇（节点编号、`GCNodeKind`、`GCRegion`、`PortRole`），但读法各一套。
- 节点种类 16 个：Data、Port、Cast、Copy、Fill、Accs、Brch、Join、Call、Bind（保留未用）、Func、Oper、Gate、Dref（仅草稿）、Loop、Dead。
- 结构化控制流是"平铺的节点 + 区域表"：BRCH 与 JOIN 互相指认，分支臂与循环的条件/体是区域表里的行，每个节点另有一列区域编号。
- 边：每个节点一段输入（普通、`with`、控制），顺序边与同步边放在两张侧表里。
- 能推导却存着的：BRCH↔JOIN 互指与重复的臂数、入口/出口/返回节点、`GCOperBody` 里缓存的内核指针、草稿急切维护的反向使用表。
- 成对各写一份的谓词：`LoopView`/`LoopDraftView`、`decidingRegionOf`/`decidingRegionOfDraft`、标签与权限的两套重载；`ControlRegions`、`NodeRoleRegistry` 只认冻结的图。
- 已有的 `GraphRead`（`compile/gir/graph_read.h`）是两种表示之上的一个小读面，只覆盖求导提升与编码自检用到的部分，没有顺序边、同步边、区域、循环。
- 读冻结图最多的：`src/runtime`、`passes/trans`、`passes/test`、并行后端、`execute`、`modules/transforms`；三个执行后端只读冻结图。

**算子与事实**
- 中心是 `OperatorTable`，按 `OperId` 存每个算子一条 `OperatorSemantics`，外加解析器、折叠器、原位形式、复用提示等旁字段。
- 存在两处以上的性质：效应（`sem::Effect` 与 `module::OperatorPurity`）、宏（算子、节点标志、图标志、标签四处）、解析器（表与 `OperatorGroup`）、逐元素（标志与 `elementCalls`）、权限（声明、标签、节点三层）；导数规则按字符串名字存，其余全按 `OperId`。
- 事实框架（`runtime/facts.h`）已有种类登记、每个程序一个存储、按版本戳懒失效；但**锚点只能是冻结的图**，草稿上不能挂事实。效应汇总、使用索引、执行计划、`ControlRegions`、写法提取这几样分析各自缓存在框架之外。

## 2.1 图的读接口（图车道）

**接口的形状**（核心抽象第 1、2 节）：
- 一个只读视图 `GraphView`。冻结的图与编辑会话都给出它；所有谓词只对视图写一份。
- 视图上的节点种类**正是九种**：DATA、PORT、OPER、FUNC、CALL、BIND、BRCH、LOOP、GATE。今天多出来的在视图里这样呈现：
  - Cast、Copy、Fill、Accs 不再是节点种类：它们就是普通算子，在 `lib/std` 里像其他算子一样声明（签名、`panic`、效应），前端建图时直接生成 OPER（见 2.3）；
  - JOIN 不出现，它的输出就是 BRCH 的输出；
  - Dref、Dead 是存储内部的东西，不出现在视图里。
- 结构节点**拥有区域**：BRCH 有若干臂，LOOP 有条件与体，每个区域有自己的参数端口与结果；视图按"节点 → 区域 → 区域里的节点"往下走。今天的区域表与 BRCH/JOIN 互指，由适配层翻成这个样子。
- 边**三种**：数据、同步、顺序。今天的控制输入在视图里不再是边，它表达的东西由"节点属于哪个区域"给出。
- 端口**按名字分组**：普通组、`with` 组；输入、输出、使用者都按组取，不再用"一段里的第几到第几"。
- 视图只给能存的，不给能推的。入口、出口、使用者、所在区域这些推导量都作为视图上的查询，由适配层算出或从现有缓存取，**不进接口的数据成员**。
- 节点编号：视图上的节点编号在同一条版本线上稳定（第 2 节）。适配层暂时直接用今天的编号。

**适配层**：冻结图与草稿各一个，放在图车道的目录里；它们是过渡的，阶段 3 换实现时删掉。

**一致性检验**：对测试计划里每个能建图的程序，在冻结图上与把它解码成的草稿上，跑同一组视图查询，比较结果逐项相同。这是视图"只写一份"的保证，进快层。

**第一批迁移的使用者**（检验接口够不够用，迁完即删掉被替代的那一份）：
1. `GraphRead` 的全部使用者（求导提升、编码自检）。迁完后删掉 `GraphRead`。
2. 成对的谓词：`LoopView`/`LoopDraftView`、`decidingRegionOf`/`decidingRegionOfDraft`，各合成一份写在视图上。
3. `ControlRegions` 与 `NodeRoleRegistry` 改为接受视图，从而草稿上也能用。

**完成**：
- 视图头文件评审通过；
- 两个适配层合入，一致性检验进快层且全绿；
- 第一批三项迁完，被替代的那几份已删除；
- 差分工具在改前改后两个提交上比对，无差异。

## 2.2 算子记录与事实框架的接口（算子与事实车道）

**算子记录**（核心抽象第 3 节）：
- 每个算子一条记录，按 `OperId` 存。记录有两个同等的入口：Camel 声明，和一套完整的 C++ 登记接口。C++ 的登记接口不依赖 Camel 声明也能单独用，方便第三方库作者用 C++ 实现 Camel 算子。
- 基本性质由关键字表达：`uses`、`pure`、`panic`、`T!`。`panic` 在 C++ 接口里是必填字段。
- 标签不在记录里，它们是图上的信息。
- 今天存在两处以上的性质，在记录里各只留一处：
  - 效应合一，`OperatorPurity` 并入效应；
  - 宏只留在记录里，节点标志、图标志改成从记录推出；
  - 解析器只留在记录里，`OperatorGroup` 只做分组；
  - 逐元素只留一种表达；
  - 导数规则改按 `OperId` 取，不再按字符串名字。
  - 权限的三层是否合并，在本步的评审里定：声明是记录的性质，标签是图上的信息，节点上的那一层看是不是推导量。

**事实框架**（核心抽象第 4 节）：
- 锚点改为 `GraphView`，冻结的图与草稿上都能挂事实。冻结版本上的结果长期复用，草稿上的结果随会话结束丢掉。
- 事实声明自己依赖什么（读了哪些节点与区域、读了哪些名字绑定的哪张图、读了哪些算子记录），按依赖失效。
- 本步把接口定下来，现有的种类迁到新接口上。框架之外那几样分析（效应汇总、使用索引、执行计划、`ControlRegions`、写法提取）**只登记为事实种类、由现有代码算**；把它们的计算挪进事实框架，是阶段 3 的事。

**完成**：
- 记录与事实框架的头文件评审通过；
- C++ 登记接口能单独登记一个算子，不写 Camel 声明也能被调用，并配一条用例；
- 上面列的重复性质各只剩一处；
- 现有事实种类迁到新接口，草稿上能挂事实，并配一条用例；
- 差分工具比对无差异。

## 2.3 四种节点改成普通算子（前端车道牵头，各车道迁自己的读者）

**为什么**：Cast、Copy、Fill、Accs 做的事都是算子的事（类型转换、复制、按元素构造、取成员或元素），单独作为节点种类，只会让每个读图的地方多四个分支，变换、后端、打印各写一遍。它们是普通算子，就不需要单独分类，也不需要"内建算子"这样的特殊身份。

**做法**：
1. 在 `lib/std` 里声明这四个算子（取成员的位置、构造的目标类型等写成算子的编译期参数），C++ 实现走普通的登记接口。
2. 前端建图时生成 OPER，不再生成这四种节点。
3. 读这四种节点的地方（约 60 个文件：`kernel/runtime` 12、`compile` 10、`lib/transforms` 8、`lib/test` 5、`lib/tiles` 4、优化遍 3，其余各 1–2）各由所在目录的车道迁走：需要知道"这是转换/复制/构造/取成员"的，问算子记录或按算子编号写规则，不按节点种类分支；后端要的快路径由算子的实现给出。
4. 最后一个读者迁走的那次合并里，从 `GCNodeKind` 删掉这四个种类。

**完成**：节点种类表里没有这四项；差分工具在改前改后两个提交上比对无差异；性能计划的读数不退。

## 车道与冲突

| 车道 | 做哪件 | 独占的目录（搬家后） |
|---|---|---|
| 图 | 2.1 | `kernel/graph` |
| 算子与事实 | 2.2 | `kernel/ops`、`kernel/facts` |
| 变换 | 2.1 第一批迁移的第 1 项（求导提升）；2.3 里自己目录的读者 | `lib/transforms` |
| 前端 | 2.3 的第 1、2 步 | `parse/`、`compile/` |
| 合并位 | 合并、一致性检验进快层、闸门 | 公共文件 |
| 其余车道 | 按所有权表各自收尾，不动这几块 | 各自目录 |

两条接口车道互不依赖，同时开工。2.3 与它们并行：视图从一开始就只有九种节点，2.3 完成前适配层暂把这四种节点当 OPER 交出，2.3 完成后这段映射随四个种类一起删掉。

**评审**：两份头文件由决策者逐行审，写成审查页上的一节。只把触及原则的问题拿给负责人，例如权限三层的合并若改变了用户可见的语义。
