## declaration-cost-gate（启动与声明成本的闸）

- **(a) 改量 CPU 时间，不量墙钟。** 共享主机上的墙钟随负载漂移，这正是 40/45/100/90 ms 在负载 106–130 下报红的原因；进程的 CPU 时间（用户态 + 内核态）基本不随负载变（H167 的判定已经用 CPU 中位数）。四条命令的天花板改为按 CPU 时间、取安静主机中位数加余量；"负载下红不算回归"的口径因此不需要。
- **(b) 选 3 + 2**：结构断言"每个（阶段, 模块）每轮恰好出现一次"管重复编译；绝对的 CPU 总量管整体变慢；30% 共享率这条线退休。

## loop-state-struct-shapes（哪些结构体可以做循环状态）

- **(a) 允许空结构体状态**：它是"按叶子拆成分量"的零叶子情形，不加规则、不加诊断。
- **(b) ONNX 导出对带数组字段的携带状态保持拒绝**，等原生多维数组（H17 第 2、4 项）把形状的说法定下来再处理定长数组。

## module-type-variable-argument（类型变量做模块类型的实参）

## impl-kernel-site（第一批标准库 `#impl` 的内核在哪声明）

- **选 (a)，而且取宽的那一种：声明模块可以有函数体**，`DeclarationModuleHasBody` 删除。理由不是便利：H94 已定"与 `.cmo` 同名的 `.cml` 和它是**同一个模块**"，设计原则 10.4 又要求"其余一切用 Camel 定义"——`tensor` 模块的 softmax、`log_softmax` 这类组合本来就该是 `stdlib/tensor.cml` 里的 Camel 定义，与它的原生算子声明放在一起。一个模块 = `.cml`（声明与 Camel 定义）+ `.cmo`（原生内核），"声明模块不许有函数体"与这两条都冲突。(b) 仍然拒绝：一个模块不写别的模块的签名。

## reduced-precision-text（bf16/f16 的文本）

**(i)，按值自己的类型求最短。** 7.7 的"最短、且读回来得到同一个数"是逐类型的规则——f32 打印 `0.1` 而不是 `0.10000000149011612`，正是因为"同一个数"指那个 f32；bf16/f16 是同等的浮点类型，同理 `0.1 as bf16` 打印 `0.1`。今天的 `0.100097656` 是把 bf16 当成 f32 来打印，不是规则的另一种读法。

- 实现成**一个**按格式参数化的最短文本（逐位数试到按该类型舍入读回同一个元素），f32/f64 的现有实现若能并入同一个就并入；排版规则只有一份。
- 所有转文字的路径都走它：`println`、`HalfData::toString()`、`format`、字符串插值、复数的分量、`--inspect` 的常量文本（规则统一）。
- 同一个数用 bf16 与 f32 打印可能得到同一个短文本，这是规则的必然结果。
- 用例：`reduced_scalar.cml` 的期望改为 `0.1`；再加几条——bf16 与 f16 的最大有限值、最小正规格数、次正规数、`1/3`、负零——各自按类型读回同一个元素（性质断言），不是钉文本条数。

## tensor-impl-kernel-type-rule（`log_softmax` 的内核签名）

**(b) 的正确版本：元素类型泛型加 `when` 限定为浮点。**

```camel
#impl<tensor:log_softmax>
export func log_softmax::<T>(x: Tensor<T>, axis: int? = null): Tensor<T> when is_float::<T>() { ... }
```

- 这不是假签名：`softmax` 本来就是浮点运算。今天整数张量进来、出去 f32，是一次隐式转换，按 7.x"没有隐式数值转换"本就不该有；整数张量不再接受（不计兼容），要用就先转成浮点。
- f64 进 f64 出，保持今天的行为；bf16/f16 进同类型出（内部在 f32 中算、舍入一次，与标量规则一致）——这正是 bf16/f16 成为核心类型后该有的样子。
- **不选 (c)**：类型规则写在 C++ 里、声明只"命名"它，读者看不到这个函数接受什么、返回什么，违背 10.4（语义在 Camel 里）与 4.4（适用条件只用 `when`）。H151 那句"元素类型跟随参数的签名不能作为声明"在类型参数头部声明与 `when` 落地后已经过时，删掉。
- 导出：公开的名字就是这个 Camel 定义；C++ 组是它的 `#impl` 内核，不再以同名单独导出，所以不需要"同名 Camel 定义遮蔽 C++ 组"的例外——把 `builder_modules.cpp` 那处守卫改成"带 `#impl` 的定义取代它所引用的组"。`softmax` 与其它"类型规则由内核决定"的张量算子按同一写法迁。
- ONNX 的 `LogSoftmax` 降级照旧（按内核的语义），元素类型从签名读。

## array-kernel-executors（`array::sum`/`min`/`max` 的执行器）

**A，但不新增第三份陈述。**

- `array:sum`/`min`/`max` 是数组**归约**的实现原子，与 `math:min_bf` 一类**标量二元**运算不是同一个东西——后者算两个数，前者沿一个数组做一遍归约（含 f64 累加、舍入一次，设计原则 7.7）。数组模块自己的归约内核放在 `array` 的执行器组里，是 10.4 说的"热点定义带 `#impl` 内核"的标准形态，不是重复。

## declared-extent-reaches-the-call（声明写下的 extent）

**A + D，这些都是设计原则 5.4 已经写下的规则，不需要新裁定。**

- **声明写下的形状就是值的类型**：`let a: f32[3] = …` 之后 `a: f32[3]`。数组字面量的长度静态已知，所以字面量本身就是 `f32[k]`；`let x: f32[4] = [1.0, 2.0, 3.0]` 与 `count([])`（`f32[4]` 的位置）是编译错误（`DimensionMismatch`）。`var a: f32[3]` 不能 `append`——5.4 已写明 `f32[3]` 不可追加；要可追加就写 `f32[]`。类型是你写下的，不是"给读者看的"。
- **形状未知的数组进入声明了形状的位置不隐式放行**（5.4 原文）：`f32[]` 的实参进 `f32[n]` 或 `f32[4]` 的形参是编译错误，诊断提示用 `as` 显式转换，转换处在运行时检查。今天"既不绑定也不补检查、直接放行"是缺陷。`dot(a, b)`（`f32[3]` 与 `f32[2]` 进 `f32[n], f32[n]`）报 `DimensionMismatch`。
- **D：同一条规则覆盖每种写出 extent 的方式**——字面量、维度名、`constas` 值参数、`Tensor<T, [n]>`。`total(4, [1.0, 2.0, 3.0])` 报错；数组与 `Tensor` 两条路走同一个检查（规则统一）。
- 验收：上面五个复现各一个用例（正、反各有）；`as` 的运行时检查失败给出位置；已有的 `err_call_*` 用例不变。

## h242a-capture-order-edge

**选 1，并把同一个形态用到 `:var/get` 上**——读一个 `var`，无论直接读还是经被调函数捕获读，都是一条**数据边，从最近一次写来**。

- 每次写（`:op/assn_l`，以及写了捕获变量的调用）产出这个变量的新版本；**读**（`:var/get`，以及读了捕获变量的调用）有一个数据端口，接到书写上最近一次写的产出（没有写过就接到建 cell 处）。被调用的调用节点上，这个端口的角色是"捕获"（端口角色除普通、上下文外再加这一种，来自被调函数的捕获表）。

## generic-rule-instantiation（泛型规则在哪里实例化）

**选项 2：在匹配处实例化，按类型缓存。** 这就是设计原则 5.5 的泛型模型本身——"每用一组具体类型调用，就实例化出一张类型全部具体的子图"——规则的"调用处"是匹配处。它不是"运行时单态化"：改写遍运行时，被改写的图上只有具体类型，`T` 从被匹配节点的类型绑定，和函数从实参类型绑定一样。

- **规则值**：泛型规则的 `Rule` 值带着它的模板（与泛型函数的模板是同一个东西）。规则集照常写 `[add_zero, mul_one, …]`，不写类型实参。
- **匹配**：先按结构匹配，模式变量绑定到节点；从这些节点的类型解出 `T`（解不出或冲突则不匹配）；以类型元组为键查缓存，没有就调用前端的泛型实例化得到具体的规则（模式、条件、右边），存入缓存；`when` 是编译期谓词，每个类型元组求值一次、随实例缓存。
- **不选 1**：`[add_zero::<int>, add_zero::<i32>, …]` 只是把重复从规则库挪到了规则集里，而且用户自己的数值类型（满足 `is_integer` 的）永远进不了标准库的规则集。**不选 3**：H232 的验收说的就是"同一条律只写一次"，按元素类型的重复正是它要去掉的。
- **`check`**：泛型规则对每个已登记、满足 `when` 的类型各检验一次（与第 8 节"算子变量对每个满足条件的已登记算子各检验一次"同一条）。
- **`explain`/`why_not`**：报告实例化用的类型，以及 `when` 在该类型上为假时的原因。
- **验收**：`stdlib/rules.cml` 的 int/i32 两份、float/f32/tensor 各份合为一条泛型律（条件与许可不同的除外，如浮点零律要 `finite_math`）；用户在测试里定义一个满足 `is_integer` 的类型，标准库的 `add_zero` 对它生效。

另：结合交换匹配（多重集读法）、按律去重（98 → 69 条）、改写不丢效应的引擎检查都已落地，测量用例改成了正确的期望——做得好。

## inline-order-after-body（内联之后，下一条语句靠什么排在函数体之后）

**(C) 的形态：内联进来的函数体是同步链上的一个单元——它的区域整体占据原来那条调用语句的位置。** 不选 (A)、(B)：

- (A) 把函数体的语句并入同步链，会让函数体里本不执行的效应执行（同步边传递"被用到"）。函数体不是同步块，按 F17 它的效应只在被它的结果用到时执行；内联不能改变这一点。
- (B) 让顺序边上纯节点，破坏 4.6，而且仍不够：3.4 规定同步块对纯计算也排序（计时），函数体里**纯**的部分也必须在前一条语句之后、后一条之前——只给效应节点加顺序边排不住它们。

**规则**（写进 `edges.cn.md` 第 5 节第 7 条）：

- 内联已经给函数体一个区域（`7ca495665` 说的"the region the body was given"）。这个区域**作为一条语句**挂在调用者的同步链上：同步边可以连到区域本身——链上的前一条语句 → 区域 → 后一条语句，记在区域上，不连到区域里的节点，所以"同步边不跨出区域"照旧成立。
- 含义与臂、循环体一致：区域里要执行的节点都在区域的同步前驱之后、同步后继之前；区域里**哪些**节点执行，按函数体自己的规则（从区域的结果出发，沿数据边与区域内的同步边可达），同步链用到的是区域的结果。
- 只在调用是某个同步块直接写着的语句时才需要；不在同步链上的调用，内联后直接拼接、不留区域。函数体全纯且调用不在同步块里时，区域可以被后续的遍溶掉。
- 区域对优化不设障：区域内照常做规则匹配、合并、删死代码；跨区域边界的数据边按现有区域端口的约定。
- 封存检查：区域级同步边的两端是同一块的相邻语句（或区域）；4.6 一字不改。`7ca495665` 里那条顺序边删掉。
