# 问题目录的答复（决策者 2026-10-23）

六个问题文件逐一答复，答完的文件已删除。

## declaration-cost-gate（启动与声明成本的闸）

- **(a) 改量 CPU 时间，不量墙钟。** 共享主机上的墙钟随负载漂移，这正是 40/45/100/90 ms 在负载 106–130 下报红的原因；进程的 CPU 时间（用户态 + 内核态）基本不随负载变（H167 的判定已经用 CPU 中位数）。四条命令的天花板改为按 CPU 时间、取安静主机中位数加余量；"负载下红不算回归"的口径因此不需要。
- **(b) 选 3 + 2**：结构断言"每个（阶段, 模块）每轮恰好出现一次"管重复编译；绝对的 CPU 总量管整体变慢；30% 共享率这条线退休。

## loop-state-struct-shapes（哪些结构体可以做循环状态）

- **(a) 允许空结构体状态**：它是"按叶子拆成分量"的零叶子情形，不加规则、不加诊断。
- **(b) ONNX 导出对带数组字段的携带状态保持拒绝**，等原生多维数组（H17 第 2、4 项）把形状的说法定下来再处理定长数组。

## module-type-variable-argument（类型变量做模块类型的实参）

- **选 A**：模块类型显式声明自己可参数化（`typeArguments()` 一类的标记，写进约定）；声明了的接受类型变量实参，没声明的照旧拒绝。`Device<T>` 与 `PyObject<T>` 由此同一条规则。写法按函数头声明：`export func py_wrap::<T>(x: T): PyObject<T>`，`py_wrap`/`py_unwrap` 搬进声明。

## pass-unavailable-diagnostics（模块在、遍不可用时的诊断）

1. **A**：模块加载失败时给专用的 `help`，说明是模块本身没加载成功（附它的第一条诊断），而不是讲参数写法。
2. 遍现在都是声明（H233 第 6 条）：**提供遍的模块必须在 `.cml` 里声明这些遍**，"它提供哪些遍"一律从声明读；`ckpt` 若提供遍，同样补声明。不再有"C++ 注册、诊断看不到"的一类，`onnx` 那句"provides no passes"的错话随之消失。
3. **保留两个码**：它们的修法不同（换个名字 / 补 `export`），不是同一个事实。

## perf-para-gate（并行一侧的性能闸）

- **选 B**：把已量过的便宜子集（`monte_carlo_pi.prl`，约 1.6 s）立成可进闸门的计划。度量取**同一次运行里并行对串行的加速比**（与绝对墙钟相比对负载不那么敏感），并记 CPU 时间；整条 `perf.para` 仍在发布前跑。

## precision-diagnostic-removal（`PrecisionChangeNotPermitted` 的去留）

- **选 (a)，接受删除**：裁定删掉的就是这条语义，仓库规定每个诊断码都要有生产者。
- 另做一件小事：`tiles` 拒绝"编译器引入的低精度"时，消息点名缺的是哪个许可（`change_precision` 等），而不是笼统的 "mixed GEMM permissions"。若以后需要具名的语义诊断，新分配一个码。

## impl-kernel-site（第一批标准库 `#impl` 的内核在哪声明）

- **选 (a)，而且取宽的那一种：声明模块可以有函数体**，`DeclarationModuleHasBody` 删除。理由不是便利：H94 已定"与 `.cmo` 同名的 `.cml` 和它是**同一个模块**"，设计原则 10.4 又要求"其余一切用 Camel 定义"——`tensor` 模块的 softmax、`log_softmax` 这类组合本来就该是 `stdlib/tensor.cml` 里的 Camel 定义，与它的原生算子声明放在一起。一个模块 = `.cml`（声明与 Camel 定义）+ `.cmo`（原生内核），"声明模块不许有函数体"与这两条都冲突。(b) 仍然拒绝：一个模块不写别的模块的签名。
- **泛型函数可以带 `#impl`**：内核是一条同样带类型参数的无体声明（`sum_kernel::<T>`），按 H228"一个算子、按类型的执行器"在实例化时选执行器；某个 `T` 没有执行器时，这个实例就执行函数体（函数体本来就是语义，结果相同），`std::profile` 标出它走的是哪条路。`ImplOnGenericFunction` 删除。
- 由此第一批：`array::sum`/`min`/`max`（泛型 + 按类型执行器）、`tensor` 的 `log_softmax`（`stdlib/tensor.cml` 里的定义 + 已有的 `tensor:log_softmax` 内核）现在都有了位置；Adam 等 `optim` 落地（H51 第 14 步）后接上。

## rule_when_const_node（条件里取 `const` 形参的节点）

- **选 1**：条件函数按 `const` 形参追加隐藏的节点形参，构建期把 `node_of(c)` 换成它；不引入新类型。确认语言表面：名字是 **`node_of(c)`**，只接受该规则（或 `fact` 的 `case`）自己的形参名。以后多根模式需要"整场匹配"时，再在这个基础上加，不提前造 `Match` 句柄。
- **报告里暴露的第二个问题是缺陷，一并修**：可交换算子的匹配会交换操作数顺序，带参数的事实查询却按顺序找"操作数正是这些部件的值"，找不到就让**整个遍失败**。两处都改：(1) 对声明了交换律的算子，部件查询不看顺序；(2) 条件里的事实查询找不到时，条件为假（这条规则在此不适用），而不是遍失败——条件本来就是"适用与否"的判断。

## h241-limits（H241 的三处实测边界与已合入的 F9）

这份问题写于边的模型定下之前。现在 H241 的第 1–3 项已并入 H242（图的边重构，设计稿 `docs/design/effects/edges.cn.md` 已定），以下按 H242 回答。

- **(0) F9 保留（A）。** 暂缓段写的本来就是"第 4 条照常做"，只暂缓改变哪些效应执行的部分；F9 不改变哪些效应执行。
- **(1) F1 的循环那一半是建图器的改动——并入 H242 第 2 步。** H242 本来就重写建图：只被一条臂或一个循环体用到的值，建图时就建在那个区域里，需要的区域端口由建图器建，计划生成器不再移动节点。臂的那一半也在建图时做，不在计划生成器里另做一份。`branch_arms.cpp` 与循环表的两条不变式不变——建图时就满足，它们照常校验。
- **(2) 只排序的边：要，规格就是第四种边——H242 已经这样定**（数据、同步、顺序；`Ctrl` 删除；存活只沿数据端口与同步边）。能红的用例是有的：同一资源上**前一个效应没被用到、后一个被用到**——
  ```camel
  func f(): int { let a = println(1); let b = println(2); return b }
  ```
  今天 `println(2)` 带一条从 `println(1)` 来的 `Ctrl` 边，两个反向闭包（`reportDroppedEffects` 与计划的存活）沿它把 `println(1)` 拉活，所以会打印 1。按 F1/F2 只打印 2。`effects_outside_sync.cml` 的 `returned()` 那条不红，是因为它没有后继效应。把上面这条加进 H242 的验收。
- **(3) F3：拆算子。** 这不是新的语言选择：F3 已经定了"读用到前面最近的一次写，没被读的写不执行"，剩下的是怎么实现。`var x = 1` 降为"建 cell"（不是效应，没有顺序边，被它的读写用到）加一次普通的写；写与写之间是顺序边，读用到最近一次写。未初始化的 cell 观察不到——`var` 必须有初值，任何读之前在书写上都有一次写，读用到的正是它。非捕获、不跨循环的 `var` 可以进一步完全化成值（每次写是一个值，读直接接到最近的写），这是优化，由施工方自定。
