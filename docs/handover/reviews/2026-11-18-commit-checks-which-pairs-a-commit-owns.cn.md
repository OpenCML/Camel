# 问：一张被改过的图，提交该为哪些「访问对」负责？

`2026-11-18`｜车道 `lane-txncheck`｜基线 `origin/develop = c5d5f4857`｜引 `7462ec953`（甲的插入计划）、`f71b62bb5`（乙改成按区域）

## 一、为什么必须问

计划里甲、乙两句话都是从**整张图**出发的：

```
甲：对草稿里每张改过的图，由节点推出足迹 ⇒ 足迹超出声明就拒绝
乙：对每张改过的图、每个资源：取所有访问它的节点；凡两者中至少一个是写、且可能同时执行的
    一对，要求图上有一条路径把它们排好先后 ⇒ 没有就拒绝
```

**⇒ 两句话都没有说「只算这次提交造成的那一对」。** 而按字面读，会出现一件**没人想要**的事：

```
一张图里本来就有一对无序的写（例如某个旧 pass 留下的），
今天没人管它；我这次提交只是把这张图里的一个常量改了个值 ⇒ 同一张图、同一对节点
⇒ 按字面读，这一对「没有路径排好先后」⇒ **这次提交被拒**，而它跟那一对毫无关系
```

**⇒ 于是「检不检查」变成了「这张图历史上有没有脏东西」**，而这正好是 checks 最容易变成噪音的形状：
一条谁都绕不过去的红，最后的处理方式是把它关掉。

## 二、为什么它是裁定而不是实现细节

两条路都能自圆其说，而它们**在读数上的差别是实质的**：

```
(a) **整张图**：提交是「这张图能不能发布」的问题，本来就有一对没排好的写 ⇒ 它就是不能发布，
    拒绝是对的，哪怕不是这次改出来的。**代价**：一张没被这次改动的图，会让提交红；
    而修它的人得到的信息是「有个我这次没碰的地方坏了」——这未必是坏事，但它是判定的改变。
(b) **只看这次造出来的节点**：提交只为自己造成的东西负责。**代价**：一次只调整了边的提交
    （例如只删掉一条 order 边）就有了「加了访问却没被算」的缝。
```

**⇒ 而 (b) 的缝是可以关掉的，只要把「这次提交造成的东西」定义准**：本次提交**新建**的节点
（引用在原图里不存在的那些）。删除一条 order 边是个例外——删除会把「排好的」变成「没排好的」，
而那不是新建节点。**⇒ 所以 (b) 的完整形状是：看新建节点 + 看被删掉的排序边；我只落了前一半。**

## 三、我按哪一条落的（默认建议）

```
**甲：整张图，每一次提交都问。** 甲是「这张图的体和它自己发布的类型对不对得上」——
    这与「这次改了哪里」无关：类型是提交发出去的承诺，体超出承诺就是这张图的问题。
**乙：只看这次提交新建的节点。** 一对里至少一个是本次新建的节点，才判。
    一次没有新建任何节点的提交，乙整个不问（公共编辑 `replace` / `erase` / `add_constant` /
    `eval` 都造不出带访问的节点，`replace` 还承诺「原来排好的顺序还在」，`stdlib/graph.cml`）。
```

**⇒ 落地位置**：两条都由 `camel::runtime::commitViolation` 回答，调用点在
`RuntimeGraphDraftSession::commit()`（`src/runtime/draft_session.cpp`）。**两条被点名的提交路径
在这里合成一条**：Camel 写的遍只能通过图模块重写，图模块的 `commit` 就是这个 commit。

**⇒ 分档**：`commitChecksEnabled()` 一格（发布版 `NDEBUG` 不问、debug 问、测试用
`setCommitChecksEnabled` 问），`camel::execute::camelPassCommitChecksEnabled` 读的是同一格。

## 四、如果作者要的是 (a)

改一处即可：`commitViolation(program, graph, made, askOrder)` 里把 `askOrder` 恒为 `true`、
`made` 传空（空 span 的语义是「每个节点都算」）。**代价必须先量**：

```

② 红的地方是「真的没排好」还是「我的区域判定把不同区域的节点当成了一对」
   —— 前者该修程序，后者该修我这个读数
```

**⇒ 这一条在没有量之前不要改**：它会把「甲/乙 上线」变成「先修一批旧图」。

## 五、一处必须先记下的判断依据

乙里「可能同时执行」我是**按区域**读的，不是按可达性：

```
区域的种类：body / Arm / LoopCond / LoopBody 各算一个区域；
Block / Inline / Dead 不算自己的区域（它们一定随父区域一起执行 / 是重写挖空的），
  它们的节点算在外层控制区域里；
一个区域的主人（BRCH / LOOP）在它所在的那个区域里代表它下面的全部节点
⇒ 同一个分支的两个臂里的访问**从不**被要求排序（它们不会都执行）；
  循环里的访问与循环外的访问**通过循环节点**排序（`f71b62bb5` 的细化）
```

**⇒ 而资源本身声明 `unordered` 的那些要放过**（原则 3.3：声明说顺序不要紧，就没有承诺可违）。
目前只放过一个：`stdlib/test_support.cml` 的 `rendezvous_point`。**这一条不放 `para` 计划会红。**
## 决策者答复（2026-11-18）

甲（整张图对照声明的效应）照你的默认，同意。

乙不按"只看新建节点"，也不按"整张图"，按**这次提交碰过的区域**：凡是有节点新建、删除，或有边被加、删、改接的区域，重查这个区域里的全部冲突对（按 11-18 定的口径：区域里直接的访问 + 代表下属区域的所属节点）；没碰过的区域不查。理由：
- 冲突的不变式本来就是按区域定义的（GNC："one region r"）。前端建图时编译器给冲突访问生成顺序边，所以每张图一出生就满足它；此后每次改动都经过提交，所以在归纳意义上，没碰过的区域仍然满足，碰过的区域才可能被破坏。查碰过的区域，与查整张图等价，代价只跟改动的范围成正比。
- 你页里第二节自己找到的那条缝——"删掉一条排序边会把排好的变成没排好的"——不止排序边：`replace` 改接数据边，也可能断掉原来经数据边排好先后的那条路径。按区域重查把这些一并覆盖，不需要逐种列举。
- "一张图里本来就有一对无序的写"按上面的归纳不应存在。若存在，说明有一条改图的路绕过了提交，那是缺陷：调试构建里加一个整图的断言（每次提交后对整张图跑一遍乙），抓到就报出是哪条路绕过的，而不是让下一次无关的提交替它背锅，也不是悄悄放过。
