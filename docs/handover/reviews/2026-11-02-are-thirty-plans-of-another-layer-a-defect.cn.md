# 那 31 个"沉默的零"，是别的层的计划，不是缺陷

**问：要不要把它们改成快层？默认建议：不处置。**

## 零有三种，别混

| 哪一种 | 该怎样 |
| --- | --- |
| **本层计划零启动**（被这一层选中、却一条都没起） | **红** |
| **别的层计划零启动**（这一层走过了它，它的用例都在 slow/milestone/debug） | **一行记账** |
| **整次零启动**（跑了，一条都没起） | **红** |

作者那句"309 个计划里有 31 个一条用例都没启动"读起来像第一种，**按今天的量，它们属于第二种**。

## 今天的量（在我这棵树上量，`lane-m4b`，合并 `4fa772787` 之后）

用 runner 自己的读法（`loadPlanTests` + `expandSweeps` + `testTier`）遍历 `test/plans` 的 338 个计划：

**`plans = 338, tests = 11856, zero-fast = 30`**，分布 `feat/mm` 4、`feat/opt` 1、`debug` 1、`gpu` 3、`perf` 21。

**30 个里没有一个 `total = 0`**——每个都有用例，只是 `testTier` 全不是 `fast`。**所以"删掉"这一支今天没有对象。**

**真正的缺陷是 1 个，而且已修**：`test/plans/feat/trans/cml_sweep.plan.toml` 缺计划级 `tier`，自称快层而唯一用例是 slow ⇒ 快层整遍失败。合并后它第 18 行是 `tier = "slow"`。

## 为什么不建议改层

改层不是改名：**它会改变 `npm run test` 的时长与含义**（`perf/**` 进快层，开发者那一遍就从分钟级变成十分钟级）。**"层"是使用者的契约，不是文件的一个属性。**

## 数差如实记

我量出 30，作者说 31。**我这边的口径是"快层零启动"**；`started nothing here` 那行在 `006adafb0`，**合并 `4fa772787` 之后我在 `test/tools/run-tests.mjs` 里仍然 `git grep` 零命中** ⇒ **口径的确切定义我读不到，所以我报 30 并写明算法，不声称等价于 31。**

## 一条仪表的教训（同族第三次）

我第一次跑这个脚本，输出是 **337/338 全是 0**——因为我把 `expandSweeps` 的返回值当成了全部用例，真用例一条没进。**全部为 0 正是"仪器没起来"的签名，不是"337 个沉默的零"。**

**一个均匀的零，先怀疑仪器；一个参差的零，才是数据。** 这与上月 `bin/camel` 恒 0、与本夜 `-rdynamic` 的四次假 0 是同一族。
