# `Split<F>` 的残差位，静态类型为什么填不上？

**问题一句**：作者裁定 B（2026-11-01）：残差项数由图算（`residualsOf`），`Split<F>` 的残差位由编译器在实例化时填。
建图那一处已经按图填了（`3ab045252`），**调用点的静态类型仍是一参数一槽的占位**——两层说两个数，谁去闭、怎么闭？

## 量到的三处说法（本轮读数，主机 fast 层，`BUILD_EXIT=0`）

| 函数 | 图给的项数（`residuals=`） | 调用点静态类型里的项数 | 前一半运行时的类型 |
|---|---|---|---|
| 恒等 `f(x) = x` | 0 | 1 | `(float) => (float, ())` |
| `f(x) = x*x` | 1 | 1 | `(float) => (float, (float,))` |
| `f(x, y) = x*x*y` | **3** | **2** | `(float, float) => (float, (float, float, float))` |
| `f(x) = x*x*x` | **2** | **1** | `(float) => (float, (float, float))` |
| `f(x) = x*x*x*x` | **3** | **1** | `(float) => (float, (float, float, float))` |

第二、三列是同一个运行时的两处说法：第三列是图，第一列从它来，**只有第二列是占位**。

## 占位不只是"信息少一点"：它放行一个图会否掉的程序

实测（探针，未提交）：`f(x, y) = x*x*y` 在 3、2，

```camel
let (value, res) = fwd(3.0, 2.0)
let (r0, r1) = res                       // 静态类型说两项，图里三项
println("r0=", r0)                       // 3.0
println("r1=", r1)                       // 2.0
println("tangent dy=", lin(res, 0.0, 1.0))   // 9.0，仍然对
```

编译通过、跑通，第三项 `x*x = 9.0` 被**静默丢掉**。同一件事的另一面：早先版本打印 `residuals=`，
三项的元组打印成 `(3.0, 2.0)`，两项的打印成 `(2.0)`——打印器按静态类型走。这就是为什么用例里
不再打印这个元组：读数不能建立在会撒谎的类型上。

## 试过的两条，各自停在哪

**甲 把残差位的定型推迟到 `fwd`/`lin` 的调用点。** 取消：调用点没有"推迟"这个时刻。
调用点的结果类型在调用**执行之前**由被调者的类型算出（`src/compile/gir/builder_operators.cpp:883`
的 `resolveForCall(` 就是这一步），能推迟到的只有"一个没解的类型变量"，而"编译结束后没有值带着未定类型"是原则
5.10，`any` 正是为此被删掉的。即便允许，未解变量也不带项数——它答不出 0/1/3。

**乙 每次实例化新铸一个刚性类型填那个空位。** 取消：刚性类型要**带项数**才有用，而项数正是不知道
的那个数；不带项数就只是给占位改了个名字，`3 对 2` 的差还在，只是从"看得见"变成"看不见"。这不是
代价问题，是取值问题——没有东西能给它那个数。

**丙 建图处拒绝对不上的形状**（图说 3、签名说 2 就报错）。没试，因为它是被作者否掉的 A 的变形：
把 `x*x*y` 变成不能拆，代价比占位更大，且 12/9 这两条读数会一起没。

## 一句话

调用点的类型在 GIR 建图期由 `SplitResolver::resolve(with, norm)`
（`modules/transforms/split_operator.cpp:74`）**从类型**算出，而决定残差项数的图要等到 `std::nvm`
执行 `splitKernel`（同文件 `:123`）里的 `buildSplitGraph`（`modules/transforms/split.cpp:562`）
才存在——**定型比建图早一个阶段**，所以静态类型拿不到那个数。

## 两条能闭的路，各要作者一句话

- **甲：把 `jvp`/`split` 挪进编译阶段**（设计 4.1 末尾已把"要不要把 `jvp` 挪进编译阶段（pass 或宏
  求值器）"列为等点名的事）。图在建图期就在手里，类型按图填得出来。代价：`vjp.cml` 里
  `split(jvp(f))` 的值级组合要换写法——那是 4.4 的正文，不是实现细节。
- **乙：加一个每次实例化新铸的刚性类型**，让残差的成员"不写在类型里"，并在原则 5.10 上开一条例外
  （"值可以有类型，其成员在编译结束后由图补"）。代价：一个新 `TypeCode` 和它的 `equals`/`toString`/
  布局，以及 5.10 的一条例外——这一条例外要不要开，是语言的决定，不是这一档的决定。

在裁定之前：三条读数（0 / 1 / 3）按原样留在 `test/plans/feat/transforms/split.plan.toml`，它们与
占位槽数的差就是这条问题的证词；`modules/transforms/split.h` 的说明也指到这里。
