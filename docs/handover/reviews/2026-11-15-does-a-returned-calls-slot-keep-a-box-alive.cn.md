# 调用返回之后，它留下的句柄槽还让盒子活着吗？

**状态**：待裁。本批的判据用例按文末的默认建议写（`ref.boxes_loop_ten` / `ref.boxes_loop_thousand` 断言
「`live` 不随元素数长」，递归形状那一条只断言计数等式），这条不阻塞任何工作。

## 1. 问题与最小例子

作者裁定 `Ref<T>` 是「最后一个句柄消失时盒子被释放」（原则 3.3 与 `stdlib/state.cml` 的帮助段：
`reclaimed by counting the handles that point at it: the last handle to go frees it`）。读数靠
`--gc-check foreign`（本批新增，退出时打 `FOREIGN_RESOURCES created= released= live= disposed= finalized=`）。

同一个 body、每个元素造一个盒子、盒子随元素末而死（`ref_boxes_loop_ten.cml` / `ref_boxes_loop_thousand.cml`）：

| N | nvm | fvm / jit / prl |
|---|---|---|
| 10 | `created=11 released=8 live=3` | `created=11 released=11 live=0` |
| 1000 | `created=1001 released=999 live=2` | `created=1001 released=1001 live=0` |

`live` 与 N 无关，四后端都在运行期回收——这一半是好的。

但**嵌套调用**形状（`ref_boxes_are_counted.cml`：`v + drop_many(i + 1, n)`，造盒子时一千个调用同时在
栈上）读出来是：

| 后端 | created | released | live | disposed |
|---|---|---|---|---|
| nvm / fvm / jit | 1001 | **0** | **1001** | 1001 |
| prl | 1001 | 1001 | 0 | 0 |

递归返回之后，那些盒子已经没有任何名字能取到（每个 `let r` 的作用域随调用结束）。prl 把它们放掉了，
另外三个后端一个都没放，一直计到进程退出。所以是**同一程序、两套回收行为**，且三个后端与裁定那句话
不一致。

**这是内存行为缺陷，不是正确性缺陷。** 程序的结果都正确，盒子也不泄漏到进程之外（退出时
`disposed=1001` 全放），受影响的是**进程内占着的内存**：一个长期运行、反复返回的程序会按「已返回的
调用数」无界积累盒子，直到进程退出。写成「没问题」会让这 1000 个盒子占着的内存永远没人管；写成「程序
要崩」又会读错——它不崩。

## 2. 可选方案与代价

1. **返回时清掉帧的句柄槽（或让帧存储里的死槽不再被当成根）**：三个后端与 prl 一致，裁定可被验证。
   代价是每个后端都要在返回路径上把槽写空（一次写或一个返回值覆盖），以及存在保守扫描的地方要改成精确。
2. **保留现状，把「保守扫描」写进文档**：不动后端。代价是一个长期运行的程序会按「已返回的调用数」
   无界积累盒子，直到进程退出；裁定里「最后一个句柄消失时释放」在三个后端上永远不被验证，而 prl 是
   唯一能对照的行为。
3. **两者之间**：保留保守扫描，但在返回时把帧栈指针之下的槽清掉。代价与 1 相同，收益是仍允许栈上
   其它位置保守。

## 3. 倾向

**默认建议：释放时机应当与后端无关。调用返回后已够不着的盒子，应在返回时释放；prl 已有正确行为可
对照，另外三个后端要向它看齐。**

理由：prl 已经证明这些盒子在该时刻可以释放，所以三个后端不是「保守但正确」，而是把已经死了的东西留到
进程退出。计数回收这条裁定正是本批要立起来的东西，而它在三个后端上今天没有被验证过；同一个程序在两个
后端上留下不同数量的活盒子，读代码的人无法从语言规则推出自己该看到哪一个。
代价是三个后端的返回路径要把帧的句柄槽清空（或让死槽不再被当作根），有保守扫描的地方要改成精确。

这次读数不装绿：递归那条用例只断言 `created = released + live`、`disposed = live` 与盒子确实被造出来，
`live` 的具体值写在断言失败信息里，四后端并列即可看出差异。

## 4. 被挡住的工作

没有。判据用例（元素形状）已经绿，本条目其余部分（提交、删库版残件、AST golden）不依赖这条裁定。
裁定若选 1，回补的是三个后端的返回路径；若选 2，回补的是这条用例里递归形状那一半的期望与文档。
## 决策者答复（2026-11-15）

**取 1：返回时释放，四个后端一致。** 原则 10.5"三层各管什么"写明不可变的值与 `Ref` 句柄只靠计数回收、计数归零立即释放，回收时机确定。帧里已经够不着的槽仍算根，就违反了这一条；第 3 种做法只是程度上的差别，同样不取。具体做法：返回路径把帧的句柄槽清空（递减计数），任何把帧存储当保守根扫描的地方改成精确。元素形状上 nvm 的 `live=3` / `live=2` 也是同一个缺陷，一并修到 `live=0`。

验收：三个用例在四个后端上都是 `released = created`、`live = 0`，递归那条改回断言具体值；用例写明它测的是"回收时机与后端无关"。归第 4 路（执行语义与内存），排在优先级一之后。
