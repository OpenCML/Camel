# `[[sweeps]]` 的派生数随「被命名计划里的条目数」自动增长，这是有意设计还是需要一个上限？

2026-11-05，`lane-mirror`，读数取 `fbcc210b6`。今天之前它只被读过一次（3518 / 3272），而那个数字
在十一个小时里变了两次——不是因为有人动了 sweep，而是因为有人往它命名的计划里加了用例。

## 1. 问句

**`[[sweeps]]` 的派生数会随「被命名计划里的条目数」自动增长（11 小时涨 21 条，正好是新增用例数）。
这个乘数是有意设计，还是需要一个上限？**

它是问句、不是缺陷报告，有两个原因：

- **没有任何机制在条目数变化时提示「milestone 层多了 N 条」。** `[tier]` 行只在有人真的跑该层时打印，
  而它把声明与派生合成一个数（`test/tools/tier-accounting.mjs#tierAccountingLine`）；`--tier-report`
  是今天才有的查询，跑不跑由人决定。也就是说**这个增长是静默的**——加一条快层用例的人不会看到
  milestone 层多了一条。
- **它是否可接受，取决于作者认为 milestone 层的用途是什么。** 若 milestone 层是「全量回归」，随用例
  增长正是它该有的行为；若它是「抽样回归」，它需要一个上限，而抽样率该由谁定、定在哪一档，只有作者
  能裁。这两条都自洽，代价也只有作者能权衡——所以它是一个问句。

| fast | 8624 | 214 | 1 | 8838 | 2% |

| **milestone** | **246** | **3293** | **1** | **3539** | **93%** |

- **增长**：夜里的读数是 3272 份副本，今天是 3293（+21）。对照 `eacdf5b65`（11 小时前）：它命名的
  215 个计划当时有 **3485** 条可跑条目，今天 **3507** 条（+22），多出来的 2 条进了 fast 抽样、
  20 条进了 milestone。**增长与新增用例一一对应，不是谁改了 sweep。**
- **展开维度**：`plans` 11 项 → 220 个计划文件 → 排除 5 个（`modules/autodiff`、`modules/onnx`）
  → 215 → 186 个有可跑条目（29 个零贡献）→ **3507 条可跑 = 3507 份副本** → 214 抽样进 fast
  （16 个 risk 计划中 14 个留 3 条）+ **3293 留 milestone**；那 215 个计划共 5409 条，1902 条按
  kind / `sweep = false` / `known_fail` / 自带 `--gc-` / 非运行条目排除。
- **它不冗余**：3293 份副本 → **3241** 条不同 `(tool, case, args, envs)` 命令；叠断言后 **3266** 组。
  52 份重复（1.6%），与声明侧的 155 / 8624（1.8%）同率——**sweep 是在拷贝一份已有的重复，不是造重复**。
- 条目原文与逐层展开：`test/plans/feat/mm/gc_poison_sweep.plan.toml#poison`；
  计数规则见 `docs/test-plans.md` 的「What A Layer's Entry Count Is Made Of」。

**给想自己核一遍重复率的人**——这一页的 1.6% 有同一个坑，你会撞上它：

> 按字面比参数得 2233 条不同 / 1060 条「重复」——`${backend}` 是 `test/vars.toml` 的 pass 列表，
> `.nvm/.fvm/.jit` 写法相同而流水线不同；改走 `run-tests.mjs#expandArgs` 后那 1060 是假的。

即：把 `args` 当字符串比会得到 1060 条「重复」，那是因为一份 `--gc-check poison ${case} ${backend}`
在 `.nvm` / `.fvm` / `.jit` 三份副本里写法完全相同、实际跑的是三条不同流水线。`scripts/tier-report.mjs#commandOf`
先经 `test/tools/run-tests.mjs#expandArgs` 展开再比，2233 变成 3241。**按字面比出来的冗余不是冗余。**

## 3. 三条路，各自要改什么、改多大

- **① 保持现状，只把增长暴露出来。** *谁要改*：我方，不需要作者的裁定即可做。*改多大*：0 行代码
  （`--tier-report` 今天已落地），加一句文档；`docs/test-plans.md` 那一节本轮已补上
  「派生数随被命名计划的条目数增长，且没有任何命令会通知你」这一句。*代价*：增长继续静默，除非有人
  去跑那条命令——**「可见」不等于「会被看见」**，这是这条路唯一的弱点。
- **② 给 sweep 一个显式上限或冻结清单。** *谁要改*：sweep 的拥有者（`feat/mm/gc_poison_sweep` 的作者）。
  *改多大*：`[[sweeps]]` 加一个字段（`max_copies` 或 `freeze = [...]`），改
  `test/tools/run-tests.mjs#expandSweeps` 与 schema 的 `SWEEP_FIELDS`，加自测；约一处字段 + 一条
  展开规则 + 一个 case。*代价*：上限一到，新增用例就**静默地**不进 milestone——把「静默增长」换成
  「静默截断」，除非同时让越过上限成为一条失败。
- **③ 收成一条。** *谁要改*：同样要 sweep 的拥有者点头。*改多大*：`3539 → 247`
  （`3539 − 3293 + 1`）——删掉那个 `[[sweeps]]`、留一条代表条目，一次 30 行的改动。*代价*：丢掉
  3241 条不同命令里的真实覆盖，而 `--gc-check poison` 的目的正是「在尽可能多的程序上把 safepoint 毒
  一遍」，这与 `test/plans/feat/mm/gc_poison_sweep.plan.toml#poison` 的 desc 直接冲突。

## 4. 默认（我方按此继续，不再问）

**① 保持现状 + 让增长可见。**

理由：3241 / 3293 说明它不是冗余（砍掉会丢真实覆盖，见第 3 节 ③ 的代价）；「可见」这一半今天已由
`--tier-report` 做到，剩下的只是把「派生数随条目数增长」写成文档里的一句话，而那句话本轮已进
`docs/test-plans.md`。**本轮不改任何计划、不改任何 tier、不删任何条目。**

留给下一轮的判据（如果作者裁定要上限，就按这个验收）：**新加一条用例后，
`node scripts/test.js --tier-report --tier milestone` 的派生数必须按规则变化，且作者选的那一档
（全量 or 上限）在输出里说得出来**——一个说不出来的数，又回到了今天这个静默增长。
