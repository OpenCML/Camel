# `#jvp` 这一族规则没有挂点

裁定把第 3 步的形状定成："规则是普通的 `rule` 声明，用 `#jvp(mul_jvp)` 挂在原语的声明上；类型检查时逐个原语查找它的 `#jvp` 规则，缺了在那个原语处报错。" 这个形状在今天的语言里落不下去：**这一族规则没有挂点**。`Tangent<T>` 已经能算，挡路的只剩这一句。

## 现象到符号

- **标签的宿主里没有 `rule`**：`docs/design-principles.cn.md` 第 6.2 节的宿主是 `func`、`type`、`field`、`params`、`nodes`；`stdlib/autodiff.cml#jvp` 自己声明成 `on func`，还带 `when is_function::<F>()`。所以一条 `rule mul_jvp` 带不了 `#jvp`。
- **标量原语没有声明可挂**：它们注册在 C++ 里（`:op/mul_l` 这一类），程序里只有调用点的算子，没有一条声明承载标签。`stdlib/signatures/` 下那些列算子的文件自己写明 "these declarations are not compiled"，它们不是能挂标签的声明。
- **规则名当标签实参今天被拒**：`diagnostics/registry.tsv#TagArgumentNotValue`，`#jvp(mul_jvp)` 就停在这一条。
- **于是"某条规则属于 `jvp` 族"无处可读**：`stdlib/graph.cml#rule_of` 与 `modules/autodiff/rules.h#ruleOf` 读的都是**函数图**上的 `#jvp(rule)`；`include/camel/compile/gir/rule_templates.h#genericRuleInstance` 只实例化**已经知道 id** 的规则，它不回答"哪条规则是这个原语的 `jvp` 规则"。

## 为什么不能自己定

跨不过去的是"规则族的成员关系写在哪里"。三个可能的落点各自改的是不同东西——编译器的标签机制、库的声明面、模块的注册表——后果都不在实现细节里能收回，而设计原则第 15 节把这一类留给作者。我按其中任何一个开工，都等于先替这一句裁了。

## 选项

- **① 给内置算子补一份"原语声明"**，`#jvp` 挂在它上面。**要多造**：a) 一种"这条声明就是那个内置算子"的写法（今天 `#op('...')` 只出现在不编译的签名文件里）；b) 让 `#jvp(rule)` 的实参收规则名（放开 `TagArgumentNotValue`）；c) 变换侧从声明上读这条标签。好处：与裁定的字面最接近，顺带让内置算子有一份可引用的名字；代价：声明面多一层，签名文件要么变成真声明、要么与它并存。
- **② 标签能挂到 `rule` 声明上**（扩 `tag` 的宿主种类）。**要多造**：a) 宿主种类 `on rule` 的语法与检查；b) 标签在规则声明上的存放与读取；c) 从"一个原语"找到"lhs 匹配它的那条规则"的那一步（`genericRuleInstance` 只做实例化，不做匹配）。好处：库里那批泛型标量规则直接就是这一族，不必给原语补声明；代价：动的是标签机制本身。
- **③ `jvp` 族改为按算子 id 查表**（C++ 侧一份显式表）。**要多造**：a) 表本身（算子 id → 规则 id），以及规则 id 能按名字取到；b) 一份测试守住这张表与库里那批规则不脱节；c) 以后 ONNX 导出、`vmap` 各自的族各复制一份，或再抽一层。好处：不动语言，今天就能跑通；代价：族关系住进 C++，绕开"标签是编译期事实"这个一致形状。

**默认建议：①**。它与"挂在原语的声明上"字面最接近，顺带把内置算子的名字变成可引用的东西；②动标签机制、③把族关系搬进 C++，两者都比①远。这一句补上就能开工。
