# 一个被循环体捕获的标量，抬升后静默算错

## 问什么

`jvp` 抬升一个体内读到外部值的循环时，**不拒绝、不诊断，给错数**。这页记下四条读数（含基线复现），把"错数"这件事从聊天记录里搬成不可丢的东西；成因还没找到，§5 明说拼不出自洽的机制。

## 1 纸面与实测

两条程序的形状一样，都是递推 `x ← x·c + k`，`k = 1, 10`，`s = 1`；差别只在"体里怎么读那个外部值"。

```cml
// A：捕获一个标量，体里直接读它
func f(s: float, c: float): float {
    return loop x = s for k in [1.0, 10.0] do x * c + k
}
// B：捕获一个结构体，体里通过成员投影读它
type Pair = { a: float, b: float }
func k(s: float, c: Pair): float {
    return loop x = s for kk in [1.0, 10.0] do x * c.a + c.b * kk
}
```

纸面：A `f(1,2) = (1·2+1)·2+10 = 16`，`∂/∂s = c² = 4`，`∂/∂c = 2cs+1 = 5`；B 取 `c = {a:2, b:1}` 也是 16，`∂/∂s = a² = 4`，`∂/∂a = 2sa+b = 5`，`∂/∂b = a+10 = 12`。

| 程序 | 纸面 | 实测 |
|---|---|---|
| **A 捕获标量，直接读** | 16 / 4 / 5 | **12.0 / 2.0 / 1.0** ✗ |
| B 捕获结构体，投影读 | 16 / 4 / 5 / 12 | 16.0 / 4.0 / 5.0 / 12.0 ✓ |
| 对照 `g`：把捕获换成常量（`x * 2.0 + k`） | 16 / 4 | 16.0 / 4.0 ✓ |
| 对照 `h`：`let d = c;` 再读 `d` | 16 / 4 | 12.0 / 2.0 ✗ |

读数原文（`std::nvm`）：
```
A v=  12.0 / A d1= 2.0 / A d2= 1.0
B v=  16.0  d1= 4.0 / B d2= 5.0 / B d3= 12.0
g v=  16.0   d= 4.0        h v=  12.0   d= 2.0
```
A 那条**没有任何诊断**：`REINTERP jvp function=f … tangent=computed source=ruleset rules=jvp_mul,jvp_add`，没有 `skip=`，没有 `diagnostic`。它不是"红"，它是错。

## 2 不是这两笔提交弄坏的（基线复现）

把 `modules/transforms/jvp.cpp` 换回 `542ba0dda`（develop）自带的那一份，同一个程序重跑：`g` 仍是 **16.0 / 4.0** ✓，`h` 仍是 **12.0 / 2.0** ✗。所以错数在基线就存在（`542ba0dda` 时它所在的形状还没人量过），与本支行 `7544e9221`（数组态）`e1b00e8af`（结构体态）两笔无关。

## 3 边界：标量直接读会错，结构体投影读不会

同一具身体、同一组数，只有"体里怎么读那个外部值"不同：

- 外部值是**浮点标量**、体里**直接**当操作数读 ⇒ 错（A、h）。
- 外部值是**结构体**、体里通过 `c.a` / `c.b`（`GCAccsKind::StructKey` 投影）读 ⇒ 四个数全对（B）。
- 根本没有外部值、把捕获换成**常量** ⇒ 对（g）。

所以接错的不是"capture"这个大类，是"体里对外部**已被配对**的标量节点的直接读"这一条。

## 4 探针：循环本身的接线是对的

```
PROBE loop ref=7 index=1 stateStart=1 inKind=1 inRegion=0 inType=float paired=1
```
（`kind=1` 是 Port，`inRegion=0` 在体外，`paired=1` 说明它有对。）控制变量下 `g` 打印的是同一行 —— **两条程序的循环接线一模一样**：一个 iterable、一个配对的状态输入，`capture` **不在**循环的 norm input 里（它是跨区读）。所以问题不在循环的输入表，在体里那几个节点的接线。

## 5 三个读数拼不出一个自洽的机制

把 iterable 换掉，A 的读数不收敛：

| iterable | 纸面 | 实测 |
|---|---|---|
| `[1.0, 10.0]` | 16 | 12.0 |
| `[1.0]` | 3 | **1.0** |
| `[10.0]` | 12 | **10.0** |

`12 = 1·2+10` 像是"状态没接回 `s`"；但 `[1.0]` 给 1.0（= `s`）、`[10.0]` 给 10.0（= `k`），这两条与"状态不接回"或"只跑一轮"都不合。**我拼不出一个能同时覆盖这三条的机制**，所以这页只把事实钉住，不猜成因；成因要等抬升后的图打出来再写。

## 6 抬升后的图：接线是对的，错在运行期

把 `draft` 里抬升完的图整张打出来（`h`，全部 22 个节点；`kind` 0=Data 1=Port 4=Fill 5=Accs 10=Func 11=Oper 15=Loop）：

```

0    0   1    1  float          -           -       s 的值端口
1    0   1    2  float          -           -       ds
2    0   1    3  float          -           -       c 的值端口   ← 体直接读它
3    0   1    4  float          -           -       dc
4    0   1    5  float          -           -       轮次元素 k
5    0   0    -  float          -           -       k 的零切线
6    0   1    6  (float,float)  -           -       体里的状态对端口
7    1   5    7  float          6           -       状态的值半边 .0
8    1   5    8  float          6           -       状态的切线半边 .1
9    0   0    -  float[]        -           -       iterable

11   1  10   10  float          7,2,8,3     -       mul_d 的切线调用 (x,y,dx,dy)
12   1  11   11  float          10,4        -       add_d(mul, k)
13   1  10   12  float          10,4,11,5   -       add_d 的切线调用

```

这张图**照纸面算就该是 16 / 4 / 5**：状态从 `.0` 读值、`.1` 读切线；`mul_d` 的两个操作数是"状态的值半边"和 `c` 的值端口；两个切线调用拿的是 `7,2,8,3` 与 `10,4,11,5`，与 `x·c + k` 的规则参数一一对应；循环的输入是 `[iterable, 初始对]`，体结果是那个 `(值, 切线)` 对。

它和 `g`（常量）唯一的差别是**第二个操作数**：`g` 是 `norm=5,8`，`8` 是区 0 的 **Data**（常量 `2.0`）；`h` 是 `norm=7,2`，`2` 是区 0 的 **Port**（`c` 的值端口，`di=3`）。同一形状，Data 算对、Port 算错。

所以判据里的那一问："错在值半边、整对、还是第三样" —— **第三样**：体里读捕获既不是取半边也不是取整对，而是把**体外那个端口本身**接进了体（`valueOf` 对参数端口无效，于是走了 `copyOf` 兜底，把端口原样递过去）。接线位置是对的；错在**运行期对"体内读体外端口"的取值**，而常量（Data）那条路不走这个取值。这也解释了为什么 §5 三条读数拼不出机制：它们量的是症状，机制在另一层。

## 8 试过的一次："在体内生成一份副本"（已回退，读数没变）

按裁定试了这条路：`jvp.cpp` 的 `case rt::GCNodeKind::Oper:` 里加一个 `readInBody`，凡是**体里**节点的操作数或规则切线落在**体外**的，就在体内造一份 `Copy`（`draft.addCopyNode(type)`，一条 norm 输入指向体外那份），让体里读自己这份；已经在体内、或常量（`Data` 本来没有槽）的照旧。只动了 `jvp.cpp` 一个文件。

读数**一个都没变**（同一台机、同一份 `/tmp` 程序；第一次的条件写错了，改成按新节点的 region 判之后又量了一遍，两次一样）：

| 程序 | 纸面 | 改前 | 改后 |
|---|---|---|---|
| A 纯捕获 | 16 / 4 / 5 | 12 / 2 / 1 | **12 / 2 / 1** |
| `h`（`let d = c`） | 16 / 4 | 12 / 2 | **12 / 2** |
| `g` 常量对照 | 16 / 4 | 16 / 4 | 16 / 4 ✓ |
| B 捕获结构体 | 16 / 4 / 5 / 12 | 同上 | 同上 ✓ |

所以"体里读的是体外端口、要改成体内一份"这个假设**被读数否掉了**：加了副本，错数照旧，而没有捕获的那两条一个没动。改动已回退，这一笔不留代码。下一次要查的位置从"运行期读体外端口"挪到"循环喂回去的状态是不是原来的那份"——`h` 的三个数（12、2、1）与"每轮都从初始 `s` 重来"完全吻合，但 `[1.0]` 的 1.0 与 `[10.0]` 的 10.0 又不吻合，所以这仍是待查，不是结论。

## 9 三个否证与一条线索（接手的人从这里开始）

今晚把两个假设都证否了，剩下的是一条线索。**不要再从图里找原因**。

**否证一：体内加一份副本，读数不动。** 见 §8：让体里读的那份变成体内的 `Copy`（一条 norm 输入指向体外那份），四个程序的读数一行都没变（A 仍 12/2/1，`h` 仍 12/2，`g` 与 B 本来就对）。第一次的 region 判据拿**原图节点 id** 去问 draft，条件基本不成立，等于空跑；改成按**新节点**的 region 判之后又量了一遍，两次读数一样 —— 所以"副本没生效"不成立，是"副本生效了也没用"。

**否证二：喂回去的东西同形。** 捕获程序与常量对照的**循环节点输入行逐字相同**（只有节点号与 `di` 平移）：

```
g: node=13 reg=0 kind=15 di=11 type=(float, float)  norm=7,20   with=18,16
   node=20 reg=0 kind=4  di=16 type=(float, float)  norm=19     with=0,1
h: node=14 reg=0 kind=15 di=13 type=(float, float)  norm=9,21   with=19,17
   node=21 reg=0 kind=4  di=18 type=(float, float)  norm=20     with=0,1
```

`norm[0]` 两条都是 `Data(float[])`（iterable）；`norm[1]` 两条都是 `Fill`，类型 `(float, float)`，而那个 `Fill` 的 `with` **两条都是 `0,1`** —— 端口 0 是 `s`、端口 1 是 `ds`，即"初始的那一对"。`with[0]` 两条都是体结果那个对，`with[1]` 两条都是轮次序号端口（`int`）。

**线索：同一个 `di` 读到了两样东西。** `g` 的 `di=3` 是**轮次元素 `k`**，`h` 的 `di=3` 是**捕获 `c`**（`dc` 在 `di=4`）；而两条程序的体**都读 `di=3`**，一个读到元素、一个读到捕获。要查的是**循环体执行时帧槽怎么分配、怎么解析** —— 端口在体里按 `di` 取值，还是按"它是循环的哪个输入"取值。

**结论：接线无罪、副本无效、喂回同形 ⇒ 差异不在图里，在运行期按 `di` 取值这一层。下一步不在 `jvp.cpp`，在运行期。**

## 10 按作者裁定试"把捕获当循环输入"：运行期拒绝，并给出了为什么

按裁定（甲）试了：抬升循环时，凡**体里**的节点读区 0 的非 `Data` 节点，就在体内加一个 port、把那份值追加到新循环的 **norm 输入**末尾，并把体里那些读改指向新 port（配对的值与切线是两个不同的读，各自一份，即"两半都交进去"）。只动 `jvp.cpp` 一个文件。

结果是**运行期直接拒绝**，三个程序一样：

```
error[RuntimeDiag::PassInternalError]: Pass 'std::nvm' failed with an internal error:
Runtime graph 'jvp_of_f' has LOOP node 14: its body graph returns a '(float, float)',
the state is '((float, float), float, float, float, (float, float))'.
```
（`g`/`h` 是 `LOOP node 13: … the state is '((float, float), float, (float, float))'`；B 是 `LOOP node 20: … '((float, float), Pair, Pair, float, (float, float))'`。）

这条错误不是"多打了一次端口"，它把运行期的契约说出来了：

- `include/camel/runtime/loop.cpp:131` `initialState(j) = normInputs[j + iterates]`：iterable 之后的**每一个** norm 输入都被当成一个 state，于是捕获的四份被读成了 state 的四个分量；
- `include/camel/runtime/exec_plan.h#ExecLoop`：`slots` 的排布是"state 的各分量，然后 cond 的端口，然后**体的端口：先 element，再 k 个**"——体的端口个数就是 `element + k`，**没有给捕获留位置**。

所以"把捕获加进循环的 norm 输入"这条路在运行期不成立：**循环体不可能有捕获端口**。剩下的唯一通道是把捕获**放进 state**——让它成为一个每轮原样返回的状态分量（配对的两半各占一个分量），于是循环的值类型从 `(state…)` 变成 `(state…, 捕获…)`；这要求读循环值的地方都改成 `.0` 投影（多种状态那一路在 `jvp.cpp` 里已经有这个形状）。

**这已经是"改循环的值类型"，不是"把捕获复制成输入"**，而且"抬升后的循环值类型该不该变、还是该由前端为捕获造输入口"是要作者裁的一件事，所以这一条我没有接着改：代码已回退，这一页留下契约与实测错误原文。

## 11 按裁定走"捕获进 state"：图建起来、跑起来了，读数还是 12/2/1

裁定选了"捕获进 state"，我照做：循环值类型变成 `Tuple(状态对…, 捕获…)`，每个捕获占一个 state 分量，体里为它加一个 port（排在 element 与状态之后，正是 `exec_plan` 的排布），体里原来读区 0 的那几处改读自己的 port，每轮把这个 port 原样交回去；循环的 norm 输入相应多几项；读循环值的地方只取**状态**那几个分量。中途撞到一次自己的 bug：`stateCount == 1` 那条快路先命中，投影按 `float` 取了元组的第 0 项，被运行期的边不变量逮住——

```
graph 'jvp_of_f' node 15 (5): element 0 of a ((float, float), float) is a (float, float),
the node is a float.
```

这条错误顺带说明了一件事：**那个循环的值类型只多了一个分量**（`((float, float), float)`），即 `loopCapturesOf` 只找到**一个**捕获 —— `c` 的值端口进去了，切线端口 `dc` 没有：它的读落在规则调用那个节点上，生成时不在体的区域里。修掉快路之后图建起来、跑起来了，没有任何错误：

| 程序 | 纸面 | 改前 | "捕获进 state"之后 |
|---|---|---|---|
| A | 16 / 4 / 5 | 12 / 2 / 1 | **12 / 2 / 1** |
| `h` | 16 / 4 | 12 / 2 | **12 / 2** |
| `g` 常量对照 | 16 / 4 | 16 / 4 | 16 / 4 ✓ |
| B | 16 / 4 / 5 / 12 | 全对 | 全对 ✓ |

⇒ 按停手约定停在这里：**"捕获没进循环输入"不是唯一原因** —— 它进了 state、图跑通了，错数照旧。下一步查那份**切线半边**：这次只把值那半进了 state，`dc` 仍从区 0 读；把两半都送进去再看读数，就能分开"值读错"与"切线读错"。改动已回退，这一页留读数。

## 12 两半都进了 state，读数还是 12/2/1 —— 这句话要报给作者

上一节留下的悬念补上了：`captureHalvesOf` 现在按"值 + 切线"两半取，捕获列表报 **2**，循环的值类型也真的长出了两个分量：

```
PROBE loop f=f captures=2 type=((float, float), float, float)
A v=  12.0   A d1= 2.0   A d2= 1.0        （纸面 16 / 4 / 5）
```

`g` 仍 `16.0 / 4.0` ✓，B 仍 `16.0 / 4.0 / 5.0 / 12.0` ✓，`h` 仍 `12.0 / 2.0`。

**⇒ 要报作者的一句话：捕获进 state 不是原因。** 两条通道都试过了 —— 归一输入（运行期拒绝，见 §10）、state 分量（建起来、跑通、两半都在），A 一次都没有离开 12/2/1；而**没有捕获的形状**（`g`、B）在所有版本里都正确。所以"s"被读错"这个诊断至少不完整：**改了捕获的到达方式，错数一个也没动**。

下一步该查的不再是"捕获怎么进去"，而是**体里那份乘法的两个操作数各自读到什么**：值半边现在由状态端口给（它每轮回来是对的），切线半边由规则调用给；若两者都到位而结果仍是 12/2/1，那问题在**规则调用的展开**或**循环结果对的装配**上，与捕获无关。改动已回退（这一笔不留代码），这一页留类型打印与读数。
