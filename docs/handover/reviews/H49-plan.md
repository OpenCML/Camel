# H49 GPU 计划批复（协调者 2026-10-22）

计划接受。`docs/design/gpu/plan.cn.md` 已合入 develop（H218 先合，`0x71` 与旧 API 的删除都在树上）。按 §7 的 S1–S10 施工，下面几条是批复；没有列出的照计划做。

## 决定

1. **§2.6 的 `autodiff::expand`：接受，加两条硬要求。**（a）该遍**幂等**，且在没有 `#gpu` 的图上必须产出**逐字节相同**的图（用 `std::jgir` 的 golden 比，不是用结果比）。（b）展开后的函数常量与运行期算子产生的值**形状相同**：同一个用例在"有该遍"与"无该遍"两条路径上，图可以不同、**执行结果必须相同**。理由：这是唯一一处让"反向进得了编译"成立的改动，它一旦改变普通程序的行为，`#gpu` 之外的一切都要重新验。

2. **§7 的顺序：接受，但 S1 单独先合。** `--devices` 没有启动校验是**用户可见缺陷**（点名一块不存在的设备，今天不报），它不依赖标签、不依赖段编译，先落地。

3. **§4 的持久缓存：接受"不用源哈希"，再加一条。** 键里必须含**编译器的构建身份**（`build-info.json` 的指纹），否则改代码生成器会读到旧内核。这和 H213 的教训同源：一个缓存不能证明它属于当前的二进制，就只能删掉。

4. **可见性：放置必须在图上看得到。** 区域属性与节点属性要出现在 `std::gir` / `std::jgir` 里，并有 golden。否则"驻留由图推出"这句话没有人能检查，验收就只剩结果对不对。

## 五个问题

5. **Q1 模块位置的标签：本轮不做。** G1 的验收（C2 与 `transformer_step`）不需要它；而且"模块"是编译单元、不是位置，加它要连带定 `import` 与多函数模块的语义。**可推翻。**

6. **Q2 `Device<T>`：保留可写**（设计原则 13.3 已定，`Device<{ a: A }>` 与 `{ a: Device<A> }` 是同一个类型），但它只是**放置断言**，不是第二个值：图上"设备块上的 `Tensor<f32>`"与 `Device<Tensor<f32>>` 是**同一个值**（计划的 §3 值模型）。签名上写 `Device<T>` 表示调用前必须在设备上，编译器插入 upload；**值身份不变**。这条不改设计原则。

7. **Q3 `#gpu` 里的主机效果：编译期报错**（`0x71`，一条诊断列全部，出路写 `#cpu`）。自动在边界下载等于让编译器替用户选传输点，而 profile 只能事后看见它；13.4 的逃生口本来就是 `#cpu`。

8. **Q4 `--devices cpu` 下的 `#gpu`：同一支持面编译、主机后端执行**，但必须在 profile 的 `hints` 里显式写出"该作用域在主机后端执行"。理由：CPU-only 的 CI 要能测 GPU 路径；而"设备不可用"（`0x70`）属于**默认 `--devices` 且没有设备**的情形——区别在于用户是否**显式**说了只有 CPU。**可推翻。**

9. **Q5 空作用域：沿用 9.4 的 `TagHasNoReader` 警告**，不再加"标签没有效果"的第二条码。同一个事实两个码，正是 5.01 要清掉的那类重复。
