# A 的"只带类型"的单元，类型从哪来

裁定：待裁（作者 2026-10-30 尚未定；当前按"默认建议"做）

## 现象

第 11 条定了 A（`docs/handover/reviews/questions-2026-10-30.md` §1）：跨 `yield` 的值做成单元，
单元"带类型、暂不赋值"。运行期那一半是现成的、且与 B 同形：`__builtin__var_new__`
（`src/builtin/operators/ops.cpp:215`）建的就是一个 `Tuple`，而 `Tuple::create` 把槽填成 `NullSlot`
（`include/camel/core/rtdata/tuple.h`），所以"无值单元"在运行期就是"槽里是 null"；A 与 B 的差别只在
编译期证不证。GIR 也不需要新节点种类：`OperatorIndex` 的构造子是公开的
（`include/camel/core/operator.h:70`），可以直接合成一个 `() => var T` 的 `:var/new` 实例，
用 `addOperNode(op, 0)` 建出这个单元（`src/execute/exec_plan.cpp:731` 已经处理 `norm.empty()`）。

卡住的是 `T`。单元建在"流被创建"时跑的那段体里（`src/compile/gct/builder.cpp:5685`），
那一刻要给出 `T`，而 **GCT 只认写出来的类型**：`typeScope_`/`visitType`
（`src/compile/gct/builder.h:36,61,394`）里没有表达式的类型。`loop i = 0` 的初值是个字面量，
GCT 顺手就有 `int64`；但 5.4 点名的 `pairs(n)`，内层是 `loop j = i + 1`，`i + 1` 在 GCT 处没有类型。

GCT 唯一能表达"某表达式的类型"的机制是 `typeof <expr>`（`builder.cpp:6129`，`TypeOfType::create`），
而 GIR 解析它是**在使用处把表达式建出来**（`src/compile/gir/builder_generics.cpp:2465-2489`），
也就是建在创建体里。于是：

- `pairs` 两层能过：外层 `i = 0` 是常量初值，创建时单元 `i` 已有值，探针读 `i + 1` 拿得到 `int`；
- **三层嵌套过不去**：`loop k = j + 1` 的探针在创建时读单元 `j`，而 `j` 那时还没有值——
  它会被下一页那条"写之前读"的证明拒掉，而且拒的理由离作者想说的意思很远。

## 两条路

1. **接受"三层及以上不保证"**：A 的 `T` 一律来自 `typeof <初值表达式>` 在创建处的探针。
   代价：循环状态的初值最多依赖**一层**外层状态，更深的依赖给出"写之前读"那种错误（指向不直观），
   需要写进语言参考。收益：不碰类型系统，A 本体是 3 行运行时 + GIR 一条分支 + GCT 一个
   `addCellTyped`。附带地，`for v in xs` 的迭代器类型同源可得——但只有 `xs` 是参数、局部或字面量
   （也就是"创建时读到的值与循环处的值相同"）时成立；`for v in f()` 会被拒，因为探针会把 `f()`
   建在创建体里，等于让函数体在被创建时执行了一句（违反 5.4"被调用时函数体一句都不执行"）。
2. **给 GCT 加表达式类型**：让 GCT 能算出算术、读取、调用的静态类型。两种做法：
   在 GCT 里再走一遍类型规则（等于把 GIR 的类型规则复制一份，两处会漂）；
   或给 GIR 加一个"只求类型"的构建模式（不产生节点、不连边、允许读未赋值单元，只取
   `nodeTypeOf` 的结果）。代价大（一处新的构建模式要照顾诊断、期望类型、泛型实例化），
   收益是 A 对任意深度成立、`for` 的任意序列也成立，且 5.4 里"状态 `S` 是结构体"那句将来也有路。

## 我方默认建议

按 **1** 落（现在就能把 `pairs` 与常量初值的 `while` 一起做出来），把 **2** 记为后续；
并在语言参考里写明"循环状态的初值最多依赖一层外层状态"，把限制说在明处而不是让它以
"写之前读"的样子冒出来。
