# 声明状态的载体：待作者裁定

`stdlib` 的**已声明的状态**（`prelude` 与它拉进来的模块的 parse / GCT / declare 产物）现在每个程序都重编译一遍。这一页不是实现说明，是要作者裁定两件事：**产物放在哪**、**它用什么失效键**。数字是本树 `develop` 的 Release 构建实测（估算处写明），锚点都是当前源码。

## 1. 要省的是什么

最小程序 `func main() sync { let x = 1; println(x) }`，`std::nvm`，`--time-phases` 的 `cpu_ns` 自时间，9 次取中位数（墙钟在这台共享主机上不可用：同一程序墙钟 44.8 ms、阶段和 12.24 ms）：

| 阶段（cpu 自时间） | ms | 份额 |
|---|---:|---:|
| `startup`（含 `mm_init`、`context`、`builtin_module`） | 4.326 | 35.3% |
| `parse prelude` | 1.700 | 13.9% |
| `gct prelude`（`types` 的四个阶段嵌套其内，此处已扣） | 1.708 | 14.0% |
| `declare prelude` | 2.214 | 18.1% |
| `types`（resolve + parse + gct + declare） | 1.136 | 9.3% |
| entry + teardown（`parse/compile/gct/declare min`、`gir`、`encode`、`pass`、`teardown`） | 1.139 | 9.3% |
| 合计 | **12.242** | |

前奏三步 5.62 ms（45.9%），加 `types` 是 **6.76 ms（55.2%）**；`startup` 的 35.3% 要的也是这份已声明的状态（内建模块的构造就是它的 C++ 一侧）。`import autodiff` 再 **+6.59 ms**：`autodiff` 2.51、`graph` 1.89、`rewrite` 1.49（三者都含 `cmo_load`）、entry 的 `gir` +0.74。`cmo_load` 合计 1.46 ms 是 `dlopen`，**不可缓存**；可缓存的只有 `graph`/`rewrite`/`autodiff` 三者的 parse+gct+declare 共 4.3 ms（`types` 在基线里已经编译过一次，增量不带它）——所以产物必须覆盖**声明模块通过 `rule`/标签间接拉进来的模块**，不能只覆盖程序自己 import 的那些。

要搬运的量（同一程序）：`ast.nodes 2686`、`gct.nodes 1049`、类型存储 557 个对象 / 141,813 B（约 139 KiB）；`prelude` 129 个 `func`（47 个泛型、34 条 `when`、1 个 `type`），`types` 17 个 `func`（全泛型）、8 个 `type`。

## 2. 两条路

### A. 安装内产物（构建期产出，随 install 落地）

产物是 `<install>/stdlib/declared/` 下的一份索引加每模块一份数据：安装指纹（`build-info.json` 记的那一个）、每模块的源码文本摘要、以及该模块的已声明状态（intern 的类型、GCT、declare 的产物）。

- **前提**：一个能写能读的序列化格式；一个类型读者；把生效条件挂到已有的安装指纹上（`scripts/common.js:625` 的 `sourceFingerprint` 与 `writeBuildInfo`，`scripts/collect-out.js:346` 是它的调用点）。
- **代价**：格式本身是 graph-model 第 9 步那份工作的主体，其自估 **约 1,900 行新代码**（`docs/design/graph-model/README.cn.md` §7 迁移计划，第 9 步那一行），包含写出、装载、失效；类型读者另算。产物**不会被写进 git**（落在 `out/<tag>/`，`.gitignore` 已有 `out/`，与 `*.cmo` 同理）。
- **与 graph-store v2 的先后**：紧随其后，不能并列。v2 的模型是"只有一种图、身份稳定、冻结的图就是缓存文件"（`docs/design/graph-store/README.cn.md` §2 原则 3，整份设计已确认；`docs/roadmap.cn.md` §3 写"优先实施"）；而今天同一份图**构造三遍**、图的身份是 `GCGraph*` 地址加过渡字段（同文件 §1），前端图没有可冻结的形式。在 v2 之前写产物，等于先自造一个格式，v2 落地时再写第二遍。

### B. 设计原则 10.3 的 `__cmc__/`（运行期写，放在源文件旁）+ 四条失效

- **前提**：同样要序列化格式与类型读者；还多一条今天不存在的判定——"导入方的缓存在**导出函数的签名（含推断出的返回类型）、它间接用到的模块级值、它的效应、泛型函数的体**任一项变化时失效"（`docs/design-principles.cn.md` §10.3）。这四项要每模块算指纹，而今天 `--verify-ops` 读的是源码，没有这样的指纹。
- **代价**：§10.3 明写"先默认关闭…**是否采用仍待裁定**"，打开它是另一次裁定；缓存写在用户可写目录，只读安装（发布包）里没有可写的地方，于是发布形态下等于没有；一条运行期的失效问句要长期维护。
- **与 graph-store v2 的先后**：同样在 v2 之后——10.3 的缓存文件就是冻结的图块。

**两条路不是同一件事**：A 是"构建期算一次、随安装分发、一个安装一份、跨机器可共享、运行期不写目录也没有失效问句"；B 是"每个用户、每个源目录各自算、默认关闭、按模块判定失效"。设计原则 §9.3 末条那句（`docs/design-principles.cn.md`）"声明随标准库预编译进缓存模块，编译程序时加载编译好的结果"说的是**效果**，两条路都能满足它，所以它不能当作其中一条的依据。

## 3. 前置依赖链（顺序是硬的，前一项不落地，后一项无意义）

1. **graph-store v2**：一种图、稳定身份、冻结的内存布局（`docs/design/graph-store/README.cn.md`，已确认未实施）。在此之前没有任何"可以写进文件的前端图"。
2. **序列化设施**：写出、装载、格式版本、校验，以及"装载失败即退回源路径"这一条（宁可慢，不可读错）。
3. **类型读者**：`include/camel/core/type/intern.h:13` 说"A type has no identity, only structure"——类型只能由 18 个具体类的构造器自下而上 intern 出来，从文本或二进制都没有入口；原生类型另按注册名（`registerNativeType("prelude", "Error", …)`）。这是 AST 恢复、GCT 恢复、跳过 declare 三者**共同**的前置，绕不过。
4. **产物与 stamp 对接**：产出步骤挂在 `scripts/collect-out.js:346` 的 `writeBuildInfo(config, tag)` **之前**，指纹用同一个 `sourceFingerprint()` 先算出来，同时写进产物索引与 `build-info.json`——两者一致是构造出来的，不是事后校验；运行时在 `Context::checkPreludeDeclarations()`（`src/core/context/context.cpp:733`）与 `Context::loadModuleFrom`（:933）按"格式版本 → 安装指纹 → 模块文本摘要"校验，任一不符一行 `warn` 后退回源路径。
5. **`test/tools/startup-cost.mjs` 的断言同改**：它现在要求 parse / GCT / declare 里每个 `(阶段, 模块)` **恰好出现一次**（:324）。产物一生效，`prelude`/`types` 的这些阶段就消失——闸门必须同一次改，否则要么红，要么把一个子集当成全部来定价。

## 4. 需要裁定的问题

**Q1 载体：A（安装内产物）还是 B（`__cmc__/`），还是"先只做前置层"？**
- A：前提与代价见 §2；与 v2 是"紧随其后"。
- B：前提与代价见 §2；同样在 v2 之后，且先默认关闭。
- 第三条：只做 §3 的 1–3（v2 + 序列化 + 类型读者），产物延后到 v2 落地后再定形。
- **倾向 A**，依据三条：A 的键今天就有（`sourceFingerprint` 与 `build-info.json`），B 的四条语义失效键今天没有判定手段；产物本身与用户机器无关，`startup` 那 35% 要的也是它；B 的运行期写目录在只读安装里不成立，发布形态下等于没有。

**Q2 格式：等 v2 用冻结图块，还是先自造一个临时格式？**
- 等：产物与缓存文件同形，只写一次；代价是这项排到 v2 之后。
- 临时：能提前量到收益；代价是同一份工作写两遍，且临时格式的字节布局与 v2 不同，装载器也要重写。
- **倾向"等"**。依据：graph-model 自估 1,900 行是**写一次**的成本；写两遍就不是这个量级，而这 6.76 ms 不构成等在 v2 前面的理由。

**Q3 产物覆盖到哪：只 `prelude` + `types`，还是全部声明模块？**
- 只前两个：省 6.76 ms 里的一大半，但 `import autodiff` 的 4.3 ms 不变，账会被人问第二次。
- 全部声明模块（含 `graph`/`rewrite`/`autodiff` 这些被间接拉进来的）：一次把账做完。
- **倾向全部**。依据：§1 的 `cmo_load` 不可缓存与"声明模块间接拉进来的模块"两条，只覆盖前两个会让产物看起来生效而程序仍然重编译。

**Q4 失效键：安装指纹 + 模块文本摘要，还是 10.3 的四条语义失效？**
- 文本摘要：改了含义就改了文本，先于任何读取失败；实现是一个 SHA-256，今天就有。
- 语义四条（签名/模块级值/效应/泛型体）：更精确（改注释不失效），但需要一个今天不存在的签名与效应指纹。
- **倾向文本摘要 + 安装指纹**，"宁可慢，不可读错"：注释改动导致一次重编译是可接受的代价，反过来（改了含义却命中）不是。

**Q5 `startup-cost.mjs` 的"每 (阶段, 模块) 恰好一次"改成什么？**
- 保持原样，产物生效即红；
- 改成"每个模块要么出现一次编译，要么带上装载记录"；装载记录成为一个新阶段（例如 `load declared <module>`），这样"重复编译"仍能被抓到。
- **倾向后者**，且装载阶段要进同一张阶段表，验收才可能把省下的时间对到具体阶段上。

**Q6 验收的测量口径**：2–6 ms 级的前后对比必须先有安静窗口协议（见 `docs/test-plans.md` 的"Performance Measurement"新增一节）。这一条要作者确认它是**验收前置**，而不是可选的谨慎。
