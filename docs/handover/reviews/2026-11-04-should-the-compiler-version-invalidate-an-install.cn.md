# 编译器的**版本**要不要进构建指纹？

## 问什么

`out/<tag>/build-info.json` 的 `buildOptions` 今晚起记了"哪些选项"（`scripts/common.js: buildOptions`：
`cmake/options.json` 各选项的生效值、`CAMEL_TARGET_ARCH` / `CAMEL_SKIP_PYTHON`、平台、编译器**选择**），
`scripts/build-info.js check` 拿它和"现在重建会传的选项"比，不符就拒绝 `-NoBuild` 复用。

**该判的是"这一次重建会不会得到这个安装"。编译器换一次（同一台机器上升级 clang，主机现在是
`~/camel-eval/conda/envs/clang/` 的 23.1.2），要不要让这个判据把它判成过期？**

今天记的是 `compilerFlags: "-DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++"`——**哪套编译器**，
不是**哪一版**。所以工具链升级后，旧的安装照样"匹配"。

## 读数（可复核）

- 同一棵树 `34b659107`、只差 `ENABLE_FASTVM_JIT` 的两次构建（闸门 `-Plan
  test/plans/feat/linear/jit_without_codegen.plan.toml -Tier fast -Jobs 4`）：
  源码指纹两次都是 `6469cf0e84fd…`（1300 个文件），选项指纹 `451796605bb0…`（JIT=ON）与 `c71598f0fc4a…`
  （JIT=OFF）。**同一套选项的任意次重建，选项指纹不变**（ON 那一版在三次构建里都是 `451796605bb0`），所以
  `-NoBuild` 不会因为"又建了一次"而失效——这是这条判据能用的前提。
- 工具链升级本身**不会**让 ninja 重编：编译命令行、头文件、源码都没变，`build.ninja` 的依赖判据里没有编译器
  二进制的身份。`scripts/gate-time-check.mjs` 已经把这条钉住了（"未改动的树必须零目标"，读的是 `ninja -n`）。
  也就是说：工具链升级后跑一次 `npm run build`，产物与升级前**逐字节相同**；此时的 `-NoBuild` 复用是诚实的，
  "现在重建一次"也只会得到同样的字节。
- 于是"把版本记进指纹"会拒绝一个**重建也改不动一个字节**的安装。要让它不误报，只能把版本判据改成"只在真的
  重编之后才比"，那就是另一条判据了。
- 反方向确实存在：有人删 `build/`（或改源码）重编，二进制才真的换成新编译器的产物；那种情况今天的判据不拦
  （它比选项，不比编译器），读的人只能从 `builtAt` 和 `build/footprint.json` 看出来。

## 三条路，各带代价

**A. 只记选择（现状，本页默认）**
- 判据保持"重建会不会得到这个安装"，工具链升级不会制造假过期；一条读数仍然只由树 + 选项决定，两台机器上的
  结论一致。
- 代价：升级后的安装里那块二进制是旧编译器做的，而 stamp 上看不出这一点；只有"删 `build/` 重编过"的情况才
  真的换了编译器，而那时 `-NoBuild` 不比编译器、不会拒绝。

**B. 把版本记进去（`clang --version` 或 `CMakeCache.txt` 的 `CMAKE_CXX_COMPILER_VERSION`）**
- 好处：任何"编译器不同"的安装都判过期，连删 `build/` 重编这种情况也拦得住。
- 代价：① `check` 要问一次编译器（或读 cache——而 `--install` 指向别的安装时 cache 不属于它），多一条"找不到
  编译器就没法判"的分支，而那条分支要么拒绝（`-NoBuild` 在没装编译器的机器上直接不可用）要么放行（又回到今天
  的洞）；② 工具链升级后**每个**安装都被判过期，包括按上面的读数"重建也不会变"的那些；③ 同一条读数在两台
  工具链不同的机器上得出不同结论。

**C. 记成信息，不参与判定**
- 好处：想核这件事的人能在 stamp 里看见"这个安装出自 23.1.2"，成本是一次 `clang --version` 写进 stamp。
- 代价：`check` 不比它，所以它不拦任何东西；而它长得像一条判据，读的人会以为它拦。

## 默认（本轮按这个开工，不等回复）

**走 A**，`buildOptions.compilerFlags` 只记选择，不探版本。理由：这条判据要回答的是"重建会不会得到这个安装"，
而工具链升级后重建得到的**正是**这个安装（读数第三节，且 `gate-time-check` 的零目标判据是这个结论的另一半）；
B 会把正确答案判成过期，代价是"升级一次工具链、每个安装都要重建一遍"并且多一条依赖 `PATH` 的分支。
若作者要可见性，C 是比 B 便宜的中间态，只需要在 `buildOptions` 里加一个 `compilerVersion` 字段、`check` 不读它，
本车道没有做。
