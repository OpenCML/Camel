# 产出处的那一个减一由谁发：编译器，还是运行时？

- 日期：2026-11-15
- 状态：待作者裁定；默认建议已写死在下面（编译器发 dup/drop，运行时只提供两个原语）
- 相关：原则 10.5（不可变值与 `Ref<T>` 句柄只按计数回收，计数归零立即释放）；裁定 `bed72f456`；
  记录 `2026-11-15-is-a-handles-count-the-slots-or-the-wrappers.cn.md`

## 问题

`bed72f456` 把病因定在「计数不准」：存进第二个槽、被闭包捕获、放进聚合时计数没有加一，所以计数从来不等于持有者
的数目；修法是每多一个持有者 +1、持有者消失 −1、归零即释放，四个后端调同一组核心内存层入口。

**加减已经配齐了，可每一块的计数还是到不了零。** 缺的不是「槽上的加一」，是「产出处的那一个减一」——谁发它？

## 实测：只做加一/减一的结果

在核心内存层加了 `retainCountNow` / `giveBackCountNow`（不为槽分配 wrapper），在 `Frame::set` 里对句柄槽做
「新的 +1、旧的 −1」，在 `FramePool::release` 里对每个句柄槽 −1。四个后端读数一致：

| 用例 | created | released | live |
|---|---|---|---|
| `boxes_are_counted` | 1001 | **0** | **1001** |
| `boxes_loop_ten` | 11 | **0** | **11** |
| `boxes_loop_thousand` | 1001 | **0** | **1001** |
| `boxes_made_per_call_ten` / `_thousand` | 11 / 1001 | **0** | **11 / 1001** |

`value.counter_closure` 与 `value.ref_one_cell_two_holders` 四个后端同时变红。

## 病因：出生时那一份 retain 没有主

`ForeignResourceObject::create` 一出生就 retain 一次（`refCount_` 起于 1），这份引用是「产出者手里那一份」。值被存
进槽之后，槽上又多 +1，而产出者那一份**没有任何地方还回去**：帧释放只把槽上的那一份减掉，于是计数停在 1
（或 2、3）上，永远到不了 0。这不是「减一不安全」——是**加减的配对里少了一端**。

补上这一端需要知道：一次存进槽，是**转移**了产出者手里那一份（那就不该 +1，或者该在产出处 −1），还是**复制**了
出一份新的（那就该 +1，且产出处那一份另行还给）？这个判断在运行时看不到——`Frame::set` 拿到的只是一个槽值，
不带「这一份归谁」的信息。只有编译器知道。

## 默认建议（写死）

**编译器在产出与存槽的边界发出 dup/drop（Perceus 式）：**

1. 运行时只提供两个原语——`retainCountNow`（一份新的持有者出现）与 `giveBackCountNow`（一份持有者消失）——放在核心
   内存层，四个后端共用，不为槽分配 wrapper。
2. **`Frame::set` 不承担判断转移/复制的责任**：它只存槽；加一减一由编译器发出的 dup/drop 决定，落在 `set` 之前
   或之后。
3. 相应地把「出生时那一份」也交给编译器：`create` 不再自带一份无主的引用，或者由编译器在产出点显式发一次 drop。
4. 按这个默认，**本车道不再动运行时**，等编译期那一侧；运行时这一侧的可复用件（两个原语、四个后端的同一入口）已经
   量过、可以留作基础。

替代方案（不推荐）：让 `Frame::set` 用「计数是否为 1」猜一次转移（`count == 1` 视为交出）。它在 `let b = a`
（两个槽命名同一份值）处必然猜错，正是这次要修的病灶，**不要走这条路**。
## 决策者答复（2026-11-15）

**同意由编译器一侧决定加减，运行时只提供两个原语；但"编译器"在这里指执行计划上的一次分析，所有后端共用，不是每个后端各写一份。**

1. 持有者就是图上的使用：一个值节点的产出由它的每个使用者各持一份，最后一次使用把产出者那一份交出去（转移），其余使用是复制（加一）。在执行顺序上算一次"最后使用"，就得到每个节点之后要还哪些引用。这正是 Perceus 的规则，只是作用在图上。
2. **这次分析已经有现成的一半**：`planStorageReuse` 证明存储复用时已经按执行顺序算了谁在谁之后运行、哪个值最后一次被用。最后使用由它算，不另写一份。产出的结果是计划的一部分（每个节点之后要还的引用列表），四个后端只照着执行，不各自推导（目标架构"后端不各自推导语义"）。
3. 出生时那一份归产出节点的产出，存进槽是转移，不加一；`Frame::set` 不猜，`count == 1` 的猜法不要。
4. 验收与上一页相同：在运行中途量，`live` 不随次数增长；`counter_closure`、`ref_one_cell_two_holders` 仍绿。

归第 4 路，排在优先级一之后。上一页撤回的"入口返回处收集"不要再加回来，见另一页：运行中的收集今天会撞上 defun 的类型缺陷。
