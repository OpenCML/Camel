## a-void-arm-and-a-cell-typed-arm-collide

**单元格（cell）不是值，任何取值的位置都先读出它的值。** 定为 (a)，再加一条：
1. **不取值的位置，汇合处不取值、丢掉臂的值**，与"没写 `else` 的 `if` 汇合处不取值"是同一条规则。`void` 函数里的 `return if … then null else (x = x + 1)` 就属于这种位置：两臂的效应照常发生，没有值要汇合。
2. **取值的位置，单元格先读出它的值再参与汇合**。一臂是单元格 `var T` 时，按 `T` 汇合，`void` 臂照原则给 `null`，得到 `T?`。单元格类型永远不进入汇合、实参值或绑定。
   - 这两条一起修掉 `coerceArmExit` 的段错误。
   - Release 下被编掉的那条断言，改成一条带位置的内部错误，不能再静默变成空指针。
3. **写捕获的调用交出的版本只在被读取处物化**（即 (c)）。它们是图上的状态边，不是用户可见的值类型，所以不和 (1)、(2) 冲突。
4. **Debug 下 `Node::ruleBinding` 被用在 DECL 上的断言是真缺陷**，你们修：`isGenericHere` 对 DECL 不该走 rule 绑定。

## holes-in-non-literal-positions

两条都**统一**，报点都挪到洞上。
1. **`[n]` 与 `[1.0, n]` 同判**：字面量写没写下别的元素，不影响它进不进入位置。
   - 位置给出的元素类型交给每个元素，字面量元素取它，洞对着它检查。不符就在**洞**上报 `ElementTypeMismatch`，参数、声明、箭头三处一样。
   - `wroteAnElement` 这条分界删掉。声明位回退里那一次 `coerceTo` 转换也删掉（洞不转换）。

## tail-call-chain-handoff

**接值门，即你们试的第一条路，按 5.3 与上一条"等待由只转发的 GATE 背"的裁定。** 31 条红按"形状断言可以重录、行为差异必须修"（控制边退役的裁定）处理，不是不能落地的理由。

规则只有一条：**被拼接体的链尾继承调用原来被等待的每一种方式**。
- 调用的 sync 或控制后继，改为等体的链尾（现状已做）。
- 调用的值的读者，改读一个 GATE：它读体的值，等体的链尾。调用"做完了效应才交出值"，这件事在拼接后要由这个门来表达；尾调用的值就是这样把链接到出口的。

- 体的值节点就是链尾本身：不造。

## specialized-copy-inline-call-target

**两样都要：能折就折，折不了就由程序范围的预算封住。** 链经过基函数回到环里不是问题，副本之间互相调用也是合法的递归；问题在于现在什么都停不下来。
- **折掉，这是正常的结束方式**：链上每一份副本里，出口判断（`t >= steps`）的实参都是编译期已知的，判断能折叠，就该折掉，链就在那一级自然结束。`shape_unroll` 要的正是这个。所以每造一份副本，先对它做折叠，再解析它体内的调用。
- **封住，这是兜底**：每个基函数造副本的总数，是**整个程序、跨所有轮次**的预算，不是每个会话、每一轮重新计数。用尽之后，再解析到的调用一律指向基函数，环由基函数收口。现在的读数（只走一步也照样垮）正说明预算每轮在重置：每一轮都把上一轮留在基函数上的调用再特化一次，`std::opt` 的不动点于是永远到不了。
- **"环里的 callee 不复制"那道门照旧**：副本在环里，就不内联；它们被调用，不被复制。
- **`got null`、输出全空先查清是哪一种**：超时被杀、内存耗尽，还是段错误。任何一种都不许留着：`std::opt` 必须对任何程序在有限步内停下，崩溃不是可以接受的结果。
- **验收**：
  - `shape_unroll` 在 `steps` 编译期已知时完全展开，`forward` 里没有对 `run` 的调用；`steps` 未知时，副本数不超过预算，其余调用指向基函数。
  - 那 20 条全部恢复。
  - `std::opt` 在整个语料上结束，提交信息列出最大副本数。

**第 6 条（优化改变哪些效应执行）的判据已定**（负责人选 F28 的 (d)，原则 3.3）：存活就是"从出口沿数据、with、sync、control、**顺序**边反向可达"。
- **建图时**：没有用处的效应在连链之前删掉，所以带顺序边的效应都是存活的。
- **之后的遍**：删节点时把它的顺序前驱接到后继上（与 `closeChainOver` 对 sync 边同理）；`dce` 算可达性时把顺序边算进去。
- **顺序边从不从区域外进入区域内**：臂和循环体里的效应在外层链上由 `BRCH`、`LOOP` 代表。
- 修好后 F28 的例子在优化前后都打印 `1 2 1`。
- **第 6 条再加一个用例**（ECOOP F31）：`let a = println(1); let r = if c then a else 0; return r + println(3)`，`c` 为假。解释器、`std::fvm`、`std::jit` 打印 `1 3`，`std::opt std::nvm` 只打印 `3`。效应留在书写的区域里，由任何一侧（臂里的使用，或后面的同资源效应）第一次需要时执行一次。遍不得把效应沉进臂或提到分支之前，只有可自由安排的计算能跨区域移动（原则 3.4）。
8. **带形状注解的 `let` 丢了形状**（ICPC 阅读题，ef49a1d5d 复现）：`let x: f32[3] = [1.0, 2.0, 3.0]` 之后 `x` 的类型是 `f32[]`，传给 `f32[3]` 的形参报 `ArgumentNeedsConversion`。按原则"声明写下的形状就是值的类型"，`x` 是 `f32[3]`。修在 `let` 注解给绑定定类型的那一处，补用例：传给 `f32[3]`、`f32[n]`、`f32[..]` 都接受。
9. **值没人用的语句，必须恰好有一条诊断**：`T!` 用 `UnusedFallibleValue`，不论在不在同步块；不在同步块的效应用 `EffectNotExecuted`；纯的用 `UnusedPureResult`。研究里有一题（R40-W，程序向论文侧要）在非同步函数里丢掉一个 `T!` 调用，什么诊断都没有，这是缺陷。验收：一组用例覆盖三种语句、同步与非同步两种体，各恰好一条诊断。
   - **第 9 条的两个用例**（`Camel-Archive/ICPC2027/study/read-items/programs/R40-gn-W.gn`、`R29-gn-W.gn`）都在**同步**函数体里，丢掉的是一次纯的、返回 `T!` 的调用（`check_same(a, b)`、`validate(x)`）。
     - R40 没有任何诊断，R29 报的是 `EffectNotExecuted`（被调函数是纯的，这条也不对）；
     - 两者都应当是 `UnusedFallibleValue`，即原则 3.9 第 240 行"同步块里一个 `T!` 的值没有被使用，是编译期警告"。
