# 算出来的类型能不能当字面量的头：这条规则铺到哪为止

作者说"凡是能写类型名的地方都应能写类型表达式（规则统一）"，并让在语法改动牵涉面大时单写一页。这里就是那条边界：一个规则集要把值提升成"值加零切向量"，零切向量的类型是算出来的（`Tangent<T>`），而今天用这个类型**造不出一个值**。

## 现象到符号

- `stdlib/rulesets/jvp.cml#zero_tangent` 要返回 `Tangent<T>`。对 `T = float` 它写得出（`0 as T`）；对 `T = (float, int)` 它的切空间是 `(float, ())`，只能靠逐成员构造：`Tangent<T> { static for n, _ in fields T => zero_tangent(x.[n]) }`。**这一句解析不了**：字面量的头部只收类型名，`stdlib/optim.cml#zeros_tree` 里同样的写法只对类型**变量** `P` 成立，对类型**调用** `Tangent<T>` 不成立。
- 同一件事出现在语法文档里：`docs/language/en/06_expressions.md` 说 `match type` 后面、`fields` 后面都是类型位置（那里 `(` 就是类型的开头），而字面量头部不是——**同样是"一个类型该能站的地方"，两处的规则不同**。
- 语法是手写的：`src/parse/syntax/parser_expr.cpp` 解析字面量，`src/parse/ast/type.cpp` 解析类型；两条路径今天不共用。

## 为什么不能自己定

"铺到哪为止"不是实现细节：只放宽字面量头部，`as` 的右侧、泛型实参、`match type` 的分支就仍各写各的；一条规则铺到所有类型位置，改的是语法的形状，牵动解析、AST 与后端的"期望类型"传递，还要决定类型调用作为头部时如何推导成员的类型（今天的头部类型**就是**成员类型的来源）。这落在作者那句"规则统一"的射程里，但射程的端点由作者定。

## 选项

- **① 只放宽字面量的头部**：`Tangent<T> { ... }` 这种头部按类型表达式解析，别处不动。**要多造**：字面量解析路径对头部的解析改走类型表达式，AST 记下"头是一个类型表达式"，后端按它的类型取成员类型；一条用例守住 `Tangent<(float, int)> { ... }` 能构造、成员类型逐个对上。好处：最小改动，立刻解开规则集的元组/结构体分支；代价：规则仍不统一，"类型名 vs 类型表达式"的差别还在别处。
- **② 一条规则铺到所有类型位置**：凡是类型位置都收类型表达式（字面量头部、`as` 右侧、泛型实参、`match type`、`fields`）。**要多造**：上面那些位置逐个改解析并各配用例；还要写清"类型调用在头部时成员类型从哪来"。好处：一处规则、一处文档，`Tangent<T> { ... }` 是它的一例；代价：改的是语法本身，用例面大。
- **③ 不改语法，库侧换写法**：用一条 `let z: Tangent<T> = …` 的间接构造或一个"构造器"函数把聚合体的零切向量造出来。**要多造**：绕开头部的写法（若存在），以及它在类型上是否真的等价；一份用例守住它。好处：不动语言；代价：`Tangent<T> { ... }` 仍然是写不出来的东西，往后每一个"算出来的类型当字面量头"都要再绕一次。

**默认建议：①**。它解开今天挡住规则集的那一处，且不需要先回答"类型调用当头部时成员类型从哪来"这个更大的问题；②是作者那句"规则统一"的完整射程，适合单独一次改；③只是绕路，不解决不一致本身。

裁定之前 `stdlib/rulesets/jvp.cml` 的元组与结构体分支不落地：今天的 `zero_tangent` 只覆盖浮点标量与张量，聚合体在那里被类型拒绝（不是拿到一个错的零）。
