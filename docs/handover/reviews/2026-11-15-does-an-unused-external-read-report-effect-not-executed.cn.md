# 没人用的外部读，还要报 `EffectNotExecuted` 吗？

## 事实

原则 3.1（`docs/design-principles.cn.md:113`）把外部资源的**读**和变量的读放在一起：

> 外部资源的读与变量的读一样是依赖：结果有人用才执行，**没人用时不执行也看不出区别**（负责人 2026-11-14）。

这一句正面规定了**执行**——没人用的外部读不执行，而且这是"看不出区别"的。它没有规定**报告**：同一段没写要
不要告警。今天编译器为它报 `SemanticDiag::EffectNotExecuted`，和一个位于死区域里的**写**得到同一个码：

```cml
import { get_env } from env

func main(): int {
    get_env("CAMEL_REGION_ROOTS_NO_SUCH_VARIABLE")   // 结果没人用：不执行，并报 EffectNotExecuted
    return 0
}
```

这条读数由 `test/plans/feat/compile/region_roots.plan.toml` 的 `region_roots.read_only` 钉住（stdout 为空，恰
好一条 `EffectNotExecuted`）。

本轮的改动（区域的根，3.1「对外部资源的写由所在区域用到」）之后，`EffectNotExecuted` 只剩两类来源：**外部读**
的结果没人用，和**死区域**（循环或分支的值没人要）里的写。写在一个运行中的区域里，无论 `sync` 与否，一律不
再报。

## 为什么这需要一个答复

两种读法都站得住：

- **留着报**：`EffectNotExecuted` 是在说"你写的这条语句没跑"。外部读可能失败（打不开的文件、外部状态在读的
  那一刻变了），把它静默丢掉，读的人会以为读过；这条告警是保守方向。
- **不再报**：原则自己说"没人用时不执行也看不出区别"。既然看不出区别，报它就是噪音，而且它和"死区域里的写"
  共用一个码，会让一条本无问题的调试残留看起来像缺陷；`docs/design/effects/analysis.cn.md` §4 的另一个方向
  是把这个码整个删掉。

规则上没有第三种：一个码只能有一个含义，现在它同时表示"读没跑"和"写所在的区域没跑"。

## 默认建议（按此开工，不另等）

**保持现状：没人用的外部读继续报 `EffectNotExecuted`**，理由取上面第一条——静默丢弃一条用户写下的外部访问，
比一条可关掉的告警更糟（`-Wno-effect-not-executed` 已经提供了关闭的办法），并且**不**为了消除它去动诊断的
正文与帮助。若作者的答复是要么删掉这个码、要么把它拆成两个，那是另一轮的范围：本轮的改动只把"对外部写不再出
现"做干净，没有削弱它对外部读与死区域的报告。
## 决策者答复（2026-11-15）

**都不选：没人用的外部读不报 `EffectNotExecuted`，报"结果没人用"。** 原则 3.3 的用词：读是依赖，不是效应；所以说一个读"效应没执行"，用词本身就错了。这条语句的毛病是写下了一个没人用的值，与纯计算的结果没人用是同一件事，同一类事用同一个诊断：

1. 没人用的外部读报 `UnusedPureResult` 一类的"结果没人用"（必要时把这个诊断的正文从"不改变任何东西"放宽成"它的结果没人用，所以不执行"，帮助里提示"要它发生就用它的结果，或写进 `sync` 块"）。
2. `EffectNotExecuted` 只剩一个含义：一个写所在的区域没有运行（死区域里的写）。正文与帮助按这一个含义写。
3. 你担心的"外部读可能失败，静默丢掉会让人以为读过"由第 1 条覆盖：仍然有告警，只是说对了原因。

`region_roots.read_only` 的期望随之改成新的诊断名。归第 3 路，随区域的根这一项收尾。
