# H7 资源与副作用计划批复（协调者 2026-10-22）

计划接受，`docs/design/effects/plan.cn.md` 已合入 develop。按 §7 的十步施工，其中**第 1–2 步（内部模型、函数类型资源签名）不涉及语法、可独立先落**，先派。

这份计划值得肯定的地方先说清楚，因为它决定了批复的分量：它把"要新造一套推断"变成了"运行期已经有这套推断"——`FootprintWalk` 已是最小不动点、已丢弃本地新建资源、已按端口/捕获映射；`uses`/`pure` 落在既有的 `ResourceBinding`/`ResourceSpec` 上；`mayAlias`/`originOf` 已能判"同一个对象"与"两个新对象"。图上**只多控制边**，没有新节点/边/属性种类，`std::prl` 不用改。它还查出一个真缺口：`GraphFootprint` 把调用结果硬编码成 `Unknown`（`resources.cpp:302-303`），不补"结果来源"的话，`open` 出来的新句柄会把每个 `next` 串行。

## 五个问题

1. **Q1 `#resource` 只挂在名词性类型声明上：同意。** 别名会污染目标类型、内建类型没有身份；这条不是取舍，是唯一说得清的做法。

2. **Q2 "变化"的基线：同意相对写出来的 `uses`**（推断集超出即错误，推断集更小则警告"声明的资源已不再使用"），**"相对上一次编译"的警告等模块缓存**。理由：3.3 那句话的对象是"声明过宽"，不是"跨编译差异"；把一个警告绑在还没实现的缓存上，等于让 H7 等缓存。

3. **Q3 函数类型的资源用 `Generic` 模式在调用点实例化：同意。** 3.3 明确不做 Koka 式行多态；要求每个回调类型写资源行会把标准库的 `map`/`filter` 全部改签名，方向相反。

4. **Q4 返回的句柄按推断（`Same`/`Fresh`/`View`/`Unknown`），不按"返回即新资源"：同意，而且是必须的。** "每个值都是一个独立的资源"说的是**值**的身份，不是**返回动作**；按字面读成"返回即 Fresh"会让 `identity(s)` 之后的两个 `next` 并发，**直接算错**——这是语义错误，不是性能取舍。无体声明沿用 `ResultAlias`。

5. **Q5 `uses` 是上界约束，类型发布推断集：同意。** 只有发布推断集，"声明的资源已不再使用"才有对象；写出来的集合是承诺。**Q2 与 Q5 绑定**这一点计划自己指出了，我确认按这一对一起定。

## 需要作者裁定

- **Q2 与 Q5 是一对语言表面的选择**（`uses` 是约束还是发布值）。我按"约束 + 发布推断集"批，**可推翻**：你若选"发布写出来的集合"，Q2 的警告要重新定义，3.3 那句话也只能解释成"声明过宽时警告"。
- **`#resource` 的语法位置**（挂在 `type` 声明上）与**句柄类型的规范化**是否要进设计原则 3.3 的正文：现在是计划里的决定，建议随后并入 3.3 一段，不另立页面。
- **诊断码** `0x1A0`–`0x1A4`、`0x1001A0`、`0x3001A0` 的分配：计划查过目录（最后一条错误 `0x190`、最后一条警告 `0x100160`），我认这个块，但**错误与警告不要混在相邻号段**里，落地时按目录现有分区摆放。

## 条件

1. **第 1–2 步先落，且不引入语法**：内部模型（`ResourceClass::Handle` + 结果来源）与函数类型资源签名，能在今天的树上被测试断言（`mayAlias`/`originOf` 的用例、`GraphFootprint` 结果的用例），不需要新关键字。
2. **每一步都要有一个"会红"的用例**：这项工作的失效方式是**少生成一条控制边**，它在功能测试里通常表现为"结果仍然正确、只是变慢或偶发数据竞争"。所以第 6 步（builder 排序）必须有**图上的断言**（两条副作用之间有没有控制边），不能只靠结果比较；并说明如何在没有 TSan 的构建里让"少一条边"变红。
3. **`std::prl` 的流并发要有一个可观察的验收**：句柄类型落地后，两个不同句柄的 `next` 必须能并行、同一句柄必须有序——用 profile 的调度信息或图上的边来断言，不要用墙钟。
