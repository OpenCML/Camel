# 实参位置上递出去的闭包，要不要按引用捕获？

## 事实

第 4 步删「按引用捕获」的捕获口时，逐条放开三条保守门（`decideCaptureByValue` 的 `gate4` / `gate5` / `gate6`），
全删那一版把测试跑红 **84 条**。第一条红是：

```cml
// test/cases/linear/byref/var_param_reference.cml#main
func write_then_read(var x: int, f: (): int): int {
    x = 7
    return f()
}

func main(): int {
    var w = 0
    println(write_then_read(w, (): int => w))   // 改前打印 7，按值捕获后打印 0
    return 0
}
```

改前 **7**，改后 **0**：改后**编译通过、跑出错值**。

机制：闭包写在那个调用的**实参位置**上，而 `x = 7` 发生在**被调里**。按值捕获拿到的是闭包做出时的值（0），
所以被调读到的仍是 0。按引用捕获时两者是同一个 cell，所以是 7。

原则 3.5-198 本来该拒这条（`CapturedVarHandedToVarParameter`：「把 `var` 递给 `var` 形参」），但它的判据要求
**闭包的末次使用是一个源偏移、且写发生在它之前**。这里的末次使用**就是那次调用**，写发生在调用**里面**，
区间是空的 —— **规则漏了这个形状，报告不出来**。

所以这一门（`gate5`，按名字 `handedOver_` 判「这个名字当过任何调用的实参」）今天护的风险**没有任何人接住**。

本轮的处理（三条门逐条）：

| 门 | 处置 |
|---|---|
| `gate4`（程序级写者集，按名字） | **收窄**：`!localCell && programWrites(name)`。**局部单元**那一半本来就是假拒绝（按名字匹配够不到局部单元），删掉；**模块级单元**那一半留下，因为 `uses var` / `pure` 的账还骑在单元上（模块 `var` 那一项没落） |
| `gate5`（名字当过任何调用实参） | **留**，代码里写明「等 198 补上那个形状才删」 |
| `gate6`（捕获点与末次写的源偏移比较） | **删**（全库 0 处生效；3.5-198 已能报 `CapturedVarWrittenAfterTheClosure`，删前删后 stderr 逐字节相同） |

本轮真正删掉的是 **`gate4` 的局部那一半**与 **`gate6`**。代价：`:var/new` 410 → 408（238 文件不变），
按引用捕获口 621 → 604。**这一步的成效只有 −2 个单元 / −17 个端口，因为单元的主要来源不是这三条门**——
是模块级 `var`（`gate1` 护的那一项）、生成器与装饰块、`var` 形参，以及按单元的粘性判定。

## 补 198 之前必须先修的四处（捕获口变成值之后「不再被问」的专用诊断）

捕获口从 cell 变成值以后，闭包体里的名字**不再是变量**，通用规则先开火，专用规则根本没机会被问。这一笔修了
赋值目标那一处（把 `requireCapturedNameWritable` 重挂到端口上，否则 **3.5(197) 不再被报**），剩下的必须记下来：

| 位置 | 症状 | 覆盖 |
|---|---|---|
| `builder_calls.cpp#Builder::requireMutableArgument` 的 `isVariable` 门槛 | 按值捕获的名字递给 `var` 形参时，198 那条不再被问，落到通用赋值规则 | **今天被 `gate5` 掩盖；删 `gate5` 之前必须一起修** |
| `builder_operators.cpp`「`xs` 是持有数组的变量」那一处 | 就地重载不再命中 → 变成 `NoMatchingFunction` | **无用例覆盖，静默** |
| `builder_diagnostics.cpp`「bind it to the result」那一处 | 端口不再是变量 → 少一句提示 | **无用例覆盖** |
| `builder_control.cpp#mutableName` | 端口变成不可变 → 允许窄化 | 良性，可证明安全 |

**未查**：`builder_static.cpp` 三处常量折叠、`builder_resources.cpp` 两处、`builder.cpp` 声明处。

> **这四处里有两处没有任何用例覆盖。** 它们不会红，也不会报错——**它们只是不再说本来要说的话**。
> 补 198 时若只改那一条规则而不看这张表，就会把一个「规则丢失」当成「规则修好」。

## 为什么这需要一个答复

三种读法都站得住：

- **补 198**：让「闭包作为实参递给 `var` 形参」这一形状也被拒（判据从「源偏移区间」改成「调用区间是否覆盖写」）。
  这是最干净的：**规则覆盖了，守护者就能删**。
- **保留 gate5**：不补规则，就让编译器保守地按引用捕获这一种形状。代价是**图里多留一批 cell**，而 cell 正是第 4 步
  要消失的东西 —— 等于把这一步的一部分留在了原地。
- **既补 198 又删 gate5**：要两步同时落，落一步就会红 84 条中的一部分。

规则上没有第三种「两边都算对」：**要么规则覆盖它，要么编译器保守它**。现在是第二种，而它不在任何一条原则里
写着 —— 它是实现里的一个近似，**没有人给它名分**。

## 默认建议（按此开工，不另等）

**保持现状：`gate5` 留着，不补 198，不动行为。**

理由：这一门护的是「编译过、跑出错值」，而按值捕获错的是**值语义** —— 宁可多留一个 cell 让程序对，也不要让
程序静默地算错。**并且把 198 的区间洞记为缺陷**（`docs/design/effects/` 那一族，与本轮的捕获口分开记），
写明缺的形状是「闭包作为调用实参递给 `var` 形参，写发生在被调里」。

**这个问题不需要当轮阻塞第 4 步**：`gate5` 留着，第 4 步照样能落 `gate4`（124 处）与 `gate6`（0 处）的删除，
`var` 化 SSA 的主干不受影响。若作者答复是「补 198」，那是下一轮：先补规则、再删 `gate5`，两步不许合成一步。
## 决策者答复（2026-11-16）

**三种都不是：这个用例测的是已撤回的按引用语义，新语义下打印 0 是对的。** 按原则 3.5：闭包捕获的是创建时的值；`var` 形参是"传入值、传回新值"，`x = 7` 只改被调者自己的名字，调用结束才写回 `w`。闭包写在调用的实参位置，"最后一次被用到"就是这次调用，写回算在调用之后，所以这个调用合法，不该被 198 拒，`f()` 读到的是 0。这与 `update(x, () => x + 1)` 读旧值是同一条规则。

1. **`var_param_reference.cml` 的期望改成 0**，注释写明依据（3.5"闭包捕获的是值""`var` 形参是传入值、传回新值"）。84 条里同一形状的一并按此处理。
2. **删 `gate5`**；删之前先修你列的四处"专用诊断不再被问"（`requireMutableArgument` 的 `isVariable` 门槛、就地重载那一处、"bind it to the result"那一处、`mutableName`），每处补一个用例，证明该说的话还在说。"未查"的那几处一并查完再删。
3. **单元剩下的来源逐个清**：
   - **模块级 `var`**：按 3.5 顶层 `var` 是编译错误，`gate1` 护的东西本来就不该存在；随顶层 `var` 的迁移一起删。
   - **生成器与装饰块**：同样化成 SSA；它们若有自己的约束，写问题页说明是哪一条。
   - **`var` 形参**：写回已落地，形参在被调者里只是一个名字，不再需要单元。
   - **按单元的粘性判定**：随上面几项消失。
   每清一类，合并时报 `:var/new` 与按引用捕获口的剩余数，目标是两个都到 0。
