### growable-array-vs-tensor-in-the-onnx-exporter

1. **限额异常带上那条诊断**：`DiagnosticsLimitExceeded*` 存下触发它的那条诊断，`what()` 打印严重度、位置和消息。异常把诊断吞成一句 `std::exception`，就是丢了信息。
2. **改写模块不再用 `catch (const std::exception &)` 兜底**：`rewrite::rewrite` 和 `rewrite::run` 只捕获自己的规则错误（`RuleCompileError` 之类），转成 `RewriteInvalid`。其他异常照常往外传，pass 里报出的诊断以它本来的样子到达用户。兜底的 catch 会把别处的问题伪装成"规则写错了"。
3. **检查模式不改语义**：同一个程序加同一串 pass，在调试器里和在命令行上，诊断必须一样。调试器路径上多出来的那条 error，要找出是谁、在哪里提交的：做完上面第 1 项，`what()` 就会直接说出来。然后按"检查模式只多看、不多报"修掉，可能是现场编译 pass 模块时、或者 `SetInspectionMode` 打开的某条检查报的。
   - `debugger.dap_protocol` 连红 5 次，修好后转绿就是验收。
   - 客户端每次等 60 秒的写法留着；适配器一旦报出 `exited`，就该立刻失败并打印原因，不再干等。

## cml-read-of-a-write-and-the-write-valued-body

**裁定 1：赋值被当作值用时，取的就是写进去的那个值节点，经数据边直接用。不新建读，不新建锚点。三个候选都不选**。

- var-version-node 裁定的原话是"它的值仍是写入的值，与'版本'是两个输出"。写入的值在图里本来就有一个节点，就是写操作的右边，直接用它就行，不用回头从 cell 再读一遍。所以 SSA 转换没有读可以擦掉，出口、输出、返回值也不会指向被删掉的节点。43 条红用例和那次段错误，都出在"新建一个读"这一步上。
- **复合赋值** `x op= e` 在图里就是 `x = x op e`。`x op e` 是一个值节点，写进 `x` 的是它，复合赋值被当作值用时取的也是它。能不能原地更新，交给内存规划去判断（原地更新的统一规则），不靠专门的 `:op/assn_*_l` 算子。这些算子随之只剩"写"一种，能删就删。
- 所以 `func bump(var x: int) { x += 1 }` 函数体的值是 `x + 1` 那个节点，`bump: (var int) => int`，和 develop 一样。写本身是不是执行，照旧由它的版本有没有人用来决定：调用方之后读 `n`，接的是这次调用产出的版本。
- h464 把赋值的结果类型定为 cell，这件事保留：版本照旧是 cell，值是另一个输出。不改 h464 的基准文件。

**裁定 2：函数体末尾写 `return e` 和直接写 `e`，建出来必须是同一张图。打印形式不变，不需要负责人拍板**。

- 同一个意思建成两张图，就是规则不统一。目标形状按 H242 的边模型来：出口经数据边接值，同步链的最后一个节点经同步边接出口。值已经经数据边依赖那次写，就不再另加控制边，也不加 GATE。
  - `visitExitNode` 里那句"return GATE 即使值已经依赖控制输入也要保留"，属于要随控制边一起删掉的旧机制。
  - 隐式的函数体值如果今天漏掉了同步链，同样要补上。
- **做法**：显式 `return` 和隐式的函数体值走同一个出口函数。末尾 `return` 不加 GATE，只保留旧机制下确实还需要的同步依赖，在 H242 删除 `SYNC` 之前用控制边表达，删除之后改成同步边。
  - 会有一批函数的图改变形状，这是统一规则必须付的代价。动到的基准文件随这次提交重新录，写明原因是"末尾 `return` 与隐式值建成同一张图"。
- 打印器照旧写 `return v`。图统一以后 `var_param` 往返就是等价的，`f(): int sync { var v = 1; v = 2; v }` 这个形状补进往返用例的语料。

**先后**：先做裁定 1，`print_and_recompile` 应该只剩 `var_param` 一条红；再做裁定 2，`var_param` 转绿。

## tensor-elementwise-comparison-vs-array-equality（负责人 2026-10-25 定）

**裁定（负责人）：逐元素相等引入 `===`、`!==`；整体比较就是逐元素比较再归约成一个 `bool`**。设计原则 4.1、4.2 已写入。

- `a === b`、`a !== b`：两个数组逐个元素比较，结果是同形状的 `bool` 数组。形状规则与其他逐元素运算相同，对任何元素类型能比较的数组都成立（数组只有一套语义）。标量上 `===` 就是 `==`。重载 `===` 即得到 `!==`。
- `a == b`、`a != b`：永远返回 `bool`，意思是"形状相同且 `a === b` 处处为真"，对数字数组也一样。今天"元素类型没写落到逐元素、写了落到整体比较"的隐式分派删掉，比较的含义不再随类型写没写而变。
- `<`、`>`、`<=`、`>=`：在数字数组上逐元素比较，返回 `bool` 数组。数组整体没有大小顺序，这几个运算符在数组上不会和别的含义冲突。
- **实施**：
  - 词法里已经保留了 `===`、`!==`，删掉 `ConstructNotSupported` 那条拒绝，接到逐元素相等上；
  - 张量模块的 `__eq__`、`__neq__` 改成 `===`、`!==` 的实现，`==`、`!=` 只剩核心的整体比较一种；库里的 `eq`、`ne` 函数删掉，不留兼容；
  - `numeric_contract.cml` 这类"逐元素统计 NaN"的写法改成 `s !== s`；
  - 规则库可以加一条恒等式：`a == b` 等于"形状相同且 `all(a === b)`"；
  - 语言参考（`02_lexical`、`03_data_model`、`06_expressions`）和给 AI 的参考，随实现一起改，写成现在的语言，不写"以前不支持"。
