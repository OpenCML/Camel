# `transpose(f)` 的余切从哪里进：与 `f` 的参数并列，还是由 `split` 提供

> **问什么**：转置后的函数今天是 `transpose(f)(x, 1.0)`——`f` 的参数在前、余切在最后。要不要改成
> “余切单独进来、残差由 `split` 提供”的形状？
> **堵着谁**：`transpose` 的分支与循环（每条臂的余切都要知道自己走的是哪条臂）、以及 M4 的 `vjp`
> 的对外形状（`vjp(f)(y, ȳ)` 今天就是这个并列形状）。
> **我没能自己定的理由**：两条路都自洽，代价不同，而且它决定一个会进标准库签名的调用形状；喊一次
> 比改十次便宜。

## 事实：今天是什么样

- 直线代码：`transpose(f)` 得 `back(x, ȳ)`，`sum_of_scaled` 在 `(2.0, 1.0)` 上打 `5.0`、
  `scaled_chain` 打 `20.0`，Release 与 Debug 两遍一致。
- 分支：`pick(x) = if x > 0 then 2*x else 3*x`，`back(1.0, 1.0)` 打 `2.0`、`back(-1.0, 1.0)` 打 `3.0`；
  `merged(x) = if x > 0 then 2*x + 5*x else 4*x`，正侧 `7.0`、负侧 `4.0`。四个后端一致。
- 走哪条臂**由值决定**：没有 `x` 就不知道执行过哪条臂，因此“只给余切”在分支上今天无解。

## 三条路

### A（默认建议）——参数当残差：`back(x, ȳ)`

- 代价：**调用形状把“残差”这件事写死成“f 的参数”**。`split` 落地后，如果残差不止参数（例如闭包里
  被读到的常量、或循环携带量），这张形状就要多一个入口。
- 好处：**今天就能写、四个后端一致、直线与分支同形**；`vjp(f)(y, ȳ)` 与它一致。

### B——余切单独进：`back(ȳ)`，残差由 `split` 的另一半供给

- 代价：**要等 `split`**（M2 正在写，`split.cpp` 尚未落地）；`vjp` 的对外形状也要跟着改一次。
- 好处：**残差的来源只有一个**（`split` 的前一半），`transpose` 不再假设“残差 = 参数”；
  循环携带量、闭包常量都走同一条路。

### C——两个都留：`back(x, ȳ)` 为糖，内部转成 `back(ȳ)` 调 B

- 代价：**两份形状、两份用例、一条隐式转换**；转换里丢掉的东西（比如某个残差）出问题时，
  错会出现在糖那一层而不是实现那一层。
- 好处：今天与将来都能写。

## 判据

**改完能删掉什么**：A 今天能删掉“等 split”这一条依赖；B 将来能删掉“残差 = 参数”这个假设；
C 两个都留着，**一次都删不掉**——所以 C 只有在前两条都走不通时才选。

## 默认建议与正在做的事

**按 A 继续**：`back(x, ȳ)` 保持，`vjp(f)(y, ȳ)` 保持，`split` 落地后**先补一条 B 的用例**看它是否
更省；若 B 真的更省（残差来源唯一），再一次性把 A 换成 B，并把直线/分支用例的调用形状一起改。
在那之前，**每条臂的余切只从“执行过的那条臂”来**，两臂之间是拼接不是相加，这一点已由 `7.0 / 4.0`
两条读数钉住。
