# 监测器读的是我们推的那个分支吗？

## 问题

作者一侧的例行监测报「施工方最近 1 小时 0 笔、最后一笔 coordinator commit 在 2 小时前」，而同一时刻 `origin/develop` 上有 6 笔新提交、最新一笔在 2 分钟前。两边都没有算错：**监测器量的是 `origin/fsh-dev` 上由协调者署名的提交，而 `fsh-dev` 从不推送**（它归作者，协调者只推 `develop`，由作者决定何时合并）。

于是这个读数回答的其实是「作者最近合并了几次」，而它被读成了「施工方最近提交了几次」。**协调者的任何动作都无法改变这个数**——只要作者不合，它永远是 0。

## 证据（一次，可复核）

```
origin/develop = 16248b07d   20:27   协调者推的
origin/fsh-dev  = 0a8395f54  10:53   作者推的（其后未动）
00dc468f8       18:29   fsh-dev 上那笔「2 小时前的 coordinator commit」
```

监测器报的 `00dc468f8` 正是 `0a8395f54` 这次合并的父提交——**它量的不是提交时间，是合并时间**。同一轮它报「也没有问题页」，而 `develop` 上有 5 页。

## 默认建议（协调者按此继续，不等回复）

**监测器改读 `origin/develop`（只读），每轮先 `git fetch origin develop`。** 理由：

1. `develop` 是协调者唯一的推送目标，**它上面的时间戳才随施工而动**；
2. `fsh-dev` 的时间戳只反映作者的合并节奏，**它是一个关于作者的读数，不是一个关于施工的读数**；
3. 若作者想「只看我合并过的内容」，那就把监测拆成两个数：**`develop` 的提交数（施工在动吗）** 与 **`fsh-dev` 落后 `develop` 多少笔（我欠几次合并）**。**这两个数回答两个问题，合成一个就一个也答不对。**

## 为什么不改成「协调者去推 fsh-dev」

**那是把判据修好、把纪律弄坏。** `fsh-dev` 归作者，协调者推它会让作者的合并变成无人审核的转发；**而且一旦协调者能推，`0a8395f54` 这类「作者合并了我们」的证据就再也分不清是谁合的。**

## 关联

- 判据指向一个自己的动作无法改变的对象，是本轮反复出现的同一形状；本轮另外七例记在 `docs/handover/reports/2026-11-04-b3-reverted-and-the-ten-it-does-not-explain.cn.md`；
- 纪律原文：**不推 `origin/fsh-dev`**。
