# 流上的 `for … while c`：`c` 与"这次拉取有没有元素"谁先问？

**问谁**：语言作者（负责人）
**问什么**：设计原则 3.10 对**数组**形式的 `for … while c` 写的是"**先判断条件、再取下一个元素**"；流形式落地后（流的值＝步进函数＋状态，`for x in s` 在图上展开成已有的 `while`）我们把它实现成"**先问这次拉取有没有元素、再问 `c`**"。两种顺序在**序列到头那一轮**读数不同。请定流形式该按哪一种。

## 量到的读数（已钉进用例，`expect_stdout_exact` 精确比对，四后端一致）

同一个 `c`（每次求值打印一次）：

| 形式 | 读数 |
|---|---|
| **流**，空流 | `c` 求值 **0 次**，循环值是初值 `0`（一趟都不走） |
| **流**，`count(3)` | `c` 只在 3 个元素各问一次：`c 0`、`c 3`、`c 5`；**第 4 轮拉取为 `null` 时不再问 `c`** |
| **数组**，`[1,2,3]` | `c` 被问 **4 次**：`c 0`、`c 1`、`c 3`、`c 6` |
| **数组**，空数组 | `c` 被问 **1 次**（`c 0`） |

即：**数组形式在"发现序列到头"那一轮仍会问一次 `c`**（因为它是"先判条件、再取下一个"）；**流形式在到头那一轮一次都不问**（因为"这次拉取有没有元素"被放在问 `c` 之前）。

## 需要您定的

- **甲**：流形式保持现在这样（到头那一轮不问 `c`）⇒ 两种形式的读数**本来就不同**，我们把它写进设计稿（并说明差异的来源：流是"拉一次、看有没有值"，数组是"先判界、再取"）。
- **乙**：流形式应与数组形式**同一顺序**（到头那一轮也问一次 `c`）⇒ 我们改展开形状，改钉那两条读数（这是一次有意识的改钉，不是修 bug）。
- **丙**：别的划法（例如规定 `c` 只对"已经取到元素"的那些轮求值，数组形式的第 4 次问是数组形式自己的缺陷，也应一起改）⇒ 请说明数组形式要不要**同时**改，因为改了它会牵动既有的数组用例与 3.10 的措辞。

## 顺带一条（同一批量到的，不是开放语义但值得您知道）

条件里**不带 `sync`** 的调用会被编译器警告 `has side effects but is never executed`，并且**真的不执行**——所以条件要有可观测效应就必须写 `sync`。本轮把这一条也写进了用例注释（两种形式一致）。若您认为"条件里的不纯调用"应当有别于"语句里的不纯调用"（例如条件位置一律要求 `sync` 否则拒绝），请一并裁。

## 相关状态

- 流形式已落地：`for x in <流>` 展开成已有的 `while`（**无新节点种类、无驱动、四个后端不动**），`stream::unfold` 用 **Camel** 写在 `stdlib/stream.cml`；循环状态＝"这次拉取 ＋ 程序写的状态"，元素从这次拉取取出，下一轮的拉取在本轮体末（程序写的语句之后）。
- **"一个流只消费一次"是既定规则**（设计原则 5.4："每条执行路径上，一个流值至多有一个消费者（分支的不同臂各消费一次算一次），**在图上检查**，第二次使用是编译错误；要给多个消费者写 `tee(s, n)`"），**不在这里问**——按"既定的就实现"在做（红用例：`for x in s do …` 之后再 `s()` 必须被拒，今天静默通过）。
- **生成器体的展平（CFG 展平、活过 `yield` 的局部要有状态分量与类型、嵌套循环的状态提升、效应顺序）仍是多会话工程**；`FeatureNotSupported("generators")` 按您"随生成器车道删除"的裁定**留到与展平同批删**。
