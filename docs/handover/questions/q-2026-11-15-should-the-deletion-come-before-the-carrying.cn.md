# 先删，还是先搬：`(c)` 与 `(d)` 的顺序

## 状态：等决策者，按默认当轮开工
## 默认建议：**调换**——先 `(d1)` 删死单元，再 `(c)` 循环携带，最后 `(d2)` 按值捕获口

## 事实（车道 `lane-varcarry` 实测，非推断）

作者排的顺序是：闭包按值捕获 → 形参写回 → **分支/循环赋值自动携带 `(c)`** → **删单元节点与按引用捕获口 `(d)`**。

前三步之中，(a)(b) 已合。(c) 做到分支半时，四项 by-design 度量**仍全红**，而红的**最后一点**是：

```
arm 度量：算子差已只剩 :op/assn_l×2, :var/new×1
          但图里还多着 5 个死节点，JOIN 上还有两条来自 store 的 control 输入
```

即：**读已经取 JOIN 的值了，可旧的写单元还活着。**

## 车道的结论（可直接引用）

> `(c)` 的四项度量里，三项（`an_arm_assignment_is_the_branch_result`、`a_loop_assignment_is_the_loops_state`、`loop_write_outside_read_is_the_let_writing`）在 `(d)` 删掉无读者的 `:var/new` 与 `:op/assn_l` 之前**不可能变绿**；第四项 `closure_read_is_the_let_writing` 在 `(d)` 给出按值捕获口之前不可能变绿，而那个口与 `stdlib/stream.cml#tee`、`var_capture_reference.cml` 依赖按引用捕获相冲突。
> **所以 `(c)` 的最后一步依赖 `(d)` 的两半，作者排的顺序应当把 `(d)` 提到 `(c)` 之前。**

## 为什么这不是车道能裁的

顺序是决策者定的。**但「先建后拆」这一条在测量面前不成立**：`(c)` 的「建完」的定义里含着「拆掉旧的」，因为度量数的是**旧节点是否还在**。

**这不是执行不力，是顺序里的一个依赖没被写出来。**

## 默认建议的推理

先做 `(d1)` 的理由：
1. 它**不需要新机制**——删的是已确认无读者的节点；
2. 它**能立刻兑现三个度量**，于是「`var` 化成 SSA」的进度变成可数的 3/4；
3. 它**风险最低**：行为必须逐字节不变，反向验证可以立刻推翻。

而 `(c)` 的循环携带若先做，**它做通了三个度量也不会变绿**——因为死节点还在。**先做一件不会改变读数的事，等于把同一段路走两遍。**

## 若决策者不同意默认

代价说清楚：维持原顺序意味着 `(c)` 会先落一笔「结构对、读数不动」的改动（分支半已经就是这么落地的，`8013a20f1`），然后人们会问「为什么做完了还是红的」。**答案会是「因为还有一半在 (d) 里」——而这句话写在两个提交之间，不写在任何一处的标题上。**

## 这一页要的答复

一句话：**调换**，或 **维持原顺序（请说明为什么读数可以先不动）**。
