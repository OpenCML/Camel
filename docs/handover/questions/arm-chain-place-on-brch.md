# 分支的链位要不要同时写到 BRCH

## 问题

`buildBranch` 是否应当把分支的链位同时写到 BRCH 自己（现状只写在 JOIN 上）？

## 现象

BRCH 没有 sync 前驱，所以 `eraseNode → closeChainOver` 只转交"被删节点自身的 sync 前驱"时，BRCH 交不出任何东西：臂链入口原本从 BRCH 得到的那条 sync 被丢掉，只剩 `pruneBranch` 补写的转接（补不到的地方只剩 ctrl 副本）。

## 已实测的边界

三条都是踩过的坑，换方案时别再踩：

1. "顺 sync 用户找链尾"会拿到随后被删的嵌套区域节点，两次 SIGSEGV。
2. 把块级片段重接加回去，会把同块 `var` 的写当成片段、按布局顺序串起来，越过捕获规则：`var_capture` / `captured_write_order` 共 18＋4 红。
3. 移动语句前必须查 `waitsOn` 挡环，否则 `mlp` 的 `train_loop` 报输入环 `58←74←66←67←75←53←58`。

## 现在这条路已经不需要它

交位改为延后解析：`resolvePlaceForks` 按"一语句块内后继唯一"的不变量，把被抢位的语句移到链尾；目标用例已转绿。所以这只是"要不要顺手统一形状"的问题，不是阻塞项。

## 我们的倾向

**不改。** 延后解析已按不变量把目标用例修好；实测把链位加写到 BRCH 会让链分叉 102/103。若作者选择改，我们照做，并按上面的三条边界重跑。
