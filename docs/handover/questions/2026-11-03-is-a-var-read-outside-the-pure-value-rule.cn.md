# 链位到底是谁在承担语义：`var` 读，还是纯算术调用？

**问：`sync` 块里「这个节点占据一个链位」这件事，除了链边本身，还有谁在用它？两笔读数说：纯算术调用（`:op/add_l` 这类）的链位和 `var` 读的链位**都**在替「读不会被移过写」说话——那么「纯值从不站在链上」要落地，缺的是建图侧换个节点，还是遍侧换一种读法？**

## 1. 设计页写的是什么（原文，`docs/design/effects/edges.cn.md`，全文 61 行）

页里**没有 §5.5**：第 5 节「表示细节」的条目是 1、2、3、4、4.5、4.6、5、6、7、8（有 §4.5、§4.6，没有五节第 5 条以外的「5.5」）。相关的三处原文：

> §1（第 16 行）：「**纯计算没有顺序边；纯且不会出故障的计算也不在同步链上**（可能出故障的计算留在链上，因为故障可观察，3.4）：它执行与否完全由值是否被用到决定……同步链只连带效应的语句……；**唯一的例外是块的值接收链尾的同步边**。」

> §4.6（第 57 行）：「……**同步边只连同一个同步块直接写着的相邻语句（或链尾到块的值）**；同步边是一条链……」

> §5 第 6 条（第 59 行，`var` 的读写）：「……每次读（`:var/get`、读了捕获变量的调用）有一个数据端口接到书写上最近一次写的产出……写与写之间是顺序边，写取 cell 作位置、不取上一次写的产出。由此『读用到最近一次写、没被读的写不执行』（F3）直接由数据边与顺序边表达。」

**三处都没有说「一个纯节点占据链位」是设计的一部分。** §1 的例外只有「块的值接收链尾」，§5 第 6 条把 `var` 读的定位放在数据边 + 写与写之间的顺序边上。建图今天却给两类纯节点一个链位：`src/compile/gir/builder_expr.cpp#readVariableThrough`（`var` 参数的读）与 `src/compile/gir/builder_operators.cpp` 里算子调用建出的节点（纯算术）。**两处都在设计页里找不到依据。**

## 2. 两笔读数

**(甲) 把链位统一换成「读它的 `GATE`」**（块的值今天就是这么处理的，同一套规则，`chainPlaceFor`）：机制有效——全量 `test/cases` 语料里 `:op/add_l` 作为链起点 **387 → 0**、`:op/` 族起点 **3499 → 2303**；但 `feat/linear` 从 `873 / pass 871 / fail 0` 变成 `873 / pass 858 / fail 13`，**13 条全是错数值**：

| 用例（每种流水线一份） | 期望 | 实得 |
| --- | --- | --- |
| `var_rule_subpasses.{simplify, simplify_twice, simplify_jit, opt, opt_cse, opt_dce, opt_fold, opt_fold_cse_dce, macro_simplify_fvm}`（9） | `… branch 10801 80802 8` | `… branch 80801 80802 8` |
| `var_writes_through_recursion.{simplify, simplify_tf, macro_simplify_jit, macro_simplify_fvm}`（4） | `use: 10 counter 3 …` | `use: 30 counter 3 …` |

**(乙) 只换 `join`、`loop`、算子调用三处，`var` 读保持原样**：**同样 13 条、同样数字**（`use: 30`、`branch 80801`）。而 `Join` 与 `Loop` 两种节点在 `chainPlaceFor` 里按种类原样返回（它们是控制结构，不换），所以**真正改动了行为的只有算子调用那一处**：`let a = c + 0` 里的 `:op/add_l` 一旦不再占链位，`c += 2` 与 `let b = c + 0` 之间的先后就失了一层保证。

两个用例守的正是这条（`test/plans/feat/linear/var_reference.plan.toml` 的 `var_rule_subpasses` / `var_writes_through_recursion`）：读被移过写，两次读被并成一次。

## 3. 我方读法

改动只做了「链往下走的那一头」：`linkSyncStatement(from, to)` 仍然把同步边**写进**那个纯节点（`from` 侧不变），只在「下一个语句从哪接」那一头换成 `GATE`。链上于是出现「前一条语句 → 纯算术 → `GATE` → 后一条语句」，纯算术节点身上还带着一条 sync 前驱——**规则「纯值从不站在链上」只落了一半**。要真落地，得在写链的那一处（`builder_helpers.h#writeSyncStatement` / `linkSyncStatement`，以及 `draft.cpp#setSyncInputs`）把两端一起问，而不是在「谁当链尾」的赋值点上换节点；那是比这次更大的改动面。

这意味着有一件事得先答清楚：**纯算术节点的链位，是「读不会被移过写」的依据之一吗？**

- 若是：P0-2 的这一半不能只靠建图换节点，还要让遍侧另有一处能读到同一件事（例如读与写之间真正的顺序边），否则改完就是 `use 10 → 30`。
- 若不是：那这 13 条错数说明还有一处我没找对，需要一条能定位的读数（贴一份 `std::gir`：`let a = c + 0; c += 2` 在 `std::opt` 前后各一张），而不是继续在假设上改。

## 4. 要作者答的一句

**「`sync` 块里一次纯算术调用（`:op/add_l` 这类）和一次 `var` 参数的读（`:var/get`），是不是都在承担『这个读发生在这条链的这一点』？若是，`edges.cn.md` §1『唯一的例外是块的值接收链尾的同步边』要不要写成『只有占链位的是 `GATE`』，并另给一条让纯值仍能被顺序住的机制？」**

我方默认：**两者都在承担**（读数见 §2），因此这一半的改法必须落在「写链的那一处」而不是「谁当链尾」的赋值点；在此之前不动 `readVariableThrough` 与算子调用那两处，页里留着等裁定。
