# `residual_mlp_large_bytecode` 的时间余量在 0.2 之前就没有，现在要不要抬

## 读数

```text
pre-0.2        2.52–2.56 s   限 2.50 s（10000 / 4）   0.96–1.02x
纯 0.2         2.66 s        CI 判红
0.2 + 修复     1.75 s CPU    （poison 口径，三次取中）
```

三条读数分属两个口径，不能说成一个数：

- `2.52–2.56 s` 与 `2.66 s` 是 CI 上 `residual_mlp_large_bytecode` 的 CPU 秒，
  限是 `10000 / 4` 的 4 倍余量规则。
- `1.75 s` 是同一台机器上 `poison` 用例三次取中的 CPU 秒，用来对比
  pre-0.2 `1.72` 与 纯 0.2 `2.20`。**它与上面那两行不是同一个用例，不能直接减。**

## 判断

`0.2` 让调用者与后端之间的 run 窗口断开（`618eea077` 已修，把窗口还给持有者），
所以那 0.28 s 是**真实的回归**，已消除。

但**余量本身在 0.2 之前就不存在**：`2.52–2.56` 对 `2.50` 是 0.96–1.02 倍。
也就是说，这条用例在我开始动 0.2 之前，就已经在随机红/绿之间。

## 需要决定的事

`timeout_ms` 要不要抬，抬多少，理由写什么。

**默认建议（按此当轮开工）：抬，并且把理由写成它的真实原因。**

1. 抬到 `12000`（限变 3.0 s），给 CI 上 2.66 s 留 12% 余量 ——
   **不是**为了盖住 0.2 的回归（那个已修），而是为了让这条用例量的是
   「大字节码的编译与执行」，而不是「这台 CI 机器这个时段的负载」。
2. 理由按运行器要求写进 plan：**这条用例的正常耗时与 4 倍余量规则给出的上限
   在 0.96–1.02 之间，规则在这个量级上没有判别力。**
3. 同时记一条：`residual_mlp_large_bytecode` 这个名字对应的是「大字节码」，
   而它现在贴线的原因与字节码大小无关，与固定开销有关。**若以后要让它重新有判别力，
   该让它跑更大的输入，而不是继续抬上限。**

**若不同意抬**，备选是把它标成「只在专用机器上跑的量」，从 CI 的 4 倍余量规则里移出去，
但那会让 CI 少一条真跑的用例。两条都比维持 0.96–1.02 倍好。

**我按第 1、2、3 条开工。**
