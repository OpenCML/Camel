## 1. 「每条执行路径至多一个消费者」——「一条路径」是什么

任务书 5.28 第 4.5 条：「流值每条执行路径**至多一个消费者**，图上检查、第二次使用报错（诊断给出两处使用与 `tee` 的写法）」。

已定的只有一条：**分支的不同臂各消费一次算一次**（`if` 的两臂各消费一次合法）。下列位置没有依据：

| 位置 | 同一流值消费一次 | 该算几次 |
|---|---|---|
| `if`/`match` 的两个臂各一次 | 已定 | **一次**（合法的先例） |
| **循环体里消费一次**（多轮） | `loop ... do { let first = head(s) ... }` | ？**这就是「一次」还是「每轮一次」** |
| `match` 的**三个以上**臂 | 每臂一次 | ？ |
| 循环体里消费一次 + 循环外再消费一次 | | ？ |
| 生成器的 `yield` 与另一个消费者 | | ？ |
| `tee` 的**结果**再各消费一次 | `let (a,b) = tee(s,8); (sum(a), max(b))` | 任务书给了这一条为**合法**；那 `tee(a, k)` 再 `tee` 一次呢？ |
| 把流值**存进 `var`** 再消费 | | ？ |
| 把流值**作为参数传给函数**，函数里消费一次，调用两次 | | ？**按调用点算还是按函数体算** |

「图上检查」这半条也有分歧：图的**静态**消费者计数与「执行路径」不是一回事——同一个图上的两次使用可能落在互斥的臂里（合法），也可能落在同一个循环的轮次里（若不合法就是**运行期**的，图上判不出来）。

- **建议**：把判据定成**「图上每个流值的数据边出度 ≤ 1，除了 `tee` 的结果与互斥臂」**，并且**循环体算一次**（循环体是同一张图的一个区域，静态只有一次使用；多轮不改变静态计数）——这与「分支的臂各算一次」是同一条道理（**静态使用点**计数，不是动态次数）。再把两类今天图上判不出的情形**明确写成允许**：落在互斥臂里的两次使用、以及「按调用点算」（同一函数体被两处调用，每次调用各有一份流值）。**代价**：诊断可能漏掉一个真正的「同一轮里用了两次」的情形（若那种写法在语法上可构造）；**收益**：规则是静态的、可检查的，与任务书「图上检查」一致，且 `tee` 的验收例天然合法。
- **若选「动态判一次」**：判据要落到运行期，且「第二次使用报错」变成运行期错误，与任务书「图上检查」冲突；还要定「报错前已经算掉多少元素」。

## 2. `tee(s, n)` 的 `n`

任务书给的签名是 `(s: T.., n: int = …): (T.., T..)`——**默认值留了省略号**，非法值的行为、以及 `n` 的语义都还没定。

- `n` 的默认值是多少？（有界缓冲的默认深度：1？8？执行器的核数？目标平台相关？）
- `n <= 0` 怎么办：**报错？当作 1？当作「不限」？** 任务书说「`n` 是执行器的**提示**，不报错」——但那是针对**缓冲不够**的情形，没说 `n` 本身非法。
- `n` 与「共享缓冲语义上不限」的关系：既然语义上不限，`n` 就只是一个**性能提示**；那么一个明显荒谬的 `n`（0、负数、`2^63`）是诊断还是静默夹取？

- **建议**：`n` 默认值取一个有界的常数（建议 8，与验收例一致，让「默认」与「例子」同一条路径）；`n < 1` 是**编译期诊断**（「`tee` 的缓冲提示必须是正数」），因为那是程序写错了，不是执行器做不到；`n` 过大静默夹取到实现上限（属于「提示」，不报错）。**代价**：要加一个诊断码与目录登记；**收益**：把一个静默的怪行为变成显式的写法。

## 3. 「剖析报告 `tee` 缓冲的峰值」的格式

任务书 4.5：「剖析报告 `tee` 缓冲的峰值」。既有先例是 GPU 驻留的那一份：`modules/tiles/src/residency.cpp` 的 `residencyReport` 印成 `TILES_RESIDENCY` —— **一行一个 JSON 对象**（键 `graph`/`body`/`blocks`/`uploads`/`downloads`/`crossings`/`per_round`/`calls`），由 `modules/tiles/src/region_pass.cpp` 的 `RegionPass` 在改写前印出，**没有放置事实的程序输出不变**。

- **选项 A（建议）**：照先例，一行 `STREAM_TEE {json}` 或 `TILES_TEE {json}`，键含流值标识、`n` 给的提示、实际峰值、峰值出现的轮次；由剖析/统计遍印出，未用 `tee` 的程序输出不变。**代价**：新增一个报告名与一个用例；**收益**：与 `TILES_RESIDENCY` 同一套读法（测试能 pin 数字），且不改「没有流就没有额外输出」这条既有的输出不变性。
- **选项 B**：并入 `std::stats` 的 `GRAPH_STATS`。**代价**：`GRAPH_STATS` 是**静态**计数（graphs/nodes/edges/operators/…），峰值是**运行期**量，混在一起会让「静态统计」这条读法破掉。
- **选项 C**：只进 `std::profile` 的既有事件流（perfetto trace）。**代价**：测试里难以逐字 pin（trace 是二进制/时间轴），而任务书要的是「剖析**报告**」。
- **要一并裁的**：峰值的**单位**是元素个数还是字节（一个元素的大小取决于元素类型与是否装箱），以及**跨调用的聚合方式**（一个程序里多个 `tee` 是各报一条还是合成一条）。

## 4. 「两种调度结果逐字相同」的比较范围（**这一条最容易写出一个永远红的用例**）

任务书 5.28 第 6 条：「同一流程序**逐元素与驻留两种调度结果逐字相同**」。同时第 2 条要求「`merge`、按时间的窗口**在声明里写明不确定性**」。

**这两条放在一起就有矛盾**：按到达顺序合并（`merge`）与按时间开窗口**定义上就不确定**，它们的输出在两种调度下不保证逐字相同。若不划定范围，「逐字相同」就是一个永远无法满足的验收。

- **要裁的**：
  1. 「逐字相同」比较的**对象**是什么：stdout 的字节？还是「每个被观察到的值 + 效应的先后」？若程序不打印任何东西，比较什么？
  2. **哪些算子排除**：`merge` 与按时间窗口肯定要排除；那「按数量的窗口」呢（理论上确定）？并行调度下**纯计算的求值顺序**不影响值，但一个会把元素顺序合并的算子就影响。
  3. 比较的**规模**：两种调度在什么输入规模上比较？（驻留才有意义的最小元素数是多少——元素少于并发度时驻留退化成逐元素，那算是「两种调度」吗？）
  4. **不确定性的观测方式**：任务书说写在声明里，那测试怎么**验证声明与行为一致**（一个 `merge` 的声明说「按到达顺序」，怎么在确定性替身下测）？该稿第 7 节「定稿时补上的闭环」已有先例：「测试用确定的替身」。
- **建议**：把验收定成「**在把不确定算子排除、并以 `stdout` 字节为比较对象**」的前提下逐字相同，并要求两个方向各有一条用例：（a）**确定的**程序在两种调度下 stdout 逐字相同；（b）**含 `merge` 或按时间窗口**的程序**不**要求逐字相同，只要求「元素集合相同 + 声明里写明不确定性」有用例固定。**代价**：验收的措辞要比任务书细一档；**收益**：验收是可满足的，而且把不确定性变成了被测试的对象而不是被回避的东西。

## 5. `take(s, n)` 「只计算 n 个元素」怎么观测

任务书第 6 条。只看结果是测不出来的：把无限流整个算完再取前 n 个，结果**完全正确**。

- **选项 A（建议）**：用一个**可观测的计数**——一个每次被调用自增一个 `with` 参数变量（或一个资源上的副作用）的映射函数，测试断言计数恰为 n（或 n 加常数）。**代价**：测试里要有一个可变计数器（今天的 `var` 可用）；**收益**：不依赖剖析，逐字可 pin。
- **选项 B**：有名字的剖析事件（`take` 拉取的次数、来源的读取次数），测试断言事件计数。**代价**：要定事件名与报告格式（与第 3 节同一个问题）。
- **要一并裁的**：`take` 是否**必须**停止上游（`take(s, n)` 之后来源不再被读取），还是允许执行器多预取一个有界缓冲（那时计数是 `n + 缓冲`）。这与 3.5 的预取条件（「有界缓冲」）直接相关：**若允许预取，验收就不能写成「恰为 n」**。
