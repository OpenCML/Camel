# 预算在悬空状态下用尽：一次展开的链尾没人接

## 问题

`std::opt` 展开递归时，内联把被拼接体的语句链接到调用所在的那条链上。**当调用是块的最后一条语句时（尾调用），这次交接没有"调用之后的语句"可以承接**，于是被拼接体的链尾暂时没有后继。这在展开途中是常态：下一轮内联再拼一层时，新体的尾会接过这个位置。

**错的是"悬空状态被当成了成品"**：展开预算恰好在悬空状态下用尽，这一层就不再被内联，悬空的链尾随程序交出去，那几行打印于是从出口不可达。

## 我量到的

`std::opt growth_budget=192` 丢三行打印，`=160` 不丢，`=256` 与默认值同样丢。

1. **特化在两者都发生**：`std::opt::specialize` 那一趟的读数 `spec-made func=14`、`func=15` 在两条 trace 里完全一致。差别在最终程序：192 把那张特化体**又内联进 `__root__`**（所以 `countdown$spec6` 这张图消失了），160 没有内联、图还在。
2. **拼接探针（两种预算前七条完全一致）**：
   - 成功的只有一条：`bodyHasChain=1`、`syncIn=1`、`followers=1`、链尾 `users=1`。
   - **悬空的五条**：`hasChainPlace=0`、`bodyHasChain=1`、`syncIn=0`、`followers=0`、`ctrlIn=1`、**链尾 `users=0`**。
3. **两条 trace 的唯一分歧**：192 多做了**一次**拼接，随后预算耗尽（探针 trace 69 行对 82 行）⇒ 悬空尾进了程序。

## 机制（一句话）

悬空尾在展开途中是常态，**只有后续再拼一次把它接上时才无害**；**预算恰在悬空状态下用尽 ⇒ 悬空尾进程序 ⇒ 打印从出口不可达**。160 的"运气"是停在了一个**未拼接的调用**上——未拼接的调用是安全的（被调函数自己会跑），拼接出来的悬空尾是不安全的。

## 指名一个结点

最终程序是 17 节点的 `__root__`，其中链尾是 `g0n14`（`:io/println`，`users=0`）；同一 `sync` 块的出口门是 `g0n9`（`GATE`，已经有 `g0n7 → g0n9` 的 sync 边）。**`g0n14` 应成为 `g0n9` 的 sync 前驱，并成对写 control 边。**

## 两条候选修法与代价

1. **接块出口门**（正解）：把悬空链尾接到调用所在块的出口门上。**待确认边界**：出口门只在该块确有出口门时存在，没有出口门时怎么退，需要一句话指点。
2. **接不上就拒绝这次拼接**（保底）：这次内联不做，调用留着。**代价是少展开一层**（行为差异，绝不是纯结构变更），所以**未经同意不能落**。

两条都与"尾调用应当接在哪里"是同一个问题（见 `docs/handover/questions/tail-call-chain-handoff.md`）。
