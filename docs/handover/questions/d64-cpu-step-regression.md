# d=64：单线程一步真的比记录里的扫描慢 25% 吗？这次比较本身成立吗？

## 问题

H240 用 CPU 时间重测了同一张扫描（同一 workload、同一尺寸、同一套 `measure.py` 生成与校验），d=64 这一格
比 `examples/models/naive-in-expert-out/README.md` 的 `sweep-table`（"before the library step"）高 25%：

| | 值 | 测法 |
| --- | ---: | --- |
| 记录值 | 2.085 ms/step | `measure.py` 进程内对计时步取中位数，三轮交错，单线程，轮内范围 2.072–2.089 |
| 本次扫描，默认路径（`camel-library`） | 2.701 ms/step | 进程自身 CPU 秒数（user + system，`/usr/bin/time -v`）对步数的斜率，64/512 两步长，两轮，样本 2.254、2.701 |
| 本次扫描，去掉 `tensor::fuse`（`camel-canonical`） | 2.612 ms/step | 同一斜率，样本 2.612、2.589 |

数据在 `examples/models/naive-in-expert-out/results/2026-10-23-cpu-scale-scan.json`。

## 为什么这次比较不干净

- 记录值是墙钟、另一周（32 硬件线程上 load 63–76）；新值是 CPU 时间、load 85–97。CPU 时间更抗负载，但
  两者不是同一个量，记录值没有可以相减的 CPU 对应值，构建差异也就无法剥离。
- 这个尺寸上样本很散：`camel-library` 两轮是 2.254 与 2.701 ms（相差 20%），而记录值的轮内范围只有 0.8%。
  一步 2 ms 已接近"64 与 512 步"这条斜率的分辨率。
- 本次没有任何一格是同一构建的对照：`102dbc5d1` 加 CBLAS 默认，同时带着扫描之后的融合提交（除法 VJP
  分组、GELU 反向一遍过）。

## 为什么仍可能是真的

按最快样本算差 25%（2.589 对 2.085），远在两个散布之外；而 d=256 看不出（CPU 61.6 对记录 60.2，+2%）、
d=1024 也看不出同量级的异常（CPU 2 780 对记录墙钟 2 570，换币种后 +8%）。只在最小格出现的回归，只能来自
每步固定开销，而不是某个投影形状。

## 需要什么才能定性

一次安静主机（load 平均 < 4）上的运行：同一生成程序、d=64、64 与 512 步、三轮、两种币种，并把"记录扫描
那次的构建"和"当前构建"放在同一窗口里各测一格。本次没有这样一台主机：参考主机全程 load 55–177，报告里
逐条说明了这个负载使哪些数字不可用。
