# 生成器里"先读后写"的单元：内部错误还是用户可见诊断

> **作者的答复（18:12）**：「生成器体按源码顺序解析名字，就像任何函数；所以'写之前读'是**同一个**
> `UnresolvedReference`，臂内检查保持内部。」
>
> 按它动手的结果要记在这里：把 `visitGeneratorBody` 里那条逐语句对照声明位置的检查去掉之后，
> `yield e` 写在 `let e = 5` 之前的那段程序**仍然编过并打印 `0`**——它读到了一个空槽，而同样形状的
> 普通函数（`let x = e` 在 `let e = 5` 之前）报的是 `UnresolvedReference: 'e'`。原因是单元名在创建
> 体那一层就绑定了，那一层包着每一条臂，所以名字在臂里无处不在，不按源码顺序。要让裁定成立，还差
> 一步：**单元名只从它的声明所在的那条语句起可见**（在 GCT 的解析处按语句序号判定，命中则报
> `UnresolvedReference`），而不是在创建体里一次绑定。这一页因此留在本目录，等这一步落地。

## 现象

三个事实，缺一个就判断不了：

**① 原裁定的前提已经不成立。** `docs/handover/reviews/questions-2026-10-29.md`「写之前读由谁证——1」
定的是：不设用户可见诊断码，在造臂处做构建期检查，不满足即内部错误。它成立的前提是
"用户写不出写之前读"。这一笔把生成器体的局部变成单元之后，**单元名在创建体里就绑定了**
（`src/compile/gct/builder.cpp#Builder::visitGeneratorBody` 的 `addTypedCell` 在 `outer` 上
发 `NREF`，而名字解析按源码顺序），所以下面这段**能编出来**：

```cml
func g(): int.. sync {
    yield e          // 读
    let e = 5        // 写
}
```

**② 今天的行为是内部错误，不是诊断。** `fill` 在造臂处逐个语句对照"声明位置 ≥ 当前语句"的
单元，命中就 `ASSERT` + `InternalDiag::UnknownInternalError`（`gct/builder.cpp`，与
`builder.cpp` 里"格式串不该到 GCT"那一处的写法相同）。改这一笔之前实测过同一段程序：它打印
`0` —— 静默读了一个空槽，空的 `var T` 在 `__builtin__var_get__` 里就是 `NullSlot`。也就是说
"内部错误"至少比"静默给个 0"好，但它对用户是**编译器缺陷**的口吻（"nothing in the program is
known to be wrong"），而这明明是程序的问题。

**③ 位置只有一处。** 就是 `fill` 里那几行；要换成诊断，是把那里的 `InternalDiag` 换成一条
`SemanticDiag`（指向读的那一处、带上单元名和它被写的语句），范围一句话。

## 两条路的代价

**甲：给一条用户可见诊断。** 代价：需要一个新的诊断名（或复用"未定义的值"一类），要定
它指向读还是指向声明；另外它会在"语言允许无值声明"那天变成正式语义的一部分，现在定可能
要再改一次。收益：用户看到的是自己的错，不是编译器崩了。

**乙：留内部错误，等"语言允许无值声明"时一起定。** 代价：今天写得出这段程序的用户会看到
"编译器缺陷"，按帮助文字还会去报 bug；这与"不把编译器问题说成程序问题"（`docs/design-principles.cn.md`
14 节那类误读）相反。收益：不做可能被推翻的决定，诊断随语义一起落。

## 我方默认建议

**甲**。理由：这不是"语言还没定"的问题——**任何**一种对"已建未写的单元"的定性（拒绝、读初值、
未定值即错误值）都会让这段程序成为一个语言问题，而一段能编出来的程序不该以内部错误收场。
诊断可以先只做一件事、不预设语义：**在造臂处拒绝，说"这个单元在它被写之前被读了"，指向读的
那一处**；语义落地时只改措辞，不改诊断的存在与否。这样既不抢语言的裁定，也不把编译器缺陷
甩给用户。

## 要作者答的一句

生成器创建体里现在能写出"先读后写"（`yield e` 在 `let e = 5` 之前），今天的结果是内部错误而
不是诊断；要不要给它一个用户可见诊断？
