# 泛型规则的 check 看得到哪些类型，以及多类型参数规则

Author: 协调者（合并闸门），2026-10-24。Status: open — 两问都需要负责人裁定。测量与实现来自 `handover/h382-generic-rule-slice`（`332b56f44`/`6e37c5b91`/`9960903ed`）。

## 一、`check` 应该看得到哪些类型

裁定 `generic-rule-instantiation-set-and-predicate` 说 `check` 用"**它注册的类型 ∪ 程序的类型**"来匹配。但 maker 落地到 `check` 时两处表面不存在：

- `check(rules, samples, seed)` **手上没有程序**，所以"程序的类型"在它内部不可达；
- **没有任何东西枚举一个算子组注册了哪些类型**（`OperatorTable` 只回答"给定类型"的问题，不列类型）。

今天的行为是诚实的一行：`check([add_zero])` → `unchecked add_zero: a generic rule, whose instances are not checked here`（`modules/rewrite/module.cpp:2366`）。

**选项与代价**：

- **(A) 给 `check` 程序，并在 core 里长出"注册类型的枚举"**：正是裁定写的行为，但**改变 `check` 的声明**（这是你的表面），并新增一个 core API；约一个会话。
- **(B) 只检查同一进程里上下文已经持有的实例**：不改表面，半天；代价是**新进程什么都不检查**，"`check` 注册的类型"这部分仍未实现。
- **(C) 保持诚实的那行 `unchecked`，等表面定下来**：零成本，但裁定的一半不落地。

我倾向 **(A)**，理由是裁定已经把类型集写清、缺的只是把它喂进去的表面；但改 `check` 的声明是你的表面，所以不由我定。若你选 (A)，请顺带说清 `check` 的新声明形状（是否加一个可选程序参数、还是另给一个带程序的入口）。

## 二、带两个类型参数的规则永远无法实例化

引擎只枚举**一元组**，所以一条写两个类型参数的规则永远拿不到实例，`why_not` 如实回答 `it takes 2 type parameter(s), and it was asked for 1`。这不是缺陷报告，是**语义空白**：语言是否允许一条规则对两个类型同时量化（例如 `(T, U)` 上的交换律）？若允许，枚举空间怎么定（注册类型的笛卡尔积？只对 `when` 同时约束的组合？）；若不允许，`why_not` 应改成"这个语言里规则只对一个类型量化"，把它写成正式拒绝而不是一句计数说明。

（另有一件**无需裁定**的记录：每实例 `Rule::id` 在每条规则内从 1 重新开始，只写进等价日志、从不被读来点名规则，所以今天不可观测；若将来要用它点名，需要全局唯一或加规则前缀。）
