# 生成器体里的闭包捕获 `var`，为什么留格子？

> 一页一问。**默认建议写死在下面，本轮按默认开工，不另等。**

## 这一页要的答复

`decideCaptureByValue` 目前有三道「保守门」。负责人的下一步是**把三道门换成规则本身，然后删按引用的捕获口与单元节点**。在删 gate5 的实测里，`stream.generator*` 五条退化成 `NoMatchingFunction: :op/assn_l`，根因如下：

```
生成器把每个声明吊成格子，格子类型取 typeof <那个值>
typeof 由 inferTypeOf 在临时图里重建这个 lambda；重建时闭包的类型摘要里没有捕获，
  于是给出声明类型 () => int pure
而语句处真建出来的闭包类型是 () => int uses capture 0
:op/assn 的 (var self: T, other: T) 两个操作数于是不等
```

`gate5` 在时这个形状**捕的是格子**（`var int` 口），两次建都走「按引用」，答案相同，所以不报错。

**所以问题是：生成器体里的闭包，按值捕获 `var` 之后，那个 `var` 还必须留格子吗？**

## 默认建议（按此开工，不另等）

**必须留格子。** 依据是 `docs/design-principles.cn.md` 3.5 与 `src/compile/gir/captures.cpp#decideCaptureByValue` 文件头已经写明的语义：

> `var` 是资源；闭包按引用捕获它，所以闭包读到的是**后一次拉取写进去的值**。

生成器的拉取式执行正是「后一次拉取写进去」这个形状：`yield` 之间调用方可能已经又拉了一次，闭包在两次拉取之间被调用时必须看到最新的值。**按值捕获会让它看到创建那一刻的旧值**——这不是「保守」，这是生成器的执行模型本身。

**因此本轮的做法**：在 `include/camel/compile/gct/node.h` 的 FUNC 上加一个生成器体标记，`src/compile/gct/builder.cpp#Builder::visitGeneratorBody` 的调用处打上它，`decideCaptureByValue` 里加一条「祖先图里有生成器体或机器自己的 `__gen_*` 函数 ⇒ 捕获留格子」。

**这条不是第四道保守门，是生成器自己的语义。** 三道保守门仍按负责人的安排换掉；这一条在换完之后**应当仍然存在**。

## 若作者另有裁定

- **若说「生成器也按值捕获」**：那么 `yield` 之间的两次拉取会看到不同的值，而闭包停在旧值——**请指一句 3.5 里哪一条允许这样**，我照改，并把 `stream.generator*` 五条的期望一起改。
- **若说「生成器不该有自己的规则，用统一规则加错误」**：那么捕获 `var` 的闭包在生成器体里应当被诊断拒绝，`stream.generator*` 五条改成负例。这条会连带 `tee` 的 `Ref` 迁移（负责人已把它排在下一步），所以若走这条，请说明它是否要等 `tee` 迁完。
