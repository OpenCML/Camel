# 规则条件里取 `const` 形参的节点（`node_of`）

## 问题

规则语言第二版第 1 步要求「`const c: T` 在 `when` 与右边里是常量的值，类型是声明的类型」，评审
（`reviews/stdlib-rules.md` 第 5 条）同时指出：「需要节点本身（读事实、形状）时另用
`node_of(c1)` 一类的显式取法。这是规则语言的缺口，补进规则引擎。」

值的这一半已经落地（匹配器按声明的类型检查常量、引擎把值传给条件、`stdlib/rules.cml` 的守卫改为
写在值上）。**取节点这一半没有落地，语言里现在没有任何办法在条件里拿到 `const` 形参的节点**：

- 读事实：`analysis sign: int { on (const c: int) => c }` 这类声明查询的是**节点**
  （`sign(n: Node): int`）。`rule mul_one(const c: int, x: int) { x * c => x } when sign(c) == 1`
  这样的条件写不出来（`sign` 要 `Node`，`c` 是 `int`）。
- 形状/标签检查同理（`op(c)`、`type_of(c)`、`tag(c)`）。

证据：`test/cases/modules/rules/analysis_lib.cml` 与 `analysis_parts.cml` 原来都在 `when` 里对
`const` 形参读事实，本次改动只能把那个形参改成非 `const` 的模式变量（计划条目
`rules.analysis_reads_a_fact_in_when`、`rules.analysis_takes_the_parts_of_a_compound` 的描述已随之
改口径）。行为没有变，但「条件读某个**常量**的事实」这一路覆盖暂时没有地方写了。

`analysis_parts.cml` 还暴露了第二个后果：带参数的 analysis 查询（`mul_by_one(a: Node, b: Node)`）
要求「这些部件按模式绑定的顺序就是那个值的操作数」。`const` 形参原本把模式的操作数顺序钉住了；
换成两个普通形参后，`x * y` 的交换配对（可交换算子也会匹配）会用**交换过的**部件去问事实，而图里
没有哪个值的操作数是这样排列的，`evaluateQuery` 于是报
`Invalid argument of 'analysis': the analysis 'mul_by_one' has no value whose operands are these 2 nodes`
（`modules/rewrite/analysis.cpp:419`），整个遍失败——这不是规则语言能自己消化的错误，条件只好先按
形状把顺序钉住（该用例现在写 `when isConst(y) && mul_by_one(x, y)`）。`node_of` 一旦存在，
「`const` 形参 + 部件查询」这种组合才能按原样写回来。

机制上的难点只有一个：条件函数拿到的 `const` 形参是值，而**值不能反查节点**；节点与形参的对应关系
只有引擎知道（匹配时 `match.vars[i]` 就是该形参绑定的节点）。所以 `node_of(c)` 必须在构建期解决
「`c` 是第几个形参」，并在运行期有一个能拿到那个节点的通道。下面是三种通道与「不做」的代价。

## 选项

1. **给条件函数按形参追加隐藏的节点形参**：`func name__when(x: Node, c: float, c__node: Node)`，
   构建期把条件体里的 `node_of(c)` 重写成 `c__node`（`c` 的下标在构建期已知）。
   - 代价：条件函数的元数不再等于规则形参数（引擎的 `whenArity` 检查要按「形参数 + `const` 形参数」
     算，`popcount(constParams)` 就能推出来，无需改 `__rule` 的签名）；生成的名字会出现在诊断与
     `--dump-ast` 里；`node_of` 只接受规则的形参名。
   - 好处：没有新类型、没有新算子、没有新的运行期状态；引擎本来就为每个形参建一个 Node 句柄并
     `RootHandle` 住，只是对 `const` 形参改传节点。

2. **给条件函数加一个隐藏的 `Match` 形参**（新句柄类型），`node_of(c)` 重写成
   `__node_of(match, <下标>)`，`__node_of` 由 `rewrite` 模块实现。
   - 代价：一个用户永远不写的新内置类型 + 一个新算子；规则形参的顺序变成已编译条件的一部分；
     句柄要跨条件调用活下来（与 `Handle` 同样的 GC 处理）。
   - 好处：`node_of` 对任何形参都成立，而且这个句柄是以后「条件读整场匹配」（根节点、多根模式的
     共享变量）的现成入口。

3. **引擎在条件调用期间公布一张绑定表**，`node_of(v)` 按**值**反查节点。
   - 代价：两个形参可以持有相等的常量（`x*c1 + x*c2` 且 `c1 == c2`），按值反查有歧义；引擎要多一份
     与草稿同生命周期的状态；语义最弱（拿到的不一定是该形参绑定的那个节点）。
   - 好处：前端几乎不动（不用重写下标）。

4. **不做 `node_of`**：需要节点就写成非 `const` 的模式变量（现在测试里的做法）。
   - 代价：关于**系数**的规则无法读系数的节点，也无法既「只匹配常量」又「读它的事实」；事实/形状
     类的系数条件只能靠放宽模式来换（匹配面变大，`x * y` 不再要求 `y` 是常量）。

## 倾向

**选 1**。它把「值」与「节点」两条通道都留在条件函数的形参表里，不引入用户可见的新类型，不改
`__rule_when` 的签名，引擎侧只是对带 `const` 位的形参改传节点、并把隐藏形参一起传进去；`node_of`
的实现是构建期的一次下标替换。若负责人希望 `node_of` 以后扩展到「整场匹配」（根的节点、多根模式
里被多个根共享的变量），那应选 2，因为 1 的通道是逐个形参的、装不下匹配本身。

无论选哪个，`node_of(c)` 的名字与「只接受该规则自己的形参名」这条限制都请一并确认——它是语言表面，
不是实现细节。
