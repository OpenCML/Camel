# 内联之后：调用者下一条语句靠什么排在函数体效应之后？

## 问题

内联把一次调用换成被调函数的函数体（`src/runtime/draft_inline.cpp`）。调用者是某个 `sync` 块里的一条语句，它后面那条语句也是**同一个块**的语句。调用没了之后：

- "后面那条语句仍留在本块的同步链上"已经实现且无争议：它改为跟在**调用原先跟的那条语句**后面（不能跟函数体的出口锚点，同步边不允许跨出本块所在区域，实测 `sync edge 24 -> 5 leaves region 1 for region 0`，`test/cases/modules/graph_pass/unused_target.cml` 走 `std::opt::inline std::nvm`）。
- 但"函数体的效应先于后面那条语句"这条排序，在今天由**控制边**（调用者原有的 ctrl 边被改指到函数体出口锚点）承担；控制边按 H242 阶段 2 会删除，之后就没有边承担它了。

我按"顺序边只排序"的读法写了一条顺序边（`appendOrderDependency(后续语句, 函数体出口锚点)`），它被校验器按 **4.6** 拒绝：

```
graph 'main': order edge N -> N is on a pure node, which nothing orders
```

实测（写入两套边的探针 + 校验器，fast 层）：这类违规 **182 行**，集中在 `std::opt`（824 次拒绝）、`std::opt::inline`（205）、`std::inline`（103）、`std::macro`（64）。原因是同步块里的纯计算语句（例如 `let b = a + 1`，节点 kind 11 `Oper`）就是纯节点，而 `docs/design/effects/edges.cn.md:51`（4.6）写的是"任何纯节点上没有顺序边"。同一份文档 `:14` 又把"写在同步块里的纯计算语句"放在**同步链**上（设计原则 3.4）。

两边合起来看，设计里没有一条边能表达"调用者后续语句在函数体效应之后"：顺序边的两端按 `:11` 只允许是同一资源上的效应、或同一 `var` 的写与写；同步边不许跨区域。这是判词范围，施工方不自行决定。

**当前状态**：这条顺序边写在 `7ca495665` 里，在今天的树上**完全不可达**（builder 还不写同步边，`syncUsersOf` 恒空），所以它不影响任何测试；两套边的探针未提交（`D:\Projects\Camel-wt\h351-dualwrite-probe.patch`）。删控制边之前必须有答案，否则内联之后调用者的后续语句会排到函数体效应之前。

## 选项与代价

- **(A) 函数体的语句并入调用者的同步链**：`prev → 体入口 … 体出口 → 后续语句`，函数体仍记录在它自己的区域里。代价：跨区域的同步链要么允许（与今天"同步边不跨区域"的校验冲突，且 `draft_inline` 要把体的首尾链节点接进调用者的链），要么区域只作来源记录、链按全局语句序走；改动集中在 `draft_inline.cpp` 与 `checkSyncEdges`。收益：不用新增边种类，顺序关系全部落在同步链上，4.6 一字不改。
- **(B) 顺序边放宽到"块内语句"**：把 4.6 的"任何纯节点上没有顺序边"改成"纯节点上没有顺序边，除非它是某个 `sync` 块直接写着的语句"。代价：`checkOrderEdges` 与 `std::opt::order`（原 `std::opt::ctrl`）的传递约简都要认这条例外；顺序边从此有两种用途（资源效应之间、块内语句之间），语义面变大。收益：`draft_inline` 今天写的那条边直接合法。
- **(C) 区域自身排序**：区域的出口隐式排在"区域之后"的节点之前，由求解器按区域嵌套解释，不写任何边。代价：区域语义要新增一条可检查规则（今天校验器只查边），导出器/后端都要认；收益：内联不产生任何新边。

## 施工方建议

**(A)**。内联在语义上是"把被调的语句搬进调用者的块"，语句序本来就是这个块的书写顺序；把它表示成一条链而不是一条新用途的顺序边，既不动 4.6，也不给 `std::opt::order` 增加例外。代价是 `draft_inline` 的拼接要改（把体的入口/出口接到调用者链上），以及"同步边是否跨区域"这条校验需要按 (A) 的写法明确（区域是来源记录，链按块内书写顺序）。若负责人认为区域必须保持链的边界，则 **(B)** 是唯一不改内联结构的选项，代价是 4.6 增加一个例外。
