# `sync` 体里一个调用把元组当成了语句的值

**日期**：2026-11-19
**提出者**：车道 N（`lane-ssa`，基线 `d23ddd6f2`）
**状态**：待裁（本页写死默认建议，本车道按默认开工）
**触发**：按作者 2026-11-19 的裁（路 B）做 S4b，被调者一半成立、调用处一半落地后，`linear` 由 184 红降到 20 红，剩下的红全属同一类。

## 1. 问题（一行）

`sync` 体里 `let r = <call>`，`r` 拿到的是调用**自己的元组**（`(6, 13)`），而调用交出的值是它的第 0 份（`6`）：语句的值取自 `sync` 链登记的节点，不是调用处算出的那份。今天 `builder_operators.cpp` 里那一行的原文是

```cpp
        lastSyncedNode_ = targetNode;   // 登记之后，链上这个节点仍是调用
```

## 2. 两个候选

**(甲) 把语句的「值」和链上的「节点」分开记**：`linkNodes`/`chainedNodes_` 继续用调用节点（顺序语义一字不动），另记一份「这个语句的值」供 region 出口读，它取第 0 份。
代价：多一个成员、多一处写入；region 出口的取值来源从「链」改成「值」，凡读链当值的地方都要跟一次（`builder_expr.cpp` 的 region 出口是唯一已知读者）。

**(乙) 在 region 出口处单独判**：「若该节点是交出 `var` 形参的调用，则取第 0 份」。
代价：局部、零新状态，但等于把「调用交出什么」这个知识在第二个地方再写一遍——作者对出口类型的要求是「一处定义，不各自拼」，这一条与它相抵。

## 3. 默认建议（写死：走甲，且只改「值」那一侧）

链的语义是「这个 `sync` 块里最后一个语句的节点」，顺序消费者（`shouldAddSyncCtrlLink`、`hasControlDependency`、`linkSyncStatement`）依赖的是它；它不该因为调用交出元组而变形。而「语句的值」是另一件事，今天只是**恰好**与链上一个节点同形，路 B 把这个巧合拆开了。甲把拆开写进结构，乙把它写成第二个特例。

甲的范围写死在这里：只增「语句的值」这一份记录与 region 出口的读取，`lastSyncedNode_`、`chainedNodes_`、`linkSyncStatement` 的入参一字不改。
