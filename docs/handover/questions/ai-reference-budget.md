## 2. 再不处理会在哪一步红

- **检查器**：`scripts/camel-for-ai.mjs` 里的 `BUDGET`（`total: 112000`、`written: 55400`、每个区各有自己的上限）。超了会打印 `the document is <实际字符数> characters; its budget is 112000`（手写部分同理）并以 1 退出。
- **计划**：`test/plans/feat/docs_ai_reference.plan.toml` 的 `docs.ai_reference.current`——它跑 `node scripts/camel-for-ai.mjs --check`，`expect_exit = 0`，并断言输出里有 `characters (budget 112000)`。它在**快层闸门**（`smoke` + `test/plans/feat`，即 `camel-remote.ps1 -Plan smoke,test/plans/feat -Tier fast`）里每次都跑，所以这份文档超预算是**合并闸门的红**，不是一条可以攒着的提示。
- **先红的不一定是全文**：同一个检查还管手写部分和**每章预算**（文档"What each part costs"表最后一列，由检查从表里读出来量）。修剪前 §6 是 6,840 / 6,850——**一条新诊断的解释写进 §6 就能单独把 §6 顶红，不必等全文超**；当时 §12 是 11,501 / 11,800。修剪后 §6 = 6,666（余 184）、§12 = 11,103（余 697）。
- **涨价速度**：只把新诊断加进附录 A，按平均每行 98.4 字符算，现在的 1,768 余量大约还能容纳 **17 行**；若同时在 §12 写一条"错—诊断—改法"（本次修剪里这样一条是 300–400 字符）会快得多。四条车道各自在预算内、合在一起超 60 字符的那次读数，就是这么来的。

## 3. 要拍板的三件事

### Q1：预算该不该随"每条新诊断都要进参考"上调？上到多少、由谁定？

- **A. 不调，112,000 封顶。** 代价：每加一批诊断就必须有人腾地方，也就是 Q2 必须有答复；腾地方的单价会越来越高（冗词是有限资源，本次一次能省 1,411，下次未必）。
- **B. 上调，例如 120,000 或 128,000。** 每加 8,000 字符约合 +2,200 tokens（文档自己写着 112,000 ≈ 31,000 tokens）。代价：这份文档的用法是"整读"，预算直接对应一次上下文占用；而且诊断只增不减，上调试不出终点，只是把问题往后推。
- **C. 只调手写的 55,400，总预算不动。** 与全文预算自相矛盾（总量 = 手写 + 生成区），所以只有在同时**砍生成区**（Q3）时才成立。
- **倾向：A + Q3。** 全文封顶、先让生成区便宜下来，把"腾地方"变成一次性的机制改动，而不是每批诊断都要重新发生一次的体力活。若负责人认为 112,000 本来就是为了卡住"整读"的上下文，那 A 是唯一自洽的答案。

### Q2：若不上调，谁负责每次腾地方？

- **A. 新增诊断的车道顺手删冗词。** 代价：那条车道最清楚自己的诊断值多少字，但它每次都要重新发现可删的冗词；边际收益递减，早晚会变成"为了 40 字符改一句话"。本次能省 1,411，是因为这份文档在 §2–§13 的每章末尾都放了一个"Common errors"块（共 12 处），把该章的规则又说了一遍，本次缩短了其中 6 处；这类重复删一次就没了。
- **B. 定期由一条车道专门做。** 代价：要单独立项。按现行口径，只为维护账本/守卫的任务不单独立项，所以这条很可能一直被排在主线之后，直到闸门变红才被动启动。
- **C. 让检查器提前报警**（余量低于某个数就警告）。代价：改的是这次明确不许动的检查器与预算常量；而且警告不是失败，最容易被忽略，只在把余量写进某份计划的断言里才有效。
- **D. 维持现状**（谁先撞红谁处理）。代价：红的是合并闸门，不是那条车道自己的工作，最后落到合并的人身上——也就是本页这件事的来历。
- **倾向：A + 一条兜底**：新增诊断的车道负责把全文留在预算内；若某条车道发现"只能靠删信息才能腾出地方"，就在本目录开一个问题页，而不是自己删信息或改预算。这样"腾地方"有主，且不会静默丢掉规则。

### Q3：生成区是否应当只收必要字段？（现在每码一条、字段偏全）

- **A. 现状：每码一行，severity + 完整 message 模板全给。** 好处：读者能逐字对上 `diagnostics/registry.tsv`，不必另开一个文件。
- **B. 删掉 severity 列**（266 行里每行 4 字符，共 **1,064 字符**；代价：读者分不出错误与警告——除非按段分块，那又会动生成器，属另一条车道）。
- **C. `stdlib-signatures` 只留每个名字的第一行签名**（紧挨着的同名续行 120 行、4,765 字符是上限；代价：重载要另查 `docs/stdlib-reference.md`，而"这个名字接受什么"正是读者来附录 B 的原因）。
- **D. message 换成一句短说明。** 省得最多（26,183 字符里的大头），但代价最大：那正是"编译器会说什么"的原话，换成短说明等于把权威源从 registry 挪到人写的摘要上。
- **倾向：B 是最便宜且不丢语义的一条**（severity 可以从分块标题里读出来），C、D 都要先问"读者会不会因此漏掉重载"，建议**只做 B，并把 C、D 记成"若将来余量再次告急再议"**。
- 注意：Q3 的任何一条都要改 `scripts/camel-for-ai.mjs` 的生成逻辑或 `diagnostics/registry.tsv`，与"只动手写部分冗词"是两条不同的车道；本页交付的分支没有动它们。
