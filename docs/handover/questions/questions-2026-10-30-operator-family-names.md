# 算子族在 stdlib 里怎么露出名字：`add` 能不能重载成两个参数

要把 `#jvp(...)` 挂到标量算术算子上，先得有一条**带名字的声明**——标签挂在声明上，而今天 `:op/add_f` 在 Camel 侧没有任何声明。名字取什么，是这一页的问题。

## 现象到符号

- 今天带 `#op(...)` 的声明只有两类：`stdlib/prelude.cml#std.mem.blocks`（`:op/mem_blocks`）与那一组转换（`:op/itol`、`:op/ltol`、`:op/ftol`、`:op/dtol`、`:op/stol`、`:op/bftol`、…）。**转换的名字就是目标类型名**（`int`、`float`、`f32`），一族里每个签名一个名字，不存在跨族的命名问题。
- `add` 这个名字**已经属于集合加法**：`stdlib/prelude.cml#add::<T>(s: Set<T>): Set<T>`。要挂 `:op/add_f`，最自然的是 `add(x: f32, y: f32): f32`——**同名、不同 arity**。
- 树里**有同名重载，但没有"同名不同 arity"的先例**：`contains::<T>(xs: T[])` 与 `contains::<T>(s: Set<T>)` 同为两个参数、只是参数类型不同；`bf16`/`f16`/`c64`/`c128` 一族是同一 arity 的转换重载。`eprintln` 的两条同签名。
- 另外每个声明名都要有描述与 `@example`（`--verify-docs` 会编译它们），所以这一步不是两行代码，是"声明 + 描述 + 例子"。

## 为什么不能自己定

一个算子族在库里露出什么名字，是语言设计问题：`+` 与它背后的算子要不要有可见名、可见名要不要进重载体系、"两个参数的 `add`"与"一个参数的 `add`"是不是同一族——这些决定的是用户看到的名字，不是实现细节。另起名（`fadd` 之类）更是自创词表，不能由施工方定。

## 选项

- **① 重载 `add`**：`add(x: f32, y: f32): f32` 与 `add(x: float, y: float): float` 与既有的 `add::<T>(s: Set<T>)` 共存。**要多造**：确认解析器与库都接受同名不同 arity（树里无先例，要新增一条重载解析用例）；两条声明 + 两条描述 + 两个 `@example`。**会不会改变已有语义**：不改变既有调用；但"同名不同 arity"从此成为库里的合法形态。
- **② 给算术算子族另立名字**（例如 `add` 保持集合，算术一族叫别的）。**要多造**：一个新词表 + 它的文档与例子。**会不会改变已有语义**：不改变，但引入新词——**名字必须由作者给**，施工方不自创。
- **③ 不露出名字**：把 `#jvp(...)` 挂在一条**不 export** 的声明上，只作为标签的宿主。**要多造**：一条私有声明 + 说明它为何不可见。**会不会改变已有语义**：不改变，也不新增用户可见名；代价是"这个算子在库里有声明"这件事对用户不可见，`@example` 也不好写。

**默认建议：①**。它不引入新词，且与 `contains` 的重载先例方向一致（只是 arity 也变了，需要多一条用例把这条规则钉住）。

裁定之前 `stdlib/prelude.cml` 不新增任何算子声明；第一步停在"只报了数"。
