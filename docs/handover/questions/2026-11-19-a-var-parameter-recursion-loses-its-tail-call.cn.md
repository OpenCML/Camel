# 一个 `var` 形参的递归调用丢了尾调用

**日期**：2026-11-19
**提出者**：车道 N（`lane-ssa`，基线 `a5b2e8ce1`）
**状态**：待裁（本页写死默认建议，本车道按默认开工）
**触发**：按作者 2026-11-19 的路 B 做 S4b，`sync` 那一处（另页）改完后，剩下的红全换成这一条。

## 1. 问题（一行）

`count(var acc: int, n: int): int sync` 的 `return if n <= 1 then 0 else count(acc, n - 1)` 不再是一次尾调用：被调者交回的是**元组**，`if` 那一支的值必须是元组的第一份，于是调用之后多了一个取值的节点——而尾调用的定义就是「调用之后没有节点」。运行期读数：

```
test/cases/linear/byref/var_param_reference.cml:48:34: Maximum recursion depth (1000) exceeded
when evaluating graph 'count'. A call in tail position takes no frame ...
```

## 2. 三个候选

**(甲) 执行层认得这条调用**：尾调用的判据把「取某调用的第 0 份」视为透明。
代价：动 `src/execute/` 与四个 VM，本车道今晚被明令不碰；而且这是把一个语言级的判据写进执行层。

**(乙) 自调用的图不打包**：图在出口发现「它调用过自己」时保留老协议（`var` 形参仍是共享格子）。
代价：S4b 删不掉递归函数的那部分格子，`var_new` 不会归零；但这是**可数**的残留（一张清单），不是一条藏起来的语义变更。范围只在 `src/compile/gir/`。

**(丙) 改用例或抬深度上限**：把 `count` 改成非递归，或让运行期多跑几帧。
代价：抬深度是把语义问题藏进一个更大的数字，改用例是把钉住尾调用的判据删掉——两种都是让读数好看，不是让语言成立。

## 3. 默认建议（写死：走乙）

尾调用不是实现细节，它是**这段程序写得对不对**的问题：`count` 之所以能写 20000 层，是因为它没有帧。路 B 若不打包自调用的图，`count` 仍是尾调用，`var` 形参的写回仍走格子——今天的世界，一样的读数；而 S4b 在**非递归**的函数上照常完成，剩下的是 `var_new` 里一栏「递归函数」的残留，随时可以再报一次。

写死的范围：只在图自调用时保留老协议；不改 `count` 这类用例、不抬深度上限、不碰执行层。残留量在合并信里给数，不在这里猜。

## 4. 证据

- 补丁态（基线 `59e0da67b`）：`linear` 20 红，其中 `var_params`/`var_tensor` 的**值**问题在 `sync` 那页改完后全绿；改完后剩的红换成这一条，`byref/var_param_reference.cml` 一族 33 条同一句诊断。
- 直调、经函数值、经 `with` 的递归都读到同一句（`count` / `count_up` 两个写法各一条），说明它不是某一条调用路径的特例，而是「尾调用 + 打包」这一对本身。
