# 表达式里的嵌套调用：它的「值」靠什么存活？

日期：2026-10-30　车道：`lane-eff-rule`（第 1 条按裁定实现后未提交）

## 现象

裁定 `64af875f1` 说：语句是 `sync` 块里直接写的那一条，嵌在表达式里的调用不是语句、不占链位、
不写同步边；它的效应与可能出故障的节点，照第 7 条处理内联体的办法，从上一条语句向它们各连一条
**顺序边**，再从它们向本语句的链位连一条。按此实现后（`src/compile/gir/builder_operators.cpp`：
`visitLinkNode` 里新增"是否在另一个调用的表达式里"的判定、`nestedEffects_` 清单与两向 ORDER），
链确实短了，`TILES_OUTLINED` 中间的 5 也动了，但**闸门从 70 红变成 390 红**
（`total 7854, pass 7460, fail 390, skip 2`）。

**这些是行为错，不是快照漂移。** 四个实证：

| 用例 | 实测 | 数量 |
|---|---|---|
| `new_values.rebinding_loop.nvm` | `Index 0 is out of range for an array of length 0`（`test/cases/consistency/new_values/rebinding_loop.cml:51`） | 13 条同级红 |
| `fault.element_assigned_out_of_range` | 断言不成立，输出是运行时故障而非期望值 | 8 条 |
| `new_values.peek_loop` | 同上，数组/单元读到未写入的值 | 5 条 |
| `entering.arm_cell` | 分支臂里的单元读到上一轮的值 | 4 条 |

对照组：同一套裁定只改 tiles（不动建图）时，闸门与规则那 5 笔持平，没有行为错。所以问题出在建图这一半。

**核心一句**：**第 7 条的内联体是整段接进链的（有 SYNC），而表达式里的嵌套调用只有 ORDER；
3.1 只说从结果沿 data 与 SYNC 可达的节点执行，ORDER 不给可达、也不给存活。** 于是嵌套调用的值
一旦不占链位，就只剩"被外层语句当实参读"这一条命：外层读了就活，没直接读到（`v.push(x)` 这类
只有副作用、或读它的是同一表达式里的另一个嵌套调用）就没有任何东西保证它执行、也没有任何东西
保证它拿到的值是该拿的那个。上面 13+8+5+4 条都是这一格的形状：`var` 的写、数组的填、分支臂的
单元，都靠"它在链上"来保证顺序与存活。

## 为什么不能自己定

3.1 是负责人定的终稿（3.3：用到在建图时定下，遍不得改变），4.6 只说同步边连"直接写着"的相邻
语句，5.7 只给了内联体那一种"不是块里写的代码怎么进链"的处理。**"表达式里的嵌套调用"是第三类
不是语句、却必须执行的代码**，裁定把它交给第 7 条的办法，但第 7 条的办法里带 SYNC，而 ORDER
在模型里只说"后"，不说"活"。要不要给 ORDER 一种存活读法、或者给嵌套调用的值一个内部链位，
改的是 3.1/4.6 的口径，不是实现细节。

## 可执行的选项

**选项 A（嵌套调用的值也占链位）**：`sync` 块里，任何产出被本语句使用的嵌套调用，其节点照旧
`linkSyncStatement` 接进链（等于回到裁定之前的行为），只在**没有产出可被使用**（只带副作用、
返回 `void`）时用 ORDER。派工影响：`lane-eff-rule` 的读数回到 70 红那一套（tiles 22 条另算），
390 条行为错消失；代价是 4.6 要补一句"语句里产出值的嵌套调用按语句处理"，句子自己就是一条新规则。

**选项 B（ORDER 也给存活）**：4.6 / 3.1 补一句"顺序边两端都执行：一条顺序边的目标在其源之后
运行，两者都在链可达的意义上存活"，实现上把 `nestedEffects_` 里的节点当作"必须运行"登记进
建图的存活集合。派工影响：建图侧要新增一个"必须运行"集合并在 3.1 的可达判定里认它（
`src/runtime/graph_edges.cpp` 的封存检查要认这条读法）；行为错应当全部消失，但这是对 3.1 的
直接改写，须由作者定，且要重跑 390 条以外的全部分层。

**选项 C（编译器为它插内部链位）**：4.6 补一句"嵌套调用的值由外层语句的 data 边保证存活；
编译器须在它和外层语句之间插入内部链位（不经源码、不写 `sync` 关键字）"，实现上在建图时给
这样的节点补一个由 GATE 携带的链节。派工影响：不动 3.1 的读法，但引入"源码看不见的链节"，
图快照会普遍多出一节，重录面积比 A、B 都大。

**默认建议**：**选 C**。三个选项都能把 390 条修好，区别不在"能否修好"，而在**"谁被改"**：

- A 改的是 4.6 的"什么算语句"——而"语句 = 块里直接写着的那一条、嵌套调用不写同步边"是作者
  刚裁定的，A 等于请作者收回自己刚定的东西，今晚不做；
- B 给 ORDER 加语义（顺序边两端都存活），动的是边模型本身，牵动面最大（`std::opt` 的顺序边
  归约、封存检查、各后端的调度都要重新对一遍）；
- **C 不碰 4.6，只在 3.1 的可达定义上给"值"补一条存活凭据**，与裁定不冲突：语句还是块里直接
  写着的那一条，嵌套调用还是不写同步边，只是它产出的值经编译器插入的内部链节进入可达。

代价写明：C 引入"源码看不见的链节"，图快照会普遍多出一节，重录面积比 A、B 都大，且
`src/runtime/graph_edges.cpp` 的封存检查要认这条读法（内部链节与源码写的链节怎么区分，要一并定）。
