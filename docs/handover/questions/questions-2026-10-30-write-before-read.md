# "写之前读是编译错误"由谁证

裁定：待裁（作者 2026-10-30 尚未定；当前按"默认建议"做）

## 现象

第 11 条选了 A，附带一句"第一次写之前读是编译错误（数据流证明）"
（`docs/handover/reviews/questions-2026-10-30.md` §1）。查下来，**今天没有任何东西能证这一句**：

- 读一个单元时，若还没人写过它，GIR 就把读直接接在单元自己身上
  （`src/compile/gir/builder_expr.cpp:1483-1487`："Before any write the version is the cell
  `:var/new` made"）。也就是说，"读在写前"和"读在写后"在图上长得一样。
- 跨臂读/写正是生成器现在赖以工作的方式：`readCell`/`writeCell` 在每条臂里各写一遍，
  单元在 `step` 里被读一次以便闭包捕获（`src/compile/gct/builder.cpp:5912-5916` 的那排 touch）。
  图里没有一个"这张图执行时这个单元已经有值"的事实。
- 更麻烦的是：**A 落地之后，用户源码里写不出"写之前读"**。声明必须带值
  （`diagnostics/registry.tsv:18` 的 `MissingInitializer`），而"读一个还没声明的名字"是作用域错误，
  已经被 `UnresolvedReference` 拦住。跨 `yield` 的局部变成单元之后，写的那一段也一定在
  声明所在的那条臂里，读的那条臂都是它的后续。所以这条错误实际是**给 lowering 自己看的**，
  不是给程序看的。

## 两条路

1. **GCT 侧按 lowering 证**：造臂的时候就知道"写这个单元的是入口臂，其余臂只能经 `pc` 跳转到达"，
   所以证明就是造臂时的一个显式检查——每个读该单元的臂，其可达路径上必先经过写它的那一臂；
   不满足就是编译器自己的疏忽。代价：只对生成器内部单元成立（A 的另一半用途——跨 `yield` 的局部——
   走同一条路，也由 lowering 保证），而且它不是一条能拿来检查程序语义的规则。
   收益：可判定、不用新分析、不碰 GIR 的图。
2. **GIR 侧按图证**：一个"无初值单元"的读，若没有任何写能沿 ctrl/data 边到达它，就是错误。
   通用（局部、绑定、循环状态一套），但**弱**：跨臂的写在另一张图里，只能退化成"这台机器里存在写"
   就放行（写在不同分支里也放行）；要更准就得把 `pc` 臂之间的关系搬进 GIR，等于把 lowering 的
   知识放回图里。

## 我方默认建议

按 **1**，并且**先不新造用户可见诊断**：既然没有用户写法能触到它，就先做成造臂时的构建期检查
（不满足即内部错误 + 一条注释写明这是 lowering 的不变量），在 `builder.cpp` 造臂处留一句
"单元由入口臂写、其余臂只能从它到达"的注释。等两件事之一发生，再升级成真诊断：
语言允许无值声明，或 5.4 的结构体状态落地（那时"读在写前"会第一次变成用户能写的程序）。
