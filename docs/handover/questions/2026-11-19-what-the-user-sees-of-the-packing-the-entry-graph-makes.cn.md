# 入口图打的那个包，用户看见什么

**日期**：2026-11-19
**提出者**：车道 N（`lane-ssa`，基线 `2bc17f6cc` 之后的合并基）
**状态**：待裁（本页写死一条默认）
**触发**：作者 `b69635919`——「`graphExitTypeOf` 保持只取签名；**为 `var` 签名建的每一个图都打包，入口图也算**」——之后，`(0, 1)` 那 5 条的失败从「新改动引入的」变成了「入口图本该打包而没打包」。而入口图一旦打包，问题就移到用户身上。

## 1. 现象

`feat/compile` 有 5 条失败，`Error: unexpected output: (0, 1)`。`(0, 1)` 是「声明 `int` 的入口被当成交出 `(int, int)`」之后的输出形状：一个本不该有第二个分量的地方，多印了一个分量。

## 2. 入口图为什么不打包（两层，行号齐）

- `src/compile/gir/builder_control.cpp:4550`：`if (graph == nullptr || graph.get() != currGraph_.get()) return value;` —— 打包只对**正在构建的那个图**生效；构建入口图时 `currGraph_` 已是别的图，于是直接返回。
- `src/compile/gir/builder.cpp:147-152`：入口图（`rootGraph_`）的签名是**直接 `setFuncType(rootTypeFactory.build())` 造出来的**，`exitType` 取自 entry 的声明，**从不走 `handBackVariableParameters`**；`builder.cpp:155/167` 随后用 `entryGraph->funcType()->exitType()` 给入口 call 节点定型。

**一句**：**入口图不是「体」，它没有体可打包**——它是把 entry 函数的值接一次调用的壳，壳的出口抄 entry 的声明。

## 3. 若入口图也打包，那 10 处会变——变的是它们看到的值

导出 5 处与机器侧直读 5 处读的都是图的出口，入口图的出口从 `int` 变成 `(int, …)` 之后，它们读到元组：

- `program_emitter.cpp:528` —— 决定 main 的返回类型；
- `exec_plan.cpp:1855`、`fastvm/compile.cpp:146` —— 决定「有没有返回值」；
- `entry_args.cpp:607` —— 决定结果怎么交出去。

⇒ 所以「入口图也打包」不是一次内部改动：**它会把元组推到用户面前**。

## 4. 唯一的问题（成对，要作者选）

- **(甲)** 入口图的包**内部存在**，而**呈现时取第 0 份**：用户仍只看到 `0`。
- **(乙)** 入口图的包**呈现给用户**：那么 `(0, 1)` 是**对的**，而 `compile` 那 5 条是**通用例写错了**。

⇒ 这两条的分歧不在实现，在**语言对用户承诺什么**：入口交出的东西，是一个结果，还是「结果 + 形参们的终值」。

## 5. 默认（写死：甲）

**默认甲。** 理由：**入口没有 `var` 形参可交回**。用户写 `func main(): int`，他交出的是一个 `int`，不是「结果 + 他没有的那些形参们」。乙会让每个入口都多印一份它本来没有的东西——而这不是「打包是全的」这句话的意思：那句话说的是**图内部**怎么表示出口，不是**程序**怎么把结果交给人。

**若作者选乙**，那么 `(0, 1)` 那 5 条是通用例要改，不是编译器要改——而这一页就是那笔改动的依据。
