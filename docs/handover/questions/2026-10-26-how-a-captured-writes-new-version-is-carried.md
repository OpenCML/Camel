# 一次写捕获变量的调用，它的"新版本"怎么带出来

这条挂在"控制边收口"那条车道上。按设计稿 5.6，**每次写（赋值、写了捕获变量的调用）都产出变量的新版本**，读那一侧的端口接"书写上最近一次写的产出"。赋值类写者今天已经这么做了（`:op/assn_l` 的节点类型就是 `var int`，它交出的就是版本）。**写了捕获变量的调用交不出**：调用节点的类型是被调的返回类型（本案 `count_up`／`count` 是 `int`），它上面没有"版本"这一路产出。于是读退化成"拿 cell 当数据端口 ＋ 一条 CTRL 顶替边"，那条顶替边又被同步块的链位收进去、变成同步边，写/读的存活与执行跟着变一步（本案 `var_param_reference.cml std::opt` 实际 `1 | 7 | 10 | 5000 | 1 | …`、期望 `1 | 8 | 10 | 5000 | 3 | …`）。

我原先让车道"给这类调用加一个输出端口"，**在今天的节点模型里表达不出来**，证据是 API 本身：

- 建图侧唯一的连边入口 `link(DraftEdgeKind kind, from, to, PortRole role = Normal)`（`include/camel/compile/gir/draft_graph_builder.h:127-129`，封装它的 `linkNodes` 在 `src/compile/gir/builder_support.h:137-141` 同形）——**没有产出侧端口编号**；端口只有输入侧、且只带角色。
- `include/camel/runtime/graph.h:163-167` 写的是"**只有一种数据边**，每个端口带一个角色"。
- 多产出今天是**另立节点**表达的：LOOP 的多个收集值走"收集槽＋访问节点"（`graph.h:322-344` 的 `collectionCount`／`LoopView`），不是"一个节点两个输出"。

另外，把那条顶替边直接换成**顺序边**是不行的：4.6 不许纯读节点上有顺序边——这正是今天用 CTRL 顶替的原因。缺的就是那条"写者产出"。

## 三条可走的路（请裁一条）

- **(甲) 给节点模型加"有序产出"**：`link` 增一个产出编号，节点可以有多个有序产出。最贴近 5.6 的字面，但动的是图模型的边与端口约定（`graph.h` 那句"只有一种数据边"、端口角色、渲染、快照、导出都要跟着动）。
- **(乙) 换表示**（车道建议这条）：**写了捕获变量的调用，它的结果就是版本**（cell 型）；被调的返回值改由**访问节点**取（只有真的用到返回值时才建）。落在今天已有的机制里（访问节点＝LOOP 收集值同款），一次把病收干净：读的版本一律取写者产出 ⇒ 顶替 CTRL 消失 ⇒ 同步边提拔消失。代价是"调用节点的值＝被调返回值"这条口径要改成"调用节点的值＝它写出的变量版本，返回值走访问节点"，端口约定与宏导出据此改。**返回 void 的写者**（本案的 `bump`）在这条路下天然成立：它没有返回值可访问，结果就是版本。
- **(丙) 保持现状的 CTRL 顶替**（过渡态），等模型层定了再收。代价是那条"写没排在读之前"的错一直留在 `var` 那片（18 条 behavior 用例红），并且 5.6 与 4.6 的读法继续分叉。
