# 返回边界上清掉没人命名的盒子：清理点，还是「一个槽一个 wrapper」？

- 日期：2026-11-15
- 状态：已按选项 1 实现（`std::nvm` 在入口图返回处收一次），选项 3 留作将来
- 相关：原则 10.5（不可变值与 `Ref<T>` 句柄只按计数回收，计数归零立即释放）；裁定 `d052bcf23`

## 问题

原则 10.5 要的是时机：计数归零**立即**释放，且回收时机与后端无关。先前的读数说 nvm 在运行结束时还留着
1001 个盒子，看上去是「帧返回后没人命名的盒子仍被当成活的」。把读数挪到正确的时刻（入口图已返回、帧都已
释放、进程还没退出）之后，真相是另一回事：

## 量出来的四后端读数（created/released/live，返回时刻）

| 用例 | nvm | fvm | jit | prl |
|---|---|---|---|---|
| `boxes_are_counted` | 1001/1000/**1** | 1001/1001/0 | 1001/1001/0 | 1001/1001/0 |
| `boxes_loop_ten` | 11/8/**3** | 11/11/0 | 11/11/0 | 11/11/0 |
| `boxes_loop_thousand` | 1001/999/**2** | 1001/1001/0 | 1001/1001/0 | 1001/1001/0 |

所以：fvm/jit/prl **本来就**在返回时归零；缺的只有 nvm 的 1–3 块，那几块的最后一个句柄已随帧走了，而 nvm
只在图边界设安全点，之后没有任何收集点看过它们。**问题在 nvm 没有清理点，不在计数与持有者数目不一致。**

## 两条做法，必须分清

1. **清理**：在返回边界上让收集器把「没人命名」的盒子收掉。别名下安全——零计数的盒子没有任何持有者。
2. **减一**：谁的槽走了就给计数减一。别名下**不安全**，实测如此：一个 wrapper 会被两个槽命名（`let b = a`）
   或被闭包捕获，而每个 wrapper 只记一份计数，先走的槽归还了别人还持有的那份。

第 2 条的证据：把「释放帧时减一」和「槽被覆盖时减一」都实现在 `context/frame.h` 上试过，三例的读数确实变成
`released = created`、`live = 0`，但 `value.counter_closure` 与 `value.ref_one_cell_two_holders` 在四个后端上
同时变红。**这条证据证明的是「减一」不可行，不是「清理」不可行。**

## 结论与实现

默认建议（已实现）：**给 nvm 一个返回边界的清理点**。`NodeVMSchedPass::apply` 在入口图返回、它的帧释放之后，
请求并到达一次收集（`requestMajorCollection` + `safepoint`），那一处把最后句柄随帧走掉的盒子释放掉；它不改任何
槽的计数，所以别名不受影响。读数：三例在返回时刻 `released = created`、`live = 0`，四后端一致，`counter_closure`
与 `ref_one_cell_two_holders` 仍绿。

备选（留作将来，今天不做）：**一个槽一个 wrapper**——每次把句柄存进槽时 clone 一个 wrapper，使计数等于持有它的
槽数。代价：`Frame::set`、聚合的 `set`、闭包捕获、JIT 的内联槽都要走同一条路，每次存句柄多一次 wrapper 分配。
只有当**计数与持有者数目在语义上真的应当相等**时才需要它；今天的实现不需要，因为回收点由收集器给。
