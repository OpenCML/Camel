# 一个句柄槽记的那份计数，是槽的还是 wrapper 的？

- 日期：2026-11-15
- 状态：等作者决定
- 相关：原则 10.5（不可变值与 `Ref<T>` 句柄只按计数回收，计数归零立即释放）；裁定 `d052bcf23`

## 问题

裁定说「返回路径把帧的句柄槽清空（递减计数）」。实测这条做法会打破别名：**一个 `ForeignResourceObject`（wrapper）
会被不止一个槽命名**——把句柄赋给第二个槽、被闭包捕获都会这样——而每个 wrapper 只记一份计数。先走的槽把
那份还给计数，另一个还握着它的槽就指向一个已被释放的资源。

## 最小的例子

```cml
import state

func main(): int sync {
    let a = state::ref(1)
    let b = a                    // 两个槽命名同一个 wrapper，计数仍是 1
    state::set(a, 2)
    println(state::get(b))       // 先走的槽若归还计数，这里读的是已释放的盒子
    return 0
}
```

`test/cases/consistency/values/` 里的 `ref_one_cell_two_holders`、`counter_closure` 就是这两个形状：把「释放帧时归还计数」
和「槽被覆盖时归还计数」两种写法都试过，三例的盒子计数确实变成 `released = created`、`live = 0`，但这两个用例在
nvm/fvm/jit/prl 四个后端上同时变红。

## 先量准了时刻（这一条影响结论）

`boxes_are_counted` 那份程序（嵌套调用造 1000 个盒子、留一个），在**最后一次调用返回之后、退出之前**加一次
`FOREIGN_RESOURCES` 读数（`FOREIGN_RESOURCES_AT_RETURN`）：

| 用例 | nvm | fvm | jit | prl |
|---|---|---|---|---|
| `boxes_are_counted` | 1001/1000/**1** | 1001/1001/0 | 1001/1001/0 | 1001/1001/0 |
| `boxes_loop_ten` | 11/8/**3** | 11/11/0 | 11/11/0 | 11/11/0 |
| `boxes_loop_thousand` | 1001/999/**2** | 1001/1001/0 | 1001/1001/0 | 1001/1001/0 |

（created/released/live）所以：以前读到的 `live=1001` 是**退出时刻**的读数加一份不分配东西的程序尾部造成的假象；
返回时刻 fvm/jit/prl 本来就是 0，nvm 残余 1–3 块——那几块的最后一个句柄已经死了，但没有收集点去看它。

## 选项

1. **一个槽一个 wrapper**（默认建议）：把句柄存进槽时 clone 一个 wrapper，计数就等于持有它的槽数，返回时递减才有意义。
   代价：`Frame::set`、聚合的 set、闭包捕获、JIT 的内联槽都要走同一条路，每次存句柄多一次 wrapper 分配；收益：裁定
   的时机要求在四个后端上真正成立。
2. **接受「下一个收集点释放」**：现状（运行结束补一次收集，让退出读数确定）。代价：明确放弃时机保证；nvm 在返回
   时刻残余 1–3 块，实测如此，且这是后端差异。
3. **只在部分形状上做递减**（例如只管帧槽、不管闭包捕获）：不成立——`Ref` 被闭包捕获是既有语义，正则化不了。

倾向：1。它是存储路径的改动，不是返回路径的一行，动手前要作者确认；2 是今天已经落地的状态，可以立刻停在 2。

## 卡住的事

`ref.boxes_are_counted` / `boxes_loop_ten` / `boxes_loop_thousand` 三条断言目前量的都是**退出时刻**的值
（`released = created`、`live = 0`，四后端一致）。它们要断言的其实是返回时刻的值；在 nvm 上那个值是 1–3，不是 0。
选 1 之后才能把断言改到返回时刻。
