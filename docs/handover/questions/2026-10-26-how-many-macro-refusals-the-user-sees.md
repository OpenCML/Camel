# `std::macro` 展开时收集到的多条拒绝，用户该看到几条 · 2026-10-26

> 说明（协调者）：这条与设计原则正文**直接冲突**，所以我不自己定。落地方已按你的裁定把 12 条 `grad_function_value_*` 用例改成"位置回位置字段、关联位置 related、`std::macro` 收集全部拒绝、运行期在首处停下"，但**"收集全部"到用户眼前只剩一条**，原因是 CLI 的策略与 §8 的模型。

## 冲突点

- `docs/design-principles.cn.md` §8 第 537 行：**「`std::macro` 是流水线中的一个阶段，不是编译期。」**
- 同节第 540 行：**「macro 求值失败：按运行时故障处理，与任何遍运行中的故障相同。」**
- 而 CLI 的运行期 sink 配置是 `per_severity_limits{{Severity::Error, 0}}`（`tools/camel-cli/main.cpp:190-193`），`Diagnostics::add` 在**第一条 Error 上就 throw**（`src/core/error/diagnostics.cpp:674-694`，"limit == 0 表示允许存 0 条"），CLI 在 `:751` 捕获后只报一条。

实测（插桩）：`branch`/`parameter` 的 `refusals_ = 2`、`failures_ = 2`、`noteFailure` 被调用两次、每条拒绝各有一个 `CarriedReport` —— **收集是全的，显示只有第一条**。

## 我的建议（供你选，也可另指）

**甲（不改 §8，我倾向这条）**：**第一条拒绝照旧按运行时故障报出**（流水线在它那里停下，与 §8:540 一致），把**其余收集到的拒绝作为它的 related 位置/note 附上**（"同一个宏调用里还有 N 处不能求导，最近的一处在 …"）。好处：§8 不动、CLI 不特例化、你裁的"收集全部"对用户可见；代价：related 要能承载多条（或至少给出条数与最近一处）。

**乙（要改 §8）**：把展开期收集到的拒绝**报进模块/编译诊断容器**（多条都由 `reportModuleFailures` 打印）。代价：§8:537/540 的两句要随之改（"macro 的**展开期**拒绝是编译诊断、**求值中**的故障仍是运行时故障"），并要新加一个"pass 拒绝"信号让流水线以失败结束（现在唯一的失败信号是 `rtmDiags()->hasErrors()`，而 `apply()` 返回 nullptr 在 `pass.cpp:1915-1918` 算 **Consumed**、CLI 会以 0 退出）。

**丙**：改裁定为"macro 只报第一条"（最小改动，但 `refusals_` 收集全部这件事对用户就没有意义了）。
