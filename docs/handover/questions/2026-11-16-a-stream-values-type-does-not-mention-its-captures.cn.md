# 流值的类型说「我不捕获」，它的端口说「我捕获了三个」

> 一页一问。**默认建议写死在下面，本轮按默认开工，不另等。**

## 这一页要的答复

一个闭包的类型和它的捕获端口**对着同一件事给出了两个答案**。这不是本轮引入的，但本轮把它照出来了。

```
generators.cml，改动前（origin/develop 的树）：

  __g_71__  端口：read : var () => int uses capture 0
  __g_71__  类型：() => (int, int..)?
                          ↑ 没有 uses capture，可是它的端口里有一个格子

同一个文件，本轮之后：

  __g_72__  端口：__gen_pc__ var int, __gen_halt__ var int, x var int,
                 read var () => int uses capture 0        -- 四个格子
  __g_72__  类型：() => (int, int..)?                     -- 一个 uses capture 都没有
```

**类型是从哪儿来的**：`Builder::visitGeneratorBody` 里那个流值闭包，`*lambda << tree_->makeType(stepType)`，
而 `stepType` 是 `StreamType::stepType()` 手写的 `() => (T, T..)?`，它**只由元素类型决定**（`StreamType`
的 intern key 就是元素类型），不知道也不会写进捕获。**端口是从闭包体里的引用算出来的**（`captures.cpp`），
它数到了 3 个/4 个格子。

⇒ **两个来源**：类型说 0 个捕获，端口说 3 个。和 `NoMatchingFunction` 那一族同宗——**同一个东西，两处
各有各的答案**。今天它不可见，是因为流值闭包的捕获只有机器自己看；一旦有谁按类型读捕获（捕获普查以外的
消费者：`uses capture N` 出现在函数类型里，而闭包的类型是它可以被赋值的那个类型），它就会露出来。

**⇒ 问题是：一个闭包的类型里的 `uses capture N`，应该由捕获清单算出来，还是继续由类型的构造者填？**

## 默认建议（按此开工，不另等）

**让捕获清单成为唯一来源，类型从它读；不把 `stepType` 改成自动推导。** 在 SSA 落地之前不动手。

具体三步（按顺序，每步一次构建）：

1. 闭包的类型不从「手写的 `stepType`」来，而从**它的端口**来：闭包的类型在捕获清单定下来之后构造，
   `uses capture N` 由格子端口数目和顺序给出。
2. `StreamType::stepType()` 保留原样——**它是给程序读的类型**（`for x in s` 那一边），不是给机器闭包用的。
   机器闭包的类型是它自己的，两者本来就该分开。
3. 等第 1 步绿了，再回头问 `stepType` 要不要变（那是另一页的事）。

## 为什么现在不改

- **改它会同时动 `capture_ports_generator`（236）与 `capture_ports_closure`（83）两个数，而这两个数是今天
  仅有的两把尺。** 一次同时动两把尺，读数就不再能告诉我们是哪一步动的手。
- 本轮的靶心是**让闭包的类型只有一个来源**，而它当前被卡在更前面的一步：程序闭包在生成器体里捕获 `var`
  时，机器仍然是那个给答案的人（`2026-11-16-generators-keep-the-cell-when-the-closure-captures-a-var`）。
  那一步没动之前，改类型的来源只是把一个分叉换成另一个分叉。
- SSA 落地之后，闭包的捕获清单与类型的关系会再变一次（状态元组的来源整个换掉）。**在那之前改，改的可能
  是一段要被整段删掉的代码。**

## 附：这一页怎么被找到的

`test/cases/compile/stream/generators.cml` 的 `std::jgir` 里，把「捕获端口名 = `x`」的闭包全列出来：

| 闭包图 | 端口 `x` | 形态 | 归属 |
| --- | --- | --- | --- |
| `__g_66__` | `x` | `int`（值） | 函数 `sign` 的流值闭包（机器造） |
| `__g_63__` `__g_64__` `__g_65__` | `x` | `int`（值） | `__gen_step__` 的流值闭包（机器造） |
| `__g_71__` | `x` | `var int`（格子） | `__gen_step__` 里**程序**闭包 `() => x` |
| `__g_72__` `__g_73__` `__g_74__` | `x` | `var int`（格子） | `__gen_step__` 的流值闭包（机器造） |

**同一个闭包里没有两条路**（每个图各出现一次、一种形态）；不同类型与不同闭包之间不一致，那是允许的。
**不一致的是类型与端口**，不是端口与端口。这一页只问那一处。

## 一条判据：在 S6 之前，`capture_ports_closure` 的任何下降都应被怀疑

`83` 这个数现在**不会动**：生成器的状态元组在 SSA 之前装不下任何程序局部，所以「状态按值」传不到
程序闭包那一边（读数见 `../reports/2026-11-16-the-state-tuple-holds-nothing-but-pc-and-halt.cn.md`）。

**一个不会动的数本身就是一条判据：它动了，就说明有别的东西在改它**——那不是本页问的事，要回头找
是哪一笔改的。
