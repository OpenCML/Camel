# 0.4 只把「编译一次」放在值上，实例仍按程序的类型组合预先展开——这算 0.4 还是匹配那一项

## 读数

`test/cases/opt/generic/algebra.cml`，Release，`--time-phases`，一台 1 分钟负载 15–21 的机器
（读数只与自己的另一侧比较，不与安静主机比）：

```text
opt::saturate                     56.7 ms
  其中引擎取规则（engineRules）   29.1 ms
    其中瞬时实例化 84 条           ≈28 ms
std::opt（三次引擎调用）           87 条规则编译 = 84 条实例 + 3 条普通规则
改前 mixed 两模块两次引擎调用      168 条
改后 mixed                        84 条（第二侧 1 次命中，0 编译）
   opt::saturate 第二次            55.4 ms → 26.4 ms
```

计数口径：`phase::count("rules.compiled", 1)`，一处放在 `instanceRules` 首次编译实例处，
一处放在 `buildEngineRules` 编译普通规则处；`--time-phases` 的 `counters` 里读。

## 判断

`0.4` 的原话是「遍不再在每次调用时重编译它需要的规则集，而是拿到已经编译好的规则值」。
按这句话做完了三件可测的事：

- 普通规则按值只编译一次（`std::opt` 上 3 → 1）；
- 同一个声明在另一个模块加载里再出现时不再重编（mixed 168 → 84）；
- `engineRules` 交出 `const std::vector<Rule> &`，遍拿到的就是编译好的值，第二次调用 1 次命中。

但 `std::opt` 上 87 条里 84 条是**泛型规则按程序现有类型组合逐个展开实例**，
这不是「重编译」，而是设计 §7 那句话的另一半：「泛型规则在匹配处按类型实例化并缓存」。
今天做的是「在取规则处把程序的所有类型组合先展开」，所以类型一变就要重来。

## 问题

把「在匹配处实例化」并进 0.4，还是留给匹配那一项（按根算子 id 建索引、半朴素匹配）？

默认（我按这个走）：不动匹配器，0.4 只做「编译一次」；上面那 84 条留给匹配那一项，
因为它的改法是把实例化挪进匹配循环，属于 §7 的匹配重构，不是这一项的形状。
