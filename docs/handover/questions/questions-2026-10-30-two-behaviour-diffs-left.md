# 判定改对之后仍剩两个行为错：臂里的写抢在读到它之前，`prl` 一行不打印

日期：2026-10-30　车道：`lane-eff-rule`（第 1 条按作者的判定规则改正后；未提交）

## 现象

作者 2026-10-30 的裁定（`origin/fsh-dev@1fac91039`）改的是"嵌套"的判定：**语句的根节点是这条语句
的源码产出的最外层节点，只有作为同一语句里另一个节点的实参被读走的调用才算嵌套**。照此改后
（`visitLinkNode` 用 `operandDepth_` 判，`visitOperand` 是唯一加深度的地方；进新图不继承；进分支臂
清零），闸门从 **390 红降到 161 红**，行为错从一批降到 **5 条**，分两类。

### 类一：`entering.arm_cell.opt.{nvm,fvm,jit,prl}` 四条，同一个错位

最小程序（10 行，`/tmp/d1.cml`）：

```cml
func from_either(var x: int, c: bool): int? sync {
    return if c then x else sync { x = x - 1 }
}
func main(): int sync {
    var x: int = 1
    println(from_either(x, true) ?? -1)
    println(x)
    println(from_either(x, false) ?? -1)
    println(x)
    return 0
}
```

- `std::nvm`：`1 1 0 0`（对）。`std::opt::inline std::nvm`：`1 1 0 0`（对）。
- **`std::opt std::nvm`：`1 0 0 0`（错）**——第二行该是 `1`，得到 `0`，即第一次调用之后那次
  `println(x)` 读到了**第二次调用里 else 臂的写** `x = x - 1` 算完的值。四个后端一致，说明不是
  某个后端的问题，是图上的次序。

**这一条不是"节点没存活"**：把 `std::opt` 之后的图（`std::gir`，69 个节点、146 条边）按 3.1
从 EXIT 沿 data+SYNC 反查，**69 个节点全部可达，四个 `:io/println` 也全部可达**。所以 3.1 的
存活读法在这里是成立的，坏的是**次序**：`x = x - 1` 这个写节点被排在读它的语句之前，而它本该在
之后。图上写节点所在的链在臂内（`SYNC :op/assn_l -> GATE`、`CTRL BRCH -> :var/get`），**没有一条
边把它接在"调用这一句"在 `main` 链上的位置之后**——这正是作者裁定里"嵌套调用的值靠外层节点读到
而存活"管不到的那一半：**存活有了，先后没有**。

**给作者的判断材料（一句可裁的话，不是请示）**：`std::opt::inline` 单独跑是对的、`std::opt` 跑
是错的，两者相差的只有 `std::opt` 多出来的那几条规则；**若顺序边在规则集里被当作可归约的冗余，
那么第 7 条那套顺序边在 `std::opt` 下就不成立**——因为它归约掉的正是"谁在谁之后"，而 3.1 不给
顺序边存活，两者一起归约，剩下的就只有"都活、但先后由规则重排"。

### 类二：`new_values.sort_rebinding.prl`，一行都不打印

- `std::nvm` / `std::fvm` / `std::jit`：输出与期望一致（`[3, 1, 2] [1, 2, 3] …`）。
- **`std::prl`：零输出**（`expect_stdout` 期望 81 字节，实得 0 字节，exit 0，不是崩溃）。
- 同一个图按 3.1 反查：**77 个节点全部可达，四个 `:io/println` 全部可达**。

所以这一条也不是"节点没存活"：图是活的、四个打印都在，**是 `prl` 这一路把整张图跑成了空**。
它与类一不同源——类一是次序错（数值错），类二是一条都没跑（整段没执行），值得分开看。

## 为什么不能自己定

3.1（节点从结果沿 data 与 SYNC 可达则执行）与 4.6（语句 = 块里直接写着的那一条、嵌套调用不写
同步边）都是终稿口径，两条在类一、类二上都**成立**：反查表明没有节点掉出可达集。也就是说，这两
条错的成因在两者之外——**一条是"写节点在臂内的链位与调用这一句在块链上的位置没有先后边"，
另一条是"并行后端遇到这张图跑空"**。前者要不要给"臂里的写"补一条到外层链位的边（那就是给
4.6/5.4 加一句），后者要不要查 `prl` 的分段（那是实现问题，但如果分段依据是链形，就与第 1 条同源），
都不是改这条车道的人能定的。

## 可执行的选项

**选项 A（类一：臂里的写给一条到调用语句链位的边）**：在 4.6 或 5.4 补一句"分支臂里的语句，
其链位接在包含该分支的语句的链位之后"，建图时对臂体的 `lastSyncedNode_` 不再清零，而是接上外层
语句之前的那一节。派工影响：`arm_cell.opt` 四条应当回绿；代价是"臂是它自己的块"这条口径要写出
例外，且所有带 `sync` 臂的图快照会多出边。

**选项 B（类一：先查是不是 `std::opt` 的归约把次序弄反）**：`std::opt::inline` 单独跑是对的、
`std::opt` 跑是错的，差别在 `std::opt` 里的其它规则（顺序边归约 / 公共子表达式 / 折叠）。先在
`std::opt` 的规则上找"把 `:var/get` 排到写之后"的那一条，若是规则读错了链就改规则，不动 4.6。
派工影响：不改设计文档，只修规则；代价是需要一次规则级定位，可能只是 `order` 归约把方向弄反。

**选项 C（类二：`prl` 跑空的成因先定位，再谈是否同源）**：把 `sort_rebinding` 在 `prl` 上的
分段结果打出来（`--log-level debug` / `tiles:regions` 一类），确认是"分不出段"还是"段跑空"。
派工影响：纯诊断，不动语义；代价是 `prl` 的分段逻辑要读一遍，可能牵出与第 1 条同源的链形假设。

**默认建议**：**先 B 后 A，C 并行做**。B 是因为 `std::opt::inline` 对、`std::opt` 错，差别就在
`std::opt` 多出来的那几条规则上，先排除"规则把顺序边归约反了"这种低成本可能；若 B 排除，则 A 是对
口径的最小改动。C 与两者都不同源（一条都没跑 vs 数值错），应当单独定位、单独记账。
