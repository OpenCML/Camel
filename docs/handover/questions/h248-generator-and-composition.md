# H248：`yield` 状态机的边界与 `f..g` 的类型规则

提交给语言作者 / 决策者裁决，2026-10-24，随 H248 计划（`docs/design/io-concurrency-streams/plan.cn.md`）一起提交，由协调者指示。**计划里不自行选定语义**：片 E 与片 A2/A3 的验收形态由这里的答案决定。

## 1. `yield` 状态机的边界

已定的（任务书 5.28 第 3 条）：**头部必须写流类型**；编译成**状态机**；**区域里的循环、分支都可以 `yield`**；`unfold` 作库函数。设计稿 3.5 又定了执行模型：生成器本身就是驻留的，每拉一次从上次停下的地方继续一轮，状态一直保留。

今天最近的既有物是**循环收集槽**——`include/camel/runtime/loop.h` 第 20–28 行：图生产者可以给一个 `LOOP` 结点若干个「收集槽」，每一轮体区域产出一个值、按轮次收集成一个数组；同处注释明写 *"no source syntax exists for this yet; the H4d design"*（**源码写不出来**）。任务书 3 说 `yield` 是「现有循环收集槽的**惰性版本**」——所以它是这个模型的改造，不是新模型。

下列没有依据：

| # | 问题 | 为什么重要 |
|---|---|---|
| a | `yield` 之后**还能不能接着 `yield`**（`yield a; yield b` 同一轮）→ 一轮一个值还是多个？ | 收集槽是「一轮一个值」；一轮多个会改变状态机的形状（要记住停在哪个 `yield`） |
| b | **嵌套多层区域**里 `yield`（`loop` 里的 `if` 里的 `loop` 里 `yield`） | 状态机要压多少层「停在哪」；任务书只说「区域里的循环、分支都可以」 |
| c | `yield` 在 **`match` 的臂**里、在 **`sync` 块**里 | 臂与 `sync` 块今天都有各自的区域与效应顺序 |
| d | `yield` 之后的**效应顺序**：同一资源上，第 i 个元素与第 i+1 个元素的效应谁先 | 设计稿 3.4 把「同一资源上、跨元素的效应顺序」列为「要定的」；`sync` 块今天只给它自己直接写着的语句排序 |
| e | **故障路径**：`yield` 前一步出故障（`T!`/`FaultKind`）时生成器怎么办——流结束？故障传给消费者？ | 预取条件要求「被提前的部分必须**纯且不会出故障**」，所以故障路径正是预取边界 |
| f | **生成器值本身是否也线性**（只能消费一次） | 任务书 4.5 说的是「流值」，生成器产出的是一个流值，所以大概是；但一个**生成器函数**调用两次得到两个流值，各消费一次，必须合法——要写清 |
| g | **委托**（`yield from` / `yield*`）要不要 | 没有它，组合两个生成器只能靠 `for x in inner do yield x`（若那合法）；有它，状态机要支持子状态机 |
| h | 生成器里的 **`return`**：提前结束流？返回一个最终值？ | 收集槽的模型里循环的值是最后的状态，没有「最终值」这一档 |
| i | 生成器**没有 `yield`**（空体、或条件永不成立） | 空流是合法的（`take` 得到 0 个元素）还是诊断？ |

- **建议**（把范围收窄到一个可落地的状态机）：(a) **一轮一个值**（沿用收集槽的形状，多值要显式 `yield` 多次即在多个轮次里）；(b) 允许任意层嵌套区域，状态机记录「区域栈 + 每层的位置」；(c) `match` 的臂允许，`sync` 块**暂不允许** `yield`（先给诊断），因为 3.4 的效应顺序还没定；(d) 效应顺序**按元素的先后**（与 3.4 的「按元素的先后，顺序边随元素展开」一致）；(e) 故障传给消费者（不是静默结束流）；(f) 生成器**产出的流值**线性，**生成器函数**可调用多次；(g) 委托**本轮不做**，先要求 `for x in inner do yield x` 这一种写法，并在文档里写明；(h) `return` 结束流，不返回值（要返回值就再定义一个槽，等以后）；(i) 空流**合法**。
- **收益**：状态机只有一种形状（区域栈 + 一轮一个值），任务书「区域里的循环、分支都可以 `yield`」全覆盖；**代价**：`sync` 块里的 `yield` 与委托要等以后单独裁定。
- **若 (a) 选「一轮多个值」**：状态机的「停在哪」要变成一个更细的位置（哪个 `yield`），并且与收集槽的模型分道扬镳——`include/camel/runtime/loop.h` 的模型要跟着改，代价明显更大。

## 2. `f..g` 的类型规则

已定的（设计原则 4.2 第 258 行、任务书第 5 条）：先 `f` 后 `g`，`(f..g)(x)` 即 `g(f(x))`，与管道 `x->f->g` 同向；可用于高阶函数（`xs->map<normalize..encode>`）、规则（`map(map(xs, f), g) => map(xs, f..g)`）与遍的组合。

今天的状态：`compExpr : annoExpr (('..' | '?..') annoExpr)*`（`src/parse/syntax/parser_expr.cpp` 第 360 行），是**零个或多个的列表**，不是两层；`src/parse/ast/builder.cpp` 第 3617–3665 行把它建成一个**左结合的链**（`*dataNode << lhsNode << rhsNode`，然后 `lhsNode = dataNode`）。落图时编译成编译器自有宏算子 `:macro/cmp`（`src/compile/gct/builder.cpp` 第 2944 行），它的实现是 `return NullSlot`（`src/builtin/operators/macro.cpp` 第 12 行）——**空实现**。

下列没有依据：

| # | 问题 | 今天的相邻事实 |
|---|---|---|
| a | 两边都是函数时，**参数个数**怎么对：`f: (int) => int` 与 `g: (int, int) => int` 能组合吗？ | 管道 `x->f->g` 里 `g` 收到 `f` 的结果再带额外实参（`x->f(a, b)` 即 `f(x, a, b)`，设计原则 4.4 第 275 行）；组合要不要同样规则？ |
| b | **`with`（上下文）参数**怎么办：`f<w1>..g<w2>`？组合的结果是 `f<w1>..g<w2>` 还是一个还要吃 `w` 的函数？ | 设计原则 4.4 第 270–274 行：`with` 参数是「决定这是哪一个函数」的东西；`f<w>` 是部分应用 |
| c | **泛型函数值**：`f` 是泛型（`id::<T>`）时组合在什么时候实例化？ | 5.5 与 4.4 第 273 行「泛型函数可以出现在任何期望一个函数的位置」 |
| d | **重载 / 有多个候选**的函数值：`f..g` 里 `f` 名字有多条重载时按什么选？ | 「函数值没有身份」（设计原则第 280 行）：只由它算什么决定 |
| e | **超过两个**的链 `f..g..h`：已定是左结合（今天的 AST 就是左结合）；但**与 `->` 的优先级**关系没有依据 | 管道 `x->f->g` 与 `f..g` 必须同向（4.2 已说）；那 `x->f..g` 是什么？ |
| f | 组合出来的函数值能不能进 **`map<>` 的尖括号**（`xs->map<inc..dbl>`） | 4.2 第 258 行说可以（`xs->map<normalize..encode>`）；今天尖括号里放一个 `CompExpr` 会先撞上 `ConstructNotSupported` |
| g | 组合的值能不能**作为规则右式**（片 I 要的 `map(s, f..g)`） | `src/runtime/rules.cpp` 的项读取器只接受算子、常量、参数（第 107–148 行） |
| h | 组合里出现**效应**（`f` 或 `g` 带效应） | 图的边模型（H242）下组合要不要保留顺序边 |

- **建议**：先把范围定成 **(a) 单参数对单参数**（`f: (T) => U` 与 `g: (U) => V`，即两边各一个普通参数），其余（多参数、`with` 参数、泛型、重载、`x->f..g`）**本条不覆盖并给诊断**；**(e)** 明确 `..` 比 `->` 松（`x->f..g` 读成 `x->(f..g)`，即把组合好的函数传给管道）；**(f)** 允许进 `map<>`（4.2 已经这么写了，且这是 `xs->map<normalize..encode>` 的用法）；**(g)** 交给片 I 与 H232。**收益**：先让 `f..g` 在标量函数上可用（`inc..dbl` 的验收），把规则与高阶的复杂面交给已经要改那两个地方的 H232/H242；**代价**：多参数组合（`g` 用 `f` 的结果加一个常量）要等以后。

## 3. 两边是数时是区间——区间的读法

任务书第 5 条：「两边是函数时是组合，是数时是区间」。今天 `1..5` 报的仍然是「**function composition** is not implemented」（实测，H248 计划附录 A 的 t13）——诊断**不看操作数类型**；今天「区间」的等价写法是库函数 `range(start, end)`（`stdlib/signatures/globals.cml` 第 324 行 `export func range(start: int, end: int): int[]`），张量版是 `stdlib/signatures/tensor.cml#range`（`Tensor<int64>`）。

下列没有依据：

| # | 问题 | 相关事实 |
|---|---|---|
| a | **端点包含性**：`1..5` 是 `[1,2,3,4]` 还是 `[1,2,3,4,5]`？ | `range(a, b)` 今天的行为要看它的实现；`0..n` 是排他还是包含直接决定循环写法 |
| b | **步长**：要不要 `1..2..10`？ | `range` 有 `start/stop/step` 三个参数（张量版），数组版只有两个 |
| c | **是数组还是流？** | 区间很短（`1..5`）时数组更自然，但 `1..1000000000` 就要求它惰性；任务书第 2 条说「流是惰性序列值」 |
| d | 与 **`range(a, b)` 是否同一个东西**（`1..5` 是不是 `range(1,5)` 的糖） | 若是同一个，`range` 保留还是删除？若不同，两者要能共存且文档写清差别 |
| e | 区间能不能用在**类型位置**（`T[1..5]`）与**切片**里？ | 切片今天用 `:`（`t[a:b]`）；类型里的 `[...]` 今天是维度（整数、`?`、`..`、维度名），加区间会与维度包冲突 |
| f | **浮点**区间（`0.0..1.0`）与**字符**区间 | 4.2 说「两边是数」，是有理数还是整数？ |
| g | `1..5` **不带括号**时的读法 | 与问题 1（`as T..` 的两种读法）是同一个交界；H248 计划片 A3 因此**保留现状诊断等问题 3 的答案** |

- **建议**：(a) 端点包含性照 `range(a, b)` **今天**的行为定（保持兼容，不引入第二种约定），并在文档里逐字写出边界；(b) **本轮不做步长**（`1..2..10` 因 `..` 是列表层次，语法上会解析成三个操作数——要么明确拒绝、要么以后单列）；(c) 区间是**数组**（与 `range` 一致），要惰性就显式转流（`(1..n) as int..` 一类的写法由问题 1 定）；(d) `1..5` **就是** `range(1, 5)` 的糖，`range` 保留（它是今天的既有 API，且张量版有步长）；(e) 区间**不进类型位置**，切片保持 `:`；(f) 本轮只做整数；(g) 由问题 1 的第 3 节定。
