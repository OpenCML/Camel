# 问：拆 `T?` 的算子在 null 时，发诊断还是返回零槽？

`2026-11-18`｜基线 `origin/develop = 6a0e3fbf9`｜引 `f9d374161`（每个状态槽都是 `T?`、起点 null、没有零值拆分）

## 一、为什么必须问

`f9d374161` 裁定状态槽是 `T?`、起点 null。落地之后，**每个 pull 的头部都必须把 `T?` 拆成 `T`**，否则状态值无法使用。而拆槽要用一个算子，**表里现在只有一个能拆的，而它是不检查的那个**：

```
`operator_table.h:127-139`：`:op/tag_null_value`（id 9）是**不检查**的那个
  ⇒ `tagged.cpp:39-41`：null 时**返回一个零槽**
⇒ 第 10.4 节已写：「**它不是替代品；检查/不检查是裁定**」
```

**⇒ 所以这一问不是「用哪个算子」，是「那个算子该不该检查」。**

## 二、为什么它是裁定而不是实现细节

一旦有值走这条拆槽路，**null 有两种可能的含义**，而它们在生产上分不开：

```
(a) **null 是一个错误**（这个槽本该在 pull 之前被写上）⇒ 应当**诊断**，因为继续下去是读一个零值
(b) **null 是合法状态**（这个槽这一轮还没被写）⇒ 应当**给一个可判定的表示**，而不是零值
```

**⇒ 而「返回零槽」把 (a) 和 (b) 变成同一个结果**：**一个正常形状的值。** **⇒ 那正是今晚已经出过一次事的那一类**：`head` 截断的输出、旧二进制仍在跑、结果看起来完全正常 —— **一个会坏的东西返回了正常形状的结果。**

**⇒ 另有一条具体的约束**：`state::set` 的运行时只认 `state.ref` 的 handle（`modules/state/module.cpp:75-84`），而 `Ref<int>?` 连类型检查都过不了（`entersImplicitly`：「a T? is not a T」，`tuple.h:217-224`）。**⇒ 拆槽必须在**类型**上就成立，不能靠运行时补救。**

## 三、默认建议（按这一条开工，作者改口再退）

```
**做成「检查的」：`T?` → `T`，null 时**发诊断**、不返回零槽。**
⇒ 理由：它让 (a) 与 (b) 分开；而「不检查」的版本会让探针变绿而让语义更坏
  （正是今晚那条：**为了打通一个读数而选的检查语义，会让读数变绿而让语义变坏**）。
⇒ 而它有一个可操作的实现面：诊断只在 `T?` 的 `tag_` 为「null」时发出，
  与 `:op/tag_is_null`（已存在）的判定同源，所以两者不会给出互相矛盾的结果。
⇒ **若作者认为 (b) 合法**，则应给一个**可判定的**表示（例如让拆槽返回 `T?` 而非 `T`，
  由调用方显式判空），**而不是零槽** —— 那同样不是「返回一个正常形状的值」。
```

## 五、一处必须先记下的判断依据

「机器造」的型**没有 provenance 标记**，靠**入口唯一**可分：

```

⇒ 唯一带占位符的机器容器是 `stateType`（`gct/builder.cpp:6252-6259`），

⇒ **⇒ 门只能靠「走法 + callsite 的 machine 标志」，不能靠节点自带的位。**
```
