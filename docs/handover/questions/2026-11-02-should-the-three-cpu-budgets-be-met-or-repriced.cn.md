# 三条 CPU 预算是真超（单跑仍超 0.1%–19%）：修性能，还是按今天的机器重新定价

## 问的是什么

`test/plans/perf` 里三条按 **CPU 时间**（不是墙钟）定的预算，今天**单跑**也超，而且没有任何竞争负载：

| 用例 | 预算 | 单跑读数（`--jobs 1`，各自两次干净运行） | 超 |
|---|---|---|---|
| `startup.cost` | `17.50 s` | `17.68` / `17.74` / `17.52` s | +1.0%–1.4%，第三次 **+0.1%** |
| `collfuzz.many_small` | `151.00 s` | `161.52` / `162.49` s | +7.0% / +7.6% |
| `gc_soak_long.generational` | `70.00 s` | `83.18` / `83.45` / `80.03` s | +19% / +19% / +14% |

**三条都不改预算**（今晚的判词：改预算等于把缺陷记成通过）。要你裁的是：这三条**该怎么办**。

## 三条各自的账本（预算是怎么定出来的）

- `startup.cost`：计划里写着「**a single-run CPU reading with the smallest headroom above it: 16.22 s** measured … rounded up to the next 500 ms — **1.08x**」。即预算 = 当时的读数 × 1.08。今天读 17.5–17.7 ⇒ 比当时的读数高 **8–9%**。
- `collfuzz.many_small`：预算是 `1.63x` 该条最高读数（`90.76` / `90.72` / `92.62` s，三次窗口）。今天读 161–162 ⇒ 是当时读数的 **1.75–1.79 倍**。
- `gc_soak_long.generational`：预算是 `1.63x` 的 `42.17` / `42.36` s。今天读 80–83 ⇒ 是当时读数的 **1.9 倍**。

## 取到的证据（不是猜）

**① `gc_soak_long.generational` 的 profile（`std::profile report=true`，今天这棵树）：**

```
run 190.15 s   allocations 498020254 calls, 732.57 MiB requested, 26.61 s inside the allocators
operators (share of operator time)
  cpu  :op/atos        194000097 calls   59.10 s   52.6%
  cpu  :op/add_s       290000145 calls   46.92 s   41.8%
  cpu  :struct/len_str  98000049 calls    3.87 s    3.4%
  cpu  :struct/range     2000002 calls    2.48 s    2.2%
```
分配器统计（同一次运行）：`minor=5330`、`alloc_young_mb=12814.1`、**`minor_pause_ms=208.51`**、`major=0`。

**判断一：不是"回收变慢"** —— 整个运行里**收集器暂停合计 208.51 ms**，占 80 s 的 **0.26%**；`major=0`；分配器内部时间 26.61 s（14%）。耗时在**解释执行本身**：`:op/atos`（52.6%）与 `:op/add_s`（41.8%）合计 94%，就是这条用例每步构造 48 个字符串的活。

**判断二：不是"负载变重"** —— 同一条用例的输出 `gc_soak total=9576131` 与分配量 `alloc_young_mb=12814.1` 都没变；用例文件自 2026-10-28 只改过一处**括号**（`0..48->map` → `(0..48)->map`，`25a29bab7`，那次提交自己写着"两边打印的图相同"）。

**② 同一个计划内部的比例，把"机器"和"代码"分开了**（今天同一次 `--jobs 1` 运行，四条左右对照它们的预算基线读数）：

| 条目 | 每次运行的程序数 | 基线读数（计划里记的） | 今天 | 倍率 |
|---|---|---|---|---|
| `collfuzz.many_small` | 3200 个小程序 | 90.76 s | 161.52 s | **1.79×** |
| `collfuzz.large` | 960 | 60.24 s | 91.33 s | 1.52× |
| `collfuzz.gc` | 720 | 68.46 s | 84.25 s | 1.23× |
| `collfuzz.gc_large` | 108 个大程序 | 78.52 s | 82.21 s | **1.05×** |

**倍率随"每个程序的计算量"单调下降**（程序越小、启动与编译占比越大，涨得越多）⇒ 涨的是**每个进程的启动/编译段**，不是执行段；这与 `startup.cost`（它量的正是"每个命令的整进程 CPU"）自己 +8–9% 是同一件事。而 `gc_soak` 那条是**执行段**涨了 1.9 倍（见 ①，字符串算子）。

**③ 这台机器现在是共享的**：32 线程上同时跑着别的 worktree 的套件（本会话期间 `pgrep` 至少三条 `run-tests.mjs` 在跑）。**CPU 时间不像墙钟那样随负载漂移——但它在 SMT 兄弟争用与 LLC 压力下会涨**：同一条指令流在争用下退役得更慢。这解释了"倍率 1.05×–1.90× 各不相同"而不是所有条目同倍率。

## 两条路与代价

**A. 修性能**（把三条拉回预算内，预算不动）

- 代价：**`gc_soak` 那 1.9 倍可能是一个真回归**（执行段整体变慢，不是 GC），要有人沿着 `:op/atos`/`:op/add_s` 的路径查（字符串构造、分配、VM 分派），时间未知；
- `collfuzz.many_small` 与 `startup.cost` 的那一段落在**编译/启动**上——要修就是"每个进程的编译变快"，那是另一条线（预编译、缓存、减声明量），同样时间未知；
- 风险：如果 1.9 倍主要是机器争用（见 ③），A 会**查空**：花掉时间，读回来的仍是 1.9 倍。

**B. 按今天的机器重新定价**（把三条预算抬到今天的读数之上）

- 代价：**承认这三条界写在更安静的机器上**。对 `startup.cost` 尤其刺眼——它的预算本来就只留 `1.08x`，在一台 32 线程共享主机上，"预算 = 单次读数 ×1.08" 这件事**本身**就把共享负载的方差写成了界；
- 但 B 有一个**记录上不可逆**的后果：**"变慢"从此变成"通过"**，而且是三条一起——`gc_soak` 那 1.9 倍若是真回归，B 之后没有人会再看它。

## 默认

**按 A 走**：**这三条是单跑（`--jobs 1`）都超的，不是"今天的机器挤"能解释掉的**。今晚已有一条判词「抬预算不是放宽断言」，与之配套的另一条是「改了预算就等于把缺陷记成通过」。

**分两段做 A**（把代价压在能兑现的部分）：

1. **先证执行段的 1.9 倍**：同一台机器、同一份二进制，在**没有别的车道跑**的窗口里重测三次 `gc_soak_long.generational`。若仍是 1.9 倍 ⇒ 真回归，开一条腿查 `:op/atos`/`:op/add_s`；若回落到 ~1.2 倍 ⇒ 记成"争用敏感"，进 B 但不改预算，而是在页里留读数。
2. **启动段**：`startup.cost` 与 `collfuzz.many_small` 的 +8–9% / +75% 都落在每个进程的编译与启动上，值得单独量一次"一个 `.cml` 从进程启动到执行完毕"的分段（`std::profile` 已经能给出 `parse/declare/compile/gir/encode/pass` 的分段），把"涨在声明/解析还是执行"定下来之后再谈修法。
