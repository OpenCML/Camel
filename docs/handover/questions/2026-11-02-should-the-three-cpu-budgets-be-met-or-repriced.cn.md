# 三条 CPU 预算是真超（单跑仍超 0.1%–19%）：修性能，还是按今天的机器重新定价

## 问的是什么

`test/plans/perf` 里三条按 **CPU 时间**（不是墙钟）定的预算，今天**单跑**也超，而且没有任何竞争负载：

| 用例 | 预算 | 单跑读数（`--jobs 1`，各自两次干净运行） | 超 |
|---|---|---|---|
| `startup.cost` | `17.50 s` | `17.68` / `17.74` / `17.52` s | +1.0%–1.4%，第三次 **+0.1%** |
| `collfuzz.many_small` | `151.00 s` | `161.52` / `162.49` s | +7.0% / +7.6% |
| `gc_soak_long.generational` | `70.00 s` | `83.18` / `83.45` / `80.03` s | +19% / +19% / +14% |

**三条都不改预算**（今晚的判词：改预算等于把缺陷记成通过）。要你裁的是：这三条**该怎么办**。

## 三条各自的账本（预算是怎么定出来的）

- `startup.cost`：计划里写着「**a single-run CPU reading with the smallest headroom above it: 16.22 s** measured … rounded up to the next 500 ms — **1.08x**」。即预算 = 当时的读数 × 1.08。今天读 17.5–17.7 ⇒ 比当时的读数高 **8–9%**。
- `collfuzz.many_small`：预算是 `1.63x` 该条最高读数（`90.76` / `90.72` / `92.62` s，三次窗口）。今天读 161–162 ⇒ 是当时读数的 **1.75–1.79 倍**。
- `gc_soak_long.generational`：预算是 `1.63x` 的 `42.17` / `42.36` s。今天读 80–83 ⇒ 是当时读数的 **1.9 倍**。

## 取到的证据（不是猜）

**① `gc_soak_long.generational` 的 profile（`std::profile report=true`，今天这棵树）：**

```
run 190.15 s   allocations 498020254 calls, 732.57 MiB requested, 26.61 s inside the allocators
operators (share of operator time)
  cpu  :op/atos        194000097 calls   59.10 s   52.6%
  cpu  :op/add_s       290000145 calls   46.92 s   41.8%
  cpu  :struct/len_str  98000049 calls    3.87 s    3.4%
  cpu  :struct/range     2000002 calls    2.48 s    2.2%
```
分配器统计（同一次运行）：`minor=5330`、`alloc_young_mb=12814.1`、**`minor_pause_ms=208.51`**、`major=0`。

**判断一：不是"回收变慢"** —— 整个运行里**收集器暂停合计 208.51 ms**，占 80 s 的 **0.26%**；`major=0`；分配器内部时间 26.61 s（14%）。耗时在**解释执行本身**：`:op/atos`（52.6%）与 `:op/add_s`（41.8%）合计 94%，就是这条用例每步构造 48 个字符串的活。

**判断二：不是"负载变重"** —— 同一条用例的输出 `gc_soak total=9576131` 与分配量 `alloc_young_mb=12814.1` 都没变；用例文件自 2026-10-28 只改过一处**括号**（`0..48->map` → `(0..48)->map`，`25a29bab7`，那次提交自己写着"两边打印的图相同"）。

**② 同一个计划内部的比例，把"机器"和"代码"分开了**（今天同一次 `--jobs 1` 运行，四条左右对照它们的预算基线读数）：

| 条目 | 每次运行的程序数 | 基线读数（计划里记的） | 今天 | 倍率 |
|---|---|---|---|---|
| `collfuzz.many_small` | 3200 个小程序 | 90.76 s | 161.52 s | **1.79×** |
| `collfuzz.large` | 960 | 60.24 s | 91.33 s | 1.52× |
| `collfuzz.gc` | 720 | 68.46 s | 84.25 s | 1.23× |
| `collfuzz.gc_large` | 108 个大程序 | 78.52 s | 82.21 s | **1.05×** |

**倍率随"每个程序的计算量"单调下降**（程序越小、启动与编译占比越大，涨得越多）⇒ 涨的是**每个进程的启动/编译段**，不是执行段；这与 `startup.cost`（它量的正是"每个命令的整进程 CPU"）自己 +8–9% 是同一件事。而 `gc_soak` 那条是**执行段**涨了 1.9 倍（见 ①，字符串算子）。

**③ 这台机器现在是共享的**：32 线程上同时跑着别的 worktree 的套件（本会话期间 `pgrep` 至少三条 `run-tests.mjs` 在跑）。**CPU 时间不像墙钟那样随负载漂移——但它在 SMT 兄弟争用与 LLC 压力下会涨**：同一条指令流在争用下退役得更慢。这解释了"倍率 1.05×–1.90× 各不相同"而不是所有条目同倍率。

## 校准对照：把"机器多挤"和"它自己变慢"分开

"找个安静的窗口"在这台机器上不成立（同一时段至少三条别车道的 `run-tests.mjs` 在跑），所以改用**同窗口校准对照**：每轮里先跑两个**成本固定**的校准用例，再跑 `gc_soak`，用**比值**当读数——机器越忙，两条一起慢，比值不动。

校准用例：`fib` = `test/cases/perf/gc/fib.cml`（**不分配**，纯递归算术）`--arg n=36 std::fvm`；`alloc` = `test/cases/perf/gc/alloc_small.cml` `--timeit std::nvm/10 --arg reps=200000`（**纯分配**，计划里 `gc_timeit_cycles.generational` 的同一条命令，基线可考）。

三轮，CPU 秒（`user + sys`），同一份二进制：

| 轮 | `fib`（校准·算） | `alloc`（校准·分配） | `gc_soak` | `soak/fib` | `soak/alloc` |
|---|---|---|---|---|---|
| 1 | 3.31 | 4.64 + 0.07 | 79.53 + 0.28 | 24.04 | 16.95 |
| 2 | 3.34 | 4.67 + 0.09 | 79.52 + 0.21 | 23.89 | 16.75 |
| 3 | 3.25 | 4.63 + 0.04 | 77.99 + 0.03 | 24.07 | 16.71 |
| 均值 | **3.31** | **4.71** | **79.19** | **24.00** | **16.80** |
| 离散 | ±1.2% | ±1.0% | ±1.5% | ±0.4% | ±0.8% |

**历史比值（用计划里记的基线两个数算）**：`42.17 / 3.22 = 13.10`，`42.36 / 3.21 = 13.19` ⇒ **≈13.15**。

**结论**：

- **`gc_soak / alloc`：今天 16.80，基线 13.15 ⇒ 涨 1.28 倍（+28%）**。**只有这个数配说"它自己变慢了"**——同窗口的分配校准用例也慢了（4.71 对基线 3.22，**1.45 倍**），那部分是机器/微架构的因子，比值把它约掉了。
- **`gc_soak / fib`：今天 24.00，±0.4%**。**`fib` 没有记录过的基线，所以这个比值没有历史对照**，只能说：**今天在这台机器上，`gc_soak` 比一条固定成本的纯算术循环慢 24 倍。**
- 也就是说：**1.9 倍里约 1.45 倍是这台机器（连纯分配微基准都慢了 45%），剩下约 1.28 倍是 `gc_soak` 这一段自己的。** 前者可以用"预算按更安静的机器核定"解释，**后者不能**。
## 这 +28% 为什么没能定到一次提交（用比值二分，起不来）

判据是 `soak/alloc` 的比值（基线 13.15，今天 16.80，good 取 ≤14.5，bad 取 16.80）。**起不来，两个原因都记在这里**：

- **窗口 4568 个提交**：`gc.plan.toml` 最后一次改动是 `e7629168b`（2026-10-26），它的基线数就是那前后取的 ⇒ 可信的 good 点最早也只能取到那里，`git rev-list --count e7629168b..HEAD` = **4568** ⇒ 比值二分要 **≥12 步**，每步一次重建（约 12 分钟）+ 两条测量 ⇒ **约 2.4 小时**，超过"超过两小时就改用粗定位"的门限。
- **粗定位也缺基线**：`:op/atos` 今天 **304.6 ns/次**（59.10 s / 194,000,097 次）、`:op/add_s` **161.8 ns/次**（46.92 s / 290,000,145 次），但树里**没有任何历史单次成本**可比。

**零重建能排除的，已经排除了**（`git log -L` 每条热路径，都落在基线**之前**）：

- `__atos__`（`src/builtin/operators/cast.cpp`）最后一次改动 **2026-10-11**（`209299931`）；
- `__builtin__add_ss__`（`src/builtin/operators/ops.cpp`）最后一次改动 **2026-01-27**（`5ebffd27c`）；
- `String::from`（`include/camel/core/rtdata/string.h`）最后一次改动 **2026-03-07**（`0d387b5e1`）。

⇒ **这 1.28× 不在字符串算子自己的函数体里**。它在这三条路径**之外**：VM 的分派/帧操作（190 s 里约 57 s 落在操作符之外的 `run` 里），或**每次分配的开销**（分配器内部 26.61 s，498,020,254 次 ⇒ 约 53 ns/次；而纯分配校准自己就慢了 1.45 倍）。

**要真的定到一笔，需要**：① 一个**记录过的**历史单次成本（`atos`/`add_s`/分配各一条），或 ② 一台能跑 `perf` 的机器（这台 `perf_event_paranoid=4`、`ptrace_scope=1`，采样 60 次得 0 行），或 ③ 把 12 步重建的时间批下来。三者都没有，就只能停在这里，而不是拿一个猜测当提交号。

**而那一笔自己的证据是 18 次**：它的提交信息写着"the 3,000,000 element loop allocates **18 times** and the

**一句判断（③）**：**1.28× 与"分配慢 45%"是同一族，但不是一件事**——
- 45% 是**纯分配微基准**自己慢掉的那份，用比值约不掉，所以它**可能**是机器也可能是分配器；
- **1.28× 只存在于比值里 ⇒ 机器因子已被约掉 ⇒ 那部分只能是代码**，而且就在分配路径上；

**这一步已经做过，结果是"不动"**：把那 3 处 `GUARD`（`free_list.h:51/60/61`）临时改回 `ASSERT`、重建、同窗口测三次（实验期间只跑 `alloc` 与 `fib`，`fib` 作窗口刻度）：

**⇒ 差 0.6%，在噪声内：这 3 处 `GUARD` 不是那 45%，也不是那 1.28×。** 实验后已把那 3 处**改回 `GUARD`**（`git checkout` 复原，`git diff` 为空），并在复原后的树上重建、确认 `out/latest/libs/libcamel.so` 里 `Unaligned free block` 与 `Camel Invariant Violation` 各 1 条——**检查还在，没把它当修法**。

**真正的原因在"缝"里**：`2c1a7b6c4` 与 `1de967a2a` 在我的 `--no-merges` 列表里相邻，但它们之间隔着 **353 笔提交**（`git rev-list --count 2c1a7b6c4..1de967a2a` = 353，含整条合并进来的车道：`c7acbf856 Merge origin/develop (05bf41f24) into lane-gs6 …`）。**`--no-merges` 的列表不是一条线性次序**，相邻两项可以是几百笔之遥 ⇒ 我上一轮"36→37 平、38 跳"的读法把两个相距 353 笔的树当成了相邻。

## 两条路与代价

**A. 修性能**（把三条拉回预算内，预算不动）

- 代价：**`gc_soak` 那 1.9 倍可能是一个真回归**（执行段整体变慢，不是 GC），要有人沿着 `:op/atos`/`:op/add_s` 的路径查（字符串构造、分配、VM 分派），时间未知；
- `collfuzz.many_small` 与 `startup.cost` 的那一段落在**编译/启动**上——要修就是"每个进程的编译变快"，那是另一条线（预编译、缓存、减声明量），同样时间未知；
- 风险：如果 1.9 倍主要是机器争用（见 ③），A 会**查空**：花掉时间，读回来的仍是 1.9 倍。

**B. 按今天的机器重新定价**（把三条预算抬到今天的读数之上）

- 代价：**承认这三条界写在更安静的机器上**。对 `startup.cost` 尤其刺眼——它的预算本来就只留 `1.08x`，在一台 32 线程共享主机上，"预算 = 单次读数 ×1.08" 这件事**本身**就把共享负载的方差写成了界；
- 但 B 有一个**记录上不可逆**的后果：**"变慢"从此变成"通过"**，而且是三条一起——`gc_soak` 那 1.9 倍若是真回归，B 之后没有人会再看它。

## 默认

**按 A 走**：**这三条是单跑（`--jobs 1`）都超的，不是"今天的机器挤"能解释掉的**。今晚已有一条判词「抬预算不是放宽断言」，与之配套的另一条是「改了预算就等于把缺陷记成通过」。

**分两段做 A**（把代价压在能兑现的部分）：

1. **先证执行段的 1.9 倍**：同一台机器、同一份二进制，在**没有别的车道跑**的窗口里重测三次 `gc_soak_long.generational`。若仍是 1.9 倍 ⇒ 真回归，开一条腿查 `:op/atos`/`:op/add_s`；若回落到 ~1.2 倍 ⇒ 记成"争用敏感"，进 B 但不改预算，而是在页里留读数。
2. **启动段**：`startup.cost` 与 `collfuzz.many_small` 的 +8–9% / +75% 都落在每个进程的编译与启动上，值得单独量一次"一个 `.cml` 从进程启动到执行完毕"的分段（`std::profile` 已经能给出 `parse/declare/compile/gir/encode/pass` 的分段），把"涨在声明/解析还是执行"定下来之后再谈修法。

## 结论句

**三条的成因不同，不能用一次重定价一起处理。**

- `startup.cost`（预算只留 `1.08x`、量的是整进程 CPU）**最像"界写错了"**：它是三条里唯一一条把"单次读数 ×1.08"当界的，而共享主机上那 8% 就是方差本身；
- `gc_soak_long.generational` **最像"真回归"**：校准对照说它有 **+28%** 是比值里约不掉的，而 GC 只占 0.26%；
- `collfuzz.many_small` 落在**每个进程的启动与编译段**（1.79×，且随每程序计算量单调），既不是"界写错"也不是"执行回归"，是**第三条成因**。
