# 交接任务书

本文件说明如何接手工作和报告结果，不是历史任务清单。当前优先级见 [`docs/roadmap.cn.md`](../roadmap.cn.md)；语义以 [`docs/design-principles.cn.md`](../design-principles.cn.md) 为准。

## 1. 开工前阅读

按顺序阅读：

1. `AGENTS.md` 与 `agents/` 下的工程规则。
2. `docs/design-principles.cn.md`。它与代码、测试或其他文档冲突时，以它为准；未决问题交给语言作者，不自行裁定。
3. `docs/roadmap.cn.md`，确认当前顺序和依赖。
4. 与任务相关的设计稿及 `reviews/` 中的最新裁定。

判断现状时看当前代码、测试计划和实际运行结果，不看旧报告中的“今天”“目前”“已完成”。引用代码时使用 `path/file.cpp#Symbol`，不要依赖行号。

## 2. 这个目录放什么

- `reviews/`：语言作者及决策者的裁定和检查意见。按主题查阅，不需要顺序通读。
- `questions/`：仍待回答的问题，一页一问。已回答的页移入 `reviews/`，不要留下重复副本。
- `reports/`：过程报告和当时的测量。它们是历史证据，不是当前状态，也不是施工队列。
- git notes（`refs/notes/handover`）：部分报告的原文及验收记录。看板或提交中的 `note ⟨sha7⟩` 指向 `git notes --ref=handover show <sha>` 的参数。

历史提交本身就是最可靠的档案。不要因为旧页面仍在树里，就把其中的任务再实施一遍。

## 3. 分支与集成

- 从最新的 `origin/develop` 建 feature 分支，不直接在 `main` 上开发。
- 不额外创建 worktree，除非用户明确要求。
- 合并按代码区域串行进行，使用 `git merge --no-ff`。每条工作线先说明净改动、冲突和验证结果，再集成。
- 不并行执行会修改 Git 状态的命令。出现意外状态时先停下核对，不根据假设继续。
- 不改写共享历史，不强制推送共享分支。自己的未发布工作线需要整理时，按 `agents/branching.md` 的规则处理。
- 删除分支前保留 `archive/<name>` 标签。探针、负责人专用引用和仍被工作树使用的分支不能按普通已合分支处理。

## 4. 构建与测试

本机不做 C++ 构建；构建和测试统一经 `internal/tools/camel-remote.ps1` 在 Linux 主机上运行：

```powershell
pwsh -NoProfile -File internal/tools/camel-remote.ps1 -Path <worktree> -Plan <plan-file-or-directory> -Jobs 8
```

- 开发中跑与改动相关的计划，先手动观察真实命令行的 stdout/stderr，再固化断言。
- 收尾跑 `smoke` 和 `feat/**` 的快速层。慢测试、GC 压力、投毒扫描、随机程序和性能测试只在里程碑或相关改动需要时运行。
- 报告写清测试目标、层级、总数、通过、失败、跳过和已知失败。`skip` 不算失败，`known_fail` 不是免检名单。
- 修改诊断时同步 `diagnostics/registry.tsv` 和生成文档；修改问题页时用 `node scripts/check-doc-links.mjs --questions-index --write` 重建索引。
- 提交前运行 `node scripts/check-doc-links.mjs --all` 和 `node scripts/check-std-includes.mjs`。

详细规则见 `agents/test.md` 和 `docs/test-plans.md`。

## 5. 结果报告

报告只写结论，不写逐小时施工日志，也不把原始输出整段搬进文档。内容应覆盖：

- 做了什么，以及关键设计选择及理由。
- 用户可见的行为变化，必要时给一个前后对照。
- 测试目标、结果和覆盖的后端。
- 待裁问题、未完成的半边和下一步入口。

篇幅与改动相称，通常不超过 60 行。过程测量放在提交信息或约定的 handover note 中，不另建账本、计数表或“再确认一次”的守卫。现行文档只保留规则和结论。

## 6. 待裁问题

**任何时候都不停下来等人回答**（负责人 2026-11-14：协调者问他问题，他没看到，施工因此堵死）。问题只写成 `questions/` 里的一页，由决策者答，不在会话里直接问负责人；写完问题页，同一轮就切到不依赖这个问题的工作：同一路的下一步，或第十一节里别的路。决策者每半小时检查一次，会当轮答复；涉及原则的由决策者转给负责人。一时找不到不受影响的工作，就做第十一节第 1 路和第 7 路，它们任何时候都有活。

用户可见行为、语法、类型规则、诊断种类发生变化而规范没有答案时，在 `questions/` 写一页：

1. 问题和最小例子。
2. 可选方案及各自代价。
3. 倾向及理由。
4. 被挡住的工作，以及不依赖裁定的下一部分。

可以继续做不受影响的实现工作，但不要把默认建议写成已经裁定。答复后将页面移入 `reviews/` 并重建索引：

```powershell
node scripts/check-doc-links.mjs --questions-index --write
```

## 7. 提交前自查

- 核心和通用层不按模块名、算子名写特例；使用声明、属性、资源或语义机制。
- 同一事实只有一个来源，其他位置读取它或由它生成。
- 不另造平行机制、兼容层或过渡写法；需要删除的旧写法直接删除。
- 新值或节点在每个后端都能执行，或者在不支持的位置给出带位置的明确拒绝。
- 不通过改期望、加跳过或 `known_fail` 掩盖行为变化。每一处期望变化都能解释。
- 注释和文档描述当前规则与理由，不写任务编号、施工日期、机器路径或已经过时的过程。
