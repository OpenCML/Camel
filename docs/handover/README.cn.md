## 1. 工作流程

### 1.1 分支与工作树

- 工作树是 `D:\Projects\Camel-wt\<任务>`；分支从最新的 `origin/develop` 开，名字是 `handover/<任务编号>`，如 `handover/H1-enum`。
- **只推送你自己的 `handover/...` 分支**：`git push origin handover/H1-enum`。不推送、不修改 `develop`、`main` 或别人的分支；不强制推送（`--force`）；不改写已推送的历史。`fsh-dev` 是决策者的评审分支，它只被合入 `develop`；我们的工作不经过它。
- 需要同步时，把 `origin/develop` **合并**进你的分支（`git merge origin/develop`，合并提交），不要变基已推送的分支。
- 一个任务一个分支。任务很大时可以分几次推送，每次都能编译、相关测试通过。
- 审查通过后，由施工方协调者把你的分支合并进 `develop`（`--no-ff`）。你不需要也不应该自己合并。

### 1.2 构建与测试

- **不在本机构建**：本机跑构建会蓝屏。构建与测试都在 Linux 主机上，经 `D:\Projects\Camel-wt\camel-remote.ps1` 走（它把工作树送过去、排队取一个构建位、把退出码带回来）：
  `pwsh -NoProfile -File D:\Projects\Camel-wt\camel-remote.ps1 -Path D:\Projects\Camel-wt\<任务> -Plan <计划文件或目录> -Jobs 8`。
  产物在主机 `out/latest/bin/`。不要在本机跑 `npm run build`、`cmake` 或 `node scripts/test.js`。
- 测试分两层（H10）：日常与合入前跑 `fast` 层（`smoke` 加 `feat/**`）；慢层（PyTorch 对照、GC 压力、投毒扫描、性能基准）只在发布前，或改动确实触及 GC、内存管理、数值内核时按需跑。
- 只跑某个目标时：**目录**目标默认只跑 `fast` 层，要看慢测试加 `--tier all`；直接点名**计划文件**则整个计划都跑（点名就是意图）。`--changed` 的基线默认 `origin/develop`，可用 `CAMEL_TEST_BASE` 覆盖。分层规则见 `docs/test-plans.md`。
- **先手动跑，再写测试**（`AGENTS.md`）：新功能先在主机上用 `camel x.cml` 看清输出与诊断，再把确认过的行为写成测试。
- 工作中只跑相关的测试计划；**任务结束前在主机上跑一次快速层**（`smoke` + `feat/**`）与相关计划。
- **验收**：快速层必须全绿；`skip` 不是失败；基线是零——没有“已知失败名单”，任何一条红都要由变红的分支解释。
- 改了语法、`test/cases/parse` 下的用例或 `test/tools/parsecheck/probes.py`：在主机上更新 AST 快照 `python3 test/tools/parsecheck/check.py snapshot --update`。快照只含解析用例与探针（H188），改 `examples/`、`stdlib/`、`benchmarks/` 或别的计划的用例不会再动它。
- 改了诊断：`node scripts/diagnostics-catalog.mjs --write`。
- 每次提交前：`node scripts/check-doc-links.mjs --all`、`node scripts/check-std-includes.mjs`。

- 提交信息用英文，与仓库现有风格一致（`feat(...)`、`fix(...)`、`refactor(...)`、`docs: ...`）。

## 2. 提交前的自查清单（退回最多的问题）

这些都是 2026-10-19 审查中实际发现的问题，每一类都有真实例子。

1. **核心按名字认具体的东西。** 编译器、核心、遍里出现 `if (name == "numeric")`、`uri == "tree:tree_map"`、写死的算子/模块/类型名单。反例：`@numeric(...)` 在构建语法树时比较字符串；参数树操作在建图器里按 URI 展开。**正确做法**：用已有的通用机制（算子表与它的特性、语义声明、资源声明、装饰器、模块注册的接口），按声明的性质判断，不按名字。
2. **另造一套相似的机制。** 已有装饰器却另做一种 `@name(...)` 标注；已有原生子图调用服务，却在每个后端各写一遍高阶算子。**正确做法**：先找现有机制能否承载；不够就扩展它，不要平行再造。
3. **同一事实写在多处。** 效应既看资源声明又看签名里的 `var` 又按 URI 前缀猜；"什么是叶子"写了七份且已不一致；算子签名写在三处。**正确做法**：一个事实只有一个来源，其余处读它或由它生成。
4. **写死的上限与封闭的枚举。** 8 位的位掩码已经用满、写死的常量（应当可调的上限）。**正确做法**：可以增长的东西不用固定位宽；上限做成可配置。
5. **临时裁定语义。** 设计原则没写的行为，凭感觉定一个。**正确做法**：按第 4 节提问。
6. **为了让测试通过而改。** 改期望输出掩盖行为变化、跳过测试。**正确做法**：期望输出的每处变化都要能解释，并写进报告。
7. **兼容层与过渡方案。** 语言作者明确不要"乱七八糟的兼容"。旧写法要删就直接删干净：不留别名、过渡层，也不加"已退役，请改用 X"之类的诊断或说明；删除后它就是普通的未知名字或语法错误。
8. **只做一个后端。** Camel 有 `std::nvm`、`std::fvm`、`std::jit`、并行调度器 `std::prl`、宏求值器 `std::macro`、C++ 导出 `std::cpp`，还有 ONNX 导出与自动微分。新的值或节点要在每一处都能运行，或者在不支持的地方给出带位置的明确拒绝。测试要覆盖多个后端（看现有测试计划如何对多个调度器跑同一程序）。

## 3. 结论放在哪里

- **你的报告**：不要写进树，也不要单独提交一个报告文件。把全文（≤ 60 行，模板见下）作为最后一条消息交给协调者；协调者用 `git notes --ref=handover add -F report.md <引入提交>` 把它挂成 note，看板上只留一行。模板：

  ```markdown

  ## 设计上的选择
  （每个技术选择：选了什么、为什么、考虑过的其他做法）
  ## 用户可见的变化
  （每条配一个前后对比的例子；期望输出改了哪些、为什么）

  全套：总数 / 通过 / 失败；新增失败（应为零）；新增测试列表；覆盖了哪些后端
  ## 自查（第 2 节逐条）

  （第 4 节格式）
  ## 没做完的
  ```

- **决策者的检查意见**：写在 `fsh-dev` 上的 `docs/handover/reviews/<任务编号>.md`。开始下一步前先 `git fetch` 看有没有新的检查意见；有"退回"条目时先改完再继续。

## 4. 遇到不确定的语义怎么办

- **语义问题**（用户能看到的行为、语法、类型规则、错误的种类）不要自己定。写进报告的"待决问题"，格式：

  ```markdown
  ### Q<n>：一句话的问题
  例子：（一段 Camel 代码，以及两三种可能的结果）
  建议：（你倾向哪个、为什么）
  影响：（不定下来会挡住什么）
  ```

  然后**跳过被挡住的那部分**，继续做不受影响的部分。
- **技术选择**（数据结构、文件组织、算法）可以自己定，写进报告的"设计上的选择"。
- 判断一件事是语义还是技术：如果换一种做法，用户写的同一个程序会得到不同的结果、不同的诊断或不同的语法，就是语义。

### 5.04 H225 等价图的可视化（决策者 2026-10-22，负责人要求）

今天多写法（等价图）只能经测试遍的文字输出看到：`std::gir` 等转储遍不接受多写法，驱动在它们之前先抽取。要让用户像看 `std::gir` 那样看等价图：

1. **`std::opt::saturate`**：标准规则库饱和、不抽取的遍（参数 `rounds`、`strict`），让程序停在多写法状态。
2. **转储接受多写法**：`std::gir`/`std::rgir`（Graphviz）在多写法状态下把每个等价类画成一个虚线框（cluster），类里的每种写法是一个节点，写法的输入边指向输入所属的类（与 egg 的 `dot` 输出同一画法）；标出抽取会选中的写法（按当前代价）。`std::jgir` 同样带上等价类。
3. **导出 `egraph-serialize` 的 JSON**（`std::egraph`，或 `std::jgir` 的一个参数）：社区的 `egraph-visualizer` 等工具可以直接打开交互查看。
4. 用法写进 CLI 文档：`camel f.cml std::opt::saturate std::gir`；一个用例锁住 `x * 2` 与 `x + x` 同类时的输出。
5. 不改多写法的数据结构，只加读取与转储。

### 5.05 H226 规则库与旧 C++ 代数遍的对照测量（决策者 2026-10-22，负责人要求）

负责人问：Camel 写的规则库替换 C++ 定律表之后，优化能力与速度相比如何。现有证据只有计数语料（H65/H100：多重集相同或更好）与固定成本（H169：每次 `std::opt` 编译 `rules` 约 22 ms），没有同一负载上的速度对照。做一次对照，结论写成一页：

1. **两个构建**：删除 C++ 定律表之前的提交（`a510676bb` 的父提交）与当前树，同一台机器、同一负载。
2. **负载**：H65/H87 的元素与张量语料；C2 与 `transformer_step` 的训练步图；按 1k、10k、100k 节点生成的算术图（`progen` 或 H39 的 24000 节点负载）。
3. **量什么**：`std::opt` 的总时间拆成"加载规则库（parse/gct/声明）"与"改写本身"；改写后的节点数与算子多重集；`std::opt::saturate`（H225）每轮的写法数与时间。
4. **另量一个方案（负责人 2026-10-22）**：规则集作为语义保留在 Camel，执行时用"编译好的匹配器"——构建标准库时把 `stdlib/rules.cml` 编译成匹配自动机（或经 `std::cpp` 生成 C++），装进模块缓存；运行时不再解析规则库、也不解释执行模式。给出它相对现状与旧 C++ 的预估或原型数字。这是 10.4 "Camel 定义 + 原生实现"在规则上的形态，先量，`#impl` 在函数上证明可行后再决定是否实施。
5. **结论**：能力（哪些图更好、哪些更差，原因）；速度（固定成本与随图规模的增长，各自与旧 C++ 相比的倍数）；若改写本身慢于旧实现一个数量级以上，给出瓶颈（匹配、并查集、提交）与改法。固定成本的去除走设计原则 10.3 的 `.cmc` 缓存，本项只量不做。

### 5.06 H227 用 Camel 写编译器自己的遍：表达能力的证据（决策者 2026-10-22，负责人要求，列入主线）

负责人的立场：性能上，结构性的遍留在 C++ 是对的；但需要证据证明 Camel 原生的语言与图 API 足以写出这些遍。做法是**双实现**——默认流水线仍用 C++，同时在标准库里给出 Camel 实现，用同一套语料证明两者结果相同：

1. **库 `opt`（`stdlib/opt.cml`，Camel 写，经 `graph` 模块）**，按难度分三层，逐层落地：
   - 第一层：`opt::dce`、`opt::cse`、`opt::fold`（折叠调用算子求值）、`opt::ctrl`（控制边约简）。
   - 第二层：`opt::inline`（含增长预算与内联历史）、`opt::specialize`。
   - 第三层：`opt::vjp`——反向模式自动微分的一个子集（逐元素、矩阵乘、归约、循环区域），对照 `autodiff` 的结果。
   - 第四层（负责人 2026-10-22 同意）：**用 Camel 重写 ONNX 导出**（目标算子、降低规则、按目标支持抽取，规则语言第二版 8.9、8.11），与 C++ 导出的模型逐个对照；**改写执行器**（标准库 `semantics`：操作语义写成规则，`rewrite` 到范式即执行），与 nvm、fvm、jit、`std::cpp` 做差分测试。性能不作要求。
2. **差分验证**：每个 Camel 遍与对应的 C++ 遍在 `test/cases` 的优化语料上各跑一次，结果用 `std::cml` 的等价检查器（S0）判定**图同构**；数值结果在四个后端一致。不同构的每一处要么是 Camel 版本的缺陷，要么是 C++ 版本的缺陷，逐条结论。
3. **缺口即任务**：写不出来或写得别扭的地方（缺少的图操作、类型表达不了的结构、只能绕路的写法）逐条记下，优先补进语言或 `graph` 模块，而不是在库里绕过去。这是本项最重要的产出。
4. **一页结论**：每个遍的 Camel 行数与 C++ 行数、同构率、速度比（同一负载），以及补进语言的缺口清单。速度不作门槛。
5. 用法：`camel f.cml 'opt::cse'` 与 `std::opt::cse` 可以互换。这与 10.4 的 `#impl` 是同一个关系：Camel 遍是语义与参考，C++ 遍是实现；`#impl` 在函数上证明可行后，推广到遍（Camel 遍标出实现它的 C++ 遍）。文档的"编译器内部"一节以 Camel 版本作为可读的参考实现。

### 5.07 H228 标准库按 10.4 审计与迁移（决策者 2026-10-22，负责人同意）

依据设计原则 10.4（新改）。

1. **审计**：每个原生算子与每个标准库函数归入三类之一——原子算子、Camel 定义、Camel 定义加 `#impl`。属于组合却写成 C++ 的迁回 Camel；需要快路径的改成 Camel 定义加 `#impl`；原子算子补齐语义声明。审计表一页，随迁移一起交。
2. **`#impl` 机制**：带函数体的函数可标 `#impl<f>`，`f` 是本模块一条私有的无体声明（原生内核），签名必须与函数相同；普通遍与执行器把它当一个算子（不内联），自动微分、融合、导出与规则按需展开函数体；差分测试锁住两者一致。H64 的 Adam 是第一个用户（`optim` 用 Camel 定义，H64 的内核作快路径）。
3. **语言缺口**：泛型实例里的字面量按实例化后的类型取型（`acc: T` 处的 `0` 成为 `T`），之后 `array::sum` 只留一个泛型定义。
4. **`stdlib/array.cml` 的具体问题**：`all`/`count` 用 `loop … for … while` 写（不经中间数组、可提前结束）；`min`/`max` 用 `math::min`/`math::max` 归约，NaN 与 ±0 遵守 7.7；`sum`/`min`/`max`/`all`/`any`/`count` 在数值数组上配归约内核（求和顺序遵守 `reassociate`，`#strict` 退回顺序折叠）。
5. **验收**：一个大量使用这些函数的程序，编译时间与执行时间与改动前对照（不得变慢），数值数组上的 `sum`/`min`/`max` 与张量归约同速。
6. **声明的样板（负责人 2026-10-22 指出）**：
   - **按类型分名的执行器合到一个算子下**：`math` 的 `abs_i`/`abs_l`/`abs_f`/… 这类，一个算子 URI（`math:abs`）登记多个按元素类型的执行器，编译期按实例的具体类型选定（不是运行时读类型，与 5.5 一致）。声明于是只写一条泛型的 `export func abs(x: T): T`，不再逐类型写 `#op`。`math` 的九十多个 `#op` 应基本消失。结果类型随输入变化的（复数的 `abs` 返回实数：`c64 → f32`、`c128 → float`）现在写成"一条泛型声明加两条固定声明"（固定签名比泛型更具体，可以同名，语言参考 7.4.3），仍挂在同一个 `math:abs` 下；泛型第二期有了类型位置的类型函数后，改为一条 `abs(x: T): Real<T>`。
   - **不透明的原生类型按身份比较**：`graph` 的 `Program`/`Graph`/`Node`/`Region`/`Op`/`Tag`/`Txn`/`TypeRef` 这类句柄，`==`、`!=` 由语言统一提供"按身份相等"，模块不再逐类型声明 `operator ==`；需要的身份编号（`id`）也只声明一次。所有模块的不透明类型同一条规则（规则统一）。
   - 删去与默认 URI（`模块:函数名`）相同的冗余 `#op`。

### 5.12 H233 遍就是函数变换（决策者 2026-10-22，负责人要求；先交计划）

负责人："我希望的就是要做普通的函数变换，这才是最直观最优雅的；作为图原生语言还要包裹来包裹去，那为啥不直接用 Python。" 设计原则 9.3 已改：**遍是 `(f: F) => F!`**，接收一个函数、返回同类型的函数，与 `with_grad` 同一类；整个程序就是根函数；`Program` 只是内部表示。

1. **`graph` 模块的公开接口以函数为中心**：`open(f: F): Txn<F>`、`commit(t: Txn<F>): F!`、`graph_of(f)`、`nodes`、`users` 等照旧；`Program`、`current()`、`root(p)`、`open_function`/`to_function`（及其样本参数）从公开接口删除。程序级的信息（声明、标签、事实、特化表）经函数所在的程序读取，接口上不出现快照。
2. **流水线**：`camel f.cml mylib::simplify std::fvm` 把遍施加在程序的根函数上；Camel 写的遍签名为 `(f: F) => F!`（泛型，`F` 自动绑定），不再是 `(Program) => Program!`。
3. **对单个函数就是普通调用**：`loss->simplify`、`loss->rules::simplify->with_grad`；不需要 `optimize<pass>` 一类的包装。捕获了值的函数（闭包）照样可以变换，捕获随新函数带上。
4. **`rewrite` 模块**同样改为函数变换：`f->saturate<rules>`、`f->extract<cost>`；`stdlib/rules.cml` 的 `simplify` 等随之改签名。
5. C++ 的遍内部仍按快照工作；只有写遍的公开接口与流水线的约定变化。规则语言第二版（v2.cn.md 8.5）已按此改写。
6. **内置的遍也是函数**（负责人 2026-10-22 追问后补充）：今天的 37 个内置遍是 C++ 的 `GraphIRPass` 子类，登记在 `src/execute/pass.cpp` 的一张表里，不是函数。改为按设计原则 10.4 的同一约定——**每个内置遍是标准库里的一条无体声明**（原生实现的函数），带类型参数、`with` 参数与默认值、`when is_function::<F>()`：
   ```camel
   // stdlib/std/opt.cml（目录随 H216 的标准库布局）
   with <safe_fp: bool = false, growth_budget: int = 4096>
   export func opt::<F>(f: F): F! when is_function::<F>()
   ```
   模块遍同样（`tiles::compile` 在 `tiles` 的声明里）。于是：流水线上的每个名字都按模块与名字解析成一个函数，**删除独立的遍注册表**；`camel inspect --passes` 就是列出这些函数；Camel 里 `f->std::opt<safe_fp: true>` 与命令行 `std::opt safe_fp=true` 是同一个调用。打印、导出、执行类遍是带副作用、给出空图的函数（`std::gir`、`std::fvm`）。
7. **与 H227 对接**：Camel 写的遍是语义与参考，C++ 是实现，两者用 `#impl` 连起来——`opt::cse` 的 Camel 定义标 `#impl<cse_native>`，默认执行 C++ 版本，差分测试保证一致（设计原则 10.4 在遍上的形态）。

### 5.13 H234 适用条件 `when`（决策者 2026-10-22，负责人同意）

设计原则 5.5 新增：函数签名后的 `when 条件` 是适用条件（编译期谓词，实例化时求值）；不成立时该重载不适用，重载选择试其他候选；全不适用时在调用处报错并列出每个候选未满足的条件。规则、函数与 `match` 分支的 `when` 同一个意思。不引入 `where`。

1. 语法与类型检查：函数签名后的 `when`；条件里可用 `::<T>` 与类型谓词；重载选择把条件纳入（先精确、后进入的顺序不变，不满足条件的候选在每一步都先剔除）。
2. 标准库的谓词：`is_numeric`、`is_integer`、`is_float`、`is_ordered`、`is_function`、`is_string` 等，用 `match type` 写在库里。
3. `match` 分支守卫 `case p when 条件 =>`（负责人 2026-10-22 确认）：条件不成立时试下一个分支；带守卫的分支在穷尽性检查中不算覆盖该形状；图上与嵌套 `if` 同一种分支结构；`fact` 的 `case` 同样可以带守卫。
4. 用上它：`array::sum`/`min`/`max`（H228/H230）、遍的签名 `(f: F): F! when is_function::<F>()`（H233）。
5. 诊断：调用处列出"候选 — 未满足的条件"；条件本身编译不过是声明处的错误。

### H3：依赖节点属性的后续

**前提**：地基"装饰器通用机制"已合并。

**H3a 优化不改变图上的算子身份**（设计原则 9.6 第五条；审查 `modules.cn.md` 第 4 条）。现在 `tensor::fuse` 会把 `matmul` 换成 `matmul_blas`，把 `matmul` 加偏置、激活换成 `matmul_add`、`matmul_add_relu` 等新算子，这些新算子没有语义声明与定义图。改为：
- 图上保留原算子（`matmul`、`add`、`relu`……），融合与库实现的选择记在节点属性上（键由 `tensor` 模块注册，如"这几个节点作为一组用某实现执行"）；执行时按属性选内核。
- 选择规则读核心的统一判定：7.3（CPU 上按库实现的 f32 矩阵乘默认可用，条件是结果可复现；安全模式下用规范算法；安全模式由遍参数给出——遍参数是地基工作的一部分，用它的接口）。现在 `matmul_blas` 要求 `reassociate` 与 `change_precision` 两项许可，按 7.3 改为默认可用。
- 删除 `matmul_blas`、`matmul_add` 等作为图上算子的注册。ONNX 导出与 Tiles 看到的是原算子。
- 测试：融合前后结果在安全模式下逐位相同；默认模式下两次运行逐位相同。

**H3a 已完成**（分支 `handover/H102-fusion-keeps-operator`，报告 note ⟨ebfc812⟩）：图上的算子保持
`matmul`/`add`/`relu`，`tensor::fuse` 只写 `tensor.kernel`（"library"/"canonical"，按 7.3 的有效许可
判定，`#strict` 与 `tensor::fuse(safe_fp=true)` 得到 canonical）与 `tensor.fusion`（"linear"/
"linear_relu"，组内每个节点都写）；`matmul_blas`、`matmul_add`、`matmul_add_relu` 的注册、内核、
VJP 与 ONNX lowering 全部删除，ONNX 导出与 Tiles 的区域分析看到的就是程序写的算子。逐位证据在
`fuse_bits`（四种运行逐字节相同）与 `gemm_canonical.fused`；安全模式下融合与不融合相同是构造性的，
因为遍不改算子、CPU 上也不换内核。

**H3b 内联来源**（图存储第二版 3.3）：内联把被调函数体放进一个标注区域，记录被内联函数与调用处，嵌套内联即嵌套区域，被内联函数的声明标签挂在区域上（设计原则 9.4 的警告据此给出）。**调试器不为内联函数虚构帧**（裁定记录 2.14 该条已撤回）：内联进来的代码显示在调用者的帧里，标注来自哪个函数、哪次调用；GIR 可视化把区域画成可展开的框。同时核实 12.1 的"从分支的臂回到汇合处时不在同一行停第二次"，写测试确认，不符合就修。区域机制本身属于图存储第二版第 5 步；若该步尚未完成，本项先不做。

### H7：资源与副作用（设计原则 3.3）

**前提**：无（与 H2 的标签工作相互独立；原生算子的资源从标签改为签名中的 `uses`）。

4. **建图**：同一函数体内同一资源的执行者之间按书写顺序生成控制边；`sync` 块的语义不变；按需执行的规则不变。
