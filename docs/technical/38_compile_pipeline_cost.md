# 编译流水线的开销

> 本文量的是实现，不涉及语义。设计原则（[`../design-principles.cn.md`](../design-principles.cn.md)）对这里的任何结论都不受影响；所有改动都以"行为不变"为验收条件（第 7 节）。

本文回答三个问题：一次 `camel x.cml <遍>` 的时间与内存花在哪里；GCT 一层重构后的前后对比；按预期收益排序，后面还应该重构什么。所有数字只在 Linux x86-64（WSL2 里的容器）上测过。

## 1. 测量设施

| 设施 | 位置 | 作用 |
|---|---|---|
| 阶段计时 | `camel --time-phases[=<file>]` 或 `CAMEL_TIME_PHASES=<file>`（不带文件时写到标准错误；文件用 `=` 连在选项上，免得把后面的程序当成输出文件）；`include/camel/utils/phase_timer.h` | 每个阶段的墙钟，可选的堆分配数，JSON 输出 |

| 基准脚本 | `benchmarks/compile/bench.py` | 固定输入集、钉核、版本交替、中位数与最小值，输出 `results.json` 与 Markdown 表 |
| 多模块工程生成器 | `benchmarks/compile/gen_modules.py` | N 个模块，形状为 flat / chain / fan |

已有的设施：`--profile` 只在 debug 构建里有效；`--timeit` 计的是单个遍；`memperf` 默认编译掉。它们都不能回答"一次运行的各阶段各花多少"，所以新加了阶段计时。`camel-parsecheck bench` 原本就能把解析拆成词法 / CST / AST 三段；基准脚本直接复用它，因为解析器内部（`src/parse/`）不在本线的改动范围内。

### 1.1 阶段报告

默认关闭。关闭时每个阶段边界的开销是读一个全局标志、走一次分支；阶段只放在整个阶段外面（一个模块、一个遍），不放在任何遍历节点的循环里。报告的格式如下：

```json
{"schema":1, "total_ns":…, "peak_rss_kb":…, "alloc_shim":true,
 "alloc":{"allocations":…, "bytes":…, "frees":…, "live_bytes":…, "peak_bytes":…},
 "phases":[{"name":"gct", "detail":"main", "depth":1, "start_ns":…, "wall_ns":…,
            "allocations":…, "alloc_bytes":…, "frees":…, "live_bytes_end":…, "peak_bytes_end":…}, …],
 "counters":{"modules":…, "ast.nodes":…, "gct.nodes":…, "graph.graphs":…, "graph.nodes":…, "graph.edges":…}}
```

`counters.modules` 数的是本次运行从 Camel 源码编译过的**每一个**模块，包括遍按需编译的库模块：H100 之后 `std::opt` 的代数阶段会编译 `stdlib/rules.cml`，它 `import math` 时又把 C++ 模块 `math` 的声明模块 `stdlib/math.cml` 一起编译（H112、H121）。所以 chain-3（`main` 加三个模块，共四个**程序自己的**模块）在带遍的流水线上是 6 个。计数器本身分不出这四与二，`gct` 阶段的 `detail` 里有模块名，`bench.py` 从它得到完整名单，并把「程序自己的模块」与「库模块」分开报告：前者是输入集的横轴，后者是流水线带出来的真实额外开销，两个数都不能消失（见第 5 节）。

各阶段的名字：

- `startup`：参数解析与运行时初始化。
- `mm_init`：建立内存空间。
- `context`：创建上下文，含 `builtin_module`（内建模块）。
- `parse`：读文件、词法、CST 与 AST，每个模块一次。
- `compile`：入口模块的整个编译。其中有：
  - `gct`、`gir`：每个模块各一次；
  - `import`：编译被导入的模块，里面又有它自己的 `parse` / `gct` / `gir`；
  - `resolve`：在搜索路径中找模块文件；
  - `cmo_load`：加载 C++ 模块。
- `encode`：编码运行时图。
- `pass`：每个遍一次，`detail` 是遍的名字。
- `(counting)`：数节点本身的开销。
- `teardown`：析构上下文与模块。

阶段可以嵌套，所以表格里给的是**自身时间**：一个阶段减去嵌在它里面的阶段。`(process)` 是外部测得的子进程墙钟减去报告的总时长，也就是加载器、静态初始化与进程退出。

峰值常驻内存读 `/proc/self/status` 的 `VmHWM`。`getrusage` 报的最大值把 exec 之前的父进程（Python）也算进去了，不能用。

分配器 shim 被预加载时，libcamel 用 `dlsym` 找到它的计数函数，报告里才有分配字段；libcamel 与工具都不链接它。

### 1.2 方法

- **环境**：18 逻辑核的大小核笔记本，WSL2 容器，同时还有别的线在构建。每次运行用 `taskset -c 2` 钉在同一个核上；同一轮里被比较的几个版本交替运行，负载的变化对它们一样。
- **统计**：表里给最小值（受负载影响最小），另注中位数。每轮前记录 `/proc/loadavg`；本文的三方对比在 1 分钟负载 9.8–13 之间测得。
- **轮数**：小、中输入 9 轮，大输入 7 轮，多模块 5 轮。单次超过 5 s 的情形只跑 2 轮。
- **分配数**：每个用例在计时轮之外多跑一次带 shim 的。
- **CPU 归因**：用 shim 的 CPU 时间采样，即 `setitimer(ITIMER_PROF)` 加 `backtrace`。容器内核的时钟是 250 Hz，所以要多跑几次累积样本。每个大输入跑 10 次，约 2,500 个样本。

### 1.3 输入集

| 集 | 输入 | 行数 |
|---|---|---|
| 小 | `hello.cml`；10 行的算术程序 | 8；11 |
| 中 | `test/cases/modules/stdlib/array_basic.cml`（导入 171 行全泛型的 `stdlib/array.cml`）；`benchmarks/resnetbn/model.cml`、`benchmarks/lora/lora_mlp.cml`（导入 `camel_bench`，只编译）；progen 默认规模的程序 | 36 + 171；275；201；155 |
| 大 | progen `--size 20` 的程序（种子 2，去掉 `macro` 特性，见第 9 节）；`test/tools/scale` 的 `mixed` 形状、4000 个函数 | 1282；16407 |
| 多模块 | `gen_modules.py` 生成的工程，N = 1、2、4……128 个模块；每个模块 8 个函数、约 40 行；形状为 flat、chain、fan | 至 5,400 |

复现：`python3 benchmarks/compile/bench.py run --camel base=<HOME1> --camel new=<HOME2>`。

解析内部的拆分（`camel-parsecheck bench`，最小值，µs）：

| 输入 | 记号 | 词法 | CST | AST 构建 |
|---|---:|---:|---:|---:|
| resnetbn | 3,333 | 52 | 86 | 1,338 |

这些数字已包含 AST 线合入的 arena 化。AST 构建仍是解析的 90% 以上，但它在全流水线里已退到第四位。

几点读法：

- 小程序的 8 ms 里，5 ms 是进程本身（动态加载 libcamel 与模块、静态初始化、退出），编译不到 2 ms。
- 大程序的顺序是 GIR 构建 > 编码 ≈ GCT > 解析，四者合计占墙钟的 95%。
- `(process)` 随程序变大（44 ms）：退出时全局表的析构。

遍与后端（重构前，中位数）：

- 后端：小、中程序上 `std::nvm` / `std::fvm` / `std::jit` 的整个遍是 0.3–3.6 ms。`std::bc`（只编字节码并打印，不执行）是 0.2–2.8 ms，可作为 fvm 执行前准备的上界。progen-20 上 fvm 遍 33 ms，scale-4000 上 106 ms。
- `std::macro`、`std::opt::fold`、`cse`、`dce`、`std::opt::specialize` 在中等程序上各 0.1–3 ms。
- **`std::opt` 是例外**：36 行的 array_basic 上 124 ms，155 行的 progen-1 上 88 ms，比整个编译还慢 5 倍。
- **规模问题**：在大程序上，`std::opt::inline` 与 `std::opt` 呈超线性。以下是重构前单独一轮的测量：

  | 程序 | `std::opt::inline` | `std::opt` | 测量时负载 |
  |---|---:|---:|---:|
  | scale-4000 | 58 s | 23 s | 约 10 |
  | scale-4000 | 285 s | 72 s | 20–35 |
  | progen-20 | 4.7 s | 12.6 s | 20–35 |

| startup | 5,738 / 0.95 MB | 5.8k / 0.95 MB | 5.8k / 0.95 MB |
| mm_init | 10 / 39.9 MB | 同左 | 同左 |
| builtin_module | 2,010 / 33.7 MB | 同左 | 同左 |
| parse | 102 / 86 kB | 25k / 9.2 MB | 235k / 91 MB |
| gct | 186 / 27 kB | 66k / 9.5 MB | 704k / 98 MB |
| gir | 286 / 16.8 MB | 276k / 36.8 MB | 1.46M / 139 MB |
| encode | 286 / 67.1 MB | 197k / 83.3 MB | 1.16M / 161 MB |
| **合计** | **9.8k / 159 MB** | **574k / 221 MB** | **3.57M / 610 MB** |
| 峰值在用堆 | 158 MB | 200 MB | 467 MB |
| AST / GCT / 图 节点数 | 37 / 18 / 8 | 15k / 8.3k / 6.3k | 139k / 87k / 43k |

读法：

- **固定预留**：hello 也分配了 158 MB 堆，来自内存空间（40 MB）、内建模块（34 MB）、GIR 构建（17 MB）和编码（67 MB）的预留块。这些块大多没被触碰，所以 RSS 只有 10 MB。它们不是常驻内存的问题，但每个块都是一次 `mmap`，并在退出时释放。
- **每节点分配**：AST、GCT、GIR 三层各自每节点 8–15 次分配。scale-4000 平均每行源码 220 次分配、20 KB 常驻内存。
- **每个图的常驻成本**：多模块对照（第 5 节）给出每个函数图约 40 KB 常驻内存，这是 GIR 与编码一侧的成本。

## 4. 热点归因

scale-4000 只编译，重构前，10 次运行（12.1 s 用户态、3.4 s 内核态）。内核时间几乎全是首次触碰新内存的缺页。

| 按阶段 | 占比 | | 按原因 | 占比 |
|---|---:|---|---|---:|
| GIR 构建 | 47.5% | | 自身代码 | 35.5% |
| 编码 | 21.6% | | 分配（含新内存缺页） | 22.1% |
| GCT 构建 | 18.4% | | 哈希表（查找与 rehash） | 12.7% |
| AST 构建 | 9.4% | | 位置与语义侧表（`camel::source`） | 9.1% |
| 词法与 CST | 1.6% | | 字符串哈希 | 6.3% |
| | | | libc（memcpy、memset 等） | 5.2% |
| | | | 类型系统 | 1.9% |
| | | | shared_ptr 引用计数（未内联部分） | 1.8% |
| | | | dynamic_cast | 0.9% |

**GCT 阶段内部**（重构前）：

- 按原因：位置与语义侧表 29%，分配 24%，哈希表 21%（主要是语义侧表的 rehash），自身代码 16%。
- 按函数：`malloc` 23%，`_Hashtable::_M_rehash` 14.5%，`SourceContext::astSemantic` 11.6%，`OriginTable::derive` 4%。
- 由此可见，GCT 自己的节点表示（每节点两个 `shared_ptr` 对象加一个子节点 vector）只是一半问题；另一半是每个节点在源码映射里登记 origin 与语义包的方式。

**GIR 构建**：

- 剩余的大头是分配（23%）、字符串键的哈希表（作用域与名字查找，合计 17%）和自身代码。
- 按函数分散在 `staticArgOf`、`reportDroppedEffects`、`isEffectNode`、`GraphDraft::normInputsOf`、`DraftGraphBuilder::operTarget` 等处，没有单一热点。

**编码**：38% 是分配，见第 3 节。

归因的局限（详见 `hotspots.py` 文首）：

- 发布构建里被内联的 `shared_ptr` 计数和字符串比较，计在调用者名下，所以这两类是下界。
- 容器的 libc 没有内部符号，libc 里的样本按 shim 的 `malloc` / `free` 帧归为分配，其余列为 "libc"。

## 5. 多模块

`bench.py` 的表里，`modules` 是 `gen_modules.py` 要求的模块数 N（不含 `main`），`user` 是程序自己的模块数（N+1，含 `main`），`total` 是这次运行编译过的全部模块数（`user` 加库模块）；阶段表另有一行 `library modules`，写出库模块的名字。这里的横轴是 `user`：它才是「每多一个程序自己的模块要花多少」的量。`total` 与库模块是遍按需加载的真实成本，例如带 `std::opt` 的 chain-128 是 131（129 + `rules`、`math`），不是 129。

chain 形状，重构前，最小值：

| 模块数 | 墙钟 (ms) | resolve | parse | gct | gir | encode | 分配 | RSS (MB) |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 10.5 | 0.12 | 0.88 | 0.61 | 1.57 | 0.79 | 24k | 11.3 |
| 8 | 38.9 | 0.79 | 5.6 | 6.3 | 11.2 | 5.0 | 129k | 19.3 |
| 32 | 128 | 3.4 | 18.6 | 26.8 | 39.1 | 22.4 | 496k | 47.0 |
| 128 | 594 | 25.0 | 81.0 | 116 | 226 | 111 | 2.02M | 157 |

flat 与 fan 两种形状的数字与此相差在 ±15% 以内（`results.md` 有全表）。导入结构不影响开销：模块从缓存取用的代价可以忽略（`import` 自身 < 1 ms）。

增长的成分：

- **主体是线性的**：每个约 40 行的模块约 4.5 ms、15.6k 次分配、1.15 MB 常驻内存，与同样行数的单文件程序的成本相当。
- **每个模块的固定成本**：同为 128 个模块，每模块 1 个函数与 8 个函数对照，固定成本约 1 ms 与 0.25 MB。另外，每个函数图约 40 KB 常驻内存：模块越多、函数越多，这一项越大。
- **超线性的一项是 `resolve`**：1 个模块时 0.12 ms，128 个时 25 ms，每次导入从 0.12 ms 涨到 0.19 ms。原因是 `Context::getModulePathAndKind` 对每个候选名、每个搜索路径都 `directory_iterator` 整个目录，按文件主名逐个比较，于是 N 个模块放在一个目录里就是 O(N²)。按此推算，1,000 个模块时约 1.5 s。

## 6. GCT 重构

### 6.1 做法

旧表示：

- 每个节点是 `AbstractTreeNode` 与多态 `Load` 两个堆对象，以 `shared_ptr` 相连。
- 子节点是 `std::vector<shared_ptr>`。
- 名字存成 `Reference`：先拆成路径 vector 加标识符，用时再拼回字符串。
- 一个节点约 150–200 字节、3–4 次分配。

新表示（`include/camel/compile/gct/node.h`、`tree.h`；设计说明见 [03](03_trees_and_structures.md) 4.7）：

- **节点**：一个 32 字节、无虚表、无析构的记录：种类、两个种类专用标志、一个小枚举、子节点数、origin、子节点数组指针、一个载荷字。读取经访问器（`name()`、`data()`、`argCount()`、`caseType()` ……），每个访问器断言节点种类。
- **arena**：`gct::Tree` 持有一个 arena，由按自身大小对齐的 16 KiB 块组成，块头记着树。节点、子节点数组（倍增，旧数组留在 arena 里）和导出名列表都在其中顺序分配，树销毁时整块释放。由节点地址即可找到它的树，所以 `*parent << child` 的写法不用变。
- **名字**：在树内驻留成一个字符串指针句柄，同名节点共享同一串，取名字时不再拷贝。常数仍是 `shared_ptr`，存在树里，节点只指向它。
- **种类**：`LoadType` 改名为 `NodeKind`；`BranchKind`、`CaseType` 提到命名空间一级。

GIR builder 只做了"改用新接口"所必需的改动：

- 不再出现 `loadAs<GCT::XLoad>()`；
- 自己合成的少量节点改由 `tree_->make*` 创建；
- 四处未初始化的节点指针加了 `= nullptr`；
- `build` 改为接收 `GCT::Tree &`。

分四个提交完成，每个都能编译并通过测试：先在旧表示上加 `Tree` 与访问器，再迁移 GIR builder，再迁移 GCT builder，最后替换表示并删去 `Load` 类。

剖析显示 GCT 阶段一大半时间在源码映射的语义侧表上，所以另做了一个小而独立的修改：`OriginSemanticMap`（AST、GCT、GIR 节点的语义包表）原来是按 origin id 的 `unordered_map`，改为按 id 下标的数组。origin id 是 `OriginTable` 顺序发放的，数组可以直接索引；语义包放在 deque 里，地址稳定；id 超过 2²⁸ 时退回 map，目前没有这样的 id。

## 8. 重构清单

按预期收益排序。"归属"指应在哪一层做；GIR 数据模型另有设计在进行，涉及它的几项只提方向。

| # | 现状 | 建议的表示 / 做法 | 预期收益 | 风险 | 归属 |
|---:|---|---|---|---|---|
| 1 | `std::opt::inline` 与 `std::opt` 超线性：4,000 函数时分别 58 s、23 s；36 行程序上 simplify 也要 124 ms | 先剖析这两个遍：疑为每次改写后重扫全图或重建索引；改为工作表与增量的使用者索引 | 大程序上数量级；带遍的流水线普遍 2–5× | 改写正确性：用 progen 全矩阵守护 | 遍（`src/passes/opt/`） |
| 2 | GIR 构建：作用域与名字表以 `std::string` 为键（哈希加 rehash 约 17%）；`visit` 返回 `std::any`；每节点多次分配 | 名字用整数句柄（GCT 的树内驻留已提供稳定句柄，可提升为上下文级的整数表）；作用域改为平铺数组加句柄索引；`visit` 返回带标签的小值类型 | GIR 阶段 30–50%，即大程序墙钟 15–25% | 与 GIR 数据模型设计同时做，避免重做 | GIR 数据模型 |
| 3 | 源码映射：每个 AST、GCT、GIR 节点都要 `deriveOrigin`，`OriginRecord` 带 `std::string label` 与 `vector inputs`（约 88 字节），语义包是 `vector<SemanticPart>`（每项一个 `std::string`）；仍占 GCT 阶段 36% | label 改为枚举或静态字符串；inputs 与 parts 放进按 origin 分段的平铺池；GCT 只在与 AST 不同时登记语义包，其余按 parent 链回溯 | GCT 阶段再降约 30%，AST 与 GIR 各降 5–10%，常驻内存降约 10% | 调试器与语言服务器读这些表，接口要保持 | 源码映射（本线可做，需先与调试器线核对接口） |

| 5 | 模块解析：每次导入都遍历每个搜索目录（O(N²)）；每个用户模块构造时复制内建模块的全部引用 | 见下"模块加载方案" | 128 个模块时 `resolve` 从 25 ms 降到约 1 ms；1,000 个模块时省约 1.5 s；每模块固定成本降约 0.5 ms | 低；不改查找顺序即不改语义 | 模块加载（`src/core/module/`、`src/core/context/`） |

| 7 | 进程级：hello 中进程本身 5 ms、四个预留块共 158 MB 虚拟堆；退出时析构全局表（大程序 44 ms） | 预留块改为按需增长；退出路径在冲刷输出、释放外部资源之后跳过全局析构 | 小程序冷启动降 1–3 ms；大程序退出降几十毫秒 | 低；跳过析构需确认没有析构里写出的副作用 | 运行时与 CLI |
| 8 | AST 构建（已 arena 化）仍占解析的 90% 以上 | 剩余的大头是源码映射（同第 3 项）与节点构造 | 解析阶段约 30% | — | 解析线 |

**模块加载方案（第 5 项）**：

- 在 `Context` 里缓存每个搜索目录的列表：主名映射到 (路径, 是否 `.cmo`)，第一次用到某个目录时用一次 `directory_iterator` 建表。之后每次查找是一次哈希查找，查找顺序不变：`.cmo` 优先，再按搜索路径顺序。
- 用户模块不再在构造时把内建模块的全部引用复制进自己的表，改为名字查找时回落到内建模块。

**类型系统方案（第 6 项）**：

- 对复合类型做哈希合并：同一结构只有一个对象，存在 meta 空间、带整数 id，相等比较退化为指针或 id 比较。
- 函数类型的签名同样驻留。
- 这改变"类型对象身份"的含义，所以应与 GIR 数据模型（节点里存类型 id 还是指针）一起定。
