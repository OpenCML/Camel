# 52 模块缓存 `.cmc` 的成本模型（H216）

**这是一次测量，不是实现。** 2026-10-22，提交 `ea0e8c858`（分支 `handover/H216-cmc-cost`，从
`origin/develop` 开），主机 `88zjwei`（32 核 EPYC 7343，Ubuntu 22.04），Release 构建
`261022_070803_ea0e8c858`。窗口内 `/proc/loadavg` 从 5.00 / 10.86 / 19.01 到
5.24 / 10.81 / 18.95（1 / 5 / 15 分钟）；每条命令 3 次预热 + 41 次计时，轮内固定种子随机交替。
表中是 41 次的中位数，括号里是 p10–p90。没有改编译器，没有新增开关，没有写出任何 `.cmc`。

## 0. 回答

- **41 ms 的全导入程序**（`inspect --ops registry_all.cml`，实测 41.53 ms）：冷启动 **0**；
  全部命中 **10.60 ms**（41 ms 的 **25.9%**）；单模块编辑 **8.27 ms**（**20.2%**）。
- **8 ms 的典型程序**（`import bytes` + `import hash`，实测 8.61 ms）：冷启动 **0**；
  全部命中 **0.91 ms**（8 ms 的 **11.4%**）；单模块编辑 **0.46 ms**（**5.7%**）。
- **失效面**：源文件散列、编译器构建标识、导入路径、已经记下的接口指纹都可以便宜地比较；
  推断返回类型、推断效应、传递捕获、泛型实例的签名不能在“不编译”的前提下重算——这是设计
  的诚实边界。
- **在这些数字上，完整 `.cmc` 不值得实现**：它从 41.5 ms 里去掉 10.60 ms 毛时间，其中
  7.62 ms 来自 26 个声明模块，本来就不需要图缓存；它一分也去不掉的是 19.81 ms 的 `.cmo`
  装载（`pyplot` 一个 9.88 ms）和约 8 ms 的进程、启动与清单输出。

## 1. 量法

`--time-phases` 的报告在
[38](38_compile_pipeline_cost.md) 里，这里只用它：每个阶段是墙钟，嵌套阶段按“自身时间”
（wall 减去直接子阶段）计；`parse` / `gct` / `declare` 的 `detail` 是模块名，`cmo_load` 与
`resolve` 也是，`gir` 只有一次、`detail` 是入口模块。整进程墙钟在外部用 `perf_counter`
包住子进程。被测的命令：

```bash
C=$HOME/camel-eval/conda/envs/clang
export LD_LIBRARY_PATH=$C/lib
export CAMEL_HOME=$PWD/out/latest
export PATH=$CAMEL_HOME/bin:$PATH
export CAMEL_TIME_PHASES=/tmp/h216-phase.json

./out/latest/bin/camel inspect --ops test/cases/modules/stdlib/registry_all.cml
./out/latest/bin/camel inspect --ops tmp/h216/progs/two_cheap.cml
./out/latest/bin/camel inspect --ops tmp/h216/progs/one_math.cml
./out/latest/bin/camel inspect --ops tmp/h216/progs/one_array.cml
./out/latest/bin/camel inspect --ops tmp/h216/progs/one_bytes.cml
./out/latest/bin/camel inspect --ops tmp/h216/progs/none.cml
./out/latest/bin/camel tmp/h216/progs/none.cml std::nvm
./out/latest/bin/camel tmp/h216/progs/one_math.cml std::nvm
./out/latest/bin/camel tmp/h216/progs/one_array.cml std::nvm
```

五个被测程序（放在工作树的 `tmp/` 下；放在 `/tmp` 会让 `import math` 解析到没有 `.cmo`
的源码，见第 6 节）：

```text
module none                          module one_bytes
func main(): int { return 0 }        import bytes
                                     func main(): int { return 0 }

module one_math                      module one_array
import math                          import array
func main(): int { return 0 }        func main(): int { return 0 }

module two_cheap
import bytes
import hash
func main(): int { return 0 }
```

驱动是一个几十行的 Python 脚本：对每条命令先预热，再在每一轮里随机排列全部命令、逐个运行，
把 `CAMEL_TIME_PHASES` 指向一个新文件，读 JSON、减去子阶段、对 wall 与各阶段取中位数和
p10 / p90。数字来自这些命令；驱动只做算术，不做任何插桩。

## 3. 三种情形

### 3.1 全导入程序（41 ms）

| 情形 | `.cmc` 去掉的阶段 | ms | 占 41 ms | 占实测 41.53 ms |
|---|---|---:|---:|---:|
| (a) 冷进程，没有 `__cmc__/` | 无（还要写出缓存） | 0 | 0% | 0% |
| (b) 全部命中 | 28 个模块的 parse + gct + declare + gir | 10.60（10.40–10.85） | 25.9% | 25.5% |
| (c) 单模块编辑（`array`；入口仍命中） | 其余 27 个模块 | 8.27 | 20.2% | 19.9% |
| (c') 同上，但导出的签名也变了（入口失效） | 其余 26 个模块 | 7.65 | 18.7% | 18.4% |

(c) 的算式：`array` 自己的 `parse` 0.79 + `gct` 0.96 + `declare` 0.14 + GIR 0.42 = 2.33 ms
必须重付，所以 10.60 − 2.33 = 8.27。若签名也变了，入口的 0.41 前端与 0.22 链接也要重付，
再减 0.62 得 7.65。**单模块编辑省不到被编辑模块的任何时间**：要证明它的接口没变，至少要
parse + gct + declare，推断返回类型与效应还要建函数体；缓存只能省其余模块。

**完美缓存的底线是 30.9 ms**：41.53 的总墙钟里，19.81 是 `.cmo` 装载，约 1.80 是启动
（`startup` 0.92 + `builtin_module` 0.82 + `context` 0.06），0.74 是 `resolve`，其余约
8.5 ms 是进程装载 / 退出、参数解析与 `--ops` 的清单输出。`.cmc` 碰不到这些。

### 3.2 典型程序（一两个导入，8 ms）

这里的“8 ms”指一两个便宜导入的整进程墙钟；实测 `bytes + hash` 是 8.61 ms。三种情形对
8 ms 取百分比，括号里是对该程序实测墙钟的百分比。“编辑入口”是用户改自己的文件——最常见的
单模块编辑；此时导入全部命中。

| 程序 | 墙钟 | (a) 冷 | (b) 全命中 | (c) 编辑入口，导入命中 |
|---|---:|---:|---:|---:|
| 无导入 | 7.46 | 0 | 0.58（7.2%，7.8%） | — |
| `bytes` | 7.64 | 0 | 0.68（8.5%，8.9%） | 0.27（3.3%，3.5%） |
| `bytes + hash` | 8.61 | 0 | 0.91（11.4%，10.6%） | 0.46（5.7%，5.3%） |
| `math` | 10.20 | 0 | 2.51（31.4%，24.6%） | 2.06（25.8%，20.2%） |
| `array` | 9.96 | 0 | 2.78（34.8%，27.9%） | 2.31（28.9%，23.2%） |

- 两导入的 8 ms 形状：全命中 0.91 ms，单模块编辑 0.46 ms。一个程序编译的东西越少，
  缓存能去掉的越接近“那一个导入”的前端；典型的声明模块是 `bytes` 这一档（0.17 ms 前端），
  `math` 是重尾（2.01 ms），`array` 是唯一带体的模块。
- 如果被编辑的是那个导入而不是入口（少见），在它的签名不变时入口仍命中，缓存省下的是入口；
  `bytes + hash` 这时省 0.44 ms（5.5%），`math` 省 0.44 ms（5.4%），`array` 省 0.47 ms
  （5.9%）。签名一变，入口也失效，只剩另一个导入，接近 0。

## 4. 失效面

设计原则 [10.3](../design-principles.cn.md) 的四项，加上一项设计原则没列、但“永不失效”
必须有的编译器标识。第三列是诚实边界：能便宜地比较的，与必须重算的。

| 要失效的东西 | 便宜地决定：散列什么、比什么 | 不编译就决定不了 |
|---|---|---|
| 源文件内容（每次命中都要） | 文件字节的 128 位散列（图模型 4.5 的文件头）；本机 27 个源文件 91,894 B，加 `registry_all` 2,602 B，Python `hashlib.sha256` 501 轮中位 **0.287 ms** | —（只要读文件，不用解析） |
| 编译器构建标识与前端选项 | 文件头里的 16 字节构建散列 + 选项摘要；不同即整体失效 | — |
| 导入解析 | 名字解析到的路径（目录表 / `stat`），与记录比 | —（比的是路径，不是接口） |
| 导出签名（写出来的部分） | 声明文本的规范化散列：名字、参数与返回类型、重载集、`@effect` 注解；类型名换成所属模块的接口指纹，递归下去 | 类型的同一性依赖导入方的接口指纹；指纹本身要由 declare 产出 |
| 导出签名（推断出的返回类型） | 无：它只在建函数体时才知道（[program.cpp](../../src/compile/gir/program.cpp) 的三步，第 2 步） | 计算签名由算子的类型规则给出（[49](49_computed_signatures.md)），`.cml` 文本里没有；必须 declare / 建体 |
| 间接用到的模块级值 | 捕获表（实体 id）与每个值的类型；捕获表本身来自 link 的最小不动点（`linkCaptureSites`） | 捕获闭包要名字解析、重载与泛型实例；源文本里没有这张表。改了初值而类型、名字不变时，要证明“捕获的还是同一个值”只能重算 |
| 效应 | `@effect` 注解文本 + 算子的效应位（`OperatorTable`，随 `.cmo` 版本） | 推断效应是另一个不动点（`settleEffectfulGraphs` / `reportDroppedEffects`）；函数体改一行就可能改效应集 |
| 泛型函数的体 | 模板体源码切片的散列（图模型 4.5 的 `TMPL` 已按这个设计）；实例键 =（模板实体，类型实参） | 实例的签名、效应、捕获要在实例化后才知道；体一改，全部实例失效，“改了但实例等价”也只能建出来才知道 |
| 用到的算子 | `OPRS` 的 URI + 签名，装载时核对；主版本不同即失效 | 要 `.cmo` 已加载——这笔钱本来就要付 |

**边界。** 把两件事分开：“变没变”可以便宜地回答（源散列、导入指纹、构建标识、算子表）；
“接口变没变”对任何**推断出来的**成分都不能。源文本决定推断返回类型、推断效应、传递捕获和
泛型实例的签名，但只有经过名字解析、重载、类型规则、实例化与不动点才能得到它们；一个永不
失效的缓存不能用语法近似替代这些分析。于是它能保证的只是：**源没变的模块命中；源变了的模块
至少付它自己的 parse + gct + declare（推断部分还要建体），它的导入方要等新指纹算出来才能
证明有效。** 设计原则 10.3 的四项因此不是四个可以廉价判定的谓词，而是四类必须由前端产出的
接口事实。这也是为什么 (c) 的 8.27 ms 是上限：被编辑的模块一分不省。

## 5. 和替代方案比

四种做法的毛收益都在同一窗口里：完整 `.cmc` 10.60 ms（41 ms 的 25.9%）；把声明保留、只跳过
GIR 9.94 ms（24.2%），完整缓存多出来的 GIR 只有 0.63 ms（1.5%），因为 `array` 的泛型在这个
程序里一个实例也没建；只缓存 26 个有声明文件的原生模块的声明文本 7.62 ms（18.6%），留下
`array` 2.33 与入口 0.62；什么都不做 0。四者都不动 19.81 ms 的 `.cmo` 装载与约 8.5 ms 的
进程 / 启动 / 清单。声明文本缓存不需要序列化图，但对推断签名、推断效应与捕获仍要付同样的
分析；完整 `.cmc` 在单模块编辑时反而要把被编辑模块的 2.33 ms 全重付，声明缓存可以把这一笔
压到 GIR 的 0.42 ms。一个真正实例化 `array` 泛型的程序 GIR 会更大，本页没有量它。

## 6. 局限

- **毛收益，不是净收益。** 没有实现，所以 `.cmc` 的读入、核对、编号改写、图装载都没有量；
  10.60 ms 是“编译工作被去掉多少”的上界，不是“第二次运行快多少”。图模型说装载与模块贡献
  成线性，那是设计估算，不是本页的测量。
- **GIR 的逐模块数字是分摊的**，方法见第 2 节；阶段报告里只有一次 `gir`。
- **墙钟对负载敏感，阶段和没有那么敏感。** 同一条命令在 load 27.9 的窗口是 45.4 ms、16.7
  是 41.0 ms、5.0 是 41.5 ms；对应的 cacheable 是 10.78 / 10.60 / 10.60 ms。本文用最低负载
  的窗口，它的 41.53 ms 与任务给的“41 ms today”对得上。
- **程序形状有限。** `registry_all` 导入了 `array` 却从不调用它，所以没有泛型实例；一个真的
  用 `array` 的程序 GIR 会更大。本页也没有量 128 模块的链（[38](38_compile_pipeline_cost.md)
  里那条 441 ms 的输入，前端占 96%）——那种形状下结论可能不同。
- **一台主机、一个构建、一个程序。** 源散列是在 Python 里量的（C++ 会更快），Linux Release，
  没有 Windows 数字。
- 放在 `/tmp` 的单导入程序会把 `math` 解析到源码树里的 `stdlib/math.cml`（没有同目录的
  `.cmo`），报 `NativeDeclarationNotLoaded`；程序必须放在工作树的 `tmp/` 下。这是解析路径的
  既有行为，不是本页的改动。

## 7. 没有做什么

没有实现缓存，没有加开关，没有改编译器、加载器或任何阶段；没有提交 `.cmc`、`__cmc__/` 或
测量脚本。第 1 节的命令、第 2 节的表、第 3 节的三种情形与第 4 节的失效面就是本页的全部产出；
结论在 §0 的最后一句。
