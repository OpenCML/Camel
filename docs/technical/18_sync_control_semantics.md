# Camel 同步控制语义解读

> **先读 [`../design-principles.cn.md`](../design-principles.cn.md)。** 它是语言作者对 Camel 根本定位与执行模型的规范性说明：与实现或其他文档冲突时以它为准；它没有覆盖或标为“未定”的问题，向语言作者提问，不要自行选择。

本文档解释 Camel 的同步语义：`sync` 在语言里约束什么，编译器把它落成什么。图上的边只有三种——**数据边、同步边、顺序边**（[`../design/effects/edges.cn.md`](../design/effects/edges.cn.md) 1，设计原则 3.1）。三者回答三个不同的问题：值从哪来、哪几条语句属于一条链、哪些效应必须一前一后。把哪一半交给哪种边，是本文的主线。

- **语法语义层**（2）：`sync` 的约束与直觉语义。
- **编译实现层**（3–8）：从 AST/GCT 到 GIR 如何落地，以及各后端按什么契约执行。

## 1. 设计目标

Camel 的同步执行语义要求：

- 返回值必须正确（值语义）。
- 同步副作用（例如 `println`、`seed`、I/O、对 `var` 的写入）必须在函数对外完成前完成（时序语义）。

编译器因此要回答两件不同的事，并用不同的边回答：

- **值从哪来**：数据边。谁产出值、谁消费值，“被用到”如何沿端口传递。
- **谁先谁后**：同步边（同步块里语句之间的一条链，前一条因此也被用到）与顺序边（只排序，不传递“被用到”）。

由此得到唯一的执行规则：一个节点执行，当且仅当从程序的结果出发沿**数据边或同步边**能到达它；顺序边不参与。在要执行的节点之间，先后同时遵守三种边（edges.cn.md 2）。

## 2. 语法语义层：`sync`

本节描述“语言层”定义；后续章节给出对应实现路径。

### 2.1 语法入口（关键产生式）

- `stmtBlock : 'sync'? '{' stmtList? '}'`
- `funcDecl : frontMatter ('with' angledParams)? 'export'? 'func' (identRef | operatorName) typeParams? parentParams (':' typeExpr)? resourceClause? whenClause? stmtBlock?`
- `funcData : modifiers? angledParams? parentParams (':' typeExpr)? '=>' blockExpr`（lambda）
- `funcType : modifiers? angledParams? parentParams '=>' typeExpr resourceClause?`（函数类型）
- `modifiers : 'sync'+`

`sync` 只有一个意思：**它使它后面那个块成为同步块**。函数声明里它写在函数体位置——`func f(...): T sync { ... }`
（也就是 `stmtBlock` 的 `'sync'?`）与单独的 `sync { ... }` 都是这个写法：块自己直接写着的语句按书写顺序执行
（编译器把这些语句写成一条同步链）；写在里面的分支臂、循环体与嵌套块不继承这个顺序（2.2 的“不向内继承”）。
lambda 的函数体是块，`sync` 写在块前（`(x: int) => sync { ... }`）；lambda 头和函数类型上都没有修饰符，`sync` 是块的性质，不是类型的性质（设计原则 3.4）。

### 2.2 求值规则与 `sync` 块

Camel 的求值是**依赖驱动**的：一个表达式被求值，当且仅当它的结果（经数据边或同步边）被函数出口需要。

- **同步块之外，结果未被使用的效应调用不会执行。** 这是依赖驱动求值的自然结果，是合法的语言规则，
  不是缺陷；编译器在能够检测到时给出告警。
- **同步块**（`sync { ... }`，或以 `sync` 块作为函数体）内，**它自己直接写着的语句**按书写顺序执行，
  而且无条件执行：编译器把它们写成一条同步链，链尾连到块的值，于是“链上的语句”本身就是“被用到”。
  顺序边与它无关：顺序边只排序，不让人执行。
- **同步链上只有带效应的语句与可能出故障的语句**（故障可观察，设计原则 3.4）。纯计算、以及纯且不会出故障的
  计算不进链：它执行与否完全由值是否被用到决定，先后完全由数据依赖决定（edges.cn.md 1）。唯一的例外是
  块的值接收链尾的同步边。
- **同步块不向内继承**（设计原则 3.4，形式化 F17）：同步块只管它自己直接写着的语句；写在里面的臂、
  循环体与嵌套块按它们自己的写法执行，要同步就在那里写 `sync`。例：
  `func f(c: bool): int sync { if c then { println(1); println(2) }; return 0 }` 里 `if` 在同步链上，
  它的值是 `println(2)`，所以 `println(2)` 执行、`println(1)` 不执行；要两句都打印，写
  `if c then sync { ... }`。
- `sync` 不改变值语义，只增加顺序约束。

```camel
// 函数体不是同步块，println 的结果未被使用，因此不执行（设计如此）
func f(): int {
    println("hello")
    return 1
}

// 函数体是同步块：println 执行，然后返回 1
func g(): int sync {
    println("hello")
    return 1
}
```

### 2.3 引用、`var` 与 `let`

- Camel 中一切值**默认按引用传递**。`var` 标记可变对象，`let` 标记不可变对象。
- `var` 形参是真正的引用：被调函数对它的写入就是对调用方变量的写入；在任何调度器、任何遍之后
  （内联、特化、折叠、CSE、DCE）观察到的写入都相同。
- 被 `if` 分支或 lambda 捕获的变量也按引用捕获：在分支或 lambda 内对它的写入作用于外层变量。
- 把 `let` 绑定的（不可变）对象传给 `var`（可变）形参是**编译期错误**。
- 同一个变量传给两个 `var` 形参是别名：两个形参指同一个对象。
- `let` 的不可变性是**编译期校验**，不是对内存加锁：修改变量的操作本身是 `sync` 的，且必须声明哪个形参
  是 `var`；`let` 变量不能传给 `var` 形参，因而无从修改。
- **每次写产出变量的新版本，每次读接此前最近一次写的产出。** 写（赋值、写了捕获变量的调用）与写之间是
  顺序边：写取单元作位置，不取上一次写的产出。读（`:var/get`、读了捕获变量的调用）有一个数据端口接到
  此前最近一次写的产出，没写过则接建单元处；调用上这个端口的角色是“捕获”（edges.cn.md 5.6）。由此
  “读用到最近一次写、没被读的写不执行”是数据边的直接结果，不需要另一个顺序约定：
  `var a = 1; let b = a; modify(a)` 里 `b` 读到的是 `1`，`modify` 排在这次读之后但不改变它。
- **同步块给写入的是另一件事：无条件执行。** 同一变量在同一同步块里的多次写入按书写顺序排列：
  `before(i + 1); modify(i)` 里 `before` 排在 `modify` 之前，即使 `before` 根本没碰到 `i`。不在同步块里的写
  没人读它就不执行，编译器给出 `IgnoredSideEffect` 告警（文案说的是这件事，不是顺序）。测试
  `test/cases/linear/byref/order_direct_user.cml`（图 `order_direct_user.graph`）从图上锁定这两条：有
  `before → modify`（同一同步块里的书写顺序），也有 `modify →` 写在它之后的那次读取（读的端口接在这次写上）。
- 同步块内**它自己直接写着的**表达式按书写顺序执行（写在里面的臂、循环体与嵌套块不继承这个顺序，
  见 2.2），这也包括：以一个值结尾的同步块（值在块内最后一个表达式之后交出）、
  写在同步块里的 `sync { }` 块（它自己是外层链上的一个语句，块内按它自己的写法）、
  `let (p, q) = f()` 这样一次绑定多个名字的声明。
- 同步块内的调用按书写顺序执行：块的相邻语句之间就是同步边。副作用只在默认的无序执行下才需要
  考虑，因为它限制了重排。
- 副作用的管理与追踪仍是研究中的部分：按引用捕获、写入的追踪与各个遍相互作用不好的情形，作为研究发现
  连同复现程序记录，不做临时性的修补。

### 2.4 静态约束

- `var` 形参是资源参数（设计原则 3.3），不需要声明，也不因为“在非同步上下文里”告警。
- `sync` 只写在块之前：函数体位置（函数体是同步块）与单独的 `sync { ... }`；lambda 与函数类型的位置上
  写在实参表之前（2.1）。
- 调用带 `var` 形参的函数或算子、直接调用写入被捕获变量的函数、或进入有分支臂写入被捕获变量的分支，
  而不在同步块内：`IgnoredSideEffect` 告警。
- 把 `let` 对象传给 `var` 形参：编译期错误（见 2.3）。

### 2.5 实现现状（与上述规则的差距）

> 本小节记录**当前实现**与 2.1–2.4 规范之间的差距；规范以 2.1–2.4 为准。每条差距在代码跟上之后删除。
> 行为记录由程序运行确认（`test/cases/linear/runtime/effects_outside_sync.cml`，计划
> `linear.runtime_negative` 中的 `effects_outside_sync.*`）。

符合规范、已由测试锁定的行为：

1. 非同步函数体中，结果未被使用的效应调用（例如一条 `println(...)` 语句）不执行，在所有调度器上一致。
2. 函数体位置的 `sync` 使这个函数体成为同步块：AST 上它记在 `stmtBlock` 的 `synced` 标志上
   （`src/parse/ast/builder.cpp` 的 `visitStmtBlock`）。
3. 结果作为返回值的效应调用（`return println(...)`）在数据路径上，会执行。
4. 读接到此前最近一次写的产出（2.3）：`var a = 1; let b = a; modify(a)` 读到 `1`，六种跑法一致
   （`test/plans/feat/linear/var_read_before_write.plan.toml`）。

与规范的差距（跟踪项见 `OWNER-QUESTIONS` 的 A1、A3–A6、A9）：

- **控制边这个种类还在代码里。** 模型里只有三种边（edges.cn.md 1），控制边属于被删除的那一半：
  建图器在同步块里把相邻语句写成同步链，但一部分位置仍在写控制边，顺序约简也还读它。删除控制边的其余部分
  与 `std::opt::order` 的判据收成只读同步边、顺序边是同一件事的两半。本文描述的是模型；代码里凡是与此
  不一致的，以模型为准，差的那部分按欠账删除。
- **规范未明确、实现暂定的几点**（`var` 形参、捕获、`let` 检查、别名均已按 2.3 实现，见 8.1）：没有 `var`
  的形参视同 `let`；`var` 变量传给没有 `var` 的形参或绑定到 `let` 时取当时所持的对象（对象共享，不复制）；
  对 `s.x`、`arr[0]` 赋值是编译期错误；带 `var` 形参的函数不能交给会调用它的算子（macro 算子除外）。
- **JIT**：带 `var` 形参的图不再被排除，只把 `var` 形参继续传下去的函数在 `std::opt::inline std::jit` 下会被
  编译；但 JIT 对任何含通用算子（`OPER`）的图回退到解释器，赋值与 `:var/get` 都是这样的算子，所以读写变量
  的图仍由解释器执行（测试 `var_param_jit` 记录了这一现状）。
- **告警的范围。** 模块没有 Error 时，Warn 级诊断在编译之后、运行之前输出到标准错误
  （`Context::dumpModuleWarnings`，见 `docs/cli.md` “Warnings”）。`IgnoredSideEffect` 只对变量的写入产生；
  同步块之外、没有任何东西依赖它而被丢弃的效应（不纯算子、有副作用的函数调用、赋值、含这类分支臂的分支）
  由 `EffectNotExecuted` 报告：每张图建完后，从出口沿数据边和同步边反向可达之外的效应节点就是被丢弃的
  （`Builder::reportDroppedEffects`）。通过函数值的调用只能按类型识别。
- **写入与读取的顺序**：写与写之间、写与读之间都由三种边决定（2.3）：读接此前最近一次写的产出，同步块里的
  写按书写顺序且无条件执行。经由捕获（含模块顶层变量）的写入，对直接调用和分支已经跟踪（3.3）；
  通过函数值（作为实参、返回值或存放起来的 lambda / 函数）进行的调用不在其内：函数类型不携带“写入了哪些
  被捕获变量”这一信息。

尚待语言层面确认（实现没有替语言做决定）：

- 非同步函数体内嵌套的 `sync { ... }` 块，其值未被使用时是否执行。当前实现：块内语句彼此有序，但块尾没有
  接到外层出口，整块不执行。按“依赖驱动”规则这可以是预期行为，按“同步块按书写顺序执行”也可以认为应当
  执行；两种读法都与现有文字相容，未作选择。

## 3. 编译实现层：从 AST/GCT 到 GIR

### 3.1 AST 层标记

- 解析器在 `stmtBlock` 上记录 `synced` 标志（`func f(...): T sync { ... }` 与单独的 `sync { ... }`）。

### 3.2 GCT 层节点

- `StmtBlock(sync=...)` lower 为 `ExecLoad(synced)`。

### 3.3 GIR Builder 状态机

`src/compile/gir/builder.cpp` 中有一个关键状态：

- `synced_`：当前是否在同步执行上下文。
- `lastSyncedNode_`：这条同步链的尾（链上最后一条语句）。

行为要点：

- `visitExecNode` 进入/退出时切换 `synced_`，进入时链尾清空。
- `visitLinkNode` 在处理调用/链接时，若参数为 `var` 语义：
  - 不在同步块内（`!synced_`）=> 触发 `IgnoredSideEffect`。
  - 在 `synced_` 中，把这次调用接到链尾之后（`linkSyncStatement`，`shouldAddSyncCtrlLink` 只跳过“链尾已经是
    这次调用的直接值输入”的那一次），并更新链尾；对变量的读取（`:var/get`）同样进这条链。
  - 调用成为该变量的写入者（`recordWrite`）：每次写产出变量的新版本，此后对变量的读把端口接在这次写的
    产出上（edges.cn.md 5.6），写与写之间是顺序边。
- **被捕获的变量**（包括模块顶层变量）。函数、lambda、分支臂引用外层图的变量时，变量的单元经捕获端口进入
  子图，函数类型里没有它。Builder 为每张图记一份摘要（`CaptureSummary`）：捕获了哪些变量、函数体自己写了
  哪些、直接调用了哪些图（含分支臂）。图的写入集合是这份调用关系上的最小不动点（`capturedWritesOf`）：
  自己写的，加上被调图写的、且自己也捕获了的那些；递归调用不给函数自己的集合增加任何东西。
  - 直接调用一张图（`visitLinkNode`，被调图已知）或进入分支（`visitBrchNode`，从 `BRCH` 到 `JOIN`）时，
    对被调图捕获的每个变量：调用/分支排在该变量此前的写入者之后；被调图写它，就按上一条记为写入者
    （分支以 `BRCH` 为起点、`JOIN` 为完成点）；只读，就记为一次使用。
  - 函数体还没建完时（递归调用自身，直接或经由分支臂）它将来写什么还不知道。此时在函数体内部按
    “它捕获的变量都可能被写”来排序（保守，只多加同步/顺序约束）；函数建完后对外的摘要是精确的，告警也在全部
    函数体建完后按精确的集合发出。
  - 捕获端口绑定在被捕获的值本身（同一个节点，模块顶层的值是公共 root 上的节点），调用处传入的是同一个值
    在调用者看来的样子，不按名字在调用处重找（`src/compile/gir/captures.cpp`）。不可变值的捕获可以在
    调用之后才出现（递归函数先调用自己、后用到值），由链接步补上；变量的捕获不行：调用处已经按当时知道的
    变量排好了序，所以函数被直接调用之后再捕获变量是 `CaptureAfterRecursiveCall`。函数体在第一次被用到时
    就建出来（三步加载的第二步，`src/compile/gir/program.cpp`），这只会出现在递归里：函数在调用自己之后才
    第一次用到某个变量。写入摘要（`capturedWritesOf`）与"出口是否依赖效应"（`settleEffectfulGraphs`）都在
    全程序的函数体建完之后、在链接步取不动点。
  - 通过函数值的调用（`CALL` 节点、交给算子的 lambda）不查摘要。
- **分支与循环是块里的语句**：写在分支前面的语句是链尾，`JOIN` 跟在这个链尾之后（`linkSyncStatement`）；
  分支的两条臂是 `BRCH` 自己拥有的区域，不进这条链，它们只在被选中时执行（edges.cn.md 1.5、5.3）。
  循环同理：语句在 `LOOP` 之后接着排，条件与体是 `LOOP` 的区域。
- **块的值的落点**：链尾的同步边连到块的值——块的值节点归这个块独有（在块里新算出来、没有别的使用者）时
  直接连它；否则生成一个 `GATE`：一个数据端口读那个值、一个同步前驱是链尾，值原样放行（edges.cn.md 5.3）。
  往共享的值节点上挂同步边会让它的所有使用者都排到链之后，把链拉活，这是错的。

> 这就是语言层“同步块控制副作用可见性”的具体编译落点。

### 3.4 当前实现边界

`sync` 的实现只有三处：`stmtBlock` 的 `synced` 标志（3.1）、`StmtBlock` lower 成 `ExecLoad(synced)`（3.2），
以及建图器按 `synced_` 把相邻语句串成链（3.3）。还没有接上的一处见 2.5：函数体不是同步块时嵌套的
`sync { ... }` 块，它的块尾没有接到外层出口。**`SYNC` 节点已经不存在**：链尾接块的值时用同步边，
需要收拢时用 `GATE`（edges.cn.md 5.3），不再有一个代表“几条语句汇合”的节点。

### 3.5 顺序约简现在在哪

顺序边的传递约简只有一个入口：`std::opt::order`（`OrderReductionPass::apply`，预算 `250000`）。建图器不做传递约简：
`shouldAddSyncCtrlLink` 只在“链尾已经是直接值输入”时跳过一次链上的边（`hasDirectDataDependency`），这是精确、
局部的去重，不查路径。编码前的 `reduceControlDependencies(*prepared.draft, 8192)` 已删除。约简的判据读的是
同步块的链与顺序边：一条同步边是链上的一环，没有冗余可去；`include/camel/runtime/control.h` 的规则不变：
删除 Port/Data 的输入边和值已蕴含的边，保留 BRCH/JOIN 边界与 GATE 的第一条输入。

本轮复核复测了上一轮对比过的 6 个程序：带不带 `std::opt::order` 都与改动前逐字节相同，唯一例外是 `test/cases/linear/byref/element_assigned.cml` 在不带 `std::opt::order` 时多一条 `:var/take -> :op/assn_owned` 的边。那是 `:var/take` 与随后 `:op/assn_owned` 之间真实的顺序要求（`assn_owned` 要排在取出之后），`std::opt::order` 的传递约简会把它删掉；它不是使用关系，见下。

上一轮把 `path_assigned_allocs.cml` 的 `2 0 0` 读成“多出的边让 `:var/take` 的结果多了一个使用者，原地改写因此又复制了一次”。本轮用分配计数和运行轨迹复核，结论不同：

1. 两个图（有/无约简）里 `:var/take` 都只复制一次，`path_assigned_allocs.cml` 的整段复制序列完全相同，计数差不在复制上。
2. 第一个测量窗口里多出的 320 字节块是**数组字面量自己的构造**：GIR 是 `字面量(Data) -> COPY -> :var/new`，`COPY` 在无约简的图里被排在第一个 `std::mem::blocks()` 之后，在基线的图里排在它之前。
3. 原因不在共享判定，而在顺序没有被写进图：`:op/mem::blocks()` 这个语句节点没有任何输入（jgir 里是根），`var v = [...]` 的声明也不进入同步链（`lastSyncedNode_` 只由读、调用、分支、循环更新），所以“先构造还是先测量”不受边约束；`computeExecutionOrder` 是从出口出发的 DFS 后序，边集一变，两个互不约束的节点就换了位置。字面量的构造除了这一次分配没有可观察效应，因此图没有违反 3.3/3.4，是测量窗口写得过宽。

本轮把该用例改成用调用构造数组（`make_array()`）：调用是同步链上的语句，构造稳定地落在第一个窗口之前。四个后端在有/无 `std::opt::order` 时都是 `1 0 0`。

原地改写的共享判定不数使用者：它在建执行计划时按图定下来（`buildExecPlan`），随计划一起交给各后端执行。把值取走的读（`let y = xs`、传参、放进容器：`:var/get`）结束“旧值没有别的观察者”的证明，变量自己原地改写后的存储（`:op/assn_owned`）建立它，只喂给留不下引用的算子的读（`:var/peek`）不结束它；证明不了的格子（`var` 形参、被捕获的格子）交给更新算子在运行时问数组自己的计数（`Array::canWriteInPlace`）。顺序边只表达顺序、不读值（1），所以加一条顺序边不会让这条语句复制。

运行时那个计数数的是**名字**：`Array::canWriteInPlace` 要求块上只有这一个引用，所以值多出一个仍然活着的名字时，交出这个名字的算子先给存储加一个引用（`Array::shareForSecondName`）：块资产（`block_ != nullptr`）交出一个指向同一块的新值（只多一个引用，不复制数据），数据还在数组对象里的（内联紧凑数组）交出一份自己的数据拷贝（两个名字共用一个内联存储就是两个名字共用一个数组，而这些数据不超过内联上限，所以拷贝不产生块）。三个算子用这条规则：`:var/new`（`var v = e` 的格子是值的一个新名字）、`:op/assn`（赋值后格子也持有值）和 `:var/get`（读把值放出变量）。视、外部块、位移过的数组和槽数组写不成原地，块已经被多个值持有的也不再需要加：这些情形直接交出值本身。这样“计数为 1”就真的等于“没有别的观察者”，`rebinding_loop.cml` 一类靠读保住快照的用例仍然成立（读给存储加引用后，变量自己的下一次改写仍然复制），跨函数的 `var` 形参也不必整份复制。

## 4. 核心 GIR 节点职责

### 4.1 `BRCH`

- 表示分支选择点：第一个端口是条件，从它算出“命中分支索引”。
- 两条臂是它自己拥有的 `Arm` 区域：属于某条臂的节点只在那条臂被选中时执行。**`BRCH` 与臂之间没有边**，
  只靠区域归属（edges.cn.md 1.5）。

### 4.2 `JOIN`

- 表示分支结果汇聚点：第 0 个端口是 `BRCH` 的值（选中的臂号），其后是各臂的结果（按臂的序号）。
- 语义是“从多个候选值中选出当前路径对应的值”。它用到第 0 个端口与**被选中的那条臂**的结果端口，
  臂里的节点因此只在选中时执行（edges.cn.md 4.5）。

### 4.3 `GATE`

- 表示“值 + 同步前驱”的锚点：一个数据端口读值，一个同步前驱是同步链的链尾，值原样放行。
- 只在需要时生成：块的值节点不归这个块独有时（形参、常量、被别处也用到的节点、建在块外的节点）才插一个
  `GATE`，否则链尾的同步边直接连到块的值（edges.cn.md 5.3）。
- 它是纯的传值节点：匹配与求值时**透过**它看它的值，但 `GATE` 本身不能删除、也不能被它的输入替换——那样
  同步边会转到共享的值节点上，回到 5.3 说的问题——除非它的同步前驱已经不存在。

## 5. `EXIT` 的正确建模规则

在函数出口，编译器必须回答两个问题：

1. 返回哪个值？（通常是 `resNode`）
2. 还要等哪些同步链尾？（例如同步块最后一个效应节点、节点修饰器链尾）

若存在任何待等的链尾，`EXIT` 应锚定到 `GATE`，并满足：

- `Norm: resNode -> GATE`（数据边）
- `Sync: tail_i -> GATE`（对每个链尾）
- `Graph.output = GATE`

若不存在链尾，`Graph.output` 可直接为 `resNode`。

## 6. 为什么不是总用 `JOIN`

`JOIN` 只解决“分支值收敛”，它没有“某条链完成”这个意思：它的第 0 个端口必须有 `BRCH`，臂的结果按序号进来。
拿它当出口会让“值已就绪”与“效应已完成”混成一件事。

典型场景：

- 先得到返回值（如 `JOIN`）
- 后续仍有同步副作用（如 `println`）

若 `ExitNode` 仍指向 `JOIN`，调度器可能在副作用完成前就把函数视为完成，破坏同步语义。`GATE` 的存在就是把
“值已就绪”与“链已完成”绑定为单一出口契约。

## 7. 出口锚点怎么定（Builder 层）

1. 先收集所有待等的链尾，不先用 `resNode` 过滤（早先用 `resNode` 过滤会把 `println -> JOIN` 一类误判成潜在环，
   从而误判“无需 `GATE`”）；
2. 若存在链尾且返回节点不是 `GATE`，先建 `GATE` 并把 `Norm` 接上；
3. 再对最终的出口锚点（通常是 `GATE`）做连边合法性检查并连边。

顺序与这条策略一致：出口锚点优先保证语义正确，再做图合法性校验。

## 8. 与各执行后端的契约

- **NodeVM**：`GATE` 作为无操作节点处理，返回值仍按 `exitNode()->index()` 读取；当出口为 `GATE` 时索引转发到其 norm 输入。
- **FastVM**：`GATE` 不产生核心计算字节码，只作为图结构语义节点参与完成条件相关约定。
- **Taskflow**：`GATE` 需要有占位任务以承接依赖边，保证并行调度下的完成顺序与线性语义一致。

### 8.1 变量与按引用

`var` 变量是一个**单元**：只有一个槽位的堆对象（运行时是 `Tuple`，类型为 `TupleType::cell(T)`，打印为
`var T`）。名字绑定到的节点保存的是指向单元的指针，读写变量都是作用在单元上的算子：

| 源码 | 图 |
|---|---|
| `var x = e` | `x := OPER :var/new(e)` |
| 读取 `x` | `OPER :var/get(x)`，取该节点执行时单元里的值 |
| `x = e`、`x += e` 等 | `OPER :op/assn*(x, e)`，写入单元 |
| `var p: T` 形参 | 一个 PORT，槽位里是调用方的单元 |
| 实参传给函数的 `var` 形参 | 直接传单元节点；不是名字的表达式先由 `:var/new` 得到一个新单元 |
| 实参传给没有 `var` 的形参、`let y = x` | 传 `:var/get(x)` |
| 分支臂 / lambda 中出现 `x` | 捕获端口（with 端口或闭包槽位）里是同一个单元 |

由此，调用方、被调方、分支臂与闭包持有的是同一个指针；实参绑定、闭包 FILL、尾调用复用帧、内联把端口替换成
实参节点，复制的都只是指针，所以各调度器、各遍之后观察到的是同一个对象，不需要回写，也不要求被调帧存活。
函数类型仍记录源码签名（参数类型 `T` 与 `var` 标记）；重载决议按值类型进行（`valueTypeOf`）。

- 赋值之外不再有带 `var` 形参的内建或标准库算子：`append`、`extend`、`apply`、`array::sort` 等返回新值，
  不修改实参（设计原则 11.3）。写成语句的 `acc = acc->append<v>` 由图构建器按算子声明的原地形式
  （`OperatorTable::setInPlaceForm`）写成 `:op/assn_owned(acc, :struct/append_arr_in_place(v, :var/take(acc)))`：
  `acc` 的单元作为 `var` 实参，记为对它的一次写入；`:var/take` 在单元只持有该数组时把原数组交给原地形式，
  否则给一份复制，原地形式改完返回它（`src/builtin/operators/ops.cpp`、`struct.cpp`）。模块的算子仍可以
  声明 `var` 形参：它们收到的是这个值（`:var/get` 的结果），该调用记为对这个变量的一次写入。
- `:var/new`、`:var/get`、`:op/assn*` 都不是纯算子：折叠、CSE、特化不会越过它们；CSE 也不合并以
  `:var/get` 的结果为输入的相同表达式（两次求值之间对象可能被原地修改）。`isWrittenInPlace`
  （`include/camel/runtime/draft_writes.h`）仍用于识别传给 `var` 形参的节点。
- `let` 的检查在图构建时完成（`SemanticDiag::ImmutablePassedToVarParam`），运行期没有任何检查。

## 9. 回归样例

建议以下回归样例防止出口锚点退化：

- **返回值先就绪，后置副作用**：应生成 `GATE`，出口指向 `GATE`。
- **分支值经 `JOIN` 收敛，分支后仍有副作用**：出口仍应指向 `GATE`。
- **纯值函数（无同步副作用）**：允许出口直接为值节点。

推荐检查方式：

- `camel <file>.cml std::gir`
- 关注函数子图里 `EXIT` 入边是否来自 `GATE`，以及 `GATE` 是否同时有值输入与等待（模型里那条等待是同步边，
  见 2.5 的差距）。

## 10. 一句话总结

`JOIN` 负责“把分支值变成一个值”，`GATE` 负责“把这个值和同步链的完成点绑定为函数出口”。值靠数据边，
链靠同步边，先后靠顺序边；控制边这个种类不在模型里，代码里剩下的那一半正在删除（2.5）。
