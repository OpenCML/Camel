# Camel 设计原则与语义裁定

本文档记录语言作者对 Camel 根本定位与语义问题的明确说明，只陈述**现行**的规则。它是规范性的：当实现、其他文档或某次测试结果与本文档冲突时，以本文档为准，冲突之处应作为缺陷或待办记录下来，而不是据此修改语义。

**修改 Camel 的语义、遍、调度器、导出器或自动微分之前，必须先读本文档。** 文中没有覆盖或仍标为"未定"的问题，应向语言作者提问，不要自行选择。

规则按主题组织。每条裁定是何时、怎样定下或改定的，见 [设计原则裁定记录](design-principles-log.cn.md)（按时间排列，含已被取代或撤回的说法；其中的旧编号与本文档的新编号的对照表在该文件开头）。文中标为"倾向"或"原则上"的说法不是硬性规则，不要把它们当作禁令去实现或检验。

## 1. 根本定位

Camel 最核心的特征是图原生。其他性质都是这个定位的自然产物，不是另外附加的功能。`ZEN` 的八条是这一定位的提纲：前两条讲图是根本，其余六条是推论。

- **只建模计算意图。** Camel 的程序描述"要算什么、谁依赖谁"。它不主动承载 CPU 密集型的任务，也不承载各类配置；这些由算子、运行时和遍去处理。正因为如此它才自由灵活。
- **图是原生的，不是产物。** 图不是从别的语言的代码里捕获或恢复出来的，源码写下的就是图。
- **语言元素与图直接对应。** 理解或设计任何语言构造，都要先回答它在图上是什么。判据：语法元素必须和图有稳定的映射关系，这才体现图原生；一个构造在图上长什么样如果取决于它里面写了什么，它就不该进语言。
- **与传统控制流有所区别。** 不用语法糖去模拟传统的控制流，保持语法元素和图节点之间简单的映射关系。（这不排斥含义没有歧义的简洁写法，例如列表推导。）
- **不限于 AI。** 图上建模的是计算的意图与依赖，HPC 与各类仿真计算同样适用。对外的定位表述：Camel 是图原生的通用编程语言，AI 是它首要的应用领域；不再自称面向 AI 的领域专用语言。在论文的视角下 Camel 不主动承载 CPU 密集型的工作；在通用语言的视角下，它仍然要有一定的通用性。两种视角并存。
- **只有一门语言。** 根据类型算出类型、按类型的结构生成代码，都用主体语言写：类型是编译期的值，类型函数是在编译期运行的普通函数，用的是与值层相同的构造（见 [泛型按结构展开](design/generic-structure/README.cn.md)）。不另设一套类型层语言（如 TypeScript 的条件类型、映射类型、`infer`）。图的变换、规则、调度同样用 Camel 本身写。
- **简写可以有，语义只有一套。** 简写（如装饰器）是给库作者用的机制，可以存在，但只能是同一语义的另一种写法，不得另带规则。
- **红线要少，且每条都有强制机制；** 其余的是倾向或质量要求，按倾向记。当前的红线清单见 [重构总纲](design/blueprint/README.cn.md) 第 4 节。
- **内测阶段不考虑兼容成本。** 旧写法直接退役并给出指向新写法的诊断，不做过渡层。
- **自己的库尽量用 Camel 写**，以暴露语言的不足并吸纳进核心（见 10.4）。

## 2. 程序与图

### 2.1 语言元素与图的对应

| 语言元素 | 在图上是什么 | 由此得到的行为 |
|---|---|---|
| 表达式、算子调用 | 节点与数据边 | 按依赖求值；没有被依赖的节点不执行；互不依赖的节点可以乱序或并行 |
| `sync` 块 | 相邻表达式之间的控制边 | 块内按书写顺序执行 |
| 同一资源的副作用 | 同一函数体内、用到同一资源的副作用之间的控制边 | 按书写顺序执行（3.3） |
| 函数 | 子图 | 行为由函数自己决定；调用只是把子图节点放进更大的图里，不改变它的结构 |
| `var x = v`、读、赋值 | 建立单元、读单元、写单元三种算子节点；`x` 这个名字绑定的是单元 | 可变的是单元，不是值 |
| lambda、函数作为值 | 一个函数常量；有捕获时再加一个把捕获的值装进去的节点 | 函数值就是"图 + 捕获的值" |
| `f<w>` 作为值（部分应用） | 一个捕获了 `w` 的函数值，它的图把剩下的参数与 `w` 一起交给 `f` | 与 lambda 是同一种结构 |
| `macro` 函数（标签 `#macro`） | 可以被提前求值、结果物化为图中常量的子图 | 动态地构造静态图 |
| `if`、`match` | 一个分支，每条臂一张子图 | 只有被选中的臂求值 |
| `a ?? b`、`a !! b`、`x ?-> f` | 一个分支：条件是值上的一位标记（为空／出错），两个臂分别是原值与替代 | 与 `if` 是同一种结构 |
| `a && b`、`a \|\| b` | 一个分支：`a && b` 即 `if a then b else false`，`a \|\| b` 即 `if a then true else b` | 右边是一条臂，只在需要时求值；不可重载 |
| `a & b`、`a \| b` | 普通的算子节点 | 两边都求值；可以重载 |
| `if x != null then A else B` | 与对 `x` 的 `match` 是同一张图：进入非空那条臂的是拆开后的值 | 收窄不是另一种机制 |
| 值进入 `T?`、`T!` | 每进入一层一个装入节点 | 装入只在需要它的位置发生 |
| `enum` 的构造与 `match` | 构造是装入一个标签；`match` 是取标签、分支、在臂里取出数据 | 图上不增加节点种类；`T?`、`T!` 可以看作内建的两个 `enum` |
| `throw e` | 返回一个错误值 | 与 `return` 是同一种结构 |
| 故障隔离（`attempt`） | 对子图的一次带标记的调用 | 故障的边界就是子图的边界，结构不随子图的内容变化 |
| `map`、`filter`、`reduce`、`foreach` | 一个算子节点，元素函数作为函数值传入 | 高阶算子不是新的节点种类 |
| 泛型函数 | 子图模板；每用一组具体类型调用，实例化出一张类型全部具体的子图 | 图上只有具体类型 |
| 类型函数 | 建图时求值，图上不留节点 | 运行时不存在"类型"这种值 |
| 标签 `#` | 声明或节点上的编译期事实，图上不产生节点 | 在编译期存在，不会被"调用" |
| `loop` 表达式 | 一个 `LOOP` 节点，带条件子图、循环体子图与状态边 | 状态由循环头决定，不取决于循环体里写了什么 |
| 模块顶层的 `let` | 公共 root 图上的一个节点 | 被依赖才求值；导入不执行任何代码 |
| 函数用到模块顶层的值 | 函数图上的一个捕获端口，绑定到"模块 + 名字"，值沿调用传下来 | 不出现跨图的节点引用 |
| `import { f } from m`、`import { v } from m` | 不建任何节点：调用 `f` 是一次普通的调用；`v` 在 root 上是一条普通的边，在函数里是捕获端口 | 导入不执行任何代码 |
| 导入泛型函数 | 不建任何节点；每组类型一个实例，全程序共用，属于声明它的模块 | 图上只有具体类型 |
| `namespace`、`using namespace`、`m::f` | 图上没有任何痕迹，只决定名字解析到哪个"模块 + 限定名" | 命名空间是名字的一部分 |
| 遍 | 把一张图变成另一张图（或消费一张图）的程序 | 开放的流水线 |

### 2.2 图的结构

- **不应当出现跨图的节点引用。** 一张图里的节点不指向另一张图里的节点，图与图之间只有"图引用图"（调用）这一种关系。任何设计都要先过这一条。
- **对外的节点种类**：`DATA PORT OPER FUNC CALL FILL ACCS CAST COPY BRCH JOIN LOOP GATE SYNC`。`map` 一类高阶算子与 `attempt` 仍是算子节点，由算子表声明"会调用子图"。
- **分支臂的两种形态都是合法的图**：前端产生"每条臂一张子图"；内联之后臂的节点并入外层图、成为分支与汇合之间的一段，也是合法的。
- 图存储与图 API 的细节见 [图存储与图 API（第二版）](design/graph-store/README.cn.md)。

### 2.3 图的数据模型

- **图的数据模型是最重要的一项设计**：它要定义清楚、稳定、可以对外。模块缓存、用 Camel 写遍、把计算代码编译成 GPU 内核、`std::cpp` 都建在它上面。
- **节点属性属于对外的图数据模型**，用 Camel 写的遍也能读写。
- **编译核心的内部表示可以彻底重构**，以求全流水线的速度与内存效率。

### 2.4 容量与默认值

- **单张图没有容量上限。** 编号一律 32 位（语言作者于 2026-10-19 确认了 [图存储与图 API（第二版）](design/graph-store/README.cn.md)，原来的 65,535 上限随之取消）。
- 图、类型、元数据三块空间的总上限各 256 MB；停不下来的展开另由导出器自己的轮数预算刹住。

### 2.5 图与源码的往返

- **图与源码的表达能力相同**：任何合法的图都能写成 Camel 源码，写回再编译得到同一张图（名字、源码位置等不计）。由往返测试强制（全部测试用例与随机生成的程序）；写不回来的图结构视为语言的缺口，需要补上。
- 标准遍 `std::cml` 把当前的图导出为 Camel 源码：产物尽量可读，但不以人类易读为约束；泛型实例写成具体类型的函数，被内联的部分不必还原；大的常量放在旁边的数据文件中由源码引用。

## 3. 求值与副作用

### 3.1 按依赖求值

默认情况下求值由依赖驱动，没有固定的执行顺序。

- **同步块之外、结果没有被使用的带副作用的调用不会执行。** 这是按依赖求值的自然结果，是合法的预期行为，不是错误，不需要报错。编译器足够智能时可以给出警告。
- 资源只决定执行者之间的顺序，不决定是否执行（3.3）。
- **效应函数也返回值。** `println(x)` 返回 `x`，这样效应可以串进数据流：用到它的返回值，它就一定被执行并排在使用之前。

### 3.2 函数的行为由它自己决定

函数编译后得到自己的子图。外部调用只是把这个子图节点安排在更大的图中，不会改变它自己的结构。

```camel
func log(x: int): int {
    println(x)          // 结果没有被使用，函数体不是同步块：不执行
    return x + 1
}

func main(): int sync {
    let a = log(1)
    let b = log(a)
    return b            // 返回 3，什么都不打印
}
```

`main` 的函数体是同步块，两次 `log` 调用按顺序执行。但 `println` 属于 `log` 自己的函数体，那里不是同步块，所以不执行。要打印，`log` 应声明为 `func log(x: int): int sync { ... }`。

### 3.3 资源、`uses` 与 `pure`

- **资源**：对它的访问需要排序的东西。资源类别由库用关键字 `resource` 声明（`export resource fs`），可以分组（`resource io = [stdout, fs]`）；与其他名字共用命名空间，按同样的规则导入，可写限定名。标准库最基本的资源（`stdout`、`stderr`、`stdin`、`fs`、`clock`、`env`）默认可见。
- **每个 `var` 自动是一个资源**；函数的 `var` 形参是资源参数，在调用处对应调用者传入的那个变量；闭包捕获了 `var`，其函数类型就带着这个资源。
- **资源是函数类型的一部分**：`func save(p: Params): unit uses fs { ... }`。`uses` 后接用逗号分隔的资源列表，不加括号。原生算子（模块中无函数体的声明）在签名中写 `uses`；没有写的原生算子视为使用"全局"资源，与一切副作用保持顺序。
- **Camel 函数的资源由编译器推出**（函数体内所调用者的资源之和，递归时求不动点），不必手写；编辑器的悬停与文档以限定名显示推出的资源。显式写 `uses` 是承诺，函数体超出即为编译错误；导出函数推出的资源发生变化时给出警告。
- **效应以资源声明为准**；签名里的 `var` 由资源声明检查，不一致是声明错误。
- **`pure`** 承诺函数不使用任何资源，由编译器检查；可以写在函数声明与函数类型上（如要求回调是纯函数：`f: (x: T) => U pure`）。
- **函数类型的参数默认对资源泛型**：`f: (x: int) => int` 不写资源，表示 `f` 用什么资源都可以，调用它的函数随之使用这些资源；按实例化确定。资源少的函数可以用在要求资源多的地方，反之不行。
- **同一资源自动有序**：同一个函数体内，真正执行的、用到同一资源的副作用按书写顺序执行（编译器生成控制边）。调用另一个函数，在调用处是"一个用到其资源的副作用"；编译器不跨函数重新编排。
- **算子的纯度必须声明。** 没有声明的算子按有副作用对待（最多少优化，不会算错）；仓库内的标准库模块必须逐个算子声明，第三方模块漏了给提示。
- **算子是否可能故障不强制逐个声明**：模块作者按需声明，没有声明的按可能故障处理。
- 先例与取舍：靠推断而非强制标注（Java 受检异常的教训）；高阶函数的资源由实例化确定，不需要 Koka 式的行多态；不提供效应处理器；按具体对象（如文件句柄）区分资源暂不做，`var` 除外。
- **无序资源**：`resource net unordered` 声明的资源上的副作用之间不保持书写顺序，彼此独立时可以同时进行；"顺序无关"是声明它的库作出的承诺。需要顺序时写在 `sync` 块里，或用句柄。
- **句柄类型（按对象的资源）**：带标签 `#resource` 的类型，它的每个值都是一个独立的资源；操作在签名中写 `uses 形参名`（如 `func next(s: Stream<T>): T? uses s`），与 `var` 形参同理。对同一个句柄的操作按书写顺序，不同句柄之间互不约束；编译器在调用处推出用到的是哪个值。用于流、会话、文件句柄等。
- **并发不需要 `async`/`await`**：彼此独立的计算与无序或不同资源上的副作用可以同时进行；运行时在一个副作用等待（网络、磁盘、子进程、调用模型）时执行图上其他就绪的节点。这是实现，语义与按某个合法顺序逐个执行相同；`std::nvm` 可以逐个阻塞地执行。
- **取消**：只有声明为可取消（`cancellable`）的资源或算子上的副作用可以被取消，被取消时不得留下不一致的状态（库的责任）；不可取消的执行完、结果丢弃。标准库的 `first_of(a, b, …)` 取先成功完成者的结果、取消其余的；它的结果取决于完成的先后，这一不确定性写在它的声明中。

### 3.4 `sync` 块

写在块前的 `sync`（包括函数体的后缀写法 `func f(): T sync { ... }` 和单独的 `sync { ... }`）表示这是一个同步块：其中所有表达式按书写顺序执行，可以理解为编译器在两两之间自动插入控制边。

- 块内的副作用一定执行，并且块内一切（跨资源的、纯计算的）都按书写顺序。用于"要它发生"与"跨资源、跨纯计算的先后"（如计时）。不推广为按类别的同步。
- 在同步块里，调用什么都无所谓，有没有副作用也无所谓，因为已经有顺序了。副作用只在默认乱序的前提下才需要考虑，因为它限制了不能随意打乱顺序。

### 3.5 引用、`var` 与 `let`

- Camel 默认都是引用。闭包对变量的捕获也是引用。
- `var` 标记可变对象，`let` 标记不可变对象。
- `let` 严格意义上不可修改：会修改变量的操作必须明确声明哪个参数是 `var`；不允许把 `let` 变量传给 `var` 参数，所以理论上无法做到修改。这是**编译层面的校验约束**，不是对内存上锁。把 `let` 对象传给 `var` 参数是编译期错误。
- **可变性的声明是一个闭环。** 函数内部想修改参数，必须使用本身就具有副作用的函数：Camel 中的赋值操作就是有副作用的函数；或者使用其他内置的 C++ 算子，而这些算子的声明也明确标记了副作用，要求相应的输入参数是可变的。所以，想修改参数，前提是这个参数声明为 `var`（`modify(var i: ...)`），否则没有任何有效的办法去修改。可变性从最底层的算子声明一路向上传递，每一层都必须显式声明；没有把参数声明为 `var` 的函数不可能修改它。在函数体内对非 `var` 的参数赋值，或把它传给要求可变输入的算子，是编译期错误。
- **修改的追踪应当是完整的**：函数通过捕获（包括模块顶层的变量）写入一个 `var`，与通过 `var` 参数写入一样，调用处应当记为对该变量的一次写入。
- **带 `var` 上下文参数的函数可以部分应用**：`add<t>` 是一个写被捕获变量的函数值，它的类型带着这个资源，每次调用记为对 `t` 的一次写入。
- **Camel 崇尚不可变变量。** `var` 和赋值运算符只是为了方便留的口子，应当尽量少用。模型的计算应当用 `let` 写成纯的数据流。
- **字段与元素不可赋值**：只能给整个变量赋值。
- **微分与变量**：被求导的函数里，梯度需要经过 `var` 的读写时，直接拒绝并给出明确的诊断，不去支持。没有必要为了求导硬写 `var`。
- **模块顶层的 `var` 被函数直接读写**（如 `fib1.cml` 中的顶层 `cnt`）：没有完全实现，不是必须的情况下先不管。
- **已知的不足。** Camel 在副作用的管理与追踪方面还有缺陷，需要进一步研究。引用捕获、副作用的追踪与各个遍相互作用时出现的问题，应如实记录为待研究的发现并附最小复现；只修复明确的实现错误，不要用临时规则去掩盖。

### 3.6 高阶算子与并行

- **`map`、`filter` 的各个元素之间没有执行顺序的约定**：同步块不影响 `map` 内部的执行顺序，并行调度器可以并发执行各个元素，结果按元素位置排列；这正是并行加速的来源（见 `test/cases/para/core/monte_carlo_pi.cml`）。`foreach` 与 `reduce` 按元素顺序执行；它们的无序并行版本是 `para` 模块的 `unordered_foreach` 与 `unordered_reduce`。仓库中没有 `ordered_map` 或 `unordered_map` 算子。元素函数里的副作用在并行的 `map` 下顺序不作保证，由使用者负责。
- **高阶函数的并行来自声明的性质**（元素之间互不依赖），不来自名字；用户写的函数声明了同样的性质也可以并行。
- **并行调度的粒度**：不要细到原子级别。给每一次很小的函数调用都建一个任务没有意义，只会徒增负担。
- **并行的 `map` 中一个元素出了故障**：已经开始的元素跑完，还没开始的不再开始。多个元素同时出故障时报下标最小的那个。

### 3.7 分支与 `match`

- **没有 `else` 的 `if` 本身没有值**，它的臂可以是任何类型，臂的值被丢弃：`if debug then println('checking')` 合法，`let x = if debug then 1` 是编译期错误。图上不变：一个分支加两条臂，没写的 `else` 是一条空臂，汇合处不取值。臂里不必再为了凑类型写 `return null`。
- **分支的一条臂没有值（`void`）、另一条是 `T` 时，分支是 `T?`**，没有值的那条臂给出 `null`。
- **`match` 必须有默认分支。** 没有 `case _` 是编译期错误；`bool` 上两个字面量都列全、`enum` 列全所有变体，以及 `T?`、`T!` 的固定模式除外。编译器不追加用户看不见的分支臂。每个分支的值必须能被被匹配值的类型接受。

### 3.8 可空

- **"可能为空"与"可能出错"是两种专用的内建形式**，写作 `T?` 与 `T!`（3.9）。各带一位标记，只能用 `??`、`!!`、`?->` 和 `match` 的固定模式拆开。不做通用联合类型的运行时分辨。
- **`a ?? b` 处理空值。** 右边可以是可空的：右边是 `T?` 时结果是 `T?`，右边是 `T` 时结果是 `T`；从右向左结合，所以 `a ?? b ?? 9` 是"先试 a，再试 b，最后给默认值"。图上是一个分支。
- **值进入 `T?` 或 `T!` 的位置时自动装入**，只要目标类型已知（实参、带类型的 `let`、数组元素、分支的两条臂）；`null` 同理。反方向永不自动：`T?`、`T!` 要当 `T` 用，必须用 `??`、`!!`、`?->` 或 `match` 拆开。空数组字面量 `[]` 的元素类型同样取自目标位置。
- **`x == null`、`x != null` 可以写**，结果是 `bool`。函数值之间不能比较，但可空的函数值可以与 `null` 比较。
- **在 `if x != null then ... else ...` 的非空那条臂里，`x` 是 `T`。** 这等价于对可空值的 `match`：进入那条臂的端口带的是拆开后的值。只对 `let` 绑定与参数生效（`var` 可能被别处改写）；只认直接的写法（`x != null`、`x == null`、`null != x`，以及用 `&&` 连起来的几个，其中只要有对 `x` 的直接判空）；只在臂内生效；`||` 的 else 臂暂不收窄。在收窄的臂里再写 `let x = ...` 是重复声明。
- **收窄之后**，对已确定非空的名字仍可写 `??`、`match` 等针对 `T?` 的操作，给警告"已确定非空"；对非可空的值判空同样允许并警告（结果恒定）。

### 3.9 错误与故障

- **错误值是一个固定的内建结构**：种类名、消息、发生处的源码位置。所有可能出错的函数共用这一种错误。
- **可能出错的值只写 `T!`**，错误值只有一种类型（以 Kind 区分）；将来需要带类型的错误时，在有了 `enum` 之后以 `T ! E` 的形式加入。`?` 只是可空标记。`int?!` 允许，`int??`、`int!!` 不允许。
- **`a !! b` 处理错误**，右边可以是可空的，规则同 `??`。`x ?-> f` 在 `x` 出错时把错误原样传下去，否则调用 `f`。它们在图上都是分支。
- **`throw` 保留，含义是返回一个错误值**，与 `return` 同构，且只接错误值：`throw error('Kind', 'message')`，位置由编译器填。`try`/`catch` 不进语言：它在图上没有稳定的映射。写了应得到一条诊断，指向 `!!`、`?->` 与故障隔离。`raise` 不是语法的一部分，也不是保留字。
- **错误与故障是两回事。** 只有声明为可能失败的操作（读文件、解析、网络等）才返回错误值。除零、越界、递归过深是故障，不变成错误值，否则每个除法和下标都要处理错误。
- **故障默认带位置终止，但可以在子图边界上隔离。** 提供一个隔离算子 `attempt`：被它包住的函数里发生的故障，在边界上变成一个错误值，再用 `!!` 处理。终止之前保证清理：刷新输出，释放外部资源。

  ```camel
  let a = risky(0)                 // 故障：整个程序带位置终止
  let b = attempt(risky, 0) !! -1  // 故障被隔离，b = -1（示意）
  ```

- **没有被处理的错误值到达 `main` 的出口**：打印到标准错误，退出码非零。
- **同步块里一个 `T!` 的值没有被使用，是编译期警告**；没有 `else` 的 `if` 里，臂里一个 `T!` 没有被使用，同样警告；`let r = ...` 绑定了一个 `T!` 而 `r` 从未被使用，同样警告。故意丢弃写 `let _ = ...`。没有声明返回类型的 `main` 以一个错误值结尾，是它的特例。
- **必然出故障的常量表达式**（如 `1 / 0`）：折叠遍不折叠它，给一条带位置的警告，留到运行时。这是折叠遍自己的选择，不是对所有遍的约束（见 9.6）。
- **越界**：编译期能知道长度时（尤其是固定长度的类型），`slice` 与下标的越界应当是编译期错误，而不是悄悄截断或留到运行期。运行期的 `slice` 越界是故障，与下标越界一致；`take`、`drop` 按定义截断，不受影响；起点在终点之后的 `slice`（`xs->slice<2, 1>`）得空数组，不是故障。
- **递归深度**：尾递归要做优化，程序应尽量写成尾递归或循环；非尾递归给一个可配置的上限，默认在各调度器上统一为 1000，并行调度器同样计数。
- 数值上的故障见 5.1，归约的故障见 7.7。
- **超时是调用的参数，超时返回错误值**（`T!`），不是故障，如 `http::get(url, timeout: 5.0)`。

### 3.10 循环

- **引入 `LOOP` 节点。** 现代的计算图标准大多有这类节点，要与它们接轨就需要它。循环体是独立的子图，不并入外层图。条件子图与循环体子图共用一份捕获表；`for … while` 是同一种节点的第三种形式；有多个状态时循环体返回一个元组，`LOOP` 的值也是这个元组。
- **循环是一个带状态的表达式。** 状态写在循环头上，循环体的值是下一轮的状态，整个循环的值是最终状态。不为"循环外的 `var` 当状态"另设语句形式；只为效应而遍历用 `foreach` 等已有的办法。
- **循环头的写法是 `do` 式**：状态只声明一次，多个状态用逗号分开，循环的值是它们组成的元组；`do` 后面是一个表达式，`{` 的读法与 `then` 之后相同（`{ x: 1 }` 是结构体，`{ 5 }` 是块）。

  ```camel
  let total    = loop acc = 0 for x in xs do acc + x * x
  let (i, acc) = loop i = 1, acc = 0 while i <= n do (i + 1, acc + i)
  let p        = loop p = { x: 0 } for d in ds do { x: p.x + d }
  let found    = loop hit = -1 for x in xs while hit < 0 do if x > 9 then x else hit
  ```

- **不加 `break` 与 `continue`。** 提前结束写成循环头上的继续条件（如上面的 `found`）。
- 循环头必须有 `for` 或 `while`；`for … while` 每轮先判断条件、再取下一个元素；`for` 目前只遍历数组，字符串、映射、张量以后再加；状态的类型取初值的类型，张量形状不自动放宽，需要时写类型标注。
- **循环可以收集每轮的输出**：`LOOP` 节点除最终状态外，可以有一组"每轮产出一个值、按轮次收集成数组"的输出（对应 ONNX `Loop` 的 scan 输出）。这是图层面的能力，源码中没有对应的语法；第一个使用者是自动微分（9.9）。

## 4. 语法与运算符

### 4.1 词法与语句

- **尖括号紧贴。** `with` 实参与类型实参的尖括号必须紧贴前面的记号：`f<a>` 是带实参的 `f`，`f < a` 是比较。比较运算符 `<` 前面要有空白；`i<n` 是错误，诊断应指出原因。
- **换行结束语句**，思路同 JS 的自动分号，以符合直觉为准。括号未闭合、行尾是二元运算符或逗号等"后面必须还有东西"的记号、下一行以只能是二元的运算符开头（`->`、`.`、`??` 等）时续行；下一行以 `-`、`+`、`(`、`[` 等可以开始一个表达式的记号开头时是新语句。分号仍可用。
- **有两种身份的符号出现在行首时，取开始新东西的那种身份**：行首的 `@` 是标注，行首的 `+`、`-` 是一元的。要把矩阵乘或加减法写成两行，把运算符留在上一行末尾。
- **解析器**用手写的词法分析器与解析器，不再依赖 ANTLR，追求效率与确定性。
- **注释**只用 `//` 与 `/* */`，`#` 不表示注释；文件首行的 `#!` 仍作为解释器行被忽略。
- **文档注释**是语言的约定：声明正上方以 `///` 开头的注释是它的文档。悬停与文档只取 `///` 注释，普通的 `//` 不是文档。
- `===` 暂不支持。

### 4.2 运算符

- **`^` 比乘除高一级，从右到左结合。** `2 * 3 ^ 2` 是 18。
- **一元负号永远是运算符，不并入字面量**；它的优先级低于 `^`、高于 `->`。于是 `-2 ^ 2` 与 `-x ^ 2` 都是 -4，`-2->f` 与 `-x->f` 都是先取负再传入：字面量与变量的读法一致。`a-1` 仍是减法。`!`、`~` 与一元负号一样，优先级低于 `^`、高于 `->`：`!x->f` 先取反再传入。
- **`&&`、`||` 是不可重载的保留运算符，转译为分支。** `a && b` 即 `if a then b else false`，`a || b` 即 `if a then true else b`：右边是一条臂，只在需要时求值。两边都是 `bool`。
- **`&`、`|` 是两边都求值的普通逻辑运算，可以重载。** 只是做一点简单的逻辑运算、不需要分支时用它们；张量的逐元素逻辑运算、用户自己的类型重载的也是这一组。`a &= b` 即 `a = a & b`；`&=`、`|=` 是布尔上的与、或；位运算用函数（`bit_and` 等）。
- **`==` 与 `!=` 对数组、元组、结构体按内容逐个比较。** 两边类型必须相同，元素类型本身要能比较（含函数值的不能比），否则是编译期错误；浮点元素按浮点的规则（含 `nan` 的数组不等于它自己）。张量不在此列。图上是一个普通的算子节点。
- **张量的 `t += u` 是算出新张量再重新绑定**，与数值一致，不原地修改。要原地修改用显式的算子。
- **列表推导** `[e for x in xs if c]` 的含义是 `filter` 加 `map`，即 `xs->filter<c>->map<e>`；元素之间没有顺序约定。

### 4.3 运算符重载

- **用户可以在 Camel 源码里重载运算符**，写作 `func operator &(a: Mask, b: Mask): Mask`（写法暂定）。可重载的是今天落到 `__x__` 函数上的那些运算符；`&&`、`||` 与 `??`、`!!`、`->` 等构造不可重载。`__x__` 形式的名字仍是保留的，用户不直接写。
- 用户的重载比内建的更具体时优先；重载 `==` 即得到 `!=`（`!=` 不能单独重载）；命名空间块里声明的运算符属于模块。

### 4.4 函数与参数

- **Camel 在语言层面区分两种参数。** 一种是函数要配置的属性（`with` 参数，即上下文参数），另一种是函数要处理的输入，也就是要流过函数的东西（普通参数）。这在某种意义上弥补了 Camel 不支持面向对象的局限：别的语言里靠对象的成员来持有的配置与状态，在 Camel 里是函数的上下文参数。
- **`with` 参数适合表达模型的参数与权重**：普通参数是数据输入，`with` 参数是权重。调用除了写成 `f<w>(x)`，也可以写成 `x->f<w>`，便于链式调用，也便于把模型各层的输入输出串联起来。
- **`f<w>` 是部分应用**：`let g = f<w>` 得到一个已经配好上下文参数的函数。
- **`with` 参数不是泛型参数。** 它是上下文参数，不要拿它来声明类型参数或编译期参数。
- **泛型函数可以出现在任何期望一个函数的位置**，包括传给另一个泛型函数（见 5.5）。
- **尖括号只用于"配置"**：函数要配置的东西（`map` 的映射函数、`filter` 的条件、权重）用 `with` 参数，保留 `xs->map<f>` 的流水线写法；函数主要处理的输入（如 `grad` 要求导的函数）用普通参数：`grad(loss)`、`value_and_grad(loss)`。函数作为普通参数且在编译期已知时，编译器照样为它特化（这是优化，不是语义）。标准库各函数的归属在示例写出来后逐个确定。
- **管道调用可以带额外实参**：`x->f(a, b)` 即 `f(x, a, b)`；`x->f` 与 `x->f<w>` 不变。

## 5. 类型系统

### 5.1 基本类型与数值类型

- **数值类型不做隐式转换。** 整数不会自动变成浮点（参数、返回值都一样）；需要时显式写 `float(x)`。
- **带指数或小数点的字面量一律是浮点数。** `1e5` 是 `100000.0`。
- **转换的故障**：`int('12abc')` 是故障，整个字符串必须是一个数，要安全地解析用 `parse_int`，它返回 `int!`；值放不进目标类型的转换是故障：`int(1e30)`、`int(nan)`、`i32(5000000000)`。
- **整数加减乘的溢出、最小整数除以 -1 保持回绕。**
- **把值转成它自己的类型是合法的，什么也不做**：`xs as int[]`（`xs: int[]`）与经别名的 `p as A` 一样通过。
- 不应当存在到了运行时还不确定的类型：每个值在编译之后都有确定的类型（`any` 见 5.10）。
- **诊断与图上用源码里的类型名**（`first<int>`，不是 `first<i64>`）。
- **字面量按上下文取类型**（与 Go 的无类型常量相同）：依次取期望的类型（声明、形参、返回位置）、二元运算中另一个操作数的类型、默认类型（整数 `int`、小数 `float`、虚数 `c128`）；字面量之间的运算在编译期按精确值计算；值放不进目标类型是编译期错误。变量之间仍不做任何隐式转换。例：`x * 2 + 1`（`x` 是 `f32`）中的 `2`、`1` 都是 `f32`。
- **复数**：核心数值类型 `c64`、`c128`，在数组中紧凑存储。虚数字面量是数字紧跟后缀 `i`：`4i`、`4.0i`、`1e-3i`（十六进制、二进制不可带）；`3 + 4i` 是 `c128`，`let w: c64 = 1 - 2i`。打印为 `3+4i`。

### 5.2 命名类型与结构类型

- **有名字的结构体与 `enum` 是命名类型**：`type Point = { x: float, y: float }` 创建一个新类型，它的身份是名字加声明它的模块，属于该模块。元组、数组、函数类型，以及 `type 名字 = 另一个已有类型`，是别名，按结构比较（如 `type Pair<T> = (T, T)`）。
- **没有名字的结构体值可以直接用作结构相同的命名类型**：`let p: Point = { x: 1.0, y: 2.0 }`，字段按名字对应。**两个命名类型之间必须显式转换**（`m as Seconds`），即使结构相同；字段按名字一一对应。需要"包一层的数值"（如 `Meters`）时写成单字段结构体，不另加语法。
- **字段顺序**：命名类型的规范顺序是它的声明顺序；没有名字的结构体类型，写出的顺序是类型的一部分（顺序不同即不同类型）。参数树、检查点、`tree_paths` 的叶子顺序都按规范顺序。
- **结构类型是有限的**：结构体、元组不能直接或间接包含自身；递归的类型只能经由 `enum`。类型函数的计算因此按类型的结构终止，另有可调的展开上限。

### 5.3 `enum`

- **和类型按 Rust 的 `enum` 做**：变体有名字，可以带一个元组或一个结构体的数据，可以泛型、可以递归。

  ```camel
  type Shape = enum {
      Circle(float),
      Rect { w: float, h: float },
      Empty,
  }
  let s = Shape::Rect { w: 2.0, h: 3.0 }
  let area = match s {
      case Shape::Circle(r)     => 3.14159 * r * r
      case Shape::Rect { w, h } => w * h
      case Shape::Empty         => 0.0
  }
  type Tree<T> = enum { Leaf, Node(Tree<T>, T, Tree<T>) }
  ```

- `match` 一个 `enum` 时列全了所有变体就不必写 `case _`（与 `bool`、`T?`、`T!` 同理）。不按值的类型区分变体（那是运行时的类型判断，已排除）。现在写得出却没有值能进入的 `A | B` 退掉，`|` 只留给逻辑或。图上不增加节点种类（见 2.1）。

### 5.4 多维数组与维度

- **原生的多维数组是核心类型**：`T[维度...]`，元素类型加形状，值语义。`int[]`（一维、长度运行时才知道、可以追加）就是 `int[?]`；`f32[3]`、`f32[n, 784]`、`u8[h, w, 3]`；`int[][]` 仍是数组的数组（每行可以长短不一）。"张量"是元素为数值类型的多维数组。写 `f32[m, n]` 而不是 `f32[m][n]`：多维数组是一个整体的对象。追加只用于 `T[]`。
- **维度名在形参类型里第一次出现、且不是已有名字时自动绑定**（取代 `constas`），已有的名字是引用；只出现在返回类型里的名字是错误；只出现一次的维度名给出警告（提示写 `?`）。`?` 是不需要名字的任意大小（编译期未知，调用处做运行时检查，与 `as` 相同）；`..s` 是任意维数。维度上可以做加法与乘以常数（线性式，相等可判定），其余结果为未知。维度名只活在类型里，不能与运行时的变量同名；命名维度不产生新的实例。
- **形状未知的数组进入声明了形状的位置**：不隐式放行，用 `as` 显式转换，转换处做检查。
- **形状检查由核心负责**；逐元素运算、矩阵乘、归约等是库函数，它们的事实是算子声明上的标准标签（6.6）。稀疏、量化、分布式、表格等由库定义为命名类型，内部由核心数组组成，共同接口用泛型表达。
- 细节与理由见 [原生多维数组、内存管理与互操作](design/arrays-memory/README.cn.md)。

### 5.5 泛型

- **泛型函数按实参类型实例化。** 泛型函数是一张子图模板；每用一组具体类型调用，就实例化出一张类型全部具体的子图，函数体在这时检查。图上只有具体类型，运行时不需要类型信息。
- **类型变量用 `typeas T` 就地绑定**：在签名里第一次出现的位置写 `typeas T`，把这个位置的类型绑定为 `T`，之后直接用 `T`。

  ```camel
  func first(xs: (typeas T)[]): T { return xs[0] }   // 示意
  ```

- **泛型函数可以出现在任何期望一个函数的位置**，包括传给另一个泛型函数。编译器把它的实例化延迟到类型变量能从上下文确定时；确定不了是编译期错误，并指出哪个变量定不下来。延迟只发生在编译期，图上只有具体的实例。
- **泛型函数可以省略返回类型**，由每次实例化后的函数体推出；普通函数必须写；编辑器的悬停显示每个调用处推出的类型。
- **标准库签名的文本用类型变量，不用 `any`**（如 `print<T>(x: T)`）。参数个数可变、各参数类型不同的 Camel 函数暂不做。
- **按类型展开的操作用泛型写，不做编译器内建。** `tree_map` 这类"形状由类型决定、编译期展开"的操作，最终用 Camel 的泛型函数写在库里；为此泛型要能在编译期按结构体、元组的字段递归（设计另行讨论）。在那之前不再增加此类内建，也不另做过渡机制。原生算子的内核不在运行时读取调用的静态类型；需要按类型变化的，在编译期展开。
- `macro` 与类型计算无关，不要把类型函数建立在 `macro` 之上。
- **按结构展开的写法**（方案 A，详见 [泛型按结构展开](design/generic-structure/README.cn.md)）：`match type T { case struct => …; case tuple => …; case #leaf => …; case _ => … }` 按类型的形状在实例化时选分支；`static for (n, F) in fields T => …` 在实例化时展开字段（位置即说明绑定的种类，不写 `constas`/`typeas`；需要字段标签时写 `(n, F, tags)`）；编译期字段访问 `t.[n]`；推导式 `{ … => [n]: e }`、`( … => e )`；`static loop acc = init for (n, F) in fields T do …` 是编译期展开的折叠；可变元数 `..ts` 与展开调用 `f(t, ..ts)`，元数编译期确定、可以为 0。
- 含 `match type` 或 `static for` 的实例**自动内联**进调用者；展开失败给出带静态绑定的**实例化链**（链上的字段名连起来即路径），库可写 `static error "…"`，实例化深度上限可调；路径等由展开产生的值是运行时的值（由常量折叠），不作为编译期参数。

### 5.6 类型函数与原语

- **类型函数用专门的类型表达式来写**，在类型位置上用尖括号调用。类型总是写在 `:` 之后，所以这里的尖括号与 `with` 参数的尖括号没有歧义。带参数的类型声明就是类型函数。

  ```camel
  type Pair<T> = (T, T)                    // 示意
  func swap(p: Pair<typeas T>): Pair<T>
  ```

- **新的原语只用于主体语言无法表达的事**，以标记的形式出现，数量固定：`typeas T`、`constas n`（在签名的位置上绑定）、`typeof x`（一个表达式的静态类型）、`fields T`（一个类型的字段表）。凡是能由原语算出的（如取字段名的 `keyof`），写在库里，是类型函数或普通函数，不是关键字。
- **普通函数与类型函数在写法上对称。** `func` 定义普通函数，用 `f(...)` 调用；`type` 定义类型函数，用 `F<...>` 调用，只出现在类型的位置上，如 `type Device<T> = match type T { ... }`。类型函数没有上下文参数（`with`），尖括号里只有类型与编译期的值。区分的依据是结果：结果是类型的，用 `type` 定义；结果是值的（包括在编译期求值的判断，如 `is_numeric::<T>()`），用 `func` 定义。
- **类型函数的函数体是一个类型表达式**，不是语句块：`type P = { w: float }` 中的花括号是结构体类型，不能再兼作语句块。较复杂的计算拆成几个类型函数，或用以关键字开头的 `match type`。
- **类型只出现在类型的位置上。** 类型的位置是语法上标明的：`:` 之后、`type 名字 =` 之后、`as` 之后、`::<...>` 之中、`match type`、`fields` 之后，以及类型函数的尖括号里。类型进入值的代码只有三条路：`::<T>` 显式类型实参、`typeas` 绑定、`typeof` 取得。因此值位置上的 `f<...>` 永远是上下文参数，类型位置上的 `F<...>` 永远是类型函数调用，解析时不必知道名字指什么。
- **类型函数可以作为类型函数的实参**（高阶类型）：在类型位置上不带尖括号写类型函数的名字，即指这个类型函数本身，如 `MapLeaves<Device, Params>`。形参是类型还是类型函数，由函数体中的用法推出。
- **由字面写法算出的字段名加方括号**：推导式中 `[n]: e` 的 `n` 是编译期的值，`n: e` 的 `n` 是字面的字段名；编译期的字段访问写 `t.[n]`。

### 5.7 泛型中的名字查找

- 名字一律在定义处按词法查找；对依赖类型变量的值做运算（如叶子处的 `==`、对回调实参的重载选择）时，另在该值的类型声明所在的模块中查找重载。不看调用者导入了什么。
- 要换一种运算，把函数作为参数显式传入（如 `tree_eq<my_eq>(a, b)`）。

### 5.8 变型

- **泛型类型一律不变**：`Array<int>` 不能当 `Array<int?>` 用；隐式转换（如装入 `T?`）只发生在叶子值上，不穿透泛型类型的参数。

### 5.9 显式类型实参

调用时显式写类型参数，两层都做。

- **第一层**：只出现在返回类型里的类型参数由期望的类型推出（`let` 的标注、形参的类型、返回的位置），如 `let cfg: Config! = json::decode_as(text)`；这是 5.5 "泛型延迟到上下文能确定时实例化"的延伸。
- **第二层**：推不出来时写 `f::<T>(x)`（与 Rust 的写法相同），如 `json::decode_as::<Config>(text)`、`empty::<int>()`。按位置时，顺序是类型变量在签名中首次出现的顺序；也可以按名字写 `f::<T = int>`，不依赖位置。
- `f<w>` 仍只表示 `with` 参数与部分应用；两者都写时是 `f::<T><w>(x)`。

### 5.10 `any` 的收紧

- **`any` 只是一种简化的写法**，是类型系统成熟之前临时开的口子。**`any` 要逐步收紧**：只有在特定需求下、类型系统的表达能力暂时不够时，才临时开一个口子；凡是有明确推荐写法的情形（泛型、重载、具体类型），`any` 明确拒绝，诊断给出推荐写法。
- 现在就是编译期错误的：`any` 作 `if` 的条件、`any` 作 `match` 的对象、不经检查的 `as any as T`。
- Camel 没有在运行时判断类型的能力。

## 6. 标签与装饰器

两种机制，底层相差很大，因此写法明确区分。

### 6.1 装饰器 `@`：变换

`@d<a> func f` 即 `let f = d<a>(f₀)`，`d` 是普通函数，可以改变行为；类型装饰器是类型函数，`@D type T = E` 即 `type T = D<T₀>`；也可以装饰代码块（等价于立即调用的无参函数，行为与不加装饰的块完全相同）。一行一个，自下而上依次作用（顺序有意义，是函数组合）；重复的组合定义成新的装饰器函数。函数装饰器小写，类型装饰器大写（与类型函数一致）。

### 6.2 标签 `#`：编译期事实

- 标签附在声明或节点上，只在编译期存在，不会被"调用"，在图上不产生节点。**语言本身不赋予标签任何含义**：含义由声明它的库定义，由读取它的遍实现，后果由库负责（与第 9 节一致）；标准标签的含义写在本规范中（6.6）。
- 事实有两种：性质（不带参数，如 `#leaf`）与关系（带编译期值的参数，如 `#vjp<cube_rule>`）。多个标签写成 `#[a, b<v>]`，只有一个时可省方括号。标签名小写。
- **标签用关键字 `tag` 声明**：`export tag leaf on type`、`export tag fixed on field`、`export tag vjp<rule: func> on func`、`export tag reassociate on nodes`。`on` 列出能贴的位置：`func`、`type`、`field`、函数参数，以及 `nodes`（被标记的函数或代码块里按词法写出的节点，含分支臂、循环体、lambda，不含它调用的函数）；以后可加变体、模块。别名组 `tag finite_math = [no_nans, no_infs, no_signed_zeros, flush_subnormals]` 展开为其中各条事实。贴到未列出的位置是编译错误。
- **区域上的事实累积**：一个节点具有它所在的所有被标记区域的全部事实；带参数的同名事实以内层为准。不需要合并规则。
- **标签属于声明**（名字），与装饰器怎样包装它的实现无关。标签只能在声明处贴，不能事后给别处的声明补贴（调度是否例外另行讨论，见第 15 节）。

### 6.3 读取标签

- C++ 模块通过登记与查询接口读；编译期代码中标签是编译期的值，`match type T { case #leaf => … }`，`fields T` 同时给出每个字段的标签。
- 标签与其他名字共用命名空间，按同样方式导入，可写限定名 `#[tiles::kernel]`。
- 是否满足一个要求类标签（如 `#kernel`）由库的遍检查。

### 6.4 关键字

关键字只留给改变语义的修饰（如 `sync`、`export`、`resource`、`tag`）。`macro` 是标准标签 `#macro`（见第 8 节），不用导入即可使用。没有 `inner`、`outer`、`atomic`、`shared`：原生实现由模块中无函数体的声明表达，外部实现由模块系统承担，"作为整体、不展开"由 `#kernel` 一类标签表达，数据共享由不可变数据取代。

### 6.5 两种提前计算要分开

泛型中的 `match type`、`static for`、类型函数一定在实例化时完成，是语言语义；`#macro` 的提前求值是流水线中 `std::macro` 这个阶段做的事（第 8 节）。

### 6.6 标准标签

- **数值许可就是标签**：`#[reassociate, contract]`，不另设 `numeric` 包装与 `enum`；`finite_math` 是别名组（第 7 节）。
- **`macro` 是标准标签 `#macro`**（第 8 节）。
- **算子的事实都是标准标签**：纯度、故障、资源、数值分类、下标映射（输出的每个元素由输入的哪些元素算出）等，都是算子声明上的标准标签，含义写在本规范中；C++ 算子经同一套标签登记接口声明，Camel 写的函数由函数体自动推出。不单独设"下标语义""算子语义"等概念；现有的 `operator_semantics`、`index_semantics` 作为这些标准标签的内部存储保留。
- 切分标签 `#shard`、块内核标签 `#kernel` 见第 13 节。

## 7. 数值契约

### 7.1 规范算法

- **基准是规范算法，不是某台机器的实现**：加、减、乘、除、开方每一步按 IEEE 正确舍入，严格按程序书写的顺序，不收缩为乘加融合。按规范算法计算时（`#strict`、安全模式，见 7.4），各后端、各设备的结果逐位相同。
- **矩阵乘的规范算法是按 k 从小到大连续做乘加融合**（FMA 本身是 IEEE 规定的一次正确舍入运算，因此同样逐位可复现）；这是矩阵乘自身的规范算法，不是对"不收缩为乘加融合"的放宽。
- **定义图是规范**：融合或手写的实现必须与算子的定义图一致，故障也一致。维度可能为 1 的广播在形状确定之前不给出索引映射。
- **超越函数**（`exp`、`log`、`sin` 等）不要求跨设备逐位相同，只承诺一个写明的误差上界（以 ulp 计），逐个声明；标准库的目标是 `exp`、`log` 不超过 2 ulp；NaN、无穷、零等特殊值必须精确。

### 7.2 许可

- 许可的名字：`reassociate`（改变归约的顺序或结合方式）、`contract`（收缩为乘加融合）、`approx_math`（近似数学函数）、`change_precision`（降低输入或累加的精度，提高累加精度也属于此项）、`finite_math`（对 NaN、无穷、负零、次正规数作额外假设；是 `no_nans`、`no_infs`、`no_signed_zeros`、`flush_subnormals` 的合写）、`nondeterministic`（允许结果随调度变化的做法，如浮点原子加、用原子操作合并的 split-K）。
- **各项许可互不蕴含。** 模块只能声明算子本身做什么，不能替调用者扩大许可。
- **`unordered_reduce`** 只授予"这次归约的合并顺序可以改变"，不含其他许可。
- **精确类算子可以声明受 `finite_math` 的四项假设影响**；舍入类许可对它们仍不适用。

### 7.3 默认值：默认放宽，声明收紧

| 许可 | 默认 | 说明 |
|---|---|---|
| `reassociate` | **允许** | 改变相加的顺序与分组：并行归约、分块矩阵乘的前提 |
| `contract` | **允许** | 把乘与加合并为一次 FMA |
| `approx_math` | 不允许，用标签授予 | 近似的超越函数 |
| `change_precision` | 不允许，用标签授予 | 以较低精度（TF32、BF16 等）计算 |
| `finite_math` | 不允许，用标签授予 | 假设没有 NaN、无穷、负零、次正规数 |
| `nondeterministic` | 不允许，用标签授予 | 允许结果随调度变化的做法 |

- 默认放宽适用于张量逐元素运算，与标量相同。
- 算式优化不自动假设没有 NaN、无穷、负零或次正规数；规则仍须保留这些特殊值的行为，或检查相关显式许可。
- CPU 上按库实现的 f32 矩阵乘与 GPU 一样默认可用，条件是结果可复现（7.6，安全模式下用规范算法）；乘、加分开舍入视为累加方式的改变，属于默认允许的范围；BF16 计算只需 `change_precision`。
- 降低精度（如 f32 矩阵乘改用 bf16 或 TF32 计算）、近似数学函数、特殊值假设须显式许可。

### 7.4 收紧

- 标签 `#strict` 使所标记的函数或代码块按规范算法逐位计算，不使用任何许可（包括默认许可）。
- 整个程序用流水线参数的安全模式：`std::opt(safe_fp=true)` 与各后端的同名参数（后端关闭默认放宽，按规范算法逐位计算）。
- **`std::opt::algebra` 是独立的通用算式优化遍，`std::opt` 默认集成。** `safe_fp=true` 将算式阶段限制为严格等价的浮点变换，包括可证明等价的系数翻倍；即使节点有更宽的许可，这个阶段也不使用它来改变舍入路径。常量折叠仍按规范算法，整数仍按其位宽回绕。这是算式优化的策略选择，不是运行时算子算法或整个流水线的全局浮点开关；先前遍已经作出的改写不会回滚。

### 7.5 作用范围

- **许可写在哪段代码上就只对那段代码生效**：被调用的函数不自动继承；内联、展开定义图时许可随节点保留，并随缓存保存。
- 许可写在函数或代码块上（标签，6.2）；词法上嵌在其中的分支臂、循环体、lambda 算作同一段代码。不设模块级的默认许可；后端的入口（如 `tiles.run`）不接受许可。
- 算式优化遍可通过遍自身的参数选择数值策略（7.4）；这不构成向后续遍或被调函数传播的节点许可。
- 细节见 `docs/design/op-semantics`。

### 7.6 可复现

- 同一设备、同样配置下两次运行结果逐位相同；不得使用结果随调度变化的做法（如浮点原子加），除非授予了 `nondeterministic`。同一设备、同样卡数、同一版本的两次运行也是如此，包括 GPU 上的并行归约、按库实现的矩阵乘、多卡数据并行中跨卡的梯度求和。
- CPU 上的规范算法仍是参照答案：测试在严格模式下逐位比较，在默认模式下按误差上界比较。
- 不同设备之间逐位相同不是默认，要用严格模式。
- 跨卡求和的顺序同上。

### 7.7 特殊值与归约

- **`max`、`min` 采用 IEEE 754-2019 的 `maximum`、`minimum`**：NaN 传播，-0 小于 +0。它们满足结合律与交换律，求最大、最小值的归约不需要许可即可重排。**`relu` 定义为 `maximum(x, +0)`**。最大池化与 `log_softmax` 中的求最大值按此规则。
- **NaN 的取值**：`max`、`min`、`relu` 得出的 NaN 一律是标准的安静 NaN（打印为 `nan`）。普通算术产生的 NaN 不受此约束。
- **`argmax`、`argmin`** 按 IEEE 754-2019 的 `maximum`、`minimum` 比较：有 NaN 时返回第一个 NaN 的位置；并列时返回第一个最值的位置，+0 大于 -0。
- **归约**：对空区间的归约是故障，即使结果本身没有元素。int64 张量的求和以 int64 精确累加，溢出时回绕，与整数算术一致。
- 浮点数转成文字只有一种规则：最短、且读回来得到同一个数。`string`、`println`、`format` 一致。

## 8. `macro` 与分阶段

- `macro` 是语言核心提供的一种原生标记（标准标签 `#macro`，不用导入），用来帮助做动态的图重写：标记为 `#macro` 的函数可以被 `std::macro` 遍提前求值，把静态值算出来，形成新的静态图。
- **`macro` 本身不定义阶段，也不是必需的。** 流水线里没有 `std::macro` 遍时，macro 函数只是一个普通函数。`std::macro` 是流水线中的一个阶段，不是编译期。
- 一个值要么是编译期常量，要么是一个 macro 的返回值，只有这两种才能被 macro 处理。
- macro 函数体里有副作用时，与其他正常函数一样处理：效应在求值之时发生。这是预期行为，从实用角度无法避免。
- **macro 求值失败**：按运行时故障处理，与任何遍运行中的故障相同。（实现仍报编译期错误，改动待办，见交接任务 H2 第 6 项。）
- 在 `std::macro` 中循环至多 100 万轮（与递归上限一样可调）。
- 两种提前计算要分开（6.5）。

设计动机：Python 语言自身的动态性决定了它的灵活性，进而带来提取静态图的麻烦。Camel 希望得到静态图和完整的类型信息，以追求最好的优化空间。动态构造图的需求由 macro 系统来满足：借助多阶段图重写的流水线，先动态地构造静态图，再针对静态图做激进的优化，最后执行，或者转译成其他格式。

## 9. 遍、流水线与图重写

### 9.1 遍与阶段

- 整个运行过程被建模为多阶段的图重写。阶段由用户在命令行上组合的遍序列定义，例如 `camel xxx.cml std::macro std::opt ...`。
- 遍是把一张图变成另一张图（或消费一张图）的程序。**用 Camel 写遍的方向**：图与节点是不可变的值，遍是 `(Program) => Program!`（"遍即函数"）；改写是"一组改动 → `apply` → 新图或错误值"，不提供就地修改；模式规则写成一对参数相同的函数，左边的图是模式，右边的是替换。细节另定。
- 这种设计的出发点是工程上的方便，不是学术上的优美：一份代码，通过更改遍的组合就能做很多事——原型测试、调试、编译优化、导出部署、转译为其他格式等，而不用换一种语言把类似的逻辑再写一遍。这是图原生定位带来的特性之一。

### 9.2 显式的流水线

- **流水线由用户显式组合**，语言核心不限制遍的顺序；模块不能在导入时自动加入遍，也不能自动改变流水线。
- 不加任何用户指定的遍时，默认走 `std::default`（指向节点虚拟机；以代码为准）。
- **`std::` 前缀只给核心自带的遍**；模块的遍用模块自己的名字，别名由模块登记。
- 在命令行上写某个模块的遍（如 `onnx::export`）时，由编译器自动加载该模块；纯程序不必为了被导出而 `import` 它用不到的模块。
- **库检查自己的前提**：所需的遍不在流水线中时，给出说明要加哪个遍的诊断。
- 流水线是否可以写在源码里，尚未决定（第 15 节）。

### 9.3 遍参数

- **遍参数是流水线的通用语法**：`name(key=value, ...)` 对任何遍、调度器、模块遍都适用，参数值是 Camel 常量表达式；设置不再放在环境变量里。不是为导出单独开的功能。

### 9.4 标签的生命周期

- **标签由读取它的遍处理掉**：遍用完一个标签后，标签可以不再存在，之后的遍（如内联）不受它约束。遍的先后由用户安排。
- **库的标签可以由读取它的遍用完即去**；影响结果的标准标签（如数值许可，7.5）则留在节点上，不随遍消失。
- **标签可以声明读取它的遍**；流水线中没有这个遍时，编译器警告"标签没有效果"，使标签是否生效可以观测。
- **内联保留来源**：内联器把被内联函数的身份与它的声明标签记在节点的内联来源上；读取标签的遍若发现标签只出现在已被内联的节点上，给出"标签没有生效，因为函数已在本遍之前被内联"的警告，并说明应调整的顺序。

### 9.5 源码层规则只约束建图

- **语言核心不限制遍的顺序。** 但顺序不同，执行结果确实可能不同：遍并不保证产出同一张图，它会修改图，并且可以有副作用。**"任意遍序列下行为不变"不是 Camel 的性质，不要把它当作约定去实现或检验。**
- **源码层的限制只在"源码翻译到图"这一步生效。** `var`/`let`、`sync`、资源等规则约束的是编译器怎样构造图；图一旦得到，这些规则不再是后续图重写阶段的约束。一个遍要遵守什么约束，是这个遍自己的约定；重写之后图的语义行为是否变化，由遍的开发者和使用者各自负责。Camel 只负责编译得到图，不对遍做限制。
- 标准库里的优化遍不应把程序改错。这是普通的软件质量要求，靠测试保证。

### 9.6 优化与遍的行为

- **"开不开优化，程序的行为一样"不是 Camel 的设计原则**，语言核心也无法强行保证这种一致性。一个遍保留什么、删掉什么，由这个遍自行决定。例如同步块里结果没有被使用、但会出故障的纯计算（`let q = 1 / z`）：不加遍时故障，化简遍可以把它删掉、程序继续。这不算缺陷。
- **优化不改变图上的算子身份。** 融合、换用库实现（BLAS 等）是实现选择，记在节点属性上，图上保留原算子；新算子只在有自己的语义声明与定义图时才可出现。

### 9.7 图重写与效应

- **副作用追踪在各个遍之下的保持方式**：效应是图上的摘要（图的出口是否依赖效应、写了哪些捕获的变量），每次提交由节点重新算出并校验；遍不可能提交一张摘要与内容不符的图。遍删掉或挪动效应是否正确，仍由遍自己负责（9.5）。

### 9.8 入口与导出

- **所有遍共享 `main` 作为入口。** 导出有两种情形，取决于程序表达的是什么：
  - **程序只表达纯粹的计算意图**（这是 Camel 程序的本来面目）：程序本身不应该关心内部要怎么导出、导出什么。此时用遍的组合就能导出，例如 `camel x.cml std::macro std::opt onnx::export`，被导出的就是 `main` 所表达的计算。
  - **程序同时兼顾了计算意图之外的意图**（例如计时、跑基准测试）：这时用遍的组合去导出就不合适了。不如直接做到底，由程序内部调用算子（如 `onnx.export_model`）对自己的某个子图完成导出。
- **`main` 可以带参数。** `main` 与其他函数一样是一张子图，它的参数就是这张图的输入：导出时是模型的输入（形状取自带形状的张量类型），运行时由外部给值（命令行；缺少时给出带位置的明确错误，不用零或随机数代替），求梯度时是可以对其求导的量。`main` 不带参数时导出的是没有输入的常量模型，允许。返回单个值是一个输出；返回元组或结构体则展开为多个输出。
- **只有显式声明了返回类型的 `main`，它的返回值才算程序的结果。** 纯的 `main` 的返回值通过命令行已有的 `-o` / `--output <file>` 输出，默认是标准输出，不另设专门的选项。
- 导出（如 ONNX）是转译遍，同样建立在遍机制之上。**导出遍不必做太多检查**：能翻译就翻译，翻译不了再报错，不追求学术上的洁癖。导出遍可以做必要的适配性化简，但不应成为主力；主要的求值与化简应由 `std::macro` 和优化遍在它之前完成。

### 9.9 自动微分

- **自动微分是建立在遍机制之上的库，不是语言核心。** 它有自己的约束：没有执行过 macro 的图信息不足以做微分，所以使用 `grad` 等需要流水线里有 `std::macro`。这是库的前提条件，不是语言核心的约束；不满足时库应给出清楚的诊断。
- 被求导的函数与 `var`：见 3.5。
- **穿过循环求导**：反向需要正向每一轮的中间值（残差）。正向循环把每轮的残差作为收集输出保存（值，不是闭包），附一份说明各槽位是哪个残差的清单；反向是一个按轮次倒序的循环。每轮 O(1)，总计 O(n)。正向循环的轮数可以由条件决定。
- **残差不设上限**：与普通数组的增长相同，内存耗尽按资源耗尽带位置报告；不另设轮数上限。以后可用重算类标签（检查点）把内存降到 O(√n)，残差的设计不排斥它。
- **循环遍历或捕获的数组依赖被求导的参数时拒绝**，带位置的诊断点名 `loop` 与那个数组（数组没有切向量，悄悄丢掉梯度会得到错误结果）。
- **循环体与条件里有副作用时沿用现有规则**：副作用只在正向执行，反向是纯的；"读可微类型的 `var` 即拒绝"的检查扩展到循环的条件与循环体，诊断点名 `loop`。
- **带循环的梯度的 ONNX 导出另作一项**：残差是值，导出时映射为 `Loop` 的 scan 输出与反向 `Loop`（必要时用 ONNX 的序列类型容纳参差的嵌套循环）。

### 9.10 调度器、后端与发布

- **并行调度器把没有可并行之处的子图交给字节码解释器执行**，并按同一规则计数递归上限：调高 `--max-recursion-depth` 时，深的非尾递归在 `std::prl` 上与在 `std::fvm` 上一样跑完。
- 发布包的指令集基线是 `x86-64-v2`。

## 10. 模块与库

### 10.1 模块与图

- **模块顶层的代码不会默认执行**：Camel 不是命令式的脚本语言。顶层的语句与别处一样按依赖求值。
- **模块可以导出值。** 模块本身是一张 `__root__` 图；全程序只有一张 `__root__`，各模块顶层的节点都在上面，函数经捕获端口取值；捕获按"模块 + 名字"绑定，不按名字在调用处查找。模块顶层的一个 `let` 就是 root 上的一个节点，被依赖才求值。这样没有跨图的节点引用。合并的具体做法先出设计说明。C++ 模块也可以导出值（`math::pi`）。
- **顶层的值在 `main` 开始之前求值，依据是静态的依赖**：`main` 沿调用链静态可达的函数用到的顶层值都会求值，运行时是否走到用它的那条臂不影响。
- **模块顶层的 `let`、`var` 与书写顺序无关，只看依赖。** `let area = pi * r * r` 可以写在 `let pi` 之前；顶层值之间成环是编译期错误。函数体里的局部 `let` 仍是先声明后使用。
- **模块可以互相导入。** 为此加载分两个阶段：先收集所有模块的声明，再建函数体。模块导入自己是允许的，没有效果；类型跨模块成环给出成环的诊断并列出环。
- **不能导出 `var`**；导出读写它的函数。被导入模块里的 `main` 是普通函数。

### 10.2 命名空间与名字

- **命名空间块里可以不带前缀使用同一块及外层块里的名字。** 命名空间块里可以有值：`namespace Config { export let limit = 10 }`，用 `Config::limit`；与模块顶层的 `let` 只差名字里的路径。重开同一个命名空间块，前一块里的 `using` 不带到后一块。
- **`using namespace`**：可以对本模块的命名空间使用；只在它所在的块里生效（写在函数体里就只对那个函数生效）；两条 `using` 带来同名同签名、无法区分的名字时，在使用处报错。
- **名字的优先级只有一条规则**：局部 > 本模块（所在命名空间、外层命名空间、模块顶层）> 按名字导入的 > `using namespace` 带来的 > 内建。取第一个有这个名字的层；同一层里同名的函数合成重载集，签名相同是错误；跨层不合并。运算符重载例外，各层合并。
- **`import a from m` 是从 `m` 引入名字 `a`**，等价于 `import { a } from m`，与语言文档一致；给模块起别名写 `import m as x`。**导入可以改名**：`import { find as str_find } from str`。两个导入的名字冲突是编译期错误，不得静默取其一。允许 `import { … } from m::N`。不实现 `use`，退掉这个保留字。
- **模块可以用自己的名字限定自己的东西**：`module shapes` 里写 `shapes::area` 与写 `area` 相同。
- **诊断、调试器、语言服务器与图名一律显示完整的名字** `模块::路径::名字`，不引起歧义时省略模块名。名字有歧义时列出各个限定候选，不论导入给模块起了什么别名。

### 10.3 模块缓存

- **编译好的模块可以缓存**（`.cmo`，cached module object），使一个模块不必重新编译。每个模块的缓存是以该模块为根的一张图；它是为了方便与加速，不必等同于实际编译的最终结果。C++ 模块沿用同一个扩展名，两者靠文件头区分。
- 缓存放在源文件旁的 `__cmo__/` 目录里；先默认关闭；命中缓存的模块不重放编译期警告。导入方的缓存在下列任一项变化时失效：导出函数的签名（含推断出的返回类型）、它间接用到的模块级值、它的效应、泛型函数的函数体。

### 10.4 C++ 原生模块的位置

- **C++ 原生模块合法，但不要过度依赖**：能用 Camel 表达的尽量用 Camel，除非有明确的理由（性能、灵活性等）；实现中暴露的表达问题逐一讨论，公共的需求吸纳进语言核心。

### 10.5 库边界

- **标准库的边界**：必须接触系统或性能敏感的原语用 C++ 算子；建立在原语之上的组合逻辑用 Camel 写。Camel 写的库是子图，遍看得见；C++ 算子在图上是一个不透明的节点。
- **模块接口**：从内部头文件里整理出一层公开的 C++ 接口，按版本承诺兼容；其余内部头不作承诺。
- **内存管理的方式不进入语言的语义**：对象没有可观察的身份，回收的时机不可观察，C++ 算子通过句柄接触对象。各后端可以选适合自己的方式；后端可以少回收甚至不回收垃圾，回收的时机与是否回收都不可观察。
- **垃圾回收**：Camel 原生的小对象可以走分代管理（可以移动）；涉及外部接口时，用 Camel 原生对象来管理外部指针，外部内存不进可移动的堆。模块不得跨调用保存指向 Camel 对象的裸指针。分代回收对 C++ 算子作者的约束可以接受。落实顺序：先审计模块并立下句柄规则，再在解释执行的后端上启用分代并做压力验证，即时编译等栈映射做好之后再打开。分代回收在可用之后默认开启。
- **有身份的东西要列明**：`var` 单元、经 `var` 参数就地修改的对象、外部库包装的对象（Python 对象等）；其余的值没有可观察的身份，后端可以随意复制或共享。对象头里不加类型字。
- **内存管理分三层，都是实现方式**：编译期规划（生命周期能从图上看出的数值缓冲区）、引用计数（其余的数值缓冲区）、分代追踪回收（其余对象，含图与快照）。**紧凑的数值缓冲区里只放数字、不放引用**（由类型系统保证），因此缓冲区之间不会成环、可以零拷贝交给外部。**计数为 1 时，"返回新值"的数组操作原地进行，这是有保证的行为。** 数值数组的运行时表示兼容 DLPack（数据指针、设备、元素类型、形状、步长、偏移），与 PyTorch、NumPy、CUDA 库零拷贝交换。Python 嵌入 Camel 时形成的跨语言环第一期不回收。小型逻辑计算不得因此变慢，以性能基线核对。详见 [原生多维数组、内存管理与互操作](design/arrays-memory/README.cn.md)。

### 10.6 `std::cpp`

- **`std::cpp` 的目标是生成可以脱离运行时独立部署的程序。** 无法同义转换的情形可以引用 Camel 的运行时模块，但要尽量做干净。生成的程序要给出带源码位置的故障、遵守递归上限，尾调用不使栈增长。生成的故障报告与解释器逐字相同；递归计数精确（与各后端一致）。
- `std::cpp` 生成的模块接口用标准 C++ 类型，不暴露运行时的内部类型。
- `println<fmt>` 多出的空行、`print<fmt>` 多出的换行是解释器的缺陷，修掉解释器；去掉 `std::cpp::bench`；生成程序里的 `map`/`filter` 先串行；`main` 的参数用 `--arg name=value` 给出，与命令行一致。

## 11. 标准库约定

### 11.1 字符串与 `Bytes`

- **`string` 保证是合法的 UTF-8**，下标与长度按码点计；字节序列用内建类型 `Bytes`，两者之间显式编码、解码。`string` 只表示文本；文件接口分文本与二进制两套。另外提供按码点读写的算子。
- 字符串也有 `contains`，写法与数组的一致：`'hello'->contains<'ell'>`。

### 11.2 `Json`

- `json.decode` 返回自描述的 `Json` 类型，并提供 `decode_as<T>`（显式类型实参见 5.9）。
- 坏的 JSON 文本，`decode` 返回 `Json!` 的错误值，不是故障。
- `Json` 的访问器接受 `Json?` 与 `Json!`，以便链式取值（解析失败也能链式取值）；`as_float` 接受整数；`get<下标>` 越界给 `null`。
- **`Json` 的访问器接受 `Json!` 时，错误原样传下去**：`decode(text)->get<'a'>` 的类型是 `Json?!`，用 `!!`、`??` 处理。太深的文档报 `JsonTooDeep`（与"文本不合法"区分），默认深度上限 10000，以后作为 `decode` 的可选参数开放。

### 11.3 集合与排序

- **映射与集合做成内建类型。** 不新增字面量，用已有的数组字面量加 `as` 转换（与 `t as Tensor<...>` 同一种写法）。操作一律返回新值；查找不到的结果为空。

  ```camel
  let m = [('a', 1), ('b', 2)] as Map<string, int>   // 示意
  let v = m['a'] ?? 0
  ```

- 映射的遍历与打印按键排序；能作键的类型是整数、布尔、字符串，以及它们组成的元组。
- **`append` 返回新数组，不修改原数组**：`let ys = xs->append<5>` 之后 `xs` 不变；要"追加到变量上"写 `acc = acc->append<5>`，与 `x = x + 1` 一样。就地改写只是实现层面的优化（旧值不再被使用时可以在原处追加），不进入语义，也不另设显式的就地算子。其他标准库算子同此。纯运算的结果没有被使用（如写成语句的 `xs->append<5>`）是编译期错误，并提示改写为重新绑定。
- 返回新值与就地修改不用两个名字区分：只有 `sort`，它返回新数组；`xs = xs->sort` 在旧值不再被使用时就地排序，与 `acc = acc->append<v>` 是同一种实现层面的优化。张量保留显式的就地算子，数组不设。
- **`enum` 可以作映射的键与集合的元素**，当它所有字段的类型都可比较时；顺序先按变体在声明中的先后，再逐字段比较。

### 11.4 调用风格

- 被处理的值是普通参数，其余是 `with` 参数（`'a,b'->split<','>`、`xs->take<3>`）；两个参数地位对等时都是普通参数（`merge(m1, m2)`）。映射与集合的操作照此只保留一种写法。

### 11.5 输出与格式

- **程序的输出与 `fs` 写出的文本在各平台上是相同的字节**，Windows 上不写 `
`。浮点数转成文字的规则见 7.7。
- **字符串插值用反引号**：`` `step ${i}: loss ${l:.4f}` ``，`${表达式}` 插值，可选的 `:格式` 与 `format` 的格式说明相同；普通的 `{` 不需转义；可以跨行；是 `'...'->format<...>` 的简写，格式说明与类型不符在编译期报错。

## 13. AI 技术栈

### 13.1 调度

- **倾向（不是禁令）**：Camel 源码无损地表达计算的意图；在哪里算、怎么算这类与环境相关的内容（分块、布局、放置、内存策略），原则上不写进源码，由执行时的上下文注入（遍参数、调度文件），格式与粒度由读取它的库决定。已有的 `@gpu` 等做法保留。`@gpu` 是编译期标注：给函数的节点记上设备偏好，由 Tiles 的遍处理；没有读取它的遍时编译器给出警告（9.4）。
- **为了性能上限，允许在源码中直接写调度**：上一条是倾向，不排斥专家路径。块级内核（Tiles 路线第 6 节的 `Tile<T,[形状]>` 与 `#kernel`）把块形状写在源码里，由作者直接控制，与由 Tiles 自动决定的高层路径并存。
- **调度的粒度到函数为止**：要更精细，就把那一段提成子函数，用按函数的调度。内联之后，节点上记录的内联来源仍能把它们对应回原来的函数。自动调优按计算的结构身份（算子、形状、类型、前后关系）记录结果，不依赖名字。语言不提供"给某一步计算起名字"的机制。
- **调度也可以用 Camel 写**：意图写成一个函数，在另一个模块里用变换函数（或装饰器）调度它，不一定只能靠命令行上的遍组合。

### 13.2 低层计算

- **低层计算也用 Camel 的图表达**，不另造中间表示：物理操作（块的加载、块内矩阵乘、同步等）是后端库登记的算子，带语义声明，能给出时带 CPU 上的参考实现；逐级降低都是图到图的改写，最后一步才打印成目标代码。每一级降低后的图在可能时仍可在 CPU 上运行，与参照答案核对。

### 13.3 设备与内存

- `Device<T>` 保留，对结构体与元组按字段分配，`Device<{ a: A }>` 与 `{ a: Device<A> }` 是同一个类型。搬运是普通的有副作用的操作，可以在代码中显式写，可以由 Camel 写的变换函数作用于一个函数值而插入（"遍即函数"），也可以由优化遍自动完成。
- 异步不进入语义：顺序由数据依赖与 `sync` 决定，流、事件、重叠执行是后端的实现。
- `std::tiles` 的上传、区域执行、下载是纯计算，设备内存是不可观察的分配；相同的区域调用可以合并。

### 13.4 分布式

- 切分写成标签 `#shard<[轴名, ...]>`，可贴在函数参数上；轴名是抽象的，轴的大小在执行时注入；同样的信息也可以写在调度文件里。标准库的 `shard` 遍推导每个结果的切分、插入通信（普通的有副作用的算子）、报告不一致；推导不下去的算子（没有声明下标映射的原生算子）退为先收集再计算，结果正确但较慢。类型系统不变。跨卡求和的顺序按 7.6。

### 13.5 训练基础设施

详见 [训练基础设施设计](design/training/README.cn.md)。

- **参数树**：标准库提供 `tree_map`（可同时作用于多棵同构的树，对位的叶子作为多个实参传给回调）、`tree_unzip`、`tree_reduce` 等操作，作用于由结构体与元组嵌套成的值，叶子顺序为深度优先、按字段声明顺序；叶子边界永远由树实参的类型决定（`tree_map` 以第一棵树为准，`tree_unzip` 以给出的参照树为准），不由回调的形参类型决定；树的形状由类型决定，操作在编译期展开为逐叶的普通节点。
- **参数树的路径**写作 `blocks.0.w`，根是空路径；检查点中的名字与 `tree_paths` 的结果逐字一致；`save_tree`、`load_tree` 属于 `tree` 模块。
- **无状态随机数**：在现有带全局状态的随机数之外，提供由键决定的随机数（`key`、`fold`、`split`、`normal`、`uniform`、`randint`）。它们是纯函数，不是外部效应；规范算法为 Philox4x32-10，整数与均匀分布的结果跨设备逐位相同，正态分布按超越函数的 ulp 上界。

### 13.6 部署与数据管线

- 部署不另设格式：现有后端的格式够用，冻结后的程序也可以直接导出为 `.cml` 运行。
- 数据管线不需要语言层面的新东西，由标准库提供读取与分批工具。
- **网络与流**：`net`、`http` 模块（底层原语为 C++）；`Stream<T>` 是标准库类型（句柄类型）：按需拉取、可能无限，`for` 可以遍历，作用于流的 `map`、`filter` 等是惰性的，背压由拉取自然实现；窗口、按键聚合、合并、分批由库提供。表格兼容 Arrow C 数据接口，与 Pandas、Polars、DuckDB 零拷贝交换。长期方向是多机分布式运行时，批处理与流处理用同一个模型。详见 [网络、长耗时副作用的并发与流](design/io-concurrency-streams/README.cn.md)。

## 14. 容易出现的误读

以下都是实际发生过的误读，修改代码或文档前请对照：

1. 把"同步块之外未被使用的效应不执行"当成缺陷去修，或改成报错。——这是预期行为。
2. 仍按已退役的 `wait` 与前缀 `sync func` 来理解效应的排序。——它们已被"同一资源自动有序"与推出的 `uses` 取代；函数体后缀的 `sync`（函数体是同步块）保留。
3. 认为被同步块调用的函数，其函数体内的效应会因此执行。——函数的行为由它自己的子图决定。
4. 把 `var` 参数实现成传值再在返回时拷回。——Camel 默认是引用。
5. 把 `let` 的不可变实现成运行期的内存保护。——它是编译期校验。
6. 把 macro 函数体里的副作用当作例外或错误。——与普通函数一样处理。
7. 认为没有 `std::macro` 时 macro 函数不能运行。——此时它是普通函数。
8. 把"任意遍序列下行为不变"当成语言的约定，并据此把遍序敏感判为缺陷。——遍可以改变图并带有副作用。
9. 把自动微分的前提条件当成语言核心的约束。——它是库的约束。
10. 从派生的特性里挑一个当作 Camel 的"核心卖点"（例如"一份代码多种用途"）。——核心是图原生，其余是自然产物。
11. 为了让某个测试通过而改变语义。——先确认语义，再判断是测试错了还是实现错了。

## 15. 尚未决定的问题

遇到下列问题请向语言作者提问：

- 类型表达式语言的具体内容：预留的类型运算符 `&`、`\`、`+`、`-`、`^` 与 `ident of T` 各自的含义与去留。
- `typeof` 作用于常量值时的含义，以及它在泛型里的用法。
- 类型函数求值失败或不终止时的处理。
- 同一个可变对象在同步块之外被多处通过引用写入时的行为。
- 能否在声明之外给别处的声明补贴标签（调度是否例外）。
- **并行的 `map` 出了故障之后，下标更小、还没开始的元素是否仍然执行**（`parallel-fault-lower-elements`）：
  `range(0, 64)->map<bad>` 每个元素都出故障，而工作线程恰好先跑了第 40 个。现在的实现：只有下标大于 40 的不再开始，0 到 39 仍然执行，于是报的总是第 0 个，与线性后端相同、每次运行一致。
  候选：出故障后一律不再开始任何元素；这样"下标最小的"只在碰巧已开始的元素里取，每次运行可能不同。
- **内建算子的实参是否自动装入**（`entering-operator-args`）：`xs->append<5>`（`xs: (int?)[]`）、`len([])`。
  现在的实现：不装入，前者要写 `5 as int?`，后者的 `[]` 没有元素类型也不报错；因为内建算子的形参类型由 C++ 的类型规则从实参算出，调用之前没有目标类型。
  候选：让类型规则能报出"我接受的类型"，使内建算子与用户函数一致。
- **在源码中声明流水线**：是否允许入口文件显式写出流水线（如 `pipeline std::macro, tiles::compile, std::nvm`），与命令行一样明确、可见，并随代码提交。
