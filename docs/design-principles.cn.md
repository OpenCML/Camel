# Camel 设计原则与语义裁定

本文档记录语言作者对 Camel 根本定位与语义问题的明确说明，只陈述**现行**的规则。它是规范性的：当实现、其他文档或某次测试结果与本文档冲突时，以本文档为准，冲突之处应作为缺陷或待办记录下来，而不是据此修改语义。

**修改 Camel 的语义、遍、调度器、导出器或自动微分之前，必须先读本文档。** 文中没有覆盖或仍标为"未定"的问题，应向语言作者提问，不要自行选择。

规则按主题组织。每条裁定是何时、怎样定下或改定的，见 [设计原则裁定记录](design-principles-log.cn.md)（按时间排列，含已被取代或撤回的说法；其中的旧编号与本文档的新编号的对照表在该文件开头）。文中标为"倾向"或"原则上"的说法不是硬性规则，不要把它们当作禁令去实现或检验。

## 1. 根本定位

Camel 最核心的特征是图原生。其他性质都是这个定位的自然产物，不是另外附加的功能。`ZEN` 的八条是这一定位的提纲：前两条讲图是根本，其余六条是推论。

- **只建模计算意图。** Camel 的程序描述"要算什么、谁依赖谁"。它不主动承载 CPU 密集型的任务，也不承载各类配置；这些由算子、运行时和遍去处理。正因为如此它才自由灵活。
- **图是原生的，不是产物。** 图不是从别的语言的代码里捕获或恢复出来的，源码写下的就是图。
- **遍即函数，函数即图，执行即重写到空图。** 遍是函数变换，函数是图；从编译期求值、优化、导出到执行，都是对图的多阶段重写，产生空图时执行结束。
- **语言元素与图直接对应。** 理解或设计任何语言构造，都要先回答它在图上是什么。判据：语法元素必须和图有稳定的映射关系，这才体现图原生；一个构造在图上长什么样如果取决于它里面写了什么，它就不该进语言。
- **与传统控制流有所区别。** 不用语法糖去模拟传统的控制流，保持语法元素和图节点之间简单的映射关系。（这不排斥含义没有歧义的简洁写法，例如列表推导。）
- **不限于 AI。** 图上建模的是计算的意图与依赖，HPC 与各类仿真计算同样适用。对外的定位表述：Camel 是图原生的通用编程语言，AI 是它首要的应用领域；不再自称面向 AI 的领域专用语言。在论文的视角下 Camel 不主动承载 CPU 密集型的工作；在通用语言的视角下，它仍然要有一定的通用性。两种视角并存。
- **只有一门语言。** 根据类型算出类型、按类型的结构生成代码，都用主体语言写：类型是编译期的值，类型函数是在编译期运行的普通函数，用的是与值层相同的构造（见 [泛型按结构展开](design/generic-structure/README.cn.md)）。不另设一套类型层语言（如 TypeScript 的条件类型、映射类型、`infer`）。图的变换、规则、调度同样用 Camel 本身写。
- **简写可以有，语义只有一套。** 简写（如装饰器）是给库作者用的机制，可以存在，但只能是同一语义的另一种写法，不得另带规则。
- **红线要少，且每条都有强制机制；** 其余的是倾向或质量要求，按倾向记。当前的红线清单（每条后面是强制它的机制）：

  1. Camel 程序造不出结构上坏的图 —— 提交时的整体校验。
  2. 后端只看到可执行状态的图（每值一写法、无环、类型正确）—— 后端与导出遍入口的检查。
  3. 会出错或有效应的节点不被移出它所在的区域 —— 提交时的校验。
  4. 规则在入库前通过随机检验；分析满足合并律与单调性 —— 测试工具枚举 `rule`、`fact` 声明。
  5. 图与源码往返一致 —— 对全部测试用例与随机程序的往返测试。
  6. 结果确定（同样的输入、同样的配置，结果相同）—— 并行组合子的固定提交顺序；饱和与提取按编号决定；重复运行比对。
  7. 同一设备上数值结果可复现（未授予 `nondeterministic` 时）—— 重复运行逐位比对。
  8. 承诺（`pure`、`uses`）不被违反 —— 编译器检查。
- **内测阶段不考虑兼容成本。** 旧写法直接删除：不留别名、过渡层，也不留指向新写法的诊断或说明；删除之后它就是普通的未知名字或语法错误。
- **不留过渡，也不记录已经删掉的东西。** 过渡只存在于分支上，合入主线时已经删干净；文档按目标语言写，不标注“目标”“尚未实现”；诊断、注释、文档不写任务编号、裁定日期或指向裁定记录的引用，面向用户的诊断可以引用设计原则或语言参考的小节；编译器里没有“等以后”的拒绝——要么实现，要么变成普通的语法错误，要么换成说出语言规则本身的具名诊断。
- **自己的库尽量用 Camel 写**，以暴露语言的不足并吸纳进核心（见 10.4）。

## 2. 程序与图

### 2.1 语言元素与图的对应

| 语言元素 | 在图上是什么 | 由此得到的行为 |
|---|---|---|
| 表达式、算子调用 | 节点与数据边 | 按依赖求值；没有被依赖的节点不执行；互不依赖的节点可以乱序或并行 |
| `sync` 块 | 相邻语句之间的同步边 | 块内按书写顺序执行 |
| 同一资源的效应 | 同一函数体内、用到同一资源的效应之间的顺序边 | 按书写顺序执行（3.3） |
| 函数 | 子图 | 行为由函数自己决定；调用只是把子图节点放进更大的图里，不改变它的结构 |
| `var x = v`、读、赋值 | 建立单元、读单元、写单元三种算子节点；`x` 这个名字绑定的是单元 | 可变的是单元，不是值 |
| lambda、函数作为值 | 一个函数常量；有捕获时再加一个把捕获的值装进去的节点 | 函数值就是"图 + 捕获的值" |
| `f<w>` 作为值（部分应用） | 一个捕获了 `w` 的函数值，它的图把剩下的参数与 `w` 一起交给 `f` | 与 lambda 是同一种结构 |
| `macro` 函数（标签 `#macro`） | 可以被提前求值、结果物化为图中常量的子图 | 动态地构造静态图 |
| `if`、`match` | 一个分支，每条臂一张子图 | 只有被选中的臂求值 |
| `a ?? b`、`a !! b` | 一个分支：条件是值上的一位标记（为空／出错），两个臂分别是原值与替代 | 与 `if` 是同一种结构 |
| `x -> f`，`x` 是 `T?`／`T!` 而 `f` 只接受 `T` | 一个分支：为空／出错的臂原样交出，另一臂调用 `f` | 与 `??`、`!!` 是同一种结构 |
| `a && b`、`a \|\| b` | 一个分支：`a && b` 即 `if a then b else false`，`a \|\| b` 即 `if a then true else b` | 右边是一条臂，只在需要时求值；不可重载 |
| `a & b`、`a \| b` | 普通的算子节点 | 两边都求值；可以重载 |
| `if x != null then A else B` | 与对 `x` 的 `match` 是同一张图：进入非空那条臂的是拆开后的值 | 收窄不是另一种机制 |
| 值进入 `T?`、`T!` | 每进入一层一个装入节点 | 装入只在需要它的位置发生 |
| `enum` 的构造与 `match` | 构造是装入一个标签；`match` 是取标签、分支、在臂里取出数据 | 图上不增加节点种类；`T?`、`T!` 可以看作内建的两个 `enum` |
| `fail<'Kind'>(message)` | 一个产生故障的算子节点，类型是底类型 `never` | 与除零、越界的故障是同一种 |
| 故障隔离（`attempt`） | 对子图的一次带标记的调用 | 故障的边界就是子图的边界，结构不随子图的内容变化 |
| `map`、`filter`、`reduce`、`foreach` | 一个算子节点，元素函数作为函数值传入 | 高阶算子不是新的节点种类 |
| 泛型函数 | 子图模板；每用一组具体类型调用，实例化出一张类型全部具体的子图 | 图上只有具体类型 |
| 类型函数 | 建图时求值，图上不留节点 | 运行时不存在"类型"这种值 |
| 标签 `#` | 声明或节点上的编译期事实，图上不产生节点 | 在编译期存在，不会被"调用" |
| `loop` 表达式 | 一个 `LOOP` 节点，带条件区域、循环体区域与状态边 | 状态由循环头决定，不取决于循环体里写了什么 |
| 模块顶层的 `let` | 公共 root 图上的一个节点 | 被依赖才求值；导入不执行任何代码 |
| 函数用到模块顶层的值 | 函数图上的一个捕获端口，绑定到"模块 + 名字"，值沿调用传下来 | 不出现跨图的节点引用 |
| `import { f } from m`、`import { v } from m` | 不建任何节点：调用 `f` 是一次普通的调用；`v` 在 root 上是一条普通的边，在函数里是捕获端口 | 导入不执行任何代码 |
| 导入泛型函数 | 不建任何节点；每组类型一个实例，全程序共用，属于声明它的模块 | 图上只有具体类型 |
| `namespace`、`using namespace`、`m::f` | 图上没有任何痕迹，只决定名字解析到哪个"模块 + 限定名" | 命名空间是名字的一部分 |
| 遍 | 把一张图变成另一张图（或消费一张图）的程序 | 开放的流水线 |

### 2.2 图的结构

- **不应当出现跨图的节点引用。** 一张图里的节点不指向另一张图里的节点，图与图之间只有"图引用图"（调用）这一种关系。任何设计都要先过这一条。
- **对外的节点种类**：`DATA PORT OPER FUNC CALL FILL ACCS CAST COPY BRCH JOIN LOOP GATE`。`map` 一类高阶算子是算子节点，由算子表声明“会调用子图”；`attempt(f)` 是函数变换，它的结果函数的每次调用是一次带标记的调用（2.1）。
- **分支臂的两种形态都是合法的图**：前端产生"每条臂一张子图"；内联之后臂的节点并入外层图、成为分支与汇合之间的一段，也是合法的。
- 图存储与图 API 的细节见 [图存储与图 API（第二版）](design/graph-store/README.cn.md)。

### 2.3 图的数据模型

- **图的数据模型是最重要的一项设计**：它要定义清楚、稳定、可以对外。模块缓存、用 Camel 写遍、把计算代码编译成 GPU 内核、`std::cpp` 都建在它上面。
- **节点属性属于对外的图数据模型**，用 Camel 写的遍也能读写。
- **编译核心的内部表示可以彻底重构**，以求全流水线的速度与内存效率。

### 2.4 容量与默认值

- **单张图没有容量上限。** 编号一律 32 位（见 [图存储与图 API（第二版）](design/graph-store/README.cn.md)）。
- 图、类型、元数据三块空间的总上限各 256 MB；停不下来的展开另由导出器自己的轮数预算刹住。

### 2.5 图与源码的往返

- **图与源码的表达能力相同**：任何合法的图都能写成 Camel 源码，写回再编译得到同一张图（名字、源码位置等不计）。由往返测试强制（全部测试用例与随机生成的程序）；写不回来的图结构视为语言的缺口，需要补上。
- 标准遍 `std::cml` 把当前的图导出为 Camel 源码：产物尽量可读，但不以人类易读为约束；泛型实例写成具体类型的函数，被内联的部分不必还原；大的常量放在旁边的数据文件中由源码引用。

## 3. 求值与效应

### 3.1 按依赖求值

默认情况下求值由依赖驱动，没有固定的执行顺序。

- **同步块之外、结果没有被使用的带效应的调用不会执行。** 这是按依赖求值的自然结果，是合法的预期行为，不是错误，不需要报错。编译器足够智能时可以给出警告。
- **一个节点执行，当且仅当这次运行用到它**。只被某条臂用到的节点，只在那条臂被选中时执行；循环体里才用到的节点，零轮时不执行。实现可以按固定的计划执行，但计划必须与此一致：只被一条臂读到的节点下沉进那条臂，被几条臂读到的复制进每条臂（每次只执行一份），纯且不会出故障的节点可以留在外面。
- **顺序不决定是否执行**（形式化 F2）：同一资源上的先后、同步块的先后只约束本来就执行的效应，不会让一个效应因为排在别的效应前面而执行。图上表示顺序的关系只排序，不传递"被用到"。
- 资源只决定执行者之间的顺序，不决定是否执行（3.3）。
- **效应函数也返回值。** `println(x)` 返回 `x`，方便写 `x->println->f` 这样的调试代码，看数据在每个阶段的样子；它不是让效应执行的机制（值被用到时它自然执行）。
- **图上的边有三种**（详见 [图上的边](design/effects/edges.cn.md)）：
  - **数据边**：值从哪来。一个节点的输入是一列有序的端口，每个端口带一个**角色**——普通参数或上下文参数（`with`），角色来自被调函数的签名；边本身只有一种。不关心角色的遍（删死代码、合并公共子表达式、调度、规则的结构匹配）只看到一种边，关心角色的遍（部分应用、求导、特化、导出）读端口的角色。
  - **同步边**：同步块里相邻语句之间；后一条在前一条之后，并且前一条因此被用到。
  - **顺序边**：只排序——两端都执行时前者在后者之前，不传递"被用到"。来自同一资源上的效应之间、同一 `var` 的写与写之间，以及同步块里的调用被内联后、链上相邻语句与函数体里的效应之间。
  - **纯计算没有顺序边**；纯且不会出故障的计算也不在同步链上（同步链只连带效应或可能出故障的语句，3.4）；纯计算只有数据边，唯一的例外是作为块的值接收链尾的同步边；图上的边只有数据边、同步边、顺序边三种。
- **执行规则**：从程序的结果出发，沿数据边或同步边能到达的节点执行，顺序边不参与；要执行的节点之间，先后同时遵守三种边。本节的"用到才执行"与"顺序不决定是否执行"都是这条规则的推论。
### 3.2 函数的行为由它自己决定

函数编译后得到自己的子图。外部调用只是把这个子图节点安排在更大的图中，不会改变它自己的结构。

```camel
func log(x: int): int {
    println(x)          // 结果没有被使用，函数体不是同步块：不执行
    return x + 1
}

func main(): int sync {
    let a = log(1)
    let b = log(a)
    return b            // 返回 3，什么都不打印
}
```

`main` 的函数体是同步块，两次 `log` 调用按顺序执行。但 `println` 属于 `log` 自己的函数体，那里不是同步块，所以不执行。要打印，`log` 应声明为 `func log(x: int): int sync { ... }`。
- **纯计算是确定的**：同样的输入一定得到同样的结果。结果会随时间、调度或外部而变的操作，要么是效应（如读时钟 `now()`），要么在声明里写明不确定（如 `first_of`、按到达顺序的 `merge`）。复用结果的优化（增量计算、合并公共子表达式）依赖这一条。

### 3.3 资源、`uses` 与 `pure`

- **用词**：这整套机制叫**资源效应系统**。**资源**是效应作用的对象（控制台、文件、某个 `var`……）；**效应**是对一个资源的一次访问（读或写）；`uses R` 声明一个函数的效应集合，`pure` 是空集合。不用"副作用"一词——在 Camel 里效应与值一样是程序明写的结果，不是附带的。按资源标注效应的做法出自 Lucassen 与 Gifford 的多态效应系统（FX）。

- **资源**：对它的访问需要排序的东西。资源类别由库用关键字 `resource` 声明（`export resource fs`），可以分组（`resource io = [stdout, fs]`）；与其他名字共用命名空间，按同样的规则导入，可写限定名。标准库最基本的资源（`stdout`、`stderr`、`stdin`、`fs`、`clock`、`env`）默认可见。
- **每个 `var` 自动是一个资源**；函数的 `var` 形参是资源参数，在调用处对应调用者传入的那个变量；闭包捕获了 `var`，其函数类型就带着这个资源。
- **资源是函数类型的一部分**：`func save(p: Params): unit uses fs { ... }`。`uses` 后接用逗号分隔的资源列表，不加括号。原生算子（模块中无函数体的声明）在签名中写 `uses`；没有写的原生算子视为使用"全局"资源，与一切效应保持顺序。
- **Camel 函数的资源由编译器推出**（函数体内所调用者的资源之和，递归时求不动点），不必手写；编辑器的悬停与文档以限定名显示推出的资源。显式写 `uses` 是承诺，函数体超出即为编译错误；导出函数推出的资源发生变化时给出警告。
- **效应以资源声明为准**；签名里的 `var` 由资源声明检查，不一致是声明错误。
- **`pure`** 承诺函数不使用任何资源，由编译器检查；可以写在函数声明与函数类型上（如要求回调是纯函数：`f: (x: T) => U pure`）。标准库不用 `/// @pure` 一类注释表达纯度。
- **一个函数的资源集在它的类型里只有一种读法**：写了 `uses` 子句就是子句（对外的契约，调用者按它算，被调者以后在子句之内改函数体不牵动调用者），没写就是推断的结果；直接调用与经函数值调用读同一个类型。显式的 `uses` 是上界，`pure` 要求空集，函数体超出时报 `UsesPromiseViolated`，点出第一个超出的使用点。`stdout`、`fs` 这类程序外的资源，写出它们就承诺了它们带来的外部效应。
- **没写资源子句的函数类型，在任何位置都对资源泛型**，按实例化确定：形参（`f: (x: int) => int`）、结构体字段、`Map` 的值类型一样。资源不同的实例效应不同（同步链、执行与否都不一样），所以资源分量进入特化键。实参推断出的资源集须包含于形参要求的：资源少的函数可以用在要求资源多的地方，反之不行；一个不碰资源的 lambda、一个没写子句却不碰资源的具名函数，都能传给 `pure` 形参。值的类型打印推断出的子句。
- **`sync` 是块的性质，不是类型的性质**：`f<w>` 绑定 `var` 上下文参数后得到的值，它的资源集里有“写这个格子”；经资源泛型的形参调用它，与直接调用一样——在非同步体里丢掉结果不执行并给 `EffectNotExecuted`，在同步体里照常执行。
- **同一资源自动有序**：同一个函数体内，真正执行的、用到同一资源的效应按书写顺序执行（编译器在这些效应之间生成顺序边）。调用另一个函数，在调用处是"一个用到其资源的效应"；编译器不跨函数重新编排。
- **算子的纯度必须声明。** 没有声明的算子按有效应对待（最多少优化，不会算错）；仓库内的标准库模块必须逐个算子声明，第三方模块漏了给提示。
- **算子是否可能故障不强制逐个声明**：模块作者按需声明，没有声明的按可能故障处理。
- 先例与取舍：靠推断而非强制标注（Java 受检异常的教训）；高阶函数的资源由实例化确定，不需要 Koka 式的行多态；不提供效应处理器；按具体对象区分资源用下一条的句柄类型。
- **无序资源**：`resource net unordered` 声明的资源上的效应之间不保持书写顺序，彼此独立时可以同时进行；"顺序无关"是声明它的库作出的承诺。需要顺序时写在 `sync` 块里，或用句柄。
- **句柄类型（按对象的资源）**：带标签 `#resource` 的类型，它的每个值都是一个独立的资源；操作在签名中写 `uses 形参名`（如 `func send(c: Conn, m: Bytes): unit! uses c`），与 `var` 形参同理。对同一个句柄的操作按书写顺序，不同句柄之间互不约束；编译器在调用处推出用到的是哪个值。用于会话、连接、文件句柄等；流不是句柄，流是值（5.4）。
- **并发不需要 `async`/`await`**：彼此独立的计算与无序或不同资源上的效应可以同时进行；运行时在一个效应等待（网络、磁盘、子进程、调用模型）时执行图上其他就绪的节点。这是实现，语义与按某个合法顺序逐个执行相同；`std::nvm` 可以逐个阻塞地执行。
- **取消**：只有声明为可取消（`cancellable`）的资源或算子上的效应可以被取消，被取消时不得留下不一致的状态（库的责任）；不可取消的执行完、结果丢弃。标准库的 `first_of(a, b, …)` 取先成功完成者的结果、取消其余的；它的结果取决于完成的先后，这一不确定性写在它的声明中。
- **不同资源互不影响**："同种资源之间自然排序，通过 uses resource 系统，不同种之间互不影响，除非明确写 sync block。"冲突只按资源判断；不同资源上的效应之间没有顺序，要有顺序就写同步块。

### 3.4 `sync` 块

写在块前的 `sync`（包括函数体的后缀写法 `func f(): T sync { ... }` 和单独的 `sync { ... }`）表示这是一个同步块：**块一旦执行，它直接写着的语句里的效应一定发生，并且按书写顺序发生**（块本身执不执行，和任何表达式一样，看它是否被需要：作为语句写在非同步的函数体里、值又没人用的 `sync { ... }` 整个不执行）；纯计算没有任何可观察的先后，编译器可以自由安排它们。这与 C、Java 的 as-if 规则相同：程序能观察到的，都按书写顺序发生。**故障是可观察的**：可能出故障的计算（整数除法、下标、可能失败的转换……，按算子表的保守分类）与效应一样留在书写的位置——`let r = 5 / z; println("after")` 在 `z` 为零时不打印 `after`（Java 的精确异常同理）；只有**纯且不会出故障**的计算由编译器自由安排（与"移出循环体的部分必须纯且不会出故障"是同一个分类）。这个分类（称"可自由安排的计算"）是**一个谓词**，处处同用：离开同步链、移出循环体或臂、被改写丢掉（9.7）、内联后不连顺序边、抽取时可提前。调用按被调函数推出的事实判：函数体含可能出故障的计算、或函数是递归的（递归可能超过深度上限）就算可能出故障，与资源推断同一种做法。写在里面的臂、循环体与嵌套块不受它约束（见本节"同步块不向内继承"）。

- 用于“要它发生”与“跨资源的先后”。同步链只连带效应或可能出故障的语句（以及含这些的臂、循环等结构语句）；纯计算的语句不在链上。不推广为按类别的同步。链尾连到块的值：值节点归该块独有时，同步边直接接它；否则（形参、常量、或别处也用到的节点）经一个 `GATE`——一个数据端口、一个同步前驱、值原样放行、没有控制输入——这样它的其他使用者不会被排到链后，也不会被链拉活。
- **同步链的拼接**：被内联的函数如果是同步函数，它自己的同步链随函数体一起拼进来，调用在调用者链上原有的进出同步边保留；函数体里的效应与可能出故障的节点另有顺序边排在前一条语句之后、后一条之前。含效应或可能出故障的分支是链上的一条语句（前一条 →同步→ 分支，汇合 →同步→ 后一条）。没有表示“一段有效应的工作”的占位节点：顺序边只连真实的效应或可能出故障的节点。
- **计时用 `time::timed(f, x)`**：它运行一次 `f(x)`，交回结果与耗时。读时钟是效应，"测的就是这次计算"必须是数据依赖——`timed` 保证这次调用不被提前算掉、不被挪走或与别处合并，并在设备上等计算完成。用两次 `now()` 相减给纯计算计时测不准（常量折叠、合并、异步执行都会破坏它）。重复测量与统计用 `bench::timeit`（建在 `timed` 之上）。
- **同步块不向内继承**：同步块只管它自己直接写着的语句；写在里面的臂、循环体与嵌套块按它们自己的写法执行，要同步就在那里写 `sync`。一个块的含义不随它写在哪里而变。例：`func f(c: bool): int sync { if c then { println(1); println(2) }; return 0 }` 中 `if` 在同步链上，它的值是 `println(2)`，所以 `println(2)` 执行、`println(1)` 不执行；要两句都打印，写 `if c then sync { … }`。

### 3.5 引用、`var` 与 `let`

- Camel 默认都是引用。闭包对变量的捕获也是引用。
- `var` 标记可变对象，`let` 标记不可变对象。
- `let` 严格意义上不可修改：会修改变量的操作必须明确声明哪个参数是 `var`；不允许把 `let` 变量传给 `var` 参数，所以理论上无法做到修改。这是**编译层面的校验约束**，不是对内存上锁。把 `let` 对象传给 `var` 参数是编译期错误。
- **可变性的声明是一个闭环。** 函数内部想修改参数，必须使用本身就具有效应的函数：Camel 中的赋值操作就是有效应的函数；或者使用其他内置的 C++ 算子，而这些算子的声明也明确标记了效应，要求相应的输入参数是可变的。所以，想修改参数，前提是这个参数声明为 `var`（`modify(var i: ...)`），否则没有任何有效的办法去修改。可变性从最底层的算子声明一路向上传递，每一层都必须显式声明；没有把参数声明为 `var` 的函数不可能修改它。在函数体内对非 `var` 的参数赋值，或把它传给要求可变输入的算子，是编译期错误。
- **修改的追踪应当是完整的**：函数通过捕获（包括模块顶层的变量）写入一个 `var`，与通过 `var` 参数写入一样，调用处应当记为对该变量的一次写入。
- **带 `var` 上下文参数的函数可以部分应用**：`add<t>` 是一个写被捕获变量的函数值，它的类型带着这个资源，每次调用记为对 `t` 的一次写入。
- **Camel 崇尚不可变变量。** `var` 和赋值运算符只是为了方便留的口子，应当尽量少用。模型的计算应当用 `let` 写成纯的数据流。
- **微分与变量**：被求导的函数里，梯度需要经过 `var` 的读写时，直接拒绝并给出明确的诊断，不去支持。没有必要为了求导硬写 `var`。
- **模块顶层的 `var` 被函数直接读写**（如 `fib1.cml` 中的顶层 `cnt`）：这种用法的语义没有定全，不是必须的情况下不要写。
- **已知的不足。** Camel 在效应的管理与追踪方面还有缺陷，需要进一步研究。引用捕获、效应的追踪与各个遍相互作用时出现的问题，应如实记录为待研究的发现并附最小复现；只修复明确的实现错误，不要用临时规则去掩盖。
- **可以给以 `var` 开头的路径赋值**：`v.f = e`、`v[i] = e`、`v[i].f = e`、`v[i] += e` 等，含义是"用改好的新值整体替换 `v`"（等价于 `v = set(v, i, set(v[i], f, e))`），值语义不变：`let a = v` 之后再改 `v`，`a` 不变。没有别人共享时原地修改（10.5 的保证）。路径中的下标越界是故障（3.9）。
- **读一个 `var` 用到它前面最近的一次写**（形式化 F3），那次写因此执行；写与写之间只排序：`x = 1; x = 2; return x` 里第一次写没有被用到，不执行。
- **赋值表达式被当作值用时，它的值就是写进去的那个值节点**，经数据边直接使用，不新建读；`x op= e` 就是 `x = x op e`，被当作值用时取的是 `x op e`。函数体末尾写 `return e` 与直接写 `e` 建成同一张图。
- **`var` 的读与写**：只在自己的图里读写的 `var` 化成 SSA（读用最近一次写的值，写与写之间是顺序边）；被闭包捕获、作为 `var` 实参交出、或是本图 `var` 形参的 `var` 保留一个单元，读和读了捕获变量的调用有一个“捕获”角色的数据端口，接到最近一次写的产出。

### 3.6 高阶算子与并行

- **`map`、`filter` 的各个元素之间没有执行顺序的约定**：同步块不影响 `map` 内部的执行顺序，并行调度器可以并发执行各个元素，结果按元素位置排列；这正是并行加速的来源（见 `test/cases/para/core/monte_carlo_pi.cml`）。`foreach` 与 `reduce` 按元素顺序执行；它们的无序并行版本是 `para` 模块的 `unordered_foreach` 与 `unordered_reduce`。仓库中没有 `ordered_map` 或 `unordered_map` 算子。元素函数里的效应在并行的 `map` 下顺序不作保证，由使用者负责。
- **高阶函数的并行来自声明的性质**（元素之间互不依赖），不来自名字；用户写的函数声明了同样的性质也可以并行。
- **并行调度的粒度**：不要细到原子级别。给每一次很小的函数调用都建一个任务没有意义，只会徒增负担。
- **并行的 `map` 中一个元素出了故障**：已经开始的元素跑完，还没开始的不再开始。多个元素同时出故障时报下标最小的那个。

### 3.7 分支与 `match`

- **没有 `else` 的 `if` 本身没有值**，它的臂可以是任何类型，臂的值被丢弃：`if debug then println('checking')` 合法，`let x = if debug then 1` 是编译期错误。图上不变：一个分支加两条臂，没写的 `else` 是一条空臂，汇合处不取值。臂里不必再为了凑类型写 `return null`。
- **分支的一条臂没有值（`void`）、另一条是 `T` 时，分支是 `T?`**，没有值的那条臂给出 `null`。
- **`match` 必须有默认分支。** 没有 `case _` 是编译期错误；`bool` 上两个字面量都列全、`enum` 列全所有变体，以及 `T?`、`T!` 的固定模式除外。编译器不追加用户看不见的分支臂。每个分支的值必须能被被匹配值的类型接受。
- **`match` 的守卫**（`case p when c =>`）：守卫为假就试下一个 `case`；守卫在该 `case` 的作用域里求值，可以读模式绑定的名字；`|` 备选模式只能用每个备选里都绑定了的名字；`case` 按书写顺序试，第一个模式匹配且守卫为真的胜出；带守卫的 `case` 不计入穷尽性检查；守卫可能出故障时按 3.4，它是那条 `case` 的一部分。`T?`、`T!` 的 `match` 两侧各恰好一条不带守卫的 `case`，带守卫的同侧 `case` 写在它前面；同侧开口之后的 `case` 永远走不到，是警告。

### 3.8 可空

- **"可能为空"与"可能出错"是两种专用的内建形式**，写作 `T?` 与 `T!`（3.9）。各带一位标记，只能用 `??`、`!!`、`->` 的传递和 `match` 的固定模式拆开。不做通用联合类型的运行时分辨。
- **`a ?? b` 处理空值。** 右边可以是可空的：右边是 `T?` 时结果是 `T?`，右边是 `T` 时结果是 `T`；从右向左结合，所以 `a ?? b ?? 9` 是"先试 a，再试 b，最后给默认值"。图上是一个分支。
- **值进入 `T?` 或 `T!` 的位置时自动装入**，只要目标类型已知（实参、带类型的 `let`、数组元素、分支的两条臂）；`null` 同理。反方向永不自动：`T?`、`T!` 要当 `T` 用，必须用 `??`、`!!` 或 `match` 拆开（`->` 的传递把它交给只接受 `T` 的函数，结果仍是 `U?`、`U!`）。空数组字面量 `[]` 的元素类型同样取自目标位置。
- **`x == null`、`x != null` 可以写**，结果是 `bool`。函数值之间不能比较，但可空的函数值可以与 `null` 比较。
- **在 `if x != null then ... else ...` 的非空那条臂里，`x` 是 `T`。** 这等价于对可空值的 `match`：进入那条臂的端口带的是拆开后的值。只对 `let` 绑定与参数生效（`var` 可能被别处改写）；只认直接的写法（`x != null`、`x == null`、`null != x`，以及用 `&&` 连起来的几个，其中只要有对 `x` 的直接判空）；只在臂内生效；`||` 的 else 臂暂不收窄。在收窄的臂里再写 `let x = ...` 是重复声明。
- **收窄之后**，对已确定非空的名字仍可写 `??`、`match` 等针对 `T?` 的操作，给警告"已确定非空"；对非可空的值判空同样允许并警告（结果恒定）。

### 3.9 错误与故障

- **错误值是一个固定的内建结构**：种类名、消息、发生处的源码位置。所有可能出错的函数共用这一种错误。
- **可能出错的值只写 `T!`**，错误值只有一种类型（以 Kind 区分）；将来需要带类型的错误时，在有了 `enum` 之后以 `T ! E` 的形式加入。`?` 只是可空标记。`int?!` 允许，`int??`、`int!!` 不允许。标记从最内层写起：`T?!` 是 fallible(nullable(T))，`T!?` 是 nullable(fallible(T))。
- **`a !! b` 处理错误**，右边可以是可空的，规则同 `??`。
- **`->` 自动传递空值与错误**：`x -> f` 中 `x` 是 `T?` 或 `T!`、而 `f` 的参数只接受 `T` 时，`x` 为空就得到空、出错就把错误原样带下去，否则调用 `f`；结果是 `U?` 或 `U!`。所以管道只写正常路径，失败沿旁路走到末尾，在那里用 `??`、`!!` 处理一次：`path->read_text->parse->validate !! default`。是否拆开由 `f` 的签名在编译期决定：先按包着的值找 `f` 的重载，连同 `when` 条件，能匹配（参数类型就是 `T?`、`T!`，或者是条件允许它的泛型 `T`）就原样传进去，匹配不上再拆开（所以 `f->pass` 里 `pass` 要求 `is_function::<F>()` 时，`F!` 匹配不上，错误照常传下去）；两层标记由外往里，需要几层拆几层。没有单独的 `?->`。它们在图上都是分支。
- **错误系统的模型是 Rust 的 `Option`、`Result` 加内建语法**：`T?`、`T!` 是两个内建的 `enum`，`??`、`!!` 取默认值，`->` 传递，故障对应 panic。错误只有一种类型（以种类名区分）；需要让调用方按种类穷尽分支时，以 `T ! E` 加入（见上）。
- **没有 `throw`**：错误值就是一个值，由 `error('Kind', 'message')` 构造（位置由编译器填为构造处），用 `return` 交出；`error(...)` 构造的值进入 `T!` 的位置时一律是失败那一臂。`return` 给出的是它所在的块的值（函数体就是函数的结果，分支臂里的块就是那条臂的值），不从更外层退出；要在缺失或出错时改走另一条路，写成分支的两条臂，或交给 `->` 的传递与 `??`、`!!`。`try`/`catch` 不进语言：它在图上没有稳定的映射。`throw`、`try`、`catch`、`finally`、`raise` 都不是保留字，写了就是普通的名字或语法错误。
- **`fail<'Kind'>(message)` 在函数体里产生故障**（相当于别的语言的 panic）：用于调用方违反了前提的情况，与内建算子的除零、越界是同一种故障。它的类型是底类型 `never`：没有值，可以当作任何类型，所以能写在分支的一条臂上（`if q <= 1.0 then q else fail<'InvalidArgument'>('q > 1')`）。永不返回的函数（`exit`、永不结束的循环）也返回 `never`。故障与任何效应一样在被需要时才发生：前提检查写在数据经过的路径上，或写在 `sync` 块里。
- **错误与故障是两回事。** 只有声明为可能失败的操作（读文件、解析、网络等）才返回错误值。除零、越界、递归过深是故障，不变成错误值，否则每个除法和下标都要处理错误。
- **故障默认带位置终止，但可以在函数的边界上隔离。** `attempt(f)` 是一个函数变换：它返回一个新函数，参数与 `f` 相同，结果类型是 `f` 的结果加上 `!`；`f` 里发生的故障在这个边界上变成一个错误值（与 JAX 的 `checkify` 同一个想法）。边界必须是一次函数调用而不是一段书写范围：图上的计算按需求值、会被遍移动、会并行执行，只有子图的边界是稳定的，所以没有 `try`/`catch`。三条边界语义：
  - **结果在边界内算完**：`f` 的结果（包括结构体的字段、数组的元素）在边界内完整求值，其中的故障都算在里面；
  - **流逐次隔离**：`f` 返回流时，每一次拉取都在边界内，元素类型变成 `T!..`，出故障的那次拉取交出一个错误；
  - **效应不回滚**：故障之前已经发生的效应不撤销，图上没有事务。

  终止之前保证清理：刷新输出，释放外部资源。

  <!-- camel-snippet: fragment: a fragment of the fault example; risky is the function of the paragraph above -->

  ```camel
  let a = risky(0)                 // 故障：整个程序带位置终止
  let b = attempt(risky)(0) !! -1  // 故障被隔离，b = -1（示意）
  let c = rows->map<attempt(parse_row)>   // 每一行单独隔离
  ```

- **没有被处理的错误值到达 `main` 的出口**：打印到标准错误，退出码非零。
- **同步块里一个 `T!` 的值没有被使用，是编译期警告**；没有 `else` 的 `if` 里，臂里一个 `T!` 没有被使用，同样警告；`let r = ...` 绑定了一个 `T!` 而 `r` 从未被使用，同样警告。故意丢弃写 `let _ = ...`。没有声明返回类型的 `main` 以一个错误值结尾，是它的特例。
- **必然出故障的常量表达式**（如 `1 / 0`）：折叠遍不折叠它，给一条带位置的警告，留到运行时。这是折叠遍自己的选择，不是对所有遍的约束（见 9.6）。
- **越界**：编译期能知道长度时（尤其是固定长度的类型），`slice` 与下标的越界应当是编译期错误，而不是悄悄截断或留到运行期。运行期的 `slice` 越界是故障，与下标越界一致；`take`、`drop` 按定义截断，不受影响；起点在终点之后的 `slice`（`xs[2:1]`）得空数组，不是故障。
- **递归深度**：尾递归要做优化，程序应尽量写成尾递归或循环；非尾递归给一个可配置的上限，默认在各调度器上统一为 1000，并行调度器同样计数。
- 数值上的故障见 5.1，归约的故障见 7.7。
- **超时是调用的配置，超时返回错误值**（`T!`），不是故障，如 `url->http::get<timeout: 5.0>`。

### 3.10 循环

- **引入 `LOOP` 节点。** 现代的计算图标准大多有这类节点，要与它们接轨就需要它。条件与循环体是同一张图里的两个控制区域，与外层计算共用一个帧，不另设捕获表；`for … while` 是同一种节点的第三种形式；有多个状态时循环体返回一个元组，`LOOP` 的值也是这个元组。
- **循环是一个带状态的表达式。** 状态写在循环头上，循环体的值是下一轮的状态，整个循环的值是最终状态。不为"循环外的 `var` 当状态"另设语句形式；只为效应而遍历用 `foreach` 等已有的办法。
- **循环头的写法是 `do` 式**：状态只声明一次，多个状态用逗号分开，循环的值是它们组成的元组；`do` 后面是一个表达式，`{` 的读法与 `then` 之后相同（`{ x: 1 }` 是结构体，`{ 5 }` 是块）。

  <!-- camel-snippet: fragment: the loop forms; xs, n and ds are the surrounding example's values -->

  ```camel
  let total    = loop acc = 0 for x in xs do acc + x * x
  let (i, acc) = loop i = 1, acc = 0 while i <= n do (i + 1, acc + i)
  let p        = loop p = { x: 0 } for d in ds do { x: p.x + d }
  let found    = loop hit = -1 for x in xs while hit < 0 do if x > 9 then x else hit
  ```

- **不加 `break` 与 `continue`。** 提前结束写成循环头上的继续条件（如上面的 `found`）。
- 循环头必须有 `for` 或 `while`；`for … while` 每轮先判断条件、再取下一个元素；`for` 遍历数组（沿第一维：秩 1 时元素是 `T`，更高的秩时元素是少一维的子数组；秩未知的 `T[..]` 每轮交出的是 `T[..]`；标量不可遍历，是编译期错误）、字符串（按码点，元素是 `s[i]` 那样的单字符字符串）、映射（按键的升序，元素是键值对）；流也可以直接写在 `for` 里（`for x in s`，一轮一次拉取，流到头就结束），它是已有 `LOOP` 节点的一种读法，不引入新的节点种类、驱动或循环形式（[语言参考 7.3.2](language/07_statements.md)）；状态的类型取初值的类型，数组形状不自动放宽，需要时写类型标注。
- **循环可以收集每轮的输出**：`LOOP` 节点除最终状态外，可以有一组"每轮产出一个值、按轮次收集成数组"的输出（对应 ONNX `Loop` 的 scan 输出）。这是图层面的能力，源码中的写法见下一条；第一个使用者是自动微分（9.9）。
- **在源码中收集每轮的值不需要新语法**：把数组放进循环状态、每轮追加（`losses->append(l)`；数字数组上的 `+` 是逐元素加法，不是连接）；计数为 1 时原地更新的保证（10.5）使它不复制；编译器把"每轮向状态数组追加一个值"认作图层面的收集输出，自动微分与导出由此得到 scan 输出。

## 4. 语法与运算符

### 4.1 词法与语句

- **尖括号紧贴。** `with` 实参与类型实参的尖括号必须紧贴前面的记号：`f<a>` 是带实参的 `f`，`f < a` 是比较。比较运算符 `<` 前面要有空白；`i<n` 是错误，诊断应指出原因。
- **换行结束语句**，思路同 JS 的自动分号，以符合直觉为准。括号未闭合、行尾是二元运算符或逗号等"后面必须还有东西"的记号、下一行以只能是二元的运算符开头（`->`、`.`、`??` 等）时续行；下一行以 `-`、`+`、`(`、`[` 等可以开始一个表达式的记号开头时是新语句。分号仍可用。
- **有两种身份的符号出现在行首时，取开始新东西的那种身份**：行首的 `@` 是标注，行首的 `+`、`-` 是一元的。要把矩阵乘或加减法写成两行，把运算符留在上一行末尾。
- **解析器**用手写的词法分析器与解析器，不再依赖 ANTLR，追求效率与确定性。
- **注释**只用 `//` 与 `/* */`，`#` 不表示注释；文件首行的 `#!` 仍作为解释器行被忽略。
- **文档注释**是语言的约定：声明正上方以 `///` 开头的注释是它的文档。悬停与文档只取 `///` 注释，普通的 `//` 不是文档。
- `===`、`!==` 是逐元素的相等与不等（4.2）。

### 4.2 运算符

- **`^` 比乘除高一级，从右到左结合。** `2 * 3 ^ 2` 是 18。
- **一元负号永远是运算符，不并入字面量**；一元 `-`、`!`、`~` 比 `->` 与 `^` 结合得松，比其余二元运算符结合得紧。于是 `-2 ^ 2` 与 `-x ^ 2` 都是 -4，`-2->f` 与 `-x->f` 都是 `-(2->f)`、`-(x->f)`，`!xs->is_empty()` 是 `!(xs->is_empty())`：字面量与变量的读法一致；要先取负再传入写 `(-2)->f`。`a-1` 仍是减法。
- **`&&`、`||` 是不可重载的保留运算符，转译为分支。** `a && b` 即 `if a then b else false`，`a || b` 即 `if a then true else b`：右边是一条臂，只在需要时求值。两边都是 `bool`。
- **`&`、`|` 是两边都求值的普通逻辑运算，可以重载。** 只是做一点简单的逻辑运算、不需要分支时用它们；数组的逐元素逻辑运算、用户自己的类型重载的也是这一组。`a &= b` 即 `a = a & b`；`&=`、`|=` 是布尔上的与、或；位运算用函数（`bit_and` 等）。
- **`==` 与 `!=` 对数组、元组、结构体按内容逐个比较。** 两边类型必须相同，元素类型本身要能比较（含函数值的不能比），否则是编译期错误；浮点元素按浮点的规则（含 `nan` 的数组不等于它自己）。图上是一个普通的算子节点。
- **`===`、`!==` 是逐元素的相等与不等**：`a === b` 对两个数组逐个元素做 `==`，结果是同形状的 `bool` 数组；形状规则与其他逐元素运算相同。整体比较就是逐元素比较再归约成一个 `bool`：`a == b` 即形状相同且 `a === b` 处处为真。所以 `==` 对任何类型、任何数组（包括数字数组）都返回 `bool`，结果不因元素类型写没写而变。标量上 `===` 与 `==` 相同。重载 `===` 即得到 `!==`。
- **`<`、`>`、`<=`、`>=` 在数字数组上逐元素比较**，结果是 `bool` 数组：数组整体没有大小顺序，这几个运算符在数组上没有别的含义可冲突。
- **复合赋值 `a op= b` 就是 `a = a op b`**：只要 `a = a op b` 是合法的赋值（`a op b` 有定义，结果能赋给 `a`），`a op= b` 就合法，不论类型是谁定义的；否则是错误。所以数组的 `t += u` 是算出新数组再重新绑定，与数值一致；能否原地进行由内存规划决定（原地更新的统一规则），语义上不可观察。
- **列表推导** `[e for x in xs if c]` 的含义是 `filter` 加 `map`，即 `xs->filter<c>->map<e>`；元素之间没有顺序约定。
- **函数组合 `f..g`**：先 `f` 后 `g`，`(f..g)(x)` 即 `g(f(x))`，与管道 `x->f->g` 同向；两边是整数时 `a..b` 是区间：左闭右开 `[a, b)`（与切片 `t[a:b]` 一致），得到 `int[]`；带步长写 `range(a, b, step)`，语义照 Python：`step > 0` 时取 `a, a+step, …` 中小于 `b` 的，`step < 0` 时取大于 `b` 的，`step == 0` 是故障（常量时编译期报错）；两端都是常量而个数超过数组的上限是编译期诊断，否则是物化时的运行期故障；没有浮点区间，区间不进类型位置，`for i in 0..n` 由编译器融合、不物化数组，融合在语义上不可观察。`f..g` 就是 `(x) => g(f(x))`，类型、泛型实例化与重载都按这个 lambda 的规则；`..` 比 `->` 紧，`x->f..g` 读作 `x->(f..g)`。可用于高阶函数（`xs->map<normalize..encode>`）、规则（`map(map(xs, f), g) => map(xs, f..g)`）与遍的组合。

### 4.3 运算符重载

- **用户可以在 Camel 源码里重载运算符**，写作 `func operator &(a: Mask, b: Mask): Mask`（写法暂定）。可重载的是今天落到 `__x__` 函数上的那些运算符；`&&`、`||` 与 `??`、`!!`、`->` 等构造不可重载。`__x__` 形式的名字仍是保留的，用户不直接写。
- 用户的重载比内建的更具体时优先；重载 `==` 即得到 `!=`（`!=` 不能单独重载）；命名空间块里声明的运算符属于模块。

### 4.4 函数与参数

- **Camel 在语言层面区分两种参数。** 一种是函数要配置的属性（`with` 参数，即上下文参数），另一种是函数要处理的输入，也就是要流过函数的东西（普通参数）。这在某种意义上弥补了 Camel 不支持面向对象的局限：别的语言里靠对象的成员来持有的配置与状态，在 Camel 里是函数的上下文参数。
- **`with` 参数适合表达模型的参数与权重**：普通参数是数据输入，`with` 参数是权重，以及形状、开关、超参数、函数要调用的别的函数——凡是"决定这是哪一个函数"的东西。`logits<m>(x)` 对应数学上的 f_θ(x)：`logits<m>` 是权重为 `m` 的那个网络，再作用到数据 `x` 上。调用除了写成 `f<w>(x)`，也可以写成 `x->f<w>`，便于链式调用，也便于把模型各层的输入输出串联起来。
- **形参可以有默认值，实参可以按名字给**，普通形参与 `with` 形参同一条规则：`func scale(x: f32[n], by: f32 = 1.0)`、`with <rounds: int = 8, strict: bool = false>`；调用处 `scale(x, by: 2.0)`、`f->simplify<rounds: 16>`。默认值是编译期常量表达式，在调用处补入图中；按名字的实参写在按位置的之后；有默认值的形参之后的形参也必须有默认值。`name: value` 与结构体字面量的写法一致。同一个名字的多条重载里，含义相同的位置用同一个名字，具名实参才能对每条重载成立。
- **`f<w>` 是部分应用**：`let g = f<w>` 得到一个已经配好上下文参数的函数。
- **`with` 参数不是泛型参数。** 它是上下文参数，不要拿它来声明类型参数或编译期参数。
- **适用条件 `when`**：函数签名之后可以写 `when 条件`，条件是普通的编译期谓词（`is_numeric::<T>()`、`is_function::<F>()`，用 `match type` 写在库里，用户也可以自己写）。条件在实例化时求值；不成立时**这个重载不适用**，重载选择去试同名的其他候选；没有一个适用时在调用处报错，列出每个候选没满足的条件。`when` 在规则（"这条规则在此适用于……"）、函数（"这个重载适用于……"）与 `match` 的分支（`case p when 条件 =>`）中是同一个意思，求值的时机由所在位置决定。不另设 `where`。
- **`when` 写在它守护的体之前**：它是适用条件，属于签名，不属于体后的定义性子句（`fact` 的 `join`/`meet`/`widen`/`narrow`）。函数与规则写在签名之后、体之前，签名一行写不下时 `when` 单独一行（格式化器这样排）；`match` 的守卫同理写在 `=>` 之前（`case p when c => …`）：
  <!-- camel-snippet: fragment: 只示意 when 的位置，函数体从略 -->
  ```camel
  func softmax::<T>(x: T[n, m], axis: int = -1): T[n, m]
      when is_float::<T>()
  {
      ...
  }
  rule add_zero::<T>(x: T) when is_integer::<T>() { x + 0 => x }
  ```
- `when` 里可以调用任意纯的编译期 Camel 函数（包括用户用 `match type` 写的谓词），在实例化时求值；`WhenConditionNotConstant` 只留给条件真的读到运行期值的情况。条件里的名字按声明处解析，拼错的名字在声明处报错；依赖类型参数的检查留到实例化。两个带 `when` 的候选对同一次调用都适用时，调用处报歧义并列出两条候选，不按书写顺序取舍；同名声明按 `when` 互斥分臂就是重载，声明处的互斥检查只能抽样已登记的类型，调用处的判断才是权威的。
- **重载选择把 `with` 参数算进去**：`with` 形参的个数与名字和普通形参一样参与选择（不是它们的值）。于是同一个名字可以有 `xs->sum` 与 `xs->sum<0>` 两个形式。按名字给实参时，名字写在持有它的那张表里：普通形参在圆括号，`with` 形参在尖括号（`j->get<key: 'port'>`）。
- **泛型函数可以出现在任何期望一个函数的位置**，包括传给另一个泛型函数（见 5.5）。
- **尖括号只用于"配置"**：配置即"决定这是哪一个函数"的东西——`map` 的映射函数、`filter` 的条件、模型的权重、超参数——用 `with` 参数，保留 `xs->map<f>` 的流水线写法；流过函数的数据，以及变换类函数所变换的那个函数（如 `grad` 要求导的函数），用普通参数：`grad(loss)`、`with_grad(loss)`。函数作为普通参数且在编译期已知时，编译器照样为它特化（这是优化，不是语义）。这一区分让变换的默认行为自动得出：`grad` 对权重（`with` 参数）求导，按批映射作用于数据（普通参数）、权重共享，切分时切数据、复制权重。
- **管道调用可以带额外实参**：`x->f(a, b)` 即 `f(x, a, b)`；`x->f` 与 `x->f<w>` 不变；链式调用时接收者进入 `->` 后面那个名字的第一次调用，`x->g(1)(2)` 即 `g(x, 1)(2)`。

## 5. 类型系统

### 5.1 基本类型与数值类型

- **数值类型之间不做隐式转换。** 整数不会自动变成浮点，别的数值类型之间也一样（参数、返回值、变量之间都一样）；需要时显式写 `float(x)`。唯一会动的是**字面量**：它按上下文取类型（见本节末）。
- **带指数或小数点的字面量，默认类型是浮点数**（上下文要求 `f32` 时它就是 `f32`）：没有上下文时 `1e5` 是 `100000.0`。
- **转换的故障**：`int('12abc')` 是故障，整个字符串必须是一个数，要安全地解析用 `parse_int`，它返回 `int!`；值放不进目标类型的转换是故障：`int(1e30)`、`int(nan)`、`i32(5000000000)`。
- **整数加减乘的溢出、最小整数除以 -1 保持回绕。**
- **把值转成它自己的类型是合法的，什么也不做**：`xs as int[]`（`xs: int[]`）与经别名的 `p as A` 一样通过。
- 不应当存在到了运行时还不确定的类型：每个值在编译之后都有确定的类型（`any` 见 5.10）。
- **诊断与图上用源码里的类型名**（`first<int>`，不是 `first<i64>`）。
- **字面量按上下文取类型**（与 Go 的无类型常量相同）：依次取期望的类型（声明、形参、返回位置、二元运算或比较的一侧）、二元运算中另一个操作数的类型、默认类型（整数 `int`、小数与带指数的写法 `float`、虚数 `c128`）；字面量之间的运算在编译期按精确值计算，中间结果不溢出、不提前舍入；值放不进目标类型是编译期错误 `SemanticDiag::LiteralNotRepresentable`（消息引用源码里的写法，并给出原因：超出范围、会被截断等），指向给出类型的那个位置。变量之间仍不做任何隐式转换。例：`x * 2 + 1`（`x` 是 `f32`）中的 `2`、`1` 都是 `f32`；`0.1 + 0.2` 是离 0.3 最近的那个 double，`9223372036854775807 + 1 - 1` 是最大整数；`1 / 2` 按整数除法是 0，`1.0 / 2` 是 0.5。
- **复数**：核心数值类型 `c64`、`c128`，在数组中紧凑存储。虚数字面量是数字紧跟后缀 `i`：`4i`、`4.0i`、`1e-3i`（十六进制、二进制不可带）；`3 + 4i` 是 `c128`，`let w: c64 = 1 - 2i`。打印为 `3+4i`。
- **"有期望类型的位置"包括**：声明、形参、返回位置（含函数体的最后一个表达式，以及分支臂里的 `return`：它取臂所在位置的期望类型，与函数的返回类型无关）、二元运算的另一侧、数组字面量的元素、结构体字面量的字段、`match` 的模式（取被匹配值的类型）、`if`/`match` 各臂的值（取整个表达式的期望类型，如 `let x: float = if c then 1 else 2`）。没有期望类型时，同一数组里的字面量取"整数 < 小数 < 虚数"中最宽的一种（`[1, 2.0]` 是 `float[]`）。字面量之间的算术（含一元 `~`）在编译期精确计算，越界的折合表达式在整条表达式上报；`&&`、`||` 不做这种折合（它们是短路的分支）。放不进目标类型时报 `LiteralNotRepresentable`。`let` 绑定的值有确定的类型，此后与变量一样不做隐式转换。
- **重载选择先精确、后进入**：先找类型精确匹配的候选；没有时再让字面量进入形参类型。任一步有多个候选都是歧义错误，不按声明顺序取舍。普通调用与部分应用（`f<w>` 作值）规则相同。
- **类型名作用于数组是逐元素转换**：`f32(xs)`、`T(xs)`、`float(xs)`；没有另外的 `cast`。数组元素类型之间同样没有隐式转换（整数、`bool` 也一样）：两个元素类型不同的数组没有匹配的臂，由签名拒绝；`bool` 变成数是一次转换，掩码用 `where` 或显式转换；`if c then xs else ys` 两支元素类型不同是类型错误。
- **期望类型沿类型变量传进调用**：先把被调函数的返回类型与期望类型对齐，解出类型变量；实参里提到这些类型变量的位置代入后成为该实参的期望类型，字面量据此取类型；已经取好类型的值不转换。字面量一次舍入到目标类型。泛型函数体里的字面量在实例化时取类型，放不下就在实例化处报 `LiteralNotRepresentable`。
- **空数组字面量 `[]` 的元素类型只取自它所在的位置**：没有这样的位置（作循环初值、作泛型形参 `T[..]` 的实参）是编译错误，要写类型（`let e: f32[] = []`、`show::<f32>([])`）。`void` 不是元素类型。

### 5.2 命名类型与结构类型

- **有名字的结构体与 `enum` 是命名类型**：`type Point = { x: float, y: float }` 创建一个新类型，它的身份是名字加声明它的模块，属于该模块。元组、数组、函数类型，以及 `type 名字 = 另一个已有类型`，是别名，按结构比较（如 `type Pair<T> = (T, T)`）。
- **没有名字的结构体值可以直接用作结构相同的命名类型**：`let p: Point = { x: 1.0, y: 2.0 }`，字段按名字对应。**两个命名类型之间必须显式转换**（`m as Seconds`），即使结构相同；字段按名字一一对应。需要"包一层的数值"（如 `Meters`）时写成单字段结构体，不另加语法。
- **字段顺序**：命名类型的规范顺序是它的声明顺序；没有名字的结构体类型，写出的顺序是类型的一部分（顺序不同即不同类型）。参数树、检查点、`tree_paths` 的叶子顺序都按规范顺序。
- **结构类型是有限的**：结构体、元组不能直接或间接包含自身；递归的类型只能经由 `enum`。类型函数的计算因此按类型的结构终止，另有可调的展开上限。
- **结构体可以经由间接的类型递归**：经过数组、映射、集合或 `enum` 的递归是允许的（`type Node = { children: Node[] }`）；直接包含自身（`type A = { a: A }`）是错误。空数组字面量 `[]` 的类型按上下文取（5.1 的同一规则）。
- **函数值没有身份**：函数与区域的值只由它算什么决定，没有“是哪一个对象”之分——不能比较两个函数值是否相等，也不能取它的地址。所以只差参数名或输入的函数体、区域可以被编译器共用一份，程序观察不到。类型同样没有对象身份，只有结构：同一结构的类型在任何地方是同一个类型；维度名、包名不进类型的规范身份（打印与诊断仍用带名字的写法）。

### 5.3 `enum`

- **和类型按 Rust 的 `enum` 做**：变体有名字，可以带一个元组或一个结构体的数据，可以泛型、可以递归。

  ```camel
  type Shape = enum {
      Circle(float),
      Rect { w: float, h: float },
      Empty,
  }
  let s = Shape::Rect { w: 2.0, h: 3.0 }
  let area = match s {
      case Shape::Circle(r)     => 3.14159 * r * r
      case Shape::Rect { w, h } => w * h
      case Shape::Empty         => 0.0
  }
  type Tree<T> = enum { Leaf, Node(Tree<T>, T, Tree<T>) }
  ```

- `match` 一个 `enum` 时列全了所有变体就不必写 `case _`（与 `bool`、`T?`、`T!` 同理）。不按值的类型区分变体（那是运行时的类型判断，已排除）。`|` 只是逻辑或。图上不增加节点种类（见 2.1）。

### 5.4 多维数组与维度

- **原生的多维数组是核心类型**：`T[维度...]`，元素类型加形状，值语义。`int[]`（一维、长度运行时才知道、可以追加）就是 `int[?]`；`f32[3]`、`f32[n, 784]`、`u8[h, w, 3]`；`int[][]` 仍是数组的数组（每行可以长短不一）。元素为数值类型的多维数组就是做数值计算的对象，不另有类型名；数值运算的库叫 `tensor`（创建、形状、广播、矩阵乘），整体与沿轴的归约在 `array`；签名写 `f32[n, 784]` 或 `func f::<T>(x: T[..]) when is_numeric::<T>()`。写 `f32[m, n]` 而不是 `f32[m][n]`：多维数组是一个整体的对象。追加只用于 `T[]`。
- **维度名在形参类型里第一次出现、且不是已有名字时自动绑定**（取代 `constas`），已有的名字是引用；只出现在返回类型里的名字是错误；只出现一次的维度名给出警告（提示写 `?`）。`?` 是不需要名字的任意大小（编译期未知，调用处做运行时检查，与 `as` 相同）；`..s` 是任意维数。维度上可以做加法与乘以常数（线性式，相等可判定），其余结果为未知。维度名只活在类型里，不能与运行时的变量同名；命名维度不产生新的实例。
- **形状未知的数组进入声明了形状的位置**：不隐式放行，用 `as` 显式转换，转换处做检查。
- **形状检查由核心负责**；逐元素运算、矩阵乘、归约等是库函数，它们的事实是算子声明上的标准标签（6.6）。稀疏、量化、分布式、表格等由库定义为命名类型，内部由核心数组组成，共同接口用泛型表达。
- 细节与理由见 [原生多维数组、内存管理与互操作](design/arrays-memory/README.cn.md)。
- **下标与切片**：下标里每一维写一个位置 `i`、一个范围 `a:b`（两端可省略，可带步长 `a:b:s`），或一个整数数组 `idx`；后面没写到的维整维保留。写位置的那一维从结果里去掉，写范围的那一维保留并切片，写整数数组的那一维按下标取（即 `take`，重复下标保留）。所以 `t[i]` 是第一维的第 `i` 个（多维时是一行），`t[:, 0]` 是第二维的第 0 个，`t[a:b, c]` 在第一维切片、在第二维取位置。哪一维、什么秩都是同一套规则。**不支持负数下标**（负数是故障），最后一个元素用 `last(t)`；越界是故障。结果与原数组共用数据块还是一份拷贝，是性能上的事实，不影响值语义。
- **秩 0 就是元素本身**：`T[..]` 包括秩 0，秩为 0 的数组就是那个元素，运行期是同一个值，类型上也没有单独的“秩 0 数组”。开秩数组上写位置，结果少一维、秩仍未知（`t: f32[..]` 的 `t[0]` 是 `f32[..]`）；要元素写 `t[0] as f32`，秩不为 0 时在转换处故障。`for` 遍历 `f32[..]` 每轮交出 `f32[..]`，遍历 `f32[]`（秩已知为 1）每轮交出 `f32`；对标量 `for` 是编译期错误。
- **声明写下的形状就是值的类型**：数组字面量的长度静态已知，`let x: f32[4] = [1.0, 2.0, 3.0]` 是 `DimensionMismatch`；平铺的字面量配二维注解同样是错误，嵌套的字面量在 `f32[2, 2]` 的位置上就是一个二维数组，没有注解时 `[[1.0, 2.0], [3.0, 4.0]]` 是 `f32[][]`；`f32[3]` 不可追加，要可追加写 `f32[]`。字面量、维度名、`constas` 值参数各种写出 extent 的方式走同一个检查。步长为常量 0 的切片、常量下标或常量切片端点越出已知 extent，都是编译期错误。
- **数组与其他类型一样，只有一套语义**：值语义、下标、切片、`map`/`filter`/`sort`、追加、路径赋值对所有元素类型相同；纯数据元素（数字、复数、只由它们组成的结构体等）紧凑存储在数据块里是实现（10.5）。差别只来自元素类型本身：哪些运算符可用（数字数组有逐元素算术，因为数字有算术）、能否求导（数组的切向量是"元素的切向量组成的数组"，元素没有切向量时数组也没有）。
- **流 `T..`**：一个 `T`，后面还有不定数量的元素随时间到来——可能无限长、按需产生的序列。与 `T[..]`（后面还有不定数量的维度）同读："`..` 是不定数量的更多"。流是**值**：只有来源（读文件、收网络数据、模型逐个吐出的输出）与去处（写出）是效应，中间的变换（`map`、`filter`、`scan`、`batch`、`zip`）是纯函数。`batch(s, k)` 得到 `T[k]..`，批大小在类型里。
- **流的值是步进函数加当前状态**：一个普通的函数值，没有新的运行期表示，也没有新的节点种类。流是一等的值，可以写进签名（`func pass(s: int..): int..`）、作参数、被返回。`for` 遍历流在图上展开成已有的 `while` 循环：每轮先问条件，条件成立才调用步进函数拉取下一个元素，拉空就结束；生产者与消费者同时可见时把步进函数内联进循环体是优化，两条路结果相同。
- **流的类型的写法**：后缀一律从左到右读：`T?..` 是 `(T?)..`，`T!..` 是元素可错的流，`T[3]..` 是数组的流，`T[..]..` 是开秩数组的流，`T..?` 是可能没有的流；流不能作数组、映射、集合的元素（元素可以被多次读取，与只消费一次冲突），元组可以。
- **一个流只消费一次**：每条执行路径上，一个流值至多有一个消费者（分支的不同臂各消费一次算一次），在图上检查，第二次使用是编译错误。判据是图上的：每个流值（`var` 的每个版本各算一个，`tee` 的结果各算一个，互斥的臂合计一次）数据出度至多为 1。在循环体里消费一个循环外定义的流是错误，要逐轮消费就把流作为循环状态，或用 `for x in s`。第二次使用时诊断同时指出两处，并给出 `tee` 的写法。`tee(s, n)` 的 `n` 默认 8，`n < 1` 是编译期诊断，过大静默夹取到实现上限。要给多个消费者，显式写原语 `tee(s, n)`，得到两个流，两边各自看到完整的同一串元素；`n` 只是给执行器的缓冲提示——语义上缓冲不限，执行器可以阻塞领先的一方或扩大缓冲，不报错，内存的堆积由诊断报告。共享必须写出来，所以元素可能被留住的地方在代码里看得见（先例：Java Stream、Rust 迭代器只能消费一次）。来源上的读取只发生一次。
- **流不参与合并，也不能被捕获**：流类型的节点不参与公共子表达式合并与等价饱和的合并（两个相同的流表达式是两个流）；遍必须保持线性，封存检查核对。lambda 不能捕获流（它可能被调用任意多次）——把流作为参数传入。
- **一个元素被计算，当且仅当有消费者拉取了它**（"用到才执行"细化到元素，3.1）；背压由此而来。
- **生成器**：函数体里写 `yield` 的函数产生一个流，它的返回类型必须在函数头部写成流类型（`func pairs(n: int): (int, int).. { … yield (i, j) … }`）；简单的生成器可以用库函数 `unfold(初始状态, 步进函数)`。一轮可以 `yield` 多次，恢复点就是 `yield` 所在的位置，任意层嵌套，`match` 的臂里和 `sync` 块里可以；`yield` 之后的语句等消费者再拉时才执行，块里效应的先后照 3.4；故障发生在产生那个元素的那次拉取处；产出的流是线性的，生成器函数可以多次调用，每次得到一个流；不做委托（写 `for x in inner do yield x`）；`return` 结束流、不带值，空流合法；要交出错误元素写 `yield error(...)` 然后 `return`。生成器在图上是一个步进函数：被调用时只求实参并交出 `(step, s0)`，函数体一句都不执行；`step(s): (T, S)?` 从 `s` 记录的恢复点接着跑，跑到下一个 `yield e` 时交出 `(e, s')`，`return` 或跑完时交出 `null`；状态 `S` 是含恢复点编号、所有活过某个 `yield` 的局部变量、以及每个含 `yield` 的循环的状态的结构体，只用 `BRCH`、`LOOP` 和结构体。
- **两种调度方式，一种语义**：涉及流（消费或产生）的图，执行器可以逐元素整图执行，也可以让图驻留、元素流水线式流过；两者结果相同，条件是每条边上元素的先后保持、节点只按到达的输入计算（Kahn 进程网络的确定性条件）。按到达顺序合并多个流、按时间开窗口等会打破确定性的算子，在声明里写明。

### 5.5 泛型

- **泛型函数按实参类型实例化。** 泛型函数是一张子图模板；每用一组具体类型调用，就实例化出一张类型全部具体的子图，函数体在这时检查。图上只有具体类型，运行时不需要类型信息。
- **类型参数在函数头声明**：`func first::<T>(xs: T[]): T`。函数名后有 `::<…>` 就是泛型，没有就不是——一个函数是不是泛型，在函数头一眼可见。声明的写法与调用处显式给类型实参的写法（5.9 的 `first::<int>(xs)`）相同；调用处通常不必写，由实参推出。函数头声明的名字在函数里优先于同名的类型。规则（`rule`）与事实（`fact`）同样在名字后声明类型参数。规则还可以有 `with` 参数，写法与函数相同（`with <tile: int> rule tile_matmul(...) { ... }`）：由选用这条规则的人绑定一次（`tile_matmul<64>`，与函数的部分应用同一种写法），之后在整个程序上反复使用；它与类型参数（由匹配到的类型决定）、`const` 参数（由匹配到的常量决定）来源不同。事实（`fact`）同样可以有 `with` 参数（分析的调节项，如加宽阈值、精度），查询时写出 `range<5>(x)`，不同实参是不同的事实。标签没有 `with` 参数：标签的参数就是它构造的那条事实的全部内容。不用 `typeas`。

  ```camel
  func first::<T>(xs: T[]): T { return xs[0] }

  with <key: (x: T) => K>
  func keys::<T, K>(xs: T[]): K[] { return xs->map<key> }
  ```
- **维度名仍在形状里自动绑定**（5.4）：维度名是形状记号的一部分（如数学里的 n×k），写在形状里已经可见；需要时也可以写进函数头（`func dense::<n, k>(…)`），不强制。

- **泛型函数可以出现在任何期望一个函数的位置**，包括传给另一个泛型函数。编译器把它的实例化延迟到类型变量能从上下文确定时；确定不了是编译期错误，并指出哪个变量定不下来。延迟只发生在编译期，图上只有具体的实例。
- **泛型函数可以省略返回类型**，由每次实例化后的函数体推出；普通函数必须写；编辑器的悬停显示每个调用处推出的类型。
- **标准库签名的文本用类型变量，不用 `any`**（如 `print::<T>(x: T)`）。参数个数可变、各参数类型不同的 Camel 函数暂不做。
- **按类型展开的操作用泛型写，不做编译器内建。** `tree_map` 这类"形状由类型决定、编译期展开"的操作，最终用 Camel 的泛型函数写在库里；为此泛型要能在编译期按结构体、元组的字段递归（设计另行讨论）。在那之前不再增加此类内建，也不另做过渡机制。原生算子的内核不在运行时读取调用的静态类型；需要按类型变化的，在编译期展开。
- `macro` 与类型计算无关，不要把类型函数建立在 `macro` 之上。
- **按结构展开的写法**（方案 A，详见 [泛型按结构展开](design/generic-structure/README.cn.md)）：`match type T { case struct => …; case tuple => …; case #leaf => …; case _ => … }` 按类型的形状在实例化时选分支；一个 case 也可以写类型名（`case int`、`case MyStruct`、`case T`），按类型的**身份**精确选分支；`static for n, F in fields T => …` 在实例化时展开字段（位置即说明绑定的种类，不写 `constas`；需要字段标签时写 `n, F, tags`）；编译期字段访问 `t.[n]`；推导式 `{ … => [n]: e }`、`( … => e )`；`static loop acc = init for n, F in fields T do …` 是编译期展开的折叠；可变元数 `..ts` 与展开调用 `f(t, ..ts)`，元数编译期确定、可以为 0。`static loop`/`static for` 的 `in` 后是任何由编译期常量经“可自由安排的运算”（3.4 的那个谓词）组成的序列，编译器先求值再展开：常量数组、`range(a, b, step)`（实参是常量）、编译期元组、`indices ts`、`fields T`。`for x in ts` 每轮绑定 `ts.[i]` 这个值，其类型随位置变；区间只有 `int` 两端。`fields T` 的元素是（名字，类型，标签），头部可写 1、2 或 3 个名字，按位置取前缀；`tags` 绑定该字段上全部标签组成的编译期结构体（字段名是标签名，字段值是标签的实参记录，无参数的标签是 `{}`），同一字段上两个同名标签是编译错误。
- 含 `match type` 或 `static for` 的实例**自动内联**进调用者；展开失败给出带静态绑定的**实例化链**（链上的字段名连起来即路径），库可写 `static error "…"`，实例化深度上限可调；路径等由展开产生的值是运行时的值（由常量折叠），不作为编译期参数。
- **泛型规则的实例化**见 9.11。规则的类型参数、`const` 参数、`with` 参数来源不同：类型参数由匹配到的类型决定，`const` 参数由程序里匹配到的常量决定，`with` 参数由选用规则的人绑定一次；规则的类型实参与 `with` 实参走同一个实例化通道，实例的键是“规则 + 类型实参 + `with` 值”；`with` 参数的实参必须是编译期常量，没有绑定且无默认值的规则放进规则集是编译错误。

### 5.6 类型函数与原语

- **类型函数用专门的类型表达式来写**，在类型位置上用尖括号调用。类型总是写在 `:` 之后，所以这里的尖括号与 `with` 参数的尖括号没有歧义。带参数的类型声明就是类型函数。

  <!-- camel-snippet: fragment: a signature sketch; swap has no body and is not a loaded operator -->

  ```camel
  type Pair<T> = (T, T)                    // 示意
  func swap::<T>(p: Pair<T>): Pair<T>
  ```

- **新的原语只用于主体语言无法表达的事**，以标记的形式出现，数量固定：`::<T>`（函数头声明类型参数）、`constas n`（编译期值参数）、`typeof x`（一个表达式的静态类型）、`fields T`（一个类型的字段表）。凡是能由原语算出的（如取字段名的 `keyof`），写在库里，是类型函数或普通函数，不是关键字。
- **普通函数与类型函数在写法上对称。** `func` 定义普通函数，用 `f(...)` 调用；`type` 定义类型函数，用 `F<...>` 调用，只出现在类型的位置上，如 `type Device<T> = match type T { ... }`。类型函数没有上下文参数（`with`），尖括号里只有类型与编译期的值。区分的依据是结果：结果是类型的，用 `type` 定义；结果是值的（包括在编译期求值的判断，如 `is_numeric::<T>()`），用 `func` 定义。
- **类型函数的函数体是一个类型表达式**，不是语句块：`type P = { w: float }` 中的花括号是结构体类型，不能再兼作语句块。较复杂的计算拆成几个类型函数，或用以关键字开头的 `match type`。
- **类型只出现在类型的位置上。** 类型的位置是语法上标明的：`:` 之后、`type 名字 =` 之后、`as` 之后、`::<...>` 之中、`match type`、`fields` 之后，以及类型函数的尖括号里。`match type`、`fields` 之后的类型位置上，紧跟的 `(` 一律读作类型的开头：`fields ()` 是空元组类型，函数类型要再包一层括号（`fields ((x: int) => int)`）。类型进入值的代码只有两条路：`::<T>`（函数头声明的类型参数与调用处的显式类型实参）、`typeof` 取得。因此值位置上的 `f<...>` 永远是上下文参数，类型位置上的 `F<...>` 永远是类型函数调用，解析时不必知道名字指什么。
- **类型函数可以作为类型函数的实参**（高阶类型）：在类型位置上不带尖括号写类型函数的名字，即指这个类型函数本身，如 `MapLeaves<Device, Params>`。形参是类型还是类型函数，由函数体中的用法推出。
- **由字面写法算出的字段名加方括号**：推导式中 `[n]: e` 的 `n` 是编译期的值，`n: e` 的 `n` 是字面的字段名；编译期的字段访问写 `t.[n]`。

### 5.7 泛型中的名字查找

- 名字一律在定义处按词法查找；对依赖类型变量的值做运算（如叶子处的 `==`、对回调实参的重载选择）时，另在该值的类型声明所在的模块中查找重载。不看调用者导入了什么。
- 要换一种运算，把函数作为参数显式传入（如 `tree_eq<my_eq>(a, b)`）。
- **命名类型的运算符随类型走**：对任何命名类型的值做运算（不限于泛型），除词法可见的重载外，还在该类型声明所在模块**导出**的重载中查找；经别名或再导出得到的类型同样如此。未导出的重载不可见。

### 5.8 变型

- **泛型类型一律不变**：`Array<int>` 不能当 `Array<int?>` 用；隐式转换（如装入 `T?`）只发生在叶子值上，不穿透泛型类型的参数。

### 5.9 显式类型实参

调用时显式写类型参数，两层都做。

- **第一层**：只出现在返回类型里的类型参数由期望的类型推出（`let` 的标注、形参的类型、返回的位置），如 `let cfg: Config! = json::decode_as(text)`；这是 5.5 "泛型延迟到上下文能确定时实例化"的延伸。
- **第二层**：推不出来时写 `f::<T>(x)`（与 Rust 的写法相同），如 `json::decode_as::<Config>(text)`、`empty::<int>()`。按位置时，顺序是类型变量在签名中首次出现的顺序；也可以按名字写 `f::<T = int>`，不依赖位置。
- `f<w>` 仍只表示 `with` 参数与部分应用；两者都写时是 `f::<T><w>(x)`。
- **lambda 的参数类型可以从上下文推出**：lambda 出现在期望某个函数类型的位置（实参、`with` 实参、带标注的绑定）时，未标注的参数类型与返回类型由该函数类型推出，如 `tree_reduce<(count, leaf) => count + numel(leaf)>(model, 0)`；推不出时要求标注。
- **lambda 的形参要写括号**：`(x) => e`；没有 `x => e` 的写法（规则体里它会与规则的 `=>` 相撞）。

### 5.10 没有 `any`

- **没有 `any` 类型**：编译之后每个值都有确定的类型。接受多种类型用类型参数，并排放不同类型的值用元组或结构体，读形状已知的 JSON 用 `decode_as`。
- Camel 没有在运行时判断类型的能力。

### 5.11 特化与递归

- **声明里未定的 extent 不参与按类型特化**：形参写 `int[]`、`T[?]`、`T[..]`，实例的形参类型就是声明的类型代入类型变量之后的结果；实参的精确长度是值的性质，不进实例的键。命名维度不产生新的实例（5.4）。
- **递归的不动点**：沿当前调用环，同一个函数以相同的键再次被实例化，就复用环上已有的实例。新键的类型实参结构上包含环上已打开的那个（`T` → `T[n]` → `T[n][n]`…），特化永远到不了不动点，在第一次出现增长的调用处立即报专门的诊断；实例化深度上限只作兜底。不设按计数截断的上限。

## 6. 标签与装饰器

两种机制，底层相差很大，因此写法明确区分。

### 6.1 装饰器 `@`：变换

`@d<a> func f` 即 `let f = d<a>(f₀)`，`d` 是普通函数，可以改变行为；类型装饰器是类型函数，`@D type T = E` 即 `type T = D<T₀>`；也可以装饰代码块（等价于立即调用的无参函数，行为与不加装饰的块完全相同）。一行一个，自下而上依次作用（顺序有意义，是函数组合）；重复的组合定义成新的装饰器函数。函数装饰器小写，类型装饰器大写（与类型函数一致）。

### 6.2 标签 `#`：编译期事实

- 标签附在声明或节点上，只在编译期存在，不会被"调用"，在图上不产生节点。**语言本身不赋予标签任何含义**：含义由声明它的库定义，由读取它的遍实现，后果由库负责（与第 9 节一致）；标准标签的含义写在本规范中（6.6）。
- 事实有两种：性质（不带参数，如 `#leaf`）与关系（带编译期值的参数，如 `#vjp(cube_rule)`）。多个标签写成 `#[a, b(v)]`，只有一个时可省方括号。标签名小写。
- **标签用关键字 `tag` 声明**：`export tag leaf on type`、`export tag fixed on field`、`export tag vjp::<F>(rule: F) on func when is_function::<F>()`（形参是函数时写类型参数加条件，与遍的签名同一种写法，签名固定时写具体的函数类型 `(x: T) => R`；关键字不作类型名，也不另设"任何函数"的类型标记）、`export tag reassociate on nodes`。`on` 列出能贴的位置：`func`、`type`、`field`、函数参数，以及 `nodes`（被标记的函数或代码块里按词法写出的节点，含分支臂、循环体、lambda，不含它调用的函数）；以后可加变体；模块不是标签的位置（要给一组函数贴同一个标签，贴在命名空间块上）。别名组 `tag finite_math = [no_nans, no_infs, no_signed_zeros, flush_subnormals]` 展开为其中各条事实。贴到未列出的位置是编译错误。
- **区域上的事实累积**：一个节点具有它所在的所有被标记区域的全部事实；带参数的同名事实以内层为准。不需要合并规则。
- **标签属于声明**（名字），与装饰器怎样包装它的实现无关。标签只能在声明处贴，不能事后给别处的声明补贴（调度是否例外另行讨论，见第 15 节）。
- **命名空间块上的标签**：写在命名空间块前的标签，作用于块里直接写出的每个能贴这个标签的声明（函数、类型、嵌套的命名空间块），内层自己写的胜出；块里一个能贴的声明都没有，在标签处报错；类型的字段是类型的成员，不是块里的声明。

### 6.3 读取标签

- C++ 模块通过登记与查询接口读；编译期代码中标签是编译期的值，`match type T { case #leaf => … }`，`fields T` 同时给出每个字段的标签。
- 标签与其他名字共用命名空间，按同样方式导入，可写限定名 `#[tiles::kernel]`。
- 是否满足一个要求类标签（如 `#kernel`）由库的遍检查。

### 6.4 关键字

关键字只留给改变语义的修饰（如 `sync`、`export`、`resource`、`tag`）。`macro` 是标准标签 `#macro`（见第 8 节），不用导入即可使用。没有 `inner`、`outer`、`atomic`、`shared`：原生实现由模块中无函数体的声明表达，外部实现由模块系统承担，"作为整体、不展开"由 `#kernel` 一类标签表达，数据共享由不可变数据取代。

### 6.5 两种提前计算要分开

泛型中的 `match type`、`static for`、类型函数一定在实例化时完成，是语言语义；`#macro` 的提前求值是流水线中 `std::macro` 这个阶段做的事（第 8 节）。

### 6.6 标准标签

- **数值许可就是标签**：`#[reassociate, contract]`，不另设 `numeric` 包装与 `enum`；`finite_math` 是别名组（第 7 节）。
- **`macro` 是标准标签 `#macro`**（第 8 节）。
- **算子的事实都是标准标签**：纯度、故障、资源、数值分类、下标映射（输出的每个元素由输入的哪些元素算出）等，都是算子声明上的标准标签，含义写在本规范中；C++ 算子经同一套标签登记接口声明，Camel 写的函数由函数体自动推出。不单独设"下标语义""算子语义"等概念；现有的 `operator_semantics`、`index_semantics` 作为这些标准标签的内部存储保留。
- 切分标签 `#shard`、块内核标签 `#kernel` 见第 13 节。

## 7. 数值契约

### 7.1 规范算法

- **基准是规范算法，不是某台机器的实现**：加、减、乘、除、开方每一步按 IEEE 正确舍入，严格按程序书写的顺序，不收缩为乘加融合。按规范算法计算时（`#strict`、安全模式，见 7.4），各后端、各设备的结果逐位相同。
- **矩阵乘的规范算法是按 k 从小到大连续做乘加融合**（FMA 本身是 IEEE 规定的一次正确舍入运算，因此同样逐位可复现）；这是矩阵乘自身的规范算法，不是对"不收缩为乘加融合"的放宽。
- **定义图是规范**：融合或手写的实现必须与算子的定义图一致，故障也一致。维度可能为 1 的广播在形状确定之前不给出索引映射。
- **超越函数**（`exp`、`log`、`sin` 等）不要求跨设备逐位相同，只承诺一个写明的误差上界（以 ulp 计），逐个声明；标准库的目标是 `exp`、`log` 不超过 2 ulp；NaN、无穷、零等特殊值必须精确。

### 7.2 许可

- 许可的名字：`reassociate`（改变归约的顺序或结合方式）、`contract`（收缩为乘加融合）、`approx_math`（近似数学函数）、`change_precision`（降低输入或累加的精度，提高累加精度也属于此项）、`finite_math`（对 NaN、无穷、负零、次正规数作额外假设；是 `no_nans`、`no_infs`、`no_signed_zeros`、`flush_subnormals` 的合写）、`nondeterministic`（允许结果随调度变化的做法，如浮点原子加、用原子操作合并的 split-K）。
- **各项许可互不蕴含。** 模块只能声明算子本身做什么，不能替调用者扩大许可。
- **`unordered_reduce`** 只授予"这次归约的合并顺序可以改变"，不含其他许可。
- **精确类算子可以声明受 `finite_math` 的四项假设影响**；舍入类许可对它们仍不适用。
- **`refine_accuracy`**（规则语言第二版 8.10）：允许编译器把一种写法换成误差不更大的写法（`log(1 + x)` → `log1p(x)`、减去最大值的 softmax）。"不更大"的含义：在每个输入上，右边的误差不超过左边的误差加上该规则声明的界（以 ulp 计，默认 2），并且在某处严格更好；默认不允许，用标签授予。
- **检验这些许可的命题**：`reassociate`、`contract` 是有限值上实数相等加特殊值上逐位相等；`refine_accuracy` 是误差界；`nondeterministic` 的规则采样与“未检验（原因）”分开写，不许混（9.11）。
- **epsilon 一律是机器 epsilon**（相邻两值的相对间距 `2^(1−p)`）：bf16 `2^-7`、f16 `2^-10`、f32 `2^-23`、f64 `2^-52`。它与 `change_precision` 里一次舍入的相对误差界（bf16 `2^-8`）是两个量。

### 7.3 默认值：默认放宽，声明收紧

| 许可 | 默认 | 说明 |
|---|---|---|
| `reassociate` | **允许** | 改变相加的顺序与分组：并行归约、分块矩阵乘的前提 |
| `contract` | **允许** | 把乘与加合并为一次 FMA |
| `approx_math` | 不允许，用标签授予 | 近似的超越函数 |
| `change_precision` | 不允许，用标签授予 | 以较低精度（TF32、BF16 等）计算 |
| `finite_math` | 不允许，用标签授予 | 假设没有 NaN、无穷、负零、次正规数 |
| `nondeterministic` | 不允许，用标签授予 | 允许结果随调度变化的做法 |

- **许可管的是编译器做的改变，不是用户写下的东西。** 用户写下的类型与转换（`bf16(x)`、`f32(y)`、对数组的 `f32(xs)`）就是要求的精度，不需要许可；`change_precision` 管的是编译器以低于写下的精度计算（把 f32 的矩阵乘换成 BF16、降低累加精度）。`bf16`/`f16` 是与 `f32` 同等的浮点类型：有字面量、标量运算、比较与转换，运算在 f32 中进行并舍入一次。浮点数组的归约在 f64 中累加、舍入一次，返回元素类型。

- 默认放宽适用于数组的逐元素运算，与标量相同。
- 算式优化不自动假设没有 NaN、无穷、负零或次正规数；规则仍须保留这些特殊值的行为，或检查相关显式许可。
- CPU 上按库实现的 f32 矩阵乘与 GPU 一样默认可用，条件是结果可复现（7.6，安全模式下用规范算法）；乘、加分开舍入视为累加方式的改变，属于默认允许的范围；BF16 计算只需 `change_precision`。
- 降低精度（如 f32 矩阵乘改用 bf16 或 TF32 计算）、近似数学函数、特殊值假设须显式许可。
- **浮点的零律要 `finite_math`**：`x * 0 => 0`、`x - x => 0` 对整数精确成立，对浮点不成立（`NaN * 0`、`inf * 0` 是 NaN，负数乘 0 是 `-0`），所以浮点的零律要 `finite_math`；`x + -0.0` 是浮点自己的律（`+0.0` 不是单位元），不与整数的 `x + 0` 合并。
- **整体归约与沿轴归约同名**：`sum`、`mean`、`min`、`max`、`argmax`、`argmin` 作用于 `T[..]` 的全部元素并答元素类型；沿一个轴的形式带 `with <axis, keepdims>`（`x->sum<0>`），在同一个名字之下，由 `with` 参数区分（4.4）。

### 7.4 收紧

- 标签 `#strict` 使所标记的函数或代码块按规范算法逐位计算，不使用任何许可（包括默认许可）。
- 整个程序用流水线参数的安全模式：`std::opt safe_fp=true` 与各后端的同名参数（后端关闭默认放宽，按规范算法逐位计算）。
- **`std::opt::algebra` 是独立的通用算式优化遍，`std::opt` 默认集成。** `safe_fp=true` 将算式阶段限制为严格等价的浮点变换，包括可证明等价的系数翻倍；即使节点有更宽的许可，这个阶段也不使用它来改变舍入路径。常量折叠仍按规范算法，整数仍按其位宽回绕。这是算式优化的策略选择，不是运行时算子算法或整个流水线的全局浮点开关；先前遍已经作出的改写不会回滚。

### 7.5 作用范围

- **许可写在哪段代码上就只对那段代码生效**：被调用的函数不自动继承；内联、展开定义图时许可随节点保留，并随缓存保存。
- 许可写在函数或代码块上（标签，6.2）；词法上嵌在其中的分支臂、循环体、lambda 算作同一段代码。不设模块级的默认许可；后端的入口（如 `tiles.run`）不接受许可。
- 算式优化遍可通过遍自身的参数选择数值策略（7.4）；这不构成向后续遍或被调函数传播的节点许可。
- 细节见 `docs/design/op-semantics`。

### 7.6 可复现

- 同一设备、同样配置下两次运行结果逐位相同；不得使用结果随调度变化的做法（如浮点原子加），除非授予了 `nondeterministic`。同一设备、同样卡数、同一版本的两次运行也是如此，包括 GPU 上的并行归约、按库实现的矩阵乘、多卡数据并行中跨卡的梯度求和。
- CPU 上的规范算法仍是参照答案：测试在严格模式下逐位比较，在默认模式下按误差上界比较。
- 不同设备之间逐位相同不是默认，要用严格模式。
- 跨卡求和的顺序同上。

### 7.7 特殊值与归约

- **`max`、`min` 采用 IEEE 754-2019 的 `maximum`、`minimum`**：NaN 传播，-0 小于 +0。它们满足结合律与交换律，求最大、最小值的归约不需要许可即可重排。**`relu` 定义为 `maximum(x, +0)`**。最大池化与 `log_softmax` 中的求最大值按此规则。
- **NaN 的取值**：`max`、`min`、`relu` 得出的 NaN 一律是标准的安静 NaN（打印为 `nan`）。普通算术产生的 NaN 不受此约束。
- **`argmax`、`argmin`** 按 IEEE 754-2019 的 `maximum`、`minimum` 比较：有 NaN 时返回第一个 NaN 的位置；并列时返回第一个最值的位置，+0 大于 -0。
- **归约**：对空数组或空轴求 `sum` 得单位元 0（乘积得 1）；求 `mean`、`min`、`max`、`argmax`、`argmin` 是故障（种类 `InvalidArgument`），它们没有单位元。整数数组的求和以其元素类型精确累加，溢出时回绕，与整数算术一致。浮点数组的归约在 f64 中累加、舍入一次，返回元素类型；`mean` 的规范形是 `T(sum(float(x)) / float(numel(x)))`，在 f64 里累加并相除，最后舍入一次。`bool` 不是 `is_numeric`，`sum(bool)` 不合法，要计数先转成整数或用 `count`。
- 浮点数转成文字只有一种规则：按值自己的类型求最短、且读回来得到同一个数的文本（`f32` 的 `0.1` 写作 `0.1`，`bf16`、`f16` 各按自己的类型）。`string`、`println`、`format` 一致。
- **NaN 的文本不带符号**：任何 NaN 都写作 `nan`（格式说明要求大写时为 `NAN`），无论符号位如何、无论是否带格式说明、在哪个后端。

## 8. `macro` 与分阶段

- `macro` 是语言核心提供的一种原生标记（标准标签 `#macro`，不用导入），用来帮助做动态的图重写：标记为 `#macro` 的函数可以被 `std::macro` 遍提前求值，把静态值算出来，形成新的静态图。
- **`macro` 本身不定义阶段，也不是必需的。** 流水线里没有 `std::macro` 遍时，macro 函数只是一个普通函数。`std::macro` 是流水线中的一个阶段，不是编译期。
- 一个值要么是编译期常量，要么是一个 macro 的返回值，只有这两种才能被 macro 处理。
- macro 函数体里有效应时，与其他正常函数一样处理：效应在求值之时发生。这是预期行为，从实用角度无法避免。
- **macro 求值失败**：按运行时故障处理，与任何遍运行中的故障相同。
- 在 `std::macro` 中循环至多 100 万轮（与递归上限一样可调）。
- 两种提前计算要分开（6.5）。

设计动机：Python 语言自身的动态性决定了它的灵活性，进而带来提取静态图的麻烦。Camel 希望得到静态图和完整的类型信息，以追求最好的优化空间。动态构造图的需求由 macro 系统来满足：借助多阶段图重写的流水线，先动态地构造静态图，再针对静态图做激进的优化，最后执行，或者转译成其他格式。

## 9. 遍、流水线与图重写

### 9.1 遍与阶段

- 整个运行过程被建模为多阶段的图重写。阶段由用户在命令行上组合的遍序列定义，例如 `camel xxx.cml std::macro std::opt ...`。
- **遍的输入与输出都是图**。区别只在有没有效应：打印、导出、执行这类遍做了 IO 之后输出空图，流水线随之结束；它们与其他遍是同一种东西，不另设"消费遍"。**遍就是函数变换**：图与节点是不可变的值，遍是 `(f: F) => F!`——接收一个函数、返回同类型的函数，与 `with_grad` 同一类。整个程序就是它的根函数，流水线里的遍施加在根函数上；对单个函数施加遍就是普通的调用（`loss->simplify`），不经包装。程序的快照（`Program`）是实现内部的表示，不出现在写遍的接口上；写遍的接口以函数为中心：`open(f)` 打开一个事务，在其中 `replace`、`erase`，`commit(t)` 给出同类型的新函数（或错误值），不提供就地修改。规则是 `rule` 声明的 `Rule` 值，规则集是 `Rule[]`，调度是普通的函数（见 9.11）。
- 这种设计的出发点是工程上的方便，不是学术上的优美：一份代码，通过更改遍的组合就能做很多事——原型测试、调试、编译优化、导出部署、转译为其他格式等，而不用换一种语言把类似的逻辑再写一遍。这是图原生定位带来的特性之一。

### 9.2 显式的流水线

- **流水线由用户显式组合**，语言核心不限制遍的顺序；模块不能在导入时自动加入遍，也不能自动改变流水线。
- 不加任何用户指定的遍时，默认走 `std::default`，它指向节点虚拟机。
- **`std::` 前缀只给核心自带的遍**；模块的遍用模块自己的名字，别名由模块登记。
- 在命令行上写某个模块的遍（如 `onnx::export`）时，由编译器自动加载该模块；纯程序不必为了被导出而 `import` 它用不到的模块。
- **库检查自己的前提**：所需的遍不在流水线中时，给出说明要加哪个遍的诊断。
- 流水线是否可以写在源码里，尚未决定（第 15 节）。

### 9.3 遍参数

- **遍的设置就是它的 `with` 参数**：有名字、有类型、可以有默认值（4.4），C++ 写的遍与 Camel 写的遍同一个模型。源码里写 `f->std::opt<safe_fp: true>`。
- **命令行上，参数写成跟在遍名之后的 `key=value`**：`camel m.cml std::opt safe_fp=true onnx::export out=model.onnx std::fvm`。含 `=` 的词是参数，归属于它前面最近的遍；值按参数声明的类型解析（字符串取原文），不需要引号。
- **固定的流水线写成 Camel 函数**：遍是函数变换，流水线就是函数组合（`f->std::macro->std::opt<safe_fp: true>->tiles::compile`），按名字在命令行上使用，可以放进库里共享；不另设流水线配置文件。
- **只属于一个遍的设置是那个遍的参数**，不是全局命令行选项；全局选项只留进程级的事（回收器、内存上限、设备、模块搜索路径、诊断格式）。设置不放在环境变量里。
- **规则集显式交给遍**：标准的优化遍接受额外的规则（`std::opt` 的 `with` 参数 `rules: Rule[] = []`，与标准库那批定律合在一起用）：`f->std::opt<rules: [negate]>`，命令行 `std::opt rules=[law::negate]`。导入模块、写下规则，都不会改变别的遍做什么。
- 签名的唯一来源是 `.cml` 里的声明，C++ 只登记实现；设置不放在 `CAMEL_*` 环境变量里，行为由命令行、遍参数或构建选项决定。

### 9.4 标签的生命周期

- **标签由读取它的遍处理掉**：遍用完一个标签后，标签可以不再存在，之后的遍（如内联）不受它约束。遍的先后由用户安排。
- **库的标签可以由读取它的遍用完即去**；影响结果的标准标签（如数值许可，7.5）则留在节点上，不随遍消失。
- **标签可以声明读取它的遍**；流水线中没有这个遍时，编译器警告"标签没有效果"，使标签是否生效可以观测。
- **内联保留来源**：内联器把被内联函数的身份与它的声明标签记在节点的内联来源上；读取标签的遍若发现标签只出现在已被内联的节点上，给出"标签没有生效，因为函数已在本遍之前被内联"的警告，并说明应调整的顺序。

### 9.5 源码层规则只约束建图

- **语言核心不限制遍的顺序。** 但顺序不同，执行结果确实可能不同：遍并不保证产出同一张图，它会修改图，并且可以有效应。**"任意遍序列下行为不变"不是 Camel 的性质，不要把它当作约定去实现或检验。**
- **源码层的限制只在"源码翻译到图"这一步生效。** `var`/`let`、`sync`、资源等规则约束的是编译器怎样构造图；图一旦得到，这些规则不再是后续图重写阶段的约束。一个遍要遵守什么约束，是这个遍自己的约定；重写之后图的语义行为是否变化，由遍的开发者和使用者各自负责。Camel 只负责编译得到图，不对遍做限制。
- 标准库里的优化遍不应把程序改错。这是普通的软件质量要求，靠测试保证。

### 9.6 优化与遍的行为

- **"开不开优化，程序的行为一样"不是 Camel 的设计原则**，语言核心也无法强行保证这种一致性。一个遍保留什么、删掉什么，由这个遍自行决定。例如同步块里结果没有被使用、但会出故障的纯计算（`let q = 1 / z`）：不加遍时故障，化简遍可以把它删掉、程序继续。这不算缺陷。
- **优化不改变图上的算子身份。** 融合、换用库实现（BLAS 等）是实现选择，记在节点属性上，图上保留原算子；新算子只在有自己的语义声明与定义图时才可出现。

### 9.7 图重写与效应

- **效应追踪在各个遍之下的保持方式**：效应是图上的摘要（图的出口是否依赖效应、写了哪些捕获的变量），每次提交由节点重新算出并校验；遍不可能提交一张摘要与内容不符的图。遍删掉或挪动效应是否正确，仍由遍自己负责（9.5）。
- **改写不改变哪些效应执行**：程序的语义按源程序定义，优化必须保持它。一条规则的右边如果丢掉了左边匹配到的一部分，只有当丢掉的部分是**纯且不会出故障**的计算时这条规则才适用（3.4 的同一个谓词：`x * 0 => 0` 也不作用于 `(a / b) * 0`，否则故障消失）；等价饱和中，抽取同样不得选一个丢掉可能出故障部分的写法；这由规则引擎统一检查，规则作者不必逐条考虑。例：`x * 0 => 0` 不作用于 `println(5) * 0`——源程序里 `println(5)` 被乘法用到，所以它执行，改写后也必须执行。纯计算上的化简空间不受影响。同理，规则把一部分从函数体、循环体或臂里移到外面时，被移出的部分必须是纯且不会出故障的计算（否则空数组、零轮时会多出一个故障），由引擎统一检查。

### 9.8 入口与导出

- **所有遍共享 `main` 作为入口。** 导出有两种情形，取决于程序表达的是什么：
  - **程序只表达纯粹的计算意图**（这是 Camel 程序的本来面目）：程序本身不应该关心内部要怎么导出、导出什么。此时用遍的组合就能导出，例如 `camel x.cml std::macro std::opt onnx::export`，被导出的就是 `main` 所表达的计算。
  - **程序同时兼顾了计算意图之外的意图**（例如计时、跑基准测试）：这时用遍的组合去导出就不合适了。不如直接做到底，由程序内部调用算子（如 `onnx.export_model`）对自己的某个子图完成导出。
- **`main` 可以带参数。** `main` 与其他函数一样是一张子图，它的参数就是这张图的输入：导出时是模型的输入（形状取自带形状的数组类型），运行时由外部给值（命令行；缺少时给出带位置的明确错误，不用零或随机数代替），求梯度时是可以对其求导的量。`main` 不带参数时导出的是没有输入的常量模型，允许。返回单个值是一个输出；返回元组或结构体则展开为多个输出。
- **只有显式声明了返回类型的 `main`，它的返回值才算程序的结果。** 纯的 `main` 的返回值通过命令行已有的 `-o` / `--output <file>` 输出，默认是标准输出，不另设专门的选项。
- 导出（如 ONNX）是转译遍，同样建立在遍机制之上。**导出遍不必做太多检查**：能翻译就翻译，翻译不了再报错，不追求学术上的洁癖。导出遍可以做必要的适配性化简，但不应成为主力；主要的求值与化简应由 `std::macro` 和优化遍在它之前完成。

### 9.9 自动微分

- **自动微分是建立在遍机制之上的库，不是语言核心。** 它作用于交给它的图，不要求流水线里先有 `std::macro`；遇到它处理不了的结构（例如尚未展开的编译期构造）时，在那个位置带诊断拒绝。这些是库的前提条件，不是语言核心的约束。
- 被求导的函数与 `var`：见 3.5。
- **穿过循环求导**：反向需要正向每一轮的中间值（残差）。正向循环把每轮的残差作为收集输出保存（值，不是闭包），附一份说明各槽位是哪个残差的清单；反向是一个按轮次倒序的循环。每轮 O(1)，总计 O(n)。正向循环的轮数可以由条件决定。
- **残差不设上限**：与普通数组的增长相同，内存耗尽按资源耗尽带位置报告；不另设轮数上限。以后可用重算类标签（检查点）把内存降到 O(√n)，残差的设计不排斥它。
- **数组的切向量是"元素的切向量组成的数组"**：`f32[n]` 的是 `f32[n]`，`{x: f32, y: f32}[]` 的是同型的结构体数组；元素没有切向量（如 `string`）时数组也没有（5.4）。循环遍历或捕获的数组依赖被求导的参数、而它**没有切向量**时拒绝，带位置的诊断点名 `loop` 与那个数组；数字数组被捕获时梯度照常累加，按下标读取的反向是散射加。任何依赖被求导参数、却没有梯度通道的**连续**值，都不得悄悄丢掉梯度，一律带位置拒绝。**离散的值**（整数、布尔）对参数的导数按定义为零：由参数算出的整数或布尔再转回浮点，梯度为零而不是拒绝（与 JAX 相同）。
- **切空间按类型逐个定**：数字与布尔有切空间，就是它自己的类型（离散值的梯度是同形状、同元素类型的零）；`string`、函数没有；结构体与元组有切空间，当且仅当每个字段都有。给用户的梯度（`grad`、`with_grad` 的结果，`grad of P`）与参数同型，结构体和元组一样；循环状态、捕获的元组、反向 tape 这类机件内部的聚合只带真正需要梯度的成员，是实现的选择。梯度的元素类型是被求导值的元素类型。
- **缺规则必须拒绝**：对一个运算，要么给出正确的导数，要么在编译期拒绝并点名这个运算；跑通却给出错值不允许。数组上的 `for` 可以求导（逐轮读 `xs[t]` 的反向是按 `t` 的散射加）。每个不能求导的调用各报一条诊断，位置就在那个调用上，函数值是在哪里选出来的作为关联位置附上；`std::macro` 在编译期展开 `grad` 时收集全部拒绝，运行期才建导数图时在第一处停下。
- **循环体与条件里有效应时沿用现有规则**：效应只在正向执行，反向是纯的；"读可微类型的 `var` 即拒绝"的检查扩展到循环的条件与循环体，诊断点名 `loop`。
- **带循环的梯度的 ONNX 导出另作一项**：残差是值，导出时映射为 `Loop` 的 scan 输出与反向 `Loop`（必要时用 ONNX 的序列类型容纳参差的嵌套循环）。
- **对 `with` 参数求导**：`grad(f)`（只返回梯度）、`with_grad(f)`（返回"值连同梯度"，即 `(值, 梯度)`）对 `f` 的**第一个 `with` 参数**（模型的权重）求导，其余 `with` 参数（如超参数）当作常量；如 `with_grad(loss)<m>(x, y)` 得到 `(损失, 与 m 同型的梯度)`。推荐把变换与调用分两步写：`let loss_with_grad = with_grad(loss)`，循环内 `let (l, g) = loss_with_grad<m>(x, y)`。要对数据求导（如对抗样本）时，用 lambda 把它变成 `with` 参数。第一个 `with` 参数是 `var`、没有切向量，或函数没有 `with` 参数时，`grad` 在编译期拒绝并说明原因。

### 9.10 调度器、后端与发布

- **并行调度器把没有可并行之处的子图交给字节码解释器执行**，并按同一规则计数递归上限：调高 `--max-recursion-depth` 时，深的非尾递归在 `std::prl` 上与在 `std::fvm` 上一样跑完。
- 发布包的指令集基线是 `x86-64-v3`（AVX2 与 FMA）。

### 9.11 规则与事实

- **`rule` 声明一个类型为 `Rule` 的值**；规则集是 `Rule[]`，调度是普通的函数（`f->rewrite<rules>`、`f->saturate<rules, rounds: 8>`、`f->std::opt<rules: [negate]>`）。写下一条规则不会改变任何遍的行为，规则集一律显式交给遍（9.3）。
- **规则与事实的形参 `x: T` 的类型是 `Node<T>`**：改写只看得到图，形参必然是节点，节点有它的值类型。`Node<T>` 是可以写的类型，Camel 写的遍里可以写 `n: Node<int>`；不带实参的 `Node` 是值类型未知的节点，在它上面查询要写 `range::<int>(n)`。模式里把 `x` 当值用的地方（`x * 1`）按它的值类型检查。`const c: T` 的形参是一个类型为 `T` 的常量，条件与右边里拿到的是它的值；每个 `const` 形参另带一个隐藏的节点形参，`node_of(c)` 取它；左边没有给某个 `const` 形参绑定节点的规则在定义处被拒。
- **事实的查询实参是节点**：事实描述图上一个值怎么得来，查询只能写在规则条件、事实主体或拿到 `Node` 的遍里；在普通函数体里传一个值给查询，报的是说出这条规则的诊断。查询的类型实参照 5.9 推出，推不出就写 `::<T>`。
- **规则的 `when` 条件不能有效应**，规则定义处检查（泛型规则检查模板体和它直接调用的非泛型函数，依赖类型实参的效应在实例化处检查并报给用户）。条件里的事实查询找不到结果时条件为假（这条规则在此不适用），不是遍失败；可交换的算子上，部件查询不看操作数的顺序。
- **泛型规则在匹配处实例化**：被匹配的节点的类型解出类型参数，以类型元组为键缓存；某个类型元组做不出实例（条件为假，或模式在该类型上没有算子）是安静的，`why_not` 报告原因。规则可以有多个类型参数。规则的类型实参与 `with` 实参走同一个实例化通道，实例的键是“规则 + 类型实参 + `with` 值”（5.5）。`when` 里的名字按声明处解析（4.4）。
- **检验**：每条规则入库前经 `check`：`reassociate`、`contract` 类规则的命题是有限值上实数相等、特殊值（NaN、无穷、负零）上逐位相等，要了 `no_nans`、`no_infs`、`no_signed_zeros` 的才豁免相应特殊值；`refine_accuracy` 类规则的命题是误差界。判决只有 `proved`、`refuted`、`sampled`；采样种子由规则的身份（名字与类型元组）派生，与它在数组里的位置无关；检验的对象是模块导出的全部规则，不是手列的清单；`refuted` 的规则不得留在库里。
- **引擎统一承担的检查**（规则作者不必逐条考虑）：丢掉的部分与移出的部分必须是纯且不会出故障的计算（9.7）；规则替换了图的出口或返回值所在的节点时，由引擎把锚点移交给替换者；“这次改写会不会多算一个子表达式”这类收益归代价函数，不归规则的 `when`。

## 10. 模块与库

### 10.1 模块与图

- **模块顶层的代码不会默认执行**：Camel 不是命令式的脚本语言。顶层的语句与别处一样按依赖求值。
- **模块可以导出值。** 模块本身是一张 `__root__` 图；全程序只有一张 `__root__`，各模块顶层的节点都在上面，函数经捕获端口取值；捕获按"模块 + 名字"绑定，不按名字在调用处查找。模块顶层的一个 `let` 就是 root 上的一个节点，被依赖才求值。这样没有跨图的节点引用。合并的具体做法先出设计说明。C++ 模块也可以导出值（`math::pi`）。
- **顶层的值在 `main` 开始之前求值，依据是静态的依赖**：`main` 沿调用链静态可达的函数用到的顶层值都会求值，运行时是否走到用它的那条臂不影响。
- **模块顶层的 `let`、`var` 与书写顺序无关，只看依赖。** `let area = pi * r * r` 可以写在 `let pi` 之前；顶层值之间成环是编译期错误。函数体里的局部 `let` 仍是先声明后使用。
- **模块可以互相导入。** 为此加载分两个阶段：先收集所有模块的声明，再建函数体。模块导入自己是允许的，没有效果；类型跨模块成环给出成环的诊断并列出环。
- **不能导出 `var`**；导出读写它的函数。被导入模块里的 `main` 是普通函数。

### 10.2 命名空间与名字

- **命名空间块里可以不带前缀使用同一块及外层块里的名字。** 命名空间块里可以有值：`namespace Config { export let limit = 10 }`，用 `Config::limit`；与模块顶层的 `let` 只差名字里的路径。重开同一个命名空间块，前一块里的 `using` 不带到后一块。
- **`using namespace`**：可以对本模块的命名空间使用；只在它所在的块里生效（写在函数体里就只对那个函数生效）；两条 `using` 带来同名同签名、无法区分的名字时，在使用处报错。
- **名字的优先级只有一条规则**：局部 > 本模块（所在命名空间、外层命名空间、模块顶层）> 按名字导入的 > `using namespace` 带来的 > 内建。取第一个有这个名字的层；同一层里同名的函数合成重载集，签名相同是错误；跨层不合并。运算符重载例外，各层合并。
- **`import a from m` 是从 `m` 引入名字 `a`**，等价于 `import { a } from m`，与语言文档一致；给模块起别名写 `import m as x`。**导入可以改名**：`import { find as str_find } from str`。两个导入的名字冲突是编译期错误，不得静默取其一。允许 `import { … } from m::N`。不实现 `use`，退掉这个保留字。
- **模块的 `import` 先在模块自己的目录里找**，再按模块根（`-I` 给出的目录，按给出的顺序）、标准库的顺序找；入口程序与库模块同一条规则。这样一个库无论被谁导入，它的导入都解析到同一处。
- **一个文件就是一个模块，模块名就是文件名**：没有 `module` 声明，名字只有这一个来源，入口文件也一样（不设 `main` 这个占位名），与命令行上路径的写法无关（`./counts.cml` 与 `counts.cml` 的遍名前缀都是 `counts`）。模块可以用自己的名字限定自己的东西：`shapes.cml` 里写 `shapes::area` 与写 `area` 相同。模块在、但它没有这个遍时，报“模块没有提供这个遍”，不报“未知的遍”。
- **诊断、调试器、语言服务器与图名一律显示完整的名字** `模块::路径::名字`，不引起歧义时省略模块名。名字有歧义时列出各个限定候选，不论导入给模块起了什么别名。

### 10.3 模块缓存

- **编译好的模块可以缓存**（`.cmc`，cached module object），使一个模块不必重新编译。每个模块的缓存是以该模块为根的一张图；它是为了方便与加速，不必等同于实际编译的最终结果。本节定下它的形式与失效条件；是否采用仍待裁定。
- 缓存放在源文件旁的 `__cmc__/` 目录里；先默认关闭；命中缓存的模块不重放编译期警告。导入方的缓存在下列任一项变化时失效：导出函数的签名（含推断出的返回类型）、它间接用到的模块级值、它的效应、泛型函数的函数体。`--verify-ops` 仍读源码，不读缓存。

### 10.4 C++ 原生模块的位置

- **语义原子与实现原子分开。** 一个函数的**语义**只有两种来源：原子算子，或用 Camel 写的定义；它的**执行**可以另有原生内核。两者分开，库的形态就不必在"表达力"与"性能"之间二选一。
- **原子算子（C++ 无体声明）只在三种情形**：与外部世界打交道（I/O、操作系统、外部库、设备）；需要语言不暴露的内存与布局控制的内核（矩阵乘、卷积、`take` 与散射、排序）；标量数学函数。原子集合**最小且正交**：能由其他原子低成本组合出来的，不做原子。每个原子声明它的语义事实（纯度、资源、下标映射、定律、导数）。
- **其余一切用 Camel 定义**（默认）：softmax、规范化、损失、优化器、`tree_*`、统计、数组与字符串的工具函数。编译器看得穿它们，融合、求导、导出、规则自动适用，不为它们各写一份导数或导出规则。
- **常用而热的定义带原生内核**：Camel 函数体仍是语义，`#impl(f)` 标出实现它的原生内核 `f`（本模块一条私有的无体声明）。**默认不展开**：普通的遍与执行器把它当作一个算子，编译与执行的负担与原子算子相同；需要看内部的遍（自动微分、融合、导出、规则）才按需展开。差分测试保证两者结果一致。常用的数值操作（`sum`、`min`、`max`、`all`、数值数组上的 `map`/`reduce` 等）一开始就配内核；其余在测量表明编译器的结果明显更慢时再配，编译器追上后删除内核。
- **一个模块 = `.cml`（声明与 Camel 定义）+ `.cmo`（原生内核）**，声明模块可以有函数体。`#impl` 可以标在泛型函数上：内核是同样带类型参数的本模块私有无体声明，每个元素类型一条，各带 `when` 分臂（臂重叠是错误）；调用在实例化时按类型选执行器，某个类型没有执行器就执行函数体（函数体是语义，结果相同）。内核不能属于别的模块。“纯数据”的判断 `is_plain` 是用 Camel 写在 `types` 里的谓词，`to_bytes`、`from_bytes`、DLPack 交换、数据块的分配共用它。
- **库的编译只付一次**：库函数按实例编译、优化一次，结果进模块缓存（10.3）与特化缓存；调用处付出的是一次调用或一次内联，不是重新优化库的函数体。
- 实现中暴露的表达问题逐一讨论，公共的需求吸纳进语言核心，不在库里绕过去。

### 10.5 库边界

- **标准库的边界**：必须接触系统或性能敏感的原语用 C++ 算子；建立在原语之上的组合逻辑用 Camel 写。Camel 写的库是子图，遍看得见；C++ 算子在图上是一个不透明的节点。
- **模块接口**：从内部头文件里整理出一层公开的 C++ 接口，按版本承诺兼容；其余内部头不作承诺。
- **内存管理的方式不进入语言的语义**：对象没有可观察的身份，回收的时机不可观察，C++ 算子通过句柄接触对象。各后端可以选适合自己的方式；后端可以少回收甚至不回收垃圾，回收的时机与是否回收都不可观察。
- **垃圾回收**：Camel 原生的小对象可以走分代管理（可以移动）；涉及外部接口时，用 Camel 原生对象来管理外部指针，外部内存不进可移动的堆。模块不得跨调用保存指向 Camel 对象的裸指针。分代回收对 C++ 算子作者的约束可以接受。落实顺序：先审计模块并立下句柄规则，再在解释执行的后端上启用分代并做压力验证，即时编译等栈映射做好之后再打开。分代回收在可用之后默认开启。
- **有身份的东西要列明**：`var` 单元、经 `var` 参数就地修改的对象、外部库包装的对象（Python 对象等）；其余的值没有可观察的身份，后端可以随意复制或共享。对象头里不加类型字。
- **内存管理分三层，都是实现方式**：编译期规划（生命周期能从图上看出的数据）、**数据块**（带计数）、分代追踪回收的 GC 堆（其余对象，含图与快照）。**数据块**是核心内存层的通用机制，不专属于数组：一块**不含引用**、**地址固定**（GC 不移动它）、**带计数**的内存，可以有外部的所有者与释放回调，可以在不同设备上。使用者是纯数据元素的数组、`Bytes`、超过阈值的字符串、表格的列、内存映射的文件、外部内存（DLPack、Python 缓冲区协议、OpenCV 等），以及设备显存。**"不含引用"由类型系统保证**：纯数据类型是数字、布尔、复数，以及只由它们组成的结构体与元组；因此数据块之间不会成环、GC 不扫描它们、可以零拷贝交给外部（红线）。数据块的字节计入 GC 的触发与上限。小于阈值（256 字节）的数据内联在 GC 对象里，需要固定地址时（导出、视图）才转为数据块。**计数为 1 时，"返回新值"的操作原地进行，这是有保证的行为。** 计数必须如实：值多出一个仍然活着的持有者（存进 `var` 单元而源绑定之后还要读、被闭包捕获、存进收集槽）时，由编译器在内存规划里插入“加一”，在最后一次使用之后插入“减一”（Perceus 的做法），于是“计数为 1”恰好等于“没有别的观察者”。是否原地分三层：编译期规划证明（图上这是旧值的最后一次使用，其他只读使用者排在更新之前）、运行时数组计数为 1、都证明不了就拷贝；决定只在内存规划阶段做并写进执行计划。 数组的运行时表示兼容 DLPack（数据指针、设备、元素类型、形状、步长、偏移），与 PyTorch、NumPy、CUDA 库零拷贝交换。Python 嵌入 Camel 时形成的跨语言环第一期不回收。小型逻辑计算不得因此变慢，以性能基线核对。详见 [原生多维数组、内存管理与互操作](design/arrays-memory/README.cn.md)。

### 10.6 `std::cpp`

- **`std::cpp` 的目标是生成可以脱离运行时独立部署的程序。** 无法同义转换的情形可以引用 Camel 的运行时模块，但要尽量做干净。生成的程序要给出带源码位置的故障、遵守递归上限，尾调用不使栈增长。生成的故障报告与解释器逐字相同；递归计数精确（与各后端一致）。
- `std::cpp` 生成的模块接口用标准 C++ 类型，不暴露运行时的内部类型。
- `println<fmt>` 多出的空行、`print<fmt>` 多出的换行是解释器的缺陷，修掉解释器；去掉 `std::cpp::bench`；生成程序里的 `map`/`filter` 先串行；`main` 的参数用 `--arg name=value` 给出，与命令行一致。

### 10.7 Python 宿主边界

- 宿主（如 Python）调用 Camel 的泛型 `export func` 时，按宿主传来的实参类型实例化并缓存实例；只出现在返回类型里的类型变量才需要宿主显式给出。数组按元素类型传入，不转换（也保住零拷贝）；宿主的标量（Python 的 `int`、`float`）按字面量处理：进入形参时取形参类型，放不下报错。错误值统一成 `FaultError` 加种类名，不把错误里的字符串提升成宿主的类名。执行 Camel 期间释放 GIL，Camel 回调 Python 时再取得。

## 11. 标准库约定

### 11.1 字符串与 `Bytes`

- **`string` 保证是合法的 UTF-8**，下标与长度按码点计；字节序列用内建类型 `Bytes`，两者之间显式编码、解码。`string` 只表示文本；文件接口分文本与二进制两套。另外提供按码点读写的算子。
- 字符串也有 `contains`，写法与数组的一致：`'hello'->contains<'ell'>`。

### 11.2 `Json`

- `json.decode` 返回自描述的 `Json` 类型，并提供 `decode_as::<T>`（显式类型实参见 5.9）。
- 坏的 JSON 文本，`decode` 返回 `Json!` 的错误值，不是故障。
- `Json` 的访问器接受 `Json?` 与 `Json!`，以便链式取值（解析失败也能链式取值）；`as_float` 接受整数；`get<下标>` 越界给 `null`。
- **`Json` 的访问器接受 `Json!` 时，错误原样传下去**：`decode(text)->get<'a'>` 的类型是 `Json!?`，用 `!!`、`??` 处理。太深的文档报 `JsonTooDeep`（与"文本不合法"区分），默认深度上限 10000，以后作为 `decode` 的可选参数开放。

### 11.3 集合与排序

- **映射与集合做成内建类型。** 不新增字面量，用已有的数组字面量加 `as` 转换（与 `x as f32[2, 3]` 同一种写法）。操作一律返回新值；查找不到的结果为空。

  ```camel
  let m = [('a', 1), ('b', 2)] as Map<string, int>   // 示意
  let v = m['a'] ?? 0
  ```

- 映射的遍历与打印按键排序；能作键的类型是整数、布尔、字符串，以及它们组成的元组。
- **`append` 返回新数组，不修改原数组**：`let ys = xs->append<5>` 之后 `xs` 不变；要"追加到变量上"写 `acc = acc->append<5>`，与 `x = x + 1` 一样。就地改写只是实现层面的优化（旧值不再被使用时可以在原处追加），不进入语义，也不另设显式的就地算子。其他标准库算子同此。纯运算的结果没有被使用（如写成语句的 `xs->append<5>`）是编译期错误，并提示改写为重新绑定。
- 返回新值与就地修改不用两个名字区分：只有 `sort`，它返回新数组；`xs = xs->sort` 在旧值不再被使用时就地排序，与 `acc = acc->append<v>` 是同一种实现层面的优化，数组不设显式的就地算子。
- **`enum` 可以作映射的键与集合的元素**，当它所有字段的类型都可作键时（可作键比可比较更严：浮点可比较但不可作键）；顺序先按变体在声明中的先后，再逐字段比较。

### 11.4 调用风格

- 被处理的值是普通参数，其余是 `with` 参数（`'a,b'->split<','>`、`xs->take<3>`）；两个参数地位对等时都是普通参数（`merge(m1, m2)`）。映射与集合的操作照此只保留一种写法。

### 11.5 输出与格式

- **程序的输出与 `fs` 写出的文本在各平台上是相同的字节**，Windows 上不写 `\r\n`。浮点数转成文字的规则见 7.7。
- **字符串插值用反引号**：`` `step ${i}: loss ${l:.4f}` ``，`${表达式}` 插值，可选的 `:格式` 与 `format` 的格式说明相同；普通的 `{` 不需转义；可以跨行；是 `'...'->format<...>` 的简写，格式说明与类型不符在编译期报错。
- **数组只有一种打印形式**：嵌套的方括号，元素按值自己类型的最短文本（`[[0.0, 1.0], [2.0, 3.0]]`）；格式说明符用在数值数组上逐元素生效，括号与分隔照数组的形式（`'{:.4f}'` 作用于 `[0.7692267, 0.780836]` 得 `[0.7692, 0.7808]`）。合成的来源（不是文件的源文本）用尖括号写名字，如 `<pipeline>`。

## 13. AI 技术栈

### 13.1 调度

- **倾向（不是禁令）**：Camel 源码无损地表达计算的意图；在哪里算、怎么算这类与环境相关的内容（分块、布局、放置、内存策略），原则上不写进源码，由执行时的上下文注入（遍参数、调度文件），格式与粒度由读取它的库决定。放置是例外，写在源码里：`#gpu` 标在函数、块或命名空间块上，声明"这一段在设备上算"，由 `tiles::compile` 遍读取（第 13.4 节）。`#gpu` 范围内设备不支持的算子是编译期错误，不静默退回主机；没有读取这个标签的遍时编译器给出警告（9.4）。设备由 `--devices` 在执行时选择。
- **为了性能上限，允许在源码中直接写调度**：上一条是倾向，不排斥专家路径。块级内核（Tiles 路线第 6 节的 `Tile<T,[形状]>` 与 `#kernel`）把块形状写在源码里，由作者直接控制，与由 Tiles 自动决定的高层路径并存。
- **调度的粒度到函数为止**：要更精细，就把那一段提成子函数，用按函数的调度。内联之后，节点上记录的内联来源仍能把它们对应回原来的函数。自动调优按计算的结构身份（算子、形状、类型、前后关系）记录结果，不依赖名字。语言不提供"给某一步计算起名字"的机制。
- **调度也可以用 Camel 写**：意图写成一个函数，在另一个模块里用变换函数（或装饰器）调度它，不一定只能靠命令行上的遍组合。

### 13.2 低层计算

- **低层计算也用 Camel 的图表达**，不另造中间表示：物理操作（块的加载、块内矩阵乘、同步等）是后端库登记的算子，带语义声明，能给出时带 CPU 上的参考实现；逐级降低都是图到图的改写，最后一步才打印成目标代码。每一级降低后的图在可能时仍可在 CPU 上运行，与参照答案核对。

### 13.3 设备与内存

- `Device<T>` 保留，对结构体与元组按字段分配，`Device<{ a: A }>` 与 `{ a: Device<A> }` 是同一个类型。搬运是普通的有效应的操作，可以在代码中显式写，可以由 Camel 写的变换函数作用于一个函数值而插入（"遍即函数"），也可以由优化遍自动完成。
- 异步不进入语义：顺序由数据依赖与 `sync` 决定，流、事件、重叠执行是后端的实现。
- `tiles::compile` 的上传、区域执行、下载是纯计算，设备内存是不可观察的分配；相同的区域调用可以合并。
- **`#gpu` 作用域里写的主机效应**（`println`、`save_npy`）是程序的一部分，照常执行：放在主机上，观察点插一个显式的 `download`；它既不被拒绝也不被静默丢掉。顺序靠同步边接到替换作用域语句的节点上。`Device<T>` 是签名上的放置断言，普通值传给 `Device<T>` 形参时由遍插入 `upload`；`--devices cpu` 用同一支持面编译、由主机执行同一段图，有没有设备编译结果都一样。`tiles::compile` 不碰没有 `#gpu` 作用域的程序；作用域里的梯度靠 `std::macro` 在它之前展开，作用域里有未展开的宏算子时报缺少前置遍并点名 `std::macro`。空的作用域不警告。上传与下载的导数规则互为反向。

### 13.4 分布式

- 切分写成标签 `#shard([轴名, ...])`，可贴在函数参数上；轴名是抽象的，轴的大小在执行时注入；同样的信息也可以写在调度文件里。标准库的 `shard` 遍推导每个结果的切分、插入通信（普通的有效应的算子）、报告不一致；推导不下去的算子（没有声明下标映射的原生算子）退为先收集再计算，结果正确但较慢。类型系统不变。跨卡求和的顺序按 7.6。
- **放置（倾向，不是红线）**：用户主动声明计算放在哪里，不默认上 GPU。通常源码只写意图——`#gpu`、`#cpu` 标在函数、块或命名空间块上——数据的驻留、搬运与同步由编译器从图上推出；用哪张卡、几张卡通常是运行时配置（如 `--devices`），同一份代码换机器不必改。需要时允许在源码里写具体设备（如流水线并行的分段、为性能固定到某张卡、异构设备），运行时配置可以覆盖或补充它。工程便利与优化上限优先于"源码不含配置"的整洁。

### 13.5 训练基础设施

详见 [训练基础设施设计](design/training/README.cn.md)。

- **参数树**：标准库提供 `tree_map`（可同时作用于多棵同构的树，对位的叶子作为多个实参传给回调）、`tree_unzip`、`tree_reduce` 等操作，作用于由结构体与元组嵌套成的值，叶子顺序为深度优先、按字段声明顺序；叶子边界永远由树实参的类型决定（`tree_map` 以第一棵树为准，`tree_unzip` 以给出的参照树为准），不由回调的形参类型决定；树的形状由类型决定，操作在编译期展开为逐叶的普通节点。
- **参数树的路径**写作 `blocks.0.w`，根是空路径；检查点中的名字与 `tree_paths` 的结果逐字一致；`save_tree`、`load_tree` 属于 `ckpt` 模块，`tree_paths` 属于纯 Camel 的 `tree` 库。
- **无状态随机数**：在现有带全局状态的随机数之外，提供由键决定的随机数（`key`、`fold`、`split`、`normal`、`uniform`、`randint`）。它们是纯函数，不是外部效应；规范算法为 Philox4x32-10，整数与均匀分布的结果跨设备逐位相同，正态分布按超越函数的 ulp 上界。

### 13.6 部署与数据管线

- 部署不另设格式：现有后端的格式够用，冻结后的程序也可以直接导出为 `.cml` 运行。
- 数据管线不需要语言层面的新东西，由标准库提供读取与分批工具。
- **网络与流**：`net`、`http` 模块（底层原语为 C++）；流 `T..` 是核心类型（5.4）：按需拉取、可能无限，`for` 可以遍历，作用于流的 `map`、`filter` 等是惰性的，背压由拉取自然实现；窗口、按键聚合、合并、分批由库提供。表格兼容 Arrow C 数据接口，与 Pandas、Polars、DuckDB 零拷贝交换。长期方向是多机分布式运行时，批处理与流处理用同一个模型。详见 [网络、长耗时效应的并发与流](design/io-concurrency-streams/README.cn.md)。
- **表格** `Frame<行类型>`：行类型是普通结构体，按列存储、兼容 Arrow，可空列写 `T?`；列结构可以手写、在编译期用 `schema_of<'文件'>` 推出（可用 `camel schema` 固定进源码）、或在运行时得到 `Table` 再用 `as` 转换；不需要 `collect()`，惰性与查询优化来自按需求值与库的 `rule`，运行时按批流式执行；结果的行类型由类型函数推出。详见 [标准库的重新规划](design/stdlib/README.cn.md) 5.1。

## 14. 容易出现的误读

以下都是实际发生过的误读，修改代码或文档前请对照：

1. 把"同步块之外未被使用的效应不执行"当成缺陷去修，或改成报错。——这是预期行为。
2. 仍按已退役的 `wait` 与前缀 `sync func` 来理解效应的排序。——它们已被"同一资源自动有序"与推出的 `uses` 取代；函数体后缀的 `sync`（函数体是同步块）保留。
3. 认为被同步块调用的函数，其函数体内的效应会因此执行。——函数的行为由它自己的子图决定。
4. 把 `var` 参数实现成传值再在返回时拷回。——Camel 默认是引用。
5. 把 `let` 的不可变实现成运行期的内存保护。——它是编译期校验。
6. 把 macro 函数体里的效应当作例外或错误。——与普通函数一样处理。
7. 认为没有 `std::macro` 时 macro 函数不能运行。——此时它是普通函数。
8. 把"任意遍序列下行为不变"当成语言的约定，并据此把遍序敏感判为缺陷。——遍可以改变图并带有效应。
9. 把自动微分的前提条件当成语言核心的约束。——它是库的约束。
10. 从派生的特性里挑一个当作 Camel 的"核心卖点"（例如"一份代码多种用途"）。——核心是图原生，其余是自然产物。
11. 为了让某个测试通过而改变语义。——先确认语义，再判断是测试错了还是实现错了。
12. 把两层标记的书写顺序读反（以为 `T?!` 是"可空套可错"）。——标记从最内层写起：`T?!` 是 fallible(nullable(T))，`T!?` 是 nullable(fallible(T))；解析器与打印器一致。

## 15. 尚未决定的问题

遇到下列问题请向语言作者提问：

- 类型表达式要不要有类型运算（交、差、并之类）。文法里现在没有类型运算，没有预留的运算符；要加的时候，写法和含义一起定。
- `typeof` 作用于常量值时的含义，以及它在泛型里的用法。
- 类型函数求值失败或不终止时的处理。
- 同一个可变对象在同步块之外被多处通过引用写入时的行为。
- 能否在声明之外给别处的声明补贴标签（调度是否例外）。
- **并行的 `map` 出了故障之后，下标更小、还没开始的元素是否仍然执行**（`parallel-fault-lower-elements`）：
  `(0..64)->map<bad>` 每个元素都出故障，而工作线程恰好先跑了第 40 个。现在的实现：只有下标大于 40 的不再开始，0 到 39 仍然执行，于是报的总是第 0 个，与线性后端相同、每次运行一致。
  候选：出故障后一律不再开始任何元素；这样"下标最小的"只在碰巧已开始的元素里取，每次运行可能不同。
- **内建算子的实参是否自动装入**（`entering-operator-args`）：`xs->append<5>`（`xs: (int?)[]`）。
  现在的实现：不装入，要写 `5 as int?`；因为内建算子的形参类型由 C++ 的类型规则从实参算出，调用之前没有目标类型。
  候选：让类型规则能报出"我接受的类型"，使内建算子与用户函数一致。
- **在源码中声明流水线**：是否允许入口文件显式写出流水线（如 `pipeline std::macro, tiles::compile, std::nvm`），与命令行一样明确、可见，并随代码提交。
