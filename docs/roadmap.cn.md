# 工作路线与待办

本文件记录已经裁定、尚未完成的工作，以及等待语言作者回答的问题。裁定本身写在 [设计原则](design-principles.cn.md)（规范性文件），各项设计写在 `docs/design/` 下；尚未决定的语义问题列在设计原则第 6 节。这里只记"要做什么、做到哪、按什么顺序"。完成的条目直接删去，历史见提交记录。

更新：2026-10-19。

## 1. 已排定的顺序

1. **装饰器的通用机制**（进行中）：节点属性由库注册并随节点保留；装饰器可以修饰代码块，被修饰的块与不加修饰时行为完全相同；装饰器可以改写函数的图，而不只是包一层。
2. **`enum`**：`type Shape = enum { Circle(float), Rect { w: float, h: float }, Empty }`，`Shape::Rect { ... }` 构造，`match` 列全成员时不需要 `case _`。只有一种封闭的 `enum`。退役 `T ? U` 与 `A | B`。
3. **数值许可改为库装饰器**：`@numeric<Reassociate, Contract>`，许可是标准库 `numeric` 中的封闭 `enum`；编译器中不再有专为 `numeric` 写的代码；取消 `@name(...)` 写法，不做兼容过渡。其他模块需要自己的放宽时，定义自己的 `enum` 与装饰器。
4. **按审查结果修复**（第 4 节），需要裁定的先裁定（第 5 节）。

## 4. 审查发现（2026-10-19）

审查不分作者，覆盖 2026-10-08 以来的提交，只问"是否符合长期设计"，不问"能否运行"。完整报告（每条带位置、现状引文、理由、优雅的形式、严重度）：[前端与标准库](reviews/2026-10-19/frontend.cn.md)、[运行时与优化器](reviews/2026-10-19/runtime.cn.md)、[模块](reviews/2026-10-19/modules.cn.md)。共 42 条，归为四类：

**甲、核心按名字认具体的模块或算子（与 `@numeric` 同类）**
- 参数树 `tree_map` 等在核心建图器里按 URI 展开，`tree` 模块是空壳（三份报告都指出）。
- 遍参数只为 `std::opt` 的 `safe_fp` 写了一段专门解析；其余设置散在环境变量里。
- 核心的遍别名表写死了 `std::tiles`。
- `std::opt::algebra` 写死 12 个算子，不读算子语义。
- `append` 的就地改写按名字写死（`sort` 走通用机制）；`error` 的调用位置、`foreach` 的丢弃检查按名字判断。
- `:mark/` 高阶算子是封闭名单，每个后端各写一遍。

**乙、同一事实有多个来源**
- 效应与写入：资源声明、签名里的 `var`、按 URI 前缀猜测，三者并存，优化遍不读资源声明。
- "什么是树、什么是叶子"写了五到七份，已经不一致。
- 算子的签名、纯度、效应写在 C++ 注册、算子表、`stdlib/signatures` 三处。
- Tiles 直接读张量模块的内部注册表；Tiles 内部有四五张按名字的封闭算子清单，彼此不一致。
- 循环的轮次驱动写了三遍半；FastVM 是否降级循环取决于环境变量和调试器在不在。
- 原生算子拿到类型实参有四种做法。

**丙、缺少通用机制**
- 通用节点属性（许可列只是特例；内联来源也应记在这里，调试器才能按 2.14 显示内联函数的帧）。
- 通用的遍参数。
- 模块注册的编译期展开。
- 梯度与融合产生的算子没有语义声明与定义图；`expandDefinition` 没有调用者，Tiles 只好照 CPU 内核复刻。

**丁、语义缺口**
- `string` 与 `Bytes` 的分界未定。
- `std::tiles` 插入的节点被声明为外部效应，与"纯性能遍"矛盾。
- 2.15、2.16 的默认放宽没有落到语义层，各模块各写一份"许可对应哪种实现"。
- 设备故障按算子名判断，报告没有故障种类与位置。

不需要裁定的条目由核心或 Tiles 按报告中的"优雅的形式"修复；归属见各报告。需要裁定的列入第 5 节。

## 5. 等待语言作者回答

括号内是建议。

1. **按类型在编译期展开的操作**（`tree_map` 等）由谁提供：模块注册的通用展开机制；等类型函数能遍历结构体后用 Camel 写泛型函数；还是接受为编译器内建。原生算子的内核能否在运行时读到本次调用的静态类型（如 `load_tree` 按类型递归解码）也取决于此。（模块注册的展开机制；内核不读类型）
2. **`string` 是否保证是合法的 UTF-8**：`'中'[0]` 得到只含一个字节的字符串、本身是故障，还是下标按码点。`Bytes` 是内建类型名还是从模块导入。
3. **参数树路径的规范写法**：根写作 `""` 还是 `$`，元组下标写作 `blocks.0` 还是 `blocks[0]`，检查点文件名是否与 `tree_paths` 逐字一致。`save_tree`/`load_tree` 归 `tree`、`fs` 还是 `nn`。
4. **显式类型实参的顺序**：`func pair(b: typeas B, with a: typeas A)` 写 `pair::<int, string>` 时 `int` 绑到谁；是否需要 `pair::<A = int>` 这种不依赖位置的写法。
5. **融合换算子**：`tensor::fuse` 把 `matmul` 换成 `matmul_blas`、`matmul_add` 时，图上保留原算子、实现选择记为节点属性，还是允许出现新算子但必须带定义图。（保留原算子）
6. **`std::tiles` 的上传、区域执行、下载是否算纯计算**，即两次相同的区域调用能否被合并。（纯）
7. **2.16 的范围**：CPU 上的 f32 CBLAS 是否默认可用（现须 `reassociate` 与 `change_precision`）；乘加分开舍入算"累加顺序"还是需要许可；BF16 矩阵乘是否还须 `finite_math`。（默认可用；算累加顺序；不须）
8. **`@gpu` 的含义**：调用时的运行时偏好，还是编译期给节点标上设备偏好、由 `std::tiles` 处理；命令行没写 `std::tiles` 时 `@gpu` 是否仍走 GPU。（编译期标注）
9. **`std::` 前缀**是否只留给核心自带的遍；模块的遍由谁登记别名。（只留给核心，模块用自己的名字）
10. **遍参数**：`std::opt(safe_fp=true)` 是否是流水线的通用语法，模块遍、调度器都可带参数；参数值能否是 Camel 常量表达式。（是；能）
11. **节点属性是否属于对外的图数据模型**，用 Camel 写的遍能否读写自定义属性。（是；能）
12. **2.15 的默认放宽是否适用于张量逐元素运算**，如 `a*2 + a*3 → a*5`。（适用）
13. **`map` 的并行从哪来**：从"元素互不依赖"的声明推出，还是来自 `map` 这个名字；用户写的、声明了同样性质的高阶函数能否同样并行。（从声明推出）
14. **签名里的 `var` 与资源声明不一致时以谁为准**。（资源声明；`var` 由它检查）
