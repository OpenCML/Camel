## 2.3 `sync func` 修饰函数

（已由 2.24 撤回：前缀 `sync func` 退役，被推出的 `uses` 取代；函数体后缀的 `sync` 保留）

前缀的 `sync func f(...)` 修饰的是函数：表示这个函数有副作用，需要被同步，也就是调用方可能需要 `wait` 它。

**它与后缀的 `sync` 含义不同，这是设计如此，不要把两者等同。** 声明 `sync func` 并不意味着函数体是同步块。要让函数体按顺序执行，应写成 `sync func f(): int sync { ... }`。

## 2.6 `wait`

（已由 2.24 撤回：`wait` 退役，其作用被"同一资源自动有序"覆盖。仍然有效的"副作用声明的闭环"与"修改的追踪应当完整"见现行规则 3.5）

`wait` 的作用范围是它后面跟着的**一个表达式**。

含义：`wait` 前后的操作，如果用到了该表达式的值，或者用到了被该表达式修改的值（等效于用到了它产出的副作用），就自然要局部有序。

```camel
A(i)
wait modify(i)
B(i)
```

编译器会自动插入 A → modify → B 的控制依赖。

**副作用的声明是一个闭环。** `modify` 内部如果想修改 `i` 的值，必须使用本身就具有副作用的函数：Camel 中的赋值操作就是有副作用的函数；或者使用其他内置的 C++ 算子，而这些算子的声明也明确标记了副作用，要求相应的输入参数是可变的。所以，`modify` 想要修改参数，前提是它的这个参数一定声明为 `var`（`modify(var i: ...)`），否则它自己没有任何有效的办法去修改。

由此：
- 可变性从最底层的算子声明一路向上传递，每一层都必须显式声明；编译器只需要检查显式声明了副作用的函数，就能追踪到全部的修改。
- 没有把参数声明为 `var` 的函数不可能修改它，编译器因此不会、也不需要为它插入控制依赖。
- 在函数体内对非 `var` 的参数赋值，或把它传给要求可变输入的算子，是编译期错误。
- 检验 `wait` 的行为时，测试程序里的 `modify` 必须声明 `var i` 并确实修改了它。

**`wait` 不是机械的排序，它依靠 `var` 的使用情况来排序。** 被排在修改之前的，是此前直接使用了该变量的值的那些节点。例如 `A(i + 1); wait modify(i)`，直接使用 `i` 的是 `+`，所以 `modify` 排在 `+` 之后，而不保证排在 `A` 之后，这是正确的行为。同理，被 `wait` 的表达式如果不涉及任何 `var`（例如只有输入输出类的副作用），`wait` 没有可依据的东西，也就没有意义；这类调用应当写在同步块里，这正是同步块存在的意义。因此不写 `wait` 也不定为错误。

修改的追踪应当是完整的：函数通过捕获（包括模块顶层的变量）写入一个 `var`，与通过 `var` 参数写入一样，调用处应当记为对该变量的一次写入。

在同步块中写不写 `wait` 都无所谓。

## 2.7 补充裁定（2026-10-06）

- **张量形状的编译期检查是必要的。** 目前没有实现。实现方式：Camel 允许类型（尤其是第三方 C++ 模块引入的类型）自定义 type resolver，形状检查用 C++ 逻辑在 resolver 里完成即可，不需要改语言核心。
- **越界访问**：编译期能知道长度时（尤其是固定长度的类型），`slice` 与下标的越界应当是编译期错误，而不是悄悄截断或留到运行期。
- **`wait` 之后无人读取**：`wait modify(i)` 之后如果没有任何地方再读 `i`，这次修改不执行，这是按依赖求值的结果，可以接受。
  （已由 2.24 撤回：`wait` 退役）
- **`map` 等高阶算子的顺序**（2026-10-06 经查代码更正，此前一版写错）：同步块不影响 `map` 内部的执行顺序。`map`、`filter` 的各个元素之间没有执行顺序的约定，并行调度器可以并发执行它们，结果按元素位置排列；这正是并行加速的来源（见 `test/cases/para/core/monte_carlo_pi.cml`）。`foreach` 与 `reduce` 按元素顺序执行；它们的无序并行版本是 `para` 模块的 `unordered_foreach` 与 `unordered_reduce`。仓库中没有 `ordered_map` 或 `unordered_map` 算子。元素函数里的副作用在并行的 `map` 下顺序不作保证，由使用者负责。
- **形状未知的张量进入声明了形状的位置**：不隐式放行，用 `as` 关键字显式转换（如 `t as Tensor<const [3]>`），转换处做检查。
- **数值类型不做隐式转换。** 整数不会自动变成浮点（参数、返回值都一样）；需要时显式写 `float(x)`。
- **Camel 崇尚不可变变量。** `var` 和赋值运算符只是为了方便留的口子，应当尽量少用。模型的计算应当用 `let` 写成纯的数据流。
- **微分与变量**：被求导的函数里，梯度需要经过 `var` 的读写时，直接拒绝并给出明确的诊断，不去支持。没有必要为了求导硬写 `var`。
- **模块顶层的 `var` 被函数直接读写**（如 `fib1.cml` 中的顶层 `cnt`）：没有完全实现，不是必须的情况下先不管。
- **macro 求值失败**：按运行时故障处理，与任何遍运行中的故障相同，不作特殊处理（2026-10-19 改定；`std::macro` 是流水线中的一个阶段，不是编译期）。
- **入口与导出**：所有遍共享 `main` 作为入口。导出有两种情形，取决于程序表达的是什么：
  - **程序只表达纯粹的计算意图**（这是 Camel 程序的本来面目）：程序本身不应该关心内部要怎么导出、导出什么。此时用遍的组合就能导出，例如 `camel x.cml std::macro std::opt onnx::export`，被导出的就是 `main` 所表达的计算。
  - **程序同时兼顾了计算意图之外的意图**（例如计时、跑基准测试）：这时用遍的组合去导出就不合适了。不如直接做到底，由程序内部调用算子（如 `onnx.export_model`）对自己的某个子图完成导出。
  给遍传参数（pass args）是迟早要实现的通用机制，不是为导出单独开的功能。
  （"给遍传参数"已由 2.17 落实为通用语法；见现行规则 9.3）
- **`main` 可以带参数**（2026-10-06 定）。`main` 与其他函数一样是一张子图，它的参数就是这张图的输入：导出时是模型的输入（形状取自带形状的张量类型），运行时由外部给值（命令行；缺少时给出带位置的明确错误，不用零或随机数代替），求梯度时是可以对其求导的量。`main` 不带参数时导出的是没有输入的常量模型，允许。返回单个值是一个输出；返回元组或结构体则展开为多个输出。
- **Camel 在语言层面区分两种参数。** 一种是函数要配置的属性（`with` 参数，即上下文参数），另一种是函数要处理的输入，也就是要流过函数的东西（普通参数）。这在某种意义上弥补了 Camel 不支持面向对象的局限：别的语言里靠对象的成员来持有的配置与状态，在 Camel 里是函数的上下文参数。
- **纯的 `main` 的返回值**：通过命令行已有的 `-o` / `--output <file>` 输出，默认是标准输出。不另设专门的选项。
- **并行调度的粒度**：不要细到原子级别。给每一次很小的函数调用都建一个任务没有意义，只会徒增负担。
- （已由 2.12 取代：`any` 要逐步收紧）**静态类型为 `any` 的值打印为 `<any>` 是正常现象**：Camel 没有在运行时判断类型的能力，为了防止出现严重错误，这是最稳妥的做法。
- **`with` 参数适合表达模型的参数与权重**：普通参数是数据输入，`with` 参数是权重。调用除了写成 `f<w>(x)`，也可以写成 `x->f<w>`，便于链式调用，也便于把模型各层的输入输出串联起来。
- **在命令行上写某个模块的遍（如 `onnx::export`）时，由编译器自动加载该模块**；纯程序不必为了被导出而 `import` 它用不到的模块。
- **导出遍不必做太多检查**：能翻译就翻译，翻译不了再报错。不追求学术上的洁癖。
- **导出遍**：可以做必要的适配性化简，但不应成为主力；主要的求值与化简应由 `std::macro` 和优化遍在它之前完成。

## 2.9 补充裁定（2026-10-11）

这一组裁定面向"Camel 作为通用编程语言"的方向。在论文的视角下 Camel 不主动承载 CPU 密集型的工作；在通用语言的视角下，它仍然要有一定的通用性。两种视角并存。

**判据。** 语法元素必须和图有稳定的映射关系，这才体现图原生。下面每一条都按这个判据衡量；一个构造在图上长什么样如果取决于它里面写了什么，它就不该进语言。

带"示意"字样的代码只说明意图，具体写法以实现时的再次确认为准。

### 空值、错误与故障

- **两个运算符分开**（按语言参考 6.6）：`a ?? b` 处理空值，`a !! b` 处理错误。`x ?-> f` 在 `x` 出错时把错误原样传下去，否则调用 `f`。它们在图上都是分支。
- **"可能为空"与"可能出错"是两种专用的内建形式**，写作 `T?` 与 `T!`。各带一位标记，只能用 `??`、`!!`、`?->` 和 `match` 的固定模式拆开。不做通用联合类型的运行时分辨；2.7 中"Camel 没有在运行时判断类型的能力"不变。
- **错误值是一个固定的内建结构**：种类名、消息、发生处的源码位置。所有可能出错的函数共用这一种错误。
- **`throw` 保留，含义是返回一个错误值**，与 `return` 同构。`try`/`catch` 不进语言：它在图上没有稳定的映射。写了应得到一条诊断，指向 `!!`、`?->` 与故障隔离。
- **错误与故障是两回事。** 只有声明为可能失败的操作（读文件、解析、网络等）才返回错误值。除零、越界、递归过深是故障，不变成错误值，否则每个除法和下标都要处理错误。
- **故障默认带位置终止，但可以在子图边界上隔离。** 提供一个隔离算子（名称暂定 `attempt`）：被它包住的函数里发生的故障，在边界上变成一个错误值，再用 `!!` 处理。终止之前保证清理：刷新输出，释放外部资源。

  ```camel
  let a = risky(0)                 // 故障：整个程序带位置终止
  let b = attempt(risky, 0) !! -1  // 故障被隔离，b = -1（示意）
  ```

- **必然出故障的常量表达式**（如 `1 / 0`）：折叠遍不折叠它，给一条带位置的警告，留到运行时。这是折叠遍自己的选择，不是对所有遍的约束（见 2.10）。
- **递归深度**：尾递归要做优化，程序应尽量写成尾递归或循环；非尾递归给一个可配置的上限即可。

### 数据与控制

- **循环**：`for`/`while` 语法和图上的循环节点都可以加。循环节点要改到所有的遍、各个执行后端、自动微分和导出器，属于底层改动，先出设计稿，经语言作者过目后再动代码。
  （已由 2.10、2.13 取代：引入 `LOOP` 节点，写法见 2.13；现行规则 3.10）
- **映射与集合做成内建类型。** 不新增字面量，用已有的数组字面量加 `as` 转换（与 `t as Tensor<...>` 同一种写法）。操作一律返回新值；查找不到的结果为空。

  ```camel
  let m = [('a', 1), ('b', 2)] as Map<string, int>   // 示意
  let v = m['a'] ?? 0
  ```

- **字段与元素不可赋值**（此前已定，这里重申）：只能给整个变量赋值，所以 `append` 一类的操作返回新值，不原地修改。
- **字符串**：底层按字节存储，长度与下标按字节；另外提供按码点读写的算子。
  （已由 2.17 取代：`string` 保证是合法的 UTF-8，下标与长度按码点计；现行规则 11.1）

### 类型、泛型与类型函数

现在复杂的类型计算都由 C++ 层的算子直接实现，用户很难写出通用的泛型算子。这一项优先级很高。

- **泛型函数按实参类型实例化。** 泛型函数是一张子图模板；每用一组具体类型调用，就实例化出一张类型全部具体的子图，函数体在这时检查。图上只有具体类型，运行时不需要类型信息。
- **类型变量用 `typeas T` 就地绑定**：在签名里第一次出现的位置写 `typeas T`，把这个位置的类型绑定为 `T`，之后直接用 `T`。

  ```camel
  func first(xs: (typeas T)[]): T { return xs[0] }   // 示意
  ```

- **类型函数用专门的类型表达式来写**，在类型位置上用尖括号调用。类型总是写在 `:` 之后，所以这里的尖括号与 `with` 参数的尖括号没有歧义。带参数的类型声明就是类型函数。

  ```camel
  type Pair<T> = (T, T)                    // 示意
  func swap(p: Pair<typeas T>): Pair<T>
  ```

- **`with` 参数不是泛型参数。** 它是上下文参数（见 2.7），不要拿它来声明类型参数或编译期参数。`macro` 也与类型计算无关，不要把类型函数建立在 `macro` 之上。
- **类型里带数值的计算**（如张量的形状）：用户也应当能写，与 C++ 的 type resolver 并存。2.7 中"形状检查用 C++ 逻辑在 resolver 里完成即可"仍然成立，它说的是可以用 C++，不是只能用 C++。维度未知时结果也未知，需要时用 `as` 检查。这类数值参数怎么声明尚未决定（见第 6 节）。
  （"这类数值参数怎么声明尚未决定"已由 2.13 取代：命名维度 `constas`；现行规则 5.4）

### 标准库、模块与运行时

- **标准库的边界**：必须接触系统或性能敏感的原语用 C++ 算子；建立在原语之上的组合逻辑用 Camel 写。Camel 写的库是子图，遍看得见；C++ 算子在图上是一个不透明的节点。
- **算子的纯度必须声明。** 没有声明的算子按有副作用对待（最多少优化，不会算错）；仓库内的标准库模块必须逐个算子声明，第三方模块漏了给提示。
- **模块接口**：从内部头文件里整理出一层公开的 C++ 接口，按版本承诺兼容；其余内部头不作承诺。
- **垃圾回收**：Camel 原生的小对象可以走分代管理（可以移动）；涉及外部接口时，用 Camel 原生对象来管理外部指针，外部内存不进可移动的堆。模块不得跨调用保存指向 Camel 对象的裸指针。落实顺序：先审计模块并立下句柄规则，再在解释执行的后端上启用分代并做压力验证，即时编译等栈映射做好之后再打开。
- **单张图的容量上限（65,535）不放宽。** 它涉及底层数据结构与执行器的效率。函数是子图，一张图装不下说明某个遍把子图压平得太大了，应当让遍在容量内工作，而不是加宽寻址。
  （已由图存储第二版取代：语言作者于 2026-10-19 确认 32 位编号、不再有单图容量上限；现行规则 2.4）

### 工具与对外表述

- **调试器**提供源码行与图节点两种视图，单步也有按行与按节点两种。
- **对外的定位表述**：Camel 是图原生的通用编程语言，AI 是它首要的应用领域；不再自称面向 AI 的领域专用语言。

## 2.10 补充裁定（2026-10-12）

**一条假设。** 不应当出现跨图的节点引用：一张图里的节点不指向另一张图里的节点，图与图之间只有"图引用图"（调用）这一种关系。任何设计都要先过这一条。

**一条取舍标准。** Camel 要和传统的控制流语言有所区别。不用语法糖去模拟传统的控制流，保持语法元素和图节点之间简单的映射关系。（这不排斥含义没有歧义的简洁写法，例如列表推导。）

### 优化与行为

- **"开不开优化，程序的行为一样"不是 Camel 的设计原则**，语言核心也无法强行保证这种一致性。一个遍保留什么、删掉什么，由这个遍自行决定。例如同步块里结果没有被使用、但会出故障的纯计算（`let q = 1 / z`）：不加遍时故障，化简遍可以把它删掉、程序继续。这不算缺陷。

### 语法

- **尖括号紧贴。** `with` 实参与类型实参的尖括号必须紧贴前面的记号：`f<a>` 是带实参的 `f`，`f < a` 是比较。比较运算符 `<` 前面要有空白；`i<n` 是错误，诊断应指出原因。
- **换行结束语句**，思路同 JS 的自动分号，以符合直觉为准。细则：括号未闭合、行尾是二元运算符或逗号等"后面必须还有东西"的记号、下一行以只能是二元的运算符开头（`->`、`.`、`??` 等）时续行；下一行以 `-`、`+`、`(`、`[` 等可以开始一个表达式的记号开头时是新语句。分号仍可用。
- **解析器**用手写的词法分析器与解析器，不再依赖 ANTLR，追求效率与确定性。
- **删除 `raise`。** 它不再是语法的一部分，也不是保留字；返回错误值用 `throw`。
- （已由 2.11 取代）**负号紧贴数字字面量、且前面不是一个值时，是这个数的一部分**：`-2->f` 是 `(-2)->f`。`a-1` 仍是减法。
- **`^` 比乘除高一级，从右到左结合。** `2 * 3 ^ 2` 是 18。
- **带指数或小数点的字面量一律是浮点数。** `1e5` 是 `100000.0`。
- **`===` 暂不支持。**
- **列表推导** `[e for x in xs if c]` 的含义是 `filter` 加 `map`，即 `xs->filter<c>->map<e>`；元素之间没有顺序约定。
- **导入可以改名**：`import { find as str_find } from str`。两个导入的名字冲突是编译期错误，不得静默取其一。
- **文档注释**是语言的约定：声明正上方以 `///` 开头的注释是它的文档。

### 循环

- **引入 `LOOP` 节点。** 现代的计算图标准大多有这类节点，要与它们接轨就需要它。做得优雅一些：先加语法、节点与"把 `LOOP` 降为尾递归子图"的降级，各子系统在入口处降级；之后逐个换成原生处理。循环体是独立的子图，不并入外层图。
- **循环是一个带状态的表达式。** 状态写在循环头上，循环体的值是下一轮的状态，整个循环的值是最终状态。不为"循环外的 `var` 当状态"另设语句形式；只为效应而遍历用 `foreach` 等已有的办法。写法暂定为（已由 2.13 取代）：

  ```camel
  let (i, acc) = loop (i, acc) = (1, 0) while i <= n { (i + 1, acc + i) }
  let total    = loop acc = 0 for x in xs { acc + x * x }
  ```

- **不加 `break` 与 `continue`。** 提前结束写成循环头上的继续条件：`loop found = -1 for x in xs while found < 0 { ... }`。

### 分支与类型

- **没有 `else` 的 `if` 本身没有值**，它的臂可以是任何类型，臂的值被丢弃：`if debug then println('checking')` 合法，`let x = if debug then 1` 是编译期错误。图上不变：一个分支加两条臂，没写的 `else` 是一条空臂，汇合处不取值。臂里不必再为了凑类型写 `return null`。
- **`==` 与 `!=` 对数组、元组、结构体按内容逐个比较。** 两边类型必须相同，元素类型本身要能比较（含函数值的不能比），否则是编译期错误；浮点元素按浮点的规则（含 `nan` 的数组不等于它自己）。张量不在此列。图上是一个普通的算子节点。字符串也有 `contains`，写法与数组的一致：`'hello'->contains<'ell'>`。
- **`a ?? b` 的右边可以是可空的**：右边是 `T?` 时结果是 `T?`，右边是 `T` 时结果是 `T`；从右向左结合，所以 `a ?? b ?? 9` 是"先试 a，再试 b，最后给默认值"。`!!` 同理。图上仍是一个分支。
- **张量的 `t += u` 是算出新张量再重新绑定**，与数值一致，不原地修改。要原地修改用显式的算子。
- **`match` 必须有默认分支。** 没有 `case _` 是编译期错误；`bool` 上两个字面量都列全，以及 `T?`、`T!` 的固定模式除外。编译器不追加用户看不见的分支臂。
- **值进入 `T?` 或 `T!` 的位置时自动装入**，只要目标类型已知（实参、带类型的 `let`、数组元素、分支的两条臂）；`null` 同理。反方向永不自动：`T?`、`T!` 要当 `T` 用，必须用 `??`、`!!`、`?->` 或 `match` 拆开。空数组字面量 `[]` 的元素类型同样取自目标位置。
- **泛型函数可以出现在任何期望一个函数的位置**，包括传给另一个泛型函数。编译器把它的实例化延迟到类型变量能从上下文确定时；确定不了是编译期错误，并指出哪个变量定不下来。延迟只发生在编译期，图上只有具体的实例。
- **`f<w>` 是部分应用**：`let g = f<w>` 得到一个已经配好上下文参数的函数。
- **诊断与图上用源码里的类型名**（`first<int>`，不是 `first<i64>`）。
- **`throw` 只接错误值**：`throw error('Kind', 'message')`，位置由编译器填。`int?!` 允许，`int??`、`int!!` 不允许。故障隔离算子的名字定为 `attempt`。

### 数值

- `int('12abc')` 是故障：整个字符串必须是一个数。要安全地解析用 `parse_int`，它返回 `int!`。
- 值放不进目标类型的转换是故障：`int(1e30)`、`int(nan)`、`i32(5000000000)`。
- 整数加减乘的溢出、最小整数除以 -1 保持回绕。
- 浮点数转成文字只有一种规则：最短、且读回来得到同一个数。`string`、`println`、`format` 一致。
- `&=`、`|=` 是布尔上的与、或；位运算用函数（`bit_and` 等）。

### 效应、错误与并行

- **效应函数也返回值。** `println(x)` 返回 `x`，这样效应可以串进数据流：用到它的返回值，它就一定被执行并排在使用之前。
- **只有显式声明了返回类型的 `main`，它的返回值才算程序的结果。**
- **没有被处理的错误值到达 `main` 的出口**：打印到标准错误，退出码非零。
- **运行期的 `slice` 越界是故障**，与下标越界一致。`take`、`drop` 按定义截断，不受影响。
- **并行的 `map` 中一个元素出了故障**：已经开始的元素跑完，还没开始的不再开始。多个元素同时出故障时报下标最小的那个。

### 模块与标准库

- **模块顶层的代码不会默认执行**：Camel 不是命令式的脚本语言。顶层的语句与别处一样按依赖求值。
- **模块可以导出值。** 模块本身是一张 `__root__` 图；被导入之后各模块的 root 合并到一个公共的 root 之下，模块顶层的一个 `let` 就是 root 上的一个节点，被依赖才求值。这样没有跨图的节点引用。合并的具体做法先出设计说明。
- **标准库的调用风格**：被处理的值是普通参数，其余是 `with` 参数（`'a,b'->split<','>`、`xs->take<3>`）；两个参数地位对等时都是普通参数（`merge(m1, m2)`）。映射与集合的操作照此只保留一种写法。
- 映射的遍历与打印按键排序；能作键的类型是整数、布尔、字符串，以及它们组成的元组；`'abc'[1]` 是只含那一个字节的字符串。

### 默认值

- 非尾递归的默认上限在各调度器上统一为 1000，并行调度器同样计数。
- 发布包的指令集基线是 `x86-64-v2`。
- 图、类型、元数据三块空间的总上限各 256 MB；停不下来的展开另由导出器自己的轮数预算刹住。

## 2.11 补充裁定（2026-10-13）

### 运算符

- **`&&`、`||` 是不可重载的保留运算符，转译为分支。** `a && b` 即 `if a then b else false`，`a || b` 即 `if a then true else b`：右边是一条臂，只在需要时求值。两边都是 `bool`。
- **`&`、`|` 是两边都求值的普通逻辑运算，可以重载。** 只是做一点简单的逻辑运算、不需要分支时用它们；张量的逐元素逻辑运算、用户自己的类型重载的也是这一组。`a &= b` 即 `a = a & b`。
- **一元负号永远是运算符，不并入字面量**；它的优先级低于 `^`、高于 `->`。于是 `-2 ^ 2` 与 `-x ^ 2` 都是 -4，`-2->f` 与 `-x->f` 都是先取负再传入：字面量与变量的读法一致。`a-1` 仍是减法。（取代 2.10 中"负号紧贴数字字面量时是这个数的一部分"。）
- **有两种身份的符号出现在行首时，取开始新东西的那种身份**：行首的 `@` 是标注，行首的 `+`、`-` 是一元的。要把矩阵乘或加减法写成两行，把运算符留在上一行末尾。

### 可空与错误

- **`x == null`、`x != null` 可以写**，结果是 `bool`。函数值不能比较。
- **在 `if x != null then ... else ...` 的非空那条臂里，`x` 是 `T`。** 这等价于对可空值的 `match`：进入那条臂的端口带的是拆开后的值。只对 `let` 绑定与参数生效（`var` 可能被别处改写）；只认直接的写法（`x != null`、`x == null`，以及用 `&&` 连起来的几个）；只在臂内生效。
- **同步块里一个 `T!` 的值没有被使用，是编译期警告。** 故意丢弃写 `let _ = ...`。没有声明返回类型的 `main` 以一个错误值结尾，是它的特例。
- **分支的一条臂没有值（`void`）、另一条是 `T` 时，分支是 `T?`**，没有值的那条臂给出 `null`。

### 类型

- **`any` 只是一种简化的写法**，是类型系统成熟之前临时开的口子。不应当存在到了运行时还不确定的类型：每个值在编译之后都有确定的类型。
  （已由 2.12 进一步收紧：`any` 要逐步收紧；现行规则 5.10）

### 算子与库

- **起点在终点之后的 `slice`（`xs->slice<2, 1>`）得空数组**，不是故障；这是常规的算子行为。越界仍是故障。

### 模块

- **合并方式**：全程序一张 `__root__`，各模块顶层的节点都在上面，函数经捕获端口取值；捕获按"模块 + 名字"绑定，不按名字在调用处查找。
- **顶层的值在 `main` 开始之前求值，依据是静态的依赖**：`main` 沿调用链静态可达的函数用到的顶层值都会求值，运行时是否走到用它的那条臂不影响。
- **模块可以互相导入。** 为此加载分两个阶段：先收集所有模块的声明，再建函数体。顶层值之间的循环依赖是编译期错误。
- **不能导出 `var`**；导出读写它的函数。被导入模块里的 `main` 是普通函数。
- **编译好的模块可以缓存**（`.cmo`，cached module object），使一个模块不必重新编译。每个模块的缓存是以该模块为根的一张图；它是为了方便与加速，不必等同于实际编译的最终结果。C++ 模块沿用同一个扩展名，两者靠文件头区分。
  （已由 2026-10-22 的命名裁定修订：缓存文件是 `.cmc`，放在源文件旁的 `__cmc__/` 里，不再与 C++ 模块的 `.cmo` 共用扩展名；缓存尚未实现；现行设计原则 10.3）

### 实现方向

- **图的数据模型是最重要的一项设计**：它要定义清楚、稳定、可以对外。模块缓存、用 Camel 写遍、把计算代码编译成 GPU 内核、`std::cpp` 都建在它上面。
- **编译核心的内部表示可以彻底重构**，以求全流水线的速度与内存效率。
- **内存管理的方式不进入语言的语义**：对象没有可观察的身份，回收的时机不可观察，C++ 算子通过句柄接触对象。各后端可以选适合自己的方式。分代回收对 C++ 算子作者的约束可以接受。
- **并行调度器把没有可并行之处的子图交给字节码解释器执行。**
- **程序的输出与 `fs` 写出的文本在各平台上是相同的字节**，Windows 上不写 `\r\n`。
- **调试器**：分支的臂默认并入所在函数的帧，可以切换为显示真实的子图结构；行步进按执行的顺序，一行因为没有东西用到它的结果而没有执行时，给出说明。

## 2.12 补充裁定（2026-10-14）

### 模块与命名空间

- **模块顶层的 `let`、`var` 与书写顺序无关，只看依赖。** `let area = pi * r * r` 可以写在 `let pi` 之前；顶层值之间成环是编译期错误。函数体里的局部 `let` 仍是先声明后使用。
- **命名空间块里可以不带前缀使用同一块及外层块里的名字。**
- **`using namespace`**：可以对本模块的命名空间使用；只在它所在的块里生效（写在函数体里就只对那个函数生效）；两条 `using` 带来同名同签名、无法区分的名字时，在使用处报错。
- **名字的优先级只有一条规则**：局部 > 本模块（所在命名空间、外层命名空间、模块顶层）> 按名字导入的 > `using namespace` 带来的 > 内建。取第一个有这个名字的层；同一层里同名的函数合成重载集，签名相同是错误；跨层不合并。运算符重载例外，各层合并。
- **`import a from m` 是从 `m` 引入名字 `a`**，等价于 `import { a } from m`，与语言文档一致；给模块起别名写 `import m as x`。
- **不实现 `use`**，退掉这个保留字；允许 `import { … } from m::N`。
- **命名空间块里可以有值**：`namespace Config { export let limit = 10 }`，用 `Config::limit`；与模块顶层的 `let` 只差名字里的路径。
- **模块可以用自己的名字限定自己的东西**：`module shapes` 里写 `shapes::area` 与写 `area` 相同。
- **诊断、调试器与图名一律显示完整的名字** `模块::路径::名字`，不引起歧义时省略模块名。
- **模块缓存放在源文件旁的 `__cmo__/` 目录里**；先默认关闭；命中缓存的模块不重放编译期警告。导入方的缓存在下列任一项变化时失效：导出函数的签名（含推断出的返回类型）、它间接用到的模块级值、它的效应、泛型函数的函数体。
  （已由 2026-10-22 的命名裁定修订：目录是 `__cmc__/`，缓存文件是 `.cmc`；现行设计原则 10.3）

### 类型与转换

- **把值转成它自己的类型是合法的，什么也不做**：`xs as int[]`（`xs: int[]`）与经别名的 `p as A` 一样通过。
- **标准库签名的文本用类型变量，不用 `any`**（如 `print<T>(x: T)`）。参数个数可变、各参数类型不同的 Camel 函数暂不做。
- **`any` 要逐步收紧。** 只有在特定需求下、类型系统的表达能力暂时不够时，才临时开一个口子；凡是有明确推荐写法的情形（泛型、重载、具体类型），`any` 明确拒绝，诊断给出推荐写法。`json.decode` 改为自描述的 `Json` 类型，并提供 `decode_as<T>`。现在就改成编译期错误的：`any` 作 `if` 的条件、`any` 作 `match` 的对象、不经检查的 `as any as T`。
- **带 `var` 上下文参数的函数可以部分应用**：`add<t>` 是一个写被捕获变量的函数值，它的类型带 `sync`，每次调用记为对 `t` 的一次写入。

### 语法与收窄

- **`!`、`~` 与一元负号一样**，优先级低于 `^`、高于 `->`：`!x->f` 先取反再传入。
- **收窄的范围**：`x != null` 与 `null != x` 都收窄；`if x != null && ready then ...` 的 then 臂里 `x` 收窄（`&&` 的各项中只要有对 `x` 的直接判空）；`||` 的 else 臂暂不收窄。在收窄的臂里再写 `let x = ...` 是重复声明。
- **可空的函数值可以与 `null` 比较**；"函数值不能比较"指两个函数值之间。
- **`let r = ...` 绑定了一个 `T!` 而 `r` 从未被使用，同样警告**（与 2.11 的语句形式相同）。
- **悬停与文档只取 `///` 注释**；普通的 `//` 不是文档。

### 运算符

- **用户可以在 Camel 源码里重载运算符**，写作 `func operator &(a: Mask, b: Mask): Mask`（写法暂定）。可重载的是今天落到 `__x__` 函数上的那些运算符；`&&`、`||` 与 `??`、`!!`、`->` 等构造不可重载。`__x__` 形式的名字仍是保留的，用户不直接写。

### 集合的修改

- **`append` 返回新数组，不修改原数组**：`let ys = xs->append<5>` 之后 `xs` 不变；要"追加到变量上"写 `acc = acc->append<5>`，与 `x = x + 1` 一样。就地改写只是实现层面的优化（旧值不再被使用时可以在原处追加），不进入语义，也不另设显式的就地算子。其他标准库算子同此。迁移：纯运算的结果没有被使用（如写成语句的 `xs->append<5>`）是编译期错误，并提示改写为重新绑定。

### 图

- **对外的节点种类**：`DATA PORT OPER FUNC CALL FILL ACCS CAST COPY BRCH JOIN LOOP GATE SYNC`。`BIND`、`DREF` 移出；`map` 一类高阶算子与 `attempt` 仍是算子节点，由算子表声明"会调用子图"；算子除纯度外还声明"是否可能故障"，没有声明的按可能故障处理。
- **分支臂的两种形态都是合法的图**：前端产生"每条臂一张子图"；内联之后臂的节点并入外层图、成为分支与汇合之间的一段，也是合法的。
- **算子是否可能故障不强制逐个声明**：模块作者按需声明，没有声明的按可能故障处理。
- **副作用追踪在各个遍之下的保持方式**：效应是图上的摘要（图的出口是否依赖效应、写了哪些捕获的变量），每次提交由节点重新算出并校验；遍不可能提交一张摘要与内容不符的图。遍删掉或挪动效应是否正确，仍由遍自己负责（第 4 节）。
- **`LOOP`**：条件子图与循环体子图共用一份捕获表；`for … while` 是同一种节点的第三种形式；有多个状态时循环体返回一个元组，`LOOP` 的值也是这个元组。
- **用 Camel 写遍的方向**：图与节点是不可变的值，遍是 `(Program) => Program!`；改写是"一组改动 → `apply` → 新图或错误值"，不提供就地修改；模式规则写成一对参数相同的函数，左边的图是模式，右边的是替换。细节另定。

### 后端与运行时

- **`std::cpp` 的目标是生成可以脱离运行时独立部署的程序。** 无法同义转换的情形可以引用 Camel 的运行时模块，但要尽量做干净。生成的程序要给出带源码位置的故障、遵守递归上限，尾调用不使栈增长。
- **有身份的东西要列明**：`var` 单元、经 `var` 参数就地修改的对象、外部库包装的对象（Python 对象等）；其余的值没有可观察的身份，后端可以随意复制或共享。对象头里不加类型字。`std::cpp` 生成的模块接口用标准 C++ 类型，不暴露运行时的内部类型。
- **后端可以少回收甚至不回收垃圾**：回收的时机与是否回收都不可观察（2.11）。
- **分代回收在可用之后默认开启。**
- **并行调度器把串行子图交给字节码解释器之后，递归上限按同一规则计数**：调高 `--max-recursion-depth` 时，深的非尾递归在 `std::prl` 上与在 `std::fvm` 上一样跑完。

## 2.13 补充裁定（2026-10-15）

- **收窄之后**，对已确定非空的名字仍可写 `??`、`match` 等针对 `T?` 的操作，给警告"已确定非空"；对非可空的值判空同样允许并警告（结果恒定）。没有 `else` 的 `if`，臂里一个 `T!` 没有被使用，警告。
- **JSON**：坏的 JSON 文本，`decode` 返回 `Json!` 的错误值，不是故障。`Json` 的访问器接受 `Json?` 以便链式取值，`as_float` 接受整数，`get<下标>` 越界给 `null`。`decode_as` 暂以一个"形状值"给出目标类型，调用时显式写类型参数的写法定下之后再改。
- **`match` 的分支**：每个分支的值必须能被被匹配值的类型接受。
- **模块**：模块导入自己是允许的，没有效果；类型跨模块成环给出成环的诊断并列出环；重开同一个命名空间块，前一块里的 `using` 不带到后一块；名字有歧义时列出各个限定候选；语言服务器按完整名字展示命名空间成员；C++ 模块可以导出值（`math::pi`）。
- **集合**：返回新值与就地修改不再用两个名字区分（`sort` 与 `sorted`）：只保留 `sort`，它返回新数组；`xs = xs->sort` 在旧值不再被使用时就地排序，与 `acc = acc->append<v>` 是同一种实现层面的优化。张量保留显式的就地算子（2.10），数组不设。
- **运算符重载**：用户的重载比内建的更具体时优先；重载 `==` 即得到 `!=`；命名空间块里声明的运算符属于模块。
- **循环头的写法定为 `do` 式**（取代 2.10 的暂定写法）：状态只声明一次，多个状态用逗号分开，循环的值是它们组成的元组；`do` 后面是一个表达式，`{` 的读法与 `then` 之后相同（`{ x: 1 }` 是结构体，`{ 5 }` 是块）。

  ```camel
  let total    = loop acc = 0 for x in xs do acc + x * x
  let (i, acc) = loop i = 1, acc = 0 while i <= n do (i + 1, acc + i)
  let p        = loop p = { x: 0 } for d in ds do { x: p.x + d }
  let found    = loop hit = -1 for x in xs while hit < 0 do if x > 9 then x else hit
  ```

- **调用时显式写类型参数，两层都做。** 第一层：只出现在返回类型里的类型参数由期望的类型推出（`let` 的标注、形参的类型、返回的位置），如 `let cfg: Config! = json::decode_as(text)`；这是 2.10"泛型延迟到上下文能确定时实例化"的延伸。第二层：推不出来时写 `f::<T>(x)`（与 Rust 的写法相同），如 `json::decode_as::<Config>(text)`、`empty::<int>()`。`f<w>` 仍只表示 `with` 参数与部分应用；两者都写时是 `f::<T><w>(x)`。有了这两层之后，`decode_as` 以"形状值"给出目标类型的写法退掉。
- **和类型按 Rust 的 `enum` 做**：变体有名字，可以带一个元组或一个结构体的数据，可以泛型、可以递归。

  ```camel
  type Shape = enum {
      Circle(float),
      Rect { w: float, h: float },
      Empty,
  }
  let s = Shape::Rect { w: 2.0, h: 3.0 }
  let area = match s {
      case Shape::Circle(r)     => 3.14159 * r * r
      case Shape::Rect { w, h } => w * h
      case Shape::Empty         => 0.0
  }
  type Tree<T> = enum { Leaf, Node(Tree<T>, T, Tree<T>) }
  ```

  `match` 一个 `enum` 时列全了所有变体就不必写 `case _`（与 `bool`、`T?`、`T!` 同理）。不按值的类型区分变体（那是运行时的类型判断，2.9 已排除）。现在写得出却没有值能进入的 `A | B` 退掉，`|` 只留给逻辑或。图上不增加节点种类：构造是装入一个标签，`match` 是取标签、分支、在臂里取出数据，与 `T?`、`T!` 相同；`T?`、`T!` 可以看作内建的两个 `enum`。
- **张量的维度可以有名字**：在形参类型里第一次出现时写 `constas n` 绑定（与 `typeas T` 绑定类型变量同一模式），之后直接写 `n`；只出现在返回类型里的名字是错误。

  ```camel
  func dense(x: Tensor<f32, const [constas n, 3]>, w: Tensor<f32, const [3, constas k]>): Tensor<f32, const [n, k]>
  ```

  维度上可以做加法与乘以常数（线性式，相等可判定），其余结果记为未知。调用处的实参维度未知（`?`）时，编译期放过，在调用处做运行时检查（与 `as` 相同）。命名维度只用于检查，不产生新的实例：一个函数仍只有一张图。

- **退掉预留的 `T ? U`**：可能出错的值只写 `T!`，错误值只有一种类型（以 Kind 区分）。将来需要带类型的错误时，在有了 `enum` 之后以 `T ! E` 的形式加入。`T ?` 后面接类型时的那条特殊读法随之去掉：`?` 只是可空标记。
- **浮点的数值契约**（2.11 的"相同的字节"原本针对输出文本，这里补全计算本身）：
  - **基准是规范算法，不是某台机器的实现**：加、减、乘、除、开方每一步按 IEEE 正确舍入，严格按程序书写的顺序，不收缩为乘加融合。在这个范围内，各后端、各设备的结果逐位相同。
  - **超越函数**（`exp`、`log`、`sin` 等）不要求跨设备逐位相同，只承诺一个写明的误差上界（以 ulp 计）。
  - **各项许可互不蕴含**：改变归约的顺序或结合方式、收缩为乘加融合、使用近似数学函数、降低输入或累加的精度、对 NaN、无穷、负零、次正规数作额外假设。除下述标准算式优化遍的默认局部代数策略（2.15）与后端默认的累加顺序（2.16）外，放宽必须显式授予。模块只能声明算子本身做什么，不能替调用者扩大许可。
    （其中"除……外放宽必须显式授予"的默认值已由 2.22 取代；现行规则 7.2、7.3）
  - **`unordered_reduce`** 只授予"这次归约的合并顺序可以改变"，不含其他许可。
  - **许可写在哪段代码上就只对那段代码生效**：被调用的函数不自动继承；内联、展开定义图时许可随节点保留，并随缓存保存。授予的写法倾向于函数或代码块上的标注（如 `@numeric(reassociate, contract)`），细节见 `docs/design/op-semantics`。
    （授予的写法 `@numeric(reassociate, contract)` 已由 2.20 取代为标签 `#[reassociate, contract]`；现行规则 7.5、6.6）

- **数值契约的细则**（详见 `docs/design/op-semantics`）：
  - **矩阵乘的规范算法是按 k 从小到大连续做乘加融合**（FMA 本身是 IEEE 规定的一次正确舍入运算，因此同样逐位可复现）；这是矩阵乘自身的规范算法，不是对"不收缩为乘加融合"的放宽。
  - **`max`、`min` 采用 IEEE 754-2019 的 `maximum`、`minimum`**：NaN 传播，-0 小于 +0。它们满足结合律与交换律，求最大、最小值的归约不需要许可即可重排。**`relu` 定义为 `maximum(x, +0)`**。
  - **许可的名字**：`reassociate`、`contract`、`approx_math`、`change_precision`、`finite_math`（后者是 `no_nans`、`no_infs`、`no_signed_zeros`、`flush_subnormals` 的合写）。提高累加精度也属于 `change_precision`。
  - **作用范围**：写在函数或代码块上；词法上嵌在其中的分支臂、循环体、lambda 算作同一段代码。不设模块级的默认许可；后端的入口（如 `tiles.run`）不接受许可。算式优化遍可通过遍自身的参数选择数值策略，见 2.15；这不构成向后续遍或被调函数传播的节点许可。
    （`@numeric` 的写法已由 2.20 取代为标签；"见 2.15"处的默认值已由 2.22 取代；现行规则 7.5）
  - **超越函数**逐个声明误差上界，标准库的目标是 `exp`、`log` 不超过 2 ulp；NaN、无穷、零等特殊值必须精确。
  - **定义图是规范**：融合或手写的实现必须与算子的定义图一致。维度可能为 1 的广播在形状确定之前不给出索引映射。

- **`std::cpp`**：生成程序的故障报告与解释器逐字相同；递归计数精确（与各后端一致）；`println<fmt>` 多出的空行、`print<fmt>` 多出的换行是解释器的缺陷，修掉解释器；去掉 `std::cpp::bench`；生成程序里的 `map`/`filter` 先串行；`main` 的参数用 `--arg name=value` 给出，与命令行一致。

## 2.14 补充裁定（2026-10-16）

- **调试器**：从分支的臂回到汇合处时，不再在同一行停第二次，该行的断点只在第一次进入时命中；~~被内联的函数仍显示为它自己的帧~~（2026-10-19 撤回：Camel 的优化会合并、重排内联进来的计算，虚构的帧常常不真实；内联进来的代码显示在调用者的帧里，并标注来自哪个函数、哪次调用，见图存储第二版 3.3 的区域）。
- **`Json` 的访问器也接受 `Json!`**，使解析失败也能链式取值。
- **NaN 的取值**：`max`、`min`、`relu` 得出的 NaN 一律是标准的安静 NaN（打印为 `nan`）。普通算术产生的 NaN 不受此约束。
- **`argmax`、`argmin`** 按 IEEE 754-2019 的 `maximum`、`minimum` 比较：有 NaN 时返回第一个 NaN 的位置；并列时返回第一个最值的位置，+0 大于 -0。
- **精确类算子可以声明受 `finite_math` 的四项假设影响**；舍入类许可对它们仍不适用。`@numeric` 暂不支持写在 `wait` 块前。最大池化与 `log_softmax` 中的求最大值按新的 `max` 规则。
  （其中"`@numeric` 暂不支持写在 `wait` 块前"随 `wait` 退役（2.24）与 `@numeric` 改为标签（2.20）而作废）
- **归约**：对空区间的归约是故障，即使结果本身没有元素。int64 张量的求和以 int64 精确累加，溢出时回绕，与整数算术一致。
- **循环**：循环头必须有 `for` 或 `while`；`for … while` 每轮先判断条件、再取下一个元素；`std::macro` 中循环至多 100 万轮（与递归上限一样可调）；`for` 目前只遍历数组，字符串、映射、张量以后再加；状态的类型取初值的类型，张量形状不自动放宽，需要时写类型标注。


## 2.15 补充裁定（2026-10-18）

- **算式优化默认适当放宽，以追求优化上限。** `std::opt::algebra` 是独立的通用算式优化遍，`std::opt` 默认集成。两者默认 `safe_fp=false`：允许局部重结合和系数合并，即使没有 `@numeric(reassociate)`，因此浮点结果不承诺与优化前逐位相同。这项策略不自动允许改变精度、近似数学函数或 FMA，也不自动假设没有 NaN、无穷、负零或次正规数；规则仍须保留这些特殊值的行为，或检查相关显式许可。
  （默认值已由 2.22 取代：`reassociate`、`contract` 默认允许；其余各项与 `safe_fp` 参数仍然有效，见现行规则 7.3、7.4）
- **安全浮点模式是可选的遍参数。** `std::opt::algebra safe_fp=true` 与 `std::opt safe_fp=true` 将算式阶段限制为严格等价的浮点变换，包括可证明等价的系数翻倍；即使节点有更宽的许可，这个阶段也不使用它来改变舍入路径。常量折叠仍按规范算法，整数仍按其位宽回绕。这是算式优化的策略选择，不是运行时算子算法或整个流水线的全局浮点开关；先前遍已经作出的改写不会回滚。

## 2.16 训练基础设施的方向（2026-10-18）

详见 [训练基础设施设计](design/training/README.cn.md)。

- **参数树**：标准库提供 `tree_map`（可同时作用于多棵同构的树，对位的叶子作为多个实参传给回调）、`tree_unzip`、`tree_reduce` 等操作，作用于由结构体与元组嵌套成的值，叶子顺序为深度优先、按字段声明顺序；叶子边界永远由树实参的类型决定（`tree_map` 以第一棵树为准，`tree_unzip` 以给出的参照树为准），不由回调的形参类型决定；树的形状由类型决定，操作在编译期展开为逐叶的普通节点。`Device<T>` 对结构体与元组按字段分配，`Device<{ a: A }>` 与 `{ a: Device<A> }` 是同一个类型。
- **无状态随机数**：在现有带全局状态的随机数之外，提供由键决定的随机数（`key`、`fold`、`split`、`normal`、`uniform`、`randint`）。它们是纯函数，不是外部效应；规范算法为 Philox4x32-10，整数与均匀分布的结果跨设备逐位相同，正态分布按超越函数的 ulp 上界。
- **字节类型**：新增 `Bytes`，`string` 只表示文本；文件接口分文本与二进制两套。
- **后端默认可以改变累加顺序**（与 2.15 同一精神）：GPU 上的并行归约、按库实现的 f32 矩阵乘（如 cuBLAS，不含 TF32）、多卡数据并行中跨卡的梯度求和，默认可以采用与规范算法不同的累加顺序，不需要 `@numeric(reassociate)`。条件是结果可复现：同一设备、同样卡数、同一版本的两次运行逐位相同，因此不得使用结果随调度变化的做法（如浮点原子加）。降低精度（如 f32 矩阵乘改用 bf16 或 TF32 计算）、近似数学函数、FMA 收缩与特殊值假设仍须显式许可。后端提供安全模式参数，关闭这项默认放宽，此时按规范算法逐位计算。
  （默认值已由 2.22 取代：`reassociate`、`contract` 默认允许，可复现的条件保留；现行规则 7.3、7.6）

## 2.17 审查后的裁定（2026-10-19）

依据 [2026-10-19 的设计审查](roadmap.cn.md)。第一条由语言作者裁定；其余由语言作者授权，按审查建议定下，作者可以随时改。

- **按类型展开的操作用泛型写，不做编译器内建。** `tree_map` 这类"形状由类型决定、编译期展开"的操作，最终用 Camel 的泛型函数写在库里；为此泛型要能在编译期按结构体、元组的字段递归（设计另行讨论）。在那之前不再增加此类内建，也不另做过渡机制。原生算子的内核不在运行时读取调用的静态类型；需要按类型变化的，在编译期展开。
- **`string` 保证是合法的 UTF-8**，下标与长度按码点计；字节序列用内建类型 `Bytes`，两者之间显式编码、解码。
- **参数树的路径**写作 `blocks.0.w`，根是空路径；检查点中的名字与 `tree_paths` 的结果逐字一致；`save_tree`、`load_tree` 属于 `tree` 模块。
- **显式类型实参**：按位置时，顺序是类型变量在签名中首次出现的顺序；也可以按名字写 `f::<T = int>`，不依赖位置。
- **优化不改变图上的算子身份。** 融合、换用库实现（BLAS 等）是实现选择，记在节点属性上，图上保留原算子；新算子只在有自己的语义声明与定义图时才可出现。
- **`std::tiles` 的上传、区域执行、下载是纯计算**，设备内存是不可观察的分配；相同的区域调用可以合并。
- **2.16 的范围**：CPU 上按库实现的 f32 矩阵乘与 GPU 一样默认可用，条件同 2.16（可复现，安全模式下用规范算法）；乘、加分开舍入视为累加方式的改变，归 2.16 的默认放宽；BF16 计算只需 `change_precision`。
  （默认值已由 2.22 取代；现行规则 7.3）
- **`@gpu` 是编译期标注**：给函数的节点记上设备偏好，由 Tiles 的遍处理。流水线由用户显式组合（第 4 节），模块不能在导入时自动加入遍（2026-10-19 撤回此前的"默认流水线登记"）；没有读取它的遍时编译器给出警告（2.20）。
- **`std::` 前缀只给核心自带的遍**；模块的遍用模块自己的名字，别名由模块登记。
- **遍参数是流水线的通用语法**：`name(key=value, ...)` 对任何遍、调度器、模块遍都适用，参数值是 Camel 常量表达式；设置不再放在环境变量里。（2026-10-23 改为遍名之后的 `key=value` 词，不带括号；现行规则 9.3）
- **节点属性属于对外的图数据模型**，用 Camel 写的遍也能读写。
- **2.15 的默认放宽适用于张量逐元素运算**，与标量相同。
  （默认值已由 2.22 取代；"适用于张量逐元素运算"仍然有效，现行规则 7.3）
- **高阶函数的并行来自声明的性质**（元素之间互不依赖），不来自名字；用户写的函数声明了同样的性质也可以并行。
- **效应以资源声明为准**；签名里的 `var` 由资源声明检查，不一致是声明错误。

## 2.18 类型层的计算（2026-10-19）

- **只有一门语言。** 根据类型算出类型、按类型的结构生成代码，都用主体语言写：类型是编译期的值，类型函数是在编译期运行的普通函数，用的是与值层相同的构造（见 [泛型按结构展开](design/generic-structure/README.cn.md)）。不另设一套类型层语言（如 TypeScript 的条件类型、映射类型、`infer`）。
- **简写可以有，语义只有一套。** 简写（如装饰器）是给库作者用的机制，可以存在，但只能是同一语义的另一种写法，不得另带规则。新的**原语**只用于主体语言无法表达的事，以标记的形式出现，数量固定：`typeas T`、`constas n`（在签名的位置上绑定）、`typeof x`（一个表达式的静态类型）、`fields T`（一个类型的字段表）。凡是能由原语算出的（如取字段名的 `keyof`），写在库里，是类型函数或普通函数，不是关键字。
- **普通函数与类型函数在写法上对称。** `func` 定义普通函数，用 `f(...)` 调用；`type` 定义类型函数，用 `F<...>` 调用，只出现在类型的位置上。带参数的类型声明就是类型函数（2.9），如 `type Pair<T> = (T, T)`、`type Device<T> = match type T { ... }`。类型函数没有上下文参数（`with`），尖括号里只有类型与编译期的值。区分的依据是结果：结果是类型的，用 `type` 定义；结果是值的（包括在编译期求值的判断，如 `is_numeric::<T>()`），用 `func` 定义。
- **类型函数的函数体是一个类型表达式**，不是语句块：`type P = { w: float }` 中的花括号是结构体类型，不能再兼作语句块。较复杂的计算拆成几个类型函数，或用以关键字开头的 `match type`。
- **类型只出现在类型的位置上。** 类型的位置是语法上标明的：`:` 之后、`type 名字 =` 之后、`as` 之后、`::<...>` 之中、`match type`、`fields` 之后，以及类型函数的尖括号里。类型进入值的代码只有三条路：`::<T>` 显式类型实参、`typeas` 绑定、`typeof` 取得。因此值位置上的 `f<...>` 永远是上下文参数，类型位置上的 `F<...>` 永远是类型函数调用，解析时不必知道名字指什么。
- **类型函数可以作为类型函数的实参**（高阶类型）：在类型位置上不带尖括号写类型函数的名字，即指这个类型函数本身，如 `MapLeaves<Device, Params>`。形参是类型还是类型函数，由函数体中的用法推出。
- **由字面写法算出的字段名加方括号**：推导式中 `[n]: e` 的 `n` 是编译期的值，`n: e` 的 `n` 是字面的字段名；编译期的字段访问写 `t.[n]`。
- **结构类型是有限的**：结构体、元组不能直接或间接包含自身；递归的类型只能经由 `enum`。类型函数的计算因此按类型的结构终止，另有可调的展开上限（2.14）。

## 2.19 类型的身份与泛型中的名字查找（2026-10-19）

- **有名字的结构体与 `enum` 是命名类型**：`type Point = { x: float, y: float }` 创建一个新类型，它的身份是名字加声明它的模块，属于该模块。元组、数组、函数类型，以及 `type 名字 = 另一个已有类型`，是别名，按结构比较（如 `type Pair<T> = (T, T)`）。
- **没有名字的结构体值可以直接用作结构相同的命名类型**：`let p: Point = { x: 1.0, y: 2.0 }`，字段按名字对应。**两个命名类型之间必须显式转换**（`m as Seconds`），即使结构相同；字段按名字一一对应。需要"包一层的数值"（如 `Meters`）时写成单字段结构体，不另加语法。
- **字段顺序**：命名类型的规范顺序是它的声明顺序；没有名字的结构体类型，写出的顺序是类型的一部分（顺序不同即不同类型）。参数树、检查点、`tree_paths` 的叶子顺序都按规范顺序（2.16）。
- **泛型函数体中的名字查找**：名字一律在定义处按词法查找；对依赖类型变量的值做运算（如叶子处的 `==`、对回调实参的重载选择）时，另在该值的类型声明所在的模块中查找重载。不看调用者导入了什么。要换一种运算，把函数作为参数显式传入（如 `tree_eq<my_eq>(a, b)`）。
- **泛型类型一律不变**：`Array<int>` 不能当 `Array<int?>` 用；隐式转换只发生在叶子值上，不穿透泛型类型的参数。

## 2.20 装饰器与标签（2026-10-19）

两种机制，底层相差很大，因此写法明确区分。

- **装饰器 `@`：变换。** `@d<a> func f` 即 `let f = d<a>(f₀)`，`d` 是普通函数，可以改变行为；类型装饰器是类型函数，`@D type T = E` 即 `type T = D<T₀>`；也可以装饰代码块（等价于立即调用的无参函数，行为与不加装饰的块完全相同）。一行一个，自下而上依次作用（顺序有意义，是函数组合）；重复的组合定义成新的装饰器函数。函数装饰器小写，类型装饰器大写（与类型函数一致）。
- **标签 `#`：编译期事实。** 标签附在声明或节点上，只在编译期存在，不会被"调用"，在图上不产生节点。**语言本身不赋予标签任何含义**：含义由声明它的库定义，由读取它的遍实现，后果由库负责（与第 4 节一致）；标准标签（如数值许可、`#macro`）的含义写在本规范中。事实有两种：性质（不带参数，如 `#leaf`）与关系（带编译期值的参数，如 `#vjp<cube_rule>`）。多个标签写成 `#[a, b<v>]`，只有一个时可省方括号。标签名小写。
- **标签用关键字 `tag` 声明**：`export tag leaf on type`、`export tag fixed on field`、`export tag vjp<rule: func> on func`、`export tag reassociate on nodes`。`on` 列出能贴的位置：`func`、`type`、`field`，以及 `nodes`（被标记的函数或代码块里按词法写出的节点，含分支臂、循环体、lambda，不含它调用的函数）；以后可加参数、变体、模块。别名组 `tag finite_math = [no_nans, no_infs, no_signed_zeros, flush_subnormals]` 展开为其中各条事实。贴到未列出的位置是编译错误。
- **区域上的事实累积**：一个节点具有它所在的所有被标记区域的全部事实；带参数的同名事实以内层为准。不需要合并规则。
- **标签属于声明**（名字），与装饰器怎样包装它的实现无关。标签只能在声明处贴，不能事后给别处的声明补贴（调度是否例外另行讨论）。
- **读取标签**：C++ 模块通过登记与查询接口读；编译期代码中标签是编译期的值，`match type T { case #leaf => … }`，`fields T` 同时给出每个字段的标签。标签与其他名字共用命名空间，按同样方式导入，可写限定名 `#[tiles::kernel]`。是否满足一个要求类标签（如 `#kernel`）由库的遍检查。
- **数值许可就是标签**：`#[reassociate, contract]`，不另设 `numeric` 包装与 `enum`；`finite_math` 是别名组。2.13 的规则不变（词法生效、不被被调函数继承、随节点保留、模块不能替调用者扩大许可）。
- **关键字只留给改变语义的修饰**（如 `sync`、`export`）。**`macro` 改为标准标签 `#macro`**，不用导入即可使用；第 3 节的含义不变（`std::macro` 可以提前求值它，把结果物化为图中的常量，用来动态地构造静态图）。删除 `inner`、`outer`、`atomic`、`shared`：原生实现由模块中无函数体的声明表达，外部实现由模块系统承担，"作为整体、不展开"由 `#kernel` 一类标签表达，数据共享由不可变数据取代。
- **`#` 不再表示注释**，注释只用 `//` 与 `/* */`；文件首行的 `#!` 仍作为解释器行被忽略。
- **两种提前计算要分开**：泛型中的 `match type`、`static for`、类型函数一定在实例化时完成，是语言语义；`#macro` 的提前求值是流水线中 `std::macro` 这个阶段做的事（第 3 节）。
- **标签可以声明读取它的遍**；流水线中没有这个遍时，编译器警告"标签没有效果"，使标签是否生效可以观测。
- **库检查自己的前提**：所需的遍不在流水线中时，给出说明要加哪个遍的诊断（第 4 节）。模块不能自动改变流水线。
- **泛型函数可以省略返回类型**，由每次实例化后的函数体推出；普通函数必须写；编辑器的悬停显示每个调用处推出的类型。

## 2.21 调度与标签的生命周期（2026-10-19）

- **倾向（不是禁令）**：Camel 源码无损地表达计算的意图；在哪里算、怎么算这类与环境相关的内容（分块、布局、放置、内存策略），原则上不写进源码，由执行时的上下文注入（遍参数、调度文件），格式与粒度由读取它的库决定。已有的 `@gpu` 等做法保留。
- **为了性能上限，允许在源码中直接写调度**：上一条是倾向，不排斥专家路径。块级内核（Tiles 路线第 6 节的 `Tile<T,[形状]>` 与 `#kernel`）把块形状写在源码里，由作者直接控制，与由 Tiles 自动决定的高层路径并存。
- **调度的粒度到函数为止**：要更精细，就把那一段提成子函数，用按函数的调度。内联之后，节点上记录的内联来源仍能把它们对应回原来的函数。自动调优按计算的结构身份（算子、形状、类型、前后关系）记录结果，不依赖名字。语言不提供"给某一步计算起名字"的机制。
- **标签由读取它的遍处理掉**：遍用完一个标签后，标签可以不再存在，之后的遍（如内联）不受它约束。遍的先后由用户安排（第 4 节）。
- **内联保留来源**：内联器把被内联函数的身份与它的声明标签记在节点的内联来源上；读取标签的遍若发现标签只出现在已被内联的节点上，给出"标签没有生效，因为函数已在本遍之前被内联"的警告，并说明应调整的顺序。

## 2.22 数值许可的默认值：默认放宽，声明收紧（2026-10-19）

本条取代 2.13、2.15、2.16、2.17 中关于默认值的说法，许可本身的定义与词法规则（2.13）不变。

| 许可 | 默认 | 说明 |
|---|---|---|
| `reassociate` | **允许** | 改变相加的顺序与分组：并行归约、分块矩阵乘的前提 |
| `contract` | **允许** | 把乘与加合并为一次 FMA |
| `approx_math` | 不允许，用标签授予 | 近似的超越函数 |
| `change_precision` | 不允许，用标签授予 | 以较低精度（TF32、BF16 等）计算 |
| `finite_math` | 不允许，用标签授予 | 假设没有 NaN、无穷、负零、次正规数 |

- **收紧**：标签 `#strict` 使所标记的函数或代码块按规范算法逐位计算，不使用任何许可（包括默认许可）；整个程序用流水线参数的安全模式（如 `std::opt safe_fp=true` 与各后端的同名参数）。
- **两条保证不变**：同一设备、同样配置下两次运行结果逐位相同（不得使用结果随调度变化的做法，如浮点原子加）；CPU 上的规范算法仍是参照答案，测试在严格模式下逐位比较，在默认模式下按误差上界比较。
- 不同设备之间逐位相同不再是默认，要用严格模式。

## 2.23 AI 技术栈的主线（2026-10-19）

- **内存与设备**：`Device<T>` 保留。搬运是普通的有副作用的操作，可以在代码中显式写，可以由 Camel 写的变换函数作用于一个函数值而插入（"遍即函数"，见上文"用 Camel 写遍的方向"），也可以由优化遍自动完成。异步不进入语义：顺序由数据依赖与 `sync` 决定，流、事件、重叠执行是后端的实现。
- **调度也可以用 Camel 写**：意图写成一个函数，在另一个模块里用变换函数（或装饰器）调度它，不一定只能靠命令行上的遍组合。
- **低层计算也用 Camel 的图表达**，不另造中间表示：物理操作（块的加载、块内矩阵乘、同步等）是后端库登记的算子，带语义声明，能给出时带 CPU 上的参考实现；逐级降低都是图到图的改写，最后一步才打印成目标代码。每一级降低后的图在可能时仍可在 CPU 上运行，与参照答案核对。
- **许可 `nondeterministic`**（默认不允许，用标签授予）：允许结果随调度变化的做法，如浮点原子加、用原子操作合并的 split-K。2.22 的"同一设备可复现"保证在没有这项许可时成立。
- **C++ 原生模块合法，但不要过度依赖**：能用 Camel 表达的尽量用 Camel，除非有明确的理由（性能、灵活性等）；实现中暴露的表达问题逐一讨论，公共的需求吸纳进语言核心。
- **分布式**：切分写成标签 `#shard<[轴名, ...]>`，可贴在函数参数上（标签位置新增"参数"）；轴名是抽象的，轴的大小在执行时注入；同样的信息也可以写在调度文件里。标准库的 `shard` 遍推导每个结果的切分、插入通信（普通的有副作用的算子）、报告不一致；推导不下去的算子（没有声明下标映射的原生算子）退为先收集再计算，结果正确但较慢。类型系统不变。跨卡求和的顺序按 2.22。
- **算子的事实都是标准标签**：纯度、故障、资源、数值分类、下标映射（输出的每个元素由输入的哪些元素算出）等，都是算子声明上的标准标签，含义写在本规范中；C++ 算子经同一套标签登记接口声明，Camel 写的函数由函数体自动推出。不单独设"下标语义""算子语义"等概念；现有的 `operator_semantics`、`index_semantics` 作为这些标准标签的内部存储保留。
- **图与源码的表达能力相同**：任何合法的图都能写成 Camel 源码，写回再编译得到同一张图（名字、源码位置等不计）。由往返测试强制（全部测试用例与随机生成的程序）；写不回来的图结构视为语言的缺口，需要补上。标准遍 `std::cml` 把当前的图导出为 Camel 源码：产物尽量可读，但不以人类易读为约束；泛型实例写成具体类型的函数，被内联的部分不必还原；大的常量放在旁边的数据文件中由源码引用。部署不另设格式：现有后端的格式够用，冻结后的程序也可以直接导出为 `.cml` 运行。数据管线不需要语言层面的新东西，由标准库提供读取与分批工具。

## 2.24 资源与副作用（2026-10-19）

本条修订 2.2（前缀 `sync`）、2.6（`wait`）与语言参考 4.4，取代其中被下列各项改变的说法。

- **资源**：对它的访问需要排序的东西。资源类别由库用关键字 `resource` 声明（`export resource fs`），可以分组（`resource io = [stdout, fs]`）；与其他名字共用命名空间，按同样的规则导入，可写限定名。标准库最基本的资源（`stdout`、`stderr`、`stdin`、`fs`、`clock`、`env`）默认可见。
- **每个 `var` 自动是一个资源**；函数的 `var` 形参是资源参数，在调用处对应调用者传入的那个变量；闭包捕获了 `var`，其函数类型就带着这个资源。
- **资源是函数类型的一部分**：`func save(p: Params): unit uses fs { ... }`。`uses` 后接用逗号分隔的资源列表，不加括号。原生算子（模块中无函数体的声明）在签名中写 `uses`；没有写的原生算子视为使用"全局"资源，与一切副作用保持顺序。
- **Camel 函数的资源由编译器推出**（函数体内所调用者的资源之和，递归时求不动点），不必手写；编辑器的悬停与文档以限定名显示推出的资源。显式写 `uses` 是承诺，函数体超出即为编译错误；导出函数推出的资源发生变化时给出警告。
- **`pure`** 承诺函数不使用任何资源，由编译器检查；可以写在函数声明与函数类型上（如要求回调是纯函数：`f: (x: T) => U pure`）。
- **函数类型的参数默认对资源泛型**：`f: (x: int) => int` 不写资源，表示 `f` 用什么资源都可以，调用它的函数随之使用这些资源；按实例化确定。资源少的函数可以用在要求资源多的地方，反之不行。
- **同一资源自动有序**：同一个函数体内，真正执行的、用到同一资源的副作用按书写顺序执行（编译器生成控制边）。调用另一个函数，在调用处是"一个用到其资源的副作用"；编译器不跨函数重新编排。
- **副作用按需执行，规则不变**：结果没人用、也不在同步块里的副作用不执行。资源只决定执行者之间的顺序，不决定是否执行。
- **`sync` 块**：块内的副作用一定执行，并且块内一切（跨资源的、纯计算的）都按书写顺序。用于"要它发生"与"跨资源、跨纯计算的先后"（如计时）。不推广为按类别的同步。
- **`wait` 退役**：它的作用被"同一资源自动有序"覆盖。**前缀 `sync func` 退役**：被推出的 `uses` 取代。函数体后缀的 `sync`（函数体是同步块）保留。
- 先例与取舍：靠推断而非强制标注（Java 受检异常的教训）；高阶函数的资源由实例化确定，不需要 Koka 式的行多态；不提供效应处理器；按具体对象（如文件句柄）区分资源暂不做，`var` 除外。

## 2026-10-22（续）`import` 不执行代码：`pyplot` 的 CPython 初始化移到首次使用
