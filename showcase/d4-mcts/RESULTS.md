The comparison is exact, not a tolerance: both programs are the same search over the same IEEE-754
doubles, written in the same order, so the same arguments must give the same tree — including every
child's visits, score and mean, which the pinned goldens carry.  A difference is a defect in one of
them, not noise.  The comparison earned its keep: its first run failed on the empty board within 20
playouts because the Python counterpart seeded its root one step further along the generator than
the Camel program does (a child's key comes from its parent's, and only the root carries the
caller's seed).  Both sides were byte-identical once that was fixed.

## Performance

| metric | Camel (nvm) | Python | Camel / Python |
|---|---|---|---|
| search time (s) | 0.227 | 0.146 | 1.555 |
| playouts per second | 8816 | 13722 | 1.555 |
| peak process memory (MiB) | 24.9 | 11.5 | 2.165 |

The rows above are the `fork` case (`X..OX...O`, 2000 playouts); both are whole-process wall times,
which this host shares with other work, so they are reported and never asserted.  Every number the
search reports is exact and reproducible: nothing in it is timed.  Python is the faster side here,
which is expected: a Python node is one `__slots__` object and a board is a `list` copy, while
Camel copies the whole `State` (a nine-int array and an int) on every `apply_move` and goes through
the graph scheduler.  The empty board runs longer on both sides and the same relation holds
(Camel 1.592 s, Python 0.479 s at 5000 playouts in the same run).
