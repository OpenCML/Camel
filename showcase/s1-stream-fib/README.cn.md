# S1 — 一条斐波那契流

展示设计稿的"流与驻留执行"一行（`docs/design/showcase/README.cn.md`）要的是这样一个程序：用
`T..` 与 `yield`，并且批调度与流调度给出同一个结果。本目录是能这么做的**最小**程序：一个生成器，
它的一轮跨着那次拉取携带**两个**值。

`fib.cml` 就是整个示例。

## 这条流，逐项对应

| 代码做什么 | 它是什么意思 |
|---|---|
| `func fib(limit: int): int.. sync` | 生成器：头写 `int..`，一条 `int` 的流；体里可以 `yield` |
| `loop a = 0, b = 1 while a < limit do { … }` | 循环跨着拉取携带 `a` 与 `b`：两个单元，各自的初值写在循环所在处 |
| `yield a` | 拉取停在这里、交出 `a`；它之后的语句只在消费者再拉时才执行 |
| `(b, a + b)` | 下一轮的那一对，由上一轮算出来：体的最后一个值就是下一个状态 |
| `loop n = 0 for v in fib(50) do sync { println(v); n + 1 }` | 消费者：打印小于 50 的十个元素 |
| `loop total = 0 for v in fib(50) do total + v` | 再调一次、于是另一条流，把同样的元素加起来 |

再调用一次 `fib` 会得到一条新流：流是线性的，生成器函数可以调用任意多次。

## 这份读数钉住了什么

`test/plans/feat/showcase_s1.plan.toml` 把整份标准输出钉死——小于 50 的十个斐波那契数与它们的和
88——默认后端与 `std::prl` 各跑一遍。降级容易犯的两个错正好在这一串数里露出来、别处露不出来：
**丢掉两个携带值里的一个**，以及**在第一个状态被写动之后才写第二个状态**（`s + i` 读到的是新的
`i`）。后者不会崩，只会打印出另一个和。
