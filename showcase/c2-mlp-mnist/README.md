# C2: training an MLP on MNIST

The first example of the showcase batch (H13). The same task is written twice: once in Camel
(`train.cml`) and once in the idiomatic PyTorch a practitioner would write
(`baseline/train_torch.py`). Both read the same data and the same starting weights, train the
same 784 → 128 → 10 MLP (ReLU, Adam, softmax cross-entropy), evaluate on the same validation
set, and are compared against one set of tolerances. Every number is produced by
`compare.py`; see [RESULTS.md](RESULTS.md). The Chinese README is
[README.cn.md](README.cn.md).

## Layout

```
showcase/c2-mlp-mnist/
  train.cml                the Camel implementation (parameter tree, value_and_grad, loop, save_tree)
  baseline/train_torch.py  the PyTorch counterpart (nn.Linear, F.cross_entropy, torch.optim.Adam, state_dict)
  make_data.py             writes the data and the starting weights (MNIST or a deterministic stand-in)
  compare.py               runs both sides, compares, measures, writes RESULTS.md; exits non-zero on failure
  RESULTS.md               the latest `--profile standard` run (generated, do not edit)
  README.cn.md             Chinese README
  README.md                this file
  artifacts/               generated data and checkpoints (gitignored, not committed)
```

## Data

`make_data.py` writes the data and the starting weights both sides share:

- `train_images.npy` / `val_images.npy`: float32 `(N, 784)`, pixels in `[0, 1]`;
- `train_targets.npy` / `val_targets.npy`: one-hot targets (what `nn.softmax_cross_entropy`
  takes);
- `train_labels.npy` / `val_labels.npy`: class indices (what PyTorch's `F.cross_entropy`
  takes);
- `init/w1.npy`, `init/b1.npy`, `init/w2.npy`, `init/b2.npy`: He-normal weights and zero
  biases;
- `dataset.id`: the identity of the data (the first 16 hex digits of the SHA-256 of the
  training images and targets plus the sizes); the Camel program writes it into the
  checkpoint, and `save_tree`/`load_tree` check it, so a checkpoint cannot be loaded against
  a different data set;
- `manifest.json`: source, sizes, seed and the SHA-256 of every file.

**MNIST is never downloaded.** When the repository cache holds `mnist.npz`, the real data is
used (`--mnist <path>`, or `--source auto` to look at `.cache/mnist/mnist.npz` under the
repository root); when it does not, the script generates a **deterministic synthetic
stand-in** and records `synthetic` as the source in `manifest.json`. Each class is a fixed
set of bright rectangles on a 28×28 grid (a crude stroke), every sample is shifted by a few
pixels and gets Gaussian noise, and the result is shuffled with a fixed seed. It exists so
that the machinery the example demonstrates (data, training, evaluation, checkpoint,
comparison) works without the dataset; C2 is about the language and the example, not about
MNIST. The small CI configuration always uses the stand-in, so its numbers are identical on
every machine.

## Running it

The comparison (recommended: it prepares the data, removes the old checkpoint, runs both
sides and writes the tables):

```powershell
# small: synthetic data, 200 steps, about 5 seconds including the PyTorch import
& D:\Projects\Camel\benchmarks\.venv\Scripts\python.exe showcase\c2-mlp-mnist\compare.py --profile small

# the reported configuration: MNIST when the cache has it, the stand-in otherwise
& D:\Projects\Camel\benchmarks\.venv\Scripts\python.exe showcase\c2-mlp-mnist\compare.py --profile standard `
    --mnist D:\Projects\Camel\.cache\mnist\mnist.npz
```

`--profile`: `small` (1000/200, 200 steps, batch 50), `standard` (10000/2000, 1000 steps,
batch 100), `full` (60000/10000, 3000 steps, batch 128). `--steps`, `--batch`, `--lr`,
`--log-every`, `--threads`, `--seed` and `--source` override the profile.

The Camel program alone (first set `$env:CAMEL_HOME = "out\latest"` and put
`out\latest\bin` on `PATH`):

```powershell
camel showcase\c2-mlp-mnist\train.cml `
    --arg data=showcase/c2-mlp-mnist/artifacts/small --arg steps=200 --arg batch=50 `
    --arg lr=0.001 --arg log_every=20 --arg threads=1 `
    std::macro std::nvm
```

**Remove the `checkpoint` directory under `data` before a second run**: `save_tree` refuses
to replace an existing directory (see "Problems" below). `compare.py` removes it every time.

The PyTorch baseline alone:

```powershell
& D:\Projects\Camel\benchmarks\.venv\Scripts\python.exe showcase\c2-mlp-mnist\baseline\train_torch.py `
    --data showcase/c2-mlp-mnist/artifacts/small --steps 200 --batch 50 --lr 0.001 --log-every 20 --threads 1
```

Both programs print the same machine-readable lines (`c2 config`, `c2 init`,
`c2 step=<i> loss=<v>`, `c2 trained`, `c2 checkpoint`); `compare.py` parses only those.

## Results and tolerances

`RESULTS.md` contains three tables generated by the script:

1. **Agreement**: initial validation loss, the training loss at every logged step (the worst
   relative difference), final validation loss, final validation accuracy, and each side's
   own checkpoint round-trip drift; every row shows the difference, the tolerance and
   PASS/FAIL, and `compare.py` exits non-zero when one bound is exceeded. The small test
   plan asserts the same things, so the example cannot rot silently.
2. **Performance**: training time (the training loop only; data loading, evaluation and
   checkpointing are excluded), throughput (`steps × batch / time`), the peak working set of
   the whole process including children (psutil), the Camel compile time (the median of three
   `std::macro std::stats std::null` runs), and the whole-process wall time including
   startup.
3. **Code size**: SLOC per `// == section ==` / `# == section ==` section the two files share
   (blank lines, full-line comments, Python docstrings and C block comments are not counted;
   a code line with a trailing comment counts once).

**Why these tolerances (design principles section 7)**: bit-for-bit equality is promised only
for the canonical algorithm on one back end. These two programs compute the same f32
formulas, but the matrix kernels accumulate in a different order and Adam's bias correction
is written differently, and the difference compounds over the optimization steps, so this is
a **bounded-error** comparison: `1e-5` relative for the initial loss (the same weights and
data, one forward pass), `1e-2` relative for every logged training loss, `1e-2` relative for
the final validation loss, and `1e-2` absolute (one percentage point) for the final
validation accuracy. The checkpoint row is not a comparison between the two sides: each
implementation must load back exactly what it saved (drift zero). Under the standard
configuration the worst step is about 0.55 of the bound; see `RESULTS.md`. The `small`
configuration (synthetic stand-in) differs at the `1e-5` level.

## Side by side

- **The parameters are a type.** Camel's `type Mlp = { w1, b1, w2, b2 }` is at once the type
  of the starting weights, of the gradient and of the optimizer state;
  `value_and_grad(loss)(m, x, y)` returns a gradient tree of the same shape and
  `adam(m, g, state, lr)` consumes it, so no line in the program names a leaf. PyTorch needs
  three things — an `nn.Module`, an optimizer object and a `state_dict` — to express the same
  facts.
- **Training is an expression.** The whole run is one `loop` whose state (model, optimizer
  state, step) is written out explicitly; no step function, logging statement and state
  update have to be split across functions. PyTorch uses the idiomatic `for` loop with
  `zero_grad`/`backward`/`step`; both read clearly, but Camel has no optimizer object layer.
- **Effects are explicit.** The loop body is a `sync { ... }` block, so logging happens in
  the order written. In PyTorch `print` is sequential for free. Under the graph semantics
  (a loop may be parallelized or skipped), Camel's explicit effect block is necessary, but it
  is extra noise when writing a training loop.
- **The data pipeline.** Both sides read the `.npy` files directly. Camel takes a contiguous
  minibatch with `slice(t, 0, start, start+batch)`; the data script shuffles once, so the
  batch order per epoch is fixed. PyTorch slices the same way and is shorter to write.
- **Where Camel is shorter**: the checkpoint (`save_tree` on a tree vs `torch.save` on a
  `state_dict`), evaluation (one `argmax`/`sum` vs `no_grad` + `.item()`), and initialization
  (four `load_npy` calls vs a layer-by-layer `copy_`). PyTorch is shorter in `model` and
  `loss`, because `nn.Linear` hides the bias and the shapes.
- **The cost**: in this implementation Camel's throughput is about 0.8× PyTorch's (standard
  configuration, one thread; see `RESULTS.md`), its peak memory is about 0.35×, and its
  compile time is about 0.07 s; PyTorch is eager and has no such step. Performance is not what
  this example sets out to prove, but the numbers are reported as measured.

## Problems

The genuinely awkward parts of writing this example. Each comes with a question in the
"Open questions" section of `docs/handover/reports/H13.md`, in the handover format.

1. **`save_tree` cannot replace a checkpoint, and Camel has no way to remove a directory.**
   The signature comment says "The directory is replaced as a whole or not at all", but the
   implementation fails with `checkpoint already exists` when the directory exists
   (`modules/tree/src/checkpoint_io.cpp`). A training program therefore cannot write its
   checkpoint a second time; `fs` has `exists`, `mkdir` and even a `replace` for overwriting
   a file, but no removal, so the program cannot recover by itself. `compare.py` removes the
   directory from Python, but a Camel-only user has no equivalent.
   **Question**: is the comment right (replace as a whole, keep the old directory on
   failure), or is the implementation right (refuse)? If the latter, should `save_tree` get a
   `replace` variant (like `fs.replace`), or should `fs` get a removal operation?
   **Resolved (H20)**: the comment was right — `save_tree` replaces as a whole, keeping the
   old directory until the new one is published and putting it back on failure;
   `fs::remove` and `fs::remove_dir` return `T!`. See `## H20-4` in
   `docs/handover/reports/H20.md`.
2. **Tensors have no way to select or reorder rows, so the data pipeline shuffles outside the
   language.** The only minibatch operation is `slice(t, axis, start, end)`; `t[i]` returns a
   single scalar. There is no `gather`/`index_select`/row-selection by an index array, so
   "reshuffle every epoch" cannot be written in Camel; the example has `make_data.py` shuffle
   once and the training loop take contiguous slices. For a training example this is a real
   gap.
   **Question**: is an index-based row selection (or an array `map` plus tensor indexing)
   planned? Until it exists, is "shuffle in the data script" the accepted shape for official
   examples?
3. **Cross-entropy only takes one-hot targets, while data pipelines usually carry class
   indices.** `nn.softmax_cross_entropy` wants an `(N, 10)` one-hot tensor; MNIST's native
   label is an `(N,)` integer. To let both sides use the same data, `make_data.py` writes both
   forms (one for Camel, one for PyTorch), so the data directory carries redundant
   information. Building one-hot from indices in Camel takes a per-row
   `range(0,10) == label` plus `reshape`/`concat`, which is long and slow (the old
   `test/cases/modules/nn/mnist.cml` does exactly that).
   **Question**: is cross-entropy going to accept class indices (like `F.cross_entropy`), or
   is a `one_hot` operator planned? Is this an `nn` API question or a language-level data
   representation question?
4. **Recording a loss curve needs extra loop state or explicit printing.** A `loop` yields
   only its final state; to bring the loss of each logged step out of the loop, one either
   adds a `float[]` to the state tuple or prints inside the body and parses stdout (this
   example does the latter; `compare.py` parses it). This is not a bug, but for the common
   "training curve" need the language has no convenient way to collect a side product, and
   design principles section 15 does not cover it.
   **Question**: is this the expected usage (logging is an effect, curves are read by an
   external tool), or should there be a more direct form?

## Tests

The four problems above were decided by the review: row selection, labels, keyed randomness
and atomic `save_tree` replacement are H20; index slicing, lambda inference and
"differentiate the first parameter" are H21.  This example keeps the current spelling
(`with <m: Mlp>`, `slice`, one-hot targets, deleting the checkpoint directory from Python)
until H20-4 and H21-3 land, when it will be rewritten with
`value_and_grad(loss)(m, x, y)`, `take`/`permutation` and integer labels; the H13 report records
that order.  The review's backtick interpolation and
`let (value, gradient) = ...` destructuring are already in place.

The small configuration is registered in `test/plans/perf/showcase_c2.plan.toml`
(`tier = "slow"`): it runs 200 steps on the synthetic stand-in, runs both sides, checks the
tolerances above, and takes about six seconds.  H10's fast/slow split has landed: the default
`npm run test` skips the slow tier and `npm run test:all` (or `--tier all`) runs it.
