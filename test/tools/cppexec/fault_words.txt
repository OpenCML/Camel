# The `fault_*` cases whose fault is not what std::fvm prints, and why. The check
# (run.py --faults --fault-baseline=...) asks every such case in test/cases and requires this set to
# be exactly the ones that differ: a new name is red, and so is a name here that starts agreeing --
# in that case the line is deleted, because a list that can only grow says nothing.
#
# A fault is the language's answer, not a back end's: the sentence std::cpp prints has to be the one
# the interpreter prints, word for word. A rule that writes its own plausible sentence is the one
# mistake this list is meant to surface early -- it reads well, so nobody checks it.
#
# Two kinds of line, and the difference matters: GAP is a fault this back end does not have (write
# it, then delete the line -- a missing fault is worse than different words for one), EXCEPTION is a
# difference that is not the fault at all.
#
# EXCEPTION: the interpreter itself warns during the run (`The call of '<__assn__> ...'`), and the
# written program has nothing to warn about -- a compiler diagnostic, not a fault sentence. The
# fault line under it and the exit code are the same on both sides; only that extra warning differs.
#
# The list is empty, and the EXCEPTION above is why it can be: it had one member,
# `test/cases/consistency/faults/fault_in_sync_call.cml`, and the warning that made it an exception
# was the one a call taking a `var` argument drew outside a sync block. The ruling of 2026-11-15
# (design principles 3.1, 3.5) makes a write to a `var` a value and not an effect, so the
# interpreter no longer warns there and the two sides now agree word for word. The line was deleted
# as the rule above says; the EXCEPTION kind stays described because a diagnostic that survives on
# one side only is still the shape to look for, and an empty list is the reading this check exists to
# produce -- 48 of the 50 programs compared word for word, 2 not translated, 0 differing.
