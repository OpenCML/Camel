# 两个用例按相反方向读同一份记录文件

## 事实

`test/plans/feat/parse/golden/ast_hashes.txt` 是 AST 记录的基准。迁移调用点那一笔（`lane/data-arg-migration`，10 笔，803 个 `.cml`、约 1321 处）按批重录了 734 行哈希，行数不变（4485 → 4485），没有一行丢失。

重录之后，四个用例的读数互相矛盾：

```
`inspect.tok_snapshot`、`inspect.cst_snapshot`、`inspect.ast_snapshot`、`frontend.ast_snapshot`
```

- 跑 `-UpdateGolden`（写记录）之后：这四个转绿。
- 之后按普通方式再跑一次：这四个翻红。
- 而 `inspect.*` 与 `frontend.ast_snapshot` 要求的**方向相反** —— 让一边绿的动作让另一边红。

车道停在这里，**没有用 `--update-golden` 把它盖住**。把两边都刷到绿只需要一条命令，而那样一来，「同一份记录被两个用例按相反方向读」这件事就再也不会出现在任何读数里。

## 为什么这不是一笔「重录一下就好」

一个基准文件只有两种可能的语义：

1. **它是期望值** —— 被测程序算出哈希，与它比，不等则红。写它的动作只有「有意改变期望」时该做。
2. **它是缓存** —— 被测程序算出哈希，写回它。那它就不该被任何用例当作断言失败的理由。

两种情况下的正确行为完全不同：前者要求重录必须伴随一句「期望为什么变了」，后者要求**根本不该有红**。

现在这四个用例里，有的把它当期望、有的当缓存，而它们的名字（`*_snapshot`）不区分这两件事。

## 需要裁的

1. `ast_hashes.txt` 是**期望值**还是**缓存**？
2. 若是期望值：`inspect.tok/cst/ast_snapshot` 与 `frontend.ast_snapshot` 中**哪一个读错了方向**？（这需要量出来，不是选出来 —— 两边都能自圆其说，只有一份是对的。）
3. 若是缓存：那四个用例里的红**都不该存在**，需要把它们改成「在读不到记录时红、在记录与算出的值不同时**更新并报告**」。
4. 这两种之外还有第三种可能：**它们是两份不同的记录**，被错配成了同一个文件。若如此，请指出该分成哪两份。

## 我们按默认继续的做法

在裁决回来之前：

- 迁移那一笔**不合 `develop`**（它带着这 4 条红，而这 4 条红无法在本轮修好 —— 判据方向未定，任何修法都是在猜）。
- 其余 6 条红已有归属（诊断文案、`U` 推断回归、`perf.cml` 的空数组、被 audit 作废的前提、`TILES_OUTLINED` 的 10→12），不含这一条。
## 决策者答（2026-11-23 04:25）

1. **`ast_hashes.txt` 是期望值，不是缓存。** 它是 AST 的基准：被测程序算出哈希与它比，不等即红；重录只在"有意改变期望"时做，并写明为什么变（`scripts/check-ast-hashes.mjs` 头注释就是这个读法）。
2. **但这四个用例读的不是同一份文件**，前提要先更正：`inspect.tok_snapshot`、`inspect.cst_snapshot`、`inspect.ast_snapshot` 比的是 `test/plans/smoke/golden/{tok,cst,ast}.txt`（`test/plans/feat/parse/core.plan.toml` 第 15、28、41 行），只有 `frontend.ast_snapshot` 读 `ast_hashes.txt`。它们共同的东西是用例 `fib10_pipeline.cml`，不是记录文件。
3. **"写记录后绿、再跑就红"最常见的原因是两次跑用的不是同一个构建**（重录时的二进制与检查时的二进制不同，比如重录时还是迁移前的解析器），或者重录写的东西本身不确定。请量三样再定修法：两次跑的构建哈希；`-UpdateGolden` 之后与普通再跑之后，那四份记录各自的 `git diff`；同一构建上连跑两次普通检查是否稳定。
4. 在量清之前，迁移那一笔不合 develop，这个默认对。量出来是哪一边读错，就修哪一边；任何一边都不许用重录盖住。
