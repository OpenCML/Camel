# 块根那个句柄，编译器从哪拿它的类型与算子

**一句话**：设计说「句柄只从块头来」并删掉了 `graph_of` 这类「从普通值拿到句柄」的函数；那么 `view d = f` / `edit d = f` 里编译器**自己造**的那个块根句柄，它的类型与算子从哪里来 —— 块头隐式导入 `graph` 模块，还是编译器内建一份？

## 为什么这成了一个必须裁的问题

块头的绑定初值现在是**函数值**，不是句柄（`src/parse/src/ast/builder_expr.cpp:1609`/`:1615`）：

```
1609: node_ptr_t binding = createNodeAs<DataDeclLoad>(true, std::vector<Reference>{root});
1615: *initial << overNode;          ← 初值直接就是块头那个函数 f
```

把初值换成句柄，第一反应是让 AST 生成 `let d = <某个句柄表达式>`。但**能写出来的两种句柄表达式都被设计删掉了或写不出来**：

- `docs/design/graph-editing/README.cn.md:66`：「**句柄只从块头来**。`view d = f`、`edit d = f` 把 `d` 绑定成这个块的根句柄；`graph_of` 这类“从普通值拿到句柄”的函数删除。所以块外不存在任何句柄值，图算子在块外根本拿不到实参，调不了。」
- 同文件 `:63`：「**规则：`graph` 模块导出的类型（`Graph`、`Node<T>`、`Region`…）都是句柄类型；签名里提到句柄类型的函数就是图算子，只能在块里调用。**」

两句合起来只有一条自洽的实现：**块根句柄由编译器造**（不能写成对 `graph::graph_of`/`open` 的调用 —— 那个函数按设计要删）。但句柄类型**只有 `graph` 模块导出** ⇒ 编译器要么把这个模块带进来，要么自己内建一份。这不解决，改 AST 只是把「类型是函数」换成「类型是一个解析不到的句柄」，`nodes(d)` 仍然过不去。

同一面墙已经被另一条车道撞到并停在页里：`internal/questions/2026-11-27-where-a-blocks-root-gets-the-module-that-declares-its-operator.cn.md`（「块根拿不到声明它那个算子的模块」）与 `internal/reports/2026-11-27-a-blocks-root-needs-a-module-the-program-never-imported.cn.md`（四次推断被读数否证，缺口在语言层）。

## 三个候选

**(A) 块头隐式导入 `graph` 模块。** 任何写了 `edit`/`view` 的程序，其块头位置自带一次对 `graph` 的导入（源里没 `import` 也算）。块根本身就是「只从块头来的」那类特殊物，隐式导入只在这个位置发生。

**(B) 编译器内建块根句柄类型与算子。** 不进模块系统，在编译器的内建类型/算子表里登记「块根句柄」。

**(C) 其它口径由作者给。** 例如句柄类型改由 prelude 导出、或块头允许写一次显式导入。

## 默认做法（作者未答前，按这条开工）

**按 (A) 试，并且是带停止条件的试**：

1. AST 那两行把初值从函数值改为块根句柄；
2. 块头位置隐式引入 `graph` 模块；
3. 在 `test/plans/probe/editview.plan.toml` 上取 `nodes(d)` / `graphs(d)` 的实参类型原文（`std::gir` 或 `check` 的 stderr）；
4. **若 `probe/editview` 没有可测改善（`nodes(d)` 仍解析不到句柄），停下报读数，不再往下做** —— 那说明缺口不在「模块从哪来」，而在更上游。

选 (A) 不选 (B) 的理由：(B) 会让「哪些类型是句柄」出现两个来源（`graph` 模块的导出 + 编译器内建表），而这是本项目反复记为缺陷的形状 —— 架构的四个「唯一」明确要求身份的来源只有一处。选 (A) 则把「块头自带一次导入」当作块头这条规则的一部分，不新增第二处真相。

**能推翻这条默认的读数**：若 `graph` 模块的导入会连带把它的库图/遍挂进用户程序（`internal/questions/2026-11-25-does-importing-a-module-add-graphs-to-the-entry-program.cn.md` 记的那个问题），那隐式导入的代价就不是「多一条 import」，而是「每个块都挂 205 张库图」—— 出现这个读数就立刻停，改判 (C)。

## 这不是新问题，是一条被删掉的路留下的口

`graph_of` 被删掉是对的（它让块外能拿到句柄，于是图算子能在块外被调用）。删掉之后，**唯一还能拿到句柄的地方就是块头**，而块头自己需要这个句柄的**类型** —— 这条链的最后一环此前没有人需要，因为以前是用户写 `graph_of(f)` 拿到的。所以这不是设计遗漏，而是「删掉一条路」之后新暴露的一环。

## 决定（负责人，`D-1127-1` ③）：按 A

```
块头让程序**依赖 `graph` 模块**，走的就是普通 `import` 那一个机制
  —— `import` 不执行代码、不往当前作用域注入名字
⇒ **不新设"只依赖、不进作用域"的登记处**（那会把 import 拆成两个概念）
⇒ 块里能直接写 `nodes(d)` 这类名字，是**块头规则自己的作用域**（块内可见 graph 的导出），
   不是改用户模块的作用域
⇒ 停止条件②（导入 graph 把它的库图挂进入口程序）若触发，那是 **import 机制本身的缺陷**（11-25 那页），
   在那里修：只把用到的图链接进来，**不为块头另开路**
```
