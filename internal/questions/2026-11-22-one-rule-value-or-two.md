# `RuleObject` 与重写模块的规则值，合成一个还是两个

作者在 0.4 验收（`f0756385f`）把这条留给「变换一步」：

> **「`RuleObject` 与重写模块的规则值是两样东西，头注释说明了理由；变换一步要定它们是否合成一个规则值（规则是值，第 7 节）。」**

## 今天的两样东西

```text
RuleObject                include/camel/core/rule_index.h:48
   name / head / arity / rhsCallee / variables     ← 0.4 新搬进来的五事实
   parameterTypes: optional<vector<const Type*>>   ← 刚编译化（87a8b5749）
   condition:      const FunctionType*             ← 刚编译化，**今天无读者**
   serial                                          ← 规则值缓存的键

重写模块的规则值          modules/rewrite/rule.h
   持两条 ::Function* 或模板 id；`__rule(...)` / `__rule_generic(...)` 求值得来
   是 `Rule[]` 的元素，交给 saturate / rewrite
```

## 一个刚发现的事实，它影响这个决定

`condition` **只被写、从不被读**（`program.cpp` 填表处写，无读者）。

一个字段被写而不被读，只有两种可能：它将来要被读，或者它从来不该存在。
**这两者的处置相反**（留 / 删），而 `RuleObject` 与规则值是否合一会决定它是哪一种：

- **若合成一个**：`condition` 是那个统一规则值的一部分，读它的地方会在匹配时出现 —— 该留。
- **若保持两个**：`condition` 属于索引侧的元数据，而索引侧今天不求值条件 —— 它就是死字段，该问它当初为什么加。

## 需要决定的事

**默认建议（按此当轮开工）：保持两个，但把 `condition` 的去留写成一条判据。**

1. **不合并。** 理由是两者回答不同的问题：`RuleObject` 答「这条规则长什么样、该不该被选」
   （索引侧，全局、按族名与拼写取），重写模块的规则值答「这条规则在被选中之后怎么展开」
   （展开侧，按次求值）。**合成一个会把「选」与「展开」两件事黏在一个类型上。**
   而作者自己写在第 6 节的那句 —— 规则集是**显式交来的值**、按**根算子编号**取 ——
   说的是「怎么选」，没说「选完怎么展开」。这两件事本就该分开。
2. **`condition` 按「死字段」处理之前，先回答它为什么在那**：若它是为「条件规则」预留的，
   那预留本身要有一页说明（谁将读它、什么时候接上）；若没有那页，**下一轮删掉它**，
   并把「条件」这个概念放到真正需要它的地方（匹配处）。**不许留着一条没人读的字段当占位。**
3. **这条决定不挡第 1 项**（按根算子编号建索引）—— 那件与合并无关，可以立刻做。

**我按第 1、3 条开工：先派第 1 项；`condition` 的死字段问题按第 2 条在合并前处理（删或写清预留）。**

**若不同意保持两个，改这一页，第 1 项不受影响。**
## 决策者答（2026-11-22 10:35）

**目标是一个规则值，不是两样东西；但现在都不动，放进变换一步的施工计划。**

- 核心抽象第 7 节"规则是值"、第 6 节"规则集是显式交来的编译期值"，加上第 2 节"能推导的不存"：一条规则就是一个值（左侧模式、右侧、适用条件、参数类型）。变换要问的五件事（根算子、元数、右侧被调者、绑定的变量、名字）都能从这个值的左右两侧推出来，是对规则值的查询，不是另存的一份记录。"按根算子编号取"是规则集值上的索引，从规则值建出来，是派生的东西，不是第二种规则类型。"选"与"展开"是对同一个值的两种用法，不需要两个类型。
- 所以 `RuleObject` 加全局索引是过渡形态：0.4 的目标（遍不读语法树）它完成了，到此为止，**不再给它加字段、不再改它的键**。第 1 项"按根算子编号建索引"不在全局索引上做，那会在变换一步被整个替换；它进变换一步的施工计划，与"规则集显式交来"一起做。
- `condition` 没有读者，现在从 `RuleObject` 删掉；适用条件在变换一步随统一的规则值回来，由匹配处读。
