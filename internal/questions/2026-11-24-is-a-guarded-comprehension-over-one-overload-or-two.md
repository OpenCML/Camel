# 一个守卫过滤掉的推导，是「一个重载」还是「两个」？

**问题**：`lane/op-overload-merge` 把第四步（推导用普通名 `filter`/`map` 而不是内建组）落地之后，`consistency/shadowed`
计划里有 4 条用例变成了红，红的是同一句话：

```
fits more than one overload
```

**为什么会同时成立**：程序自己声明了 `filter(int[])`，而内建组规则也说 `filter` 可以接推导。
两者都是真的候选，于是推导得到的调用有两个候选，不再唯一。

**而这条用例现在钉的是**「推导＝内建组」。

**⇒ 所以这两句话不能同时为真：**

```
① 推导用普通名 filter/map（本车道第四步的意图）
⇒ **⇒ ② 推导得到的内建 filter 与用户声明的 filter 不共存（用例现在钉的）**
```

**⇒ 要么 ① 成立而 ② 要改用例；要么 ② 成立而 ① 不该落地。**

## 三读，各自的代价

| 读法 | 含义 | 代价 |
|---|---|---|
| **A. 推导是普通名，所以它会与用户的重载**并列**，`shadowed` 那 4 条预期要改** | 推导产出的调用于是能看见用户声明，用户能**遮住**内建 | 4 条用例的期望要改；并且「内建组」对于推导不再是特权 |
| **B. 推导仍是内建组，`shadowed` 那 4 条是对的，第四步退回** | 推导不走普通名解析，用户声明不参与 | 车道第四步的意图撤回；`shadowed` 保绿 |
| **C. 两者共存但**内建优先**（用户声明不遮，只在不冲突时可用）** | 「fits more than one overload」不再出现，而用户声明仍然可达 | 需要一条新的优先级规则，且它是**第三**种，前两种里都没有 |

## 我的默认建议：**A**

**⇒ 理由三条：**

```
**① 它只改**预期**，不改语义**（用例本来就是钉「旧行为」的那一层）
⇒ **⇒ ② 与 develop 已有的裁定同向：`range_value.cml` 写「The type is not ambient」、prelude 写「写在
   `import { … } from prelude` 之后」——两处都在说「内建不是特权,是**导入来的东西**」**
⇒ **⇒ ③ `shadowed` 这个计划名本身就在问「被遮住的时候会怎样」；它现在答的是「不会遮」**
```

**⇒ 而 C 我不建议，因为它是**为了一条用例不红而新增一条规则**：**

**⇒ 那条规则之后会与 prelude 的可见性裁定互相解释不清。**

## 我不做的

**⇒ 我不会为了让这 4 条变绿而改这条用例的期望**（那是把红搬走），也不会退回第四步（那是把车道的意图丢掉）。

**⇒ 在裁定下来之前，`lane/op-overload-merge` 保持**可合但不推**，而这 4 条红写进它的合并说明里。**
