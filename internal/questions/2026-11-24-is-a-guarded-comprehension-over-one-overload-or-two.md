# 一个守卫过滤掉的推导，是「一个重载」还是「两个」？

**问题**：`lane/op-overload-merge` 把第四步（推导用普通名 `filter`/`map` 而不是内建组）落地之后，`consistency/shadowed`
计划里有 4 条用例变成了红，红的是同一句话：

```
fits more than one overload
```

**为什么会同时成立**：程序自己声明了 `filter(int[])`，而内建组规则也说 `filter` 可以接推导。
两者都是真的候选，于是推导得到的调用有两个候选，不再唯一。

**而这条用例现在钉的是**「推导＝内建组」。

**⇒ 所以这两句话不能同时为真：**

```
① 推导用普通名 filter/map（本车道第四步的意图）
⇒ **⇒ ② 推导得到的内建 filter 与用户声明的 filter 不共存（用例现在钉的）**
```

**⇒ 要么 ① 成立而 ② 要改用例；要么 ② 成立而 ① 不该落地。**

## 三读，各自的代价

| 读法 | 含义 | 代价 |
|---|---|---|
| **A. 推导是普通名，所以它会与用户的重载**并列**，`shadowed` 那 4 条预期要改** | 推导产出的调用于是能看见用户声明，用户能**遮住**内建 | 4 条用例的期望要改；并且「内建组」对于推导不再是特权 |
| **B. 推导仍是内建组，`shadowed` 那 4 条是对的，第四步退回** | 推导不走普通名解析，用户声明不参与 | 车道第四步的意图撤回；`shadowed` 保绿 |
| **C. 两者共存但**内建优先**（用户声明不遮，只在不冲突时可用）** | 「fits more than one overload」不再出现，而用户声明仍然可达 | 需要一条新的优先级规则，且它是**第三**种，前两种里都没有 |

## 我的默认建议：**A**

**⇒ 理由三条：**

```
**① 它只改**预期**，不改语义**（用例本来就是钉「旧行为」的那一层）
⇒ **⇒ ② 与 develop 已有的裁定同向：`range_value.cml` 写「The type is not ambient」、prelude 写「写在
   `import { … } from prelude` 之后」——两处都在说「内建不是特权,是**导入来的东西**」**
⇒ **⇒ ③ `shadowed` 这个计划名本身就在问「被遮住的时候会怎样」；它现在答的是「不会遮」**
```

**⇒ 而 C 我不建议，因为它是**为了一条用例不红而新增一条规则**：**

**⇒ 那条规则之后会与 prelude 的可见性裁定互相解释不清。**

## 我不做的

**⇒ 我不会为了让这 4 条变绿而改这条用例的期望**（那是把红搬走），也不会退回第四步（那是把车道的意图丢掉）。

**⇒ 在裁定下来之前，`lane/op-overload-merge` 保持**可合但不推**，而这 4 条红写进它的合并说明里。**
## 决策者答（2026-11-24）

**不用新裁定，两条原则已经定了它，而三读都与它们不完全相合。**

- 原则「列表推导」一条：`[e for x in xs if c]` 的含义就是 `xs->filter<c>->map<e>`。所以推导里的 `filter`、`map` 就是写在那里的普通名字，按普通名字解析——这一半 A 说对了。
- 原则「名字的优先级只有一条规则」：局部 > 本模块 > 按名字导入的 > `using namespace` > 内建；**取第一个有这个名字的层，跨层不合并**（只有 `operator` 重载各层合并）。程序在模块顶层声明的 `filter` 在「本模块」层，prelude 的 `filter` 在「内建」层——前者把后者**遮住**，两者从不进同一个候选集。

所以正确的读数既不是「两个都合适」（A 的并列），也不是「推导＝内建」（B），也不是「内建优先」（C）：**本模块的 `filter` 遮住内建的**，推导用的就是它；它的签名接不住推导给的参数，就报「没有合适的重载」，不回落到内建。`shadowed` 这个计划问的正是这件事，四条用例的期望改成这个答案。

而「fits more than one overload」本身是名字解析的缺陷：`#op` 声明是函数（只是函数体在 C++），不是 `operator` 重载，不该跨层合并；车道把 `#op` 组当成了运算符那样各层合并。修它，判据是这四条从「两个候选」变成上面那个答案，且 `operator +` 等真正的运算符重载仍各层合并（反例一条）。

**另一处要纠正：prelude 不是"导入来的东西"。** 原则里它是「内建」层——不导入就看得见；11-23 那页（`how-a-named-type-says-it-converts-to-a-stream` ④）已答：prelude 导出的类型与函数一样不用导入。`range_value.cml` 的「not in the ambient layer」、prelude 里「写在 `import { … } from prelude` 之后」是当时实现的描述，不是裁定，与原则相反，随修复一起改。`values` 那 9 条红（推导里的 `filter`/`map` 要 import 才看得见）是同一个缺陷，不是旧账。`lane/range-rn` 的「prelude 免 import」正是落实这一条，不要整条丢弃：取它的这一半，它的「解析期合并 `#op` 组」那一半不要——develop 已有导出期的做法，同一件事只留一种机制。
