# map、filter、reduce 在图上原生：`EACH` 节点

负责人 2026-11-28 定：`map`、`filter`、`reduce` 这类"每一轮各算各的"的重复，在图上要有自己的节点。它取代 `2026-11-28-refactor-not-patch.cn.md` 第四件"map 是循环"里的第二刀；第一刀（推导式的元素函数从位置取类型）照旧有效。

## 为什么

今天它们是一组标记算子（`:mark/map_arr`、`:mark/filter_arr`、`:mark/reduce_arr`、`:mark/foreach_arr`），带来四个问题：

1. **算子反过来调后端**：内核要回调当前后端去跑元素函数，算子不再是值到值。
2. **每个后端各写一遍循环**：`fvm` 是一个 C++ 的 `for`，每个元素付一次完整调用入口；`jit` 没有循环可编。
3. **"元素互不依赖"不在图上**：`prl` 只能按算子名去认（`taskflow.cpp#mark_map_arr`），违反原则 3.6"并行来自声明的性质，不来自名字"。
4. **遍看不见里面的结构**：融合、求导、批处理都只能为每个标记算子单写规则。

前端把它们编成 `LOOP` 也不行：`LOOP` 带状态，下一轮依赖上一轮，图上就丢了"各轮互不依赖"这条性质。

图上的重复本来就有两种：

- **有状态的**：下一轮用上一轮的结果，即 `LOOP`。`fold`、`while`、`count`、带效应的 `foreach` 属于这一种。
- **无依赖的**：每一轮各算各的，即本页的 `EACH`。

## 节点

- **迭代空间**：一个或几个等长的集合（数组、范围），决定轮数。长度不等时的规则与今天的 `zip` 相同。
- **体区域**：一个区域，输入这一轮的元素（以及下标），输出这一轮的结果。区域机制与分支的臂、循环体是同一套。
- **汇合方式**：每轮的结果怎样合成节点的值。只有下面三种：
  - **按位置收集**（`map`）：第 i 轮的结果放在第 i 位。
  - **按位置保留**（`filter`）：留下判定为真的元素，保持原来的顺序。
  - **结合归约**（`reduce`）：用一个满足结合律的运算合并，`initial` 是它的单位元。是否满足结合律由声明回答，见下面"待负责人定"。
- **语义只说结果，不说先后**。结果是确定的，由两件事保证：体不写共享状态；汇合方式与顺序无关。
- **检查复用提交规则**：提交本来就要求"冲突的访问有先后"，`EACH` 的各轮之间没有先后，所以体里一旦写共享资源，提交就拒绝，不另立规则。原则 3.6 要求元素函数是纯的，这一条随之满足。
- **故障**按原则 3.6 已定的规则处理：报下标最小的那个故障，所有后端一致。

## 各后端怎样调度

| 后端 | 调度方式 |
|---|---|
| `nvm` | 下标从 0 走到 n−1，每轮执行一次体区域 |
| `fvm` | 字节码生成时把体区域降成一个字节码循环，体内联 |
| `jit` | 编译这同一个循环 |
| `prl` | 按原则 3.6 的粒度把下标范围切块并发；它认的是节点种类与汇合方式，不是名字 |
| `std::cpp` | 翻译成一个 `for` |
| GPU 与 ONNX | 体是逐元素运算时提升成张量运算，否则用 ONNX 的 `Loop` |

没有哪个算子去调后端，也没有哪个算子内核里写循环。

## 删掉的

- 四个标记算子：`:mark/map_arr`、`:mark/filter_arr`、`:mark/reduce_arr`、`:mark/foreach_arr`。
- 它们在每个后端里的内核：`fvm` 的元素调用、`callElement`，`prl` 的 `mark_map_arr`，`nvm` 与 `jit` 各自的对应实现。
- 求导、融合、批处理里为这几个标记算子单写的规则，改由 `EACH` 上的结构规则代替。

`prelude.cml` 里的 `map`、`filter`、`zip` 与推导式改成构造 `EACH`。`map`、`filter` 的元素函数补上 `pure`，与原则 3.6 一致。带效应、按顺序执行的 `foreach` 归 `LOOP`。

## 施工顺序

每一步单独成一笔，每一笔都有读数。

1. **节点与体区域**：图模型、编码与 `std::jgir` 规范形；提交检查把各轮当作没有先后。用例：体里写共享资源被拒，带位置。
2. **`nvm` 执行**：三种汇合方式各一条用例，故障报下标最小的那个。
3. **`fvm` 与 `jit`**：字节码生成把 `EACH` 降成循环。判据：输出与 `nvm` 逐字节相同；在工作站净场窗口量每元素耗时，`fvm` 与 `nvm` 同一量级，`jit` 更快。
4. **`prl`**：按节点切块并发。判据：输出与 `nvm` 逐字节相同；`binary-trees` 一类有并行加速；`git grep mark_map_arr` 零命中。
5. **库与推导式**：改成构造 `EACH`，删掉四个标记算子及其内核。判据：`git grep ':mark/map_arr\|:mark/filter_arr\|:mark/reduce_arr'` 零命中；整层新增红为空。
6. **变换**：`EACH` 上的求导结构规则（反向是对体求反向的 `EACH`，再把共享输入的余切归约起来），以及 `EACH` 套 `EACH` 的融合（用 Camel 写成一个遍）。判据：与 `with_grad` 数值一致；融合前后输出相同。

## 待负责人定

- **`reduce` 的语义**：今天的 `reduce` 是从左到右折叠，归 `LOOP`。要并行归约，运算必须满足结合律。推荐拆成两个名字：`fold` 顺序折叠，归 `LOOP`；`reduce` 要求运算声明满足结合律，归 `EACH`。也可以不拆名字，在元素函数上加 `assoc` 声明。定之前，第 1 到 5 步只做 `map` 与 `filter`，`reduce` 维持现状。
- **体里有效应、但不在乎顺序的写法**（`unordered_map` 一类）：先不支持。效应照旧按顺序执行，归 `LOOP`。
