# 锁：要紧的互斥一律由锁保证，约定不算保证

一条只写在说明里的"不许并行"，忘了就没人拦；锁拦得住，而且读数里看得见。所以凡是"同时做会出错"的事，都由锁保证；锁给不了的，就在读数里写明当时的情形，而不是靠约定假装它没发生。

## 现有的锁（保留）

| 锁 | 机制 | 保证什么 |
|---|---|---|
| 状态文件 | 工作站上的 Windows 命名互斥量（`Global\CamelBuildState` 等） | 读-改-写不丢更新；崩溃时 `AbandonedMutexException` 照常释放 |
| 令牌池 | 构建机上的令牌池（`host-tokens.sh`，默认 24） | 我们在构建机上同时起的工作进程（测试用例、编译单元、clang 检查单元）不超过池的大小；构建与测试取同一个池，没有固定的构建槽与测试槽（见"改为按进程发令牌"） |
| 树锁 | 主机 `flock -n /tmp/camel-tree-<key>.lock` | 清扫拿不到锁就不删这棵树（11-17 三次删掉正在测的检出就是这里修的） |
| 通道目标 | 插件的 `oversight_claim` | 派工只投给一个会话 |
| 插件的量 | 插件内 `beating` 标志 | 两次量不重叠 |

flock 挂在文件描述符上，进程一死就释放，不会有陈旧锁。

## "同一台主机远程跑一律串行"这条约定：撤掉，换成锁与读数

它的来由是 11-22 的清扫竞态（两条并行跑，一条的读数删掉了另一条正在用的检出）。那个竞态已由树锁修掉。剩下的真实风险只有一个：**并行负载污染读数**——主机负载常在 15–42，两条一起跑时，谁也说不清一条红是不是自己的。分两类处理：

1. **构建也从令牌池取。** 原先的两个固定构建槽让 8 条车道加合并位同时只有两个在构建，其余排队；改为构建把令牌池交给 ninja，有空令牌就能开工。
2. **每份读数写明它是怎么跑的。** 运行登记（`run-registry.jsonl`）补上：拿到的是第几个槽（主机脚本拿到锁后报出槽号），计划开始与结束时主机上同时在跑的其他运行（runId、阶段），以及开始、结束时的负载。于是"两条并行、各自红"与"两条串行、一条红"在读数里分得开。
3. **构建机不跑性能测试，也不为它独占（负责人 2026-11-26）。** 构建机只管对错；性能读数在工作站上由后端提速车道量（`2026-11-25-backend-speed.cn.md`），交稿前另做干净测量。所以构建机上不跑 `perf/**`，带耗时预算的用例只判结果、不判耗时，没有任何运行独占构建机。独占的代码路径、为它保留的旧锁与"时间敏感"的读法一并删掉；计划文件里"时间敏感"那个字段若再无读者，也删。

   推而广之（负责人同日）：耗时长的、或者只为测耗时的测试，构建机上能不跑就不跑。
   - 只为测耗时的用例（唯一的判定就是耗时）归后端提速车道，在工作站上跑，构建机上不跑。
   - 耗时长的用例按实测归入慢层：拿最近一次整层快层的逐条耗时排序，定一个门槛（例如构建机上超过 10 秒），超过的标为慢层；门槛和它省下的时间写进合并说明，按实测，不按名单。
   - 慢层不在车道、合并位和晋级的运行里跑。它每天在收工时的 GitHub Actions 那一轮里跑一次；Actions 跑不了的（要 GPU 或要构建机资源的），只在构建机空闲时跑，和 GPU 测试一样。

## 槽限的是运行个数，还要限每个运行的进程数

槽位只保证"同时几个运行"，不管"一个运行里开多少进程"：两个构建槽各带 `-Jobs 8`，测试槽里的计划再开自己的并行，三个合法占用就能推出 150 多个进程（11-23 夜量到负载 88/32）。每条车道只看到"我这次跑得慢"，以为是自己的改动慢，原因却在别人的槽上。

（这一段按槽算预算，已由下一节改为按进程发令牌；留在这里是因为它量到的那个数——三个合法占用推出 150 多个进程——是下面这个池子的来由。）所以每个槽有固定的进程预算，由主机脚本按槽号设定，调用方传的 `-Jobs` 只能往下压、不能往上抬：构建槽各 8、测试槽 16，合计等于核数（32）；独占主机的时间敏感运行拿全部 32。运行登记记下预算（`jobs`），面板与插件据此判断负载是否在预算内。负载持续超过核数的 1.5 倍时插件提醒，说明有运行绕过了槽或预算。"负载高就手动降 `-Jobs`"这种约定撤掉。

## 改为按进程发令牌（负责人 2026-11-24，取代上一节的按槽预算）

按运行计数的槽有两个毛病：一个测试运行不管实际用几个核都占满整个测试槽，跑到只剩一个长用例的尾巴时，整台机器的测试配额被一个进程锁着；绕过槽的运行（车道里直接跑的测试、`merge-lane` 自己开的 clang 进程）不受任何限制，11-24 我们自己的进程到过 84 个。

改成 make/ninja 的 jobserver 那种令牌池：

- **构建机上一个令牌池**，大小可配（默认 24，32 核给同机别人的程序留余量）。
- **每启动一个工作进程先取一个令牌，结束就还**：一个测试用例、一个编译单元、一个 clang 语法检查单元都算一个。跑测工具按用例取；构建把令牌池交给 ninja（ninja 支持 jobserver 客户端协议），cmake 构建与 clang 语法检查走同一个池。
- **"一次只能一个测试运行"取消**：并发总量由令牌池管，几个运行同时跑也不会超；一个运行跑到尾巴只占它还在用的那几个令牌，其余自动还回去。
- **取不到令牌就排队**，读数里打印"在等令牌、池里谁占着几个"；不许"等一会儿取不到就先跑"。
- **崩掉的运行不能把令牌带走**：令牌随进程退出自动归还（用文件锁或 FIFO 读写这类进程一死就释放的机制），或者有一条按记录回收的规则（持有者进程不在了就收回）。
- **没有独占**：构建机不跑性能测试（见上文第 3 条），任何运行都只按它启动的进程取令牌。

### 取锁的代码只有一份（11-24 三个测试槽没生效的教训）

每个工作树跑的是自己那份 `camel-remote.ps1`，它现场生成主机上的 `run.sh`。所以改了取锁方式的那一笔只对它自己的工作树生效：11-24 开出三个测试槽后，合并位的工作树还是旧版，照样排在旧的单锁上，新锁文件一次都没人用过。更糟的是，新旧两种取锁方式同时在用时，它们彼此不互斥，锁等于没有。令牌池上线会撞上同一件事：旧工作树起的运行不取令牌，池子管不住。

所以取锁、取令牌、写登记这几件放在主机上的一个固定脚本里（例如 `~/camel-work/bin/camel-run`，由一个跟踪 `origin/integration` 的检出安装，和监督插件的活目录一个做法），各工作树生成的 `run.sh` 只调用它，不再各带一份。改取锁方式的那条车道要测自己的版本时显式指定，读数里写明。验收：所有工作树起的运行在主机上走的是同一个脚本（登记里记脚本的版本号），换一次脚本对之后所有运行立即生效。

### 面板跟着改（负责人 2026-11-24 问：改成令牌池后泳道图还能看吗）

负责人看的是 panel-deck 的 Camel 面板（不在本仓库）。它的时间轴已经以运行登记 `run-registry.jsonl` 为主：按 runId 取最后一行，一行是"某个工作树在某台机器上"，构建和测试各一组泳道；两个状态文件只作兜底、历史与摘要卡。所以泳道图在令牌池下照样成立，要改的是登记里的几个字段和面板上几处含义，不是重写面板。

**登记（本仓库，`camel-remote.ps1`）**
- **字段向后兼容**：已有字段的含义不变。`queuedAt` 改为"开始等令牌"的时刻，于是面板现有的"排队"那一段直接变成"等令牌"，不用改面板。
- **新增** `tokens`（此刻持有的令牌数）、`tokensPeak`（这次运行的峰值）、`pool`（写这行时池子的 `{size, inUse}`）。
- **补心跳**：现在登记只在阶段变化时写，一个长计划跑半小时可以一行不写；面板"5 分钟没有新快照就当作已死"会把活着的运行画成不在跑（11-24 opertarget 的登记 35 分钟没动，进程一直在起用例）。运行活着时至少每 60 秒写一行，令牌数变化时也写（至多每 10 秒一次）。
- **本地构建也写登记**，这样面板不再需要状态文件兜底。

**面板（panel-deck，几处小改）**
- 测试泳道不再表示"谁持有测试锁"（令牌池下没有这把锁），而是"每个工作树的测试运行"；几个运行同时跑本来就各占一行，段上标出持有的令牌数。
- 表头的"主机 · 2 构建中 · 1 排队"加上"令牌 18/24"。
- 可选：顶上一条令牌占用的堆叠带，按车道分色。
- 摘要卡与历史改从登记取：登记按 runId 保留每个运行的关键时间戳，`recent[]` 能给的它都有。

**状态文件**：面板不再读 `build-state.json` / `test-state.json` 之后，再删它们的写入；在那之前照写，面板不会有一段瞎掉。

验收：同时起两个测试运行和一个构建，`ps` 里我们的工作进程数不超过令牌池大小；一个运行只剩一个长用例时，另一个运行能拿到其余令牌并跑起来；杀掉一个运行，它的令牌在一分钟内回到池里；读数里每次运行打印取到与归还的令牌数；登记里三个运行的 tokens 之和等于主机上实际持有的锁文件数，一个运行在跑长用例时登记仍每分钟有新行。

## 补一把锁：develop 只有一个写入者

现在"develop 只由合并位推"也是约定。改成钩子：仓库提供 `scripts/hooks/pre-push`，所有车道工作树安装它；推往 `refs/heads/develop` 时，只有合并位的工作树（路径写在 `camel-gate.local.json` 的 `mergeWorktree`）放行，其余拒绝并说明原因。

## 验收

- `agents/dispatch.md` 里"一律串行"那条删掉，换成"进程数由令牌池决定、计划一槽、读数带宽度与并行情况"。
- 运行登记每行有 `buildJobs`、`testSlot`、`overlapping`、`loadAtStart`、`loadAtEnd`；两处不同的原因看得见：`buildJobs` 是构建实际拿到的令牌数，`jobsRequested` 是命令行写的那个。
- 同时起三个运行（两个测试、一个构建）时，主机上我们的工作进程数不超过池子大小（`ps -e -o comm= | grep -c camel` 一类，池子大小写在 `host-tokens.sh show` 里）。
- 没有"等构建槽"这回事：日志里不再出现 `waiting for a host build slot`，构建启动时直接报它拿到的宽度。
- 在非合并位的工作树 `git push origin develop` 被钩子拒绝；合并位照常。
