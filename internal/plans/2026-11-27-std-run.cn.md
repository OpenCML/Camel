# `std::run`：运行这一步的名字

负责人 2026-11-27 定：加一个调度阶段的别名 `std::run`，意思是"运行这个程序"，只在不关心哪个后端时写它；目标默认是 `std::fastvm`，可以配置。原则第 9 节（遍、默认流水线两处）已改成：写下的遍跑完、图还没变空时交给 `std::run`。

为什么：读者不需要先认识后端清单，才能读懂"编译、改写、运行"这条流水线。`std::fvm`、`std::nvm` 这些名字留给后端本身就是重点的地方。

## 要做的

1. **`std::run` 是一个别名，目标可以配置。** `.opencmlrc` 加一项（建议 `passes.run`），值是一个调度遍的名字，默认 `std::fastvm`。别名的目标在解析流水线时读配置，与其他别名同一处解析；不另建一张表。给的目标不是调度遍时，与未知遍同样在开跑前报 `UnrecognizedGraphPass` 一类的诊断，并说明是 `passes.run` 的值。
2. **默认的最后一步是 `std::run`。** `passes.fallback` 不配置时的默认值从 `std::default` 改成 `std::run`；一个遍都没写时跑的也是它。
3. **`std::default` 删掉**，不留别名、不留指向新名的诊断（不计兼容）。仓库里所有出现处一起改：docs（cli.md 第 169、342 行一带，cli.cn.md，language/04，technical/04、44，tutorial/17 两份及其渲染脚本，design/cli），scripts（camel-pass-pipelines、camel-pass-scan），src（pass.cpp 别名表、sched.h 注释、camel-cli 的 config 与 opencmlrc、debugger server 的注释），以及测试里的用例与期望。
4. **默认后端从 `std::nvm` 换成 `std::fvm` 的影响要量**：没写遍的用例从今以后由 `std::fvm` 跑。在尖端上跑一遍快层，新增的红逐条分两类：
   - `std::fvm` 与 `std::nvm` 答得不一样：这是 `std::fvm` 的缺陷（`std::nvm` 是参考语义），单列报决策者，不改期望；
   - 用例测的本来就是参考语义、只是没写遍：在用例里显式写 `std::nvm`，提交说明逐条写理由。
5. **文档**：docs/cli.md 的别名一段写 `std::run` 及其配置项；`passes.fallback` 一段写默认值；`.opencmlrc` 的说明写新项。

## 验收

- `camel f.cml` 与 `camel f.cml std::run` 都由 `std::fvm` 跑（看 `--dump-after-each-pass` 或运行记录里的阶段名）；`.opencmlrc` 设 `passes.run = "std::nvm"` 后都由 `std::nvm` 跑；设成一个转译遍时开跑前报错并点名配置项。
- `git grep 'std::default'` 在仓库里没有结果（历史记录与日志文件除外）。
- 快层在尖端上对上次晋级零新增红；第 4 条里第一类缺陷单列，不算进"改期望"。
