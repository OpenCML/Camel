# 合并排队：集成分支、多个合并位并行、develop 定期前进

负责人 2026-11-24：合并位是瓶颈，要解决；待合分支多时多开几个合并分支、归并着合；develop 稍有落后没关系。

## 为什么慢（11-24 的读数）

- 每两小时进 develop 的合并：0–2 点 12、2–4 点 5、4–6 点 1、6–12 点每两小时 4–5、12 点后接近 0。已交回的车道等合要几个小时；未合分支堆过 20 条，分支闸门于是禁止开新车道。
- 每条合并测两遍（基线、合并后），碰内核的一遍十几分钟；只有一个合并位、一个测试槽，构建机还被别人的程序占着（负载 60–70，32 核）。
- 合并位的工作树把 `develop` 检出着，负责人在主检出里切不回 `develop`（git 不许同一分支两处检出）。

## 分支

| 分支 | 谁写 | 前进方式 |
|---|---|---|
| `develop` | 负责人可直接写；智能体只在"晋级"时快进 | 定期从 `integration` 快进，前进的每一版都过了全快层 |
| `integration` | 只有集成步骤一个写者 | 合并位的结果按顺序并入 |
| `seat/merge-<n>` | 各合并位自己的私有分支 | 合并位在上面合车道、过闸 |

智能体的工作树都不检出 `develop`。车道从 `integration` 的尖端出发（比 develop 新，冲突少）。

## 流程

1. **车道交回** → 进合并队列（一个文件，每项：车道、提交、改动文件集、`--changed` 选出的计划集）。
2. **分给合并位**：队列短时一个合并位；排着的多（比如超过 4 项）就开到 2–3 个。分法：改动文件与选出的计划都不相交的，分到不同合并位并行；相干的放进同一个合并位，按顺序合。
3. **合并位**：从 `integration` 尖端出发，把分到的车道依次合进 `seat/merge-<n>`，按精确选测试的结果过闸（基线在 `integration` 尖端上测，按尖端与用例缓存）。结论行写明 `pushed` 与原因，"测过且绿"和"已经落地"分开写。
4. **集成**（一个写者）：按顺序把各合并位的结果并入 `integration`。合并位的起点就是当前尖端的，快进；不是的，看 `integration` 上多出来的提交是否选得中本合并位的计划——选不中就复用读数并在通过记录里写明理由，选得中就在合起来的树上只重测两边碰到的计划。合起来红了，在合并位一级二分，退回那一位。
5. **晋级**：每一两个小时，或 `integration` 上攒了几条车道，在它的尖端把快层全跑一遍，与上一次晋级时的读数逐条比，没有新红、没有换红，就把 `develop` 快进过去。这一遍兼作每天的全量与"develop 上有哪些红"那张表的更新。
6. **负责人直接写进 `develop` 的提交**（如发版后的版本号）：集成步骤先把 `origin/develop` 合进 `integration`，再接着并。
7. **文档、backlog**：照样走 `integration`，"只多文档提交就复用读数"。

## 算力

- 测试槽改成 3 个（两个合并位 + 晋级），按槽重分进程预算，合计不超过核数；构建槽照旧两个。读数里记下当时同时在跑的槽与主机负载。
- 计时类的测量只在独占主机时跑（锁计划已有）。

## 插件

- 分支闸门数的是"还没进 `integration` 的车道分支"；`integration` 与 `seat/` 下的分支不算车道。
- "develop 多久没前进"换成两条：`integration` 多久没前进（合并位卡住）、离上一次晋级多久（晋级卡住）。
- 热加载仍只读 `origin/develop`：插件只载入晋级过的版本。

## 谁来做

合并位、集成与晋级都是常驻子代理（铁律 3）；集成与晋级是同一个，因为两件事都是单一写者。协调者只往队列放车道、读结论、处理被拒的。

## 第一步（现在）

合并位的工作树改到私有分支 `seat/merge`（已在做，`D-1124-19`），推送用 `git push origin HEAD:develop`；这一步让负责人能在主检出里切回 `develop`。再按上面的分支与流程搭 `integration`，原来直接推 `develop` 的改成推 `integration`。

## 验收

- 队列里同时有几项互不相干的车道：两三个合并位并行测，全部进了 `integration`，总用时与串行对比。
- 两项相干（造一对改同一文件的探针车道）：进同一个合并位、按顺序合；让前一项故意红，后一项不会被带进 `integration`。
- 晋级：`develop` 每次前进前都有一份全快层读数，与上一次逐条比过。
- 一天下来报：已交回到进 `integration` 的中位等待时间、`integration` 每两小时前进几次、`develop` 晋级几次。

## 晋级由空闲的合并位做

晋级不需要一个专门的人：`integration` 前进之后，**空闲的那个合并位**接这一笔。它有 3 号槽的使用权，也已经有热的工作树，所以它做的只是「合一次 `develop` 尖端、跑一次整层快层、比红表、够了就推」。

- **触发**：`integration` 前进之后，或距上次晋级三小时，先到者为准。
- **谁做**：三个合并位里当时空闲的那一个；两个都在跑时，谁先空谁做。
- **失败就停**：新增红不为 0 时**不推**，报红的用例名与失败的第一条期望，然后停——晋级失败比晋级错了好。
- **报一行**：`promoted <sha> | fast: <N> cases, <pass>/<fail> | new reds: <n> | slot 3 | queue <秒>`。
- **文档不再推 `develop`**：有了 `integration` 之后，backlog、问题页、计划页一律推 `integration`，`develop` 只由晋级快进；推前核 `git rev-list origin/integration..HEAD` 里只有文档提交。

**第 3 步的两条逐字命令**：

```powershell
git push origin origin/integration:refs/heads/develop
git ls-remote origin refs/heads/develop
```

第 1 条把 `integration` 快进到 `develop`（不带任何新提交）；第 2 条是核对，输出里 `refs/heads/develop` 的 sha 必须等于 `integration` 的 sha，否则这次晋级没有落。

**为什么要比红表而不是只看红数**：整层跑一次会带上上游所有改动（判据修正、唤醒、收尾规矩），那些改动第一次被整层跑时，红的位置会动；只看红数会把「换了一条红」读成「没有新增红」。
