不够走完"改 → 重建 → 量四组 → 量闭包/捕获"，所以按你的规则停在干净树上，把方案写在这里。

## 为什么是"改一个判定的输入"，不是"造节点"

`if c then { x = 1 }` 现在走 `joinsNoValue` 这条路（`builder_control.cpp:2621`），于是
`addArm` 把 `joinType` 定成 `void`（`:2643-2649`），合并点不选值。而**带值分支**那一套
（A、D 两个程序证明正确）就在同一个函数里：只要 `joinsNoValue` 为假、`absentElse` 为假，
`addArm` 就会给每条臂建 GATE、把臂的值链进合并点、并按臂的值定 `joinType`。

所以 ②a 的做法是**在分支开始建之前，把这个语句形分支判定成值分支**：

1. **预扫描**（在建臂之前，`builder_control.cpp:2608-2621` 一带）：看这个 `if` 的 then 臂里
   是否有且只有一条对**外层 `var`** 的赋值语句，且该 `var` 不在 `escapingVariables_` 里、
   不是 `var` 形参、分支之后还会被读。满足则 `dropsArmValues = false`、
   `branchTakesNoValue(gct)` 对这条路径返回 false——即按值分支建。
   两条臂都写的情形**不做**（`x = if c then a else b` 留到下一笔）。
2. **缺席 else 的槽**：值分支没有 else 时那条臂给 `null`，用上一轮那段已写好的逻辑把
   槽 1 换成"分支之前的版本"（`valueVersionOf` 的第二操作数，或单元的 `:var/new` 输入），
   并把 `joinType` 定为该值的类型。
3. **版本**：`mergeArmVariables` 之后 `setModifier(variable, joinNode)`（上一轮那条，
   `[DBG-H]/[DBG-I]` 证明必要）。
4. **折叠**：承认"版本来源是值合并点"（上一轮那段，已写好）。
5. **逃逸**：只对满足第 1 条窄条件的 `var` 不记逃逸——在 `requireMutableArgument` 之外，
   由分支建图时对那一个变量做 `escapingVariables_.erase`（窄、局部、可解释），
   而不是对所有赋值算子放开（那样会带坏 `q2`，上一轮已验证）。

## 这一轮为什么停手

第 1 条的预扫描要读 GCT 的臂体、要判断"分支之后还会被读"（后者可以在折叠阶段兜底：若没人读，

这四处一改，必须至少两轮 build+量 才能确认，而一轮 build 加四组量加闭包计划约 5–8 分钟、
两个来回就超出我这一轮的预算。**留下一棵全绿的树 + 一份能一次改完的方案，比留下半棵树好。**
