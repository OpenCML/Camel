# 那一行单独落地会改语义：直线情形成功，分支情形把写丢了

日期 2026-11-15。分支 `lane-varscope`，基线 `749748d7d`。**改动已撤回**，`src/` 与基线逐字节相同。

## 落地的那一行（撤回前）

`builder_operators.cpp` 里 `requireMutableArgument(arg, calleeLabel)` 外面加了一个例外：
调用方是赋值算子（`targetOperator->uri()` 以 `:op/assn` 开头）时不记逃逸。依据是赋值算子本身就是
"写"，调用返回后它不存在，不能把单元带走。

## 直线情形：成功（"免费的 SSA"确实存在）

`q3`（`var x = 0; x = 1; println(x)`，无分支无循环）：

```
:var/get 计数 = 0
N03 [label="1"]                  ← 字面量 1
N03 -> N05 [1|0 NORM]            ← println 直接吃写进去的那个值
N02 :var/new  N04 :op/assn_l     ← 单元与写还在（写留在时间线上），但已经没人读单元了
```

输出 `1`，与改前一致。**直线情形的 SSA 是由原有折叠免费得到的，不需要新代码。**

## 分支情形：语义被改坏了

`q1`（`var x = 0; if c then { x = 1 }; println(x)`）在同一个 build 下：

```
:var/get 计数 = 0                       （改前是 1）
nvm true=0  false=0                      （改前是 1 / 0）
fvm true=0  false=0
jit true=0  false=0
prl true=0  false=0
```

四个后端一致地**把分支里的写丢了**：读折叠成了分支之前的值（0），而不是合并点的值。
原因是那个读的版本来源是合并点，而折叠对"来源不是赋值算子"的处理在这条路径上退回到
"单元造出来时的值"，于是 `1` 丢了。

## 结论（这是这一轮真正买到的东西）

**这一行不能单独落地。** 放开逃逸判定后，直线情形自动变对，但分支情形的读会被折叠成错的值；
所以它必须与 ②a 的值合并点**同一个提交**落地——先把合并点做成带值的、让折叠承认合并点为版本
来源，再放开逃逸判定。顺序反过来就会出现"中间的树能编译、测试也绿，但 `q1` 打印 0 0"的状态，
那正是你说的"第 2 项被提前做了一半"的样子。
