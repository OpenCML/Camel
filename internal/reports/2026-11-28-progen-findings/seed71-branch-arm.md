# Finding: an `:op/copy` runs between a BRCH and its JOIN and belongs to both arms

`23b0204cf9` (`lane/progen`) · build host `zjwei@camel-work` ·
`[load]` 39.50 → 32.43 (1m) during these runs · 2026-11-28 ·
**program legal, front end accepts it, the runtime graph breaks the branch-arm invariant.**

- **Seed**: `71`, default feature set, `generate.VERSION` 9.
- **Where it fails** (the compiler's own check, not a pass): runtime graph `main`, reported as
  `InternalDiag::UnknownInternalError` at `1:1` (the invariant is not located in the source).
- **Rule**: the branch-arm invariant, `docs/technical/17_graph_rewrite_api_contracts.md` 4.1 — "a
  node between a BRCH and its JOIN belongs to exactly one arm". Checked by
  `validateRuntimeBranchArms` (`src/kernel/runtime/branch_arms.cpp:99`), which fails at
  `src/kernel/runtime/branch_arms.cpp:358-370` (the site that computes `ownArm` and `theirArm` and
  finds them different); the message is built at `src/kernel/runtime/branch_arms.cpp:88-95`.
- **Outcome**: `RUN_ERROR` on **every** one of the seven stage prefixes measured
  (`none`, `macro`, `inline`, `fold`, `cse`, `algebra`, `dce`, each ending `std::nvm`): the graph is
  already wrong when it is first committed, so no pass is implicated.

## The diagnostic, verbatim

```
InternalDiag::UnknownInternalError at 1:1 | An error has occurred: Runtime graph 'main' breaks the branch-arm invariant: OPER 82 (:op/access) runs between BRCH 28 and its JOIN 27 and belongs to two arms, 0 and 1: it would run only when arm 0 is taken, and arm 1 reads it (see docs/technical/17_graph_rewrite_api_contracts.md, 4.1).
```

`OPER 82` is the node the check reports for this program; the eleven-line reduction below reports
`OPER 4 (:op/copy)` in the same position, so **the report names whichever operator happens to sit on
the offending edge**, and the defect is not specific to `:op/access` or `:op/copy`.

## The program, verbatim (11 lines, the reducer's output)

Shrunk by `test/tools/progen/reduce.py` until no single further removal reproduced the same
signature. It needs nothing: one function, no import, no stdlib call.

```
func main() sync {

        var v50 = false;
        v50 = false && v50;
        null;
    } else sync {
        println('');
        null;

    let n64 = 0;
}
```

## Reading

- **The program is legal.** `main` declares no return value; each arm is a `sync` block whose last
  expression is `null`, so both arms give nothing (design principles 3.7: an arm needs no value);
  `var v50` is written inside its own arm; `let n64 = 0` after the `if` statement is unused and
  legal.
- **The engine says its own store is broken.** This is the store's self-check at commit
  (`src/kernel/runtime/graph_build.h:201`), not a back end declining to run something.
- **The shape that triggers it is a branch with two effectful arms, where one arm owns a `var`
  cell.** The copy of the cell value is placed between the BRCH and the JOIN (so both arms' reads
  can reach it) while the region of the arm it was written in says it belongs to that arm only.
  Whichever of the two positions the builder intended, the graph as committed contradicts itself:
  the checked property is "exactly one", and the reported node has two.
- **The `true` condition does not matter.** Folding `if true` away would remove the BRCH; the defect
  is in how the two-arm graph was built, which is why it is reported at the invariant and not as an
  optimization result. (Whether a folding pass would hide it is irrelevant to the defect: it fails
  with no pass at all.)
- **Nothing in the generator asks for this shape.** `var` in a sync arm, an `&&` reading it, and a
  `println` in the other arm are ordinary productions; the same shape is generated by many seeds
  that pass, so the difference is not a construct but a placement.
- **What is not claimed here.** Which builder step puts the copy on the wrong side of the region
  boundary is **not** determined. The eleven lines above are the unit to bisect on; the owner's next
  step is the GIR builder's arm-region assignment (`src/compile/src/gir/builder_variables.cpp:267`
  draws the same boundary for loops) and whatever copies an owned cell across it.
