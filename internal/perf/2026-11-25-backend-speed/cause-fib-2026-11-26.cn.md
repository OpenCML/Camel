# `fib(30)` 的 nvm / fvm 为什么从 ~50 ms 变成 ~155 ms

> 一页查因记录，不含任何 `src/` 改动（`git status` 干净）。量法只有两样，都是这条车道已有的：
> `camel --output-format json --timeit std::<be>/<N> <prog>`，以及 `load-gate.ps1 -Seconds 60 -Step 4`
> （28 核 × 15% = 4.2 busy cores，60 s 内 15 个采样一个都不许达到）。

**结论三句：**

1. **不是机器、不是量具、不是程序**：把 2026-10-20 的提交 `e8abfc30` 今天在本机重建，量到的三个数
   与基线页当时的记录差 ≤8%。
2. **不是一笔退化，是两段台阶 + 一段持续的缓涨**：`10-26 03:56 → 04:00` 的**一笔**（fvm 48.6 → 101，×2.1）、
   `11-17 → 11-23` 的一组合并（113 → 164，×1.45）、以及 nvm 在 11-23 之后继续涨到 880。
3. **慢在「执行每一个字节码/结点」这一层**：帧建立、调用绑定、GC、程序形状、某一台 VM 的循环，逐条都被读数排除；
   `std::stats` 在快端与慢端**逐字段相同**（27 结点 / 33 边 / 1112 字节），同一张图今天 fvm 要跑两倍的时间。
   再往下一行（哪个 opcode）这一页**没有钉到**——本机没有可用剖面（见 §6），不编。

## 0. 「~50 ms」是哪个程序

`docs/technical/07_jit_architecture.md` §11.1 的「纯解释器 (`std::fvm`) ~50ms」与
`docs/performance/graph-store-baseline.md`（2026-10-20，同一台机器）里 `fib.deep` 的 **fvm 55.8 ms**
指的是**同一个程序**：`test/cases/perf/fib_recursive.cml`（`let idx = 30`，外面套 `now()` / `format` / `println`）。

`benchmarks/parallel/cases/fib.cml` 是另一个文件（只打印、无计时外壳）。今天两者同值
（fvm 155.2 vs 154.5，§1），所以「~50 ms」指哪一个都不改变结论；页内所有梯子用 `fib_recursive.cml`。

**jit 是反方向的**：`fib(30)` 的 jit 从 84.7 ms（10-20）变成 4.9 ms（今天），×0.06 ——
这是双入口 + rbx/r12 寄存器缓存那笔的收益。所以本页写的是「两个解释器退步、JIT 大幅进步」，
不是「整体退步」。

## 4. 二分区间（端点都是今天量的，不是翻历史）

判据线画在 **75 ms**（快端 48–57，慢端 97–118，两端各留 ~50% 余量）。

- **区间一**：`d078264af8 … 06bb6a2e53`，即 **2026-10-26 03:56 → 04:00**（4 分钟、1 个提交）。
  这一笔是合并/落地提交 `06bb6a2e53`（"P4 lands on develop: the tensor alias becomes the array,
  the module's slice kernel and its by-whose-array dispatch go, the stdlib signature region writes

## 6. 结论：慢在哪一步

**慢在「执行一个字节码位」这一层；不在帧建立、不在调用绑定、不在 GC、不在程序形状、不在某一台 VM 独有的循环。**

三个后端的同一张图的对照把范围压到这一层：`std::cpp` 2.85 ms、`std::jit` 4.9 ms、`std::fvm` 154.5 ms、
`std::nvm` 880 ms。前两者把结点「编译掉」了，后两者每执行一个结点都要付一次固定成本；
**这个固定成本在 2026-10-26 04:00 的 `06bb6a2e53` 里翻了一倍**（fvm 48.6 → 101，图逐字段不变），
又在 11-17 → 11-23 涨了 45%，nvm 还多涨了一次到 835–880。

**没有钉到的那一层**（写清楚，不补）：那一笔提交里到底是「操作数取用变慢」「每个算子多做一次类型/转换检查」
还是「字节码的快速路径命中率掉了」，本页没有读数可指 —— `opperf` 在本机编不过，也没有采样剖面。
已知的约束是：**fvm ×2.08 而 nvm ×1.33**，同一笔提交里两者幅度相差 1.6 倍，
所以它不是「所有后端等幅变慢」的纯值层改动，更像「字节码/操作数这一层付得更多」。
