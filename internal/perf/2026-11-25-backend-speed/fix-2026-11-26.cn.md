**机器 `KOGLER-WORKSTATION`，28 逻辑核。本页每一条都是这台工作站上量的：不与 88 构建机的读数相比，也不与 `table.cn.md` 里 2026-11-25 那一轮的读数混在一张表里。**

这一笔只回答一件事：`small_calls`（2e6 次尾递归、每轮三次调用）在 `std::jit` 上为什么从 115 ms 掉到 1.7–2.5 s，改的是哪条路，改回多少。`fib(30)` 与其余 23 格作为「没有变差」的对照写进来。

## 根因（实测）

`std::jit` 的 framed code 每做一次调用都回到驱动 `runFramedJit`，而驱动在**每次调用**上读三次「这张版本的引擎状态」：

| 位置 | 读的是什么 | 一次读的代价 |
|---|---|---|
| `startCallee` 的 `jitFnOf(target)` | 被调者图的编译入口 | `execPlanOf`（事实存储取计划）+ 全局锁 + `unordered_map` |
| `startCallee` 的 `fastVmJitFramedOf(target)` | 那段代码是不是 framed | 同上，再来一次 |
| 返回路径的 `jitFnOf(caller->graph())` | 调用者图的编译入口 | 同上，第三次 |

`small_calls` 一轮 = 6e6 次这样的调用（2e6 × 3）。改前的读数 `1774.5 ms`（样本 2–5 的中位数）减掉改后的 `103.2 ms`，差 1671 ms / 6e6 ≈ **280 ns/次**。

`fib(30)` 的调用是自递归、编译成 native 调用、不经过驱动，所以那一格一直是 4.5–5.5 ms：**同一条 15 倍只出现在「每调用一次走一次计划查表」的路上**，两者不矛盾。

## 改法（三条边界）

1. **执行计划仍是事实存储里那一条不可变事实，没有另存一份计划**，也没有把计划的内容拷进引擎。`68f6844368` 把「引擎为这张版本做出来的东西」（字节码起止、JIT 入口、flags、调用计数）从计划移进了 `fastVmStateOf` 那张表；这一笔改的是**读它**的路。
2. 编译打补丁时就把「被调者的入口」与「这段代码是不是 framed」一起写进**调用点自己的 bytecode** 第四条额外字（第 63 位，捕获掩码之上），驱动每调用只做两次 plain load；返回路径把**调用者的入口**随 pc、resume 地址一起压进 `callerEntryStack_`，返回时直接取回。
3. 走「解释执行尾调用」到达的被调者手里没有调用点字节码，那条路照旧问版本状态：那是**一条这样到达的图**，不是调用的稳态。

`bytecode.h` 的改动对 fvm 的读法没有语义差：捕获掩码仍是 32 位并按 32 位取出，第 63 位只有 JIT 的补丁会写，无 JIT 的构建从不置它。

### 每个采样分别是谁（`first` 为什么高过 `steady`）

在同一进程内连跑 3 次、每次都是全新的图（所以每轮都要重新编译这三张图），一个进程的 5 次独立重复：

```
run 1 : 100.3 | 105.8 | 99.8      run 4 : 101.9 | 102.2 | 102.0
run 2 : 102.6 | 100.3 | 99.8      run 5 : 103.1 | 100.4 | 101.6
run 3 : 101.1 | 100.8 | 100.4
```

即 `first` 与第 2–3 次在本机是**同一量级**（那批 100.3–103.1 与 99.8–105.8）。上一轮里 `first 143.1` 的那种值是**冷进程的离群采样**（同一格后来 3 轮 24 格里 first 是 99.7–104.3），不是 codegen：`-vv` 的日志显示那三张图**每一轮都重新编译**（每轮三条 `compiled & cached graph`），编译成本落在**每一个**采样里，不是只落在第一个里。
