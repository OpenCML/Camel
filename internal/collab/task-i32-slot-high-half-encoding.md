# 卡：`i32` 结果写进槽时,高 32 位是"保留符号扩展"还是"清零"——两种编码都出现过,今天只有整字比较看得见

**发现者**：`lane-backend-speed`（修 nvm `==` 整字比较时顺带测出来），2026-11-28 07:5x。

## 事实（读数，不是推断）

同一份程序：`let a: i32 = -3; let z: i32 = 0;`
在 `__builtin__eq__` 的定义处打 gate（`ops.cpp:575`），`a` 与 `a + z` 两个 `i32` 落进 64 位槽后：

```
[CMP-GATE] eq type0=0 type1=0 lhs=0xfffffffffffffffd rhs=0x00000000fffffffd
```

- 两侧 `TypeCode` 都是 `Int32`（`type0/type1 = 0`），**值是同一个 `-3`**；
- 但**槽的高 32 位一个保留符号扩展、一个留零** ⇒ 同一份数值有两种编码。

## 这条编码差异今天在哪里可见

| 路径 | 读法 | 结果（修复后） |
|---|---|---|
| `==`（`comparePair` 的 `Int32`） | 已改为 `fromSlot<Int32>` 比那 32 位 | 一致 |
| `<` / `>` | 走 `norm.get<Int32>` 按 32 位读 | 一直一致 |
| 集合键（`Set<i32>` / `Map<i32,int>`）| `compareKeys` / `Table::equals` | **一致**：`[m, m + z] as Set<i32>` ⇒ `len = 1`；`[(m,1),(m+z,2)] as Map<i32,int>` ⇒ `len = 1`、`t[m] = 2`，三后端相同 |
| 任何"整字当值"的地方 | 读整 64 位 | **只有这里会被骗** |

⇒ **已经修好的那一处（整字比较）是唯一被证实的受害面**；集合键被实测排除了。

## 要问的是"规范",不是"再修一处"

`toSlot` 对小于槽宽的类型是"低字节保留、其余清零"（`rtdata/base.h:149-152`）；但 `i32` 结果从**更宽的路径**（算术、宽化再窄化）落回槽里时，会出现保留符号扩展的那种编码。两种都自洽，问题只在**有没有一条规范说"槽里小类型的无效位必须是什么"**：

1. 若有规范（比如"无效位一律清零"），那符号扩展那种编码就是**缺陷**，需要一处修（写槽时统一走 `toSlot`），并获得"三条整字读法都安全"的保证；
2. 若没有规范，则应**写进设计文档**："小类型在槽里的无效位不参与值，任何整字读法都是错的" —— 这样以后谁写整字比较都能查到。

## 边界

- 本卡**不是**紧急修复卡：比较已修、集合键已验、三后端已一致；
- **不许**为了"让编码统一"去改 `toSlot`/宽化路径而没有规范依据（那会动到每条算术路径）；
- 若决定改，必须给：`i32`/`bool` 的写槽读数（两种路径各一次）+ 三条整字读法（比较、集合键、哈希若存在）的三后端读数 + `feat/compile`/`feat/modules`/`feat/trans` 甲 0。
