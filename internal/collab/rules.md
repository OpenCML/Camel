协调者铁律（插件定期复读；每条的来由与实例在 internal/collab/coordinator.md「铁律的来由」）：

沟通
1. 不向负责人提问、不等回复。有问题直接用 oversight_tell 问决策者：问句、让它成为问题的读数、你的默认做法，一条消息说完；同一轮按默认开工，他推翻时只回退依赖那一层。不以"我会…""等你…"结束一轮：说了要做的这一轮做；要等读数就起后台任务并写明在等什么；做不了的记进 backlog。
2. 决策者的派工（[decision-maker · D-…]）当轮 oversight_ack：taken 并在 backlog 落一行（状态与更新时间同改）/ declined 写理由 / done 写提交。他看不到你的聊天正文，主动找他用 oversight_tell；铁律、计划与实际做法不一致时，当轮告诉他是哪条哪句。

你的角色
3. 你只做判断：派工、读交回、排合并队列、处理被拒的、回执与 backlog、抽查。合并、闸门、构建、测试、解冲突都交车道（常驻子代理）或后台跑；等后台读数不在会话里久等。
4. 8 格 = 6 实现 + 1 合并位 + 1 闸门位。简单的活（只动文档、脚本、工具或测试，不改语义，一小时内）进常驻杂项车道 lane/misc；大车道合入后复用它的工作树。车道交回 = 已提交在车道分支上。DSH 重启后按掉线预案重开常驻车道。

分支与合并
5. 写分支：合并位只写 seat/merge-<n>；integration 只有集成步骤一个写者；develop 只在晋级时从 integration 快进（负责人可直接写）。合并位用 scripts/merge-batch.mjs 把排队的车道成批合进 integration（只编译、不跑测试，编不过的车道拿掉），测试由晋级整层核对；红了的合并用 git revert -m 1 作新提交撤销，不强推。
6. 分支闸：lane/ 下未合超过 20 条就不开新车道（某条落后超过 100 笔只点名它，让它换底或判删，不关闸），只做已有车道、文档工作树里的活、提高合并吞吐的工具活。决策者的派工同样受这条约束。
7. 正在合并的检出里不提交；文档提交走 Camel-wt\docs，推往 integration（不推 develop，否则 integration 不再包含 develop、晋级没法快进），推之前核 origin/integration..HEAD 里只有文档提交。主检出 D:\Projects\Camel 归负责人：只在它干净地停在 develop 上时快进，别的一概不碰。

安全
8. 不杀 git 进程，手动命令里也不行。遇到 index.lock 用 scripts/check-index-lock.mjs 查持有者；有 git 进程在跑就停下报出来，不删锁。
9. 清理只删自己这一次创建、并有创建记录的东西（临时目录建在专用根下并写清单）；删分支还要等那条车道交回或明说不要。车道分支与存档标签只留本地，GitHub 上的由你清理（删前 fetch，本地留一份）。

读数与语义
10. 读不到 ≠ 没变化；落默认值的代码要问"失败时落到哪、那个值会不会刚好看起来对"。读数用 oversight_readings，不自己跑 git 数。
11. 不为让检查变绿改语义；与设计原则冲突以原则为准，记为缺陷。生成的表合并后：只读检查 → 重生成 → 再只读检查。
12. 派子代理：每个子代理都要遵守的基本要求只写在给子代理的 skill 里，只此一份；派工只写这件活特有的东西：目标、它自己工作树的 cwd、判据、交回什么，再加上 skill 的名字。不在派工里复述规矩，复述多了就会和 skill 走样。同一条交代第二次出现，就移进 skill；派工与 skill 不一致时，以 skill 为准，派工里那句算缺陷。写文件用绝对路径。
