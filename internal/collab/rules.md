协调者铁律（插件每小时复读一次；全文在 internal/collab/coordinator.md §0）：
1. 不向负责人提问、不等回复。问句只有一个出口：internal/questions/ 一页一问，带默认建议，同一轮按默认开工。
2. 决策者的派工带 [decision-maker · D-…] 前缀，当轮 oversight_ack（taken 并记进 backlog / declined 写理由 / done 写提交）；主动找他用 oversight_tell。他看不到你的聊天正文。
3. 8 格 = 6 实现 + 1 合并位 + 1 闸门位。develop 只有合并位写；合并不挡派工；合完就推，先推再测，不攒。
4. 分支闸：未合车道分支 > 20 或最落后 > 100 笔 ⇒ 停派新分支，转审计合并。判据看有没有未合内容，不看名字。
5. 会话只做判断；闸门、解冲突、长测试交车道或后台跑，不占住会话。
6. 读不到 ≠ 没变化；查不到就落默认值的代码，要问"失败时它落到哪、那个值会不会刚好看起来对"。
7. 不为让检查变绿而改语义；与设计原则冲突以原则为准，冲突记为缺陷。
8. 生成的表（问题页索引等）合并后先跑只读检查，再重生成，再跑一次只读。
9. 写文件一律绝对路径；派子代理传它自己的工作树 cwd。
10. 读数用 oversight_readings，不自己跑 git 数车道和分支。
11. 不许杀 git 进程，手动命令里也不许。git 正在写索引时被杀，索引会坏——比合并失败糟，
    而且坏得安静：下一次读到的是一份不是任何人的写法的索引。遇到 `index.lock`：
    跑 `node scripts/check-index-lock.mjs --root <检出>` 看谁持有、持了多久；是后台只读程序就等它，
    并查它为什么拿锁（git 面板的补丁是否被覆盖）。合并一律走 `internal/tools/merge-lane.ps1`，
    它只在「锁超过 120 秒**且**没有任何 git 进程」时才删锁；有 git 进程就停下报出来。
12. 清理只删**自己这一次创建**的东西。判据来自**创建时的记录**，不来自"看起来没人在用"——
    「看起来没人在用」不是一个读数，它是对没人读过的状态的猜测。别的东西再像垃圾也不删，报出来。
    两条实例：我删掉了一条仍在等 CI 结果的车道检出；一条车道删掉了 `~/camel-work/Camel.git`
    （配置里的共享 staging bare）。两次的判据都是"看起来没人用"，而两次都有使用者。
    机制在 `internal/tools/` 的清理脚本：宿主与工作站的临时检出、回放工作树、沙箱一律建在
    一个专用根下（`~/camel-work/tmp/<车道>-<时间>/`），创建时写一份清单；清理脚本只接受这个根下、
    清单里有的路径，根外一律拒绝并报出路径。
13. **交回 = 已提交在车道分支上。**「完成、未提交、等点名」不算交回。
    工作区里的改动没有任何记录保护：一次误清理、一次检出、一次重命名就没了，而且丢得安静。
    提交是记录，不是放行；合并位是否放行与这条无关。
    车道分支与存档标签**只留在本地，不推 GitHub**：GitHub 将公开，只放 develop、fsh-dev、release、
    main 与各人的开发分支。偶尔丢一条车道的活可以接受（负责人 2026-11-24）。
    GitHub 上的车道分支与存档标签由协调者自己清理，不用另请授权；删之前先 fetch，确认本地有一份。

14. **`merge-lane` 在某个检出里跑时，那个检出里不许提交任何东西。**
    `merge-lane` 的中间状态就是那个检出的 `HEAD`；在它上面提交，再推 `develop`，会把一笔**还没比对过**的合并
    顺带推上共享分支，而推的那一刻没有任何一步会失败。
    实例：`D-1123-115` 的 backlog 行提交在 `abed9ea896`（一笔正在被比对的合并）之上并推了 `develop`，
    `origin/develop` 于是带着一笔未验证的合并。
    **文档提交走一个只做文档的工作树**（`D:\Projects\Camel-wt\docs`，分支 `docs/coordinator`，基于 `origin/develop`）；
    推之前核 `git rev-list origin/develop..HEAD` 里**只有文档提交**——不是「看起来只有」。

15. **闸门红了不进共享分支；但红了的合并不靠强推去撤销。**
    强推 `develop` 会让每一条已经取到它的车道分支都带着一笔 `develop` 上不存在的合并。
    红了的合并用 `git revert -m 1 <合并提交>` 撤销，作为**新提交**经 `merge-lane` 推：记录完整，谁都不用重来。
    「撤销」也是一次合并，所以它同样要过闸门。
