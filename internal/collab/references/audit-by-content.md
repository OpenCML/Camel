# 按内容判"一条未合枝还有没有活"

闸门看"未合条数"，但条数不等于活。本手法回答：一条枝的改动，有多少字面内容已在 `integration` 尖上。
它比 `git cherry` 一列稳，也比"看枝名/看最后提交标题"稳——后者两次把已落地的枝当成没做的活。

作者：`lane-parked-rebase`（2026-11-28 20:4x 交回，正文由协调者落盘；判据与读数都是那条车道取的）。

## 步骤

1. **固定尖**：`TIP=$(git rev-parse origin/integration)`；全程只读。
2. **每条枝取自己的改动**：`MB=$(git merge-base $TIP $b)`；文件表 `git diff --name-only $MB..$b`。
3. **逐文件取新增行**：`git diff $MB..$b -- <f>` 里 `^+[^+]` 的行，trim 后丢掉空行与 `<10` 字符的行
   （短行会假命中）。
4. **问尖端同文件**：`git show $TIP:<f>` 是否包含该行；命中/总数 = 该文件的内容命中率。
   这里的"包含"是**逐行字面包含**——同一行被重排或换了换行位置就判不命中，这也是为什么第 6 步要用
   `90/10` 的阈值而不是要求全等。
5. **按种类分开计**：代码（`src/`、`test/`、`scripts/`、`CMakeLists` 等）与文档/报告/基准
   （`docs/`、`internal/`、`benchmarks/`）。两类常不同：代码 99% + 报告 45% 就是"代码已落地、报告未进"。
6. **判词**：两类都 `≥90%` ⇒ 内容已落地（可退役）；都 `≤10%` ⇒ 还有活；`10–90%` ⇒ 说不清，单列不猜。
7. **交叉校验** `git cherry $TIP $b` 的 `+` 数：`+` 是"该笔补丁在尖端无等价补丁"。
   `+>0` 但命中率高 ⇒ 同一改动以别的写法落地，按内容判；`+0` 而命中率低 ⇒ 说不清。
8. **不要用 `git apply --reverse` 判**：即使已知已合入的提交也 reverse 失败，因为之后别的车道改过同一文件、
   上下文漂移。

## 例

- `lane/rescue-1` ⇒ 旧 25 行 `0/25`、新 25 行 `25/25` ⇒ 已落地。
- `lane/progen-findings` ⇒ 代码 `87/88 = 99%`、报告 `162/357 = 45%` ⇒ 代码已落地、两份报告 `0` 命中。

## 退役前还要三样（`ahead=0` 只说明"枝尖是尖端祖先"，不说明"没人用"）

`ahead=0` 的枝**常常**正被某条车道停在上面干活；删 ref 会把那条车道打断。退役前对每条核：

- (a) `git worktree list --porcelain` 里没有 `branch refs/heads/<枝>`；
- (b) 没有在跑的车道绑定它（这一栏要问协调者要名单，"工作树是否占名"只是代理判据）；
- (c) 若有树占名，那棵树的 `git -C <tree> status --porcelain` 是干净的。

三样都过才删；删前 `fetch`、本地打 `archive/<日期>-<枝名>` 标签留一份。
> 佐证（2026-11-28 21:0x）：两轮盘点之间 `block-hash` 树从 `dirty=11 / ahead=7` 变成 `dirty=0 / ahead=8`（20:32 → 21:00 提交了）——"30 分钟有写"这个代理能区分"刚停"与"正在干"，而按进程名猜不能。
