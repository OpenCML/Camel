## 1. 派工提示必须含的四块

1. **基线**：`origin/develop` 的 sha（现取，不要抄旧值）+ 那一项计划的 `total/pass/fail/known`。
2. **一条可测判据**：能说「不」的那种。写清「改前应当红/绿」与「改后应当绿/红」。

## 3. 禁止项（每一份派工提示都要照抄这几行）

```
**★ 不许 `git stash`** —— 工作树之间共享一个 stash 栈，2026-11-15 出过事故。要暂存就 `git commit` 到一个临时分支。
**★ 生成物不许手解** —— 冲突一律用生成器重录：

   `messages/*.h`                   ⇒ `node scripts/diagnostics-catalog.mjs --write`
**★ 任何 `stdlib/*.cml`（含 `stdlib/rulesets/`）的改动 ⇒ 必须重生成 `docs/stdlib-reference.md`**，否则 `registry.reference_is_generated` 会红，而**没有任何计划看得见它**。

**★ 不许在本机构建**（会蓝屏）。构建只在 88zjwei 上，用 `internal/tools/camel-remote.ps1`。
**★ 手工 `ssh` 必须写 `ssh 88zjwei`，不许写 `ssh 88zjwei@10.126.62.88`。** 主机名带 `@` 地址时 rsync/ssh 不走 `~/.ssh/config` 里那个 `Host 88zjwei`（`IdentityFile` 只写在那里），于是卡在口令提示。2026-11-22 一条车道的 `-Clean` 因此没跑成。
**★ 新工作树缺 `internal/tools/camel-gate.local.json`（git-ignored）⇒ 首跑 exit 2。** 从主检出复制过去，不入库。
**★ `-AstOnly` 的写法**：`-AstOnly 'a,b'`（逗号）与 `-AstOnly @('a','b')` 等价 —— 逗号由工具拆开，`pwsh -File` 把 `'a','b'` 也送成同一个含逗号字符串，同样拆开。**重复写 `-AstOnly a -AstOnly b` 仍是 PowerShell 自己的绑定错误**（引擎在脚本体执行前就拒绝，工具够不着），改写成上面两种之一。一个 `.cml` 都选不出的 glob 会让工具当场 exit 2 并点名它，不会走到主机才回一句 `--only selected none`。
**★ 合并者：先提交后验证。** `git merge --no-commit` 之前不该有自己的脏改动；冲突一律用生成器解。
```

## 4. 合并时额外要核的

- [ ] **`git diff A..B` 是两点，会把落后分支「缺失的提交」算成它的改动。** 比一个分支少了什么用 `A...B`（三点）。
- [ ] **`git cherry origin/develop <branch>` 是等价判据**（patch-id）：输出 `-` 表示该补丁已在主干。**同一个补丁换过 sha 时，它不会重复计数，但也不要用 `merge-base --is-ancestor` 判它是祖先。**
- [ ] **合完的那个数要等于算式**。若不等，先停：可能有一笔的用例没进来，或有重复计数。
- [ ] **一条改动让目标变绿时，必须同时问它让谁变红。**
- [ ] **`known_fail` 不是「已验证通过」。** 合并说明里要写明它是「量到红、有主、目标算术写在旁边」。
  > 出处：2026-11-20，二阶导的三组数字（2.0 / 12.0 / `[[2,3],[3,4]]`）在 `jvp` 墙后面被钉成 `known_fail`。
- [ ] **红着的分支不因「落后」被硬合进 `develop`。** 在做中的活留在分支上继续做，只把 `develop` 合进它，不反过来。
- [ ] **合不进去或语义已被取代的不许硬合**，要一句「哪一笔被什么取代」。

## 5. 报告格式

≤12 行，必含：

1. 判据逐条（**达成/未达成**，未达成就说未达成，不要含糊）
2. 原行读数（计划的话给 `[SUMMARY]` 原行与 `killed`）
3. 改在哪（`文件:行`）
4. 提交 sha + **已推的分支名**
5. 未做/超范围的，逐条列出
6. 结尾「跑完报我、等点名」

## 6. 派工者自己的三条

- **不空等。** 车道大部分时间是**不需要主机**的：读代码、判判据、写 `.cml`、二分提交、写页 —— 都无主机。要跑时才报「等位」。
- **不向用户提问。** 有疑问写成一页一问（`internal/questions/`），写死默认建议，并按默认当轮开工。
- **合并迟到比实现迟到代价大。** 成熟的提交不许因为「想先确认」而压着；判定不确定时改成**事后判 + 可回退**（合完跑，只有合后才红就 `git revert --no-commit` 撤回来）。
  > 出处：2026-11-20，我要求合并位「先证实某条红是既有红再合」，主干因此停了 28 分钟。
- **主机上的并行度由槽决定，不由约定决定。** 构建两把锁（`/tmp/camel-host-build-{1,2}.lock`）、计划一把（`/tmp/camel-host-test.lock`）、每个检出一把树锁；拿到哪把就是哪一档，拿不到就等，等不到是 `state=noslot`（没读到，不是红也不是绿）。这条不再写成"不许并行"：11-22 那个清扫竞态已由树锁挡掉，**剩下的真实风险是并行负载污染读数**——所以每份运行登记带 `slot`、`overlapping`、`loadAtStart`/`loadAtEnd`，"两条同时跑、各自红"与"一条独占主机时红"因此分得开。**时间敏感的计划**（计划文件里 `time_sensitive = true`）把测试槽和两个构建槽一起拿下，跑完一起放，它的读数不受别人的构建干扰；哪些计划算时间敏感由计划文件自己说，不靠名单。

## 8. 闸门、分支卫生、合并位（只追加，2026-11-23 由协调者从私有工作流并入）

这一节以前只在协调者本机的工作说明里，决策者看不到。**从今以后流程只改这一份**。

### 8.1 分支卫生是硬闸，不是建议

- **未合进 `develop` 的车道分支 > 20 个，或任一未合分支落后 `origin/develop` > 100 commits ⇒ 立刻停派新分支**，转入清理与审计合并。
- 判据看 **commits 数，不是天数**。分支「老」不要紧，**落后多少**才要紧：落后 100+ 的分支合并时冲突面不可控，它自己的改动也会因为「基线太旧、跑不出真红」而无法验证。
- 触发后按序收拾，**不许把「清理」理解成删分支**：① 先把手上正在合的合完并推（已合未推比未合更贵）；② 逐条 `git merge origin/develop` 进落后分支、解冲突、小跑（它自己的计划 + `-Changed`）、合、推；③ **合不进去或语义已被后来的改动取代的，不许硬合** —— 写一句「哪一笔被什么取代」再决定丢弃还是重派。
- **`U>20` / `maxBehind>100` 不是「清理分支」，是停派新分支转审计合并。** 两者的区别：后者要先让 `U` 与 `maxBehind` 降下来，才允许开新线。

### 8.2 十道闸门，与合并的判据

`npm run gates` 跑 `scripts/gates.mjs` 的十道：doc-links、citations、questions-index、process-traces、plan-fields、grammar、headers、ast-hashes、operator-panic、generated。

- **退出码的含义分开看**：`exit 2` = **读不到这棵树**（环境问题，不是判词）；`exit 1` = **读到了，而且不对**。把两者混成一个「红」会让环境问题冒充代码问题。
- **合并的判据是本地闸门，不是 GitHub Actions。** 全平台 CI **不随每次合并触发**，只在每天收工、搬家窗口关窗前、发版前各跑一轮。理由：过去 24 小时手动触发 32 轮，5 绿 / 13 红 / 14 被取消 —— 一道大多时候是红的闸门，会训练人跳过它。
- **`declared > started` 是缺陷**（声明了没跑起来）；`declared < started` 正常。两个数必须分开报：闸门 `total`（跑起来的用例数）与 `git grep -c '^\[\[tests\]\]' -- 'test/plans/**/*.plan.toml'` 的块数/文件数。
- **留在 `develop` 上的红，必须是能当轮修的红。**

### 8.3 `develop` 只能有一个写入者

- **全权唯一有权 `git push origin develop` 的是合并位那条车道。** 两条车道同时推，后推的必被拒（non-fast-forward），然后 rebase 再推 —— 每合一条撞一次，而它撞的时刻正是它该前进的时刻。
- **这条现在有钩子，不再靠记性。** `scripts/hooks/pre-push`（由 `.husky/pre-push` 调用，先于任何读 stdin 的东西）在推 `refs/heads/develop` 时，比对 `internal/tools/camel-gate.local.json` 的 `mergeWorktree`：只有那个工作树放行，其余拒绝并写明是哪个树、该改哪个键。**读不到设置不是放行**——键缺失或文件不可读都拒绝。一个工作树要跑钩子，得有 `.husky/_`（`husky install` 生成、git-ignored）；车道工作树向来没有它，于是两个钩子都不跑——要这条锁生效，先装它。
- **按延迟分格，不按数量分**：6 格给「短而确定」的实现活，2 格给「长而串行」的合并与测量。**合并位不许自己跑长测试**；真要跑就 `run_in_background`，继续干别的。
- **合并不挡派工。** 一条车道报来，立刻派下一条实现，再把它的分支交给合并 —— 两件事并行，不是先后。
- **合并位不凭「工作树停在合并中间」或「`develop` 25 分钟没动」判「卡住」。** 前者要同时查 `git log` 里有没有那个 merge commit；后者要先问它在跑什么。2026-11-18 凭这两个信号各误判一次。

### 8.4 派工的可执行细节

- **派工提示的正文只有三样**（模板见本文 §6）：① 基线 sha；② 这条车道要判的那**一件**事；③ 红线里要排除的具体文件 + 哪条车道正在改哪一段。
- **`subagent` 必须传 `cwd: "D:\Projects\Camel-wt\<lane>"`**，不传则子代理的工作目录是主检出 —— 于是它改的是别人的树。
- **每次改文件前 `git rev-parse --show-toplevel`**，应是自己的 `Camel-wt/<lane>`。路径一律绝对，`edit`/`write` 与 .NET 调用都一样：后果不只是「写错地方」，**读也会读错**，于是出现「改了却没变化」。
- **PowerShell 里 `git commit -m` 带 `()` 或 `"` 会坏**，走 `[System.IO.File]::WriteAllText` 写文件再 `-F`。**临时文件名不要用固定路径** —— 别人留下的同名文件会让提交说明变成上一件事的话。
- **`git fetch` 的退出码要报出来。** 不报的话，一串「没变化」的读数是建在没人刷新的引用上的：**读不到 ≠ 没变化。**
### 8.5 一个读数属于它的树，也属于它的构建（2026-11-23 起）

树能从 `git rev-parse` 问出来，构建不能 —— 它没有名字。于是「同一个构建」这件事从来没进过判据，而它是几类诡异读数最常见的成因。

- **「重录后绿、再跑就红」先怀疑两次跑用的不是同一个构建。** 重录时的二进制与检查时的二进制不同（重录时还是改动前的解析器），读数就会在两次之间翻转，而两次各自的输出都自洽。量三样再改：**两次跑的构建哈希**；**重录后与再跑后各份记录的 `git diff`（分开列，不要合成一份）**；**同一构建上连跑两次普通检查是否稳定**。
- **不许用重录盖住方向不明的红。** 让两边都绿只需要一条命令，而那样一来「两个用例要求相反的东西」就再也不会出现在任何读数里。
- **「几个用例读同一份文件」这种前提要验。** 名字像（`*_snapshot`）不等于读的是同一份：`inspect.tok/cst/ast_snapshot` 比的是各自 `smoke/golden/` 下的文件，`frontend.ast_snapshot` 才读 `ast_hashes.txt`；四个用例共同的是那个测试程序，不是记录文件。**把两条路径描述成一条，会让一个不存在的问题看起来像存在。**
- **栈要分层写清谁在谁的上面。** 只在某棵树上出现的红，它的修法也只能在那棵树上验；从基线新开一条支去改，会在干净的树上什么也复现不出来，然后把「一条都找不到」当成「没有这个缺口」。
- **`git merge --no-ff` 自己会提交**，所以之后那句 `git commit -F` 是**空操作**，而 `develop` 不重写 —— 那句话就永久丢了。**合并之后要写说明，用 `git commit --amend -F <file>`。 **但冲突合并（`merge` 报 `Automatic merge failed`）之后 `--amend` 会报 `You are in the middle of a merge`，那时要用 `git commit -F <file>`** —— 所以判据是「这次 merge 自己提交了吗」，不是「用了 `--no-ff` 没有」。** 这一条已经犯过两次，两次都是「合并完立刻去合下一笔」的时候。
