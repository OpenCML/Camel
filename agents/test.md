# Test Rules

Read [`../docs/design-principles.cn.md`](../docs/design-principles.cn.md) first. Do not change semantics to make a test pass.

## Running tests

Do not build Camel on this workstation. Use the remote Linux build host through the repository's only gate entry:

```powershell
pwsh -NoProfile -File internal/tools/camel-remote.ps1 -Path <worktree> -Plan <plan-file-or-directory> -Jobs 8
```

The wrapper transports the current branch and uncommitted changes, builds, runs the selected plans and returns their exit code. Do not invoke another copy of the wrapper or a hand-written build command.

During development, run the plans touched by the change plus `smoke`. Before finishing, run `smoke` and `feat/**` on the host. A plan file named explicitly runs in full, regardless of the selected tier; a directory selects its `fast` layer by default.

Useful local, non-build checks:

```powershell
node scripts/check-doc-links.mjs --all
node scripts/check-std-includes.mjs
node scripts/conflict-markers.mjs
node scripts/diagnostics-catalog.mjs --check
```

## Test layers

- `fast`: `smoke` and `feat/**`, the ordinary acceptance layer.
- `slow`: explicit slow plans and slow entries, used when the change warrants them or before release.
- `milestone`: full regression, GC poison/stress, random programs, PyTorch comparisons and performance work. Run it on a quiet host at 09:00 Asia/Shanghai each day and before every release.
- `debug`: assertions that require a Debug build. Select it only with `--tier debug`; it is excluded from Release layers.
- `all`: every plan except the deliberate `debug` tier, not a synonym for fast.

Do not run full stress or performance suites to "be safe". Use the relevant named plan. See `docs/test-plans.md` for the authoritative selection rules.

## Evidence and provenance

- Record the test target, tier, total, pass, fail, skip and known-failure counts, and the tested commit. `skip` is not failure; an empty selection is not a green run.
- **`total` is not coverage: report `total - skip`.** A skipped case and a passing case are the same shape in the totals. On 2026-11-15 the GPU layer printed `total=146 pass=19 fail=3 skip=124`: 124 were skipped because the probe `test/tools/have-cuda-device.mjs` found no visible device, so that layer's real coverage on that host was **22 cases**, and a ratchet over the other 124 would have measured nothing. State the coverage next to the total, and say plainly that a fix verified on 22 cases does not speak for the rest.
- **Two numbers printed side by side must carry their units, or someone will add them.** `checked 19, declined 3` reads as "19 examined plus 3 skipped, of 22 sites"; the two numbers in fact counted different things -- call sites and readings -- and a site can produce several readings. The same confusion had already happened once with `185` (a count of red *cases*) against `3` (a count of declined *readings*). If the two numbers answer different questions, do not force them into one unit; make the line say so, and say that they must not be summed.
- Every reading belongs to a tree and a build. Do not quote a SHA for a dirty tree; the runner's `[provenance]` line is the source of this information.
- **A run may not leave a file in the checkout it tested.** The runner reads `git status --porcelain --untracked-files=normal` before its first test and after its last, prints the result on the `[TREE]` line after `[SUMMARY]`, and fails when a path appeared during the run -- naming the path and the tests that were running when it appeared. The reason is the first bullet: a run that leaves a file behind makes the next `[provenance]` read `(dirty: N files)` and stop naming a commit, the wrapper carries that file to the host on every run, and `--changed` counts it as a changed file. A test's own program runs from the checkout root because `${test_tmp}` is repository-relative, so a program that starts other programs must give them a directory of their own: `scripts/check-plan-refs.mjs` runs each of the 3,844 cases it drives in its own directory under `CAMEL_TEST_TMPDIR`, and not doing that is what left fourteen files in the repository root.
- Before treating a failure as new, check whether it exists on the base and whether another branch already fixed it. Do not diagnose from a truncated tail alone; read the full output named by the runner.
- **Quote only flags the tool actually has.** An unknown flag is not an error in most of these scripts: it is ignored and the default path runs, so the command succeeds, prints a plausible reading, and the premise you attached to it is false. On 2026-11-15 two instructions carried flags that do not exist -- `test.js --changed-base <sha>` (the override is `$env:CAMEL_TEST_BASE`) and `check-doc-links.mjs --check` (the modes are `--citations`, `--default-roots`, `--questions-index`, `--technical-index`) -- and both produced readings that looked like answers. `--changed-base 0e94f3b` was worse than ignored: the runner read `0e94f3b` as a **target path**, so the base silently stayed `origin/develop` while the command still ran. Before writing a flag into a dispatch, run the tool's usage or read its argument parser; **a reading is only as good as the flag it was asked for.** The same holds for field names written into a plan. `run-tests.mjs` accepts `exit_code`, `stdout_normalized`, `stderr_normalized`, `output_normalized` and `diagnostics`; `stdout` is the *result's* field, not the comparison's, so a differential entry using it fails before the program runs. On 2026-11-16 a lane reported its four backends in agreement on a plan whose three non-default entries all read `runner error: unsupported differential field: stdout` -- the lane had never built or run it, and the error looked like a semantic red rather than a misspelled key. **A scope is part of the vocabulary too**: `test/plans/feat/parse/golden/ast_hashes.txt` records every `.cml` in the repository (88 parse cases, 227 probes, 4054 others), not only `test/cases/`, so moving a probe program out of `test/cases/` does not move it out of the record -- a lane made that error the same day by putting its probes under `test/probe/` in the belief that the file only covers expectations, and `frontend.ast_snapshot` was the thing that said otherwise.
- **A stale binary gives a credible false red.** After merging, rebuild before measuring: on 2026-11-15 a lane measured on a local binary older than the merge and saw five reds (`ref.one_box_two_names.*`) that did not exist on the host build, and another lane saw two reds from a `SyntaxDiag` change that predated its checkout. The reading is the same shape as a real regression, so nothing in the output tells you it is stale -- only the build stamp and the order of operations do.
- **A check that normalizes a path must cross the drive-letter colon.** `check-doc-snippets.mjs` erased the directory part of a diagnostic path with `(?:[^\s:()]*[\\/])?`, whose character class has no `:`, so on Windows it could not see past `D:` and compared `D:<file>:4:15` against a page that says `<file>:4:15`. The same document therefore passed on Linux and failed on Windows, and the page was correct all along. Where a check feeds a tool an absolute path and then compares text, make the normalization platform-independent and say so in the comment.
- **A rule that changes what the compiler accepts must be measured on every family that accepts it, not on the plan directory it lives in.** Three times on 2026-11-15 a lane ran only its own plans, reported green, and a control tree showed the new rule had refused programs that were working: a fold that made reads observe later writes (`new_values`); an effect check that refused every `tiles::compile` call site; and a closure rule that refused the standard library's own `stdlib/stream.cml#tee` together with `byref` and `stream.tee_*` -- 208 reds against 10 on the control tree, invisible from `feat/compile` alone. The reading that catches this is `--changed` over the whole tree **plus the families the rule can reach**; do not copy the lane's directory list into the gate, because that list is exactly the thing that was too small. Measure the same batch on the base tree so that a family already red is not counted as new.
- **A reading without a pinned base is not a weaker reading; it is a different measurement that prints the same shape.** On 2026-11-16 a batch measured with `-ChangedBase 13e833fb0` read `total 4797 / pass 4762 / fail 6`; the same batch, run without the pin after `develop` had moved 15 commits, read `total 7447 / pass 29`. Both lines have the shape of an answer -- a total, a pass and a fail count -- and nothing in either says whether a base was named, so a reader compares them as if they were one trend. Whatever a diff-based reading is compared to must be decided before the run, be printed on the line that reports it, and be the same base on both sides of the comparison. When the base moves mid-flight, the reading that was taken against the old one does not become wrong; it becomes uncomparable, which is a state the numbers cannot show.
- **`skip` describes the host, not the layer.** On 2026-11-15 the GPU layer reported `skip=124, pass=22` in the afternoon and `skip=0, pass=131, fail=15` that evening with no change to the layer: the probe `test/tools/have-cuda-device.mjs` found a device the second time. Coverage is meaningful only with the host and the time attached; a `total - skip` quoted without them describes a machine, and comparing two of them across runs compares the machines.
- **The build host's 1-minute load is 22–31 all day, and its source is not this project.** Four inference servers (`vllm serve --model Qwen/Qwen3-8B`, up for days) share it, so the runner's `[load] WARNING: 1m load 22.13 > 8 -- readings taken now are not comparable to quiet-host readings` is that host's normal condition and not an incident. `total`, `pass` and `fail` are structural -- what ran and what it decided -- and they hold. The per-case milliseconds are environmental, and there is no quiet reading on this host to compare them against, so do not compare them across nights at all; compare them only within one run, where both sides met the same load.
- **A check over an empty set passes.** When a checker iterates a collection it parsed out of a data file, pin a lower bound on the collection's size, or a parse that silently yields nothing reads exactly like a clean result. On 2026-11-15 a merge resolved a conflict by rewriting `diagnostics/registry.tsv` with CRLF line endings; the consumer splits on `\n` and kept a `\r`, so the `field[6] === 'edit'` set came out **empty** and `fixes_apply` -- a property quantified over that set -- reported success. Nothing in the output distinguished "every entry is fine" from "there were no entries". The separator a script assumes is part of the file's contract, and CRLF is the failure mode that survives every editor and every diff.
- **A failed command produces an empty set, and an empty set passes.** On 2026-11-15 a branch-hygiene count derived `O` from `git ls-remote`; one attempt died with `Connection closed by UNKNOWN port 65535`, printed nothing, and the count computed **0** -- which satisfies the gate. The retry that succeeded reported 3. `asked and there are none` and `could not ask` are different states that render identically in an empty list, so read the exit code before trusting an empty result, and say in the output which of the two it was.
- **An authorized exception is recorded as an exception, never as an ordinary instance.** When a documented precondition does not hold and the step proceeds on an explicit order -- a worktree removed while its branch is still a commit ahead -- the record must name the rule that was not met and who waived it. Otherwise the next reader sees a successful step and infers that the rule permits it, and the rule erodes one legitimate-looking exception at a time.
- **An invisible door and a missing door look the same from a failure.** Before concluding that a capability does not exist, read the tool's own parameter table, not the reports of the people who could not find it. On 2026-11-15 three lanes failed to record AST hashes and each reported it as something a lane "cannot do"; a fourth lane and the coordinator agreed and proposed building an escape hatch. `camel-remote.ps1` had carried `-UpdateAstHashes` all along, and its own description read "which a lane cannot do, and a lane that skipped it left a red window on the base branch" -- the door existed, its sign was invisible. The correction was to make the existing door readable (print the binary's build time; accept `-AstOnly` so an update cannot rewrite every stale line) rather than to open a parallel second door, because two doors to the same room guarantee that one is eventually used for the wrong job.
- **A condition that never fires and a condition that fires with no effect look identical from outside.** Before changing how a pass decides something, put a counter on the branch's exits and read it, rather than reasoning about whether the branch is reached. On 2026-11-15 one rework wrote four separate guards into the same fold and three of them were wrong in exactly this way: a `joinsNoValue` guard that was entered and had no effect, a narrow condition that could never match a straight-line program, a "straight-line only" definition that was never enforced inside the fold, and a bail-out that fell back to the same value as the case it was meant to separate. Each was found by printing counts, none by re-reading the code. The related trap is a probe whose condition cannot hold at all: a probe that required "the cell is this node's first input" was pointed at a set of *read* nodes, whose first input is their version, so it printed nothing on every run -- which read exactly like "this path is never taken".
- **A passing case's stdout is not in the runner's output.** The runner prints a case's stdout head when it fails, so a probe that prints and does not change the result is invisible: the run is green and the reading does not exist. Either put the probe's number into an assertion the plan already checks, or let an assertion fail once to surface the output and then remove the probe -- and say that you did, because a temporary red in the history is otherwise indistinguishable from a defect you left behind.
- `null` is absence of an exit code, not a timeout. A signal, timeout and failure to start are different outcomes.
- **Pin the criterion on stdout, not on the exit code.** In Camel a `func main(): int` returns the process exit code, so `return println(x)` makes the exit code *be* the value under test: on 2026-11-16 a lane wrote `expect_exit = 0` for a program printing `1`, and the case went red with `exit 1` while stdout was correct. The two things a run produces -- what the program printed and whether it finished -- collapse into one number exactly where the program is written in that shape, and the assertion then measures `println`'s return value instead of the run. Assert the value on stdout and make `main` `return 0`.
- **A shared host checkout named after a lane has its identity in the branch.** `camel-remote.ps1` transmits the working tree and checks out the branch it names, so switching branches inside such a checkout leaves the host with a branch it was pushed plus whatever the previous run left. On 2026-11-16 a lane created a temporary branch in its own worktree to measure an older commit; the host's `~/camel-work/<lane>` afterwards had no `.git` and no `out/latest/bin/camel`, and the run reported `total 8886, pass 5850, fail 3024` with `[TREE] not judged: git status failed: fatal: not a git repository`. **3024 is the reading of a host with no binary, and it has the shape of a reading.** To measure an older tree, give it its own worktree and its own lane name; do not change what an existing lane's directory points at.
- **A run that failed to measure produces "not investigated", never "the empty set".** The failed run above printed a `[SUMMARY]` line and a `fail` count, and the question it was meant to answer -- which reds already exist on the base -- was left unanswered. A failed measurement is exactly the shape of the answer that would have been convenient: zero new reds. Say "未查" and leave the inference labelled as an inference.
- **`killed by a signal: N` counts reds by how they ended, not processes that died.** `run-tests.mjs` increments it only for a case whose status is `fail` and whose result carries a signal -- its sibling `timedOut` counts the other way a failure can end without an exit code -- so a case that ends by a designed `abort()` and *passes* never appears in this number at all, though `test/plans/debug/view_escape` exists precisely to abort on purpose. Read it as a description of failures, and the same plan showed both shapes on 2026-11-16: `pass: 1, fail: 2, killed by a signal: 2` while it was red for a stale `expect_stderr_contains`, and `pass: 3, fail: 0` with no `killed` once the expectation was repaired -- the aborts happened in both runs. Distinguish it from a truncated run by the names, not the count: a truncation reports far fewer results than it declared started, and no `[SUMMARY]` line near it is trustworthy.
- **A mechanism explained wrongly is worse than a mechanism left unexplained**, because it makes the number look accounted for and teaches the wrong reading. The rule above was first written as "the debug tier's killed cases are the designed aborts passing" -- half right and half backwards: those aborts *pass*, so they were never counted at all. The reading that settled it was the source, `run-tests.mjs`'s `if (outcome.status === 'fail' && outcome.result)` beside `summary.crashed++`, and the check is cheap: run the same plan in both states and see the number move. Where a rule states a mechanism, that mechanism is part of the rule and is checked like any other claim.
- Keep logs and probe artifacts outside the worktree. Never kill a shared-host process by a broad program-name pattern.
- Build with Release for routine verification. Use Debug only for debug-only behavior; `GUARD` must remain active in Release, while `ASSERT` may be compiled out.

## Writing and changing tests

- Manually run a new feature or case first and inspect stdout/stderr. Only then encode the observed contract in a plan.
- Test behavior and invariants, not counters that move with unrelated edits. Use exact output where formatting matters, and properties where implementation may vary.
- Cover every affected backend, or require a located refusal on unsupported ones. A rule shared by several backends should have one shared case, not separate implementations.
- Put generated files and fixtures under `test/`; keep temporary probes outside it. Do not create test or report scaffolding when the project has no need for it.
- **Any edit to a `.cml` file under `test/cases/` changes its recorded AST hash -- comments and `desc` strings included.** The snapshot records a hash of the file's bytes, so a citation fix that touches only a comment breaks `frontend.ast_snapshot` exactly like a syntax change. On 2026-11-15 a documentation commit (`4da099048`) rewrote `questions/` to `reviews/` inside two `desc` strings of `test/cases/compile/ref/ref_boxes_made_per_call_*.cml` and left the snapshot stale; the resulting red was then attributed to three unrelated lanes, because attribution had reasoned "that commit could not have touched hashes". Do not narrow the scope of this rule to syntax or `test/cases/parse`: the case that broke it was neither. Re-record with `check.py snapshot --update --only '<pattern>'` per file, never a bulk `--update`. Changes to diagnostics require `diagnostics/registry.tsv` followed by `node scripts/diagnostics-catalog.mjs --write`. Before a merge, run `-Check ast-hashes` to read those files by name instead of a red plan.
- Do not weaken an assertion, delete a case or mark a failure merely to make the suite green. Explain every changed expectation in the change report.

## `known_fail`

A known failure is a precisely described open defect, not a budget or an exemption:

- Use `known_fail = ["backend"]` with a `backends` list, and `known_fail = true` without one.
- Include `known_fail_owner`, a concrete `known_fail_reason`, and `known_fail_msg` containing the expected diagnostic fragment.
- The runner rejects a marked case that starts passing, a missing expected message, or a failure whose reason differs from the pinned fragment. Remove a stale mark in the same commit that fixes the case.
- Real compiler internal errors on runnable programs are not marked known. They are ordinary failures requiring rework.

## Selection and generated checks

- `--changed` selects plans from the changed paths and their declared cases. An unreadable base or selection is an error, not a reason to run the whole fast layer. An empty selection means no tests ran; name the intended plans explicitly.
- `CAMEL_TEST_BASE` overrides the comparison base when necessary.
- A new plan needs a selection rule or a deliberate exclusion, so it cannot silently disappear from `--changed` and layer accounting.
- Regenerate rather than hand-edit generated indexes, diagnostics, standard-library references and snapshots. Checks that examine zero items fail rather than pass.
- **An instrument fix is accepted by two counts, not one: how many reds turned green, and how many greens turned red.** On 2026-11-15 the round-trip comparison reported `unfaithful=3` and named the class `PORT` with `0 on the right`; nothing had lost a port. `class_difference` broke ties between equally scored classes by colour hash, so it accused a class that carried no difference, and three lanes spent hours chasing it and each wrote a wrong attribution. The repair moved classes whose own label counts are equal in both documents to the end, printed how many other classes had moved, and said outright when the difference was in edges rather than in vertices. Acceptance was `equivalent 700 → 710` with **zero** reversals. Turning reds green without a single reversal is the signature of a criterion that was too narrow; turning reds green while anything turns red is the signature of one that was tightened in one place and loosened in another, with the two hiding each other.
- **A diff report that names one class must say how many others moved.** Otherwise the reader cannot tell "this is the difference" from "this is the first of several differences the report happened to print". The reader in that situation is not a person with time to check; it is the next agent, who will treat the name as the answer.
- **A coordinator's documentation commit is a vehicle for the merge lane's unpushed merges.** `git push` publishes `origin/develop..develop` in full, so a commit whose own diff is `1 file changed, 1 insertion(+)` can carry five unmeasured merge commits to the remote; the number printed for the commit describes the commit, not the push. On 2026-11-15 this is exactly how two lanes' merges reached `develop` without a combined gate reading, minutes after the coordinator had told the merge lane not to push an unmeasured combination. Before committing on `develop`, print `git rev-list --count origin/develop..develop` and the composition of that range; if it holds work that is not yours, either wait for it to be pushed or do not push from here. And while merges are sitting unpushed, the merge lane must assume someone else's next push will carry them, so the gate runs immediately after the merge rather than after the batch.
- **A guard printed by the same command that acts can only testify, never prevent.** The paragraph above was written and then violated within the hour by the person who wrote it: the `ahead=11` reading and the `commit` and the `push` sat in one `pwsh` invocation, so the reading arrived after the decision was already encoded, and eleven unmeasured commits went to the remote for the second time that evening. The guard must be a separate invocation that ends the turn, with an explicit "this may be pushed" between it and the push. Anything else is a record of the violation, formatted like a check.
- **A case turning red asks one question first: is it testing a rule that was retired? Declining to change an expectation can invite the old mechanism back.** On 2026-11-16 the loop lane found two cases red under the new `var` semantics and repaired *the mechanism* so the old readings would hold: it made the loop state announce that it wrote (which brought `IgnoredSideEffect` back under the name "missing `sync`") and it re-added the `COPY -> LOOP` order edge (which lives in the retired rule "writes to the same `var` are ordered"). Both were written up — by the coordinator, in the merge body — as the two deep lessons of the night. The author reverted both: under 「an assignment to a `var` is not an effect」 there is no `sync` to miss and no order edge between writes, so the *expectations* were what had to change. The rule to apply, in the author's words: **when an old case goes red under the new semantics, first ask whether it tests a retired rule; if so change the expectation and name the principle clause in the commit; if not, change the implementation. Never rebuild the old mechanism to keep an old reading.** The discipline that "you may not silence a red by editing its expectation" is correct and was enforced all night; it is incomplete without this question, and its incompleteness shows up as a *new* mechanism that nobody asked for. A lane that finds itself adding machinery in order to keep a number green is already in this failure; so is a coordinator who calls that machinery a lesson.
